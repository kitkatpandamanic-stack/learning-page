# SQL: PandaDev vs the outside world

Compared 2026-10-16 at repo HEAD `e5e43cb` by the learning-architect agent. Read-only run: nothing in `content/` or `src/` was changed. I read all 60 EN lessons in `content/courses/sql/`, `course.yml`, the frontmatter and task text of all 40 problems in `content/practice/sql/`, and spot-checked RU twins in all 20 modules and capstones. Research basis: [research/summary.md](../research/summary.md) ("Consensus curriculum → SQL", "Current versions → SQL (PostgreSQL)", "Top confusions → SQL", design rules) and the SQL sections of the five research files. Citations: `[summary]`, `[official-docs S24]` and so on.

**Runner:** learners run SQL in PGlite. The installed `node_modules/@electric-sql/pglite` is 0.5.8, and its `pglite.wasm` reports **PostgreSQL 18.3**. `package-lock.json` pins 0.5.9 (not inspected, presumably also 18.x). Every PG 18 feature the course uses (virtual generated columns, `RETURNING old/new`, skip scan, `NOT NULL … NOT VALID`, `uuidv7()`) can be run in the browser. Extensions (`btree_gist`, `tablefunc`, `ltree`, `pg_trgm`) and a second session can't, and the lessons say so where it matters.

**Verdict**

1. This is the deepest free-style SQL course I know of. It covers all 34 consensus topics in some form (none missing), and its L2–L3 (EXPLAIN, MVCC, RLS, zero-downtime migrations, partitioning, replication) goes further than any course in the research [courses].
2. It is current with PostgreSQL 18. Identity columns, `text`, `timestamptz`, `numeric` for money, half-open date ranges and `NOT EXISTS` are all taught head-on. The leftovers are 8 lines of new-table DDL that use `timestamp` without a time zone, and a seed database built on `serial` + `timestamp`.
3. The order is the main issue. `CASE` (●●●, L0–1) first appears at L2, and so does top-N per group (L1). DML is at L1 rather than L0. Parameters and injection come at L3, a level after the consensus.
4. Lesson craft is strong: 412 runnable examples, 113 quizzes that use misconceptions, and 60/60 exercises checked against the database (45 of them change the data and rerun the learner's query). The weak spots are single, near-answer hints (48 of 60 hints have a long code span), only 2 predict-before-run prompts, only 2 of 16 modules with a mini-project, and nothing that lets engineers skip ahead.
5. Two learner misconceptions from the one SQL misconception study get no attention at all: `==`/`IS` for equality (28% of answers) and "DISTINCT is always needed" (24%) [learning-science S47, single study].

## Out of date or incorrect

Checked against "Current versions and changes" in [summary.md](../research/summary.md) and [official-docs S20–S25]. Only cases verified in the files are listed.

**1. New tables created with `timestamp` (no time zone).** "Don't Do This" says `timestamptz` [official-docs S24], and the course's own L1 lesson says so too (`designing-tables/01-creating-tables.mdx:127–173`). These new-table definitions contradict it:

- `advanced-queries/03-jsonb-and-arrays.mdx:225` and `:296`: `happened_at timestamp NOT NULL`
- `scaling/02-backups-and-replication.mdx:394` (exercise starter) and `:446` (solution): `finished_at timestamp NOT NULL`
- `scaling/03-choosing-a-database.mdx:48`, `:101`, `:160`: `sold_at timestamp NOT NULL`
- `multi-tenant-saas/03-saas-launch-review.mdx:208`: `created_at timestamp NOT NULL` in `activity_log`, although Part 1 says every table has `created_at timestamptz NOT NULL DEFAULT now()`

Change: use `timestamptz` and regenerate the outputs (they gain `+00`), EN + RU. Related: `data-modeling/02-advanced-constraints.mdx:220` uses `tsrange` while the callout at `:286` says "use `tstzrange` for real-world times". Use `tstzrange` in the example. Tables generated with `CREATE TABLE AS … timestamp '2025-01-01' + …` in the EXPLAIN lessons are lower priority, since they're throwaway data.

**2. The sample database uses `serial` and `timestamp`.** `src/lib/runner/sql-seed.ts` lines 12, 43, 68, 101, 114, 146 (`id serial PRIMARY KEY`, 6 tables) and line 70 (`ordered_at timestamp`). This is app code (owner decision), and the lessons are honest about it (`designing-tables/01-creating-tables.mdx:173` and `:252`). The cost is that learners see the legacy forms in every `\d`-style look, and two lessons build on them: `changing-data/03` (`currval('orders_id_seq')`) and the "sequence gotcha" in `security/01-roles-and-privileges`. Switching the seed would change many expected outputs, which is effort L. I recommend leaving it, unless the seed changes for another reason.

**3. EXPLAIN and `BUFFERS`.** `indexes-and-performance/01-explain-query-plans.mdx:362` says "`EXPLAIN (ANALYZE, BUFFERS)` shows…", and the workflow in `indexes-and-performance/03-query-tuning.mdx:342` tells you to write `BUFFERS`. Since PG 18, `EXPLAIN ANALYZE` includes buffers automatically [official-docs S22]. It isn't wrong (the option still works, and the lessons' own examples write `BUFFERS OFF`), but add "(since PostgreSQL 18 this is on by default with ANALYZE)" to both lines.

**Checked and current:** identity columns, `text` over `varchar(n)`, `numeric` for money, the `BETWEEN`-on-timestamps trap, `NOT IN` → `NOT EXISTS`, virtual generated columns as the PG 18 default (`data-modeling/02`), skip scan softening the leftmost-prefix rule (`indexes-and-performance/02`), `RETURNING old/new` (`changing-data/02`, `transactions-and-concurrency/03`), `NOT NULL … NOT VALID` (`data-modeling/03`), `uuidv7()` (`multi-tenant-saas/01`), `UNIQUE NULLS NOT DISTINCT`, the PG 15 `public` schema change, `MAINTAIN` (17) and `transaction_timeout` (17). No table inheritance, no `money` type, no rules. `VACUUM FULL` → `pg_repack` (`transactions-and-concurrency/03`) is right today. Revisit it when PG 19 ships `REPACK CONCURRENTLY` (RC only [official-docs S23]).

**Length and difficulty.** The L1 → L2 step is the steepest: about +30% prose and +5 minutes. `indexes-and-performance/01–02` (2,189 and 2,246 prose words) and `scaling/02` (2,685) are the densest; 2,685 words of prose plus code in 24 minutes is tight. Within levels the difficulty climbs smoothly. Each capstone is clearly the hardest part of its level.

**Exercise tests.** Strong. All 60 exercises check against the database with `rerun(...)` or `query(...)`. In 45 of them a check changes the data and runs the learner's query again, so hard-coded answers fail; the other 15 (mostly DDL and data-change tasks) query the resulting tables. Edge cases are tested on purpose: 23:59 on 31 March, ties, NULL cities, a tenant with no setting. I found no exercise with weak tests. Two small notes: test names show learners the expected values (by design), and the L2 `EXPLAIN` exercises check plan text with regexes, which could break on a PGlite upgrade.

**Design rules** [summary design-rules table]:

- **Worked examples (rule 4): strong.** About 7 runnable examples per lesson, each explained underneath. Capstones label their steps ("Step 1: a total for every order"). There is no deliberate fading across a module.
- **Predict before run (rule 5): weak.** Explicit "predict before you run" prompts: 2 (`aggregation/03` TryIt, `subqueries/03` TryIt). By a keyword count, 37 of 113 quizzes ask what a query returns, but they come after the outputs are shown. Note: quiz ids are positional, so a predict quiz inserted before existing quizzes shifts old progress [lessons-learned "Content"]. Prose prompts or appended quizzes avoid that.
- **Notional machines / intermediate tables (rule 7): partial.** There are good ones: GROUP BY "piles" (`aggregation/02`), FK arrows (`joins/01`), the recursion step table (`advanced-queries/02`), session timelines and live `ctid`/`xmin` tables (L3). A join's intermediate "every pair" table is described in words but never drawn. The logical order is a list, not tables flowing step to step.
- **Misconception distractors (rule 11): strong in content, with a cue problem.** Distractors use `= NULL`, AND-before-OR, HAVING aliases, LEFT JOIN + WHERE, `count(*)` vs `count(col)`, `rank` vs `dense_rank` and `last_value` frames. But the correct option is index 1 in 76 of 113 quizzes (67%; index 0: 2, index 2: 31, index 3: 4), and the longest option in 70 (62%, ties counted). This matches the site-wide finding in [learning-experience.md](learning-experience.md).
- **Graduated hints (rule 10): split.** Practice: 40/40 problems have 3 steps ending in a skeleton. Lessons: 60/60 have one hint, and 48 of them contain a code span of 35+ characters, usually most of the answer (e.g. `sorting-and-limiting/03-null-values.mdx:352`, `aggregation/03-having.mdx:218`). `<HintSteps>` exists (`src/components/mdx/hint-steps.tsx`), but SQL lessons don't use more than one step.
- **Placement and skipping (rule 13): missing.** No "Already know this?" in any SQL lesson (grep 0).
- **Projects (rule 16): thin.** Mini-projects in 2 of 16 modules (`aggregation/03`, `designing-tables/03`), plus a 3-part capstone per level.

## Strengths

- **The real L2–L3.** Every course in the research stops before EXPLAIN in depth, replication or MVCC, and only CS50 SQL reaches indexes, transactions and injection [courses "Level 3"]. PandaDev has 12 L3 lessons on concurrency, modelling, security and operations, plus a 3-part senior capstone.
- **Real PostgreSQL 18 in the browser, kept current.** Learners run PG 18 features that most tutorials don't yet mention.
- **The top confusions are taught as traps, with the wrong query run first:** `NOT IN` + NULL, ON vs WHERE, fan-out, `count(*)` on outer joins, `BETWEEN` on timestamps, the alias in WHERE.
- **Database-checked tests on every exercise, and anti-hard-coding reruns in 45 of 60.** That's stricter than SQLBolt's tasks, and pgexercises' checking is unconfirmed [courses S17, S19].
- **One sample database for the whole course**, like pgexercises [courses S19], so later lessons can tell "business stories" (cancelled orders, partial months, whales).
- **EN + RU parity.** The only free RU SQL course in the research (Hexlet) stops before JOINs [courses S23].
- **Production habits from L1:** SELECT before UPDATE, `RETURNING`, short transactions, lock timeouts, tested restores, and "write the metric definition down".
