# How people learn programming best: learning science and computing-education research

Researched 2026-10-15 by the learning-architect agent (research-only run, no comparison with PandaDev content yet).

This file is about how people learn, not what to teach. Overview: the strongest evidence (meta-analyses) supports retrieval practice, spacing, informative feedback, and worked examples for novices that fade into independent problem solving. Programming-specific research adds reading and tracing before writing, Parsons problems as a fast practice format, subgoal labels, and explicit mental models of how code runs (notional machines). Gamification has small positive average effects, but badly designed rewards, leaderboards, and streak punishment can backfire. Most help for beginners gets in the way of experts (expertise reversal), so a site that serves both needs placement checks and skippable scaffolding. Language-specific misconception research is solid for variables, references, loops, recursion and SQL. For JS async and TypeScript it is thin, and most of what exists is practitioner opinion.

**Evidence tags used below:** **[meta]** meta-analysis or systematic review of many studies · **[several]** several independent studies or a narrative review · **[single]** one study (sample noted where known) · **[opinion]** expert or practitioner guidance, company data, or my inference from the research. "Abstract only" means I read the abstract or a summary, not the full text.

## Lesson design

- **Worked examples first for novices, then fade them.** Studying a fully worked example beats solving the same problem unaided early in learning, because it frees working memory for the pattern itself. Removing worked steps one at a time ("fading") eases the move to independent solving. Adding prompts that ask "which rule did this step use?" also helped far transfer. **[several]** [S8][S10]
- **Label the sub-steps of a procedure (subgoal labels).** Short functional labels on worked examples ("set up the loop variable", "update the total") let novices see the structure that experts have automated. In a semester-long CS1 study, exam averages did not differ, but fewer students failed or dropped out. Shorter studies found better early performance and persistence. **[several]** [S6][S7]
- **Teach reading and tracing before writing.** Novices who can trace code (follow it step by step, tracking each variable) and explain it in plain words write code better. In exam data, tracing and explaining together explained a large share of the variance in code-writing scores. This is correlational, not proof of cause. One theory of instruction sequences the skills explicitly (trace semantics → write syntax → read templates → write with templates) and reported higher exercise completion and fewer errors in an exploratory study. **[several]** for the correlation, **[single]** for the sequence [S11][S12]
- **Predict, then run.** Asking learners to commit to a prediction before seeing an outcome improves learning across many domains, because the surprise when the prediction is wrong flags a gap. It works best when learners know enough to predict rather than guess. PRIMM (Predict, Run, Investigate, Modify, Make) builds lessons around this. The PRIMM authors report positive classroom results, but I could only confirm the framework and teacher experiences, not the size of the outcome effect. **[several]** for prediction (mostly outside programming), **[single]/[opinion]** for PRIMM [S2][S3][S15]
- **Use, then modify, then create.** Start with working code the learner runs, then has them change it, then build something new with the same structures. In one middle-school comparison, learners in the Use-Modify-Create order rated the early coding tasks as less difficult. The evidence on learning gains is thinner than the framework's popularity suggests. **[single]** [S4][S1]
- **Make the notional machine visible.** A notional machine is a simplified, accurate model of what the computer does when code runs (for example, a variable as a labelled box; a reference as an arrow to an object). Novices' own models are often non-viable and drawn from surface features of the syntax. In a Java course, about a third held a wrong model of value assignment and only 17% a viable model of reference assignment. Students with viable models scored better. A follow-up found that cognitive conflict (a prediction the learner's model gets wrong) plus visualisation worked better than visualisation alone. Learners can hold several conflicting models at once, so check models more than once. **[several]** [S13][S14][S42]
- **Manage cognitive load: one new element at a time.** Working memory holds only a few new elements. Keep explanations next to the code they describe (no split attention), cut decoration, and pre-teach terms before a dense example. **[several]** (cognitive load theory, widely replicated, though it has critics) [S1][S8]
- **Struggle first can help, but only with prior knowledge.** "Productive failure" (attempt a hard problem, then get instruction) beat instruction-first in a meta-analysis of 53 studies. Coverage stresses it needs prior knowledge, carefully designed problems, and usually group work, and most of the studies were maths and science. This fits expertise reversal: worked examples for true beginners, problem-first for learners who already have the basics. **[meta]** (secondary coverage only) [S16][S9]
- **Move between concrete and abstract.** RPF guides recommend "semantic waves": start from a concrete everyday example, name the technical concept, then return to code. Also recommended: live coding that includes real mistakes and debugging. **[opinion]** [S1]

## Exercises, feedback and hints

- **Parsons problems are an efficient practice step.** Learners put mixed-up lines of code in order. They solve these much faster than writing or fixing equivalent code, with similar learning gains and retention a week later. Adaptive Parsons problems (which merge or remove blocks when a learner struggles) were solved about twice as often. Distractor lines (wrong lines mixed in) raise difficulty and load. Whether they help learning is unsettled: this is my reading, and I did not check the review's conclusion on it. **[meta]** (2022 review) [S5][S1]
- **Feedback works, and informative feedback works best.** Across 435 studies the average feedback effect was medium (d ≈ 0.48), with large variation. Feedback with more information (what is wrong, why, and how to improve) beat bare right/wrong. **[meta]** [S18]
- **Auto-graders mostly say what is wrong, not what to do next.** A review of 101 programming-feedback tools found most feedback points out mistakes and rarely helps learners fix them or choose a next step. Test names and failure messages are the main feedback channel in a test-based exercise. **[meta]** [S17]
- **Explained hints feel better; the learning gain is unproven.** Next-step code hints with a short explanation of why were rated more relevant and easier to connect to the task, but made little difference to performance. Self-explanation prompts alongside hints were studied too. **[single]** [S19]
- **Plan for hint abuse.** In one tutor, learners clicked through hints on 36% of actions (14% when rapid repeats count as one) to reach the bottom-out answer. "Gaming the system" was more strongly linked to lower learning than any other off-task behaviour. Forced delays between hint levels just led learners to find another way to game the system. Graduated hints (nudge → concept → partial code), with the full solution last and clearly marked, are the standard design. **[several]** [S20]
- **Novice-friendly error messages: worth doing, effect unsettled.** About 50 years of research agree that compiler messages are hard for novices. Recommended fixes include plain wording, context, a positive tone, examples of the same error, a hint at the fix, and good timing. Controlled studies conflict: one found enhanced Java messages made no difference, while a larger study (~200 students, ~50,000 errors) found fewer errors and fewer repeats. **[meta]** for the problem, **[several, conflicting]** for the fix [S21][S22][S23]
- **AI explanations of errors are not a silver bullet.** LLM-written error explanations were sometimes clearer than the original messages. But in a 106-novice study, GPT-4 explanations sped up fixes on only 1 of 6 tasks, and expert-written explanations beat both GPT-4 and the stock messages. **[single]** ×2 [S24][S25]
- **Unrestricted AI help during practice can harm later performance.** In a field experiment with ~1,000 students, a plain chat AI raised practice scores but lowered exam scores (−17%) once it was removed. A tutor version that was told to give hints rather than answers avoided most of that harm. In observed novice programming sessions, AI sped up students who already had a plan and misled students who were struggling ("widening gap"). **[single]** large RCT + **[single]** qualitative [S26][S27]
- **Practice at the same time as learning, in small steps.** Use-Modify-Create and PRIMM both start with modifying given code before creating from a blank editor. Blank-editor tasks come last. **[opinion]**, consistent with worked-example research [S2][S4][S8]

## Quizzes, review and memory

- **Retrieval practice beats rereading.** Testing yourself beats restudying the same material: g ≈ 0.50 in a lab-focused meta-analysis and g ≈ 0.61 in one that included classrooms. I took these figures from secondary summaries, and both match what I remember of the papers. The benefit roughly doubled when feedback followed the answer (g ≈ 0.73 with feedback vs 0.39 without, per a secondary summary). **[meta]** [S28][S29]
- **Multiple choice is fine, especially with feedback.** In the classroom-inclusive meta-analysis, multiple-choice practice gave strong testing effects, and practice that matched the final test format helped. The two meta-analyses disagree on format, partly because they cover different studies. **[meta, partly conflicting]** [S29][S28]
- **Space the reviews out, with growing gaps.** Spaced study beats massed study, and the best gap grows with how long you need to remember: roughly 20–40% of the delay for a 1-week test, and 5–10% for a 1-year test. Practice testing and spacing are the two techniques a major review rated "high utility". Rereading and highlighting were rated low. **[meta]** + **[single, large]** [S30][S31][S32]
- **Interleave similar-looking problem types.** Mixing problem types in one session beat blocking them (g ≈ 0.42), but the effect varies a lot and is biggest when the categories look alike and must be told apart. For programming this suggests mixing problems where the learner must choose the tool (for vs while, `map` vs `forEach`, WHERE vs HAVING). That application is my inference: I found no programming-specific study. **[meta]** + **[opinion]** [S33][S30]
- **Use misconceptions as distractors and ask for confidence.** The SQL prevalence study built multiple-choice options from known misconceptions and asked for a certainty rating. Many wrong answers were given with high confidence, which a plain right/wrong score hides. Concept inventories and RPF's "alternative conceptions" guide recommend the same approach. **[single]** + **[opinion]** [S47][S1]
- **Flashcards for syntax and vocabulary.** Hermans recommends spaced flashcards for syntax and core idioms, on the grounds that chunks stored in long-term memory free working memory for reading code. Experts remember more code because they chunk it. **[opinion grounded in several]** [S35]
- **The six student strategies.** The Learning Scientists' free materials cover spaced practice, retrieval practice, elaboration, interleaving, concrete examples and dual coding (words plus visuals). They are a useful public checklist, licensed for non-commercial use only. **[opinion grounded in meta]** [S34]

## Motivation and gamification

- **Gamification helps a little on average.** Across studies, effects were small to medium: cognitive outcomes g ≈ 0.49, motivation g ≈ 0.36, behaviour g ≈ 0.25. Only the cognitive effect held up in the more rigorous studies. Which game elements cause the effect is still unclear. **[meta]** [S36]
- **Leaderboards plus forced badges can backfire.** In a semester-long class comparison, the gamified section (badges, coins, leaderboard) reported less intrinsic motivation, satisfaction and empowerment over time, and scored lower on the final exam through that motivation drop. The authors suggested social comparison and forced badge-earning as causes, but that was not tested. The sample was small (80) and the elements were bundled. **[single]** [S37]
- **Expected, contingent rewards can crowd out interest. Informative praise does not.** Across 128 experiments, expected tangible rewards for doing, finishing or performing a task reduced later free-choice interest, while positive informational feedback increased it. How far this applies to points in an app is debated (the 1999 paper was answering a rival meta-analysis). **[meta, contested]** [S38]
- **Intact streaks keep people going; broken ones discourage them, less so if repairable.** Showing a behaviour log as an unbroken streak increased continued engagement, even when the actual behaviour was the same. After a break, engagement dropped more when people blamed themselves and less when the streak could be repaired. The authors advise against notifications that point out a broken streak. **[several]** (7 studies, consumer settings) [S39]
- **Streak freezes are an industry practice with only company evidence.** Duolingo reports that streaks drive retention through loss aversion, that the fear of losing a streak can stop people starting, and that freezes give leniency. Critics note freezes can become a crutch. None of this is independently verified. **[opinion (industry)]** [S40]
- **Reward the learning behaviour, not the clicks.** Since hint abuse and guess-and-check predict lower learning [S20], XP that pays the same for a bottom-out solution as for an independent solve rewards gaming. This is my inference from the research. No gamification study I found tested it directly. **[opinion]**

## Beginners vs experts

- **What helps beginners can hurt experts (expertise reversal).** Detailed worked examples, integrated explanations and heavy guidance help novices but become redundant for experienced learners and can lower their performance. They have to reconcile the guidance with what they already know. Instruction should fade as expertise grows. **[several]** (reviews) [S8][S9]
- **Quick diagnostic checks can place learners.** Kalyuga's reviews describe rapid tests ("show the first step you would take") that estimate expertise in minutes and can route learners to worked examples or straight to problems. **[several]** [S9]
- **Experts chunk and novices don't.** Experienced programmers see familiar patterns as single chunks, so the same code puts less load on them. Novice-sized steps feel slow to experts, while expert-sized steps overload novices. **[several]** [S35]
- **Prior languages are both help and hazard.** Many difficulties come from prior knowledge: natural language, maths, and earlier programming languages. In SQL, a whole category of misconceptions comes from previous course knowledge, and the most common SQL misconception (accepting `==` or `IS` for equality) partly comes from English ("city is London") and from other languages. Learners switching languages need a "false friends" list. **[meta]** (review, abstract only) + **[single]** [S41][S46][S47]
- **AI tools widen the gap.** Students with a plan get faster with AI suggestions. Students without metacognitive strategies get misled or get a false sense of progress. Engineers and beginners need different guidance on AI use. **[single]** [S27][S26]

## Misconceptions by language

Level tags: L0 Beginner, L1 Junior, L2 Middle, L3 Senior (where the misconception usually first matters). Most misconception research comes from Java, Python and Scratch. Cross-language items are listed once under the first language they matter in and marked "(all)".

### JavaScript

- **L0 (all): `=` is a maths equation or works both ways.** Learners read `a = b` as "a and b are now linked" or as symmetric, and expect later changes to `b` to update `a`. **[several]** [S42][S41]
- **L0 (all): a variable keeps a history of its values or holds several.** **[several]** [S41]
- **L0 (all): the program "knows what I meant".** Pea's classic bugs: parallelism (a `while` condition is checked continuously, not once per pass), intentionality (the program looks ahead), and a hidden-mind "superbug". **[single, classic]** [S43]
- **L0: `==` and `===` are interchangeable, or coercion is random.** Real code coerces types in about 80% of function runs, and most coercions are harmless. Beginners' confusion with `==` is reported widely by practitioners, but I found no learner study. **[single (code)]** + **[opinion]** [S51]
- **L1 (all): copying an object or array variable copies the object.** Reference assignment is the weakest mental model in the Java research (17% viable). JS objects and arrays behave the same way. **[single]** [S42]
- **L1: `const` makes a value immutable.** It only stops reassigning the name. **[opinion]**
- **L1: array methods all return new arrays.** Some mutate in place (`sort`, `reverse`, `splice`, `push`), others return new arrays (`map`, `filter`, `toSorted`). **[opinion]**
- **L2: `await` freezes the whole program; a 0 ms `setTimeout` runs immediately; awaits written one after another run in parallel; forgetting `await` gives the data.** These are widely reported by practitioners. Developer studies find promise anti-patterns (unhandled rejections, missing returns in `.then` chains) in real Node.js apps. I found no novice study, so an event-loop notional machine (call stack, task and microtask queues) is the obvious teaching tool. **[opinion]** + **[single (developers)]** [S50][S13]
- **L2: closures capture a value rather than a variable** (the classic `var`-in-a-loop surprise). **[opinion]**
- **L2: `this` is fixed by where a function is written.** It is fixed by how the function is called, except for arrow functions. **[opinion]**

### Python

- **L0: `print` and `return` are the same thing.** Teachers report this widely. I found no study that measures it. **[opinion]**
- **L0: `input()` gives a number.** It gives a string, so `"5" + "3"` is `"53"`. **[opinion]**
- **L0: indentation is cosmetic.** **[opinion]**
- **L0 (all): off-by-one with `range`.** `range(n)` stops before `n`, and the loop variable after the loop holds the last value it took. Loop-boundary errors are among the most common novice bugs across languages. **[several]** [S41][S43]
- **L1: `b = a` copies a list.** It makes a second name for the same list. List referencing showed up as a misconception in a Python exam analysis, and it matches the reference results above. **[single]** ×2 [S45][S42]
- **L1: default arguments are created fresh on each call.** The Python tutorial warns that defaults are evaluated only once, so a mutable default is shared across calls. **[fact + opinion]** [S55]
- **L1 (all): recursion is a loop.** The "loop model" treats a recursive call as jumping back to the top with new values. It works for tail recursion but fails when work happens after the call returns. Experts tend to hold the "copies model" (each call is a separate copy with its own variables). Students who showed the right model with diagrams often lost it without them, so keep using diagrams. Base cases are a known separate difficulty. **[several]** [S44]
- **L2: `is` and `==` are the same.** `is` checks identity and `==` checks value. Small-integer and string caching makes `is` look right by accident. **[opinion]**
- **L2: a generator or iterator can be looped over again.** **[opinion]**
- **L2/L3: calling an `async def` function runs it.** It returns a coroutine that does nothing until awaited (Python warns "never awaited"). The same event-loop model as JS applies. **[opinion]**

### TypeScript

- **L0/L1: types exist at runtime and check incoming data.** Types are erased at compile time, so JSON from an API is not validated by a type annotation. The handbook says so explicitly. I found no learner-misconception study. **[fact]** [S54] + **[opinion]**
- **L1: `as` converts or checks a value.** A type assertion only tells the compiler to trust you. **[fact]** [S54] + **[opinion]**
- **L1: `any` is rare and explicit.** In a study of 151 public repos, `any` was everywhere and mostly inferred rather than written, so it spreads silently unless strict settings catch it. In a 604-project mining study, less `any` correlated with somewhat better code quality. **[single]** [S53]
- **L2: static types catch most bugs.** In a study of fixed public JS bugs, adding TS or Flow types would have caught about 15%. That is a real but partial benefit, and the authors call it an underestimate because types also help during development. **[single]** [S52][S53]
- **L2: TS checks types by name (nominally), the way Java and C# do.** TS is structural: any value with the right shape fits the type. Excess-property checks apply only to fresh object literals, which surprises learners. **[opinion]**
- **L2/L3: turning off `strictNullChecks` or using `!` is harmless.** It hides null and undefined bugs. **[opinion]**

### SQL

- **L0: `==` or `IS` works for equality.** This was the most common misconception in a 249-student, 6-university survey (28% of answers on those items, held with high confidence). It comes partly from English ("city is London") and other languages. **[single]** [S47]
- **L0: the WHERE clause needs brackets.** **[single]** [S47]
- **L0/L1: `DISTINCT` is always needed, even when selecting a primary key.** 24% of answers, with high confidence. Also: DISTINCT "takes the first item" (11%). **[single]** [S47]
- **L1: join conditions.** Learners add needless primary-key/foreign-key comparisons (23%), drop table qualifiers on ambiguous columns (13%), or join on unrelated columns. In a 33,000-query analysis, missing, inconsistent and wrong join conditions were among the most persistent errors. Logical errors outlasted syntax errors. **[single]** ×2 (large) [S47][S48]
- **L1: "counting" in the question means COUNT, GROUP BY and HAVING.** Learners reach for an aggregation template even when a plain join answers the question, or put COUNT in WHERE. **[single]** [S47]
- **L1: comparing rows needs only one copy of the table** (a self-join is needed). 14% of answers. **[single]** [S47]
- **L1: NULL is a value like any other.** `x = NULL` is never true (use `IS NULL`), `NULL = NULL` is not true, `NOT IN` against a list containing NULL returns no rows, and `COUNT(col)` skips NULLs while `COUNT(*)` does not. The behaviour is documented fact, but I found no study measuring how common these learner errors are. **[fact]** [S49] + **[opinion]**
- **L2: CTE scoping.** "A CTE is not a table, so it can't go in FROM" and related errors were among 10 new misconceptions found in 2023. **[single]** [S47]
- **L1/L2: SQL runs top to bottom as written.** Learners expect a SELECT alias to work in WHERE. The logical order is FROM → WHERE → GROUP BY → HAVING → SELECT → ORDER BY. The SQL researchers suggest SQL-specific notional machines (diagrams of intermediate result tables) as a promising, untested fix. **[opinion]** + **[single]** [S47]

## Takeaways for PandaDev

1. **Lesson shape:** for new concepts, lead with a worked example (with short subgoal labels on its steps), then a predict-the-output question before running it, then a modify task, then a create task. Fade the support across a module, not just within one lesson. [S2][S6][S8][S10][S15]
2. **Reading before writing:** in each L0 to L1 module, include at least one trace or explain-in-plain-words task (step through the code and track each variable's value) before the first blank-editor exercise. Parsons problems (adaptive if possible) are a cheap bridge between reading and writing. [S5][S11][S12]
3. **Mental models on purpose:** for assignment, references, loops, recursion, the event loop and SQL evaluation order, show a consistent notional machine (boxes, arrows, call frames, queues, intermediate tables). Pair it with a prediction the learner's likely wrong model gets wrong (cognitive conflict). [S13][S42][S44][S47]
4. **Exercise feedback:** write test names and failure messages that say what was expected, what happened, and what to look at next. Plain right/wrong is the weakest kind of feedback. [S17][S18][S21]
5. **Hints:** graduate them (nudge → concept → partial code), put the full solution last, and keep it distinct. If AI help is ever added, it should give hints and refuse to hand over answers. [S19][S20][S26][S27]
6. **Quizzes:** build distractors from documented misconceptions (the lists above), give feedback that explains the answer, and consider a confidence rating to catch confidently held wrong models. [S28][S29][S47]
7. **Review:** schedule quiz review with growing gaps, and mix similar-looking problem types in review sets (for vs while, WHERE vs HAVING) rather than blocking by lesson. [S31][S32][S33]
8. **XP and streaks:** make XP feedback about progress, not a contingent wage. Avoid paying the same XP for revealed solutions as for independent solves. Keep streaks repairable (freezes) and never shame a broken streak. Treat leaderboards as optional and low-stakes. [S36][S37][S38][S39]
9. **Engineers:** offer "already know this?" placement checks (a few first-step or predict questions) that let experienced learners skip worked examples and go straight to problems. Fully guided content can slow them down. [S8][S9]
10. **Language switchers:** give each course a short "false friends" note for learners who know another language (`==` in SQL, `is` in Python vs SQL `IS`, structural vs nominal types in TS, `const` vs immutability). [S41][S47]

Open points I could not confirm: the size of PRIMM's outcome effect [S3]; exact effect sizes inside Rowland and Adesope (taken from secondary summaries); the details of Sinha & Kapur [S16]; any peer-reviewed study of novice misconceptions in JS async, `this`, closures, or TypeScript; how common the SQL NULL misconceptions are; independent evidence on streak freezes.
