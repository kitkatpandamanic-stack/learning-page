Welcome to the Level 1 capstone! Over three parts you'll build a **habit tracker** that runs in the browser: you add habits like "Read 10 pages" or "Swim on Mondays and Wednesdays", tick them off each day, and watch your **streaks** grow. 🔥 Everything is typed, it's saved in `localStorage`, and the logic is tested.

Here's the plan:

- **Part 1 (this one):** the types for habits, schedules and check-ins, plus pure functions that answer "is this habit due today?" and "how long is my streak?".
- **Part 2:** a generic `Store<T>`, a `HabitTracker` class with private state, and saving and loading with validated JSON.
- **Part 3:** the page: a typed form, today's list with check buttons and streak badges.

This part uses [discriminated unions](/learn/typescript/discriminated-unions) and `assertNever`, `Record` lookup tables from [Utility Types](/learn/typescript/utility-types), `readonly` properties, and an idea from the [parking garage](/learn/typescript/structural-typing-and-class-design): never read the real clock inside your logic.

## Dates as plain strings

A habit tracker is all about **days**: which days a habit is due, which days you did it. We'll store every day as a string in the **ISO format** `"2026-03-16"`: year, month, day, always with two-digit months and days. That might look old-fashioned next to JavaScript's `Date` objects, but strings have big advantages here:

- They turn into JSON and back without any work, which matters when we save to `localStorage` in Part 2. (A `Date` becomes a string in JSON anyway, and doesn't come back as a `Date`.)
- They have **no time and no time zone**. A habit is done "on 16 March", not "at 23:59:59.999 in London".
- Because the biggest unit comes first, ISO dates **compare and sort correctly as text**:

<CodeExample output={`true
false
[ '2026-02-28', '2026-03-02', '2026-03-14' ]`}>

```ts
type IsoDate = string; // "2026-03-16": year-month-day

const start: IsoDate = "2026-03-09";
const end: IsoDate = "2026-03-14";

console.log(start < end); // compared letter by letter
console.log("2026-12-01" < "2026-02-01");

const days: IsoDate[] = ["2026-03-14", "2026-02-28", "2026-03-02"];
console.log([...days].sort()); // oldest first
```

</CodeExample>

`type IsoDate = string` is just a **name** for `string`: it tells the reader what kind of string to expect, but TypeScript still accepts any string, even `"14/03/2026"`. In Level 3 you'll meet **branded types**, which can tell the two apart. For now, we'll check dates where they come **in** (Part 2) and keep everything inside clean.

### A few date helpers

For date **arithmetic** ("the day before", "which weekday?") we briefly turn the string into a `Date` and back. Two small new things make that safe:

- `new Date("2026-03-16T00:00:00Z")` is midnight on that day in **UTC**, the time zone with no daylight saving. The `Z` at the end means UTC.
- The `getUTC...` and `setUTC...` methods work in UTC too, so the result is the same on every computer in the world. `getUTCDay()` gives the weekday as a number, **counting from Sunday**: 0 is Sunday, 1 is Monday... 6 is Saturday.

<CodeExample output={`2026-03-02
2026-02-28
mon
2026-03-16`}>

```ts
type IsoDate = string;
type Weekday = "mon" | "tue" | "wed" | "thu" | "fri" | "sat" | "sun";

// getUTCDay() counts from Sunday (0) to Saturday (6)
const WEEKDAYS: Weekday[] = [
  "sun", "mon", "tue", "wed", "thu", "fri", "sat",
];

function toDate(date: IsoDate): Date {
  return new Date(`${date}T00:00:00Z`); // midnight UTC
}

function toIsoDate(date: Date): IsoDate {
  return date.toISOString().slice(0, 10);
}

function addDays(date: IsoDate, days: number): IsoDate {
  const d = toDate(date);
  d.setUTCDate(d.getUTCDate() + days);
  return toIsoDate(d);
}

function weekdayOf(date: IsoDate): Weekday {
  return WEEKDAYS[toDate(date).getUTCDay()];
}

// The Monday of the week that date is in
function startOfWeek(date: IsoDate): IsoDate {
  const daysSinceMonday = (toDate(date).getUTCDay() + 6) % 7;
  return addDays(date, -daysSinceMonday);
}

console.log(addDays("2026-02-27", 3)); // across a month
console.log(addDays("2026-03-01", -1)); // and back
console.log(weekdayOf("2026-03-16"));
console.log(startOfWeek("2026-03-22")); // a Sunday
```

</CodeExample>

`setUTCDate` is clever: give it day 30 of February and it rolls over into March, so `addDays` never has to know how long a month is. `toISOString()` gives `"2026-03-02T00:00:00.000Z"`, and `.slice(0, 10)` keeps just the date part. In `startOfWeek`, `(getUTCDay() + 6) % 7` turns "days since Sunday" into "days since Monday": Monday gives 0, Sunday gives 6.

## Today is a parameter

Here's a rule for the whole project: **no function in the logic reads the real date**. No `new Date()` without an argument, no `Date.now()`. Whenever a function needs "today", it takes it as a parameter:

```ts
// 🤔 Hard to test: the answer changes every day
function streakToday(habit: Habit, checkIns: CheckIn[]): number {
  const today = toIsoDate(new Date()); // reads the clock
  // ...
}

// ✅ Easy to test: same inputs, same answer, forever
function streak(
  habit: Habit,
  checkIns: CheckIn[],
  today: IsoDate,
): number {
  // ...
}
```

It's the same idea as the `FakeClock` in the parking garage: if time comes **in** through a parameter, a test can say "pretend it's Tuesday 17 March 2026" and get the same answer on every run, in every time zone. Only the page in Part 3 asks the browser for the real date, once, at the very edge of the app.

<Callout type="tip" title="Pure functions">

A function whose result depends only on its parameters, and which changes nothing outside itself, is called a **pure function**. Everything in this part is pure: no clock, no storage, no page. Pure functions are the easiest code in the world to test, reuse and trust, so it pays to put as much logic in them as you can.

</Callout>

## Three kinds of schedule

Habits repeat in different ways. Some are **daily** ("Read 10 pages"), some are on **certain weekdays** ("Swim on Mon, Wed, Fri"), and some just need doing **a number of times a week**, on whichever days suit you ("Yoga twice a week"). Each kind needs different data, which makes it a perfect [discriminated union](/learn/typescript/discriminated-unions):

```ts
type Schedule =
  | { kind: "daily" }
  | { kind: "weekly"; days: Weekday[] }
  | { kind: "timesPerWeek"; times: number };
```

A daily habit needs nothing else, a weekly one needs its days, and a times-per-week one needs a number. Nonsense schedules can't even be written:

```ts
const a: Schedule = { kind: "weekly" };
// ❌ Error: Type '{ kind: "weekly"; }' is not assignable to type 'Schedule'.

const b: Schedule = { kind: "daily", days: ["mon"] };
// ❌ Error: Object literal may only specify known properties, and 'days' does not exist in type '{ kind: "daily"; }'.

const c: Schedule = { kind: "weekly", days: ["mon", "thur"] };
// ❌ Error: Type '"thur"' is not assignable to type 'Weekday'. Did you mean '"thu"'?
```

Compare that with one object full of optional properties (`days?`, `times?`), where every function would have to wonder which ones are really there.

The first function on schedules turns one into text for the page. A `Record<Weekday, string>` gives every weekday a short name (and TypeScript makes sure none is missing), and `assertNever` makes sure every kind of schedule is handled:

<CodeExample output={`Every day
Mon, Wed, Fri
2 times a week`}>

```ts
type Weekday = "mon" | "tue" | "wed" | "thu" | "fri" | "sat" | "sun";

type Schedule =
  | { kind: "daily" }
  | { kind: "weekly"; days: Weekday[] }
  | { kind: "timesPerWeek"; times: number };

function assertNever(value: never): never {
  throw new Error(`Unexpected value: ${JSON.stringify(value)}`);
}

const DAY_NAMES: Record<Weekday, string> = {
  mon: "Mon", tue: "Tue", wed: "Wed", thu: "Thu",
  fri: "Fri", sat: "Sat", sun: "Sun",
};

function describeSchedule(schedule: Schedule): string {
  switch (schedule.kind) {
    case "daily":
      return "Every day";
    case "weekly":
      return schedule.days.map((day) => DAY_NAMES[day]).join(", ");
    case "timesPerWeek":
      return `${schedule.times} times a week`;
    default:
      return assertNever(schedule);
  }
}

console.log(describeSchedule({ kind: "daily" }));
console.log(
  describeSchedule({ kind: "weekly", days: ["mon", "wed", "fri"] }),
);
console.log(describeSchedule({ kind: "timesPerWeek", times: 2 }));
```

</CodeExample>

The payoff comes later. If you ever add a `{ kind: "monthly"; dayOfMonth: number }` schedule, `describeSchedule` stops compiling with `Argument of type '{ kind: "monthly"; dayOfMonth: number; }' is not assignable to parameter of type 'never'.`, and so does every other `switch` over schedules in the project. The compiler writes your to-do list. 📋

## Habits and check-ins

Now the two main characters. A **habit** has an id that never changes, a name and a schedule. A **check-in** records that a habit was done on a day:

```ts
interface Habit {
  readonly id: string;
  name: string;
  schedule: Schedule;
}

interface CheckIn {
  readonly id: string; // one per habit per day
  readonly habitId: string;
  readonly date: IsoDate;
}

function checkInId(habitId: string, date: IsoDate): string {
  return `${habitId}@${date}`;
}
```

Notice the check-in's `id`. Instead of a random id, it's built from the habit and the day: `"h1@2026-03-16"`. That's a small design decision with a big effect: you can't do the same habit twice on one day, because the second check-in would have the **same id**. In Part 2 the store will refuse duplicate ids, so this rule will be enforced for free.

Check-ins are `readonly` all the way: a check-in is a fact about the past. To undo one, you remove it; you never edit it.

## Is it due today?

The page will show the habits that are **due** on the chosen day. A daily habit is always due; a weekly one only on its days. A times-per-week habit is due **every** day, because any day can count towards the target. Let's print a whole week:

<CodeExample output={`mon: Read, Swim, Yoga
tue: Read, Yoga
wed: Read, Swim, Yoga
thu: Read, Yoga
fri: Read, Swim, Yoga
sat: Read, Yoga
sun: Read, Yoga`}>

```ts

}

}

  | { kind: "daily" }
```

## Counting streaks

A **streak** is how many times in a row you've kept a habit going. It sounds simple, but "in a row" hides three rules. Here's a daily habit, checked in on the 14th, 15th and 16th, seen from different days:

```text
           13   14   15   16   17   18
check-ins   ·    ✓    ✓    ✓    ·    ·
on the 16th:     ←─── 3 ───→             streak 3
on the 17th:     ←─── 3 ───→   (today)   streak 3
on the 18th:                    ✗        streak 0
```

1. **Count back from today**, one due day at a time, while the days are done.
2. **Today doesn't break a streak.** On the 17th you haven't done it yet, but the day isn't over, so the streak is still 3. A missed day in the **past** ends it: on the 18th, the 17th was missed, so the streak is 0.
3. **Days off don't count.** For a habit due on Mon, Wed and Fri, Tuesday is skipped as if it weren't there.

Here are the rules as code. `dayStreak` gets the dates the habit was done and walks back from `today`:

```ts
// Due days in a row that were done, counting back from today
function dayStreak(
  habit: Habit,
  dates: IsoDate[],
  today: IsoDate,
): number {
  if (dates.length === 0) return 0;
  const first = [...dates].sort()[0];
  let count = 0;
  for (let day = today; day >= first; day = addDays(day, -1)) {
    if (!isDue(habit, day)) continue; // a day off
    if (dates.includes(day)) {
      count++;
    } else if (day !== today) {
      break; // a missed day ends the streak
    }
  }
  return count;
}
```

A few things to notice:

- The `for` loop counts **dates** instead of numbers: it starts at `today`, and `addDays(day, -1)` steps back one day each time. With a `for` loop, `continue` still runs that step, so skipping a day off can't get stuck.
- The loop **must** end somewhere. `day >= first` (a string comparison, which works for ISO dates) stops it at the oldest check-in: before that, nothing can be done. Without it, a weekly habit with no days at all would loop forever.
- `[...dates].sort()` sorts a **copy**, so the caller's array isn't changed.

Times-per-week habits count **weeks** instead of days: how many weeks in a row reached the target. The current week counts once it's reached, but, like today, it can't break the streak while it's still going. `timesInWeek` counts the dates from a Monday to the Sunday after it:

```ts
// How many dates fall in the week that starts on monday
function timesInWeek(dates: IsoDate[], monday: IsoDate): number {
  const sunday = addDays(monday, 6);
  return dates.filter((d) => d >= monday && d <= sunday).length;
}

// Weeks in a row that reached the target
function weekStreak(
  times: number,
  dates: IsoDate[],
  today: IsoDate,
): number {
  if (dates.length === 0 || times < 1) return 0;
  const first = startOfWeek([...dates].sort()[0]);
  const thisMonday = startOfWeek(today);
  let count = 0;
  let monday = thisMonday;
  while (monday >= first) {
    if (timesInWeek(dates, monday) >= times) {
      count++;
    } else if (monday !== thisMonday) {
      break; // a missed week ends the streak
    }
    monday = addDays(monday, -7);
  }
  return count;
}
```

Finally, `streak` puts it together. It picks out this habit's dates, ignores check-ins **after** `today` (they haven't happened yet, from today's point of view), and chooses the right counter for the schedule. Two `case` labels in a row share one branch:

<CodeExample output={`Read: 3
Swim: 3
Yoga: 2`}>

```ts
type IsoDate = string;
type Weekday = "mon" | "tue" | "wed" | "thu" | "fri" | "sat" | "sun";
const WEEKDAYS: Weekday[] = [
  "sun", "mon", "tue", "wed", "thu", "fri", "sat",
];
function toDate(date: IsoDate): Date {
  return new Date(`${date}T00:00:00Z`);
}
function addDays(date: IsoDate, days: number): IsoDate {
  const d = toDate(date);
  d.setUTCDate(d.getUTCDate() + days);
  return d.toISOString().slice(0, 10);
}
function weekdayOf(date: IsoDate): Weekday {
  return WEEKDAYS[toDate(date).getUTCDay()];
}
function startOfWeek(date: IsoDate): IsoDate {
  const daysSinceMonday = (toDate(date).getUTCDay() + 6) % 7;
  return addDays(date, -daysSinceMonday);
}

type Schedule =
  | { kind: "daily" }
  | { kind: "weekly"; days: Weekday[] }
  | { kind: "timesPerWeek"; times: number };
interface Habit {
  readonly id: string;
  name: string;
  schedule: Schedule;
}
interface CheckIn {
  readonly id: string;
  readonly habitId: string;
  readonly date: IsoDate;
}
function assertNever(value: never): never {
  throw new Error(`Unexpected value: ${JSON.stringify(value)}`);
}
function isDue(habit: Habit, date: IsoDate): boolean {
  const schedule = habit.schedule;
  switch (schedule.kind) {
    case "daily":
    case "timesPerWeek":
      return true;
    case "weekly":
      return schedule.days.includes(weekdayOf(date));
    default:
      return assertNever(schedule);
  }
}

// ===== Streaks =====
function doneDates(
  habitId: string,
  checkIns: readonly CheckIn[],
): IsoDate[] {
  return checkIns
    .filter((c) => c.habitId === habitId)
    .map((c) => c.date);
}

function timesInWeek(dates: IsoDate[], monday: IsoDate): number {
  const sunday = addDays(monday, 6);
  return dates.filter((d) => d >= monday && d <= sunday).length;
}

  habit: Habit,
  dates: IsoDate[],
  today: IsoDate,
): number {

  const first = [...dates].sort()[0];
  let count = 0;
  for (let day = today; day >= first; day = addDays(day, -1)) {
    if (!isDue(habit, day)) continue;
    if (dates.includes(day)) {
      count++;
    } else if (day !== today) {
      break;
    }
  }
  return count;
}

function weekStreak(
  times: number,
  dates: IsoDate[],
  today: IsoDate,
): number {
  if (dates.length === 0 || times < 1) return 0;
  const first = startOfWeek([...dates].sort()[0]);
  const thisMonday = startOfWeek(today);
  let count = 0;
  let monday = thisMonday;
  while (monday >= first) {
    if (timesInWeek(dates, monday) >= times) {
      count++;
    } else if (monday !== thisMonday) {
      break;
    }
    monday = addDays(monday, -7);
  }
  return count;
}

function streak(
  habit: Habit,
  checkIns: readonly CheckIn[],
  today: IsoDate,
): number {
  // Check-ins after today don't count (yet)
  const dates = doneDates(habit.id, checkIns)
    .filter((d) => d <= today);
  const schedule = habit.schedule;
  switch (schedule.kind) {
    case "daily":
    case "weekly":
      return dayStreak(habit, dates, today);
    case "timesPerWeek":
      return weekStreak(schedule.times, dates, today);
    default:
      return assertNever(schedule);
  }
}

  return dates.map((date) => ({
    id: `${habitId}@${date}`,
    habitId,
    date,

}

const log: CheckIn[] = [
  ...did("h1", "2026-03-14", "2026-03-15", "2026-03-16"),
  ...did("h2", "2026-03-11", "2026-03-13", "2026-03-16"),
  ...did("h3", "2026-03-03", "2026-03-05", "2026-03-10"),
  ...did("h3", "2026-03-14", "2026-03-17"),
];

for (const habit of habits) {
  console.log(`${habit.name}: ${streak(habit, log, "2026-03-17")}`);
}
```

</CodeExample>

Check the answers against the rules. **Read** was done on the 14th, 15th and 16th, and today (the 17th) isn't over: 3 days. **Swim** skips its days off and counts Wed 11, Fri 13 and Mon 16: 3. **Yoga** reached 2 in the weeks starting 2 and 9 March, and this week (1 so far) doesn't break the streak yet: 2 weeks.

<Callout type="warning" title="Dates are a classic home for bugs">

Month ends, leap years, "is today included?", weeks starting on Sunday or Monday... Date code is full of off-by-one traps, and they're easy to miss by just reading. That's why the next step is **tests**: a list of exact days with the exact answers you expect.

</Callout>

## Testing with Vitest

So far you've checked results by printing them and reading the output. Real projects let a **test runner** do the checking. PandaDev's editor has [Vitest](https://vitest.dev) built in, a popular test runner for TypeScript. You'll learn it properly in Level 2; for this project you only need three functions:

- `describe(name, fn)` groups related tests;
- `it(name, fn)` is one test, named like a sentence: "it counts days in a row";
- `expect(actual).toBe(expected)` checks one value. (`toEqual` compares arrays and objects by their contents.)

You import them at the top, and the tests run after the rest of the code. Each passing test gets a ✓, a failing one a × with what went wrong:

<CodeExample output={`✓ addDays > moves across the end of a month
✓ addDays > goes back with a negative number
✓ addDays > knows about leap years

Tests  3 passed (3)`}>

```ts
import { describe, it, expect } from "vitest";

type IsoDate = string;

function addDays(date: IsoDate, days: number): IsoDate {
  const d = new Date(`${date}T00:00:00Z`);
  d.setUTCDate(d.getUTCDate() + days);
  return d.toISOString().slice(0, 10);
}

describe("addDays", () => {
  it("moves across the end of a month", () => {
    expect(addDays("2026-02-27", 3)).toBe("2026-03-02");
  });
  it("goes back with a negative number", () => {
    expect(addDays("2026-03-01", -1)).toBe("2026-02-28");
  });
  it("knows about leap years", () => {
    expect(addDays("2028-02-28", 1)).toBe("2028-02-29");
  });
});
```

</CodeExample>

Because every function in this part is pure and takes `today` as a parameter, a test is just "these inputs give this answer". No setup, no waiting until next Tuesday. 🐼
