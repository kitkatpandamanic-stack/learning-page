Real applications spend most of their time **waiting**: for a server, a database, a timer. This lesson recaps how promises and `async`/`await` work as it goes (the JavaScript lessons on [promises](/learn/javascript/promises) and [async/await](/learn/javascript/async-await) explain them step by step, if you'd like a warm-up). The focus is on what TypeScript adds: it tracks what every promise will **eventually** hold, catches the classic "forgot to `await`" bug before it ships, and makes you deal honestly with errors that can be anything at all. ⏳

## `Promise<T>`: a value that arrives later

A promise is a box that will hold a value **later**. Its type says what will be inside: `Promise<number>` will give you a `number`, `Promise<void>` gives you nothing useful (it just tells you when something has finished). When you `await` a `Promise<T>`, you get a plain `T`:

<CodeExample output={`Rolling...
You rolled a 4
Double: 8`}>

```ts
function wait(ms: number): Promise<void> {
  return new Promise((resolve) => setTimeout(resolve, ms));
}

function rollDice(): Promise<number> {
  return new Promise((resolve) => {
    setTimeout(() => resolve(4), 50);
  });
}

console.log("Rolling...");
await wait(100);
const roll = await rollDice(); // roll: number
console.log(`You rolled a ${roll}`);
console.log(`Double: ${roll * 2}`);
```

</CodeExample>

`new Promise(...)` hands your function a `resolve` callback: calling `resolve(value)` fills the box, and everyone awaiting it carries on. Notice that we never told `new Promise(...)` what it holds: TypeScript worked it out from the function's return type. Without that hint it can't know, and falls back to `unknown`. Pass the type yourself with `new Promise<number>(...)`, and TypeScript checks what you `resolve` with too:

```ts
const answer = new Promise((resolve) => resolve(42));
const value: number = await answer;
// ❌ Error: Type 'unknown' is not assignable to type 'number'.

const typed = new Promise<number>((resolve) => resolve("42"));
// ❌ Error: Argument of type 'string' is not assignable to parameter of type 'number | PromiseLike<number>'.
```

## Async functions return promises

An `async` function **always** returns a promise, even when it returns a plain value. So its return type is `Promise<...>` of whatever you `return`:

<CodeExample output={`Mei
nobody`}>

```ts
type User = { id: number; name: string };

const users: User[] = [
  { id: 1, name: "Mei" },
  { id: 2, name: "Sam" },
];

const wait = (ms: number) =>
  new Promise<void>((resolve) => setTimeout(resolve, ms));

async function findUser(id: number): Promise<User | undefined> {
  await wait(50); // pretend this is a database
  return users.find((user) => user.id === id);
}

const mei = await findUser(1);
console.log(mei?.name ?? "nobody");

const ghost = await findUser(99);
console.log(ghost?.name ?? "nobody");
```

</CodeExample>

TypeScript could infer `Promise<User | undefined>` by itself, but in real projects it's good practice to **write the return type** of async functions that other code calls. It documents the contract ("this might not find anyone"), and if you change the body by mistake, the error appears inside the function instead of in ten callers. If you write the type without the `Promise`, TypeScript tells you exactly what to do:

```ts
async function countUsers(): number {
  // ❌ Error: The return type of an async function or method must be the global Promise<T> type. Did you mean to write 'Promise<number>'?
  return users.length;
}
```

### The forgotten `await`

The most common async bug of all is forgetting `await`. In JavaScript you get `undefined` or a mysterious `[object Promise]` at runtime. In TypeScript you get a compile error, because a `Promise<User>` is not a `User`:

```ts
async function getUser(id: number): Promise<User> {
  // ...
}

const user = getUser(1); // forgot await: user is Promise<User>
console.log(user.name);
// ❌ Error: Property 'name' does not exist on type 'Promise<User>'.

async function isAdmin(): Promise<boolean> {
  // ...
}

if (isAdmin()) {
  // ❌ Error: This condition will always return true since this 'Promise<boolean>' is always defined.
}
```

The second one is nasty in plain JavaScript: a promise object is always truthy, so **everyone** would be an admin. In your editor, both errors even come with a hint: "Did you forget to use 'await'?"

## `Awaited<T>`: what's inside the box

Sometimes you need the type a promise **resolves to**, for example the result of a function you didn't write. You met both tools in [Utility Types](/learn/typescript/utility-types): `ReturnType` gives you the promise, and **`Awaited<T>`** unwraps it, layer by layer, exactly like `await` does:

<CodeExample output={`Mei has 120 followers
Awaited unwraps every layer`}>

```ts
async function loadProfile(id: number) {
  return { id, name: "Mei", followers: 120 };
}

// ReturnType gives the promise; Awaited unwraps it
type Pending = ReturnType<typeof loadProfile>;
type Profile = Awaited<ReturnType<typeof loadProfile>>;

function greet(profile: Profile): string {
  return `${profile.name} has ${profile.followers} followers`;
}

const pending: Pending = loadProfile(1);
console.log(greet(await pending));

type Deep = Awaited<Promise<Promise<string>>>; // string
const text: Deep = "Awaited unwraps every layer";
console.log(text);
```

</CodeExample>

`Awaited<ReturnType<typeof fn>>` is a pattern you'll see a lot in real code, especially for functions from libraries whose result types aren't exported.

## `Promise.all` with typed results

`Promise.all` runs several promises **at the same time** and waits for all of them. Give it an array of **different** promises and TypeScript treats it as a **tuple**: each position keeps its own type, so destructuring gives you perfectly typed variables:

<CodeExample output={`Mei: 1 post, 3 unread
[ 'Mei', 'Sam' ]`}>

```ts
type User = { id: number; name: string };
type Post = { title: string; likes: number };

const wait = (ms: number) =>
  new Promise<void>((resolve) => setTimeout(resolve, ms));

async function getUser(id: number): Promise<User> {
  await wait(100);
  return { id, name: id === 1 ? "Mei" : "Sam" };
}

async function getPosts(userId: number): Promise<Post[]> {
  await wait(100);
  return [{ title: "Why pandas love bamboo", likes: 42 }];
}

async function getUnread(): Promise<number> {
  await wait(100);
  return 3;
}

// Three different types, loaded at the same time
const [user, posts, unread] = await Promise.all([
  getUser(1),
  getPosts(1),
  getUnread(),
]);
// user: User, posts: Post[], unread: number
console.log(`${user.name}: ${posts.length} post, ${unread} unread`);

// The same type many times: an array
const team = await Promise.all([1, 2].map((id) => getUser(id)));
console.log(team.map((u) => u.name)); // team: User[]
```

</CodeExample>

All three requests take 100 ms each, but together they take about 100 ms, not 300, because they run in parallel. If any one of them **rejects**, `Promise.all` rejects straight away and you lose the other results. That's often what you want ("no user, no page"), but not always.

## `Promise.allSettled`: narrowing each result

When some results are optional (a dashboard can show the weather even if the news failed), use **`Promise.allSettled`**. It never rejects; it gives back one result per promise. Each result has the type `PromiseSettledResult<T>`, which is a [discriminated union](/learn/typescript/discriminated-unions) on its `status` field:

- `{ status: "fulfilled"; value: T }`
- `{ status: "rejected"; reason: any }`

So you can't read `value` until you've checked `status`, exactly like any other tagged union:

```ts
const results = await Promise.allSettled([getUser(1)]);
console.log(results[0].value);
// ❌ Error: Property 'value' does not exist on type 'PromiseSettledResult<User>'.
```

Check the tag first, and TypeScript narrows each result:

<CodeExample output={`✅ Mei
❌ Error: User 99 not found
✅ Sam
2 of 3 loaded`}>

```ts
type User = { id: number; name: string };

const users: User[] = [
  { id: 1, name: "Mei" },
  { id: 2, name: "Sam" },
];

async function getUser(id: number): Promise<User> {
  const user = users.find((u) => u.id === id);
  if (!user) throw new Error(`User ${id} not found`);
  return user;
}

const results = await Promise.allSettled([
  getUser(1),
  getUser(99),
  getUser(2),
]);

for (const result of results) {
  if (result.status === "fulfilled") {
    console.log("✅", result.value.name); // value: User
  } else {
    console.log("❌", String(result.reason)); // reason: any
  }
}

const found = results
  .filter((r) => r.status === "fulfilled")
  .map((r) => r.value); // User[]
console.log(found.length, "of", results.length, "loaded");
```

</CodeExample>

The `filter` line works because TypeScript (since version 5.5) **infers a type predicate** from `r => r.status === "fulfilled"`, so the filtered array only holds fulfilled results. In older projects you'll see it written out: `(r): r is PromiseFulfilledResult<User> => r.status === "fulfilled"`.

## Callbacks vs promises

Before promises, async APIs took a **callback**, often in the "error first" style that Node made popular. You can type them, but look at how much the types **can't** tell you:

<CodeExample output={`dark 16
Error: No settings called "party"`}>

```ts
type Settings = { theme: "light" | "dark"; fontSize: number };
type Callback<T> = (error: Error | null, result?: T) => void;

// An old callback-style API (think of Node's fs functions)
function loadSettings(name: string, done: Callback<Settings>) {
  setTimeout(() => {
    if (name === "default") {
      done(null, { theme: "dark", fontSize: 16 });
    } else {
      done(new Error(`No settings called "${name}"`));
    }
  }, 50);
}

// The same thing as a promise
function loadSettingsAsync(name: string): Promise<Settings> {
  return new Promise((resolve, reject) => {
    loadSettings(name, (error, result) => {
      if (error) reject(error);
      else if (result) resolve(result);
    });
  });
}

const settings = await loadSettingsAsync("default");
console.log(settings.theme, settings.fontSize);

try {
  await loadSettingsAsync("party");
} catch (error) {
  console.log(String(error));
}
```

</CodeExample>

The `Callback<T>` type can't express "when `error` is `null`, `result` is definitely there", so we need the extra `else if (result)` check, and nothing stops a caller from ignoring `error` altogether. A `Promise<Settings>` says it all in one type: you either get `Settings`, or it rejects. That's why modern TypeScript code **wraps** callback APIs in promises once, at the edge (Node even ships promise versions, like `fs/promises`), and uses `async`/`await` everywhere else.

## Errors in `catch` are `unknown`

In JavaScript you can `throw` **anything**: an `Error`, a string, a number, an object. So what's the type of `error` in a `catch` block? TypeScript's honest answer, under `strict`, is **`unknown`** (the `useUnknownInCatchVariables` option, which `strict` turns on):

```ts
try {
  await saveGame();
} catch (error) {
  console.log(error.message);
  // ❌ Error: 'error' is of type 'unknown'.
}
```

You have to **narrow** it before using it, just like any other [`unknown` value](/learn/typescript/type-guards-and-unknown), usually with `instanceof Error`. Most projects write a tiny helper once and use it everywhere:

<CodeExample output={`Server is sleeping
a plain string
Something went wrong`}>

```ts
function errorMessage(error: unknown): string {
  if (error instanceof Error) return error.message;
  if (typeof error === "string") return error;
  return "Something went wrong";
}

const attempts: (() => Promise<void>)[] = [
  async () => {
    throw new Error("Server is sleeping");
  },
  async () => {
    throw "a plain string";
  },
  async () => {
    throw { code: 42 };
  },
];

for (const attempt of attempts) {
  try {
    await attempt();
  } catch (error) {
    // error: unknown
    console.log(errorMessage(error));
  }
}
```

</CodeExample>

<Callout type="warning" title="Promise rejections are still any">

There's one gap: the callback of a promise's `.catch((error) => ...)` and the `reason` of a rejected `allSettled` result are typed as **`any`**, for historical reasons. So `.catch((error) => console.log(error.mesage))` compiles, typo and all. Annotate it yourself: `.catch((error: unknown) => ...)`, and TypeScript makes you narrow it just like in a `catch` block.

</Callout>

## Cancelling with `AbortController`

Some work should be **cancelled**: the user left the page, or typed a new search. The standard tool is an **`AbortController`**: it has a `signal` (an `AbortSignal`) that you pass to the work, and an `abort()` method that fires it. `fetch` accepts a signal, and so can your own async functions. Make it an **optional parameter**, so callers who don't care can leave it out:

<CodeExample output={`Slept 50 ms
AbortError: woken up
TimeoutError: woken up`}>

```ts
function sleep(ms: number, signal?: AbortSignal): Promise<void> {
  return new Promise((resolve, reject) => {
    if (signal?.aborted) {
      reject(signal.reason); // cancelled before we even started
      return;
    }
    const timer = setTimeout(resolve, ms);
    signal?.addEventListener("abort", () => {
      clearTimeout(timer);
      reject(signal.reason); // reason: any
    });
  });
}

await sleep(50); // no signal: it just waits
console.log("Slept 50 ms");

// Cancel it yourself...
const controller = new AbortController();
setTimeout(() => controller.abort(), 100);
try {
  await sleep(2000, controller.signal);
} catch (error) {
  if (error instanceof Error) console.log(`${error.name}: woken up`);
}

// ...or let a timeout signal do it
try {
  await sleep(2000, AbortSignal.timeout(100));
} catch (error) {
  if (error instanceof Error) console.log(`${error.name}: woken up`);
}
```

</CodeExample>

`controller.abort()` rejects with an error named `AbortError`, and **`AbortSignal.timeout(ms)`** gives you a ready-made signal that aborts with a `TimeoutError`. Both are `DOMException`s, which are `Error`s, so `instanceof Error` narrows them. Check `error.name`, not the message: messages differ between browsers.

## A typed timeout helper

Not everything accepts a signal. To put a time limit on **any** promise, race it against a timer. This is a perfect job for a [generic function](/learn/typescript/generic-functions): whatever `T` goes in, the same `T` comes out:

<CodeExample output={`HI
Timed out after 100 ms`}>

```ts
class TimeoutError extends Error {
  constructor(ms: number) {
    super(`Timed out after ${ms} ms`);
    this.name = "TimeoutError";
  }
}

async function withTimeout<T>(
  promise: Promise<T>,
  ms: number,
): Promise<T> {
  let timer: ReturnType<typeof setTimeout> | undefined;
  // never resolves, only rejects: so its type is Promise<never>
  const timeout = new Promise<never>((_, reject) => {
    timer = setTimeout(() => reject(new TimeoutError(ms)), ms);
  });
  try {
    return await Promise.race([promise, timeout]);
  } finally {
    clearTimeout(timer); // don't leave the timer running
  }
}

const slowNumber = new Promise<number>((resolve) => {
  setTimeout(() => resolve(42), 500);
});

const fast = await withTimeout(Promise.resolve("hi"), 100);
console.log(fast.toUpperCase()); // fast: string

try {
  const n = await withTimeout(slowNumber, 100); // n: number
  console.log(n + 1);
} catch (error) {
  if (error instanceof TimeoutError) console.log(error.message);
}
```

</CodeExample>

Three details are worth stealing for your own code:

- **`Promise<never>`**: the timeout promise never resolves, so its value type is `never`. `Promise.race` of a `Promise<T>` and a `Promise<never>` is a `Promise<T>`, because `never` disappears from a union. No casts needed.
- **`ReturnType<typeof setTimeout>`**: `setTimeout` returns a `number` in browsers but a `Timeout` object in Node. This type works in both.
- **A custom error class** means callers can test `error instanceof TimeoutError` and react differently to a timeout than to other failures.

<Callout type="tip" title="In real projects">

Prefer passing an `AbortSignal` when the work supports it (like `fetch`): a timeout helper only stops **waiting**, while a signal actually **cancels** the request. Use `withTimeout` for things that can't be cancelled, and remember the slow work may still finish in the background.

</Callout>

## Recap

- `Promise<T>` is a value of type `T` that arrives later; `await` turns it into a `T`. Give `new Promise<T>` its type when TypeScript can't infer it.
- `async` functions return `Promise<...>`; write that return type on functions others call. Forgetting `await` becomes a type error instead of a runtime surprise.
- `Awaited<T>` unwraps promises, often as `Awaited<ReturnType<typeof fn>>`.
- `Promise.all` keeps each position's type (a tuple); `Promise.allSettled` gives a union you narrow on `status`.
- Wrap callback APIs in promises once, at the edge.
- `catch (error)` gives `unknown`: narrow with `instanceof Error` (or an `errorMessage` helper). Annotate `.catch((error: unknown) => ...)` yourself.
- Cancel with `AbortController` / `AbortSignal.timeout`, and limit any promise with a generic `withTimeout<T>` built on `Promise<never>`.
