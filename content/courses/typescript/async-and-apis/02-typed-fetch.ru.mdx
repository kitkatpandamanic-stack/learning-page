Почти любое приложение общается с API, и именно здесь гарантии TypeScript **слабее всего**: данные приходят извне программы, и компилятор их никогда не видел. В этом уроке вы найдёте дыру в типах `fetch`, увидите, почему популярное быстрое исправление — обман, и напишете помощники, которые честно говорят, что они знают, а что нет, — с типизированными ошибками и типизированными опциями запроса. 🌐

В PandaDev встроено учебное API (`https://api.pandadev.test`), поэтому примеры работают без интернета и всегда дают одинаковые ответы. Настоящие API работают так же.

## Что даёт `fetch`

`fetch(url)` отправляет HTTP-запрос и возвращает промис **ответа** (response); затем `res.json()` читает тело ответа как JSON (в уроке JavaScript [Основы fetch](/learn/javascript/fetch-basics) это разобрано по шагам). TypeScript знает все его типы: `fetch(url)` возвращает `Promise<Response>`, а у `Response` есть типизированные `status` (`number`), `ok` (`boolean`), `headers` и так далее. Но посмотрите, что даёт `res.json()`:

<CodeExample output={`200 true application/json; charset=utf-8
The Bamboo Heist
undefined`}>

```ts
const res = await fetch("https://api.pandadev.test/movies/1");
// res: Response
console.log(res.status, res.ok, res.headers.get("content-type"));

const movie = await res.json(); // movie: any
console.log(movie.title);
console.log(movie.titel); // опечатка, а TypeScript молчит
```

</CodeExample>

`res.json()` возвращает `Promise<any>`. Иначе и быть не может: TypeScript не знает, что пришлёт сервер. Но `any` **выключает** проверку типов, поэтому опечатка `titel` проскакивает, а `any` расползается: передайте `movie` в другие функции — и они тоже лишатся проверок.

## Почему `as Movie` — это обман

Быстрое исправление, которое встречается во многих проектах, — сказать TypeScript, что это за данные, через аннотацию или приведение `as`:

<CodeExample output={`{ error: 'Movie not found' }
Упало с ошибкой TypeError`}>

```ts
const API = "https://api.pandadev.test";

type Movie = {
  id: number;
  title: string;
  year: number;
  rating: number;
};

async function getMovie(id: number): Promise<Movie> {
  const res = await fetch(`${API}/movies/${id}`);
  return (await res.json()) as Movie; // «поверь мне»
}

const movie = await getMovie(99); // movie: Movie... правда?
console.log(movie);

try {
  console.log(movie.title.toUpperCase());
} catch (error) {
  if (error instanceof Error) {
    console.log("Упало с ошибкой", error.name);
  }
}
```

</CodeExample>

Теперь редактор автодополняет `movie.title`, и это **кажется** безопасным. Но `as Movie` ничего не проверяет: это обещание, которое компилятору даёте **вы**. Здесь сервер ответил 404 с `{ error: 'Movie not found' }`, и у нашего `Movie` вообще не оказалось `title`. Программа падает далеко от настоящей ошибки, а типы уверяли, что такого быть не может.

<Callout type="danger" title="Приведение типа переносит баг, а не исправляет его">

`as` (как и аннотация типа для данных типа `any`) уместно, когда вы **знаете** то, чего не знает TypeScript. С данными из сети, файла, `localStorage` или `JSON.parse` всё наоборот: вы их тоже не знаете. Серверы меняются, деплои ломаются, вместо JSON приходят страницы ошибок. Считайте внешние данные `unknown`, пока не проверили их.

</Callout>

Сохраните результат как `unknown` — и TypeScript заставит проверить его перед использованием:

```ts
const data: unknown = await res.json();
console.log(data.title);
// ❌ Error: 'data' is of type 'unknown'.
```

## Дженерик `getJson<T>` и его проблема с честностью

Раз каждый запрос повторяет одни и те же строки, хочется написать один дженерик-помощник:

<CodeExample output="undefined">

```ts
const API = "https://api.pandadev.test";

type Weather = { city: string; temperature: number };

async function getJson<T>(url: string): Promise<T> {
  const res = await fetch(url);
  return res.json(); // any молча становится T: никакой ошибки!
}

// Упс: не тот URL для этого типа. Но всё компилируется.
const weather = await getJson<Weather>(`${API}/movies/1`);
console.log(weather.temperature); // weather: Weather... правда?
```

</CodeExample>

Выглядит аккуратно, но это тот же обман в маскировке: `getJson<Weather>` — просто `as Weather` в более красивой обёртке. `T` выбирает **вызывающий код**, и никто его не проверяет. Хорошее правило: если параметр типа (type parameter) встречается только в **возвращаемом типе** функции, скорее всего, функция делает приведение.

Честная версия принимает **проверку** данных — здесь это [защитник типа](/learn/typescript/type-guards-and-unknown) (type guard), вроде тех, что вы писали на Уровне 1. Теперь `T` выводится из защитника, а данные действительно проверены до того, как функция их вернёт:

<CodeExample output={`Tokyo: 22°C
Неожиданные данные от https://api.pandadev.test/movies/1`}>

```ts
const API = "https://api.pandadev.test";

type Weather = { city: string; temperature: number };

function isWeather(data: unknown): data is Weather {
  return (
    typeof data === "object" &&
    data !== null &&
    "city" in data &&
    typeof data.city === "string" &&
    "temperature" in data &&
    typeof data.temperature === "number"
  );
}

async function getJson<T>(
  url: string,
  check: (data: unknown) => data is T,
): Promise<T> {
  const res = await fetch(url);
  const data: unknown = await res.json();
  if (!check(data)) {
    throw new Error(`Неожиданные данные от ${url}`);
  }
  return data; // data: T, это доказала проверка
}

// T выводится из защитника: weather имеет тип Weather
const weather = await getJson(`${API}/weather?city=Tokyo`, isWeather);
console.log(`${weather.city}: ${weather.temperature}°C`);

try {
  await getJson(`${API}/movies/1`, isWeather);
} catch (error) {
  if (error instanceof Error) console.log(error.message);
}
```

</CodeExample>

Теперь неправильный URL приводит к ошибке **на границе**, с понятным сообщением, а не к `undefined` где-то в глубине приложения. Правда, писать защитники вроде `isWeather` вручную для больших объектов утомительно. В следующем уроке вы замените их **схемами**, которые из одного описания дают и проверку, и тип.

<Callout type="tip" title="В реальных проектах: ts-reset">

Некоторые команды ставят [`@total-typescript/ts-reset`](https://github.com/total-typescript/ts-reset): эта библиотека меняет встроенные типы так, что `res.json()` и `JSON.parse` возвращают `unknown` вместо `any`. Тогда уже сам компилятор напоминает всем о валидации.

```ts
// reset.d.ts (после npm i -D @total-typescript/ts-reset)
import "@total-typescript/ts-reset";
```

</Callout>

## HTTP-ошибки: `res.ok` и типизированный класс ошибки

Помните, что `fetch` **отклоняется**, только если запрос вообще не удалось выполнить (нет сети, плохой URL, отмена). Ответ 404 или 500 — это всё равно **ответ**, поэтому промис выполняется:

<CodeExample output={`false 404 Not Found
{ error: 'Movie not found' }`}>

```ts
const res = await fetch("https://api.pandadev.test/movies/99");
console.log(res.ok, res.status, res.statusText);
console.log(await res.json());
```

</CodeExample>

Поэтому проверяйте `res.ok` сами. Если хотите, чтобы вызывающий код обрабатывал сбои через `try`/`catch`, бросайте **собственный класс ошибки**, который несёт подробности. Благодаря `instanceof` вызывающий код получает их полностью типизированными (конструктор использует **параметры-свойства** из урока [Классы и модификаторы доступа](/learn/typescript/classes-and-access-modifiers) — `readonly status: number`, — чтобы объявить и заполнить поля за один шаг):

<CodeExample output={`{ id: 4, title: 'Type my fetch calls', done: false }
400 title is required`}>

```ts
const API = "https://api.pandadev.test";

class HttpError extends Error {
  constructor(
    readonly status: number,
    readonly body: unknown,
  ) {
    super(apiMessage(body) ?? `HTTP ${status}`);
    this.name = "HttpError";
  }
}

// Большинство API объясняют ошибку в отдельном поле; здесь это "error"
function apiMessage(body: unknown): string | undefined {
  if (
    typeof body === "object" &&
    body !== null &&
    "error" in body &&
    typeof body.error === "string"
  ) {
    return body.error;
  }
  return undefined;
}

async function send(path: string, init?: RequestInit) {
  const res = await fetch(API + path, init);
  const body: unknown =
    res.status === 204 ? null : await res.json();
  if (!res.ok) throw new HttpError(res.status, body);
  return body;
}

type NewTodo = { title: string; done?: boolean };

async function createTodo(input: NewTodo): Promise<unknown> {
  return send("/todos", {
    method: "POST",
    headers: { "Content-Type": "application/json" },
    body: JSON.stringify(input),
  });
}

console.log(await createTodo({ title: "Type my fetch calls" }));

try {
  await createTodo({ title: "" });
} catch (error) {
  if (error instanceof HttpError) {
    console.log(error.status, error.message); // status: number
  }
}
```

</CodeExample>

На что стоит обратить внимание:

- **`RequestInit`** — встроенный тип объекта опций `fetch`, поэтому `send` принимает ровно то же, что и `fetch` (method, headers, body, signal…), с автодополнением.
- **`NewTodo`** описывает то, что мы *отправляем*: `createTodo({ titel: "x" })` — ошибка компиляции, так что плохие запросы ловятся ещё до того, как покинут ваш компьютер.
- `createTodo` честно возвращает `Promise<unknown>`: ответ мы ещё не проверили. (В следующем уроке это исправим как следует.)
- У ответа **204 No Content** нет тела, поэтому `res.json()` для него не вызываем.

## Ошибки как значения: тип `Result`

У бросания исключений есть слабость, знакомая по прошлому уроку: в `catch` ошибка имеет тип `unknown`, и ничто в типе функции не говорит, **что** она может бросить. Многие команды на TypeScript предпочитают **возвращать** сбои — в виде `Result`, дженерик-объединения из урока [Дженерик-типы и классы](/learn/typescript/generic-types-and-classes):

```ts
type Result<T, E> =
  | { ok: true; value: T }
  | { ok: false; error: E };
```

Теперь возможные сбои — часть типа функции, и вызывающий код **не может** добраться до значения без проверки:

```ts
const result: Result<number, string> = await getSomething();
console.log(result.value * 2);
// ❌ Error: Property 'value' does not exist on type 'Result<number, string>'.
```

Сделайте и саму ошибку размеченным объединением — и каждый вид сбоя сможет нести свои данные:

<CodeExample output={`Cairo: 31°C
Нет погоды для "Atlantis"
Сервер ответил 400`}>

```ts
const API = "https://api.pandadev.test";

type Result<T, E> =
  | { ok: true; value: T }
  | { ok: false; error: E };

type WeatherError =
  | { kind: "not-found"; city: string }
  | { kind: "http"; status: number }
  | { kind: "invalid" };

async function getTemperature(
  city: string,
): Promise<Result<number, WeatherError>> {
  const query = new URLSearchParams({ city });
  const res = await fetch(`${API}/weather?${query}`);
  if (res.status === 404) {
    return { ok: false, error: { kind: "not-found", city } };
  }
  if (!res.ok) {
    return { ok: false, error: { kind: "http", status: res.status } };
  }
  const data: unknown = await res.json();
  if (
    typeof data === "object" && data !== null &&
    "temperature" in data && typeof data.temperature === "number"
  ) {
    return { ok: true, value: data.temperature };
  }
  return { ok: false, error: { kind: "invalid" } };
}

for (const city of ["Cairo", "Atlantis", ""]) {
  const result = await getTemperature(city);
  if (result.ok) {
    console.log(`${city}: ${result.value}°C`); // value: number
    continue;
  }
  const error = result.error; // error: WeatherError
  switch (error.kind) {
    case "not-found":
      console.log(`Нет погоды для "${error.city}"`);
      break;
    case "http":
      console.log(`Сервер ответил ${error.status}`);
      break;
    case "invalid":
      console.log("Сервер прислал что-то странное");
      break;
  }
}
```

</CodeExample>

Что же выбрать? Зависит от ситуации, и в реальных проектах встречается и то и другое:

- **Бросайте исключения** для действительно неожиданных проблем и когда большинство вызывающих просто пропускает ошибки наверх, к одному обработчику (странице ошибки, middleware ошибок в Express). Так код «счастливого пути» остаётся коротким.
- **Возвращайте `Result`**, когда сбои **ожидаемы** и вызывающий код должен обрабатывать их по-разному: «не найдено» показывает сообщение, «нет сети» — кнопку повтора. Тогда компилятор следит, чтобы никто ничего не забыл, а при добавлении нового вида ошибки показывает каждый `switch`, который нужно обновить.

Что бы вы ни выбрали, будьте последовательны в пределах одного слоя приложения: если смешать оба подхода в одном API, каждому вызывающему придётся писать и `try`/`catch`, и `if (!result.ok)`.

## Параметры запроса из типизированных опций

Эндпоинты поиска принимают **параметры запроса** (query parameters), например `/movies?search=panda&limit=2`. Собирать такую строку вручную через `+` ненадёжно: забудьте закодировать `&` или пробел — и сервер получит другой вопрос. Опишите опции типом, а кодирование доверьте `URL` и `URLSearchParams`:

<CodeExample output={`https://api.pandadev.test/movies
https://api.pandadev.test/movies?search=bamboo+%26+tea&limit=2
https://api.pandadev.test/movies?genre=sci-fi&page=2
200 https://api.pandadev.test/movies?genre=comedy&limit=3`}>

```ts
const API = "https://api.pandadev.test";

type Genre = "action" | "comedy" | "drama" | "family" | "sci-fi";

type MovieSearch = {
  search?: string;
  genre?: Genre;
  page?: number;
  limit?: number;
};

function moviesUrl(options: MovieSearch = {}): string {
  const url = new URL("/movies", API);
  for (const [key, value] of Object.entries(options)) {
    if (value !== undefined) {
      url.searchParams.set(key, String(value));
    }
  }
  return url.toString();
}

console.log(moviesUrl());
console.log(moviesUrl({ search: "bamboo & tea", limit: 2 }));
console.log(moviesUrl({ genre: "sci-fi", page: 2, search: undefined }));

const res = await fetch(moviesUrl({ genre: "comedy", limit: 3 }));
console.log(res.status, res.url);
```

</CodeExample>

Именно в **объекте опций** TypeScript отрабатывает свой хлеб. Все опции необязательны, так что вызывающий код передаёт только нужное, в любом порядке, а ошибки ловятся прямо в месте вызова:

```ts
moviesUrl({ genre: "horror" });
// ❌ Error: Type '"horror"' is not assignable to type 'Genre | undefined'.
moviesUrl({ serch: "panda" });
// ❌ Error: Object literal may only specify known properties, but 'serch' does not exist in type 'MovieSearch'. Did you mean to write 'search'?
moviesUrl({ page: "2" });
// ❌ Error: Type 'string' is not assignable to type 'number'.
```

Обратите внимание на проверку `value !== undefined`: без неё `{ search: undefined }` отправил бы `search=undefined` — классический баг, при котором ищутся фильмы с названием «undefined».

Соберите слой запросов типизированного API-клиента. Он никогда не бросает исключений: любой исход превращается в `Result<unknown, ApiError>`. (В следующем уроке вы замените `unknown` на проверенные типы.)

1. `request(path, options)`:
   - отправляет `options.method` (по умолчанию `"GET"`); если есть `body`, отправляет его как JSON (заголовок `Content-Type` плюс `JSON.stringify`);
   - сдаётся через `options.timeoutMs` (по умолчанию `2000`) с помощью `AbortSignal.timeout`;
   - если `fetch` отклоняется: `TimeoutError` превращается в `{ kind: "timeout", ms }`, всё остальное — в `{ kind: "network", message }`;
   - читает тело (`null` для 204 или для тела, которое не является JSON); если `!res.ok`, возвращает `{ kind: "http", status, message }`, взяв сообщение из `apiMessage(body)`, а если его нет — `` `HTTP ${status}` ``;
   - иначе возвращает `{ ok: true, value: body }`.
2. `moviesPath(options)` возвращает `"/movies"` плюс закодированную строку запроса (query string), пропуская опции со значением `undefined` (без `?`, если опций нет).
3. TypeScript уже ругается на `describeError`: проверка через `never` нашла необработанный вид ошибки. Добавьте его, возвращая `` `Нет ответа за ${ms} мс.` ``.

<Hint>

Перехватывайте только вызов `fetch`: объявите `let res: Response;` перед `try { res = await fetch(API + path, init); } catch (error) { ... }`. Для тела: `res.status === 204 ? null : await res.json().catch(() => null)`. В `moviesPath` заполните `new URLSearchParams()` в цикле по `Object.entries(options)`, а затем используйте `params.toString()`.

```ts
const API = "https://api.pandadev.test";

type Result<T, E> =
  | { ok: true; value: T }
  | { ok: false; error: E };

type ApiError =
  | { kind: "network"; message: string }
  | { kind: "timeout"; ms: number }
  | { kind: "http"; status: number; message: string };

type RequestOptions = {
  method?: "GET" | "POST" | "PATCH" | "DELETE";
  body?: unknown;
  timeoutMs?: number;
};

// Готово к использованию: сообщение об ошибке от API, если оно есть
function apiMessage(body: unknown): string | undefined {
  if (
    typeof body === "object" &&
    body !== null &&
    "error" in body &&
    typeof body.error === "string"
  ) {
    return body.error;
  }
  return undefined;
}

async function request(
  path: string,
  options: RequestOptions = {},
): Promise<Result<unknown, ApiError>> {
  const { method = "GET", body, timeoutMs = 2000 } = options;
  const init: RequestInit = {
    method,
    signal: AbortSignal.timeout(timeoutMs),
  };
  if (body !== undefined) {
    init.headers = { "Content-Type": "application/json" };
    init.body = JSON.stringify(body);
  }

  let res: Response;
  try {
    res = await fetch(API + path, init);
  } catch (error) {
    if (error instanceof Error && error.name === "TimeoutError") {
      return { ok: false, error: { kind: "timeout", ms: timeoutMs } };
    }
    const message =
      error instanceof Error ? error.message : String(error);
    return { ok: false, error: { kind: "network", message } };
  }

  const data: unknown =
    res.status === 204 ? null : await res.json().catch(() => null);
  if (!res.ok) {
    const message = apiMessage(data) ?? `HTTP ${res.status}`;
    return {
      ok: false,
      error: { kind: "http", status: res.status, message },
    };
  }
  return { ok: true, value: data };
}

type MovieSearch = {
  search?: string;
  genre?: "action" | "comedy" | "drama" | "family" | "sci-fi";
  page?: number;
  limit?: number;
};

function moviesPath(options: MovieSearch = {}): string {
  const params = new URLSearchParams();
  for (const [key, value] of Object.entries(options)) {
    if (value !== undefined) params.set(key, String(value));
  }
  const query = params.toString();
  return query ? `/movies?${query}` : "/movies";
}

function describeError(error: ApiError): string {
  switch (error.kind) {
    case "network":
      return "Похоже, вы не в сети.";
    case "timeout":
      return `Нет ответа за ${error.ms} мс.`;
    case "http":
      return `Сервер ответил ${error.status}: ${error.message}`;
    default: {
      const unhandled: never = error;
      return unhandled;
    }
  }
}

// Пробуем
console.log(moviesPath({ search: "panda", limit: 2 }));
for (const path of ["/movies/2", "/movies/99", "/offline"]) {
  const result = await request(path);
  if (result.ok) console.log("OK:", result.value);
  else console.log(describeError(result.error));
}
const slow = await request("/delay/1500", { timeoutMs: 300 });
if (!slow.ok) console.log(describeError(slow.error));
```

## Итоги

- `fetch` возвращает `Promise<Response>`, но `res.json()` имеет тип `any` — дыра в типах ровно там, где в программу входят внешние данные.
- `as Movie` (или `getJson<T>`, у которого `T` есть только в возвращаемом типе) — это обещание компилятору, а не проверка. Держите внешние данные в `unknown`, пока не провалидируете их.
- Честный помощник принимает проверку (сейчас — защитник типа, в следующем уроке — схему) и выводит `T` из неё.
- `fetch` отклоняется, только когда ответ вообще не пришёл; HTTP-ошибки проверяйте через `res.ok`.
- Бросайте типизированный класс ошибки (`HttpError` со `status`) или возвращайте `Result<T, E>` с размеченным объединением ошибок, чтобы вызывающий код был обязан обработать каждый сбой.
- Описывайте опции запроса типом с необязательными свойствами и собирайте URL через `URL`/`URLSearchParams`, пропуская `undefined`.
