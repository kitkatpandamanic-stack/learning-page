Настоящие приложения большую часть времени **ждут**: сервера, базы данных, таймера. По ходу урока мы повторим, как работают промисы и `async`/`await` (если хотите размяться, в уроках JavaScript про [промисы](/learn/javascript/promises) и [async/await](/learn/javascript/async-await) всё разобрано по шагам). Но главное здесь — что добавляет TypeScript: он следит, что **в итоге** окажется в каждом промисе, ловит классическую ошибку «забыл `await`» ещё до релиза и заставляет честно обрабатывать ошибки, которые могут оказаться чем угодно. ⏳

## `Promise<T>`: значение, которое придёт позже

Промис (promise) — это коробка, в которой значение появится **позже**. Его тип говорит, что будет внутри: `Promise<number>` даст вам `number`, а `Promise<void>` не даст ничего полезного (он просто сообщает, что что-то закончилось). Когда вы пишете `await` перед `Promise<T>`, вы получаете обычный `T`:

<CodeExample output={`Бросаем кубик...
Выпало 4
Вдвое больше: 8`}>

```ts
function wait(ms: number): Promise<void> {
  return new Promise((resolve) => setTimeout(resolve, ms));
}

function rollDice(): Promise<number> {
  return new Promise((resolve) => {
    setTimeout(() => resolve(4), 50);
  });
}

console.log("Бросаем кубик...");
await wait(100);
const roll = await rollDice(); // roll: number
console.log(`Выпало ${roll}`);
console.log(`Вдвое больше: ${roll * 2}`);
```

</CodeExample>

`new Promise(...)` передаёт вашей функции колбэк `resolve`: вызов `resolve(value)` наполняет коробку, и все, кто её ждёт, продолжают работу. Заметьте: мы нигде не сказали `new Promise(...)`, что в нём лежит, — TypeScript понял это из типа возвращаемого значения функции. Без такой подсказки он узнать не может и откатывается к `unknown`. Укажите тип сами — `new Promise<number>(...)`, — и TypeScript заодно проверит, с чем вы вызываете `resolve`:

```ts
const answer = new Promise((resolve) => resolve(42));
const value: number = await answer;
// ❌ Error: Type 'unknown' is not assignable to type 'number'.

const typed = new Promise<number>((resolve) => resolve("42"));
// ❌ Error: Argument of type 'string' is not assignable to parameter of type 'number | PromiseLike<number>'.
```

## Async-функции возвращают промисы

`async`-функция **всегда** возвращает промис, даже если внутри вы возвращаете обычное значение. Поэтому её возвращаемый тип — `Promise<...>` от того, что стоит в `return`:

<CodeExample output={`Mei
никого`}>

```ts
type User = { id: number; name: string };

const users: User[] = [
  { id: 1, name: "Mei" },
  { id: 2, name: "Sam" },
];

const wait = (ms: number) =>
  new Promise<void>((resolve) => setTimeout(resolve, ms));

async function findUser(id: number): Promise<User | undefined> {
  await wait(50); // представим, что это база данных
  return users.find((user) => user.id === id);
}

const mei = await findUser(1);
console.log(mei?.name ?? "никого");

const ghost = await findUser(99);
console.log(ghost?.name ?? "никого");
```

</CodeExample>

TypeScript и сам вывел бы `Promise<User | undefined>`, но в реальных проектах принято **явно писать возвращаемый тип** async-функций, которые вызывает другой код. Он документирует контракт («может никого не найти»), а если вы по ошибке измените тело, ошибка появится внутри функции, а не в десяти местах вызова. Если написать тип без `Promise`, TypeScript прямо подскажет, что делать:

```ts
async function countUsers(): number {
  // ❌ Error: The return type of an async function or method must be the global Promise<T> type. Did you mean to write 'Promise<number>'?
  return users.length;
}
```

### Забытый `await`

Самая частая асинхронная ошибка — забыть `await`. В JavaScript вы получите `undefined` или загадочный `[object Promise]` во время выполнения. В TypeScript — ошибку компиляции, потому что `Promise<User>` — это не `User`:

```ts
async function getUser(id: number): Promise<User> {
  // ...
}

const user = getUser(1); // забыли await: user — это Promise<User>
console.log(user.name);
// ❌ Error: Property 'name' does not exist on type 'Promise<User>'.

async function isAdmin(): Promise<boolean> {
  // ...
}

if (isAdmin()) {
  // ❌ Error: This condition will always return true since this 'Promise<boolean>' is always defined.
}
```

Вторая ошибка в обычном JavaScript особенно коварна: объект промиса всегда истинный, так что админом оказался бы **каждый**. В редакторе к обеим ошибкам даже прилагается подсказка: «Did you forget to use 'await'?» («Вы не забыли `await`?»).

## `Awaited<T>`: что лежит в коробке

Иногда нужен тип, которым промис **выполнится**, — например, результат функции, которую писали не вы. Оба инструмента вы встречали в уроке [Утилитные типы](/learn/typescript/utility-types): `ReturnType` даёт сам промис, а **`Awaited<T>`** разворачивает его слой за слоем — ровно так же, как это делает `await`:

<CodeExample output={`У Mei 120 подписчиков
Awaited разворачивает все слои`}>

```ts
async function loadProfile(id: number) {
  return { id, name: "Mei", followers: 120 };
}

// ReturnType даёт промис, Awaited его разворачивает
type Pending = ReturnType<typeof loadProfile>;
type Profile = Awaited<ReturnType<typeof loadProfile>>;

function greet(profile: Profile): string {
  return `У ${profile.name} ${profile.followers} подписчиков`;
}

const pending: Pending = loadProfile(1);
console.log(greet(await pending));

type Deep = Awaited<Promise<Promise<string>>>; // string
const text: Deep = "Awaited разворачивает все слои";
console.log(text);
```

</CodeExample>

`Awaited<ReturnType<typeof fn>>` — шаблон, который часто встречается в реальном коде, особенно для функций из библиотек, чьи типы результатов не экспортируются.

## `Promise.all` с типизированными результатами

`Promise.all` запускает несколько промисов **одновременно** и ждёт их все. Передайте ему массив **разных** промисов — и TypeScript будет считать его **кортежем** (tuple): каждая позиция сохраняет свой тип, так что после деструктуризации вы получаете идеально типизированные переменные:

<CodeExample output={`Mei: постов — 1, непрочитанных — 3
[ 'Mei', 'Sam' ]`}>

```ts
type User = { id: number; name: string };
type Post = { title: string; likes: number };

const wait = (ms: number) =>
  new Promise<void>((resolve) => setTimeout(resolve, ms));

async function getUser(id: number): Promise<User> {
  await wait(100);
  return { id, name: id === 1 ? "Mei" : "Sam" };
}

async function getPosts(userId: number): Promise<Post[]> {
  await wait(100);
  return [{ title: "Почему панды любят бамбук", likes: 42 }];
}

async function getUnread(): Promise<number> {
  await wait(100);
  return 3;
}

// Три разных типа, загружаются одновременно
const [user, posts, unread] = await Promise.all([
  getUser(1),
  getPosts(1),
  getUnread(),
]);
// user: User, posts: Post[], unread: number
console.log(
  `${user.name}: постов — ${posts.length}, непрочитанных — ${unread}`,
);

// Один и тот же тип много раз: массив
const team = await Promise.all([1, 2].map((id) => getUser(id)));
console.log(team.map((u) => u.name)); // team: User[]
```

</CodeExample>

Каждый из трёх запросов занимает 100 мс, но вместе они занимают около 100 мс, а не 300, потому что выполняются параллельно. Если хотя бы один из них **отклоняется** (rejects), `Promise.all` сразу отклоняется тоже, и остальные результаты теряются. Часто именно это и нужно («нет пользователя — нет страницы»), но не всегда.

## `Promise.allSettled`: сужаем каждый результат

Когда часть результатов необязательна (дашборд может показать погоду, даже если новости не загрузились), используйте **`Promise.allSettled`**. Он никогда не отклоняется и возвращает по одному результату на каждый промис. Каждый результат имеет тип `PromiseSettledResult<T>` — это [размеченное объединение](/learn/typescript/discriminated-unions) по полю `status`:

- `{ status: "fulfilled"; value: T }`
- `{ status: "rejected"; reason: any }`

Поэтому читать `value`, пока вы не проверили `status`, нельзя — как и в любом другом размеченном объединении:

```ts
const results = await Promise.allSettled([getUser(1)]);
console.log(results[0].value);
// ❌ Error: Property 'value' does not exist on type 'PromiseSettledResult<User>'.
```

Сначала проверьте метку — и TypeScript сузит тип каждого результата:

<CodeExample output={`✅ Mei
❌ Error: User 99 not found
✅ Sam
загружено 2 из 3`}>

```ts
type User = { id: number; name: string };

const users: User[] = [
  { id: 1, name: "Mei" },
  { id: 2, name: "Sam" },
];

async function getUser(id: number): Promise<User> {
  const user = users.find((u) => u.id === id);
  if (!user) throw new Error(`User ${id} not found`);
  return user;
}

const results = await Promise.allSettled([
  getUser(1),
  getUser(99),
  getUser(2),
]);

for (const result of results) {
  if (result.status === "fulfilled") {
    console.log("✅", result.value.name); // value: User
  } else {
    console.log("❌", String(result.reason)); // reason: any
  }
}

const found = results
  .filter((r) => r.status === "fulfilled")
  .map((r) => r.value); // User[]
console.log("загружено", found.length, "из", results.length);
```

</CodeExample>

Строка с `filter` работает, потому что TypeScript (начиная с версии 5.5) **выводит предикат типа** (type predicate) из `r => r.status === "fulfilled"`, и в отфильтрованном массиве остаются только выполненные результаты. В старых проектах вы увидите его написанным вручную: `(r): r is PromiseFulfilledResult<User> => r.status === "fulfilled"`.

## Колбэки против промисов

До появления промисов асинхронные API принимали **колбэк** (callback), часто в стиле «сначала ошибка», который популяризировал Node. Их можно типизировать, но посмотрите, сколького типы сказать **не могут**:

<CodeExample output={`dark 16
Error: Нет настроек с именем "party"`}>

```ts
type Settings = { theme: "light" | "dark"; fontSize: number };
type Callback<T> = (error: Error | null, result?: T) => void;

// Старое API на колбэках (вспомните функции fs в Node)
function loadSettings(name: string, done: Callback<Settings>) {
  setTimeout(() => {
    if (name === "default") {
      done(null, { theme: "dark", fontSize: 16 });
    } else {
      done(new Error(`Нет настроек с именем "${name}"`));
    }
  }, 50);
}

// То же самое в виде промиса
function loadSettingsAsync(name: string): Promise<Settings> {
  return new Promise((resolve, reject) => {
    loadSettings(name, (error, result) => {
      if (error) reject(error);
      else if (result) resolve(result);
    });
  });
}

const settings = await loadSettingsAsync("default");
console.log(settings.theme, settings.fontSize);

try {
  await loadSettingsAsync("party");
} catch (error) {
  console.log(String(error));
}
```

</CodeExample>

Тип `Callback<T>` не может выразить «когда `error` равно `null`, `result` точно есть», поэтому нужна лишняя проверка `else if (result)`, и ничто не мешает вызывающему коду вообще проигнорировать `error`. А `Promise<Settings>` говорит всё одним типом: либо вы получите `Settings`, либо промис отклонится. Поэтому современный код на TypeScript **оборачивает** API на колбэках в промисы один раз, на границе (Node даже поставляет промис-версии, например `fs/promises`), а везде дальше использует `async`/`await`.

## Ошибки в `catch` имеют тип `unknown`

В JavaScript можно бросить (`throw`) **что угодно**: `Error`, строку, число, объект. Какой же тогда тип у `error` в блоке `catch`? Честный ответ TypeScript в режиме `strict` — **`unknown`** (это опция `useUnknownInCatchVariables`, которую включает `strict`):

```ts
try {
  await saveGame();
} catch (error) {
  console.log(error.message);
  // ❌ Error: 'error' is of type 'unknown'.
}
```

Перед использованием его нужно **сузить** (narrowing), как и любое другое [значение типа `unknown`](/learn/typescript/type-guards-and-unknown), — обычно через `instanceof Error`. В большинстве проектов один раз пишут крошечную вспомогательную функцию и используют её везде:

<CodeExample output={`Server is sleeping
просто строка
Что-то пошло не так`}>

```ts
function errorMessage(error: unknown): string {
  if (error instanceof Error) return error.message;
  if (typeof error === "string") return error;
  return "Что-то пошло не так";
}

const attempts: (() => Promise<void>)[] = [
  async () => {
    throw new Error("Server is sleeping");
  },
  async () => {
    throw "просто строка";
  },
  async () => {
    throw { code: 42 };
  },
];

for (const attempt of attempts) {
  try {
    await attempt();
  } catch (error) {
    // error: unknown
    console.log(errorMessage(error));
  }
}
```

</CodeExample>

<Callout type="warning" title="Отклонения промисов всё ещё any">

Есть одна дыра: параметр колбэка в `.catch((error) => ...)` у промиса и `reason` у отклонённого результата `allSettled` по историческим причинам имеют тип **`any`**. Поэтому `.catch((error) => console.log(error.mesage))` компилируется — вместе с опечаткой. Указывайте тип сами: `.catch((error: unknown) => ...)`, и TypeScript заставит сузить его так же, как в блоке `catch`.

</Callout>

## Отмена через `AbortController`

Некоторую работу нужно **отменять**: пользователь ушёл со страницы или ввёл новый поисковый запрос. Стандартный инструмент для этого — **`AbortController`**: у него есть `signal` (объект `AbortSignal`), который вы передаёте в работу, и метод `abort()`, который этот сигнал подаёт. `fetch` принимает сигнал, и ваши собственные async-функции тоже могут. Сделайте его **необязательным параметром**, чтобы вызывающий код, которому отмена не нужна, мог его не передавать:

<CodeExample output={`Поспали 50 мс
AbortError: разбудили
TimeoutError: разбудили`}>

```ts
function sleep(ms: number, signal?: AbortSignal): Promise<void> {
  return new Promise((resolve, reject) => {
    if (signal?.aborted) {
      reject(signal.reason); // отменили ещё до старта
      return;
    }
    const timer = setTimeout(resolve, ms);
    signal?.addEventListener("abort", () => {
      clearTimeout(timer);
      reject(signal.reason); // reason: any
    });
  });
}

await sleep(50); // без сигнала: просто ждёт
console.log("Поспали 50 мс");

// Отменяем сами...
const controller = new AbortController();
setTimeout(() => controller.abort(), 100);
try {
  await sleep(2000, controller.signal);
} catch (error) {
  if (error instanceof Error) console.log(`${error.name}: разбудили`);
}

// ...или пусть это сделает сигнал с тайм-аутом
try {
  await sleep(2000, AbortSignal.timeout(100));
} catch (error) {
  if (error instanceof Error) console.log(`${error.name}: разбудили`);
}
```

</CodeExample>

`controller.abort()` отклоняет промис ошибкой с именем `AbortError`, а **`AbortSignal.timeout(ms)`** даёт готовый сигнал, который срабатывает с ошибкой `TimeoutError`. Обе — это `DOMException`, а `DOMException` — это `Error`, так что `instanceof Error` их сужает. Проверяйте `error.name`, а не текст сообщения: сообщения в разных браузерах разные.

## Типизированный помощник для тайм-аута

Не всё умеет принимать сигнал. Чтобы ограничить по времени **любой** промис, устройте ему гонку с таймером. Это идеальная задача для [дженерик-функции](/learn/typescript/generic-functions): какой `T` вошёл, такой `T` и вышел:

<CodeExample output={`HI
Timed out after 100 ms`}>

```ts
class TimeoutError extends Error {
  constructor(ms: number) {
    super(`Timed out after ${ms} ms`);
    this.name = "TimeoutError";
  }
}

async function withTimeout<T>(
  promise: Promise<T>,
  ms: number,
): Promise<T> {
  let timer: ReturnType<typeof setTimeout> | undefined;
  // никогда не выполняется, только отклоняется: тип Promise<never>
  const timeout = new Promise<never>((_, reject) => {
    timer = setTimeout(() => reject(new TimeoutError(ms)), ms);
  });
  try {
    return await Promise.race([promise, timeout]);
  } finally {
    clearTimeout(timer); // не оставляем таймер работать
  }
}

const slowNumber = new Promise<number>((resolve) => {
  setTimeout(() => resolve(42), 500);
});

const fast = await withTimeout(Promise.resolve("hi"), 100);
console.log(fast.toUpperCase()); // fast: string

try {
  const n = await withTimeout(slowNumber, 100); // n: number
  console.log(n + 1);
} catch (error) {
  if (error instanceof TimeoutError) console.log(error.message);
}
```

</CodeExample>

Три детали стоит утащить в свой код:

- **`Promise<never>`**: промис тайм-аута никогда не выполняется, поэтому тип его значения — `never`. `Promise.race` от `Promise<T>` и `Promise<never>` — это `Promise<T>`, потому что `never` исчезает из объединения. Никаких приведений типов не нужно.
- **`ReturnType<typeof setTimeout>`**: в браузерах `setTimeout` возвращает `number`, а в Node — объект `Timeout`. Этот тип подходит для обоих случаев.
- **Собственный класс ошибки** позволяет вызывающему коду проверить `error instanceof TimeoutError` и реагировать на тайм-аут иначе, чем на другие сбои.

<Callout type="tip" title="В реальных проектах">

Если работа поддерживает `AbortSignal` (как `fetch`), лучше передавайте сигнал: помощник с тайм-аутом лишь перестаёт **ждать**, а сигнал действительно **отменяет** запрос. Используйте `withTimeout` для того, что отменить нельзя, и помните, что медленная работа может всё равно завершиться в фоне.

</Callout>

type User = { id: number; name: string };
type Weather = { city: string; temperature: number };

// Ненастоящие сервисы (их не меняйте)
const wait = (ms: number) =>
  new Promise<void>((resolve) => setTimeout(resolve, ms));

async function getUser(id: number): Promise<User> {
  await wait(150);
  if (id !== 1) throw new Error(`User ${id} not found`);
  return { id, name: "Mei" };
}

async function getWeather(city: string): Promise<Weather> {
  await wait(city === "Atlantis" ? 1000 : 150);
  return { city, temperature: 14 };
}

class TimeoutError extends Error {
  constructor(ms: number) {
    super(`Timed out after ${ms} ms`);
    this.name = "TimeoutError";
  }
}

async function withTimeout<T>(
  promise: Promise<T>,
  ms: number,
): Promise<T> {
  let timer: ReturnType<typeof setTimeout> | undefined;
  const timeout = new Promise<never>((_, reject) => {
    timer = setTimeout(() => reject(new TimeoutError(ms)), ms);
  });
  try {
    return await Promise.race([promise, timeout]);
  } finally {
    clearTimeout(timer);
  }
}

function errorMessage(error: unknown): string {
  if (error instanceof Error) return error.message;
  if (typeof error === "string") return error;
  return "Что-то пошло не так";
}

type Dashboard = {
  user: User | null;
  weather: Weather | null;
  errors: string[];
};

async function loadDashboard(
  userId: number,
  city: string,
): Promise<Dashboard> {
  const [user, weather] = await Promise.allSettled([
    withTimeout(getUser(userId), 200),
    withTimeout(getWeather(city), 200),
  ]);
  const errors: string[] = [];
  if (user.status === "rejected") {
    errors.push(errorMessage(user.reason));
  }
  if (weather.status === "rejected") {
    errors.push(errorMessage(weather.reason));
  }
  return {
    user: user.status === "fulfilled" ? user.value : null,
    weather: weather.status === "fulfilled" ? weather.value : null,
    errors,
  };
}

console.log(await loadDashboard(1, "London"));
console.log(await loadDashboard(99, "Atlantis"));

  // @ts-expect-error: withTimeout сохраняет тип промиса
  const s: Promise<string> = withTimeout(Promise.resolve(1), 10);
}

## Итоги

- `Promise<T>` — это значение типа `T`, которое придёт позже; `await` превращает его в `T`. Указывайте тип `new Promise<T>`, когда TypeScript не может его вывести.
- `async`-функции возвращают `Promise<...>`; пишите этот возвращаемый тип у функций, которые вызывает другой код. Забытый `await` становится ошибкой типов, а не сюрпризом во время выполнения.
- `Awaited<T>` разворачивает промисы, часто в виде `Awaited<ReturnType<typeof fn>>`.
- `Promise.all` сохраняет тип каждой позиции (кортеж); `Promise.allSettled` даёт объединение, которое вы сужаете по `status`.
- Оборачивайте API на колбэках в промисы один раз, на границе.
- `catch (error)` даёт `unknown`: сужайте через `instanceof Error` (или вспомогательную функцию `errorMessage`). В `.catch((error: unknown) => ...)` указывайте тип сами.
- Отменяйте работу через `AbortController` / `AbortSignal.timeout`, а любой промис ограничивайте по времени дженерик-функцией `withTimeout<T>` на основе `Promise<never>`.
