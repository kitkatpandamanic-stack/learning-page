Almost every app talks to an API, and that's exactly where TypeScript's guarantees are **weakest**: the data comes from outside your program, and the compiler has never seen it. In this lesson you'll find the hole in `fetch`'s types, see why the popular quick fix is a lie, and build helpers that are honest about what they know, with typed errors and typed query options. 🌐

PandaDev has a practice API built in (`https://api.pandadev.test`), so these examples work offline and always give the same answers. Real APIs work the same way.

## What `fetch` gives you

`fetch(url)` sends an HTTP request and gives you a promise of the **response**; `res.json()` then reads the response body as JSON (the JavaScript lesson [Fetch Basics](/learn/javascript/fetch-basics) covers it step by step). TypeScript knows all of its types: `fetch(url)` returns a `Promise<Response>`, and a `Response` has a typed `status` (`number`), `ok` (`boolean`), `headers` and so on. But look at what `res.json()` gives you:

<CodeExample output={`200 true application/json; charset=utf-8
The Bamboo Heist
undefined`}>

```ts
const res = await fetch("https://api.pandadev.test/movies/1");
// res: Response
console.log(res.status, res.ok, res.headers.get("content-type"));

const movie = await res.json(); // movie: any
console.log(movie.title);
console.log(movie.titel); // a typo, and TypeScript says nothing
```

</CodeExample>

`res.json()` returns `Promise<any>`. It has to: TypeScript can't know what a server will send. But `any` switches type checking **off**, so the typo `titel` sails through, and `any` spreads: pass `movie` to other functions and they lose their checks too.

## Why `as Movie` is a lie

The quick fix you'll see in many codebases is to tell TypeScript what the data is, with an annotation or an `as` cast:

<CodeExample output={`{ error: 'Movie not found' }
Crashed with a TypeError`}>

```ts
const API = "https://api.pandadev.test";

type Movie = {
  id: number;
  title: string;
  year: number;
  rating: number;
};

async function getMovie(id: number): Promise<Movie> {
  const res = await fetch(`${API}/movies/${id}`);
  return (await res.json()) as Movie; // "trust me"
}

const movie = await getMovie(99); // movie: Movie... really?
console.log(movie);

try {
  console.log(movie.title.toUpperCase());
} catch (error) {
  if (error instanceof Error) console.log("Crashed with a", error.name);
}
```

</CodeExample>

The editor now autocompletes `movie.title`, which **feels** safe. But `as Movie` checks nothing; it's a promise **you** make to the compiler. Here the server answered 404 with `{ error: 'Movie not found' }`, and our `Movie` had no `title` at all. The crash happens far away from the real mistake, and the types told us it couldn't happen.

<Callout type="danger" title="A cast moves the bug, it doesn't fix it">

`as` (and annotating `any` data with a type) is fine when you **know** something TypeScript doesn't. Data from a network, a file, `localStorage` or `JSON.parse` is the opposite: you don't know it either. Servers change, deploys go wrong, error pages come back instead of JSON. Treat outside data as `unknown` until you've checked it.

</Callout>

Store the result as `unknown` instead, and TypeScript makes you check before you use it:

```ts
const data: unknown = await res.json();
console.log(data.title);
// ❌ Error: 'data' is of type 'unknown'.
```

## A generic `getJson<T>` and its honesty problem

Since every request repeats the same lines, it's tempting to write one generic helper:

<CodeExample output="undefined">

```ts
const API = "https://api.pandadev.test";

type Weather = { city: string; temperature: number };

async function getJson<T>(url: string): Promise<T> {
  const res = await fetch(url);
  return res.json(); // any quietly becomes T: no error!
}

// Oops: the wrong URL for this type. It still compiles.
const weather = await getJson<Weather>(`${API}/movies/1`);
console.log(weather.temperature); // weather: Weather... really?
```

</CodeExample>

It looks clean, but it's the same lie wearing a disguise: `getJson<Weather>` is just `as Weather` in a nicer shape. The **caller** picks `T`, and nothing ever checks it. A good rule: if a type parameter only appears in the **return type** of a function, the function is probably casting.

The honest version takes a **check** for the data, here a [type guard](/learn/typescript/type-guards-and-unknown) like the ones you wrote in Level 1. Now `T` is inferred from the guard, and the data really is proven before it's returned:

<CodeExample output={`Tokyo: 22°C
Unexpected data from https://api.pandadev.test/movies/1`}>

```ts
const API = "https://api.pandadev.test";

type Weather = { city: string; temperature: number };

function isWeather(data: unknown): data is Weather {
  return (
    typeof data === "object" &&
    data !== null &&
    "city" in data &&
    typeof data.city === "string" &&
    "temperature" in data &&
    typeof data.temperature === "number"
  );
}

async function getJson<T>(
  url: string,
  check: (data: unknown) => data is T,
): Promise<T> {
  const res = await fetch(url);
  const data: unknown = await res.json();
  if (!check(data)) {
    throw new Error(`Unexpected data from ${url}`);
  }
  return data; // data: T, proven by the check
}

// T is inferred from the guard: weather is Weather
const weather = await getJson(`${API}/weather?city=Tokyo`, isWeather);
console.log(`${weather.city}: ${weather.temperature}°C`);

try {
  await getJson(`${API}/movies/1`, isWeather);
} catch (error) {
  if (error instanceof Error) console.log(error.message);
}
```

</CodeExample>

The wrong URL now fails **at the edge**, with a clear message, instead of as `undefined` deep inside your app. Writing guards like `isWeather` by hand gets tiring for big objects, though. In the next lesson you'll replace them with **schemas** that produce the check and the type from one definition.

<Callout type="tip" title="In real projects: ts-reset">

Some teams install [`@total-typescript/ts-reset`](https://github.com/total-typescript/ts-reset), which changes the built-in types so `res.json()` and `JSON.parse` return `unknown` instead of `any`. Then the compiler itself reminds everyone to validate.

```ts
// reset.d.ts (after npm i -D @total-typescript/ts-reset)
import "@total-typescript/ts-reset";
```

</Callout>

## HTTP errors: `res.ok` and a typed error class

Remember that `fetch` only **rejects** when the request couldn't be made at all (no network, a bad URL, an abort). A 404 or 500 is still a **response**, so the promise resolves:

<CodeExample output={`false 404 Not Found
{ error: 'Movie not found' }`}>

```ts
const res = await fetch("https://api.pandadev.test/movies/99");
console.log(res.ok, res.status, res.statusText);
console.log(await res.json());
```

</CodeExample>

So check `res.ok` yourself. If you want callers to handle failures with `try`/`catch`, throw a **custom error class** that carries the details. Thanks to `instanceof`, callers get those details fully typed (the constructor uses **parameter properties** from [Classes & Access Modifiers](/learn/typescript/classes-and-access-modifiers), `readonly status: number`, to declare and set fields in one go):

<CodeExample output={`{ id: 4, title: 'Type my fetch calls', done: false }
400 title is required`}>

```ts
const API = "https://api.pandadev.test";

class HttpError extends Error {
  constructor(
    readonly status: number,
    readonly body: unknown,
  ) {
    super(apiMessage(body) ?? `HTTP ${status}`);
    this.name = "HttpError";
  }
}

// Most APIs explain errors in a field; this one calls it "error"
function apiMessage(body: unknown): string | undefined {
  if (
    typeof body === "object" &&
    body !== null &&
    "error" in body &&
    typeof body.error === "string"
  ) {
    return body.error;
  }
  return undefined;
}

async function send(path: string, init?: RequestInit) {
  const res = await fetch(API + path, init);
  const body: unknown =
    res.status === 204 ? null : await res.json();
  if (!res.ok) throw new HttpError(res.status, body);
  return body;
}

type NewTodo = { title: string; done?: boolean };

async function createTodo(input: NewTodo): Promise<unknown> {
  return send("/todos", {
    method: "POST",
    headers: { "Content-Type": "application/json" },
    body: JSON.stringify(input),
  });
}

console.log(await createTodo({ title: "Type my fetch calls" }));

try {
  await createTodo({ title: "" });
} catch (error) {
  if (error instanceof HttpError) {
    console.log(error.status, error.message); // status: number
  }
}
```

</CodeExample>

A few things to notice:

- **`RequestInit`** is the built-in type of `fetch`'s options object, so `send` accepts exactly what `fetch` does (method, headers, body, signal…), with autocomplete.
- **`NewTodo`** types what we *send*: `createTodo({ titel: "x" })` would be a compile error, so bad requests are caught before they leave your machine.
- `createTodo` honestly returns `Promise<unknown>`: we haven't checked the answer yet. (The next lesson fixes that properly.)
- **204 No Content** has no body, so we don't call `res.json()` on it.

## Errors as values: a `Result` type

Throwing has a weakness you met in the last lesson: in `catch`, the error is `unknown`, and nothing in a function's type says **what** it can throw. Many TypeScript teams prefer to **return** failures instead, as a `Result`, the generic discriminated union from [Generic Types and Classes](/learn/typescript/generic-types-and-classes):

```ts
type Result<T, E> =
  | { ok: true; value: T }
  | { ok: false; error: E };
```

Now the possible failures are part of the function's type, and the caller **can't** reach the value without checking:

```ts
const result: Result<number, string> = await getSomething();
console.log(result.value * 2);
// ❌ Error: Property 'value' does not exist on type 'Result<number, string>'.
```

Make the error a discriminated union too, and every kind of failure can carry its own data:

<CodeExample output={`Cairo: 31°C
No weather for "Atlantis"
The server said 400`}>

```ts
const API = "https://api.pandadev.test";

type Result<T, E> =
  | { ok: true; value: T }
  | { ok: false; error: E };

type WeatherError =
  | { kind: "not-found"; city: string }
  | { kind: "http"; status: number }
  | { kind: "invalid" };

async function getTemperature(
  city: string,
): Promise<Result<number, WeatherError>> {
  const query = new URLSearchParams({ city });
  const res = await fetch(`${API}/weather?${query}`);
  if (res.status === 404) {
    return { ok: false, error: { kind: "not-found", city } };
  }
  if (!res.ok) {
    return { ok: false, error: { kind: "http", status: res.status } };
  }
  const data: unknown = await res.json();
  if (
    typeof data === "object" && data !== null &&
    "temperature" in data && typeof data.temperature === "number"
  ) {
    return { ok: true, value: data.temperature };
  }
  return { ok: false, error: { kind: "invalid" } };
}

for (const city of ["Cairo", "Atlantis", ""]) {
  const result = await getTemperature(city);
  if (result.ok) {
    console.log(`${city}: ${result.value}°C`); // value: number
    continue;
  }
  const error = result.error; // error: WeatherError
  switch (error.kind) {
    case "not-found":
      console.log(`No weather for "${error.city}"`);
      break;
    case "http":
      console.log(`The server said ${error.status}`);
      break;
    case "invalid":
      console.log("The server sent something odd");
      break;
  }
}
```

</CodeExample>

Which should you use? It depends, and both are common in real projects:

- **Throw** for truly unexpected problems and when most callers just let errors bubble up to one handler (an error page, Express's error middleware). It keeps happy-path code short.
- **Return a `Result`** when failures are **expected** and callers must handle them differently: "not found" shows a message, "network" shows a retry button. The compiler then makes sure nobody forgets, and adding a new error kind shows you every `switch` that needs updating.

Whatever you choose, be consistent within one layer of your app; mixing both in one API makes every caller write both `try`/`catch` and `if (!result.ok)`.

## Query parameters from typed options

Search endpoints take **query parameters** like `/movies?search=panda&limit=2`. Building that string by hand with `+` is fragile: forget to encode a `&` or a space and the server gets a different question. Describe the options with a type, and let `URL` and `URLSearchParams` do the encoding:

<CodeExample output={`https://api.pandadev.test/movies
https://api.pandadev.test/movies?search=bamboo+%26+tea&limit=2
https://api.pandadev.test/movies?genre=sci-fi&page=2
200 https://api.pandadev.test/movies?genre=comedy&limit=3`}>

```ts
const API = "https://api.pandadev.test";

type Genre = "action" | "comedy" | "drama" | "family" | "sci-fi";

type MovieSearch = {
  search?: string;
  genre?: Genre;
  page?: number;
  limit?: number;
};

function moviesUrl(options: MovieSearch = {}): string {
  const url = new URL("/movies", API);
  for (const [key, value] of Object.entries(options)) {
    if (value !== undefined) {
      url.searchParams.set(key, String(value));
    }
  }
  return url.toString();
}

console.log(moviesUrl());
console.log(moviesUrl({ search: "bamboo & tea", limit: 2 }));
console.log(moviesUrl({ genre: "sci-fi", page: 2, search: undefined }));

const res = await fetch(moviesUrl({ genre: "comedy", limit: 3 }));
console.log(res.status, res.url);
```

</CodeExample>

The **options object** is where TypeScript earns its keep. Every option is optional, so callers pass only what they need, in any order, and mistakes are caught at the call site:

```ts
moviesUrl({ genre: "horror" });
// ❌ Error: Type '"horror"' is not assignable to type 'Genre | undefined'.
moviesUrl({ serch: "panda" });
// ❌ Error: Object literal may only specify known properties, but 'serch' does not exist in type 'MovieSearch'. Did you mean to write 'search'?
moviesUrl({ page: "2" });
// ❌ Error: Type 'string' is not assignable to type 'number'.
```

Note the `value !== undefined` check: without it, `{ search: undefined }` would send `search=undefined`, a classic bug that searches for movies called "undefined".

Build the request layer of a typed API client. It never throws: every outcome becomes a `Result<unknown, ApiError>`. (In the next lesson you'll replace `unknown` with validated types.)

1. `request(path, options)`:
   - send `options.method` (default `"GET"`); if there's a `body`, send it as JSON (the `Content-Type` header plus `JSON.stringify`);
   - give up after `options.timeoutMs` (default `2000`) with `AbortSignal.timeout`;
   - if `fetch` rejects: a `TimeoutError` becomes `{ kind: "timeout", ms }`, anything else `{ kind: "network", message }`;
   - read the body (`null` for a 204 or a body that isn't JSON); if `!res.ok`, return `{ kind: "http", status, message }` using `apiMessage(body)`, or `` `HTTP ${status}` `` if there's none;
   - otherwise return `{ ok: true, value: body }`.
2. `moviesPath(options)` returns `"/movies"` plus an encoded query string, skipping `undefined` options (no `?` when there are none).
3. TypeScript already complains about `describeError`: the `never` check found an unhandled kind. Add it, returning `` `No answer after ${ms} ms.` ``.

<Hint>

Inside `catch`, `error` is `unknown`, so check `error instanceof Error && error.name === "TimeoutError"`. Build `init` as a `RequestInit` with `signal: AbortSignal.timeout(timeoutMs)`. For the body: `res.status === 204 ? null : await res.json().catch(() => null)`. For `moviesPath`, fill a `new URLSearchParams()` in a loop over `Object.entries(options)`, then use `params.toString()`.

</Hint>

```ts
const API = "https://api.pandadev.test";

type Result<T, E> =
  | { ok: true; value: T }
  | { ok: false; error: E };

type ApiError =
  | { kind: "network"; message: string }
  | { kind: "timeout"; ms: number }
  | { kind: "http"; status: number; message: string };

type RequestOptions = {
  method?: "GET" | "POST" | "PATCH" | "DELETE";
  body?: unknown;
  timeoutMs?: number;
};

// Ready to use: the API's error message, if there is one
function apiMessage(body: unknown): string | undefined {
  if (
    typeof body === "object" &&
    body !== null &&
    "error" in body &&
    typeof body.error === "string"
  ) {
    return body.error;
  }
  return undefined;
}

async function request(
  path: string,
  options: RequestOptions = {},
): Promise<Result<unknown, ApiError>> {
  const { method = "GET", body, timeoutMs = 2000 } = options;
  const init: RequestInit = {
    method,
    signal: AbortSignal.timeout(timeoutMs),
  };
  if (body !== undefined) {
    init.headers = { "Content-Type": "application/json" };
    init.body = JSON.stringify(body);
  }

  let res: Response;
  try {
    res = await fetch(API + path, init);
  } catch (error) {
    if (error instanceof Error && error.name === "TimeoutError") {
      return { ok: false, error: { kind: "timeout", ms: timeoutMs } };
    }
    const message =
      error instanceof Error ? error.message : String(error);
    return { ok: false, error: { kind: "network", message } };
  }

  const data: unknown =
    res.status === 204 ? null : await res.json().catch(() => null);
  if (!res.ok) {
    const message = apiMessage(data) ?? `HTTP ${res.status}`;
    return {
      ok: false,
      error: { kind: "http", status: res.status, message },
    };
  }
  return { ok: true, value: data };
}

type MovieSearch = {
  search?: string;
  genre?: "action" | "comedy" | "drama" | "family" | "sci-fi";
  page?: number;
  limit?: number;
};

function moviesPath(options: MovieSearch = {}): string {
  const params = new URLSearchParams();
  for (const [key, value] of Object.entries(options)) {
    if (value !== undefined) params.set(key, String(value));
  }
  const query = params.toString();
  return query ? `/movies?${query}` : "/movies";
}

function describeError(error: ApiError): string {
  switch (error.kind) {
    case "network":
      return "You seem to be offline.";
    case "timeout":
      return `No answer after ${error.ms} ms.`;
    case "http":
      return `The server said ${error.status}: ${error.message}`;
    default: {
      const unhandled: never = error;
      return unhandled;
    }
  }
}

// Try it out
console.log(moviesPath({ search: "panda", limit: 2 }));
for (const path of ["/movies/2", "/movies/99", "/offline"]) {
  const result = await request(path);
  if (result.ok) console.log("OK:", result.value);
  else console.log(describeError(result.error));
}
const slow = await request("/delay/1500", { timeoutMs: 300 });
if (!slow.ok) console.log(describeError(slow.error));
```

## Recap

- `fetch` returns `Promise<Response>`, but `res.json()` is `any`: a hole in your types right where outside data comes in.
- `as Movie` (or a `getJson<T>` whose `T` only appears in the return type) is a promise to the compiler, not a check. Keep outside data `unknown` until you've validated it.
- An honest helper takes a check (a type guard now, a schema next lesson) and infers `T` from it.
- `fetch` only rejects when no response arrives; check `res.ok` for HTTP errors.
- Throw a typed error class (`HttpError` with `status`), or return a `Result<T, E>` with a discriminated error union so callers must handle each failure.
