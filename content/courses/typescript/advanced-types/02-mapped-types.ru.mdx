В уроке [Утилитные типы](/learn/typescript/utility-types) вы видели определение `Partial` и обещание: часть `[K in ...]` — это **сопоставленный тип** (mapped type), и писать такие типы самостоятельно вы научитесь на Уровне 3. Вот мы и здесь. Условные типы ([предыдущий урок](/learn/typescript/conditional-types-and-infer)) принимают решения об **одном** типе. Сопоставленные типы **проходят циклом по ключам** и строят новый объектный тип свойство за свойством. Вместе они — основа почти любого «производного» типа в современном коде: состояние формы из модели, обработчики из списка событий, типизированный клиент из описания API. 🔁

## Цикл по ключам

Сопоставленный тип похож на индексную сигнатуру с `in`:

```ts
type Flags = { [K in "darkMode" | "beta"]: boolean };
// { darkMode: boolean; beta: boolean }

type MyRecord<K extends PropertyKey, V> = { [P in K]: V };
```

`K in Keys` перебирает каждый член объединения ключей (`PropertyKey` — это `string | number | symbol`). Настоящая сила появляется, когда вы перебираете ключи **другого** типа через `keyof T` и смотрите на тип каждого свойства через `T[K]`. Вот форма, валидаторы которой выведены из структуры самой формы:

<CodeExample output={`{ age: 'Вам должно быть не меньше 13 лет', terms: 'Примите условия' }
{}`}>

```ts
interface SignUp {
  email: string;
  age: number;
  terms: boolean;
}

type Validators<T> = {
  [K in keyof T]: (value: T[K]) => string | null;
};
type Errors<T> = { [K in keyof T]?: string };

const rules: Validators<SignUp> = {
  email: (v) => (v.includes("@") ? null : "Введите корректный email"),
  age: (v) => (v >= 13 ? null : "Вам должно быть не меньше 13 лет"),
  terms: (v) => (v ? null : "Примите условия"),
};

function validate<T>(values: T, validators: Validators<T>): Errors<T> {
  const errors: Errors<T> = {};
  for (const key in validators) {
    const message = validators[key](values[key]);
    if (message !== null) {
      errors[key] = message;
    }
  }
  return errors;
}

const young = { email: "mei@panda.dev", age: 12, terms: false };
const adult = { email: "sam@panda.dev", age: 30, terms: true };
console.log(validate(young, rules));
console.log(validate(adult, rules));
```

</CodeExample>

Посмотрите, что вы получаете даром. Параметр `v` в каждом валидаторе имеет правильный тип (`string`, `number`, `boolean`) без единой аннотации. А когда в следующем месяце кто-нибудь добавит в `SignUp` поле `country`, объект с правилами перестанет компилироваться, пока в нём не появится валидатор для этого поля:

```ts
const rules: Validators<SignUp> = {
  email: (v) => (v.includes("@") ? null : "Введите корректный email"),
  age: (v) => (v >= 13 ? null : "Вам должно быть не меньше 13 лет"),
  terms: (v) => (v ? null : "Примите условия"),
};
// ❌ Error: Property 'country' is missing in type '{ email: (v: string) => "Введите корректный email" | null; age: (v: number) => "Вам должно быть не меньше 13 лет" | null; terms: (v: boolean) => "Примите условия" | null; }' but required in type 'Validators<SignUp>'.
```

В этом и смысл производных типов: **один источник истины**, а компилятор сам проводит вас по всем местам, которые нужно изменить.

## Модификаторы: `readonly` и `?`

Сопоставленный тип может добавлять и убирать два **модификатора** (modifiers) свойств. Чтобы добавить их, поставьте `readonly` перед ключом или `?` после него; чтобы убрать — допишите перед ними `-` (`+` тоже существует и означает «добавить», но его никто не пишет). Этого достаточно, чтобы пересобрать четыре утилитных типа:

```ts
type MyPartial<T> = { [K in keyof T]?: T[K] };
type MyRequired<T> = { [K in keyof T]-?: T[K] };
type MyReadonly<T> = { readonly [K in keyof T]: T[K] };
type Mutable<T> = { -readonly [K in keyof T]: T[K] };
```

`Mutable` не встроен в язык, но это классика. Вот где он окупается: помощник «измени копию» — идея, на которой построена библиотека Immer (её использует Redux Toolkit). Состояние везде остаётся `readonly`, и только внутри функции-рецепта можно писать в **черновик** (draft):

<CodeExample output={`light 14
dark 16`}>

```ts
type Mutable<T> = { -readonly [K in keyof T]: T[K] };

interface Settings {
  readonly theme: "light" | "dark";
  readonly fontSize: number;
  readonly shortcuts: readonly string[];
}

// Меняем копию, никогда не оригинал (идея Immer)
function produce<T>(base: T, recipe: (draft: Mutable<T>) => void): T {
  const draft: Mutable<T> = structuredClone(base);
  recipe(draft);
  return draft;
}

const current: Settings = {
  theme: "light",
  fontSize: 14,
  shortcuts: ["ctrl+s"],
};

const next = produce(current, (draft) => {
  draft.theme = "dark";
  draft.fontSize += 2;
});

console.log(current.theme, current.fontSize);
console.log(next.theme, next.fontSize);
```

</CodeExample>

Как и встроенный `Readonly`, `Mutable` — **поверхностный** (shallow): он меняет только свойства верхнего уровня. `draft.shortcuts` по-прежнему `readonly string[]`:

```ts
produce(current, (draft) => {
  draft.shortcuts.push("ctrl+k");
  // ❌ Error: Property 'push' does not exist on type 'readonly string[]'.
});
```

Для глубокой версии нужен сопоставленный тип, который вызывает сам себя через условный тип; `DeepReadonly` и его родственников вы соберёте в уроке [Свои утилитные типы](/learn/typescript/building-utility-types).

## Гомоморфные сопоставленные типы сохраняют модификаторы

В `MyPartial` произошло кое-что неочевидное: мы только **добавили** `?`, а свойства `readonly` так и остались `readonly`. Сопоставленный тип по `keyof T` называется **гомоморфным** (homomorphic, «той же формы»), и он копирует модификаторы каждого свойства из `T`. `Pick` тоже гомоморфный, потому что его ключи ограничены `keyof T`:

```ts
interface Profile {
  readonly id: string;
  name: string;
  bio?: string;
}

type Copy<T> = { [K in keyof T]: T[K] };
type A = Copy<Profile>;
// { readonly id: string; name: string; bio?: string }

type MyPick<T, K extends keyof T> = { [P in K]: T[P] };
type B = MyPick<Profile, "id" | "bio">;
// { readonly id: string; bio?: string }
```

Как только TypeScript перестаёт видеть `keyof T` в сопоставленном типе, он перестаёт копировать модификаторы. Сохраните ключи сначала в псевдониме — и модификаторы молча исчезнут:

```ts
type ProfileKey = keyof Profile;
type Flat = { [K in ProfileKey]: Profile[K] };
// { id: string; name: string; bio: string | undefined }
```

`id` больше не `readonly`, а `bio` стало **обязательным** (в нём может лежать `undefined`, но само свойство должно быть). Такую ошибку никогда не заметят на код-ревью: тип по-прежнему «выглядит правильно». А тест типов с `Equal` сразу её поймает.

У гомоморфных сопоставленных типов есть ещё одна суперспособность: на **массиве или кортеже** они отображают элементы и возвращают массив или кортеж. Именно так `Promise.all` типизирован в библиотеке TypeScript (сопоставленный тип с `Awaited<T[P]>`). Тот же приём позволяет дождаться **объекта** промисов:

<CodeExample output={`Входящие: Mei, новых: 3`}>

```ts
type Resolved<T> = { [K in keyof T]: Awaited<T[K]> };

async function allProps<T extends object>(
  tasks: T,
): Promise<Resolved<T>> {
  const entries = await Promise.all(
    Object.entries(tasks).map(async ([key, task]) => {
      return [key, await task] as const;
    }),
  );
  return Object.fromEntries(entries) as Resolved<T>;
}

const wait = (ms: number) =>
  new Promise<void>((resolve) => setTimeout(resolve, ms));

async function loadUser() {
  await wait(30);
  return { name: "Mei", plan: "pro" };
}

async function loadUnread() {
  await wait(10);
  return 3;
}

const page = await allProps({
  user: loadUser(),
  unread: loadUnread(),
  title: "Входящие", // обычные значения тоже подходят
});

console.log(`${page.title}: ${page.user.name}, новых: ${page.unread}`);
```

</CodeExample>

Загрузки идут параллельно, а `page` имеет тип `{ user: { name: string; plan: string }; unread: number; title: string }` — с именами вместо позиций в кортеже. (`as` нужен потому, что `Object.fromEntries` возвращает расплывчатый `{ [k: string]: ... }`; сопоставленный тип честно описывает то, что получилось.)

<Callout type="tip" title="Пересоберите утилиту — и протестируйте её">

`Omit` сочетает оба инструмента этого модуля: `type MyOmit<T, K extends PropertyKey> = MyPick<T, Exclude<keyof T, K>>`. Поскольку он проходит через `Pick` с ключами из `keyof T`, модификаторы сохраняются. Каждый раз, когда вы пишете такой тип, закрепите его тестом типов: против настоящего типа, `Expect<Equal<MyOmit<Profile, "id">, Omit<Profile, "id">>>`, и против выписанной вручную структуры, где есть свойство `readonly` и необязательное свойство. Именно на этих двух случаях самописные сопоставленные типы и ломаются.

</Callout>

## Переименование ключей через `as`

Начиная с TypeScript 4.1, сопоставленный тип может ещё и **переименовывать** ключи с помощью конструкции `as`: `[K in keyof T as NewName]`. Новое имя обычно строят из **шаблонного литерального типа** (template literal type) — это тема следующего урока. Вот короткий анонс, который превращает каждое свойство в геттер:

<CodeExample output={`PO 8
[ 'getName', 'getAge' ]`}>

```ts
type Getters<T> = {
  [K in keyof T as `get${Capitalize<string & K>}`]: () => T[K];
};

function makeGetters<T extends object>(obj: T): Getters<T> {
  const getters: Record<string, () => unknown> = {};
  for (const key of Object.keys(obj)) {
    const name = `get${key[0].toUpperCase()}${key.slice(1)}`;
    getters[name] = () => obj[key as keyof T];
  }
  return getters as Getters<T>;
}

const panda = makeGetters({ name: "Po", age: 7 });
console.log(panda.getName().toUpperCase(), panda.getAge() + 1);
console.log(Object.keys(panda));
```

</CodeExample>

`string & K` нужен потому, что ключи бывают ещё числами и символами, а `Capitalize` работает только со строками: пересечение оставляет лишь строковые ключи. Обратите внимание: тип и код времени выполнения описывают правило переименования каждый по отдельности. Тип не может проверить, что `makeGetters` действительно создаёт `getName`, поэтому реализация и заканчивается одним приведением.

Конструкция `as` умеет и **фильтровать**: если новое имя — `never`, свойство отбрасывается. Объедините это с условным типом — и сможете выбирать ключи по **типу их значения**:

<CodeExample output="65 5">

```ts
type KeysOfType<T, V> = keyof {
  [K in keyof T as T[K] extends V ? K : never]: T[K];
};

interface Order {
  id: string;
  total: number;
  shipping: number;
  paid: boolean;
}

type MoneyField = KeysOfType<Order, number>; // "total" | "shipping"

function sumBy<T>(items: T[], key: KeysOfType<T, number>): number {
  let sum = 0;
  for (const item of items) {
    sum += item[key] as number; // TypeScript не видит, что это число
  }
  return sum;
}

const orders: Order[] = [
  { id: "o1", total: 40, shipping: 5, paid: true },
  { id: "o2", total: 25, shipping: 0, paid: false },
];
const field: MoneyField = "shipping";
console.log(sumBy(orders, "total"), sumBy(orders, field));
```

</CodeExample>

Для вызывающего кода это прекрасно: редактор подсказывает только `"total"` и `"shipping"`, а ошибка читается ясно:

```ts
sumBy(orders, "id");
// ❌ Error: Argument of type '"id"' is not assignable to parameter of type '"total" | "shipping"'.
```

А вот внутри функции TypeScript не может понять, что `item[key]` — число для неизвестного `T`, поэтому нужно приведение. Альтернатива — наложить ограничение на `T`: `function sumBy<T extends Record<K, number>, K extends keyof T>(items: T[], key: K)`. Приведение тогда не нужно, но вызывающие получают сообщение хуже (`Argument of type 'Order[]' is not assignable to parameter of type 'Record<"id", number>[]'.`, и указывает оно на **orders**, а не на ключ). Что лучше, зависит от того, кто чаще читает ошибки: пользователи библиотеки или её сопровождающие.

## Сопоставленные типы по объединениям

`in` перебирает **любое** объединение, а не только ключи. Вместе с `as` это превращает объединение событий в объект с отдельным обработчиком для каждого события:

```ts
type AppEvent =
  | { type: "login"; userId: string }
  | { type: "logout"; userId: string; reason: "manual" | "timeout" }
  | { type: "purchase"; userId: string; amount: number };

type Handlers = {
  [E in AppEvent as E["type"]]: (event: E) => void;
};
// { login: (event: { type: "login"; ... }) => void; logout: ...; ... }
```

Каждый обработчик получает ровно своё событие. Но попробуйте **вызвать** нужный обработчик — и вы упрётесь в одно из самых известных ограничений TypeScript:

```ts
function dispatch(event: AppEvent, handlers: Handlers) {
  handlers[event.type](event);
  // ❌ Error: Argument of type 'AppEvent' is not assignable to parameter of type 'never'.
}
```

TypeScript не отслеживает, что `event.type` и `event` связаны **друг с другом** (это называется **коррелированным объединением**, correlated union). `handlers[event.type]` может оказаться любым из трёх обработчиков, поэтому безопасен для всех сразу только аргумент, который одновременно является каждым событием, — то есть `never`. Решение, которое рекомендует сама команда TypeScript: **начните с карты** «имя события → данные» и выведите из неё и объединение, и обработчики:

<CodeExample output={`[ 'mei: вход', 'mei: оплата £12', 'mei: выход (timeout)' ]`}>

```ts
// Начинаем с карты: имя события -> что событие несёт
interface EventMap {
  login: { userId: string };
  logout: { userId: string; reason: "manual" | "timeout" };
  purchase: { userId: string; amount: number };
}

// Выводим из неё объединение событий...
type AppEvent<K extends keyof EventMap = keyof EventMap> = {
  [P in K]: { type: P } & EventMap[P];
}[K];

// ...и объект с отдельным обработчиком для каждого события
type Handlers = {
  [K in keyof EventMap]: (event: AppEvent<K>) => void;
};

function dispatch<K extends keyof EventMap>(
  event: AppEvent<K>,
  handlers: Handlers,
): void {
  handlers[event.type](event);
}

const log: string[] = [];
const handlers: Handlers = {
  login: (e) => log.push(`${e.userId}: вход`),
  logout: (e) => log.push(`${e.userId}: выход (${e.reason})`),
  purchase: (e) => log.push(`${e.userId}: оплата £${e.amount}`),
};

dispatch({ type: "login", userId: "mei" }, handlers);
dispatch({ type: "purchase", userId: "mei", amount: 12 }, handlers);
dispatch({ type: "logout", userId: "mei", reason: "timeout" }, handlers);
console.log(log);
```

</CodeExample>

`{ [P in K]: ... }[K]` — распространённая идиома: постройте объект с одной записью на каждый ключ, а затем обратитесь к нему по всем ключам сразу, чтобы получить **объединение** его значений. `AppEvent` (со значением по умолчанию) — то же объединение трёх событий, что и раньше, а `AppEvent<"login">` — только событие входа. Поскольку всё выражено через одно и то же `K`, TypeScript теперь видит, что обработчик и событие совпадают, — без всяких приведений. Новое событие — это одна строка в `EventMap`, и каждый объект `Handlers` сразу потребует для него обработчик.

## Когда выводить, а когда выписывать

Сопоставленные типы настолько удобны, что команды ими злоупотребляют. В одном проекте, который я ревьюил, каждая структура данных API выводилась из модели базы данных цепочками вроде `Partial<Omit<Pick<DbUser, ...>, ...>>` в пять уровней. Переименование одного столбца сломало сразу сорок типов, и все ошибки указывали на **производные** имена, так что никто не мог понять, какой API на самом деле изменился. Несколько правил:

- **Модели предметной области — выписывайте.** `User`, `Order` и `Invoice` — это словарь вашего приложения. Описывайте их явно, интерфейсами, чтобы они читались в подсказках и ошибках.
- **Варианты модели — выводите.** Валидаторы, карты ошибок, патчи, представления только для чтения и карты обработчиков должны следовать за моделью автоматически; здесь сопоставленные типы и блистают.
- **Структуры, которые меняются по разным причинам, — не выводите.** Ответ API и строка в базе данных сегодня могут выглядеть одинаково, но меняются по разным причинам (публичный контракт против решения о хранении). Вывод одного из другого связывает их. Лучше преобразуйте одно в другое в коде.
- **Подсказки показывают формулы.** Редактор покажет `Validators<SignUp>`, а не его свойства. Для типов, которые часто читают, есть известный приём `type Simplify<T> = { [K in keyof T]: T[K] } & {}`: подсказки раскрываются. Он также превращает пересечение вроде `{ a: 1 } & { b: 2 }` в один объектный тип — иначе строгие тесты с `Equal` считают его отличным от `{ a: 1; b: 2 }`.
- **Считайте приведения.** Сопоставленный тип, которому нужно приведение внутри каждой использующей его функции (как в `sumBy`), всё равно оправдан, если он защищает много вызывающих мест. Если только одно — напишите простую версию.

<Callout type="warning" title="Сопоставленные типы не создают код времени выполнения">

Сопоставленный тип описывает объект, но никогда его не создаёт. `Getters<T>`, `Setters<T>` и `Resolved<T>` обещают, что определённые свойства существуют, и сдержать это обещание может только ваш код времени выполнения (и его тесты). Когда производный тип и код, который строит объект, следуют одному правилу (например, «добавить `get` и сделать первую букву заглавной»), держите их рядом и тестируйте оба.

</Callout>

Библиотеки форм (React Hook Form, Formik, TanStack Form) — это в основном сопоставленные типы поверх структуры **вашей** формы. Соберите маленькую: `createForm(initial, validators)` возвращает модель формы с текущими значениями, сеттером для каждого поля, методом `toggle` для полей-флажков и валидацией.

**Типы.** Замените каждый `unknown` сопоставленным типом:

1. `Validators<T>`: валидатор `(value: T[K]) => string | null` для **каждого** поля, включая необязательные (форма должна решить, что значит пустой реферальный код).
2. `Errors<T>`: необязательное сообщение об ошибке (`string`) **только для чтения** для каждого поля.
3. `Setters<T>`: `setEmail`, `setAge` и так далее, каждый принимает тип своего поля. Сеттеры всегда обязательные, даже для необязательных полей.
4. `FlagFields<T>`: объединение имён полей, тип значения которых — логический.

Строки `Expect<Equal<...>>` компилируются, только когда ваши типы в точности верны, а каждая строка с `// @ts-expect-error` проходит, только когда строка под ней **является** ошибкой.

**Поведение.** Затем напишите `createForm`:

- `values()` возвращает текущие значения: сначала это **копия** `initial`. Каждое изменение (сеттер или `toggle`) заменяет их **новым** объектом, как состояние в React.
- В `set` по одному сеттеру на каждый ключ `validators` (валидаторы перечисляют все поля, даже те, которых нет в `initial`).
- `toggle(field)` переключает логическое поле.
- `errors()` запускает каждый валидатор на текущих значениях и возвращает объект только с сообщениями полей, не прошедших проверку.

<Hint>

**Типы:** `Validators` нужен `-?`: `{ [K in keyof T]-?: (value: T[K]) => string | null }`. `Errors` — это `{ readonly [K in keyof T]?: string }`. `Setters` переименовывает ключи через `as`, как `Getters` в уроке, плюс `-?`. Для `FlagFields` отфильтруйте ключи через `as T[K] extends boolean ? K : never` и возьмите `keyof` результата, как в `KeysOfType`.

**Поведение:** начните с `let values: T = { ...initial };`. Соберите сеттеры в `const set: Record<string, (value: unknown) => void> = {}`, перебирая `Object.keys(validators)`; каждый делает `values = { ...values, [key]: value };`. Верните его как `set as Setters<T>` (единственное приведение: TypeScript не может проверить переименование). `toggle(field)` — это `values = { ...values, [field]: !values[field] };`. В `errors()` пройдите циклом `for (const key in validators)`, вызовите `validators[key](values[key])` и соберите сообщения, которые не равны `null`, в изменяемый объект `{ [K in keyof T]?: string }`.

</Hint>

type Equal<A, B> =
  (<X>() => X extends A ? 1 : 2) extends
  (<X>() => X extends B ? 1 : 2) ? true : false;
type Expect<T extends true> = T;

type Validators<T> = {
  [K in keyof T]-?: (value: T[K]) => string | null;
};

type Errors<T> = { readonly [K in keyof T]?: string };

type Setters<T> = {
  [K in keyof T as `set${Capitalize<string & K>}`]-?: (
    value: T[K],
  ) => void;
};

type FlagFields<T> = keyof {
  [K in keyof T as T[K] extends boolean ? K : never]: T[K];
};

interface Form<T> {
  values(): T;
  set: Setters<T>;
  toggle(field: FlagFields<T>): void;
  errors(): Errors<T>;
}

function createForm<T extends object>(
  initial: T,
  validators: Validators<T>,
): Form<T> {
  let values: T = { ...initial };

  const set: Record<string, (value: unknown) => void> = {};
  for (const key of Object.keys(validators)) {
    const name = `set${key[0].toUpperCase()}${key.slice(1)}`;
    set[name] = (value) => {
      values = { ...values, [key]: value };
    };
  }

  return {
    values: () => values,
    set: set as Setters<T>,
    toggle(field) {
      values = { ...values, [field]: !values[field] };
    },
    errors() {
      const errors: { [K in keyof T]?: string } = {};
      for (const key in validators) {
        const message = validators[key](values[key]);
        if (message !== null) {
          errors[key] = message;
        }
      }
      return errors;
    },
  };
}

## Итоги

- **Сопоставленный тип** `{ [K in Keys]: ... }` строит объектный тип, перебирая объединение ключей; с `keyof T` и `T[K]` он преобразует другой тип свойство за свойством.
- **Модификаторы**: добавляйте `readonly` / `?`, убирайте их через `-readonly` / `-?`. Ничего больше в `Partial`, `Required`, `Readonly` и `Mutable` нет, и все они **поверхностные**.
- **Гомоморфные** сопоставленные типы (по `keyof T`, как `Pick`) копируют `readonly` и `?` из оригинала и отображают массивы и кортежи поэлементно (так типизирован `Promise.all`). Спрячьте ключи за псевдонимом — и модификаторы потеряются.
- **Переименование ключей** через `as` меняет имена ключей (`get${Capitalize<...>}`) и **фильтрует** их (`as ... ? K : never`), например чтобы выбрать ключи по типу значения.
- Отображение **объединения** даёт обработчики для каждого варианта. Чтобы вызывать их без приведений, **начните с карты** (`EventMap`) и выведите из неё и объединение, и обработчики.
- Модели предметной области выписывайте; их варианты выводите. Держите независимыми типы, которые меняются по разным причинам, следите, сколько приведений требует производный тип, и тестируйте каждый самописный сопоставленный тип — особенно со свойствами `readonly` и необязательными свойствами.
