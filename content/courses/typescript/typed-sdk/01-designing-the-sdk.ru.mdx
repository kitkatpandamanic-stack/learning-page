Добро пожаловать в **итоговый проект Уровня 3** — финальный проект всего курса TypeScript! 🎓 За три части вы спроектируете, соберёте и выпустите **`@pandadev/sdk`** — типобезопасный SDK для учебного API PandaDev: фильмов, пользователей, постов и задач. SDK (software development kit) — это пакет, который компания публикует, чтобы другие разработчики могли пользоваться её API, не читая документацию по HTTP: вспомните `stripe`, `@octokit/rest` или `openai` в npm.

SDK — идеальный проект уровня Senior, потому что его пользователи — **другие разработчики**, а для них типы **и есть** пользовательский интерфейс. Сделайте их правильно — и люди будут открывать для себя API через автодополнение, а ошибки будут видны красными подчёркиваниями, а не ответами 400 в продакшене. Вот обещание, которое мы сдержим: **если ваш код компилируется, он отправляет запросы, понятные API, а всё, что приходит в ответ, проверено.**

## Начнём с дизайн-документа

Вы уже собирали типизированные клиенты. В уроке [Общие типы для клиента и сервера](/learn/typescript/sharing-types-between-client-and-server) **тип**-контракт описывал ваш собственный API, а клиент доверял серверу через одно приведение типа; в [итоговом проекте Уровня 2](/learn/typescript/the-typed-client) клиент проверял каждый ответ общими схемами. SDK для **публичного** API — взрослая версия обоих подходов, и у неё новые проблемы: его будут вызывать тысячи незнакомых людей, из TypeScript **и** из обычного JavaScript, через нестабильные сети, а каждое изменение его типов — это изменение в сборках его пользователей. Поэтому начинаем так, как это делают Senior-разработчики, — с короткого **дизайн-документа** (design doc).

### Цели и не-цели

**Цели для 1.0:**

- Покрыть фильмы учебного API (с поиском и страницами), пользователей, посты и задачи (с созданием, изменением и удалением).
- **Единое описание API** — единственный источник истины: методы, пути, параметры пути, query, тело и ответ записаны один раз, и каждый тип выводится из этого описания.
- **Типизированный ввод:** опечатка в настройке query, пропущенный параметр пути или id задачи там, где нужен id фильма, не компилируются.
- **Проверенный вывод:** каждый ответ валидируется во время выполнения. Мы не деплоим этот API, значит, не доверяем ему.
- **Ожидаемые сбои — это значения:** `Result` с типизированной размеченной `ApiError`, никаких неожиданных исключений.
- **Устойчивость:** безопасные запросы повторяются с backoff; страницы можно обойти через `for await`.
- **Ноль зависимостей во время выполнения**, только ESM, работает везде, где есть `fetch` (браузеры, Node 20+, edge-среды).

**Не-цели для 1.0:** кеширование, сценарии аутентификации, хуки React, эндпоинты погоды и рецептов и генерация кода из файла OpenAPI. Записанные не-цели — это то, что не даёт версии 1.0 так никогда и не выйти; а ещё у всех появляется список, о котором можно спорить к версии 1.1.

### Сначала место вызова

Senior-разработчики проектируют SDK **снаружи внутрь**: сначала пишут пример для README, а потом строят то, что ему нужно. Если пример выглядит неуклюже, значит, ошибка в дизайне, и выяснить это сейчас гораздо дешевле, чем после 1.0. Вот наш пример:

```ts
import { createPandaClient, paginate, MovieId } from "@pandadev/sdk";

const panda = createPandaClient();

const id = MovieId.parse(1); // проверенный, брендированный id
const movie = await panda.getMovie({ params: { id } });
if (movie.ok) {
  console.log(movie.value.title); // string, проверено во время выполнения
} else {
  console.log(movie.error.kind); // "network" | "http" | ...
}

await panda.createTodo({ body: { title: "Выпустить SDK" } });

const dramas = paginate(panda.searchMovies, { genre: "drama" });
for await (const film of dramas) {
  console.log(film.title); // все страницы, загружаются по ходу дела
}
```

Каждый вызов принимает **один объект**, в котором до трёх именованных частей: `params`, `query` и `body`, — та же форма, что у клиента-по-контракту в Уровне 2. Именованные части невозможно перепутать, добавление необязательной части позже никого не сломает, и они никогда не конфликтуют, даже если у параметра пути и настройки query одинаковое имя.

### Решения и компромиссы

| Решение | Вместо | Почему |
| --- | --- | --- |
| Один **объект-описание**, типы выводятся из него | Методы и типы, написанные вручную | Две копии расходятся, одна — нет. Добавить эндпоинт — это одна запись. |
| Собственное описание | Генерация кода из файла **OpenAPI** | Учебный API не публикует файл OpenAPI. Когда API его публикует, генераторы вроде openapi-typescript используют ровно те приёмы с типами, что есть в этом уроке. |
| **Проверять каждый ответ** | Доверять серверу через приведение типа | Мы не управляем деплоями этого API. Схема превращает расхождение в одну понятную ошибку с путём, прямо на границе. |
| `Result` для ожидаемых сбоев, **throw** для багов | Бросать всё подряд или `Result` для всего | Вызывающий код обязан обработать 404 и оборванные соединения, поэтому это значения. Плохой ввод от вызывающего — баг в его коде, поэтому он бросает исключение, как `TypeError`. |
| **Брендированные id** (`MovieId`, `TodoId`) | Простые числа | `getMovie` с id задачи — баг, который можно исключить при компиляции, причём бесплатно. |
| Своя крошечная библиотека схем | zod или valibot | Ноль зависимостей для пользователей. Настоящая версия 1.x могла бы вместо этого принимать любую библиотеку, совместимую со **Standard Schema**, чтобы пользователи приносили свою. |

Одно различие из таблицы стоит рассмотреть ещё раз. В Уровне 2 ответ, не прошедший схему, был ошибкой `"invalid"`. В SDK важно, **что именно** неверно: плохой **ввод** — это баг вызывающего кода, и он бросает `ValidationError` ещё до отправки, а плохой **ответ** означает, что API изменился, и становится значением-ошибкой `{ kind: "invalid-response" }`, которое вызывающий код может показать или отправить в отчёт. Две причины, два владельца, два механизма.

## Схемы, ещё раз

Ответы проверяются библиотекой схем, которую вы написали в уроке [Валидация во время выполнения](/learn/typescript/runtime-validation): у `Schema<T>` есть метод `parse`, который превращает `unknown` в `T` или бросает `ValidationError` с путём, а `Infer<typeof schema>` достаёт тип обратно. SDK нужно одно, чего та библиотека не умела: **необязательные поля** (optional fields). Ими полны настройки query вроде `search` и тела вроде изменения задачи.

`object()` из Уровня 2 сопоставлял каждому ключу `Infer<...>`. Добавьте в эту библиотеку схему `optional()` — и поле сможет хранить `undefined`, но ключ останется **обязательным**:

```ts
const NewTodo = object({ title: string(), done: optional(boolean()) });
type NewTodo = Infer<typeof NewTodo>;

const draft: NewTodo = { title: "Nap" };
// ❌ Error: Property 'done' is missing in type '{ title: string; }' but required in type '{ title: string; done: boolean | undefined; }'.
```

Исправление использует два инструмента из урока [Сопоставленные типы](/learn/typescript/mapped-types). `optional()` помечает свою схему как `optional: true`, а тип объекта делит ключи на два сопоставленных типа: один без `?`, другой с ним. `Simplify` из урока [Собственные утилитные типы](/learn/typescript/building-utility-types) снова сливает их в один читаемый объект:

<CodeExample output={`{ title: 'Nap' }
{ title: 'Nap', done: true }
body.done: expected a boolean, got "yes"`}>

```ts
class ValidationError extends Error {
  constructor(path: string, expected: string, got: unknown) {
    const where = path || "value";
    super(`${where}: expected ${expected}, got ${JSON.stringify(got)}`);
    this.name = "ValidationError";
  }
}

type Schema<T> = {
  parse: (value: unknown, path?: string) => T;
  optional?: true; // задаётся только в optional()
};
type Infer<S extends Schema<unknown>> = ReturnType<S["parse"]>;
type Simplify<T> = { [K in keyof T]: T[K] } & {};

function primitive<T>(
  expected: string,
  test: (value: unknown) => value is T,
): Schema<T> {
  return {
    parse(value, path = "") {
      if (!test(value)) {
        throw new ValidationError(path, expected, value);
      }
      return value;
    },
  };
}

const string = () =>
  primitive("a string", (v): v is string => typeof v === "string");
const boolean = () =>
  primitive("a boolean", (v): v is boolean => typeof v === "boolean");

function optional<T>(
  schema: Schema<T>,
): Schema<T | undefined> & { optional: true } {
  return {
    optional: true,
    parse: (value, path) =>
      value === undefined ? undefined : schema.parse(value, path),
  };
}

type Shape = Record<string, Schema<unknown>>;
type OptionalKeys<S extends Shape> = {
  [K in keyof S]: S[K] extends { optional: true } ? K : never;
}[keyof S];
type ObjectOf<S extends Shape> = Simplify<
  { [K in Exclude<keyof S, OptionalKeys<S>>]: Infer<S[K]> } & {
    [K in OptionalKeys<S>]?: Infer<S[K]>;
  }
>;

function object<S extends Shape>(shape: S): Schema<ObjectOf<S>> {
  return {
    parse(value, path = "") {
      if (typeof value !== "object" || value === null) {
        throw new ValidationError(path, "an object", value);
      }
      const input = value as Record<string, unknown>;
      const result: Record<string, unknown> = {};
      for (const key in shape) {
        const where = path ? `${path}.${key}` : key;
        const parsed = shape[key].parse(input[key], where);
        if (parsed !== undefined) result[key] = parsed;
      }
      return result as ObjectOf<S>;
    },
  };
}

const NewTodo = object({ title: string(), done: optional(boolean()) });
type NewTodo = Infer<typeof NewTodo>;
// { title: string; done?: boolean | undefined }

const draft: NewTodo = { title: "Nap" }; // done можно не указывать
console.log(NewTodo.parse(draft));
console.log(NewTodo.parse({ title: "Nap", done: true, admin: true }));
try {
  NewTodo.parse({ title: "Nap", done: "yes" }, "body");
} catch (error) {
  if (error instanceof ValidationError) console.log(error.message);
}
```

</CodeExample>

`OptionalKeys` — это идиома `{ ... }[keyof S]` из урока [Шаблонные литеральные типы](/learn/typescript/template-literal-types): строим объект с записью для каждого ключа, а затем индексируем его и получаем объединение ключей, чья схема говорит `optional: true`. Во время выполнения `object()` пропускает ключи со значением `undefined`, поэтому у `{ title: 'Nap' }` не вырастает `done: undefined`, и тела запросов, которые мы отправим позже, остаются чистыми. И, как раньше, ключи, которых нет в форме (`admin`), внутрь не попадают.

Есть ещё одна маленькая схема: `DELETE` отвечает **204 No Content**, а клиент читает это как `null`, поэтому `nothing()` принимает ровно `null` — как в итоговом проекте Уровня 2.

## Брендированные id, разобранные на границе

Все id учебного API — числа. Фильм 3 и задача 3 — разные вещи, но `number` их не различает, так что `panda.getMovie({ params: { id: todo.id } })` скомпилируется и тихо загрузит не то. Это именно тот баг, которому посвящён урок [Брендированные типы и типобезопасные API](/learn/typescript/branded-types-and-type-safe-apis), а наши схемы — идеальное место для бренда: **умный конструктор** (smart constructor), который одновременно является схемой.

<CodeExample output={`/movies/42 43
params.id: expected a TodoId, got 0
params.id: expected a TodoId, got 1.5
params.id: expected a TodoId, got "7"`}>

```ts
class ValidationError extends Error {
  constructor(path: string, expected: string, got: unknown) {
    const where = path || "value";
    super(`${where}: expected ${expected}, got ${JSON.stringify(got)}`);
    this.name = "ValidationError";
  }
}

type Schema<T> = { parse: (value: unknown, path?: string) => T };
type Infer<S extends Schema<unknown>> = ReturnType<S["parse"]>;

declare const brand: unique symbol;
type Brand<T, Name extends string> = T & { readonly [brand]: Name };

// Схема для id и единственный способ его создать
function brandedId<Name extends string>(
  name: Name,
): Schema<Brand<number, Name>> {
  return {
    parse(value, path = "") {
      const ok =
        typeof value === "number" &&
        Number.isSafeInteger(value) &&
        value > 0;
      if (!ok) throw new ValidationError(path, `a ${name}`, value);
      return value as Brand<number, Name>; // проверено чуть выше
    },
  };
}

// Одно имя для схемы (значения) и типа, который она создаёт
const MovieId = brandedId("MovieId");
type MovieId = Infer<typeof MovieId>;
const TodoId = brandedId("TodoId");
type TodoId = Infer<typeof TodoId>;

function moviePath(id: MovieId): string {
  return `/movies/${id}`;
}

// id извне (из URL, из формы) один раз проходит через parse
const fromUrl = "42";
const id = MovieId.parse(Number(fromUrl));
console.log(moviePath(id), id + 1);

for (const bad of [0, 1.5, "7"]) {
  try {
    TodoId.parse(bad, "params.id");
  } catch (error) {
    if (error instanceof ValidationError) console.log(error.message);
  }
}
```

</CodeExample>

- **`MovieId` — одновременно значение и тип.** Значение — это схема (и единственный способ создать id), тип — то, что она создаёт. Одно имя в разных пространствах имён: тот же приём, что `const Movie = z.object(...)` / `type Movie = z.infer<typeof Movie>` в zod.
- **id из ответов приходят уже брендированными, бесплатно.** Схема `Movie` использует `id: MovieId`, поэтому `movie.id` — это `MovieId`, `todo.id` — `TodoId`, и id переходят из одного вызова в другой, и никому не нужно разбирать их заново.
- **id извне один раз проходят через `parse`.** Число из URL или формы остаётся просто `number`, пока его не проверит `MovieId.parse`. `id + 1` — снова обычный `number`: арифметика намеренно сбрасывает бренды.

Теперь путаница — это ошибка компиляции, как и пропущенная проверка:

```ts
panda.getMovie({ params: { id: todo.id } });
// ❌ Error: Type 'Brand<number, "TodoId">' is not assignable to type 'Brand<number, "MovieId">'.

panda.getMovie({ params: { id: 1 } });
// ❌ Error: Type 'number' is not assignable to type 'Brand<number, "MovieId">'.
```

<Callout type="warning" title="Не выпускайте набор для подделки">

У пользователей будет соблазн написать `1 as MovieId`. На собственном код-ревью считайте это багом. В SDK сделайте честный путь простым: `MovieId.parse(1)` ничуть не длиннее, описан в README и говорит правду. Бренд, который по всей кодовой базе подделывают через `as`, хуже, чем никакого бренда, потому что непроверенные значения теперь **выглядят** проверенными.

</Callout>

## Одно описание для всего API

Теперь сердце дизайна. Контракт в уроке Уровня 2 [Общие типы](/learn/typescript/sharing-types-between-client-and-server) был **типом**, поэтому исчезал во время выполнения, и клиенту приходилось доверять серверу. Наше описание — **значение**: у каждого эндпоинта есть метод, путь, схемы для его params, query и тела и схема для ответа. Клиент читает его во время выполнения, чтобы собирать запросы и проверять ответы, а компилятор читает его **тип**, чтобы вывести сигнатуру каждого метода.

Как мы его объявляем, важно не меньше, чем что в нём лежит. Три варианта вы знаете по уроку [Вариантность и вывод типов](/learn/typescript/variance-and-inference):

- **Аннотация** `const pandaApi: ApiDescription = { ... }` проверяет объект, а потом забывает его: ключи становятся `string`, а пути — `` `/${string}` ``. У клиента, выведенного из такого типа, есть метод для любой возможной строки, так что `panda.getMovei()` компилируется. Бесполезно.
- **`as const satisfies ApiDescription`** проверяет объект **и** сохраняет каждый ключ и литерал. Это работает.
- **Функция `defineApi`** с `const`-параметром типа делает то же, что `as const satisfies`, и может проверить ещё одну вещь, недоступную `satisfies`: что `params` каждого эндпоинта совпадают с `:params` в **его собственном** пути.

Эта дополнительная проверка переиспользует `ParamNames` из урока [Шаблонные литеральные типы](/learn/typescript/template-literal-types), который достаёт имена параметров из строки пути:

<CodeExample output={`GET    /movies/:id getMovie
GET    /todos      listTodos
PATCH  /todos/:id  updateTodo`}>

```ts
type Schema<T> = { parse: (value: unknown, path?: string) => T };
// Заглушки вместо настоящих схем, чтобы пример был коротким
const id: Schema<number> = { parse: (value) => Number(value) };
const json: Schema<unknown> = { parse: (value) => value };

type Method = "GET" | "POST" | "PUT" | "PATCH" | "DELETE";

interface Endpoint {
  method: Method;
  path: `/${string}`;
  params?: Record<string, Schema<unknown>>;
  body?: Schema<unknown>;
  response: Schema<unknown>;
}
type ApiDescription = Record<string, Endpoint>;

type ParamNames<P extends string> =
  P extends `${string}:${infer Name}/${infer Rest}`
    ? Name | ParamNames<Rest>
    : P extends `${string}:${infer Name}`
      ? Name
      : never;

type ParamsFor<P extends string> = [ParamNames<P>] extends [never]
  ? {}
  : { params: Record<ParamNames<P>, Schema<string | number>> };

type CheckParams<A extends ApiDescription> = {
  [K in keyof A]: ParamsFor<A[K]["path"]>;
};

function defineApi<const A extends ApiDescription>(
  api: A & CheckParams<A>,
): A {
  return api;
}

const api = defineApi({
  getMovie: {
    method: "GET",
    path: "/movies/:id",
    params: { id },
    response: json,
  },
  listTodos: { method: "GET", path: "/todos", response: json },
  updateTodo: {
    method: "PATCH",
    path: "/todos/:id",
```

Тип параметра — `A & CheckParams<A>`. TypeScript выводит `A` из написанного вами объекта (`const` сохраняет каждый литерал), а затем проверяет тот же объект на соответствие `CheckParams<A>` — сопоставленному типу, который требует запись `params` с одной схемой на каждый `:name` в каждом пути. Поэтому переименованный параметр, забытые `params` или выдуманный метод дают ошибку прямо там, где вы их написали:

```ts
getMovie: {
  method: "GET",
  path: "/movies/:id",
  params: { movieId: MovieId },
  // ❌ Error: Type '{ movieId: Schema<Brand<number, "MovieId">>; }' is not assignable to type '{ readonly movieId: Schema<Brand<number, "MovieId">>; } & Record<"id", Schema<string | number>>'.
  response: Movie,
},
listTodos: { method: "FETCH", path: "/todos", response: array(Todo) },
// ❌ Error: Type '"FETCH"' is not assignable to type 'Method'.
```

Дочитайте первое сообщение до конца: `Record<"id", ...>` говорит, что путь хочет `id`. Не самое дружелюбное сообщение на свете, но оно указывает на правильную строку, и видят его только авторы самого SDK.

Тесты типов в примере тоже заслуживают пояснения. `Route` собирает `"PATCH /todos/:id"` из литеральных типов описания — доказательство, что по пути ничего не расширилось. Литералы здесь сохраняют две вещи: `const`-параметр типа и само ограничение, потому что TypeScript сохраняет литерал вроде `"GET"`, когда проверяет его на соответствие литеральным типам вроде `Method` или `` `/${string}` `` (поэтому и один `satisfies` сработал бы). `const` добавляет везде `readonly` и покрывает значения, которые ограничение не описывает. Тестам всё равно, кто сделал работу: что бы кто-то ни поменял позже, на выходе всё равно должно получаться `"PATCH /todos/:id"`.

## Выводим типы

Когда описание готово, каждый тип, который видят пользователи, — это **производная** от него. Начнём с ввода. Каждый эндпоинт вносит до трёх частей, и каждая часть — условный тип с `infer` из урока [Условные типы и infer](/learn/typescript/conditional-types-and-infer):

```ts
type ParamsInput<E> = E extends { params: infer P extends Shape }
  ? { params: ObjectOf<P> }
  : {};
```

Читайте так: «если у эндпоинта есть `params`, захватить их форму как `P` и потребовать `{ params: ... }` с типом, который создаёт каждая схема; иначе ничего не добавлять». `infer P extends Shape` захватывает и ограничивает за один шаг, поэтому `ObjectOf<P>` разрешён. `QueryInput` и `BodyInput` устроены так же, с одной особенностью для query: когда **все** поля query необязательные, весь `query` тоже должен быть необязательным. Проверка для этого — `{} extends Infer<Q>`: если пустой объект — допустимый query, никто не обязан его передавать.

Три части склеиваются вместе и выравниваются:

```ts
type Input<E extends Endpoint> = Simplify<
  ParamsInput<E> & QueryInput<E> & BodyInput<E>
>;
type Output<E extends Endpoint> = Infer<E["response"]>;

// Нет обязательного ввода: аргумент можно не передавать
type InputArgs<E extends Endpoint> = {} extends Input<E>
  ? [input?: Input<E>]
  : [input: Input<E>];

type Client<A extends ApiDescription> = {
  [K in keyof A]: (
    ...input: InputArgs<A[K]>
  ) => Promise<Result<Output<A[K]>, ApiError>>;
};
```

- **`InputArgs`** — это приём с rest-кортежем из упражнения с типизированным переводчиком в уроке про шаблонные литеральные типы: `panda.listTodos()` вообще не нужен аргумент, а `panda.getMovie()` без params — ошибка.
- **`Client<A>`** — один гомоморфный сопоставленный тип: по методу на эндпоинт, у каждого свой ввод и вывод. Поскольку он проходит по `keyof A`, он даже сохраняет JSDoc-комментарии описания, так что комментарий у записи `getMovie` появляется, когда пользователь наводит курсор на `panda.getMovie`.
- **`Result` и `ApiError`** проектируются сейчас, ещё до появления кода. Дизайн-документ, в котором прописаны типы сбоев, — способ договориться в команде об обработке ошибок, пока не стало поздно.

```ts
type Result<T, E> =
  | { ok: true; value: T }
  | { ok: false; error: E };

type ApiError =
  | { kind: "network"; message: string }
  | { kind: "http"; status: number; message: string }
  | { kind: "invalid-response"; message: string };
```

Вот что пользователи получают от всего этого — бесплатно и на каждом эндпоинте:

```ts
panda.getMovie();
// ❌ Error: Expected 1 arguments, but got 0.

panda.searchMovies({ query: { limit: "5" } });
// ❌ Error: Type 'string' is not assignable to type 'number'.

panda.createTodo({ body: { done: true } });
// ❌ Error: Property 'title' is missing in type '{ done: true; }' but required in type '{ title: string; done?: boolean | undefined; }'.

const movie = await panda.getMovie({ params: { id } });
movie.value;
// ❌ Error: Property 'value' does not exist on type 'Result<{ id: Brand<number, "MovieId">; title: string; year: number; director: string; genres: string[]; rating: number; minutes: number; }, ApiError>'.
```

Последнее сообщение показывает, как окупается дизайнерское решение. Поскольку `Output` берётся из схемы, подсказка показывает настоящую форму фильма, а не имя, которое пришлось бы искать.

## Тесты типов — это спецификация

Выведенные типы — настоящий продукт SDK, поэтому их тестируют, как любой продукт. Инструменты вы знаете по уроку [Тестирование типов](/learn/typescript/testing-types): `Expect<Equal<A, B>>` для «этот тип ровно такой» и `// @ts-expect-error` для «этот вызов **не** должен компилироваться». Вместе они превращают пункты дизайн-документа в то, что компилятор проверяет при каждом изменении:

```ts
type _tests = [
  Expect<Equal<Input<PandaApi["getMovie"]>,
    { params: { id: MovieId } }>>,
  Expect<Equal<Input<PandaApi["updateTodo"]>, {
    params: { id: TodoId };
    body: { title?: string; done?: boolean };
  }>>,
  Expect<Equal<Output<PandaApi["deleteTodo"]>, null>>,
];

async function typeTests(panda: Client<PandaApi>, todo: Todo) {
  await panda.listTodos(); // ничего не обязательно, поэтому без аргумента
  // @ts-expect-error: TodoId — это не MovieId
  await panda.getMovie({ params: { id: todo.id } });
}
```

Функция `typeTests` никогда не вызывается: её тело существует только для компилятора. Две привычки из этого модуля делают тесты типов полезными:

- **Тестируйте случаи ошибок.** Каждая строка `// @ts-expect-error` — это обещание из дизайн-документа («перепутанные id не компилируются»). Если рефакторинг сделает `Client` слишком свободным, например туда пролезет `any`, строка скомпилируется, и TypeScript сообщит *Unused '@ts-expect-error' directive.* Одни только строки «счастливого пути» этого бы не заметили.
- **Фиксируйте точные формы через `Equal`.** `Equal` нарочно строгий: `{ title?: string }` и `{ title: string | undefined }` — разные типы, и пересечение отличается от своей выровненной версии. Именно в этом разница между `object()` из Уровня 2 и нашим, и именно поэтому `Input` заканчивается на `Simplify`.

## От ввода к запросу

Последний кусочек части 1 — первый кусочек кода времени выполнения: `buildRequest(baseUrl, endpoint, input)` превращает запись описания и ввод вызывающего кода в простой объект запроса `{ method, url, headers, body }`. Он ничего не отправляет, поэтому его легко тестировать, а в части 2 клиент будет передавать его результат в `fetch`.

Его сигнатура показывает приём, который вы видели в типизированном эмиттере событий из урока про шаблонные литеральные типы: **точная поверхность поверх свободно типизированной начинки**. Вызывающий код никогда не вызывает `buildRequest` напрямую; он вызывает `panda.getMovie(...)`, у которого точные типы. Внутри ввод — просто `RawInput`, `{ params?: Record<string, unknown>; query?: unknown; body?: unknown }`, и каждая часть проверяется своей схемой во время выполнения. Это не паранойя: SDK будут вызывать из обычного JavaScript (где типы никто не проверяет) и из TypeScript с редким `as any` тут и там, а понятная `ValidationError` до отправки лучше, чем 400 от сервера.

Подстановка параметров пути показывает обе половины. Вот та же идея в виде маленькой функции, типизированной для вызывающих через `ParamNames`:

<CodeExample output={`/movies/7
/users/1/posts/2
/tags/sci-fi%20%26%20drama%2F2
/todos`}>

```ts
type ParamNames<P extends string> =
  P extends `${string}:${infer Name}/${infer Rest}`
    ? Name | ParamNames<Rest>
    : P extends `${string}:${infer Name}`
      ? Name
      : never;

// Точный тип для вызывающих, простой Record внутри
function fillPath<P extends string>(
  path: P,
  params: Record<ParamNames<P>, string | number>,
): string {
  const values: Record<string, string | number> = params;
  return path.replace(/:(\w+)/g, (_, name: string) =>
    encodeURIComponent(String(values[name])),
  );
}

console.log(fillPath("/movies/:id", { id: 7 }));
console.log(fillPath("/users/:userId/posts/:postId", {
  userId: 1,
  postId: 2,
}));
console.log(fillPath("/tags/:name", { name: "sci-fi & drama/2" }));
console.log(fillPath("/todos", {}));
```

</CodeExample>

`encodeURIComponent` обязателен: без него `"sci-fi & drama/2"` превратился бы в лишний сегмент пути и сломанный URL. Вызывающие получают точный тип — `Record<"id", string | number>` для `"/movies/:id"`; внутри `values` — обычный `Record<string, ...>`, а имена находит регулярное выражение. Неправильное имя ловится там, где его написали:

```ts
fillPath("/movies/:id", { movieId: 7 });
// ❌ Error: Object literal may only specify known properties, and 'movieId' does not exist in type 'Record<"id", string | number>'.
```

`buildRequest` делает то же со схемами `params` эндпоинта, так что значения тоже проверяются (`params.id: expected a MovieId, got "7"`). Затем он добавляет query и тело:

- **Query:** разобрать `input.query ?? {}` схемой query эндпоинта (путь `"query"`), положить каждое значение в `URLSearchParams` и дописать `?...`, только если там что-то есть. Поскольку `object()` отбрасывает значения `undefined`, `{ search: undefined, limit: 2 }` превращается просто в `?limit=2`.
- **Тело:** разобрать `input.body` схемой тела (путь `"body"`), отправить его как JSON и добавить заголовок `Content-Type: application/json`. Кроме того, каждый запрос просит JSON через `Accept: application/json`.

Постройте фундамент `@pandadev/sdk`. Библиотека схем (с `optional`, `nothing` и `brandedId`) и модели (`Movie`, `User`, `Post`, `Todo`, `NewTodo`, `TodoPatch` и четыре схемы id) готовы. Всё, что ниже, — ваше:

1. **`ParamNames<P>`**: имена `:params` в пути в виде объединения (`never` для пути без них). Это тип из урока [Шаблонные литеральные типы](/learn/typescript/template-literal-types).
2. **Остаток `pandaApi`**: `getUser` (`GET /users/:id`, params `{ id: UserId }`, ответ `User`), `listPosts` (`GET /posts`, необязательный query `userId` типа `UserId`, массив `Post`), `createTodo` (`POST /todos`, тело `NewTodo`, ответ `Todo`), `updateTodo` (`PATCH /todos/:id`, `TodoId`, тело `TodoPatch`, ответ `Todo`) и `deleteTodo` (`DELETE /todos/:id`, `TodoId`, без содержимого: `nothing()`).
3. **`ParamsInput`, `QueryInput` и `BodyInput`** и сопоставленный тип **`Client<A>`**, как в уроке.
4. **`buildRequest(baseUrl, endpoint, input)`**: подставьте `:params` (проверенные и закодированные), добавьте строку запроса (только если в ней что-то есть) и JSON-тело с его `Content-Type`. Каждая часть проверяется своей схемой с путями `params.<name>`, `query` и `body`, чтобы ошибки говорили, где проблема. Уберите завершающие слеши из `baseUrl`.
5. **Тесты для умного конструктора**: в пустом `describe("brandedId")` проверьте, что `MovieId.parse` принимает положительное целое число и отклоняет `0`, отрицательные числа, дроби и строки с ошибкой `ValidationError`.

Тесты типов внизу — это дизайн-документ в коде: стартовый код проваливает их все, поэтому не запустится, пока ваши типы не станут правильными. Дальше эстафету принимают тесты Vitest и проверки.

```ts
  constructor(path: string, expected: string, got: unknown) {

    super(`${where}: expected ${expected}, got ${JSON.stringify(got)}`);
    this.name = "ValidationError";
  }

type Schema<T> = {
  parse: (value: unknown, path?: string) => T;
  optional?: true;
};
type Infer<S extends Schema<unknown>> = ReturnType<S["parse"]>;
type Simplify<T> = { [K in keyof T]: T[K] } & {};

function primitive<T>(
  expected: string,
  test: (value: unknown) => value is T,
): Schema<T> {
  return {
    parse(value, path = "") {
      if (!test(value)) {
        throw new ValidationError(path, expected, value);
      }
      return value;
    },
  };
}

function array<T>(item: Schema<T>): Schema<T[]> {
  return {
    parse(value, path = "") {
      if (!Array.isArray(value)) {
        throw new ValidationError(path, "an array", value);
      }
      return value.map((v, i) => item.parse(v, `${path}[${i}]`));
    },
  };
}

function optional<T>(
  schema: Schema<T>,
): Schema<T | undefined> & { optional: true } {
  return {
    optional: true,
    parse: (value, path) =>
      value === undefined ? undefined : schema.parse(value, path),
  };
}

function isRecord(value: unknown): value is Record<string, unknown> {
  return (
    typeof value === "object" && value !== null && !Array.isArray(value)
  );
}

type Shape = Record<string, Schema<unknown>>;
// Ключи, чья схема — optional(...)
type OptionalKeys<S extends Shape> = {
  [K in keyof S]: S[K] extends { optional: true } ? K : never;
}[keyof S];
type ObjectOf<S extends Shape> = Simplify<
  { [K in Exclude<keyof S, OptionalKeys<S>>]: Infer<S[K]> } & {
    [K in OptionalKeys<S>]?: Infer<S[K]>;
  }
>;

function object<S extends Shape>(shape: S): Schema<ObjectOf<S>> {
  return {
    parse(value, path = "") {
      if (!isRecord(value)) {
        throw new ValidationError(path, "an object", value);
      }
      const result: Record<string, unknown> = {};
      for (const key in shape) {
        const where = path ? `${path}.${key}` : key;
        const parsed = shape[key].parse(value[key], where);
        if (parsed !== undefined) result[key] = parsed;
      }
      // каждый ключ проверен, так что это приведение безопасно
      return result as ObjectOf<S>;
    },
  };
}

  input: RawInput = {},
): SdkRequest {
  const path = endpoint.path.replace(/:(\w+)/g, (_, name: string) => {
    const schema = endpoint.params?.[name];
    if (!schema) throw new Error(`Нет схемы для :${name}`);
    const value = schema.parse(input.params?.[name], `params.${name}`);
    return encodeURIComponent(String(value));
  });
  let url = baseUrl.replace(/\/+$/, "") + path;
  if (endpoint.query) {
    const query = endpoint.query.parse(input.query ?? {}, "query");
    const search = new URLSearchParams();
    for (const [key, value] of Object.entries(query)) {
      search.set(key, String(value));
    }
    if (search.size > 0) url += `?${search}`;
  }
  const headers: Record<string, string> = {
    Accept: "application/json",
  };
  const request: SdkRequest = { method: endpoint.method, url, headers };
  if (endpoint.body) {
    const body = endpoint.body.parse(input.body, "body");
    request.body = JSON.stringify(body);
    headers["Content-Type"] = "application/json";
  }
  return request;
}
```

## Что вы построили

- **Дизайн-документ**: цели и не-цели, сначала место вызова и таблица решений, включая разделение на брошенные `ValidationError` для плохого ввода и значения `invalid-response` для плохих ответов.
- Библиотеку схем, которая понимает **необязательные поля** (`OptionalKeys`, `ObjectOf`), плюс `nothing()` для ответов 204.
- **Брендированные id**, чьи схемы — их умные конструкторы, так что id проверяются один раз и переходят брендированными из ответа в запрос.
- **`pandaApi`** — единое описание всего API, объявленное через `defineApi`, так что каждый литерал уцелел, а у каждого `:param` есть схема.
- **Выведенные типы**: `Input`, `Output` и сопоставленный `Client<A>`, всё из описания, а `Result` и `ApiError` спроектированы заранее.
- **Тесты типов**, которые закрепляют дизайн, и **`buildRequest`**, который проверяет ввод вызывающего кода и превращает его в запрос.

Сети пока не видно. В **части 2** описание станет работающим клиентом с типизированными ошибками, повторами с backoff, пагинацией и хуками. 🔌
