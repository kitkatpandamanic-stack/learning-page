The compiler already catches a whole family of bugs: a string where a number belongs, a missing property, a forgotten `null` check. So do you still need tests? Yes, because types and tests answer **different questions**. Types prove that the pieces **fit together**. Tests prove that the code **does the right thing**: that 10% off £4.50 is £4.05 and not £4.95. The compiler is perfectly happy with the wrong maths. 🧮

In this lesson you'll write Vitest tests in TypeScript, and make the tests themselves well typed: test data that can't drift away from your models, mocks that can't return nonsense, and helpers for code that returns `Result` types.

## Vitest runs TypeScript as it is

[Vitest](https://vitest.dev) is the most popular test runner for modern TypeScript projects. If you did the JavaScript testing module ([Your First Tests](/learn/javascript/first-tests)), everything you know still applies. In a real project you install it and put the tests next to the code, in files ending in `.test.ts`:

```bash
npm install --save-dev vitest
npx vitest        # watch mode: reruns the tests when you save
npx vitest run    # run once (what CI does)
```

```ts title="price.test.ts"
import { describe, it, expect } from "vitest";
import { priceLabel } from "./price";

describe("priceLabel", () => {
  it("formats pounds and pence", () => {
    expect(priceLabel(1250, "GBP")).toBe("£12.50");
  });
});
```

No build step and no config: Vitest strips the types and runs the file. In this editor the code under test and its tests live in one file, and the tests run after the code, like `vitest run`:

<CodeExample output={`✓ priceLabel > formats pounds and pence
✓ priceLabel > pads small amounts

Tests  2 passed (2)`}>

```ts
import { describe, it, expect } from "vitest";

type Currency = "GBP" | "EUR";

function priceLabel(cents: number, currency: Currency): string {
  const symbol = currency === "GBP" ? "£" : "€";
  return `${symbol}${(cents / 100).toFixed(2)}`;
}

describe("priceLabel", () => {
  it("formats pounds and pence", () => {
    expect(priceLabel(1250, "GBP")).toBe("£12.50");
  });

  it("pads small amounts", () => {
    expect(priceLabel(5, "EUR")).toBe("€0.05");
  });
});
```

</CodeExample>

The **test file is type-checked too**, so a test can't call the code the wrong way:

```ts
priceLabel(1250, "USD");
// ❌ Error: Argument of type '"USD"' is not assignable to parameter of type 'Currency'.
priceLabel("12.50", "GBP");
// ❌ Error: Argument of type 'string' is not assignable to parameter of type 'number'.
```

That changes **what is worth testing**. In plain JavaScript you might write a test for "what if someone passes a string?". In TypeScript, code inside your project can't do that, so don't spend tests on it, and don't write tests like `expect(typeof priceLabel(5, "EUR")).toBe("string")`: the return type already says so. Spend your tests on **behaviour**: calculations, rules, rounding, edge cases and error paths. (Data from **outside** your program, like JSON from an API, is a different story: there the types are only a promise, and you test the code that [validates it](/learn/typescript/runtime-validation).)

<Callout type="warning" title="Vitest doesn't type-check your tests">

When Vitest strips the types, it doesn't check them. On your machine, a test file full of type errors still runs, and may even pass. The PandaDev editor checks types before running, but in a real project you run the type checker separately: `npx tsc --noEmit` checks every file without producing any output, and CI runs it next to `vitest run`. [Testing Types](/learn/typescript/testing-types) shows the full setup.

</Callout>

## Test data factories

Real models have many fields, and most tests care about only one or two of them. Writing a complete object in every test is noisy, and it's fragile. Add one required field to `User` and every test that builds a user breaks with the same error:

```ts
const mei: User = {
  id: "user-1",
  name: "Mei",
  email: "mei@pandadev.test",
  role: "member",
  plan: "free",
};
// ❌ Error: Property 'joined' is missing in type '{ id: string; name: string; email: string; role: "member"; plan: "free"; }' but required in type 'User'.
```

The fix most larger codebases use is a **test data factory**: a function that returns a complete, valid object with sensible defaults, and takes **overrides** for the fields a test cares about. The [utility type](/learn/typescript/utility-types) **`Partial<User>`** makes every property optional, which is exactly the type of "some fields to change":

<CodeExample output={`{
  id: 'user-1',
  name: 'Mei',
  email: 'mei@pandadev.test',
  role: 'member',
  plan: 'pro',
  joined: '2026-01-15'
}
✓ canExport > lets pro users export
✓ canExport > lets admins export, even on the free plan
✓ canExport > stops free members

Tests  3 passed (3)`}>

```ts
import { describe, it, expect } from "vitest";

interface User {
  id: string;
  name: string;
  email: string;
  role: "admin" | "member";
  plan: "free" | "pro";
  joined: string; // ISO date, e.g. "2026-01-15"
}

// The code under test
function canExport(user: User): boolean {
  return user.role === "admin" || user.plan === "pro";
}

// A test data factory: sensible defaults, override what matters
function makeUser(overrides: Partial<User> = {}): User {
  return {
    id: "user-1",
    name: "Mei",
    email: "mei@pandadev.test",
    role: "member",
    plan: "free",
    joined: "2026-01-15",
    ...overrides,
  };
}

console.log(makeUser({ plan: "pro" }));

describe("canExport", () => {
  it("lets pro users export", () => {
    expect(canExport(makeUser({ plan: "pro" }))).toBe(true);
  });

  it("lets admins export, even on the free plan", () => {
    expect(canExport(makeUser({ role: "admin" }))).toBe(true);
  });

  it("stops free members", () => {
    expect(canExport(makeUser())).toBe(false);
  });
});
```

</CodeExample>

Look at what the tests say now: `makeUser({ plan: "pro" })` reads as "a user, any user, who is on the pro plan". The detail that matters for the test is the only detail you see. And the factory is typed, so overrides are checked like any other code:

```ts
makeUser({ plan: "gold" });
// ❌ Error: Type '"gold"' is not assignable to type '"free" | "pro" | undefined'.
makeUser({ nmae: "Bao" });
// ❌ Error: Object literal may only specify known properties, and 'nmae' does not exist in type 'Partial<User>'.
```

When `User` gets a new required field, you add one default to `makeUser`, and every test keeps working. The explicit return type `: User` matters here: it makes the compiler check that the defaults really form a complete `User`.

<Callout type="note" title="Two things Partial won't catch">

- `Partial` is **shallow**. For a nested object such as `address`, an override replaces the whole nested object, so pass a complete one (or give the factory its own `makeAddress`).
- `makeUser({ name: undefined })` compiles, and the spread then overwrites the default with `undefined`. The compiler flag `exactOptionalPropertyTypes` turns that into an error. Without it, simply don't pass `undefined` overrides.

In real projects, teams with many models often use a factory library (such as fishery) or generate realistic values with `@faker-js/faker`. The idea is the same: one place that knows how to build a valid object.

</Callout>

## Typed mocks with vi.fn

A **mock function** from `vi.fn()` stands in for a dependency and records every call. Without a type, Vitest has to assume the most general function there is, `(...args: any[]) => any`, and `any` switches the compiler off for everything it touches:

```ts
const loose = vi.fn().mockResolvedValue({ name: "Mei" });
const user = await loose("u1");
// Compiles! (and crashes when it runs)
console.log(user.emial.toLowerCase());
```

So give the mock the **type of the function it replaces**: `vi.fn<(id: string) => Promise<User>>()`. Even better, name the dependency's type once and use the name in the code **and** in the tests, so they can never disagree:

<CodeExample output={`MEI@PANDADEV.TEST / Welcome, Mei!
✓ welcome > emails the user
✓ welcome > does nothing for unknown users

Tests  2 passed (2)`}>

```ts
import { describe, it, expect, vi } from "vitest";

interface User {
  id: string;
  name: string;
  email: string;
}

type LoadUser = (id: string) => Promise<User | undefined>;
type SendEmail = (to: string, text: string) => Promise<void>;

// The code under test: both dependencies are passed in
async function welcome(
  id: string,
  deps: { loadUser: LoadUser; sendEmail: SendEmail },
): Promise<boolean> {
  const user = await deps.loadUser(id);
  if (!user) return false;
  await deps.sendEmail(user.email, `Welcome, ${user.name}!`);
  return true;
}

describe("welcome", () => {
  it("emails the user", async () => {
    const loadUser = vi.fn<LoadUser>().mockResolvedValue({
      id: "u1",
      name: "Mei",
      email: "mei@pandadev.test",
    });
    const sendEmail = vi.fn<SendEmail>().mockResolvedValue();

    expect(await welcome("u1", { loadUser, sendEmail })).toBe(true);

    const [to, text] = sendEmail.mock.calls[0];
    console.log(to.toUpperCase(), "/", text);
    expect(loadUser).toHaveBeenCalledWith("u1");
  });

  it("does nothing for unknown users", async () => {
    const loadUser = vi.fn<LoadUser>().mockResolvedValue(undefined);
    const sendEmail = vi.fn<SendEmail>();

    expect(await welcome("u9", { loadUser, sendEmail })).toBe(false);
    expect(sendEmail).not.toHaveBeenCalled();
  });
});
```

</CodeExample>

The typed mock pays off in three places:

- **What it returns is checked.** `mockResolvedValue` wants exactly what the real function resolves to, so a half-made user is caught before the test runs.
- **How it's called is checked.** The code can only call it with the right arguments.
- **Its calls are typed.** `sendEmail.mock.calls[0]` is a `[to: string, text: string]` tuple, so `to.toUpperCase()` is safe and autocompleted.

```ts
const loadUser = vi.fn<LoadUser>().mockResolvedValue({ name: "Mei" });
// ❌ Error: Argument of type '{ name: string; }' is not assignable to parameter of type 'User'.
```

There are a few more ways to say which function a mock replaces:

- `vi.fn((a: number) => a * 2)`: with an implementation, the type is inferred from it.
- `vi.fn<typeof sendWelcome>()`: borrow the type of a real function with `typeof`.
- `vi.fn<Mailer["send"]>()`: borrow the type of a method from an interface (an indexed access type).

When a mock lives in a variable that `beforeEach` refills, annotate the variable with the **`Mock`** type from Vitest:

```ts
import { beforeEach, vi, type Mock } from "vitest";

type SendEmail = (to: string, text: string) => Promise<void>;

let sendEmail: Mock<SendEmail>;

beforeEach(() => {
  sendEmail = vi.fn<SendEmail>(); // a fresh mock for every test
});
```

**`vi.spyOn(object, "method")`** is typed from the object, so it knows that `Math.random` returns a number. Spying on a misspelt method name is an error too:

<CodeExample output={`✓ turns the highest random number into 6

Tests  1 passed (1)`}>

```ts
import { it, expect, vi, afterEach } from "vitest";

function rollDie(): number {
  return Math.floor(Math.random() * 6) + 1;
}

afterEach(() => {
  vi.restoreAllMocks(); // put the real Math.random back
});

it("turns the highest random number into 6", () => {
  vi.spyOn(Math, "random").mockReturnValue(0.9999);
  expect(rollDie()).toBe(6);
});
```

</CodeExample>

```ts
vi.spyOn(Math, "random").mockReturnValue("0.5");
// ❌ Error: Argument of type 'string' is not assignable to parameter of type 'number'.
```

## Typed tables with it.each

**`it.each`** runs one test per row of a table, and TypeScript types the test function's parameters from the rows. There's one catch: in an array like `[0, "GBP", "£0.00"]`, TypeScript widens `"GBP"` to `string`, and a `string` isn't a `Currency`:

```ts
it.each([
  [0, "GBP", "£0.00"],
  [99, "EUR", "€0.99"],
])("formats %s %s as %s", (cents, currency, label) => {
  expect(priceLabel(cents, currency)).toBe(label);
  // ❌ Error: Argument of type 'string' is not assignable to parameter of type 'Currency'.
});
```

Add **`as const`** to keep the literal types, or (often more readable) use **object rows** and name the row type once with `it.each<Case>`:

<CodeExample output={`✓ priceLabel > formats 0 GBP as £0.00
✓ priceLabel > formats 99 EUR as €0.99
✓ priceLabel > formats 1250 GBP as £12.50
✓ shows 5 in 'EUR' as '€0.05'
✓ shows 100000 in 'GBP' as '£1000.00'

Tests  5 passed (5)`}>

```ts
import { describe, it, expect } from "vitest";

type Currency = "GBP" | "EUR";

function priceLabel(cents: number, currency: Currency): string {
  const symbol = currency === "GBP" ? "£" : "€";
  return `${symbol}${(cents / 100).toFixed(2)}`;
}

describe("priceLabel", () => {
  // Tuple rows: each row is inferred as [number, Currency, string]
  it.each([
    [0, "GBP", "£0.00"],
    [99, "EUR", "€0.99"],
    [1250, "GBP", "£12.50"],
  ] as const)("formats %s %s as %s", (cents, currency, label) => {
    expect(priceLabel(cents, currency)).toBe(label);
  });
});

type Case = { cents: number; currency: Currency; label: string };

// Object rows: name the row type once
it.each<Case>([
  { cents: 5, currency: "EUR", label: "€0.05" },
  { cents: 100000, currency: "GBP", label: "£1000.00" },
])("shows $cents in $currency as $label", (row) => {
  expect(priceLabel(row.cents, row.currency)).toBe(row.label);
});
```

</CodeExample>

With a named row type, every row is checked like any object literal, so a typo in a table of fifty cases is caught at once:

```ts
it.each<Case>([
  { cents: 5, curency: "EUR", label: "€0.05" },
  // ❌ Error: Object literal may only specify known properties, but 'curency' does not exist in type 'Case'. Did you mean to write 'currency'?
])("shows $cents in $currency as $label", (row) => {
  expect(priceLabel(row.cents, row.currency)).toBe(row.label);
});
```

## Testing errors and Result types

Code can report failure in two ways, and each has its own style of test. For **thrown errors**, `toThrow` takes a message (part of it is enough) or an error **class**. A custom error class makes the test precise, because it can't be confused with an unrelated `TypeError`:

<CodeExample output={`✓ parseQuantity > parses whole numbers
✓ parseQuantity > rejects 0
✓ parseQuantity > rejects -2
✓ parseQuantity > rejects 1.5
✓ parseQuantity > rejects lots
✓ parseQuantity > says what was wrong

Tests  6 passed (6)`}>

```ts
import { describe, it, expect } from "vitest";

class QuantityError extends Error {
  constructor(public readonly input: string) {
    super(`Not a valid quantity: "${input}"`);
    this.name = "QuantityError";
  }
}

function parseQuantity(input: string): number {
  const n = Number(input);
  if (!Number.isInteger(n) || n < 1) {
    throw new QuantityError(input);
  }
  return n;
}

describe("parseQuantity", () => {
  it("parses whole numbers", () => {
    expect(parseQuantity("3")).toBe(3);
  });

  it.each(["0", "-2", "1.5", "lots"])("rejects %s", (input) => {
    expect(() => parseQuantity(input)).toThrow(QuantityError);
  });

  it("says what was wrong", () => {
    expect(() => parseQuantity("lots")).toThrow('"lots"');
  });
});
```

</CodeExample>

Typed code often **returns** its errors instead, as a `Result` union, `{ ok: true; value: T } | { ok: false; error: E }`, like the one in [Typed Fetch](/learn/typescript/typed-fetch). Then the error cases are part of the signature, and a test checks them like any other value. Comparing the whole result with `toEqual` is the simplest test and checks everything at once.

When you want to dig into the value, though, you hit a wall. Vitest's `expect` checks things **at runtime**, but the compiler doesn't know what an `expect` proved:

```ts
const result = validateSignup("Mei@PandaDev.test", "bamboo42");
expect(result.ok).toBe(true);
expect(result.value.email).toBe("mei@pandadev.test");
// ❌ Error: Property 'value' does not exist on type 'Result<{ email: string; }, string>'.
```

The tidy fix is a pair of small **test helpers** that narrow the result and hand back the inside, or fail the test with a useful message:

<CodeExample output={`✓ validateSignup > accepts a valid signup and lowercases the email
✓ validateSignup > reports a missing email
✓ validateSignup > reports a short password
× validateSignup > shows a helpful message when the helper fails
  → Error: Expected ok, got {"kind":"missing","field":"email"}

Tests  1 failed | 3 passed (4)`}>

```ts
import { describe, it, expect } from "vitest";

type Result<T, E> = { ok: true; value: T } | { ok: false; error: E };

type SignupError =
  | { kind: "missing"; field: "email" | "password" }
  | { kind: "too-short"; min: number };

type Signup = { email: string; password: string };

function validateSignup(
  email: string,
  password: string,
): Result<Signup, SignupError> {
  if (email === "") {
    return { ok: false, error: { kind: "missing", field: "email" } };
  }
  if (password === "") {
    return { ok: false, error: { kind: "missing", field: "password" } };
  }
  if (password.length < 8) {
    return { ok: false, error: { kind: "too-short", min: 8 } };
  }
  return { ok: true, value: { email: email.toLowerCase(), password } };
}

// Test helpers: hand back the value (or error), or fail the test
function expectOk<T, E>(result: Result<T, E>): T {
  if (!result.ok) {
    const error = JSON.stringify(result.error);
    throw new Error(`Expected ok, got ${error}`);
  }
  return result.value;
}

function expectErr<T, E>(result: Result<T, E>): E {
  if (result.ok) {
    const value = JSON.stringify(result.value);
    throw new Error(`Expected an error, got ${value}`);
  }
  return result.error;
}

describe("validateSignup", () => {
  it("accepts a valid signup and lowercases the email", () => {
    const result = validateSignup("Mei@PandaDev.test", "bamboo42");
    const signup = expectOk(result);
    expect(signup.email).toBe("mei@pandadev.test");
  });

  it("reports a missing email", () => {
    expect(validateSignup("", "bamboo42")).toEqual({
      ok: false,
      error: { kind: "missing", field: "email" },
    });
  });

  it("reports a short password", () => {
    const error = expectErr(validateSignup("mei@pandadev.test", "abc"));
    expect(error).toEqual({ kind: "too-short", min: 8 });
  });

  it("shows a helpful message when the helper fails", () => {
    expectOk(validateSignup("", "abc"));
  });
});
```

</CodeExample>

The last test fails on purpose, to show what you'd see: not a vague "expected false to be true", but the actual error that came back. Inside the helpers an ordinary `if` narrows the union, so `expectOk` returns a real `Signup` and the test gets autocomplete on `signup.email`. Helpers like these usually live in a shared `test-utils.ts` file.

<Callout type="tip" title="One test per error variant">

A union like `SignupError` is a checklist: every `kind` is a situation the code promises to report. Write at least one test per variant, and when someone adds a new variant, the missing test is easy to spot in review. If you need to call a function with a **wrong** type on purpose (say, to test how it treats bad input from plain JavaScript), [Testing Types](/learn/typescript/testing-types) shows the safe way to do it.

</Callout>

A shop's checkout works out the order total (with coupons) and then charges the customer through an injected `charge` function. Both return `Result` values. Write the tests, without changing the code under test. The checks will sneak eight different bugs into it, and your tests must catch every one.

1. **Type the factory.** `makeOrder` doesn't compile yet: give `overrides` the type `Partial<Order>` with a default of `{}`, and give the function the return type `Order`.
2. **Test `orderTotal`** with an `it.each` table (object rows with a named row type work well). Cover: the default order (£4.50 = `450`), an item with `qty: 3`, the `PANDA10` coupon (10% off), and a total where the discount leaves half a penny, which must be rounded to the **nearest** penny (`HALF` on an item of `999` gives `500`). Then test both errors: an empty order, and the unknown coupon `"FREE"` (check the whole error, including the coupon).
3. **Test `checkout`** with typed mocks made by `vi.fn<Charge>()`: it charges the order's **email** with the total and resolves to the receipt; a declined payment comes back as a `payment-declined` error with the **reason** from `charge`; and an invalid order is never charged.

You need at least **6** passing tests (each `it.each` row counts as one).

<Hint>

The factory: `function makeOrder(overrides: Partial<Order> = {}): Order { ... }`. A table: `type TotalCase = { name: string; order: Partial<Order>; total: number };` then `it.each<TotalCase>([{ name: "one item", order: {}, total: 450 }, ...])("totals $name", ({ order, total }) => { expect(orderTotal(makeOrder(order))).toEqual({ ok: true, value: total }); });`. For checkout: `const charge = vi.fn<Charge>().mockResolvedValue({ ok: true, receipt: "r-77" });`, then `await checkout(makeOrder({ coupon: "HALF" }), charge)` and `expect(charge).toHaveBeenCalledWith("mei@pandadev.test", 225)`. For the invalid order, use `vi.fn<Charge>()` and `expect(charge).not.toHaveBeenCalled()`.

import { describe, it, expect, vi } from "vitest";

// ---- The code under test (don't change it) ----
// Prices are in pence
type Item = { sku: string; price: number; qty: number };

interface Order {
  id: string;
  email: string;
  items: Item[];
  coupon: string | null;
}

type Result<T, E> = { ok: true; value: T } | { ok: false; error: E };

type CheckoutError =
  | { kind: "empty-order" }
  | { kind: "unknown-coupon"; coupon: string }
  | { kind: "payment-declined"; reason: string };

// Coupon code → percent off
const COUPONS = new Map([
  ["PANDA10", 10],
  ["HALF", 50],
]);

function orderTotal(order: Order): Result<number, CheckoutError> {
  if (order.items.length === 0) {
    return { ok: false, error: { kind: "empty-order" } };
  }
  let total = 0;
  for (const item of order.items) {
    total += item.price * item.qty;
  }
  if (order.coupon === null) {
    return { ok: true, value: total };
  }
  const percent = COUPONS.get(order.coupon);
  if (percent === undefined) {
    const coupon = order.coupon;
    return { ok: false, error: { kind: "unknown-coupon", coupon } };
  }
  const discounted = (total * (100 - percent)) / 100;
  return { ok: true, value: Math.round(discounted) };
}

type Payment =
  | { ok: true; receipt: string }
  | { ok: false; reason: string };
type Charge = (email: string, pence: number) => Promise<Payment>;

async function checkout(
  order: Order,
  charge: Charge,
): Promise<Result<string, CheckoutError>> {
  const total = orderTotal(order);
  if (!total.ok) return total;
  const payment = await charge(order.email, total.value);
  if (!payment.ok) {
    const reason = payment.reason;
    return { ok: false, error: { kind: "payment-declined", reason } };
  }
  return { ok: true, value: payment.receipt };
}

// ---- Your tests ----
function makeOrder(overrides: Partial<Order> = {}): Order {
  return {
    id: "order-1",
    email: "mei@pandadev.test",
    items: [{ sku: "tea", price: 450, qty: 1 }],
    coupon: null,
    ...overrides,
  };
}

type TotalCase = {
  name: string;
  order: Partial<Order>;
  total: number;
};

describe("orderTotal", () => {
  it.each<TotalCase>([
    { name: "one item", order: {}, total: 450 },
    {
      name: "a quantity",
      order: { items: [{ sku: "tea", price: 450, qty: 3 }] },
      total: 1350,
    },
    { name: "PANDA10", order: { coupon: "PANDA10" }, total: 405 },
    {
      name: "HALF, rounded",
      order: {
        items: [{ sku: "mug", price: 999, qty: 1 }],
        coupon: "HALF",
      },
      total: 500,
    },
  ])("totals $name", ({ order, total }) => {
    const result = orderTotal(makeOrder(order));
    expect(result).toEqual({ ok: true, value: total });
  });

  it("rejects an empty order", () => {
    expect(orderTotal(makeOrder({ items: [] }))).toEqual({
      ok: false,
      error: { kind: "empty-order" },
    });
  });

  it("rejects an unknown coupon", () => {
    expect(orderTotal(makeOrder({ coupon: "FREE" }))).toEqual({
      ok: false,
      error: { kind: "unknown-coupon", coupon: "FREE" },
    });
  });
});

describe("checkout", () => {
  it("charges the customer the total", async () => {
    const charge = vi.fn<Charge>().mockResolvedValue({
      ok: true,
      receipt: "r-77",
    });
    const order = makeOrder({
      email: "bao@pandadev.test",
      coupon: "HALF",
    });

    const result = await checkout(order, charge);

    expect(result).toEqual({ ok: true, value: "r-77" });
    expect(charge).toHaveBeenCalledTimes(1);
    expect(charge).toHaveBeenCalledWith("bao@pandadev.test", 225);
  });

  it("reports a declined payment", async () => {
    const charge = vi.fn<Charge>().mockResolvedValue({
      ok: false,
      reason: "Card expired",
    });
    const result = await checkout(makeOrder(), charge);
    expect(result).toEqual({
      ok: false,
      error: { kind: "payment-declined", reason: "Card expired" },
    });
  });

  it("doesn't charge an invalid order", async () => {
    const charge = vi.fn<Charge>();
    const result = await checkout(makeOrder({ items: [] }), charge);
    expect(result.ok).toBe(false);
    expect(charge).not.toHaveBeenCalled();
  });
});

## Recap

- Types prove the pieces fit; tests prove the behaviour is right. Don't test what the compiler already guarantees; test logic, edge cases and error paths.
- Vitest runs `.test.ts` files directly but **doesn't type-check** them: run `tsc --noEmit` as well.
- A **test data factory** like `makeUser(overrides: Partial<User> = {}): User` keeps tests short and survives model changes. Mind that `Partial` is shallow.
- Type your mocks: `vi.fn<SendEmail>()`, `vi.fn<typeof realFn>()` or `vi.fn<Mailer["send"]>()`. Then return values, calls and `mock.calls` are all checked. Use `Mock<T>` for mock variables; `vi.spyOn` is typed from the object.
- In `it.each`, keep literal types with `as const`, or use object rows with a named row type: `it.each<Case>([...])`.
- Test thrown errors with `toThrow(ErrorClass)` or a message; test `Result` values with `toEqual`, or with `expectOk`/`expectErr` helpers that narrow the union.
