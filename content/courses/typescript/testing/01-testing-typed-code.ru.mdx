Компилятор уже ловит целое семейство багов: строку там, где нужно число, отсутствующее свойство, забытую проверку на `null`. Так нужны ли ещё тесты? Да, потому что типы и тесты отвечают на **разные вопросы**. Типы доказывают, что детали **стыкуются друг с другом**. Тесты доказывают, что код **делает то, что нужно**: что скидка 10% с £4.50 — это £4.05, а не £4.95. Неправильная арифметика компилятор вполне устраивает. 🧮

В этом уроке вы будете писать тесты Vitest на TypeScript и сделаете хорошо типизированными сами тесты: тестовые данные, которые не могут разойтись с моделями, моки, которые не могут вернуть чепуху, и помощники для кода, возвращающего типы `Result`.

## Vitest запускает TypeScript как есть

[Vitest](https://vitest.dev) — самый популярный запускатель тестов (test runner) для современных проектов на TypeScript. Если вы проходили модуль о тестировании в курсе JavaScript ([Ваши первые тесты](/learn/javascript/first-tests)), всё, что вы знаете, по-прежнему работает. В реальном проекте его устанавливают, а тесты кладут рядом с кодом в файлы с окончанием `.test.ts`:

```bash
npm install --save-dev vitest
npx vitest        # режим наблюдения: перезапускает тесты при сохранении
npx vitest run    # один прогон (так делает CI)
```

```ts title="price.test.ts"
import { describe, it, expect } from "vitest";
import { priceLabel } from "./price";

describe("priceLabel", () => {
  it("форматирует фунты и пенсы", () => {
    expect(priceLabel(1250, "GBP")).toBe("£12.50");
  });
});
```

Ни шага сборки, ни настройки: Vitest стирает типы и запускает файл. В этом редакторе тестируемый код и его тесты живут в одном файле, а тесты запускаются после кода, как при `vitest run`:

<CodeExample output={`✓ priceLabel > форматирует фунты и пенсы
✓ priceLabel > дополняет нулями маленькие суммы

Tests  2 passed (2)`}>

```ts
import { describe, it, expect } from "vitest";

type Currency = "GBP" | "EUR";

function priceLabel(cents: number, currency: Currency): string {
  const symbol = currency === "GBP" ? "£" : "€";
  return `${symbol}${(cents / 100).toFixed(2)}`;
}

describe("priceLabel", () => {
  it("форматирует фунты и пенсы", () => {
    expect(priceLabel(1250, "GBP")).toBe("£12.50");
  });

  it("дополняет нулями маленькие суммы", () => {
    expect(priceLabel(5, "EUR")).toBe("€0.05");
  });
});
```

</CodeExample>

**Файл с тестами тоже проходит проверку типов**, так что тест не может вызвать код неправильно:

```ts
priceLabel(1250, "USD");
// ❌ Error: Argument of type '"USD"' is not assignable to parameter of type 'Currency'.
priceLabel("12.50", "GBP");
// ❌ Error: Argument of type 'string' is not assignable to parameter of type 'number'.
```

Это меняет то, **что стоит тестировать**. В обычном JavaScript вы могли бы написать тест «а что, если кто-то передаст строку?». В TypeScript код внутри проекта так сделать не может, так что не тратьте на это тесты и не пишите тестов вроде `expect(typeof priceLabel(5, "EUR")).toBe("string")`: возвращаемый тип уже говорит об этом. Тратьте тесты на **поведение**: вычисления, правила, округление, граничные случаи и пути ошибок. (С данными **извне** программы, например JSON из API, история другая: там типы — лишь обещание, и тестировать нужно код, который [их проверяет](/learn/typescript/runtime-validation).)

<Callout type="warning" title="Vitest не проверяет типы в ваших тестах">

Стирая типы, Vitest их не проверяет. На вашем компьютере файл тестов, полный ошибок типов, всё равно запустится и может даже пройти. Редактор PandaDev проверяет типы перед запуском, но в реальном проекте проверку типов запускают отдельно: `npx tsc --noEmit` проверяет все файлы, ничего не создавая, а CI запускает её рядом с `vitest run`. Полная настройка показана в уроке [Тестирование типов](/learn/typescript/testing-types).

</Callout>

## Фабрики тестовых данных

У настоящих моделей много полей, а большинству тестов важны лишь одно-два из них. Писать в каждом тесте полный объект — шумно и хрупко. Добавьте в `User` одно обязательное поле, и каждый тест, который создаёт пользователя, сломается с одной и той же ошибкой:

```ts
const mei: User = {
  id: "user-1",
  name: "Mei",
  email: "mei@pandadev.test",
  role: "member",
  plan: "free",
};
// ❌ Error: Property 'joined' is missing in type '{ id: string; name: string; email: string; role: "member"; plan: "free"; }' but required in type 'User'.
```

Решение, которым пользуется большинство крупных проектов, — **фабрика тестовых данных** (test data factory): функция, которая возвращает полный, корректный объект с разумными значениями по умолчанию и принимает **переопределения** (overrides) для полей, важных конкретному тесту. [Утилитный тип](/learn/typescript/utility-types) **`Partial<User>`** делает все свойства необязательными — это ровно тип «каких-то полей, которые нужно поменять»:

<CodeExample output={`{
  id: 'user-1',
  name: 'Mei',
  email: 'mei@pandadev.test',
  role: 'member',
  plan: 'pro',
  joined: '2026-01-15'
}
✓ canExport > разрешает экспорт пользователям pro
✓ canExport > разрешает экспорт админам, даже на бесплатном тарифе
✓ canExport > не пускает бесплатных участников

Tests  3 passed (3)`}>

```ts
import { describe, it, expect } from "vitest";

interface User {
  id: string;
  name: string;
  email: string;
  role: "admin" | "member";
  plan: "free" | "pro";
  joined: string; // дата ISO, например "2026-01-15"
}

// Тестируемый код
function canExport(user: User): boolean {
  return user.role === "admin" || user.plan === "pro";
}

// Фабрика тестовых данных: разумные значения по умолчанию,
// переопределяем то, что важно
function makeUser(overrides: Partial<User> = {}): User {
  return {
    id: "user-1",
    name: "Mei",
    email: "mei@pandadev.test",
    role: "member",
    plan: "free",
    joined: "2026-01-15",
    ...overrides,
  };
}

console.log(makeUser({ plan: "pro" }));

describe("canExport", () => {
  it("разрешает экспорт пользователям pro", () => {
    expect(canExport(makeUser({ plan: "pro" }))).toBe(true);
  });

  it("разрешает экспорт админам, даже на бесплатном тарифе", () => {
    expect(canExport(makeUser({ role: "admin" }))).toBe(true);
  });

  it("не пускает бесплатных участников", () => {
    expect(canExport(makeUser())).toBe(false);
  });
});
```

</CodeExample>

Посмотрите, что теперь говорят тесты: `makeUser({ plan: "pro" })` читается как «пользователь, любой, у которого тариф pro». Единственная деталь, которую вы видите, — та, что важна для теста. А раз фабрика типизирована, переопределения проверяются, как любой другой код:

```ts
makeUser({ plan: "gold" });
// ❌ Error: Type '"gold"' is not assignable to type '"free" | "pro" | undefined'.
makeUser({ nmae: "Bao" });
// ❌ Error: Object literal may only specify known properties, and 'nmae' does not exist in type 'Partial<User>'.
```

Когда у `User` появится новое обязательное поле, вы добавите одно значение по умолчанию в `makeUser`, и все тесты продолжат работать. Явный возвращаемый тип `: User` здесь важен: благодаря ему компилятор проверяет, что значения по умолчанию действительно образуют полный `User`.

<Callout type="note" title="Две вещи, которые Partial не поймает">

- `Partial` **поверхностный**. Для вложенного объекта, например `address`, переопределение заменяет весь вложенный объект целиком, так что передавайте его полностью (или заведите для фабрики свою `makeAddress`).
- `makeUser({ name: undefined })` компилируется, и spread затем затирает значение по умолчанию на `undefined`. Флаг компилятора `exactOptionalPropertyTypes` превращает это в ошибку. Без него просто не передавайте переопределения со значением `undefined`.

В реальных проектах команды с большим числом моделей часто используют библиотеку фабрик (например, fishery) или генерируют правдоподобные значения с помощью `@faker-js/faker`. Идея та же: одно место, которое знает, как собрать корректный объект.

</Callout>

## Типизированные моки с vi.fn

**Мок-функция** (mock function) из `vi.fn()` подменяет зависимость (dependency) и записывает каждый вызов. Без типа Vitest вынужден предполагать самую общую функцию из возможных, `(...args: any[]) => any`, а `any` отключает компилятор для всего, к чему прикасается:

```ts
const loose = vi.fn().mockResolvedValue({ name: "Mei" });
const user = await loose("u1");
// Компилируется! (и падает при запуске)
console.log(user.emial.toLowerCase());
```

Поэтому дайте моку **тип функции, которую он подменяет**: `vi.fn<(id: string) => Promise<User>>()`. А ещё лучше — один раз назовите тип зависимости и используйте это имя и в коде, **и** в тестах, чтобы они никогда не расходились:

<CodeExample output={`MEI@PANDADEV.TEST / Добро пожаловать, Mei!
✓ welcome > отправляет пользователю письмо
✓ welcome > ничего не делает для неизвестных пользователей

Tests  2 passed (2)`}>

```ts
import { describe, it, expect, vi } from "vitest";

interface User {
  id: string;
  name: string;
  email: string;
}

type LoadUser = (id: string) => Promise<User | undefined>;
type SendEmail = (to: string, text: string) => Promise<void>;

// Тестируемый код: обе зависимости передаются снаружи
async function welcome(
  id: string,
  deps: { loadUser: LoadUser; sendEmail: SendEmail },
): Promise<boolean> {
  const user = await deps.loadUser(id);
  if (!user) return false;
  await deps.sendEmail(user.email, `Добро пожаловать, ${user.name}!`);
  return true;
}

describe("welcome", () => {
  it("отправляет пользователю письмо", async () => {
    const loadUser = vi.fn<LoadUser>().mockResolvedValue({
      id: "u1",
      name: "Mei",
      email: "mei@pandadev.test",
    });
    const sendEmail = vi.fn<SendEmail>().mockResolvedValue();

    expect(await welcome("u1", { loadUser, sendEmail })).toBe(true);

    const [to, text] = sendEmail.mock.calls[0];
    console.log(to.toUpperCase(), "/", text);
    expect(loadUser).toHaveBeenCalledWith("u1");
  });

  it("ничего не делает для неизвестных пользователей", async () => {
    const loadUser = vi.fn<LoadUser>().mockResolvedValue(undefined);
    const sendEmail = vi.fn<SendEmail>();

    expect(await welcome("u9", { loadUser, sendEmail })).toBe(false);
    expect(sendEmail).not.toHaveBeenCalled();
  });
});
```

</CodeExample>

Типизированный мок окупается в трёх местах:

- **Проверяется, что он возвращает.** `mockResolvedValue` требует ровно то, чем выполняется настоящая функция, так что недоделанный пользователь ловится до запуска теста.
- **Проверяется, как его вызывают.** Код может вызвать его только с правильными аргументами.
- **Его вызовы типизированы.** `sendEmail.mock.calls[0]` — это кортеж `[to: string, text: string]`, так что `to.toUpperCase()` безопасен и автодополняется.

```ts
const loadUser = vi.fn<LoadUser>().mockResolvedValue({ name: "Mei" });
// ❌ Error: Argument of type '{ name: string; }' is not assignable to parameter of type 'User'.
```

Есть ещё несколько способов сказать, какую функцию подменяет мок:

- `vi.fn((a: number) => a * 2)`: если есть реализация, тип выводится из неё.
- `vi.fn<typeof sendWelcome>()`: позаимствуйте тип настоящей функции через `typeof`.
- `vi.fn<Mailer["send"]>()`: позаимствуйте тип метода из интерфейса (индексный тип доступа).

Если мок хранится в переменной, которую заново заполняет `beforeEach`, аннотируйте переменную типом **`Mock`** из Vitest:

```ts
import { beforeEach, vi, type Mock } from "vitest";

type SendEmail = (to: string, text: string) => Promise<void>;

let sendEmail: Mock<SendEmail>;

beforeEach(() => {
  sendEmail = vi.fn<SendEmail>(); // свежий мок для каждого теста
});
```

**`vi.spyOn(object, "method")`** типизируется по объекту, так что он знает, что `Math.random` возвращает число. Шпионить за методом с опечаткой в имени — тоже ошибка:

<CodeExample output={`✓ превращает самое большое случайное число в 6

Tests  1 passed (1)`}>

```ts
import { it, expect, vi, afterEach } from "vitest";

function rollDie(): number {
  return Math.floor(Math.random() * 6) + 1;
}

afterEach(() => {
  vi.restoreAllMocks(); // возвращаем настоящий Math.random
});

it("превращает самое большое случайное число в 6", () => {
  vi.spyOn(Math, "random").mockReturnValue(0.9999);
  expect(rollDie()).toBe(6);
});
```

</CodeExample>

```ts
vi.spyOn(Math, "random").mockReturnValue("0.5");
// ❌ Error: Argument of type 'string' is not assignable to parameter of type 'number'.
```

## Типизированные таблицы с it.each

**`it.each`** запускает по одному тесту на каждую строку таблицы, а TypeScript типизирует параметры тестовой функции по этим строкам. Есть одна ловушка: в массиве вроде `[0, "GBP", "£0.00"]` TypeScript расширяет `"GBP"` до `string`, а `string` — это не `Currency`:

```ts
it.each([
  [0, "GBP", "£0.00"],
  [99, "EUR", "€0.99"],
])("форматирует %s %s как %s", (cents, currency, label) => {
  expect(priceLabel(cents, currency)).toBe(label);
  // ❌ Error: Argument of type 'string' is not assignable to parameter of type 'Currency'.
});
```

Добавьте **`as const`**, чтобы сохранить литеральные типы, или (часто это читается лучше) используйте **строки-объекты** и один раз назовите тип строки через `it.each<Case>`:

<CodeExample output={`✓ priceLabel > форматирует 0 GBP как £0.00
✓ priceLabel > форматирует 99 EUR как €0.99
✓ priceLabel > форматирует 1250 GBP как £12.50
✓ показывает 5 в 'EUR' как '€0.05'
✓ показывает 100000 в 'GBP' как '£1000.00'

Tests  5 passed (5)`}>

```ts
import { describe, it, expect } from "vitest";

type Currency = "GBP" | "EUR";

function priceLabel(cents: number, currency: Currency): string {
  const symbol = currency === "GBP" ? "£" : "€";
  return `${symbol}${(cents / 100).toFixed(2)}`;
}

describe("priceLabel", () => {
  // Строки-кортежи: каждая выводится как [number, Currency, string]
  it.each([
    [0, "GBP", "£0.00"],
    [99, "EUR", "€0.99"],
    [1250, "GBP", "£12.50"],
  ] as const)("форматирует %s %s как %s", (cents, currency, label) => {
    expect(priceLabel(cents, currency)).toBe(label);
  });
});

type Case = { cents: number; currency: Currency; label: string };

// Строки-объекты: тип строки называем один раз
it.each<Case>([
  { cents: 5, currency: "EUR", label: "€0.05" },
  { cents: 100000, currency: "GBP", label: "£1000.00" },
])("показывает $cents в $currency как $label", (row) => {
  expect(priceLabel(row.cents, row.currency)).toBe(row.label);
});
```

</CodeExample>

С именованным типом строки каждая строка проверяется, как любой объектный литерал, так что опечатка в таблице из пятидесяти случаев ловится сразу:

```ts
it.each<Case>([
  { cents: 5, curency: "EUR", label: "€0.05" },
  // ❌ Error: Object literal may only specify known properties, but 'curency' does not exist in type 'Case'. Did you mean to write 'currency'?
])("показывает $cents в $currency как $label", (row) => {
  expect(priceLabel(row.cents, row.currency)).toBe(row.label);
});
```

## Тестирование ошибок и типов Result

Код может сообщить о сбое двумя способами, и для каждого свой стиль тестов. Для **брошенных ошибок** `toThrow` принимает сообщение (достаточно его части) или **класс** ошибки. Собственный класс ошибки делает тест точным, потому что его не спутать с посторонним `TypeError`:

<CodeExample output={`✓ parseQuantity > разбирает целые числа
✓ parseQuantity > отклоняет 0
✓ parseQuantity > отклоняет -2
✓ parseQuantity > отклоняет 1.5
✓ parseQuantity > отклоняет lots
✓ parseQuantity > сообщает, что было не так

Tests  6 passed (6)`}>

```ts
import { describe, it, expect } from "vitest";

class QuantityError extends Error {
  constructor(public readonly input: string) {
    super(`Некорректное количество: "${input}"`);
    this.name = "QuantityError";
  }
}

function parseQuantity(input: string): number {
  const n = Number(input);
  if (!Number.isInteger(n) || n < 1) {
    throw new QuantityError(input);
  }
  return n;
}

describe("parseQuantity", () => {
  it("разбирает целые числа", () => {
    expect(parseQuantity("3")).toBe(3);
  });

  it.each(["0", "-2", "1.5", "lots"])("отклоняет %s", (input) => {
    expect(() => parseQuantity(input)).toThrow(QuantityError);
  });

  it("сообщает, что было не так", () => {
    expect(() => parseQuantity("lots")).toThrow('"lots"');
  });
});
```

</CodeExample>

Типизированный код часто **возвращает** свои ошибки вместо того, чтобы бросать их, — в виде объединения `Result`, `{ ok: true; value: T } | { ok: false; error: E }`, как в уроке [Типизированный fetch](/learn/typescript/typed-fetch). Тогда варианты ошибок становятся частью сигнатуры, и тест проверяет их, как любое другое значение. Сравнить весь результат через `toEqual` — самый простой тест, и он проверяет всё сразу.

Но когда хочется покопаться в значении, вы упираетесь в стену. `expect` из Vitest проверяет всё **во время выполнения**, а компилятор не знает, что именно доказал `expect`:

```ts
const result = validateSignup("Mei@PandaDev.test", "bamboo42");
expect(result.ok).toBe(true);
expect(result.value.email).toBe("mei@pandadev.test");
// ❌ Error: Property 'value' does not exist on type 'Result<{ email: string; }, string>'.
```

Аккуратное решение — пара маленьких **тестовых помощников**, которые сужают тип результата и отдают содержимое либо проваливают тест с полезным сообщением:

<CodeExample output={`✓ validateSignup > принимает регистрацию и приводит email к нижнему регистру
✓ validateSignup > сообщает об отсутствии email
✓ validateSignup > сообщает о слишком коротком пароле
× validateSignup > показывает полезное сообщение, когда помощник не срабатывает
  → Error: Ожидался ok, получено {"kind":"missing","field":"email"}

Tests  1 failed | 3 passed (4)`}>

```ts
import { describe, it, expect } from "vitest";

type Result<T, E> = { ok: true; value: T } | { ok: false; error: E };

type SignupError =
  | { kind: "missing"; field: "email" | "password" }
  | { kind: "too-short"; min: number };

type Signup = { email: string; password: string };

function validateSignup(
  email: string,
  password: string,
): Result<Signup, SignupError> {
  if (email === "") {
    return { ok: false, error: { kind: "missing", field: "email" } };
  }
  if (password === "") {
    return { ok: false, error: { kind: "missing", field: "password" } };
  }
  if (password.length < 8) {
    return { ok: false, error: { kind: "too-short", min: 8 } };
  }
  return { ok: true, value: { email: email.toLowerCase(), password } };
}

// Тестовые помощники: отдают значение (или ошибку) либо валят тест
function expectOk<T, E>(result: Result<T, E>): T {
  if (!result.ok) {
    const error = JSON.stringify(result.error);
    throw new Error(`Ожидался ok, получено ${error}`);
  }
  return result.value;
}

function expectErr<T, E>(result: Result<T, E>): E {
  if (result.ok) {
    const value = JSON.stringify(result.value);
    throw new Error(`Ожидалась ошибка, получено ${value}`);
  }
  return result.error;
}

describe("validateSignup", () => {
  it("принимает регистрацию и приводит email к нижнему регистру", () => {
    const result = validateSignup("Mei@PandaDev.test", "bamboo42");
    const signup = expectOk(result);
    expect(signup.email).toBe("mei@pandadev.test");
  });

  it("сообщает об отсутствии email", () => {
    expect(validateSignup("", "bamboo42")).toEqual({
      ok: false,
      error: { kind: "missing", field: "email" },
    });
  });

  it("сообщает о слишком коротком пароле", () => {
    const error = expectErr(validateSignup("mei@pandadev.test", "abc"));
    expect(error).toEqual({ kind: "too-short", min: 8 });
  });

  it("показывает полезное сообщение, когда помощник не срабатывает", () => {
    expectOk(validateSignup("", "abc"));
  });
});
```

</CodeExample>

Последний тест падает намеренно, чтобы показать, что вы увидите: не расплывчатое «expected false to be true», а настоящую ошибку, которая вернулась. Внутри помощников обычный `if` сужает объединение, так что `expectOk` возвращает настоящий `Signup`, а в тесте работает автодополнение для `signup.email`. Такие помощники обычно живут в общем файле `test-utils.ts`.

<Callout type="tip" title="По тесту на каждый вариант ошибки">

Объединение вроде `SignupError` — это чек-лист: каждый `kind` — ситуация, о которой код обещает сообщить. Пишите хотя бы один тест на каждый вариант, и когда кто-то добавит новый вариант, недостающий тест будет легко заметить на ревью. Если нужно намеренно вызвать функцию с **неправильным** типом (скажем, чтобы проверить, как она обходится с плохим вводом из обычного JavaScript), безопасный способ показан в уроке [Тестирование типов](/learn/typescript/testing-types).

## Итоги

- Типы доказывают, что детали стыкуются; тесты доказывают, что поведение правильное. Не тестируйте то, что уже гарантирует компилятор; тестируйте логику, граничные случаи и пути ошибок.
- Vitest запускает файлы `.test.ts` напрямую, но **не проверяет** в них типы: дополнительно запускайте `tsc --noEmit`.
- **Фабрика тестовых данных** вроде `makeUser(overrides: Partial<User> = {}): User` делает тесты короткими и переживает изменения модели. Помните, что `Partial` поверхностный.
- Типизируйте моки: `vi.fn<SendEmail>()`, `vi.fn<typeof realFn>()` или `vi.fn<Mailer["send"]>()`. Тогда проверяются и возвращаемые значения, и вызовы, и `mock.calls`. Для переменных с моками используйте `Mock<T>`; `vi.spyOn` типизируется по объекту.
- В `it.each` сохраняйте литеральные типы через `as const` или используйте строки-объекты с именованным типом строки: `it.each<Case>([...])`.
- Брошенные ошибки тестируйте через `toThrow(ErrorClass)` или по сообщению; значения `Result` — через `toEqual` или помощники `expectOk`/`expectErr`, которые сужают объединение.
