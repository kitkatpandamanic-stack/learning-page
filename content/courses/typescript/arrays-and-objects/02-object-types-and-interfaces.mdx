Objects group related values together: a user has a name, an email and an age. In TypeScript you describe that **shape** once, and the compiler checks that every object really has it. No more typos like `user.emial` sneaking through! 🐼

## Object type annotations

An object type lists each property with its type, separated by semicolons, inside curly braces:

<CodeExample output={`Mo is 3 years old
Bao is 1 years old`}>

```ts
const pet: { name: string; age: number } = { name: "Mo", age: 3 };

function describePet(p: { name: string; age: number }): string {
  return `${p.name} is ${p.age} years old`;
}

console.log(describePet(pet));
console.log(describePet({ name: "Bao", age: 1 }));
```

</CodeExample>

If a required property is missing, TypeScript tells you which one:

```ts
const pet: { name: string; age: number } = { name: "Mo" };
// ❌ Error: Property 'age' is missing in type '{ name: string; }' but required in type '{ name: string; age: number; }'.
```

## Naming shapes with `type`

Writing the same shape twice is tiring and easy to get wrong. A **type alias** gives it a name you can reuse anywhere:

<CodeExample output={`{ name: 'Mo', age: 3 }
Mo is older`}>

```ts
type Pet = {
  name: string;
  age: number;
};

const mo: Pet = { name: "Mo", age: 3 };
const bao: Pet = { name: "Bao", age: 1 };

function older(a: Pet, b: Pet): Pet {
  return a.age >= b.age ? a : b;
}

console.log(mo);
console.log(`${older(mo, bao).name} is older`);
```

</CodeExample>

## Interfaces

An **interface** is another way to name an object shape. It looks almost the same, just without the `=`:

<CodeExample output="Mei <mei@panda.dev>">

```ts
interface User {
  name: string;
  email: string;
}

function contactLine(user: User): string {
  return `${user.name} <${user.email}>`;
}

const mei: User = { name: "Mei", email: "mei@panda.dev" };
console.log(contactLine(mei));
```

</CodeExample>

So which one should you use? For describing objects, they're nearly interchangeable:

| | `type` | `interface` |
| --- | --- | --- |
| Describes object shapes | ✅ | ✅ |
| Can be extended | ✅ (with `&`) | ✅ (with `extends`) |
| Unions like `"a" \| "b"` and function types | ✅ | ❌ |

<Callout type="tip" title="A simple rule">

Use `interface` for object shapes and `type` for everything else (unions, function types, tuples). Many teams do this. What matters most is being consistent in one project.

</Callout>

## Optional and readonly properties

Add **`?`** after a property name to make it **optional**: objects may leave it out. Add **`readonly`** in front to stop it being changed after the object is created:

<CodeExample output={`Mei Lin (no phone)
Sam: 0123 456`}>

```ts
interface Member {
  readonly id: number;
  name: string;
  phone?: string; // string | undefined
}

function phoneLine(m: Member): string {
  if (m.phone === undefined) {
    return `${m.name} (no phone)`;
  }
  return `${m.name}: ${m.phone}`;
}

const mei: Member = { id: 1, name: "Mei" };
const sam: Member = { id: 2, name: "Sam", phone: "0123 456" };
mei.name = "Mei Lin"; // fine: name isn't readonly

console.log(phoneLine(mei));
console.log(phoneLine(sam));
```

</CodeExample>

Trying to change a `readonly` property is an error:

```ts
mei.id = 99;
// ❌ Error: Cannot assign to 'id' because it is a read-only property.
```

<Callout type="note">

Like `readonly` arrays, `readonly` properties are a **compile-time** check. They don't freeze the object at runtime, they just stop your code (and your teammates' code) from changing it by accident.

</Callout>

## Excess property checks

When you write an object literal directly where a type is expected, TypeScript also complains about **extra** properties it doesn't know. This catches typos and leftover data:

```ts
type Pet = { name: string; age: number };

const pet: Pet = { name: "Mo", age: 2, colour: "black" };
// ❌ Error: Object literal may only specify known properties, and 'colour' does not exist in type 'Pet'.
```

If `colour` really belongs to a pet, add it to the type (maybe as `colour?: string`). If it doesn't, remove it.

## Extending interfaces

An interface can **extend** another one: it gets all of the parent's properties, plus its own. This avoids repeating shared properties:

<CodeExample output={`Rex the Labrador, age 4
{ name: 'Rex', age: 4, breed: 'Labrador' }`}>

```ts
interface Animal {
  name: string;
  age: number;
}

interface Dog extends Animal {
  breed: string;
}

const rex: Dog = { name: "Rex", age: 4, breed: "Labrador" };

function introduce(dog: Dog): string {
  return `${dog.name} the ${dog.breed}, age ${dog.age}`;
}

console.log(introduce(rex));
console.log(rex);
```

</CodeExample>

A `Dog` is also an `Animal`, so you can pass `rex` to any function that expects an `Animal`. With `type` aliases you get the same effect with `&`: `type Dog = Animal & { breed: string };`.

interface Book {
  readonly isbn: string;
  title: string;
  author: string;
  pages: number;
  rating?: number;

  return `${text}, rated ${book.rating}/5`;

  title: "Dune",
  author: "Frank Herbert",
  pages: 412,
  rating: 5,
};

console.log(describeBook(dune));

## Recap

- Describe objects with `{ name: string; age: number }`, or name the shape with `type` or `interface`.
- `interface` is great for object shapes; `type` can also name unions and function types.
- `prop?: T` makes a property optional; `readonly prop: T` stops it being reassigned.
- Object literals with unknown extra properties are flagged (excess property checks).
- `interface Dog extends Animal` reuses every property of `Animal` and adds more.
