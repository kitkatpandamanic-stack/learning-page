You already know how to change a web page with [the DOM](/learn/javascript/the-dom) and [events](/learn/javascript/events) in JavaScript. TypeScript knows the DOM too: every element, every event and every browser API has a type. That means it can warn you about the classic page bugs **before** you open the browser: an element that isn't there, an input you read as a number, a click handler that expects a key. In this lesson you'll write page code that TypeScript is happy with, and that doesn't fall over when the page isn't quite what you expected. 🧩

The examples in this lesson run in a real page next to the code. Press **Run** to try them, and change them as much as you like.

## Elements have types

Every element on a page is an object, and TypeScript has a type for each kind. They form a family tree, from the most general type to the most specific:

```text
EventTarget              can receive events
└─ Node                  anything in the page tree, even text
   └─ Element            any tag, HTML or SVG
      └─ HTMLElement     any HTML tag: style, hidden, dataset…
         ├─ HTMLInputElement    value, checked, valueAsNumber…
         ├─ HTMLButtonElement   disabled, type…
         ├─ HTMLFormElement     reset(), requestSubmit()…
         └─ HTMLLIElement, HTMLParagraphElement, …
```

The lower you go, the more TypeScript lets you do. An `HTMLInputElement` has a `value`, but a plain `Element` doesn't, because most elements (a `<p>`, an SVG circle) have no value at all.

So what type do you get when you look an element up? It depends on what TypeScript can work out from your code:

| Code                                 | Type                          |
| ------------------------------------ | ----------------------------- |
| `document.querySelector("input")`    | `HTMLInputElement \| null`    |
| `document.querySelector("#name")`    | `Element \| null`             |
| `document.getElementById("name")`    | `HTMLElement \| null`         |
| `document.querySelectorAll("li")`    | `NodeListOf<HTMLLIElement>`   |
| `document.createElement("button")`   | `HTMLButtonElement`           |

With a **tag name** like `"input"`, TypeScript knows exactly which element you'll get. With an **id or a class**, it can't know: `#name` could be on an input, a heading or an SVG shape. And the lookups can always come back empty, hence the `| null`.

<TryIt

  code={`// Tag names give precise types
const input = document.querySelector("input");
const button = document.querySelector("button");
// An id doesn't, but HTMLElement has textContent
const out = document.getElementById("out");

if (input && button && out) {
  button.addEventListener("click", () => {

/>

Hover over the variables in a real editor and you'll see `HTMLInputElement | null`, `HTMLButtonElement | null` and `HTMLElement | null`. Inside the `if`, the `null` is gone, and TypeScript remembers that even inside the click listener.

## Dealing with null

Without a check, TypeScript stops you. Here's what happens when you read an input by its id:

```ts
const nameInput = document.querySelector("#name");
console.log(nameInput.value);
// ❌ Error: 'nameInput' is possibly 'null'.
// ❌ Error: Property 'value' does not exist on type 'Element'.
```

Two separate problems: the element might be **missing**, and even if it's there, TypeScript doesn't know it's an **input**. Let's take them one at a time.

A missing element is a real bug that happens all the time: a typo in the selector, an id renamed in the HTML, a script that runs before the page is ready. You have three ways to deal with `null`:

1. **Check and stop early.** `if (!button) throw new Error("No #save button")` gives a clear error message in the right place, and after it TypeScript knows the element exists.
2. **Optional chaining** for elements that are really optional: `banner?.remove()` does nothing when there's no banner.
3. **The non-null assertion `!`**: `document.querySelector("button")!` tells TypeScript "trust me, it's there". It removes `null` from the type and checks nothing (more about it in [Type Guards & unknown](/learn/typescript/type-guards-and-unknown)).

<Callout type="warning" title="The ! is a promise, not a check">

If you're wrong about a `!`, the code crashes later with a vague `Cannot read properties of null`, far away from the real mistake. Prefer a check that throws a helpful message. Keep `!` for places where you're truly sure, such as an element that's written right there in your own HTML, a line above the script.

</Callout>

One catch with option 1 in bigger scripts: the narrowing doesn't reach inside **function declarations**.

```ts
const list = document.querySelector("ul");
if (!list) throw new Error("No list on the page");

function render(): void {
  list.replaceChildren();
  // ❌ Error: 'list' is possibly 'null'.
}
```

Function declarations are **hoisted**: you could call `render()` at the very top of the file, before the check has run, so TypeScript doesn't rely on it. (Arrow functions created after the check, like the click listener above, are fine.) The neat fix is to do the check **inside a function that returns the element**, so the variable's type never contains `null` in the first place. You'll build exactly that in the next section.

## Getting the right element type

Now the second problem: `Element` has no `value`. TypeScript offers three ways to say which element you expect, and they're **not** equally safe:

```ts
// 1. A type argument: "this selector finds an input"
const a = document.querySelector<HTMLInputElement>("#name");
// a: HTMLInputElement | null

// 2. A cast with as: "trust me, it's an input"
const b = document.querySelector("#name") as HTMLInputElement;
// b: HTMLInputElement (the null quietly disappeared!)

// 3. instanceof: actually check it while the code runs
const c = document.querySelector("#name");
if (c instanceof HTMLInputElement) {
  // c: HTMLInputElement
}
```

Options 1 and 2 are only **claims**. Types disappear when the code runs, so if the HTML says `<p id="name">`, nothing complains: `b.value` is `undefined` and `b.value.trim()` crashes. Option 3 is a real runtime check, and TypeScript **narrows** the type inside the `if`, just like the [`instanceof` narrowing](/learn/typescript/union-types) you used with your own classes.

Checking every element by hand gets repetitive, so many projects wrap it in a small [generic](/learn/typescript/generic-functions) helper. It finds an element, checks that it exists and is the expected kind, and returns it with the precise type, without `null`:

<TryIt
  language="typescript"
  html={`<label>Celsius <input id="celsius" type="number" value="20"></label>
<p id="result"></p>`}
  code={`function query<T extends Element>(
  selector: string,
  type: new () => T,
): T {
  const element = document.querySelector(selector);
  if (!(element instanceof type)) {
    throw new Error(\`Expected \${selector} to be \${type.name}\`);
  }
  return element;
}

const celsius = query("#celsius", HTMLInputElement);
const result = query("#result", HTMLParagraphElement);

function convert(): void {
  const c = celsius.valueAsNumber; // a number, NaN when empty
  result.textContent = Number.isNaN(c)
    ? "Type a temperature"
    : \`\${c} °C = \${(c * 9 / 5 + 32).toFixed(1)} °F\`;
}

celsius.addEventListener("input", convert);
convert();

// A wrong guess fails loudly, with a helpful message
try {
  query("#result", HTMLInputElement);
} catch (error) {
  console.log(error instanceof Error ? error.message : error);
}`}
/>

The second parameter is the **class itself**: like [any class](/learn/typescript/structural-typing-and-class-design), `HTMLInputElement` is a value as well as a type, and `new () => T` means "something you can create a `T` with". Pass `HTMLInputElement` and `T` becomes `HTMLInputElement`, so `celsius.valueAsNumber` is allowed. A missing element and a wrong element both throw straight away, with a message that names the selector. The rest of this lesson uses `query` for its examples; in a real project it would live in its own module, which is the topic of the next lesson.

Notice `valueAsNumber`. An input's `value` is **always a string**, even with `type="number"`, so `const age: number = ageInput.value` is a type error. Use `valueAsNumber` (or `Number(input.value)`) and check for `NaN`.

## Creating elements

`document.createElement` takes a tag name, so its result is always precise: `createElement("li")` is an `HTMLLIElement`, `createElement("input")` is an `HTMLInputElement`. TypeScript then checks what you do with it:

```ts
const item = document.createElement("li");
item.disabled = true;
// ❌ Error: Property 'disabled' does not exist on type 'HTMLLIElement'.
```

A list item can't be disabled, so that line was a bug anyway. A `createElement("button")` would accept it.

**Data attributes** get types too. `element.dataset` holds **strings** only, and reading one gives `string | undefined`, because the attribute might not be there:

```ts
const button = document.createElement("button");
button.dataset.id = 3;
// ❌ Error: Type 'number' is not assignable to type 'string'.
button.dataset.id = String(3); // ✅

const id: string = button.dataset.id;
// ❌ Error: Type 'string | undefined' is not assignable to type 'string'.
const id2 = Number(button.dataset.id); // ✅ a number (NaN if missing)
```

In JavaScript, `button.dataset.id = 3` quietly turns `3` into `"3"`. TypeScript makes you write the conversion, so nobody is surprised later when `"3" + 1` gives `"31"`.

## Typed events

When you call `addEventListener` with an event name, TypeScript looks up the right event type for you:

| Event name             | Event type      | Handy properties                    |
| ---------------------- | --------------- | ----------------------------------- |
| `"click"`              | `PointerEvent`  | `clientX`, `button`, `shiftKey`     |
| `"keydown"`, `"keyup"` | `KeyboardEvent` | `key`, `code`, `ctrlKey`            |
| `"submit"`             | `SubmitEvent`   | `submitter`, `preventDefault()`     |
| `"input"`              | `InputEvent`    | `data`, `inputType`                 |
| `"change"`             | `Event`         | `target`, `currentTarget`           |

(`PointerEvent` is a `MouseEvent` with extra details about the pointer, such as a pen or a finger.) In an inline arrow function, you get all of this for free, and typos are caught:

```ts
document.addEventListener("keydown", (event) => {
  console.log(event.kye);
  // ❌ Error: Property 'kye' does not exist on type 'KeyboardEvent'.
});
```

When the handler is a **separate function**, there's nothing to infer from, so annotate the parameter yourself. TypeScript then checks that the function fits the event:

<TryIt
  language="typescript"
  html={`<p>Click here, then press ← and →</p>
<p id="slide" style="font-size: 48px">🐼</p>
<p id="info"></p>`}
  code={`function query<T extends Element>(
  selector: string,
  type: new () => T,
): T {
  const element = document.querySelector(selector);
  if (!(element instanceof type)) {
    throw new Error(\`Expected \${selector} to be \${type.name}\`);
  }
  return element;
}

const slides = ["🐼", "🎋", "🍵", "🏯"];
let index = 0;

const slide = query("#slide", HTMLParagraphElement);
const info = query("#info", HTMLParagraphElement);

function show(): void {
  slide.textContent = slides[index];
  info.textContent = \`Slide \${index + 1} of \${slides.length}\`;
}

function onKey(event: KeyboardEvent): void {
  if (event.key === "ArrowRight") {
    index = (index + 1) % slides.length;
  } else if (event.key === "ArrowLeft") {
    index = (index - 1 + slides.length) % slides.length;
  } else {
    return; // not our key
  }
  show();
}

document.addEventListener("keydown", onKey);
show();`}
/>

Try registering `onKey` for `"click"` instead: TypeScript reports `No overload matches this call.` with a long explanation, because a click is a `PointerEvent`, which has no `key`.

## event.target and delegation

There's one event property that surprises everyone:

```ts
form.addEventListener("submit", (event) => {
  console.log(event.target.value);
  // ❌ Error: 'event.target' is possibly 'null'.
  // ❌ Error: Property 'value' does not exist on type 'EventTarget'.
});
```

`event.target` is typed as the most general `EventTarget | null`. That's honest: events **bubble**, so the target could be any element inside, or even the document or the window. (`event.currentTarget` has the same type, for the same reason.) Two good ways out:

- If you already have the element in a variable, **use the variable**. Inside a form's submit listener, read `nameInput.value`, not `event.target`.
- With **event delegation**, where one listener handles many children, **narrow** the target with `instanceof`.

Here's delegation with typed data. One listener on the list handles every vote button, including the ones `render()` creates later:

<TryIt
  language="typescript"
  html={`<style>
  li { margin: 6px 0; }
  li button { margin-left: 8px; }
</style>
<p>Vote for the best snack:</p>
<ul></ul>`}
  code={`function query<T extends Element>(
  selector: string,
  type: new () => T,
): T {
  const element = document.querySelector(selector);
  if (!(element instanceof type)) {
    throw new Error(\`Expected \${selector} to be \${type.name}\`);
  }
  return element;
}

interface Snack {
  id: number;
  name: string;
  votes: number;
}

const snacks: Snack[] = [
  { id: 1, name: "Bamboo", votes: 2 },
  { id: 2, name: "Apples", votes: 0 },
  { id: 3, name: "Leaf tea", votes: 1 },
];

const list = query("ul", HTMLUListElement);

function render(): void {
  list.replaceChildren();
  for (const snack of snacks) {
    const item = document.createElement("li");
    item.textContent = snack.name;

    const button = document.createElement("button");
    button.textContent = \`👍 \${snack.votes}\`;
    button.dataset.id = String(snack.id);

    item.append(button);
    list.append(item);
  }
}

list.addEventListener("click", (event) => {
  // Clicks on the text or the gaps are ignored
  if (!(event.target instanceof HTMLButtonElement)) return;

  const id = Number(event.target.dataset.id);
  const snack = snacks.find((s) => s.id === id);
  if (!snack) return;

  snack.votes++;
  console.log(\`\${snack.name}: \${snack.votes} votes\`);
  render();
});

render();`}
/>

Inside the listener, after the `instanceof` check, `event.target` is an `HTMLButtonElement`, so `dataset` is available. And `find` returns `Snack | undefined`, so TypeScript makes sure you handle an unknown id.

## Saving data with localStorage

`localStorage` stores **strings**. `getItem` returns `string | null` (`null` when nothing is saved yet), and passing that straight to `JSON.parse` is an error:

```ts
JSON.parse(localStorage.getItem("settings"));
// ❌ Error: Argument of type 'string | null' is not assignable to parameter of type 'string'.
```

The bigger danger is the other way round. `JSON.parse` returns `any`, so this compiles without a word:

```ts
const settings: Settings = JSON.parse(text); // no error, no check!
```

But the saved text could be anything: data from an older version of your app, a value someone edited in the browser's DevTools, or half-written JSON. Treat it like any other data from outside: give it the type `unknown` and check it with a [type guard](/learn/typescript/type-guards-and-unknown) before you use it.

<TryIt
  language="typescript"
  html={`<label><input type="checkbox" id="dark"> Dark mode</label>
<label>Size <input type="range" id="size" min="12" max="28"></label>
<p id="sample">The quick panda naps under the bamboo.</p>`}
  code={`function query<T extends Element>(
  selector: string,
  type: new () => T,
): T {
  const element = document.querySelector(selector);
  if (!(element instanceof type)) {
    throw new Error(\`Expected \${selector} to be \${type.name}\`);
  }
  return element;
}

interface Settings {
  dark: boolean;
  fontSize: number;
}

const DEFAULTS: Settings = { dark: false, fontSize: 16 };

function isSettings(value: unknown): value is Settings {
  return (
    typeof value === "object" &&
    value !== null &&
    "dark" in value &&
    typeof value.dark === "boolean" &&
    "fontSize" in value &&
    typeof value.fontSize === "number"
  );
}

function loadSettings(): Settings {
  const text = localStorage.getItem("settings");
  if (text === null) return DEFAULTS; // nothing saved yet
  try {
    const data: unknown = JSON.parse(text);
    return isSettings(data) ? data : DEFAULTS;
  } catch {
    return DEFAULTS; // not even valid JSON
  }
}

function saveSettings(settings: Settings): void {
  localStorage.setItem("settings", JSON.stringify(settings));
}

const dark = query("#dark", HTMLInputElement);
const size = query("#size", HTMLInputElement);
const sample = query("#sample", HTMLParagraphElement);

function apply(settings: Settings): void {
  dark.checked = settings.dark;
  size.value = String(settings.fontSize);
  sample.style.fontSize = \`\${settings.fontSize}px\`;
  sample.style.background = settings.dark ? "#1e1b4b" : "";
  sample.style.color = settings.dark ? "#e0e7ff" : "";
}

function onChange(): void {
  const settings: Settings = {
    dark: dark.checked,
    fontSize: Number(size.value),
  };
  saveSettings(settings);
  apply(settings);
}

dark.addEventListener("change", onChange);
size.addEventListener("input", onChange);

const settings = loadSettings();
console.log("Loaded:", settings);
apply(settings);`}
/>

Change the settings, then press **Run** again: the preview keeps its storage between runs, just like a browser keeps it between page reloads, so your settings come back. A broken saved value can't crash the page: it falls back to the defaults.

<Callout type="tip" title="Validate where data comes in">

Check outside data **once**, at the edge, in a function like `loadSettings`. Everything after that works with a real `Settings` and needs no more checks. The same idea works for data from forms, URLs and, later in the course, APIs.

</Callout>

Build a profile form whose card updates as you type, and which saves the profile safely. The page, the `Profile` type, an `isTheme` guard and the `query` helper from this lesson are ready.

1. **Fix the element types.** Use `query()` with the right class for each element: `HTMLFormElement`, `HTMLInputElement`, `HTMLSelectElement`, `HTMLParagraphElement`, `HTMLDivElement`, and `HTMLElement` for the `<strong>`.
2. **`renderPreview()`** puts the trimmed name in `#card-name` (or `Your name` when it's blank), `Age: <age>` in `#card-age` (or `Age: ?` when the age box is empty), and the selected theme in the card's `data-theme`. Call it on every `input` event of the form (one listener on the form hears all three fields).
3. **`readProfile()`** returns a `Profile` built from the form, or an error message:
   - `Name needs at least 2 characters` if the trimmed name is shorter than 2;
   - `Age must be a whole number from 1 to 120` otherwise, if the age isn't;
   - `Pick a theme` if the select's value isn't a `Theme`.
4. On **submit**: stop the page reload, then show the error from `readProfile()` in `#message`, or save the profile as JSON in `localStorage` under `"profile"` and show `Saved!`.
5. **`loadProfile()`** returns the saved profile, or `null` if nothing is saved, the JSON is broken or the data has the wrong shape.

Try it in the preview: fill in the form and press **Save profile**.

<Hint>

```ts
type Theme = "bamboo" | "night";

interface Profile {
  name: string;
  age: number;
  theme: Theme;
}

function isTheme(value: string): value is Theme {
  return value === "bamboo" || value === "night";
}

function query<T extends Element>(
  selector: string,
  type: new () => T,
): T {
  const element = document.querySelector(selector);
  if (!(element instanceof type)) {
    throw new Error(`Expected ${selector} to be ${type.name}`);
  }
  return element;
}

const form = query("#profile", HTMLFormElement);
const nameInput = query("#name", HTMLInputElement);
const ageInput = query("#age", HTMLInputElement);
const themeSelect = query("#theme", HTMLSelectElement);
const message = query("#message", HTMLParagraphElement);
const card = query("#card", HTMLDivElement);
const cardName = query("#card-name", HTMLElement);
const cardAge = query("#card-age", HTMLParagraphElement);

function renderPreview(): void {
  cardName.textContent = nameInput.value.trim() || "Your name";
  cardAge.textContent = `Age: ${ageInput.value || "?"}`;
  card.dataset.theme = themeSelect.value;
}

function readProfile(): Profile | string {
  const name = nameInput.value.trim();
  if (name.length < 2) {
    return "Name needs at least 2 characters";
  }
  const age = ageInput.valueAsNumber; // NaN when empty
  if (!Number.isInteger(age) || age < 1 || age > 120) {
    return "Age must be a whole number from 1 to 120";
  }
  const theme = themeSelect.value;
  if (!isTheme(theme)) {
    return "Pick a theme";
  }
  return { name, age, theme };
}

function isProfile(value: unknown): value is Profile {
  return (
    typeof value === "object" &&
    value !== null &&
    "name" in value &&
    typeof value.name === "string" &&
    "age" in value &&
    typeof value.age === "number" &&
    "theme" in value &&
    typeof value.theme === "string" &&
    isTheme(value.theme)
  );
}

function loadProfile(): Profile | null {
  const text = localStorage.getItem("profile");
  if (text === null) return null;
  try {
    const data: unknown = JSON.parse(text);
    return isProfile(data) ? data : null;
  } catch {
    return null;
  }
}

form.addEventListener("input", renderPreview);

form.addEventListener("submit", (event) => {
  event.preventDefault();
  const result = readProfile();
  if (typeof result === "string") {
    message.textContent = result;
    return;
  }
  localStorage.setItem("profile", JSON.stringify(result));
  message.textContent = "Saved!";
});

// Bonus: fill the form from the saved profile (press Run again)
const saved = loadProfile();
if (saved) {
  nameInput.value = saved.name;
  ageInput.value = String(saved.age);
  themeSelect.value = saved.theme;
}

renderPreview();
```

## Recap

- DOM types form a family: `Element` → `HTMLElement` → `HTMLInputElement` and friends. Tag selectors and `createElement` give precise types; ids and classes give `Element`.
- Lookups can return `null`. Check and throw a helpful error, use `?.` for optional elements, and keep `!` for when you're truly sure.
- `querySelector<T>` and `as` are claims; `instanceof` is a real check that narrows. A small generic `query(selector, Class)` helper does it everywhere.
- `addEventListener` infers the event type (`PointerEvent`, `KeyboardEvent`, `SubmitEvent`…); annotate named handlers yourself. `event.target` is an `EventTarget | null`: use your element variable, or narrow with `instanceof`.
- Input values and `dataset` values are strings: convert with `valueAsNumber`, `Number()` or `String()`.
- `localStorage` gives `string | null` and `JSON.parse` gives `any`: treat saved data as `unknown` and validate it with a type guard.
