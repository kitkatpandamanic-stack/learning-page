Every time you've pressed **Run** on PandaDev, a type checker has been working in the background, with settings somebody chose for you. In your own projects, **you** choose them, in a file called `tsconfig.json`. In this lesson you'll meet the compiler `tsc`, learn the options you'll see in nearly every project, switch on some extra safety, and find out how TypeScript actually runs in the real world. 🛠️

## tsc: check and compile

The TypeScript compiler, **`tsc`**, does two separate jobs:

1. **Type-check** your code and report errors.
2. **Emit** JavaScript: remove the types and write `.js` files that browsers and Node.js can run.

Install it into a project and create a config file:

```bash
npm install -D typescript   # tsc for this project
npx tsc --init              # creates tsconfig.json
```

Once a project has a `tsconfig.json`, run `tsc` **without** file names, and it reads the settings and finds the files by itself:

```bash
npx tsc            # check everything, then write the .js files
npx tsc --noEmit   # only check, write nothing
npx tsc --watch    # check again every time you save
```

Errors show the file, the line and the column, and `tsc` exits with an error code, so scripts and CI pipelines stop when the types are wrong:

```text
src/main.ts(5,19): error TS2345: Argument of type 'number' is not assignable to parameter of type 'string'.
```

<Callout type="note" title="tsc file.ts and a tsconfig.json don't mix">

In Level 0 you saw `npx tsc hello.ts`. That's fine in a folder without a config. Since TypeScript 6, if there **is** a `tsconfig.json`, naming a file is an error, so you don't accidentally ignore your project's settings:

```text
error TS5112: tsconfig.json is present but will not be loaded if files are specified on commandline. Use '--ignoreConfig' to skip this error.
```

</Callout>

## tsconfig.json

Here's a typical config for a browser app. The options are grouped by the question they answer:

```json title="tsconfig.json"
{
  "compilerOptions": {
    "strict": true,

    "target": "es2022",
    "lib": ["es2023", "dom", "dom.iterable"],

    "module": "esnext",
    "moduleResolution": "bundler",
    "verbatimModuleSyntax": true,

    "noEmit": true
  },
  "include": ["src"]
}
```

### How strict is the checking?

**`strict: true`** switches on a whole family of checks at once. You've been relying on them since your first lesson:

| Part of strict                 | What it catches                                         |
| ------------------------------ | ------------------------------------------------------- |
| `noImplicitAny`                | `Parameter 'name' implicitly has an 'any' type.`        |
| `strictNullChecks`             | `'input' is possibly 'null'.`                           |
| `useUnknownInCatchVariables`   | `'e' is of type 'unknown'.` (using a caught error)      |
| `strictPropertyInitialization` | class fields that are never given a value               |
| `strictFunctionTypes` and more | callbacks with the wrong parameter types, and others    |

Without `strictNullChecks`, `null` and `undefined` are allowed **everywhere**, and most of the last two lessons' checks would silently disappear. Since TypeScript 6, `strict` is on even if you leave it out, but write it anyway: it documents your intent, and older versions and other tools still default to off.

### What JavaScript comes out, and which built-ins exist?

**`target`** is the JavaScript version `tsc` writes. Newer syntax is rewritten into older syntax when the target needs it. Modern browsers and Node.js handle `es2022` or later easily. (Very old targets like `es5` are deprecated in TypeScript 6.)

**`lib`** decides which **built-in types** exist. `"dom"` brings `document`, `HTMLInputElement` and everything from lesson 1; leave it out and the DOM simply doesn't exist for the checker:

```ts
document.querySelector("h1");
// ❌ Error: Cannot find name 'document'. Do you need to change your target library? Try changing the 'lib' compiler option to include 'dom'.
```

That's a feature for Node.js projects: there is no `document` on a server, so you don't want to be allowed to use it. Instead, Node projects install `@types/node` and list it in **`types`**: `"types": ["node"]`. (Since TypeScript 6, `@types` packages with globals are only loaded when you list them there.)

You've already seen this on PandaDev: plain TypeScript snippets run in a Web Worker and are checked without the DOM library, while page exercises like the ones in lesson 1 get `"dom"`. Same compiler, different `lib`.

### How do imports work?

**`module`** says what kind of modules your code uses, and **`moduleResolution`** how an import path is turned into a file. There are two common setups:

- **Bundled apps** (Vite and friends): `"module": "esnext"` with `"moduleResolution": "bundler"`. Imports look like `"./profile"`, without an extension.
- **Node.js programs**: `"module": "nodenext"` (the resolution follows automatically). Imports follow Node's rules, so `"./profile.js"`, as you saw in the last lesson.

**`verbatimModuleSyntax`** makes you mark type-only imports with `type`, so tools that remove types file by file never guess wrong. Also from the last lesson.

### Which files, and where does the output go?

- **`include`** lists the folders (or patterns) that belong to the project. Your `.d.ts` files must be inside them too.
- **`rootDir`** and **`outDir`**: where the source lives and where the `.js` goes. With `"rootDir": "src"` and `"outDir": "dist"`, the file `src/main.ts` becomes `dist/main.js`.
- **`noEmit`**: don't write any files at all. Use it when another tool runs your code (see below) and `tsc` is only there to check.

For example, with `rootDir` and `outDir` set, this `src/main.ts`:

```ts title="src/main.ts"
function greet(name: string): string {
  return `Hello, ${name}!`;
}

console.log(greet("Mei"));
```

compiles to `dist/main.js`, the same code minus the types (the `export {}` just marks the file as a module):

```js title="dist/main.js"
function greet(name) {
    return `Hello, ${name}!`;
}
console.log(greet("Mei"));
export {};
```

<Callout type="tip" title="PandaDev's settings">

The editors on this site use these options: `"strict": true`, `"target": "es2022"`, `"module": "esnext"`, `"moduleResolution": "bundler"`, `"moduleDetection": "force"` (every snippet is a module, which is why top-level `await` works), `"esModuleInterop": true` and `"noEmit": true`, with `lib` set to `es2023` plus either the Web Worker or the DOM types. If you copy them into a new project, your code will be checked exactly like here.

</Callout>

## Extra safety flags

Some useful checks are **not** part of `strict`, usually because switching them on in an old project produces lots of errors. In a new project, they're well worth it. In fact `tsc --init` in TypeScript 6 already switches on the first two.

### noUncheckedIndexedAccess

Without this flag, TypeScript assumes every array index and every key lookup finds something:

```ts
const names: string[] = [];
const first = names[0]; // type: string, value: undefined!
```

With **`noUncheckedIndexedAccess`**, lookups with `[...]` honestly include `undefined`, so you must handle a miss:

```ts
const names: string[] = ["Mei", "Sam"];
const first: string = names[0];
// ❌ Error: Type 'string | undefined' is not assignable to type 'string'.

const prices: Record<string, number> = { tea: 3 };
console.log(prices["cake"].toFixed(2));
// ❌ Error: Object is possibly 'undefined'.
```

Even `if (names.length > 0)` doesn't convince the checker that `names[0]` exists. These patterns do, and they're good style with or without the flag:

<CodeExample output={`MEI
1
3
3
sam`}>

```ts
const names = ["Mei", "Sam"];
const scores: Record<string, number> = { mei: 12, sam: 7 };

// 1. Read it once, then check it
const first = names[0];
if (first !== undefined) {
  console.log(first.toUpperCase());
}

// 2. A default value with ??
console.log((scores["ana"] ?? 0) + 1);

// 3. for...of only visits items that exist
for (const name of names) {
  console.log(name.length);
}

// 4. at() returns string | undefined even without the flag
const last = names.at(-1);
console.log(last?.toLowerCase());
```

</CodeExample>

### exactOptionalPropertyTypes

An optional property `theme?: string` can mean two things: "the property may be **missing**" or "it may be there with the value **`undefined`**". By default TypeScript allows both, and that hides a nasty bug. Remember the `Partial` updates from [Working with Typed Data](/learn/typescript/typed-data)? Spreading a change with an explicit `undefined` wipes out a required property:

<CodeExample output={`{ theme: undefined, fontSize: 14 }
undefined`}>

```ts
interface Settings {
  theme: string;
  fontSize: number;
}

function update(
  settings: Settings,
  changes: Partial<Settings>,
): Settings {
  return { ...settings, ...changes };
}

const current: Settings = { theme: "night", fontSize: 14 };
const next = update(current, { theme: undefined });
console.log(next);
console.log(typeof next.theme); // the type says string!
```

</CodeExample>

With **`exactOptionalPropertyTypes`**, `?` only means "may be missing", and the bad call is caught:

```ts
update(current, { theme: undefined });
// ❌ Error: Argument of type '{ theme: undefined; }' is not assignable to parameter of type 'Partial<Settings>' with 'exactOptionalPropertyTypes: true'. Consider adding 'undefined' to the types of the target's properties.
```

If a property really may hold `undefined`, say so: `theme?: string | undefined`.

### noImplicitReturns and noFallthroughCasesInSwitch

Two smaller flags for classic slips. **`noImplicitReturns`** reports functions where some paths forget to `return`:

```ts
function label(score: number) {
  // ❌ Error: Not all code paths return a value.
  if (score > 10) {
    return "high";
  } else if (score > 5) {
    return "mid";
  }
}
```

**`noFallthroughCasesInSwitch`** reports a `case` that runs on into the next one because its `break` is missing:

```ts
switch (size) {
  case "s":
  // ❌ Error: Fallthrough case in switch.
    price = 1;
  case "m":
    price = 2;
    break;
}
```

You may also meet `noUnusedLocals` and `noUnusedParameters`, which report variables and parameters you never use. Many teams leave those to a linter instead.

## Running TypeScript for real

Here's the surprise: most tools that **run** TypeScript don't **check** it. They delete the types and run the JavaScript that's left, which is very fast. Checking is `tsc`'s job. The common ways to run code:

| Tool                        | Command                    | Type-checks? |
| --------------------------- | -------------------------- | ------------ |
| `tsc` then Node.js          | `npx tsc && node dist/main.js` | yes      |
| Node.js directly            | `node main.ts`             | no           |
| tsx                         | `npx tsx main.ts`          | no           |
| Vite (browser apps)         | `npm run dev`              | no           |

- **Node.js** (22.18 and newer) can run `.ts` files directly by stripping the types. Only syntax that can simply be erased is allowed, so enums, namespaces and constructor [parameter properties](/learn/typescript/classes-and-access-modifiers) fail:

  ```text
  SyntaxError [ERR_UNSUPPORTED_TYPESCRIPT_SYNTAX]: TypeScript enum is not supported in strip-only mode
  ```

  The flag **`erasableSyntaxOnly`** makes `tsc` report that syntax in your editor first (`This syntax is not allowed when 'erasableSyntaxOnly' is enabled.`). One more reason this course prefers unions of string literals over enums.
- **tsx** is a small npm tool that runs any TypeScript file, enums included, and restarts on changes with `npx tsx watch main.ts`.
- **Vite** serves browser apps and compiles each file as it's requested. Create one with `npm create vite@latest my-app -- --template vanilla-ts`. Its build script runs `tsc` before `vite build`, so a type error stops the build.

So in every setup, keep `tsc --noEmit` in your workflow, for example as npm scripts:

```json title="package.json"
{
  "scripts": {
    "dev": "vite",
    "typecheck": "tsc --noEmit",
    "build": "tsc --noEmit && vite build"
  }
}
```

<Callout type="warning" title="It runs, so it's fine?">

Because `node main.ts`, tsx and Vite skip type checking, code with type errors runs anyway, right up until it hits the bug the checker tried to tell you about. Run `npm run typecheck` before you commit, and have your CI run it on every pull request so broken types never reach the main branch.

</Callout>

## Your editor runs TypeScript too

The red squiggles, the types you see on hover, auto-imports and "rename everywhere" all come from TypeScript itself: editors such as VS Code run its **language service** in the background, using the **same** `tsconfig.json` as `tsc`. A few things worth knowing:

- **F12** (Go to Definition) on something from a package opens its `.d.ts` file: a great way to learn what a library really accepts.
- **F2** renames a variable, function or property in every file that uses it, safely, because the editor knows the types.
- **Quick fixes** (Ctrl+. or Cmd+.) add missing imports, missing properties and more.
- The editor only checks files you have **open**. `tsc --noEmit` checks the whole project.
- If the editor and `tsc` disagree, the editor may be using a different TypeScript version. In VS Code, run **TypeScript: Select TypeScript Version** and pick the workspace version. After changing `tsconfig.json`, **TypeScript: Restart TS Server** makes it reload.

You can't change compiler flags in this editor, so the starter gives the shop's lookup tables the type `Lookup<T>`, which makes every `prices[item]` a `number | undefined`, exactly like the flag would. Two functions don't compile any more. Make the whole shop module safe:

1. **`priceOf(item)`** returns the price, or `undefined` for an item the shop doesn't sell. The type test checks that its return type admits it.
2. **`orderTotal(order)`** adds up the prices of the known items and collects the names of the unknown ones in `unknown`, in order. `["tea", "pizza", "cake"]` gives `{ total: 7.5, unknown: ["pizza"] }`.
3. **`restock(item, amount)`** adds `amount` to the item's stock (an item with no stock entry starts at `0`), saves it in `stock` and returns the new count.
4. **`lowStock(limit)`** returns the names of the items with **fewer** than `limit` in stock, sorted A to Z.

No `!` and no `as`: handle the `undefined` properly.

<Hint>

1. Change the return type to `number | undefined`.
2. Read the price into a variable once, `const price = prices[item]`, then `if (price === undefined)` push the name to `unknown`, `else` add it to `total`.
3. `(stock[item] ?? 0) + amount` gives the new count; then write it back with `stock[item] = count`.
4. Loop over `Object.entries(stock)`: each entry is `[string, number | undefined]`, so check `count !== undefined && count < limit`. Sort with `(a, b) => a.localeCompare(b)`.

</Hint>

<Solution>

```ts
// The team is switching on noUncheckedIndexedAccess. The
// PandaDev editor can't change compiler flags, so this type
// makes every lookup exactly as honest as the flag would:
type Lookup<T> = { [key: string]: T | undefined };

const prices: Lookup<number> = { tea: 3, cake: 4.5, bamboo: 1.25 };
const stock: Lookup<number> = { tea: 12, cake: 0, bamboo: 30 };

interface OrderTotal {
  total: number;
  unknown: string[];
}

function priceOf(item: string): number | undefined {
  return prices[item];
}

function orderTotal(order: string[]): OrderTotal {
  let total = 0;
  const unknown: string[] = [];
  for (const item of order) {
    const price = prices[item];
    if (price === undefined) {
      unknown.push(item);
    } else {
      total += price;
    }
  }
  return { total, unknown };
}

function restock(item: string, amount: number): number {
  const count = (stock[item] ?? 0) + amount;
  stock[item] = count;
  return count;
}

function lowStock(limit: number): string[] {
  const low: string[] = [];
  for (const [item, count] of Object.entries(stock)) {
    if (count !== undefined && count < limit) {
      low.push(item);
    }
  }
  return low.sort((a, b) => a.localeCompare(b));
}

// Type tests: never called, only type-checked. The line
// under the expect-error comment MUST be a type error.
function typeTests(): void {
  // @ts-expect-error: a lookup can miss
  const sure: number = priceOf("tea");
  const maybe: number | undefined = priceOf("tea");
  const order: OrderTotal = orderTotal(["tea"]);
  const count: number = restock("tea", 1);
  const items: string[] = lowStock(5);
}

console.log(priceOf("cake"), priceOf("pizza")); // 4.5 undefined
console.log(orderTotal(["tea", "pizza", "cake"]));
// { total: 7.5, unknown: [ 'pizza' ] }
console.log(lowStock(10)); // [ 'cake' ]
```

## Recap

- `tsc` type-checks and emits JavaScript. In a project, run `npx tsc` (or `npx tsc --noEmit` to only check) and let `tsconfig.json` choose the files.
- `strict` is the must-have family of checks. `target` sets the output JavaScript, `lib` the built-in types (`"dom"` for browsers, `"types": ["node"]` for Node), `module`/`moduleResolution` how imports work, and `include`/`rootDir`/`outDir`/`noEmit` the files.
- Extra safety: `noUncheckedIndexedAccess` (lookups can miss), `exactOptionalPropertyTypes` (missing is not the same as `undefined`), `noImplicitReturns` and `noFallthroughCasesInSwitch`.
- Node.js, tsx and Vite **run** TypeScript by stripping types without checking them. Keep `tsc --noEmit` in your scripts and CI; `erasableSyntaxOnly` keeps your code strippable.
- Your editor uses the same TypeScript and `tsconfig.json`: use Go to Definition, rename and quick fixes, and pick the workspace TypeScript version.
