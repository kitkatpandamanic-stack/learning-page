Каждый раз, когда вы нажимали **«Запустить»** на PandaDev, в фоне работала проверка типов с настройками, которые кто-то выбрал за вас. В собственных проектах их выбираете **вы** — в файле `tsconfig.json`. В этом уроке вы познакомитесь с компилятором `tsc`, узнаете параметры, которые встречаются почти в каждом проекте, включите дополнительную защиту и выясните, как TypeScript на самом деле запускают в реальном мире. 🛠️

## tsc: проверка и компиляция

Компилятор TypeScript, **`tsc`**, выполняет две отдельные работы:

1. **Проверяет типы** в вашем коде и сообщает об ошибках.
2. **Генерирует** (emit) JavaScript: удаляет типы и записывает файлы `.js`, которые могут запускать браузеры и Node.js.

Установите его в проект и создайте файл конфигурации:

```bash
npm install -D typescript   # tsc для этого проекта
npx tsc --init              # создаёт tsconfig.json
```

Когда в проекте есть `tsconfig.json`, запускайте `tsc` **без** имён файлов: он сам прочитает настройки и найдёт файлы:

```bash
npx tsc            # проверить всё, затем записать файлы .js
npx tsc --noEmit   # только проверить, ничего не записывать
npx tsc --watch    # проверять заново при каждом сохранении
```

В ошибках указаны файл, строка и столбец, а `tsc` завершается с кодом ошибки, поэтому скрипты и CI-пайплайны останавливаются, если типы неверны:

```text
src/main.ts(5,19): error TS2345: Argument of type 'number' is not assignable to parameter of type 'string'.
```

<Callout type="note" title="tsc file.ts и tsconfig.json не сочетаются">

На Уровне 0 вы видели `npx tsc hello.ts`. В папке без конфигурации так можно. Начиная с TypeScript 6, если `tsconfig.json` **есть**, указание файла — ошибка, чтобы вы случайно не проигнорировали настройки проекта:

```text
error TS5112: tsconfig.json is present but will not be loaded if files are specified on commandline. Use '--ignoreConfig' to skip this error.
```

</Callout>

## tsconfig.json

Вот типичная конфигурация для браузерного приложения. Параметры сгруппированы по вопросам, на которые они отвечают:

```json title="tsconfig.json"
{
  "compilerOptions": {
    "strict": true,

    "target": "es2022",
    "lib": ["es2023", "dom", "dom.iterable"],

    "module": "esnext",
    "moduleResolution": "bundler",
    "verbatimModuleSyntax": true,

    "noEmit": true
  },
  "include": ["src"]
}
```

### Насколько строгая проверка?

**`strict: true`** включает сразу целое семейство проверок. Вы полагаетесь на них с самого первого урока:

| Часть strict                   | Что она ловит                                           |
| ------------------------------ | ------------------------------------------------------- |
| `noImplicitAny`                | `Parameter 'name' implicitly has an 'any' type.`        |
| `strictNullChecks`             | `'input' is possibly 'null'.`                           |
| `useUnknownInCatchVariables`   | `'e' is of type 'unknown'.` (при использовании пойманной ошибки) |
| `strictPropertyInitialization` | поля класса, которым так и не присвоили значение        |
| `strictFunctionTypes` и другие | колбэки с неверными типами параметров и прочее          |

Без `strictNullChecks` значения `null` и `undefined` разрешены **везде**, и большинство проверок из двух прошлых уроков молча исчезли бы. Начиная с TypeScript 6, `strict` включён, даже если его не указывать, но всё равно пишите его: так вы явно обозначаете намерение, а старые версии и другие инструменты по умолчанию его выключают.

### Какой JavaScript получится и какие встроенные типы существуют?

**`target`** — версия JavaScript, которую пишет `tsc`. Если этого требует target, новый синтаксис переписывается в более старый. Современные браузеры и Node.js легко справляются с `es2022` и новее. (Совсем старые target вроде `es5` в TypeScript 6 объявлены устаревшими.)

**`lib`** определяет, какие **встроенные типы** существуют. `"dom"` добавляет `document`, `HTMLInputElement` и всё из урока 1; уберите его — и для проверки типов DOM просто не будет:

```ts
document.querySelector("h1");
// ❌ Error: Cannot find name 'document'. Do you need to change your target library? Try changing the 'lib' compiler option to include 'dom'.
```

Для проектов на Node.js это полезно: на сервере нет `document`, так что пользоваться им и не должно быть можно. Вместо этого Node-проекты устанавливают `@types/node` и перечисляют его в **`types`**: `"types": ["node"]`. (Начиная с TypeScript 6, пакеты `@types` с глобальными объявлениями загружаются, только если они там перечислены.)

На PandaDev вы это уже видели: обычные фрагменты TypeScript запускаются в Web Worker и проверяются без библиотеки DOM, а упражнения со страницей, как в уроке 1, получают `"dom"`. Компилятор тот же, `lib` разный.

### Как работают импорты?

**`module`** говорит, какие модули использует ваш код, а **`moduleResolution`** — как путь импорта превращается в файл. Есть две распространённые конфигурации:

- **Приложения со сборкой** (Vite и подобные): `"module": "esnext"` вместе с `"moduleResolution": "bundler"`. Импорты выглядят как `"./profile"`, без расширения.
- **Программы на Node.js**: `"module": "nodenext"` (resolution подставляется автоматически). Импорты следуют правилам Node, поэтому пишется `"./profile.js"`, как вы видели в прошлом уроке.

**`verbatimModuleSyntax`** заставляет помечать импорты только типов словом `type`, чтобы инструменты, удаляющие типы пофайлово, никогда не ошибались. Это тоже из прошлого урока.

### Какие файлы и куда идёт результат?

- **`include`** перечисляет папки (или шаблоны), которые входят в проект. Ваши файлы `.d.ts` тоже должны лежать внутри них.
- **`rootDir`** и **`outDir`**: где лежит исходный код и куда пишутся `.js`. С `"rootDir": "src"` и `"outDir": "dist"` файл `src/main.ts` превращается в `dist/main.js`.
- **`noEmit`**: вообще не записывать файлы. Используйте его, когда код запускает другой инструмент (см. ниже), а `tsc` нужен только для проверки.

Например, при заданных `rootDir` и `outDir` вот этот `src/main.ts`:

```ts title="src/main.ts"
function greet(name: string): string {
  return `Привет, ${name}!`;
}

console.log(greet("Mei"));
```

компилируется в `dist/main.js` — тот же код без типов (`export {}` просто помечает файл как модуль):

```js title="dist/main.js"
function greet(name) {
    return `Привет, ${name}!`;
}
console.log(greet("Mei"));
export {};
```

<Callout type="tip" title="Настройки PandaDev">

Редакторы на этом сайте используют такие параметры: `"strict": true`, `"target": "es2022"`, `"module": "esnext"`, `"moduleResolution": "bundler"`, `"moduleDetection": "force"` (каждый фрагмент — модуль, поэтому и работает `await` на верхнем уровне), `"esModuleInterop": true` и `"noEmit": true`, а `lib` — это `es2023` плюс типы либо Web Worker, либо DOM. Если скопировать их в новый проект, ваш код будет проверяться точно так же, как здесь.

</Callout>

## Дополнительные флаги безопасности

Некоторые полезные проверки **не** входят в `strict`, обычно потому, что в старом проекте их включение даёт кучу ошибок. В новом проекте они того стоят. Более того, `tsc --init` в TypeScript 6 уже включает первые два.

### noUncheckedIndexedAccess

Без этого флага TypeScript считает, что каждый индекс массива и каждый поиск по ключу что-то находят:

```ts
const names: string[] = [];
const first = names[0]; // тип: string, значение: undefined!
```

С **`noUncheckedIndexedAccess`** обращения через `[...]` честно включают `undefined`, поэтому промах нужно обработать:

```ts
const names: string[] = ["Mei", "Sam"];
const first: string = names[0];
// ❌ Error: Type 'string | undefined' is not assignable to type 'string'.

const prices: Record<string, number> = { tea: 3 };
console.log(prices["cake"].toFixed(2));
// ❌ Error: Object is possibly 'undefined'.
```

Даже `if (names.length > 0)` не убеждает проверку типов, что `names[0]` существует. А вот эти приёмы убеждают, и они хороши сами по себе — с флагом или без:

<CodeExample output={`MEI
1
3
3
sam`}>

```ts
const names = ["Mei", "Sam"];
const scores: Record<string, number> = { mei: 12, sam: 7 };

// 1. Прочитать один раз, затем проверить
const first = names[0];
if (first !== undefined) {
  console.log(first.toUpperCase());
}

// 2. Значение по умолчанию через ??
console.log((scores["ana"] ?? 0) + 1);

// 3. for...of обходит только существующие элементы
for (const name of names) {
  console.log(name.length);
}

// 4. at() возвращает string | undefined даже без флага
const last = names.at(-1);
console.log(last?.toLowerCase());
```

</CodeExample>

### exactOptionalPropertyTypes

Необязательное свойство `theme?: string` может означать две вещи: «свойства может **не быть**» или «оно может быть, но со значением **`undefined`**». По умолчанию TypeScript разрешает и то и другое, и за этим прячется неприятная ошибка. Помните обновления через `Partial` из урока [Работа с типизированными данными](/learn/typescript/typed-data)? Если распаковать изменения с явным `undefined`, обязательное свойство сотрётся:

<CodeExample output={`{ theme: undefined, fontSize: 14 }
undefined`}>

```ts
interface Settings {
  theme: string;
  fontSize: number;
}

function update(
  settings: Settings,
  changes: Partial<Settings>,
): Settings {
  return { ...settings, ...changes };
}

const current: Settings = { theme: "night", fontSize: 14 };
const next = update(current, { theme: undefined });
console.log(next);
console.log(typeof next.theme); // а тип говорит, что это string!
```

</CodeExample>

С **`exactOptionalPropertyTypes`** знак `?` означает только «может отсутствовать», и плохой вызов ловится:

```ts
update(current, { theme: undefined });
// ❌ Error: Argument of type '{ theme: undefined; }' is not assignable to parameter of type 'Partial<Settings>' with 'exactOptionalPropertyTypes: true'. Consider adding 'undefined' to the types of the target's properties.
```

Если свойство действительно может хранить `undefined`, так и напишите: `theme?: string | undefined`.

### noImplicitReturns и noFallthroughCasesInSwitch

Два флага поменьше для классических оплошностей. **`noImplicitReturns`** сообщает о функциях, в которых на некоторых путях забыт `return`:

```ts
function label(score: number) {
  // ❌ Error: Not all code paths return a value.
  if (score > 10) {
    return "high";
  } else if (score > 5) {
    return "mid";
  }
}
```

**`noFallthroughCasesInSwitch`** сообщает о `case`, который «проваливается» в следующий, потому что в нём нет `break`:

```ts
switch (size) {
  case "s":
  // ❌ Error: Fallthrough case in switch.
    price = 1;
  case "m":
    price = 2;
    break;
}
```

Вам могут встретиться и `noUnusedLocals` с `noUnusedParameters`, которые сообщают о переменных и параметрах, которые нигде не используются. Многие команды оставляют это линтеру.

## Запускаем TypeScript по-настоящему

А вот и сюрприз: большинство инструментов, которые **запускают** TypeScript, его **не проверяют**. Они удаляют типы и выполняют оставшийся JavaScript, и это очень быстро. Проверка — работа `tsc`. Распространённые способы запустить код:

| Инструмент                  | Команда                    | Проверяет типы? |
| --------------------------- | -------------------------- | --------------- |
| `tsc`, затем Node.js        | `npx tsc && node dist/main.js` | да          |
| Node.js напрямую            | `node main.ts`             | нет             |
| tsx                         | `npx tsx main.ts`          | нет             |
| Vite (браузерные приложения) | `npm run dev`             | нет             |

- **Node.js** (22.18 и новее) умеет запускать файлы `.ts` напрямую, вырезая типы. Разрешён только синтаксис, который можно просто стереть, поэтому enum, namespace и [свойства-параметры](/learn/typescript/classes-and-access-modifiers) конструктора не работают:

  ```text
  SyntaxError [ERR_UNSUPPORTED_TYPESCRIPT_SYNTAX]: TypeScript enum is not supported in strip-only mode
  ```

  Флаг **`erasableSyntaxOnly`** заставляет `tsc` сообщать о таком синтаксисе заранее, прямо в редакторе (`This syntax is not allowed when 'erasableSyntaxOnly' is enabled.`). Ещё одна причина, по которой этот курс предпочитает объединения строковых литералов, а не enum.
- **tsx** — небольшой npm-инструмент, который запускает любой файл TypeScript, включая enum, и перезапускается при изменениях с помощью `npx tsx watch main.ts`.
- **Vite** обслуживает браузерные приложения и компилирует каждый файл в момент запроса. Создать проект можно командой `npm create vite@latest my-app -- --template vanilla-ts`. Его скрипт сборки запускает `tsc` перед `vite build`, так что ошибка типа останавливает сборку.

Поэтому при любой конфигурации держите `tsc --noEmit` в своём рабочем процессе, например в виде npm-скриптов:

```json title="package.json"
{
  "scripts": {
    "dev": "vite",
    "typecheck": "tsc --noEmit",
    "build": "tsc --noEmit && vite build"
  }
}
```

<Callout type="warning" title="Запускается — значит, всё в порядке?">

Поскольку `node main.ts`, tsx и Vite пропускают проверку типов, код с ошибками типов всё равно запускается — ровно до того момента, когда натыкается на баг, о котором пыталась предупредить проверка. Запускайте `npm run typecheck` перед коммитом и настройте CI на запуск этой команды для каждого пул-реквеста, чтобы сломанные типы никогда не попадали в основную ветку.

</Callout>

## Ваш редактор тоже запускает TypeScript

Красные волнистые подчёркивания, типы при наведении, автоимпорт и «переименовать везде» — всё это делает сам TypeScript: редакторы вроде VS Code запускают в фоне его **языковой сервис** (language service), используя **тот же** `tsconfig.json`, что и `tsc`. Несколько полезных вещей:

- **F12** (Go to Definition, «Перейти к определению») на чём-то из пакета открывает его файл `.d.ts` — отличный способ узнать, что библиотека принимает на самом деле.
- **F2** переименовывает переменную, функцию или свойство во всех файлах, где они используются, и делает это безопасно, потому что редактор знает типы.
- **Быстрые исправления** (quick fixes, Ctrl+. или Cmd+.) добавляют недостающие импорты, отсутствующие свойства и многое другое.
- Редактор проверяет только **открытые** файлы. `tsc --noEmit` проверяет весь проект.
- Если редактор и `tsc` не согласны, возможно, редактор использует другую версию TypeScript. В VS Code выполните **TypeScript: Select TypeScript Version** и выберите версию из рабочей области. После изменения `tsconfig.json` команда **TypeScript: Restart TS Server** заставит его перечитать настройки.

Менять флаги компилятора в этом редакторе нельзя, поэтому в заготовке таблицы магазина получили тип `Lookup<T>`, из-за которого каждое `prices[item]` имеет тип `number | undefined` — ровно как при включённом флаге. Две функции больше не компилируются. Сделайте весь модуль магазина безопасным:

1. **`priceOf(item)`** возвращает цену или `undefined` для товара, которого магазин не продаёт. Тест типов проверяет, что возвращаемый тип это допускает.
2. **`orderTotal(order)`** складывает цены известных товаров и собирает названия неизвестных в `unknown` по порядку. `["tea", "pizza", "cake"]` даёт `{ total: 7.5, unknown: ["pizza"] }`.
3. **`restock(item, amount)`** прибавляет `amount` к запасу товара (товар без записи о запасе начинается с `0`), сохраняет результат в `stock` и возвращает новое количество.
4. **`lowStock(limit)`** возвращает названия товаров, которых на складе **меньше** `limit`, отсортированные по алфавиту.

Никаких `!` и `as`: обработайте `undefined` как следует.

<Hint>

1. Замените возвращаемый тип на `number | undefined`.
2. Прочитайте цену в переменную один раз, `const price = prices[item]`, затем `if (price === undefined)` добавьте название в `unknown`, а в ветке `else` прибавьте цену к `total`.
3. `(stock[item] ?? 0) + amount` даёт новое количество; затем запишите его обратно через `stock[item] = count`.
4. Пройдитесь циклом по `Object.entries(stock)`: каждая запись — это `[string, number | undefined]`, поэтому проверьте `count !== undefined && count < limit`. Сортируйте через `(a, b) => a.localeCompare(b)`.

```ts
// Команда включает noUncheckedIndexedAccess. Редактор
// PandaDev не может менять флаги компилятора, поэтому этот тип
// делает каждое обращение ровно таким же честным, как флаг:
type Lookup<T> = { [key: string]: T | undefined };

const prices: Lookup<number> = { tea: 3, cake: 4.5, bamboo: 1.25 };
const stock: Lookup<number> = { tea: 12, cake: 0, bamboo: 30 };

interface OrderTotal {
  total: number;
  unknown: string[];
}

function priceOf(item: string): number | undefined {
  return prices[item];
}

function orderTotal(order: string[]): OrderTotal {
  let total = 0;
  const unknown: string[] = [];
  for (const item of order) {
    const price = prices[item];
    if (price === undefined) {
      unknown.push(item);
    } else {
      total += price;
    }
  }
  return { total, unknown };
}

function restock(item: string, amount: number): number {
  const count = (stock[item] ?? 0) + amount;
  stock[item] = count;
  return count;
}

function lowStock(limit: number): string[] {
  const low: string[] = [];
  for (const [item, count] of Object.entries(stock)) {
    if (count !== undefined && count < limit) {
      low.push(item);
    }
  }
  return low.sort((a, b) => a.localeCompare(b));
}

// Тесты типов: функция не вызывается, только проверяется.
// Строка под комментарием expect-error ОБЯЗАНА быть ошибкой типа.
function typeTests(): void {
  // @ts-expect-error: обращение может промахнуться
  const sure: number = priceOf("tea");
  const maybe: number | undefined = priceOf("tea");
  const order: OrderTotal = orderTotal(["tea"]);
  const count: number = restock("tea", 1);
  const items: string[] = lowStock(5);
}

console.log(priceOf("cake"), priceOf("pizza")); // 4.5 undefined
console.log(orderTotal(["tea", "pizza", "cake"]));
// { total: 7.5, unknown: [ 'pizza' ] }
console.log(lowStock(10)); // [ 'cake' ]
```

## Итоги

- `tsc` проверяет типы и генерирует JavaScript. В проекте запускайте `npx tsc` (или `npx tsc --noEmit`, чтобы только проверить), а файлы пусть выбирает `tsconfig.json`.
- `strict` — обязательное семейство проверок. `target` задаёт выходной JavaScript, `lib` — встроенные типы (`"dom"` для браузеров, `"types": ["node"]` для Node), `module`/`moduleResolution` — как работают импорты, а `include`/`rootDir`/`outDir`/`noEmit` — файлы.
- Дополнительная защита: `noUncheckedIndexedAccess` (обращение может промахнуться), `exactOptionalPropertyTypes` (отсутствие — не то же самое, что `undefined`), `noImplicitReturns` и `noFallthroughCasesInSwitch`.
- Node.js, tsx и Vite **запускают** TypeScript, вырезая типы без проверки. Держите `tsc --noEmit` в своих скриптах и в CI; `erasableSyntaxOnly` гарантирует, что типы из вашего кода можно просто вырезать.
- Ваш редактор использует тот же TypeScript и тот же `tsconfig.json`: пользуйтесь переходом к определению, переименованием и быстрыми исправлениями и выбирайте версию TypeScript из рабочей области.
