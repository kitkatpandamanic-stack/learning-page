Real projects aren't one file. Your code is split into **modules**, and a lot of the code you run isn't yours at all: npm packages, scripts loaded from a CDN, the browser itself. In this lesson you'll see how types travel between your own files, where TypeScript finds the types of everybody else's code, and what to do when there aren't any. 📦

<Callout type="note" title="Examples in this lesson">

The PandaDev editor runs one file at a time, so multi-file examples are shown as plain files, with the file name on top. Every snippet you run here is still a module, so `import` from the built-in packages, `export`, `declare` and `declare global` all work.

</Callout>

## Modules in TypeScript

TypeScript uses the same `import` and `export` as JavaScript (see [Modules: import and export](/learn/javascript/modules) if you need a refresher). The difference: you can export **types** as well as values. Here is the `query` helper from the last lesson, moved into its own module, plus a module of shared types:

```ts title="src/dom.ts"
export function query<T extends Element>(
  selector: string,
  type: new () => T,
): T {
  const element = document.querySelector(selector);
  if (!(element instanceof type)) {
    throw new Error(`Expected ${selector} to be ${type.name}`);
  }
  return element;
}
```

```ts title="src/profile.ts"
export type Theme = "bamboo" | "night";

export interface Profile {
  name: string;
  age: number;
  theme: Theme;
}

export function isTheme(value: string): value is Theme {
  return value === "bamboo" || value === "night";
}
```

```ts title="src/main.ts"
import { query } from "./dom";
import { isTheme, type Profile } from "./profile";

const nameInput = query("#name", HTMLInputElement);
const fallback: Profile = { name: "Guest", age: 1, theme: "bamboo" };
```

The types flow across files: in `main.ts`, `fallback` is checked against the `Profile` interface from `profile.ts`, and if someone renames `theme` there, every file that uses it gets an error.

<Callout type="warning" title="Sometimes you write .js for a .ts file">

With a bundler such as Vite, you write `"./profile"` as above. Projects that run on Node.js with `"module": "nodenext"` must write `"./profile.js"`, even though the file on disk is `profile.ts`, because the import has to point at the file that will **run** after compiling. TypeScript tells you if you forget:

```text
error TS2835: Relative import paths need explicit file extensions in ECMAScript imports when '--moduleResolution' is 'node16' or 'nodenext'. Did you mean './profile.js'?
```

</Callout>

## Type-only imports

Look at the second import in `main.ts` again: `type Profile`. The word `type` marks an import as **type-only**: it's used by the type checker and then removed completely, so nothing about it is left in the JavaScript. There are two ways to write it:

```ts
// The whole import is types only
import type { Profile, Theme } from "./profile";

// Mixed: isTheme is a value, Profile is a type
import { isTheme, type Profile } from "./profile";

// Re-export types from another module
export type { Profile, Theme } from "./profile";
```

Imports from packages work the same way. In this example, Express (a popular package for web servers, which you'll use properly in Level 2) provides both values (`express()`) and types (`Request`, `Response`). The handler is written on its own, so its parameters need Express's types:

<CodeExample output={`200 [ { id: 1, text: 'Buy bamboo' } ]`}>

```ts
import express from "express";
import type { Request, Response } from "express";
import request from "supertest";

interface Note {
  id: number;
  text: string;
}

const notes: Note[] = [{ id: 1, text: "Buy bamboo" }];

// A handler written on its own needs Express's types
function listNotes(req: Request, res: Response<Note[]>): void {
  res.json(notes);
}

const app = express();
app.get("/notes", listNotes);

const res = await request(app).get("/notes");
console.log(res.status, res.body);
```

</CodeExample>

### Why it matters

Why bother marking types? Because many tools that run TypeScript **don't type-check at all**. Vite, Node.js and most bundlers simply delete the types and run what's left, and they look at **one file at a time**. When such a tool sees `import { Item } from "./prices.ts"`, it can't tell whether `Item` is a type (delete it) or a value (keep it) without reading the other file. If it guesses wrong, the code crashes. Here's what Node.js really prints when it runs a file that imports the interface `Item` without `type`:

```text
SyntaxError: The requested module './prices.ts' does not provide an export named 'Item'
```

With `import { total, type Item }` the import of `Item` is deleted, and the same file runs fine. The `tsconfig.json` option **`verbatimModuleSyntax`** (lesson 3) makes TypeScript insist on it, so you find out in your editor instead of at runtime:

```ts
import { Item } from "./prices.js";
// ❌ Error: 'Item' is a type and must be imported using a type-only import when 'verbatimModuleSyntax' is enabled.
```

## Where types come from

When you write `import ... from "something"`, TypeScript goes looking for its types:

1. **Your own files.** `"./profile"` finds `profile.ts` (or `profile.tsx`, or `profile.d.ts`). Types come straight from your code.
2. **Packages that ship their own types.** Many packages, like Vitest, Zod or date-fns, are written in TypeScript or include type files. Their `package.json` points at them, and you get types the moment you install the package.
3. **DefinitelyTyped.** For packages written in plain JavaScript, the community keeps types in a huge shared repository called **DefinitelyTyped**. They're published as separate `@types/...` packages, which you install as dev dependencies:

```bash
npm install express            # the code
npm install -D @types/express  # its types, from DefinitelyTyped
```

On npmjs.com, a small **TS** badge next to a package name means it ships its own types; a **DT** badge means there's an `@types` package for it.

4. **Nothing found.** Then TypeScript gives up. In strict mode, using a package without types is an error, here for a made-up package called `panda-slug`:

```text
error TS7016: Could not find a declaration file for module 'panda-slug'. '…/node_modules/panda-slug/index.js' implicitly has an 'any' type.
  Try `npm i --save-dev @types/panda-slug` if it exists or add a new declaration (.d.ts) file containing `declare module 'panda-slug';`
```

The browser's own types work the same way. `HTMLInputElement`, `document` and `localStorage` from the last lesson are described in **`lib.dom.d.ts`**, a file of about 45,000 lines that comes with TypeScript. Here's a tiny piece of it, slightly simplified:

```ts title="node_modules/typescript/lib/lib.dom.d.ts"
interface HTMLInputElement extends HTMLElement {
  value: string;
  valueAsNumber: number;
  // …hundreds more lines
}

declare var HTMLInputElement: {
  prototype: HTMLInputElement;
  new(): HTMLInputElement;
};
```

That `new(): HTMLInputElement` is why `query("#name", HTMLInputElement)` matched the `new () => T` parameter of your helper.

## Declaration files

A file ending in **`.d.ts`** is a **declaration file**. It contains only types: no function bodies, no values, nothing that runs. It describes code that lives somewhere else. When a library is compiled, TypeScript can write one for you next to each `.js` file (with the `declaration` option). For a file like this:

```ts title="src/prices.ts"
export interface Item {
  name: string;
  price: number;
}

export function total(items: Item[]): number {
  return items.reduce((sum, item) => sum + item.price, 0);
}
```

the compiler produces the code (`prices.js`) and this declaration file:

```ts title="dist/prices.d.ts"
export interface Item {
    name: string;
    price: number;
}
export declare function total(items: Item[]): number;
```

The keyword **`declare`** means "this exists, trust me, here is its type". It never creates anything. That's exactly how a JavaScript package and its types get shipped together.

### Writing one for an untyped package

When a package has no types and no `@types` package, you can write the declarations yourself. Describe just the parts you use, in a `.d.ts` file inside your project:

```ts title="src/types/panda-slug.d.ts"
declare module "panda-slug" {
  export function slugify(text: string, separator?: string): string;
}
```

Now the import is typed, and mistakes are caught:

```ts title="src/main.ts"
import { slugify } from "panda-slug";

slugify("Hello Panda World"); // "hello-panda-world"
slugify(42);
// ❌ Error: Argument of type 'number' is not assignable to parameter of type 'string'.
```

In a hurry, the one-line version `declare module "panda-slug";` (no body) silences the error too, but then everything from the package is `any` and `slugify(42)` compiles. Fine as a first step, not as an end state.

<Callout type="danger" title="TypeScript believes your declarations">

A declaration is a promise, and nobody checks it against the real JavaScript. If your `.d.ts` says `slugify` returns a `string` but it really returns `undefined` for empty input, TypeScript will happily trust you and the bug slips through. Read the library's docs or code, describe only what you use, and update it when you upgrade the package. If you write good types for a popular package, consider sending them to DefinitelyTyped so everyone benefits.

</Callout>

## Global declarations

Not everything arrives through `import`. A `<script>` tag can load an analytics snippet or an old library from a CDN, and servers often write settings into the page. These create **global** variables that TypeScript has never heard of:

```ts
miniChart.bars(chart, [3, 8, 5]);
// ❌ Error: Cannot find name 'miniChart'.
console.log(window.appConfig.siteName);
// ❌ Error: Property 'appConfig' does not exist on type 'Window & typeof globalThis'.
```

Describe them with **`declare global`**. Inside it, `const` declares a global variable, and `interface Window` **adds** properties to the existing `Window` interface (interfaces with the same name merge). In this page, a script tag creates both globals before your code runs:

In a real project these declarations go in a file such as `src/globals.d.ts`. One detail: a file with `import` or `export` in it is a **module**, and globals in a module must be wrapped in `declare global { … }`, as above. A `.d.ts` file with no imports or exports is a **global script**, so there you can write `declare const miniChart: MiniChart;` and `interface Window { … }` directly. Either way, make sure the file is inside the folders your `tsconfig.json` includes, which is exactly where the next lesson starts.

```ts
type ToastKind = "info" | "success" | "error";

interface ToastOptions {
  kind?: ToastKind;
}

interface PandaToast {
  version: string;
  show(message: string, options?: ToastOptions): number;
  dismiss(id: number): boolean;
}

declare global {
  const pandaToast: PandaToast;
}

function notifySaved(count: number): number {
  const noun = count === 1 ? "note" : "notes";
  return pandaToast.show(`Saved ${count} ${noun}`, {
    kind: "success",
  });
}

function notifyError(error: unknown): number {
  const message =
    error instanceof Error ? error.message : "Something went wrong";
  return pandaToast.show(message, { kind: "error" });
}

function clearAll(ids: number[]): number {
  let removed = 0;
  for (const id of ids) {
    if (pandaToast.dismiss(id)) {
      removed++;
    }
  }
  return removed;
}

// under each expect-error comment MUST be a type error.
function typeTests(): void {

  // These must compile
  const id: number = pandaToast.show("Hi", { kind: "info" });
  const removed: boolean = pandaToast.dismiss(id);
  const version: string = pandaToast.version;
```

## Recap

- TypeScript modules export and import **types** as well as values, so one interface can be shared by every file.
- `import type { X }` and `import { value, type X }` mark type-only imports; they vanish from the JavaScript. Tools that compile one file at a time need them, and `verbatimModuleSyntax` enforces them.
- TypeScript finds types in your own `.ts` files, in packages that ship their own, in `@types/*` packages from DefinitelyTyped (`npm install -D @types/x`), and in its built-in `lib.*.d.ts` files.
- A **`.d.ts` declaration file** holds only types. `declare` says "this exists" without creating anything; `declare module "x" { … }` types an untyped package.
- `declare global { … }` describes globals made by script tags; `interface Window { … }` inside it adds to the window. Declarations are promises: TypeScript trusts them, so keep them accurate.
