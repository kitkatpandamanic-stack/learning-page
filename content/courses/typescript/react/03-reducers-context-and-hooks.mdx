With a handful of `useState` calls, a component is easy to follow. Add a few more features and the update logic spreads across a dozen event handlers, the same data is passed through five layers of props, and loading code is copied from component to component. React has a tool for each of those problems: **reducers**, **context** and **custom hooks**. They all lean on types you already know (discriminated unions, `never`, generics), and together they're the backbone of the kanban board you'll build at the end of this lesson. 📋

## useReducer: every update in one place

A **reducer** is a plain function that takes the current state and an **action** (a description of what happened) and returns the **next** state:

```text
(state, action) => nextState
```

Components no longer change state themselves; they **dispatch** actions, and the reducer decides what each one means. In TypeScript the actions are a **discriminated union**, with `type` as the tag:

<TryIt
  language="tsx"
  code={`import { useReducer, useState } from "react";
import type { SubmitEvent } from "react";
import { createRoot } from "react-dom/client";

type Filter = "all" | "open" | "done";
type Todo = { id: number; title: string; done: boolean };
type State = { todos: Todo[]; filter: Filter; nextId: number };

type Action =
  | { type: "added"; title: string }
  | { type: "toggled"; id: number }
  | { type: "filterChanged"; filter: Filter };

function todosReducer(state: State, action: Action): State {
  switch (action.type) {
    case "added": {
      const todo = { id: state.nextId, title: action.title, done: false };
      return {
        ...state,
        todos: [...state.todos, todo],
        nextId: state.nextId + 1,
      };
    }
    case "toggled":
      return {
        ...state,
        todos: state.todos.map((t) =>
          t.id === action.id ? { ...t, done: !t.done } : t
        ),
      };
    case "filterChanged":
      return { ...state, filter: action.filter };
  }
}

const FILTERS: Filter[] = ["all", "open", "done"];

function Todos() {
  const [state, dispatch] = useReducer(todosReducer, {
    todos: [{ id: 1, title: "Read about reducers", done: true }],
    filter: "all",
    nextId: 2,
  });
  const [title, setTitle] = useState("");

  function handleSubmit(event: SubmitEvent<HTMLFormElement>) {
    event.preventDefault();
    if (title.trim() === "") return;
    dispatch({ type: "added", title: title.trim() });
    setTitle("");
  }

  const visible = state.todos.filter((t) =>
    state.filter === "all" ? true
    : state.filter === "done" ? t.done
    : !t.done
  );

  return (
    <>
      <form onSubmit={handleSubmit}>
        <input value={title} onChange={(e) => setTitle(e.target.value)} />
        <button>Add</button>
      </form>
      {FILTERS.map((f) => (
        <button key={f} disabled={f === state.filter}
          onClick={() => dispatch({ type: "filterChanged", filter: f })}>
          {f}
        </button>
      ))}
      <ul>
        {visible.map((t) => (
          <li key={t.id}>
            <label>
              <input type="checkbox" checked={t.done}
                onChange={() => dispatch({ type: "toggled", id: t.id })} />
              {t.title}
            </label>
          </li>
        ))}
      </ul>
    </>
  );
}

createRoot(document.getElementById("root")!).render(<Todos />);`}
/>

`useReducer(reducer, initialState)` returns the state and a **`dispatch`** function, and both are typed from the reducer: `dispatch` accepts exactly the `Action` union. Inside each `case`, TypeScript has narrowed `action`, so `action.title` only exists in `"added"`. Mistakes in actions can't reach the reducer:

```tsx
dispatch({ type: "added" });
// ❌ Error: Argument of type '{ type: "added"; }' is not assignable to parameter of type 'Action'.
// Property 'title' is missing in type '{ type: "added"; }' but required in type '{ type: "added"; title: string; }'.

dispatch({ type: "toggle", id: 1 });
// ❌ Error: Type '"toggle"' is not assignable to type '"added" | "toggled" | "filterChanged"'. Did you mean '"toggled"'?
```

Some practical points:

- **Annotate the reducer** (`(state: State, action: Action): State`) and let `useReducer` infer the rest. The return type matters: it catches a misspelt field such as `return { ...state, filtr: action.filter }` (`Object literal may only specify known properties, but 'filtr' does not exist in type 'State'. Did you mean to write 'filter'?`). Older tutorials write `useReducer<Reducer<State, Action>>(...)`; with React 19's types that's an error (`Expected 2 type arguments, but got 1.`), and you don't need it.
- **Name actions after what happened** (`"added"`, `"toggled"`) rather than as commands. It reads like a log of events, and one action can update several parts of the state.
- **A reducer must be pure**: no `fetch`, no `Math.random()`, no changing `state`. That's why `nextId` lives in the state instead of in a global counter.

## Reducers are easy to test

Because a reducer is a plain function, you can run it **without React**. It even has the exact shape `Array.prototype.reduce` expects (that's where the name comes from), so replaying a list of actions is one line:

<CodeExample output={`[
  { id: 1, title: 'Plan', done: true },
  { id: 2, title: 'Build', done: false }
]
open 3
0`}>

```ts
type Filter = "all" | "open" | "done";
type Todo = { id: number; title: string; done: boolean };
type State = { todos: Todo[]; filter: Filter; nextId: number };

type Action =
  | { type: "added"; title: string }
  | { type: "toggled"; id: number }
  | { type: "filterChanged"; filter: Filter };

function assertNever(value: never): never {
  throw new Error(`Unhandled action: ${JSON.stringify(value)}`);
}

function todosReducer(state: State, action: Action): State {
  switch (action.type) {
    case "added": {
      const todo = { id: state.nextId, title: action.title, done: false };
      return {
        ...state,
        todos: [...state.todos, todo],
        nextId: state.nextId + 1,
      };
    }
    case "toggled":
      return {
        ...state,
        todos: state.todos.map((t) =>
          t.id === action.id ? { ...t, done: !t.done } : t
        ),
      };
    case "filterChanged":
      return { ...state, filter: action.filter };
    default:
      return assertNever(action);
  }
}

const start: State = { todos: [], filter: "all", nextId: 1 };
const actions: Action[] = [
  { type: "added", title: "Plan" },
  { type: "added", title: "Build" },
  { type: "toggled", id: 1 },
  { type: "filterChanged", filter: "open" },
];

const end = actions.reduce(todosReducer, start);
console.log(end.todos);
console.log(end.filter, end.nextId);
console.log(start.todos.length); // the start state is untouched
```

</CodeExample>

This version also has a **`default`** case with the `assertNever` helper from [Discriminated Unions](/learn/typescript/discriminated-unions). After the three `case`s, TypeScript has narrowed `action` to `never`, so the call compiles. Now add a fourth action, `{ type: "removed"; id: number }`, to the union and forget to handle it, and the compiler points straight at the reducer:

```ts
default:
  return assertNever(action);
  // ❌ Error: Argument of type '{ type: "removed"; id: number; }' is not assignable to parameter of type 'never'.
```

In a big app with dozens of actions, that's the difference between "the delete button silently does nothing" and a red line in the editor before you've even run the code. (If a bad action does sneak in at runtime, say from old saved data, `assertNever` throws a clear error instead of returning `undefined`.)

<Callout type="tip" title="useState or useReducer?">

Use `useState` for independent, simple values: a text box, an open/closed flag. Reach for `useReducer` when **several pieces of state change together**, when the next state depends on the previous one in non-trivial ways, or when you'd like to test the update logic on its own. Many components start with `useState` and switch to a reducer when the handlers start to repeat each other.

</Callout>

## Typed context

Passing the same props through components that don't use them, just to reach a deeply nested child, is called **prop drilling**. **Context** lets a parent make a value available to **every** component below it, however deep. You create one with `createContext<Type>(defaultValue)`, provide a value high up in the tree, and read it anywhere below with `useContext`.

What should the default be? Usually there's no sensible "board" or "current user" outside the provider, so the common pattern is: default to **`null`**, and wrap `useContext` in a **custom hook** that throws if the provider is missing:

<TryIt
  language="tsx"
  code={`import { createContext, useContext, useState } from "react";
import type { ReactNode } from "react";
import { createRoot } from "react-dom/client";

type Theme = "light" | "dark";
type ThemeContextValue = { theme: Theme; toggle: () => void };

const ThemeContext = createContext<ThemeContextValue | null>(null);

function useTheme(): ThemeContextValue {
  const value = useContext(ThemeContext);
  if (value === null) {
    throw new Error("useTheme must be used inside <ThemeProvider>");
  }
  return value; // ThemeContextValue: null is ruled out
}

function ThemeProvider({ children }: { children: ReactNode }) {
  const [theme, setTheme] = useState<Theme>("light");
  const toggle = () => setTheme((t) => (t === "light" ? "dark" : "light"));
  return (
    <ThemeContext value={{ theme, toggle }}>{children}</ThemeContext>
  );
}

function ThemeButton() {
  const { theme, toggle } = useTheme();
  const next = theme === "light" ? "dark" : "light";
  return <button onClick={toggle}>Switch to {next}</button>;
}

function Card({ title }: { title: string }) {
  const { theme } = useTheme();
  const dark = theme === "dark";
  return (
    <article style={{ background: dark ? "#1e1b4b" : "#f5f3ff",
                      color: dark ? "white" : "black",
                      padding: 12, margin: "8px 0", borderRadius: 8 }}>
      {title}
    </article>
  );
}

function App() {
  return (
    <ThemeProvider>
      <ThemeButton />
      <Card title="Plan the board" />
      <Card title="Write the reducer" />
    </ThemeProvider>
  );
}

createRoot(document.getElementById("root")!).render(<App />);`}
/>

Neither `ThemeButton` nor `Card` receives a single prop about the theme, yet both are fully typed. Move `<ThemeButton />` **outside** `<ThemeProvider>` in `App` and run it again: instead of a confusing `Cannot read properties of null` somewhere deep inside the button, you get your own clear message.

Why the hook instead of calling `useContext(ThemeContext)` in each component? Because then every component would get `ThemeContextValue | null` and need its own null check:

```tsx
const value = useContext(ThemeContext);
value.toggle();
// ❌ Error: 'value' is possibly 'null'.
```

The hook does that check **once**, and every caller gets a non-null, fully typed value.

<Callout type="note" title="Providers in React 19 and before">

Since React 19 you render the context itself as the provider: `<ThemeContext value={...}>`. In older code (and older tutorials) you'll see `<ThemeContext.Provider value={...}>`, which still works. Either way, every component that reads the context re-renders when its `value` changes, so keep a context focused on one job (a theme, a board, a signed-in user) rather than one giant "app state" context.

</Callout>

## Generic custom hooks

A **custom hook** is a function whose name starts with `use` and that calls other hooks. It's how you reuse **stateful logic** (not markup) between components, and generics make one hook work for any type of data. Two hooks need a quick introduction first:

- **`useEffect(fn, [deps])`** runs `fn` **after** React has updated the page, and again whenever one of the listed dependencies changes. It's for talking to things outside React: storage, the network, timers. If `fn` returns a function, React calls it to **clean up** before running the effect again (or when the component disappears).
- **`useState(() => initial)`** with a function computes the initial value **once**, on the first render, instead of on every render.

### useLocalStorage&lt;T&gt;

State that survives a page reload, for any type:

<TryIt
  language="tsx"
  code={`import { useEffect, useState } from "react";
import { createRoot } from "react-dom/client";

function useLocalStorage<T>(
  key: string,
  initial: T,
  isValid: (value: unknown) => value is T,
) {
  const [value, setValue] = useState<T>(() => {
    try {
      const saved = localStorage.getItem(key);
      if (saved !== null) {
        const parsed: unknown = JSON.parse(saved);
        if (isValid(parsed)) return parsed;
      }
    } catch {
      // broken JSON: fall back to the initial value
    }
    return initial;
  });

  useEffect(() => {
    localStorage.setItem(key, JSON.stringify(value));
  }, [key, value]);

  return [value, setValue] as const;
}

const isString = (v: unknown): v is string => typeof v === "string";
const isNumber = (v: unknown): v is number => typeof v === "number";

function BoardSettings() {
  const [title, setTitle] =
    useLocalStorage("board-title", "My board", isString);
  const [limit, setLimit] = useLocalStorage("wip-limit", 3, isNumber);

  return (
    <>
      <input value={title} onChange={(e) => setTitle(e.target.value)} />
      <p>
        Max cards in Doing: {limit}{" "}
        <button onClick={() => setLimit((n) => n + 1)}>+1</button>
      </p>
      <h2>{title}</h2>
    </>
  );
}

createRoot(document.getElementById("root")!).render(<BoardSettings />);`}
/>

Change the title, click **+1**, then press **Run** again: the values come back. (The preview keeps its `localStorage` between runs, like a browser keeps it between page loads.) What the types are doing:

- **`T` is inferred** from the arguments: `string` for the title, `number` for the limit. So `setLimit` only accepts numbers (or an updater on numbers), with no type written at the call site.
- **`isValid` keeps the type honest.** `JSON.parse` returns `any`, and storage can hold anything: data saved by an older version of your app, or something a user typed into the dev tools. Parsing into `unknown` and checking with a **type guard** means `T` is only returned when the data really is a `T`.
- **`as const`** on the return value makes it a **tuple**, `readonly [T, Dispatch<SetStateAction<T>>]`, like `useState`'s. Without it, TypeScript infers an **array** whose items are "either the value or the setter", and the setter can't be called:

```tsx
return [value, setValue]; // without as const

setLimit(5);
// ❌ Error: This expression is not callable.
// Not all constituents of type 'number | Dispatch<SetStateAction<number>>' are callable.
```

### useFetch&lt;T&gt; with a status union

Loading data has three states, and they're exactly the kind of thing a discriminated union models well: there's never `data` and an `error` at the same time, and no data while loading. Rather than three separate `useState`s (`loading`, `error`, `data`) that can contradict each other, the hook returns **one** value:

<TryIt
  language="tsx"
  code={`import { useEffect, useState } from "react";
import { createRoot } from "react-dom/client";

const API = "https://api.pandadev.test";

type FetchState<T> =
  | { status: "loading" }
  | { status: "error"; message: string }
  | { status: "success"; data: T };

type Loaded<T> = { url: string; state: FetchState<T> };

function useFetch<T>(
  url: string,
  parse: (json: unknown) => T,
): FetchState<T> {
  const [loaded, setLoaded] = useState<Loaded<T> | null>(null);

  useEffect(() => {
    const controller = new AbortController();
    async function load() {
      try {
        const res = await fetch(url, { signal: controller.signal });
        if (!res.ok) throw new Error(\`HTTP \${res.status}\`);
        const data = parse(await res.json());
        setLoaded({ url, state: { status: "success", data } });
      } catch (err) {
        if (controller.signal.aborted) return; // a newer url won
        const message = err instanceof Error ? err.message : String(err);
        setLoaded({ url, state: { status: "error", message } });
      }
    }
    load();
    return () => controller.abort();
  }, [url, parse]);

  // A result for an older url means the new one is still loading
  if (loaded === null || loaded.url !== url) return { status: "loading" };
  return loaded.state;
}

type User = { id: number; name: string; email: string };

function isUser(value: unknown): value is User {
  return (
    typeof value === "object" && value !== null &&
    "id" in value && typeof value.id === "number" &&
    "name" in value && typeof value.name === "string" &&
    "email" in value && typeof value.email === "string"
  );
}

function parseUsers(json: unknown): User[] {
  if (Array.isArray(json) && json.every(isUser)) return json;
  throw new Error("Unexpected data from the API");
}

function UserList({ url }: { url: string }) {
  const users = useFetch(url, parseUsers); // FetchState<User[]>

  switch (users.status) {
    case "loading":
      return <p>Loading...</p>;
    case "error":
      return <p>😿 Couldn't load users: {users.message}</p>;
    case "success":
      return (
        <ul>
          {users.data.map((u) => (
            <li key={u.id}>{u.name} ({u.email})</li>
          ))}
        </ul>
      );
  }
}

function App() {
  const [path, setPath] = useState<"/users" | "/status/500">("/users");
  return (
    <>
      <button onClick={() => setPath("/users")}>Users</button>{" "}
      <button onClick={() => setPath("/status/500")}>Broken API</button>
      <UserList url={\`\${API}\${path}\`} />
    </>
  );
}

createRoot(document.getElementById("root")!).render(<App />);`}
/>

PandaDev has a practice API built in, so this works offline and always gives the same answers. Real APIs work the same way. Click **Broken API** to see the error state. The `switch` in `UserList` is the payoff: inside `case "success"`, TypeScript knows `users.data` exists and is a `User[]`; in `case "error"` there's a `message` and no `data`.

The `parse` parameter is there for honesty. A hook declared as `useFetch<T>(url: string)` that returns `await res.json()` compiles happily, because `res.json()` returns `any`. But then `useFetch<User[]>(url)` is a promise nobody checks: if the server sends something else, the "typed" data is wrong and the crash happens far away, in some component that trusted it. Asking for a `parse` function puts the check at the edge, where the data comes in, just like in [Runtime Validation](/learn/typescript/runtime-validation). In real projects that function is often a schema from a validation library such as **zod** (`UsersSchema.parse`), and the loading logic itself often comes from a library such as **TanStack Query**, whose `useQuery` returns the same kind of status union.

<Callout type="warning" title="Stable functions in dependency arrays">

`parse` is in the effect's dependency array, so React re-runs the effect when it changes. Pass a function defined **outside** the component, like `parseUsers` here. An inline arrow, `useFetch(url, (json) => ...)`, is a **new** function on every render, which would start a new request on every render, forever. (If a parse function must live inside a component, wrap it in `useCallback`.)

</Callout>

Time to build the **typed kanban board**: three columns, cards you can add, move left and right, and delete. All updates go through a reducer, and the components reach the board through a typed context. The starter **doesn't type-check** yet: `Action` is `never` and the context's value type is `unknown`. Steps:

1. **`Action`**: a discriminated union of `"added"` (with a `title`), `"moved"` (with an `id` and `to`, a `Column`) and `"deleted"` (with an `id`).
2. **`boardReducer`**: handle each action, always returning **new** objects and arrays. A new card gets the id `` `c${state.nextId}` ``, starts in `"todo"`, and `nextId` goes up by one. Add a `default` case with `assertNever`.
3. **`BoardContextValue`**: an object with the board `state` and `dispatch` (type it as `Dispatch<Action>`).
4. **`useBoard`**: return the context value, or `throw new Error(...)` with a helpful message when it's `null`.
5. **`AddCardForm`**: get `dispatch` from `useBoard()`, dispatch `"added"` with the trimmed title (ignore blank titles), then clear the input.
6. **`CardView`**: add `<button className="left">←</button>` and `<button className="right">→</button>` only when `left` / `right` exist, each with an `aria-label` like `Move to Doing` (use `TITLES`), plus `<button className="delete">✕</button>`. They dispatch `"moved"` and `"deleted"`.

The type tests at the bottom must keep passing: they check that `Action` accepts exactly the right shapes. Try your board in the preview: add a card and walk it across to **Done**.

`type Action = | { type: "added"; title: string } | { type: "moved"; id: string; to: Column } | { type: "deleted"; id: string };`. In the reducer: for `"added"`, `` const card: Card = { id: `c${state.nextId}`, title: action.title, column: "todo" }; `` and return `{ cards: [...state.cards, card], nextId: state.nextId + 1 }`; for `"moved"`, `state.cards.map((c) => c.id === action.id ? { ...c, column: action.to } : c)`; for `"deleted"`, `filter`. The context type: `{ state: BoardState; dispatch: Dispatch<Action> }`. In `useBoard`: `const value = useContext(BoardContext); if (value === null) throw new Error("useBoard must be used inside BoardContext"); return value;`. In `CardView`: `const { dispatch } = useBoard();` and `{left && (<button className="left" aria-label={...} onClick={() => dispatch({ type: "moved", id: card.id, to: left })}>←</button>)}`.

```tsx
import { createContext, useContext, useReducer, useState } from "react";
import type { Dispatch, SubmitEvent } from "react";
import { createRoot } from "react-dom/client";

const COLUMNS = ["todo", "doing", "done"] as const;
type Column = (typeof COLUMNS)[number];

const TITLES: Record<Column, string> = {
  todo: "To do",
  doing: "Doing",
  done: "Done",
};

type Card = { id: string; title: string; column: Column };
type BoardState = { cards: Card[]; nextId: number };

type Action =
  | { type: "added"; title: string }
  | { type: "moved"; id: string; to: Column }
  | { type: "deleted"; id: string };

function assertNever(value: never): never {
  throw new Error(`Unhandled action: ${JSON.stringify(value)}`);
}

function boardReducer(state: BoardState, action: Action): BoardState {
  switch (action.type) {
    case "added": {
      const card: Card = {
        id: `c${state.nextId}`,
        title: action.title,
        column: "todo",
      };
      return { cards: [...state.cards, card], nextId: state.nextId + 1 };
    }
    case "moved":
      return {
        ...state,
        cards: state.cards.map((c) =>
          c.id === action.id ? { ...c, column: action.to } : c
        ),
      };
    case "deleted":
      return {
        ...state,
        cards: state.cards.filter((c) => c.id !== action.id),
      };
    default:
      return assertNever(action);
  }
}

type BoardContextValue = {
  state: BoardState;
  dispatch: Dispatch<Action>;
};

const BoardContext = createContext<BoardContextValue | null>(null);

function useBoard(): BoardContextValue {
  const value = useContext(BoardContext);
  if (value === null) {
    throw new Error("useBoard must be used inside BoardContext");
  }
  return value;
}

// The column before or after this one (undefined at the edges)
function neighbour(column: Column, step: -1 | 1): Column | undefined {
  return COLUMNS[COLUMNS.indexOf(column) + step];
}

function AddCardForm() {
  const { dispatch } = useBoard();
  const [title, setTitle] = useState("");

  function handleSubmit(event: SubmitEvent<HTMLFormElement>) {
    event.preventDefault();
    const trimmed = title.trim();
    if (trimmed === "") return;
    dispatch({ type: "added", title: trimmed });
    setTitle("");
  }

  return (
    <form className="add" onSubmit={handleSubmit}>
      <input
        name="title"
        value={title}
        onChange={(e) => setTitle(e.target.value)}
        placeholder="New card"
      />
      <button type="submit">Add</button>
    </form>
  );
}

function CardView({ card }: { card: Card }) {
  const { dispatch } = useBoard();
  const left = neighbour(card.column, -1);
  const right = neighbour(card.column, 1);
  const moveTo = (to: Column) =>
    dispatch({ type: "moved", id: card.id, to });

  return (
    <li className="card">
      <span className="title">{card.title}</span>
      {left && (
        <button
          className="left"
          aria-label={`Move to ${TITLES[left]}`}
          onClick={() => moveTo(left)}
        >
          ←
        </button>
      )}
      {right && (
        <button
          className="right"
          aria-label={`Move to ${TITLES[right]}`}
          onClick={() => moveTo(right)}
        >
          →
        </button>
      )}
      <button
        className="delete"
        onClick={() => dispatch({ type: "deleted", id: card.id })}
      >
        ✕
      </button>
    </li>
  );
}

function ColumnView({ column }: { column: Column }) {
  const { state } = useBoard();
  const cards = state.cards.filter((c) => c.column === column);

  return (
    <section className={`column ${column}`}>
      <h2>{TITLES[column]} ({cards.length})</h2>
      {cards.length === 0 ? (
        <p className="empty">No cards</p>
      ) : (
        <ul>
          {cards.map((card) => (
            <CardView key={card.id} card={card} />
          ))}
        </ul>
      )}
    </section>
  );
}

const INITIAL: BoardState = {
  cards: [
    { id: "c1", title: "Plan the board", column: "done" },
    { id: "c2", title: "Write the reducer", column: "doing" },
    { id: "c3", title: "Style the cards", column: "todo" },
  ],
  nextId: 4,
};

function App() {
  const [state, dispatch] = useReducer(boardReducer, INITIAL);

  return (
    <BoardContext value={{ state, dispatch }}>
      <h1>🐼 Kanban</h1>
      <AddCardForm />
      <div className="board" style={{ display: "flex", gap: 16 }}>
        {COLUMNS.map((column) => (
          <ColumnView key={column} column={column} />
        ))}
      </div>
    </BoardContext>
  );
}

createRoot(document.getElementById("root")!).render(<App />);

// Type tests: each line under @ts-expect-error MUST be an error
const ok: Action = { type: "moved", id: "c1", to: "done" };
// @ts-expect-error: "archive" is not a Column
const bad1: Action = { type: "moved", id: "c1", to: "archive" };
// @ts-expect-error: "added" needs a title
const bad2: Action = { type: "added" };
// @ts-expect-error: there is no "renamed" action
const bad3: Action = { type: "renamed", id: "c1" };
```

## In real projects

The board you just built has the same architecture as many production React apps, just smaller:

- **One reducer per feature**, with its actions as a discriminated union and an `assertNever` default, tested with plain Vitest tests like the `reduce` example above (no browser needed; see [Testing Typed Code](/learn/typescript/testing-typed-code)).
- **A context plus a `useX()` hook per feature** (`useBoard`, `useAuth`, `useCart`), each throwing a clear error outside its provider.
- **Generic hooks** for repeated logic, or a library that provides them: TanStack Query for server data, React Hook Form for forms, and Redux Toolkit or Zustand when many features share a lot of state (they use the same reducer-and-actions idea, with even more type inference).
- To start a typed React project on your computer:

```bash
npm create vite@latest kanban -- --template react-ts
cd kanban
npm install
npm run dev
```

Vite's template sets up `.tsx`, `@types/react` and strict mode, and its build runs `tsc` so type errors stop a broken build from shipping.

## Recap

- **`useReducer(reducer, initialState)`** keeps all update logic in one pure function. Type the actions as a **discriminated union**, annotate the reducer's parameters and return type, and let `dispatch` be inferred: it only accepts valid actions.
- An **`assertNever` default** makes every forgotten action a compile error; reducers can be tested without React, even with `actions.reduce(reducer, start)`.
- **Typed context**: `createContext<Value | null>(null)` plus a **`useX()` hook** that throws when the provider is missing, so every caller gets a non-null value. In React 19, `<MyContext value={...}>` is the provider.
- **Custom hooks** reuse stateful logic; generics make them work for any type. Return tuples **`as const`**, validate data from storage or the network with **type guards** or a parse function instead of trusting `any`.
- Model async state as a **status union** (`loading` / `error` / `success`) instead of separate booleans, and keep functions in dependency arrays stable.
