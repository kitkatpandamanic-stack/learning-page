Most TypeScript you'll write at work runs in a **React** app. The good news: a React component is just a **function that takes one object and returns some markup**, and you already know how to type functions and objects. In this module you'll type every part of a React app, and finish by building a typed **kanban board** (a task board with "To do", "Doing" and "Done" columns). ⚛️

This lesson explains each React idea briefly as it comes up. If you'd like a slower introduction to React itself first, the JavaScript course has one: [Components and JSX](/learn/javascript/components-and-jsx).

## A component in TypeScript

React files that contain markup end in **`.tsx`** instead of `.ts`. The markup is **JSX**: HTML-like syntax inside JavaScript, which the build tool turns into function calls. A **component** is a function whose name starts with a capital letter and that returns JSX. Press **Run**:

<TryIt
  language="tsx"
  code={`import { createRoot } from "react-dom/client";

function Greeting({ name }: { name: string }) {
  return <h1>Hello, {name}! 🐼</h1>;
}

const root = createRoot(document.getElementById("root")!);
root.render(
  <>
    <Greeting name="Mei" />
    <Greeting name="Bao" />
  </>
);`}
/>

What's happening:

- `Greeting` receives its **props** (short for properties) as one object. We destructure `name` straight away and type the object like any other parameter: `{ name: string }`.
- You use a component like an HTML tag, and pass props like attributes: `<Greeting name="Mei" />`. Strings go in quotes; anything else goes in curly braces, like `count={3}`.
- `<>...</>` is a **fragment**: it groups two elements without adding an extra `<div>` (a component must return one root).
- `createRoot(...)` hands the page's `<div id="root">` over to React, and `render` draws the app inside it.

Notice the **`!`** after `getElementById("root")`. The DOM's types say it returns `HTMLElement | null`, because an element with that id might not exist. `createRoot` needs a real element, so without the `!` you get:

```tsx
createRoot(document.getElementById("root"));
// ❌ Error: Argument of type 'HTMLElement | null' is not assignable to parameter of type 'Container'.
```

The `!` is a **non-null assertion**: "trust me, it's there". It's fine here because the page's HTML always has that element, and this one line is the only place you need it (see [Typing the DOM](/learn/typescript/typing-the-dom) for the safer checks you'd use elsewhere). Inside components you'll handle `null` properly.

## Typing props

Writing the props type inline gets long quickly. Give it a name instead. The convention is the component's name plus **`Props`**:

<TryIt
  language="tsx"
  code={`import { createRoot } from "react-dom/client";

type TaskCardProps = {
  title: string;
  assignee: string;
  points: number;
};

function TaskCard({ title, assignee, points }: TaskCardProps) {
  return (
    <article className="card">
      <h3>{title}</h3>
      <p>
        {assignee} · {points} {points === 1 ? "point" : "points"}
      </p>
    </article>
  );
}

createRoot(document.getElementById("root")!).render(
  <>
    <TaskCard title="Design the board" assignee="Mei" points={3} />
    <TaskCard title="Write the reducer" assignee="Sam" points={1} />
  </>
);`}
/>

Now TypeScript checks **every place** the component is used, which is where most React bugs hide:

```tsx
<TaskCard title="Design the board" assignee="Mei" />
// ❌ Error: Property 'points' is missing in type '{ title: string; assignee: string; }' but required in type 'TaskCardProps'.

<TaskCard title="Design" assignee="Mei" points="3" />
// ❌ Error: Type 'string' is not assignable to type 'number'.

<Greeting nme="Mei" />
// ❌ Error: Type '{ nme: string; }' is not assignable to type 'IntrinsicAttributes & { name: string; }'.
// Property 'nme' does not exist on type 'IntrinsicAttributes & { name: string; }'. Did you mean 'name'?
```

`IntrinsicAttributes` in that last message is React's set of props that **every** component accepts, such as `key`. You can ignore it when reading the error: the useful part is at the end.

And if you forget to type the props at all, strict mode won't let it slide:

```tsx
function Card({ title }) {
  // ❌ Error: Binding element 'title' implicitly has an 'any' type.
  return <h2>{title}</h2>;
}
```

### `type` or `interface`?

Both work for props, exactly as in [Object Types and Interfaces](/learn/typescript/object-types-and-interfaces):

```tsx
interface TaskCardProps {
  title: string;
  assignee: string;
  points: number;
}
```

Many React codebases use **`type`** for props, because props often grow into unions and combinations (`A & B`, `A | B`) that only `type` can express, as you'll see below. Pick one style per project and stick to it; in this module we use `type`.

## Optional props and default values

Mark a prop **optional** with `?`. If it has a sensible default, give it one in the destructuring, just like a default parameter. Inside the component, TypeScript then knows the value is always there:

<TryIt
  language="tsx"
  code={`import { createRoot } from "react-dom/client";

type BadgeProps = {
  label: string;
  count?: number; // number | undefined
  tone?: "neutral" | "warning";
};

function Badge({ label, count, tone = "neutral" }: BadgeProps) {
  // tone is "neutral" | "warning" here (never undefined)
  const colour = tone === "warning" ? "#b45309" : "#6d28d9";
  return (
    <span style={{ color: colour, marginRight: 12 }}>
      {label}
      {count !== undefined && <strong> ({count})</strong>}
    </span>
  );
}

createRoot(document.getElementById("root")!).render(
  <p>
    <Badge label="To do" count={4} />
    <Badge label="Blocked" count={0} tone="warning" />
    <Badge label="Archive" />
  </p>
);`}
/>

`count` has no default, so it stays `number | undefined` and must be checked before use. Notice the check is `count !== undefined`, not just `count &&`: with `&&`, a count of `0` would be treated as "missing" (and React would print a stray `0`). The double braces in `style={{ ... }}` are an expression (outer pair) containing an object of CSS properties (inner pair).

## Children: `ReactNode`

Whatever you put **between** a component's tags arrives as a prop called **`children`**. Wrapper components such as cards, panels and layouts use it. Its type is **`ReactNode`**: anything React can render (elements, strings, numbers, arrays of those, `null`, `undefined` and booleans, which render nothing):

<TryIt
  language="tsx"
  code={`import type { ReactNode } from "react";
import { createRoot } from "react-dom/client";

type PanelProps = {
  title: string;
  children: ReactNode;
};

function Panel({ title, children }: PanelProps) {
  return (
    <section
      style={{ border: "1px solid #7c3aed", borderRadius: 12,
               padding: "4px 16px", marginBottom: 12 }}
    >
      <h3>{title}</h3>
      {children}
    </section>
  );
}

createRoot(document.getElementById("root")!).render(
  <>
    <Panel title="Doing">
      <p>Write the reducer</p>
      <p>Style the cards</p>
    </Panel>
    <Panel title="Done">{2 + 1} tasks finished 🎉</Panel>
  </>
);`}
/>

`import type` imports only a type, which disappears when the code is compiled. A component that doesn't declare `children` refuses them, which catches content that would silently never appear:

```tsx
<Greeting name="Mei">Hi there</Greeting>
// ❌ Error: Type '{ children: string; name: string; }' is not assignable to type 'IntrinsicAttributes & { name: string; }'.
// Property 'children' does not exist on type 'IntrinsicAttributes & { name: string; }'.
```

<Callout type="tip" title="ReactNode, not JSX.Element">

You may see `children: JSX.Element` or `ReactElement` in older code. Those only allow a **single element**, so plain text, numbers, lists or `null` are rejected. For children, `ReactNode` is almost always what you want. React also has a helper, `PropsWithChildren<P>`, which adds `children?: ReactNode` to a props type `P`.

</Callout>

## Variants as union props

Buttons, alerts and badges usually come in a few styles. Model them as a **union of string literals**, not as `string` and not as several booleans:

```tsx
// ❌ What does <Button isPrimary isGhost /> look like?
type ButtonProps = { isPrimary?: boolean; isGhost?: boolean };

// ✅ Exactly one variant, and the editor suggests the options
type ButtonProps = { variant: "primary" | "ghost" };
```

With booleans, nothing stops someone from switching on both. A union makes the impossible combination impossible to write. A `Record` keyed by the union then guarantees there's a style for **every** variant:

<TryIt
  language="tsx"
  code={`import type { ReactNode } from "react";
import { createRoot } from "react-dom/client";

type Variant = "primary" | "ghost" | "danger";

const STYLES: Record<Variant, { background: string; color: string }> = {
  primary: { background: "#7c3aed", color: "white" },
  ghost: { background: "transparent", color: "#7c3aed" },
  danger: { background: "#dc2626", color: "white" },
};

type ButtonProps = {
  variant: Variant;
  children: ReactNode;
};

function Button({ variant, children }: ButtonProps) {
  return (
    <button style={{ ...STYLES[variant], marginRight: 8 }}>
      {children}
    </button>
  );
}

createRoot(document.getElementById("root")!).render(
  <>
    <Button variant="primary">Add card</Button>
    <Button variant="ghost">Cancel</Button>
    <Button variant="danger">Delete</Button>
  </>
);`}
/>

Add `"success"` to `Variant` and TypeScript immediately reports that `STYLES` is missing it. A typo in a variant is caught where the button is used:

```tsx
<Button variant="dagner">Delete</Button>
// ❌ Error: Type '"dagner"' is not assignable to type 'Variant'. Did you mean '"danger"'?
```

## Props that belong together

Sometimes props only make sense **in certain combinations**. An avatar shows either an image (which needs `src` **and** `alt`) or initials, never both. Optional props can't say that: `{ src?: string; alt?: string; initials?: string }` happily accepts none of them, or all three. A **discriminated union** can, just like the ones in [Discriminated Unions](/learn/typescript/discriminated-unions):

<TryIt
  language="tsx"
  code={`import { createRoot } from "react-dom/client";

type AvatarProps =
  | { kind: "image"; src: string; alt: string }
  | { kind: "initials"; initials: string };

function Avatar(props: AvatarProps) {
  if (props.kind === "image") {
    // Here TypeScript knows props has src and alt
    return <img src={props.src} alt={props.alt} width={40} />;
  }
  // Here it must be the "initials" kind
  return (
    <span style={{ background: "#ede9fe", borderRadius: 20,
                   padding: 10 }}>
      {props.initials}
    </span>
  );
}

createRoot(document.getElementById("root")!).render(
  <p>
    <Avatar kind="initials" initials="ML" />{" "}
    <Avatar kind="image" src="/panda.png" alt="Bao the panda" />
  </p>
);`}
/>

(The image file doesn't exist in this preview, so the browser shows its `alt` text.) Mixed-up props are now type errors:

```tsx
<Avatar kind="image" initials="ML" />
// ❌ Error: Type '{ kind: "image"; initials: string; }' is not assignable to type 'IntrinsicAttributes & AvatarProps'.
// Property 'initials' does not exist on type 'IntrinsicAttributes & { kind: "image"; src: string; alt: string; }'.
```

Notice that `Avatar` takes `props` as a whole and checks `props.kind` **before** reading the other props. Destructuring `{ kind, src }` in the parameter list fails, because `src` doesn't exist on every member of the union.

## Callback props

Data flows **down** through props. When a child needs to tell its parent that something happened (a click, a choice), the parent passes a **function** as a prop. Type it like any callback, and by convention give it a name starting with `on`:

<TryIt
  language="tsx"
  code={`import { createRoot } from "react-dom/client";

type Task = { id: string; title: string };

type TaskListProps = {
  tasks: Task[];
  onSelect: (id: string) => void;
};

function TaskList({ tasks, onSelect }: TaskListProps) {
  return (
    <ul>
      {tasks.map((task) => (
        <li key={task.id}>
          <button onClick={() => onSelect(task.id)}>
            {task.title}
          </button>
        </li>
      ))}
    </ul>
  );
}

const tasks: Task[] = [
  { id: "t1", title: "Design the board" },
  { id: "t2", title: "Write the reducer" },
];

function handleSelect(id: string) {
  console.log("Selected", id);
}

createRoot(document.getElementById("root")!).render(
  <TaskList tasks={tasks} onSelect={handleSelect} />
);`}
/>

Click the buttons and watch the output. A few details:

- `onSelect: (id: string) => void` documents exactly what the child sends up. The return type **`void`** means "the child ignores whatever you return", so any function taking a string fits.
- `onClick={() => onSelect(task.id)}` wraps the call in an arrow function. Writing `onClick={onSelect(task.id)}` would call it **during rendering**, and TypeScript catches it: `Type 'void' is not assignable to type 'MouseEventHandler<HTMLButtonElement> | undefined'.`
- Lists rendered with `map` need a **`key`** on each item: a value that's unique among the siblings and stable, like an id. React uses it to tell the items apart when the list changes.
- Naming convention: props are `onSomething`, the functions you pass to them are `handleSomething`.

## Extending native element props

A `Button` component that wraps `<button>` should still accept everything a normal button does: `type`, `disabled`, `onClick`, `aria-label`... Listing them all by hand is hopeless. **`ComponentProps<"button">`** gives you the full, typed set of props of the `<button>` element, and you add your own with `&`:

<TryIt
  language="tsx"
  code={`import type { ComponentProps } from "react";
import { createRoot } from "react-dom/client";

type ButtonProps = ComponentProps<"button"> & {
  variant?: "primary" | "ghost";
};

function Button({ variant = "primary", ...rest }: ButtonProps) {
  return <button className={\`btn \${variant}\`} {...rest} />;
}

createRoot(document.getElementById("root")!).render(
  <p>
    <Button type="submit" onClick={(e) => console.log(e.type)}>
      Save
    </Button>{" "}
    <Button variant="ghost" disabled aria-label="Close">✕</Button>
  </p>
);`}
/>

`...rest` collects every other prop (including `children` and `onClick`) and `{...rest}` spreads them onto the real `<button>`. Even the click handler's `e` is typed for you, as a mouse event on a button. The native props stay strict:

```tsx
<Button type="sumbit">Save</Button>
// ❌ Error: Type '"sumbit"' is not assignable to type '"button" | "submit" | "reset" | undefined'. Did you mean '"submit"'?

<Button href="/board">Board</Button>
// ❌ Error: Property 'href' does not exist on type 'IntrinsicAttributes & ClassAttributes<HTMLButtonElement> & ButtonHTMLAttributes<HTMLButtonElement> & { ...; }'. Did you mean 'ref'?
```

Two related tricks you'll meet in real projects (`Omit` is one of the [utility types](/learn/typescript/utility-types)):

```tsx
// Replace a native prop with your own version: Omit removes it first
type TextFieldProps = Omit<ComponentProps<"input">, "onChange"> & {
  onChange: (value: string) => void;
};

// Reuse ANOTHER component's props, e.g. to wrap it
type FancyAvatarProps = ComponentProps<typeof Avatar> & {
  online: boolean;
};
```

## Generic components

A component can have a **type parameter**, just like a [generic function](/learn/typescript/generic-functions). A list that works for any item type, and still knows which type it holds:

<TryIt
  language="tsx"
  code={`import type { ReactNode } from "react";
import { createRoot } from "react-dom/client";

type ListProps<T> = {
  items: T[];
  getKey: (item: T) => string;
  renderItem: (item: T) => ReactNode;
};

function List<T>({ items, getKey, renderItem }: ListProps<T>) {
  return (
    <ul>
      {items.map((item) => (
        <li key={getKey(item)}>{renderItem(item)}</li>
      ))}
    </ul>
  );
}

const people = [
  { id: "u1", name: "Mei", tasks: 3 },
  { id: "u2", name: "Sam", tasks: 1 },
];

createRoot(document.getElementById("root")!).render(
  <List
    items={people}
    getKey={(person) => person.id}
    renderItem={(person) => \`\${person.name}: \${person.tasks} tasks\`}
  />
);`}
/>

`T` is **inferred** from `items`, so inside `renderItem`, `person` has the type `{ id: string; name: string; tasks: number }`. Try `person.age`: it's an error. (If you write a generic component as an **arrow function** in a `.tsx` file, write `<T,>(props: ListProps<T>) => ...` with a comma, so the parser doesn't read `<T>` as a JSX tag.)

## Why not `React.FC`?

You'll see this style in many tutorials and older codebases:

```tsx
import type { FC } from "react";

const Greeting: FC<{ name: string }> = ({ name }) => <h1>Hi, {name}</h1>;
```

It works, but most teams now prefer a plain function with typed props, as in this lesson, because:

- `FC` used to add a hidden `children` prop to **every** component (until React 18), so components accepted content they never showed. Old habits and old answers online still assume that.
- It **can't express generic components** like `List<T>` above.
- It adds nothing that a typed parameter doesn't already give you, and it's more to read.

You also don't need to annotate the **return type** of a component: TypeScript infers it from the JSX.

<Callout type="note" title="In real projects">

A typical component file exports its props type too, so other components can reuse it: `export type TaskCardProps = { ... }` next to `export function TaskCard(...)`. Vite's `react-ts` template and Next.js set up `.tsx`, JSX and React's types for you; React's types come from the **`@types/react`** package.

</Callout>

```tsx
import type { ComponentProps, ReactNode } from "react";
import { createRoot } from "react-dom/client";

type Priority = "low" | "medium" | "high";

type ButtonProps = ComponentProps<"button"> & {
  variant?: "primary" | "ghost";
};

function Button({ variant = "primary", ...rest }: ButtonProps) {
```

## Recap

- Components are functions in **`.tsx`** files; props arrive as **one object**, typed like any parameter. Name the type `ComponentNameProps`; `type` and `interface` both work.
- `createRoot(document.getElementById("root")!)`: the `!` is needed because `getElementById` returns `HTMLElement | null`.
- Optional props use `?`; a default in the destructuring removes `undefined` inside the component.
- **`children: ReactNode`** accepts anything React can render. Components without `children` in their props refuse content.
- Use **unions** for variants (`"primary" | "ghost"`) instead of `string` or boolean flags, and **discriminated unions** for props that only make sense together; narrow with `props.kind` before reading the rest.
- Callback props look like `onSelect: (id: string) => void`; pass functions, don't call them.
- **`ComponentProps<"button">`** (plus `&`, `Omit` and `...rest`) extends native elements; `ComponentProps<typeof X>` reuses another component's props.
- Components can be **generic** (`List<T>`). Prefer plain functions with typed props over `React.FC`.
