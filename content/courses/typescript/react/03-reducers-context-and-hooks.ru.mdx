Пока в компоненте несколько вызовов `useState`, за ним легко следить. Добавьте ещё пару функций — и логика обновлений расползается по десятку обработчиков событий, одни и те же данные передаются через пять слоёв пропсов, а код загрузки копируется из компонента в компонент. Для каждой из этих проблем в React есть инструмент: **редьюсеры** (reducers), **контекст** (context) и **собственные хуки** (custom hooks). Все они опираются на уже знакомые вам типы (размеченные объединения, `never`, дженерики), и вместе они составляют каркас канбан-доски, которую вы соберёте в конце урока. 📋

## useReducer: все обновления в одном месте

**Редьюсер** — это обычная функция, которая принимает текущее состояние и **действие** (action — описание того, что произошло) и возвращает **следующее** состояние:

```text
(state, action) => nextState
```

Компоненты больше не меняют состояние сами; они **отправляют** (dispatch) действия, а редьюсер решает, что каждое из них означает. В TypeScript действия — это **размеченное объединение** с тегом `type`:

<TryIt
  language="tsx"
  code={`import { useReducer, useState } from "react";
import type { SubmitEvent } from "react";
import { createRoot } from "react-dom/client";

type Filter = "all" | "open" | "done";
type Todo = { id: number; title: string; done: boolean };
type State = { todos: Todo[]; filter: Filter; nextId: number };

type Action =
  | { type: "added"; title: string }
  | { type: "toggled"; id: number }
  | { type: "filterChanged"; filter: Filter };

function todosReducer(state: State, action: Action): State {
  switch (action.type) {
    case "added": {
      const todo = { id: state.nextId, title: action.title, done: false };
      return {
        ...state,
        todos: [...state.todos, todo],
        nextId: state.nextId + 1,
      };
    }
    case "toggled":
      return {
        ...state,
        todos: state.todos.map((t) =>
          t.id === action.id ? { ...t, done: !t.done } : t
        ),
      };
    case "filterChanged":
      return { ...state, filter: action.filter };
  }
}

const FILTERS: Filter[] = ["all", "open", "done"];

function Todos() {
  const [state, dispatch] = useReducer(todosReducer, {
    todos: [{ id: 1, title: "Почитать о редьюсерах", done: true }],
    filter: "all",
    nextId: 2,
  });
  const [title, setTitle] = useState("");

  function handleSubmit(event: SubmitEvent<HTMLFormElement>) {
    event.preventDefault();
    if (title.trim() === "") return;
    dispatch({ type: "added", title: title.trim() });
    setTitle("");
  }

  const visible = state.todos.filter((t) =>
    state.filter === "all" ? true
    : state.filter === "done" ? t.done
    : !t.done
  );

  return (
    <>
      <form onSubmit={handleSubmit}>
        <input value={title} onChange={(e) => setTitle(e.target.value)} />
        <button>Добавить</button>
      </form>
      {FILTERS.map((f) => (
        <button key={f} disabled={f === state.filter}
          onClick={() => dispatch({ type: "filterChanged", filter: f })}>
          {f}
        </button>
      ))}
      <ul>
        {visible.map((t) => (
          <li key={t.id}>
            <label>
              <input type="checkbox" checked={t.done}
                onChange={() => dispatch({ type: "toggled", id: t.id })} />
              {t.title}
            </label>
          </li>
        ))}
      </ul>
    </>
  );
}

createRoot(document.getElementById("root")!).render(<Todos />);`}
/>

`useReducer(reducer, initialState)` возвращает состояние и функцию **`dispatch`**, и обе типизированы по редьюсеру: `dispatch` принимает ровно объединение `Action`. Внутри каждого `case` TypeScript уже сузил тип `action`, поэтому `action.title` существует только в `"added"`. Ошибочные действия до редьюсера не доберутся:

```tsx
dispatch({ type: "added" });
// ❌ Error: Argument of type '{ type: "added"; }' is not assignable to parameter of type 'Action'.
// Property 'title' is missing in type '{ type: "added"; }' but required in type '{ type: "added"; title: string; }'.

dispatch({ type: "toggle", id: 1 });
// ❌ Error: Type '"toggle"' is not assignable to type '"added" | "toggled" | "filterChanged"'. Did you mean '"toggled"'?
```

Несколько практических советов:

- **Аннотируйте редьюсер** (`(state: State, action: Action): State`), а остальное пусть выведет `useReducer`. Возвращаемый тип важен: он ловит опечатку в поле вроде `return { ...state, filtr: action.filter }` (`Object literal may only specify known properties, but 'filtr' does not exist in type 'State'. Did you mean to write 'filter'?`). В старых туториалах пишут `useReducer<Reducer<State, Action>>(...)`; с типами React 19 это ошибка (`Expected 2 type arguments, but got 1.`), да и не нужно.
- **Называйте действия по тому, что произошло** (`"added"`, `"toggled"`), а не как команды. Тогда они читаются как журнал событий, и одно действие может обновлять несколько частей состояния.
- **Редьюсер должен быть чистым**: никаких `fetch`, `Math.random()` и изменений `state`. Поэтому `nextId` живёт в состоянии, а не в глобальном счётчике.

## Редьюсеры легко тестировать

Раз редьюсер — обычная функция, его можно запускать **без React**. У него даже ровно та форма, которую ожидает `Array.prototype.reduce` (отсюда и название), так что прогнать список действий можно одной строкой:

<CodeExample output={`[
  { id: 1, title: 'План', done: true },
  { id: 2, title: 'Сборка', done: false }
]
open 3
0`}>

```ts
type Filter = "all" | "open" | "done";
type Todo = { id: number; title: string; done: boolean };
type State = { todos: Todo[]; filter: Filter; nextId: number };

type Action =
  | { type: "added"; title: string }
  | { type: "toggled"; id: number }
  | { type: "filterChanged"; filter: Filter };

function assertNever(value: never): never {
  throw new Error(`Необработанное действие: ${JSON.stringify(value)}`);
}

function todosReducer(state: State, action: Action): State {
  switch (action.type) {
    case "added": {
      const todo = { id: state.nextId, title: action.title, done: false };
      return {
        ...state,
        todos: [...state.todos, todo],
        nextId: state.nextId + 1,
      };
    }
    case "toggled":
      return {
        ...state,
        todos: state.todos.map((t) =>
          t.id === action.id ? { ...t, done: !t.done } : t
        ),
      };
    case "filterChanged":
      return { ...state, filter: action.filter };
    default:
      return assertNever(action);
  }
}

const start: State = { todos: [], filter: "all", nextId: 1 };
const actions: Action[] = [
  { type: "added", title: "План" },
  { type: "added", title: "Сборка" },
  { type: "toggled", id: 1 },
  { type: "filterChanged", filter: "open" },
];

const end = actions.reduce(todosReducer, start);
console.log(end.todos);
console.log(end.filter, end.nextId);
console.log(start.todos.length); // начальное состояние не тронуто
```

</CodeExample>

В этой версии есть ещё ветка **`default`** с помощником `assertNever` из урока [Размеченные объединения](/learn/typescript/discriminated-unions). После трёх `case` TypeScript сузил `action` до `never`, поэтому вызов компилируется. Теперь добавьте в объединение четвёртое действие, `{ type: "removed"; id: number }`, и забудьте его обработать — компилятор сразу укажет на редьюсер:

```ts
default:
  return assertNever(action);
  // ❌ Error: Argument of type '{ type: "removed"; id: number; }' is not assignable to parameter of type 'never'.
```

В большом приложении с десятками действий это разница между «кнопка удаления молча ничего не делает» и красной линией в редакторе ещё до запуска кода. (А если плохое действие всё же проберётся во время выполнения, скажем из старых сохранённых данных, `assertNever` выбросит понятную ошибку вместо того, чтобы вернуть `undefined`.)

<Callout type="tip" title="useState или useReducer?">

Используйте `useState` для независимых простых значений: текстового поля, флага «открыто/закрыто». Берите `useReducer`, когда **несколько частей состояния меняются вместе**, когда следующее состояние нетривиально зависит от предыдущего или когда хочется тестировать логику обновлений отдельно. Многие компоненты начинают с `useState` и переходят на редьюсер, когда обработчики начинают повторять друг друга.

</Callout>

## Типизированный контекст

Передачу одних и тех же пропсов через компоненты, которые их не используют, лишь бы дотянуться до глубоко вложенного потомка, называют **prop drilling** («сверление пропсами»). **Контекст** позволяет родителю сделать значение доступным **всем** компонентам ниже него, как бы глубоко они ни были. Вы создаёте его через `createContext<Type>(defaultValue)`, передаёте значение высоко в дереве и читаете его где угодно ниже через `useContext`.

Каким должно быть значение по умолчанию? Обычно вне провайдера никакой осмысленной «доски» или «текущего пользователя» нет, поэтому распространённый паттерн такой: по умолчанию **`null`**, а `useContext` обёрнут в **собственный хук**, который выбрасывает ошибку, если провайдера нет:

<TryIt
  language="tsx"
  code={`import { createContext, useContext, useState } from "react";
import type { ReactNode } from "react";
import { createRoot } from "react-dom/client";

type Theme = "light" | "dark";
type ThemeContextValue = { theme: Theme; toggle: () => void };

const ThemeContext = createContext<ThemeContextValue | null>(null);

function useTheme(): ThemeContextValue {
  const value = useContext(ThemeContext);
  if (value === null) {
    throw new Error("useTheme нужно вызывать внутри <ThemeProvider>");
  }
  return value; // ThemeContextValue: null исключён
}

function ThemeProvider({ children }: { children: ReactNode }) {
  const [theme, setTheme] = useState<Theme>("light");
  const toggle = () => setTheme((t) => (t === "light" ? "dark" : "light"));
  return (
    <ThemeContext value={{ theme, toggle }}>{children}</ThemeContext>
  );
}

function ThemeButton() {
  const { theme, toggle } = useTheme();
  const next = theme === "light" ? "dark" : "light";
  return <button onClick={toggle}>Переключить на {next}</button>;
}

function Card({ title }: { title: string }) {
  const { theme } = useTheme();
  const dark = theme === "dark";
  return (
    <article style={{ background: dark ? "#1e1b4b" : "#f5f3ff",
                      color: dark ? "white" : "black",
                      padding: 12, margin: "8px 0", borderRadius: 8 }}>
      {title}
    </article>
  );
}

function App() {
  return (
    <ThemeProvider>
      <ThemeButton />
      <Card title="Спланировать доску" />
      <Card title="Написать редьюсер" />
    </ThemeProvider>
  );
}

createRoot(document.getElementById("root")!).render(<App />);`}
/>

Ни `ThemeButton`, ни `Card` не получают ни одного пропа про тему, но оба полностью типизированы. Перенесите `<ThemeButton />` **за пределы** `<ThemeProvider>` в `App` и запустите снова: вместо невнятного `Cannot read properties of null` где-то глубоко в кнопке вы увидите своё понятное сообщение.

Зачем хук, а не `useContext(ThemeContext)` в каждом компоненте? Потому что тогда каждый компонент получал бы `ThemeContextValue | null` и нуждался бы в собственной проверке на null:

```tsx
const value = useContext(ThemeContext);
value.toggle();
// ❌ Error: 'value' is possibly 'null'.
```

Хук делает эту проверку **один раз**, и каждый вызывающий получает не-null значение с полными типами.

<Callout type="note" title="Провайдеры в React 19 и раньше">

Начиная с React 19 провайдером служит сам контекст: `<ThemeContext value={...}>`. В старом коде (и старых туториалах) вы увидите `<ThemeContext.Provider value={...}>`, и это тоже по-прежнему работает. В любом случае каждый компонент, читающий контекст, перерисовывается при изменении его `value`, поэтому держите контекст сосредоточенным на одной задаче (тема, доска, вошедший пользователь), а не делайте один гигантский контекст «состояния приложения».

</Callout>

## Обобщённые собственные хуки

**Собственный хук** — это функция, чьё имя начинается с `use` и которая вызывает другие хуки. Так переиспользуют **логику с состоянием** (а не разметку) между компонентами, а дженерики позволяют одному хуку работать с данными любого типа. Сначала коротко о двух хуках:

- **`useEffect(fn, [deps])`** запускает `fn` **после** того, как React обновил страницу, и снова — каждый раз, когда меняется одна из перечисленных зависимостей. Он нужен для общения с внешним по отношению к React миром: хранилищем, сетью, таймерами. Если `fn` возвращает функцию, React вызывает её для **очистки** перед повторным запуском эффекта (или когда компонент исчезает).
- **`useState(() => initial)`** с функцией вычисляет начальное значение **один раз**, при первом рендере, а не при каждом.

### useLocalStorage&lt;T&gt;

Состояние, которое переживает перезагрузку страницы, для любого типа:

<TryIt
  language="tsx"
  code={`import { useEffect, useState } from "react";
import { createRoot } from "react-dom/client";

function useLocalStorage<T>(
  key: string,
  initial: T,
  isValid: (value: unknown) => value is T,
) {
  const [value, setValue] = useState<T>(() => {
    try {
      const saved = localStorage.getItem(key);
      if (saved !== null) {
        const parsed: unknown = JSON.parse(saved);
        if (isValid(parsed)) return parsed;
      }
    } catch {
      // сломанный JSON: возвращаемся к начальному значению
    }
    return initial;
  });

  useEffect(() => {
    localStorage.setItem(key, JSON.stringify(value));
  }, [key, value]);

  return [value, setValue] as const;
}

const isString = (v: unknown): v is string => typeof v === "string";
const isNumber = (v: unknown): v is number => typeof v === "number";

function BoardSettings() {
  const [title, setTitle] =
    useLocalStorage("board-title", "Моя доска", isString);
  const [limit, setLimit] = useLocalStorage("wip-limit", 3, isNumber);

  return (
    <>
      <input value={title} onChange={(e) => setTitle(e.target.value)} />
      <p>
        Максимум карточек «В работе»: {limit}{" "}
        <button onClick={() => setLimit((n) => n + 1)}>+1</button>
      </p>
      <h2>{title}</h2>
    </>
  );
}

createRoot(document.getElementById("root")!).render(<BoardSettings />);`}
/>

Измените название, нажмите **+1**, а затем снова **«Запустить»**: значения вернутся. (Превью хранит свой `localStorage` между запусками, как браузер — между загрузками страницы.) Что делают типы:

- **`T` выводится** из аргументов: `string` для названия, `number` для лимита. Поэтому `setLimit` принимает только числа (или обновитель для чисел), и при вызове не нужно писать ни одного типа.
- **`isValid` сохраняет честность типа.** `JSON.parse` возвращает `any`, а в хранилище может лежать что угодно: данные, сохранённые старой версией приложения, или то, что пользователь ввёл в инструментах разработчика. Разбор в `unknown` и проверка **защитником типа** означают, что `T` возвращается, только когда данные действительно `T`.
- **`as const`** у возвращаемого значения делает его **кортежем** `readonly [T, Dispatch<SetStateAction<T>>]`, как у `useState`. Без него TypeScript выводит **массив**, элементы которого — «либо значение, либо сеттер», и сеттер нельзя вызвать:

```tsx
return [value, setValue]; // без as const

setLimit(5);
// ❌ Error: This expression is not callable.
// Not all constituents of type 'number | Dispatch<SetStateAction<number>>' are callable.
```

### useFetch&lt;T&gt; с объединением статусов

У загрузки данных три состояния, и это ровно то, что хорошо описывает размеченное объединение: `data` и `error` никогда не бывают одновременно, а во время загрузки данных нет. Вместо трёх отдельных `useState` (`loading`, `error`, `data`), которые могут противоречить друг другу, хук возвращает **одно** значение:

<TryIt
  language="tsx"
  code={`import { useEffect, useState } from "react";
import { createRoot } from "react-dom/client";

const API = "https://api.pandadev.test";

type FetchState<T> =
  | { status: "loading" }
  | { status: "error"; message: string }
  | { status: "success"; data: T };

type Loaded<T> = { url: string; state: FetchState<T> };

function useFetch<T>(
  url: string,
  parse: (json: unknown) => T,
): FetchState<T> {
  const [loaded, setLoaded] = useState<Loaded<T> | null>(null);

  useEffect(() => {
    const controller = new AbortController();
    async function load() {
      try {
        const res = await fetch(url, { signal: controller.signal });
        if (!res.ok) throw new Error(\`HTTP \${res.status}\`);
        const data = parse(await res.json());
        setLoaded({ url, state: { status: "success", data } });
      } catch (err) {
        if (controller.signal.aborted) return; // победил более новый url
        const message = err instanceof Error ? err.message : String(err);
        setLoaded({ url, state: { status: "error", message } });
      }
    }
    load();
    return () => controller.abort();
  }, [url, parse]);

  // Результат для старого url значит, что новый ещё загружается
  if (loaded === null || loaded.url !== url) return { status: "loading" };
  return loaded.state;
}

type User = { id: number; name: string; email: string };

function isUser(value: unknown): value is User {
  return (
    typeof value === "object" && value !== null &&
    "id" in value && typeof value.id === "number" &&
    "name" in value && typeof value.name === "string" &&
    "email" in value && typeof value.email === "string"
  );
}

function parseUsers(json: unknown): User[] {
  if (Array.isArray(json) && json.every(isUser)) return json;
  throw new Error("Неожиданные данные от API");
}

function UserList({ url }: { url: string }) {
  const users = useFetch(url, parseUsers); // FetchState<User[]>

  switch (users.status) {
    case "loading":
      return <p>Загрузка...</p>;
    case "error":
      return <p>😿 Не удалось загрузить пользователей: {users.message}</p>;
    case "success":
      return (
        <ul>
          {users.data.map((u) => (
            <li key={u.id}>{u.name} ({u.email})</li>
          ))}
        </ul>
      );
  }
}

function App() {
  const [path, setPath] = useState<"/users" | "/status/500">("/users");
  return (
    <>
      <button onClick={() => setPath("/users")}>Пользователи</button>{" "}
      <button onClick={() => setPath("/status/500")}>Сломанный API</button>
      <UserList url={\`\${API}\${path}\`} />
    </>
  );
}

createRoot(document.getElementById("root")!).render(<App />);`}
/>

В PandaDev встроен учебный API, поэтому пример работает без сети и всегда даёт одни и те же ответы. Настоящие API работают так же. Нажмите **«Сломанный API»**, чтобы увидеть состояние ошибки. `switch` в `UserList` — это награда за труды: внутри `case "success"` TypeScript знает, что `users.data` существует и имеет тип `User[]`; в `case "error"` есть `message` и нет `data`.

Параметр `parse` нужен для честности. Хук, объявленный как `useFetch<T>(url: string)` и возвращающий `await res.json()`, спокойно компилируется, потому что `res.json()` возвращает `any`. Но тогда `useFetch<User[]>(url)` — обещание, которое никто не проверяет: если сервер пришлёт что-то другое, «типизированные» данные окажутся неверными, а падение случится далеко, в каком-нибудь компоненте, который им поверил. Требуя функцию `parse`, вы ставите проверку на границе, там, где данные входят в программу, — ровно как в уроке [Валидация во время выполнения](/learn/typescript/runtime-validation). В реальных проектах такой функцией часто служит схема из библиотеки валидации вроде **zod** (`UsersSchema.parse`), а саму логику загрузки часто берут из библиотеки вроде **TanStack Query**, чей `useQuery` возвращает такое же объединение статусов.

<Callout type="warning" title="Стабильные функции в массивах зависимостей">

`parse` входит в массив зависимостей эффекта, поэтому React перезапускает эффект, когда она меняется. Передавайте функцию, определённую **вне** компонента, как `parseUsers` здесь. Стрелочная функция прямо в вызове, `useFetch(url, (json) => ...)`, — это **новая** функция при каждом рендере, а значит, новый запрос при каждом рендере, и так бесконечно. (Если функция разбора обязана жить внутри компонента, оберните её в `useCallback`.)

</Callout>

Стартовый код пока **не проходит проверку типов**: `Action` — это `never`, а тип значения контекста — `unknown`. Шаги:

1. **`Action`**: размеченное объединение из `"added"` (с `title`), `"moved"` (с `id` и `to` типа `Column`) и `"deleted"` (с `id`).
2. **`boardReducer`**: обработайте каждое действие, всегда возвращая **новые** объекты и массивы. Новая карточка получает id `` `c${state.nextId}` ``, начинает в `"todo"`, а `nextId` увеличивается на единицу. Добавьте ветку `default` с `assertNever`.
3. **`BoardContextValue`**: объект с состоянием доски `state` и `dispatch` (типизируйте его как `Dispatch<Action>`).
4. **`useBoard`**: верните значение контекста или выполните `throw new Error(...)` с полезным сообщением, если оно `null`.
5. **`AddCardForm`**: получите `dispatch` из `useBoard()`, отправьте `"added"` с обрезанным названием (пустые названия игнорируйте), затем очистите поле.
6. **`CardView`**: добавьте `<button className="left">←</button>` и `<button className="right">→</button>`, только когда существуют `left` / `right`, у каждой — `aria-label` вида `Переместить в «В работе»` (используйте `TITLES`), плюс `<button className="delete">✕</button>`. import { createContext, useContext, useReducer, useState } from "react";
import type { Dispatch, SubmitEvent } from "react";
import { createRoot } from "react-dom/client";

const COLUMNS = ["todo", "doing", "done"] as const;
type Column = (typeof COLUMNS)[number];

const TITLES: Record<Column, string> = {
  todo: "Сделать",
  doing: "В работе",
  done: "Готово",
};

type Card = { id: string; title: string; column: Column };
type BoardState = { cards: Card[]; nextId: number };

type Action =
  | { type: "added"; title: string }
  | { type: "moved"; id: string; to: Column }
  | { type: "deleted"; id: string };

function assertNever(value: never): never {
  throw new Error(`Необработанное действие: ${JSON.stringify(value)}`);
}

function boardReducer(state: BoardState, action: Action): BoardState {
  switch (action.type) {
    case "added": {
      const card: Card = {
        id: `c${state.nextId}`,
        title: action.title,
        column: "todo",
      };
      return { cards: [...state.cards, card], nextId: state.nextId + 1 };
    }
    case "moved":
      return {
        ...state,
        cards: state.cards.map((c) =>
          c.id === action.id ? { ...c, column: action.to } : c
        ),
      };
    case "deleted":
      return {
        ...state,
        cards: state.cards.filter((c) => c.id !== action.id),
      };
    default:
      return assertNever(action);
  }
}

type BoardContextValue = {
  state: BoardState;
  dispatch: Dispatch<Action>;
};

const BoardContext = createContext<BoardContextValue | null>(null);

function useBoard(): BoardContextValue {
  const value = useContext(BoardContext);
  if (value === null) {
    throw new Error("useBoard нужно вызывать внутри BoardContext");
  }
  return value;
}

  return COLUMNS[COLUMNS.indexOf(column) + step];

        placeholder="Новая карточка"

    </form>
  );
}

  const right = neighbour(card.column, 1);
  const moveTo = (to: Column) =>

      <span className="title">{card.title}</span>

## В реальных проектах

Доска, которую вы только что собрали, устроена так же, как многие продакшен-приложения на React, просто она меньше:

- **Один редьюсер на фичу**, с действиями в виде размеченного объединения и веткой `default` с `assertNever`, протестированный обычными тестами Vitest, как в примере с `reduce` выше (браузер не нужен; см. [Тестирование типизированного кода](/learn/typescript/testing-typed-code)).
- **Контекст плюс хук `useX()` на каждую фичу** (`useBoard`, `useAuth`, `useCart`), и каждый выбрасывает понятную ошибку вне своего провайдера.
- **Обобщённые хуки** для повторяющейся логики — или библиотека, которая их предоставляет: TanStack Query для серверных данных, React Hook Form для форм, а Redux Toolkit или Zustand — когда множество фич делят много общего состояния (они используют ту же идею редьюсера и действий, с ещё более мощным выводом типов).

Шаблон Vite настраивает `.tsx`, `@types/react` и строгий режим, а его сборка запускает `tsc`, так что ошибки типов не дадут выпустить сломанную сборку.

## Итоги

- **`useReducer(reducer, initialState)`** держит всю логику обновлений в одной чистой функции. Типизируйте действия как **размеченное объединение**, аннотируйте параметры и возвращаемый тип редьюсера и позвольте `dispatch` вывестись: он принимает только допустимые действия.
- Ветка **`default` с `assertNever`** превращает каждое забытое действие в ошибку компиляции; редьюсеры можно тестировать без React, даже через `actions.reduce(reducer, start)`.
- **Типизированный контекст**: `createContext<Value | null>(null)` плюс **хук `useX()`**, который выбрасывает ошибку, если провайдера нет, — так каждый вызывающий получает не-null значение. В React 19 провайдер — это `<MyContext value={...}>`.
- **Собственные хуки** переиспользуют логику с состоянием; дженерики позволяют им работать с любым типом. Возвращайте кортежи **`as const`**, проверяйте данные из хранилища или сети **защитниками типа** или функцией разбора, а не доверяйте `any`.
- Описывайте асинхронное состояние **объединением статусов** (`loading` / `error` / `success`) вместо отдельных логических флагов и держите функции в массивах зависимостей стабильными.
