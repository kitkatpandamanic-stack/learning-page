The components from the last lesson always show the same thing for the same props. Real interfaces change: a counter goes up, a form fills in, a card moves to another column. Data that changes over time and should update the screen is called **state**. In this lesson you'll type state, events and forms, the parts of a React app where most runtime bugs come from (and where TypeScript catches most of them). 🔁

If state and events in React are new to you, the JavaScript course explains them step by step in [State and Events](/learn/javascript/state-and-events). Here we focus on the types.

## useState and inference

**`useState(initial)`** gives a component memory. It returns a pair: the current value and a **setter**. Calling the setter stores a new value and makes React **re-render** the component (call the function again) with it:

<TryIt
  language="tsx"
  code={`import { useState } from "react";
import { createRoot } from "react-dom/client";

function Counter() {
  const [count, setCount] = useState(0);     // number
  const [label, setLabel] = useState("Bao"); // string

  return (
    <p>
      <button onClick={() => setCount(count + 1)}>
        {label} has eaten {count} bamboo 🎋
      </button>{" "}
      <button onClick={() => setLabel(label === "Bao" ? "Mei" : "Bao")}>
        Switch panda
      </button>
    </p>
  );
}

createRoot(document.getElementById("root")!).render(<Counter />);`}
/>

You didn't write a single type, yet everything is typed: TypeScript **infers** the state's type from the initial value, so `count` is a `number` and `setCount` only accepts numbers:

```tsx
setCount("1");
// ❌ Error: Argument of type 'string' is not assignable to parameter of type 'SetStateAction<number>'.
```

`SetStateAction<number>` means "a number, **or** a function that gets the previous number and returns the next one". That second form, the **updater function**, is what you use when the new value depends on the old one: `setCount((c) => c + 1)`. Its parameter `c` is inferred as `number` too.

Two rules for hooks (functions whose names start with `use`): call them only inside components or your own hooks, and only at the **top level**, never inside an `if` or a loop. React tells them apart by the order they're called in.

## When inference isn't enough

Inference only sees the **first** value. When that value doesn't tell the whole story, pass the type yourself as a **type argument**: `useState<Type>(initial)`. Three cases come up all the time.

**1. State that starts empty.** "No user selected yet" is `null`, but later it will be a `User`. From `useState(null)` alone TypeScript infers the type `null`, forever:

```tsx
const [user, setUser] = useState(null);
setUser(mei);
// ❌ Error: Argument of type '{ name: string; email: string; }' is not assignable to parameter of type 'SetStateAction<null>'.
```

**2. Empty arrays.** An empty array literal gives TypeScript nothing to go on, so `useState([])` becomes `never[]`: an array that can never hold anything.

```tsx
const [tasks, setTasks] = useState([]);
setTasks([{ id: "t1", title: "Plan" }]);
// ❌ Error: Type '{ id: string; title: string; }' is not assignable to type 'never'.
```

**3. A few allowed values.** `useState("idle")` infers plain `string`, so `setStatus("idel")` compiles. A union type keeps the state honest.

Here are all three fixed. Click the names:

<TryIt
  language="tsx"
  code={`import { useState } from "react";
import { createRoot } from "react-dom/client";

type User = { id: number; name: string; email: string };
type Status = "idle" | "saving" | "saved";

const USERS: User[] = [
  { id: 1, name: "Mei Lin", email: "mei@pandadev.test" },
  { id: 2, name: "Sam Ortiz", email: "sam@pandadev.test" },
];

function UserPicker() {
  const [selected, setSelected] = useState<User | null>(null);
  const [history, setHistory] = useState<string[]>([]);
  const [status, setStatus] = useState<Status>("idle");

  function pick(user: User) {
    setSelected(user);
    setHistory((h) => [...h, user.name]);
    setStatus("saved");
  }

  return (
    <>
      {USERS.map((u) => (
        <button key={u.id} onClick={() => pick(u)}>{u.name}</button>
      ))}
      <p>
        {selected === null
          ? "Nobody selected"
          : \`Selected: \${selected.email}\`}
      </p>
      <p>Status: {status} · History: {history.join(", ")}</p>
    </>
  );
}

createRoot(document.getElementById("root")!).render(<UserPicker />);`}
/>

With `User | null`, TypeScript makes you handle "nobody yet" before touching the user: write `selected.email` outside the check and you get `'selected' is possibly 'null'.` That's exactly the bug ("Cannot read properties of null") you'd otherwise find in production.

<Callout type="warning" title="Don't lie to useState">

`useState<User>({} as User)` or `useState<any>(null)` make the errors go away by **removing** the checks: the empty object claims to have an `email` it doesn't have. If a value can be missing, say so with `| null` and handle it. The compiler then reminds you everywhere it matters.

</Callout>

## Updating objects and arrays

React decides whether to re-render by checking if the state is a **new** value. So never change state in place (`tasks.push(...)`, `task.done = true`); always create a new array or object with spread, `map` and `filter`. TypeScript keeps an eye on those copies too:

```tsx
const [task, setTask] = useState<Task>(firstTask);

setTask({ ...task, done: true });       // ✅ new object
setTask({ ...task, dnoe: true });
// ❌ Error: Object literal may only specify known properties, and 'dnoe' does not exist in type 'SetStateAction<Task>'.

setTasks((prev) => [...prev, newTask]);                  // add
setTasks((prev) => prev.filter((t) => t.id !== id));     // remove
setTasks((prev) =>
  prev.map((t) => (t.id === id ? { ...t, done: !t.done } : t))
);                                                       // change one
```

Marking the item types `readonly` (or using `ReadonlyArray<Task>`) even turns an accidental `push` into a type error, if your team wants that extra safety.

## Event types

React passes every event handler an **event object**. When you write the handler **inline**, TypeScript already knows its type from the prop, so you rarely need to annotate it:

```tsx
<input onChange={(e) => setText(e.target.value)} />
// e is ChangeEvent<HTMLInputElement>, e.target.value is a string
```

Once you move the handler into a named function, the context is gone and strict mode wants a type:

```tsx
function handleChange(event) {
  // ❌ Error: Parameter 'event' implicitly has an 'any' type.
  setText(event.target.value);
}
```

The types you'll use most, all imported from `"react"`:

| Prop | Event type |
| --- | --- |
| `onChange` on `<input>` | `ChangeEvent<HTMLInputElement>` |
| `onChange` on `<select>` / `<textarea>` | `ChangeEvent<HTMLSelectElement>` / `ChangeEvent<HTMLTextAreaElement>` |
| `onSubmit` on `<form>` | `SubmitEvent<HTMLFormElement>` |
| `onClick` | `MouseEvent<HTMLButtonElement>` (or the element it's on) |
| `onKeyDown` / `onKeyUp` | `KeyboardEvent<HTMLInputElement>` |

The type argument is the element the handler is attached to. Each one also has a handler type, like `ChangeEventHandler<HTMLInputElement>`, if you prefer to type the whole function: `const handleChange: ChangeEventHandler<HTMLInputElement> = (e) => ...`.

<TryIt
  language="tsx"
  code={`import { useState } from "react";
import type { ChangeEvent, KeyboardEvent, MouseEvent } from "react";
import { createRoot } from "react-dom/client";

function SearchBox() {
  const [query, setQuery] = useState("");

  function handleChange(event: ChangeEvent<HTMLInputElement>) {
    setQuery(event.target.value);
  }

  function handleKeyDown(event: KeyboardEvent<HTMLInputElement>) {
    if (event.key === "Escape") setQuery("");
  }

  function handleClick(event: MouseEvent<HTMLButtonElement>) {
    const button = event.currentTarget; // HTMLButtonElement
    console.log(\`\${button.name} clicked, shift: \${event.shiftKey}\`);
  }

  return (
    <p>
      <input
        value={query}
        onChange={handleChange}
        onKeyDown={handleKeyDown}
        placeholder="Type, then press Escape"
      />{" "}
      <button name="search" onClick={handleClick}>Search</button>
      <br />You typed: {query || "(nothing)"}
    </p>
  );
}

createRoot(document.getElementById("root")!).render(<SearchBox />);`}
/>

A box like this, whose `value` comes from state and whose `onChange` updates that state, is a **controlled input**: React is always in charge of what it shows, so clearing it is just `setQuery("")`.

Notice `event.currentTarget.name`. **`currentTarget`** is the element the handler is attached to, so React types it precisely (`HTMLButtonElement`). **`target`** is wherever the event started, which for a click could be an icon inside the button, so it's only an `EventTarget`: `event.target.name` is an error (`Property 'name' does not exist on type 'EventTarget'.`). Change events on form fields are the exception: there `target` is typed as the field.

<Callout type="tip" title="Not sure of an event type? Ask the editor">

Write the handler inline first, then hover over `e` in your editor: it shows the exact type, for example `ChangeEvent<HTMLSelectElement, HTMLSelectElement>` (recent React types add the element that fired the event as a second type argument; you can leave it out). Copy it into your named handler. Also make sure the type comes from `"react"`: `MouseEvent`, `KeyboardEvent` and `SubmitEvent` also exist as **DOM** types with the same names, and if you forget the import, you get the DOM one and a confusing error.

</Callout>

In older code and tutorials you'll see `FormEvent<HTMLFormElement>` for submit handlers. It still works, but recent versions of `@types/react` mark it as deprecated in favour of `SubmitEvent`, so your editor shows it crossed out.

## Select values are just strings

A `<select>` usually stands for a union, like a task priority. But the browser only knows text, so `event.target.value` is a `string`:

```tsx
const PRIORITIES = ["low", "medium", "high"] as const;
type Priority = (typeof PRIORITIES)[number]; // "low" | "medium" | "high"

function handlePriority(event: ChangeEvent<HTMLSelectElement>) {
  setPriority(event.target.value);
  // ❌ Error: Argument of type 'string' is not assignable to parameter of type 'SetStateAction<"low" | "medium" | "high">'.
}
```

Don't silence it with `as Priority`: the options in the HTML and the type could drift apart, and the cast would hide it. Check the value with a [type guard](/learn/typescript/type-guards-and-unknown) instead, and the union stays trustworthy:

```tsx
function isPriority(value: string): value is Priority {
  return PRIORITIES.some((p) => p === value);
}

function handlePriority(event: ChangeEvent<HTMLSelectElement>) {
  const value = event.target.value;
  if (isPriority(value)) setPriority(value); // ✅ value is Priority here
}
```

`as const` makes `PRIORITIES` a readonly tuple of the three exact strings, and `(typeof PRIORITIES)[number]` turns it into the union. One list gives you both the **options to render** and the **type**, so they can't drift apart.

## Controlled forms with a typed form state

A real form has several fields. Keep them together in **one object** typed as the form's data, and write one small, generic helper that updates any field with a value of the **right type** for that field:

<TryIt
  language="tsx"
  code={`import { useState } from "react";
import type { ChangeEvent, SubmitEvent } from "react";
import { createRoot } from "react-dom/client";

const PRIORITIES = ["low", "medium", "high"] as const;
type Priority = (typeof PRIORITIES)[number];

type TaskDraft = { title: string; priority: Priority; points: number };

const EMPTY: TaskDraft = { title: "", priority: "medium", points: 1 };

function isPriority(value: string): value is Priority {
  return PRIORITIES.some((p) => p === value);
}

function TaskForm() {
  const [draft, setDraft] = useState<TaskDraft>(EMPTY);

  function update<K extends keyof TaskDraft>(
    key: K,
    value: TaskDraft[K],
  ) {
    setDraft((d) => ({ ...d, [key]: value }));
  }

  function handlePriority(event: ChangeEvent<HTMLSelectElement>) {
    const value = event.target.value;
    if (isPriority(value)) update("priority", value);
  }

  function handlePoints(event: ChangeEvent<HTMLInputElement>) {
    const points = event.target.valueAsNumber;
    update("points", Number.isNaN(points) ? 0 : points);
  }

  // Derived from the state, so it can never be out of date
  const problem =
    draft.title.trim() === "" ? "Give the task a title"
    : draft.points < 1 ? "Points must be at least 1"
    : null;

  function handleSubmit(event: SubmitEvent<HTMLFormElement>) {
    event.preventDefault(); // no page reload
    if (problem !== null) return;
    console.log("New task:", { ...draft, title: draft.title.trim() });
    setDraft(EMPTY);
  }

  return (
    <form onSubmit={handleSubmit}>
      <input
        value={draft.title}
        onChange={(e) => update("title", e.target.value)}
        placeholder="Title"
      />{" "}
      <select value={draft.priority} onChange={handlePriority}>
        {PRIORITIES.map((p) => <option key={p}>{p}</option>)}
      </select>{" "}
      <input type="number" value={draft.points} onChange={handlePoints}
        style={{ width: 50 }} />{" "}
      <button type="submit" disabled={problem !== null}>Add</button>
      <p>{problem ?? "Ready to add ✔"}</p>
    </form>
  );
}

createRoot(document.getElementById("root")!).render(<TaskForm />);`}
/>

The helper `update<K extends keyof TaskDraft>(key: K, value: TaskDraft[K])` is the `keyof` / `T[K]` pattern from [Generic Functions](/learn/typescript/generic-functions), put to work: `update("points", "3")` is an error because `TaskDraft["points"]` is `number`, and `update("titel", ...)` is an error because there's no such key. A few more things worth noticing:

- **Number inputs give strings too.** `event.target.value` is always a string; `valueAsNumber` gives a number, or `NaN` when the box is empty.
- **The problem message is derived**, not stored in state: it's calculated from `draft` on every render, so it can't get out of sync.
- **`onSubmit` on the form** (not `onClick` on the button) handles both the button and the Enter key, and `event.preventDefault()` stops the browser from reloading the page.

<Callout type="note" title="The [event.target.name] shortcut">

Many JavaScript tutorials update forms with one handler: `setDraft({ ...draft, [e.target.name]: e.target.value })`. It compiles, but TypeScript can't check it: `name` is any string, and every value is a string, so a typo in a `name` attribute or a number field filled with text slips through. The keyed helper above costs one line more and keeps every field typed. Form libraries such as React Hook Form are built around the same idea.

</Callout>

## Refs: reaching the DOM element

Sometimes you need the real DOM element, for example to **focus** an input after submitting. **`useRef`** gives you a box whose `.current` React fills with the element. Pass the element type, and `null` as the starting value, because the element doesn't exist until React has drawn it:

<TryIt
  language="tsx"
  code={`import { useRef, useState } from "react";
import { createRoot } from "react-dom/client";

function QuickAdd() {
  const inputRef = useRef<HTMLInputElement>(null);
  const renders = useRef(0); // a value that survives re-renders
  const [items, setItems] = useState<string[]>([]);
  renders.current++;

  function add() {
    const input = inputRef.current;
    if (input === null) return; // not on the page yet
    if (input.value.trim() !== "") {
      setItems((list) => [...list, input.value.trim()]);
    }
    input.value = "";
    input.focus();
  }

  return (
    <>
      <input ref={inputRef} placeholder="Idea" />{" "}
      <button onClick={add}>Add</button>
      <ul>{items.map((item, i) => <li key={i}>{item}</li>)}</ul>
      <small>Rendered {renders.current} times</small>
    </>
  );
}

createRoot(document.getElementById("root")!).render(<QuickAdd />);`}
/>

`useRef<HTMLInputElement>(null)` has the type `RefObject<HTMLInputElement | null>`, so TypeScript insists you handle the moment before React attaches the element:

```tsx
inputRef.current.focus();
// ❌ Error: 'inputRef.current' is possibly 'null'.

inputRef.current?.focus(); // ✅ does nothing if it's not there
```

Forget the type argument and you get `useRef(null)`, a ref that can only ever hold `null`: `ref.current?.focus()` then fails with `Property 'focus' does not exist on type 'never'.`

The second ref, `useRef(0)`, holds a plain **value** that survives re-renders but, unlike state, **doesn't cause** one when it changes. It's the place for things like timer ids: `useRef<number | null>(null)`. (This input is **uncontrolled**: the browser keeps its text, and we read it through the ref. That's fine for a quick add box; for forms with validation, prefer controlled inputs. The list uses the index as `key` only because items are never removed or reordered.)

## Lifting state up with typed callbacks

When two components need the same state, move it up to their closest common **parent**, pass it down as props, and pass down **callbacks** for changing it. A form that adds tasks and a list that shows them both need the task list, so `App` owns it:

<TryIt
  language="tsx"
  code={`import { useState } from "react";
import type { SubmitEvent } from "react";
import { createRoot } from "react-dom/client";

type Task = { id: string; title: string };

type AddTaskProps = { onAdd: (title: string) => void };

function AddTask({ onAdd }: AddTaskProps) {
  const [title, setTitle] = useState("");

  function handleSubmit(event: SubmitEvent<HTMLFormElement>) {
    event.preventDefault();
    if (title.trim() === "") return;
    onAdd(title.trim());
    setTitle("");
  }

  return (
    <form onSubmit={handleSubmit}>
      <input value={title} onChange={(e) => setTitle(e.target.value)} />
      <button>Add</button>
    </form>
  );
}

type TaskListProps = { tasks: Task[]; onRemove: (id: string) => void };

function TaskList({ tasks, onRemove }: TaskListProps) {
  if (tasks.length === 0) return <p>Nothing to do 🎉</p>;
  return (
    <ul>
      {tasks.map((t) => (
        <li key={t.id}>
          {t.title} <button onClick={() => onRemove(t.id)}>✕</button>
        </li>
      ))}
    </ul>
  );
}

function App() {
  const [tasks, setTasks] = useState<Task[]>([
    { id: "t1", title: "Plan the board" },
  ]);

  function addTask(title: string) {
    setTasks((prev) => [...prev, { id: crypto.randomUUID(), title }]);
  }

  function removeTask(id: string) {
    setTasks((prev) => prev.filter((t) => t.id !== id));
  }

  return (
    <>
      <AddTask onAdd={addTask} />
      <TaskList tasks={tasks} onRemove={removeTask} />
      <p>{tasks.length} tasks</p>
    </>
  );
}

createRoot(document.getElementById("root")!).render(<App />);`}
/>

Data flows **down** (`tasks`), events flow **up** (`onAdd`, `onRemove`), and each piece of state has **one owner**. The count isn't state at all: it's derived from `tasks`.

You *could* pass the setter itself down: `setTasks` has the type `Dispatch<SetStateAction<Task[]>>`, and a child could take a prop of that type. Prefer callbacks named after **what happened** (`onAdd: (title: string) => void`): the child doesn't need to know how the parent stores tasks, the parent stays in control of ids and validation, and the prop type documents exactly what the child sends.

```tsx
import { useRef, useState } from "react";
import type { ChangeEvent, SubmitEvent } from "react";
import { createRoot } from "react-dom/client";

const PRIORITIES = ["low", "medium", "high"] as const;
type Priority = (typeof PRIORITIES)[number];

type Task = { id: string; title: string; priority: Priority };
type TaskDraft = Omit<Task, "id">;

const EMPTY: TaskDraft = { title: "", priority: "medium" };

function isPriority(value: string): value is Priority {
  return PRIORITIES.some((p) => p === value);
}

type TaskFormProps = { onAdd: (draft: TaskDraft) => void };

function TaskForm({ onAdd }: TaskFormProps) {
  const [draft, setDraft] = useState<TaskDraft>(EMPTY);
  const [error, setError] = useState<string | null>(null);
  const titleRef = useRef<HTMLInputElement>(null);

  function handleTitle(event: ChangeEvent<HTMLInputElement>) {
    setDraft({ ...draft, title: event.target.value });
  }

  function handlePriority(event: ChangeEvent<HTMLSelectElement>) {
    const value = event.target.value;
    if (isPriority(value)) setDraft({ ...draft, priority: value });
  }

  function handleSubmit(event: SubmitEvent<HTMLFormElement>) {
    event.preventDefault();
    const title = draft.title.trim();
    if (title === "") {
      setError("Give the task a title");
      return;
    }
    onAdd({ title, priority: draft.priority });
    setDraft(EMPTY);
    setError(null);
    titleRef.current?.focus();
  }

  return (
    <form onSubmit={handleSubmit}>
      <input
        name="title"
        ref={titleRef}
        value={draft.title}
        onChange={handleTitle}
        placeholder="New task"
      />
      <select
        name="priority"
        value={draft.priority}
        onChange={handlePriority}
      >
        {PRIORITIES.map((p) => <option key={p}>{p}</option>)}
      </select>
      <button type="submit">Add</button>
      {error !== null && <p className="error">{error}</p>}
    </form>
  );
}

let nextId = 1;

function App() {
  const [tasks, setTasks] = useState<Task[]>([]);

  function handleAdd(draft: TaskDraft) {
    setTasks((prev) => [...prev, { id: `t${nextId++}`, ...draft }]);
  }

  return (
    <main>
      <TaskForm onAdd={handleAdd} />
      <ul className="tasks">
        {tasks.map((task) => (
          <li key={task.id} className={task.priority}>
            {task.title}
          </li>
        ))}
      </ul>
      <p className="count">{tasks.length} tasks</p>
    </main>
  );
}

createRoot(document.getElementById("root")!).render(<App />);
```

## Recap

- `useState` **infers** its type from the initial value. Pass a type argument when that isn't enough: `useState<User | null>(null)`, `useState<Task[]>([])`, `useState<Status>("idle")`. Never paper over it with `any` or `{} as T`.
- Setters take a value or an **updater** `(prev) => next`; always create new objects and arrays.
- Inline handlers are typed for you. Named handlers need React's event types: `ChangeEvent<HTMLInputElement>`, `SubmitEvent<HTMLFormElement>`, `MouseEvent<HTMLButtonElement>`, `KeyboardEvent<...>`, imported from `"react"`. `currentTarget` is precise; `target` may not be.
- Form fields give **strings**: narrow `<select>` values to a union with a type guard, and use `valueAsNumber` for numbers.
- Keep a form in one typed object and update it with a keyed helper `update<K extends keyof T>(key: K, value: T[K])`; derive validation messages instead of storing them.
- `useRef<HTMLInputElement>(null)` reaches a DOM element; handle `null` with `?.`. `useRef(value)` keeps a value without re-rendering.
- **Lift state up** to the common parent and pass down callbacks named after what happened (`onAdd: (draft: TaskDraft) => void`).
