In the last lesson you wrote generic **functions**. The same idea works for **types** and **classes**: write the shape once, with a type parameter where the details go, and fill it in later. That's how `Array<T>`, `Record<K, V>` and `Map<K, V>` are built, and by the end of this lesson you'll have written your own `Result<T, E>` and a generic `Stack<T>`. 📦

## Generic type aliases and interfaces

Add a type parameter after the name of an interface or a type alias, and use it inside:

<CodeExample output={`{ value: 28, label: 'age' }
{ first: 'Mei', second: 120 }
Sam`}>

```ts
interface Box<T> {
  value: T;
  label: string;
}

type Pair<A, B> = {
  first: A;
  second: B;
};

type Nullable<T> = T | null;

const age: Box<number> = { value: 28, label: "age" };
const score: Pair<string, number> = { first: "Mei", second: 120 };
let winner: Nullable<string> = null;
winner = "Sam";

console.log(age);
console.log(score);
console.log(winner);
```

</CodeExample>

`Box<number>` is a `Box` whose `value` is a `number`, and `Box<string[]>` would hold a list of strings. One difference from generic functions: in a type annotation, TypeScript does **not** guess the type argument for you. You have to write it:

```ts
const b: Box = { value: 1, label: "x" };
// ❌ Error: Generic type 'Box<T>' requires 1 type argument(s).
```

Generic types and generic functions work great together. Many APIs return long lists one **page** at a time. `Page<T>` describes a page of anything, and `paginate` builds one from any list:

<CodeExample output={`{ items: [ 'Leeds', 'Lagos' ], page: 2, totalPages: 3 }
[ 5 ]`}>

```ts
interface Page<T> {
  items: T[];
  page: number;
  totalPages: number;
}

function paginate<T>(all: T[], page: number, size: number): Page<T> {
  const start = (page - 1) * size;
  return {
    items: all.slice(start, start + size),
    page,
    totalPages: Math.ceil(all.length / size),
  };
}

const cities = ["Lima", "Oslo", "Leeds", "Lagos", "Rome"];
console.log(paginate(cities, 2, 2)); // Page<string>
console.log(paginate([1, 2, 3, 4, 5], 3, 2).items); // number[]
```

</CodeExample>

## `Result<T, E>`: a generic discriminated union

Here's one of the most useful generic types you'll ever write. A function that can fail either gives you a **value** or an **error**. Model that as a union with an `ok` tag, and make both sides generic:

```ts
type Result<T, E = string> =
  | { ok: true; value: T }
  | { ok: false; error: E };
```

`T` is the type of a successful value, and `E` is the type of the error. `E = string` is a **default**, so `Result<number>` means `Result<number, string>`. Because `ok` is a tag (`true` or `false`), checking it narrows the result, just like any other [discriminated union](/learn/typescript/discriminated-unions):

<CodeExample output={`Next year you'll be 29
Error: "-3" is not an age
Error: "old" is not an age`}>

```ts
type Result<T, E = string> =
  | { ok: true; value: T }
  | { ok: false; error: E };

function parseAge(text: string): Result<number> {
  const age = Number(text);
  if (!Number.isInteger(age) || age < 0) {
    return { ok: false, error: `"${text}" is not an age` };
  }
  return { ok: true, value: age };
}

for (const input of ["28", "-3", "old"]) {
  const result = parseAge(input);
  if (result.ok) {
    console.log(`Next year you'll be ${result.value + 1}`);
  } else {
    console.log(`Error: ${result.error}`);
  }
}
```

</CodeExample>

The caller **can't forget** that parsing might fail. Reading `value` before checking `ok` is an error, because a failed result has no `value`:

```ts
const result = parseAge("28");
console.log(result.value);
// ❌ Error: Property 'value' does not exist on type 'Result<number, string>'.
```

The error side doesn't have to be a string. A union of literals tells the caller exactly what can go wrong: `Result<User, "not-found" | "banned">`. You'll use that in this module's mini-project.

<Callout type="tip" title="Result vs throwing">

Throwing an error is invisible in a function's type: nothing in `parseAge(text: string): number` warns you that it might throw. A `Result` puts failure **in the type**, so TypeScript reminds every caller to handle it. Use `Result` for failures that are part of normal life (bad input, a missing record), and keep `throw` for real bugs.

</Callout>

The same trick works for any set of states. Data loaded from a server is loading, loaded or failed. One generic type covers every kind of data, and one generic function can describe them all:

<CodeExample output={`Loading…
3 messages
Something went wrong: Server is down
It's 14°C`}>

```ts
type RemoteData<T> =
  | { status: "loading" }
  | { status: "success"; data: T }
  | { status: "error"; message: string };

function describe<T>(
  state: RemoteData<T>,
  show: (data: T) => string,
): string {
  switch (state.status) {
    case "loading":
      return "Loading…";
    case "success":
      return show(state.data);
    case "error":
      return `Something went wrong: ${state.message}`;
  }
}

const inbox: RemoteData<string[]> = {
  status: "success",
  data: ["Hi", "Lunch?", "See you"],
};
const failed: RemoteData<string[]> = {
  status: "error",
  message: "Server is down",
};
const weather: RemoteData<{ temp: number }> = {
  status: "success",
  data: { temp: 14 },
};

const count = (list: string[]) => `${list.length} messages`;
console.log(describe({ status: "loading" }, count));
console.log(describe(inbox, count));
console.log(describe(failed, count));
console.log(describe(weather, (w) => `It's ${w.temp}°C`));
```

</CodeExample>

## Generic classes

A [class](/learn/typescript/classes-and-access-modifiers) can have type parameters too. Put them after the class name, and every field and method can use them. Here's a **stack**: the last item you push is the first one you pop, like a pile of plates (or the Back button in a browser):

<CodeExample output={`/basket
/shop
2`}>

```ts
class Stack<T> {
  private items: T[] = [];

  push(item: T): void {
    this.items.push(item);
  }

  pop(): T | undefined {
    return this.items.pop();
  }

  peek(): T | undefined {
    return this.items[this.items.length - 1];
  }

  get size(): number {
    return this.items.length;
  }
}

const history = new Stack<string>();
history.push("/home");
history.push("/shop");
history.push("/basket");

console.log(history.pop());
console.log(history.peek());
console.log(history.size);
```

</CodeExample>

`new Stack<string>()` creates a stack of strings, so every method knows about it: `pop()` returns `string | undefined`, and pushing the wrong thing is caught:

```ts
history.push(42);
// ❌ Error: Argument of type 'number' is not assignable to parameter of type 'string'.
```

When the constructor takes a `T`, TypeScript infers it, just like with generic functions. When it doesn't, like `new Stack()` with no arguments, there's nothing to infer from and `T` becomes `unknown`. So write the type argument whenever you create an empty collection.

<Callout type="note" title="Map is a generic class too">

JavaScript's built-in `Map` stores key-value pairs, and TypeScript types it as `Map<K, V>`. Unlike a `Record`, its `get` is honest about missing keys:

```ts
const stock = new Map<string, number>();
stock.set("tea", 12);
const cake = stock.get("cake"); // number | undefined
stock.set("cake", "3");
// ❌ Error: Argument of type 'string' is not assignable to parameter of type 'number'.
```

`has(key)`, `delete(key)`, `size` and `values()` round it off. `Set<T>` (a collection of unique values) is generic in the same way.

</Callout>

## Constraints in classes

Constraints work on classes exactly like on functions. This leaderboard needs a `score` to sort by and a `name` to show, but it keeps the **full** type of whatever you put in, so extra properties like `country` are still there when you get the entries back:

<CodeExample output={`Ana (BR): 150
Mei (CN): 120`}>

```ts
class Leaderboard<T extends { name: string; score: number }> {
  private entries: T[] = [];

  add(entry: T): void {
    this.entries.push(entry);
  }

  top(count: number): T[] {
    return [...this.entries]
      .sort((a, b) => b.score - a.score)
      .slice(0, count);
  }
}

interface Player {
  name: string;
  score: number;
  country: string;
}

const board = new Leaderboard<Player>();
board.add({ name: "Mei", score: 120, country: "CN" });
board.add({ name: "Sam", score: 95, country: "NG" });
board.add({ name: "Ana", score: 150, country: "BR" });

for (const p of board.top(2)) {
  console.log(`${p.name} (${p.country}): ${p.score}`);
}
```

</CodeExample>

A type that doesn't fit the constraint is rejected as soon as you create the class:

```ts
const broken = new Leaderboard<{ name: string }>();
// ❌ Error: Type '{ name: string; }' does not satisfy the constraint '{ name: string; score: number; }'.
```

## Read-only arrays: `ReadonlyArray<T>`

Classes like `Stack` and `Leaderboard` keep their list `private`, so nobody can mess with it from outside. But what if callers need to **see** the items? Returning the array itself would let them `push` into your private data behind your back.

The answer is a read-only type. In Level 0 you met [`readonly string[]`](/learn/typescript/arrays-and-tuples). `ReadonlyArray<T>` is the same type, spelt as a generic, and both have no `push`, `pop`, `sort` or other methods that change the array:

```ts
class Playlist<T> {
  private songs: T[] = [];

  add(song: T): void {
    this.songs.push(song);
  }

  get all(): ReadonlyArray<T> {
    return [...this.songs]; // a copy, typed as read-only
  }
}

const playlist = new Playlist<string>();
playlist.add("Panda Blues");
playlist.all.push("Sneaky song");
// ❌ Error: Property 'push' does not exist on type 'readonly string[]'.
```

Read-only arrays are also the best type for **parameters** that only read a list. A function that takes `readonly number[]` accepts both normal and read-only arrays, but one that takes `number[]` refuses read-only ones, because it *could* change them:

<CodeExample output={`12.5
6`}>

```ts
function total(prices: readonly number[]): number {
  let sum = 0;
  for (const p of prices) {
    sum += p;
  }
  return sum;
}

const basket: number[] = [4.5, 8];
const fixed: ReadonlyArray<number> = [1, 2, 3];

console.log(total(basket)); // a normal array is fine
console.log(total(fixed)); // and so is a read-only one
```

</CodeExample>

<Callout type="warning" title="Read-only is a compile-time promise">

Like every type, `readonly` disappears when the code runs. If you hand out your private array typed as `ReadonlyArray<T>`, plain JavaScript (or a sneaky `as` cast) can still change it. That's why `Playlist` returns a **copy**: the type stops honest mistakes, and the copy protects your data no matter what.

</Callout>

A print shop needs a **queue**: jobs are printed in the order they arrive (first in, first out), the opposite of a stack. The starter's `Queue` uses `any`, so it accepts anything and checks nothing. Make it generic and finish it:

1. Turn it into `class Queue<T>` and replace every `any` with the right type.
2. `enqueue(item)` adds an item at the **back**.
3. `dequeue()` removes the **front** item and returns `{ ok: true, value: item }`, or `{ ok: false, error: "Queue is empty" }` when there's nothing to remove.
4. `peek()` returns the front item without removing it (`undefined` if the queue is empty), and `size` is the number of items.
5. `toArray()` returns a **copy** of the items, front first, typed as a read-only array.

The type tests at the bottom are written for a finished `Queue<T>`: the `// @ts-expect-error` lines pass only when the line below them **is** an error.

<Hint>

Start with `class Queue<T>` and `private items: T[] = [];`. `enqueue` is a `push`. In `dequeue`, return the error result first if `this.items.length === 0`. Otherwise read the front item with `this.items[0]`, then remove it with `this.items.shift()`. (Using the value that `shift()` returns doesn't work directly: its type is `T | undefined`, and `value` must be a `T`.) For `toArray`, return `[...this.items]` with the return type `readonly T[]` (or `ReadonlyArray<T>`).

</Hint>

<Solution>

```ts
type Result<T, E> =
  | { ok: true; value: T }
  | { ok: false; error: E };

interface PrintJob {
  file: string;
  pages: number;
}

class Queue<T> {
  private items: T[] = [];

  enqueue(item: T): void {
    this.items.push(item);
  }

  dequeue(): Result<T, string> {
    if (this.items.length === 0) {
      return { ok: false, error: "Queue is empty" };
    }
    const item = this.items[0];
    this.items.shift();
    return { ok: true, value: item };
  }

  peek(): T | undefined {
    return this.items[0];
  }

  get size(): number {
    return this.items.length;
  }

  toArray(): readonly T[] {
    return [...this.items];
  }
}

// ===== Type tests: don't change anything below =====
const test = new Queue<PrintJob>();
// @ts-expect-error: only print jobs can join this queue
test.enqueue("notes.txt");
// @ts-expect-error: the copy is read-only
test.toArray().push({ file: "x.pdf", pages: 1 });

const jobs = new Queue<PrintJob>();
jobs.enqueue({ file: "report.pdf", pages: 12 });
jobs.enqueue({ file: "photo.png", pages: 1 });
const next = jobs.dequeue();
if (next.ok) {
  const pages: number = next.value.pages;
  console.log(`Printing ${next.value.file} (${pages} pages)`);
} else {
  console.log(next.error);
}
console.log(jobs.size, jobs.peek());
// Printing report.pdf (12 pages)
// 1 { file: 'photo.png', pages: 1 }
```

</Solution>

## Recap

- Interfaces and type aliases can have type parameters: `Box<T>`, `Pair<A, B>`, `Page<T>`. In annotations you must write the type argument.
- `Result<T, E>` is a generic discriminated union: check `ok` before reading `value` or `error`, and failure can't be ignored.
- Generic unions like `RemoteData<T>` model states (loading, success, error) for any kind of data.
- Generic classes (`Stack<T>`, `Queue<T>`, the built-in `Map<K, V>`) keep every method in sync with one item type.
- Constraints (`T extends { score: number }`) work on classes too, and the full type of `T` is kept.
- `ReadonlyArray<T>` (`readonly T[]`) hands out lists that can't be changed by mistake; use it for parameters that only read, and return copies of private data.
