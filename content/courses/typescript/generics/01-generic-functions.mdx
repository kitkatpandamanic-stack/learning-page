You've already used generics without writing any: `Array<string>`, `Record<string, number>` and `Partial<Contact>` are all **generic types**, types that take another type as an input. In this lesson you'll write your own **generic functions**: one function that works for numbers, strings, users or anything else, and still knows exactly what goes in and what comes out. 🧩

## The problem: one job, many types

Here's a tiny job: give back the first item of a list. With what you know so far, you'd write it once per type:

<CodeExample output={`3
Mei`}>

```ts
function firstNumber(items: number[]): number | undefined {
  return items[0];
}

function firstString(items: string[]): string | undefined {
  return items[0];
}

console.log(firstNumber([3, 1, 2]));
console.log(firstString(["Mei", "Sam"]));
```

</CodeExample>

The two bodies are identical. Only the types differ, and a third list type would need a third copy. You might try to escape with `any`, but that switches the checker off. TypeScript has no idea what comes out, so it lets a bug straight through:

```ts
function firstAny(items: any[]): any {
  return items[0];
}

const n = firstAny([3, 1, 2]);
n.toUpperCase(); // no error... 💥 crashes when it runs
```

`unknown` is safe, but now you can't do anything with the result without checking it first, even though you *know* it's a number:

```ts
function firstUnknown(items: unknown[]): unknown {
  return items[0];
}

const u = firstUnknown([1.5, 2]);
console.log(u.toFixed(1));
// ❌ Error: 'u' is of type 'unknown'.
```

What we want is a way to say: "the item that comes out has the **same type** as the items that went in, whatever that type is."

## Type parameters

That's exactly what a **type parameter** does. Write it in angle brackets after the function name, then use it like any other type:

<CodeExample output={`3.0
MEI
[ true ]`}>

```ts
function first<T>(items: T[]): T | undefined {
  return items[0];
}

function wrap<T>(value: T): T[] {
  return [value];
}

const n = first([3, 1, 2]); // T is number
const who = first(["Mei", "Sam"]); // T is string
const flags = wrap(true); // T is boolean

console.log(n?.toFixed(1));
console.log(who?.toUpperCase());
console.log(flags);
```

</CodeExample>

Read `first<T>` as "first, for some type `T`". `T` is a placeholder, just like a normal parameter is a placeholder for a value. Each time you call the function, TypeScript fills `T` in: with `number` for the first call and `string` for the second. So `n` is `number | undefined`, and calling `.toUpperCase()` on it would be an error, just as it should be.

A function with a type parameter is called a **generic function**. The name `T` (for "type") is only a convention. Any name works, and longer names like `Item` are great when a function has several.

<Callout type="note" title="Types still vanish">

Type parameters are a compile-time idea. When the code runs, `first` is just a plain JavaScript function. Generics don't make your code slower or bigger; they only make the checker smarter.

</Callout>

## Inference vs explicit type arguments

Most of the time you never write `T` yourself when you call a generic function: TypeScript **infers** it from the arguments. You *can* pass it explicitly in angle brackets, and then TypeScript checks the arguments against it:

```ts
first<string>([1, 2]);
// ❌ Error: Type 'number' is not assignable to type 'string'.
```

You need an explicit type argument when the arguments don't tell the whole story. Here `fill` makes a list of a given length. `fill(3, 0)` is clearly a `number[]`, but for empty cinema seats, `fill(4, null)` would infer `T` as `null`, and you could never put a name in a seat:

```ts
const seats = fill(4, null);
seats[1] = "Mei";
// ❌ Error: Type '"Mei"' is not assignable to type 'null'.
```

Say what you mean with `<string | null>`:

<CodeExample output={`[ 0, 0, 0 ]
[ null, 'Mei', null, null ]`}>

```ts
function fill<T>(length: number, value: T): T[] {
  return Array.from({ length }, () => value);
}

const zeros = fill(3, 0); // number[]
const seats = fill<string | null>(4, null); // (string | null)[]
seats[1] = "Mei";

console.log(zeros);
console.log(seats);
```

</CodeExample>

<Callout type="tip" title="Let inference do the work">

Start without type arguments. Only add them when TypeScript infers something too narrow (like `null` above) or has nothing to infer from (you'll see that case under "Default type parameters" below).

</Callout>

## Several type parameters

A function can have as many type parameters as it needs, separated by commas. `pair` keeps two values of two different types together, and `swap` flips them, so the types swap places too:

<CodeExample output={`[ 'Mei', 28 ]
[ 28, 'Mei' ]
28.0`}>

```ts
function pair<A, B>(first: A, second: B): [A, B] {
  return [first, second];
}

function swap<A, B>(p: [A, B]): [B, A] {
  return [p[1], p[0]];
}

const person = pair("Mei", 28); // [string, number]
const flipped = swap(person); // [number, string]

console.log(person);
console.log(flipped);
console.log(flipped[0].toFixed(1));
```

</CodeExample>

These return [tuples](/learn/typescript/arrays-and-tuples), so TypeScript knows that `flipped[0]` is a `number` and `flipped[1]` is a `string`.

## Constraints with `extends`

Inside a generic function, TypeScript only lets you do things that work for **every** possible `T`. That's a problem if you need something specific, like an `id`:

```ts
function findById<T>(items: T[], id: string): T | undefined {
  return items.find((item) => item.id === id);
  // ❌ Error: Property 'id' does not exist on type 'T'.
}
```

TypeScript is right: `T` could be `number`, and numbers have no `id`. A **constraint** limits which types `T` can be. `T extends { id: string }` means "any type, as long as it has a string `id`":

<CodeExample output={`3.5
pro`}>

```ts
interface Product {
  id: string;
  name: string;
  price: number;
}

interface Member {
  id: string;
  name: string;
  plan: "free" | "pro";
}

function findById<T extends { id: string }>(
  items: T[],
  id: string,
): T | undefined {
  return items.find((item) => item.id === id);
}

const products: Product[] = [
  { id: "p1", name: "Tea", price: 3.5 },
  { id: "p2", name: "Cake", price: 4 },
];
const members: Member[] = [{ id: "m1", name: "Mei", plan: "pro" }];

const tea = findById(products, "p1"); // Product | undefined
console.log(tea?.price);

const mei = findById(members, "m1"); // Member | undefined
console.log(mei?.plan);
```

</CodeExample>

Why not just write `items: { id: string }[]` without a generic? Because then the result would be a plain `{ id: string }`, and everything else about the product would be forgotten:

```ts
function findAny(items: { id: string }[], id: string) {
  return items.find((item) => item.id === id);
}

const tea = findAny(products, "p1"); // { id: string } | undefined
console.log(tea?.price);
// ❌ Error: Property 'price' does not exist on type '{ id: string; }'.
```

The generic version **remembers** the full type you passed in. And items without an `id` are still rejected:

```ts
const pets = [{ name: "Mo" }];
findById(pets, "1");
// ❌ Error: Argument of type '{ name: string; }[]' is not assignable to parameter of type '{ id: string; }[]'.
```

Constraints work with any type. `T extends { length: number }` accepts strings and arrays, because both have a `length`:

<CodeExample output={`panda
[ 1, 2, 3 ]`}>

```ts
function longest<T extends { length: number }>(a: T, b: T): T {
  return a.length >= b.length ? a : b;
}

console.log(longest("panda", "fox"));
console.log(longest([1, 2], [1, 2, 3]));
```

</CodeExample>

## `keyof` and `T[K]`

Two small type operators make generics really powerful with objects:

- **`keyof T`** is the union of the property names of `T`. For a `User` with `id`, `name` and `age`, `keyof User` is `"id" | "name" | "age"`.
- **`T[K]`** is an **indexed access type**: the type of property `K` in `T`. `User["age"]` is `number`.

Put them together, and you can write a function that reads any property and returns its exact type:

<CodeExample output={`29
MEI`}>

```ts
interface User {
  id: string;
  name: string;
  age: number;
}

type UserKey = keyof User; // "id" | "name" | "age"
type Age = User["age"]; // number

function getProperty<T, K extends keyof T>(obj: T, key: K): T[K] {
  return obj[key];
}

const mei: User = { id: "u1", name: "Mei", age: 28 };

const age = getProperty(mei, "age"); // number
const name = getProperty(mei, "name"); // string

console.log(age + 1);
console.log(name.toUpperCase());
```

</CodeExample>

`K extends keyof T` is a constraint that uses the **first** type parameter: "`K` must be one of `T`'s keys". So a typo in the key is caught, and TypeScript even lists the keys you could use in the editor:

```ts
getProperty(mei, "emial");
// ❌ Error: Argument of type '"emial"' is not assignable to parameter of type 'keyof User'.
```

## Generic callbacks

Generics shine when you pass [callbacks](/learn/typescript/arrow-functions-and-callbacks). Here's a home-made `map` and `filter`. `mapItems` needs two type parameters: `T` for the items that go in and `U` for whatever the callback returns:

<CodeExample output={`[ '£4.50', '£12.00', '£7.25' ]
[ 4.5, 7.25 ]`}>

```ts
function mapItems<T, U>(items: T[], fn: (item: T) => U): U[] {
  const result: U[] = [];
  for (const item of items) {
    result.push(fn(item));
  }
  return result;
}

function filterItems<T>(
  items: T[],
  keep: (item: T) => boolean,
): T[] {
  const result: T[] = [];
  for (const item of items) {
    if (keep(item)) {
      result.push(item);
    }
  }
  return result;
}

const prices = [4.5, 12, 7.25];

const labels = mapItems(prices, (p) => `£${p.toFixed(2)}`);
const cheap = filterItems(prices, (p) => p < 10);

console.log(labels); // string[]
console.log(cheap); // number[]
```

</CodeExample>

Watch how the types flow. From `prices`, TypeScript infers `T = number`. That gives the callback's `p` the type `number` (no annotation needed), and the callback returns a string, so `U = string` and `labels` is a `string[]`. This is exactly how the real `map` and `filter` on arrays are typed.

## Default type parameters

Sometimes there's nothing to infer from. `createInbox()` takes no arguments, so TypeScript can't guess what kind of messages it holds. Without help, `T` becomes `unknown` and the messages are hard to use:

```ts
const chat = createInbox();
chat.send("Hi!");
console.log(chat.all()[0].toUpperCase());
// ❌ Error: Object is of type 'unknown'.
```

A **default type parameter** (`T = string`) says what `T` should be when nobody says otherwise. You can still pick a different type explicitly:

<CodeExample output={`[ 'Hi!', 'Lunch?' ]
[ { level: 2, text: 'Disk almost full' } ]`}>

```ts
function createInbox<T = string>() {
  const messages: T[] = [];
  return {
    send(message: T) {
      messages.push(message);
    },
    all() {
      return messages;
    },
  };
}

const chat = createInbox(); // T = string (the default)
chat.send("Hi!");
chat.send("Lunch?");

const alerts = createInbox<{ level: number; text: string }>();
alerts.send({ level: 2, text: "Disk almost full" });

console.log(chat.all());
console.log(alerts.all());
```

</CodeExample>

Defaults are even more common on generic **types**, which you'll write in the next lesson.

## When NOT to use a generic

Generics are fun, so it's tempting to add them everywhere. A good rule of thumb: **a type parameter should appear at least twice**. It's there to connect things, like the type of an input to the type of the output. If it's used only once, it does nothing a plain type couldn't:

```ts
// 🤔 T is used once, so it connects nothing
function printLength<T extends { length: number }>(value: T): void {
  console.log(value.length);
}

// ✅ the same thing, simpler
function printLength(value: { length: number }): void {
  console.log(value.length);
}
```

<Callout type="warning" title="A generic return type can be a lie">

Watch out for a type parameter that appears **only in the return type**:

```ts
function parseJson<T>(text: string): T {
  return JSON.parse(text);
}

const user = parseJson<User>('{ "nmae": "Mei" }');
// no error, but this is NOT a User!
```

Nothing checks that the parsed data really is a `User`. It's a type cast in disguise. For data from outside your program, parse to `unknown` and [check it with type guards](/learn/typescript/type-guards-and-unknown) before you trust it.

</Callout>

A teammate wrote these list helpers with `any`. They work, but TypeScript can't check anything that goes through them. Make them **generic**, and finish the two bodies that are still empty:

1. `last(items)` returns the last item, or `undefined` for an empty array.
2. `pluck(items, key)` returns every item's value for `key`. `pluck(books, "year")` must be a `number[]`, and a key that doesn't exist must be an error.
3. `countBy(items, getKey)` returns how many items give each key, like `{ "sci-fi": 2, classic: 1 }`. Inside the callback, the item must have its real type.
4. `updateById(items, id, changes)` returns a **new** array where the item with that `id` has the `changes` applied. Only items with a string `id` are allowed, and `changes` must be a `Partial` of the item type.

The lines with `// @ts-expect-error` are **type tests**: they pass only when the line below really **is** an error. With `any`, nothing is an error, so TypeScript reports "Unused '@ts-expect-error' directive." until your types are right.

<Hint>

1. `last<T>(items: T[]): T | undefined`.
2. Use two type parameters, like `getProperty` in the lesson: `pluck<T, K extends keyof T>(items: T[], key: K): T[K][]`.
3. Give the callback the type `(item: T) => string`. In the body, start with `const counts: Record<string, number> = {};` and add `(counts[key] ?? 0) + 1` for each item.
4. Constrain `T` with `T extends { id: string }`, type `changes` as `Partial<T>` and `map` over the items, returning `{ ...item, ...changes }` for the matching one.

</Hint>

```ts
interface Book {
  id: string;
  title: string;
  genre: string;
  year: number;
}

const books: Book[] = [
  { id: "b1", title: "Dune", genre: "sci-fi", year: 1965 },
  { id: "b2", title: "Emma", genre: "classic", year: 1815 },
  { id: "b3", title: "Neuromancer", genre: "sci-fi", year: 1984 },
];

function last<T>(items: T[]): T | undefined {
  return items[items.length - 1];
}

function pluck<T, K extends keyof T>(items: T[], key: K): T[K][] {
  return items.map((item) => item[key]);
}

function countBy<T>(
  items: T[],
  getKey: (item: T) => string,
): Record<string, number> {
  const counts: Record<string, number> = {};
  for (const item of items) {
    const key = getKey(item);
    counts[key] = (counts[key] ?? 0) + 1;
  }
  return counts;
}

function updateById<T extends { id: string }>(
  items: T[],
  id: string,
  changes: Partial<T>,
): T[] {
  return items.map((item) =>
    item.id === id ? { ...item, ...changes } : item,
  );
}

// ===== Type tests: don't change anything below =====
const newest: Book | undefined = last(books);
const years: number[] = pluck(books, "year");
// @ts-expect-error: "author" is not a key of Book
pluck(books, "author");
const perGenre = countBy(books, (b) => b.genre);
// @ts-expect-error: b is a Book, and books have no pages
countBy(books, (b) => b.pages);
const fixed: Book[] = updateById(books, "b2", { year: 1816 });
// @ts-expect-error: year must be a number
updateById(books, "b2", { year: "1816" });
// @ts-expect-error: numbers have no id
updateById([1, 2, 3], "1", {});

console.log(newest?.title); // Neuromancer
console.log(years); // [ 1965, 1815, 1984 ]
console.log(perGenre); // { 'sci-fi': 2, classic: 1 }
console.log(fixed[1]);
// { id: 'b2', title: 'Emma', genre: 'classic', year: 1816 }
```

</Solution>

## Recap

- A **type parameter** like `<T>` is a placeholder for a type, filled in each time the function is called.
- TypeScript usually **infers** type arguments; write them explicitly (`fill<string | null>(...)`) when inference is too narrow or has nothing to go on.
- Functions can have several type parameters (`<A, B>`), and **defaults** (`<T = string>`) for when nothing can be inferred.
- **Constraints** (`T extends { id: string }`) let you use specific properties while still remembering the full type.
- `keyof T` is the union of `T`'s keys and `T[K]` is the type of one property: `<T, K extends keyof T>` makes safe property helpers.
- A type parameter should connect things: if it appears only once, or only in the return type, you probably don't need it.
