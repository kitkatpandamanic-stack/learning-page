In Level 0 you used [`Partial<T>` and `Record<K, V>`](/learn/typescript/typed-data) to type update objects and lookup tables. They're part of a whole toolbox that comes with TypeScript: **utility types**, generic types that take one type and turn it into another. In this lesson you'll meet the most useful ones, each doing a real job, and then use them to build a generic data store. 🧰

## Utility types are generic types

There's no magic in utility types. They're ordinary generic types, written in TypeScript's own library files. Here's how `Partial` is defined:

```ts
type Partial<T> = {
  [K in keyof T]?: T[K];
};
```

Read it as: "for every key `K` of `T`, an **optional** property with the same type `T[K]`". You know `keyof` and `T[K]` from [generic functions](/learn/typescript/generic-functions). The `[K in ...]` part is a **mapped type**, which you'll learn to write yourself in Level 3. For now, using these types is what matters.

Why derive types instead of writing them out by hand? Because a derived type **stays in sync**. Add a property to `User` and every type built from it (`Partial<User>`, `Omit<User, "id">`, ...) updates by itself. With hand-written copies, you'd have to remember to change each one.

## `Partial`, `Required` and `Readonly`

These three change the **modifiers** of every property:

- `Partial<T>` makes every property optional (perfect for "changes" objects).
- `Required<T>` makes every property required: the opposite of `Partial`.
- `Readonly<T>` makes every property `readonly`.

`Required` is handy for settings. Users may set some options, and you fill in the rest from defaults. After that, every option is guaranteed to be there, and the type should say so:

<CodeExample output={`{ theme: 'dark', pageSize: 20, language: 'en' }
40`}>

```ts
interface Settings {
  theme?: "light" | "dark";
  pageSize?: number;
  language?: string;
}

const defaults: Required<Settings> = {
  theme: "light",
  pageSize: 20,
  language: "en",
};

function resolveSettings(chosen: Settings): Required<Settings> {
  return { ...defaults, ...chosen };
}

const settings = resolveSettings({ theme: "dark" });
console.log(settings);
console.log(settings.pageSize * 2); // a number, never undefined
```

</CodeExample>

Without `Required`, `settings.pageSize` would be `number | undefined`, and you'd need a check or a `??` every time you used it.

`Readonly<T>` is great for parameters a function must not change. And `Object.freeze` returns a `Readonly` object, so you get protection when the code runs **and** a type error before it does:

```ts
interface Order {
  readonly id: string;
  status: "pending" | "shipped";
}

function printLabel(order: Readonly<Order>) {
  order.status = "shipped";
  // ❌ Error: Cannot assign to 'status' because it is a read-only property.
}

const limits = Object.freeze({ maxItems: 50, maxWeight: 20 });
limits.maxItems = 500;
// ❌ Error: Cannot assign to 'maxItems' because it is a read-only property.
```

<Callout type="note" title="Shallow, not deep">

`Partial`, `Required` and `Readonly` only change the **top-level** properties. In a `Readonly<User>`, you can't reassign `user.address`, but you can still change `user.address.city`. Level 3 shows how to build "deep" versions.

</Callout>

## `Pick` and `Omit`: shaping objects

`Pick<T, Keys>` keeps only some properties, and `Omit<T, Keys>` keeps everything **except** some. They're perfect for the different shapes the same data takes on its way through an app. A sign-up form sends a user without an `id` (the server makes one), and a public profile must never include the password hash:

<CodeExample output={`{
  name: 'Mei',
  email: 'mei@panda.dev',
  passwordHash: 'x8f2',
  id: 'u1',
  createdAt: '2026-03-14'
}
{ id: 'u1', name: 'Mei' }`}>

```ts
interface User {
  id: string;
  name: string;
  email: string;
  passwordHash: string;
  createdAt: string;
}

// What the sign-up form sends: everything but id and createdAt
type NewUser = Omit<User, "id" | "createdAt">;

// What other people may see
type PublicUser = Pick<User, "id" | "name">;

let nextId = 1;

function createUser(input: NewUser): User {
  const id = `u${nextId}`;
  nextId++;
  return { ...input, id, createdAt: "2026-03-14" };
}

function toPublic(user: User): PublicUser {
  return { id: user.id, name: user.name };
}

const mei = createUser({
  name: "Mei",
  email: "mei@panda.dev",
  passwordHash: "x8f2",
});
console.log(mei);
console.log(toPublic(mei));
```

</CodeExample>

Shapes like `NewUser` and `PublicUser` are often called **DTOs** (data transfer objects): the shape of data as it moves between parts of a system. Deriving them from `User` means a sign-up can't sneak in its own `id`:

```ts
createUser({
  id: "admin",
  name: "Mei",
  email: "mei@panda.dev",
  passwordHash: "x8f2",
});
// ❌ Error: Object literal may only specify known properties, and 'id' does not exist in type 'NewUser'.
```

<Callout type="warning" title="Types don't remove data">

`toPublic` builds a **new** object with just two properties. If it simply did `return user;`, TypeScript would accept it (a `User` has everything a `PublicUser` needs), but the password hash would still be in the object at runtime, and would be sent wherever that object goes. A type describes data; it never strips anything out. When data must not leak, copy only what you need.

</Callout>

One more difference: `Pick` checks that the keys exist, but `Omit` doesn't. `Omit<User, "passwrd">` is happily accepted and omits nothing, so double-check your spelling:

```ts
type Oops = Pick<User, "passwrd">;
// ❌ Error: Type '"passwrd"' does not satisfy the constraint 'keyof User'.
```

## `Record`: complete lookup tables

`Record<K, V>` is an object with keys of type `K` and values of type `V`. With a union of literals as `K`, TypeScript makes sure **every** key is present, so adding a new status later points you to every table that needs a new entry:

<CodeExample output={`{ pending: 2, shipped: 1, delivered: 0 }
⏳ Waiting for payment`}>

```ts
type OrderStatus = "pending" | "shipped" | "delivered";

const labels: Record<OrderStatus, string> = {
  pending: "⏳ Waiting for payment",
  shipped: "🚚 On its way",
  delivered: "✅ Delivered",
};

function countByStatus(
  statuses: OrderStatus[],
): Record<OrderStatus, number> {
  const counts: Record<OrderStatus, number> = {
    pending: 0,
    shipped: 0,
    delivered: 0,
  };
  for (const status of statuses) {
    counts[status]++;
  }
  return counts;
}

console.log(countByStatus(["pending", "shipped", "pending"]));
console.log(labels.pending);
```

</CodeExample>

Forget one key, and TypeScript tells you which:

```ts
const short: Record<OrderStatus, string> = {
  pending: "⏳",
  shipped: "🚚",
};
// ❌ Error: Property 'delivered' is missing in type '{ pending: string; shipped: string; }' but required in type 'Record<OrderStatus, string>'.
```

## `Exclude`, `Extract` and `NonNullable`

The next three work on **unions**, not on objects:

- `Exclude<U, X>` removes the members of `U` that fit `X`.
- `Extract<U, X>` keeps only the members of `U` that fit `X`.
- `NonNullable<T>` removes `null` and `undefined`.

`Extract` is especially useful with [discriminated unions](/learn/typescript/discriminated-unions): it pulls out one variant by its tag, so you can write a function that only accepts circles:

<CodeExample output={`[ 'pending', 'paid' ]
12.57
[ 'mei@panda.dev', 'sam@panda.dev' ]`}>

```ts
type Status = "pending" | "paid" | "shipped" | "cancelled";

// "pending" | "paid" | "shipped"
type ActiveStatus = Exclude<Status, "cancelled">;
// "shipped" | "cancelled"
type FinalStatus = Extract<Status, "shipped" | "cancelled">;

const canStillCancel: Exclude<ActiveStatus, FinalStatus>[] = [
  "pending",
  "paid",
];
console.log(canStillCancel);

type Shape =
  | { kind: "circle"; radius: number }
  | { kind: "square"; side: number };

type Circle = Extract<Shape, { kind: "circle" }>;

function circleArea(c: Circle): number {
  return Math.PI * c.radius ** 2; // no need to check kind
}
console.log(circleArea({ kind: "circle", radius: 2 }).toFixed(2));

// A generic helper: drop the nulls and undefineds from a list
function compact<T>(items: T[]): NonNullable<T>[] {
  const result: NonNullable<T>[] = [];
  for (const item of items) {
    if (item !== null && item !== undefined) {
      result.push(item);
    }
  }
  return result;
}

const emails = ["mei@panda.dev", null, "sam@panda.dev", undefined];
console.log(compact(emails)); // string[]
```

</CodeExample>

`emails` has the type `(string | null | undefined)[]`, so `T` is `string | null | undefined` and `compact` returns `NonNullable<T>[]`, which is exactly `string[]`.

## `ReturnType`, `Parameters` and `Awaited`

Sometimes the type you need is hidden inside a **function**: what it returns, or what it takes. These utilities get it out for you. To refer to a function in a type, use `typeof` with its name:

<CodeExample output={`{ userId: 'u1', token: 'tok-u1', expiresInDays: 7 }`}>

```ts
function createSession(userId: string, days: number) {
  return { userId, token: `tok-${userId}`, expiresInDays: days };
}

// { userId: string; token: string; expiresInDays: number }
type Session = ReturnType<typeof createSession>;
// [userId: string, days: number]
type SessionArgs = Parameters<typeof createSession>;

const args: SessionArgs = ["u1", 7];
const session: Session = createSession(...args);
console.log(session);
```

</CodeExample>

This is useful when a function's result has no named type (common with libraries), or when you want a type to follow a function automatically. Forgetting `typeof` is a classic slip, and TypeScript even suggests the fix:

```ts
type Session = ReturnType<createSession>;
// ❌ Error: 'createSession' refers to a value, but is being used as a type here. Did you mean 'typeof createSession'?
```

An `async` function always returns a **Promise**: a value that arrives later. (You'll work with promises properly in Level 2.) `await` unwraps a promise when the code runs, and **`Awaited<T>`** does the same for types:

<CodeExample output={`Mei has 120 followers`}>

```ts
async function loadProfile(id: string) {
  return { id, name: "Mei", followers: 120 };
}

// Promise<{ id: string; name: string; followers: number }>
type ProfilePromise = ReturnType<typeof loadProfile>;
// { id: string; name: string; followers: number }
type Profile = Awaited<ProfilePromise>;

function describeProfile(p: Profile): string {
  return `${p.name} has ${p.followers} followers`;
}

const profile = await loadProfile("u1");
console.log(describeProfile(profile));
```

</CodeExample>

## Combining utility types

Utility types are just types, so you can nest them. The most common combination is an **update patch**: any property may change, except the ones that must never change. That's `Partial` of an `Omit`:

<CodeExample output={`{ id: 'u1', name: 'Mei Lin', email: 'mei@panda.dev' }`}>

```ts
interface User {
  id: string;
  name: string;
  email: string;
}

type UserPatch = Partial<Omit<User, "id">>;

function updateUser(user: User, patch: UserPatch): User {
  return { ...user, ...patch };
}

const mei: User = { id: "u1", name: "Mei", email: "mei@panda.dev" };
console.log(updateUser(mei, { name: "Mei Lin" }));
```

</CodeExample>

Changing the `id` is now a type error, not a bug report three weeks later:

```ts
updateUser(mei, { id: "u99" });
// ❌ Error: Object literal may only specify known properties, and 'id' does not exist in type 'Partial<Omit<User, "id">>'.
```

<Callout type="tip" title="Name your combinations">

`Partial<Omit<User, "id">>` is easy to read once, but tiring the fifth time. Give it a name like `UserPatch` and use that everywhere. The name also tells readers **why** the type exists.

</Callout>

Time to put the whole module together. Build `Store<T>`, a generic in-memory store that works for books, users, orders or anything else with an `id`. (A real app would put a database behind the same methods.) It uses the `Result` type from the last lesson for errors, and tells **subscribers** about every change, so other parts of an app (a list on screen, a log, a save button) can react.

**Types.** The three `TYPES:` comments mark what to fix. The `// @ts-expect-error` lines are type tests that pass only when the line below them **is** an error, so the starter won't run until all three are done:

1. Only types with a string `id` may be stored: add a constraint to `T`.
2. `update`'s `changes` may contain any property **except** `id`.
3. `list()` returns a **read-only** array.

**Behaviour.** Then make every method work, as described in the comments:

- `add(item)` stores the item, or returns a `"duplicate-id"` error if that id is taken.
- `get(id)` returns the item, or `undefined`.
- `update(id, changes)` replaces the item with a **new** object that has the changes applied (don't change the old object: listeners get it as `previous`). A missing id is a `"not-found"` error.
- `remove(id)` deletes the item and returns it, or a `"not-found"` error.
- `find(predicate)` returns every item for which `predicate` returns `true`.
- `list()` returns a copy of all items in the order they were added.
- `subscribe(listener)` registers a listener and returns a function that removes it. After every **successful** `add`, `update` and `remove`, call each listener with an `"added"`, `"updated"` (with `previous`) or `"removed"` event.

<Hint>

**Types:** `class Store<T extends { id: string }>`, `changes: Partial<Omit<T, "id">>` and `list(): readonly T[]`.

**Behaviour:** the `Map` does most of the work: `has`, `get`, `set` and `delete`, and it remembers the order of insertion. In `add`, check `this.items.has(item.id)` first and `return fail(...)` for a duplicate. In `update`, get the `previous` item, return `fail(...)` if it's `undefined`, and build the new one with `const item: T = { ...previous, ...changes, id };`. `list()` can be `[...this.items.values()]`, and `find` can filter that list. Write a small `private emit(event: StoreEvent<T>)` method that loops over `this.listeners` and calls each one, and call it after each successful change. To unsubscribe, `filter` the listener out of `this.listeners`.

</Hint>

<Solution>

```ts
type Result<T, E> =
  | { ok: true; value: T }
  | { ok: false; error: E };

type StoreError =
  | { type: "duplicate-id"; id: string }
  | { type: "not-found"; id: string };

type StoreEvent<T> =
  | { type: "added"; item: T }
  | { type: "updated"; item: T; previous: T }
  | { type: "removed"; item: T };

type Listener<T> = (event: StoreEvent<T>) => void;

function fail(error: StoreError): { ok: false; error: StoreError } {
  return { ok: false, error };
}

class Store<T extends { id: string }> {
  private items = new Map<string, T>();
  private listeners: Listener<T>[] = [];

  add(item: T): Result<T, StoreError> {
    if (this.items.has(item.id)) {
      return fail({ type: "duplicate-id", id: item.id });
    }
    this.items.set(item.id, item);
    this.emit({ type: "added", item });
    return { ok: true, value: item };
  }

  get(id: string): T | undefined {
    return this.items.get(id);
  }

  update(
    id: string,
    changes: Partial<Omit<T, "id">>,
  ): Result<T, StoreError> {
    const previous = this.items.get(id);
    if (previous === undefined) {
      return fail({ type: "not-found", id });
    }
    // a new object; the id always stays the same
    const item: T = { ...previous, ...changes, id };
    this.items.set(id, item);
    this.emit({ type: "updated", item, previous });
    return { ok: true, value: item };
  }

  remove(id: string): Result<T, StoreError> {
    const item = this.items.get(id);
    if (item === undefined) {
      return fail({ type: "not-found", id });
    }
    this.items.delete(id);
    this.emit({ type: "removed", item });
    return { ok: true, value: item };
  }

  find(predicate: (item: T) => boolean): T[] {
    return this.list().filter(predicate);
  }

  list(): readonly T[] {
    return [...this.items.values()];
  }

  subscribe(listener: Listener<T>): () => void {
    this.listeners.push(listener);
    return () => {
      this.listeners = this.listeners.filter((l) => l !== listener);
    };
  }

  private emit(event: StoreEvent<T>): void {
    for (const listener of this.listeners) {
      listener(event);
    }
  }
}

interface Book {
  id: string;
  title: string;
  author: string;
  year: number;
}

// ===== Type tests: don't change these =====
// @ts-expect-error: items without an id can't be stored
```

## Recap

- **Utility types** are generic types from TypeScript's library that derive new types from existing ones, so they stay in sync.
- `Partial`, `Required` and `Readonly` change every property's modifiers (shallowly).
- `Pick` and `Omit` shape objects into DTOs like `NewUser` or `PublicUser`; types never strip data at runtime, so copy only what you need.
- `Record<Union, V>` makes complete lookup tables: every key must be there.
- `Exclude`, `Extract` and `NonNullable` filter unions; `Extract` picks one variant out of a discriminated union.
- `ReturnType<typeof fn>`, `Parameters<typeof fn>` and `Awaited<T>` get types out of functions and promises.
- Combine them for real jobs: `Partial<Omit<T, "id">>` is the classic update patch.

🎉 You've finished the Generics module. You can now write functions, types and classes that work for any type without giving up safety, the same tools that power `Array`, `Map` and every utility type.
