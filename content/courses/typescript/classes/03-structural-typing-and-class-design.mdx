In languages like Java or C#, an object has the type `Point` only if it was made by the `Point` class. TypeScript works differently: it cares about an object's **shape**, not about where it came from. That has surprising and useful consequences for classes. In this lesson you'll learn them, see how to design classes that are easy to change and test, learn when **not** to write a class, and then build a parking garage. 🚗

## Structural typing: shapes, not names

TypeScript checks whether a value has the right **properties with the right types**. If it does, it fits, whatever made it. This is called **structural typing** (or "duck typing": if it walks like a duck and quacks like a duck, it's a duck 🦆):

<CodeExample output={`5
10
false`}>

```ts
class Point {
  constructor(public x: number, public y: number) {}
}

function distance(a: Point, b: Point): number {
  return Math.hypot(b.x - a.x, b.y - a.y);
}

// An object literal can be a Point: no `new` needed
const corner: Point = { x: 3, y: 4 };
console.log(distance(new Point(0, 0), corner));

// A different class with the same x and y fits too
class Pixel {
  constructor(
    public x: number,
    public y: number,
    public colour: string,
  ) {}
}
console.log(distance(new Pixel(0, 0, "red"), { x: 6, y: 8 }));

// ...but it was never made by Point
console.log(corner instanceof Point);
```

</CodeExample>

`Pixel` has nothing to do with `Point`, but it has an `x` and a `y` that are numbers, so it fits wherever a `Point` is needed. The extra `colour` doesn't matter. Methods are part of the shape too: if `Point` had a `describe()` method, the object literal would need one as well.

The last line is the catch: TypeScript was happy that `corner` is a `Point`, but at runtime it's a plain object. `instanceof` checks **how an object was made**, not its shape, so it says `false`.

## Private members change the rules

There's one exception. A class with a `private` or `protected` member can't be faked: only objects made by that class (or its subclasses) fit its type:

```ts
class Account {
  constructor(private balance: number) {}
}

const fake: Account = { balance: 1_000_000 };
// ❌ Error: Type '{ balance: number; }' is not assignable to type 'Account'.
```

Even another class with an identical private member doesn't fit, because TypeScript says the two privates come from "separate declarations":

```ts
class SavingsAccount {
  constructor(private balance: number) {}
}

const savings: Account = new SavingsAccount(50);
// ❌ Error: Type 'SavingsAccount' is not assignable to type 'Account'.
```

That's a feature: if a class keeps private state, every object of that type really went through its constructor and its rules. Nobody can hand you a home-made "account" with a balance of a million.

## A class is a type and a value

When you write `class Lamp { ... }`, you get **two** things with one name:

- a **type**, `Lamp`: the shape of the objects it makes;
- a **value**, `Lamp`: the class itself, which you can call with `new`, pass to functions and read static members from.

Sometimes you want to pass the class itself, not one of its objects. The type of "something you can call with `new`" is written `new (...params) => Type`:

<CodeExample output={`💡 lamp in the hall
💡 lamp in the kitchen
🌀 fan in the bedroom`}>

```ts
interface Device {
  readonly room: string;
  describe(): string;
}

class Lamp implements Device {
  constructor(readonly room: string) {}
  describe(): string {
    return `💡 lamp in the ${this.room}`;
  }
}

class Fan implements Device {
  constructor(readonly room: string) {}
  describe(): string {
    return `🌀 fan in the ${this.room}`;
  }
}

// Any class whose constructor takes a room and makes a Device
type DeviceClass = new (room: string) => Device;

function install(Kind: DeviceClass, rooms: string[]): Device[] {
  return rooms.map((room) => new Kind(room));
}

const devices = [
  ...install(Lamp, ["hall", "kitchen"]),
  ...install(Fan, ["bedroom"]),
];
for (const d of devices) {
  console.log(d.describe());
}
```

</CodeExample>

To refer to the type of one **particular** class (including its static members), use **`typeof`**: `typeof Lamp` is the type of the class itself, while `Lamp` is the type of its objects. Mixing the two up is a classic mistake:

```ts
function build(Kind: Lamp): Lamp {
  return new Kind("hall");
  // ❌ Error: This expression is not constructable.
}

function buildLamp(Kind: typeof Lamp): Lamp {
  return new Kind("hall"); // fine
}
```

## Narrowing with `instanceof`

In [Union Types](/learn/typescript/union-types) you narrowed values with `instanceof`. With your own classes it becomes really useful, especially for **custom errors**. A caught error is `unknown` (anything can be thrown), and `instanceof` tells TypeScript exactly which class you're dealing with:

<CodeExample output={`Garage is full (2 spots). Try another one!
Car parked`}>

```ts
class GarageFullError extends Error {
  constructor(readonly capacity: number) {
    super(`Garage is full (${capacity} spots)`);
    this.name = "GarageFullError";
  }
}

function enter(parked: number, capacity: number): void {
  if (parked >= capacity) {
    throw new GarageFullError(capacity);
  }
  console.log("Car parked");
}

function tryToPark(parked: number): void {
  try {
    enter(parked, 2);
  } catch (err) {
    // err: unknown
    if (err instanceof GarageFullError) {
      // err: GarageFullError, so .capacity is allowed
      console.log(`${err.message}. Try another one!`);
    } else {
      throw err; // not ours: let it carry on
    }
  }
}

tryToPark(2);
tryToPark(1);
```

</CodeExample>

`instanceof` works only with **classes**, because only classes exist at runtime. It can't check an interface or a type alias, and it says `false` for plain objects that merely have the right shape (like `corner` earlier), including everything that comes from `JSON.parse`. For data, a tag field such as `kind` is usually the better way to tell variants apart, as you saw in [Discriminated Unions](/learn/typescript/discriminated-unions).

## Composition over inheritance

Say a parking meter needs to know the time and a price list. You could try inheritance (`class Meter extends Clock`?), but a meter **isn't** a clock. It **has** a clock. That's the idea behind **composition**: instead of inheriting behaviour, an object is **given** the parts it needs, usually through its constructor.

<CodeExample output={`£0
£4
£2`}>

```ts
interface Clock {
  now(): number; // milliseconds
}

interface PricingRule {
  price(minutes: number): number;
}

class Meter {
  private startedAt = 0;

  constructor(
    private readonly clock: Clock,
    private readonly pricing: PricingRule,
  ) {}

  start(): void {
    this.startedAt = this.clock.now();
  }

  stop(): string {
    const ms = this.clock.now() - this.startedAt;
    const minutes = Math.ceil(ms / 60_000);
    return `£${this.pricing.price(minutes)}`;
  }
}

// A clock we control: perfect for examples and tests
class FakeClock implements Clock {
  private time = 0;
  now(): number {
    return this.time;
  }
  advance(minutes: number): void {
    this.time += minutes * 60_000;
  }
}

// Plain objects can be PricingRules: structural typing!
const perHour: PricingRule = {
  price: (minutes) => Math.ceil(minutes / 60) * 2,
};
const firstHourFree: PricingRule = {
  price: (minutes) =>
    minutes <= 60 ? 0 : Math.ceil((minutes - 60) / 60) * 2,
};

const clock = new FakeClock();
const town = new Meter(clock, perHour);
const mall = new Meter(clock, firstHourFree);

town.start();
mall.start();
clock.advance(50);
console.log(mall.stop()); // 50 minutes at the mall
clock.advance(40);
console.log(town.stop()); // 90 minutes in town
console.log(mall.stop()); // 90 minutes at the mall
```

</CodeExample>

Look at what composition bought us:

- **Mix and match.** Two clocks and two pricing rules make four kinds of meter, without a single subclass. With inheritance you'd need `TownMeter`, `MallMeter`, `TestTownMeter`...
- **Easy testing.** The meter never calls `Date.now()` itself. In real use you'd pass a clock whose `now()` returns `Date.now()`; in tests, a `FakeClock` makes time do exactly what you want. Passing in what a class needs like this is called **dependency injection**.
- **Small promises.** `Meter` depends only on two tiny interfaces, so anything that fits them works.

<Callout type="tip" title="Is a or has a?">

Before you write `extends`, say it out loud: "a `Lamp` **is a** `Device`" sounds right, so inheritance can work. "A `Meter` is a `Clock`" sounds wrong: the meter **has a** clock, so pass one in. When in doubt, choose composition. It's much easier to add inheritance later than to untangle it.

</Callout>

## When a class is overkill

Classes are great, but not everything needs one. A class with no state is just a function wearing a costume:

```ts
// A class with nothing to remember...
class FeeCalculator {
  calculate(minutes: number, rate: number): number {
    return Math.ceil(minutes / 60) * rate;
  }
}
const fee1 = new FeeCalculator().calculate(90, 2);

// ...is simpler as a plain function
function calculateFee(minutes: number, rate: number): number {
  return Math.ceil(minutes / 60) * rate;
}
const fee2 = calculateFee(90, 2);
```

The same goes for objects that only hold data: an `interface` or `type` describes them, and any object literal fits. Data from an API or `JSON.parse` is **never** an instance of your class anyway.

A class earns its place when:

- it has **state that changes** over time and **rules** that must protect it (`private` fields, checks in methods), like a bank account or a garage;
- you create **many objects** with the same behaviour;
- you need **`instanceof`**, as with custom errors;
- the tools you use expect classes.

Otherwise, reach for **types and functions**. Lots of excellent TypeScript code has very few classes. 🐼

Time to put the whole module together. A parking garage has spots of different sizes, vehicles come and go, and every stay is charged by its length. The sizes, prices, `Vehicle`, a `FakeClock` and the result types are given. Build the rest:

1. **`fee(size, minutes)`**: stays of up to `FREE_MINUTES` (15) are free. Otherwise every **started** hour costs `HOURLY_RATE[size]`, so 16 or 60 minutes in a car cost £2, and 61 minutes cost £4. (No state, so a plain function is perfect.)
2. **`Spot`**: make `id` and `size` `readonly`, and finish `fits(vehicle)`: a vehicle fits a spot of its own size or bigger. Use `SIZE_RANK`.
3. **`Garage`**:
   - Keep `spots` **private**. Store what the garage earned in a private field and expose it with a `get earned()` getter.
   - `freeSpots`: how many spots are free.
   - `park(vehicle)`: if that plate is already parked, return `{ ok: false, reason: "already-parked" }`. Otherwise use the **first** free spot that fits, `occupy` it with the time from the clock, and return `{ ok: true, spotId }`. No spot? `{ ok: false, reason: "full" }`.
   - `leave(plate)`: find the spot with that plate (or return `{ ok: false, reason: "not-found" }`). Work out the minutes with `Math.ceil((now - since) / 60_000)` and the fee for the **vehicle's** size (a car in a van spot pays the car rate). Release the spot, add the fee to the takings, and return `{ ok: true, spotId, minutes, fee }`.

Always get the time from `this.clock`, never from `Date.now()`, so the fake clock can control it. The `@ts-expect-error` lines are type tests: they pass once the garage and its spots protect their data.

<Hint>

`fee`: return `0` when `minutes <= FREE_MINUTES`, otherwise `Math.ceil(minutes / 60) * HOURLY_RATE[size]`. `fits`: `SIZE_RANK[vehicle.size] <= SIZE_RANK[this.size]`.

In `Garage`, rename the takings field (for example `private takings = 0;`) so it doesn't clash with the getter. For "already parked", `this.spots.some((s) => s.parked?.vehicle.plate === vehicle.plate)` works, and `find((s) => s.isFree && s.fits(vehicle))` finds the spot. In `leave`, loop over the spots and copy `spot.parked` into a `const`: once you've checked that it isn't `null`, TypeScript lets you read `.vehicle` and `.since`.

</Hint>

```ts
// ===== Given: sizes, prices, vehicles, time =====
type Size = "motorbike" | "car" | "van";

// To compare sizes: a bigger number is a bigger size
const SIZE_RANK: Record<Size, number> = {
  motorbike: 1,
  car: 2,
  van: 3,
};
// £ per started hour, by the VEHICLE's size
const HOURLY_RATE: Record<Size, number> = {
  motorbike: 1,
  car: 2,
  van: 3,
};
const FREE_MINUTES = 15;

class Vehicle {
  constructor(readonly plate: string, readonly size: Size) {}
}

interface Clock {
  now(): number; // milliseconds
}

class FakeClock implements Clock {
  private time = 0;
  now(): number {
    return this.time;
  }
  advance(minutes: number): void {
    this.time += minutes * 60_000;
  }
}

type ParkResult =
  | { ok: true; spotId: string }
  | { ok: false; reason: "full" | "already-parked" };

type LeaveResult =
  | { ok: true; spotId: string; minutes: number; fee: number }
  | { ok: false; reason: "not-found" };

type Parked = { readonly vehicle: Vehicle; readonly since: number };

// ===== Your code =====

function fee(size: Size, minutes: number): number {
  if (minutes <= FREE_MINUTES) {
    return 0;
  }
  return Math.ceil(minutes / 60) * HOURLY_RATE[size];
}

class Spot {
  private current: Parked | null = null;

  constructor(readonly id: string, readonly size: Size) {}

  get parked(): Parked | null {
    return this.current;
  }

  get isFree(): boolean {
    return this.current === null;
  }

  fits(vehicle: Vehicle): boolean {
    return SIZE_RANK[vehicle.size] <= SIZE_RANK[this.size];
  }

  occupy(vehicle: Vehicle, since: number): void {
    this.current = { vehicle, since };
  }

  release(): void {
    this.current = null;
  }
}

class Garage {
  private readonly spots: Spot[];
  private takings = 0;

  constructor(spots: Spot[], private readonly clock: Clock) {
    this.spots = [...spots]; // our own copy of the list
  }

  get earned(): number {
    return this.takings;
  }

  get freeSpots(): number {
    return this.spots.filter((s) => s.isFree).length;
  }

  park(vehicle: Vehicle): ParkResult {
    const plate = vehicle.plate;
    if (this.spots.some((s) => s.parked?.vehicle.plate === plate)) {
      return { ok: false, reason: "already-parked" };
    }
    const spot = this.spots.find((s) => s.isFree && s.fits(vehicle));
    if (spot === undefined) {
      return { ok: false, reason: "full" };
    }
    spot.occupy(vehicle, this.clock.now());
    return { ok: true, spotId: spot.id };
  }

  leave(plate: string): LeaveResult {
    for (const spot of this.spots) {
      const parked = spot.parked;
      if (parked !== null && parked.vehicle.plate === plate) {
        const ms = this.clock.now() - parked.since;
        const minutes = Math.ceil(ms / 60_000);
        const cost = fee(parked.vehicle.size, minutes);
        spot.release();
        this.takings += cost;
        return { ok: true, spotId: spot.id, minutes, fee: cost };
      }
    }
    return { ok: false, reason: "not-found" };
  }
}

// Type tests (never called). Don't change them.
function typeTests(garage: Garage, spot: Spot): void {
  const free: number = garage.freeSpots;
  const earned: number = garage.earned;
  // Structural typing: any { plate, size } object works
  garage.park({ plate: "PLAIN 1", size: "car" });
  // @ts-expect-error: the spots are the garage's business
  garage.spots;
  // @ts-expect-error: only the garage changes its takings
  garage.earned = 1_000_000;
  // @ts-expect-error: a spot's id never changes
  spot.id = "Z9";
  // @ts-expect-error: a spot's size never changes
```

## Recap

- TypeScript compares classes by **shape** (structural typing): object literals and unrelated classes with the same members fit a class type.
- `private` and `protected` members make a class type un-fakeable: only objects made by that class fit.
- A class is both a **type** (its objects) and a **value** (the class itself). `typeof Lamp` is the class's own type; `new (room: string) => Device` describes any matching class.
- `instanceof` narrows to a class, which is perfect for custom errors in `catch`. It doesn't work with interfaces or plain objects.
- Prefer **composition** ("has a") over inheritance ("is a"): pass in a clock or a pricing rule, and testing becomes easy.
- Use a class for changing state with rules to protect; for plain data and stateless logic, types and functions are simpler.
