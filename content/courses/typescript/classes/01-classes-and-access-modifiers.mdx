So far you've described objects with interfaces and built them with `{ ... }`. That's perfect for plain data. But some objects also have **behaviour** and **data to protect**: a bank account shouldn't let anyone set its balance to a million. A **class** bundles data and the methods that work on it, and TypeScript adds two things JavaScript classes don't have: **types** for every field and method, and **access modifiers** that say who is allowed to touch what. 🔒

## A class with typed fields

In a TypeScript class, every field is **declared** at the top with its type, just like the properties of an interface. The constructor's parameters are typed like any function's:

<CodeExample output={`Mei is 3 years old
Panda { name: 'Mei', age: 3 }
Bao is older`}>

```ts
class Panda {
  name: string;
  age: number;

  constructor(name: string, age: number) {
    this.name = name;
    this.age = age;
  }

  describe(): string {
    return `${this.name} is ${this.age} years old`;
  }
}

function older(a: Panda, b: Panda): Panda {
  return a.age >= b.age ? a : b;
}

const mei = new Panda("Mei", 3);
const bao = new Panda("Bao", 5);
console.log(mei.describe());
console.log(mei);
console.log(`${older(mei, bao).name} is older`);
```

</CodeExample>

Two things to notice:

- **A class is also a type.** `older(a: Panda, b: Panda)` accepts any `Panda` object. You get a type for free with every class you write.
- **Methods are typed like functions.** `describe(): string` must return a string, and calling `mei.describe(42)` would be an error.

In JavaScript you can attach any property in the constructor. TypeScript wants to know about it first:

```ts
class Ticket {
  constructor(plate: string) {
    this.plate = plate;
    // ❌ Error: Property 'plate' does not exist on type 'Ticket'.
  }
}
```

The fix is to declare it: `plate: string;` above the constructor. That one line also documents the shape of every `Ticket` for whoever reads the class next.

## Every field must get a value

With `strict` on, TypeScript checks that every declared field really gets a value, so you can't forget one and read `undefined` later:

```ts
class Ticket {
  plate: string;
  spot: number;
  // ❌ Error: Property 'spot' has no initializer and is not definitely assigned in the constructor.

  constructor(plate: string) {
    this.plate = plate;
  }
}
```

There are four ways to fix it, and each one says something different:

<CodeExample output={`Game { turn: 'X', moves: 0, winner: undefined, board: [ '', '', '' ] }
undefined`}>

```ts
class Game {
  turn: "X" | "O";   // 1. assigned in the constructor
  moves = 0;         // 2. an initializer (type inferred: number)
  winner?: "X" | "O"; // 3. optional: may be undefined
  board!: string[];  // 4. "trust me": reset() sets it

  constructor() {
    this.turn = "X";
    this.reset();
  }

  reset(): void {
    this.board = ["", "", ""];
  }
}

const game = new Game();
console.log(game);
console.log(game.winner);
```

</CodeExample>

Every declared field exists on the object from the start, in the order you declared them. That's why `winner` shows up as `undefined` until a game is won.

The `!` after `board` is a **definite assignment assertion**. TypeScript doesn't look inside `reset()`, so it can't see that the constructor sets `board`. The `!` tells it "I promise this gets a value". Use it rarely: if you're wrong, TypeScript stays quiet and your code reads `undefined`. Options 1 to 3 are always safer.

## Parameter properties: a shortcut

Declaring a field, taking a parameter and copying one into the other is so common that TypeScript has a shortcut. Put a modifier such as `public` or `readonly` in front of a constructor parameter, and it becomes a field automatically:

<CodeExample output={`Panda { name: 'Mei', age: 3 }
Mei`}>

```ts
class Panda {
  constructor(public name: string, public age: number) {}
}

// Exactly the same as:
//   name: string;
//   age: number;
//   constructor(name: string, age: number) {
//     this.name = name;
//     this.age = age;
//   }

const mei = new Panda("Mei", 3);
console.log(mei);
console.log(mei.name);
```

</CodeExample>

These are called **parameter properties**. The constructor body is empty (`{}`), because TypeScript writes the copying for you. Without a modifier, `name` would just be an ordinary parameter, not a field.

<Callout type="note" title="TypeScript-only syntax">

Parameter properties are one of the few TypeScript features that **generate** JavaScript code instead of just being removed. Most projects use them happily, but a few tools that only strip types away (such as Node's built-in TypeScript support) don't accept them. You'll see why in Level 3. For now: they're fine, and you'll meet them in lots of real code.

</Callout>

## `public`, `private` and `protected`

An **access modifier** says who may use a member (a field or method):

| Modifier | Who can use it |
| --- | --- |
| `public` (the default) | Anyone |
| `private` | Only code inside this class |
| `protected` | This class and its subclasses (next lesson) |

Making a field `private` lets the class protect its **rules**. Here, the only ways to change the balance are `deposit` and `withdraw`, and both check the amount:

<CodeExample output={`Balance: 30
Not enough money for 100
Balance: 30`}>

```ts
class BankAccount {
  private balance = 0;

  constructor(public owner: string) {}

  deposit(amount: number): void {
    if (amount <= 0) {
      throw new RangeError("Deposit must be positive");
    }
    this.balance += amount;
  }

  withdraw(amount: number): boolean {
    if (amount > this.balance) {
      console.log(`Not enough money for ${amount}`);
      return false;
    }
    this.balance -= amount;
    return true;
  }

  report(): string {
    return `Balance: ${this.balance}`;
  }
}

const account = new BankAccount("Mei");
account.deposit(50);
account.withdraw(20);
console.log(account.report());
account.withdraw(100);
console.log(account.report());
```

</CodeExample>

Code outside the class can't sneak around the rules:

```ts
account.balance = 1_000_000;
// ❌ Error: Property 'balance' is private and only accessible within class 'BankAccount'.
```

Writing `public` is optional, since it's the default. Many teams leave it out on fields and methods, but write it in parameter properties, where a modifier is needed anyway.

## `readonly` fields

A `readonly` field can be set where it's declared or in the constructor, and **never again**. It's ideal for ids and anything that identifies an object. Modifiers combine, too: `private readonly` is a value only the class can see, and even the class can't change after construction:

<CodeExample output={`Order #17 for Sam: 2 items
[ 'tea', 'cake' ]`}>

```ts
class Order {
  readonly items: string[] = [];

  constructor(
    readonly id: number,
    private readonly customer: string,
  ) {}

  add(item: string): void {
    this.items.push(item); // fine: the array itself can change
  }

  summary(): string {
    const count = this.items.length;
    return `Order #${this.id} for ${this.customer}: ${count} items`;
  }
}

const order = new Order(17, "Sam");
order.add("tea");
order.add("cake");
console.log(order.summary());
console.log(order.items);
```

</CodeExample>

```ts
order.id = 18;
// ❌ Error: Cannot assign to 'id' because it is a read-only property.
order.items = [];
// ❌ Error: Cannot assign to 'items' because it is a read-only property.
```

Notice that `order.items.push(...)` still works. `readonly` stops the **field** being pointed at a new array, but the array it holds can still change. If the contents must not change either, use the `readonly string[]` type you met with arrays.

## TypeScript's `private` vs JavaScript's `#private`

JavaScript has its own private fields, written with `#`. They look similar, but they work at completely different times:

- TypeScript's **`private`** is a **compile-time** check. It's erased with the other types, so at runtime the field is an ordinary property.
- JavaScript's **`#private`** is enforced **at runtime** by the JavaScript engine. Outside the class, the field truly can't be seen.

You can see the difference by printing the objects:

<CodeExample output={`TsWallet { balance: 10 }
JsWallet {}
{"balance":10}
{}
10`}>

```ts
class TsWallet {
  private balance = 10;
}

class JsWallet {
  #balance = 10;

  get balance(): number {
    return this.#balance;
  }
}

const ts = new TsWallet();
const js = new JsWallet();
console.log(ts);
console.log(js);
console.log(JSON.stringify(ts));
console.log(JSON.stringify(js));
console.log(ts["balance"]); // allowed: an escape hatch
```

</CodeExample>

The `TsWallet`'s balance shows up when printed and in JSON, and TypeScript even allows `ts["balance"]` with square brackets as a deliberate escape hatch. The `#balance` field is invisible from outside, and TypeScript reports any attempt to use it:

```ts
js.#balance;
// ❌ Error: Property '#balance' is not accessible outside class 'JsWallet' because it has a private identifier.
```

<Callout type="tip" title="Which one should I use?">

Both are fine, so follow your project's style. `private` is common in TypeScript code and reads nicely, especially in parameter properties. Choose `#private` when the privacy must hold **at runtime** too, for example in a library used from plain JavaScript, or when objects get logged or turned into JSON and must not leak a secret.

</Callout>

## Methods and `this`

Inside a method, `this` is the object the method was called on. That breaks if you pass a method somewhere **on its own**, as a callback. The method gets separated from its object, and `this` becomes `undefined`:

```ts
class Counter {
  count = 0;

  increment(): void {
    this.count++;
  }
}

const counter = new Counter();
const inc = counter.increment;
inc();
// 💥 TypeError: Cannot read properties of undefined (reading 'count')
```

TypeScript doesn't catch this by default. You can ask it to, with a fake first parameter called `this` that says which object the method needs. It's checked by TypeScript and removed from the JavaScript:

```ts
class Counter {
  count = 0;

  increment(this: Counter): void {
    this.count++;
  }
}

const counter = new Counter();
const inc = counter.increment;
inc();
// ❌ Error: The 'this' context of type 'void' is not assignable to method's 'this' of type 'Counter'.
```

When a method is **meant** to be passed around as a callback, write it as an **arrow function field** instead. Arrow functions don't have their own `this`; they keep the `this` of the object they were created in:

<CodeExample output={`6
2`}>

```ts
class Counter {
  count = 0;
  clicks = 0;

  add = (amount: number): void => {
    this.count += amount;
    this.clicks++;
  };
}

const counter = new Counter();
[1, 2, 3].forEach(counter.add); // no crash!
console.log(counter.count);

const other = new Counter();
other.add(1);
other.add(1);
console.log(other.clicks);
```

</CodeExample>

The trade-off: a normal method is shared by all instances, but an arrow function field is a new function in **every** object. That's fine for a few objects, so use it for callbacks and keep normal methods for everything else.

## Getters and setters

A **getter** (`get`) looks like a property from the outside but runs a method when it's read. A **setter** (`set`) runs when you assign to it, which makes it a good place to check values. A getter without a setter is automatically **read-only**:

<CodeExample output={`Target: 21°C (69.8°F)
Thermostat: 30°C is out of range
Target: 21°C (69.8°F)`}>

```ts
class Thermostat {
  private celsius = 20;

  get target(): number {
    return this.celsius;
  }

  set target(value: number) {
    if (value < 5 || value > 28) {
      console.log(`Thermostat: ${value}°C is out of range`);
      return;
    }
    this.celsius = value;
  }

  get fahrenheit(): number {
    return (this.celsius * 9) / 5 + 32;
  }

  show(): string {
    return `Target: ${this.target}°C (${this.fahrenheit}°F)`;
  }
}

const home = new Thermostat();
home.target = 21; // runs the setter
console.log(home.show());
home.target = 30; // rejected
console.log(home.show());
```

</CodeExample>

```ts
home.fahrenheit = 100;
// ❌ Error: Cannot assign to 'fahrenheit' because it is a read-only property.
```

A `private` field plus a **public getter** is a very common pattern: everyone can read the value, but only the class can change it.

## Static members

A **static** member belongs to the **class itself**, not to each object. Use it for things shared by all instances, such as a counter for ids, a constant, or a helper that creates objects:

<CodeExample output={`#1 Mei
#2 Sam
#3 Guest
Tickets cost £3`}>

```ts
class Ticket {
  static readonly PRICE = 3;
  private static nextNumber = 1;

  readonly number: number;

  constructor(readonly holder: string) {
    this.number = Ticket.nextNumber++;
  }

  static forGuest(): Ticket {
    return new Ticket("Guest");
  }
}

const tickets = [
  new Ticket("Mei"),
  new Ticket("Sam"),
  Ticket.forGuest(),
];
for (const t of tickets) {
  console.log(`#${t.number} ${t.holder}`);
}
console.log(`Tickets cost £${Ticket.PRICE}`);
```

</CodeExample>

You reach static members through the class name, `Ticket.PRICE`, never through an instance. Modifiers work on them too: `nextNumber` is `private static`, so only `Ticket` can hand out numbers.

```ts
const t = new Ticket("Mei");
t.PRICE;
// ❌ Error: Property 'PRICE' does not exist on type 'Ticket'. Did you mean to access the static member 'Ticket.PRICE' instead?
```

## Recap

- Declare every field with its type; the class name is also a type for its objects.
- Under `strict`, every field needs a value: an initializer, a constructor assignment, `?` for optional, or (rarely) `!`.
- **Parameter properties** like `constructor(readonly id: string)` declare and set a field in one go.
- `public` is the default, `private` is for the class only, `protected` adds subclasses; `readonly` fields can't be reassigned after construction.
- TypeScript's `private` is checked at compile time and erased; JavaScript's `#private` is enforced at runtime.
- Pass methods as callbacks carefully: a `this` parameter catches mistakes, and arrow function fields keep `this`.
- Getters and setters look like properties but run code; a getter on its own is read-only. **Static** members belong to the class itself.
