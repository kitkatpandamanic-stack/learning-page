In the last lesson every class stood on its own. Real programs have **families** of related classes: a lamp, a speaker and a thermostat are all smart-home devices. They share some code, and they each do something special. In this lesson you'll share code with `extends`, make promises with `implements`, write **abstract classes**, and treat very different objects the same way through an interface. 🏠

## `extends` and `super`

A class can **extend** another one: it gets every field and method of its **parent** (or **base**) class and can add its own. If the child has a constructor, it must call `super(...)`, which runs the parent's constructor:

<CodeExample output={`Desk lamp
40
Lamp { name: 'Desk lamp', watts: 40 }
true`}>

```ts
class Device {
  constructor(readonly name: string) {}

  describe(): string {
    return this.name;
  }
}

class Lamp extends Device {
  constructor(name: string, readonly watts: number) {
    super(name); // runs Device's constructor
  }
}

const lamp = new Lamp("Desk lamp", 40);
console.log(lamp.describe()); // inherited from Device
console.log(lamp.watts);
console.log(lamp);
console.log(lamp instanceof Device);
```

</CodeExample>

Notice that `name` has no modifier in `Lamp`'s constructor. It's an ordinary parameter that is passed on to `super`, because `Device` already declares the field. Only the new field, `watts`, gets `readonly`.

TypeScript makes sure the parent is set up properly. Forgetting `super(...)`, or using `this` before it, is an error:

```ts
class Lamp extends Device {
  constructor(name: string, readonly watts: number) {
    console.log("Making a lamp");
    // ❌ Error: Constructors for derived classes must contain a 'super' call.
  }
}

class Speaker extends Device {
  volume: number;

  constructor(name: string) {
    this.volume = 3;
    // ❌ Error: 'super' must be called before accessing 'this' in the constructor of a derived class.
    super(name);
  }
}
```

A `Lamp` **is a** `Device`, so you can pass a lamp anywhere a `Device` is expected, for example into a `Device[]` array.

## Overriding methods with `override`

A child class can replace a parent's method with its own version. Mark it with the **`override`** keyword, and call the parent's version with `super.method()` if you want to build on it:

<CodeExample output={`Doorbell
Desk lamp: off
Desk lamp: on, 40 W`}>

```ts
class Device {
  constructor(readonly name: string) {}

  describe(): string {
    return this.name;
  }
}

class Lamp extends Device {
  private on = false;

  constructor(name: string, readonly watts: number) {
    super(name);
  }

  toggle(): void {
    this.on = !this.on;
  }

  override describe(): string {
    if (!this.on) {
      return `${super.describe()}: off`;
    }
    return `${super.describe()}: on, ${this.watts} W`;
  }
}

const lamp = new Lamp("Desk lamp", 40);
const devices: Device[] = [new Device("Doorbell"), lamp];
for (const d of devices) {
  console.log(d.describe());
}
lamp.toggle();
console.log(lamp.describe());
```

</CodeExample>

Even though `devices` is a `Device[]`, calling `d.describe()` on the lamp runs **`Lamp`'s** version. The object decides which method runs, not the type of the variable.

Why write `override` at all? Because it turns a silent bug into an error. If you misspell the method name, you'd accidentally create a brand new method and the parent's one would still run. With `override`, TypeScript checks that the parent really has that method:

```ts
class Lamp extends Device {
  override descibe(): string {
    // ❌ Error: This member cannot have an 'override' modifier because it is not declared in the base class 'Device'. Did you mean 'describe'?
    return "lamp";
  }
}
```

An override must also stay **compatible** with the parent. Code that works with any `Device` expects `describe()` to give back a string, so a child can't change that:

```ts
class Radio extends Device {
  override describe(): number {
    // ❌ Error: Property 'describe' in type 'Radio' is not assignable to the same property in base type 'Device'.
    return 101.5;
  }
}
```

<Callout type="tip" title="Make override required">

On its own, `override` is optional: leaving it out isn't an error. The `noImplicitOverride` setting in `tsconfig.json` makes it **required**, so every override is clearly marked. It's worth switching on in real projects; you'll configure TypeScript yourself later in this level.

</Callout>

## `protected` in practice

A `private` member is hidden even from child classes. When a child **needs** something from its parent, mark it **`protected`**: the class and its subclasses can use it, but code outside can't:

<CodeExample output={`Kitchen speaker is off
Kitchen speaker: volume 4`}>

```ts
class Device {
  protected powered = false;

  constructor(readonly name: string) {}

  turnOn(): void {
    this.powered = true;
  }
}

class Speaker extends Device {
  private volume = 3;

  louder(): void {
    if (!this.powered) { // allowed: Speaker is a subclass
      console.log(`${this.name} is off`);
      return;
    }
    this.volume++;
    console.log(`${this.name}: volume ${this.volume}`);
  }
}

const speaker = new Speaker("Kitchen speaker");
speaker.louder();
speaker.turnOn();
speaker.louder();
```

</CodeExample>

```ts
speaker.powered = true;
// ❌ Error: Property 'powered' is protected and only accessible within class 'Device' and its subclasses.
```

Start with `private`, and only loosen it to `protected` when a subclass really needs it. Everything `protected` becomes something subclasses rely on, which makes the parent class harder to change later.

## `implements`: keeping a promise

An interface describes a shape. A class can **promise** to have that shape with `implements`, and TypeScript checks the promise right where the class is written:

<CodeExample output={`Kettle: boiling ☕
Kettle: off`}>

```ts
interface Switchable {
  readonly isOn: boolean;
  turnOn(): void;
  turnOff(): void;
}

class Kettle implements Switchable {
  isOn = false;

  turnOn(): void {
    this.isOn = true;
    console.log("Kettle: boiling ☕");
  }

  turnOff(): void {
    this.isOn = false;
    console.log("Kettle: off");
  }
}

const kettle = new Kettle();
kettle.turnOn();
kettle.turnOff();
```

</CodeExample>

Forget a member and you hear about it immediately, even if no code uses the class yet:

```ts
class Kettle implements Switchable {
  // ❌ Error: Class 'Kettle' incorrectly implements interface 'Switchable'.
  isOn = false;

  turnOn(): void {
    this.isOn = true;
  }
}
```

A class can only `extend` **one** parent, but it can `implement` **as many interfaces as you like**, and do both at once:

```ts
class SmartBulb extends Device implements Switchable, Dimmable {
  // must have everything from Switchable AND Dimmable
}
```

<Callout type="warning" title="implements only checks">

`implements` doesn't add anything to the class or give types to its methods. You still write every member yourself, with full types. This surprises many people:

```ts
interface Dimmable {
  setBrightness(level: number): void;
}

class SmartBulb implements Dimmable {
  setBrightness(level) {}
  // ❌ Error: Parameter 'level' implicitly has an 'any' type.
}
```

</Callout>

## Polymorphism through an interface

Here's where interfaces really shine. A function that takes `Switchable[]` works with **any** class that has that shape, whether or not the classes are related. One call, a different behaviour for each object: that's called **polymorphism**:

<CodeExample output={`Kettle: off
Hall light: off
Garden pump: off`}>

```ts
interface Switchable {
  readonly isOn: boolean;
  turnOn(): void;
  turnOff(): void;
}

class Kettle implements Switchable {
  isOn = true;
  turnOn(): void {
    this.isOn = true;
  }
  turnOff(): void {
    this.isOn = false;
    console.log("Kettle: off");
  }
}

class Light implements Switchable {
  private level = 100;
  constructor(readonly room: string) {}

  get isOn(): boolean {
    return this.level > 0;
  }
  turnOn(): void {
    this.level = 100;
  }
  turnOff(): void {
    this.level = 0;
    console.log(`${this.room} light: off`);
  }
}

class Pump implements Switchable {
  isOn = true;
  turnOn(): void {
    this.isOn = true;
  }
  turnOff(): void {
    this.isOn = false;
    console.log("Garden pump: off");
  }
}

function leaveHome(things: Switchable[]): void {
  for (const thing of things) {
    thing.turnOff();
  }
}

leaveHome([new Kettle(), new Light("Hall"), new Pump()]);
```

</CodeExample>

`leaveHome` knows nothing about kettles, lights or pumps. It only knows the `Switchable` interface. You can add a `Heater` next year without changing it. Notice also that `Light` keeps the promise of `readonly isOn` with a **getter**, while `Kettle` uses a plain field: the interface only cares that `isOn` can be read.

## Abstract classes

Sometimes several classes share real **code**, not just a shape. An **abstract class** is a parent class that's meant only to be extended. It can contain normal fields and methods, plus **abstract** methods: a name and a type, but no body. Every child must fill those in:

<CodeExample output={`Desk lamp: on
Living room: 21°C
Smoke alarm: OK, battery 80%`}>

```ts
abstract class Device {
  constructor(readonly name: string) {}

  abstract status(): string;

  report(): string {
    return `${this.name}: ${this.status()}`;
  }
}

class Lamp extends Device {
  on = true;

  status(): string {
    return this.on ? "on" : "off";
  }
}

class Thermostat extends Device {
  constructor(name: string, private celsius: number) {
    super(name);
  }

  status(): string {
    return `${this.celsius}°C`;
  }
}

class SmokeAlarm extends Device {
  battery = 80;

  status(): string {
    return `OK, battery ${this.battery}%`;
  }
}

const home: Device[] = [
  new Lamp("Desk lamp"),
  new Thermostat("Living room", 21),
  new SmokeAlarm("Smoke alarm"),
];
for (const device of home) {
  console.log(device.report());
}
```

</CodeExample>

`report()` is written once in `Device` and calls `status()`, a method that only the children provide. The parent describes **the steps**, and each child fills in **the blank**.

An abstract class can't be created on its own (what would its `status()` do?), and a child that forgets an abstract method is caught:

```ts
const mystery = new Device("Mystery box");
// ❌ Error: Cannot create an instance of an abstract class.

class Doorbell extends Device {}
// ❌ Error: Non-abstract class 'Doorbell' does not implement inherited abstract member status from class 'Device'.
```

## Abstract class or interface?

Both describe what children or implementers must have, so how do you choose?

| | Interface | Abstract class |
| --- | --- | --- |
| Contains code and fields | ❌ shape only | ✅ |
| How many per class | as many as you like | only one parent |
| Exists at runtime (works with `instanceof`) | ❌ erased | ✅ |
| Plain objects can match it | ✅ | only if it has no `private`/`protected` members |

Some rules of thumb:

- **Start with an interface.** It's the lightest promise: it costs nothing at runtime, and any class (or plain object) can keep it.
- **Use an abstract class** when the children truly share **code or state**, like `report()` above.
- **Use both** when it helps: an interface for the promise (`Switchable`), and an abstract class as an optional helper that implements it.

You can't use an interface with `instanceof`, because interfaces disappear when the types are removed:

```ts
if (thing instanceof Switchable) {
  // ❌ Error: 'Switchable' only refers to a type, but is being used as a value here.
}
```

<Callout type="warning" title="Keep family trees shallow">

`Device` → `Lamp` → `SmartLamp` → `ColourSmartLamp`... Deep inheritance chains are hard to follow and break easily: a change at the top can surprise every class below it. One or two levels is usually plenty. In the next lesson you'll see **composition**, the popular alternative.

</Callout>

  constructor(name: string, private annualSalary: number) {

  override monthlyPay(): number {
    return this.hours * this.rate;

    return `${super.payslip()} for ${this.hours} h`;
  }

    total += person.monthlyPay();
  }
  return total;

## Recap

- `class Child extends Parent` inherits everything; a child constructor must call `super(...)` before using `this`.
- Mark replaced methods with `override` (typos become errors) and reuse the parent's version with `super.method()`. Overrides must stay compatible.
- `protected` members are shared with subclasses but hidden from everyone else. Prefer `private` until a subclass needs access.
- `implements` checks that a class keeps an interface's promise. A class can implement many interfaces, but extend only one class.
- Code that depends on an interface works with **any** class that has that shape: that's polymorphism.
- **Abstract classes** share code and leave `abstract` methods for children to fill in. Start with an interface; reach for an abstract class when children share real code.
