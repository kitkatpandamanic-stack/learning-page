В прошлом уроке каждый класс стоял особняком. В реальных программах встречаются **семейства** родственных классов: лампа, колонка и термостат — всё это устройства умного дома. У них есть общий код, и при этом каждое делает что-то своё. В этом уроке вы будете делиться кодом через `extends`, давать обещания через `implements`, писать **абстрактные классы** (abstract classes) и обращаться с совсем разными объектами одинаково — через интерфейс. 🏠

## `extends` и `super`

Класс может **расширять** (extend) другой класс: он получает все поля и методы **родительского** (или **базового**) класса и может добавить свои. Это и есть **наследование** (inheritance). Если у дочернего класса есть конструктор, он обязан вызвать `super(...)`, который запускает конструктор родителя:

<CodeExample output={`Настольная лампа
40
Lamp { name: 'Настольная лампа', watts: 40 }
true`}>

```ts
class Device {
  constructor(readonly name: string) {}

  describe(): string {
    return this.name;
  }
}

class Lamp extends Device {
  constructor(name: string, readonly watts: number) {
    super(name); // запускает конструктор Device
  }
}

const lamp = new Lamp("Настольная лампа", 40);
console.log(lamp.describe()); // унаследован от Device
console.log(lamp.watts);
console.log(lamp);
console.log(lamp instanceof Device);
```

</CodeExample>

Обратите внимание: у `name` в конструкторе `Lamp` нет модификатора. Это обычный параметр, который передаётся дальше в `super`, ведь `Device` уже объявляет это поле. `readonly` получает только новое поле `watts`.

TypeScript следит, чтобы родитель был правильно настроен. Забыть `super(...)` или использовать `this` до него — ошибка:

```ts
class Lamp extends Device {
  constructor(name: string, readonly watts: number) {
    console.log("Делаем лампу");
    // ❌ Error: Constructors for derived classes must contain a 'super' call.
  }
}

class Speaker extends Device {
  volume: number;

  constructor(name: string) {
    this.volume = 3;
    // ❌ Error: 'super' must be called before accessing 'this' in the constructor of a derived class.
    super(name);
  }
}
```

`Lamp` **является** `Device`, поэтому лампу можно передать везде, где ожидается `Device`, например положить в массив `Device[]`.

## Переопределение методов с `override`

Дочерний класс может заменить метод родителя своей версией. Пометьте её ключевым словом **`override`**, а если хотите опереться на родительскую версию, вызовите её через `super.method()`:

<CodeExample output={`Дверной звонок
Настольная лампа: выкл
Настольная лампа: вкл, 40 Вт`}>

```ts
class Device {
  constructor(readonly name: string) {}

  describe(): string {
    return this.name;
  }
}

class Lamp extends Device {
  private on = false;

  constructor(name: string, readonly watts: number) {
    super(name);
  }

  toggle(): void {
    this.on = !this.on;
  }

  override describe(): string {
    if (!this.on) {
      return `${super.describe()}: выкл`;
    }
    return `${super.describe()}: вкл, ${this.watts} Вт`;
  }
}

const lamp = new Lamp("Настольная лампа", 40);
const devices: Device[] = [new Device("Дверной звонок"), lamp];
for (const d of devices) {
  console.log(d.describe());
}
lamp.toggle();
console.log(lamp.describe());
```

</CodeExample>

Хотя `devices` — это `Device[]`, вызов `d.describe()` для лампы запускает версию **`Lamp`**. Какой метод выполнится, решает объект, а не тип переменной.

Зачем вообще писать `override`? Потому что он превращает тихую ошибку в явную. Если вы опечатаетесь в имени метода, то случайно создадите совершенно новый метод, а выполняться по-прежнему будет родительский. С `override` TypeScript проверяет, что у родителя действительно есть такой метод:

```ts
class Lamp extends Device {
  override descibe(): string {
    // ❌ Error: This member cannot have an 'override' modifier because it is not declared in the base class 'Device'. Did you mean 'describe'?
    return "лампа";
  }
}
```

Переопределение также должно оставаться **совместимым** с родителем. Код, который работает с любым `Device`, ожидает, что `describe()` вернёт строку, поэтому дочерний класс не может это изменить:

```ts
class Radio extends Device {
  override describe(): number {
    // ❌ Error: Property 'describe' in type 'Radio' is not assignable to the same property in base type 'Device'.
    return 101.5;
  }
}
```

<Callout type="tip" title="Сделайте override обязательным">

Сам по себе `override` необязателен: если его не написать, ошибки не будет. Настройка `noImplicitOverride` в `tsconfig.json` делает его **обязательным**, и тогда каждое переопределение явно помечено. В реальных проектах её стоит включать; настраивать TypeScript сами вы будете дальше на этом уровне.

</Callout>

## `protected` на практике

Член `private` скрыт даже от дочерних классов. Когда дочернему классу **нужно** что-то от родителя, пометьте это как **`protected`**: класс и его подклассы могут этим пользоваться, а код снаружи — нет:

<CodeExample output={`Колонка на кухне: выключена
Колонка на кухне: громкость 4`}>

```ts
class Device {
  protected powered = false;

  constructor(readonly name: string) {}

  turnOn(): void {
    this.powered = true;
  }
}

class Speaker extends Device {
  private volume = 3;

  louder(): void {
    if (!this.powered) { // можно: Speaker — подкласс
      console.log(`${this.name}: выключена`);
      return;
    }
    this.volume++;
    console.log(`${this.name}: громкость ${this.volume}`);
  }
}

const speaker = new Speaker("Колонка на кухне");
speaker.louder();
speaker.turnOn();
speaker.louder();
```

</CodeExample>

```ts
speaker.powered = true;
// ❌ Error: Property 'powered' is protected and only accessible within class 'Device' and its subclasses.
```

Начинайте с `private` и ослабляйте до `protected`, только когда подклассу это действительно нужно. Всё `protected` становится тем, на что опираются подклассы, а значит, родительский класс потом будет труднее менять.

## `implements`: держим обещание

Интерфейс (interface) описывает форму. Класс может **пообещать**, что у него такая форма, с помощью `implements`, и TypeScript проверяет обещание прямо там, где написан класс:

<CodeExample output={`Чайник: кипит ☕
Чайник: выкл`}>

```ts
interface Switchable {
  readonly isOn: boolean;
  turnOn(): void;
  turnOff(): void;
}

class Kettle implements Switchable {
  isOn = false;

  turnOn(): void {
    this.isOn = true;
    console.log("Чайник: кипит ☕");
  }

  turnOff(): void {
    this.isOn = false;
    console.log("Чайник: выкл");
  }
}

const kettle = new Kettle();
kettle.turnOn();
kettle.turnOff();
```

</CodeExample>

Забудьте какой-нибудь член — и сразу об этом узнаете, даже если класс ещё нигде не используется:

```ts
class Kettle implements Switchable {
  // ❌ Error: Class 'Kettle' incorrectly implements interface 'Switchable'.
  isOn = false;

  turnOn(): void {
    this.isOn = true;
  }
}
```

Класс может расширять (`extend`) только **одного** родителя, но реализовывать (`implement`) **сколько угодно интерфейсов** — и делать то и другое одновременно:

```ts
class SmartBulb extends Device implements Switchable, Dimmable {
  // должен содержать всё из Switchable И Dimmable
}
```

<Callout type="warning" title="implements только проверяет">

`implements` ничего не добавляет в класс и не задаёт типы его методам. Каждый член вы всё равно пишете сами, с полными типами. Многих это удивляет:

```ts
interface Dimmable {
  setBrightness(level: number): void;
}

class SmartBulb implements Dimmable {
  setBrightness(level) {}
  // ❌ Error: Parameter 'level' implicitly has an 'any' type.
}
```

</Callout>

## Полиморфизм через интерфейс

Вот где интерфейсы по-настоящему блистают. Функция, принимающая `Switchable[]`, работает с **любым** классом такой формы, независимо от того, связаны классы между собой или нет. Один вызов — и своё поведение у каждого объекта: это называется **полиморфизмом** (polymorphism):

<CodeExample output={`Чайник: выкл
Прихожая: свет выключен
Садовый насос: выкл`}>

```ts
interface Switchable {
  readonly isOn: boolean;
  turnOn(): void;
  turnOff(): void;
}

class Kettle implements Switchable {
  isOn = true;
  turnOn(): void {
    this.isOn = true;
  }
  turnOff(): void {
    this.isOn = false;
    console.log("Чайник: выкл");
  }
}

class Light implements Switchable {
  private level = 100;
  constructor(readonly room: string) {}

  get isOn(): boolean {
    return this.level > 0;
  }
  turnOn(): void {
    this.level = 100;
  }
  turnOff(): void {
    this.level = 0;
    console.log(`${this.room}: свет выключен`);
  }
}

class Pump implements Switchable {
  isOn = true;
  turnOn(): void {
    this.isOn = true;
  }
  turnOff(): void {
    this.isOn = false;
    console.log("Садовый насос: выкл");
  }
}

function leaveHome(things: Switchable[]): void {
  for (const thing of things) {
    thing.turnOff();
  }
}

leaveHome([new Kettle(), new Light("Прихожая"), new Pump()]);
```

</CodeExample>

`leaveHome` ничего не знает о чайниках, лампах и насосах. Она знает только интерфейс `Switchable`. В следующем году можно добавить `Heater` (обогреватель), не меняя её. Заметьте также, что `Light` выполняет обещание `readonly isOn` с помощью **геттера**, а `Kettle` — обычным полем: интерфейсу важно лишь, чтобы `isOn` можно было прочитать.

## Абстрактные классы

Иногда у нескольких классов общий настоящий **код**, а не только форма. **Абстрактный класс** — это родительский класс, предназначенный только для расширения. В нём могут быть обычные поля и методы, а также **абстрактные** методы: имя и тип, но без тела. Каждый дочерний класс обязан их заполнить:

<CodeExample output={`Настольная лампа: вкл
Гостиная: 21°C
Датчик дыма: OK, заряд 80%`}>

```ts
abstract class Device {
  constructor(readonly name: string) {}

  abstract status(): string;

  report(): string {
    return `${this.name}: ${this.status()}`;
  }
}

class Lamp extends Device {
  on = true;

  status(): string {
    return this.on ? "вкл" : "выкл";
  }
}

class Thermostat extends Device {
  constructor(name: string, private celsius: number) {
    super(name);
  }

  status(): string {
    return `${this.celsius}°C`;
  }
}

class SmokeAlarm extends Device {
  battery = 80;

  status(): string {
    return `OK, заряд ${this.battery}%`;
  }
}

const home: Device[] = [
  new Lamp("Настольная лампа"),
  new Thermostat("Гостиная", 21),
  new SmokeAlarm("Датчик дыма"),
];
for (const device of home) {
  console.log(device.report());
}
```

</CodeExample>

`report()` написан один раз в `Device` и вызывает `status()` — метод, который предоставляют только дочерние классы. Родитель описывает **шаги**, а каждый потомок заполняет **пропуск**.

Создать абстрактный класс сам по себе нельзя (что бы делал его `status()`?), а потомок, забывший абстрактный метод, будет пойман:

```ts
const mystery = new Device("Загадочная коробка");
// ❌ Error: Cannot create an instance of an abstract class.

class Doorbell extends Device {}
// ❌ Error: Non-abstract class 'Doorbell' does not implement inherited abstract member status from class 'Device'.
```

## Абстрактный класс или интерфейс?

Оба описывают, что должно быть у потомков или реализаций. Как же выбрать?

| | Интерфейс | Абстрактный класс |
| --- | --- | --- |
| Содержит код и поля | ❌ только форма | ✅ |
| Сколько на один класс | сколько угодно | только один родитель |
| Существует во время выполнения (работает с `instanceof`) | ❌ стирается | ✅ |
| Обычные объекты могут ему соответствовать | ✅ | только если нет членов `private`/`protected` |

Несколько практических правил:

- **Начинайте с интерфейса.** Это самое лёгкое обещание: оно ничего не стоит во время выполнения, и его может выполнить любой класс (или обычный объект).
- **Берите абстрактный класс**, когда у потомков действительно общий **код или состояние**, как `report()` выше.
- **Используйте оба**, когда это помогает: интерфейс для обещания (`Switchable`) и абстрактный класс как необязательный помощник, который его реализует.

Интерфейс нельзя использовать с `instanceof`, потому что интерфейсы исчезают, когда удаляются типы:

```ts
if (thing instanceof Switchable) {
  // ❌ Error: 'Switchable' only refers to a type, but is being used as a value here.
}
```

<Callout type="warning" title="Не растите глубокие родословные">

`Device` → `Lamp` → `SmartLamp` → `ColourSmartLamp`... В глубоких цепочках наследования трудно разобраться, и они легко ломаются: изменение наверху может удивить каждый класс ниже. Одного-двух уровней обычно более чем достаточно. В следующем уроке вы увидите **композицию** — популярную альтернативу.

</Callout>

1. Сделайте `Employee` **абстрактным**, а `monthlyPay()` превратите в абстрактный метод.
2. `Salaried`: зарплата за месяц — годовой оклад, делённый на 12 и округлённый через `Math.round`.
3. `Hourly`: `logHours(h)` добавляет часы; зарплата за месяц — часы × ставка. **Переопределите** `payslip()`, чтобы к тексту родителя добавлялось `" for 15 h"` (с реальными часами).
4. `Freelancer`: **реализуйте** `Payable` (не расширяя `Employee`). Зарплата за месяц — сумма его счетов.
5. `totalPayroll(people)` складывает зарплаты всех за месяц. Функция работает с любым `Payable`.

В заготовке ошибки типов по двум причинам. Строка с `@ts-expect-error` — это **тест типов**: она проходит, только если `new Employee(...)` **является** ошибкой, поэтому не пройдёт, пока `Employee` не станет абстрактным. А `Freelancer` пока не соответствует `Payable`.

<Hint>

Напишите `abstract class Employee` и замените метод на `abstract monthlyPay(): number;` (без тела). В потомках добавьте `override monthlyPay(): number { ... }`. Для расчётного листка напишите `override payslip(): string` и верните `super.payslip()`, добавив в конец `" for "`, часы и `" h"`. Фрилансеру нужны `class Freelancer implements Payable` и метод `monthlyPay()`, который складывает `this.invoices` циклом или через `reduce`.

```ts
interface Payable {
  readonly name: string;
  monthlyPay(): number;
}

abstract class Employee implements Payable {
  constructor(
    readonly name: string,
    protected readonly role: string,
  ) {}

  abstract monthlyPay(): number;

  payslip(): string {
    return `${this.name} (${this.role}): £${this.monthlyPay()}`;
  }
}

class Salaried extends Employee {
  constructor(name: string, private annualSalary: number) {
    super(name, "salaried");
  }

  override monthlyPay(): number {
    return Math.round(this.annualSalary / 12);
  }
}

class Hourly extends Employee {
  private hours = 0;

  constructor(name: string, private rate: number) {
    super(name, "hourly");
  }

  logHours(hours: number): void {
    this.hours += hours;
  }

  override monthlyPay(): number {
    return this.hours * this.rate;
  }

  override payslip(): string {
    return `${super.payslip()} for ${this.hours} h`;
  }
}

class Freelancer implements Payable {
  private invoices: number[] = [];

  constructor(readonly name: string) {}

  sendInvoice(amount: number): void {
    this.invoices.push(amount);
  }

  monthlyPay(): number {
    return this.invoices.reduce((sum, a) => sum + a, 0);
  }
}

function totalPayroll(people: Payable[]): number {
  let total = 0;
  for (const person of people) {
    total += person.monthlyPay();
  }
  return total;
}

// Тесты типов (никогда не вызываются). Не меняйте их.
function typeTests(): void {
  // @ts-expect-error: Employee должен быть абстрактным
  new Employee("Ana", "mystery");
  const team: Payable[] = [
    new Salaried("Mei", 36000),
    new Hourly("Sam", 12),
    new Freelancer("Ana"),
  ];
}

const mei = new Salaried("Mei", 36000);
const sam = new Hourly("Sam", 12);
sam.logHours(10);
sam.logHours(5);
const ana = new Freelancer("Ana");
ana.sendInvoice(400);
ana.sendInvoice(250);

console.log(mei.payslip()); // Mei (salaried): £3000
console.log(sam.payslip()); // Sam (hourly): £180 for 15 h
console.log(totalPayroll([mei, sam, ana])); // 3830
```

## Итоги

- `class Child extends Parent` наследует всё; конструктор потомка обязан вызвать `super(...)` до использования `this`.
- Помечайте заменённые методы через `override` (опечатки становятся ошибками) и переиспользуйте версию родителя через `super.method()`. Переопределения должны оставаться совместимыми.
- Члены `protected` доступны подклассам, но скрыты от всех остальных. Предпочитайте `private`, пока подклассу не понадобится доступ.
- `implements` проверяет, что класс выполняет обещание интерфейса. Класс может реализовывать много интерфейсов, но расширять только один класс.
- Код, зависящий от интерфейса, работает с **любым** классом такой формы: это полиморфизм.
- **Абстрактные классы** делятся кодом и оставляют `abstract`-методы потомкам. Начинайте с интерфейса; абстрактный класс берите, когда у потомков действительно общий код.
