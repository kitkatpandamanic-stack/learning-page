Индикаторы загрузки, которые никогда не исчезают, сообщения об ошибке рядом с результатами, «оплаченный» заказ без даты оплаты: многие повседневные ошибки возникают из-за данных в состоянии, которое **должно быть невозможным**. В этом уроке вы освоите самый полезный в TypeScript приём, чтобы с ними покончить, — **размеченное объединение** (discriminated union). Именно так профессиональный код на TypeScript описывает всё, у чего есть несколько состояний. 🚦

## Проблема: флаги и необязательные свойства

Представьте страницу поиска фильмов. Запрос может ещё не начаться, загружаться, завершиться с результатами или упасть с ошибкой. Первая попытка часто выглядит так — одно логическое значение и два необязательных свойства:

<CodeExample output={`Загрузка...
Ошибка: ?
Получено фильмов: 0`}>

```ts
interface RequestState {
  isLoading: boolean;
  data?: string[];
  error?: string;
}

function render(state: RequestState): string {
  if (state.isLoading) {
    return "Загрузка...";
  }
  if (state.error) {
    return `Ошибка: ${state.error}`;
  }
  return `Получено фильмов: ${state.data?.length ?? 0}`;
}

// Бессмыслица, но TypeScript всё это устраивает:
console.log(render({ isLoading: true, error: "Тайм-аут" }));
console.log(render({ isLoading: false, data: ["Up"], error: "?" }));
console.log(render({ isLoading: false }));
```

</CodeExample>

Тип допускает бессмысленные сочетания: загрузка **и** ошибка, результаты **и** ошибка, завершение **без** данных. Каждой функции, которая читает состояние, приходится угадывать, каким свойствам верить, и каждая такая догадка — место для ошибки. А с ещё одним флагом число возможных сочетаний снова удваивается.

## Объединения с меткой

Решение — перечислить состояния, которые **действительно** могут быть, у каждого — ровно те данные, что ему нужны, и дать каждому свойство с **литеральным типом**, которое говорит, что это за состояние:

```ts
type RequestState =
  | { status: "idle" }
  | { status: "loading" }
  | { status: "success"; data: string[] }
  | { status: "error"; message: string };
```

Это **размеченное объединение** (его ещё называют **объединением с меткой**, tagged union). Общее литеральное свойство, здесь `status`, называют **меткой** (tag) или **дискриминантом** (discriminant). Проверка метки сужает весь объект, и TypeScript знает, какие ещё свойства у него есть:

<CodeExample output={`Результатов: 2
Сбой: Нет сети
loading`}>

```ts
type RequestState =
  | { status: "idle" }
  | { status: "loading" }
  | { status: "success"; data: string[] }
  | { status: "error"; message: string };

function describe(state: RequestState): string {
  if (state.status === "success") {
    return `Результатов: ${state.data.length}`; // есть data
  }
  if (state.status === "error") {
    return `Сбой: ${state.message}`; // есть message
  }
  return state.status; // "idle" | "loading"
}

console.log(describe({ status: "success", data: ["Up", "Coco"] }));
console.log(describe({ status: "error", message: "Нет сети" }));
console.log(describe({ status: "loading" }));
```

</CodeExample>

Пока метка не проверена, безопасно читать только `status`: это единственное свойство, которое есть у каждого члена:

```ts
function count(state: RequestState): number {
  return state.data.length;
  // ❌ Error: Property 'data' does not exist on type 'RequestState'.
}
```

<Callout type="note" title="Метка должна быть литеральным типом">

Приём работает только потому, что каждый `status` — точное значение вроде `"success"`. Будь метка обычной `string`, проверка `state.status === "success"` ничего не сказала бы TypeScript об остальном объекте. Популярные имена для метки — `kind`, `type` и `status`; выберите одно и используйте его во всём проекте.

</Callout>

## Сужение с помощью `switch`

Когда вариантов больше двух, лучше всего читается `switch` по метке. Внутри каждого `case` состояние сужено до одного варианта:

<CodeExample output={`Найдите фильм
Загрузка...
Найдено 2: Up, Coco
Ошибка: Тайм-аут`}>

```ts
type RequestState =
  | { status: "idle" }
  | { status: "loading" }
  | { status: "success"; data: string[] }
  | { status: "error"; message: string };

function render(state: RequestState): string {
  switch (state.status) {
    case "idle":
      return "Найдите фильм";
    case "loading":
      return "Загрузка...";
    case "success":
      return `Найдено ${state.data.length}: ${state.data.join(", ")}`;
    case "error":
      return `Ошибка: ${state.message}`;
  }
}

console.log(render({ status: "idle" }));
console.log(render({ status: "loading" }));
console.log(render({ status: "success", data: ["Up", "Coco"] }));
console.log(render({ status: "error", message: "Тайм-аут" }));
```

</CodeExample>

Обратите внимание: после `switch` нет `return`. TypeScript видит, что четыре case охватывают все возможные `status`, поэтому функция всегда возвращает строку.

## Сделайте невозможные состояния невозможными

Теперь попробуйте собрать одно из бессмысленных состояний из начала урока. TypeScript откажется, и ошибка точно скажет, что не так:

```ts
const a: RequestState = { status: "loading", data: ["Up"] };
// ❌ Error: Object literal may only specify known properties, and 'data' does not exist in type '{ status: "loading"; }'.

const b: RequestState = { status: "success" };
// ❌ Error: Type '{ status: "success"; }' is not assignable to type 'RequestState'.

const c: RequestState = { status: "done" };
// ❌ Error: Type '"done"' is not assignable to type '"idle" | "loading" | "success" | "error"'.
```

Состояние загрузки не может нести данные, успех не может забыть свои данные, а статуса `"done"` просто не существует. Эту идею часто формулируют так: **«сделайте невозможные состояния невозможными»** (make impossible states impossible). Проектируйте типы так, чтобы плохие сочетания нельзя было даже записать, вместо того чтобы проверять их повсюду во время выполнения.

<Callout type="tip" title="Связанные между собой логические флаги — тревожный знак">

Если вы замечаете два-три логических значения или необязательных свойства, которые имеют смысл только в определённых сочетаниях (`isLoading`, `hasError`, `isDone`...), обычно это замаскированное размеченное объединение. Перечислите реальные состояния, дайте каждому свои данные — и вопросы «а что, если оба true?» исчезнут.

</Callout>

## Проверка полноты с `assertNever`

В уроке [Литеральные типы и switch](/learn/typescript/literal-types-and-switch) вы ловили забытые случаи с помощью переменной типа `never` в `default`. В реальных проектах эта проверка обычно живёт в крошечной вспомогательной функции, общей для всей кодовой базы:

<CodeExample output={`true
false`}>

```ts
type RequestState =
  | { status: "idle" }
  | { status: "loading" }
  | { status: "success"; data: string[] }
  | { status: "error"; message: string };

function assertNever(value: never): never {
  throw new Error(`Неожиданное значение: ${JSON.stringify(value)}`);
}

function canRetry(state: RequestState): boolean {
  switch (state.status) {
    case "error":
      return true;
    case "idle":
    case "loading":
    case "success":
      return false;
    default:
      return assertNever(state);
  }
}

console.log(canRetry({ status: "error", message: "Тайм-аут" }));
console.log(canRetry({ status: "loading" }));
```

</CodeExample>

`assertNever` принимает только `never`, поэтому код компилируется, лишь когда все варианты обработаны до `default`. Функция делает две работы:

- **Во время компиляции** забытый случай становится ошибкой типа, которая указывает ровно на тот `switch`, который нужно исправить.
- **Во время выполнения**, если плохие данные всё-таки просочатся (скажем, старый сервер пришлёт статус, о котором вы никогда не слышали), она выбросит понятную ошибку, а не вернёт молча `undefined`.

Её возвращаемый тип тоже `never`: функция, которая всегда выбрасывает исключение, никогда не возвращает значение, поэтому `return assertNever(state)` подходит к любому возвращаемому типу.

## Добавляем новый вариант

Вот где размеченные объединения по-настоящему окупаются. Через несколько месяцев приложение учится автоматически повторять неудачные запросы, и вы добавляете новое состояние:

```ts
type RequestState =
  | { status: "idle" }
  | { status: "loading" }
  | { status: "success"; data: string[] }
  | { status: "error"; message: string }
  | { status: "retrying"; attempt: number };
```

Не нужно искать по коду все места, где используется состояние: компилятор сам их перечислит. Обе функции из этого урока теперь с ошибками:

```ts
function render(state: RequestState): string {
  // ❌ Error: Function lacks ending return statement and return type does not include 'undefined'.
  switch (state.status) {
    // ...четыре старых case...
  }
}

function canRetry(state: RequestState): boolean {
  switch (state.status) {
    // ...четыре старых case...
    default:
      return assertNever(state);
      // ❌ Error: Argument of type '{ status: "retrying"; attempt: number; }' is not assignable to parameter of type 'never'.
  }
}
```

В `render` нет case для `"retrying"`, так что функция может дойти до конца, ничего не вернув, а `canRetry` передаёт в `assertNever` настоящее состояние. Добавьте `case "retrying":` в каждую из них — и ошибки исчезнут. В большом приложении это превращает вопрос «мы всё обновили?» из нервного поиска в чек-лист, который за вас составляет компилятор.

<Callout type="warning" title="default, который возвращает значение, прячет новые варианты">

`default: return "Unknown";` молча обрабатывает любой будущий вариант, поэтому компилятор не сможет о них предупредить. Когда вы делаете switch по собственному объединению, перечисляйте случаи явно, а `default` оставьте для `assertNever`.

</Callout>

type Circle = { kind: "circle"; radius: number };
type Rectangle = { kind: "rectangle"; width: number; height: number };
type Triangle = { kind: "triangle"; base: number; height: number };
type Shape = Circle | Rectangle | Triangle;

function assertNever(value: never): never {
  throw new Error(`Неизвестная фигура: ${JSON.stringify(value)}`);
}

function area(shape: Shape): number {
  switch (shape.kind) {
    case "circle":
      return Math.PI * shape.radius ** 2;
    case "rectangle":
      return shape.width * shape.height;
    case "triangle":
      return (shape.base * shape.height) / 2;
    default:
      return assertNever(shape);
  }
}

function scale(shape: Shape, factor: number): Shape {
  switch (shape.kind) {
    case "circle":
      return { kind: "circle", radius: shape.radius * factor };
    case "rectangle":
      return {
        kind: "rectangle",
        width: shape.width * factor,
        height: shape.height * factor,
      };
    case "triangle":
      return {
        kind: "triangle",
        base: shape.base * factor,
        height: shape.height * factor,
      };
    default:
      return assertNever(shape);
  }
}

  { kind: "circle", radius: 2 },
  { kind: "rectangle", width: 3, height: 4 },
  { kind: "triangle", base: 6, height: 2 },
];

  console.log(
    `${shape.kind}: ${area(shape).toFixed(2)}, ` +
      `вдвое крупнее: ${area(bigger).toFixed(2)}`,
  );
}

// rectangle: 12.00, вдвое крупнее: 48.00

## Итоги

- **Размеченное объединение** — это объединение объектных типов с общим свойством-**меткой** литерального типа (`kind`, `type` или `status`).
- Проверка метки через `if` или `switch` сужает весь объект до одного варианта.
- Дайте каждому состоянию ровно те данные, которые ему нужны, и невозможные сочетания нельзя будет даже записать: **сделайте невозможные состояния невозможными**.
- Несколько логических значений или необязательных свойств, зависящих друг от друга, — обычно замаскированное размеченное объединение.
- `assertNever(value: never): never` в `default` превращает забытые случаи в ошибку типа и выбрасывает исключение, если плохие данные просочатся во время выполнения.
- Когда вы добавляете вариант, компилятор указывает на каждый `switch`, которому нужен новый case.
