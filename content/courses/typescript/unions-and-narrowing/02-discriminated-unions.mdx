Loading spinners that never stop, error messages next to the results, a "paid" order with no payment date: many everyday bugs come from data that's in a state that **should be impossible**. In this lesson you'll learn the most useful pattern in TypeScript for stopping them: the **discriminated union**. It's how professional TypeScript code models anything that has several states. 🚦

## The problem: flags and optional properties

Imagine a page that searches for films. The request can be idle, loading, finished with results, or failed. A first try often looks like this, with a boolean and two optional properties:

<CodeExample output={`Loading...
Error: ?
Got 0 films`}>

```ts
interface RequestState {
  isLoading: boolean;
  data?: string[];
  error?: string;
}

function render(state: RequestState): string {
  if (state.isLoading) {
    return "Loading...";
  }
  if (state.error) {
    return `Error: ${state.error}`;
  }
  return `Got ${state.data?.length ?? 0} films`;
}

// Nonsense, but TypeScript is happy with all of these:
console.log(render({ isLoading: true, error: "Timeout" }));
console.log(render({ isLoading: false, data: ["Up"], error: "?" }));
console.log(render({ isLoading: false }));
```

</CodeExample>

The type allows combinations that make no sense: loading **and** failed, results **and** an error, finished with **no** data. Every function that reads the state has to guess which properties to trust, and each guess is a place for a bug. With one more flag, the number of possible combinations doubles again.

## Tagged unions

The fix is to list the states that **can** happen, each with exactly the data it needs, and give every one a property with a **literal type** that says which state it is:

```ts
type RequestState =
  | { status: "idle" }
  | { status: "loading" }
  | { status: "success"; data: string[] }
  | { status: "error"; message: string };
```

This is a **discriminated union** (also called a **tagged union**). The shared literal property, here `status`, is the **tag** or **discriminant**. Checking the tag narrows the whole object, so TypeScript knows which other properties exist:

<CodeExample output={`2 results
Failed: Offline
loading`}>

```ts
type RequestState =
  | { status: "idle" }
  | { status: "loading" }
  | { status: "success"; data: string[] }
  | { status: "error"; message: string };

function describe(state: RequestState): string {
  if (state.status === "success") {
    return `${state.data.length} results`; // has data
  }
  if (state.status === "error") {
    return `Failed: ${state.message}`; // has message
  }
  return state.status; // "idle" | "loading"
}

console.log(describe({ status: "success", data: ["Up", "Coco"] }));
console.log(describe({ status: "error", message: "Offline" }));
console.log(describe({ status: "loading" }));
```

</CodeExample>

Before you check the tag, only `status` is safe to read, because it's the one property every member has:

```ts
function count(state: RequestState): number {
  return state.data.length;
  // ❌ Error: Property 'data' does not exist on type 'RequestState'.
}
```

<Callout type="note" title="The tag must be a literal type">

The trick only works because each `status` is an exact value like `"success"`. If the tag were a plain `string`, checking `state.status === "success"` couldn't tell TypeScript anything about the rest of the object. Common tag names are `kind`, `type` and `status`; pick one and use it consistently in a project.

</Callout>

## Narrowing with `switch`

When there are more than two variants, a `switch` on the tag reads best. Inside each `case`, the state is narrowed to that one variant:

<CodeExample output={`Search for a film
Loading...
Found 2: Up, Coco
Error: Timeout`}>

```ts
type RequestState =
  | { status: "idle" }
  | { status: "loading" }
  | { status: "success"; data: string[] }
  | { status: "error"; message: string };

function render(state: RequestState): string {
  switch (state.status) {
    case "idle":
      return "Search for a film";
    case "loading":
      return "Loading...";
    case "success":
      return `Found ${state.data.length}: ${state.data.join(", ")}`;
    case "error":
      return `Error: ${state.message}`;
  }
}

console.log(render({ status: "idle" }));
console.log(render({ status: "loading" }));
console.log(render({ status: "success", data: ["Up", "Coco"] }));
console.log(render({ status: "error", message: "Timeout" }));
```

</CodeExample>

Notice there's no `return` after the `switch`. TypeScript can see that the four cases cover every possible `status`, so the function always returns a string.

## Make impossible states impossible

Now try to build one of the nonsense states from the start of the lesson. TypeScript refuses, with an error that says exactly what's wrong:

```ts
const a: RequestState = { status: "loading", data: ["Up"] };
// ❌ Error: Object literal may only specify known properties, and 'data' does not exist in type '{ status: "loading"; }'.

const b: RequestState = { status: "success" };
// ❌ Error: Type '{ status: "success"; }' is not assignable to type 'RequestState'.

const c: RequestState = { status: "done" };
// ❌ Error: Type '"done"' is not assignable to type '"idle" | "loading" | "success" | "error"'.
```

A loading state can't carry data, a success can't forget its data, and there's no such status as `"done"`. This idea is often summed up as **"make impossible states impossible"**: design your types so that bad combinations can't even be written, instead of checking for them everywhere at runtime.

<Callout type="tip" title="Booleans that belong together are a warning sign">

When you notice two or three booleans or optional properties that only make sense in certain combinations (`isLoading`, `hasError`, `isDone`...), that's usually one discriminated union in disguise. List the real states, give each one its own data, and the "what if both are true?" questions disappear.

</Callout>

## Exhaustiveness with `assertNever`

In [Literal Types & switch](/learn/typescript/literal-types-and-switch) you used a `never` variable in `default` to catch forgotten cases. In real projects that check usually lives in a tiny helper that's shared by the whole codebase:

<CodeExample output={`true
false`}>

```ts
type RequestState =
  | { status: "idle" }
  | { status: "loading" }
  | { status: "success"; data: string[] }
  | { status: "error"; message: string };

function assertNever(value: never): never {
  throw new Error(`Unexpected value: ${JSON.stringify(value)}`);
}

function canRetry(state: RequestState): boolean {
  switch (state.status) {
    case "error":
      return true;
    case "idle":
    case "loading":
    case "success":
      return false;
    default:
      return assertNever(state);
  }
}

console.log(canRetry({ status: "error", message: "Timeout" }));
console.log(canRetry({ status: "loading" }));
```

</CodeExample>

`assertNever` accepts only `never`, so it compiles only when every variant has been handled before `default`. It does two jobs:

- **At compile time**, a forgotten case is a type error, pointing at the exact `switch` to fix.
- **At runtime**, if bad data sneaks in anyway (say, an old server sends a status you've never heard of), it throws a clear error instead of quietly returning `undefined`.

Its return type is `never` too: a function that always throws never returns, so `return assertNever(state)` fits any return type.

## Adding a new variant

Here's where discriminated unions really pay off. Months later, the app learns to retry failed requests automatically, so you add a new state:

```ts
type RequestState =
  | { status: "idle" }
  | { status: "loading" }
  | { status: "success"; data: string[] }
  | { status: "error"; message: string }
  | { status: "retrying"; attempt: number };
```

You don't need to search the code for every place that uses the state: the compiler lists them for you. Both functions from this lesson are now errors:

```ts
function render(state: RequestState): string {
  // ❌ Error: Function lacks ending return statement and return type does not include 'undefined'.
  switch (state.status) {
    // ...the four old cases...
  }
}

function canRetry(state: RequestState): boolean {
  switch (state.status) {
    // ...the four old cases...
    default:
      return assertNever(state);
      // ❌ Error: Argument of type '{ status: "retrying"; attempt: number; }' is not assignable to parameter of type 'never'.
  }
}
```

`render` has no case for `"retrying"`, so it could reach the end without returning, and `canRetry` passes a real state to `assertNever`. Add a `case "retrying":` to each one and the errors go away. In a big app this turns "did we update everything?" from a nervous search into a checklist the compiler writes for you.

<Callout type="warning" title="A default that returns a value hides new variants">

`default: return "Unknown";` handles every future variant silently, so the compiler can't warn you about them. When you switch over a union you own, list the cases explicitly and save `default` for `assertNever`.

</Callout>

A drawing app stores shapes with one loose type where every size is optional. Model them properly, then work with them:

1. Replace `Shape` with a **discriminated union** tagged by `kind`: a `"circle"` with a `radius`, a `"rectangle"` with a `width` and a `height`, and a `"triangle"` with a `base` and a `height`. The three `@ts-expect-error` lines at the bottom are **type tests**: they pass only when that line **is** an error, so they fail until your union rejects those bad shapes. Don't change them.
2. `area(shape)` returns the area: π × radius² for a circle (use `Math.PI`), width × height for a rectangle, and base × height ÷ 2 for a triangle. Call `assertNever(shape)` in `default`.
3. `scale(shape, factor)` returns a **new** shape of the same kind with every size multiplied by `factor`.

<Hint>

Write one type per variant, for example `type Circle = { kind: "circle"; radius: number };`, then `type Shape = Circle | Rectangle | Triangle;`. In both functions, `switch (shape.kind)` with one `case` per variant; inside each case TypeScript knows exactly which sizes exist. For `scale`, return an object literal such as `{ kind: "circle", radius: shape.radius * factor }`.

</Hint>

<Solution>

```ts
type Circle = { kind: "circle"; radius: number };
type Rectangle = { kind: "rectangle"; width: number; height: number };
type Triangle = { kind: "triangle"; base: number; height: number };
type Shape = Circle | Rectangle | Triangle;

function assertNever(value: never): never {
  throw new Error(`Unexpected shape: ${JSON.stringify(value)}`);
}

function area(shape: Shape): number {
  switch (shape.kind) {
    case "circle":
      return Math.PI * shape.radius ** 2;
    case "rectangle":
      return shape.width * shape.height;
    case "triangle":
      return (shape.base * shape.height) / 2;
    default:
      return assertNever(shape);
  }
}

function scale(shape: Shape, factor: number): Shape {
  switch (shape.kind) {
    case "circle":
      return { kind: "circle", radius: shape.radius * factor };
    case "rectangle":
      return {
        kind: "rectangle",
        width: shape.width * factor,
        height: shape.height * factor,
      };
    case "triangle":
      return {
        kind: "triangle",
        base: shape.base * factor,
        height: shape.height * factor,
      };
    default:
      return assertNever(shape);
  }
}

const shapes: Shape[] = [
  { kind: "circle", radius: 2 },
  { kind: "rectangle", width: 3, height: 4 },
  { kind: "triangle", base: 6, height: 2 },
];
for (const shape of shapes) {

}
```

## Recap

- A **discriminated union** is a union of object types that share a **tag** property with a literal type (`kind`, `type` or `status`).
- Checking the tag with `if` or `switch` narrows the whole object to one variant.
- Give each state exactly the data it needs, and impossible combinations can't even be written: **make impossible states impossible**.
- Several booleans or optional properties that depend on each other are usually a discriminated union in disguise.
- `assertNever(value: never): never` in `default` makes forgotten cases a type error, and throws if bad data sneaks in at runtime.
- When you add a variant, the compiler points at every `switch` that needs a new case.
