So far TypeScript has narrowed types from checks it already understands: `typeof`, `in`, `instanceof`, tags. But what about data that arrives from **outside** your program, such as a JSON file, a form or another server? TypeScript has no idea what's inside it. In this lesson you'll teach TypeScript new checks with **type guards**, validate unknown data step by step, and see why the shortcuts `!` and `as` can quietly break your safety net. Then you'll build a payment status handler that trusts nothing. 🛡️

## When a boolean isn't enough

Checks get long, so it's natural to move them into a function. But watch what happens to the narrowing:

```ts
interface Fish {
  name: string;
  swim(): string;
}

interface Bird {
  name: string;
  fly(): string;
}

function isFish(pet: Fish | Bird): boolean {
  return "swim" in pet;
}

function move(pet: Fish | Bird): string {
  if (isFish(pet)) {
    return pet.swim();
    // ❌ Error: Property 'swim' does not exist on type 'Fish | Bird'.
  }
  return pet.fly();
}
```

The check inside `isFish` is fine, but its return type `boolean` only says "true or false". It doesn't say **what** being true means, so TypeScript can't narrow `pet` in `move`.

## Type predicates: `value is Type`

Change the return type to a **type predicate**: `pet is Fish`. It still returns a boolean at runtime, but now it tells TypeScript: "if this returns `true`, `pet` is a `Fish`". A function like this is called a **type guard**:

<CodeExample output={`[ 'Nemo swims', 'Tweety flies', 'Dory swims' ]
[ 'Nemo', 'Dory' ]`}>

```ts
interface Fish {
  name: string;
  swim(): string;
}

interface Bird {
  name: string;
  fly(): string;
}

function isFish(pet: Fish | Bird): pet is Fish {
  return "swim" in pet;
}

function move(pet: Fish | Bird): string {
  if (isFish(pet)) {
    return pet.swim(); // pet: Fish
  }
  return pet.fly(); // pet: Bird
}

const pets: (Fish | Bird)[] = [
  { name: "Nemo", swim: () => "Nemo swims" },
  { name: "Tweety", fly: () => "Tweety flies" },
  { name: "Dory", swim: () => "Dory swims" },
];

console.log(pets.map(move));

const fish = pets.filter(isFish); // Fish[]
console.log(fish.map((f) => f.name));
```

</CodeExample>

The `false` branch narrows too: after the `if`, `pet` is a `Bird`. And look at `filter`: passing a type guard gives you a `Fish[]`, not a `(Fish | Bird)[]`.

For simple checks, TypeScript can even work out the predicate itself, as long as you don't write a return type. That's why filtering out `null` gives a clean array:

<CodeExample output="[ 'MEI', 'SAM', 'ANA' ]">

```ts
const names = ["Mei", null, "Sam", null, "Ana"];
// names: (string | null)[]

const real = names.filter((name) => name !== null);
// real: string[]
console.log(real.map((name) => name.toUpperCase()));
```

</CodeExample>

<Callout type="danger" title="A type predicate is a promise you make">

TypeScript **doesn't check** that your guard is right. It believes whatever the predicate says, so a wrong guard is worse than none:

```ts
// ⚠️ Wrong: "4-letter names are fish"
function isFish(pet: Fish | Bird): pet is Fish {
  return pet.name.length === 4;
}

const toby: Bird = { name: "Toby", fly: () => "Toby flies" };
if (isFish(toby)) {
  toby.swim(); // compiles, then crashes: toby.swim is not a function
}
```

Keep guards small and obviously correct, and test them with good **and** bad values.

</Callout>

## `unknown` vs `any`, again

In [any, unknown, null & undefined](/learn/typescript/special-types) you learned that `unknown` is the safe "I don't know yet". Here's why that matters so much: `JSON.parse` returns **`any`**. Whatever comes out of it switches the checker off, typos included:

<CodeExample output="Cannot read properties of undefined (reading 'toUpperCase')">

```ts
const text = '{ "name": "Mei", "age": 31 }';

const user = JSON.parse(text); // any: no checks at all!
try {
  console.log(user.nmae.toUpperCase()); // typo, no error
} catch (error) {
  if (error instanceof Error) {
    console.log(error.message);
  }
}
```

</CodeExample>

The fix is one annotation: `const data: unknown = JSON.parse(text);`. Now TypeScript won't let you touch `data` until you've proved what it is:

```ts
const data: unknown = JSON.parse(text);
console.log(data.name);
// ❌ Error: 'data' is of type 'unknown'.
```

Treat everything from the outside world this way: parsed JSON, data from `localStorage`, messages from other windows, responses from servers. It all starts as `unknown`, and type guards turn it into types you can trust.

## Validating unknown data step by step

How do you prove that an `unknown` value is a `User`? One property at a time. A small `isObject` guard does the first step: it turns `unknown` into `Record<string, unknown>`, an object whose properties you can **read** but must still check:

<CodeExample output={`✅ Mei is 31
❌ Not a user: { "name": "Sam", "age": "31" }
❌ Not a user: [1, 2, 3]
❌ Not a user: null`}>

```ts
interface User {
  name: string;
  age: number;
  email?: string;
}

function isObject(value: unknown): value is Record<string, unknown> {
  return (
    typeof value === "object" && value !== null && !Array.isArray(value)
  );
}

function isUser(value: unknown): value is User {
  if (!isObject(value)) {
    return false;
  }
  // value: Record<string, unknown>, so every property is unknown
  if (typeof value.name !== "string") {
    return false;
  }
  if (typeof value.age !== "number") {
    return false;
  }
  if (value.email !== undefined && typeof value.email !== "string") {
    return false;
  }
  return true;
}

const inputs = [
  '{ "name": "Mei", "age": 31 }',
  '{ "name": "Sam", "age": "31" }',
  '[1, 2, 3]',
  'null',
];

for (const text of inputs) {
  const data: unknown = JSON.parse(text);
  if (isUser(data)) {
    console.log(`✅ ${data.name} is ${data.age}`); // data: User
  } else {
    console.log(`❌ Not a user: ${text}`);
  }
}
```

</CodeExample>

Each check rules out one way the data could be wrong, using the narrowing tools from [Union Types](/learn/typescript/union-types). Notice `typeof null === "object"` in JavaScript, which is why `isObject` checks for `null` separately.

<Callout type="warning" title="Array.isArray gives you any[]">

On an `unknown` value, `Array.isArray(data)` narrows to `any[]`, not `unknown[]`. So after it, TypeScript stops checking again: `return data;` would happily pass unchecked items off as `User[]`. Check the items too, for example with `data.filter(isUser)`, which gives a real `User[]`.

</Callout>

## Assertion functions: `asserts value is Type`

A type guard returns `true` or `false`, and you write the `if`. Sometimes bad data simply means "stop": there's nothing sensible to do but throw. An **assertion function** does exactly that. Its return type `asserts value is User` means "if this function returns at all, `value` is a `User`":

<CodeExample output={`{ name: 'Mei', age: 31 }
Expected a user, got {"name":"Sam"}`}>

```ts
interface User {
  name: string;
  age: number;
}

function isObject(value: unknown): value is Record<string, unknown> {
  return (
    typeof value === "object" && value !== null && !Array.isArray(value)
  );
}

function isUser(value: unknown): value is User {
  return (
    isObject(value) &&
    typeof value.name === "string" &&
    typeof value.age === "number"
  );
}

function assertIsUser(value: unknown): asserts value is User {
  if (!isUser(value)) {
    throw new Error(`Expected a user, got ${JSON.stringify(value)}`);
  }
}

function loadUser(text: string): User {
  const data: unknown = JSON.parse(text);
  assertIsUser(data);
  // From here on, data: User
  return data;
}

console.log(loadUser('{ "name": "Mei", "age": 31 }'));
try {
  loadUser('{ "name": "Sam" }');
} catch (error) {
  if (error instanceof Error) {
    console.log(error.message);
  }
}
```

</CodeExample>

No `if` needed after the call: the narrowing applies to **every** line below it. Use a guard when bad data is a normal case you handle (skip it, show a message), and an assertion when bad data means something is broken.

<Callout type="note" title="Write assertion functions with function">

If you write an assertion function as an arrow function in a `const`, calling it gives a puzzling error: "Assertions require every name in the call target to be declared with an explicit type annotation." The simple fix is to use a `function` declaration, as above.

</Callout>

## The non-null assertion `!`

Putting `!` after an expression tells TypeScript "this is **not** `null` or `undefined`, trust me". It removes them from the type, but it checks nothing at runtime. When you're wrong, the crash happens later, somewhere else, with a vague message:

<CodeExample output={`Mei
Cannot read properties of undefined (reading 'name')`}>

```ts
interface User {
  id: number;
  name: string;
}

const users: User[] = [
  { id: 1, name: "Mei" },
  { id: 2, name: "Sam" },
];

// "Trust me, it's there": the ! removes undefined
const mei = users.find((u) => u.id === 1)!;
console.log(mei.name);

try {
  const ghost = users.find((u) => u.id === 3)!;
  console.log(ghost.name);
} catch (error) {
  if (error instanceof Error) {
    console.log(error.message);
  }
}
```

</CodeExample>

A better habit: handle the missing case, or fail **right away** with a message that explains it. A tiny general-purpose `assert` helper makes that a single line, and it narrows just like `!` does:

<CodeExample output={`Sam
No user with id 3`}>

```ts
interface User {
  id: number;
  name: string;
}

const users: User[] = [
  { id: 1, name: "Mei" },
  { id: 2, name: "Sam" },
];

function assert(
  condition: unknown,
  message: string,
): asserts condition {
  if (!condition) {
    throw new Error(message);
  }
}

function getUser(id: number): User {
  const user = users.find((u) => u.id === id); // User | undefined
  assert(user, `No user with id ${id}`);
  return user; // user: User
}

console.log(getUser(2).name);
try {
  console.log(getUser(3).name);
} catch (error) {
  if (error instanceof Error) {
    console.log(error.message);
  }
}
```

</CodeExample>

`asserts condition` (without `is`) means "if this returns, `condition` was truthy", so `user` can't be `undefined` after the call. "No user with id 3" is a lot easier to debug than "reading 'name'".

## `as` casts and their dangers

`value as User` is a **type assertion**, often called a cast. It doesn't convert or check anything: it just tells the compiler to treat the value as a `User`. With outside data, that's a lie TypeScript can't catch:

<CodeExample output="NaN">

```ts
interface User {
  name: string;
  age: number;
}

const user = JSON.parse('{ "name": "Mei" }') as User;
console.log(user.age + 1); // TypeScript thinks age is a number
```

</CodeExample>

TypeScript does stop the most obvious nonsense, when the two types have nothing in common:

```ts
const n = "hello" as number;
// ❌ Error: Conversion of type 'string' to type 'number' may be a mistake because neither type sufficiently overlaps with the other. If this was intentional, convert the expression to 'unknown' first.
```

The message hints at the escape hatch, `"hello" as unknown as number`, which compiles. If you ever find yourself writing a double cast like that, stop: the types are telling you something is wrong.

Here's how the tools in this lesson compare:

| Tool | Checks at runtime? | Use it for |
| --- | --- | --- |
| Type guard `x is T` | ✅ yes, you write the checks | data that may or may not be valid |
| Assertion `asserts x is T` | ✅ yes, throws if wrong | data that **must** be valid |
| Non-null `x!` | ❌ no | rare cases you can prove, better avoided |
| Cast `x as T` | ❌ no | rare cases where you know more than TypeScript |

<Callout type="tip" title="In real projects">

Many teams turn on lint rules that flag `!` and `as` in code review, and they write guards or use a validation library (like zod) at the edges of the app, where data comes in. You'll build a tiny validation library yourself in Level 2. For now, a good rule: **`unknown` at the edges, guards to get in, real types inside.**

</Callout>

```ts
// Amounts are in pence (1250 = £12.50), so sums stay exact.
type Payment =
  | { status: "pending"; id: string; amount: number }
  | { status: "paid"; id: string; amount: number }
  | { status: "failed"; id: string; amount: number; reason: string }
  | {
      status: "refunded";
      id: string;
      amount: number;
      refunded: number; // pence given back
    };

interface Summary {
  count: number; // valid payments
  collected: number; // pence we keep
  pending: number; // payments still pending
  failed: number; // failed payments
}

function assertNever(value: never): never {
  throw new Error(`Unexpected value: ${JSON.stringify(value)}`);
}

function isObject(value: unknown): value is Record<string, unknown> {
  return (
    typeof value === "object" && value !== null && !Array.isArray(value)
  );
}

function pounds(pence: number): string {
  return `£${(pence / 100).toFixed(2)}`;
}

// ===== Your code =====

function isPayment(value: unknown): value is Payment {
  if (!isObject(value)) {
    return false;
  }
  if (typeof value.id !== "string") {
    return false;
  }
  if (typeof value.amount !== "number") {
    return false;
  }
  switch (value.status) {
    case "pending":
    case "paid":
      return true;
    case "failed":
      return typeof value.reason === "string";
    case "refunded":
      return typeof value.refunded === "number";
    default:
      return false; // a status we don't know
  }
}

function parsePayments(json: string): Payment[] {
  let data: unknown;
  try {
    data = JSON.parse(json);
  } catch {
    return []; // not valid JSON
  }
  if (!Array.isArray(data)) {
    return [];
  }
  return data.filter(isPayment);
}

function describePayment(payment: Payment): string {
  const { id, amount } = payment;
  switch (payment.status) {
    case "pending":
      return `${id}: ${pounds(amount)} pending`;
    case "paid":
      return `${id}: ${pounds(amount)} paid`;
    case "failed":
      return `${id}: ${pounds(amount)} failed (${payment.reason})`;
    case "refunded": {
      const back = pounds(payment.refunded);
      return `${id}: ${back} of ${pounds(amount)} refunded`;
    }
    default:
      return assertNever(payment);
  }
}

function summarise(payments: Payment[]): Summary {
  const summary: Summary = {
    count: payments.length,
    collected: 0,
    pending: 0,
    failed: 0,
  };
  for (const payment of payments) {
    switch (payment.status) {
      case "pending":
        summary.pending++;
        break;
      case "paid":
        summary.collected += payment.amount;
        break;
      case "failed":
        summary.failed++;
        break;
      case "refunded":
        summary.collected += payment.amount - payment.refunded;
        break;
      default:
        assertNever(payment);
    }
  }
  return summary;
}

// ===== Try it out =====
const webhookLog = `[
```

## Recap

- A **type guard** returns a **type predicate** `value is T`: if it returns `true`, TypeScript narrows to `T` (and `filter(guard)` gives a `T[]`).
- TypeScript trusts your predicate without checking it, so keep guards small, correct and tested.
- `JSON.parse` returns `any`: store the result as `unknown` and validate it before use.
- Validate step by step: `isObject` first, then each property with `typeof`; remember `Array.isArray` gives `any[]`, so check the items too.
- An **assertion function** (`asserts value is T`, or `asserts condition`) throws on bad data and narrows every line after the call.
- `!` and `as` change what TypeScript believes without checking anything; prefer guards, assertions and clear errors.
- **`unknown` at the edges, guards to get in, real types inside.**
