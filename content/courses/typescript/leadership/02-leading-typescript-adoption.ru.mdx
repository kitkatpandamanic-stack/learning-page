Рано или поздно вы становитесь «человеком по TypeScript»: к вам приходят спросить, почему ошибка не имеет смысла, стоит ли включать флаг и как типизировать странную штуку, которую возвращает API. С этого момента ваше влияние зависит уже не столько от типов, которые вы пишете сами, сколько от того, как с типами работает **вся команда**: общая базовая конфигурация, соглашения, которым люди действительно следуют, переход на строгий режим, не останавливающий работу над фичами, junior-разработчики, которые растут, и умение вовремя сказать «типов достаточно». Этот урок — план действий. 🧭

## Общая базовая конфигурация

В кодовой базе с двенадцатью пакетами и двенадцатью написанными вручную файлами `tsconfig.json` настройки расползаются. В одном пакете вдруг обнаруживается `"strict": false`, в другом — опечатка в имени флага, которую молча игнорируют уже год, и никто не знает, какие правила где действуют. Решение — одна **базовая конфигурация** (base config), которую расширяет каждый пакет:

```jsonc title="tsconfig.base.json"
{
  "compilerOptions": {
    // Корректность: то, что в команде не обсуждается
    "strict": true,
    "noUncheckedIndexedAccess": true,
    "noImplicitOverride": true,
    "noImplicitReturns": true,
    "noFallthroughCasesInSwitch": true,

    // Модули: так же, как работают наш бандлер и Node
    "target": "ES2022",
    "module": "ESNext",
    "moduleResolution": "bundler",
    "verbatimModuleSyntax": true,
    "isolatedModules": true,

    // Скорость: не перепроверять файлы .d.ts каждой библиотеки
    "skipLibCheck": true,
    "noEmit": true
  }
}
```

```jsonc title="packages/checkout/tsconfig.json"
{
  "extends": "../../tsconfig.base.json",
  "include": ["src"]
}
```

Начиная с TypeScript 6, `strict` включён, даже если вы его не указали, так что новые проекты сразу строгие. В старых кодовых базах в конфигурации обычно записано `"strict": false` (часто его добавили в день обновления, чтобы сборка осталась зелёной). В любом случае пишите `"strict": true` явно: это документирует решение. Все эти флаги вы встречали в уроке [tsconfig и компилятор](/learn/typescript/tsconfig-and-the-compiler). Вопрос лидерства — **какие из них попадут в базовую конфигурацию**. Несколько критериев:

- **Ловит ли флаг баги, которые у нас действительно были?** Посмотрите на недавние инциденты и баг-тикеты. Если три из последних десяти ошибок в продакшене были «Cannot read properties of undefined» после поиска по ключу, `noUncheckedIndexedAccess` заслужил своё место.
- **Сколько он стоит?** Включите его в отдельной ветке и посчитайте ошибки. Двадцать — это полдня. Четыре тысячи — это проект (см. ниже).
- **Исправления механические или требуют размышлений?** Механические исправления можно раздать или автоматизировать скриптом; исправлениям, которым нужно знание предметной области, нужны владельцы.
- **Не конфликтует ли он с нашими инструментами?** `exactOptionalPropertyTypes` отлично подходит для библиотек и API в стиле «патчей», но типы некоторых UI-библиотек писались без расчёта на него. Попробуйте, прежде чем решать.

Что бы вы ни выбрали, запишите рядом, **почему** (комментарием или короткой записью о решении), и сделайте `tsc --noEmit` **обязательной проверкой** в CI. Базовая конфигурация, которая работает только в редакторах у некоторых людей, — не базовая конфигурация.

## Соглашения: коротко, с причинами, под контролем инструментов

Документ с соглашениями (conventions) — это место, где команда записывает, как она пользуется TypeScript. Работают те, что **короткие**, объясняют **причину** каждого правила (люди следуют правилам, которые понимают) и ссылаются на правило линтера везде, где проверить может машина:

```markdown title="docs/typescript.md"
# Как мы пишем на TypeScript

1. Данные снаружи (HTTP, JSON, хранилище, env) приходят как `unknown`
   и проверяются схемой. Почему: во время выполнения типов нет.
2. Никаких `any` и никаких `as` за пределами валидаторов и тестов.
   (lint: no-explicit-any, no-unsafe-*)
3. Фиксированные наборы значений — объединения, выведенные из массива
   `as const`, а не enum. Почему: один источник и для типа, и для проверки.
4. Ожидаемые сбои возвращают `Result`; баги выбрасывают исключения.
5. Каждый `switch` по объединению исчерпывающий.
   (lint: switch-exhaustiveness-check)
6. Экспортируемые функции объявляют тип возвращаемого значения.
   (lint: explicit-module-boundary-types)
7. `@ts-expect-error` требует причины и тикета. Никаких `@ts-ignore`.
   (lint: ban-ts-comment)
8. Формы объектов — `interface`; объединения и всё остальное — `type`.
   Почему: без причины. Мы выбрали один вариант, чтобы больше об этом не спорить.
```

Правило 8 заслуживает пояснения. У некоторых вопросов, вроде `type` против `interface` или того, где ставить точки с запятой, нет по-настоящему правильного ответа, а команда может потерять на них часы ревью. Ценность — в том, чтобы **решить один раз**, а не в самом выборе. Запишите, дайте ссылку и двигайтесь дальше.

Правило 3 стоит увидеть в коде, потому что это как раз такое соглашение, которое тихо предотвращает баги. Список значений существует **один раз**, и из него получаются и тип, и проверка во время выполнения:

<CodeExample output={`pro: £9.00 a month
enterprise: not a plan
team: £29.00 a month`}>

```ts
// Один список значений: его используют и тип, и проверка во время выполнения
const PLANS = ["free", "pro", "team"] as const;
type Plan = (typeof PLANS)[number]; // "free" | "pro" | "team"

function isPlan(value: string): value is Plan {
  return PLANS.some((plan) => plan === value);
}

// Таблицы поиска — это Record<Union, …>: новый тариф не скомпилируется,
// пока в каждой таблице не появится запись для него
const PRICE_PENCE: Record<Plan, number> = {
  free: 0,
  pro: 900,
  team: 2900,
};

// Значения снаружи (форма, URL, JSON) проверяются один раз
for (const input of ["pro", "enterprise", "team"]) {
  if (isPlan(input)) {
    const price = (PRICE_PENCE[input] / 100).toFixed(2);
    console.log(`${input}: £${price} a month`);
  } else {
    console.log(`${input}: not a plan`);
  }
}
```

</CodeExample>

Когда отдел продаж добавит `"enterprise"` в `PLANS`, `isPlan` автоматически начнёт его принимать, а каждая таблица поиска, которая о нём забыла, перестанет компилироваться:

```ts
const PRICE_PENCE: Record<Plan, number> = {
// ❌ Error: Property 'enterprise' is missing in type '{ free: number; pro: number; team: number; }' but required in type 'Record<"free" | "pro" | "team" | "enterprise", number>'.
```

<Callout type="tip" title="Соглашения — это тоже код">

Храните документ с соглашениями в репозитории и меняйте его через пул-реквесты, как любой другой код. Когда один и тот же комментарий на ревью появляется снова и снова, решение — новое правило линтера или новая строчка в документе, а не тот же комментарий в двадцатый раз. Когда правило постоянно отключают, оно, скорее всего, неверное: обсудите его и поменяйте.

</Callout>

## Переход на строгий режим в большой кодовой базе

Включение `strict` (или `strictNullChecks`, самой большой его части) в кодовой базе на 300 000 строк может разом дать тысячи ошибок. Исправить их в одном пул-реквесте нельзя, и заморозить работу над фичами на месяц тоже нельзя. Нужен план, который позволит кодовой базе становиться строже **постепенно**, при этом новый код будет строгим с первого дня.

| Стратегия | Как | Когда выбирать |
| --- | --- | --- |
| **Всё сразу** (big bang) | Включить и исправить всё за один раз | маленькая кодовая база, максимум несколько сотен ошибок |
| **Флаг за флагом** | сначала `noImplicitAny`, потом `strictNullChecks`, потом остальные | ошибки распределены равномерно; каждый флаг — отдельная веха |
| **Папка за папкой** | вторая конфигурация, `tsconfig.strict.json`, включающая только переведённые папки; CI запускает обе | у кода понятные модули с понятными владельцами |
| **Файл за файлом** | strict везде, с комментарием-исключением в начале каждого непереведённого файла | большая запутанная кодовая база; новые файлы автоматически строгие |
| **Подавить и выжигать** | `@ts-expect-error` на каждой существующей ошибке, а затем постепенно их убирать | ошибок мало в каждом файле, но файлов много |

Конфигурация «папка за папкой» — это обычный TypeScript:

```jsonc title="tsconfig.strict.json"
{
  "extends": "./tsconfig.json",
  "compilerOptions": { "strict": true },
  // Добавляйте сюда папки по мере перевода
  "include": ["src/shared", "src/billing"]
}
```

Для подхода «файл за файлом» популярен инструмент **typescript-strict-plugin**: основная конфигурация остаётся нестрогой, плагин (зарегистрированный в `plugins` в `tsconfig.json`) проверяет строгие правила в каждом файле, который не начинается с `//@ts-strict-ignore`, а в комплекте идёт скрипт, который добавляет этот комментарий в каждый файл, где сейчас есть ошибки:

```bash
npm install --save-dev typescript-strict-plugin
npx update-strict-comments   # пометить файлы, которые падают сегодня
npx tsc-strict               # CI: строгие ошибки во всех остальных файлах
```

С этого момента каждый новый файл строгий, а перевод файла означает удалить один комментарий и исправить то, что всплывёт.

### Сделайте это измеримым и позвольте числу только уменьшаться

Переход без цифр тихо глохнет. Посчитайте оставшиеся ошибки по командам, закоммитьте эти числа и пусть CI падает, когда они **растут**. Когда они падают, меньшее число становится новой базовой линией. Это **храповик** (ratchet) — та же идея, что и при миграции с JS на TS, — и он превращает «надо бы уже закончить со strict» в видимую общую динамику:

<CodeExample output={`Payments   9 → 6
Discovery  4 → 5 ❌ new errors
Platform   2 → 0 🎉 done
Total      15 → 11
CI fails: new strict errors from Discovery`}>

```ts
// Сегодняшний вывод `tsc -p tsconfig.strict.json`, по строке на ошибку
// (сообщения обрезаны)
const tscOutput = `
src/billing/invoice.ts(14,7): error TS2322
src/billing/invoice.ts(31,12): error TS18048
src/billing/refunds.ts(9,3): error TS18048
src/billing/refunds.ts(40,18): error TS2345
src/billing/tax.ts(5,10): error TS7006
src/billing/tax.ts(22,5): error TS18047
src/search/query.ts(8,20): error TS7006
src/search/query.ts(19,4): error TS2532
src/search/ranking.ts(3,15): error TS7006
src/search/filters.ts(12,9): error TS18048
src/search/filters.ts(30,2): error TS2322
`;

const TEAMS = ["Payments", "Discovery", "Platform"] as const;
type Team = (typeof TEAMS)[number];

// Кто какой папкой владеет (как файл CODEOWNERS)
const owners: Record<string, Team> = {
  "src/billing/": "Payments",
  "src/search/": "Discovery",
  "src/shared/": "Platform",
};

// Цифры прошлой недели, закоммиченные как strict-baseline.json
const baseline: Record<Team, number> = {
  Payments: 9,
  Discovery: 4,
  Platform: 2,
};

function ownerOf(file: string): Team {
  for (const [folder, team] of Object.entries(owners)) {
    if (file.startsWith(folder)) return team;
  }
  throw new Error(`Nobody owns ${file}: add it to owners`);
}

const today: Record<Team, number> = {
  Payments: 0,
  Discovery: 0,
  Platform: 0,
};
for (const line of tscOutput.trim().split("\n")) {
  const file = line.slice(0, line.indexOf("("));
  today[ownerOf(file)]++;
}

const worse: Team[] = [];
for (const team of TEAMS) {
  const [before, now] = [baseline[team], today[team]];
  let note = "";
  if (now > before) {
    note = "❌ new errors";
    worse.push(team);
  } else if (now === 0) {
    note = "🎉 done";
  }
  console.log(`${team.padEnd(10)} ${before} → ${now} ${note}`.trim());
}

const total = (counts: Record<Team, number>) =>
  TEAMS.reduce((sum, team) => sum + counts[team], 0);
console.log(`Total      ${total(baseline)} → ${total(today)}`);
console.log(
  worse.length > 0
    ? `CI fails: new strict errors from ${worse.join(", ")}`
    : "CI passes: commit the lower numbers as the new baseline",
);
```

</CodeExample>

Группировка по **владельцу** важна не меньше самих цифр. «Осталось 11 строгих ошибок» — ничья задача. «У Discovery 5, и за неделю стало больше» — разговор, который может провести один тимлид. Обратите внимание: скрипт ещё и громко падает на файле без владельца, так что ничего не проваливается в щели.

<Callout type="danger" title="Флаг включён, а код стал хуже">

Одна знакомая команда включила `strictNullChecks` во всём большом приложении за две недели. Секрет: везде, где жаловался компилятор, кто-то добавлял `!` или `as any`. Около 1800 штук. Флаг был включён, дашборд зелёный, а код стал **менее** безопасным, чем раньше: каждый `!` теперь выглядел как сознательное, прошедшее ревью решение, и никто не мог отличить настоящие от panic-исправлений. Через год их всё ещё находили — по одному падению за раз.

Подавления во время перехода допустимы, но они должны быть **видимыми и измеримыми**: комментарий-исключение в начале файла или `@ts-expect-error` с номером тикета. Никогда не «исправление», которое выглядит как настоящий код. Заставить ошибку исчезнуть — не то же самое, что сделать код правильным.

</Callout>

Сработает ли всё это, решает человеческая сторона:

- **Сначала объясните, зачем.** «В прошлом квартале у нас было 14 падений в продакшене из-за `undefined`; `strictNullChecks` поймал бы 11» — убеждает. «Strict — это лучшая практика» — нет.
- **Новый код строгий с первого дня.** Куча уменьшается, только если никто не подкладывает в неё новое.
- **Сделайте исправление простым.** Короткая страница с десятью самыми частыми строгими ошибками и способом исправить каждую, канал в чате, еженедельные «часы консультаций», парное программирование.
- **Делите работу честно.** Каждая команда переводит свой код, понемногу каждый спринт, а храповик ведёт счёт. Один герой, который делает всё, выгорает, а остальные ничему не учатся.
- **Празднуйте вехи.** «Payments полностью на strict 🎉» в командном канале ничего не стоит и работает.

## Честно измеряем типобезопасность

То, что измеряют, получает внимание, поэтому выбирайте цифры, которые указывают на реальную безопасность. Самая известная — **покрытие типами** (type coverage): доля идентификаторов, чей тип — не `any`. Его вычисляет инструмент `type-coverage`, который печатает что-то вроде `4021 / 4235 94.94%` и может ронять CI ниже порога:

```bash
npx type-coverage --at-least 95   # падает ниже 95%
npx type-coverage --detail        # перечисляет каждый any, файл:строка
```

Рядом с ним отслеживайте:

- **«Аварийные люки»**: количество `as`, `!`, `@ts-expect-error` и подавлений линтера по папкам с течением времени. Об этом могут сообщать правила typescript-eslint, а может хватить и простого `grep -c`.
- **Прогресс строгого режима**: переведённые файлы или папки и итоговая цифра храповика.
- **Результаты**: цифра, которая действительно важна. Сколько ошибок в продакшене — это «Cannot read properties of undefined» или «x is not a function»? Ваш трекер ошибок знает. Работа над типами должна вести эту линию вниз.

Остерегайтесь **закона Гудхарта** (Goodhart's law): когда мера становится целью, она перестаёт быть хорошей мерой. Сделайте «98% покрытия типами» жёсткой целью — и кто-нибудь превратит `any` в `as unknown as Order`. Покрытие растёт, безопасность остаётся ровно той же. Поэтому отслеживайте несколько цифр вместе (покрытие **и** приведения типов), смотрите на тренды, а не на отдельные значения, и продолжайте читать diff.

## Наставничество junior-разработчиков в типах

Junior-разработчики обычно знакомятся с TypeScript через его ошибки, а длинные ошибки пугают. Одна из самых полезных вещей, которым можно научить, — как их **читать**. Вот типичная:

```ts
const order: Order = fromForm;
// ❌ Error: Type '{ id: string; customer: { name: string; address: { street: string; postcode: number; }; }; }' is not assignable to type 'Order'.
//   The types of 'customer.address.postcode' are incompatible between these types.
//     Type 'number' is not assignable to type 'string'.
```

Научите их **читать снизу вверх**. Первая строка говорит: «что-то где-то не подходит». Последние строки говорят, что именно: путь `customer.address.postcode` и само несоответствие — `number` там, где должна быть `string`. Наведение курсора на значения в редакторе и вставка маленького примера в [TypeScript Playground](https://www.typescriptlang.org/play) — ещё два повседневных инструмента, которые стоит показать.

Кроме того:

- **Исправляйте тип, а не ошибку.** Когда в PR junior-разработчика есть `as any`, не говорите просто «никаких приведений». Спросите: «что сказала ошибка?» — и прочитайте её вместе. Обычно ошибка была права, а исправление — защитник типа или более точный тип. Такой разговор учит больше любого правила.
- **Учите в правильном порядке.** Сначала объединения и сужение типов — они окупаются каждый день. Дженерики — когда понадобится написать переиспользуемый помощник. Условные и сопоставленные типы — гораздо позже и в основном для чтения кода библиотек.
- **Объясняйте причины соглашений.** «Мы разбираем env в типизированную конфигурацию, *чтобы опечатка в LOG_LEVEL ломала запуск, а не будила нас в 3 часа ночи*» — запоминается; «всегда проверяйте конфигурацию» — нет.
- **Ревьюйте великодушно.** В PR junior-разработчика выберите два-три самых важных момента про типы. Двадцать комментариев о `readonly` и типах возвращаемых значений похоронят тот единственный, что про непроверенный JSON.
- **Программируйте в паре над реальными задачами.** Вместе убрать один настоящий `as` (найти, откуда приходит значение, написать защитника типа, добавить тест) — значит пройти всю цепочку.
- **Сделайте незнание безопасным.** «Я тоже не знаю, почему TypeScript выводит такой тип, давай разберёмся» от senior-разработчика даёт всем разрешение спрашивать.

## Дизайн-документы для изменений, завязанных на типы

Некоторые изменения типов не меньше нового сервиса: поменять доменный тип, который используют 400 файлов, ввести брендированные id, перевести обработку ошибок на `Result` или перепроектировать типы пакета, от которого зависят другие команды. Они заслуживают короткого **дизайн-документа** (design doc) до того, как кто-то напишет код (общий шаблон есть в уроке [Код-ревью и техническое лидерство](/learn/javascript/code-review-and-leadership)). Для изменений типов важнее всего несколько разделов:

```markdown
# Дизайн: брендированные id для заказов и покупателей

## Контекст
Дважды за этот год OrderId передавали туда, где должен быть CustomerId.

## Предлагаемые типы (вставьте настоящие объявления)
type OrderId = string & { readonly __brand: "OrderId" };

## До и после — в трёх реальных местах вызова

## Как теперь выглядят ошибки (вставьте ошибки компилятора)

кодмод обновляет импорты; по одному PR на пакет.

## Стоимость
Время проверки типов до/после (tsc --extendedDiagnostics).

## Тесты типов
## Рассмотренные альтернативы
## Выкатка и как её откатить
```

Два раздела особенны именно для TypeScript. Раздел **«Как теперь выглядят ошибки»** заставляет вставить настоящие ошибки, которые увидят разработчики: если их невозможно прочитать, дизайн не готов. А раздел **«Миграция»** обычно опирается на `@deprecated`, который редакторы показывают зачёркнутым, а правило `no-deprecated` из typescript-eslint умеет о нём сообщать:

```ts
/** @deprecated Используйте `OrderId`. Будет удалён в v5. */
export type LegacyOrderId = string;
```

## Когда перестать добавлять типы

У типов есть цена: время на написание, время на чтение, время на компиляцию и время на изменения, когда бизнес передумает. Лучше всего они окупаются в некоторых местах:

- **Границы**: HTTP, JSON, база данных, пользовательский ввод, конфигурация. Именно здесь входит большинство реальных багов.
- **Общие доменные типы**, от которых зависят многие файлы и команды.
- **Публичные API** пакетов и модулей.
- **Часто меняющийся код**, где компилятор находит каждое место, до которого должно дойти изменение.

И хуже — в других: одноразовые скрипты, прототипы, которые вы выбросите, внутренности тестов и связующий код, который просто передаёт значения дальше. Он всё равно должен быть строгим и без `any`, но брендированные типы или конечный автомат в системе типов ему не нужны.

Признаки того, что кодовая база зашла слишком далеко: код на уровне типов длиннее кода времени выполнения, который он описывает; пул-реквесты по нескольку дней застревают на головоломке с типами; время проверки типов ползёт вверх; ошибки, которые никто не может прочитать; junior-разработчики, которые боятся трогать папку с типами. Хорошее практическое правило: **тип заслуживает своего места, если он предотвращает ошибку, которую кто-то вполне может совершить, и цена его понятна команде.**

<Callout type="note" title="Лидерство — это в основном про умолчания">

Большинство разработчиков никогда не читают документ с соглашениями. Они копируют код по соседству, принимают подсказки редактора и делают всё, что пропускает CI. Поэтому ведите через умолчания: строгая базовая конфигурация, конфигурация линтера, которая ловит частые ошибки, примеры в кодовой базе, которые стоит копировать, и шаблоны для новых пакетов. Сделайте безопасный путь простым — и большая часть команды последует за вами без лишних указаний.

</Callout>

| Переменная | Правила | По умолчанию |
| --- | --- | --- |
| `PORT` | только цифры, от 1 до 65535; становится `number` | `3000` |
| `LOG_LEVEL` | `debug`, `info`, `warn` или `error` | `"info"` |
| `DATABASE_URL` | обязательная; должна начинаться с `postgres://` | нет |
| `FEATURES` | имена известных фич через запятую: `new-checkout`, `dark-mode`, `beta-search`. Пробелы вокруг имён и пустые элементы игнорируются | без фич |

- `config` доступен только для чтения, `logLevel` — объединение четырёх уровней, а `features` — `ReadonlySet` из известных имён фич, так что `config.features.has("dark-mod")` — ошибка типа.

<Hint>

1. Следуйте правилу 3 из документа с соглашениями: `const LOG_LEVELS = ["debug", "info", "warn", "error"] as const;` и `type LogLevel = (typeof LOG_LEVELS)[number];`, и то же самое для `FEATURES`. 2. Сделайте каждое свойство `Config` `readonly`, а `features` — `ReadonlySet<Feature>`.
3. В `loadConfig` собирайте сообщения в массив `errors`, а не возвращайтесь на первой же проблеме. `env[name] || undefined` считает `""` незаданным. Для `PORT` проверьте `/^\d+$/` до `Number(...)`: `Number(" 80")` — это `80`, а `Number("")` — `0`.
4. В `shouldLog` классический баг: `"error" >= "info"` сравнивает строки по алфавиту, поэтому даёт `false`. Сравнивайте позиции: `LOG_LEVELS.indexOf(level)`.

</Hint>

import { describe, it, expect } from "vitest";

type Env = Record<string, string | undefined>; // как process.env

// Один список значений: из него получаются и типы, И проверки
const LOG_LEVELS = ["debug", "info", "warn", "error"] as const;
type LogLevel = (typeof LOG_LEVELS)[number];

const FEATURES = ["new-checkout", "dark-mode", "beta-search"] as const;
type Feature = (typeof FEATURES)[number];

interface Config {
  readonly port: number;
  readonly logLevel: LogLevel;
  readonly databaseUrl: string;
  readonly features: ReadonlySet<Feature>;
}

type LoadResult =
  | { ok: true; config: Config }
  | { ok: false; errors: string[] };

function isOneOf<T extends string>(
  options: readonly T[],
  value: string,
): value is T {
  return options.some((option) => option === value);
}

function loadConfig(env: Env): LoadResult {
  const errors: string[] = [];
  // И отсутствие, и пустая строка означают «не задано»
  const read = (name: string) => env[name] || undefined;

  let port = 3000;
  const rawPort = read("PORT");
  if (rawPort !== undefined) {
    const n = Number(rawPort);
    if (/^\d+$/.test(rawPort) && n >= 1 && n <= 65535) {
      port = n;
    } else {
      errors.push(`PORT must be 1 to 65535, got "${rawPort}"`);
    }
  }

  let logLevel: LogLevel = "info";
  const rawLevel = read("LOG_LEVEL");
  if (rawLevel !== undefined) {
    if (isOneOf(LOG_LEVELS, rawLevel)) {
      logLevel = rawLevel;
    } else {
      const options = LOG_LEVELS.join(", ");
      errors.push(`LOG_LEVEL must be ${options}, got "${rawLevel}"`);
    }
  }

  const databaseUrl = read("DATABASE_URL") ?? "";
  if (!databaseUrl.startsWith("postgres://")) {
    errors.push("DATABASE_URL must be a postgres:// URL");
  }

  const features = new Set<Feature>();
  for (const part of (read("FEATURES") ?? "").split(",")) {
    const name = part.trim();
    if (name === "") continue;
    if (isOneOf(FEATURES, name)) {
      features.add(name);
    } else {
      errors.push(`FEATURES: unknown feature "${name}"`);
    }
  }

  if (errors.length > 0) return { ok: false, errors };
  const config = { port, logLevel, databaseUrl, features };
  return { ok: true, config };
}

function shouldLog(config: Config, level: LogLevel): boolean {
  const rank = (l: LogLevel) => LOG_LEVELS.indexOf(l);
  return rank(level) >= rank(config.logLevel);
}

## Итоги

- Дайте команде **одну базовую конфигурацию tsconfig**, которую расширяет каждый пакет, с причинами для каждого флага, и сделайте `tsc --noEmit` обязательной проверкой в CI. Выбирайте флаги по тем багам, которые они ловят, и по цене их внедрения.
- Держите **документ с соглашениями** коротким, с причиной для каждого правила, и переносите в линтер каждое правило, которое может проверить машина. Споры о вкусах решайте один раз.
- Вводите **строгий режим** постепенно: новый код строгий с первого дня, непереведённые файлы помечены на виду, оставшиеся ошибки считаются **по владельцам** с храповиком в CI. Никогда не «исправляйте» ошибки через `!` или `as any`.
- **Измеряйте** покрытие вместе с «аварийными люками» и реальными ошибками в продакшене; одна цифра в роли цели провоцирует подгонку (закон Гудхарта).
- **Наставляйте**: учите читать ошибки снизу вверх, спрашивайте «что сказала ошибка?» вместо запрета приведений и выбирайте те немногие комментарии, которые действительно важны.
- Пишите **дизайн-документ** для изменений типов с широким охватом: вставляйте предлагаемые типы и ошибки, которые увидят люди, и планируйте миграцию через `@deprecated`.
- **Остановитесь**, когда типы стоят дороже, чем ошибки, которые они предотвращают. Ведите через хорошие умолчания, чтобы безопасный путь был простым.
