Обычно вы не задумываетесь, почему `Dog` подходит туда, где ожидается `Animal`. Это просто работает. Но ошибки, которые проскальзывают через строгую кодовую базу на TypeScript, обычно живут как раз в закоулках этих правил: обработчик события, который проходит проверку типов и всё равно падает, опечатка в ключе конфигурации, которая компилируется, дженерик-функция, которая «услужливо» принимает значение, которое должна была отвергнуть. В этом уроке вы точно разберёте правила **совместимости типов** (assignability), увидите, где TypeScript намеренно их нарушает, а потом научитесь управлять **выводом типов** (inference) с помощью `NoInfer`, `const`-параметров типа и `satisfies`. ⚖️

## Совместимость определяется формой

TypeScript сравнивает типы по их **структуре**, как вы видели в уроке про [структурную типизацию](/learn/typescript/structural-typing-and-class-design): значение подходит к типу, если в нём есть всё, чего тип требует. Лишние свойства не мешают, и они остаются в объекте:

<CodeExample output={`(3, 4)
{ x: 3, y: 4, label: 'Дом' }
(0, 0)`}>

```ts
interface Point {
  x: number;
  y: number;
}

function formatPoint(p: Point): string {
  return `(${p.x}, ${p.y})`;
}

const pin = { x: 3, y: 4, label: "Дом" };
console.log(formatPoint(pin)); // всё в порядке: у pin есть x и y
console.log(pin); // лишнее свойство label никуда не делось

const origin: Point = { x: 0, y: 0 };
console.log(formatPoint(origin));
```

</CodeExample>

Тогда почему здесь ошибка?

```ts
const home: Point = { x: 3, y: 4, label: "Дом" };
// ❌ Error: Object literal may only specify known properties, and 'label' does not exist in type 'Point'.
```

Это **проверка лишних свойств** (excess property check), и это намеренное исключение. Она работает только для **свежего** объектного литерала, написанного прямо там, где ожидается тип. Через `Point` никто никогда не сможет прочитать `label`, поэтому такое свойство здесь — почти наверняка опечатка или недоразумение. Когда объект уже сохранён в переменной, его вполне законно могут использовать и как значение других типов, поэтому проверка отключается. Spread (`{ ...pin }`) тоже её отключает — это частый путь, которым проскальзывают лишние данные.

Стоит знать ещё два пограничных случая. У **слабого типа** (weak type) все свойства необязательные, так что структурно к нему подошло бы почти что угодно. Поэтому TypeScript требует хотя бы одно общее свойство — и это ловит классическую опечатку в названии параметра:

```ts
interface SaveOptions {
  overwrite?: boolean;
  backup?: boolean;
}
function save(name: string, options: SaveOptions) {}

const opts = { overwrit: true };
save("notes.txt", opts);
// ❌ Error: Type '{ overwrit: boolean; }' has no properties in common with type 'SaveOptions'.
```

И ещё: **`{}` — это не «пустой объект»**. Он означает «любое значение, кроме `null` и `undefined`», поэтому `const n: {} = "hello"` компилируется. Если нужно «любое не-примитивное значение», используйте `object`, а для «вообще что угодно» — `unknown`.

## Вариантность: как ведут себя контейнеры

Интересный вопрос не в том, подходит ли `Dog` вместо `Animal`. Интересно, подходит ли **контейнер** с собаками вместо контейнера с животными: можно ли присвоить `Box<Dog>` в `Box<Animal>`? Ответ зависит от того, что контейнер **делает** со своим содержимым, и называется это **вариантностью** (variance):

| Вариантность | Что значит | Типичный пример |
| --- | --- | --- |
| **Ковариантность** (covariant) | `Box<Dog>` подходит вместо `Box<Animal>` (то же направление) | то, что только **читают**: возвращаемые типы, `readonly Dog[]`, `Promise<Dog>` |
| **Контравариантность** (contravariant) | `Box<Animal>` подходит вместо `Box<Dog>` (обратное направление) | то, во что только **записывают**: параметры функций |
| **Инвариантность** (invariant) | ни в одну сторону | то, что и читают, **и** записывают |
| **Бивариантность** (bivariant) | в обе стороны (ненадёжно) | параметры методов, см. ниже |

Простое правило: **чтение ковариантно, запись контравариантна, и то и другое — инвариантно.** Посмотрим, где TypeScript ему следует, а где нет.

## Массивы ковариантны, и это ненадёжно

Изменяемый массив и читают, **и** записывают, так что по правилу выше он должен быть инвариантным. Но TypeScript всё равно делает массивы ковариантными, потому что код вида «передать мой `Dog[]` в функцию, которая принимает `Animal[]`» встречается на каждом шагу. Цена — настоящая дыра в типах:

<CodeExample output={`Woof!
Tom: dog.bark is not a function`}>

```ts
interface Animal {
  name: string;
}
interface Dog extends Animal {
  bark(): string;
}
interface Cat extends Animal {
  meow(): string;
}

const dogs: Dog[] = [{ name: "Rex", bark: () => "Woof!" }];
const animals: Animal[] = dogs; // можно: массивы ковариантны
const tom: Cat = { name: "Tom", meow: () => "Meow" };
animals.push(tom); // и это можно...

for (const dog of dogs) {
  try {
    console.log(dog.bark());
  } catch (error) {
    console.log(`${dog.name}: ${(error as Error).message}`);
  }
}
```

</CodeExample>

`animals` и `dogs` — это **один и тот же** массив, так что кошка оказалась в списке собак без единой ошибки типов. В реальном коде это прячется в хелпере вроде `addDefaults(items: Item[])`, который добавляет элементы в любой переданный ему массив. Решение — честно описать, что функция делает на самом деле: если она только **читает**, пусть принимает `readonly`-массив. Массивы только для чтения ковариантны **надёжно**, ведь записать в них кошку никто не сможет:

```ts
const someAnimals: readonly Animal[] = dogs; // ✅ безопасно
someAnimals.push(tom);
// ❌ Error: Property 'push' does not exist on type 'readonly Animal[]'.
```

## Параметры функций контравариантны

Теперь обратное направление. **Обработчик** — это обещание: «дайте мне собаку, и я с ней разберусь». Функция, которая умеет обрабатывать **любое** животное, это обещание выполняет, поэтому её можно использовать везде, где нужен обработчик собак:

<CodeExample output={`Привет, Rex
Woof!`}>

```ts
interface Animal {
  name: string;
}
interface Dog extends Animal {
  bark(): string;
}

type Handler<T> = (value: T) => void;

const logName: Handler<Animal> = (a) => console.log(`Привет, ${a.name}`);
const playFetch: Handler<Dog> = (d) => console.log(d.bark());

// Оба справятся с собакой: logName обрабатывает ЛЮБОЕ животное
const dogHandlers: Handler<Dog>[] = [logName, playFetch];

const rex: Dog = { name: "Rex", bark: () => "Woof!" };
for (const handle of dogHandlers) {
  handle(rex);
}
```

</CodeExample>

В обратную сторону обещание было бы нарушено: список обработчиков животных могут вызвать с кошкой, и `playFetch` упадёт. TypeScript не разрешает:

```ts
const animalHandlers: Handler<Animal>[] = [playFetch];
// ❌ Error: Type 'Handler<Dog>' is not assignable to type 'Handler<Animal>'.
```

Значит, `Handler<T>` **контравариантен** по `T`: стрелка разворачивается. Возвращаемые типы ведут себя обычно (функция, возвращающая `Dog`, подходит туда, где ожидается функция, возвращающая `Animal`), так что функциональный тип контравариантен по параметрам и ковариантен по результату.

## Методы бивариантны, и это сделано намеренно

А вот дыра, которая удивляет даже опытных разработчиков. Запишите ту же идею в интерфейсе **синтаксисом метода** — и проверка исчезнет:

<CodeExample output={`Rex говорит Woof!
dog.bark is not a function`}>

```ts
interface Animal {
  name: string;
}
interface Dog extends Animal {
  bark(): string;
}

// Синтаксис метода: admit(animal: Animal): void
interface Shelter {
  admit(animal: Animal): void;
}

const dogsOnly: Shelter = {
  // Принято, хотя обрабатывает только собак!
  admit(dog: Dog) {
    console.log(`${dog.name} говорит ${dog.bark()}`);
  },
};

const rex: Dog = { name: "Rex", bark: () => "Woof!" };
const tom: Animal = { name: "Tom" };

dogsOnly.admit(rex);
try {
  dogsOnly.admit(tom); // по типу подходит любое животное
} catch (error) {
  console.log((error as Error).message);
}
```

</CodeExample>

Флаг `strictFunctionTypes` (входит в `strict`) делает **свойства функционального типа** контравариантными, но намеренно оставляет параметры **методов** **бивариантными**: их проверяют в обе стороны, поэтому более узкий параметр проскальзывает. Зачем оставлять известную дыру? Из-за массивов. В `Array<T>` метод `push(...items: T[])` объявлен именно как метод; если бы методы проверялись строго, `Dog[]` перестал бы подходить вместо `Animal[]`, и сломалась бы гора существующего кода.

В своих интерфейсах вы можете включить надёжную проверку, записывая колбэки как **свойства**:

```ts
interface Shelter {
  admit: (animal: Animal) => void; // синтаксис свойства
}

const dogsOnly: Shelter = {
  admit(dog: Dog) {
    console.log(`${dog.name} говорит ${dog.bark()}`);
  },
};
// ❌ Error: Type '(dog: Dog) => void' is not assignable to type '(animal: Animal) => void'.
```

<Callout type="tip" title="Сделайте это правилом линтера">

Используйте синтаксис свойства для колбэков и обработчиков в интерфейсах, которые проектируете сами (`onChange: (value: T) => void`), и пусть за этим следит линтер: правило `method-signature-style` из typescript-eslint с опцией `"property"` само перепишет сигнатуры методов. С классами история другая: их методы по-прежнему сравниваются бивариантно — ещё одна причина передавать обычные функции, а не объекты с методами.

</Callout>

## Аннотации вариантности: `in` и `out`

Обычно TypeScript **вычисляет** вариантность дженерик-типа по его структуре. Но начиная с TypeScript 4.7 её можно и **объявить** у параметра типа: `out T` — ковариантность (T только выходит наружу), `in T` — контравариантность (T только входит), `in out T` — инвариантность:

```ts
interface Producer<out T> {
  get: () => T;
}
interface Consumer<in T> {
  accept: (value: T) => void;
}
interface Cell<in out T> {
  get(): T;
  set(value: T): void;
}

declare const dogCell: Cell<Dog>;
const animalCell: Cell<Animal> = dogCell;
// ❌ Error: Type 'Cell<Dog>' is not assignable to type 'Cell<Animal>'.
```

Аннотации **проверяются** по структуре, так что неверная аннотация — это ошибка, а не враньё:

```ts
interface Wrong<out T> {
// ❌ Error: Type 'Wrong<sub-T>' is not assignable to type 'Wrong<super-T>' as implied by variance annotation.
  accept: (value: T) => void;
}
```

Обратите внимание на `Cell`: из-за одних только методов он был бы бивариантным (и `Cell<Dog>` подходил бы вместо `Cell<Animal>`), а `in out` делает его по-настоящему инвариантным. Когда аннотации стоят того?

- Чтобы **задокументировать намерение** в публичном дженерик-типе, который будут читать люди: `Consumer<in T>` говорит многое всего двумя буквами.
- Чтобы **исправить** бивариантность методов в типе, который принадлежит вам, как в `Cell`.
- Ради **производительности и точности** на больших рекурсивных типах, где вычисление вариантности идёт медленно или сдаётся. Команда TypeScript добавила аннотации отчасти именно поэтому.

Не расставляйте их повсюду: для обычных типов вычисленная вариантность верна, а аннотация — ещё одна вещь, которую надо держать в согласии с кодом.

## Как TypeScript выводит аргументы типа

Когда вы вызываете `pickOne(a, b)` без `<T>`, TypeScript должен сам вычислить `T`. Каждое место, где `T` встречается в типе параметра, — это **точка вывода** (inference site), и каждый аргумент в ней даёт **кандидата** (candidate). Затем TypeScript объединяет кандидатов:

```ts
function pickOne<T>(a: T, b: T): T {
  return Math.random() < 0.5 ? a : b;
}

const n = pickOne(1, 2); // T — это 1 | 2: кандидаты одного вида объединены
declare const name: string;
declare const age: number;
pickOne(name, age);
// ❌ Error: Argument of type 'number' is not assignable to parameter of type 'string'.
```

Совместимые кандидаты (два числовых литерала) объединяются, несвязанные — нет. TypeScript выбирает одного (здесь первого), а остальные помечает как ошибки. Сам он никогда не придумает `string | number`; если вам нужно именно это, напишите `pickOne<string | number>(name, age)`. Колбэки — особый случай: если аргумент — функция, параметры которой без аннотаций, TypeScript сначала выводит тип из **других** аргументов, а затем по результату типизирует параметры колбэка. Поэтому `items.map((item) => ...)` знает, что такое `item`.

В большинстве случаев это именно то, что нужно. Но иногда точка вывода — та, из которой вы **не** хотите, чтобы TypeScript что-то узнавал.

### `NoInfer`: «проверь, но не делай выводов»

Светофор принимает список цветов и начальный цвет. Начальный цвет должен быть **одним из** цветов, но он тоже точка вывода, поэтому опечатка превращается в новый цвет:

```ts
function createLight<C extends string>(colours: C[], initial: C) {
  // ...
}

createLight(["red", "amber", "green"], "blue"); // никакой ошибки!
// C — это "red" | "amber" | "green" | "blue"
```

Если обернуть параметр в **`NoInfer<C>`** (TypeScript 5.4), эта точка вывода исчезнет. `C` выводится только из `colours`, а `initial` лишь **проверяется** на соответствие:

<CodeExample output={`amber
red`}>

```ts
function createLight<C extends string>(
  colours: C[],
  initial: NoInfer<C>,
) {
  let current = initial;
  return {
    show: () => current,
    next() {
      const i = colours.indexOf(current);
      current = colours[(i + 1) % colours.length];
    },
  };
}

const light = createLight(["red", "amber", "green"], "red");
light.next();
console.log(light.show());
light.next();
light.next();
console.log(light.show());
```

</CodeExample>

```ts
createLight(["red", "amber", "green"], "blue");
// ❌ Error: Argument of type '"blue"' is not assignable to parameter of type '"red" | "amber" | "green"'.
```

Берите `NoInfer` всякий раз, когда один аргумент **задаёт** набор значений, а другой должен **выбирать из** него: значение по умолчанию, начальное состояние, запасной маршрут. До версии 5.4 того же эффекта добивались вторым параметром типа (`<C extends string, D extends C>`).

### `const`-параметры типа: сохраняем литералы

Обратная проблема: при выводе TypeScript **расширяет** литералы, так что `["/", "/courses"]` становится `string[]`, и любая строка оказывается допустимым маршрутом. Вызывающий код мог бы написать `as const`, но о нём забывают. **`const`-параметр типа** (TypeScript 5.0) просит узкий тип за вызывающего:

<CodeExample output={`https://panda.dev/courses
[ '/', '/courses', '/pricing' ]`}>

```ts
function defineRoutes<const T extends readonly string[]>(paths: T) {
  return {
    paths,
    link: (path: T[number]) => `https://panda.dev${path}`,
  };
}

const routes = defineRoutes(["/", "/courses", "/pricing"]);
console.log(routes.link("/courses"));
console.log(routes.paths);
```

</CodeExample>

```ts
routes.link("/cources");
// ❌ Error: Argument of type '"/cources"' is not assignable to parameter of type '"/" | "/courses" | "/pricing"'.
```

Есть одна тонкость: `const` влияет только на литералы, **написанные прямо в вызове**. Если передать переменную, объявленную как `const list = ["/", "/courses"]`, она уже имеет тип `string[]` ещё до того, как функция её увидит.

## `satisfies`, аннотация и `as const`

Вы уже встречали `satisfies` для тестовых данных в уроке [Внедрение зависимостей и фейки](/learn/typescript/dependency-injection-and-fakes). Теперь видно, что он на самом деле делает с выводом типов. Есть три способа задать тип объектному литералу, и они не взаимозаменяемы:

<CodeExample output={`1500
5
[ 'free', 'team' ]`}>

```ts
interface Plan {
  priceCents: number;
  seats: number | "unlimited";
}

// 1. Аннотация: проверено, но подробности забыты
const annotated: Record<string, Plan> = {
  free: { priceCents: 0, seats: 1 },
  team: { priceCents: 1500, seats: "unlimited" },
};

// 2. satisfies: проверено, и подробности сохранены
const plans = {
  free: { priceCents: 0, seats: 1 },
  team: { priceCents: 1500, seats: "unlimited" },
} satisfies Record<string, Plan>;

type PlanName = keyof typeof plans; // "free" | "team"

function upgradeCost(from: PlanName, to: PlanName): number {
  return plans[to].priceCents - plans[from].priceCents;
}

console.log(upgradeCost("free", "team"));
console.log(plans.free.seats + 4); // здесь seats — это number
console.log(Object.keys(annotated));
```

</CodeExample>

С аннотацией побеждает **объявленный** тип. TypeScript проверяет литерал на соответствие `Record<string, Plan>`, а всё остальное забывает. Ключами теперь может быть «любая строка», так что опечатка компилируется и падает во время выполнения, а `seats` снова `number | "unlimited"` — даже там, где вы написали `1`:

```ts
annotated.fre.priceCents; // компилируется! (и падает при запуске)
annotated.free.seats + 4;
// ❌ Error: Operator '+' cannot be applied to types 'string | number' and 'number'.
```

С `satisfies` побеждает **выведенный** тип, а проверка всё равно выполняется:

```ts
plans.fre;
// ❌ Error: Property 'fre' does not exist on type '{ free: { priceCents: number; seats: number; }; team: { priceCents: number; seats: "unlimited"; }; }'. Did you mean 'free'?
const broken = {
  free: { priceCents: 0, seat: 1 },
} satisfies Record<string, Plan>;
// ❌ Error: Object literal may only specify known properties, but 'seat' does not exist in type 'Plan'. Did you mean to write 'seats'?
```

`as const` — третий инструмент: он **ничего не** проверяет, но делает всё `readonly` и сохраняет каждый литерал (`priceCents: 1500`, а не `number`). Сочетайте их как `as const satisfies Record<string, Plan>` — получится таблица поиска, которая проверена, точна и заморожена на уровне типов.

| Что вы пишете | Проверяется? | Какой тип получаете |
| --- | --- | --- |
| `const x: T = ...` | ✅ | `T` (подробности потеряны) |
| `const x = ... satisfies T` | ✅ | выведенный тип (подробности сохранены) |
| `const x = ... as const` | ❌ | литералы только для чтения |
| `as const satisfies T` | ✅ | литералы только для чтения |

Хорошее правило по умолчанию: **аннотируйте** параметры функций, возвращаемые типы и всё публичное (объявленный тип — это контракт), а **`satisfies`** используйте для объектов конфигурации и таблиц поиска, где самое полезное — именно точные ключи.

interface SizeInfo {
  label: string;
  chestCm: number;
}

const sizes = {
  s: { label: "Small", chestCm: 90 },
  m: { label: "Medium", chestCm: 100 },
  l: { label: "Large", chestCm: 110 },
} satisfies Record<string, SizeInfo>;
type Size = keyof typeof sizes;

// Синтаксис свойства: параметры проверяются контравариантно
// (`in T` документирует, что Listener только потребляет T)
interface Listener<in T> {
  onChange: (value: T) => void;
}

interface Select<T extends string> {
  readonly value: T;
  choose(option: string): boolean;
  subscribe(listener: Listener<T>): () => void;
}

function createSelect<T extends string>(
  options: readonly T[],
  initial: NoInfer<T>,
): Select<T> {
  let value = initial;
  const listeners = new Set<Listener<T>>();
  // массивы только для чтения ковариантны:
  // расширить до string безопасно
  const known: readonly string[] = options;
  const isOption = (option: string): option is T =>
    known.includes(option);

  return {
    get value() {
      return value;
    },
    choose(option) {
      if (!isOption(option)) return false;
      if (option !== value) {
        value = option;
        for (const listener of listeners) listener.onChange(value);
      }
      return true;
    },
    subscribe(listener) {
      listeners.add(listener);
      return () => listeners.delete(listener);
    },
  };
}

function sortLabels(labels: readonly string[]): string[] {
  return [...labels].sort();
}

  const _any: Listener<Size> = smallOnly;
  const fixedOrder = ["b", "a"] as const;
  const _sorted: string[] = sortLabels(fixedOrder);
}

## Итоги

- Совместимость типов **структурная**: лишние свойства допустимы, кроме **свежего объектного литерала** (проверка лишних свойств) и **слабых типов**, у которых все свойства необязательные. `{}` означает «что угодно, кроме `null`/`undefined`».
- **Вариантность** описывает, как совместимость контейнера следует за совместимостью содержимого: чтение **ковариантно**, запись **контравариантна**, и то и другое — **инвариантно**.
- Изменяемые **массивы ковариантны**, и это ненадёжно; если вы только читаете, принимайте `readonly`-массивы.
- **Параметры функций контравариантны** при `strictFunctionTypes`, но **параметры методов бивариантны**. Записывайте колбэки в интерфейсах синтаксисом свойства (и проверяйте это линтером).
- **Аннотации `in` / `out`** объявляют вариантность; они проверяются компилятором, документируют намерение, могут исправить бивариантность методов и помогают на больших рекурсивных типах.
- TypeScript выводит аргументы типа из **точек вывода**. `NoInfer<T>` убирает точку вывода (значения по умолчанию, начальные значения), а **`const`-параметр типа** сохраняет литералы узкими.
- **Аннотация** — побеждает объявленный тип; **`satisfies`** — проверено, и побеждает выведенный тип; **`as const`** — литералы только для чтения, без проверки; `as const satisfies` даёт и то и другое.
