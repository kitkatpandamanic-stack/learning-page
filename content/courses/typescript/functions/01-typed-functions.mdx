Functions are where types really start to pay off. Once you tell TypeScript what a function **takes** and what it **gives back**, it checks every single call for you, so a wrong argument is caught before the code even runs.

## Typing parameters

Add a type after each parameter name with a colon, exactly like you do for variables:

<CodeExample output={`Hi, Mei!
Hi, Mei!`}>

```ts
function greet(name: string, times: number) {
  for (let i = 0; i < times; i++) {
    console.log(`Hi, ${name}!`);
  }
}

greet("Mei", 2);
```

</CodeExample>

Now TypeScript knows that `name` is a string and `times` is a number. Pass the wrong kind of value and you get an error straight away:

```ts
greet("Mei", "2");
// ❌ Error: Argument of type 'string' is not assignable to parameter of type 'number'.
```

## Why you must annotate parameters

TypeScript is great at guessing (**inferring**) types, but it can't guess a parameter's type: the function could be called with anything. In strict mode, leaving a parameter without a type is an error:

```ts
function double(n) {
  // ❌ Error: Parameter 'n' implicitly has an 'any' type.
  return n * 2;
}
```

If this were allowed, `n` would silently become `any` and TypeScript would stop checking it. That's why the rule is simple: **always give your parameters a type**.

<CodeExample output="14">

```ts
function double(n: number) {
  return n * 2;
}

console.log(double(7));
```

</CodeExample>

## Return types

You can also say what the function **returns**. The return type goes after the closing bracket of the parameter list:

<CodeExample output={`12
5`}>

```ts
function area(width: number, height: number): number {
  return width * height;
}

const room = area(3, 4);
console.log(room);
console.log(area(2.5, 2));
```

</CodeExample>

The return type is a promise: "this function always gives back a number". If you break the promise, TypeScript tells you:

```ts
function area(width: number, height: number): number {
  return `${width * height} m²`;
  // ❌ Error: Type 'string' is not assignable to type 'number'.
}
```

## Inferred return types

You don't _have_ to write the return type. TypeScript looks at your `return` statements and works it out:

<CodeExample output={`5
number
pass`}>

```ts
function add(a: number, b: number) {
  return a + b; // inferred return type: number
}

function grade(score: number) {
  if (score >= 50) {
    return "pass";
  }
  return "fail";
}

const total = add(2, 3); // total is a number
console.log(total);
console.log(typeof total);
console.log(grade(72)); // type: "pass" | "fail"
```

</CodeExample>

Notice that `grade` gets the literal union `"pass" | "fail"`, which is more precise than plain `string`.

<Callout type="tip" title="When to write the return type">

**Parameters:** always. **Return types:** optional. Many teams still write them on important functions, because it documents the function and catches mistakes _inside_ it, like forgetting to return in one branch.

</Callout>

## `void`: functions that return nothing

Some functions do a job (like printing) but don't give anything back. Their return type is **`void`**:

<CodeExample output={`Mei scored 42 points
Sam scored 7 points
undefined`}>

```ts
function logScore(player: string, score: number): void {
  console.log(`${player} scored ${score} points`);
}

logScore("Mei", 42);
const result = logScore("Sam", 7);
console.log(result);
```

</CodeExample>

At runtime a `void` function gives back `undefined`, but the type says "don't use this result". Returning a value by accident is caught:

```ts
function logScore(player: string, score: number): void {
  return score;
  // ❌ Error: Type 'number' is not assignable to type 'void'.
}
```

<Callout type="note">

A function with no `return` and no annotation is inferred as `void` automatically, so `function sayHi() { console.log("Hi"); }` already has the return type `void`.

</Callout>

The starter code has **type errors**: the parameters have no types. Add the types, then finish `ticketPrice(age)` so it returns `5` for children under 12, `7` for people aged 65 and over, and `10` for everyone else.

<Hint>

Write `age: number` and `name: string`. For the price, use `if (age < 12)` first, then `if (age >= 65)`, and finally `return 10`. Adding `: number` after `ticketPrice(age: number)` makes TypeScript check every branch returns a number.

<Solution>

```ts
function ticketPrice(age: number): number {
  if (age < 12) {
    return 5;
  }
  if (age >= 65) {
    return 7;
  }
  return 10;
}

function describeTicket(name: string, age: number): string {
  return name + " pays " + ticketPrice(age);
}

console.log(describeTicket("Mei", 9)); // Mei pays 5
console.log(describeTicket("Sam", 30)); // Sam pays 10
```

</Solution>

## Recap

- Type parameters with `name: type`. Strict mode makes untyped parameters an error (implicit `any`).
- Write a return type after the brackets: `function area(w: number, h: number): number`.
- If you leave the return type out, TypeScript infers it from your `return` statements.
- `void` means "returns nothing useful", for functions that only do a job like printing.
