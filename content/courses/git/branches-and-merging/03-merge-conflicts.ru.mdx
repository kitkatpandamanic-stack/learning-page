Чаще всего слияние просто срабатывает. Но рано или поздно вы увидите вот это: `CONFLICT (content): Merge conflict in hours.txt`. В первый раз выглядит страшно. На самом деле ничего не сломалось и ничего не пропало: Git просто задаёт вопрос, на который не может ответить сам. ⚔️

В этом уроке вы узнаете, когда и почему так бывает, как читать то, что показывает Git, как разрешить конфликт и закончить слияние, и как отступить, если разбираться прямо сейчас не хочется.

## Репозиторий для примеров

Примеры начинаются в `cafe`, на `main`. В `hours.txt` одна строка, `Открыто с 9 до 17`. А потом эту же строку поменяли двое:

```bash
git switch -c weekend
echo "Открыто с 10 до 16" > hours.txt
git add hours.txt
git commit -m "Открываться позже в выходные"

git switch main
echo "Открыто с 8 до 18" > hours.txt
git add hours.txt
git commit -m "Работать дольше"
```

Мэй, которая помогает в кафе, сделала ветку `weekend` для часов в выходные. А Панда тем временем поменяла обычные часы на `main`. На картинке две дорожки, как в примере с коммитом слияния из прошлого урока:

## Откуда берутся конфликты

Когда ушли вперёд обе ветки, Git объединяет их изменения **построчно**. Изменения в разных файлах объединяются легко. Изменения в **разных строках одного файла** — тоже. Здесь одна ветка поменяла первую строку меню, а другая — последнюю, и слияние (в этом примере оно уже сделано) сохранило обе правки:

<CodeExample setup={`mkdir cafe
cd cafe
git init

echo "Мятный чай" >> menu.txt
echo "Шоколадный торт" >> menu.txt
git add menu.txt
git commit -m "Начать меню"
git switch -c cakes
echo "Зелёный чай" > menu.txt
echo "Чёрный чай" >> menu.txt
echo "Мятный чай" >> menu.txt
echo "Морковный торт" >> menu.txt
git commit -am "Заменить на морковный торт"
git switch main
echo "Жасминовый чай" > menu.txt
echo "Чёрный чай" >> menu.txt
echo "Мятный чай" >> menu.txt

Чёрный чай

```bash
cat menu.txt
```

</CodeExample>

А в нашем `cafe` обе ветки поменяли **одну и ту же строку** `hours.txt`, причём по-разному. Кафе открыто с 8 до 18 или с 10 до 16? А может, и так и так, в разные дни? Git не может знать, что вы имели в виду, поэтому останавливается и спрашивает. Это и есть **конфликт слияния** (merge conflict).

## Конфликт

Панда на `main` вливает ветку Мэй:

<CodeExample setup={`mkdir cafe
cd cafe
git init
echo "Зелёный чай" > menu.txt
git add menu.txt
git commit -m "Начать меню"
echo "Открыто с 9 до 17" > hours.txt
git add hours.txt
git commit -m "Добавить часы работы"
git switch -c weekend
echo "Открыто с 10 до 16" > hours.txt
git add hours.txt
git commit -m "Открываться позже в выходные"
git switch main
echo "Открыто с 8 до 18" > hours.txt
git add hours.txt
git commit -m "Работать дольше"`} output={`Auto-merging hours.txt
CONFLICT (content): Merge conflict in hours.txt
Automatic merge failed; fix conflicts and then commit the result.`}>

```bash
git merge weekend
```

</CodeExample>

- **`Auto-merging hours.txt`** («автослияние hours.txt»): Git попытался объединить две версии файла.
- **`CONFLICT (content)`**: не получилось, потому что с обеих сторон поменялись одни и те же строки. Если в слиянии несколько файлов, строка `CONFLICT` будет для каждого файла, где случилось столкновение; остальные слились нормально.
- **`Automatic merge failed; fix conflicts and then commit the result.`** («автоматическое слияние не удалось; исправьте конфликты и закоммитьте результат») — это ваш список дел: исправить файлы, потом закоммитить.

Теперь слияние **в процессе**. Git остановился на полпути и ждёт вас. Вы ничего не потеряли: `main` по-прежнему указывает на «Работать дольше», а `weekend` не тронута.

## Читаем git status во время слияния

Если не понимаете, что происходит, спросите `git status`:

<CodeExample setup={`mkdir cafe
cd cafe
git init
echo "Зелёный чай" > menu.txt
git add menu.txt
git commit -m "Начать меню"
echo "Открыто с 9 до 17" > hours.txt
git add hours.txt
git commit -m "Добавить часы работы"
git switch -c weekend
echo "Открыто с 10 до 16" > hours.txt
git add hours.txt
git commit -m "Открываться позже в выходные"
git switch main
echo "Открыто с 8 до 18" > hours.txt
git add hours.txt
git commit -m "Работать дольше"
git merge weekend`} output={`On branch main
You have unmerged paths.
  (fix conflicts and run "git commit")
  (use "git merge --abort" to abort the merge)

Unmerged paths:
  (use "git add <file>..." to mark resolution)
	both modified:   hours.txt

no changes added to commit (use "git add" and/or "git commit -a")`}>

```bash
git status
```

</CodeExample>

- **`You have unmerged paths.`** («у вас есть неслитые пути»): вы посреди слияния с конфликтами. Две подсказки ниже — два выхода: исправить и закоммитить или `git merge --abort`.
- **`Unmerged paths:`** перечисляет файлы с конфликтами. **`both modified`** («изменён с обеих сторон») значит, что файл поменяли обе ветки.
- **`(use "git add <file>..." to mark resolution)`**: когда файл исправлен, `git add` сообщает об этом Git.

Если другая ветка поменяла ещё и файлы, которые слились без проблем, `git status` перечислит их в разделе `Changes to be committed:`. Git уже добавил их в индекс, и они войдут в коммит слияния вместе с вашим исправлением.

В `git status -s` конфликтный файл выглядит как **`UU hours.txt`** (unmerged, «не слит» с обеих сторон).

## Маркеры конфликта

Git записал в `hours.txt` **обе** версии и обрамил их маркерами:

<CodeExample setup={`mkdir cafe
cd cafe
git init
echo "Зелёный чай" > menu.txt
git add menu.txt
git commit -m "Начать меню"
echo "Открыто с 9 до 17" > hours.txt
git add hours.txt
git commit -m "Добавить часы работы"
git switch -c weekend
echo "Открыто с 10 до 16" > hours.txt
git add hours.txt
git commit -m "Открываться позже в выходные"
git switch main
echo "Открыто с 8 до 18" > hours.txt
git add hours.txt
git commit -m "Работать дольше"
git merge weekend`} output={`<<<<<<< HEAD
Открыто с 8 до 18
=======
Открыто с 10 до 16
>>>>>>> weekend`}>

```bash
cat hours.txt
```

</CodeExample>

- **`<<<<<<< HEAD`** начинает конфликт. Под ним — **ваша** версия: ветки, на которой вы стоите, `main` (HEAD).
- **`=======`** разделяет две версии.
- Под ним — **их** версия, из ветки, которую вы вливаете, вплоть до **`>>>>>>> weekend`**: этот маркер заканчивает конфликт и называет ветку.

Маркеры появляются только вокруг строк, которые столкнулись. В файле побольше всё остальное уже слито. Вот меню подлиннее, где одну строку поменяли обе ветки: Панда на `main` заменила чёрный чай на эрл грей, а ветка `prices` добавила к чёрному чаю цену:

<CodeExample setup={`mkdir cafe
cd cafe
git init
echo "Зелёный чай" > menu.txt
echo "Чёрный чай" >> menu.txt
echo "Мятный чай" >> menu.txt
echo "Лимонный тарт" >> menu.txt
git add menu.txt
git commit -m "Начать меню"
git switch -c prices
echo "Зелёный чай" > menu.txt
echo "Чёрный чай — 3 монеты" >> menu.txt
echo "Мятный чай" >> menu.txt
echo "Лимонный тарт" >> menu.txt
git commit -am "Указать цену чёрного чая"
git switch main
echo "Зелёный чай" > menu.txt
echo "Эрл грей" >> menu.txt
echo "Мятный чай" >> menu.txt
echo "Лимонный тарт" >> menu.txt
git commit -am "Заменить чёрный чай на эрл грей"`} output={`Auto-merging menu.txt
CONFLICT (content): Merge conflict in menu.txt
Automatic merge failed; fix conflicts and then commit the result.
Зелёный чай
<<<<<<< HEAD
Эрл грей
=======
Чёрный чай — 3 монеты
>>>>>>> prices
Мятный чай
Лимонный тарт`}>

```bash
git merge prices
cat menu.txt
```

</CodeExample>

`Зелёный чай`, `Мятный чай` и `Лимонный тарт` стоят вне маркеров: о них никто не спорил.

## Разрешаем конфликт

**Разрешить** конфликт — значит решить, что должно быть в файле, и записать ровно это, **не оставив ни одного маркера**. Можно оставить свою версию, их версию или объединить обе. Решать вам, а часто — вам вместе с автором другой стороны.

Панда и Мэй договорились: в будни с 8 до 18, в выходные с 10 до 16. Редактора в этом терминале нет, поэтому запишите файл целиком заново через `echo` и `>`. Дальше слияние заканчивают три шага:

1. **Запишите** файл таким, каким он должен быть.
2. **`git add`** — отметьте конфликт как разрешённый.
3. **`git commit`** — создайте коммит слияния.

<CodeExample setup={`mkdir cafe
cd cafe
git init
echo "Зелёный чай" > menu.txt
git add menu.txt
git commit -m "Начать меню"
echo "Открыто с 9 до 17" > hours.txt
git add hours.txt
git commit -m "Добавить часы работы"
git switch -c weekend
echo "Открыто с 10 до 16" > hours.txt
git add hours.txt
git commit -m "Открываться позже в выходные"
git switch main
echo "Открыто с 8 до 18" > hours.txt
git add hours.txt
git commit -m "Работать дольше"
git merge weekend`} output={`Открыто с 8 до 18, в выходные с 10 до 16
On branch main
All conflicts fixed but you are still merging.
  (use "git commit" to conclude merge)

Changes to be committed:
	modified:   hours.txt

[main 39d067a] Слить часы выходных
39d067a (HEAD -> main) Слить часы выходных
a543134 Работать дольше
b85a0e2 (weekend) Открываться позже в выходные
bfa1c10 Добавить часы работы
f1707e2 Начать меню`}>

```bash
echo "Открыто с 8 до 18, в выходные с 10 до 16" > hours.txt
cat hours.txt
git add hours.txt
git status
git commit -m "Слить часы выходных"
git log --oneline
```

</CodeExample>

- После `git add` команда `git status` пишет `All conflicts fixed but you are still merging.` («все конфликты исправлены, но слияние ещё идёт»). Слияние не закончено, пока вы не закоммитите.
- Получился обычный **коммит слияния** с двумя родителями, как в прошлом уроке. Как и любой коммит слияния, он не выводит список изменённых файлов.
- Если попробовать закоммитить, **пока** не все конфликтные файлы исправлены и добавлены, Git остановится с `error: Committing is not possible because you have unmerged files.`
- Вместо `git commit -m "…"` слияние можно закончить и командой **`git merge --continue`**. Она создаёт коммит слияния с сообщением, которое Git подготовил заранее, — `Merge branch 'weekend'`. (На вашем компьютере она сначала откроет редактор с этим сообщением.)

Файл из нескольких строк пишите так же, как на уровне 0: первую строку через `>`, остальные через `>>`. Или возьмите **`printf`**: он пишет текст, как `echo`, но `\n` внутри кавычек начинает новую строку. `printf "Зелёный чай\nЭрл грей\n" > menu.txt` записывает две строки за раз.

<Callout type="tip" title="Разрешение конфликтов на вашем компьютере">

На своём компьютере откройте файл в редакторе, удалите строки с маркерами и поправьте текст. Потом `git add` и `git commit`, как здесь. Просто `git commit` без `-m` откроет редактор с готовым сообщением `Merge branch 'weekend'`: сохраните и закройте его, чтобы закончить.

</Callout>

## Не коммитьте маркеры

Здесь есть одна ловушка. `git add` отмечает файл как разрешённый, **что бы в нём ни было**. Если добавить файл, где ещё остались маркеры, Git вам поверит, и следующий коммит сохранит в истории `<<<<<<< HEAD` и всё остальное. Поэтому проверяйте перед `git add`. Выведите файл через `cat` или поручите поиск маркеров `grep` (из модуля «Конвейеры и текст»):

<CodeExample setup={`mkdir cafe
cd cafe
git init
echo "Зелёный чай" > menu.txt
git add menu.txt
git commit -m "Начать меню"
echo "Открыто с 9 до 17" > hours.txt
git add hours.txt
git commit -m "Добавить часы работы"
git switch -c weekend
echo "Открыто с 10 до 16" > hours.txt
git add hours.txt
git commit -m "Открываться позже в выходные"
git switch main
echo "Открыто с 8 до 18" > hours.txt
git add hours.txt
git commit -m "Работать дольше"
git merge weekend`} output={`1:<<<<<<< HEAD`}>

```bash
grep -n "<<<<<<<" hours.txt
```

</CodeExample>

Совпадение значит, что файл ещё не готов. Когда `grep` ничего не выводит, маркеров больше нет.

## Передумали: git merge --abort

Бывает, что конфликт сейчас не вам решать: сначала надо спросить Мэй, или рабочий день уже кончился. **`git merge --abort`** отменяет слияние и возвращает всё как было до `git merge`:

<CodeExample setup={`mkdir cafe
cd cafe
git init
echo "Зелёный чай" > menu.txt
git add menu.txt
git commit -m "Начать меню"
echo "Открыто с 9 до 17" > hours.txt
git add hours.txt
git commit -m "Добавить часы работы"
git switch -c weekend
echo "Открыто с 10 до 16" > hours.txt
git add hours.txt
git commit -m "Открываться позже в выходные"
git switch main
echo "Открыто с 8 до 18" > hours.txt
git add hours.txt
git commit -m "Работать дольше"
git merge weekend`} output={`On branch main
nothing to commit, working tree clean
Открыто с 8 до 18`}>

```bash
git merge --abort
git status
cat hours.txt
```

</CodeExample>

Маркеров нет, в `hours.txt` снова версия `main`, и коммита слияния не появилось. Коммит на `weekend` никуда не делся, так что `git merge weekend` можно запустить снова, когда будете готовы. Если никакого слияния не идёт, `--abort` ответит `fatal: There is no merge to abort (MERGE_HEAD missing).`

Это ещё одна причина **коммитить перед слиянием**: `--abort` возвращает файлы к последнему коммиту, и документация Git предупреждает, что незакоммиченные изменения, сделанные до слияния, не всегда удаётся восстановить.

<Exercise

  language="shell"
  setup={`mkdir cafe

## Как избегать конфликтов

Конфликты — это нормально, и разрешить их можно всегда. Но маленькие разрешать куда проще, чем большие, и тут помогают несколько привычек:

- **Сливайте маленькими порциями и часто.** Ветка, которая живёт полдня, затрагивает пару строк. Ветка, которая живёт месяц, затрагивает всё — как и ветки всех остальных.
- **Одна задача — одна ветка.** Ветка `weekend-hours`, которая меняет только часы, вряд ли столкнётся с веткой, которая меняет только меню.
- **Вливайте `main` в свою ветку**, пока работаете над долгой задачей. На своей ветке `git merge main` забирает всё новое с `main` (коммит слияния будет называться `Merge branch 'main' into weekend`). Тогда конфликт всплывёт рано и маленьким, у вас на ветке, а не весь разом в конце.
- **Не переформатируйте то, чего не меняли.** Если заодно переставить отступы во всём файле или переставить строки, изменится каждая строка, и с вами столкнётся любая другая ветка, которая правит этот файл.
- **Договаривайтесь.** Если вы знаете, что Мэй переделывает часы, займитесь другим или подождите, пока её ветку сольют.

Вот как выглядит вливание `main` в свою ветку. Панда добавила на `main` чёрный чай, а Мэй, ещё работая на `weekend`, влила `main` в свою ветку и продолжила работу:

## Частые ошибки

- **Паника при виде `CONFLICT`.** Ничего не пропало. Прочитайте `git status`: там перечислены файлы и оба выхода.
- **Коммит с маркерами в файле.** `git add` этого не проверяет. Сначала посмотрите через `cat` или `grep -n "<<<<<<<"`.
- **Забыли `git add`** после исправления файла. `git status` так и будет писать `Unmerged paths`, пока вы его не добавите, а `git commit` откажется работать.
- **Снова запускаете `git merge`**, чтобы «доделать» слияние. Заканчивают слияние через `git commit` или `git merge --continue` (или отменяют через `git merge --abort`).
- **Бросили слияние на полпути** и взялись за другую работу. Сначала закончите или отмените его. Посреди слияния Git даже не даст переключить ветку: `fatal: cannot switch branch while merging`.

## Итоги

- **Конфликт слияния** случается, когда обе ветки по-разному поменяли **одни и те же строки**. Разные строки и разные файлы сливаются сами.
- `CONFLICT (content): Merge conflict in файл` значит, что слияние остановилось на полпути. Ничего не пропало.
- **`git status`** пишет `You have unmerged paths` и помечает каждый файл как `both modified` (`UU` в `git status -s`).
- В файле от **`<<<<<<< HEAD`** до **`=======`** — версия вашей ветки; от **`=======`** до **`>>>>>>> ветка`** — вливаемая.
- Чтобы разрешить: запишите файл таким, каким он должен быть, **без маркеров**, потом **`git add`** и **`git commit`** (или **`git merge --continue`**).
- **`git merge --abort`** отменяет слияние и возвращает всё как было.
- Меньше и мельче конфликты: сливайте маленькими порциями и часто, одна задача — одна ветка, вливайте `main` в долгие ветки, не переформатируйте то, чего не меняли.
