Most merges just work. But sooner or later you'll see this: `CONFLICT (content): Merge conflict in hours.txt`. It looks scary the first time. It isn't: nothing is broken and nothing is lost. Git is simply asking you a question it can't answer on its own. ⚔️

In this lesson you'll learn when and why that happens, how to read what Git shows you, how to settle a conflict and finish the merge, and how to back out if you'd rather not deal with it now.

## The examples' repository

The examples start in `cafe`, on `main`. `hours.txt` holds one line, `Open 9 to 5`. Then two people changed that same line:

```bash
git switch -c weekend
echo "Open 10 to 4" > hours.txt
git add hours.txt
git commit -m "Open later at weekends"

git switch main
echo "Open 8 to 6" > hours.txt
git add hours.txt
git commit -m "Open longer"
```

Mei, who helps at the café, made the `weekend` branch for the weekend hours. Meanwhile Panda changed the everyday hours on `main`. The picture shows two lanes, like the merge commit example in the last lesson:

## Why conflicts happen

When both branches moved, Git combines their changes **line by line**. Changes to different files combine easily. So do changes to **different lines of the same file**. Here one branch changed the first line of a menu and the other changed the last line, and the merge (already done in this example) kept both:

<CodeExample setup={`mkdir cafe
cd cafe
git init
echo "Green tea" > menu.txt
echo "Black tea" >> menu.txt
echo "Mint tea" >> menu.txt
echo "Chocolate cake" >> menu.txt
git add menu.txt
git commit -m "Start the menu"
git switch -c cakes
echo "Green tea" > menu.txt
echo "Black tea" >> menu.txt
echo "Mint tea" >> menu.txt
echo "Carrot cake" >> menu.txt
git commit -am "Swap to carrot cake"
git switch main
echo "Jasmine tea" > menu.txt
echo "Black tea" >> menu.txt
echo "Mint tea" >> menu.txt
echo "Chocolate cake" >> menu.txt

git merge cakes -m "Merge the cakes"`} output={`Jasmine tea
Black tea
Mint tea

```bash
cat menu.txt
```

</CodeExample>

But in our `cafe`, both branches changed **the same line** of `hours.txt`, in different ways. Should the café open 8 to 6, or 10 to 4? Maybe both, on different days? Git can't know what you mean, so it stops and asks. That's a **merge conflict**.

## The conflict

Panda, on `main`, merges Mei's branch:

<CodeExample setup={`mkdir cafe
cd cafe
git init
echo "Green tea" > menu.txt
git add menu.txt
git commit -m "Start the menu"
echo "Open 9 to 5" > hours.txt
git add hours.txt
git commit -m "Add opening hours"
git switch -c weekend
echo "Open 10 to 4" > hours.txt
git add hours.txt
git commit -m "Open later at weekends"
git switch main
echo "Open 8 to 6" > hours.txt
git add hours.txt
git commit -m "Open longer"`} output={`Auto-merging hours.txt
CONFLICT (content): Merge conflict in hours.txt
Automatic merge failed; fix conflicts and then commit the result.`}>

```bash
git merge weekend
```

</CodeExample>

- **`Auto-merging hours.txt`**: Git tried to combine the two versions of the file.
- **`CONFLICT (content)`**: it couldn't, because the same lines changed on both sides. A merge with several files lists one `CONFLICT` line for each file that clashed; the others merged fine.
- **`Automatic merge failed; fix conflicts and then commit the result.`** is your to-do list: fix the files, then commit.

The merge is now **in progress**. Git has stopped halfway and is waiting for you. You haven't lost anything: `main` still points at `Open longer`, and `weekend` is untouched.

## Reading git status during a merge

When you're unsure what's going on, `git status` tells you:

<CodeExample setup={`mkdir cafe
cd cafe
git init
echo "Green tea" > menu.txt
git add menu.txt
git commit -m "Start the menu"
echo "Open 9 to 5" > hours.txt
git add hours.txt
git commit -m "Add opening hours"
git switch -c weekend
echo "Open 10 to 4" > hours.txt
git add hours.txt
git commit -m "Open later at weekends"
git switch main
echo "Open 8 to 6" > hours.txt
git add hours.txt
git commit -m "Open longer"
git merge weekend`} output={`On branch main
You have unmerged paths.
  (fix conflicts and run "git commit")
  (use "git merge --abort" to abort the merge)

Unmerged paths:
  (use "git add <file>..." to mark resolution)
	both modified:   hours.txt

no changes added to commit (use "git add" and/or "git commit -a")`}>

```bash
git status
```

</CodeExample>

- **`You have unmerged paths.`**: you're in the middle of a merge with conflicts. The two hints are your two ways out: fix and commit, or `git merge --abort`.
- **`Unmerged paths:`** lists the files with conflicts. **`both modified`** means both branches changed the file.
- **`(use "git add <file>..." to mark resolution)`**: once a file is fixed, `git add` tells Git so.

If the other branch also changed files that merged cleanly, `git status` lists them under `Changes to be committed:`. Git has already staged them, and they'll go into the merge commit with your fix.

In `git status -s` a conflicted file shows up as **`UU hours.txt`** ("unmerged" on both sides).

## Conflict markers

Git has written **both** versions into `hours.txt`, with markers around them:

<CodeExample setup={`mkdir cafe
cd cafe
git init

git commit -m "Start the menu"

echo "Open 10 to 4" > hours.txt

git switch main
echo "Open 8 to 6" > hours.txt

git merge weekend`} output={`<<<<<<< HEAD
Open 8 to 6
=======
Open 10 to 4
>>>>>>> weekend`}>

```bash
cat hours.txt
```

</CodeExample>

- **`<<<<<<< HEAD`** starts the conflict. Below it is **your** version: the branch you're on, `main` (HEAD).
- **`=======`** divides the two versions.
- Below it is **their** version, from the branch you're merging in, down to **`>>>>>>> weekend`**, which ends the conflict and names that branch.

Only the lines that clash get markers. In a bigger file, everything else is already merged. Here a longer menu had one line changed on both branches: Panda swapped black tea for Earl Grey on `main`, while a `prices` branch put a price on the black tea:

## Resolving the conflict

**Resolving** a conflict means deciding what the file should say, and then writing exactly that, **with no markers left**. You can keep your version, keep theirs, or combine them. It's your call, and often a quick chat with whoever wrote the other side.

Panda and Mei agree: open 8 to 6 on weekdays and 10 to 4 at weekends. There's no editor in this terminal, so write the whole file again with `echo` and `>`. Then three steps finish the merge:

1. **Write** the file the way it should be.
2. **`git add`** it, to mark the conflict as resolved.
3. **`git commit`**, to make the merge commit.

<CodeExample setup={`mkdir cafe
cd cafe
git init
echo "Green tea" > menu.txt
git add menu.txt
git commit -m "Start the menu"

echo "Open 10 to 4" > hours.txt
git add hours.txt
git commit -m "Open later at weekends"
git switch main
echo "Open 8 to 6" > hours.txt
git add hours.txt
git commit -m "Open longer"
git merge weekend`} output={`Open 8 to 6, at weekends 10 to 4
On branch main
All conflicts fixed but you are still merging.
  (use "git commit" to conclude merge)

Changes to be committed:
	modified:   hours.txt

[main dc5bae6] Merge the weekend hours
dc5bae6 (HEAD -> main) Merge the weekend hours
c7f5195 Open longer
1ccf96c (weekend) Open later at weekends

```bash
echo "Open 8 to 6, at weekends 10 to 4" > hours.txt
cat hours.txt
git add hours.txt
git status
git commit -m "Merge the weekend hours"
git log --oneline
```

</CodeExample>

- After `git add`, `git status` says `All conflicts fixed but you are still merging.` The merge isn't done until you commit.
- The commit is an ordinary **merge commit** with two parents, like in the last lesson. Like any merge commit, it prints no list of changed files.
- If you try to commit **before** every conflicted file is fixed and added, Git stops with `error: Committing is not possible because you have unmerged files.`
- Instead of `git commit -m "…"`, you can also finish with **`git merge --continue`**. It makes the merge commit with the message Git prepared, `Merge branch 'weekend'`. (On your computer it opens your editor with that message first.)

For a file with several lines, write the first line with `>` and add the rest with `>>`, as you did in Level 0. Or use **`printf`**, which writes text like `echo` does, but where `\n` inside the quotes starts a new line: `printf "Green tea\nEarl Grey\n" > menu.txt` writes two lines in one go.

<Callout type="tip" title="Resolving on your own computer">

On your computer, open the file in your editor, delete the marker lines and fix the text. Editors like VS Code highlight conflicts and offer buttons such as "Accept Current Change" (yours), "Accept Incoming Change" (theirs) and "Accept Both Changes". Then `git add` and `git commit` as here. Plain `git commit` with no `-m` opens your editor with the message `Merge branch 'weekend'` ready: save and close it to finish.

</Callout>

## Don't commit the markers

There's one trap. `git add` marks a file as resolved **whatever is in it**. If you `git add` a file that still has markers, Git believes you, and the next commit saves `<<<<<<< HEAD` and all the rest into your history. So check before you add. `cat` the file, or let `grep` (from Pipes & Text) look for markers:

<CodeExample setup={`mkdir cafe
cd cafe
git init
echo "Green tea" > menu.txt
git add menu.txt
git commit -m "Start the menu"
echo "Open 9 to 5" > hours.txt
git add hours.txt
git commit -m "Add opening hours"
git switch -c weekend
echo "Open 10 to 4" > hours.txt
git add hours.txt
git commit -m "Open later at weekends"
git switch main
echo "Open 8 to 6" > hours.txt
git add hours.txt
git commit -m "Open longer"
git merge weekend`} output={`1:<<<<<<< HEAD`}>

```bash
grep -n "<<<<<<<" hours.txt
```

</CodeExample>

A match means the file isn't ready yet. When `grep` prints nothing, the markers are gone.

## Changed your mind: git merge --abort

Sometimes a conflict isn't yours to settle right now: you need to ask Mei first, or it's the end of the day. **`git merge --abort`** cancels the merge and puts everything back as it was before you ran `git merge`:

<CodeExample setup={`mkdir cafe
cd cafe
git init
echo "Green tea" > menu.txt
git add menu.txt
git commit -m "Start the menu"
echo "Open 9 to 5" > hours.txt
git add hours.txt
git commit -m "Add opening hours"
git switch -c weekend
echo "Open 10 to 4" > hours.txt
git add hours.txt
git commit -m "Open later at weekends"
git switch main
echo "Open 8 to 6" > hours.txt
git add hours.txt
git commit -m "Open longer"
git merge weekend`} output={`On branch main
nothing to commit, working tree clean
Open 8 to 6`}>

```bash
git merge --abort
git status
cat hours.txt
```

</CodeExample>

The markers are gone, `hours.txt` is back to `main`'s version, and no merge commit was made. `weekend` still has its commit, so you can run `git merge weekend` again whenever you're ready. When there's no merge going on, `--abort` says `fatal: There is no merge to abort (MERGE_HEAD missing).`

This is one more reason to **commit before you merge**: `--abort` resets your files to the last commit, and Git's manual warns that uncommitted changes from before the merge can't always be brought back.

## Avoiding conflicts

Conflicts are normal, and you can always resolve them. But small ones are much easier than big ones, so a few habits help:

- **Merge small and often.** A branch that lives for an afternoon touches a few lines. A branch that lives for a month touches everything, and so does everyone else's.
- **One task per branch.** A branch called `weekend-hours` that only changes the hours is unlikely to clash with a branch that only changes the menu.
- **Bring `main` into your branch** while you work on a long task. On your branch, `git merge main` takes in what's new on `main` (the merge commit is called `Merge branch 'main' into weekend`). Any conflict shows up early and small, on your branch, instead of all at once at the end.
- **Don't reformat what you didn't change.** Re-indenting a whole file or reordering lines "while you're there" changes every line, and any other branch that edits that file will clash with you.
- **Talk to each other.** If you know Mei is reworking the hours, change something else or wait for her branch to be merged first.

Here's what bringing `main` into a branch looks like. Panda added black tea on `main`; Mei, still working on `weekend`, merged `main` into her branch and then carried on:

## Common mistakes

- **Panicking at `CONFLICT`.** Nothing is lost. Read `git status`: it lists the files and both ways out.
- **Committing with markers still in the file.** `git add` doesn't check. Look first with `cat` or `grep -n "<<<<<<<"`.
- **Forgetting `git add`** after fixing a file. `git status` keeps saying `Unmerged paths` until you add it, and `git commit` refuses.
- **Running `git merge` again** to "finish" the merge. You finish a merge with `git commit` or `git merge --continue` (or cancel it with `git merge --abort`).
- **Leaving the merge half-done** and carrying on with other work. Finish it or abort it before anything else. Git even refuses to switch branches mid-merge: `fatal: cannot switch branch while merging`.

## Recap

- A **merge conflict** happens when both branches changed **the same lines** differently. Different lines and different files merge on their own.
- `CONFLICT (content): Merge conflict in file` means the merge stopped halfway. Nothing is lost.
- **`git status`** shows `You have unmerged paths` and lists each file as `both modified` (`UU` in `git status -s`).
- In the file, **`<<<<<<< HEAD`** to **`=======`** is your branch's version; **`=======`** to **`>>>>>>> branch`** is the incoming one.
- To resolve: write the file as it should be, with **no markers**, then **`git add`** it and **`git commit`** (or **`git merge --continue`**).
- **`git merge --abort`** cancels the merge and puts everything back.
- Fewer, smaller conflicts: merge small and often, one task per branch, bring `main` into long-lived branches, don't reformat what you didn't change.
