The desserts are ready! 🍰 On the `desserts` branch Panda has a chocolate cake and a lemon tart, and now they should go on the real menu, on `main`. Joining one branch's work into another is called **merging**, and it's what makes branches useful: you build something on the side, then bring it home in one step.

In this lesson you'll merge with `git merge`, meet the two ways a merge can turn out (a **fast-forward** and a **merge commit**), and put it all together into the everyday feature-branch flow.

## The examples' repository

The examples start in `cafe` again. `main` has two commits, and `desserts` has two more on top of them:

```bash

echo "Chocolate cake" > cake.txt
git add cake.txt
git commit -m "Add chocolate cake"
echo "Lemon tart" > tart.txt

```

## git merge: bring a branch in

**`git merge name`** brings the commits of the branch `name` into **the branch you're on**. So first switch to the branch that should receive the work, then name the one to bring in:

<CodeExample setup={`mkdir cafe
cd cafe
git init
echo "Green tea" > menu.txt
git add menu.txt
git commit -m "Start the menu"
echo "Open 9 to 5" > hours.txt
git add hours.txt
git commit -m "Add opening hours"
git switch -c desserts
echo "Chocolate cake" > cake.txt
git add cake.txt
git commit -m "Add chocolate cake"
echo "Lemon tart" > tart.txt
git add tart.txt
git commit -m "Add lemon tart"`} output={`Switched to branch 'main'
Updating 316e1fa..835001f
Fast-forward
 cake.txt | 1 +
 tart.txt | 1 +
 2 files changed, 2 insertions(+)
 create mode 100644 cake.txt
 create mode 100644 tart.txt
835001f (HEAD -> main, desserts) Add lemon tart
b81b667 Add chocolate cake
316e1fa Add opening hours
17532b2 Start the menu`}>

```bash
git switch main
git merge desserts
git log --oneline
```

</CodeExample>

Read it from the top:

- **`Updating 316e1fa..835001f`**: `main` goes from its old commit to `desserts`' newest one.
- **`Fast-forward`**: how Git did it (more on this in a moment).
- Then a summary like the one `git commit` prints: which files changed, and `create mode` for the new ones. `cake.txt` and `tart.txt` are now in the folder on `main`.
- In the log, `main` and `desserts` point at the same commit. `main` has the desserts!

The direction matters. `git merge desserts` on `main` changes `main` and leaves `desserts` alone. The same command on `desserts` with `main` would do the opposite.

## Fast-forward: the label just moves

Look at the picture before the merge again: `main` was **behind** `desserts`, with no commits of its own since `desserts` started. There was nothing to join. All Git had to do was move the `main` label forward along the line, to where `desserts` is. That's a **fast-forward**, and it makes **no new commit**:

<GitGraph setup={`mkdir cafe
cd cafe

git add hours.txt
git commit -m "Add opening hours"

git add cake.txt

git merge desserts`} caption="After the fast-forward: still one straight line, and main moved up to desserts' newest commit." />

Merge the same branch again and Git has nothing to do: it says `Already up to date.`

## When both branches moved: a merge commit

Often `main` doesn't wait. While the desserts were being made, Panda also added black tea on `main`. Now each branch has a commit the other doesn't:

Moving the label can't work any more: `main` would lose the black tea. So Git makes a new commit that joins the two lines: a **merge commit**. It needs a message, and **`-m`** gives it one, just like with `git commit`:

<CodeExample setup={`mkdir cafe
cd cafe
git init
echo "Green tea" > menu.txt
git add menu.txt
git commit -m "Start the menu"
echo "Open 9 to 5" > hours.txt

git switch -c desserts
echo "Chocolate cake" > cake.txt
git add cake.txt
git commit -m "Add chocolate cake"
echo "Lemon tart" > tart.txt
git add tart.txt
git commit -m "Add lemon tart"
git switch main
echo "Black tea" >> menu.txt
git add menu.txt
git commit -m "Add black tea"`} output={`Merge made by the 'ort' strategy.
 cake.txt | 1 +
 tart.txt | 1 +
 2 files changed, 2 insertions(+)
 create mode 100644 cake.txt
 create mode 100644 tart.txt
399060e (HEAD -> main) Add the desserts
d5cfd46 Add black tea
835001f (desserts) Add lemon tart
b81b667 Add chocolate cake
316e1fa Add opening hours
17532b2 Start the menu`}>

```bash
git merge desserts -m "Add the desserts"
git log --oneline
```

</CodeExample>

- **`Merge made by the 'ort' strategy.`** means Git combined the two branches and made a merge commit. "ort" is just the name of the method Git uses to combine them; you'll see it in every merge like this.
- The summary below lists what the merge brought into `main`: the two dessert files.
- `main` now has everything: the black tea **and** the desserts.

## A commit with two parents

Every commit remembers the commit that came before it, its **parent**. A merge commit is special: it has **two parents**, one from each branch. `git log` shows them on a `Merge:` line:

<CodeExample setup={`mkdir cafe
cd cafe
git init
echo "Green tea" > menu.txt
git add menu.txt
git commit -m "Start the menu"
echo "Open 9 to 5" > hours.txt
git add hours.txt
git commit -m "Add opening hours"
git switch -c desserts
echo "Chocolate cake" > cake.txt
git add cake.txt
git commit -m "Add chocolate cake"
echo "Lemon tart" > tart.txt
git add tart.txt
git commit -m "Add lemon tart"
git switch main
echo "Black tea" >> menu.txt
git add menu.txt
git commit -m "Add black tea"
git merge desserts -m "Add the desserts"`} output={`commit 399060ed5d35719b9782f608f3dcb4f296785ee0 (HEAD -> main)
Merge: d5cfd46 835001f
Author: Panda <panda@pandadev.dev>
Date:   Mon Jan 5 09:06:00 2026 +0000

    Add the desserts`}>

```bash
git log -n 1
```

</CodeExample>

`d5cfd46` is the black tea commit (where `main` was) and `835001f` is the lemon tart (where `desserts` was). The first parent is always the branch you were on. That's how Git knows the merge contains both histories, and why `git log` on `main` now lists the dessert commits too.

<Callout type="tip" title="Merging on your own computer">

Without `-m`, `git merge` on your computer opens your text editor with a message already written, `Merge branch 'desserts'`. Save and close the editor to finish the merge. To skip the editor and keep that message, add **`--no-edit`**. The practice terminal has no editor, so here a merge without `-m` simply uses `Merge branch 'desserts'`.

</Callout>

## Always a merge commit: --no-ff

A fast-forward leaves no trace that a branch ever existed: the cake and tart commits just sit in `main`'s straight line. Some teams want every feature to show up as its own bump in the history. **`--no-ff`** ("no fast-forward") tells Git to make a merge commit even when it could fast-forward:

<CodeExample setup={`mkdir cafe
cd cafe
git init
echo "Green tea" > menu.txt
git add menu.txt
git commit -m "Start the menu"
echo "Open 9 to 5" > hours.txt
git add hours.txt
git commit -m "Add opening hours"
git switch -c desserts
echo "Chocolate cake" > cake.txt
git add cake.txt
git commit -m "Add chocolate cake"
echo "Lemon tart" > tart.txt
git add tart.txt
git commit -m "Add lemon tart"
git switch main`} output={`Merge made by the 'ort' strategy.
 cake.txt | 1 +
 tart.txt | 1 +
 2 files changed, 2 insertions(+)
 create mode 100644 cake.txt
 create mode 100644 tart.txt
a2f49c8 (HEAD -> main) Merge the desserts
835001f (desserts) Add lemon tart
b81b667 Add chocolate cake
316e1fa Add opening hours
17532b2 Start the menu`}>

```bash
git merge --no-ff -m "Merge the desserts" desserts
git log --oneline
```

</CodeExample>

<GitGraph setup={`mkdir cafe
cd cafe

git add menu.txt
git commit -m "Start the menu"
echo "Open 9 to 5" > hours.txt
git add hours.txt

Which is better? Neither. A fast-forward keeps the history a simple line; `--no-ff` keeps each feature visibly grouped, and costs an extra commit each time. Teams pick one and stick to it.

## Which branches are merged?

After a while a repository collects branches, and you forget which ones are done. **`git branch --merged`** lists the branches whose commits are all on the branch you're on already, and **`git branch --no-merged`** lists those that still have commits of their own. Here `desserts` has been merged into `main`, and `drinks` has a commit that `main` doesn't have yet:

<CodeExample setup={`mkdir cafe
cd cafe
git init
echo "Green tea" > menu.txt
git add menu.txt
git commit -m "Start the menu"
echo "Open 9 to 5" > hours.txt
git add hours.txt
git commit -m "Add opening hours"
git switch -c desserts
echo "Chocolate cake" > cake.txt
git add cake.txt
git commit -m "Add chocolate cake"
echo "Lemon tart" > tart.txt
git add tart.txt
git commit -m "Add lemon tart"
git switch main
git merge desserts
git switch -c drinks
echo "Mint tea" >> menu.txt
git add menu.txt

```bash

git branch --no-merged
```

</CodeExample>

A merged branch is safe to delete: its commits stay in `main`'s history whatever happens to the label. `git branch -d` makes the same check for you. It deletes a merged branch, and refuses one that isn't, with the `not fully merged` error you met in the last lesson.

## The feature-branch flow

Put it together and you get the way most developers work, every day, even alone on one computer:

1. Start from `main`: `git switch main`.
2. Make a branch for one task, named after it: `git switch -c opening-hours`.
3. Work and commit on it, as many commits as the task needs.
4. When it's done, go back: `git switch main`.
5. Merge it: `git merge opening-hours` (with `-m` or `--no-edit` if Git needs a message).
6. Delete it: `git branch -d opening-hours`.

`main` always holds finished work, and every unfinished idea lives on its own branch until it's ready. If an idea fails, you delete its branch with `-D`, and `main` never knew about it.

Two habits keep merges smooth:

- **Commit before you merge.** Run `git status` first: it should say `working tree clean`. Git refuses to merge when the merge would overwrite your uncommitted changes, and even when it doesn't refuse, mixing unsaved work into a merge makes it hard to undo.
- **Check the name.** `git merge dessert` (a typo) says `merge: dessert - not something we can merge`. `git branch` shows the real names.

## Recap

- **`git merge name`** brings branch `name` into **the branch you're on**. Switch to the receiving branch (usually `main`) first.
- **Fast-forward:** when your branch has no commits of its own, Git just moves its label forward. No new commit.
- **Merge commit:** when both branches moved, Git joins them with a new commit that has **two parents** (`Merge:` in `git log`). Output: `Merge made by the 'ort' strategy.`
- **`-m "message"`** names the merge commit; on your computer, without it Git opens an editor (`--no-edit` keeps the default message).
- **`--no-ff`** makes a merge commit even when a fast-forward was possible.
- **`git branch --merged`** / **`--no-merged`** show which branches are done; **`git branch -d`** deletes a merged branch.
- The **feature-branch flow:** `switch -c`, commit, `switch main`, `merge`, `branch -d`. Commit everything before you merge.
