Panda keeps the café's menu in a Git repository. Now Panda wants to try out a desserts page, but the menu on `main` works, and a half-finished idea shouldn't get in its way. Copy the whole folder to `cafe-desserts-test`? You know where that ends: `backup`, `backup-2`, `backup-final`. 🌱

Git has a better answer: a **branch**. A branch lets you work on an idea in its own line of history, while `main` stays exactly as it was. If the idea works, you bring it back into `main` (that's the next lesson). If it doesn't, you throw the branch away. In this lesson you'll make branches, move between them and see what happens to your files when you do.

## The examples' repository

The examples in this lesson start inside `cafe`, a repository with two commits on `main`:

```bash
echo "Green tea" > menu.txt
git add menu.txt
git commit -m "Start the menu"

echo "Open 9 to 5" > hours.txt
git add hours.txt
git commit -m "Add opening hours"
```

## A branch is a label on a commit

You've been on a branch all along: `main`. Every `git status` starts with `On branch main`.

A **branch** is just a **name that points at a commit**, like a sticky label. `main` points at your newest commit, `Add opening hours`. When you commit, Git makes the new commit and moves the label up to it. That's all a branch is: Git doesn't copy any files to make one. That's why making a branch is instant, even in a huge project.

Here is the `cafe` repository as a picture. You met this **Commits** box in Level 0: one dot per commit, newest at the top.

## HEAD: where you are

A repository can have many branches, but you're always on one of them. **`HEAD`** is how Git remembers which: it points at the branch you're on. That's what `(HEAD -> main)` in `git log` means: "HEAD points at main, and main points at this commit".

When you commit, the branch that HEAD points at is the one that moves. The other branches stay where they are.

## Listing branches: git branch

**`git branch`** with nothing after it lists the branches. A star marks the one you're on:

<CodeExample setup={`mkdir cafe
cd cafe
git init
echo "Green tea" > menu.txt
git add menu.txt
git commit -m "Start the menu"
echo "Open 9 to 5" > hours.txt
git add hours.txt
git commit -m "Add opening hours"`} output={`* main
* main 316e1fa Add opening hours`}>

```bash
git branch
git branch -v
```

</CodeExample>

**`git branch -v`** ("verbose") adds the commit each branch points at: its short hash and message.

## Making a branch: git branch name

**`git branch`** followed by a name makes a new branch, pointing at the commit you're on:

<CodeExample setup={`mkdir cafe
cd cafe
git init
echo "Green tea" > menu.txt
git add menu.txt
git commit -m "Start the menu"
echo "Open 9 to 5" > hours.txt
git add hours.txt
git commit -m "Add opening hours"`} output={`  desserts
* main
316e1fa (HEAD -> main, desserts) Add opening hours
17532b2 Start the menu`}>

```bash
git branch desserts
git branch
git log --oneline
```

</CodeExample>

- `git branch desserts` prints nothing. Silence means it worked.
- Now there are two labels on the same commit: `main` and `desserts`. No files were copied and no commit was made.
- The star is still on `main`. **Making a branch doesn't move you to it.** This is the most common branch mistake: you make a branch, commit, and the commit lands on `main`.

<GitGraph setup={`mkdir cafe
cd cafe
git init
echo "Green tea" > menu.txt
git add menu.txt
git commit -m "Start the menu"
echo "Open 9 to 5" > hours.txt
git add hours.txt
git commit -m "Add opening hours"
git branch desserts`} caption="Two labels on one commit. HEAD is still on main." />

Branch names can't contain spaces. Use short names with dashes, like `desserts`, `fix-typo` or `new-logo`.

## Switching: git switch

**`git switch`** followed by a branch name moves you to that branch:

<CodeExample setup={`mkdir cafe
cd cafe
git init
echo "Green tea" > menu.txt
git add menu.txt
git commit -m "Start the menu"
echo "Open 9 to 5" > hours.txt
git add hours.txt
git commit -m "Add opening hours"
git branch desserts`} output={`Switched to branch 'desserts'
* desserts
  main
316e1fa (HEAD -> desserts, main) Add opening hours
17532b2 Start the menu`}>

```bash
git switch desserts
git branch
git log --oneline
```

</CodeExample>

The star moved, and the log now says `HEAD -> desserts`: your next commit goes on `desserts`.

## What happens to your files when you switch

Here's the part that surprises everyone the first time. Watch `cake.txt`:

<CodeExample setup={`mkdir cafe
cd cafe
git init
echo "Green tea" > menu.txt
git add menu.txt
git commit -m "Start the menu"
echo "Open 9 to 5" > hours.txt
git add hours.txt
git commit -m "Add opening hours"
git branch desserts
git switch desserts
echo "Chocolate cake" > cake.txt
git add cake.txt
git commit -m "Add chocolate cake"`} output={`cake.txt  hours.txt  menu.txt
Switched to branch 'main'
hours.txt  menu.txt
b81b667 (desserts) Add chocolate cake
316e1fa (HEAD -> main) Add opening hours
17532b2 Start the menu`}>

```bash
ls
git switch main
ls
git log --oneline --all
```

</CodeExample>

- On `main`, `cake.txt` is gone from the folder! That's right: `main` doesn't have the cake yet. **When you switch, Git makes your folder look like the newest commit of that branch.**
- Nothing is lost. The cake is safe in the `desserts` commit, and `git switch desserts` brings `cake.txt` straight back.
- Plain `git log` shows only the history of where you are, so on `main` it wouldn't show the cake commit at all. **`git log --all`** shows the commits of **every** branch, each with its labels.

Now suppose Panda also commits on `main` while the desserts are still being worked on: black tea goes on the menu. The two branches have each moved on from the same commit, and the picture shows them side by side, each in its own **lane**:

<GitGraph setup={`mkdir cafe
cd cafe
git init
echo "Green tea" > menu.txt
git add menu.txt
git commit -m "Start the menu"
echo "Open 9 to 5" > hours.txt
git add hours.txt
git commit -m "Add opening hours"
git branch desserts
git switch desserts
echo "Chocolate cake" > cake.txt
git add cake.txt
git commit -m "Add chocolate cake"

git add menu.txt
git commit -m "Add black tea"`} caption="Both branches grew from Add opening hours. main has the black tea, desserts has the cake, and neither has the other's commit yet." />

On `main`, `menu.txt` has two teas and there's no `cake.txt`. On `desserts`, the menu has only green tea, but there's a cake. Each branch is its own version of the project.

## Shortcuts: git switch -c and git switch -

You'll make a branch and switch to it so often that there's a shortcut. **`git switch -c name`** ("create") does both in one go. And **`git switch -`** takes you back to the branch you were on before, like `cd -` does for folders:

<CodeExample setup={`mkdir cafe
cd cafe
git init
echo "Green tea" > menu.txt
git add menu.txt
git commit -m "Start the menu"
echo "Open 9 to 5" > hours.txt
git add hours.txt
git commit -m "Add opening hours"`} output={`Switched to a new branch 'drinks'
Switched to branch 'main'
Switched to branch 'drinks'`}>

```bash
git switch -c drinks
git switch -
git switch -
```

</CodeExample>

From now on, `git switch -c` is the usual way to start a branch.

<Callout type="tip" title="Started on main by mistake?">

It happens: you start changing files and then realise they belong on a branch. If you haven't committed yet, run `git switch -c new-branch`. Your uncommitted changes come with you onto the new branch, and you commit them there. `main` stays as it was.

</Callout>

## The older way: git checkout

`git switch` arrived in Git 2.23, in 2019. Before that, everybody switched branches with **`git checkout`**, and you'll still see it in older tutorials and in your colleagues' commands:

| Older command            | Newer command          |
| ------------------------ | ---------------------- |
| `git checkout desserts`  | `git switch desserts`  |
| `git checkout -b drinks` | `git switch -c drinks` |
| `git checkout -`         | `git switch -`         |

Both work, here and on your computer. `git switch` was added because `git checkout` does several different jobs (it can also overwrite files with an older version), and a command that only switches branches is harder to misuse. Git's own manual called `git switch` "experimental" until Git 2.51 (2025), but it's the recommended way now.

## Renaming and deleting branches

Typo in a name? **`git branch -m old new`** ("move") renames a branch. Its commits stay exactly where they were: only the label changes. If you're on the branch you want to rename, `git branch -m new` is enough.

**`git branch -d name`** deletes a branch, that is, its label:

<CodeExample setup={`mkdir cafe
cd cafe
git init
echo "Green tea" > menu.txt
git add menu.txt
git commit -m "Start the menu"
echo "Open 9 to 5" > hours.txt
git add hours.txt
git commit -m "Add opening hours"
git branch desert`} output={`  desserts
* main
Deleted branch desserts (was 316e1fa).`}>

```bash
git branch -m desert desserts
git branch
git branch -d desserts
```

</CodeExample>

That branch was safe to delete: it pointed at a commit that `main` has too. But what if a branch has commits that are on no other branch? Here `snacks` has one commit that `main` doesn't:

<CodeExample setup={`mkdir cafe
cd cafe
git init
echo "Green tea" > menu.txt
git add menu.txt
git commit -m "Start the menu"
echo "Open 9 to 5" > hours.txt
git add hours.txt
git commit -m "Add opening hours"
git switch -c snacks
echo "Crisps" > snacks.txt
git add snacks.txt
git commit -m "Add crisps"
git switch main`} output={`error: the branch 'snacks' is not fully merged
hint: If you are sure you want to delete it, run 'git branch -D snacks'
hint: Disable this message with "git config set advice.forceDeleteBranch false"
Deleted branch snacks (was b1cea28).`}>

```bash
git branch -d snacks
git branch -D snacks
```

</CodeExample>

- **`-d`** is the safe delete. It refuses when the branch has commits that aren't on the branch you're on yet ("not fully merged"), because deleting the label would leave those commits with no name to find them by.
- **`-D`** deletes anyway. Use it only for an idea you really want to throw away, like this one.
- You can't delete the branch you're on. Switch to another branch first.

## "Your local changes would be overwritten"

What if you have changes you haven't committed yet, and you switch? There are two cases.

If the other branch has the **same** version of the changed file, Git simply switches, and your uncommitted change comes along. It doesn't belong to any branch yet: it lands on whichever branch you commit it on.

If the other branch has a **different** version of that file, Git would have to overwrite your change to switch. It refuses instead. Here, `desserts` changed `menu.txt` in one of its commits, and Panda has an uncommitted line in `menu.txt` on `main`:

<CodeExample setup={`mkdir cafe
cd cafe
git init
echo "Green tea" > menu.txt
git add menu.txt
git commit -m "Start the menu"
echo "Open 9 to 5" > hours.txt
git add hours.txt
git commit -m "Add opening hours"
git switch -c desserts
echo "Green tea with lemon" > menu.txt
git commit -am "Add lemon"
git switch main`} output={`error: Your local changes to the following files would be overwritten by checkout:
	menu.txt
Please commit your changes or stash them before you switch branches.
Aborting
On branch main
Changes not staged for commit:
  (use "git add <file>..." to update what will be committed)
  (use "git restore <file>..." to discard changes in working directory)
	modified:   menu.txt

no changes added to commit (use "git add" and/or "git commit -a")`}>

```bash
echo "Jasmine tea" >> menu.txt
git switch desserts
git status
```

</CodeExample>

`Aborting` means nothing happened: you're still on `main`, and your change is still there. You have three ways out:

- **Commit it** on this branch (`git add`, `git commit`), then switch. This is the usual answer.
- **Throw the change away** with `git restore menu.txt` if you don't want it (you met `git restore` in Everyday Git). Then switch.
- **Put it aside** for later with `git stash`, the "stash" the message mentions. You'll learn it in Level 2.

## Recap

- A **branch** is a name that points at a commit. Committing moves the branch you're on up to the new commit. Making one copies no files.
- **`HEAD`** points at the branch you're on: `(HEAD -> main)`.
- **`git branch`** lists branches (the star is where you are); **`-v`** adds each one's commit. **`git branch name`** makes a branch but doesn't switch to it.
- **`git switch name`** moves you to a branch; **`git switch -c name`** makes one and switches; **`git switch -`** goes back. Older commands: `git checkout name`, `git checkout -b name`.
- Switching makes your folder look like that branch's newest commit. **`git log --oneline --all`** shows every branch's commits.
- **`git branch -m old new`** renames; **`-d`** deletes a merged branch; **`-D`** deletes one whose commits are nowhere else.
- "Your local changes … would be overwritten": commit (or restore) your change first, then switch.
