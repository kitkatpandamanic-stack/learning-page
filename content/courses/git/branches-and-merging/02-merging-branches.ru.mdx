Десерты готовы! 🍰 На ветке `desserts` у Панды есть шоколадный торт и лимонный тарт, и теперь им пора в настоящее меню, на `main`. Перенос работы одной ветки в другую называется **слиянием** (merge), и именно оно делает ветки полезными: вы собираете что-то в стороне, а потом одним шагом возвращаете домой.

В этом уроке вы будете сливать ветки командой `git merge`, познакомитесь с двумя исходами слияния — **перемоткой** (fast-forward) и **коммитом слияния** (merge commit) — и соберёте всё вместе в ежедневный порядок работы через ветки задач.

## Репозиторий для примеров

Примеры снова начинаются в `cafe`. На `main` два коммита, а на `desserts` поверх них ещё два:

```bash
git switch -c desserts
echo "Шоколадный торт" > cake.txt
git add cake.txt
git commit -m "Добавить шоколадный торт"
echo "Лимонный тарт" > tart.txt
git add tart.txt
git commit -m "Добавить лимонный тарт"
```

## git merge: вливаем ветку

**`git merge имя`** приносит коммиты ветки `имя` **в ту ветку, на которой вы стоите**. Поэтому сначала переключитесь на ветку, которая должна получить работу, а потом назовите ту, которую вливаете:

<CodeExample setup={`mkdir cafe
cd cafe
git init
echo "Зелёный чай" > menu.txt
git add menu.txt
git commit -m "Начать меню"
echo "Открыто с 9 до 17" > hours.txt
git add hours.txt
git commit -m "Добавить часы работы"
git switch -c desserts
echo "Шоколадный торт" > cake.txt
git add cake.txt
git commit -m "Добавить шоколадный торт"
echo "Лимонный тарт" > tart.txt
git add tart.txt
git commit -m "Добавить лимонный тарт"`} output={`Switched to branch 'main'
Updating bfa1c10..b454101
Fast-forward
 cake.txt | 1 +
 tart.txt | 1 +
 2 files changed, 2 insertions(+)
 create mode 100644 cake.txt
 create mode 100644 tart.txt
b454101 (HEAD -> main, desserts) Добавить лимонный тарт
c5e7ee1 Добавить шоколадный торт
bfa1c10 Добавить часы работы
f1707e2 Начать меню`}>

```bash
git switch main
git merge desserts
git log --oneline
```

</CodeExample>

Читаем сверху вниз:

- **`Updating bfa1c10..b454101`** («обновляю»): `main` переходит со своего старого коммита на последний коммит `desserts`.
- **`Fast-forward`** («перемотка»): так Git это сделал (подробнее чуть ниже).
- Дальше сводка, как после `git commit`: какие файлы изменились, и `create mode` для новых. `cake.txt` и `tart.txt` теперь лежат в папке на `main`.
- В log `main` и `desserts` указывают на один коммит. Десерты на `main`!

Направление важно. `git merge desserts` на `main` меняет `main` и не трогает `desserts`. Та же команда на `desserts` с `main` сделала бы наоборот.

## Перемотка: метка просто сдвигается

Ещё раз посмотрите на картинку до слияния: `main` **отставал** от `desserts` и с тех пор, как появилась `desserts`, своих коммитов не получал. Соединять было нечего. Git оставалось лишь передвинуть метку `main` вперёд по линии, туда, где стоит `desserts`. Это и есть **перемотка** (fast-forward), и **нового коммита она не создаёт**:

<GitGraph setup={`mkdir cafe
cd cafe
git init

git switch -c desserts
echo "Шоколадный торт" > cake.txt
git add cake.txt

Если слить ту же ветку ещё раз, делать Git будет нечего, и он скажет `Already up to date.` («уже актуально»).

## Обе ветки ушли вперёд: коммит слияния

Часто `main` не стоит на месте. Пока готовились десерты, Панда добавила на `main` ещё и чёрный чай. Теперь у каждой ветки есть коммит, которого нет у другой:

<GitGraph setup={`mkdir cafe
cd cafe
git init
echo "Зелёный чай" > menu.txt
git add menu.txt
git commit -m "Начать меню"
echo "Открыто с 9 до 17" > hours.txt
git add hours.txt
git commit -m "Добавить часы работы"
git switch -c desserts
echo "Шоколадный торт" > cake.txt
git add cake.txt

echo "Лимонный тарт" > tart.txt
git add tart.txt
git commit -m "Добавить лимонный тарт"
git switch main
echo "Чёрный чай" >> menu.txt
git add menu.txt
git commit -m "Добавить чёрный чай"`} caption="После «Добавить часы работы» ветки разошлись: чёрный чай на main, десерты на своей дорожке." />

Просто сдвинуть метку уже нельзя: `main` потерял бы чёрный чай. Поэтому Git создаёт новый коммит, который соединяет две линии, — **коммит слияния**. Ему нужно сообщение, и **`-m`** задаёт его, как и у `git commit`:

<CodeExample setup={`mkdir cafe
cd cafe
git init
echo "Зелёный чай" > menu.txt
git add menu.txt
git commit -m "Начать меню"
echo "Открыто с 9 до 17" > hours.txt
git add hours.txt
git commit -m "Добавить часы работы"
git switch -c desserts
echo "Шоколадный торт" > cake.txt
git add cake.txt
git commit -m "Добавить шоколадный торт"
echo "Лимонный тарт" > tart.txt
git add tart.txt
git commit -m "Добавить лимонный тарт"
git switch main
echo "Чёрный чай" >> menu.txt
git add menu.txt
git commit -m "Добавить чёрный чай"`} output={`Merge made by the 'ort' strategy.
 cake.txt | 1 +
 tart.txt | 1 +
 2 files changed, 2 insertions(+)
 create mode 100644 cake.txt
 create mode 100644 tart.txt
1885a5d (HEAD -> main) Добавить десерты
5b88101 Добавить чёрный чай
b454101 (desserts) Добавить лимонный тарт
c5e7ee1 Добавить шоколадный торт
bfa1c10 Добавить часы работы
f1707e2 Начать меню`}>

```bash
git merge desserts -m "Добавить десерты"
git log --oneline
```

</CodeExample>

- **`Merge made by the 'ort' strategy.`** значит, что Git объединил две ветки и создал коммит слияния. «ort» — просто название способа, которым Git их объединяет; оно будет в каждом таком слиянии.
- Сводка ниже показывает, что слияние принесло в `main`: два файла с десертами.
- Теперь на `main` есть всё: и чёрный чай, **и** десерты.

## Коммит с двумя родителями

Каждый коммит помнит коммит, который был перед ним, — своего **родителя** (parent). Коммит слияния особенный: у него **два родителя**, по одному от каждой ветки. `git log` показывает их в строке `Merge:`:

<CodeExample setup={`mkdir cafe
cd cafe
git init
echo "Зелёный чай" > menu.txt
git add menu.txt
git commit -m "Начать меню"
echo "Открыто с 9 до 17" > hours.txt
git add hours.txt
git commit -m "Добавить часы работы"
git switch -c desserts
echo "Шоколадный торт" > cake.txt
git add cake.txt
git commit -m "Добавить шоколадный торт"
echo "Лимонный тарт" > tart.txt
git add tart.txt
git commit -m "Добавить лимонный тарт"
git switch main
echo "Чёрный чай" >> menu.txt
git add menu.txt
git commit -m "Добавить чёрный чай"
git merge desserts -m "Добавить десерты"`} output={`commit 1885a5dc80d76aabfb6f3d517f96a7da3b3850b4 (HEAD -> main)
Merge: 5b88101 b454101
Author: Panda <panda@pandadev.dev>
Date:   Mon Jan 5 09:06:00 2026 +0000

    Добавить десерты`}>

```bash
git log -n 1
```

</CodeExample>

`5b88101` — коммит с чёрным чаем (там стоял `main`), а `b454101` — лимонный тарт (там стояла `desserts`). Первый родитель — всегда ветка, на которой вы были. Так Git знает, что слияние содержит обе истории, и поэтому `git log` на `main` теперь показывает и коммиты с десертами.

<Callout type="tip" title="Слияние на вашем компьютере">

Без `-m` команда `git merge` на вашем компьютере откроет текстовый редактор с уже написанным сообщением `Merge branch 'desserts'`. Сохраните файл и закройте редактор, чтобы закончить слияние. Чтобы обойтись без редактора и оставить это сообщение, добавьте **`--no-edit`**. В учебном терминале редактора нет, поэтому здесь слияние без `-m` просто берёт сообщение `Merge branch 'desserts'`.

</Callout>

## Всегда коммит слияния: --no-ff

После перемотки не остаётся никаких следов того, что ветка вообще была: коммиты с тортом и тартом просто стоят в прямой линии `main`. Некоторые команды хотят, чтобы каждая задача была видна в истории отдельным «горбом». **`--no-ff`** (no fast-forward, «без перемотки») велит Git создать коммит слияния, даже когда можно было перемотать:

<CodeExample setup={`mkdir cafe

 cake.txt | 1 +
 tart.txt | 1 +
 2 files changed, 2 insertions(+)
 create mode 100644 cake.txt
 create mode 100644 tart.txt
45f7fde (HEAD -> main) Слить десерты


</CodeExample>

## Какие ветки уже слиты?

Со временем в репозитории копятся ветки, и уже не помнишь, какие из них готовы. **`git branch --merged`** выводит ветки, все коммиты которых уже есть на текущей ветке, а **`git branch --no-merged`** — те, у которых ещё есть свои коммиты. Здесь `desserts` уже слита в `main`, а на `drinks` есть коммит, которого у `main` пока нет:

<CodeExample setup={`mkdir cafe
cd cafe
git init
echo "Зелёный чай" > menu.txt
git add menu.txt
git commit -m "Начать меню"
echo "Открыто с 9 до 17" > hours.txt
git add hours.txt
git commit -m "Добавить часы работы"
git switch -c desserts
echo "Шоколадный торт" > cake.txt
git add cake.txt
git commit -m "Добавить шоколадный торт"
echo "Лимонный тарт" > tart.txt
git add tart.txt
git commit -m "Добавить лимонный тарт"


Слитую ветку можно спокойно удалить: её коммиты останутся в истории `main`, что бы ни случилось с меткой. `git branch -d` делает ту же проверку за вас: слитую ветку удаляет, а неслитую — отказывается, с ошибкой `not fully merged` из прошлого урока.

## Уборка: удаляем слитую ветку

Когда ветка слита, её метка своё отработала. Удалите её, чтобы `git branch` показывал только то, что ещё в работе:

<CodeExample setup={`mkdir cafe

b454101 (HEAD -> main) Добавить лимонный тарт
c5e7ee1 Добавить шоколадный торт

</CodeExample>

Ветки нет, а все коммиты на месте: удаление ветки убирает только метку.

## Работа через ветки задач

Если сложить всё вместе, получится то, как работает большинство разработчиков, каждый день, даже в одиночку на одном компьютере:

1. Начните с `main`: `git switch main`.
2. Создайте ветку под одну задачу и назовите её по задаче: `git switch -c opening-hours`.
3. Работайте и коммитьте на ней — столько коммитов, сколько нужно задаче.
4. Когда готово, вернитесь: `git switch main`.
5. Влейте ветку: `git merge opening-hours` (с `-m` или `--no-edit`, если Git попросит сообщение).
6. Удалите её: `git branch -d opening-hours`.

На `main` всегда лежит законченная работа, а каждая недоделанная идея живёт на своей ветке, пока не будет готова. Если идея не удалась, вы удаляете её ветку через `-D`, и `main` о ней даже не узнает.

Две привычки помогают сливать без проблем:

- **Коммитьте перед слиянием.** Сначала выполните `git status`: он должен сказать `working tree clean`. Git отказывается сливать, если слияние затёрло бы ваши незакоммиченные изменения, и даже когда не отказывается, несохранённая работа, перемешанная со слиянием, мешает его отменить.
- **Проверяйте имя.** `git merge dessert` (с опечаткой) ответит `merge: dessert - not something we can merge`. Настоящие имена покажет `git branch`.

## Итоги

- **`git merge имя`** приносит ветку `имя` **в текущую ветку**. Сначала переключитесь на ту, что получает работу (обычно `main`).
- **Перемотка (fast-forward):** если у вашей ветки нет своих коммитов, Git просто сдвигает её метку вперёд. Нового коммита нет.
- **Коммит слияния:** если ушли вперёд обе ветки, Git соединяет их новым коммитом с **двумя родителями** (`Merge:` в `git log`). Вывод: `Merge made by the 'ort' strategy.`
- **`-m "сообщение"`** задаёт сообщение коммита слияния; на вашем компьютере без него Git откроет редактор (`--no-edit` оставляет сообщение по умолчанию).
- **`--no-ff`** создаёт коммит слияния, даже когда перемотка возможна.
- **`git branch --merged`** / **`--no-merged`** показывают, какие ветки готовы; **`git branch -d`** удаляет слитую ветку.
- **Работа через ветки задач:** `switch -c`, коммиты, `switch main`, `merge`, `branch -d`. Перед слиянием всё закоммитьте.
