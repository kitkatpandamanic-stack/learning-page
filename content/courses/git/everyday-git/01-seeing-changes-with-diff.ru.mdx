`git status` говорит, **какие** файлы изменились, но не говорит, **что** в них изменилось. А перед коммитом важно именно это: вы поменяли ту цену, которую хотели, или заодно пробрался случайно нажатый символ? 🔍

**`git diff`** отвечает на этот вопрос строка за строкой, в том же формате с `+` и `-`, который вы видели в `git show`. В этом уроке вы узнаете, какие две версии сравнивает каждая форма `git diff`, научитесь сравнивать любые два коммита и наконец прочитаете строки с `@@`, которые на уровне 0 мы пропускали.

## git diff: неподготовленные изменения

Зара решила работать на час дольше. Она записывает новые часы в `hours.txt` и, прежде чем делать что-то ещё, смотрит, что изменилось:

<CodeExample setup={`mkdir bakery
cd bakery
git init
echo "1. Круассан - 2.50" > menu.txt
echo "2. Бублик - 2.00" >> menu.txt
echo "3. Маффин - 2.20" >> menu.txt
echo "4. Булочка с корицей - 3.00" >> menu.txt
echo "5. Брауни - 2.80" >> menu.txt

git add menu.txt
git commit -m "Добавить меню"
echo "Открыто каждый день, с 8:00 до 18:00" > hours.txt
git add hours.txt
git commit -m "Добавить часы работы"
echo "10. Банановый хлеб - 2.60" >> menu.txt
git add menu.txt
git commit -m "Добавить банановый хлеб"`} output={` M hours.txt
diff --git a/hours.txt b/hours.txt
index b2bbb4a..2c6e8f4 100644
--- a/hours.txt
+++ b/hours.txt
@@ -1 +1 @@
-Открыто каждый день, с 8:00 до 18:00
+Открыто каждый день, с 8:00 до 19:00`}>

```bash
echo "Открыто каждый день, с 8:00 до 19:00" > hours.txt
git status -s
git diff
```

</CodeExample>

`git status -s` сообщает только ` M hours.txt`: файл изменён, но не подготовлен. `git diff` показывает само изменение: строка с `18:00` удалена (`-`), а строка с `19:00` добавлена (`+`).

**`git diff`** без ничего после него сравнивает **рабочую папку** с **областью подготовки**. Иначе говоря, он показывает изменения, которые ещё можно добавить через `git add`, но которые вы пока не добавили. Сразу после коммита в области подготовки лежит ровно то же, что в этом коммите, поэтому сейчас это то же самое, что «изменения с последнего коммита».

<Callout type="tip" title="git diff на вашем компьютере">

На настоящем компьютере удалённые строки обычно красные, а добавленные зелёные. Длинный diff открывается в том же **пейджере** (pager), что и длинный `git log`: листайте стрелками или пробелом, а чтобы вернуться к приглашению, нажмите **`q`**.

</Callout>

## Читаем фрагмент

На уровне 0 вы пропускали строку, которая начинается с `@@`. Пора её прочитать. На этот раз Зара поменяла в `menu.txt` две цены: круассан в строке 1 и яблочный пирог в строке 9.

index e34b5c4..1e19c15 100644
--- a/menu.txt
+++ b/menu.txt
@@ -1,4 +1,4 @@
-1. Круассан - 2.50
+1. Круассан - 2.70
 2. Бублик - 2.00

@@ -6,5 +6,5 @@

```bash

```

</CodeExample>

Четыре строки вверху — заголовок файла, как в `git show`: `diff --git` называет файл, строка `index` — служебные пометки Git, а `---` и `+++` отмечают старую версию (`a/`) и новую (`b/`).

Дальше идут **фрагменты** (hunks): куски файла вокруг каждого изменения. Каждый фрагмент начинается со строки между знаками `@@`:

- **`@@ -1,4 +1,4 @@`**: часть после `-` относится к **старой** версии, часть после `+` — к **новой**. `-1,4` значит «в старой версии этот кусок начинается со строки 1 и занимает 4 строки». `+1,4` говорит то же о новой версии.
- Строки, которые начинаются с **пробела**, не менялись. Это **контекст**: вокруг каждого изменения Git показывает до 3 неизменённых строк, чтобы было видно, где оно находится.
- Строки с **`-`** удалены, строки с **`+`** добавлены — это вы уже знаете.
- **`@@ -6,5 +6,5 @@`** начинает второй фрагмент, со строки 6. Строка 5 слишком далеко от обоих изменений, чтобы попасть в контекст, поэтому Git её пропускает. Если два изменения рядом (между ними 6 неизменённых строк или меньше), их контекст пересёкся бы, и Git объединяет их в один фрагмент.

Самое интересное в числах заголовка начинается, когда файл растёт или уменьшается. Здесь Зара добавляет в конец морковный торт:

```bash
echo "11. Морковный торт - 3.20" >> menu.txt
```

**`@@ -8,3 +8,4 @@`**: в старой версии кусок — это строки с 8 по 10 (3 строки), в новой — строки с 8 по 11 (4 строки). На одну строку больше — ту, что с `+`. И ещё две мелочи:

- Если кусок длиной всего **в одну строку**, Git не пишет длину: `@@ -1 +1 @@` (как в примере с часами выше) значит «строка 1, и в старой, и в новой версии».
- У **нового файла** вы увидите `@@ -0,0 +1 @@`: до — ноль строк, после — одна.

<Callout type="note" title="Текст после второго @@">

На вашем компьютере после заголовка фрагмента иногда стоит текст, например `@@ -3,4 +3,4 @@ Бублик`. Это ближайшая строка **над** фрагментом, которая начинается с буквы. В коде это обычно имя функции, в которой изменение, — так проще понять, где вы. Учебный терминал этот текст не показывает. (Строки нашего меню начинаются с цифр, так что на вашем компьютере у этого меню его тоже не будет.)

</Callout>

## Подготовленные изменения: git diff --staged

Что будет с `git diff`, когда изменение подготовлено? Зара подготавливает новые часы и смотрит снова:

echo "7. Лимонный тарт - 3.50" >> menu.txt

git add hours.txt
git commit -m "Добавить часы работы"

git add menu.txt
git commit -m "Добавить банановый хлеб"`} output={`diff --git a/hours.txt b/hours.txt
index b2bbb4a..2c6e8f4 100644
--- a/hours.txt
+++ b/hours.txt
@@ -1 +1 @@
-Открыто каждый день, с 8:00 до 18:00
+Открыто каждый день, с 8:00 до 19:00`}>

```bash
echo "Открыто каждый день, с 8:00 до 19:00" > hours.txt
git add hours.txt
git diff
git diff --staged
```

</CodeExample>

Первый `git diff` не выводит **ничего**. Изменение никуда не делось: теперь оно в области подготовки, рабочая папка и область подготовки совпадают, и обычному `git diff` показывать нечего.

**`git diff --staged`** сравнивает область подготовки с **последним коммитом**. Он показывает ровно то, что сохранит следующий `git commit`, поэтому это лучшая последняя проверка перед коммитом. **`git diff --cached`** — другое имя той же команды; в чужих заметках встречаются оба.

Есть ещё один промежуток, через который можно посмотреть: **`git diff HEAD`** сравнивает рабочую папку с последним коммитом, неважно, подготовлены изменения или нет. (`HEAD`, как вы видели в `git log`, означает коммит, на котором вы сейчас.) Здесь `hours.txt` подготовлен, а `menu.txt` — нет:

Итак, есть три способа посмотреть — по одному на каждый промежуток между тремя местами, где живёт ваша работа:

| Команда             | Что с чем сравнивает                     | Что показывает                         |
| ------------------- | ---------------------------------------- | -------------------------------------- |
| `git diff`          | область подготовки → рабочая папка       | изменения, которые ещё не подготовлены |
| `git diff --staged` | последний коммит → область подготовки    | что сохранит следующий коммит          |
| `git diff HEAD`     | последний коммит → рабочая папка         | всё, что изменилось с последнего коммита |

## Сравниваем два коммита

`git diff` умеет сравнивать и любые два коммита. Дайте ему два хеша, **сначала более старый**, и он покажет, что изменилось от первого ко второму:

<CodeExample setup={`mkdir bakery
cd bakery
git init
echo "1. Круассан - 2.50" > menu.txt
echo "2. Бублик - 2.00" >> menu.txt
echo "3. Маффин - 2.20" >> menu.txt
echo "4. Булочка с корицей - 3.00" >> menu.txt
echo "5. Брауни - 2.80" >> menu.txt
echo "6. Печенье - 1.50" >> menu.txt
echo "7. Лимонный тарт - 3.50" >> menu.txt
echo "8. Чизкейк - 4.00" >> menu.txt
echo "9. Яблочный пирог - 3.80" >> menu.txt
git add menu.txt
git commit -m "Добавить меню"
echo "Открыто каждый день, с 8:00 до 18:00" > hours.txt
git add hours.txt
git commit -m "Добавить часы работы"
echo "10. Банановый хлеб - 2.60" >> menu.txt

+Открыто каждый день, с 8:00 до 18:00

```bash
git log --oneline
git diff 7011e3e ae1677d
```

</CodeExample>

От первого коммита до самого нового появился `hours.txt` (`new file`), а в меню стало на одну строку больше. Заметьте: это **один** diff, а не по одному на каждый коммит. Git сравнивает два снимка и пропускает всё, что было между ними.

- **Порядок важен.** `git diff ae1677d 7011e3e` покажет те же изменения наоборот: `hours.txt` как удалённый файл, а банановый хлеб как строку с `-`.
- **Две точки** делают то же самое: `git diff 7011e3e..ae1677d` — просто другая запись `git diff 7011e3e ae1677d`.
- **Один коммит** сравнивается с рабочей папкой: `git diff 7011e3e` покажет всё, что изменилось с первого коммита, включая правки, которые вы ещё не закоммитили.

## Частые ошибки

- **Ждать, что `git diff` покажет подготовленные изменения.** После `git add` обычный `git diff` молчит. Чтобы увидеть, что вы собираетесь закоммитить, используйте `git diff --staged`.
- **Искать новый файл в `git diff`.** Неотслеживаемые файлы там не появляются никогда. Их перечисляет `git status`.
- **Путать порядок коммитов.** `git diff новый старый` превращает каждый `+` в `-`. Сначала старый, потом новый.
- **Думать, что заголовок фрагмента считает изменения.** `@@ -6,5 +6,5 @@` — это номер первой строки и длина для каждой версии, а не «6 удалено, 5 добавлено».

## Итоги

- **`git diff`** показывает неподготовленные изменения: рабочая папка в сравнении с областью подготовки.
- **`git diff --staged`** (или `--cached`) показывает, что сохранит следующий коммит: область подготовки в сравнении с последним коммитом.
- **`git diff HEAD`** показывает всё с последнего коммита, подготовленное и нет.
- **`git diff A B`** (или `A..B`) сравнивает два коммита, сначала более старый. Один diff показывает разницу между двумя концами, что бы ни происходило между ними.
- **`--stat`** даёт сводку в одну строку на файл; **`-- файл`** ограничивает diff одним файлом.
- В заголовке фрагмента вроде **`@@ -8,3 +8,4 @@`** с каждой стороны — номер первой строки и длина: старая версия после `-`, новая после `+`. Строки с пробелом в начале — неизменённый контекст.
- Новые, неотслеживаемые файлы в `git diff` не появляются; их показывает `git status`.

Дальше: [Игнорируем файлы: .gitignore](/learn/git/ignoring-files) — чтобы логи, результаты сборки и секреты никогда не попадали в коммит.
