Ошибаются все: правка пошла не туда, файл подготовили случайно, в сообщении коммита опечатка или в коммит не попал файл. В Git почти всё это исправляется одной командой. 🩹

Каждая ошибка живёт в одном из трёх мест, через которые проходит ваша работа, и у каждого места своя отмена:

| Ошибка в…            | Чем отменить                 | Что делает                                       |
| -------------------- | ---------------------------- | ------------------------------------------------ |
| рабочей папке        | `git restore файл`           | выбрасывает ваши правки                          |
| области подготовки   | `git restore --staged файл`  | убирает файл из подготовки и сохраняет правки    |
| последнем коммите    | `git commit --amend`         | заменяет последний коммит исправленным           |

В примерах — репозиторий Зары `bakery` из двух прошлых уроков: `menu.txt` и `hours.txt`, три коммита, и для начала рабочая папка чистая.

## Выбрасываем правку: git restore

Эту подсказку в `git status` вы видите ещё с уровня 0: `(use "git restore <file>..." to discard changes in working directory)` («используйте git restore, чтобы отменить изменения в рабочей папке»). Вот она в деле. Зара вставила текст не в тот файл и затёрла часы работы:

**`git restore файл`** возвращает файл к тому виду, в каком он лежит в **области подготовки**. Здесь ничего не подготовлено, так что это версия из последнего коммита. Как и большинство команд Git, при успехе она ничего не печатает; `git status` и `cat` показывают, что правки больше нет.

Удалённые файлы она тоже возвращает. Помните «отмены нет» про `rm`? Для файла, который есть в коммите, теперь есть:

` D` значит «удалён из рабочей папки, не подготовлен». Один `git restore` — и меню на месте.

<Callout type="danger" title="git restore не отменить">

Выброшенные правки никогда не коммитились, поэтому у Git нет их копии. Они пропадают навсегда. Сначала запустите `git diff` и убедитесь, что действительно готовы это потерять. А с `git restore .` будьте особенно осторожны: эта команда выбрасывает правки **во всех** файлах папки.

</Callout>

## Убираем файл из подготовки: git restore --staged

Подготовили то, что ещё не готово? **`git restore --staged файл`** убирает его из области подготовки и не трогает ваши правки:

## Когда плохая правка уже подготовлена

Тут есть ловушка. Обычный `git restore` копирует файл **из области подготовки**. Если плохая правка подготовлена, в области подготовки лежит плохая версия, и `git restore` возвращает… плохую версию. Отменяйте в два шага: сначала уберите из подготовки, потом выбросьте правку:

echo "6. Печенье - 1.50" >> menu.txt

echo "8. Чизкейк - 4.00" >> menu.txt
echo "9. Яблочный пирог - 3.80" >> menu.txt
git add menu.txt
git commit -m "Добавить меню"
echo "Открыто каждый день, с 8:00 до 18:00" > hours.txt
git add hours.txt
git commit -m "Добавить часы работы"
echo "10. Банановый хлеб - 2.60" >> menu.txt
git add menu.txt
git commit -m "Добавить банановый хлеб"`} output={`M  hours.txt
 M hours.txt
Открыто каждый день, с 8:00 до 18:00`}>

```bash
echo "Закрыто" > hours.txt
git add hours.txt
git restore hours.txt
git status -s
git restore --staged hours.txt
git status -s
git restore hours.txt
git status -s
cat hours.txt
```

</CodeExample>

Следите за кодами: после первого `git restore` по-прежнему `M ` (подготовлен). `git restore --staged` превращает его в ` M` (не подготовлен), и только после этого `git restore` возвращает часы из коммита, а `git status -s` больше ничего не показывает.

<Callout type="note" title="Старый способ: git checkout -- файл">

`git restore` появился в Git 2.23, в 2019 году. До этого правки выбрасывали через `git checkout`, и вы ещё встретите его в старых руководствах и ответах в интернете:

```bash
git checkout -- hours.txt
```

Это то же самое, что `git restore hours.txt`. `--` значит «дальше идёт имя файла». `git checkout` делает несколько разных дел, в том числе переключает ветки (это следующий модуль), поэтому в Git и добавили `git restore` с более понятным названием. Пользуйтесь `git restore`, а старую команду просто узнавайте при встрече.

</Callout>

## Исправляем последний коммит: git commit --amend

Бывает, что ошибка уже в коммите: опечатка в сообщении или файл, который забыли подготовить. Если это **последний** коммит, его исправит **`git commit --amend`** (amend — «исправить»).

### Сообщение получше

Зара коммитит в спешке:

echo "4. Булочка с корицей - 3.00" >> menu.txt
echo "5. Брауни - 2.80" >> menu.txt
echo "6. Печенье - 1.50" >> menu.txt
echo "7. Лимонный тарт - 3.50" >> menu.txt
echo "8. Чизкейк - 4.00" >> menu.txt
echo "9. Яблочный пирог - 3.80" >> menu.txt
git add menu.txt
git commit -m "Добавить меню"
echo "Открыто каждый день, с 8:00 до 18:00" > hours.txt

[main 67bc5c6] Открываться на час позже
 Date: Mon Jan 5 09:04:00 2026 +0000
 1 file changed, 1 insertion(+), 1 deletion(-)
67bc5c6 (HEAD -> main) Открываться на час позже

```bash
echo "Открыто каждый день, с 8:00 до 19:00" > hours.txt
```

</CodeExample>

`git commit --amend -m "…"` заменил коммит таким же, но с новым сообщением. Лишняя строка ` Date:` показывает дату исходного коммита: при исправлении она сохраняется. От опечатки в истории не осталось и следа.

Но посмотрите на хеш: был `4bf5217`, стал `67bc5c6`. Коммит нельзя изменить, потому что его хеш вычисляется из всего содержимого, сообщения в том числе. Поэтому `--amend` не правит старый коммит, а создаёт **новый** и ставит его на место старого.

### Не исправляйте то, чем уже поделились

Раз исправление подменяет коммит новым, оно безопасно, только пока коммит **только ваш**. На уровне 2 вы начнёте отправлять коммиты на общий сервер (вроде GitHub), откуда их копируют коллеги. Если исправить коммит, который у кого-то уже есть, в вашей истории и в их истории окажутся две разные версии одного коммита, и разбираться с этим — настоящая головная боль.

Правило: **исправляйте только коммиты, которыми ещё не поделились.** Чтобы поправить коммит, которым уже поделились, делают новый коммит поверх.

Отмены покрупнее — например, вернуться на несколько коммитов назад или отменить коммит, которым уже поделились, — делаются через `git reset` и `git revert`. Они будут на уровне 3, а пока учебный терминал отвечает на них «isn't in this practice terminal yet» («этого в учебном терминале пока нет»).

## Частые ошибки

- **Запустить `git restore` для нужных правок.** Они пропадут навсегда. Сначала проверьте через `git diff`.
- **Ждать, что `git restore` отменит подготовленное изменение.** Он копирует из области подготовки, поэтому сначала уберите файл из подготовки через `--staged`.
- **Думать, что `--staged` выбрасывает правки.** Он только убирает из подготовки; правки остаются в файле.
- **Исправить коммит, когда нужен был новый.** `--amend` меняет последний коммит. Если тот коммит был закончен и хорош, сделайте новый.
- **Исправить коммит, которым уже поделились.** На своём компьютере это нормально, но когда коммит есть у других — жди беды.

## Итоги

- **`git restore файл`** выбрасывает неподготовленные правки и возвращает удалённые файлы — из области подготовки. Отменить это нельзя.
- **`git restore --staged файл`** убирает файл из подготовки и сохраняет правки. Новый файл снова становится неотслеживаемым.
- **Подготовленная** плохая правка отменяется в два шага: `git restore --staged файл`, потом `git restore файл`.
- **`git checkout -- файл`** — старый способ выбросить правки; он встречается в старых руководствах.
- **`git commit --amend -m "…"`** заменяет последний коммит новым: с новым сообщением и всем, что вы подготовили после. **`--no-edit`** сохраняет сообщение.
- После исправления у коммита **новый хеш**. Исправляйте только коммиты, которыми ещё не поделились; совместная работа будет на уровне 2, а `git reset` и `git revert` — на уровне 3.

Модуль **«Git каждый день»** пройден: вы видите, что именно изменилось, не пускаете мусор в историю и отменяете повседневные ошибки. Дальше: [Что такое ветка?](/learn/git/what-is-a-branch) — вы начнёте работать сразу с несколькими линиями истории. 🌿
