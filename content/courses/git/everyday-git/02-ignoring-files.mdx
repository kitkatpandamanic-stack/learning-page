Every project collects files that don't belong in its history: logs that grow every time you run the program, folders a tool rebuilds for you, a password file, the junk your operating system leaves behind. Delete them, and they come back. Leave them, and one quick `git add .` sweeps them all into a commit. 🧹

The fix is a small file called **`.gitignore`**: a list of names and patterns that Git should act as if it can't see. In this lesson you'll write one, learn its patterns, test them, and find out what to do about a file that's already been committed.

## Files that don't belong in Git

Tom is building a website for his plant shop. His repository, `plant-shop`, has one commit with `index.html` and `style.css`. Since then, a few other files have turned up:

<CodeExample setup={`mkdir -p plant-shop/build plant-shop/logs
cd plant-shop
git init
echo "<h1>Tom's Plant Shop</h1>" > index.html
echo "body { color: green; }" > style.css
git add .
git commit -m "Add the home page"
echo "Server started" > server.log
echo "Page not found: /cactus" > logs/errors.log
echo "<h1>Tom's Plant Shop</h1>" > build/index.html
echo "API_KEY=test-1234" > .env
touch .DS_Store`} output={`On branch main
Untracked files:
  (use "git add <file>..." to include in what will be committed)
	.DS_Store
	.env
	build/
	logs/
	server.log

nothing added to commit but untracked files present (use "git add" to track)`}>

```bash
git status
```

</CodeExample>

None of the untracked files should ever be committed:

- **`server.log`** and **`logs/`**: **log files** that a program writes while it runs. They change all the time and are only useful on the computer that made them.
- **`build/`**: **build output**, files a tool makes from your own files (a shrunk copy of the site, say). You can always make them again, so storing them only bloats the history.
- **`.env`**: **secrets**, like passwords and API keys (`.env` is the usual name for this file). Anyone who can see the repository could read them.
- **`.DS_Store`**: system junk. macOS leaves one in every folder you open in Finder. (Windows has `Thumbs.db`.)

In real projects you'll meet more: `node_modules/` (packages a JavaScript project downloads) or `__pycache__/` (Python's compiled files).

## Your first .gitignore

`.gitignore` is a plain text file in the top folder of the repository, with **one pattern per line**. Its name starts with a dot, so it's hidden, like `.git`. Tom writes one with `echo` and checks the status again:

<CodeExample setup={`mkdir -p plant-shop/build plant-shop/logs
cd plant-shop
git init
echo "<h1>Tom's Plant Shop</h1>" > index.html
echo "body { color: green; }" > style.css
git add .
git commit -m "Add the home page"
echo "Server started" > server.log
echo "Page not found: /cactus" > logs/errors.log
echo "<h1>Tom's Plant Shop</h1>" > build/index.html
echo "API_KEY=test-1234" > .env
touch .DS_Store`} output={`*.log
build/
.env
.DS_Store
On branch main
Untracked files:
  (use "git add <file>..." to include in what will be committed)
	.gitignore

nothing added to commit but untracked files present (use "git add" to track)`}>

```bash
echo "*.log" > .gitignore
echo "build/" >> .gitignore
echo ".env" >> .gitignore
echo ".DS_Store" >> .gitignore
cat .gitignore
git status
```

</CodeExample>

All the junk is gone from the list. The files are still there (`ls -a` shows them), Git just doesn't mention them any more. The only new file is `.gitignore` itself, and that one **should** be committed: it's part of the project, so everyone who works on it gets the same rules.

<CodeExample setup={`mkdir -p plant-shop/build plant-shop/logs
cd plant-shop
git init
echo "<h1>Tom's Plant Shop</h1>" > index.html
echo "body { color: green; }" > style.css
git add .
git commit -m "Add the home page"
echo "Server started" > server.log
echo "Page not found: /cactus" > logs/errors.log
echo "<h1>Tom's Plant Shop</h1>" > build/index.html
echo "API_KEY=test-1234" > .env
touch .DS_Store
echo "*.log" > .gitignore
echo "build/" >> .gitignore
echo ".env" >> .gitignore
echo ".DS_Store" >> .gitignore`} output={`[main 98f54a3] Add a .gitignore
 1 file changed, 4 insertions(+)
 create mode 100644 .gitignore
On branch main
nothing to commit, working tree clean`}>

```bash
git add .
git commit -m "Add a .gitignore"
git status
```

</CodeExample>

Now `git add .` is safe again: it stages `.gitignore` and skips everything the file lists.

## Patterns

Each line of `.gitignore` is a **pattern**, much like the wildcards you used with `ls` and `rm`. These cover nearly everything you'll need:

| Pattern       | Ignores                                                         |
| ------------- | --------------------------------------------------------------- |
| `.env`        | every file or folder called `.env`, in any folder               |
| `*.log`       | every name that ends in `.log`, in any folder                   |
| `build/`      | folders called `build`, with everything inside them             |
| `/config.txt` | `config.txt` in the top folder only                             |
| `!keep.log`   | nothing: it's an exception that brings `keep.log` back          |
| `# Logs`      | nothing: a line starting with `#` is a comment                  |

A few details are worth knowing:

- **No slash** in the pattern means "anywhere": `*.log` matched both `server.log` and `logs/errors.log` above.
- **A slash at the end** means "only folders": `build/` ignores a folder called `build`, but not a file with that name.
- **A slash at the start** means "only in the top folder" (the one with `.gitignore` in it).
- Blank lines are skipped, so you can group rules with comments.

Here's the difference a leading slash makes. Tom has two files called `config.txt`: his own settings at the top, and a page of documentation in `docs/`:

<CodeExample setup={`mkdir -p plant-shop/docs
cd plant-shop
git init
echo "<h1>Tom's Plant Shop</h1>" > index.html
git add .
git commit -m "Add the home page"
echo "debug=true" > config.txt
echo "How to set up the shop" > docs/config.txt`} output={`?? config.txt
?? docs/
?? .gitignore
?? .gitignore
?? docs/`}>

```bash
git status -s
echo "config.txt" > .gitignore
git status -s
echo "/config.txt" > .gitignore
git status -s
```

</CodeExample>

Each `echo` with `>` replaces the whole `.gitignore` with one line, so you can compare the two rules. With `config.txt`, both files disappear, the documentation too. With `/config.txt`, only the top one is ignored, and `docs/` shows up again.

## Exceptions with !

A line starting with **`!`** makes an exception to an earlier rule. Tom wants to ignore all logs except `keep.log`, a short log he shares with his designer:

<CodeExample setup={`mkdir -p plant-shop/build plant-shop/logs
cd plant-shop
git init
echo "<h1>Tom's Plant Shop</h1>" > index.html
echo "body { color: green; }" > style.css
git add .
git commit -m "Add the home page"
echo "Server started" > server.log
echo "Page not found: /cactus" > logs/errors.log
echo "<h1>Tom's Plant Shop</h1>" > build/index.html
echo "API_KEY=test-1234" > .env
touch .DS_Store
echo "Moved the cactus photo" > keep.log`} output={`# Logs, except the one we share
*.log
!keep.log
?? .DS_Store
?? .env
?? .gitignore
?? build/
?? keep.log`}>

```bash
echo "# Logs, except the one we share" > .gitignore
echo "*.log" >> .gitignore
echo "!keep.log" >> .gitignore
cat .gitignore
git status -s
```

</CodeExample>

`server.log` is still ignored and `logs/` stays hidden, but `keep.log` is back. Order matters: Git reads the file from top to bottom and the **last** line that matches wins, so the `!` line must come **after** `*.log`.

<Callout type="warning" title="You can't bring back a file from an ignored folder">

If a folder is ignored, Git doesn't even look inside it. So `build/` followed by `!build/keep.txt` doesn't work: `keep.txt` stays ignored with the rest of the folder.

</Callout>

## Is this file ignored? git check-ignore

When a file shows up (or doesn't) and you're not sure why, ask Git. **`git check-ignore`** takes file names and prints back the ones that are ignored. It prints nothing for a file that isn't:

<CodeExample setup={`mkdir -p plant-shop/build plant-shop/logs
cd plant-shop
git init
echo "<h1>Tom's Plant Shop</h1>" > index.html
echo "body { color: green; }" > style.css
git add .
git commit -m "Add the home page"
echo "Server started" > server.log
echo "Page not found: /cactus" > logs/errors.log
echo "<h1>Tom's Plant Shop</h1>" > build/index.html
echo "API_KEY=test-1234" > .env
touch .DS_Store
echo "*.log" > .gitignore
echo "build/" >> .gitignore
echo ".env" >> .gitignore
echo ".DS_Store" >> .gitignore`} output={`server.log
logs/errors.log
build/index.html
build/new-page.html`}>

```bash
git check-ignore server.log
git check-ignore logs/errors.log build/index.html index.html
git check-ignore index.html
git check-ignore build/new-page.html
```

</CodeExample>

`index.html` isn't ignored, so it's missing from the answer. The last line shows that the file doesn't even have to exist yet: anything you put in `build/` later is ignored too.

On your own computer, **`git check-ignore -v`** ("verbose") also says which rule matched, as `file:line:pattern` and then the name:

```text
.gitignore:1:*.log	server.log
```

## Ignored files and git add

What if you name an ignored file directly, as in `git add server.log`? Git refuses. It prints `The following paths are ignored by one of your .gitignore files`, lists the file, and suggests `-f` ("force") if you really want to add it.

You almost never do. If you find yourself forcing a file in, it's usually a sign the rule is too wide: change `.gitignore` instead (with an `!` exception, say).

## Ignoring doesn't untrack

Here's the catch that surprises everyone once. `.gitignore` is about **untracked** files only. A file that's already in a commit stays tracked, whatever `.gitignore` says.

In this version of the project, Tom committed `server.log` before he knew better. He adds `*.log` to `.gitignore`, the server writes another line, and…

<CodeExample setup={`mkdir plant-shop
cd plant-shop
git init
echo "<h1>Tom's Plant Shop</h1>" > index.html
echo "Server started" > server.log
git add .
git commit -m "Add the home page"`} output={`On branch main
Changes not staged for commit:
  (use "git add <file>..." to update what will be committed)
  (use "git restore <file>..." to discard changes in working directory)
	modified:   server.log

Untracked files:
  (use "git add <file>..." to include in what will be committed)
	.gitignore

no changes added to commit (use "git add" and/or "git commit -a")`}>

```bash
echo "*.log" > .gitignore
echo "Server stopped" >> server.log
git status
```

</CodeExample>

…`server.log` is still listed as modified. Git keeps tracking it, because it's in the last commit. To stop, remove it from the **staging area** but keep it on disk with **`git rm --cached`** ("cached" is the staging area's older name, as in `git diff --cached`):

<CodeExample setup={`mkdir plant-shop
cd plant-shop
git init
echo "<h1>Tom's Plant Shop</h1>" > index.html
echo "Server started" > server.log
git add .
git commit -m "Add the home page"
echo "*.log" > .gitignore
echo "Server stopped" >> server.log`} output={`rm 'server.log'
On branch main
Changes to be committed:
  (use "git restore --staged <file>..." to unstage)
	deleted:    server.log

Untracked files:
  (use "git add <file>..." to include in what will be committed)
	.gitignore

index.html  server.log
[main 3078e22] Stop tracking server.log
 2 files changed, 1 insertion(+), 1 deletion(-)
 create mode 100644 .gitignore
 delete mode 100644 server.log
On branch main
nothing to commit, working tree clean`}>

```bash
git rm --cached server.log
git status
ls
git add .gitignore
git commit -m "Stop tracking server.log"
git status
```

</CodeExample>

- `git rm --cached` prints `rm 'server.log'` and stages the file as **deleted**: the next commit won't have it.
- `ls` shows the file is still in the folder. Without `--cached`, `git rm` would delete it from the disk too.
- After the commit, the working tree is clean: `server.log` is now untracked **and** ignored, so Git stays quiet however much the server writes.

The file is gone only from the **new** commits. The old ones still hold it: run `git show` on the first commit and it's there. That's what you want for a log, but not for a secret.

<Callout type="danger" title="A committed secret is a leaked secret">

If a password or key ever gets into a commit, `git rm --cached` and `.gitignore` won't take it back out of the history, and anyone with a copy of the repository can still read it. Treat it as leaked: **change the password or make a new key**. The safe habit is to put `.env` in `.gitignore` **before** your first commit.

</Callout>

## Common mistakes

- **Expecting `.gitignore` to untrack a committed file.** It doesn't. Use `git rm --cached file`, then commit.
- **Forgetting to commit `.gitignore`.** It's a normal project file. Commit it so the rules travel with the project.
- **Putting the `!` exception first.** The last matching line wins, so `!keep.log` must come after `*.log`.
- **Running `git rm` without `--cached`.** That deletes the file from the folder too. With a log you may not mind, but with your settings you would.
- **Adding a secret first and ignoring it later.** By then it's in the history. Ignore `.env` before the first commit.

<Callout type="tip" title="On your own computer">

- GitHub keeps ready-made `.gitignore` files for most languages and tools at [github.com/github/gitignore](https://github.com/github/gitignore): a good place to start a new project's file.
- Junk that every project on your computer makes, like `.DS_Store`, can go in your **own** ignore file instead: `~/.config/git/ignore`. Git reads it in every repository, so you don't have to add the same line to each project.

</Callout>

## Recap

- **`.gitignore`** lists patterns, one per line, for **untracked** files that Git should act as if it can't see. Commit it with the project.
- **`*.log`** matches in every folder, **`build/`** matches folders only, **`/config.txt`** only the top folder, **`!keep.log`** makes an exception, and **`#`** starts a comment.
- The **last** matching line wins, and a file inside an ignored folder can't be brought back with `!`.
- **`git check-ignore file`** prints the file's name if it's ignored (`-v` on your computer also shows the rule).
- `.gitignore` doesn't untrack anything: **`git rm --cached file`** stops tracking a committed file and keeps it on the disk.
- A secret that was ever committed stays in the history: change it.
