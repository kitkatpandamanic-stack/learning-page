В любом проекте копятся файлы, которым не место в истории: логи, которые растут при каждом запуске программы, папки, которые инструмент собирает заново сам, файл с паролем, мусор, который оставляет операционная система. Удалите их — они появятся снова. Оставите — один быстрый `git add .` сметёт их все в коммит. 🧹

Решение — маленький файл **`.gitignore`**: список имён и шаблонов, которые Git должен делать вид, что не видит. В этом уроке вы напишете такой файл, разберётесь с его шаблонами, проверите их и узнаете, что делать с файлом, который уже успели закоммитить.

## Файлы, которым не место в Git

Том делает сайт для своего магазина растений. В его репозитории `plant-shop` один коммит с `index.html` и `style.css`. С тех пор появилось ещё несколько файлов:

<CodeExample setup={`mkdir -p plant-shop/build plant-shop/logs
cd plant-shop
git init
echo "<h1>Tom's Plant Shop</h1>" > index.html
echo "body { color: green; }" > style.css
git add .
git commit -m "Добавить главную страницу"
echo "Server started" > server.log
echo "Page not found: /cactus" > logs/errors.log
echo "<h1>Tom's Plant Shop</h1>" > build/index.html
echo "API_KEY=test-1234" > .env
touch .DS_Store`} output={`On branch main
Untracked files:
  (use "git add <file>..." to include in what will be committed)
	.DS_Store
	.env
	build/
	logs/
	server.log

nothing added to commit but untracked files present (use "git add" to track)`}>

```bash
git status
```

</CodeExample>

Ни один из неотслеживаемых файлов нельзя коммитить:

- **`server.log`** и **`logs/`** — **логи** (log files): программа записывает их, пока работает. Они всё время меняются и полезны только на том компьютере, где появились.
- **`build/`** — **результаты сборки** (build output): файлы, которые инструмент делает из ваших файлов (например, сжатую копию сайта). Их всегда можно собрать заново, так что в истории они только занимают место.
- **`.env`** — **секреты**: пароли и ключи API (`.env` — обычное имя для такого файла). Их сможет прочитать любой, кто видит репозиторий.
- **`.DS_Store`** — системный мусор. macOS оставляет такой файл в каждой папке, которую вы открыли в Finder. (В Windows похожий файл называется `Thumbs.db`.)

В настоящих проектах встретятся и другие: `node_modules/` (пакеты, которые скачивает проект на JavaScript) или `__pycache__/` (скомпилированные файлы Python).

## Ваш первый .gitignore

`.gitignore` — обычный текстовый файл в верхней папке репозитория, **по одному шаблону на строку**. Его имя начинается с точки, поэтому он скрытый, как `.git`. Том записывает его через `echo` и снова смотрит статус:

<CodeExample setup={`mkdir -p plant-shop/build plant-shop/logs
cd plant-shop
git init
echo "<h1>Tom's Plant Shop</h1>" > index.html
echo "body { color: green; }" > style.css
git add .
git commit -m "Добавить главную страницу"
echo "Server started" > server.log
echo "Page not found: /cactus" > logs/errors.log
echo "<h1>Tom's Plant Shop</h1>" > build/index.html
echo "API_KEY=test-1234" > .env
touch .DS_Store`} output={`*.log
build/
.env
.DS_Store
On branch main
Untracked files:
  (use "git add <file>..." to include in what will be committed)
	.gitignore

nothing added to commit but untracked files present (use "git add" to track)`}>

```bash
echo "*.log" > .gitignore
echo "build/" >> .gitignore
echo ".env" >> .gitignore
echo ".DS_Store" >> .gitignore
cat .gitignore
git status
```

</CodeExample>

Весь мусор пропал из списка. Сами файлы на месте (`ls -a` их покажет), просто Git о них больше не упоминает. Единственный новый файл — сам `.gitignore`, и вот его коммитить **нужно**: он часть проекта, и у всех, кто над ним работает, будут одни и те же правила.

<CodeExample setup={`mkdir -p plant-shop/build plant-shop/logs
cd plant-shop
git init
echo "<h1>Tom's Plant Shop</h1>" > index.html
echo "body { color: green; }" > style.css
git add .
git commit -m "Добавить главную страницу"
echo "Server started" > server.log
echo "Page not found: /cactus" > logs/errors.log
echo "<h1>Tom's Plant Shop</h1>" > build/index.html
echo "API_KEY=test-1234" > .env
touch .DS_Store
echo "*.log" > .gitignore
echo "build/" >> .gitignore
echo ".env" >> .gitignore
echo ".DS_Store" >> .gitignore`} output={`[main b1535c0] Добавить .gitignore
 1 file changed, 4 insertions(+)
 create mode 100644 .gitignore
On branch main
nothing to commit, working tree clean`}>

```bash
git add .
git commit -m "Добавить .gitignore"
git status
```

</CodeExample>

Теперь `git add .` снова безопасен: он подготавливает `.gitignore` и пропускает всё, что в нём перечислено.

## Шаблоны

Каждая строка `.gitignore` — это **шаблон** (pattern), очень похожий на шаблоны, которые вы использовали с `ls` и `rm`. Вот эти покрывают почти всё, что понадобится:

| Шаблон        | Что игнорирует                                                   |
| ------------- | ---------------------------------------------------------------- |
| `.env`        | каждый файл или папку с именем `.env`, в любой папке             |
| `*.log`       | каждое имя, которое заканчивается на `.log`, в любой папке       |
| `build/`      | папки с именем `build` вместе со всем содержимым                 |
| `/config.txt` | `config.txt` только в верхней папке                              |
| `!keep.log`   | ничего: это исключение, которое возвращает `keep.log`            |
| `# Логи`      | ничего: строка, которая начинается с `#`, — комментарий          |

Несколько деталей, которые стоит знать:

- **Нет косой черты** в шаблоне — значит «где угодно»: `*.log` выше подошёл и к `server.log`, и к `logs/errors.log`.
- **Косая черта в конце** значит «только папки»: `build/` игнорирует папку `build`, но не файл с таким именем.
- **Косая черта в начале** значит «только в верхней папке» (той, где лежит `.gitignore`).
- Пустые строки пропускаются, так что правила можно группировать с комментариями.

Вот какую разницу даёт косая черта в начале. У Тома два файла `config.txt`: его собственные настройки наверху и страница документации в `docs/`:

<CodeExample setup={`mkdir -p plant-shop/docs
cd plant-shop
git init
echo "<h1>Tom's Plant Shop</h1>" > index.html
git add .
git commit -m "Добавить главную страницу"
echo "debug=true" > config.txt
echo "Как настроить магазин" > docs/config.txt`} output={`?? config.txt
?? docs/
?? .gitignore
?? .gitignore
?? docs/`}>

```bash
git status -s
echo "config.txt" > .gitignore
git status -s
echo "/config.txt" > .gitignore
git status -s
```

</CodeExample>

Каждый `echo` с `>` заменяет весь `.gitignore` одной строкой, так что два правила легко сравнить. С `config.txt` пропадают оба файла, и документация тоже. С `/config.txt` игнорируется только верхний, а `docs/` снова появляется.

## Исключения с !

Строка, которая начинается с **`!`**, делает исключение из правила выше. Том хочет игнорировать все логи, кроме `keep.log` — короткого лога, которым он делится с дизайнером:

<CodeExample setup={`mkdir -p plant-shop/build plant-shop/logs
cd plant-shop
git init
echo "<h1>Tom's Plant Shop</h1>" > index.html
echo "body { color: green; }" > style.css
git add .
git commit -m "Добавить главную страницу"
echo "Server started" > server.log
echo "Page not found: /cactus" > logs/errors.log
echo "<h1>Tom's Plant Shop</h1>" > build/index.html
echo "API_KEY=test-1234" > .env
touch .DS_Store
echo "Moved the cactus photo" > keep.log`} output={`# Логи, кроме общего
*.log
!keep.log
?? .DS_Store
?? .env
?? .gitignore
?? build/
?? keep.log`}>

```bash
echo "# Логи, кроме общего" > .gitignore
echo "*.log" >> .gitignore
echo "!keep.log" >> .gitignore
cat .gitignore
git status -s
```

</CodeExample>

`server.log` по-прежнему игнорируется, `logs/` не видно, а `keep.log` вернулся. Порядок важен: Git читает файл сверху вниз, и побеждает **последняя** подходящая строка, поэтому строка с `!` должна стоять **после** `*.log`.

<Callout type="warning" title="Файл из игнорируемой папки не вернуть">

Если папка игнорируется, Git даже не заглядывает внутрь. Поэтому `build/`, а за ним `!build/keep.txt` не сработает: `keep.txt` останется игнорируемым вместе со всей папкой.

</Callout>

## Игнорируется ли файл? git check-ignore

Если файл появился в списке (или пропал) и непонятно почему, спросите Git. **`git check-ignore`** принимает имена файлов и печатает обратно те, что игнорируются. Для файла, который не игнорируется, он не печатает ничего:

<CodeExample setup={`mkdir -p plant-shop/build plant-shop/logs
cd plant-shop
git init
echo "<h1>Tom's Plant Shop</h1>" > index.html
echo "body { color: green; }" > style.css
git add .
git commit -m "Добавить главную страницу"
echo "Server started" > server.log
echo "Page not found: /cactus" > logs/errors.log
echo "<h1>Tom's Plant Shop</h1>" > build/index.html
echo "API_KEY=test-1234" > .env
touch .DS_Store
echo "*.log" > .gitignore
echo "build/" >> .gitignore
echo ".env" >> .gitignore
echo ".DS_Store" >> .gitignore`} output={`server.log
logs/errors.log
build/index.html
build/new-page.html`}>

```bash
git check-ignore server.log
git check-ignore logs/errors.log build/index.html index.html
git check-ignore index.html
git check-ignore build/new-page.html
```

</CodeExample>

`index.html` не игнорируется, поэтому его нет в ответе. Последняя строка показывает, что файлу даже не обязательно существовать: всё, что вы потом положите в `build/`, тоже будет игнорироваться.

На вашем компьютере **`git check-ignore -v`** (verbose — «подробно») ещё и говорит, какое правило сработало: в виде `файл:строка:шаблон`, а за ним имя:

```text
.gitignore:1:*.log	server.log
```

## Игнорируемые файлы и git add

А если назвать игнорируемый файл прямо, как в `git add server.log`? Git откажется. Он напечатает `The following paths are ignored by one of your .gitignore files` («эти пути игнорируются одним из ваших файлов .gitignore»), перечислит файл и подскажет `-f` (force — «принудительно»), если вы действительно хотите его добавить.

Почти никогда не хотите. Если приходится добавлять файл силой, обычно это значит, что правило слишком широкое: лучше поправить `.gitignore` (например, исключением с `!`).

## Игнорирование не снимает отслеживание

Вот ловушка, на которой все хотя бы раз попадаются. `.gitignore` касается только **неотслеживаемых** файлов. Файл, который уже есть в коммите, остаётся отслеживаемым, что бы ни говорил `.gitignore`.

В этой версии проекта Том закоммитил `server.log`, когда ещё не знал, что так не надо. Он добавляет `*.log` в `.gitignore`, сервер дописывает строку, и…

<CodeExample setup={`mkdir plant-shop
cd plant-shop
git init
echo "<h1>Tom's Plant Shop</h1>" > index.html
echo "Server started" > server.log
git add .
git commit -m "Добавить главную страницу"`} output={`On branch main
Changes not staged for commit:
  (use "git add <file>..." to update what will be committed)
  (use "git restore <file>..." to discard changes in working directory)
	modified:   server.log

Untracked files:
  (use "git add <file>..." to include in what will be committed)
	.gitignore

no changes added to commit (use "git add" and/or "git commit -a")`}>

```bash
echo "*.log" > .gitignore
echo "Server stopped" >> server.log
git status
```

</CodeExample>

…`server.log` по-прежнему в списке изменённых. Git продолжает его отслеживать, потому что файл есть в последнем коммите. Чтобы это прекратить, уберите его из **области подготовки**, но оставьте на диске командой **`git rm --cached`** («cached» — старое название области подготовки, как в `git diff --cached`):

<CodeExample setup={`mkdir plant-shop
cd plant-shop
git init
echo "<h1>Tom's Plant Shop</h1>" > index.html
echo "Server started" > server.log
git add .
git commit -m "Добавить главную страницу"
echo "*.log" > .gitignore
echo "Server stopped" >> server.log`} output={`rm 'server.log'
On branch main
Changes to be committed:
  (use "git restore --staged <file>..." to unstage)
	deleted:    server.log

Untracked files:
  (use "git add <file>..." to include in what will be committed)
	.gitignore

index.html  server.log
[main b41fce9] Перестать отслеживать server.log
 2 files changed, 1 insertion(+), 1 deletion(-)
 create mode 100644 .gitignore
 delete mode 100644 server.log
On branch main
nothing to commit, working tree clean`}>

```bash
git rm --cached server.log
git status
ls
git add .gitignore
git commit -m "Перестать отслеживать server.log"
git status
```

</CodeExample>

- `git rm --cached` печатает `rm 'server.log'` и подготавливает файл как **удалённый** (deleted): в следующем коммите его не будет.
- `ls` показывает, что файл по-прежнему в папке. Без `--cached` команда `git rm` удалила бы его и с диска.
- После коммита рабочая папка чистая: `server.log` теперь неотслеживаемый **и** игнорируемый, так что Git молчит, сколько бы сервер ни писал.

Файл пропал только из **новых** коммитов. Старые его по-прежнему хранят: выполните `git show` для первого коммита — он там. Для лога это ровно то, что нужно, а вот для секрета — нет.

<Callout type="danger" title="Закоммиченный секрет — утёкший секрет">

Если пароль или ключ хоть раз попал в коммит, `git rm --cached` и `.gitignore` не уберут его из истории, и любой, у кого есть копия репозитория, всё ещё может его прочитать. Считайте, что он утёк: **смените пароль или выпустите новый ключ**. Безопасная привычка — добавить `.env` в `.gitignore` **до** первого коммита.

</Callout>

В `plant-shop` у Тома с первого коммита накопился мусор. Уберите его из Git навсегда, **не удаляя файлы**:

1. Запустите `git status`, чтобы увидеть неотслеживаемые файлы.
2. Напишите `.gitignore`, который игнорирует **все** файлы `.log` (в любой папке), всю папку `build`, `.env` и `.DS_Store`. Пользуйтесь шаблонами, чтобы завтрашние логи и файлы сборки тоже игнорировались.
3. Снова запустите `git status`: единственным неотслеживаемым файлом должен остаться `.gitignore`.
4. Закоммитьте `.gitignore` со своим сообщением и закончите чистым `git status`.

<Hint>

Четыре вида мусора — значит, четыре строки. Один шаблон со `*` покрывает все логи, где бы они ни лежали, а шаблон с `/` в конце — целую папку.

</Hint>

<Hint>

`echo "…" > .gitignore` записывает первую строку, а `>>` добавляет остальные. Потом `git add .gitignore` и `git commit -m "…"`.

</Hint>

Том закоммитил `server.log` в самом первом коммите, и теперь `git status` пристаёт к нему после каждого запуска сервера. Исправьте это раз и навсегда:

1. Запустите `git status`: `server.log` показан как изменённый.
2. Создайте `.gitignore` со строкой `*.log`.
3. Перестаньте отслеживать `server.log`, **не удаляя его** из папки.
4. Закоммитьте оба изменения с сообщением `Перестать отслеживать server.log` и проверьте, что `git status` чистый.

<Hint>

</Hint>

## Частые ошибки

- **Ждать, что `.gitignore` снимет отслеживание с закоммиченного файла.** Не снимет. Выполните `git rm --cached файл`, потом коммит.
- **Забыть закоммитить `.gitignore`.** Это обычный файл проекта. Закоммитьте его, чтобы правила путешествовали вместе с проектом.
- **Поставить исключение с `!` первым.** Побеждает последняя подходящая строка, поэтому `!keep.log` должна идти после `*.log`.
- **Запустить `git rm` без `--cached`.** Тогда файл удалится и из папки. Лог, может, и не жалко, а вот свои настройки — жалко.
- **Сначала добавить секрет, а потом его игнорировать.** К тому времени он уже в истории. Игнорируйте `.env` до первого коммита.

<Callout type="tip" title="На вашем компьютере">

- На GitHub есть готовые `.gitignore` для большинства языков и инструментов: [github.com/github/gitignore](https://github.com/github/gitignore). С них удобно начинать файл для нового проекта.
- Мусор, который появляется в любом проекте на вашем компьютере, вроде `.DS_Store`, можно записать в **свой собственный** файл игнорирования: `~/.config/git/ignore`. Git читает его в каждом репозитории, так что одну и ту же строку не придётся добавлять в каждый проект.

</Callout>

## Итоги

- **`.gitignore`** перечисляет шаблоны, по одному на строку, для **неотслеживаемых** файлов, которые Git должен делать вид, что не видит. Коммитьте его вместе с проектом.
- **`*.log`** подходит в любой папке, **`build/`** — только к папкам, **`/config.txt`** — только в верхней папке, **`!keep.log`** делает исключение, а **`#`** начинает комментарий.
- Побеждает **последняя** подходящая строка, а файл внутри игнорируемой папки через `!` не вернуть.
- **`git check-ignore файл`** печатает имя файла, если он игнорируется (`-v` на вашем компьютере ещё и показывает правило).
- `.gitignore` ни с чего не снимает отслеживание: **`git rm --cached файл`** перестаёт отслеживать закоммиченный файл и оставляет его на диске.
- Секрет, который хоть раз попал в коммит, остаётся в истории: смените его.

Дальше: [Отменяем изменения](/learn/git/undoing-changes) — выбросим правку, уберём файл из области подготовки и исправим последний коммит.
