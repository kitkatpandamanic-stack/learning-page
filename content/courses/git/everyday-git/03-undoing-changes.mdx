Everyone makes mistakes: an edit that went wrong, a file staged by accident, a commit with a typo in its message or a file missing. With Git, most of these take one command to fix. 🩹

Each mistake lives in one of the three places your work moves through, and each place has its own undo:

| The mistake is in…   | Undo it with                 | What it does                                     |
| -------------------- | ---------------------------- | ------------------------------------------------ |
| the working folder   | `git restore file`           | throws your edits away                           |
| the staging area     | `git restore --staged file`  | unstages the file and keeps your edits           |
| the last commit      | `git commit --amend`         | replaces the last commit with a fixed one        |

The examples use Zara's `bakery` repository from the last two lessons: `menu.txt` and `hours.txt`, three commits, and a clean working tree to start.

## Throw away an edit: git restore

You've seen this hint in `git status` since Level 0: `(use "git restore <file>..." to discard changes in working directory)`. Here it is in action. Zara pasted something into the wrong file and wiped out her opening hours:

**`git restore file`** puts the file back the way it is in the **staging area**. Nothing is staged here, so that's the version from the last commit. Like most Git commands that work, it prints nothing; `git status` and `cat` show the edit is gone.

It brings back deleted files too. Remember "there is no undo" for `rm`? For a file that's in a commit, there is now:

` D` means deleted from the working folder, not staged. One `git restore` and the menu is back.

<Callout type="danger" title="git restore can't be undone">

Edits you throw away were never committed, so Git has no copy of them. They're gone for good. Run `git diff` first and make sure it's really what you want to lose. And take extra care with `git restore .`: it throws away the edits in **every** file in the folder.

</Callout>

## When a bad edit is already staged

There's a trap here. Plain `git restore` copies the file back **from the staging area**. If the bad edit is staged, the staging area holds the bad version, so `git restore` puts back… the bad version. Undo it in two steps: unstage first, then throw the edit away:

<CodeExample setup={`mkdir bakery
cd bakery
git init
echo "1. Croissant - 2.50" > menu.txt
echo "2. Bagel - 2.00" >> menu.txt
echo "3. Muffin - 2.20" >> menu.txt
echo "4. Cinnamon roll - 3.00" >> menu.txt
echo "5. Brownie - 2.80" >> menu.txt
echo "6. Cookie - 1.50" >> menu.txt
echo "7. Lemon tart - 3.50" >> menu.txt
echo "8. Cheesecake - 4.00" >> menu.txt
echo "9. Apple pie - 3.80" >> menu.txt
git add menu.txt
git commit -m "Add the menu"
echo "Open every day, 8:00 to 18:00" > hours.txt
git add hours.txt
git commit -m "Add opening hours"
echo "10. Banana bread - 2.60" >> menu.txt
git add menu.txt
git commit -m "Add banana bread"`} output={`M  hours.txt
 M hours.txt
Open every day, 8:00 to 18:00`}>

```bash
echo "Closed" > hours.txt
git add hours.txt
git restore hours.txt
git status -s
git restore --staged hours.txt
git status -s
git restore hours.txt
git status -s
cat hours.txt
```

</CodeExample>

Follow the codes: after the first `git restore`, it's still `M ` (staged). `git restore --staged` turns it into ` M` (not staged), and only then does `git restore` bring back the committed hours, with nothing left in `git status -s`.

<Callout type="note" title="The older way: git checkout -- file">

`git restore` arrived in Git 2.23, in 2019. Before that, you threw edits away with `git checkout`, and you'll still see it in older tutorials and answers online:

```bash
git checkout -- hours.txt
```

This does the same as `git restore hours.txt`. The `--` means "what follows is a file name". `git checkout` does several different jobs, including switching branches (that's the next module), which is why Git added `git restore` with a clearer name. Use `git restore`; just recognise the other one when you meet it.

</Callout>

## Fix the last commit: git commit --amend

Sometimes the mistake is already committed: a typo in the message, or a file you forgot to stage. If it's the **last** commit, **`git commit --amend`** fixes it.

`git commit --amend -m "…"` replaced the commit with one that has the new message. The extra ` Date:` line shows the date of the original commit: amending keeps it. The history has no trace of the typo.

Look at the hash, though: the commit was `3323a8c`, now it's `98e076a`. A commit can never change, because its hash is calculated from everything in it, the message included. So `--amend` doesn't edit the old commit: it makes a **new** commit and puts it in the old one's place.

### Don't amend what you've shared

Because amending swaps the commit for a new one, it's safe only while the commit is **yours alone**. In Level 2 you'll start sending commits to a shared server (like GitHub) where teammates copy them. If you amend a commit that someone else already has, your history and theirs now hold two different versions of it, and sorting that out is a real headache.

The rule: **amend only commits you haven't shared yet.** To fix a commit that's already shared, you make a new commit on top instead.

Bigger undos, like going back several commits or undoing a commit that's already shared, use `git reset` and `git revert`. They come in Level 3; until then this practice terminal answers them with "isn't in this practice terminal yet".

## Common mistakes

- **Running `git restore` on edits you wanted.** They're gone for good. Check with `git diff` first.
- **Expecting `git restore` to undo a staged change.** It copies from the staging area, so unstage with `--staged` first.
- **Thinking `--staged` throws edits away.** It only unstages; the edits stay in the file.
- **Amending when you meant a new commit.** `--amend` changes the last commit. If that commit was finished and good, make a new one instead.
- **Amending a shared commit.** Fine on your own computer, trouble once others have it.

## Recap

- **`git restore file`** throws away unstaged edits and brings back deleted files, from the staging area. It can't be undone.
- **`git restore --staged file`** unstages a file and keeps its edits. A new file goes back to untracked.
- A **staged** bad edit takes two steps: `git restore --staged file`, then `git restore file`.
- **`git checkout -- file`** is the older way to throw edits away; you'll meet it in older tutorials.
- **`git commit --amend -m "…"`** replaces the last commit with a new one: a new message, plus anything you've staged since. **`--no-edit`** keeps the message.
- Amending makes a **new hash**. Amend only commits you haven't shared; sharing comes in Level 2, and `git reset` and `git revert` in Level 3.
