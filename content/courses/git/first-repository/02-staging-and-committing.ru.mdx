В прошлом уроке вы создали репозиторий, и Git заметил новый файл, но назвал его **неотслеживаемым** (untracked). Теперь вы сохраните этот файл в истории Git — сделаете свой первый **коммит**. 📸

Сохранение версии в Git всегда проходит в **два шага**: сначала вы выбираете, что в неё войдёт, а потом сохраняете с сообщением. Это похоже на групповое фото: сначала вы приглашаете людей на сцену, потом делаете снимок. Кто не вышел на сцену, тот в кадр не попал.

## Три места, где живёт ваша работа

Git представляет проект как три места:

```text
┌─────────────────────┐
│    рабочая папка    │   ваши файлы, которые вы правите
└──────────┬──────────┘
           │ git add
           ▼
┌─────────────────────┐
│ область подготовки  │   то, что войдёт в следующий коммит
└──────────┬──────────┘
           │ git commit
           ▼
┌─────────────────────┐
│     репозиторий     │   сохранённая история (внутри .git)
└─────────────────────┘
```


- **Рабочая папка** (working folder) — папка проекта, которую вы видите через `ls`. Здесь вы, как обычно, создаёте и меняете файлы.
- **Область подготовки** (staging area) — список изменений, которые войдут в **следующий** коммит. Изменения попадают туда командой `git add`. Её ещё называют **индексом** (index), а добавление в неё — **индексацией**.
- **Репозиторий** — это история: все коммиты, сохранённые внутри `.git`. `git commit` берёт всё из области подготовки и сохраняет как новый коммит.

Зачем нужен средний шаг? Чтобы вы сами решали, что войдёт в каждый коммит. Допустим, вы исправили опечатку в одном файле и начали новый рецепт в другом: благодаря области подготовки их можно сохранить двумя отдельными коммитами, каждый со своим сообщением.

## Добавляем файл в индекс: git add

Каждый пример в этом уроке начинается в репозитории `recipes` (вы находитесь внутри него) с одним неотслеживаемым файлом `pancakes.txt` — как в конце прошлого урока. **`git add`** с именем файла кладёт этот файл в область подготовки:

<CodeExample setup={`mkdir recipes
cd recipes
git init
echo "Блины: 2 яйца, 1 стакан молока, 1 стакан муки" > pancakes.txt`} output={`On branch main

No commits yet

Changes to be committed:
  (use "git rm --cached <file>..." to unstage)
	new file:   pancakes.txt`}>

```bash
git add pancakes.txt
git status
```

</CodeExample>

Если всё получилось, `git add` ничего не выводит. Результат показывает `git status`: `pancakes.txt` переехал из «Untracked files» в **Changes to be committed** («изменения, которые будут закоммичены») с пометкой `new file` («новый файл»). Он подготовлен, но **ещё не сохранён**. Пока вы не сделаете коммит, в истории ничего нет. (Подсказку в скобках пока пропустите: отмену изменений мы разберём на уровне 1.)

## Сохраняем: git commit -m

**`git commit -m "сообщение"`** сохраняет всё из области подготовки как новый коммит. Текст после **`-m`** (message) — это **сообщение коммита**: короткая заметка о том, что меняет эта версия. Возьмите его в кавычки, ведь в нём есть пробелы.

<CodeExample setup={`mkdir recipes
cd recipes
git init
echo "Блины: 2 яйца, 1 стакан молока, 1 стакан муки" > pancakes.txt`} output={`[main (root-commit) 8391db2] Добавить рецепт блинов
 1 file changed, 1 insertion(+)
 create mode 100644 pancakes.txt
On branch main
nothing to commit, working tree clean`}>

```bash
git add pancakes.txt
git commit -m "Добавить рецепт блинов"
git status
```

</CodeExample>

Ваш первый коммит! 🎉 Разберём, что напечатал Git:

- **`[main (root-commit) 8391db2]`** — коммит лёг на линию истории `main`. `root-commit` («корневой коммит») значит, что он самый первый. `8391db2` — начало его **хеша** (hash), уникального идентификатора коммита. Читать хеши вы научитесь в следующем уроке. (В учебном терминале часы фиксированные, поэтому хеш каждый раз один и тот же. На вашем компьютере он будет другим.)
- **`Добавить рецепт блинов`** — ваше сообщение.
- **`1 file changed, 1 insertion(+)`** — изменился один файл, в нём одна новая строка. `create mode 100644` просто означает, что появился новый обычный файл.

А `git status` теперь пишет **nothing to commit, working tree clean** — «нечего коммитить, рабочая папка чистая»: каждый файл в рабочей папке совпадает с последним коммитом. Именно к этому спокойному состоянию стоит приходить после каждого куска работы.

<Callout type="warning" title="Здесь всегда пишите -m">

На настоящем компьютере `git commit` без `-m` открывает **текстовый редактор**, чтобы вы написали сообщение в нём. Учебный терминал редакторы открывать не умеет, поэтому останавливается с ошибкой `Aborting commit due to empty commit message` («коммит отменён: пустое сообщение»). Привыкайте писать `git commit -m "…"` с сообщением в кавычках: так работает везде.

</Callout>

## Меняем файл и коммитим снова

Теперь `pancakes.txt` **отслеживается** (tracked): он есть в коммите, и Git замечает любое его изменение. Начнём с репозитория с этим единственным коммитом и допишем строку в рецепт:

<CodeExample setup={`mkdir recipes
cd recipes
git init
echo "Блины: 2 яйца, 1 стакан молока, 1 стакан муки" > pancakes.txt
git add pancakes.txt
git commit -m "Добавить рецепт блинов"`} output={`On branch main
Changes not staged for commit:
  (use "git add <file>..." to update what will be committed)
  (use "git restore <file>..." to discard changes in working directory)
	modified:   pancakes.txt

no changes added to commit (use "git add" and/or "git commit -a")`}>

```bash
echo "Жарить каждый блин по 1 минуте с каждой стороны" >> pancakes.txt
git status
```

</CodeExample>

Файл **изменён** (modified), а изменение **не подготовлено** (not staged). Дальше те же два шага: `git add`, затем `git commit`. На этот раз попробуйте **`git add .`**: точка означает «эта папка», поэтому команда сразу подготавливает все новые и изменённые файлы в ней.

<CodeExample setup={`mkdir recipes
cd recipes
git init
echo "Блины: 2 яйца, 1 стакан молока, 1 стакан муки" > pancakes.txt
git add pancakes.txt
git commit -m "Добавить рецепт блинов"`} output={`[main b89e058] Добавить время жарки блинов
 1 file changed, 1 insertion(+)
b89e058 (HEAD -> main) Добавить время жарки блинов
8391db2 Добавить рецепт блинов`}>

```bash
echo "Жарить каждый блин по 1 минуте с каждой стороны" >> pancakes.txt
git add .
git commit -m "Добавить время жарки блинов"
git log --oneline
```

</CodeExample>

`git log --oneline` перечисляет коммиты от новых к старым: две версии рецепта, у каждой своё сообщение. Как читать историю по-настоящему, вы узнаете в [следующем уроке](/learn/git/reading-the-history).

<Callout type="tip" title="git add . добавляет всё">

`git add .` — это быстро, но команда подготавливает **все** изменения в папке, включая файлы, которые вы коммитить не собирались. Сначала запустите `git status`, чтобы точно знать, что попадёт в коммит.

</Callout>

## Короткая версия git status

Когда вы освоились с длинным `git status`, **`git status -s`** (short — «коротко») сообщает то же самое, по одной строке на файл. Вот новый файл и изменение в `pancakes.txt` до и после `git add .`:

<CodeExample setup={`mkdir recipes
cd recipes
git init
echo "Блины: 2 яйца, 1 стакан молока, 1 стакан муки" > pancakes.txt
git add pancakes.txt
git commit -m "Добавить рецепт блинов"`} output={` M pancakes.txt
?? waffles.txt
M  pancakes.txt
A  waffles.txt`}>

```bash
echo "Вафли: 2 яйца, 2 стакана муки" > waffles.txt
echo "Подавать с мёдом" >> pancakes.txt
git status -s
git add .
git status -s
```

</CodeExample>

Две буквы перед именем — это два столбца: **левый** относится к области подготовки, **правый** — к рабочей папке.

| Код   | Что значит                                    |
| ----- | --------------------------------------------- |
| `??`  | неотслеживаемый: Git не хранит этот файл      |
| ` M`  | изменён, но ещё не подготовлен                |
| `M `  | изменён и подготовлен                         |
| `A `  | новый файл, добавлен в область подготовки     |

Когда всё закоммичено, `git status -s` не выводит вообще ничего.

## Хорошие сообщения коммитов

История полезна ровно настолько, насколько хороши её сообщения. Через месяц на вопрос «что я тут делал?» ответит сообщение — или никто. Хорошее сообщение:

- **Короткое**: одна строка, примерно до 50 символов.
- **В повелительной форме**: «Добавить рецепт супа», а не «Добавил рецепт супа» или «Добавление супа». Читайте его как «этот коммит должен… добавить рецепт супа». Так советуют и правила самого Git (по-английски это «Add soup recipe»).
- **О том, что и зачем**: «Исправить время жарки тонких блинов» говорит гораздо больше, чем «Обновить файл».

| Бесполезно         | Лучше                                     |
| ------------------ | ----------------------------------------- |
| `всякое`           | `Добавить рецепт вафель`                  |
| `изменения`        | `Взять 3 яйца, чтобы блины были пышными`  |
| `починил`          | `Исправить опечатку в названии супа`      |
| `pancakes.txt`     | `Добавить время жарки блинов`             |

<Callout type="note" title="По-русски или по-английски?">

В этом курсе сообщения коммитов на русском. Во многих командах и почти во всех открытых (open-source) проектах их пишут по-английски: `Add waffle recipe`, `Fix the typo in the soup title`. Правило о повелительной форме работает в обоих языках. В команде пишите так, как принято в команде.

</Callout>

И **коммитьте часто, маленькими шагами**: один коммит — одна мысль. Маленькие коммиты легко описать, легко прочитать потом и легко отменить. «Добавить рецепт вафель» — хороший коммит, а «Добавить вафли, починить суп, всё переименовать» — это три коммита.

## Частые ошибки

- **Коммит без `git add`.** Git не создаёт коммит, а показывает статус, который заканчивается строкой `nothing added to commit but untracked files present` («в коммит ничего не добавлено, но есть неотслеживаемые файлы») или `no changes added to commit` («в коммит не добавлено изменений»). Сначала подготовьте, потом коммитьте.
- **Думать, что `git add` сохраняет.** Подготовленного изменения ещё нет в истории. Сохраняет только `git commit`.
- **`git add` без файла.** Git ответит `Nothing specified, nothing added.` («ничего не указано, ничего не добавлено»). Укажите имя файла или `.` для всего сразу.
- **Забытые кавычки.** В `git commit -m Добавить рецепт супа` сообщением станет только `Добавить`, а что делать с `рецепт` и `супа`, Git не знает и останавливается с ошибкой. Берите сообщение в кавычки.

## Итоги

- У Git **три места**: **рабочая папка** (ваши файлы), **область подготовки**, или индекс (следующий коммит), и **репозиторий** (сохранённая история).
- **`git add файл`** подготавливает один файл; **`git add .`** — все изменения в папке.
- **`git commit -m "сообщение"`** сохраняет подготовленное как новый коммит. Без `-m` настоящий компьютер откроет редактор.
- `git status` показывает, что не отслеживается, изменено или подготовлено; **working tree clean** значит, что всё закоммичено. `git status -s` — однострочная версия.
- Хорошее сообщение **короткое**, в **повелительной форме** («Добавить…», «Исправить…») и говорит, **что и зачем**.
- **Коммитьте часто, маленькими шагами**: одна мысль — один коммит.
