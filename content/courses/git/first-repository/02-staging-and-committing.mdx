In the last lesson you made a repository, and Git spotted a new file but called it **untracked**. Now you'll save that file in Git's history: your first **commit**. 📸

Saving a version in Git always takes **two steps**: first you choose what goes in, then you save it with a message. It's a little like a group photo. First you invite people onto the stage, then you take the picture. Anyone who isn't on the stage isn't in the photo.

## Three places your work lives

Git thinks about your project in three places:

```text
┌──────────────────┐
│  working folder  │   your files, as you edit them
└────────┬─────────┘
         │ git add
         ▼
┌──────────────────┐
│   staging area   │   what goes into the next commit
└────────┬─────────┘
         │ git commit
         ▼
┌──────────────────┐
│    repository    │   the saved history (inside .git)
└──────────────────┘
```

- The **working folder** is the project folder you see with `ls`. You create and change files here, as usual.
- The **staging area** is a list of changes that will go into the **next** commit. You put changes there with `git add`. (It's also called the **index**.)
- The **repository** is the history: every commit, saved inside `.git`. `git commit` takes everything in the staging area and saves it as a new commit.

Why the middle step? Because you decide what each commit contains. You might fix a typo in one file and start a new recipe in another: with the staging area you can save them as two separate commits, each with its own message.

## Stage a file with git add

Every example in this lesson starts in a repository called `recipes` (you're inside it) with one untracked file, `pancakes.txt`, just like at the end of the last lesson. **`git add`** followed by a file name puts that file in the staging area:

<CodeExample setup={`mkdir recipes
cd recipes
git init
echo "Pancakes: 2 eggs, 1 cup of milk, 1 cup of flour" > pancakes.txt`} output={`On branch main

No commits yet

Changes to be committed:
  (use "git rm --cached <file>..." to unstage)
	new file:   pancakes.txt`}>

```bash
git add pancakes.txt
git status
```

</CodeExample>

`git add` prints nothing when it works. `git status` shows the result: `pancakes.txt` has moved from "Untracked files" to **Changes to be committed**, labelled `new file`. It's staged, but **not saved yet**. Nothing is in the history until you commit. (Ignore the hint in brackets for now; undoing comes in Level 1.)

## Save it with git commit -m

**`git commit -m "message"`** saves everything in the staging area as a new commit. The text after **`-m`** is the commit **message**: a short note that says what this version changes. Put it in quotes, because it has spaces in it.

<CodeExample setup={`mkdir recipes
cd recipes
git init
echo "Pancakes: 2 eggs, 1 cup of milk, 1 cup of flour" > pancakes.txt`} output={`[main (root-commit) 3910c23] Add pancake recipe
 1 file changed, 1 insertion(+)
 create mode 100644 pancakes.txt
On branch main
nothing to commit, working tree clean`}>

```bash
git add pancakes.txt
git commit -m "Add pancake recipe"
git status
```

</CodeExample>

Your first commit! 🎉 Here's what Git printed:

- **`[main (root-commit) 3910c23]`**: the commit went onto the `main` line of history. `root-commit` means it's the very first one. `3910c23` is the start of its **hash**, the commit's unique ID. You'll read hashes in the next lesson. (This practice terminal uses a fixed clock, so you get the same hash every time. On your own computer it'll be different.)
- **`Add pancake recipe`**: your message.
- **`1 file changed, 1 insertion(+)`**: one file changed, with one new line. `create mode 100644` just means a new, ordinary file appeared.

And `git status` now says **nothing to commit, working tree clean**: every file in the working folder matches the last commit. That's the calm state you want to reach after each piece of work.

<Callout type="warning" title="Always write -m here">

On a real computer, `git commit` without `-m` opens a **text editor** for you to write the message in. This practice terminal can't open editors, so it stops with `Aborting commit due to empty commit message`. Get into the habit of `git commit -m "…"` with the message in quotes: it works everywhere.

</Callout>

## Change a file and commit again

Now that `pancakes.txt` is **tracked** (it's in a commit), Git notices every change to it. Starting from the repository with that one commit, add a line to the recipe:

<CodeExample setup={`mkdir recipes
cd recipes
git init
echo "Pancakes: 2 eggs, 1 cup of milk, 1 cup of flour" > pancakes.txt
git add pancakes.txt
git commit -m "Add pancake recipe"`} output={`On branch main
Changes not staged for commit:
  (use "git add <file>..." to update what will be committed)
  (use "git restore <file>..." to discard changes in working directory)
	modified:   pancakes.txt

no changes added to commit (use "git add" and/or "git commit -a")`}>

```bash
echo "Fry each pancake for 1 minute on each side" >> pancakes.txt
git status
```

</CodeExample>

The file is **modified**, and the change is **not staged**. It's the same two steps as before: `git add`, then `git commit`. This time, try **`git add .`**: the dot means "this folder", so it stages every new and changed file in it at once.

<CodeExample setup={`mkdir recipes
cd recipes
git init
echo "Pancakes: 2 eggs, 1 cup of milk, 1 cup of flour" > pancakes.txt
git add pancakes.txt
git commit -m "Add pancake recipe"`} output={`[main e1238d3] Add frying time to pancakes
 1 file changed, 1 insertion(+)
e1238d3 (HEAD -> main) Add frying time to pancakes
3910c23 Add pancake recipe`}>

```bash
echo "Fry each pancake for 1 minute on each side" >> pancakes.txt
git add .
git commit -m "Add frying time to pancakes"
git log --oneline
```

</CodeExample>

`git log --oneline` lists the commits, newest first: two versions of the recipe, each with its own message. You'll learn to read the history properly in [the next lesson](/learn/git/reading-the-history).

<Callout type="tip" title="git add . adds everything">

`git add .` is quick, but it stages **every** change in the folder, including files you didn't mean to commit. Run `git status` first, so you know exactly what's going in.

</Callout>

## The short version of git status

Once you know the long `git status`, **`git status -s`** ("short") gives the same news in one line per file. Here a new file and a change to `pancakes.txt` are listed before and after `git add .`:

<CodeExample setup={`mkdir recipes
cd recipes
git init
echo "Pancakes: 2 eggs, 1 cup of milk, 1 cup of flour" > pancakes.txt
git add pancakes.txt
git commit -m "Add pancake recipe"`} output={` M pancakes.txt
?? waffles.txt
M  pancakes.txt
A  waffles.txt`}>

```bash
echo "Waffles: 2 eggs, 2 cups of flour" > waffles.txt
echo "Serve with honey" >> pancakes.txt
git status -s
git add .
git status -s
```

</CodeExample>

The two letters before each name are two columns: the **left** one is the staging area, the **right** one is the working folder.

| Code  | Meaning                                   |
| ----- | ----------------------------------------- |
| `??`  | untracked: Git isn't keeping this file    |
| ` M`  | modified, but not staged yet              |
| `M `  | modified and staged                       |
| `A `  | a new file, added to the staging area     |

When everything is committed, `git status -s` prints nothing at all.

## Good commit messages

Your history is only as useful as its messages. In a month, "what was I doing here?" is answered by the message, or not at all. Good messages are:

- **Short**: one line, about 50 characters or fewer.
- **Written as a command**: "Add soup recipe", not "Added soup recipe" or "Adding soup". Read it as "this commit will… add soup recipe". Git's own guidelines ask for this style.
- **About what and why**: "Fix cooking time for thin pancakes" says much more than "Update file".

| Not helpful        | Better                              |
| ------------------ | ----------------------------------- |
| `stuff`            | `Add waffle recipe`                 |
| `changes`          | `Use 3 eggs so pancakes are fluffy` |
| `fixed it`         | `Fix the typo in the soup title`    |
| `pancakes.txt`     | `Add frying time to pancakes`       |

And **commit often, in small steps**: one commit for one idea. Small commits are easy to describe, easy to read later and easy to undo. "Add waffle recipe" is a good commit; "Add waffles, fix soup, rename everything" is three.

## Common mistakes

- **Committing without `git add`.** Git makes no commit and prints the status instead, ending in `nothing added to commit but untracked files present` or `no changes added to commit`. Stage first, then commit.
- **Thinking `git add` saves.** A staged change isn't in the history yet. Only `git commit` saves it.
- **Running `git add` with no file.** Git says `Nothing specified, nothing added.` Give it a file name, or `.` for everything.
- **Forgetting the quotes.** In `git commit -m Add soup recipe`, only `Add` is the message, and Git doesn't know what to do with `soup` and `recipe`, so it stops with an error. Put the message in quotes.

## Recap

- Git has **three places**: the **working folder** (your files), the **staging area** (the next commit) and the **repository** (the saved history).
- **`git add file`** stages one file; **`git add .`** stages every change in the folder.
- **`git commit -m "message"`** saves what's staged as a new commit. Without `-m`, a real computer opens an editor.
- `git status` shows what's untracked, modified or staged; **working tree clean** means everything is committed. `git status -s` is the one-line version.
- Good messages are **short**, written as a **command** ("Add…", "Fix…") and say **what and why**.
- **Commit often, in small steps**: one idea per commit.
