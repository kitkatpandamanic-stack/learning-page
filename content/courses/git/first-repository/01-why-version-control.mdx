Have you ever had a folder that looks like this? 🙈

```text
essay.docx
essay_v2.docx
essay_final.docx
essay_final_v2.docx
essay_final_v2_REALLY_final.docx
```

Which one is the newest? What changed between `v2` and `final`? Which one did your teacher already read? Nobody knows, not even the person who made them. In this lesson you'll meet the tool programmers use instead of copies: **version control**. By the end you'll have turned a folder into your first **Git repository**.

## The trouble with copies

Saving a copy before a big change is a good instinct. The trouble is everything the copies _don't_ tell you:

- **What changed?** You'd have to open two files side by side and hunt for differences.
- **Why did it change?** The file name can't explain that "v2 cuts the boring intro".
- **Who changed it, and when?** Not a word about it, so when two people send copies back and forth, someone's work gets overwritten.
- **Which is the real one?** Copies pile up, and soon nobody dares to delete any of them.

Code has the same problem, only worse: a project can have hundreds of files, and one wrong change can break the whole thing.

## What version control does

A **version control system** is a program that remembers every saved version of your project for you. You keep working in **one folder**, with **one copy** of each file, and whenever you reach a good moment you tell it "save this version". Later you can:

- see the **whole list** of saved versions, newest first,
- see exactly **what changed** in each one, line by line,
- read **who** saved it, **when** and **why**,
- go back to any older version if something breaks.

The most popular version control system by far is **Git**. It's free, it runs on your own computer, and almost every software team in the world uses it. That's the one you'll learn in this course.

## Repositories and commits

Two words come up all the time with Git:

- A **repository** (or **repo**) is a project folder that Git looks after: your files plus the full history of their saved versions.
- A **commit** is one saved version: a **snapshot** of all the project's files at one moment. Each commit also records a **message** that says what changed, the **author** who made it and the **date**.

So the essay folder above becomes one `essay.docx` in a repository, and the history inside Git reads something like "Write the first draft", "Cut the boring intro", "Fix the spelling in the title". Each of those is a commit.

<Callout type="note" title="Git and GitHub are not the same thing">

**Git** is the program on your computer that keeps the history. **GitHub** is a website that stores Git repositories online, so you can share them and work on them with other people. You'll connect a repository to a website like that in Level 2. Everything in Level 0 happens on your own computer (here: in your browser), with no website and no account.

</Callout>

## Make a folder a repository with git init

Every Git command starts with the word `git`, then the thing you want it to do. To start tracking a folder, go into it and run **`git init`** ("initialise"):

<CodeExample output={`Initialized empty Git repository in /home/panda/recipes/.git/`}>

```bash
mkdir recipes
cd recipes
git init
```

</CodeExample>

That's it: `recipes` is now a repository. "Empty" means there are no commits in it yet. On your own computer the path will be your own folder, like `/Users/mei/recipes/.git/` on a Mac.

You only run `git init` **once per project**, at the start. You don't need it again to save new versions.

## The hidden .git folder

The message says Git made something called `.git` inside `recipes`. But plain `ls` shows nothing at all:

<CodeExample setup={`mkdir recipes
cd recipes
git init`} output={`.  ..  .git`}>

```bash
ls
ls -a
```

</CodeExample>

Names that start with a dot are **hidden**, and `ls` skips them. **`ls -a`** ("all") shows them too: `.` is this folder, `..` is the one above it, and **`.git`** is where Git keeps the whole history of your project: every commit, every message, every old version of every file.

<Callout type="warning" title="Never edit or delete .git">

Leave the `.git` folder alone: Git looks after it. Don't edit the files inside, and don't delete it. **Deleting `.git` deletes the whole history**, and your folder becomes an ordinary folder again. Your files stay, but every saved version is gone.

</Callout>

## Ask Git what's going on with git status

**`git status`** is the command you'll run more than any other. It tells you where things stand right now. In a brand-new repository there isn't much to tell:

<CodeExample setup={`mkdir recipes
cd recipes
git init`} output={`On branch main

No commits yet

nothing to commit (create/copy files and use "git add" to track)`}>

```bash
git status
```

</CodeExample>

- **`On branch main`**: `main` is the name of the main line of your history. You'll meet branches in Level 1. On your computer Git may say `master` unless you set it up otherwise; that's just an older name for the same thing.
- **`No commits yet`**: nothing has been saved so far.
- The last line tells you what to do next: make some files.

So let's make one, with `echo` and `>` as you did in Files & Folders, and ask again:

<CodeExample setup={`mkdir recipes
cd recipes
git init`} output={`On branch main

No commits yet

Untracked files:
  (use "git add <file>..." to include in what will be committed)
	pancakes.txt

nothing added to commit but untracked files present (use "git add" to track)`}>

```bash
echo "Pancakes: 2 eggs, 1 cup of milk, 1 cup of flour" > pancakes.txt
git status
```

</CodeExample>

Git has noticed `pancakes.txt`, but lists it under **Untracked files**. **Untracked** means "Git can see this file, but it isn't keeping its history yet". Making a new file never adds it to Git by itself: you decide which files go into a commit. The hint in brackets mentions `git add`, and that's exactly where [the next lesson](/learn/git/staging-and-committing) starts. 🐼

In a real terminal, `git status` may also colour the file names (untracked ones are often red). The words are the same.

## Common mistakes

Run a Git command in a folder that isn't a repository, and Git says so:

<CodeExample output={`fatal: not a git repository (or any of the parent directories): .git`}>

```bash
git status
```

</CodeExample>

Here you're in your home folder `~`, which has no `.git`. Git also looks in the folders above (the "parent directories") and finds none there either. **`fatal:`** means Git stopped without doing anything. The fix is almost always `cd` into your project first. When in doubt, `pwd` shows where you are.

<Callout type="danger" title="Run git init in the project folder, not your home folder">

Running `git init` in `~` turns your **whole home folder** into one giant repository, so `git status` lists everything you own. Always `cd` into the project folder first and check with `pwd`. If it does happen in a repository with no commits yet, delete just that new folder with `rm -r .git` from the same place, after checking with `pwd` that you're where you think you are.

</Callout>

## Recap

- Copies like `final_v2_REALLY_final` don't say what changed, why, who or when. **Version control** does.
- **Git** is a version control system that runs on your computer. **GitHub** is a website that hosts Git repositories.
- A **repository** is a project folder plus its history. A **commit** is a saved snapshot with a message, an author and a date.
- **`git init`** turns the folder you're in into a repository, once per project.
- The history lives in the hidden **`.git`** folder (`ls -a` shows it). Never edit or delete it.
- **`git status`** shows where things stand. New files start out **untracked**.
- `fatal: not a git repository` means you're not inside a repository: `cd` into the project first.
