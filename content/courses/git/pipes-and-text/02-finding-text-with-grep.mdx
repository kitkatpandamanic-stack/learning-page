`head` and `tail` show the start and the end of a file. But what about the one line in the middle that says something went wrong? 🔎 **`grep`** finds it: give it some text, and it prints every line that contains it. Developers use it every day to find errors in logs, a function in a big project, or every note they've left in their code.

The odd name comes from an old editor command, `g/re/p`: "**g**lobally search for a **r**egular **e**xpression and **p**rint the lines".

## Your first grep

`grep` takes a **pattern** (the text to look for) and then a file. It prints every line of the file that contains the pattern. In the first examples, the home folder holds the tea shop's `menu.txt`:

```text
Green tea
Black tea
Jasmine tea
Teapot, glass
Steamed buns
Iced tea with lemon
Tea time cake
```

<CodeExample setup={`echo "Green tea" > menu.txt
echo "Black tea" >> menu.txt
echo "Jasmine tea" >> menu.txt
echo "Teapot, glass" >> menu.txt
echo "Steamed buns" >> menu.txt
echo "Iced tea with lemon" >> menu.txt
echo "Tea time cake" >> menu.txt`} output={`Green tea
Black tea
Jasmine tea
Steamed buns
Iced tea with lemon`}>

```bash
grep tea menu.txt
```

</CodeExample>

Look closely at what it found:

- `Steamed buns` is there, because `grep` looks for the letters `tea` **anywhere** in the line, not for whole words, and S**tea**med has them.
- `Teapot` and `Tea time cake` are missing: by default, uppercase and lowercase letters are **different**.

When nothing matches, `grep` prints nothing at all.

## Options that change what grep finds

**`-i`** ("ignore case") treats uppercase and lowercase as the same:

<CodeExample setup={`echo "Green tea" > menu.txt
echo "Black tea" >> menu.txt
echo "Jasmine tea" >> menu.txt
echo "Teapot, glass" >> menu.txt
echo "Steamed buns" >> menu.txt
echo "Iced tea with lemon" >> menu.txt
echo "Tea time cake" >> menu.txt`} output={`Green tea
Black tea
Jasmine tea
Teapot, glass
Steamed buns
Iced tea with lemon
Tea time cake`}>

```bash
grep -i tea menu.txt
```

</CodeExample>

**`-w`** ("word") only matches **whole words**. A word is a run of letters, digits and underscores, so `tea` inside `Steamed` or `Teapot` no longer counts. Options combine, as with `ls -la`, so `-iw` means whole words in any case:

<CodeExample setup={`echo "Green tea" > menu.txt
echo "Black tea" >> menu.txt
echo "Jasmine tea" >> menu.txt
echo "Teapot, glass" >> menu.txt
echo "Steamed buns" >> menu.txt
echo "Iced tea with lemon" >> menu.txt
echo "Tea time cake" >> menu.txt`} output={`Green tea
Black tea
Jasmine tea
Iced tea with lemon
Green tea
Black tea
Jasmine tea
Iced tea with lemon
Tea time cake`}>

```bash
grep -w tea menu.txt
grep -iw tea menu.txt
```

</CodeExample>

**`-v`** ("invert") flips the search: it prints the lines that **don't** match. That's handy for throwing lines away, like the ordinary messages in a log, so the unusual ones stand out:

<CodeExample setup={`echo "Green tea" > menu.txt
echo "Black tea" >> menu.txt
echo "Jasmine tea" >> menu.txt
echo "Teapot, glass" >> menu.txt
echo "Steamed buns" >> menu.txt
echo "Iced tea with lemon" >> menu.txt
echo "Tea time cake" >> menu.txt`} output={`Teapot, glass
Tea time cake`}>

```bash
grep -v tea menu.txt
```

</CodeExample>

## Options that change what grep prints

**`-n`** ("number") puts the line number in front of each match, so you know where to look. **`-c`** ("count") prints only how many lines match:

<CodeExample setup={`echo "Green tea" > menu.txt
echo "Black tea" >> menu.txt
echo "Jasmine tea" >> menu.txt
echo "Teapot, glass" >> menu.txt
echo "Steamed buns" >> menu.txt
echo "Iced tea with lemon" >> menu.txt
echo "Tea time cake" >> menu.txt`} output={`1:Green tea
2:Black tea
3:Jasmine tea
5:Steamed buns
6:Iced tea with lemon
5
7`}>

```bash
grep -n tea menu.txt
grep -c tea menu.txt
grep -ic tea menu.txt
```

</CodeExample>

`-c` counts **lines**, not matches: a line with `tea` in it twice still counts once.

## Quotes around the pattern

The shell splits your command into words at every space before `grep` even starts. To search for text with a space in it, put the whole pattern in **quotes**:

<CodeExample setup={`echo "Green tea" > menu.txt
echo "Black tea" >> menu.txt
echo "Jasmine tea" >> menu.txt
echo "Teapot, glass" >> menu.txt
echo "Steamed buns" >> menu.txt
echo "Iced tea with lemon" >> menu.txt
echo "Tea time cake" >> menu.txt`} output={`Iced tea with lemon`}>

```bash
grep "Iced tea" menu.txt
```

</CodeExample>

Without quotes, `grep` takes the first word as the pattern and **every other word as a file name**. Here someone checks whether the menu has bubble tea, first with quotes and then without:

<CodeExample setup={`echo "Green tea" > menu.txt
echo "Black tea" >> menu.txt
echo "Jasmine tea" >> menu.txt
echo "Teapot, glass" >> menu.txt
echo "Steamed buns" >> menu.txt
echo "Iced tea with lemon" >> menu.txt
echo "Tea time cake" >> menu.txt`} output={`grep: tea: No such file or directory`}>

```bash
grep "bubble tea" menu.txt
grep bubble tea menu.txt
```

</CodeExample>

The first command found nothing (there's no bubble tea on the menu), so it printed nothing. The second one looked for `bubble` in two files, `tea` and `menu.txt`, and there's no file called `tea`.

Quote every pattern that has spaces or characters the shell treats specially, like `*`, `?` or `$`. **Single quotes** `'…'` are the safest: inside them, the shell changes nothing at all.

## Searching a whole project with -r

In the next examples you're inside a small project, the code of the tea shop's website:

```text
tea-shop
├── README.md
└── src
    ├── cart.js
    ├── menu.js
    └── style.css
```

Developers leave notes in their code like `TODO` (still to do) and `FIXME` (something's broken). Give `grep` several files, and it puts the file's name in front of each line it finds:

<Callout type="note" title="On your computer">

- The files may come in a different order, and the names may start with `./`, as in `./src/menu.js`. That always happens when you search `.` (`grep -r TODO .`), and on a Mac even without it.
- In a Git repository, `grep -r` also looks inside the hidden `.git` folder, and can find matches there: Git keeps your last commit message in it, for one. **`git grep TODO`** searches only the files Git tracks.

</Callout>

## A few special characters

A `grep` pattern isn't only plain text: a few characters have special meanings. Patterns like these are called **regular expressions**, a small language of their own. Three are enough for now:

| Character | Means                     | Example     | Matches lines that…        |
| --------- | ------------------------- | ----------- | -------------------------- |
| `^`       | the start of the line     | `'^Tea'`    | start with `Tea`           |
| `$`       | the end of the line       | `'lemon$'`  | end with `lemon`           |
| `.`       | any one character         | `'t.a'`     | have `t`, any character, `a` |

Here's a price list where they help, and where one of them gets in the way:

```text
green tea 1.50
black tea 1.20
jasmine tea 2.10
teapot 125
```

<CodeExample setup={`echo "green tea 1.50" > prices.txt
echo "black tea 1.20" >> prices.txt
echo "jasmine tea 2.10" >> prices.txt
echo "teapot 125" >> prices.txt`} output={`teapot 125
green tea 1.50
black tea 1.20
jasmine tea 2.10
green tea 1.50
teapot 125
green tea 1.50`}>

```bash
grep '^t' prices.txt
grep '0$' prices.txt
grep '1.5' prices.txt
grep -F '1.5' prices.txt
```

</CodeExample>

- `'^t'` found only `teapot`: the other lines have a `t`, but not at the start.
- `'0$'` found the three prices that end in `0`.
- `'1.5'` also matched `teapot 125`, because `.` means **any** character, and `2` is a character.
- **`-F`** ("fixed") turns all the special meanings off, so `.` is just a dot. Use it when you search for text with dots, like prices, versions or file names.

One more: with **`-E`** ("extended"), a `|` means **or**. Here's every `TODO` and every `FIXME` in the project at once:

<CodeExample setup={`mkdir -p tea-shop/src
cd tea-shop
echo "# Tea Shop" > README.md

echo "}" >> src/menu.js

src/cart.js:// TODO: empty the cart after paying

```bash
grep -rE 'TODO|FIXME' src
```

</CodeExample>

<Callout type="tip" title="grep patterns aren't wildcards">

In `ls *.txt`, a `*` means "any text". In a `grep` pattern it means something else ("repeat the character before me"), so don't carry wildcards over. For finding text, plain words with `-i`, `-w` and `-F` get you a long way.

</Callout>

<Callout type="warning" title="Common mistakes">

- The file before the pattern: `grep menu.txt tea` looks for the text `menu.txt` in a file called `tea`. The pattern always comes first.
- A folder without `-r`: `grep: src: Is a directory`.
- A pattern with spaces but no quotes: the words after the first one become file names.
- Forgetting that case matters: `grep error` misses `ERROR`. Add `-i` when you're not sure.
- No file at all: on your computer, `grep tea` on its own waits for you to type text. Press **Ctrl+C** to get your prompt back.

</Callout>

## Recap

- `grep pattern file` prints the lines that contain the pattern, anywhere in the line, with case mattering. Give it several files and it puts the file name in front.
- `-i` ignores case, `-w` matches whole words, `-v` prints the lines that **don't** match.
- `-n` adds line numbers, `-c` counts the matching lines, `-l` lists the matching files.
- `-r` searches a folder and everything inside it; without a folder, the one you're in.
- Quote patterns with spaces or special characters; single quotes are the safest.
- `^` is the start of a line, `$` the end, `.` any one character. `-F` makes the pattern plain text, and `-E` lets `|` mean "or".
