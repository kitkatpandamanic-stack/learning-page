Welcome to the **Level 1 capstone project**! 🎬 **Lina** runs the Friday Film Club in her neighbourhood library, and her friend **Omar** helps with the club's small website. They keep it in a Git repository, and you've just joined the team. Your first job: add a page with the **autumn schedule**, so members know which film is on each Friday.

On a team you don't work straight on `main`. Over two parts you'll do what developers do every day:

- **Part 1 (this lesson):** explore the repository, build the schedule page on its own branch over a few small commits, keep generated files out of Git and fix two mistakes.
- **Part 2:** Omar's work lands on `main` in the meantime. You'll merge it, sort out the conflict and bring your feature into `main`.

You know everything you need from Level 1:

- **head**, **wc**, **grep**, pipes with **cut**, **sort**, **uniq -c** and **tee**, and redirects (Pipes & Text),
- **git diff**, **.gitignore**, **git restore** and **git commit --amend** (Everyday Git),
- **git branch**, **git switch**, **git merge** and merge conflicts (Branches & Merging).

## What's in the film list

Before you change a file, find out what's in it. `head` shows the first lines, `wc -l` counts them, and `grep` finds the lines you're after:

Each line is one film: its **title**, **year** and **genre**, split by commas. So there are 10 films, 4 of them animation, and `grep -n` says which lines the comedies are on.

How many films of **each** genre are there? That's a job for a pipe. `cut -d, -f3` keeps only the third comma-separated field, `sort` puts equal genres next to each other, and `uniq -c` counts each run of equal lines:

```bash
cut -d, -f3 films.txt | head -n 3
cut -d, -f3 films.txt | sort | uniq -c
cut -d, -f3 films.txt | sort | uniq -c | sort -rn
```

</CodeExample>

- The first line checks the start of the pipe on its own: it really is just the genres.
- `uniq -c` only merges **neighbouring** lines, so `sort` must come first. Without it, the two `animation` lines at the top and the ones further down would be counted separately.
- `sort -rn` at the end sorts by the count, biggest first (`-n` numbers, `-r` reversed).

On a Mac, `wc` and `uniq -c` pad the numbers with a different number of spaces. The numbers are the same.

Lina would like to keep that count. `tee` shows what comes through the pipe **and** saves it in a file. Put it in a folder of its own, `reports`:

```bash
mkdir reports
cut -d, -f3 films.txt | sort | uniq -c | tee reports/genres.txt
```

<Callout type="tip" title="Build pipes one step at a time">

Run the first command alone, look at its output, then add `| next-command` and run it again. When a long pipe prints something odd, cut it back until it doesn't. [Look back at pipes and redirects](/learn/git/pipes-and-redirects) if `|`, `>` and `tee` feel rusty.

</Callout>

## A branch for the feature

`git switch -c` makes a branch and switches to it in one go. `git branch -v` lists the branches with the commit each one points at:

	.DS_Store

```bash
git status
echo ".DS_Store" > .gitignore
echo "reports/" >> .gitignore
git status
git check-ignore .DS_Store reports/genres.txt index.html
```

</CodeExample>

Neither of the two untracked names belongs in the repository:

- **`.DS_Store`** is Mac junk.
- **`reports/genres.txt`** is **generated**: one pipe makes it again from `films.txt` at any time. If you committed it, it would go stale the moment someone adds a film, and the history would fill up with copies of a report.

A `.gitignore` file in the top folder lists names Git should leave alone, one rule per line. `reports/` with a slash at the end means "the folder `reports` and everything in it". After that, `git status` only shows `.gitignore` itself, and `git check-ignore` prints the names that are ignored: `index.html` isn't on the list, so Git still tracks it.

Commit `.gitignore` like any other file. Then the rules are shared: when Omar's Mac makes its own `.DS_Store`, Git ignores his too. [Look back at ignoring files](/learn/git/ignoring-files) for more patterns.
