The author is Omar, and his commit changes the `<nav>` line. Your commit "Link the schedule from the home page" changed **the same line**, to `Home | Film list | Schedule`. Git can combine changes to different parts of a file by itself, but here both sides rewrote one line in different ways. Git won't guess which one wins: that's a **merge conflict**, and you'll have to decide.

## Which way to merge

There are two ways to bring the branches together:

1. Switch to `main` and merge `schedule` into it. Any conflict then gets sorted out **on `main`**.
2. First merge `main` into `schedule`. You sort out the conflict **on your branch** and check the result there. Then you merge `schedule` into `main`, which goes through without trouble.

Teams usually pick the second way: it keeps Lina's rule, because `main` never holds a half-finished merge. That's the plan for this part.

The merge stopped halfway. `git status` calls `index.html` **both modified**: changed on both branches in a clash. Git has written both versions into the file, between **conflict markers**:

- From `<<<<<<< HEAD` to `=======` is **your** version. `HEAD` is the branch you're on, `schedule`.
- From `=======` to `>>>>>>> main` is the version from the branch you're merging in, Omar's.
- The lines outside the markers didn't clash, so Git kept them as they are.

The rest of your work isn't affected: only you changed `schedule.html`, `films.txt` and `.gitignore`, so there's nothing there to clash.

## Resolving the conflict

To **resolve** a conflict, you edit the file into the version it should be, and that means deciding, not just picking a side. Here both changes are good ideas: Omar's shorter "Films" and your new "Schedule" link. So the right line keeps **both**:

```text
<nav>Home | Films | Schedule</nav>
```

On your own computer you'd open `index.html` in a code editor, delete the three marker lines and fix the menu line. (VS Code even shows buttons like "Accept Both Changes" above a conflict.) The practice terminal has no editor, but the file is three lines long, so write it again with `echo`. Then check that no marker is left over:

<Callout type="danger" title="Git doesn't check for leftover markers">

As soon as you `git add` a file, Git counts its conflict as resolved, markers or not. Commit a file with `<<<<<<<` still in it, and the site shows those lines to every visitor. Always read the file (or `grep` for the markers) before `git add`.

</Callout>

Two steps finish the merge:

1. **`git add index.html`** tells Git the conflict in this file is resolved.
2. **`git commit`** makes the **merge commit**. Give it a message with `-m`. On your own computer, plain `git commit` opens an editor with a message Git has already written, like "Merge branch 'main' into schedule".

- **Fast-forward**: `main`'s newest commit, Omar's `1c67f83`, is already inside `schedule`'s history, because you merged it in. There's nothing left to join, so Git just moves the `main` label forward to your merge commit. No new commit, and no chance of a conflict.

<Callout type="note" title="-d is the safe delete">

`git branch -d` refuses to delete a branch whose commits aren't in the branch you're on yet: `error: the branch 'schedule' is not fully merged`. That protects unfinished work. `-D` deletes it anyway, so use it only for a branch you really want to throw away. And you can't delete the branch you're on: switch away first.

</Callout>

- In "Look before you merge", try the other way round: `git switch main`, then `git merge schedule`. You get the same conflict, but now `HEAD` means `main` and the bottom half is labelled `schedule`.
- Run `git diff 8a46cb2 HEAD --stat` at the end of the last exercise to see everything the team changed since Lina's last commit.
- Count the screenings with `grep -c "<p>" schedule.html`, then add `<p>27 Nov: Coco</p>` on a new branch, `more-films`, and merge it into `main` with `git merge --no-ff -m "Merge more-films" more-films`. Look at the **Commits** picture: `--no-ff` makes a merge commit even when a fast-forward would do.

## Congratulations! 🎉🐼

You've finished **Level 1** of Git & Terminal. You can search, count and sort text with `grep`, `wc`, `sort` and `uniq`, chain commands with pipes and save their output, see exactly what changed with `git diff`, keep junk out with `.gitignore`, undo a slip with `git restore` and `--amend`, and work on branches that you merge back, conflicts and all. That's how most developers spend their day in Git.

So far the whole team has shared one repository on one computer. Level 2 makes it real teamwork:

- **Remotes:** copy a repository with `git clone`, send your commits with `git push` and get your teammates' with `git pull`.
- **Stash & Tags:** put unfinished work aside for a moment, and mark releases.
- **Team Workflows:** feature branches, pull requests and code review, the way teams work on GitHub.
- **Scripts & Environment:** environment variables, `PATH`, permissions and your first shell scripts.
