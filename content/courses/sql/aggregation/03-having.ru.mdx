Теперь вы умеете считать и складывать по группам. Следующий вопрос всегда звучит так: «…но покажи мне только интересные группы»: страны, где хотя бы два покупателя, заказы дороже 100, категории, где товар заканчивается. 🔍

`WHERE` с этим не справится, потому что он работает с отдельными строками ещё до того, как появились группы. Для групп есть второй фильтр: **`HAVING`**. В конце урока вы соберёте весь модуль воедино в мини-проекте — сводке продаж для магазина.

## HAVING фильтрует группы

**`HAVING`** идёт сразу после `GROUP BY` и оставляет только те группы, для которых его условие истинно. Обычно в условии используется агрегат. В каких странах хотя бы два покупателя?

<CodeExample output={` country | customers
---------+-----------
 UK      |         4
 Japan   |         2
 Russia  |         2
(3 rows)`}>

```sql
SELECT country, count(*) AS customers
FROM customers
GROUP BY country
HAVING count(*) >= 2
ORDER BY customers DESC, country;
```

</CodeExample>

Без строки с `HAVING` вы получили бы все 15 стран. С ней остаются только группы, в которых 2 или больше покупателей.

Агрегат в `HAVING` не обязан быть в списке `SELECT`. Какие режиссёры сняли хотя бы один фильм с рейтингом 8 или выше?

<CodeExample output={`  director  | films
------------+-------
 Ada Brooks |     3
 Ravi Patel |     2
(2 rows)`}>

```sql
SELECT director, count(*) AS films
FROM movies
GROUP BY director
HAVING max(rating) >= 8
ORDER BY director;
```

</CodeExample>

## WHERE или HAVING

Оба фильтруют, но в разные моменты:

- **`WHERE`** фильтрует **строки** **до** группировки. Агрегаты в нём использовать нельзя (групп ещё нет).
- **`HAVING`** фильтрует **группы** **после** того, как вычислены агрегаты.

В одном запросе можно использовать оба. Среди фильмов начиная с 2016 года — у каких жанров средний рейтинг 7 или выше?

<CodeExample output={`   genre   | films | average_rating
-----------+-------+----------------
 adventure |     1 |            7.9
 sci-fi    |     2 |            7.7
 drama     |     1 |            7.6
 comedy    |     2 |            7.5
(4 rows)`}>

```sql
SELECT
  genre,
  count(*) AS films,
  round(avg(rating), 1) AS average_rating
FROM movies
WHERE year >= 2016
GROUP BY genre
HAVING avg(rating) >= 7
ORDER BY average_rating DESC, genre;
```

</CodeExample>

Сначала `WHERE` убрал фильмы до 2016 года (поэтому в drama учитывается только один фильм), затем были созданы группы, а потом `HAVING` отбросил жанры со средним рейтингом ниже 7.

Если условию не нужен агрегат, пишите его в `WHERE`: `HAVING genre = 'drama'` сработает, но PostgreSQL придётся строить группы только для того, чтобы их выбросить. Ранняя фильтрация понятнее и быстрее.

## В каком порядке выполняется запрос

Вы **пишете** части запроса в одном порядке, а PostgreSQL **выполняет** их в другом. Это объясняет почти каждое «почему это не работает?» при работе с группами:

```text
Вы пишете:                     PostgreSQL выполняет:

SELECT   ...                   1. FROM      берёт таблицу
FROM     ...                   2. WHERE     оставляет подходящие строки
WHERE    ...                   3. GROUP BY  создаёт группы
GROUP BY ...                   4. HAVING    оставляет подходящие группы
HAVING   ...                   5. SELECT    вычисляет столбцы
ORDER BY ...                   6. ORDER BY  сортирует результат
LIMIT    ...                   7. LIMIT     оставляет первые строки
```

Поэтому:

- `WHERE` не может использовать агрегаты: на шаге 2 групп ещё нет.
- `HAVING` не может использовать псевдонимы, которые вы задаёте в `SELECT`, потому что `SELECT` выполняется **после** него, на шаге 5. Вместо этого повторите выражение: `HAVING count(*) >= 3`, а не `HAVING films >= 3`.
- `ORDER BY` **может** использовать псевдонимы, потому что выполняется после `SELECT`.

Вот эта ошибка с псевдонимом в действии:

<CodeExample output={`ERROR:  column "films" does not exist
LINE 4: HAVING films >= 3;
               ^`}>

```sql
SELECT director, count(*) AS films
FROM movies
GROUP BY director
HAVING films >= 3;
```

</CodeExample>

(PostgreSQL делает одно дружелюбное исключение: в `GROUP BY` можно использовать псевдоним из `SELECT`, как вы видели с `GROUP BY month`. В `WHERE` и `HAVING` — нельзя.)

<Callout type="warning" title="HAVING не найдёт того, чего нет">

`HAVING` может только оставлять или отбрасывать существующие группы. Страна, где **ноль** покупателей, вообще не встречается в `customers`, поэтому никакой `HAVING` не покажет её с количеством 0. Чтобы найти то, чего не хватает (например, покупателей, которые ни разу ничего не заказали), нужен `LEFT JOIN` — одна из первых тем Уровня 1.

</Callout>

## Мини-проект: сводка продаж магазина

Пора применить весь модуль на деле. Владелец магазина готовится к встрече с инвесторами, и ему нужны три ответа, плотно набитых цифрами. Вы будете работать с `order_items` (одна строка на каждый товар в заказе: `order_id`, `product_id`, `quantity`, `unit_price`) и `products` (`category`, `price`, `stock`).

Напишите **три запроса** в таком порядке. 📈

**1. Главные цифры.** Одна строка из `order_items` со столбцами:
- `orders`: сколько всего **разных** заказов,
- `units`: общее проданное количество,
- `revenue`: сумма `quantity * unit_price`.

**2. Крупные заказы.** По строке на каждый заказ, сумма которого **120 или больше**, со столбцами:
- `order_id`,
- `items`: сколько в нём строк заказа (разных товаров),
- `total`: сумма заказа — сложенные `quantity * unit_price`.

Сначала самая большая сумма; при равных суммах первым идёт меньший `order_id`.

**3. Отчёт о пополнении склада.** По строке на каждую **категорию** товаров, в которой есть хотя бы один товар с остатком **меньше 5** штук, со столбцами:
- `category`,
- `products`: сколько товаров в категории (всех, а не только тех, что заканчиваются),
- `units`: общий остаток на складе,
- `stock_value`: сумма `price * stock`.

Отсортируйте по `category`. (Подсказка к части «хотя бы один товар с остатком меньше 5»: подумайте, о чём говорит **наименьший** остаток в категории.)

<Hint>

1. `GROUP BY` не нужен: `count(DISTINCT order_id)`, `sum(quantity)` и `sum(quantity * unit_price)`.
2. `GROUP BY order_id`, затем `HAVING sum(quantity * unit_price) >= 120` (помните, что в `HAVING` нельзя использовать псевдоним `total`). Отсортируйте через `ORDER BY total DESC, order_id`.
3. `GROUP BY category`. Если наименьший остаток в категории меньше 5, значит, хотя бы одного товара мало: `HAVING min(stock) < 5`. Не используйте `WHERE stock < 5`: так вы выбросите остальные товары ещё до подсчёта.

</Hint>

<Solution>

```sql
-- 1. Главные цифры
SELECT
  count(DISTINCT order_id) AS orders,
  sum(quantity) AS units,
  sum(quantity * unit_price) AS revenue
FROM order_items;

-- 2. Крупные заказы
SELECT
  order_id,
  count(*) AS items,
  sum(quantity * unit_price) AS total
FROM order_items
GROUP BY order_id
HAVING sum(quantity * unit_price) >= 120
ORDER BY total DESC, order_id;

-- 3. Отчёт о пополнении склада
SELECT
  category,
  count(*) AS products,
  sum(stock) AS units,
  sum(price * stock) AS stock_value
FROM products
GROUP BY category
HAVING min(stock) < 5
ORDER BY category;
```

</Solution>

</Exercise>

Эти цифры включают отменённые заказы, потому что `order_items` ничего не знает о статусе заказа: он хранится в таблице `orders`. Объединять две таблицы — как раз задача **соединений** (joins), и это первое, что вы изучите на Уровне 1. 🐼

## Итоги

- **`HAVING`** фильтрует **группы** после `GROUP BY`, обычно с помощью агрегата: `HAVING count(*) >= 2`. В нём можно использовать агрегаты, которых нет в списке `SELECT`.
- **`WHERE`** фильтрует **строки** до группировки и не может использовать агрегаты. Используйте `WHERE` для всего, где агрегат не нужен.
- PostgreSQL выполняет запрос в порядке **FROM → WHERE → GROUP BY → HAVING → SELECT → ORDER BY → LIMIT**, поэтому в `HAVING` нельзя использовать псевдонимы из `SELECT`, а в `ORDER BY` — можно.
- `HAVING min(x) < 5` означает «хотя бы одна строка в группе меньше 5»; `HAVING max(x) >= 8` — «хотя бы одна равна 8 или больше».
- `HAVING` не может придумать группы, в которых нет строк; чтобы найти отсутствующее, нужны соединения (Уровень 1).
