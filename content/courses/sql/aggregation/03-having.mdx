You can now count and add things up per group. The next question is always "…but only show me the interesting groups": countries with at least two customers, orders worth more than 100, categories that are running out of stock. 🔍

`WHERE` can't do that, because it works on single rows, before any groups exist. For groups there's a second filter: **`HAVING`**. At the end of this lesson you'll put the whole module together in a mini-project: a sales summary for the shop.

## HAVING filters groups

**`HAVING`** comes right after `GROUP BY` and keeps only the groups where its condition is true. The condition usually uses an aggregate. Which countries have at least two customers?

<CodeExample output={` country | customers
---------+-----------
 UK      |         4
 Japan   |         2
 Russia  |         2
(3 rows)`}>

```sql
SELECT country, count(*) AS customers
FROM customers
GROUP BY country
HAVING count(*) >= 2
ORDER BY customers DESC, country;
```

</CodeExample>

Without the `HAVING` line you'd get all 15 countries. With it, only the groups whose count is 2 or more survive.

The aggregate in `HAVING` doesn't have to be in the `SELECT` list. Which directors have made at least one film rated 8 or higher?

<CodeExample output={`  director  | films
------------+-------
 Ada Brooks |     3
 Ravi Patel |     2
(2 rows)`}>

```sql
SELECT director, count(*) AS films
FROM movies
GROUP BY director
HAVING max(rating) >= 8
ORDER BY director;
```

</CodeExample>

## WHERE vs HAVING

Both filter, but at different moments:

- **`WHERE`** filters **rows**, **before** they're grouped. It can't use aggregates (there are no groups yet).
- **`HAVING`** filters **groups**, **after** the aggregates are calculated.

You can use both in one query. Among films from 2016 onwards, which genres average a rating of 7 or more?

<CodeExample output={`   genre   | films | average_rating
-----------+-------+----------------
 adventure |     1 |            7.9
 sci-fi    |     2 |            7.7
 drama     |     1 |            7.6
 comedy    |     2 |            7.5
(4 rows)`}>

```sql
SELECT
  genre,
  count(*) AS films,
  round(avg(rating), 1) AS average_rating
FROM movies
WHERE year >= 2016
GROUP BY genre
HAVING avg(rating) >= 7
ORDER BY average_rating DESC, genre;
```

</CodeExample>

`WHERE` first removed the films from before 2016 (so drama only counts one film), then the groups were made, then `HAVING` dropped the genres whose average was below 7.

If a condition doesn't need an aggregate, put it in `WHERE`: `HAVING genre = 'drama'` works, but it makes PostgreSQL build groups only to throw them away. Filtering early is clearer and faster.

## The order a query runs in

You **write** the clauses in one order, but PostgreSQL **runs** them in another. This explains almost every "why doesn't this work?" moment with groups:

```text
You write:                     PostgreSQL runs:

SELECT   ...                   1. FROM      take the table
FROM     ...                   2. WHERE     keep matching rows
WHERE    ...                   3. GROUP BY  make the groups
GROUP BY ...                   4. HAVING    keep matching groups
HAVING   ...                   5. SELECT    calculate the columns
ORDER BY ...                   6. ORDER BY  sort the result
LIMIT    ...                   7. LIMIT     keep the first rows
```

So:

- `WHERE` can't use aggregates: the groups don't exist yet at step 2.
- `HAVING` can't use the aliases you give in `SELECT`, because `SELECT` runs **after** it at step 5. Repeat the expression instead: `HAVING count(*) >= 3`, not `HAVING films >= 3`.
- `ORDER BY` **can** use aliases, because it runs after `SELECT`.

Here's that alias mistake in action:

<CodeExample output={`ERROR:  column "films" does not exist
LINE 4: HAVING films >= 3;
               ^`}>

```sql
SELECT director, count(*) AS films
FROM movies
GROUP BY director
HAVING films >= 3;
```

</CodeExample>

(PostgreSQL does make one friendly exception: `GROUP BY` may use a `SELECT` alias, as you saw with `GROUP BY month`. `WHERE` and `HAVING` may not.)

<Callout type="warning" title="HAVING can't find what isn't there">

`HAVING` can only keep or drop groups that exist. A country with **zero** customers never appears in `customers`, so no `HAVING` can show it with a count of 0. Finding things that are missing (like customers who never ordered) needs a `LEFT JOIN`, one of the first things you'll learn in Level 1.

</Callout>

## Mini-project: Shop sales summary

Time to put the whole module to work. The shop's owner is preparing for a meeting with investors and needs three numbers-packed answers. You'll use `order_items` (one row per product in an order: `order_id`, `product_id`, `quantity`, `unit_price`) and `products` (`category`, `price`, `stock`).

Write **three queries**, in this order. 📈

**1. Headline numbers.** One row from `order_items` with:
- `orders`: how many **different** orders there are,
- `units`: the total quantity sold,
- `revenue`: the total of `quantity * unit_price`.

**2. Big orders.** One row per order whose total is **120 or more**, with:
- `order_id`,
- `items`: how many order lines (different products) it has,
- `total`: the order's total, `quantity * unit_price` added up.

Biggest total first; for equal totals, the smaller `order_id` first.

**3. Restock report.** One row per product **category** that has at least one product with **fewer than 5** items in stock, with:
- `category`,
- `products`: how many products the category has (all of them, not only the low ones),
- `units`: its total stock,
- `stock_value`: the total of `price * stock`.

Sorted by `category`. (Hint for the "at least one product below 5" part: think about what the **smallest** stock in the category tells you.)

<Hint>

1. No `GROUP BY` needed: `count(DISTINCT order_id)`, `sum(quantity)` and `sum(quantity * unit_price)`.
2. `GROUP BY order_id`, then `HAVING sum(quantity * unit_price) >= 120` (remember, `HAVING` can't use the `total` alias). Sort with `ORDER BY total DESC, order_id`.
3. `GROUP BY category`. If the smallest stock in a category is below 5, at least one product is low: `HAVING min(stock) < 5`. Don't use `WHERE stock < 5`: that would throw away the other products before counting them.

</Hint>

<Solution>

```sql
-- 1. Headline numbers
SELECT
  count(DISTINCT order_id) AS orders,
  sum(quantity) AS units,
  sum(quantity * unit_price) AS revenue
FROM order_items;

-- 2. Big orders
SELECT
  order_id,
  count(*) AS items,
  sum(quantity * unit_price) AS total
FROM order_items
GROUP BY order_id
HAVING sum(quantity * unit_price) >= 120
ORDER BY total DESC, order_id;

-- 3. Restock report
SELECT
  category,
  count(*) AS products,
  sum(stock) AS units,
  sum(price * stock) AS stock_value
FROM products
GROUP BY category
HAVING min(stock) < 5
ORDER BY category;
```

</Solution>

</Exercise>

These figures include cancelled orders, because `order_items` doesn't know an order's status: that lives in the `orders` table. Combining the two tables is exactly what **joins** are for, and they're the first thing you'll learn in Level 1. 🐼

## Recap

- **`HAVING`** filters **groups** after `GROUP BY`, usually with an aggregate: `HAVING count(*) >= 2`. It can use aggregates that aren't in the `SELECT` list.
- **`WHERE`** filters **rows** before grouping and can't use aggregates. Use `WHERE` for anything that doesn't need one.
- PostgreSQL runs a query as **FROM → WHERE → GROUP BY → HAVING → SELECT → ORDER BY → LIMIT**, so `HAVING` can't use `SELECT` aliases but `ORDER BY` can.
- `HAVING min(x) < 5` means "at least one row in the group is below 5"; `HAVING max(x) >= 8` means "at least one is 8 or more".
- `HAVING` can't invent groups that have no rows; finding missing things needs joins (Level 1).
