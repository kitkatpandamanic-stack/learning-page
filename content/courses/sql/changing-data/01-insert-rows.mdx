Up to now you've only **read** data. Real apps write to their database all the time: a new customer signs up, someone places an order, a product goes on sale. In this module you'll learn the three statements that change data: **INSERT** adds rows, **UPDATE** changes them and **DELETE** removes them.

This lesson is about `INSERT`. Don't worry about breaking anything: every run here starts from a fresh copy of the sample database, so your changes vanish the next time you press Run. Experiment freely! 🐼

## Your first INSERT

To add a row, name the table, list the columns you're filling in, and give the values in the same order:

<CodeExample output={`INSERT 0 1

 id |     name      | category | price | stock
----+---------------+----------+-------+-------
  1 | Jasmine Tea   | tea      |  6.50 |    40
  2 | Matcha Powder | tea      | 14.00 |    12
  3 | Earl Grey     | tea      |  5.25 |     0
 16 | Oolong Tea    | tea      |  9.50 |    30
(4 rows)`}>

```sql
INSERT INTO products (name, category, price, stock)
VALUES ('Oolong Tea', 'tea', 9.50, 30);

SELECT id, name, category, price, stock
FROM products
WHERE category = 'tea'
ORDER BY id;
```

</CodeExample>

When an `INSERT` succeeds, PostgreSQL answers with a **command tag**: `INSERT 0 1`. The `1` is the number of rows added. (The `0` is a leftover from very old PostgreSQL versions and is always 0; you can ignore it.)

The values must match the columns **one for one**: the first value goes into `name`, the second into `category`, and so on. Text goes in single quotes, numbers don't.

## Columns you leave out

Look at the new row's `id`: you didn't give one, yet it's `16`. The `id` column is set up to **number new rows automatically**, so the database picks the next free number. Leaving it out is exactly right: picking ids yourself is a recipe for clashes.

Any other column you skip gets its **default** value, or `NULL` if it has no default. In `products`, `stock` defaults to `0`:

<CodeExample output={`INSERT 0 1

 id |   name    | price | stock
----+-----------+-------+-------
 16 | Panda Mug |  8.00 |     0
(1 row)`}>

```sql
INSERT INTO products (name, category, price)
VALUES ('Panda Mug', 'kitchen', 8.00);

SELECT id, name, price, stock
FROM products
WHERE name = 'Panda Mug';
```

</CodeExample>

You'll learn how to set up defaults and automatic ids yourself in the Designing Tables module.

<Callout type="warning" title="Always list the columns">

You *can* skip the column list, `INSERT INTO products VALUES (…)`, but then you must give a value for **every** column, in the order they were created, including the id. The day someone adds a column to the table, every such `INSERT` breaks or, worse, puts values into the wrong columns. Listing the columns makes your `INSERT` say exactly what it means.

</Callout>

## Several rows at once

Put several rows after `VALUES`, separated by commas. It's one statement, so it's faster than many single inserts, and it's **all or nothing**: if one row is rejected, none of them are added.

<CodeExample output={`INSERT 0 3

 id |     name     |  city  | joined_on
----+--------------+--------+------------
 21 | Liam O'Brien | Dublin | 2025-07-01
 22 | Aisha Bello  | Lagos  | 2025-07-02
 23 | Mateo Rossi  | NULL   | 2025-07-02
(3 rows)`}>

```sql
INSERT INTO customers (name, email, city, country, joined_on)
VALUES
  ('Liam O''Brien', 'liam@pandadev.test', 'Dublin', 'Ireland',
   '2025-07-01'),
  ('Aisha Bello', 'aisha@pandadev.test', 'Lagos', 'Nigeria',
   '2025-07-02'),
  ('Mateo Rossi', 'mateo@pandadev.test', NULL, 'Italy', '2025-07-02');

SELECT id, name, city, joined_on
FROM customers
WHERE joined_on >= '2025-07-01'
ORDER BY id;
```

</CodeExample>

Two details in there:

- To put an apostrophe inside a text value, **double it**: `'Liam O''Brien'` stores `Liam O'Brien`.
- Write `NULL` (no quotes) for a value you don't know. `'NULL'` in quotes would be the four-letter word "NULL".

## Getting values back with RETURNING

After inserting a customer, an app usually needs the new **id** straight away, for example to show their profile page. Add `RETURNING` and the `INSERT` hands back the columns you ask for, just like a `SELECT`:

<CodeExample output={` id |   name   | joined_on
----+----------+------------
 21 | Jun Park | 2025-07-03
(1 row)`}>

```sql
INSERT INTO customers (name, email, country, joined_on)
VALUES ('Jun Park', 'jun@pandadev.test', 'South Korea', '2025-07-03')
RETURNING id, name, joined_on;
```

</CodeExample>

`RETURNING *` returns every column, including the ones the database filled in for you. It works on multi-row inserts too, with one result row per inserted row. You'll see `RETURNING` again on `UPDATE` and `DELETE`.

## When the database says no

Tables have **constraints**: rules the data must follow. PostgreSQL checks every new row against them and rejects the whole statement if a rule is broken. In the sample database, every customer's email must be unique:

<CodeExample output={`ERROR:  duplicate key value violates unique constraint "customers_email_key"
DETAIL:  Key (email)=(mei@pandadev.test) already exists.`}>

```sql
INSERT INTO customers (name, email, country, joined_on)
VALUES ('Mei Again', 'mei@pandadev.test', 'UK', '2025-07-01');
```

</CodeExample>

The `DETAIL` line tells you exactly which value clashed. Other rules you'll bump into:

- **NOT NULL**: a required column is missing, e.g. a customer without an email.
- **CHECK**: a value breaks a rule, e.g. a product with a price of `0` (prices must be above zero).
- **FOREIGN KEY**: a reference points at nothing, e.g. an order for a customer that doesn't exist:

<CodeExample output={`ERROR:  insert or update on table "orders" violates foreign key constraint "orders_customer_id_fkey"
DETAIL:  Key (customer_id)=(999) is not present in table "customers".`}>

```sql
INSERT INTO orders (customer_id, ordered_at, status)
VALUES (999, '2025-07-01 10:00', 'paid');
```

</CodeExample>

These errors are your friends. They stop bad data at the door, so the rest of your app can trust what's in the database.

## Copying rows with INSERT … SELECT

Instead of `VALUES`, you can give `INSERT` a **query**. Every row the query returns gets inserted. This is how you copy, archive or pre-fill data without listing it by hand.

The example creates a small `wishlist` table first. Don't worry about `CREATE TABLE` yet; the Designing Tables module covers it properly. Then it adds every tea to Mei's wishlist (customer 1) in one go:

<CodeExample output={`CREATE TABLE

INSERT 0 3

     name      |  added_on
---------------+------------
 Earl Grey     | 2025-07-01
 Jasmine Tea   | 2025-07-01
 Matcha Powder | 2025-07-01
(3 rows)`}>

```sql
CREATE TABLE wishlist (
  customer_id integer,
  product_id integer,
  added_on date
);

INSERT INTO wishlist (customer_id, product_id, added_on)
SELECT 1, id, '2025-07-01'
FROM products
WHERE category = 'tea';

SELECT p.name, w.added_on
FROM wishlist AS w
JOIN products AS p ON p.id = w.product_id
ORDER BY p.name;
```

</CodeExample>

The `SELECT` must return the same number of columns as the column list, in the same order. A handy habit: write and run the `SELECT` on its own first, check the rows look right, and only then put `INSERT INTO … (…)` in front of it.

## Using a new id straight away

Remember CTEs from [the WITH lesson](/learn/sql/common-table-expressions)? A CTE can contain an `INSERT … RETURNING`, and the main statement can use what it returned. Here a brand-new customer and their first order are created in **one** statement, with the order pointing at the customer's new id:

<CodeExample output={` id | customer_id | status
----+-------------+--------
 41 |          21 | paid
(1 row)`}>

```sql
WITH new_customer AS (
  INSERT INTO customers (name, email, country, joined_on)
  VALUES ('Kofi Mensah', 'kofi@pandadev.test', 'Ghana', '2025-07-04')
  RETURNING id
)
INSERT INTO orders (customer_id, ordered_at, status)
SELECT id, '2025-07-04 12:00', 'paid'
FROM new_customer
RETURNING id, customer_id, status;
```

</CodeExample>

The new customer got id 21 and the order id 41, and the order already points at its customer. No guessing ids, and no gap between the two steps where things could go wrong.

## Recap

- `INSERT INTO table (col1, col2) VALUES (v1, v2);` adds a row; the tag `INSERT 0 n` says how many.
- Leave out the `id` and the database numbers the row; other skipped columns get their **default** or `NULL`.
- Always **list the columns**; double an apostrophe inside text: `'O''Brien'`.
- `VALUES (…), (…), (…)` adds many rows in one all-or-nothing statement.
- `RETURNING id` (or `RETURNING *`) hands back what was inserted, including generated values.
- Constraints (NOT NULL, UNIQUE, CHECK, FOREIGN KEY) reject bad rows with a clear error.
- `INSERT INTO … SELECT …` inserts every row a query returns; a CTE with `INSERT … RETURNING` lets you use a new id straight away.
