Prices change, orders get shipped, customers move house, and old data gets cleaned up. That's the job of **UPDATE** (change existing rows) and **DELETE** (remove rows).

Both are simple to write, and both can do a lot of damage with one missing line. So this lesson teaches the statements **and** the habits that professionals use to change data without a nasty surprise.

## UPDATE: change some rows

`UPDATE` names the table, says what to change with `SET`, and picks the rows with `WHERE`:

<CodeExample output={`UPDATE 1

 id |    name     | price
----+-------------+-------
  1 | Jasmine Tea |  7.00
(1 row)`}>

```sql
UPDATE products
SET price = 7.00
WHERE id = 1;

SELECT id, name, price
FROM products
WHERE id = 1;
```

</CodeExample>

The tag `UPDATE 1` tells you **how many rows** changed. Get in the habit of reading it: if you expected 1 and it says 15, something is wrong.

You can change several columns at once, separated by commas, and the new value can be calculated from the old one. Tea gets 10% more expensive and a fresh delivery of 10 packs each:

<CodeExample output={`UPDATE 3

     name      | price | stock
---------------+-------+-------
 Jasmine Tea   |  7.15 |    50
 Matcha Powder | 15.40 |    22
 Earl Grey     |  5.78 |    10
(3 rows)`}>

```sql
UPDATE products
SET
  price = round(price * 1.10, 2),
  stock = stock + 10
WHERE category = 'tea';

SELECT name, price, stock
FROM products
WHERE category = 'tea'
ORDER BY id;
```

</CodeExample>

On the right of `=`, `price` and `stock` mean the row's **current** values, so `stock = stock + 10` adds 10 to whatever each row had.

## The missing WHERE

`WHERE` is optional, and that's the danger. Without it, `UPDATE` changes **every row** in the table:

<CodeExample output={`UPDATE 15

 priced_at_1
-------------
          15
(1 row)`}>

```sql
-- Meant to fix the price of one product...
UPDATE products
SET price = 1.00;

SELECT count(*) AS priced_at_1
FROM products
WHERE price = 1.00;
```

</CodeExample>

All 15 products now cost 1.00. There's no "are you sure?" and no undo button. On a real database, the only way back is a backup, or a transaction you haven't committed yet (next lesson).

<Callout type="danger" title="SELECT first, then UPDATE">

Before you change or delete anything, write it as a **SELECT** with the same `WHERE` and run it. Check the rows and the count. Only then replace `SELECT … FROM` with `UPDATE … SET` (or `DELETE FROM`), keeping the `WHERE` exactly as it was. Many developers type the `WHERE` line **first** so they can't accidentally run the statement without it.

</Callout>

Here's that habit in action. Which products are sold out?

<CodeExample output={` id |     name     | stock
----+--------------+-------
  3 | Earl Grey    |     0
  9 | Clean Python |     0
(2 rows)`}>

```sql
SELECT id, name, stock
FROM products
WHERE stock = 0
ORDER BY id;
```

</CodeExample>

Two rows, as expected. Now the same `WHERE` in an `UPDATE`:

<CodeExample output={`UPDATE 2`}>

```sql
UPDATE products
SET stock = 50
WHERE stock = 0;
```

</CodeExample>

`UPDATE 2`, matching the `SELECT`. 👍

## Seeing what changed with RETURNING

Like `INSERT`, `UPDATE` can end with `RETURNING` to show the rows it changed. Since **PostgreSQL 18**, you can even ask for the value **before** and **after** the change with `old.` and `new.`. Here's a 20% spring sale on toys:

<CodeExample output={`     name      |  was  |  now
---------------+-------+-------
 Plush Panda   | 18.00 | 14.40
 Wooden Puzzle | 11.40 |  9.12
 Kite          | 15.00 | 12.00
(3 rows)`}>

```sql
UPDATE products
SET price = round(price * 0.8, 2)
WHERE category = 'toys'
RETURNING name, old.price AS was, new.price AS now;
```

</CodeExample>

That's a perfect record of what the statement did. (On older PostgreSQL versions, `RETURNING price` gives the new value only.)

<Callout type="warning" title="WHERE city = NULL matches nothing">

To find missing values in an `UPDATE` or `DELETE`, use `IS NULL`, just like in a `SELECT`. `UPDATE customers SET city = 'Unknown' WHERE city = NULL` reports `UPDATE 0`, because `= NULL` is never true. Write `WHERE city IS NULL`. Setting a value **to** `NULL` is fine, though: `SET city = NULL`.

</Callout>

## UPDATE … FROM: using another table

Sometimes the new values live somewhere else. A delivery arrives with a list of products and quantities. `UPDATE … FROM` joins the table you're updating with another source, and the `WHERE` says how they match up.

Here the delivery note is written as a small inline table with `VALUES`, called `d`, with the columns `(name, qty)`:

<CodeExample output={`     name     | was | now
--------------+-----+-----
 Earl Grey    |   0 |  24
 Clean Python |   0 |  10
 Tea Pot      |   6 |  12
(3 rows)`}>

```sql
UPDATE products AS p
SET stock = p.stock + d.qty
FROM (VALUES
  ('Earl Grey', 24),
  ('Clean Python', 10),
  ('Tea Pot', 6)
) AS d (name, qty)
WHERE p.name = d.name
RETURNING p.name, old.stock AS was, new.stock AS now;
```

</CodeExample>

The source after `FROM` can be any table, a subquery or a `VALUES` list. Only rows of `products` that find a match are updated.

<Callout type="warning" title="One match per row">

If a row of the target table matches **several** rows of the `FROM` source, PostgreSQL uses just one of them, and you can't tell which. Had the delivery listed Earl Grey twice, only one line would be added, silently. When the source can have duplicates, add them up first (for example with a `GROUP BY` subquery or CTE), so each target row matches exactly once.

</Callout>

For a simple condition on another table, a subquery works too: `UPDATE orders SET status = 'shipped' WHERE status = 'paid' AND customer_id IN (SELECT id FROM customers WHERE country = 'Japan')`.

## DELETE: remove rows

`DELETE FROM` plus a `WHERE` removes the matching rows. Nina Novak (customer 20) never ordered anything and wants her account removed:

<CodeExample output={`DELETE 1

 customers
-----------
        19
(1 row)`}>

```sql
DELETE FROM customers
WHERE id = 20;

SELECT count(*) AS customers FROM customers;
```

</CodeExample>

Everything you learned about `UPDATE` applies here too: the tag says how many rows went, `DELETE FROM customers;` with no `WHERE` empties the whole table, and `RETURNING` shows what was removed.

Foreign keys protect you from leaving orphans behind. Mei Lin (customer 1) has orders that point at her row, so the database refuses to delete her:

<CodeExample output={`ERROR:  update or delete on table "customers" violates foreign key constraint "orders_customer_id_fkey" on table "orders"
DETAIL:  Key (id)=(1) is still referenced from table "orders".`}>

```sql
DELETE FROM customers
WHERE id = 1;
```

</CodeExample>

To remove her you'd first have to delete (or reassign) the rows that point at her: her order items, then her orders, then the customer. Delete the "children" before the "parent".

A subquery in the `WHERE` lets you delete rows based on another table. This removes every item that belongs to a cancelled order:

<CodeExample output={`DELETE 15`}>

```sql
DELETE FROM order_items
WHERE order_id IN (
  SELECT id FROM orders WHERE status = 'cancelled'
);
```

</CodeExample>

<Callout type="tip" title="Deleting for real is a big decision">

Many apps never really delete important rows. They add a column like `deleted_at` and set it instead (a **soft delete**), so mistakes can be undone and history is kept. You'll design that in Level 3. To empty a whole table quickly, there's also `TRUNCATE table_name;`, which is much faster than `DELETE` on big tables, and even more final.

</Callout>

## Recap

- `UPDATE table SET col = value, … WHERE …;` changes rows; `DELETE FROM table WHERE …;` removes them.
- The tag (`UPDATE 3`, `DELETE 1`) is the number of rows affected. Check it.
- **No `WHERE` means every row.** Run a `SELECT` with the same `WHERE` first.
- In `SET`, column names mean the row's current values: `stock = stock + 10`.
- `RETURNING` shows the changed rows; in PostgreSQL 18, `old.col` and `new.col` show before and after.
- `UPDATE … FROM` takes new values from another table, subquery or `VALUES` list; make sure each row matches once.
- Foreign keys stop you deleting a row that others point at: delete the children first.
