В Части 1 вы сделали так, что строка не может **ссылаться** на другого арендатора. Но ничто не мешает приложению **читать** строки другого арендатора. За годы в PandaTasks появятся сотни запросов от десятка разработчиков, и в каждом нужно не забыть `WHERE tenant_id = …`. Утечки данных в мультиарендных продуктах очень часто сводятся ровно к одному забытому условию: эндпоинт вроде `GET /tasks/:id`, который проверяет, что пользователь вошёл в систему, но не проверяет, что задача принадлежит его компании. 🕳️

В этой части вы заставите PostgreSQL самостоятельно охранять границу арендатора с помощью **защиты на уровне строк (row-level security, RLS)** из урока [Защита на уровне строк](/learn/sql/row-level-security), чтобы забытый фильтр возвращал пустоту, а не чужие данные. Проверки в приложении остаются, а RLS — это **вторая линия обороны** под ними.

## План

Три роли, три задачи:

| Роль | Кто использует | Что может |
| --- | --- | --- |
| Владелец (роль миграций) | Миграции, которые запускает конвейер деплоя | Создавать и изменять таблицы; владеет ими |
| `app_user` | Приложение, через пулер | Читать и писать строки — **только текущего арендатора** |
| `support_admin` | Внутренний инструмент поддержки с аудитом | Читать по всем арендаторам (`BYPASSRLS`) |

И одно правило для каждого запроса, который обрабатывает приложение:

```ts
// в приложении: каждый запрос выполняется в одной транзакции
// и сообщает PostgreSQL, от имени какого арендатора действует
await db.transaction(async (tx) => {
  await tx.query("SELECT set_config('app.tenant_id', $1, true)", [
    String(session.tenantId), // из проверенного входа, никогда не из URL
  ]);
  return handler(tx);
});
```

`set_config(…, true)` действует **в пределах транзакции**, как `SET LOCAL`: значение исчезает при `COMMIT`, поэтому это безопасно с PgBouncer в режиме транзакций, как вы видели в уроке [Бэкапы, репликация и пул соединений](/learn/sql/backups-and-replication). Сессионный `SET` остался бы на соединении из пула и мог бы достаться запросу **следующего арендатора** — ровно тот баг, который мы пытаемся предотвратить.

## Шаг 1: кто текущий арендатор?

Политикам (policies) нужен ответ на один вопрос: от имени какого арендатора действует эта транзакция? Небольшая функция читает настройку. Важная деталь — что происходит, когда настройки **нет**:

<CodeExample output={`CREATE FUNCTION

 not_set
---------
    NULL
(1 row)

BEGIN

 set_config
------------
 1
(1 row)

 in_transaction
----------------
              1
(1 row)

COMMIT

 after_commit
--------------
         NULL
(1 row)`}>

```sql
CREATE FUNCTION current_tenant_id() RETURNS bigint
LANGUAGE sql STABLE
AS $$
  SELECT nullif(current_setting('app.tenant_id', true), '')::bigint
$$;

SELECT current_tenant_id() AS not_set;

BEGIN;
SELECT set_config('app.tenant_id', '1', true);
SELECT current_tenant_id() AS in_transaction;
COMMIT;

SELECT current_tenant_id() AS after_commit;
```

</CodeExample>

- `current_setting('app.tenant_id', true)`: второй аргумент, `missing_ok`, возвращает `NULL` вместо ошибки, если настройку ни разу не задавали.
- После окончания настройки в пределах транзакции значение становится **пустой строкой**, а не `NULL`; `nullif(…, '')` тоже превращает его в `NULL`.
- Политика `tenant_id = current_tenant_id()` с `NULL` никогда не бывает истинной, поэтому запрос, забывший указать арендатора, **не видит ни одной строки** и не может ничего записать. Схема **отказывает в закрытую сторону (fails closed)**.
- `STABLE` сообщает планировщику, что результат не меняется в течение запроса, поэтому функция вычисляется один раз на запрос, а не на каждую строку, и её можно использовать даже в поиске по индексу.

(Чтобы демо было коротким, арендатор задаётся на всю сессию через `false`. Настоящее приложение использует `true` внутри каждой транзакции, как выше.)

Каждый запрос выполнялся **без** `WHERE tenant_id = …`, и каждый арендатор видел только свои задачи. Две части политики выполняют разную работу:

- **`USING (…)`** фильтрует строки, которые инструкция может **видеть**: `SELECT`, а также строки, которые могут затронуть `UPDATE` или `DELETE`. Строки, не прошедшие проверку, молча невидимы, будто их нет.
- **`WITH CHECK (…)`** проверяется на **записываемых** строках: новых строках из `INSERT` и новой версии строки после `UPDATE`. Строки, не прошедшие проверку, вызывают ошибку. Без этого арендатор мог бы выполнить `UPDATE tasks SET tenant_id = 2` и перекинуть свои строки другому арендатору.

Политика без предложения `FOR` применяется ко всем командам (`FOR ALL`). Можно также написать отдельные политики `FOR SELECT`, `FOR INSERT` и так далее — например, чтобы участники могли читать, а удалять — только администраторы.

### FORCE и кто обходит RLS

Три вида ролей политики **не** затрагивают:

- **суперпользователи** — всегда;
- роли с атрибутом **`BYPASSRLS`** (так `support_admin` читает по всем арендаторам);
- **владелец таблицы** — если у таблицы нет **`FORCE ROW LEVEL SECURITY`**.

Третий пункт кусает реальные команды: приложение подключается той же ролью, что запускала миграции, значит, владеет таблицами, и RLS тихо ничего не делает. `FORCE` закрывает эту дыру, но лучшее решение — то, что выше: отдельная непривилегированная `app_user`. А поскольку суперпользователи полностью обходят RLS, **приложение никогда не должно подключаться как суперпользователь**.

<Callout type="warning" title="Представления могут обходить RLS">

Представление (view) обычно выполняется с привилегиями своего **владельца**. Если владелец — роль миграций (суперпользователь или владелец таблицы), RLS **внутри** представления пропускается, и `SELECT count(*) FROM task_titles` через представление посчитает задачи всех арендаторов. Начиная с PostgreSQL 15 создавайте представления для приложения с **`WITH (security_invoker = true)`**, чтобы они проверяли RLS от имени роли, которая к ним обращается. То же относится к функциям `SECURITY DEFINER`: они выполняются от имени владельца, поэтому используйте их только намеренно и фильтруйте внутри по `current_tenant_id()`.

</Callout>

## Шаг 3: защитите каждую таблицу — и сохраните это

В PandaTasks появятся таблицы для комментариев, вложений, меток, счетов… и однажды кто-то добавит таблицу и забудет её политику. Это предотвращают две привычки. Во-первых, генерируйте политики одинаково для каждой таблицы со столбцом `tenant_id`, безопасно экранируя имена через `format('%I')`:

<CodeExample output={`CREATE TABLE

CREATE TABLE

CREATE TABLE

CREATE FUNCTION

NOTICE:  protected comments
NOTICE:  protected projects
NOTICE:  protected tasks
DO

 tablename |    policyname    |               qual
-----------+------------------+-----------------------------------
 comments  | tenant_isolation | (tenant_id = current_tenant_id())
 projects  | tenant_isolation | (tenant_id = current_tenant_id())
 tasks     | tenant_isolation | (tenant_id = current_tenant_id())
(3 rows)

CREATE TABLE

 unprotected
-------------
 attachments
(1 row)`}>

```sql
CREATE TABLE projects (tenant_id bigint NOT NULL, name text);
CREATE TABLE tasks (tenant_id bigint NOT NULL, title text);
CREATE TABLE comments (tenant_id bigint NOT NULL, body text);

CREATE FUNCTION current_tenant_id() RETURNS bigint
LANGUAGE sql STABLE
AS $$
  SELECT nullif(current_setting('app.tenant_id', true), '')::bigint
$$;

DO $$
DECLARE
  t text;
BEGIN
  FOR t IN
    SELECT table_name
    FROM information_schema.columns
    WHERE table_schema = 'public' AND column_name = 'tenant_id'
    ORDER BY table_name
  LOOP
    EXECUTE format('ALTER TABLE %I ENABLE ROW LEVEL SECURITY', t);
    EXECUTE format('ALTER TABLE %I FORCE ROW LEVEL SECURITY', t);
    EXECUTE format(
      'CREATE POLICY tenant_isolation ON %I
         USING (tenant_id = current_tenant_id())
         WITH CHECK (tenant_id = current_tenant_id())', t);
    RAISE NOTICE 'protected %', t;
  END LOOP;
END
$$;

SELECT tablename, policyname, qual
FROM pg_policies
ORDER BY tablename;

-- через несколько месяцев новая миграция забывает про RLS
CREATE TABLE attachments (tenant_id bigint NOT NULL, url text);

-- сторожевой запрос: таблицы арендаторов без RLS
SELECT c.relname AS unprotected
FROM pg_class AS c
JOIN pg_namespace AS n ON n.oid = c.relnamespace
WHERE n.nspname = 'public'
  AND c.relkind IN ('r', 'p')
  AND NOT c.relrowsecurity
  AND EXISTS (
    SELECT 1
    FROM pg_attribute AS a
    WHERE a.attrelid = c.oid
      AND a.attname = 'tenant_id'
      AND NOT a.attisdropped
  )
ORDER BY c.relname;
```

</CodeExample>

Во-вторых, запускайте этот **сторожевой запрос в CI** после миграций: если он возвращает хоть одну строку, сборка падает. `pg_class.relrowsecurity` и `relforcerowsecurity` показывают, включена ли RLS и принудительна ли она, а `relkind` `'r'` и `'p'` — это обычные и секционированные таблицы.

Ещё лучше — написать **тест изоляции**: создайте двух арендаторов с данными, затем выполните настоящие запросы приложения как `app_user` для арендатора A и проверьте, что не вернулось ни одной строки арендатора B. Такой тест ловит баги, которые сторожевой запрос поймать не может, например опечатку в политике.

## Глобальные таблицы и границы RLS

Не у каждой таблицы есть `tenant_id`. `users` — глобальная таблица, но участник Acme должен видеть только пользователей Acme. Политика может использовать подзапрос (subquery):

```sql
ALTER TABLE users ENABLE ROW LEVEL SECURITY;
CREATE POLICY same_tenant_users ON users FOR SELECT
  USING (EXISTS (
    SELECT 1
    FROM memberships AS m
    WHERE m.user_id = users.id
      AND m.tenant_id = current_tenant_id()
  ));
```

`memberships` тоже защищена своей политикой, поэтому подзапрос видит только участников текущего арендатора. Делайте подзапросы в политиках простыми и индексированными: они выполняются для каждой проверяемой строки.

Несколько граничных случаев, о которых стоит знать:

- **Проверки ограничений видят все строки.** Внешние ключи и ограничения уникальности проверяются без RLS — поэтому составные ключи из Части 1 по-прежнему работают. Это также означает, что глобальный `UNIQUE (slug)` сообщает арендатору, что «globex» уже занят. Для slug это нормально; для всего чувствительного делайте уникальность в пределах арендатора.
- **Фоновым задачам** (письма, выгрузки, ночные отчёты) тоже нужен арендатор. Запускайте их для каждого арендатора с настройкой или отдельной, намеренно привилегированной ролью — но никогда не используйте втихую роль владельца.
- **Производительность**: политика добавляется к каждому запросу, поэтому каждый индекс на таблице арендатора должен **начинаться с `tenant_id`**. Планы вы проверите в Части 3.

## Итоги

- RLS — это **вторая линия обороны**: проверки в приложении остаются, а забытый `WHERE tenant_id` возвращает пустоту вместо утечки.
- Приложение подключается **непривилегированной ролью** (не суперпользователь, не владелец, без `BYPASSRLS`); инструменты поддержки используют отдельную роль `BYPASSRLS` с аудитом.
- Каждый запрос задаёт арендатора **внутри своей транзакции** через `set_config('app.tenant_id', …, true)`: это безопасно с пулом в режиме транзакций.
- **`current_tenant_id()`** возвращает `NULL`, когда настройки нет или она пустая, поэтому политики **отказывают в закрытую сторону**.
- **`USING`** фильтрует то, что видит инструкция; **`WITH CHECK`** отклоняет строки, записываемые за пределы арендатора. **`FORCE ROW LEVEL SECURITY`** применяет политики и к владельцу.
- Представлениям нужен **`security_invoker = true`**; функции `SECURITY DEFINER` и фоновые задачи требуют аккуратности.
- Генерируйте политики для **каждой** таблицы с `tenant_id` и запускайте в CI **сторожевой запрос** и тесты изоляции.
