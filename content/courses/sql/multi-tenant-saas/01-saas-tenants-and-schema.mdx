Welcome to the Level 3 capstone. You're the database lead at a start-up building **PandaTasks**, a project and task tracker sold to companies. Each customer company is a **tenant**: Acme Ltd signs up, invites its people, creates projects and tasks, and must never, ever see a single row that belongs to Globex. 🐼

Over three parts you'll design, secure and prepare this database for launch, using everything from Level 3:

1. **Tenants and the schema** (this part): the tenancy model, keys and constraints that make cross-tenant mistakes impossible.
2. **Isolating tenants**: roles and row-level security, so a forgotten `WHERE` can't leak data.
3. **Launch review**: indexes and partitioning for tenant data, a migration plan, and the final checklist.

## The brief

Here's what product and the founders have told you:

- **Isolation is the top requirement.** One company seeing another company's tasks would end the business.
- About **5,000 tenants** in the first year. Most are small teams; a few enterprise customers will have millions of tasks.
- A **user** (one email address) can belong to **several tenants**, for example a freelancer who works for two clients, with a role in each: `owner`, `admin` or `member`.
- Tenants are on a **plan**: `free`, `pro` or `enterprise`, with limits per plan.
- Every change is recorded in an **activity log**, kept for a time that depends on the plan.
- Tenants can ask for **all their data to be exported or deleted** (GDPR), and support staff sometimes need to look across tenants.

## Three ways to host many tenants

Before any `CREATE TABLE`, choose the **tenancy model**. There are three classic options:

| | Database per tenant | Schema per tenant | Shared tables + `tenant_id` |
| --- | --- | --- | --- |
| Isolation | Strongest | Strong | Enforced by keys and RLS |
| Migrations | Run 5,000 times | Run 5,000 times | Run once |
| Connections | A pool per database | Shared, `search_path` per request | Shared |
| Cross-tenant reports | Very hard | Hard | Plain SQL |
| Cost per small tenant | High | Medium | Tiny |
| Moving a big tenant out | Already separate | Easy | Needs a copy by `tenant_id` |
| Works up to | Hundreds of tenants | Low thousands | Hundreds of thousands+ |

Database- or schema-per-tenant looks safest, but with thousands of tenants every migration becomes a fleet operation that can fail half-way, catalogs grow huge, and connection pools multiply. Most SaaS products, from small start-ups to Salesforce-scale platforms, use **shared tables with a `tenant_id` column**, made safe by constraints and **row-level security**, and move only the very biggest customers onto their own servers if they must.

That's PandaTasks' choice too. The rule that follows is simple and strict: **every table that holds tenant data has a `tenant_id` column**, even when it could be found through a join. It's what row-level security filters on, what every index starts with, and what you'd shard by one day.

## Tenants, users and memberships

`tenants` and `users` are the two "global" tables. A user isn't owned by one tenant, so the link between them is its own table, **`memberships`**, with the role. Plans and roles are a small fixed set, so they're `ENUM` types:

```sql
CREATE TYPE member_role AS ENUM ('owner', 'admin', 'member');

CREATE TABLE tenants (
  id bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  slug text NOT NULL UNIQUE,
  name text NOT NULL,
  plan plan NOT NULL DEFAULT 'free'

CREATE TABLE users (
  id bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  email text NOT NULL,
  name text NOT NULL

-- one account per email, whatever the capitals

  tenant_id bigint NOT NULL REFERENCES tenants ON DELETE CASCADE,
  user_id bigint NOT NULL REFERENCES users ON DELETE CASCADE,
  role member_role NOT NULL DEFAULT 'member',
  PRIMARY KEY (tenant_id, user_id)
);

  ('ada@globex.test', 'Ada Brooks'),

SELECT t.name AS tenant, u.name AS member, m.role

ORDER BY t.name, u.name;
```

</CodeExample>

Ada works for Acme and Globex, and Mei is in Acme and Initech, with different roles in each. A few deliberate choices:

- **`memberships` has the primary key `(tenant_id, user_id)`**, with `tenant_id` first. Most lookups are "the members of this tenant", and other tables will point at this pair.
- The email rule is a **unique index on `lower(email)`**, so `Mei@Acme.test` can't sign up twice.
- `ON DELETE CASCADE` from `tenants` means deleting a tenant removes its memberships. Users stay, because they may belong elsewhere.
- In the real product every table also has `created_at timestamptz NOT NULL DEFAULT now()`. We leave timestamps out of the examples to keep the output short.

## Making cross-tenant references impossible

Now projects and tasks. Here's the subtle bug that shared-table designs are famous for. With an ordinary foreign key on `project_id`, nothing stops a task of **Globex** from pointing at a project of **Acme**:

<CodeExample output={`CREATE TABLE

CREATE TABLE

INSERT 0 2

INSERT 0 1

 task_tenant | project_tenant |       title
-------------+----------------+-------------------
           2 |              1 | Steal the roadmap
(1 row)`}>

```sql
CREATE TABLE projects (
  id bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  tenant_id bigint NOT NULL,
  name text NOT NULL
);

-- the naive version: project_id alone
CREATE TABLE tasks (
  id bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  tenant_id bigint NOT NULL,
  project_id bigint NOT NULL REFERENCES projects,
  title text NOT NULL
);

INSERT INTO projects (tenant_id, name) VALUES
  (1, 'Acme roadmap'), (2, 'Globex website');

-- a bug in the app (or an attacker guessing ids) does this:
INSERT INTO tasks (tenant_id, project_id, title)
VALUES (2, 1, 'Steal the roadmap');

SELECT
  k.tenant_id AS task_tenant,
  p.tenant_id AS project_tenant,
  k.title
FROM tasks AS k
JOIN projects AS p ON p.id = k.project_id;
```

</CodeExample>

The database accepted a Globex task inside Acme's project. Now any screen that lists "tasks of the Acme roadmap" shows Globex's task to Acme, and maybe the reverse. Application code is supposed to check this, on every endpoint, forever.

The fix is to make the **tenant part of the key**. Give `projects` the primary key `(tenant_id, id)`, and let tasks reference that **pair**. A **composite foreign key** requires both columns to match the same row, so a task and its project must be in the same tenant:

<CodeExample output={`CREATE TABLE

CREATE TABLE

INSERT 0 2

INSERT 0 1

ERROR:  insert or update on table "tasks" violates foreign key constraint "tasks_tenant_id_project_id_fkey"
DETAIL:  Key (tenant_id, project_id)=(2, 1) is not present in table "projects".`}>

```sql
CREATE TABLE projects (
  tenant_id bigint NOT NULL,
  id bigint GENERATED ALWAYS AS IDENTITY,
  name text NOT NULL,
  PRIMARY KEY (tenant_id, id),
  UNIQUE (tenant_id, name)
);

CREATE TABLE tasks (
  tenant_id bigint NOT NULL,
  id bigint GENERATED ALWAYS AS IDENTITY,
  project_id bigint NOT NULL,
  title text NOT NULL,
  PRIMARY KEY (tenant_id, id),
  FOREIGN KEY (tenant_id, project_id)
    REFERENCES projects (tenant_id, id) ON DELETE CASCADE
);

INSERT INTO projects (tenant_id, name) VALUES
  (1, 'Acme roadmap'), (2, 'Globex website');

-- same tenant: fine
INSERT INTO tasks (tenant_id, project_id, title)
VALUES (1, 1, 'Plan Q3');

-- across tenants: rejected by the database itself
INSERT INTO tasks (tenant_id, project_id, title)
VALUES (2, 1, 'Steal the roadmap');
```

</CodeExample>

The same pattern applies to every reference inside a tenant. An assignee isn't just "a user": it must be a **member of the same tenant**, so the task's foreign key points at `memberships (tenant_id, user_id)`. Per-tenant names get per-tenant uniqueness: `UNIQUE (tenant_id, name)` lets Acme and Globex both have a project called "Website", but not two in the same company.

<Callout type="note" title="ON DELETE SET NULL for one column">

What should happen to a task when its assignee leaves the company (their membership is deleted)? The task should stay, unassigned. But a plain `ON DELETE SET NULL` on the foreign key `(tenant_id, assignee_id)` would set **both** columns to `NULL`, and `tenant_id` is `NOT NULL`, so the delete would fail. Since PostgreSQL 15 you can name the columns to clear: `ON DELETE SET NULL (assignee_id)`. A composite foreign key with any `NULL` column isn't checked at all, so an unassigned task (`assignee_id IS NULL`) is fine.

</Callout>

## Choosing ids

PandaTasks uses `bigint` identity columns: compact, fast, and easy to read in support tickets. Two things to keep in mind:

- **Ids are global**, shared by all tenants, so they **leak information**. If a new Globex task gets id 1,000,042, Globex can watch the number grow and estimate how busy the whole platform is. Never rely on an id being hard to guess: authorisation (and RLS, in the next part) is what protects data.
- If ids must be generated outside the database or must not reveal counts, use **UUIDs**. PostgreSQL 18 has a built-in **`uuidv7()`**, which puts a timestamp first. New ids are then almost always larger than older ones, so they're inserted at the end of the B-tree index, like a sequence, instead of at random places all over it, the main performance problem of random `gen_random_uuid()` (version 4) keys.

```sql
CREATE TABLE api_keys (
  id uuid PRIMARY KEY DEFAULT uuidv7(),
  tenant_id bigint NOT NULL REFERENCES tenants,
  label text NOT NULL
);
```

Users often want short, human numbers per tenant too ("PT-42" in Acme's own sequence). That's a **display number**, stored in its own column with `UNIQUE (tenant_id, number)`, never the primary key.

Create PandaTasks' **`tasks`** table so the database itself enforces the tenant rules. Columns:

- **`tenant_id`** `bigint NOT NULL`, **`id`** `bigint GENERATED ALWAYS AS IDENTITY`, **`project_id`** `bigint NOT NULL`, **`title`** `text NOT NULL`,
- **`status`** `text NOT NULL`, default **`'todo'`**, allowing only `'todo'`, `'doing'` and `'done'`,
- **`assignee_id`** `bigint`, which may be `NULL`.

Rules:

1. The primary key is **`(tenant_id, id)`**.
2. A task's project must belong to the **same tenant**; deleting a project **deletes its tasks**.
3. An assignee must be a **member of the same tenant**. When that membership is deleted, the task **stays** and only `assignee_id` becomes `NULL`.

The inserts and the query at the bottom should then run. The checks try to break your rules with bad inserts and deletes. 🔒

The status rule is `CHECK (status IN ('todo', 'doing', 'done'))` on the column, next to `DEFAULT 'todo'`.

## Recap

- PandaTasks uses **shared tables with a `tenant_id`** on every tenant-owned table: one migration path, cheap small tenants, plain SQL for reports. Database- and schema-per-tenant isolate more but don't scale to thousands of tenants.
- **Users are global**; **memberships `(tenant_id, user_id)`** carry each user's role per tenant.
- Tenant-owned tables use **`PRIMARY KEY (tenant_id, id)`**, and references inside a tenant are **composite foreign keys** that include `tenant_id`, so cross-tenant links are impossible.
- **`ON DELETE SET NULL (column)`** clears only the named column of a composite key.
- Per-tenant rules use per-tenant uniqueness, like **`UNIQUE (tenant_id, name)`**.
- Global ids leak counts and can be guessed; **`uuidv7()`** gives index-friendly UUIDs. Authorisation, not secret ids, protects data.
