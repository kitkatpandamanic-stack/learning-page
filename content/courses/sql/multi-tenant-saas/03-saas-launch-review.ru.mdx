PandaTasks запускается на следующей неделе. Схема разделяет арендаторов (Часть 1), а защита на уровне строк охраняет каждый запрос (Часть 2). Теперь — проверка, которую проводит каждая серьёзная команда до прихода настоящих клиентов: будет ли всё **быстро** при тысячах арендаторов, сможет ли команда **менять** схему без простоя, сможет ли **удалить** арендатора по запросу и **восстановиться** после плохого дня? 🚀

## Индексы для данных арендаторов

С RLS к каждому запросу к таблице арендатора добавляется `tenant_id = current_tenant_id()`. Поэтому правило для индексов простое: **каждый индекс на таблице арендатора начинается с `tenant_id`**. Тогда фильтр по арендатору и собственные условия запроса используют один индекс вместе, а строки каждого арендатора лежат в нём рядом.

Продакт назвал два самых горячих запроса: **доска проекта** (задачи одного проекта по статусу) и **«мои открытые задачи»** для вошедшего пользователя. Вот они — выполненные от имени приложения, с действующей политикой:

Вся суть — в длинной строке `Index Cond`. PostgreSQL **встроил (inlined)** `current_tenant_id()` (это простая SQL-функция `STABLE`) и использовал условие политики по **первому столбцу индекса** вместе с `assignee_id`. Он выбрал **частичный** индекс, потому что `status <> 'done'` из запроса совпадает с `WHERE` индекса, так что выполненных задач в нём даже нет. Разработчик вообще не писал фильтр по арендатору, а запрос всё равно читает только записи индекса Globex. Запрос доски точно так же использует `tasks_board_idx`.

Ещё две привычки для индексов арендаторов:

- **Ограничения уникальности — тоже в пределах арендатора**: `UNIQUE (tenant_id, name)` заодно служит индексом для «найти проект по имени» у этого арендатора.
- **Внешним ключам нужны индексы на ссылающейся стороне**: `tasks (tenant_id, project_id)` покрыт индексом доски (его первыми двумя столбцами), поэтому удаление проекта не сканирует все задачи.

## Киты и шумные соседи

Арендаторы никогда не бывают одного размера. У типичного SaaS тысячи крошечных арендаторов и горстка **китов (whales)**, у которых большая доля всех строк. Следите за этим с первого дня:

<CodeExample output={`CREATE TABLE

 tenant-5 |   562 |       3.2
(5 rows)`}>

```sql
CREATE TABLE tasks (
  tenant_id bigint NOT NULL,
  title text NOT NULL
);

-- каждый арендатор вдвое меньше предыдущего
INSERT INTO tasks (tenant_id, title)
SELECT t, 'Task ' || g
FROM generate_series(1, 5) AS t
CROSS JOIN generate_series(1, 18000) AS g
WHERE g <= 18000 / power(2, t);

SELECT
  'tenant-' || tenant_id AS tenant,
  count(*) AS tasks,
  round(100.0 * count(*) / sum(count(*)) OVER (), 1) AS share_pct
FROM tasks
GROUP BY tenant_id
ORDER BY tasks DESC, tenant_id;
```

</CodeExample>

Одному арендатору принадлежит больше половины данных. Киты создают проблему **шумных соседей (noisy neighbours)**: их большие отчёты съедают CPU и ввод-вывод, которые нужны маленьким арендаторам для загрузки страниц. Обычные средства защиты — примерно в том порядке, в каком команды их внедряют:

- **Лимиты на арендатора** в приложении (ограничения частоты запросов, размера страниц, очереди выгрузок) и `statement_timeout` для роли приложения, чтобы ни один запрос не выполнялся минутами.
- Тяжёлые отчёты и выгрузки — на **реплике для чтения** или заранее посчитанные в сводных таблицах.
- **Шардирование по `tenant_id`**: инструменты вроде **Citus** распределяют арендаторов по многим серверам и держат все строки арендатора вместе, так что соединения остаются локальными. Это работает только потому, что в каждой таблице есть `tenant_id`, и каждый ключ и внешний ключ его включает. Схема из Части 1 оставляет эту дверь открытой.
- Перенос отдельного кита в **собственную базу данных**: его легко скопировать (`WHERE tenant_id = …` для каждой таблицы), но тогда приложение должно направлять запросы этого арендатора в другое место.

## Секционирование журнала активности

В **журнал активности** попадает строка на каждое изменение у каждого арендатора, и это первая таблица, которая дорастёт до сотен миллионов строк. В неё только добавляют, читают её в основном как «недавняя активность моего арендатора», и у неё есть правило хранения по сроку, — поэтому она идеально подходит для **месячных секций по диапазону**, как в уроке [Секционирование больших таблиц](/learn/sql/table-partitioning). RLS требует одного дополнительного соображения:

```sql
CREATE TABLE activity_log (
  tenant_id bigint NOT NULL,
  id bigint GENERATED ALWAYS AS IDENTITY,
  created_at timestamp NOT NULL,
  action text NOT NULL,
  -- ключ секционирования должен входить в ключ; этот порядок также
  -- подходит для «последней активности моего арендатора»
  PRIMARY KEY (tenant_id, created_at, id)
) PARTITION BY RANGE (created_at);

CREATE TABLE activity_log_2025_06 PARTITION OF activity_log
  FOR VALUES FROM ('2025-06-01') TO ('2025-07-01');
CREATE TABLE activity_log_2025_07 PARTITION OF activity_log
  FOR VALUES FROM ('2025-07-01') TO ('2025-08-01');

INSERT INTO activity_log (tenant_id, created_at, action)
SELECT g % 3 + 1,
  timestamp '2025-06-01' + g * interval '7 minutes',
  'task.updated'
FROM generate_series(0, 12000) AS g;

CREATE FUNCTION current_tenant_id() RETURNS bigint
LANGUAGE sql STABLE
AS $$
  SELECT nullif(current_setting('app.tenant_id', true), '')::bigint
$$;

-- RLS и привилегии только на РОДИТЕЛЕ
ALTER TABLE activity_log ENABLE ROW LEVEL SECURITY;
CREATE POLICY tenant_isolation ON activity_log
  USING (tenant_id = current_tenant_id())
  WITH CHECK (tenant_id = current_tenant_id());
CREATE ROLE app_user NOLOGIN;
GRANT SELECT, INSERT ON activity_log TO app_user;

SET ROLE app_user;
SELECT set_config('app.tenant_id', '2', false);

-- через родителя: политики действуют, только строки арендатора 2
SELECT tableoid::regclass AS partition, count(*) AS events
FROM activity_log
GROUP BY partition
ORDER BY partition;

-- напрямую к секции: отказ
SELECT count(*) FROM activity_log_2025_06;
```

</CodeExample>

Политики секционированной таблицы применяются к запросам **через родителя**. Запрос, который напрямую называет секцию, проверяет собственные настройки RLS этой секции — они отдельные, и здесь их нет. Это безопасно только потому, что у `app_user` **нет привилегий на секции**, и прямой запрос отклоняется. Так и держите: выдавайте права на родителя, никогда — на секции, и пусть сторожевой запрос из Части 2 учитывает таблицы с `relkind = 'p'`.

Срок хранения зависит от тарифа: enterprise хранит два года, бесплатные арендаторы — 30 дней. Удаление месячных секций дёшево обеспечивает **самое длинное** правило. Для более коротких правил по тарифам либо каждую ночь запускайте небольшой пакетный `DELETE` для каждого бесплатного арендатора, либо просто **скрывайте** старые строки в приложении и дайте им уйти вместе с секцией. Договоритесь, какой вариант выбираете, до запуска и пропишите это в политике конфиденциальности.

## План миграций, который не уронит сайт

После запуска каждое изменение схемы выполняется, пока клиенты работают. Первое уже запланировано: у задач появится `priority`. Прежде чем писать миграцию, знайте, какие инструкции `ALTER TABLE` дешёвые, а какие **перезаписывают** всю таблицу под эксклюзивной блокировкой. `relfilenode`, id файла данных таблицы, меняется, когда таблица перезаписывается:

<CodeExample output={`CREATE TABLE

INSERT 0 20000

CREATE TABLE

INSERT 0 1

ALTER TABLE

 rewritten
-----------
 f
(1 row)

ALTER TABLE

 rewritten
-----------
 t
(1 row)`}>

```sql
CREATE TABLE tasks (
  tenant_id bigint NOT NULL,
  id bigint GENERATED ALWAYS AS IDENTITY,
  title text NOT NULL,
  PRIMARY KEY (tenant_id, id)
);
INSERT INTO tasks (tenant_id, title)
SELECT g % 10 + 1, 'Task ' || g
FROM generate_series(1, 20000) AS g;

CREATE TABLE file_before (node oid);
INSERT INTO file_before
SELECT relfilenode FROM pg_class WHERE relname = 'tasks';

-- константное значение по умолчанию: хранится в каталоге, мгновенно
ALTER TABLE tasks ADD COLUMN priority smallint NOT NULL DEFAULT 2;
SELECT relfilenode <> (SELECT node FROM file_before) AS rewritten
FROM pg_class
WHERE relname = 'tasks';

-- смена типа: каждая строка перезаписывается, под блокировкой
ALTER TABLE tasks ALTER COLUMN priority TYPE integer;
SELECT relfilenode <> (SELECT node FROM file_before) AS rewritten
FROM pg_class
WHERE relname = 'tasks';
```

</CodeExample>

Добавление столбца с константным значением по умолчанию (PostgreSQL 11+) — это изменение в каталоге, которое занимает миллисекунды. Смена его типа перезаписала все 20 000 строк; на таблице размером с кита это минуты простоя. Правила миграций PandaTasks, основанные на уроке [Миграции без простоя](/learn/sql/zero-downtime-migrations), записанные для команды:

```text
1. Каждая миграция начинается с:  SET lock_timeout = '3s';
   (если долгий запрос блокирует ALTER, быстро падаем и повторяем,
    а не выстраиваем все остальные запросы в очередь за ним)
2. Новые столбцы: допускающие NULL или с константным DEFAULT. Никаких перезаписей.
3. Индексы:   CREATE INDEX CONCURRENTLY ... (вне транзакции)
4. Ограничения и внешние ключи: добавляем NOT VALID, затем
              ALTER TABLE ... VALIDATE CONSTRAINT ... отдельным шагом позже
5. Заполнение данных (backfill): пакетами (например, по 5000 строк, по одному
              арендатору), каждый пакет — своя транзакция, с паузой между ними
6. Expand / contract: добавляем новое, выкатываем код, который пишет
   в оба места, заполняем данные, переключаем чтение и только потом удаляем старое.
```

`NOT VALID` заставляет PostgreSQL сразу применять новое ограничение к **новым** строкам, не проверяя существующие под тяжёлой блокировкой. Затем `VALIDATE CONSTRAINT` проверяет старые строки с блокировкой, при которой чтение и запись продолжаются.

## Выгрузка и удаление арендатора

Когда клиент уходит и просит удалить свои данные, должно исчезнуть всё с его `tenant_id`: задачи, проекты, членства, активность, файлы и их копии в кешах и поисковых индексах. С `ON DELETE CASCADE` от `tenants` инструкция `DELETE FROM tenants WHERE id = 42` делает это в **одной транзакции**. Для маленького арендатора это нормально. Для кита это миллионы удалений строк в одной транзакции: долгие блокировки, огромный всплеск WAL для реплик и мёртвые строки повсюду. Удаляйте крупных арендаторов **пакетами**: сначала дочерние строки, а строку арендатора — последней:

```sql
-- повторяйте, пока не удалится 0 строк, по транзакции на пакет
DELETE FROM tasks
WHERE (tenant_id, id) IN (
  SELECT tenant_id, id
  FROM tasks
  WHERE tenant_id = 42
  LIMIT 5000
);
```

Помните о бэкапах: удалённые данные продолжают жить в старых бэкапах, пока те не истекут. В политике конфиденциальности должно быть указано, сколько это длится (например, «в течение 35 дней»).

CREATE TYPE plan AS ENUM ('free', 'pro', 'enterprise');
CREATE TABLE tenants (
  id bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  slug text NOT NULL UNIQUE,
  plan plan NOT NULL
);
CREATE TABLE plan_limits (
  plan plan PRIMARY KEY,
  max_projects integer -- NULL означает без ограничений
);
CREATE TABLE projects (
  tenant_id bigint NOT NULL REFERENCES tenants,
  id bigint GENERATED ALWAYS AS IDENTITY,
  name text NOT NULL,
  PRIMARY KEY (tenant_id, id)
);
CREATE TABLE tasks (
  tenant_id bigint NOT NULL,
  id bigint GENERATED ALWAYS AS IDENTITY,
  project_id bigint NOT NULL,
  title text NOT NULL,
  status text NOT NULL DEFAULT 'todo',
  assignee_id bigint,
  PRIMARY KEY (tenant_id, id),
  FOREIGN KEY (tenant_id, project_id)
    REFERENCES projects (tenant_id, id)
);

SELECT p.tenant_id, p.id, 'Task ' || g,
  (ARRAY['todo', 'doing', 'done', 'done'])[g % 4 + 1],
  g % 50 + 1
FROM generate_series(1, 14000) AS g
JOIN projects AS p ON p.id = g % 7 + 1;
ANALYZE tasks;

CREATE INDEX tasks_board_idx
  ON tasks (tenant_id, project_id, status);
CREATE INDEX tasks_open_by_assignee_idx
  ON tasks (tenant_id, assignee_id)
  WHERE status <> 'done';

WITH project_counts AS (
  SELECT tenant_id, count(*) AS projects
  FROM projects
  GROUP BY tenant_id
),
open_counts AS (
  SELECT tenant_id, count(*) AS open_tasks
  FROM tasks
  WHERE status <> 'done'
  GROUP BY tenant_id
)
SELECT
  t.slug,
  t.plan,
  coalesce(pc.projects, 0) AS projects,
  coalesce(oc.open_tasks, 0) AS open_tasks,
  coalesce(coalesce(pc.projects, 0) > l.max_projects, false)
    AS over_limit
FROM tenants AS t
JOIN plan_limits AS l ON l.plan = t.plan
LEFT JOIN project_counts AS pc ON pc.tenant_id = t.id
LEFT JOIN open_counts AS oc ON oc.tenant_id = t.id
ORDER BY t.slug;
