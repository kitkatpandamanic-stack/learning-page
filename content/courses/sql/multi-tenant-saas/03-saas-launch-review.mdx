## Indexes for tenant data

With RLS, every query on a tenant table gets `tenant_id = current_tenant_id()` added to it. So the rule for indexes is simple: **every index on a tenant table starts with `tenant_id`**. Then the tenant filter and the query's own conditions use one index together, and each tenant's rows sit next to each other in it.

Product has named the two hottest queries: the **project board** (tasks of one project, by status) and **"my open tasks"** for the person logged in. Here they are, run as the app, with the policy in place:

```sql
FROM tasks
WHERE assignee_id = 7 AND status <> 'done';
```

</CodeExample>

The long `Index Cond` line is the point. PostgreSQL **inlined** `current_tenant_id()` (it's a simple `STABLE` SQL function) and used the policy's condition on the **first column of the index**, together with `assignee_id`. It picked the **partial** index, because the query's `status <> 'done'` matches the index's `WHERE`, so done tasks aren't even in it. The developer wrote no tenant filter at all, and the query still only reads Globex's index entries. The board query uses `tasks_board_idx` the same way.

Two more habits for tenant indexes:

- **Unique constraints are per tenant** too: `UNIQUE (tenant_id, name)` doubles as an index for "find a project by name" in that tenant.
- **Foreign keys need indexes on the referencing side**: `tasks (tenant_id, project_id)` is covered by the board index (its first two columns), so deleting a project doesn't scan all tasks.

## Whales and noisy neighbours

Tenants are never the same size. A typical SaaS has thousands of tiny tenants and a handful of **whales** that hold a big share of all rows. Track it from day one:

<CodeExample output={`CREATE TABLE

INSERT 0 17437

  tenant  | tasks | share_pct
----------+-------+-----------
 tenant-1 |  9000 |      51.6
 tenant-2 |  4500 |      25.8
 tenant-3 |  2250 |      12.9
 tenant-4 |  1125 |       6.5
 tenant-5 |   562 |       3.2
(5 rows)`}>

```sql
CREATE TABLE tasks (
  tenant_id bigint NOT NULL,
  title text NOT NULL
);

-- each tenant half the size of the one before
INSERT INTO tasks (tenant_id, title)
SELECT t, 'Task ' || g
FROM generate_series(1, 5) AS t
CROSS JOIN generate_series(1, 18000) AS g
WHERE g <= 18000 / power(2, t);

SELECT
  'tenant-' || tenant_id AS tenant,
  count(*) AS tasks,
  round(100.0 * count(*) / sum(count(*)) OVER (), 1) AS share_pct
FROM tasks
GROUP BY tenant_id
ORDER BY tasks DESC, tenant_id;
```

</CodeExample>

One tenant owns more than half of the data. Whales cause **noisy-neighbour** problems: their big reports eat the CPU and I/O that small tenants' page loads need. The usual defences, roughly in the order teams adopt them:

- **Per-tenant limits** in the app (rate limits, page sizes, export queues) and a `statement_timeout` for the app role, so no request runs for minutes.
- Heavy reports and exports on a **read replica**, or precomputed in summary tables.
- **Sharding by `tenant_id`**: tools such as **Citus** spread tenants over many servers and keep all of a tenant's rows together, so joins stay local. That only works because every table has `tenant_id` and every key and foreign key includes it. Part 1's design keeps that door open.
- Moving a single whale to its **own database**, which is easy to copy out (`WHERE tenant_id = …` on every table) but means the app must route that tenant's requests elsewhere.

## Partitioning the activity log

The **activity log** gets a row for every change in every tenant, and it's the first table to reach hundreds of millions of rows. It's append-only, read mostly as "recent activity of my tenant", and has a retention rule, so it's a perfect fit for **monthly range partitions**, as in [Partitioning Big Tables](/learn/sql/table-partitioning). RLS needs one extra thought:

```sql
CREATE TABLE activity_log (

  FOR VALUES FROM ('2025-07-01') TO ('2025-08-01');

INSERT INTO activity_log (tenant_id, created_at, action)
SELECT g % 3 + 1,
  timestamp '2025-06-01' + g * interval '7 minutes',
  'task.updated'
FROM generate_series(0, 12000) AS g;

CREATE FUNCTION current_tenant_id() RETURNS bigint
LANGUAGE sql STABLE
AS $$
  SELECT nullif(current_setting('app.tenant_id', true), '')::bigint
$$;

-- RLS and privileges on the PARENT only
ALTER TABLE activity_log ENABLE ROW LEVEL SECURITY;
CREATE POLICY tenant_isolation ON activity_log
  USING (tenant_id = current_tenant_id())
  WITH CHECK (tenant_id = current_tenant_id());
CREATE ROLE app_user NOLOGIN;
GRANT SELECT, INSERT ON activity_log TO app_user;

SET ROLE app_user;
SELECT set_config('app.tenant_id', '2', false);

-- through the parent: policies apply, only tenant 2's rows
SELECT tableoid::regclass AS partition, count(*) AS events
FROM activity_log
GROUP BY partition
ORDER BY partition;

-- straight at a partition: refused
SELECT count(*) FROM activity_log_2025_06;
```

</CodeExample>

Policies on a partitioned table apply to queries **through the parent**. A query that names a partition directly checks that partition's own RLS settings, which are separate, and here it has none. That's safe only because `app_user` has **no privileges on the partitions**, so the direct query is refused. Keep it that way: grant on the parent, never on partitions, and let the guard query from Part 2 include `relkind = 'p'` tables.

Retention depends on the plan: enterprise keeps two years, free tenants 30 days. Dropping monthly partitions enforces the **longest** rule cheaply. For shorter per-plan rules, either run a small batched `DELETE` per free tenant each night, or simply **hide** older rows in the app and let them age out with the partition. Agree on which one before launch, and write it in the privacy policy.

## A migration plan that won't take the site down

After launch, every schema change runs while customers are working. The first one is already planned: tasks get a `priority`. Before writing any migration, know which `ALTER TABLE` statements are cheap and which **rewrite** the whole table under an exclusive lock. `relfilenode`, the id of the table's data file, changes when the table is rewritten:

<CodeExample output={`CREATE TABLE

INSERT 0 20000

CREATE TABLE

INSERT 0 1

ALTER TABLE

 rewritten
-----------
 f
(1 row)

ALTER TABLE

 rewritten
-----------
 t
(1 row)`}>

```sql
CREATE TABLE tasks (
  tenant_id bigint NOT NULL,
  id bigint GENERATED ALWAYS AS IDENTITY,
  title text NOT NULL,
  PRIMARY KEY (tenant_id, id)
);
INSERT INTO tasks (tenant_id, title)
SELECT g % 10 + 1, 'Task ' || g
FROM generate_series(1, 20000) AS g;

CREATE TABLE file_before (node oid);
INSERT INTO file_before
SELECT relfilenode FROM pg_class WHERE relname = 'tasks';

-- a constant default: stored in the catalog, instant
ALTER TABLE tasks ADD COLUMN priority smallint NOT NULL DEFAULT 2;
SELECT relfilenode <> (SELECT node FROM file_before) AS rewritten
FROM pg_class
WHERE relname = 'tasks';

-- changing the type: every row is rewritten, under a lock
ALTER TABLE tasks ALTER COLUMN priority TYPE integer;
SELECT relfilenode <> (SELECT node FROM file_before) AS rewritten
FROM pg_class
WHERE relname = 'tasks';
```

</CodeExample>

Adding a column with a constant default (PostgreSQL 11+) is a catalog change that takes milliseconds. Changing its type rewrote all 20,000 rows; on a whale-sized table that's minutes of downtime. PandaTasks' migration rules, based on [Zero-Downtime Migrations](/learn/sql/zero-downtime-migrations), written down for the team:

```text
1. Every migration starts with:  SET lock_timeout = '3s';
   (if a long query blocks the ALTER, fail fast and retry,
    instead of queueing every other query behind it)
2. New columns: nullable or with a constant default. Never a rewrite.
3. Indexes:   CREATE INDEX CONCURRENTLY ... (outside a transaction)
4. Constraints and foreign keys: add NOT VALID, then
              ALTER TABLE ... VALIDATE CONSTRAINT ... in a later step
5. Backfills: in batches (e.g. 5,000 rows, one tenant at a time),
              each batch its own transaction, with a pause between
6. Expand / contract: add the new thing, deploy code that writes
   both, backfill, switch reads, and only then drop the old thing.
```

`NOT VALID` makes PostgreSQL enforce a new constraint for **new** rows immediately, without checking existing rows under a heavy lock. `VALIDATE CONSTRAINT` then checks the old rows with a lock that lets reads and writes continue.

## Exporting and deleting a tenant

When a customer leaves and asks for their data to be deleted, everything with their `tenant_id` must go: tasks, projects, memberships, activity, files, and their copies in caches and search indexes. With `ON DELETE CASCADE` from `tenants`, `DELETE FROM tenants WHERE id = 42` does it in **one transaction**. For a small tenant that's fine. For a whale, it's millions of row deletions in one transaction: long locks, a huge burst of WAL for the replicas, and dead rows everywhere. Delete big tenants in **batches**, children first, then the tenant row last:

```sql
-- repeat until it deletes 0 rows, one transaction per batch
DELETE FROM tasks
WHERE (tenant_id, id) IN (
  SELECT tenant_id, id
  FROM tasks
  WHERE tenant_id = 42
  LIMIT 5000
);
```

Remember the backups: deleted data lives on in old backups until they expire. Your privacy policy should say how long that is (for example "within 35 days").

## Recap

- With RLS, **every index on a tenant table starts with `tenant_id`**; check hot queries with `EXPLAIN` **as `app_user`** to see the policy used as an index condition. Partial indexes fit "open items" queries.
- Track tenant sizes: **whales** cause noisy-neighbour problems. Limits, timeouts, replicas and, eventually, **sharding by `tenant_id`** (possible because every key includes it).
- Partition append-only tenant data (the **activity log**) by month; put RLS and privileges on the **parent only**.
- Know which `ALTER TABLE` rewrites the table. Migrations use **`lock_timeout`**, **`CONCURRENTLY`**, **`NOT VALID` + `VALIDATE`**, batched backfills and expand/contract.
- Delete big tenants in **batches**, and remember the copies in backups, caches and search indexes.
- Go through the **launch checklist**: isolation, roles, requests, performance, big tables, concurrency, changes, recovery, tenants.
