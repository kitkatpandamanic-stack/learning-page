Until now you've queried tables that someone else designed: `customers`, `orders`, `products`. Every one of them started life as a **`CREATE TABLE`** statement, where somebody decided which columns the table has and what kind of value each column may hold.

In this lesson you'll become that somebody. 🐼 You'll create tables, choose **data types** for their columns, let PostgreSQL number your rows for you, and change or remove tables when your plans change.

## Your first CREATE TABLE

A `CREATE TABLE` statement names the table and lists its columns. Each column gets a **name** and a **data type**, separated by commas:

<CodeExample output={`CREATE TABLE

INSERT 0 2

     title      |  held_on   | seats | price | is_online
----------------+------------+-------+-------+-----------
 Intro to SQL   | 2025-09-06 |    30 | 12.50 | f
 Pandas & Plots | 2025-09-13 |    20 |  0.00 | t
(2 rows)`}>

```sql
CREATE TABLE workshops (
  title text,
  held_on date,
  seats integer,
  price numeric(6, 2),
  is_online boolean
);

INSERT INTO workshops (title, held_on, seats, price, is_online)
VALUES
  ('Intro to SQL', '2025-09-06', 30, 12.5, false),
  ('Pandas & Plots', '2025-09-13', 20, 0, true);

SELECT * FROM workshops;
```

</CodeExample>

PostgreSQL answers `CREATE TABLE` when the table exists. From then on it behaves exactly like the sample tables: you can `INSERT` into it, `SELECT` from it, join it to other tables.

Notice how PostgreSQL **shaped the values** to fit their types: `12.5` became `12.50` because `price` keeps two decimal places, and booleans print as `t` and `f` (for true and false).

<Callout type="note" title="Every run starts fresh">

Tables you create here only live for one run: each time you press **Run**, you get a fresh copy of the sample database. That's handy while you experiment, because a mistake is never permanent. On a real server, a table stays until somebody drops it.

</Callout>

Table names follow the same style as column names: **lower case with underscores** (`order_items`, not `OrderItems`), and usually **plural**, because a table holds many things.

## Choosing data types

A column's **data type** decides which values it accepts and what you can do with them. You can add numbers, but not text; you can subtract dates to get days between them. These types cover most tables you'll ever build:

| Type | Holds | Example |
| --- | --- | --- |
| `text` | Text of any length | `'Mei Lin'` |
| `integer` | Whole numbers up to about ±2.1 billion | `42` |
| `bigint` | Bigger whole numbers | `9000000000` |
| `numeric(p, s)` | Exact decimals: `p` digits, `s` after the point | `12.50` |
| `boolean` | `true` or `false` | `true` |
| `date` | A calendar day | `'2025-09-06'` |
| `timestamptz` | A moment in time, with time zone | `'2025-09-06 18:30+01'` |

PostgreSQL **checks every value** against its column's type. Text that isn't a number can't sneak into a number column:

<CodeExample output={`CREATE TABLE

ERROR:  invalid input syntax for type integer: "thirty"
LINE 7: VALUES ('Intro to SQL', 'thirty');
                                ^`}>

```sql
CREATE TABLE workshops (
  title text,
  seats integer
);

INSERT INTO workshops (title, seats)
VALUES ('Intro to SQL', 'thirty');
```

</CodeExample>

That's one of the big wins of a database over a spreadsheet: the wrong kind of data is stopped at the door, and every program reading the table can trust that `seats` is a number.

### Money: numeric, not float

For prices and money, always use **`numeric`**. It stores decimals **exactly**. The other decimal types, `real` and `double precision` (also called `float`), are fast but approximate, which is fine for measurements and terrible for money:

<CodeExample output={`      float_sum      | numeric_sum
---------------------+-------------
 0.30000000000000004 |         0.3
(1 row)

 rounded
---------
   12.35
(1 row)

ERROR:  numeric field overflow
DETAIL:  A field with precision 6, scale 2 must round to an absolute value less than 10^4.`}>

```sql
SELECT 0.1::float + 0.2::float AS float_sum,
  0.1::numeric + 0.2::numeric AS numeric_sum;

SELECT 12.345::numeric(6, 2) AS rounded;

SELECT 12345.6::numeric(6, 2) AS too_big;
```

</CodeExample>

`numeric(6, 2)` means "6 digits in total, 2 of them after the decimal point", so the biggest value is `9999.99`. Extra decimals are rounded; a number that's too big is an error rather than a silent mistake. Plain `numeric` with no limits also works and stores whatever you give it.

### Text: just use text

Many databases make you pick a length, like `varchar(255)`. In PostgreSQL, **`text` is the normal choice**: it has no length limit and is just as fast. `varchar(n)` exists too, but if you need a rule such as "at most 50 characters", there's a clearer tool for it: a `CHECK` constraint, which you'll meet in the next lesson.

### Dates and times: date or timestamptz

- **`date`** is a calendar day with no time: birthdays, due dates, the day a workshop is held.
- **`timestamptz`** ("timestamp with time zone") is an exact **moment**: when an order was placed, when a user signed in.

`timestamptz` stores the moment in UTC and shows it in the **session's time zone**. The same moment looks different in London and Tokyo, but it's still the same moment:

<CodeExample output={`SET

CREATE TABLE

INSERT 0 1

       starts_at
------------------------
 2025-09-06 17:30:00+00
(1 row)

SET

       starts_at
------------------------
 2025-09-07 02:30:00+09
(1 row)`}>

```sql
SET timezone = 'UTC';

CREATE TABLE talks (
  title text,
  starts_at timestamptz
);

-- 18:30 in London (summer time, UTC+1)
INSERT INTO talks (title, starts_at)
VALUES ('Panda Keynote', '2025-09-06 18:30+01');

SELECT starts_at FROM talks;

SET timezone = 'Asia/Tokyo';

SELECT starts_at FROM talks;
```

</CodeExample>

There's also plain **`timestamp`** (without time zone), which the sample `orders.ordered_at` column uses. It stores a date and a clock time but doesn't know *where*, so `09:00` could mean nine o'clock anywhere in the world. For moments that real people and servers in different places care about, prefer `timestamptz`.

<Callout type="tip" title="Pick the narrowest type that fits">

A type is a free rule. Store a yes/no answer as `boolean`, not as the text `'yes'`; a day as `date`, not as `'06/09/2025'`. Then sorting, maths and comparisons all just work, and nobody can store `'maybe'` or `'31/02/2025'`.

</Callout>

## Identity columns: let the database number rows

Almost every table has an **`id`** column: a number that identifies each row, so other tables can point at it ("order 17 belongs to customer 8"). You don't want to invent those numbers yourself. An **identity column** makes PostgreSQL hand out 1, 2, 3… automatically:

<CodeExample output={`CREATE TABLE

INSERT 0 2

 id |     title
----+----------------
  1 | Intro to SQL
  2 | Pandas & Plots
(2 rows)

ERROR:  cannot insert a non-DEFAULT value into column "id"
DETAIL:  Column "id" is an identity column defined as GENERATED ALWAYS.
HINT:  Use OVERRIDING SYSTEM VALUE to override.`}>

```sql
CREATE TABLE workshops (
  id integer GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  title text
);

INSERT INTO workshops (title)
VALUES ('Intro to SQL'), ('Pandas & Plots');

SELECT id, title FROM workshops ORDER BY id;

INSERT INTO workshops (id, title) VALUES (7, 'Lucky Seven');
```

</CodeExample>

Read `id integer GENERATED ALWAYS AS IDENTITY PRIMARY KEY` piece by piece:

- **`integer`**: the ids are whole numbers (use `bigint` for tables that may one day pass two billion rows).
- **`GENERATED ALWAYS AS IDENTITY`**: PostgreSQL always picks the value. Trying to choose one yourself is an error, which protects you from clashing ids. `GENERATED BY DEFAULT AS IDENTITY` is the relaxed version: it picks a value unless you give one.
- **`PRIMARY KEY`**: the column identifies rows, so it must be unique and never empty. More on keys in the next lesson.

To find out which id a new row got, add **`RETURNING`** to the insert:

<CodeExample output={`CREATE TABLE

 id |    title
----+--------------
  1 | Intro to SQL
(1 row)`}>

```sql
CREATE TABLE workshops (
  id integer GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  title text
);

INSERT INTO workshops (title)
VALUES ('Intro to SQL')
RETURNING id, title;
```

</CodeExample>

<Callout type="note" title="What about serial?">

The sample tables use `id serial PRIMARY KEY`. **`serial`** is the older way to get automatic numbers and you'll see it in lots of existing databases. It works, but identity columns are the SQL standard and are stricter, so prefer `GENERATED ... AS IDENTITY` in new tables.

</Callout>

## Looking at a table's structure

How do you see which columns a table has? In the **psql** terminal client, you'd type a shortcut:

```text
shop=> \d products
                             Table "public.products"
  Column  |     Type     | Nullable |               Default
----------+--------------+----------+--------------------------------------
 id       | integer      | not null | nextval('products_id_seq'::regclass)
 name     | text         | not null |
 ...
```

Shortcuts like `\d` belong to psql, not to SQL, so they don't work here. The same information is available to plain SQL in **`information_schema`**, a set of built-in tables that describe your database:

<CodeExample output={` column_name | data_type | is_nullable | column_default
-------------+-----------+-------------+----------------
 name        | text      | NO          | NULL
 category    | text      | NO          | NULL
 price       | numeric   | NO          | NULL
 stock       | integer   | NO          | 0
(4 rows)`}>

```sql
SELECT column_name, data_type, is_nullable, column_default
FROM information_schema.columns
WHERE table_name = 'products'
  AND column_name <> 'id'
ORDER BY ordinal_position;
```

</CodeExample>

`ordinal_position` is the column's place in the table (1, 2, 3…), so ordering by it lists the columns in the order they were created.

## Changing a table with ALTER TABLE

Plans change. **`ALTER TABLE`** changes a table that already has data in it, without starting over:

<CodeExample output={`CREATE TABLE

INSERT 0 2

ALTER TABLE

ALTER TABLE

ALTER TABLE

ALTER TABLE

 id |     title      | capacity | level
----+----------------+----------+-------
  1 | Intro to SQL   |       30 | all
  2 | Pandas & Plots |       20 | all
(2 rows)`}>

```sql
CREATE TABLE workshops (
  id integer GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  title text,
  seats integer,
  room text
);

INSERT INTO workshops (title, seats, room)
VALUES ('Intro to SQL', 30, 'B12'), ('Pandas & Plots', 20, 'B14');

-- add a column (existing rows get the default)
ALTER TABLE workshops ADD COLUMN level text DEFAULT 'all';

-- rename a column
ALTER TABLE workshops RENAME COLUMN seats TO capacity;

-- remove a column (and its data!)
ALTER TABLE workshops DROP COLUMN room;

-- change a column's type
ALTER TABLE workshops ALTER COLUMN capacity TYPE bigint;

SELECT * FROM workshops ORDER BY id;
```

</CodeExample>

The most common forms:

- `ALTER TABLE t ADD COLUMN name type` adds a column. Existing rows get `NULL`, or the `DEFAULT` if you give one.
- `ALTER TABLE t RENAME COLUMN old TO new` and `ALTER TABLE t RENAME TO new_name` rename things.
- `ALTER TABLE t DROP COLUMN name` removes a column **and all its values**.
- `ALTER TABLE t ALTER COLUMN name TYPE new_type` converts a column. If PostgreSQL can't convert automatically (say, text to numbers), add `USING` with an expression that does it: `ALTER COLUMN price TYPE numeric USING price::numeric`.

On a busy production database, some of these changes lock the table or rewrite every row, so teams plan them carefully. You'll learn the safe recipes in Level 3; for now, enjoy the freedom of a database only you are using.

## Removing a table with DROP TABLE

**`DROP TABLE`** deletes a table: its columns, its rows, everything. `IF EXISTS` stops it from failing when the table isn't there, which is handy at the top of a script you run again and again:

<CodeExample output={`DROP TABLE

NOTICE:  table "workshops" does not exist, skipping
DROP TABLE

CREATE TABLE

 count
-------
     0
(1 row)`}>

```sql
DROP TABLE movies;

DROP TABLE IF EXISTS workshops;

CREATE TABLE workshops (
  id integer GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  title text
);

SELECT count(*) FROM workshops;
```

</CodeExample>

Yes, that dropped the sample `movies` table. Don't worry: the next run starts with a fresh copy. There's a sibling statement, `CREATE TABLE IF NOT EXISTS`, which skips the creation when the table is already there.

<Callout type="danger" title="There is no undo">

On a real server, `DROP TABLE` (and `DROP COLUMN`) is instant and permanent: there's no recycle bin. Real teams protect themselves with backups and by giving most users no permission to drop anything. Before dropping, double-check **which database** you're connected to: "I thought I was on my laptop, not production" is a classic disaster story.

</Callout>

If other tables point at the one you're dropping (orders point at customers, for example), PostgreSQL refuses to drop it. `DROP TABLE customers CASCADE` would drop the links too; use it only when you understand exactly what goes with it.

## Recap

- `CREATE TABLE name (column type, ...)` creates a table; names are lower_snake_case and usually plural.
- Everyday types: `text`, `integer`/`bigint`, `numeric(p, s)` for exact decimals and money, `boolean`, `date`, and `timestamptz` for moments in time.
- PostgreSQL rejects values that don't fit a column's type, so the data stays trustworthy.
- `id integer GENERATED ALWAYS AS IDENTITY PRIMARY KEY` numbers rows automatically; `RETURNING id` tells you the new id.
- `information_schema.columns` describes any table's columns (psql's `\d` does the same in the terminal).
- `ALTER TABLE` adds, renames, drops and retypes columns; `DROP TABLE` (with `IF EXISTS`) removes a whole table, permanently on a real server.
