Data types stop `'thirty'` from landing in a number column. But they can't stop a **negative** price, two customers with the **same email**, or an order for a customer who **doesn't exist**. Those are all valid numbers and texts, just wrong ones.

**Constraints** are rules you attach to a table, and PostgreSQL enforces them on every single insert and update, whichever app, script or tired human is writing. Bugs come and go; constraints keep the data honest. 🛡️

## A table with no rules

Here's what a table without constraints lets through:

<CodeExample output={`CREATE TABLE

INSERT 0 3

 name |       email       | age
------+-------------------+-----
 Mei  | mei@pandadev.test |  34
 Mei  | mei@pandadev.test |  -3
 NULL | NULL              |  29
(3 rows)`}>

```sql
CREATE TABLE members (
  name text,
  email text,
  age integer
);

INSERT INTO members (name, email, age)
VALUES
  ('Mei', 'mei@pandadev.test', 34),
  ('Mei', 'mei@pandadev.test', -3),
  (NULL, NULL, 29);

SELECT * FROM members;
```

</CodeExample>

A duplicate member, a negative age and a member with no name at all. Each problem will come back later as a confusing bug ("why did Mei get two welcome emails?"). Let's add the rules one by one.

## NOT NULL and DEFAULT

**`NOT NULL`** means "this column must always have a value". **`DEFAULT`** gives a value to use when an insert doesn't mention the column:

<CodeExample output={`CREATE TABLE

INSERT 0 1

 name |       email       | joined_on  | is_active
------+-------------------+------------+-----------
 Mei  | mei@pandadev.test | 2025-01-15 | t
(1 row)

ERROR:  null value in column "name" of relation "members" violates not-null constraint
DETAIL:  Failing row contains (null, sam@pandadev.test, 2025-01-15, t).`}>

```sql
CREATE TABLE members (
  name text NOT NULL,
  email text NOT NULL,
  joined_on date NOT NULL DEFAULT '2025-01-15',
  is_active boolean NOT NULL DEFAULT true
);

INSERT INTO members (name, email)
VALUES ('Mei', 'mei@pandadev.test');

SELECT * FROM members;

INSERT INTO members (name, email)
VALUES (NULL, 'sam@pandadev.test');
```

</CodeExample>

The first insert only gave `name` and `email`, so `joined_on` and `is_active` took their defaults. The second insert broke the rule, and PostgreSQL refused the whole row, telling you exactly which column and which row.

In real tables the default for a date is usually **`current_date`**, and for a moment `now()`: `created_at timestamptz NOT NULL DEFAULT now()`. (This lesson uses a fixed date so the output is the same every time you run it.)

<Callout type="tip" title="NOT NULL should be your default">

Most columns should be `NOT NULL`. Allow `NULL` only when "unknown" or "doesn't apply" is a real, meaningful answer, like a customer's `city` (the sample database has two customers without one) or a loan's `returned_on` (not returned yet). Every nullable column is a place where queries need to think about three-valued logic.

</Callout>

## PRIMARY KEY

A **primary key** is the column (or columns) that identifies each row. It combines two rules: values must be **unique** and **not null**. A table has at most one primary key, and nearly every table should have one:

<CodeExample output={`ERROR:  duplicate key value violates unique constraint "products_pkey"
DETAIL:  Key (id)=(1) already exists.`}>

```sql
INSERT INTO products (id, name, category, price)
VALUES (1, 'Oolong', 'tea', 9.00);
```

</CodeExample>

Product 1 is already Jasmine Tea, so a second product 1 is refused. The constraint got an automatic name, **`products_pkey`**, which is what error messages show.

A primary key can span **several columns**. The sample `order_items` table has `PRIMARY KEY (order_id, product_id)`: an order can contain many products, and a product can appear in many orders, but the same product can appear only **once per order** (that's what `quantity` is for):

<CodeExample output={`ERROR:  duplicate key value violates unique constraint "order_items_pkey"
DETAIL:  Key (order_id, product_id)=(1, 8) already exists.`}>

```sql
INSERT INTO order_items (order_id, product_id, quantity, unit_price)
VALUES (1, 8, 1, 29.00);
```

</CodeExample>

Most tables use a **surrogate key**: a meaningless `id` number generated by the database, like the identity columns from [the previous lesson](/learn/sql/creating-tables). The alternative is a **natural key**, a real-world value such as an email or an ISBN. Natural keys look tempting, but real-world values change (people change emails) and are sometimes reused, so a stable `id` plus a `UNIQUE` rule on the natural value is usually the better design.

## UNIQUE

**`UNIQUE`** forbids duplicates in a column that isn't the primary key. Emails, usernames and product codes are typical:

<CodeExample output={`ERROR:  duplicate key value violates unique constraint "customers_email_key"
DETAIL:  Key (email)=(mei@pandadev.test) already exists.`}>

```sql
INSERT INTO customers (name, email, country, joined_on)
VALUES ('Mei Again', 'mei@pandadev.test', 'UK', '2025-07-01');
```

</CodeExample>

A UNIQUE constraint can also cover a **combination** of columns: `UNIQUE (team_id, shirt_number)` lets two teams each have a number 10, but not one team with two.

One surprise: **NULLs don't clash**. Because `NULL` means "unknown", PostgreSQL doesn't consider two NULLs equal, so a `UNIQUE` column can hold many of them. If one NULL should be the limit, write `UNIQUE NULLS NOT DISTINCT`, or (more often) make the column `NOT NULL`.

## CHECK

A **`CHECK`** constraint is a condition every row must pass, written like a `WHERE` condition. The sample `products` table has `CHECK (price > 0)`, so even an update can't make a price negative:

<CodeExample output={`ERROR:  new row for relation "products" violates check constraint "products_price_check"
DETAIL:  Failing row contains (1, Jasmine Tea, tea, -1.00, 40).`}>

```sql
UPDATE products SET price = -1 WHERE id = 1;
```

</CodeExample>

Checks can compare **several columns** of the same row, and you can **name** constraints with `CONSTRAINT name`, so error messages say what went wrong in your words:

<CodeExample output={`CREATE TABLE

INSERT 0 1

ERROR:  new row for relation "trips" violates check constraint "trips_dates_in_order"
DETAIL:  Failing row contains (Lisbon, 2025-08-10, 2025-08-03, 3).`}>

```sql
CREATE TABLE trips (
  city text NOT NULL,
  starts_on date NOT NULL,
  ends_on date NOT NULL,
  travellers integer NOT NULL CHECK (travellers BETWEEN 1 AND 12),
  CONSTRAINT trips_dates_in_order CHECK (ends_on >= starts_on)
);

INSERT INTO trips VALUES ('Kyoto', '2025-04-01', '2025-04-09', 2);

INSERT INTO trips VALUES ('Lisbon', '2025-08-10', '2025-08-03', 3);
```

</CodeExample>

A check written **after** the columns, like `trips_dates_in_order`, is a **table constraint**; one written inside a column definition, like the `travellers` check, is a **column constraint**. They work the same way. Checks are great for allowed lists too: the sample `orders` table has `CHECK (status IN ('paid', 'shipped', 'delivered', 'cancelled'))`.

<Callout type="warning" title="CHECK passes on NULL">

A check fails only when its condition is **false**. With a NULL, `travellers BETWEEN 1 AND 12` is unknown, not false, so the row is accepted. That's why checks are usually paired with `NOT NULL`, as in the `trips` table above.

</Callout>

## FOREIGN KEY: links between tables

A **foreign key** says "the value in this column must exist in that other table". It's what keeps relationships between tables valid. The sample `orders.customer_id` is declared as `REFERENCES customers (id)`, so an order can't point at a customer who doesn't exist, and a customer who has orders can't simply vanish:

<CodeExample output={`ERROR:  insert or update on table "orders" violates foreign key constraint "orders_customer_id_fkey"
DETAIL:  Key (customer_id)=(999) is not present in table "customers".`}>

```sql
INSERT INTO orders (customer_id, ordered_at, status)
VALUES (999, '2025-07-01 10:00', 'paid');
```

</CodeExample>

<CodeExample output={`ERROR:  update or delete on table "customers" violates foreign key constraint "orders_customer_id_fkey" on table "orders"
DETAIL:  Key (id)=(1) is still referenced from table "orders".`}>

```sql
DELETE FROM customers WHERE id = 1;
```

</CodeExample>

The table being pointed at (`customers`) is the **parent**; the one doing the pointing (`orders`) is the **child**. Without this constraint, deleting a customer would leave **orphan** orders that belong to nobody, and every report joining orders to customers would quietly lose them.

### What happens on delete?

When a parent row is deleted, the foreign key's **`ON DELETE`** rule decides what happens to its children:

| Rule | When the parent is deleted |
| --- | --- |
| `NO ACTION` (the default) / `RESTRICT` | The delete fails while children exist |
| `CASCADE` | The children are deleted too |
| `SET NULL` | The children's foreign key becomes `NULL` |
| `SET DEFAULT` | The children's foreign key gets its default |

Pick the rule that matches the real world. On a blog, comments make no sense without their post, so they should go with it; a post's editor leaving the company shouldn't delete the post; and an author with posts shouldn't be deletable at all:

<CodeExample output={`CREATE TABLE

CREATE TABLE

CREATE TABLE

INSERT 0 3

INSERT 0 2

INSERT 0 3

DELETE 1

 id | post_id |  body
----+---------+---------
  1 |       1 | So true
  2 |       1 | Zzz
(2 rows)

DELETE 1

 id |     title      | author_id | editor_id
----+----------------+-----------+-----------
  1 | Why pandas nap |         1 |      NULL
(1 row)

ERROR:  update or delete on table "authors" violates foreign key constraint "posts_author_id_fkey" on table "posts"
DETAIL:  Key (id)=(1) is still referenced from table "posts".`}>

```sql
CREATE TABLE authors (
  id integer GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  name text NOT NULL
);

CREATE TABLE posts (
  id integer GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  title text NOT NULL,
  author_id integer NOT NULL REFERENCES authors (id),
  editor_id integer REFERENCES authors (id) ON DELETE SET NULL
);

CREATE TABLE comments (
  id integer GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  post_id integer NOT NULL
    REFERENCES posts (id) ON DELETE CASCADE,
  body text NOT NULL
);

INSERT INTO authors (name) VALUES ('Mei'), ('Sam'), ('Ada');
INSERT INTO posts (title, author_id, editor_id)
VALUES ('Why pandas nap', 1, 3), ('Bamboo, ranked', 2, 3);
INSERT INTO comments (post_id, body)
VALUES (1, 'So true'), (1, 'Zzz'), (2, 'Ten out of ten');

-- CASCADE: the post's comments go with it
DELETE FROM posts WHERE id = 2;
SELECT * FROM comments ORDER BY id;

-- SET NULL: Ada leaves, her posts lose their editor
DELETE FROM authors WHERE id = 3;
SELECT * FROM posts ORDER BY id;

-- NO ACTION: Mei still has posts, so she can't be deleted
DELETE FROM authors WHERE id = 1;
```

</CodeExample>

<Callout type="tip" title="Index your foreign keys">

PostgreSQL automatically indexes primary keys and UNIQUE columns, but **not** foreign key columns. Joins on `orders.customer_id` and every delete from `customers` (which must look for children) get faster with an index: `CREATE INDEX ON orders (customer_id);`. You'll learn how indexes work in Level 2.

</Callout>

## Adding constraints to an existing table

Forgot a rule? `ALTER TABLE ... ADD CONSTRAINT` adds it later. PostgreSQL first checks **every existing row**, and refuses if any of them already break the rule:

<CodeExample output={`ALTER TABLE

ALTER TABLE

ERROR:  check constraint "products_stock_positive" of relation "products" is violated by some row`}>

```sql
ALTER TABLE products
  ADD CONSTRAINT products_name_unique UNIQUE (name);

ALTER TABLE products
  ADD CONSTRAINT products_stock_not_negative CHECK (stock >= 0);

ALTER TABLE products
  ADD CONSTRAINT products_stock_positive CHECK (stock > 0);
```

</CodeExample>

The last one fails because Earl Grey and Clean Python have a stock of 0: you'd have to fix (or delete) those rows first. Related commands: `ALTER TABLE t ALTER COLUMN c SET NOT NULL`, `ALTER COLUMN c SET DEFAULT value`, and `ALTER TABLE t DROP CONSTRAINT name` to remove a rule.

To see a table's constraints, ask `information_schema` again:

<CodeExample output={`       constraint_name       | constraint_type
-----------------------------+-----------------
 orders_customer_id_fkey     | FOREIGN KEY
 orders_customer_id_not_null | CHECK
 orders_id_not_null          | CHECK
 orders_ordered_at_not_null  | CHECK
 orders_pkey                 | PRIMARY KEY
 orders_status_check         | CHECK
 orders_status_not_null      | CHECK
(7 rows)`}>

```sql
SELECT constraint_name, constraint_type
FROM information_schema.table_constraints
WHERE table_name = 'orders'
ORDER BY constraint_name;
```

</CodeExample>

Each rule shows up with its name. Since PostgreSQL 18, `NOT NULL` rules are listed too, as `CHECK` constraints named `..._not_null`.

## Recap

- **Constraints** are rules PostgreSQL enforces on every insert and update, no matter who writes the data.
- `NOT NULL` requires a value; `DEFAULT` fills one in when an insert leaves the column out.
- `PRIMARY KEY` = unique + not null, one per table, possibly over several columns like `(order_id, product_id)`.
- `UNIQUE` forbids duplicates (NULLs don't count as duplicates); `CHECK (condition)` rejects rows where the condition is false.
- `REFERENCES parent (id)` is a foreign key: children must point at existing parents. `ON DELETE CASCADE`, `SET NULL` or the default `NO ACTION` decide what a parent's delete does.
- `ALTER TABLE ... ADD CONSTRAINT` adds a rule later, but only if every existing row already obeys it.
