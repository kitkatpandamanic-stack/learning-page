Типы данных не дают `'thirty'` попасть в числовой столбец. Но они не помешают **отрицательной** цене, двум покупателям с **одинаковым email** или заказу от покупателя, которого **не существует**. Всё это допустимые числа и строки — просто неправильные.

**Ограничения** (constraints) — это правила, которые вы прикрепляете к таблице, и PostgreSQL проверяет их при каждой вставке и каждом обновлении, кто бы ни записывал данные: приложение, скрипт или уставший человек. Баги приходят и уходят, а ограничения поддерживают данные в честном виде. 🛡️

## Таблица без правил

Вот что пропускает таблица без ограничений:

<CodeExample output={`CREATE TABLE

INSERT 0 3

 name |       email       | age
------+-------------------+-----
 Mei  | mei@pandadev.test |  34
 Mei  | mei@pandadev.test |  -3
 NULL | NULL              |  29
(3 rows)`}>

```sql
CREATE TABLE members (
  name text,
  email text,
  age integer
);

INSERT INTO members (name, email, age)
VALUES
  ('Mei', 'mei@pandadev.test', 34),
  ('Mei', 'mei@pandadev.test', -3),
  (NULL, NULL, 29);

SELECT * FROM members;
```

</CodeExample>

Участник-дубликат, отрицательный возраст и участник вообще без имени. Каждая из этих проблем позже вернётся в виде запутанного бага («почему Мэй получила два приветственных письма?»). Давайте добавлять правила по одному.

## NOT NULL и DEFAULT

**`NOT NULL`** означает «в этом столбце всегда должно быть значение». **`DEFAULT`** задаёт значение, которое используется, когда вставка не упоминает столбец:

<CodeExample output={`CREATE TABLE

INSERT 0 1

 name |       email       | joined_on  | is_active
------+-------------------+------------+-----------
 Mei  | mei@pandadev.test | 2025-01-15 | t
(1 row)

ERROR:  null value in column "name" of relation "members" violates not-null constraint
DETAIL:  Failing row contains (null, sam@pandadev.test, 2025-01-15, t).`}>

```sql
CREATE TABLE members (
  name text NOT NULL,
  email text NOT NULL,
  joined_on date NOT NULL DEFAULT '2025-01-15',
  is_active boolean NOT NULL DEFAULT true
);

INSERT INTO members (name, email)
VALUES ('Mei', 'mei@pandadev.test');

SELECT * FROM members;

INSERT INTO members (name, email)
VALUES (NULL, 'sam@pandadev.test');
```

</CodeExample>

Первая вставка указала только `name` и `email`, поэтому `joined_on` и `is_active` получили значения по умолчанию. Вторая вставка нарушила правило, и PostgreSQL отклонил строку целиком, точно указав, какой столбец и какая строка виноваты.

В настоящих таблицах значение по умолчанию для даты обычно **`current_date`**, а для момента времени — `now()`: `created_at timestamptz NOT NULL DEFAULT now()`. (В этом уроке используется фиксированная дата, чтобы вывод был одинаковым при каждом запуске.)

<Callout type="tip" title="NOT NULL — ваш выбор по умолчанию">

Большинство столбцов должны быть `NOT NULL`. Разрешайте `NULL`, только когда «неизвестно» или «не применимо» — настоящий осмысленный ответ, как `city` у покупателя (в учебной базе у двух покупателей город не указан) или `returned_on` у выдачи книги (ещё не вернули). Каждый столбец, допускающий NULL, — это место, где запросам приходится думать о трёхзначной логике.

</Callout>

## PRIMARY KEY

**Первичный ключ** (primary key) — это столбец (или столбцы), который идентифицирует каждую строку. Он объединяет два правила: значения должны быть **уникальными** и **не NULL**. У таблицы может быть не больше одного первичного ключа, и почти у каждой таблицы он должен быть:

<CodeExample output={`ERROR:  duplicate key value violates unique constraint "products_pkey"
DETAIL:  Key (id)=(1) already exists.`}>

```sql
INSERT INTO products (id, name, category, price)
VALUES (1, 'Oolong', 'tea', 9.00);
```

</CodeExample>

Товар 1 — это уже Jasmine Tea, поэтому второй товар 1 отклоняется. Ограничение получило автоматическое имя **`products_pkey`** — его и показывают сообщения об ошибках.

Первичный ключ может охватывать **несколько столбцов**. У учебной таблицы `order_items` есть `PRIMARY KEY (order_id, product_id)`: в заказе может быть много товаров, а товар может встречаться во многих заказах, но один и тот же товар может встретиться **только один раз в заказе** (для этого есть `quantity`):

<CodeExample output={`ERROR:  duplicate key value violates unique constraint "order_items_pkey"
DETAIL:  Key (order_id, product_id)=(1, 8) already exists.`}>

```sql
INSERT INTO order_items (order_id, product_id, quantity, unit_price)
VALUES (1, 8, 1, 29.00);
```

</CodeExample>

Большинство таблиц используют **суррогатный ключ** (surrogate key): ничего не значащий номер `id`, который генерирует база, как столбцы идентификации из [предыдущего урока](/learn/sql/creating-tables). Альтернатива — **естественный ключ** (natural key), значение из реального мира, например email или ISBN. Естественные ключи выглядят заманчиво, но значения из реального мира меняются (люди меняют email) и иногда используются повторно, поэтому стабильный `id` плюс правило `UNIQUE` на естественном значении — обычно более удачная схема.

## UNIQUE

**`UNIQUE`** запрещает дубликаты в столбце, который не является первичным ключом. Типичные примеры — email, имена пользователей и артикулы товаров:

<CodeExample output={`ERROR:  duplicate key value violates unique constraint "customers_email_key"
DETAIL:  Key (email)=(mei@pandadev.test) already exists.`}>

```sql
INSERT INTO customers (name, email, country, joined_on)
VALUES ('Mei Again', 'mei@pandadev.test', 'UK', '2025-07-01');
```

</CodeExample>

Ограничение UNIQUE может охватывать и **сочетание** столбцов: `UNIQUE (team_id, shirt_number)` позволяет двум командам иметь по десятому номеру, но не одной команде — два.

Один сюрприз: **NULL не конфликтуют**. Поскольку `NULL` означает «неизвестно», PostgreSQL не считает два NULL равными, так что в столбце с `UNIQUE` их может быть сколько угодно. Если допустим только один NULL, напишите `UNIQUE NULLS NOT DISTINCT` или (чаще) сделайте столбец `NOT NULL`.

## CHECK

Ограничение **`CHECK`** — это условие, которому должна удовлетворять каждая строка; оно записывается так же, как условие в `WHERE`. У учебной таблицы `products` есть `CHECK (price > 0)`, поэтому даже обновление не сделает цену отрицательной:

<CodeExample output={`ERROR:  new row for relation "products" violates check constraint "products_price_check"
DETAIL:  Failing row contains (1, Jasmine Tea, tea, -1.00, 40).`}>

```sql
UPDATE products SET price = -1 WHERE id = 1;
```

</CodeExample>

Проверки могут сравнивать **несколько столбцов** одной строки, а ограничениям можно давать **имена** с помощью `CONSTRAINT name`, чтобы сообщения об ошибках объясняли, что не так, вашими словами:

<CodeExample output={`CREATE TABLE

INSERT 0 1

ERROR:  new row for relation "trips" violates check constraint "trips_dates_in_order"
DETAIL:  Failing row contains (Lisbon, 2025-08-10, 2025-08-03, 3).`}>

```sql
CREATE TABLE trips (
  city text NOT NULL,
  starts_on date NOT NULL,
  ends_on date NOT NULL,
  travellers integer NOT NULL CHECK (travellers BETWEEN 1 AND 12),
  CONSTRAINT trips_dates_in_order CHECK (ends_on >= starts_on)
);

INSERT INTO trips VALUES ('Kyoto', '2025-04-01', '2025-04-09', 2);

INSERT INTO trips VALUES ('Lisbon', '2025-08-10', '2025-08-03', 3);
```

</CodeExample>

Проверка, записанная **после** столбцов, как `trips_dates_in_order`, — это **ограничение таблицы** (table constraint); проверка внутри определения столбца, как у `travellers`, — **ограничение столбца** (column constraint). Работают они одинаково. Проверки отлично подходят и для списков допустимых значений: у учебной таблицы `orders` есть `CHECK (status IN ('paid', 'shipped', 'delivered', 'cancelled'))`.

<Callout type="warning" title="CHECK пропускает NULL">

Проверка не проходит, только когда её условие **ложно**. С NULL выражение `travellers BETWEEN 1 AND 12` даёт «неизвестно», а не «ложь», поэтому строка принимается. Вот почему проверки обычно сочетают с `NOT NULL`, как в таблице `trips` выше.

</Callout>

## FOREIGN KEY: связи между таблицами

**Внешний ключ** (foreign key) говорит: «значение в этом столбце должно существовать в той, другой таблице». Именно он поддерживает связи между таблицами в корректном состоянии. Учебный столбец `orders.customer_id` объявлен как `REFERENCES customers (id)`, поэтому заказ не может ссылаться на несуществующего покупателя, а покупатель с заказами не может просто исчезнуть:

<CodeExample output={`ERROR:  insert or update on table "orders" violates foreign key constraint "orders_customer_id_fkey"
DETAIL:  Key (customer_id)=(999) is not present in table "customers".`}>

```sql
INSERT INTO orders (customer_id, ordered_at, status)
VALUES (999, '2025-07-01 10:00', 'paid');
```

</CodeExample>

<CodeExample output={`ERROR:  update or delete on table "customers" violates foreign key constraint "orders_customer_id_fkey" on table "orders"
DETAIL:  Key (id)=(1) is still referenced from table "orders".`}>

```sql
DELETE FROM customers WHERE id = 1;
```

</CodeExample>

Таблица, на которую ссылаются (`customers`), — **родительская** (parent); таблица, которая ссылается (`orders`), — **дочерняя** (child). Без этого ограничения удаление покупателя оставило бы **осиротевшие** (orphan) заказы, которые никому не принадлежат, и каждый отчёт, соединяющий заказы с покупателями, тихо терял бы их.

### Что происходит при удалении?

Когда родительская строка удаляется, правило **`ON DELETE`** внешнего ключа решает, что будет с её дочерними строками:

| Правило | Когда родитель удаляется |
| --- | --- |
| `NO ACTION` (по умолчанию) / `RESTRICT` | Удаление не проходит, пока есть дочерние строки |
| `CASCADE` | Дочерние строки тоже удаляются |
| `SET NULL` | Внешний ключ дочерних строк становится `NULL` |
| `SET DEFAULT` | Внешний ключ дочерних строк получает значение по умолчанию |

Выбирайте правило, которое соответствует реальному миру. В блоге комментарии без своего поста не имеют смысла, поэтому должны уходить вместе с ним; уход редактора поста из компании не должен удалять пост; а автора, у которого есть посты, вообще нельзя удалять:

<CodeExample output={`CREATE TABLE

CREATE TABLE

CREATE TABLE

INSERT 0 3

INSERT 0 2

INSERT 0 3

DELETE 1

 id | post_id |  body
----+---------+---------
  1 |       1 | So true
  2 |       1 | Zzz
(2 rows)

DELETE 1

 id |     title      | author_id | editor_id
----+----------------+-----------+-----------
  1 | Why pandas nap |         1 |      NULL
(1 row)

ERROR:  update or delete on table "authors" violates foreign key constraint "posts_author_id_fkey" on table "posts"
DETAIL:  Key (id)=(1) is still referenced from table "posts".`}>

```sql
CREATE TABLE authors (
  id integer GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  name text NOT NULL
);

CREATE TABLE posts (
  id integer GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  title text NOT NULL,
  author_id integer NOT NULL REFERENCES authors (id),
  editor_id integer REFERENCES authors (id) ON DELETE SET NULL
);

CREATE TABLE comments (
  id integer GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  post_id integer NOT NULL
    REFERENCES posts (id) ON DELETE CASCADE,
  body text NOT NULL
);

INSERT INTO authors (name) VALUES ('Mei'), ('Sam'), ('Ada');
INSERT INTO posts (title, author_id, editor_id)
VALUES ('Why pandas nap', 1, 3), ('Bamboo, ranked', 2, 3);
INSERT INTO comments (post_id, body)
VALUES (1, 'So true'), (1, 'Zzz'), (2, 'Ten out of ten');

-- CASCADE: комментарии поста удаляются вместе с ним
DELETE FROM posts WHERE id = 2;
SELECT * FROM comments ORDER BY id;

-- SET NULL: Ада уходит, её посты теряют редактора
DELETE FROM authors WHERE id = 3;
SELECT * FROM posts ORDER BY id;

-- NO ACTION: у Мэй ещё есть посты, поэтому её нельзя удалить
DELETE FROM authors WHERE id = 1;
```

</CodeExample>

<Callout type="tip" title="Индексируйте внешние ключи">

PostgreSQL автоматически создаёт индексы для первичных ключей и столбцов с UNIQUE, но **не** для столбцов внешних ключей. Соединения по `orders.customer_id` и каждое удаление из `customers` (которому нужно искать дочерние строки) работают быстрее с индексом: `CREATE INDEX ON orders (customer_id);`. Как устроены индексы, вы узнаете на Уровне 2.

</Callout>

## Добавляем ограничения в существующую таблицу

Забыли правило? `ALTER TABLE ... ADD CONSTRAINT` добавит его позже. Сначала PostgreSQL проверяет **каждую существующую строку** и отказывается, если хоть одна из них уже нарушает правило:

<CodeExample output={`ALTER TABLE

ALTER TABLE

ERROR:  check constraint "products_stock_positive" of relation "products" is violated by some row`}>

```sql
ALTER TABLE products
  ADD CONSTRAINT products_name_unique UNIQUE (name);

ALTER TABLE products
  ADD CONSTRAINT products_stock_not_negative CHECK (stock >= 0);

ALTER TABLE products
  ADD CONSTRAINT products_stock_positive CHECK (stock > 0);
```

</CodeExample>

Последняя команда не проходит, потому что у Earl Grey и Clean Python запас равен 0: сначала пришлось бы исправить (или удалить) эти строки. Родственные команды: `ALTER TABLE t ALTER COLUMN c SET NOT NULL`, `ALTER COLUMN c SET DEFAULT value` и `ALTER TABLE t DROP CONSTRAINT name`, чтобы убрать правило.

Чтобы увидеть ограничения таблицы, снова спросите `information_schema`:

<CodeExample output={`       constraint_name       | constraint_type
-----------------------------+-----------------
 orders_customer_id_fkey     | FOREIGN KEY
 orders_customer_id_not_null | CHECK
 orders_id_not_null          | CHECK
 orders_ordered_at_not_null  | CHECK
 orders_pkey                 | PRIMARY KEY
 orders_status_check         | CHECK
 orders_status_not_null      | CHECK
(7 rows)`}>

```sql
SELECT constraint_name, constraint_type
FROM information_schema.table_constraints
WHERE table_name = 'orders'
ORDER BY constraint_name;
```

</CodeExample>

Каждое правило показано со своим именем. Начиная с PostgreSQL 18, в списке есть и правила `NOT NULL` — как ограничения `CHECK` с именами вида `..._not_null`.

Сейчас база данных ветеринарной клиники принимает что угодно. 🐾 Добавьте ограничения в две инструкции `CREATE TABLE` (вставки и последний запрос не меняйте), чтобы:

- **owners**: `name` и `email` обязательны, и у двух владельцев не может быть одинакового email.
- **pets**:
  - `owner_id` обязателен и должен быть id существующего владельца; когда владельца удаляют, **его питомцы удаляются тоже**.
  - `name`, `species` и `weight_kg` обязательны.
  - `species` — одно из значений `'cat'`, `'dog'` или `'rabbit'`.
  - `weight_kg` больше 0.
  - `vaccinated` обязателен и равен `false`, если вставка не указывает иное.

<Hint>

Добавляйте правила сразу после типа каждого столбца, например `email text NOT NULL UNIQUE`. Внешний ключ: `owner_id integer NOT NULL REFERENCES owners (id) ON DELETE CASCADE`. Используйте `CHECK (species IN ('cat', 'dog', 'rabbit'))` и `CHECK (weight_kg > 0)`, а столбцу `vaccinated` дайте и `NOT NULL`, и `DEFAULT false`.

</Hint>

<Solution>

```sql
CREATE TABLE owners (
  id integer GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  name text NOT NULL,
  email text NOT NULL UNIQUE
);

CREATE TABLE pets (
  id integer GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  owner_id integer NOT NULL
    REFERENCES owners (id) ON DELETE CASCADE,
  name text NOT NULL,
  species text NOT NULL
    CHECK (species IN ('cat', 'dog', 'rabbit')),
  weight_kg numeric(5, 2) NOT NULL CHECK (weight_kg > 0),
```

## Итоги

- **Ограничения** — это правила, которые PostgreSQL проверяет при каждой вставке и обновлении, кто бы ни записывал данные.
- `NOT NULL` требует значения; `DEFAULT` подставляет значение, когда вставка не упоминает столбец.
- `PRIMARY KEY` = уникальность + не NULL, один на таблицу, может охватывать несколько столбцов, как `(order_id, product_id)`.
- `UNIQUE` запрещает дубликаты (NULL дубликатами не считаются); `CHECK (условие)` отклоняет строки, для которых условие ложно.
- `REFERENCES parent (id)` — внешний ключ: дочерние строки должны ссылаться на существующих родителей. `ON DELETE CASCADE`, `SET NULL` или стандартное `NO ACTION` определяют, что делает удаление родителя.
- `ALTER TABLE ... ADD CONSTRAINT` добавляет правило позже, но только если ему уже подчиняются все существующие строки.
