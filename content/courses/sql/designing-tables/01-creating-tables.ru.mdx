До сих пор вы писали запросы к таблицам, которые спроектировал кто-то другой: `customers`, `orders`, `products`. Каждая из них появилась на свет благодаря инструкции **`CREATE TABLE`**: в ней кто-то решил, какие столбцы будут у таблицы и какие значения может хранить каждый столбец.

В этом уроке этим «кем-то» станете вы. 🐼 Вы будете создавать таблицы, выбирать **типы данных** (data types) для их столбцов, поручать PostgreSQL нумерацию строк, а ещё менять и удалять таблицы, когда планы меняются.

## Ваш первый CREATE TABLE

Инструкция `CREATE TABLE` задаёт имя таблицы и перечисляет её столбцы. У каждого столбца (column) есть **имя** и **тип данных**, столбцы разделяются запятыми:

<CodeExample output={`CREATE TABLE

INSERT 0 2

     title      |  held_on   | seats | price | is_online
----------------+------------+-------+-------+-----------
 Intro to SQL   | 2025-09-06 |    30 | 12.50 | f
 Pandas & Plots | 2025-09-13 |    20 |  0.00 | t
(2 rows)`}>

```sql
CREATE TABLE workshops (
  title text,
  held_on date,
  seats integer,
  price numeric(6, 2),
  is_online boolean
);

INSERT INTO workshops (title, held_on, seats, price, is_online)
VALUES
  ('Intro to SQL', '2025-09-06', 30, 12.5, false),
  ('Pandas & Plots', '2025-09-13', 20, 0, true);

SELECT * FROM workshops;
```

</CodeExample>

Когда таблица создана, PostgreSQL отвечает `CREATE TABLE`. Дальше она ведёт себя точно так же, как таблицы из учебной базы: в неё можно делать `INSERT`, из неё — `SELECT`, её можно соединять с другими таблицами.

Обратите внимание, как PostgreSQL **подогнал значения** под их типы: `12.5` превратилось в `12.50`, потому что `price` хранит два знака после запятой, а логические значения печатаются как `t` и `f` (true и false).

<Callout type="note" title="Каждый запуск начинается с чистого листа">

Таблицы, которые вы здесь создаёте, живут только в течение одного запуска: каждый раз, когда вы нажимаете **«Запустить»**, вы получаете свежую копию учебной базы данных. Для экспериментов это удобно: любая ошибка не навсегда. На настоящем сервере таблица существует, пока её кто-нибудь не удалит.

</Callout>

Имена таблиц пишутся в том же стиле, что и имена столбцов: **строчными буквами с подчёркиваниями** (`order_items`, а не `OrderItems`) и обычно **во множественном числе**, потому что таблица хранит много объектов.

## Выбираем типы данных

**Тип данных** столбца определяет, какие значения он принимает и что с ними можно делать. Числа можно складывать, а текст — нет; из одной даты можно вычесть другую и получить число дней между ними. Эти типы покрывают почти все таблицы, которые вам когда-либо придётся создавать:

| Тип | Что хранит | Пример |
| --- | --- | --- |
| `text` | Текст любой длины | `'Mei Lin'` |
| `integer` | Целые числа примерно до ±2,1 миллиарда | `42` |
| `bigint` | Целые числа побольше | `9000000000` |
| `numeric(p, s)` | Точные десятичные числа: `p` цифр, из них `s` после запятой | `12.50` |
| `boolean` | `true` или `false` | `true` |
| `date` | Календарный день | `'2025-09-06'` |
| `timestamptz` | Момент времени с часовым поясом | `'2025-09-06 18:30+01'` |

PostgreSQL **проверяет каждое значение** на соответствие типу столбца. Текст, который не является числом, не проскользнёт в числовой столбец:

<CodeExample output={`CREATE TABLE

ERROR:  invalid input syntax for type integer: "thirty"
LINE 7: VALUES ('Intro to SQL', 'thirty');
                                ^`}>

```sql
CREATE TABLE workshops (
  title text,
  seats integer
);

INSERT INTO workshops (title, seats)
VALUES ('Intro to SQL', 'thirty');
```

</CodeExample>

Это одно из главных преимуществ базы данных перед электронной таблицей: данные неподходящего вида останавливаются на входе, и любая программа, читающая таблицу, может быть уверена, что `seats` — это число.

### Деньги: numeric, а не float

Для цен и денег всегда используйте **`numeric`**. Он хранит десятичные числа **точно**. Другие дробные типы, `real` и `double precision` (его ещё называют `float`), быстрые, но приблизительные: для измерений это нормально, а для денег — ужасно:

<CodeExample output={`      float_sum      | numeric_sum
---------------------+-------------
 0.30000000000000004 |         0.3
(1 row)

 rounded
---------
   12.35
(1 row)

ERROR:  numeric field overflow
DETAIL:  A field with precision 6, scale 2 must round to an absolute value less than 10^4.`}>

```sql
SELECT 0.1::float + 0.2::float AS float_sum,
  0.1::numeric + 0.2::numeric AS numeric_sum;

SELECT 12.345::numeric(6, 2) AS rounded;

SELECT 12345.6::numeric(6, 2) AS too_big;
```

</CodeExample>

`numeric(6, 2)` означает «всего 6 цифр, из них 2 после запятой», поэтому самое большое значение — `9999.99`. Лишние знаки после запятой округляются, а слишком большое число вызывает ошибку, а не тихую порчу данных. Просто `numeric` без ограничений тоже работает и хранит всё, что вы ему дадите.

### Текст: просто используйте text

Во многих базах данных нужно указывать длину, например `varchar(255)`. В PostgreSQL **обычный выбор — `text`**: у него нет ограничения длины, и он работает так же быстро. `varchar(n)` тоже существует, но если вам нужно правило вроде «не больше 50 символов», для этого есть более наглядный инструмент — ограничение `CHECK`, с которым вы познакомитесь в следующем уроке.

### Даты и время: date или timestamptz

- **`date`** — календарный день без времени: дни рождения, сроки сдачи, день проведения мастер-класса.
- **`timestamptz`** («timestamp with time zone», метка времени с часовым поясом) — точный **момент**: когда был оформлен заказ, когда пользователь вошёл в систему.

`timestamptz` хранит момент в UTC, а показывает его в **часовом поясе сессии**. Один и тот же момент выглядит по-разному в Лондоне и Токио, но остаётся тем же моментом:

<CodeExample output={`SET

CREATE TABLE

INSERT 0 1

       starts_at
------------------------
 2025-09-06 17:30:00+00
(1 row)

SET

       starts_at
------------------------
 2025-09-07 02:30:00+09
(1 row)`}>

```sql
SET timezone = 'UTC';

CREATE TABLE talks (
  title text,
  starts_at timestamptz
);

-- 18:30 в Лондоне (летнее время, UTC+1)
INSERT INTO talks (title, starts_at)
VALUES ('Panda Keynote', '2025-09-06 18:30+01');

SELECT starts_at FROM talks;

SET timezone = 'Asia/Tokyo';

SELECT starts_at FROM talks;
```

</CodeExample>

Есть ещё обычный **`timestamp`** (без часового пояса) — его использует столбец `orders.ordered_at` в учебной базе. Он хранит дату и время на часах, но не знает, *где* они, поэтому `09:00` может означать девять часов где угодно в мире. Для моментов, которые важны людям и серверам в разных местах, выбирайте `timestamptz`.

<Callout type="tip" title="Выбирайте самый узкий подходящий тип">

Тип — это бесплатное правило. Храните ответ «да/нет» как `boolean`, а не как текст `'yes'`; день — как `date`, а не как `'06/09/2025'`. Тогда сортировка, вычисления и сравнения просто работают, и никто не сможет сохранить `'maybe'` или `'31/02/2025'`.

</Callout>

## Столбцы идентификации: пусть база нумерует строки

Почти у каждой таблицы есть столбец **`id`** — число, которое идентифицирует каждую строку, чтобы другие таблицы могли на неё ссылаться («заказ 17 принадлежит покупателю 8»). Придумывать такие числа самому не хочется. **Столбец идентификации** (identity column) заставляет PostgreSQL выдавать 1, 2, 3… автоматически:

<CodeExample output={`CREATE TABLE

INSERT 0 2

 id |     title
----+----------------
  1 | Intro to SQL
  2 | Pandas & Plots
(2 rows)

ERROR:  cannot insert a non-DEFAULT value into column "id"
DETAIL:  Column "id" is an identity column defined as GENERATED ALWAYS.
HINT:  Use OVERRIDING SYSTEM VALUE to override.`}>

```sql
CREATE TABLE workshops (
  id integer GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  title text
);

INSERT INTO workshops (title)
VALUES ('Intro to SQL'), ('Pandas & Plots');

SELECT id, title FROM workshops ORDER BY id;

INSERT INTO workshops (id, title) VALUES (7, 'Lucky Seven');
```

</CodeExample>

Разберём `id integer GENERATED ALWAYS AS IDENTITY PRIMARY KEY` по частям:

- **`integer`**: идентификаторы — целые числа (для таблиц, которые однажды могут перевалить за два миллиарда строк, берите `bigint`).
- **`GENERATED ALWAYS AS IDENTITY`**: значение всегда выбирает PostgreSQL. Попытка задать его самому — ошибка, и это защищает от конфликтующих id. `GENERATED BY DEFAULT AS IDENTITY` — мягкий вариант: значение выбирается, если вы его не указали.
- **`PRIMARY KEY`**: столбец идентифицирует строки, поэтому он должен быть уникальным и никогда не пустым. Подробнее о ключах — в следующем уроке.

Чтобы узнать, какой id получила новая строка, добавьте к вставке **`RETURNING`**:

<CodeExample output={`CREATE TABLE

 id |    title
----+--------------
  1 | Intro to SQL
(1 row)`}>

```sql
CREATE TABLE workshops (
  id integer GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  title text
);

INSERT INTO workshops (title)
VALUES ('Intro to SQL')
RETURNING id, title;
```

</CodeExample>

<Callout type="note" title="А как же serial?">

В учебных таблицах используется `id serial PRIMARY KEY`. **`serial`** — более старый способ получить автоматическую нумерацию, и вы встретите его во многих существующих базах. Он работает, но столбцы идентификации входят в стандарт SQL и строже, поэтому в новых таблицах предпочитайте `GENERATED ... AS IDENTITY`.

</Callout>

## Смотрим на структуру таблицы

Как увидеть, какие столбцы есть у таблицы? В терминальном клиенте **psql** вы бы набрали короткую команду:

```text
shop=> \d products
                             Table "public.products"
  Column  |     Type     | Nullable |               Default
----------+--------------+----------+--------------------------------------
 id       | integer      | not null | nextval('products_id_seq'::regclass)
 name     | text         | not null |
 ...
```

Команды вроде `\d` принадлежат psql, а не SQL, поэтому здесь они не работают. Те же сведения доступны обычному SQL через **`information_schema`** — набор встроенных таблиц, которые описывают вашу базу данных:

<CodeExample output={` column_name | data_type | is_nullable | column_default
-------------+-----------+-------------+----------------
 name        | text      | NO          | NULL
 category    | text      | NO          | NULL
 price       | numeric   | NO          | NULL
 stock       | integer   | NO          | 0
(4 rows)`}>

```sql
SELECT column_name, data_type, is_nullable, column_default
FROM information_schema.columns
WHERE table_name = 'products'
  AND column_name <> 'id'
ORDER BY ordinal_position;
```

</CodeExample>

`ordinal_position` — это место столбца в таблице (1, 2, 3…), так что сортировка по нему выводит столбцы в том порядке, в котором их создали.

## Меняем таблицу с ALTER TABLE

Планы меняются. **`ALTER TABLE`** изменяет таблицу, в которой уже есть данные, без того чтобы начинать всё заново:

<CodeExample output={`CREATE TABLE

INSERT 0 2

ALTER TABLE

ALTER TABLE

ALTER TABLE

ALTER TABLE

 id |     title      | capacity | level
----+----------------+----------+-------
  1 | Intro to SQL   |       30 | all
  2 | Pandas & Plots |       20 | all
(2 rows)`}>

```sql
CREATE TABLE workshops (
  id integer GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  title text,
  seats integer,
  room text
);

INSERT INTO workshops (title, seats, room)
VALUES ('Intro to SQL', 30, 'B12'), ('Pandas & Plots', 20, 'B14');

-- добавить столбец (существующие строки получат значение по умолчанию)
ALTER TABLE workshops ADD COLUMN level text DEFAULT 'all';

-- переименовать столбец
ALTER TABLE workshops RENAME COLUMN seats TO capacity;

-- удалить столбец (вместе с данными!)
ALTER TABLE workshops DROP COLUMN room;

-- изменить тип столбца
ALTER TABLE workshops ALTER COLUMN capacity TYPE bigint;

SELECT * FROM workshops ORDER BY id;
```

</CodeExample>

Самые частые формы:

- `ALTER TABLE t ADD COLUMN name type` добавляет столбец. Существующие строки получают `NULL` или значение `DEFAULT`, если вы его задали.
- `ALTER TABLE t RENAME COLUMN old TO new` и `ALTER TABLE t RENAME TO new_name` переименовывают.
- `ALTER TABLE t DROP COLUMN name` удаляет столбец **вместе со всеми его значениями**.
- `ALTER TABLE t ALTER COLUMN name TYPE new_type` преобразует столбец. Если PostgreSQL не может преобразовать данные сам (скажем, текст в числа), добавьте `USING` с выражением, которое это делает: `ALTER COLUMN price TYPE numeric USING price::numeric`.

В нагруженной рабочей базе некоторые из этих изменений блокируют таблицу или переписывают каждую строку, поэтому команды тщательно их планируют. Безопасные рецепты вы изучите на Уровне 3, а пока наслаждайтесь свободой базы, которой пользуетесь только вы.

## Удаляем таблицу с DROP TABLE

**`DROP TABLE`** удаляет таблицу: её столбцы, её строки — всё. `IF EXISTS` не даёт команде упасть, если таблицы нет, — это удобно в начале скрипта, который вы запускаете снова и снова:

<CodeExample output={`DROP TABLE

NOTICE:  table "workshops" does not exist, skipping
DROP TABLE

CREATE TABLE

 count
-------
     0
(1 row)`}>

```sql
DROP TABLE movies;

DROP TABLE IF EXISTS workshops;

CREATE TABLE workshops (
  id integer GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  title text
);

SELECT count(*) FROM workshops;
```

</CodeExample>

Да, это удалило учебную таблицу `movies`. Не волнуйтесь: следующий запуск начнётся со свежей копии. Есть и родственная инструкция `CREATE TABLE IF NOT EXISTS`, которая пропускает создание, если таблица уже есть.

<Callout type="danger" title="Отменить нельзя">

На настоящем сервере `DROP TABLE` (и `DROP COLUMN`) срабатывает мгновенно и навсегда: корзины нет. Настоящие команды защищаются резервными копиями и тем, что у большинства пользователей просто нет права что-либо удалять. Прежде чем удалять, перепроверьте, **к какой базе** вы подключены: «я думал, что работаю на своём ноутбуке, а не в продакшене» — классическая история катастрофы.

</Callout>

Если на удаляемую таблицу ссылаются другие (например, заказы ссылаются на покупателей), PostgreSQL откажется её удалять. `DROP TABLE customers CASCADE` удалил бы и эти связи; используйте его, только если точно понимаете, что удалится вместе с таблицей.

INSERT INTO plants (name, price, in_stock, arrived_on)

## Итоги

- `CREATE TABLE name (column type, ...)` создаёт таблицу; имена пишутся в lower_snake_case и обычно во множественном числе.
- Повседневные типы: `text`, `integer`/`bigint`, `numeric(p, s)` для точных дробей и денег, `boolean`, `date` и `timestamptz` для моментов времени.
- PostgreSQL отклоняет значения, которые не подходят под тип столбца, поэтому данным можно доверять.
- `id integer GENERATED ALWAYS AS IDENTITY PRIMARY KEY` нумерует строки автоматически; `RETURNING id` сообщает id новой строки.
- `information_schema.columns` описывает столбцы любой таблицы (в терминале то же самое делает `\d` из psql).
- `ALTER TABLE` добавляет, переименовывает, удаляет столбцы и меняет их тип; `DROP TABLE` (с `IF EXISTS`) удаляет таблицу целиком — на настоящем сервере навсегда.
