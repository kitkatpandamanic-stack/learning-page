Вы уже умеете создавать таблицы и защищать их ограничениями. Остался последний большой вопрос: **какие таблицы вообще создавать**. Хранить ли данные покупателя в каждом заказе или в отдельной таблице? Куда девать авторов книги, если их у неё трое?

Умение хорошо отвечать на такие вопросы называется **нормализацией** (normalisation): это организация данных так, чтобы **каждый факт хранился ровно в одном месте**. В этом уроке вы увидите, что идёт не так без неё, изучите три классических правила (1НФ, 2НФ, 3НФ), а затем спроектируете полноценную базу данных библиотеки. 📚

## Беда одной большой таблицы

Электронные таблицы соблазняют сложить всё в одну широкую таблицу. Вот лист записи на занятия в школе программирования, который хранится именно так:

<CodeExample output={`CREATE TABLE

INSERT 0 5

UPDATE 1

 teacher | room
---------+------
 Mr Ito  | C3
 Ms Kim  | B12
 Ms Kim  | D4
(3 rows)`}>

```sql
CREATE TABLE signups (
  student text,
  student_email text,
  class text,
  teacher text,
  room text
);

INSERT INTO signups VALUES
  ('Mei', 'mei@pandadev.test', 'SQL Basics', 'Ms Kim', 'B12'),
  ('Sam', 'sam@pandadev.test', 'SQL Basics', 'Ms Kim', 'B12'),
  ('Mei', 'mei@pandadev.test', 'Python 101', 'Mr Ito', 'C3'),
  ('Ada', 'ada@pandadev.test', 'Python 101', 'Mr Ito', 'C3'),
  ('Ada', 'ada@pandadev.test', 'Web Design', 'Ms Kim', 'B12');

-- Ms Kim переезжает в кабинет D4... но обновляется только одна строка
UPDATE signups SET room = 'D4'
WHERE student = 'Mei' AND class = 'SQL Basics';

SELECT DISTINCT teacher, room
FROM signups
ORDER BY teacher, room;
```

</CodeExample>

Теперь Ms Kim находится **в двух кабинетах сразу**. Кабинет повторяется во многих строках, поэтому все копии нужно обновлять вместе, и одна забытая строка заставляет данные противоречить сами себе. Это **аномалия обновления** (update anomaly). У плоской таблицы есть ещё две проблемы:

- **Аномалия вставки** (insert anomaly): нельзя добавить новый курс, пока на него кто-нибудь не запишется, потому что строка — это и *есть* запись на курс.
- **Аномалия удаления** (delete anomaly): если Ада отменит Web Design, удаление её строки уничтожит и единственное упоминание о том, что такой курс существует и кто его ведёт.

У всех трёх одна причина: таблица хранит **несколько разных фактов** (кто такие студенты, какие есть курсы, кто где преподаёт) в одних и тех же строках.

## Разбиваем на таблицы

Лекарство — дать каждому виду объектов собственную таблицу и **связать** таблицы ключами:

<CodeExample output={`CREATE TABLE

CREATE TABLE

CREATE TABLE

CREATE TABLE

INSERT 0 2

INSERT 0 3

INSERT 0 3

INSERT 0 5

UPDATE 1

 student |   class    | teacher | room
---------+------------+---------+------
 Ada     | Python 101 | Mr Ito  | C3
 Ada     | Web Design | Ms Kim  | D4
 Mei     | Python 101 | Mr Ito  | C3
 Mei     | SQL Basics | Ms Kim  | D4
 Sam     | SQL Basics | Ms Kim  | D4
(5 rows)`}>

```sql
CREATE TABLE teachers (
  id integer GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  name text NOT NULL,
  room text NOT NULL
);

CREATE TABLE classes (
  id integer GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  name text NOT NULL UNIQUE,
  teacher_id integer NOT NULL REFERENCES teachers (id)
);

CREATE TABLE students (
  id integer GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  name text NOT NULL,
  email text NOT NULL UNIQUE
);

CREATE TABLE enrolments (
  student_id integer REFERENCES students (id) ON DELETE CASCADE,
  class_id integer REFERENCES classes (id) ON DELETE CASCADE,
  PRIMARY KEY (student_id, class_id)
);

INSERT INTO teachers (name, room)
VALUES ('Ms Kim', 'B12'), ('Mr Ito', 'C3');
INSERT INTO classes (name, teacher_id)
VALUES ('SQL Basics', 1), ('Python 101', 2), ('Web Design', 1);
INSERT INTO students (name, email)
VALUES ('Mei', 'mei@pandadev.test'), ('Sam', 'sam@pandadev.test'),
  ('Ada', 'ada@pandadev.test');
INSERT INTO enrolments VALUES (1, 1), (2, 1), (1, 2), (3, 2), (3, 3);

-- теперь переезд — это ОДНО обновление
UPDATE teachers SET room = 'D4' WHERE name = 'Ms Kim';

-- а соединение восстанавливает старый лист, когда он нужен
SELECT s.name AS student, c.name AS class, t.name AS teacher, t.room
FROM enrolments AS e
JOIN students AS s ON s.id = e.student_id
JOIN classes AS c ON c.id = e.class_id
JOIN teachers AS t ON t.id = c.teacher_id
ORDER BY s.name, c.name;
```

</CodeExample>

Теперь каждый факт живёт в одном месте: кабинет Ms Kim записан в **одной строке**, поэтому её переезд — одно обновление, которое не может выполниться наполовину. Новый курс может существовать без студентов, а удаление записи на курс никогда не удаляет сам курс. Когда снова нужен широкий вид, его на лету строит **соединение** (JOIN). Вот сделка, которую предлагает нормализация: **записывайте каждый факт один раз, соединяйте при чтении**.

## «Один ко многим» и «многие ко многим»

Разбивая данные на таблицы, вы на самом деле решаете, как таблицы **связаны**. Бывает три вида связей (relationships):

**Один ко многим (1:N, one-to-many)** — самая частая связь. Один преподаватель ведёт много курсов; у каждого курса один преподаватель. Один покупатель оформляет много заказов; у каждого заказа один покупатель. Правило: **внешний ключ ставится на стороне «многих»**. `classes.teacher_id` и `orders.customer_id` — именно такие ключи.

**Многие ко многим (N:M, many-to-many)**: студент посещает много курсов, а на курсе много студентов. Ни один столбец не может это хранить: студенту понадобился бы список курсов. Вместо этого добавляют **связующую таблицу** (join table, её ещё называют junction или link table) с одной строкой на каждую пару, как `enrolments`. Её первичный ключ — пара внешних ключей, поэтому один и тот же студент не может записаться на один и тот же курс дважды.

Такая таблица есть и в учебной базе: **`order_items`** связывает заказы и товары. А ещё связующая таблица может хранить факты о самой паре: `order_items.quantity` не принадлежит ни заказу, ни товару по отдельности — только сочетанию «этот товар в этом заказе».

**Один к одному (1:1, one-to-one)**: каждой строке соответствует не больше одной строки другой таблицы, например пользователь и его настройки профиля. Такое встречается реже и обычно делается внешним ключом с ограничением `UNIQUE` или просто дополнительными столбцами в той же таблице.

```text
customers 1 ──< N orders 1 ──< N order_items N >── 1 products
departments 1 ──< N employees
employees 1 ──< N employees     (manager_id: кто кем руководит)
```

Таблица `employees` связана даже **сама с собой**: `manager_id` — это связь «один ко многим» от руководителя к его подчинённым, хранящаяся в той же таблице.

## Нормальные формы: 1НФ, 2НФ и 3НФ

Проектировщики баз данных описывают, «насколько нормализована» таблица, с помощью **нормальных форм** (normal forms). Каждая следующая добавляет правило к предыдущей. Учебные определения заучивать не нужно, но каждую проблему стоит узнавать в лицо.

### Первая нормальная форма (1НФ): одно значение в ячейке

Каждый столбец хранит **одно значение**, и нет повторяющихся групп столбцов. Вот что нарушает 1НФ:

- столбец `tags` со значением `'sql, python, beginner'`,
- столбцы `phone1`, `phone2`, `phone3`.

Списки, спрятанные в тексте, трудно правильно запрашивать:

<CodeExample output={`CREATE TABLE

INSERT 0 3

        title
---------------------
 Intro to SQL
 MySQL vs PostgreSQL
(2 rows)`}>

```sql
CREATE TABLE articles (
  title text NOT NULL,
  tags text
);

INSERT INTO articles VALUES
  ('Intro to SQL', 'sql, beginner'),
  ('MySQL vs PostgreSQL', 'mysql, postgresql'),
  ('Python for data', 'python, pandas');

SELECT title FROM articles WHERE tags LIKE '%sql%' ORDER BY title;
```

</CodeExample>

Мы просили статьи с тегом `sql`, а получили ещё и статью с `mysql`. Посчитать статьи по тегам, переименовать тег или защититься от опечаток было бы так же неудобно. Схема в 1НФ — это таблица `tags` плюс связующая таблица `article_tags`: снова связь «многие ко многим».

### Вторая нормальная форма (2НФ): зависимость от всего ключа

Это важно для таблиц с **составным ключом** (composite key). Каждый остальной столбец должен зависеть от **всего** ключа, а не от его части. Представьте `order_items` с дополнительным столбцом `product_name`:

```text
 order_id | product_id | quantity | product_name
----------+------------+----------+--------------
        1 |          8 |        3 | Algorithms in Pictures
        6 |          8 |        2 | Algorithms in Pictures
```

`quantity` зависит от пары (этот товар в этом заказе), а `product_name` — **только от `product_id`**. Поэтому название повторяется в каждом заказе, и переименование товара требует обновить их все: аномалия обновления вернулась. Название должно жить в `products`.

### Третья нормальная форма (3НФ): ничего, кроме ключа

Каждый неключевой столбец должен описывать **ключ строки**, а не другой неключевой столбец. Представьте `employees` со столбцом `department_location`: местоположение зависит от отдела, а не от сотрудника. Переезд отдела продаж в Лиссабон потребовал бы обновить каждого продавца. Поэтому учебная база хранит `location` в `departments`.

Знаменитая формулировка всех трёх: каждый столбец должен зависеть **от ключа** (1НФ), **от всего ключа** (2НФ) **и ни от чего, кроме ключа** (3НФ).

<Callout type="note" title="Бывают и другие нормальные формы">

Существуют более строгие формы (НФБК, 4НФ, 5НФ) для более редких ситуаций. На практике большинство команд стремится к схеме в 3НФ, где у каждой таблицы есть понятный первичный ключ, а у каждой связи — внешний ключ.

</Callout>

## Когда копировать данные намеренно

Нормализация — отправная точка, а не религия. Иногда скопировать значение **правильно**, потому что копия означает нечто другое. Посмотрите на `order_items.unit_price`: разве это не копия `products.price`?

<CodeExample output={`UPDATE 1

 order_id |          name          | unit_price | price_today
----------+------------------------+------------+-------------
        1 | Algorithms in Pictures |      29.00 |       35.00
        1 | Kite                   |      15.00 |       15.00
(2 rows)`}>

```sql
-- Algorithms in Pictures дорожает
UPDATE products SET price = 35.00 WHERE id = 8;

SELECT oi.order_id, p.name, oi.unit_price, p.price AS price_today
FROM order_items AS oi
JOIN products AS p ON p.id = oi.product_id
WHERE oi.order_id = 1
ORDER BY p.name;
```

</CodeExample>

Нет: `unit_price` — это цена **в момент продажи**, другой факт, чем сегодняшняя цена. Если бы заказы просто брали `products.price`, каждое изменение цены переписывало бы историю старых заказов и счетов. Та же идея применима к адресам покупателей в отправленных заказах, курсам валют в платежах и именам в сертификатах.

Ещё команды намеренно **денормализуют** данные (denormalise) ради скорости, например хранят столбец `orders.total`, чтобы нагруженной странице не приходилось каждый раз складывать позиции. Это компромисс: чтение становится быстрее, но теперь кто-то должен поддерживать копию в правильном состоянии. Начинайте с нормализованной схемы и копируйте данные, только когда можете объяснить зачем.

<Callout type="tip" title="Сначала проектируйте на бумаге">

Прежде чем писать хоть один `CREATE TABLE`, выпишите **сущности** (существительные), с которыми работает ваше приложение: книги, читатели, выдачи. Каждая обычно становится таблицей. Затем для каждой пары спросите «один или много?» в обе стороны. «Один ко многим» получает внешний ключ на стороне «многих», «многие ко многим» — связующую таблицу. Пять минут с карандашом избавляют от мучительных миграций потом.

</Callout>

Вот что рассказал вам библиотекарь:

- В библиотеке есть **книги** (books) с названием `title` (обязательно), `isbn` (обязательно, и у двух книг не может быть одинакового) и годом издания `published_year` (целое число, может быть неизвестен).
- У книги может быть **несколько авторов**, а автор может написать несколько книг. Авторы уже готовы (`authors`), а связь между книгами и авторами хранится в связующей таблице **`book_authors`** (`book_id`, `author_id`). Её первичный ключ — пара; если книгу удаляют, её связи с авторами удаляются вместе с ней.
- У **читателей** (members) есть имя `name` (обязательно), `email` (обязателен и уникален) и день, когда они записались, `joined_on` (обязательно).
- **Выдача** (loan) фиксирует, что читатель взял книгу: `book_id` и `member_id` (оба обязательны и указывают на настоящие строки), `borrowed_on` и `due_on` (обязательные даты) и `returned_on` (пусто, пока книгу не вернут). Срок возврата должен быть **позже** даты выдачи, а вернуть книгу **раньше**, чем её взяли, нельзя. Книгу, у которой есть выдачи, удалить нельзя.
- У каждой таблицы, кроме `book_authors`, первичный ключ — столбец идентификации `id`, как у `authors`.

Ваши задачи:

1. Напишите четыре недостающие инструкции `CREATE TABLE`, чтобы инструкции `INSERT` библиотекаря выполнились. Создавайте таблицы в таком порядке, чтобы каждая таблица, на которую вы ссылаетесь, уже существовала.
2. В конце напишите **отчёт о просрочках** на 1 июня 2025 года: каждая выдача, по которой книгу ещё не вернули и у которой `due_on` раньше `'2025-06-01'`, со столбцами `title`, `member` (имя читателя), `due_on` и `days_overdue` (`'2025-06-01'` минус `due_on`, в днях); сначала самые просроченные, затем по названию.

<Hint>

Сначала создайте `books` и `members`, затем `book_authors` и `loans`, которые на них ссылаются. Полезные кусочки: `isbn text NOT NULL UNIQUE`, `book_id integer NOT NULL REFERENCES books (id)` (правило по умолчанию уже запрещает удалять книгу, у которой есть выдачи), `REFERENCES books (id) ON DELETE CASCADE` в `book_authors`, `PRIMARY KEY (book_id, author_id)` и проверки уровня таблицы вроде `CHECK (due_on > borrowed_on)`. Для отчёта соедините `loans` с `books` и `members`, отфильтруйте условием `l.returned_on IS NULL AND l.due_on < '2025-06-01'` и вычислите `date '2025-06-01' - l.due_on AS days_overdue` (разность двух дат — целое число дней).

</Hint>

```sql
CREATE TABLE authors (
  id integer GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  name text NOT NULL
);

CREATE TABLE books (
  id integer GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  title text NOT NULL,
  isbn text NOT NULL UNIQUE,
  published_year integer
);

CREATE TABLE book_authors (
  book_id integer REFERENCES books (id) ON DELETE CASCADE,
  author_id integer REFERENCES authors (id),
  PRIMARY KEY (book_id, author_id)
);

CREATE TABLE members (
  id integer GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  name text NOT NULL,
  email text NOT NULL UNIQUE,
  joined_on date NOT NULL
);

CREATE TABLE loans (
  id integer GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  book_id integer NOT NULL REFERENCES books (id),
  member_id integer NOT NULL REFERENCES members (id),
  borrowed_on date NOT NULL,
  due_on date NOT NULL,
  returned_on date,
  CHECK (due_on > borrowed_on),
  CHECK (returned_on >= borrowed_on)
);

ORDER BY days_overdue DESC, b.title;
```

## Итоги

- **Нормализация** хранит каждый факт ровно в одном месте; одна большая таблица порождает аномалии обновления, вставки и удаления.
- **Один ко многим**: внешний ключ ставится на стороне «многих» (`orders.customer_id`).
- **Многие ко многим**: добавьте **связующую таблицу**, первичный ключ которой — пара внешних ключей (`order_items`, `enrolments`, `book_authors`); в ней можно хранить факты о паре, например `quantity`.
- **1НФ**: одно значение в ячейке, никаких списков и столбцов `phone1`/`phone2`. **2НФ**: столбцы зависят от всего составного ключа. **3НФ**: столбцы не зависят ни от чего, кроме ключа.
- Соединения восстанавливают широкий вид при чтении; копировать данные можно, когда копия означает другое (цена на момент продажи) или когда вы сознательно денормализуете ради скорости.
