You can now create tables and protect them with constraints. The last big question is **which tables to create at all**. Should a customer's details live in every order, or in their own table? Where do a book's authors go when a book has three of them?

Answering these questions well is called **normalisation**: organising data so that **every fact is stored in exactly one place**. In this lesson you'll see what goes wrong without it, learn the three classic rules (1NF, 2NF, 3NF), and then design a complete library database. 📚

## The trouble with one big table

Spreadsheets tempt us to put everything in one wide table. Here's a coding school's sign-up sheet, stored exactly like that:

<CodeExample output={`CREATE TABLE

INSERT 0 5

UPDATE 1

 teacher | room
---------+------
 Mr Ito  | C3
 Ms Kim  | B12
 Ms Kim  | D4
(3 rows)`}>

```sql
CREATE TABLE signups (
  student text,
  student_email text,
  class text,
  teacher text,
  room text
);

INSERT INTO signups VALUES
  ('Mei', 'mei@pandadev.test', 'SQL Basics', 'Ms Kim', 'B12'),
  ('Sam', 'sam@pandadev.test', 'SQL Basics', 'Ms Kim', 'B12'),
  ('Mei', 'mei@pandadev.test', 'Python 101', 'Mr Ito', 'C3'),
  ('Ada', 'ada@pandadev.test', 'Python 101', 'Mr Ito', 'C3'),
  ('Ada', 'ada@pandadev.test', 'Web Design', 'Ms Kim', 'B12');

-- Ms Kim moves to room D4... but only one row gets updated
UPDATE signups SET room = 'D4'
WHERE student = 'Mei' AND class = 'SQL Basics';

SELECT DISTINCT teacher, room
FROM signups
ORDER BY teacher, room;
```

</CodeExample>

Ms Kim is now in **two rooms at once**. Because the room is repeated in many rows, every copy has to be updated together, and one forgotten row makes the data contradict itself. This is an **update anomaly**. The flat table has two more problems:

- **Insert anomaly**: you can't add a new class until a student signs up, because a row *is* a sign-up.
- **Delete anomaly**: if Ada cancels Web Design, deleting her row also deletes the only record that the class exists and who teaches it.

All three come from the same root cause: the table stores **several different facts** (who the students are, what the classes are, who teaches where) in the same rows.

## Splitting into tables

The cure is to give each kind of thing its own table and **link** them with keys:

<CodeExample output={`CREATE TABLE

CREATE TABLE

CREATE TABLE

CREATE TABLE

INSERT 0 2

INSERT 0 3

INSERT 0 3

INSERT 0 5

UPDATE 1

 student |   class    | teacher | room
---------+------------+---------+------
 Ada     | Python 101 | Mr Ito  | C3
 Ada     | Web Design | Ms Kim  | D4
 Mei     | Python 101 | Mr Ito  | C3
 Mei     | SQL Basics | Ms Kim  | D4
 Sam     | SQL Basics | Ms Kim  | D4
(5 rows)`}>

```sql
CREATE TABLE teachers (
  id integer GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  name text NOT NULL,
  room text NOT NULL
);

CREATE TABLE classes (
  id integer GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  name text NOT NULL UNIQUE,
  teacher_id integer NOT NULL REFERENCES teachers (id)
);

CREATE TABLE students (
  id integer GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  name text NOT NULL,
  email text NOT NULL UNIQUE
);

CREATE TABLE enrolments (
  student_id integer REFERENCES students (id) ON DELETE CASCADE,
  class_id integer REFERENCES classes (id) ON DELETE CASCADE,
  PRIMARY KEY (student_id, class_id)
);

INSERT INTO teachers (name, room)
VALUES ('Ms Kim', 'B12'), ('Mr Ito', 'C3');
INSERT INTO classes (name, teacher_id)
VALUES ('SQL Basics', 1), ('Python 101', 2), ('Web Design', 1);
INSERT INTO students (name, email)
VALUES ('Mei', 'mei@pandadev.test'), ('Sam', 'sam@pandadev.test'),
  ('Ada', 'ada@pandadev.test');
INSERT INTO enrolments VALUES (1, 1), (2, 1), (1, 2), (3, 2), (3, 3);

-- the move is now ONE update
UPDATE teachers SET room = 'D4' WHERE name = 'Ms Kim';

-- and a join rebuilds the old sheet whenever we need it
SELECT s.name AS student, c.name AS class, t.name AS teacher, t.room
FROM enrolments AS e
JOIN students AS s ON s.id = e.student_id
JOIN classes AS c ON c.id = e.class_id
JOIN teachers AS t ON t.id = c.teacher_id
ORDER BY s.name, c.name;
```

</CodeExample>

Now every fact lives in one place: Ms Kim's room is in **one row**, so moving her is one update and can't go half wrong. A new class can exist with no students, and deleting an enrolment never deletes a class. Whenever you want the wide view back, a **join** builds it on the fly. That's the deal normalisation offers: **write each fact once, join when you read**.

## One-to-many and many-to-many

When you split data into tables, you're really deciding how the tables **relate**. There are three kinds of relationship:

**One-to-many (1:N)** is the most common. One teacher teaches many classes; each class has one teacher. One customer places many orders; each order has one customer. The rule: **the foreign key goes on the "many" side**. `classes.teacher_id` and `orders.customer_id` are exactly that.

**Many-to-many (N:M)**: a student takes many classes and a class has many students. No single column can hold that, because a student would need a list of classes. Instead you add a **join table** (also called a junction or link table) with one row per pair, like `enrolments`. Its primary key is the pair of foreign keys, so the same student can't enrol in the same class twice.

The sample database has one too: **`order_items`** links orders and products. And a join table can carry facts about the pair itself: `order_items.quantity` belongs to neither the order nor the product alone, but to "this product in this order".

**One-to-one (1:1)**: each row matches at most one row of another table, such as a user and their profile settings. It's rarer, and usually a foreign key with a `UNIQUE` constraint, or simply more columns in the same table.

```text
customers 1 ──< N orders 1 ──< N order_items N >── 1 products
departments 1 ──< N employees
employees 1 ──< N employees     (manager_id: who manages whom)
```

The `employees` table even relates to **itself**: `manager_id` is a one-to-many link from a manager to the people they manage, stored in the same table.

## The normal forms: 1NF, 2NF and 3NF

Database designers describe "how normalised" a table is with **normal forms**. Each one adds a rule to the one before. You don't need to memorise the textbook definitions, but you should recognise each kind of problem.

### First normal form (1NF): one value per cell

Every column holds a **single value**, and there are no repeating groups of columns. These break 1NF:

- a `tags` column with `'sql, python, beginner'`,
- columns `phone1`, `phone2`, `phone3`.

Lists hidden in text are hard to query correctly:

<CodeExample output={`CREATE TABLE

INSERT 0 3

        title
---------------------
 Intro to SQL
 MySQL vs PostgreSQL
(2 rows)`}>

```sql
CREATE TABLE articles (
  title text NOT NULL,
  tags text
);

INSERT INTO articles VALUES
  ('Intro to SQL', 'sql, beginner'),
  ('MySQL vs PostgreSQL', 'mysql, postgresql'),
  ('Python for data', 'python, pandas');

SELECT title FROM articles WHERE tags LIKE '%sql%' ORDER BY title;
```

</CodeExample>

We asked for articles tagged `sql` and also got the `mysql` one. Counting articles per tag, renaming a tag or stopping typos would all be just as awkward. The 1NF design is a `tags` table plus an `article_tags` join table: a many-to-many relationship again.

### Second normal form (2NF): depend on the whole key

This matters for tables with a **composite key**. Every other column must depend on the **whole** key, not just part of it. Imagine `order_items` with an extra `product_name` column:

```text
 order_id | product_id | quantity | product_name
----------+------------+----------+--------------
        1 |          8 |        3 | Algorithms in Pictures
        6 |          8 |        2 | Algorithms in Pictures
```

`quantity` depends on the pair (this product in this order), but `product_name` depends **only on `product_id`**. So the name is repeated for every order, and renaming the product means updating all of them: the update anomaly is back. The name belongs in `products`.

### Third normal form (3NF): nothing but the key

Every non-key column must describe **the row's key**, not another non-key column. Imagine `employees` with a `department_location` column: the location depends on the department, not on the employee. Moving the Sales department to Lisbon would mean updating every salesperson. That's why the sample database keeps `location` in `departments`.

A famous summary of all three: every column must depend on **the key** (1NF), **the whole key** (2NF), **and nothing but the key** (3NF).

<Callout type="note" title="Further normal forms exist">

There are stricter forms (BCNF, 4NF, 5NF) that handle rarer situations. In practice, a design in 3NF where every table has a clear primary key and every relationship has a foreign key is what most teams aim for.

</Callout>

## When to copy data on purpose

Normalisation is the starting point, not a religion. Sometimes copying a value is **correct**, because the copy means something different. Look at `order_items.unit_price`: isn't that a copy of `products.price`?

<CodeExample output={`UPDATE 1

 order_id |          name          | unit_price | price_today
----------+------------------------+------------+-------------
        1 | Algorithms in Pictures |      29.00 |       35.00
        1 | Kite                   |      15.00 |       15.00
(2 rows)`}>

```sql
-- Algorithms in Pictures gets more expensive
UPDATE products SET price = 35.00 WHERE id = 8;

SELECT oi.order_id, p.name, oi.unit_price, p.price AS price_today
FROM order_items AS oi
JOIN products AS p ON p.id = oi.product_id
WHERE oi.order_id = 1
ORDER BY p.name;
```

</CodeExample>

No: `unit_price` is the price **at the moment of the sale**, a different fact from today's price. If orders only looked up `products.price`, every price change would rewrite the history of old orders and invoices. Customer addresses on shipped orders, exchange rates on payments and names on certificates follow the same idea.

Teams also **denormalise** on purpose for speed, for example by keeping an `orders.total` column so a busy page doesn't add up items every time. That's a trade-off: reads get faster, but now something must keep the copy correct. Start normalised, and copy data only when you can say why.

<Callout type="tip" title="Design on paper first">

Before writing any `CREATE TABLE`, list the **things** (nouns) your app deals with: books, members, loans. Each one usually becomes a table. Then, for every pair, ask "one or many?" in both directions. One-to-many gets a foreign key on the many side; many-to-many gets a join table. Five minutes with a pencil saves painful migrations later.

</Callout>

Here's what the librarian told you:

- The library has **books** with a `title` (required), an `isbn` (required, and no two books share one) and a `published_year` (a whole number, may be unknown).
- A book can have **several authors**, and an author can write several books. Authors are already done for you (`authors`), and the link between books and authors goes in a join table **`book_authors`** (`book_id`, `author_id`). Its primary key is the pair; if a book is deleted, its author links go with it.
- **Members** have a `name` (required), an `email` (required and unique) and the day they joined, `joined_on` (required).
- A **loan** records that a member borrowed a book: `book_id` and `member_id` (both required, pointing at real rows), `borrowed_on` and `due_on` (required dates), and `returned_on` (empty until the book comes back). The due date must be **after** the borrow date, and a book can't be returned **before** it was borrowed. A book that has loans can't be deleted.
- Every table except `book_authors` gets an identity `id` primary key, like `authors`.

## Recap

- **Normalisation** stores every fact in exactly one place; one big table causes update, insert and delete anomalies.
- **One-to-many**: put the foreign key on the "many" side (`orders.customer_id`).
- **Many-to-many**: add a **join table** whose primary key is the pair of foreign keys (`order_items`, `enrolments`, `book_authors`); it can hold facts about the pair, like `quantity`.
- **1NF**: one value per cell, no lists or `phone1`/`phone2` columns. **2NF**: columns depend on the whole composite key. **3NF**: columns depend on nothing but the key.
- Joins rebuild the wide view when you read; copying data is fine when the copy means something else (a price at the time of sale) or when you denormalise deliberately for speed.
