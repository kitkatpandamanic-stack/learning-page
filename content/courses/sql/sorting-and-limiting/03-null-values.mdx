Real data has gaps. A customer skips the "city" box when signing up; the boss of the company has no manager. SQL marks a missing value with a special value called **`NULL`**. NULL behaves differently from everything else, and it's behind a lot of "why is my result wrong?" moments. After this lesson, it won't catch you out. 🕵️

## What NULL means

`NULL` means **"unknown"** or **"no value here"**. Two customers in the sample database have no city stored:

<CodeExample output={`    name     |    city    | country
-------------+------------+---------
 Mei Lin     | London     | UK
 Ada Brooks  | London     | UK
 Omar Haddad | NULL       | Egypt
 Zara Khan   | NULL       | UK
 Tom Baker   | Manchester | UK
(5 rows)`}>

```sql
SELECT name, city, country
FROM customers
WHERE country IN ('UK', 'Egypt')
ORDER BY id;
```

</CodeExample>

NULL is **not** the same as `0`, and it's not the same as empty text `''`. Zero is a number we know; empty text is text we know is empty. NULL says "we don't know".

<Callout type="note" title="How NULL is displayed">

This site prints missing values as `NULL` so you can spot them. In PostgreSQL's own command-line tool, `psql`, they show up as an **empty cell** by default, which is easy to mistake for empty text.

</Callout>

## Why = NULL finds nothing

Let's find the customers with no city. This looks right, but returns nothing:

<CodeExample output={` name | city
------+------
(0 rows)`}>

```sql
SELECT name, city
FROM customers
WHERE city = NULL;
```

</CodeExample>

Think of NULL as "unknown". Is an unknown city equal to an unknown value? Nobody can say, so the answer isn't true or false: it's **unknown** too. Any comparison with NULL (`=`, `<>`, `<`, `>`…) gives NULL:

<CodeExample output={`  a   |  b   |  c   | d
------+------+------+---
 NULL | NULL | NULL | t
(1 row)`}>

```sql
SELECT NULL = NULL AS a,
  1 = NULL AS b,
  NULL <> 'London' AS c,
  NULL IS NULL AS d;
```

</CodeExample>

(PostgreSQL prints **true** as `t` and **false** as `f`.) `WHERE` only keeps rows where the condition is **true**, so `city = NULL` never keeps anything.

## IS NULL and IS NOT NULL

To test for a missing value, use the special operators **`IS NULL`** and **`IS NOT NULL`**. They always answer a plain true or false:

<CodeExample output={`    name     | city | country
-------------+------+---------
 Omar Haddad | NULL | Egypt
 Zara Khan   | NULL | UK
(2 rows)

     name     | job_title
--------------+-----------
 Grace Hopper | CEO
(1 row)`}>

```sql
SELECT name, city, country
FROM customers
WHERE city IS NULL
ORDER BY name;

-- Who has no manager?
SELECT name, job_title
FROM employees
WHERE manager_id IS NULL;
```

</CodeExample>

`WHERE city IS NOT NULL` gives the other 18 customers.

## Three-valued logic

Because of NULL, a condition in SQL can have **three** results: **true**, **false** or **unknown** (NULL). This is called **three-valued logic**. `AND`, `OR` and `NOT` follow common sense once you read NULL as "unknown":

| Expression        | Result  | Why                                        |
| ----------------- | ------- | ------------------------------------------ |
| `TRUE AND NULL`   | NULL    | depends on the unknown part                |
| `FALSE AND NULL`  | `false` | false whatever the unknown is              |
| `TRUE OR NULL`    | `true`  | true whatever the unknown is               |
| `FALSE OR NULL`   | NULL    | depends on the unknown part                |
| `NOT NULL`        | NULL    | the opposite of unknown is still unknown   |

This matters in real queries. Which UK customers **don't** live in London?

<CodeExample output={`   name    |    city
-----------+------------
 Tom Baker | Manchester
(1 row)`}>

```sql
SELECT name, city
FROM customers
WHERE country = 'UK' AND city <> 'London'
ORDER BY name;
```

</CodeExample>

Zara Khan is missing! Her city is NULL, so `city <> 'London'` is unknown, and `WHERE` drops her. Whether that's right depends on the question. If "not known to live in London" should include her, say so:

<CodeExample output={`   name    |    city
-----------+------------
 Tom Baker | Manchester
 Zara Khan | NULL
(2 rows)`}>

```sql
SELECT name, city
FROM customers
WHERE country = 'UK'
  AND (city <> 'London' OR city IS NULL)
ORDER BY name;
```

</CodeExample>

PostgreSQL also has a shortcut for this: `city IS DISTINCT FROM 'London'` treats NULL as an ordinary value, so it's true for Zara too.

<Callout type="warning" title="The NOT IN trap">

`3 NOT IN (1, 2, NULL)` is not true! It means `3 <> 1 AND 3 <> 2 AND 3 <> NULL`, and the last part is unknown, so the whole thing is unknown. A `NOT IN` list (or, later, a subquery) that contains a NULL makes `NOT IN` match **nothing**. Keep NULLs out of `NOT IN` lists.

</Callout>

## NULL in calculations

Maths with an unknown value gives an unknown answer. If any part of an expression is NULL, the result is usually NULL:

<CodeExample output={` sum_result | product
------------+---------
       NULL |    NULL
(1 row)`}>

```sql
SELECT 1 + NULL AS sum_result, NULL * 10 AS product;
```

</CodeExample>

So `price * stock` would be NULL for any product with a missing stock count. When you add things up with functions like `sum()` in the Counting & Grouping module, you'll see that they **skip** NULLs instead.

## COALESCE: a fallback for missing values

**`coalesce(a, b, ...)`** returns the **first value that isn't NULL**. It's the standard way to show a fallback instead of NULL:

<CodeExample output={`    name     |    city
-------------+------------
 Mei Lin     | London
 Ada Brooks  | London
 Omar Haddad | unknown
 Zara Khan   | unknown
 Tom Baker   | Manchester
(5 rows)`}>

```sql
SELECT name, coalesce(city, 'unknown') AS city
FROM customers
WHERE country IN ('UK', 'Egypt')
ORDER BY id;
```

</CodeExample>

When `city` has a value, `coalesce` returns it; when it's NULL, it moves on to `'unknown'`. You can give it as many values as you like:

<CodeExample output={` first_known
-------------
 third
(1 row)`}>

```sql
SELECT coalesce(NULL, NULL, 'third', 'fourth') AS first_known;
```

</CodeExample>

The fallback must be the **same type** as the column. `department_id` holds numbers, so its fallback must be a number too:

<CodeExample output={`     name     | department
--------------+------------
 Grace Hopper |          0
 Alan Turing  |          1
 Ada Lovelace |          1
(3 rows)`}>

```sql
SELECT name, coalesce(department_id, 0) AS department
FROM employees
WHERE id <= 3
ORDER BY id;
```

</CodeExample>

`coalesce(department_id, 'none')` would fail with `invalid input syntax for type integer: "none"`, because PostgreSQL tries to turn `'none'` into a number.

<Callout type="tip" title="COALESCE only changes the result">

`coalesce(city, 'unknown')` doesn't change the table: the city is still NULL in the database. It only changes what this query shows. That's usually what you want for reports.

</Callout>

## Sorting NULLs

When you sort, PostgreSQL treats NULL as **bigger than any other value**. So NULLs come **last** in ascending order and **first** with `DESC`:

<CodeExample output={`    name     |    city
-------------+------------
 Ada Brooks  | London
 Mei Lin     | London
 Tom Baker   | Manchester
 Omar Haddad | NULL
 Zara Khan   | NULL
(5 rows)

    name     |    city
-------------+------------
 Omar Haddad | NULL
 Zara Khan   | NULL
 Tom Baker   | Manchester
 Ada Brooks  | London
 Mei Lin     | London
(5 rows)`}>

```sql
SELECT name, city
FROM customers
WHERE country IN ('UK', 'Egypt')
ORDER BY city, name;

SELECT name, city
FROM customers
WHERE country IN ('UK', 'Egypt')
ORDER BY city DESC, name;
```

</CodeExample>

To choose for yourself, add **`NULLS FIRST`** or **`NULLS LAST`** after the column (and after `DESC`, if there is one):

<CodeExample output={`    name     |    city
-------------+------------
 Omar Haddad | NULL
 Zara Khan   | NULL
 Ada Brooks  | London
 Mei Lin     | London
 Tom Baker   | Manchester
(5 rows)

    name     |    city
-------------+------------
 Tom Baker   | Manchester
 Ada Brooks  | London
 Mei Lin     | London
 Omar Haddad | NULL
 Zara Khan   | NULL
(5 rows)`}>

```sql
-- Missing cities first, to fix them
SELECT name, city
FROM customers
WHERE country IN ('UK', 'Egypt')
ORDER BY city NULLS FIRST, name;

-- Z to A, but missing cities at the end
SELECT name, city
FROM customers
WHERE country IN ('UK', 'Egypt')
ORDER BY city DESC NULLS LAST, name;
```

</CodeExample>

`ORDER BY rating DESC NULLS LAST` is a common one: "best first, and unrated items at the bottom, not the top".

The shop is planning deliveries outside London. Write a query on `customers` that:

- shows the columns `name`, `town` and `country`, where `town` is the customer's city, or the text `'unknown'` when the city is missing;
- leaves out customers whose city is London, but **keeps** customers whose city is missing (someone needs to call them!);
- lists the customers with a **missing city first** (sorted by name), then everyone else **by city, A to Z**.

The starter query has two NULL bugs: it loses the customers with no city, and it would sort them last. You should get 18 rows.

<Hint>

- Column: `coalesce(city, 'unknown') AS town`.
- Filter: `city <> 'London' OR city IS NULL`.

```sql
WHERE city <> 'London' OR city IS NULL

```

## Recap

- `NULL` means a missing or unknown value. It isn't `0` and it isn't `''`.
- Comparisons with NULL give NULL (unknown), and `WHERE` only keeps rows that are **true**. Use `IS NULL` / `IS NOT NULL`.
- SQL uses **three-valued logic**: true, false and unknown. Conditions like `city <> 'London'` silently drop NULL rows; add `OR city IS NULL` when you need them.
- Keep NULLs out of `NOT IN` lists: one NULL makes `NOT IN` match nothing.
- Arithmetic with NULL gives NULL. `coalesce(a, b, ...)` returns the first value that isn't NULL.
- NULLs sort last in ascending order and first with `DESC`; change that with `NULLS FIRST` / `NULLS LAST`.
