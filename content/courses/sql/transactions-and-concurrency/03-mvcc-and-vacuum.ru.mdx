Команда заметила, что таблица `sessions` стала тормозить. В ней было около 10 000 строк, но на диске она занимала **9 ГБ**, и даже `SELECT count(*)` выполнялся секундами. Строки обновлялись каждые несколько секунд (`last_seen_at` каждой сессии), и это нормально. Ненормальным было другое: **три недели назад** разработчик открыл транзакцию в SQL-консоли, выполнил один запрос и ушёл в отпуск, оставив окно открытым. Эта единственная простаивающая транзакция не давала PostgreSQL убирать **никакие** старые версии строк во всей базе данных. Её завершение и запуск `VACUUM` вернули всё в норму, а чтобы вернуть место на диске, понадобилось окно обслуживания. 🧹

Чтобы понять, как одна простаивающая сессия может такое натворить, нужно разобраться в механизме, который лежит под каждой транзакцией в PostgreSQL: **MVCC** (multi-version concurrency control, многоверсионное управление конкурентным доступом).

## У каждой строки есть скрытые столбцы

У каждой таблицы есть **системные столбцы (system columns)**, которые не видны в `SELECT *`, но их можно запросить по имени:

- **`xmin`**: id транзакции, которая **создала** эту версию строки,
- **`xmax`**: id транзакции, которая её **удалила или заблокировала** (0, если такой нет),
- **`ctid`**: физический адрес версии — (номер страницы, слот на странице).

Каждая транзакция, которая что-то меняет, получает **идентификатор транзакции (transaction id, xid)** — число, которое постоянно растёт. Посмотрим:

<CodeExample output={`CREATE TABLE

INSERT 0 3

 ctid  | xmin | xmax | id | hits
-------+------+------+----+------
 (0,1) | 754  | 0    |  1 |    0
 (0,2) | 754  | 0    |  2 |    0
 (0,3) | 754  | 0    |  3 |    0
(3 rows)`}>

```sql
CREATE TABLE counters (
  id integer PRIMARY KEY,
  hits integer NOT NULL
);
INSERT INTO counters VALUES (1, 0), (2, 0), (3, 0);

SELECT ctid, xmin, xmax, id, hits
FROM counters
ORDER BY id;
```

</CodeExample>

Все три строки созданы одной и той же транзакцией (`INSERT`), поэтому у них общий `xmin`, и они лежат в слотах с 1 по 3 на странице 0. (Номера xid зависят от того, сколько транзакций сервер выполнил до этого, поэтому на настоящем сервере у вас они будут другими. Важно то, как они соотносятся друг с другом.)

## UPDATE записывает новую версию

Теперь ключевой факт этого урока. PostgreSQL **никогда не меняет строку на месте**. `UPDATE` записывает **новую версию** строки и помечает старую как удалённую, выставляя её `xmax`:

<CodeExample output={`CREATE TABLE

INSERT 0 3

UPDATE 1

 ctid  | xmin | xmax | id | hits
-------+------+------+----+------
 (0,1) | 754  | 0    |  1 |    0
 (0,4) | 755  | 0    |  2 |    1
 (0,3) | 754  | 0    |  3 |    0
(3 rows)`}>

```sql
CREATE TABLE counters (
  id integer PRIMARY KEY,
  hits integer NOT NULL
);
INSERT INTO counters VALUES (1, 0), (2, 0), (3, 0);

UPDATE counters SET hits = hits + 1 WHERE id = 2;

SELECT ctid, xmin, xmax, id, hits
FROM counters
ORDER BY id;
```

</CodeExample>

Строка 2 теперь живёт в **слоте 4** с новым `xmin` (транзакцией `UPDATE`). В слоте 2 всё ещё лежит старая версия с `hits = 0`, и её `xmax` указывает на ту же транзакцию. Запросом её уже никто не увидит, но место на странице она занимает: это **мёртвый кортеж (dead tuple)** («кортеж» (tuple) — так PostgreSQL называет версию строки). `DELETE` работает так же: он только выставляет `xmax`, а строка остаётся на диске, пока её не уберут.

Зачем такая окольная схема? Затем, что она делает чтение и запись независимыми. Транзакции, начавшейся **до** обновления, всё ещё нужна **старая** версия — и вот она, на месте.

## Снимки: кто какую версию видит

Когда начинается инструкция (в read committed) или транзакция (в repeatable read), она делает **снимок (snapshot)**: записывает, какие транзакции были зафиксированы в этот момент. Версия строки видна вам, если:

- транзакция из её `xmin` **зафиксирована до вашего снимка** (или это ваша собственная транзакция), и
- её `xmax` равен 0 или принадлежит транзакции, которая **была прервана** или **ещё не была зафиксирована**, когда делался ваш снимок.

Вот как работают временные диаграммы из двух прошлых уроков:

```text
A: BEGIN ISOLATION LEVEL REPEATABLE READ;
A: SELECT hits FROM counters WHERE id = 2;  -- 0 (снимок сделан)
                                B: UPDATE counters SET hits = 1
                                     WHERE id = 2;   -- новая версия
                                B: COMMIT;
A: SELECT hits FROM counters WHERE id = 2;  -- всё ещё 0: версия B
                                            -- новее, чем снимок A
A: COMMIT;
```

Чтобы A прочитала согласованную картину, пока B писала, никакие блокировки не понадобились: каждая просто смотрит на свою версию. Это и есть правило «читающие никогда не блокируют пишущих» из прошлого урока.

**Прерванная (aborted)** транзакция тоже оставляет следы. Её версии остаются на диске, но их xid помечен как прерванный, поэтому все их игнорируют:

<CodeExample output={`CREATE TABLE

INSERT 0 3

BEGIN

UPDATE 1

ROLLBACK

 ctid  | xmin | xmax | id | hits
-------+------+------+----+------
 (0,1) | 754  | 0    |  1 |    0
 (0,2) | 754  | 0    |  2 |    0
 (0,3) | 754  | 755  |  3 |    0
(3 rows)`}>

```sql
CREATE TABLE counters (
  id integer PRIMARY KEY,
  hits integer NOT NULL
);
INSERT INTO counters VALUES (1, 0), (2, 0), (3, 0);

BEGIN;
UPDATE counters SET hits = 99 WHERE id = 3;
ROLLBACK;

SELECT ctid, xmin, xmax, id, hits
FROM counters
ORDER BY id;
```

</CodeExample>

У строки 3 ненулевой `xmax`, но она жива и у неё `hits = 0`: транзакция, которая пыталась её заменить, откатилась. Поэтому же `ROLLBACK` в PostgreSQL мгновенный, сколько бы работы ни сделала транзакция: отменять ничего не нужно, версии просто никогда не становятся видимыми.

<Callout type="tip" title="Трюк на xmax: вставлено или обновлено?">

`INSERT … ON CONFLICT DO UPDATE` записывает обновлённую версию с выставленным `xmax` (строка была заблокирована во время конфликта), а у только что вставленной строки `xmax = 0`. Поэтому `RETURNING (xmax = 0) AS inserted` долго был популярным способом их различить. Однако он опирается на деталь реализации. В PostgreSQL 18 появился документированный способ: **`RETURNING old.*, new.*`**, где `old` равно NULL для вставленной строки. Он пригодится вам в упражнении.

</Callout>

## Мёртвые кортежи и раздувание таблиц

Каждый `UPDATE` оставляет после себя мёртвый кортеж. Обновите каждую строку таблицы один раз — и в ней будет по **две** версии каждой строки. Следите за размером таблицы из 20 000 строк:

<CodeExample output={`CREATE TABLE

INSERT 0 20000

 before
--------
 712 kB
(1 row)

UPDATE 20000

 after_update
--------------
 1416 kB
(1 row)

DO

 n_live_tup | n_dead_tup
------------+------------
      20000 |      20000
(1 row)`}>

```sql
CREATE TABLE visits (id integer, hits integer);
INSERT INTO visits SELECT g, 0 FROM generate_series(1, 20000) AS g;

SELECT pg_size_pretty(pg_relation_size('visits')) AS before;

UPDATE visits SET hits = hits + 1;

SELECT pg_size_pretty(pg_relation_size('visits')) AS after_update;

-- статистика отправляется пачками; опубликуем её прямо сейчас
DO $$ BEGIN PERFORM pg_stat_force_next_flush(); END $$;

SELECT n_live_tup, n_dead_tup
FROM pg_stat_user_tables
WHERE relname = 'visits';
```

</CodeExample>

Таблица выросла вдвое, а `pg_stat_user_tables` насчитывает 20 000 **мёртвых кортежей**: старых версий, которые уже никто не видит. Лишний размер — это не только место на диске: каждое последовательное сканирование читает и мёртвые кортежи, а индексы на них указывают. Таблицу, в которой много мёртвого места, называют **раздутой (bloated)**.

## VACUUM наводит порядок

**`VACUUM`** находит мёртвые кортежи, которые **уже не может понадобиться ни одной выполняющейся транзакции**, и помечает их место как свободное для новых версий. Обычно он не возвращает место операционной системе, а делает его **пригодным для повторного использования**:

<CodeExample output={`CREATE TABLE

INSERT 0 20000

UPDATE 20000

DO

VACUUM

 n_dead_tup |  size
------------+---------
          0 | 1416 kB
(1 row)

UPDATE 20000

  size
---------
 1416 kB
(1 row)

VACUUM

  size
--------
 712 kB
(1 row)`}>

```sql
CREATE TABLE visits (id integer, hits integer);
INSERT INTO visits SELECT g, 0 FROM generate_series(1, 20000) AS g;
UPDATE visits SET hits = hits + 1;
DO $$ BEGIN PERFORM pg_stat_force_next_flush(); END $$;

VACUUM visits;
SELECT n_dead_tup,
  pg_size_pretty(pg_relation_size('visits')) AS size
FROM pg_stat_user_tables
WHERE relname = 'visits';

-- следующее полное обновление повторно использует освобождённое место
UPDATE visits SET hits = hits + 1;
SELECT pg_size_pretty(pg_relation_size('visits')) AS size;

-- VACUUM FULL переписывает таблицу компактно
VACUUM FULL visits;
SELECT pg_size_pretty(pg_relation_size('visits')) AS size;
```

</CodeExample>

- После `VACUUM` мёртвых кортежей не осталось, но размер файла прежний.
- Следующий полный `UPDATE` вообще не увеличивает таблицу: новые версии ложатся в место, освобождённое `VACUUM`. Таблица, которую регулярно очищают, стабилизируется на постоянном размере.
- **`VACUUM FULL`** записывает совершенно новую компактную копию таблицы и возвращает место. Всё это время он держит блокировку **`ACCESS EXCLUSIVE`**, которая блокирует даже `SELECT`, поэтому на нагруженной продакшен-таблице это авария. Вместо него команды используют расширение `pg_repack`, которое делает то же самое без остановки работы.

У `VACUUM` есть и другие задачи: он обновляет **карту видимости (visibility map)**, которая позволяет сканированию только по индексу не заглядывать в таблицу, и **замораживает** старые строки, что подводит нас к одному пугающему слову.

### Переполнение счётчика транзакций (wraparound)

Идентификаторы транзакций — 32-битные числа, поэтому примерно через 4 миллиарда они заканчиваются и **идут по кругу (wrap around)**. Чтобы «более старый» по-прежнему означал более старый, `VACUUM` **замораживает (freezes)** строки с достаточно старым `xmin`, помечая их как видимые всем навсегда. Если заморозка слишком отстаёт (потому что vacuum не может запуститься или его постоянно отменяют), PostgreSQL громко предупреждает, а в конце концов **отказывается начинать новые транзакции**, чтобы защитить ваши данные. У нескольких известных компаний из-за этого были многочасовые аварии. Мониторинг — это один запрос: `SELECT datname, age(datfrozenxid) FROM pg_database;` с оповещением, когда значение превысит несколько сотен миллионов.

## Autovacuum

Сегодня никто не запускает `VACUUM` вручную по расписанию. Фоновый процесс **autovacuum** следит за статистикой и очищает таблицу, когда число её мёртвых кортежей превышает порог:

<CodeExample output={`              name              | setting
--------------------------------+---------
 autovacuum                     | on
 autovacuum_naptime             | 60
 autovacuum_vacuum_scale_factor | 0.2
 autovacuum_vacuum_threshold    | 50
(4 rows)`}>

```sql
SELECT name, setting
FROM pg_settings
WHERE name IN ('autovacuum', 'autovacuum_vacuum_threshold',
  'autovacuum_vacuum_scale_factor', 'autovacuum_naptime')
ORDER BY name;
```

</CodeExample>

Таблица очищается, когда `мёртвых кортежей > threshold + scale_factor × строк`: 50 + 20% таблицы. Для таблицы из 1 000 строк это 250 мёртвых строк — отлично. Для таблицы из **100 миллионов строк** это 20 миллионов мёртвых строк, прежде чем что-то произойдёт, а это слишком поздно. Решение — индивидуальные настройки для больших нагруженных таблиц:

```sql
ALTER TABLE events SET (
  autovacuum_vacuum_scale_factor = 0.01,  -- 1% вместо 20%
  autovacuum_vacuum_cost_limit = 2000     -- пусть работает быстрее
);
```

<Callout type="warning" title="Никогда не отключайте autovacuum">

Когда autovacuum появляется в `pg_stat_activity` в час пик, возникает соблазн его отключить. Не делайте этого: мёртвые кортежи продолжат копиться, запросы замедлятся, и в итоге защита от переполнения счётчика транзакций запустит аварийную очистку в самый неподходящий момент. Если autovacuum не справляется, сделайте его **более** агрессивным, а не менее.

</Callout>

## HOT-обновления и fillfactor

Есть ещё один трюк, который экономит много работы. Если `UPDATE` не меняет **ни одного индексированного столбца**, а новая версия **помещается на ту же страницу**, PostgreSQL делает **HOT**-обновление (heap-only tuple): индексы вообще не трогаются, а старую версию можно убрать прямо на месте при последующих чтениях этой страницы, не дожидаясь `VACUUM`.

Чтобы оставить на каждой странице место для HOT-обновлений, задайте часто обновляемым таблицам меньший **`fillfactor`**. Сравните одно и то же обновление на двух таблицах:

<CodeExample output={`CREATE TABLE

CREATE TABLE

INSERT 0 10000

INSERT 0 10000

 packed_before | roomy_before
---------------+--------------
 360 kB        | 712 kB
(1 row)

UPDATE 10000

UPDATE 10000

DO

 relname | n_tup_upd | n_tup_hot_upd |  size
---------+-----------+---------------+--------
 packed  |     10000 |             0 | 712 kB
 roomy   |     10000 |         10000 | 712 kB
(2 rows)`}>

```sql
CREATE TABLE packed (id integer PRIMARY KEY, hits integer);
CREATE TABLE roomy (id integer PRIMARY KEY, hits integer)
  WITH (fillfactor = 50);
INSERT INTO packed SELECT g, 0 FROM generate_series(1, 10000) AS g;
INSERT INTO roomy SELECT g, 0 FROM generate_series(1, 10000) AS g;

SELECT pg_size_pretty(pg_relation_size('packed')) AS packed_before,
  pg_size_pretty(pg_relation_size('roomy')) AS roomy_before;

UPDATE packed SET hits = hits + 1;
UPDATE roomy SET hits = hits + 1;

DO $$ BEGIN PERFORM pg_stat_force_next_flush(); END $$;
SELECT relname, n_tup_upd, n_tup_hot_upd,
  pg_size_pretty(pg_relation_size(relid)) AS size
FROM pg_stat_user_tables
WHERE relname IN ('packed', 'roomy')
ORDER BY relname;
```

</CodeExample>

`packed` заполняет свои страницы целиком, поэтому новая версия не помещается рядом со старой: ни одно из её обновлений не HOT, каждое ещё и записало новую запись в индекс первичного ключа, а таблица выросла вдвое. `roomy` изначально вдвое больше (каждая страница наполовину пуста), но каждое её обновление — HOT, и она не растёт вовсе. Для таблицы вроде `sessions`, которую постоянно обновляют по неиндексированному столбцу, это именно тот обмен, который вам нужен. Это же повод дважды подумать, прежде чем индексировать постоянно меняющийся столбец: индекс делает HOT-обновления невозможными.

## Долгие транзакции: тихий убийца

Вернёмся к истории из начала. `VACUUM` может удалить мёртвый кортеж, только если **он уже не может понадобиться ни одной выполняющейся транзакции**. PostgreSQL отслеживает самый старый снимок, который ещё используется, — **горизонт xmin (xmin horizon)**. Всё, что удалено после этой точки, приходится хранить в **каждой** таблице базы данных, потому что та старая транзакция может прочитать любую из них:

```text
09:00  A: BEGIN; SELECT ... ;   -- и разработчик уходит на обед
09:00 - 17:00  приложение обновляет 2 миллиона строк во многих таблицах
               autovacuum запускается каждую минуту и удаляет... ничего:
               каждый мёртвый кортеж новее снимка A
17:00  таблицы разрослись, запросы стали медленнее
17:05  A: ROLLBACK;            -- горизонт сдвигается, VACUUM наконец чистит
```

Обычные причины, примерно в порядке того, как часто они встречаются:

- **Idle in transaction**: приложение или консоль, которые выполнили `BEGIN` и так и не закончили (забытый `commit()`, HTTP-вызов внутри транзакции, упавший обработчик, держащий своё соединение).
- **Долгие запросы** на основном сервере: огромный отчёт, `pg_dump`, заполнение данных при миграции в одной транзакции.
- **Брошенные слоты репликации** и реплики с `hot_standby_feedback`, выполняющие долгие запросы: они тоже удерживают горизонт.

Защита — это настройки плюс мониторинг:

```sql
-- Завершать сессии, которые простаивают внутри транзакции
ALTER DATABASE shop SET idle_in_transaction_session_timeout = '5min';
-- Ограничить одну инструкцию и (PostgreSQL 17+) всю транзакцию
ALTER ROLE app SET statement_timeout = '30s';
ALTER ROLE app SET transaction_timeout = '5min';

-- Самые старые открытые транзакции прямо сейчас
SELECT pid, usename, state, now() - xact_start AS open_for,
  left(query, 50) AS query
FROM pg_stat_activity
WHERE xact_start IS NOT NULL
ORDER BY xact_start
LIMIT 5;
```

Плитка дашборда с «возрастом самой старой транзакции» и оповещение, скажем, на 30 минутах поймали бы трёхнедельную транзакцию в первый же день.

Каждое утро задача применяет прайс-лист поставщика с помощью upsert. Это работает, но **обновляет каждую строку из списка**, даже если цена не изменилась. На настоящей таблице (200 000 товаров, примерно 1% меняется за день) это 200 000 новых версий строк и 198 000 мёртвых кортежей в день впустую, плюс отчёт, по которому не понять, что на самом деле произошло. Измените инструкцию так, чтобы:

1. строка с **той же** ценой вообще не обновлялась (без новой версии) — с помощью `WHERE` у `DO UPDATE`,
2. она возвращала `sku`, `price` и `inserted`: `true` для нового товара, `false` для обновлённого. Неизменённые строки не возвращаются, потому что их не трогали.

В сравнении используйте `IS DISTINCT FROM`, а не `<>`, чтобы оно работало, даже если цена когда-нибудь окажется NULL.

<Hint>

`ON CONFLICT (sku) DO UPDATE SET price = excluded.price WHERE prices.price IS DISTINCT FROM excluded.price` обновляет только настоящие изменения (внутри `DO UPDATE` `prices` — существующая строка, а `excluded` — предложенная). Для флага: PostgreSQL 18 позволяет использовать в `RETURNING` `old` и `new`, и `old.sku IS NULL AS inserted` истинно, когда старой строки не было. (`xmax = 0 AS inserted` тоже работает.)

</Hint>

<Solution>

```sql
CREATE TABLE prices (
  sku text PRIMARY KEY,
  price numeric(8, 2) NOT NULL
);
INSERT INTO prices VALUES
  ('tea-jasmine', 6.50),
  ('tea-matcha', 14.00),
  ('tea-earl-grey', 5.25);

INSERT INTO prices (sku, price) VALUES
  ('tea-jasmine', 6.50),
  ('tea-matcha', 15.00),
  ('tea-oolong', 9.00)
ON CONFLICT (sku) DO UPDATE SET price = excluded.price
WHERE prices.price IS DISTINCT FROM excluded.price
RETURNING new.sku, new.price, old.sku IS NULL AS inserted;
```

</Solution>

## Итоги

- Каждая версия строки несёт **`xmin`** (кто её создал), **`xmax`** (кто её удалил или заблокировал) и **`ctid`** (где она лежит).
- **`UPDATE` записывает новую версию**, а `DELETE` только выставляет `xmax`; старые версии становятся **мёртвыми кортежами**. `ROLLBACK` мгновенный, потому что версии прерванных транзакций просто игнорируются.
- **Снимки** решают, какие версии видит каждая инструкция или транзакция, поэтому читающие и пишущие никогда не блокируют друг друга.
- **`VACUUM`** делает место мёртвых кортежей пригодным для повторного использования, обновляет карту видимости и **замораживает** старые строки, чтобы предотвратить переполнение счётчика xid. `VACUUM FULL` уменьшает файл, но полностью блокирует таблицу.
- **Autovacuum** делает это автоматически; для больших нагруженных таблиц уменьшайте `autovacuum_vacuum_scale_factor` и никогда его не отключайте.
- **HOT-обновления** не трогают индексы, когда не меняется ни один индексированный столбец и на странице есть место; меньший **`fillfactor`** оставляет это место.
- Одна **долгая или простаивающая транзакция** удерживает горизонт xmin и останавливает очистку во всей базе: задайте `idle_in_transaction_session_timeout`, следите за `pg_stat_activity` и настройте оповещения о старых транзакциях.
- Не записывайте версии, которые вам не нужны: пропускайте обновления, ничего не меняющие, с помощью `WHERE … IS DISTINCT FROM …`.

Это машинное отделение конкурентного доступа в PostgreSQL. Дальше в Уровне 3 — продвинутое моделирование данных.
