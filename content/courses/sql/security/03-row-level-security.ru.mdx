Привилегии работают на уровне таблиц и столбцов: роль либо может читать `notes`, либо нет. Большинству приложений нужно что-то тоньше: **каждый пользователь может читать таблицу заметок, но только свои строки**. Обычно это правило живёт в коде приложения в виде `WHERE owner_id = …`, о котором должен помнить каждый запрос. Стоит один раз забыть (в новом эндпоинте, отчёте или админке) — и один клиент видит данные другого. Это одна из самых частых серьёзных ошибок в мультиарендных (multi-tenant) системах. **Защита на уровне строк (row-level security, RLS)** переносит правило в базу данных, где оно автоматически применяется к каждому запросу. 🧱

Во всех примерах используется небольшая таблица заметок, принадлежащих клиентам из учебной базы, и роль `app_user`, которая изображает веб-приложение:

```sql
CREATE TABLE notes (
  id integer GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  owner_id integer NOT NULL REFERENCES customers (id),
  body text NOT NULL
);

INSERT INTO notes (owner_id, body) VALUES
  (1, 'Mei: buy jasmine tea'),
  (1, 'Mei: call Sam'),
  (2, 'Sam: fix the kite'),
  (3, 'Ada: read The Bamboo Code');

CREATE ROLE app_user NOLOGIN;
GRANT SELECT, INSERT, UPDATE, DELETE ON notes TO app_user;
```

## Включаем: по умолчанию всё запрещено

`ALTER TABLE … ENABLE ROW LEVEL SECURITY` включает RLS. С этого момента обычная роль видит только строки, которые разрешает какая-нибудь **политика (policy)**. Если политик нет совсем, это значит **ничего**:

INSERT 0 4

GRANT

---------

(1 row)

RESET

---------------------
                   4
(1 row)`}>

```sql
CREATE TABLE notes (
  id integer GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  owner_id integer NOT NULL REFERENCES customers (id),
  body text NOT NULL
);
INSERT INTO notes (owner_id, body) VALUES
  (1, 'Mei: buy jasmine tea'), (1, 'Mei: call Sam'),
  (2, 'Sam: fix the kite'), (3, 'Ada: read The Bamboo Code');
CREATE ROLE app_user NOLOGIN;
GRANT SELECT, INSERT, UPDATE, DELETE ON notes TO app_user;

ALTER TABLE notes ENABLE ROW LEVEL SECURITY;

SET ROLE app_user;
SELECT count(*) AS visible FROM notes;
RESET ROLE;

SELECT count(*) AS visible_to_postgres FROM notes;
```

</CodeExample>

Ошибки нет, просто нет строк: RLS работает как **фильтр**, словно невидимый `WHERE`. Второй подсчёт показывает главное исключение: на **суперпользователей**, роли с `BYPASSRLS` и (как вы скоро увидите) **владельца таблицы** RLS не действует.

## Кто текущий пользователь?

Политике нужно знать, кто спрашивает. Есть два распространённых ответа:

1. **Отдельная роль базы данных на каждого пользователя** (`current_user`). Просто, но для веб-приложений встречается редко: понадобились бы тысячи ролей и отдельное подключение на каждого пользователя.
2. **Одна роль для приложения плюс параметр (setting)**, который приложение задаёт в начале каждого запроса: `set_config('app.user_id', '42', …)`. Политики читают его через `current_setting('app.user_id', true)`. Параметры с точкой в имени, вроде `app.user_id`, можно придумывать самим.

## Пишем политики: USING и WITH CHECK

У политики две части:

- **`USING (…)`**: какие **существующие** строки роль может видеть, изменять или удалять.
- **`WITH CHECK (…)`**: какие **новые** строки (вставленные или полученные в результате обновления) допустимы. Если её не указать, `USING` используется для обоих случаев.

<CodeExample output={`CREATE TABLE

INSERT 0 4

CREATE ROLE

GRANT

ALTER TABLE

CREATE POLICY

SET

 set_config
------------
 1
(1 row)

 id |         body
----+----------------------
  1 | Mei: buy jasmine tea
  2 | Mei: call Sam
(2 rows)

UPDATE 0

DELETE 2

ERROR:  new row violates row-level security policy for table "notes"`}>

```sql
CREATE TABLE notes (
  id integer GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  owner_id integer NOT NULL REFERENCES customers (id),
  body text NOT NULL
);
INSERT INTO notes (owner_id, body) VALUES
  (1, 'Mei: buy jasmine tea'), (1, 'Mei: call Sam'),
  (2, 'Sam: fix the kite'), (3, 'Ada: read The Bamboo Code');
CREATE ROLE app_user NOLOGIN;
GRANT SELECT, INSERT, UPDATE, DELETE ON notes TO app_user;
ALTER TABLE notes ENABLE ROW LEVEL SECURITY;

CREATE POLICY notes_own ON notes
  TO app_user
  USING (owner_id = current_setting('app.user_id', true)::integer)
  WITH CHECK (owner_id = current_setting('app.user_id', true)::integer);

-- Запрос от Mei (клиент 1)
SET ROLE app_user;
SELECT set_config('app.user_id', '1', false);

SELECT id, body FROM notes ORDER BY id;

-- Заметка Sam невидима, поэтому изменить её тоже нельзя
UPDATE notes SET body = 'hacked' WHERE id = 3;
DELETE FROM notes;

-- Запись заметки за другого пользователя: WITH CHECK отказывает
INSERT INTO notes (owner_id, body) VALUES (2, 'Mei was here');
```

</CodeExample>

Внимательно посмотрите на результаты. `UPDATE 0`: для Mei заметки Sam просто не существует. `DELETE 2` без `WHERE` удалил **только собственные заметки Mei**: политика добавляется к каждой инструкции. А `INSERT` громко падает, потому что нарушение `WITH CHECK` — это ошибка, а не фильтр.

### Политики для отдельных команд и их сочетание

`CREATE POLICY … FOR SELECT | INSERT | UPDATE | DELETE | ALL` ограничивает политику одним видом инструкций, а `TO role` — определёнными ролями. Когда действует несколько **разрешительных (permissive)** политик (это вариант по умолчанию), строка допускается, если её разрешает **любая** из них (они объединяются через `OR`). **Ограничительная политика (`RESTRICTIVE`)** должна выполняться **дополнительно** (она объединяется через `AND`) — это удобно для правил, которые действуют поверх всего остального:

<TryIt language="sql" code={`CREATE TABLE notes (
  id integer GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  owner_id integer NOT NULL,
  body text NOT NULL,
  shared boolean NOT NULL DEFAULT false,
  archived boolean NOT NULL DEFAULT false
);
INSERT INTO notes (owner_id, body, shared, archived) VALUES
  (1, 'Mei: private', false, false),
  (2, 'Sam: shared with everyone', true, false),
  (2, 'Sam: private', false, false),
  (2, 'Sam: old shared note', true, true);
CREATE ROLE app_user NOLOGIN;
GRANT SELECT, INSERT, UPDATE, DELETE ON notes TO app_user;
ALTER TABLE notes ENABLE ROW LEVEL SECURITY;

-- Разрешительные: свои заметки ИЛИ общие (для чтения)
CREATE POLICY own_notes ON notes TO app_user
  USING (owner_id = current_setting('app.user_id', true)::integer);
CREATE POLICY read_shared ON notes FOR SELECT TO app_user
  USING (shared);

-- Ограничительная: архивные заметки скрыты от всех и всегда
CREATE POLICY hide_archived ON notes AS RESTRICTIVE TO app_user
  USING (NOT archived);

SELECT id, body FROM notes ORDER BY id;`} />

## Владелец таблицы и FORCE

RLS не действует на **владельца** таблицы. Это удобно для миграций и опасно, когда приложение подключается **как владелец**, а в небольших проектах так бывает очень часто: вы включаете RLS, пишете аккуратные политики — а они молча ничего не делают. Вот ловушка и решение — **`FORCE ROW LEVEL SECURITY`**:

<CodeExample output={`CREATE ROLE

CREATE TABLE

INSERT 0 2

ALTER TABLE

ALTER TABLE

CREATE POLICY

 set_config
------------
 1
(1 row)

SET

 owner_sees
------------
          2
(1 row)

RESET

ALTER TABLE

SET

 owner_sees_with_force
-----------------------
                     1
(1 row)`}>

```sql
CREATE ROLE app_owner NOLOGIN;
CREATE TABLE notes (
  id integer GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  owner_id integer NOT NULL,
  body text NOT NULL
);
INSERT INTO notes (owner_id, body) VALUES
  (1, 'Mei: buy jasmine tea'), (2, 'Sam: fix the kite');
ALTER TABLE notes OWNER TO app_owner;
ALTER TABLE notes ENABLE ROW LEVEL SECURITY;
CREATE POLICY notes_own ON notes
  USING (owner_id = current_setting('app.user_id', true)::integer);

SELECT set_config('app.user_id', '1', false);

SET ROLE app_owner;
SELECT count(*) AS owner_sees FROM notes;
RESET ROLE;

ALTER TABLE notes FORCE ROW LEVEL SECURITY;

SET ROLE app_owner;
SELECT count(*) AS owner_sees_with_force FROM notes;
```

</CodeExample>

Лучшая конфигурация сочетает оба урока этого модуля: приложение подключается под ролью, которая **не владеет** таблицами (минимальные привилегии), **и** вы включаете `FORCE` RLS на таблицах арендаторов как вторую страховку. Суперпользователи и роли с `BYPASSRLS` по-прежнему обходят RLS — это то, что нужно для резервных копий и администрирования, и ещё одна причина, по которой приложение никогда не должно быть суперпользователем.

## Безопасная установка пользователя при пуле подключений

Приложения делят несколько подключений к базе между множеством запросов (**пул подключений, connection pool**). Если запрос A задаст `app.user_id = 1` на всю сессию и забудет его сбросить, запрос B на том же подключении выполнится от имени пользователя 1. Поэтому задавайте параметр **на уровне транзакции**: третий аргумент `set_config` — это `is_local`, и `true` означает «до конца этой транзакции» (то же самое, что `SET LOCAL`):

<CodeExample output={`BEGIN

 set_config
------------
 1
(1 row)

 during
--------
 1
(1 row)

COMMIT

 after | is_empty_text
-------+---------------
       | t
(1 row)

 as_integer
------------
       NULL
(1 row)`}>

```sql
BEGIN;
SELECT set_config('app.user_id', '1', true);
SELECT current_setting('app.user_id', true) AS during;
COMMIT;

SELECT current_setting('app.user_id', true) AS after,
  current_setting('app.user_id', true) = '' AS is_empty_text;

SELECT nullif(current_setting('app.user_id', true), '')::integer
  AS as_integer;
```

</CodeExample>

Здесь важны две детали:

- `current_setting(name, true)`: `true` означает «если параметра нет — ничего страшного, верни NULL», а не выбрасывай ошибку. Политика, сравнивающая с NULL, не подходит ни под одну строку, поэтому запрос, который забыл задать пользователя, **безопасно отказывает (fails closed)**: он не видит ни одной строки.
- После того как значение, локальное для транзакции, перестаёт действовать, параметр существует, но равен **пустой строке**, а `''::integer` — это ошибка. Оберните его: `nullif(current_setting('app.user_id', true), '')::integer`.

В коде приложения запрос тогда выглядит так:

```js
// node-postgres: по транзакции на запрос, пользователь задаётся внутри неё
const client = await pool.connect();
try {
  await client.query("BEGIN");
  await client.query("SELECT set_config('app.user_id', $1, true)", [
    String(session.userId),
  ]);
  const { rows } = await client.query("SELECT * FROM notes");
  await client.query("COMMIT");
} finally {
  client.release();
}
```

## Ловушки, которые обходят ваши политики

- **Представления (views)** по умолчанию выполняются с привилегиями **владельца** представления. Представление, созданное суперпользователем или владельцем таблицы, показывает все строки каждому, кто может его читать. Создавайте представления с `WITH (security_invoker = true)` (PostgreSQL 15+), чтобы RLS применялась к тому, кто выполняет запрос.
- **Функции `SECURITY DEFINER`** тоже выполняются от имени своего владельца, поэтому тоже обходят RLS. Пишите их осторожно или не используйте с таблицами под RLS.
- **Уникальность и внешние ключи выдают существование строк.** Вставка повторяющейся почты падает, даже если другая строка невидима, и пользователь узнаёт, что она существует. Проверки внешних ключей тоже игнорируют RLS.
- **Производительность**: политика становится частью `WHERE` каждого запроса, поэтому **проиндексируйте** столбцы, которые она использует (`owner_id`, `tenant_id`). Если записать чтение параметра как подзапрос, `(SELECT current_setting(…))`, PostgreSQL вычислит его один раз на запрос, а не на каждую строку:

```text
EXPLAIN SELECT * FROM notes WHERE body LIKE '%tea%';   -- от имени app_user
 Bitmap Heap Scan on notes
   Recheck Cond: (owner_id = (InitPlan 1).col1)      ← политика
   Filter: (body ~~ '%tea%'::text)                   ← ваш WHERE
   InitPlan 1                                        ← параметр читается один раз
   ->  Bitmap Index Scan on notes_owner_id_idx
```

## Итоги

- **`ENABLE ROW LEVEL SECURITY`** делает таблицу «по умолчанию всё запрещено»; **политики** говорят, какими строками может пользоваться каждая роль. Суперпользователи, роли с `BYPASSRLS` и **владелец** (если не включить **`FORCE`**) обходят RLS.
- **`USING`** фильтрует существующие строки (невидимые строки нельзя изменить или удалить); **`WITH CHECK`** проверяет новые строки и выбрасывает ошибку. Разрешительные политики объединяются через `OR`, ограничительные (`RESTRICTIVE`) — через `AND`.
- Определяйте пользователя через параметр: `set_config('app.user_id', …, true)` на каждую транзакцию, а читайте через `nullif(current_setting('app.user_id', true), '')`, чтобы при отсутствии пользователя не было видно ничего.
- Следите за обходными путями: представления (используйте `security_invoker`), функции `SECURITY DEFINER`, проверки уникальности и внешних ключей. Индексируйте столбцы из политик.
- Тестируйте политики через **`SET ROLE`** с разными пользователями, как любой другой код безопасности.
