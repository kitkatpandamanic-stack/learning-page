31 января 2017 года инженер GitLab поздно ночью боролся с проблемами репликации и выполнил команду удаления на сервере, который считал сломанной репликой. Это был **основной сервер (primary)**. Около 300 ГБ продакшен-данных исчезли за секунды. Затем команда выяснила, что ни один из пяти способов резервного копирования и репликации не позволяет просто восстановить данные: дампы уже какое-то время молча не создавались, и никто этого не заметил. Восстановились из снимка диска, которому случайно оказалось шесть часов, и шесть часов работы пользователей пропали навсегда. GitLab опубликовал всю историю, и её до сих пор обязательно читать. 🔥

В этой истории нет ничего про синтаксис SQL. Она про **эксплуатацию**: что происходит, когда умирает диск, падает регион или кто-то запускает не ту команду. В этом уроке вы узнаете, как PostgreSQL бэкапят, реплицируют и поддерживают доступным, и как не дать собственному приложению завалить его соединениями.

## RPO и RTO: сначала решите, что вам нужно

Прежде чем выбирать инструмент, согласуйте с бизнесом два числа:

- **RPO, recovery point objective (целевая точка восстановления)**: сколько данных вы можете позволить себе **потерять**, в единицах времени. «RPO 5 минут» означает, что после катастрофы могут пропасть максимум изменения за последние пять минут.
- **RTO, recovery time objective (целевое время восстановления)**: сколько вы можете позволить себе **простаивать**. «RTO 1 час» означает, что база данных должна снова обслуживать запросы в течение часа.

И то и другое стоит денег, и они тянут архитектуру в разные стороны:

| Схема | Типичный RPO | Типичный RTO |
| --- | --- | --- |
| Только ночной `pg_dump` | До 24 часов | Часы (восстановление + перестроение индексов) |
| Базовый бэкап + архивирование WAL | От секунд до минут | От десятков минут до часов |
| + потоковая реплика, ручное переключение | Секунды | Минуты (кто-то должен действовать) |
| + синхронная реплика, автоматическое переключение | Ноль (для закоммиченных данных) | Меньше минуты |

Учебному проекту хватит первой строки. Платёжной системе нужна последняя — **и** бэкапы, потому что, как вы увидите, реплики не защищают от ошибок.

## WAL: как PostgreSQL запоминает каждое изменение

Почти всё в этом уроке строится на одном механизме. Прежде чем изменить файл данных, PostgreSQL записывает описание изменения в **журнал предзаписи (write-ahead log, WAL)** — последовательность файлов в каталоге `pg_wal`. При `COMMIT` PostgreSQL убеждается, что WAL надёжно лежит на диске; сами файлы данных можно обновить позже. Если сервер падает, он воспроизводит WAL с последней контрольной точки, и ничего закоммиченного не теряется.

Каждая позиция в WAL — это **номер последовательности журнала (log sequence number, LSN)**, например `0/3A0F2C8`, и можно измерить, сколько WAL записала инструкция, сравнив LSN до и после. Сравним удаление 50 000 строк с удалением таблицы того же размера:

<CodeExample output={`CREATE TABLE AS

CREATE TABLE AS

CREATE TABLE

INSERT 0 1

DELETE 50000

INSERT 0 1

DROP TABLE

INSERT 0 1

     step     | wal_kb
--------------+--------
 after delete |   2743
 after drop   |      3
(2 rows)`}>

```sql
CREATE TABLE logs_old AS
SELECT g AS id, 'event ' || g AS message
FROM generate_series(1, 50000) AS g;
CREATE TABLE logs_copy AS TABLE logs_old;

-- запоминаем позицию WAL после каждого шага
CREATE TABLE wal_marks (step text, lsn pg_lsn);
INSERT INTO wal_marks VALUES ('start', pg_current_wal_lsn());

DELETE FROM logs_old;
INSERT INTO wal_marks VALUES ('after delete', pg_current_wal_lsn());

DROP TABLE logs_copy;
INSERT INTO wal_marks VALUES ('after drop', pg_current_wal_lsn());

SELECT step, wal_kb
FROM (
  SELECT
    step,
    lsn,
    round(pg_wal_lsn_diff(lsn, lag(lsn) OVER (ORDER BY lsn)) / 1024)
      AS wal_kb
  FROM wal_marks
) AS steps
WHERE step <> 'start'
ORDER BY lsn;
```

</CodeExample>

`pg_wal_lsn_diff(a, b)` возвращает число байтов между двумя позициями. `DELETE` записал больше 2,5 МБ WAL (по записи на каждую строку), а `DROP TABLE` — около 3 кБ. Это аргумент про хранение по сроку из урока [Секционирование больших таблиц](/learn/sql/table-partitioning), только под другим углом: каждый байт WAL ещё и нужно заархивировать для бэкапов и отправить на каждую реплику.

Благодаря WAL работают три разные вещи:

1. **Восстановление после сбоя**: воспроизвести WAL после падения.
2. **Восстановление на момент времени**: восстановить старую копию файлов, а затем воспроизвести заархивированный WAL до любого выбранного момента.
3. **Репликация**: непрерывно отправлять WAL на другой сервер и воспроизводить его там.

## Логические бэкапы с pg_dump

**`pg_dump`** подключается как обычный клиент и выписывает SQL (или сжатый архив), нужный для воссоздания одной базы данных: инструкции `CREATE TABLE`, данные, индексы, ограничения. Он читает всё внутри одной транзакции (transaction), поэтому дамп — это **согласованный снимок**, даже пока приложение продолжает писать.

```bash
# формат custom (-Fc): сжатый, и pg_restore может выбирать из него части
pg_dump --format=custom --file=shop_2025-06-01.dump shop

# восстановление в новую пустую базу в 4 параллельных потока
createdb shop_restored
pg_restore --jobs=4 --dbname=shop_restored shop_2025-06-01.dump

# только одна таблица, в виде обычного читаемого SQL
pg_dump --table=orders --data-only shop > orders.sql

# роли и табличные пространства в pg_dump не попадают: выгружайте их отдельно
pg_dumpall --globals-only > globals.sql
```

Логические бэкапы переносимы: их можно восстановить в **более новую мажорную версию** PostgreSQL, на другую машину или платформу, поэтому они отлично подходят для миграций и копирования данных в тестовое окружение. Их ограничения:

- Это снимок **одного момента**. С ночными дампами ваш RPO — до 24 часов.
- Восстановление большой базы медленное: каждая строка вставляется заново, каждый индекс перестраивается. База на 1 ТБ может восстанавливаться много часов, что может сорвать ваш RTO.

## Физические бэкапы и восстановление на момент времени

**Физический бэкап** вместо этого копирует файлы базы данных. **`pg_basebackup`** делает согласованную копию всего кластера (всех баз данных на сервере), пока тот продолжает работать. Сам по себе это ещё один снимок. Но в сочетании с **архивированием WAL** он становится гораздо мощнее:

```text
                          непрерывный архив WAL
базовый бэкап (вс)    -->  WAL WAL WAL WAL WAL WAL WAL ...  --> сейчас
         |                                    ^
  восстановить файлы,               воспроизвести до среды 14:31:59,
  затем воспроизвести WAL...        за секунду до неудачного DELETE
```

```bash
# 1. postgresql.conf на основном сервере: архивировать каждый завершённый файл WAL
#    archive_mode = on
#    archive_command = 'pgbackrest --stanza=main archive-push %p'

# 2. базовый бэкап, например раз в неделю
pg_basebackup --pgdata=/backups/base_2025-06-01 \
  --wal-method=stream --checkpoint=fast --progress

# 3. катастрофа: восстановите базовый бэкап в новый каталог данных,
#    затем в postgresql.conf восстановленного сервера:
#    restore_command = 'pgbackrest --stanza=main archive-get %f "%p"'
#    recovery_target_time = '2025-06-04 14:31:59+00'
touch /var/lib/postgresql/data/recovery.signal
pg_ctl start   # воспроизводит WAL, останавливается на цели и ждёт
```

Это **восстановление на момент времени (point-in-time recovery, PITR)**: базу можно восстановить на **любую секунду**, покрытую архивом, — например, за секунду до того, как кто-то выполнил `DELETE` без `WHERE`. RPO сокращается до времени с момента последнего заархивированного файла WAL (от секунд до минут; на спокойном сервере `archive_timeout` принудительно переключает файл не реже чем раз в N секунд).

Скрипты для `archive_command` вручную больше никто не пишет. Инструменты вроде **pgBackRest**, **Barman** и **WAL-G** берут на себя сжатие, шифрование, параллельную передачу, хранение в S3 или аналогах, хранение по сроку и проверку. Управляемые сервисы (Amazon RDS, Google Cloud SQL, Azure, Supabase, Neon…) делают то же самое за кнопкой «восстановить на момент времени».

<Callout type="danger" title="Непроверенный бэкап — не бэкап">

У GitLab бэкапы были настроены. Не было доказательства, что они работают. Практика в продакшене:

- **Восстанавливайте регулярно и автоматически**, например каждую неделю на временный сервер, затем запускайте проверочные запросы (число строк, последний `created_at`) и поднимайте тревогу, если что-то не так.
- **Следите** за последним успешным бэкапом и архивом WAL (`pg_stat_archiver` показывает `last_archived_time` и `failed_count`).
- Храните бэкапы в **другом аккаунте и регионе**, чтобы одна ошибка или один скомпрометированный ключ не могли удалить и базу, и её бэкапы.
- Замеряйте, сколько длится восстановление. Это число **и есть** ваш реальный RTO.

</Callout>

## Репликация: живая копия базы данных

**Потоковая репликация (streaming replication)** подключает **резервный сервер (standby)**, или реплику, к **основному (primary)**. Основной сервер передаёт свой WAL по мере записи, а резервный непрерывно его воспроизводит, так что он — почти живая побайтовая копия всего кластера. При включённом `hot_standby` (по умолчанию) резервный сервер ещё и отвечает на запросы **только для чтения**.

```text
           запись + чтение                    только чтение
 app  ------------------->  PRIMARY  ----WAL---->  STANDBY (реплика)
                              |                       |
                              +-------WAL------>  STANDBY 2 (другая зона)
```

Узнать, к какой стороне вы подключены, можно через `pg_is_in_recovery()`: на основном сервере это `false`, на резервном — `true`. На основном сервере в **`pg_stat_replication`** есть строка на каждый подключённый резервный сервер с LSN, которые он получил и воспроизвёл. Вот строки, похожие на те, что она показывает, превращённые в отчёт об отставании:

<CodeExample output={`   standby    |   state   | lag_kb
--------------+-----------+--------
 replica-b    | catchup   |  20480
 replica-a    | streaming |     64
 replica-west | streaming |      0
(3 rows)`}>

```sql
-- на настоящем основном сервере: FROM pg_stat_replication
WITH replication_status (standby, state, sent_lsn, replay_lsn) AS (
  VALUES
    ('replica-a', 'streaming', pg_lsn '0/5A010000', pg_lsn '0/5A000000'),
    ('replica-b', 'catchup', pg_lsn '0/5A010000', pg_lsn '0/58C10000'),
    ('replica-west', 'streaming', pg_lsn '0/5A010000',
      pg_lsn '0/5A010000')
)
SELECT
  standby,
  state,
  round(pg_wal_lsn_diff(sent_lsn, replay_lsn) / 1024) AS lag_kb
FROM replication_status
ORDER BY lag_kb DESC, standby;
```

</CodeExample>

В `pg_stat_replication` также есть столбцы `write_lag`, `flush_lag` и `replay_lag` в виде интервалов — именно по ним срабатывают оповещения на большинстве дашбордов.

### Асинхронная или синхронная

По умолчанию репликация **асинхронная**: `COMMIT` возвращается, как только WAL оказался на диске основного сервера, а резервный догоняет мгновением позже. Это быстро, но если основной сервер умирает, последние несколько транзакций, не дошедших до резервного, при переключении теряются. RPO маленький, но не нулевой.

При **синхронной** репликации `COMMIT` ждёт, пока резервный сервер подтвердит, что WAL есть и у него:

```text
# postgresql.conf на основном сервере
synchronous_standby_names = 'ANY 1 (replica_a, replica_b)'
synchronous_commit = on   # или remote_apply: ждать, пока изменения воспроизведены
```

Теперь закоммиченная транзакция существует на двух серверах, и переключение ничего не теряет. Цена — каждый коммит ждёт сетевой круг, поэтому синхронный резервный сервер держите поблизости (в другой зоне, а не на другом континенте). Используйте `ANY 1 (…)` с **двумя** кандидатами: если синхронный резервный сервер один и он падает, каждый коммит на основном **зависает**, пока тот не вернётся.

`synchronous_commit` можно менять даже для отдельной транзакции (`SET LOCAL synchronous_commit = off` для вставки в лог, потерю которой вы переживёте), так что важные и неважные записи могут платить разную цену.

### Реплики для чтения и устаревшие данные

Отправка запросов только на чтение (отчёты, страницы поиска) на реплики снимает нагрузку с основного сервера. Но реплики всегда немного отстают, и это вызывает классический баг:

```text
1. пользователь сохраняет новое фото профиля -> UPDATE на основном сервере
2. страница перезагружается                  -> SELECT на реплике
3. реплика отстаёт на 300 мс                 -> показывается старое фото
4. пользователь загружает фото ещё раз...
```

Типичные решения: читать **свои недавние записи** с основного сервера (например, несколько секунд после того, как пользователь что-то изменил), держать критичные чтения (платежи, права доступа) на основном сервере или заставить приложение запоминать LSN своей записи и читать только с той реплики, чей `pg_last_wal_replay_lsn()` уже его прошёл.

### Логическая репликация

Потоковая репликация копирует **всё**, и только между серверами одной мажорной версии. **Логическая репликация (logical replication)** вместо этого передаёт изменения строк выбранных таблиц:

```sql
-- на источнике
CREATE PUBLICATION shop_pub FOR TABLE orders, order_items;

-- на приёмнике (где таблицы уже есть)
CREATE SUBSCRIPTION shop_sub
  CONNECTION 'host=old-db dbname=shop user=replicator'
  PUBLICATION shop_pub;
```

Она работает между мажорными версиями, поэтому это стандартный способ **обновиться почти без простоя**: реплицируйте в новую версию, дайте ей догнать, затем переключите приложение. Инструменты захвата изменений данных (change data capture, CDC), например **Debezium**, читают тот же поток, чтобы наполнять поисковые индексы, кеши и хранилища данных.

<Callout type="warning" title="Репликация — это не бэкап">

Реплика копирует **каждое** изменение, включая ошибки. `DROP TABLE orders` на основном сервере за миллисекунды воспроизводится на каждом резервном. Реплики защищают от сбоев **железа**; от **людей и багов** защищают только бэкапы с PITR. Нужно и то и другое.

</Callout>

## Высокая доступность и переключение

**Высокая доступность (high availability, HA)** означает, что база данных продолжает работать, когда сервер умирает. Если есть резервный сервер, **переключение (failover)** выглядит так: заметить, что основного сервера нет, **повысить (promote)** резервный (`pg_ctl promote` или `SELECT pg_promote()`) и направить на него приложение.

Сделать это автоматически сложнее, чем кажется. Опасность — **split brain (расщепление)**: старый основной сервер не умер, а лишь оказался отрезан от сети, и теперь два сервера принимают запись, а их данные расходятся. Настоящие HA-инструменты решают это через **хранилище консенсуса**, которое решает, кто лидер, плюс **изоляцию (fencing)**, гарантирующую, что старый основной сервер перестаёт принимать запись:

- **Patroni** (с etcd или Consul) — самый распространённый open-source вариант; он ещё и пересобирает упавшие узлы как новые резервные.
- Операторы Kubernetes, например **CloudNativePG**, делают то же самое в Kubernetes.
- Управляемые сервисы делают это за вас (например, RDS Multi-AZ, Cloud SQL HA), обычно переключаясь примерно за минуту.

Приложениям тоже есть что делать. Драйверы на основе libpq принимают несколько хостов и умеют находить тот, что доступен для записи:

```text
postgresql://db1,db2,db3/shop?target_session_attrs=read-write
```

А ещё приложения должны **повторять** транзакцию, которая упала из-за обрыва соединения во время переключения, поэтому делайте записи безопасными для повтора (идемпотентными).

## Пул соединений

Последняя проблема масштабирования обычно приходит раньше остальных. Каждое соединение с PostgreSQL — это отдельный **серверный процесс** со своей памятью, а `max_connections` (по умолчанию 100) ограничивает, сколько их может быть:

<CodeExample output={` max_connections
-----------------
 100
(1 row)`}>

```sql
SHOW max_connections;
```

</CodeExample>

Теперь посчитаем для типичного развёртывания: 20 серверов приложения, у каждого пул из 10 соединений, плюс фоновые воркеры и cron-задачи. Это уже больше 200 соединений, и большинство из них в любой момент простаивают. Увеличение `max_connections` до 2000 проблему не решает: тысячи процессов соревнуются за CPU и память, и пропускная способность **падает**. База данных с 16 ядрами CPU в любом случае может выполнять одновременно лишь около 16 запросов. Serverless-функции делают всё ещё хуже, ведь каждый экземпляр может открыть своё соединение.

Решение — **пулер соединений (connection pooler)**, например **PgBouncer** (или PgCat, Supavisor, RDS Proxy), между приложениями и базой данных. Тысячи клиентских соединений делят небольшой пул настоящих серверных соединений:

```text
 app 1 ──┐
 app 2 ──┤  2000 клиентских       ┌── 40 серверных
   ...   ├──соединений──> PgBouncer ──соединений──> PostgreSQL
 app 20 ─┘                        └──
```

У PgBouncer три **режима пула (pooling modes)**:

| Режим | Серверное соединение ваше на… | Примечания |
| --- | --- | --- |
| `session` | всё клиентское соединение | Безопасно для всего, но экономит мало |
| `transaction` | одну транзакцию | Обычный выбор: огромная экономия |
| `statement` | одну инструкцию | Никаких транзакций из нескольких инструкций |

В **режиме транзакций** ваша следующая транзакция может выполниться на **другом** серверном соединении. Поэтому всё, что живёт в **сессии**, ломается или протекает между клиентами: `SET` без `LOCAL`, сессионные advisory-блокировки, `LISTEN`, временные таблицы, сохраняемые между транзакциями, и (в старых версиях PgBouncer) подготовленные выражения. Настройки нужно задавать **для каждой транзакции**:

<CodeExample output={`BEGIN

SET

 statement_timeout
-------------------
 2s
(1 row)

COMMIT

 statement_timeout
-------------------
 0
(1 row)

 tenant
--------
 42
(1 row)

 tenant
--------

(1 row)`}>

```sql
BEGIN;
SET LOCAL statement_timeout = '2s';
SHOW statement_timeout;
COMMIT;

-- после конца транзакции снова значение по умолчанию
SHOW statement_timeout;

-- set_config(name, value, is_local => true) — то же самое, что
-- SET LOCAL, и работает с любым значением, например с параметром
SELECT set_config('app.tenant_id', '42', true) AS tenant;
SELECT current_setting('app.tenant_id', true) AS tenant;
```

</CodeExample>

Вне явной транзакции каждая инструкция — сама себе транзакция, поэтому второй вызов `current_setting` уже видит пустое значение. Именно на это поведение вы будете опираться в итоговом проекте, где каждый запрос сообщает PostgreSQL, от имени какого арендатора он действует.

<Callout type="tip" title="Маленькие пулы быстрее">

Хорошая отправная точка для общего числа активных серверных соединений — небольшое кратное числу ядер CPU базы данных (например, ядра × 2–4), а не сотни. Лишние запросы недолго ждут в очереди пулера, и это дешевле, чем сотни процессов, дерущихся за CPU. Добавьте тайм-ауты, чтобы один плохой клиент не мог держать соединение вечно: `statement_timeout`, `idle_in_transaction_session_timeout` и `lock_timeout`.

</Callout>

RPO вашей команды — **15 минут**, а правило гласит: «успешный полный бэкап не реже чем раз в **24 часа**». Напишите отчёт, который видит дежурный инженер, на момент **`2025-06-01 12:00`** (используйте это фиксированное время, а не `now()`), по строке на базу данных, отсортированный по `db_name`, с такими столбцами:

- **`db_name`**
- **`hours_since_full`**: целое число часов (с округлением) с момента последнего **успешного** полного бэкапа или `NULL`, если такого нет.
- **`data_loss_minutes`**: целое число минут (с округлением) с момента последнего успешного бэкапа **любого** вида (полного или WAL). Столько данных вы потеряли бы, если бы сервер умер прямо сейчас.
- **`at_risk`**: `true`, когда `hours_since_full` больше 24, **или** `data_loss_minutes` больше 15, **или** вообще нет успешного бэкапа, по которому можно мерить; иначе `false`. Это значение никогда не должно быть `NULL`.

<Hint>

Используйте агрегаты с `FILTER`: `max(finished_at) FILTER (WHERE kind = 'full' AND ok)` — последний удачный полный бэкап, а `max(finished_at) FILTER (WHERE ok)` — последний удачный бэкап любого вида. Превратите интервал в часы через `extract(epoch FROM timestamp '2025-06-01 12:00' - …) / 3600`, затем `round(…)`. Если сначала вычислить два значения в CTE, выражение `at_risk` останется читаемым. Оберните сравнения в `coalesce(…, true)`, чтобы отсутствующий бэкап считался риском.

</Hint>

<Solution>

```sql
CREATE TABLE backup_runs (
  id integer GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  db_name text NOT NULL,
  kind text NOT NULL CHECK (kind IN ('full', 'wal')),
  finished_at timestamp NOT NULL,
  ok boolean NOT NULL
);

INSERT INTO backup_runs (db_name, kind, finished_at, ok) VALUES
  ('billing', 'full', '2025-06-01 02:00', true),
  ('billing', 'wal', '2025-06-01 11:58', true),
  ('shop', 'full', '2025-06-01 03:00', true),
  ('shop', 'wal', '2025-06-01 09:30', true),
  ('shop', 'wal', '2025-06-01 11:59', false),
  ('analytics', 'full', '2025-05-29 04:00', true),
  ('analytics', 'full', '2025-06-01 04:00', false),
  ('analytics', 'wal', '2025-06-01 11:57', true),
  ('auth', 'full', '2025-06-01 01:00', true),
  ('auth', 'wal', '2025-06-01 11:59', true);

WITH latest AS (
  SELECT
    db_name,
    max(finished_at) FILTER (WHERE kind = 'full' AND ok) AS last_full,
    max(finished_at) FILTER (WHERE ok) AS last_good
  FROM backup_runs
  GROUP BY db_name
),
ages AS (
  SELECT
    db_name,
    round(extract(epoch FROM timestamp '2025-06-01 12:00'
      - last_full) / 3600) AS hours_since_full,
    round(extract(epoch FROM timestamp '2025-06-01 12:00'
      - last_good) / 60) AS data_loss_minutes
  FROM latest
)
SELECT
  db_name,
  hours_since_full,
  data_loss_minutes,
  coalesce(hours_since_full > 24 OR data_loss_minutes > 15, true)
    AS at_risk
FROM ages
ORDER BY db_name;
```

</Solution>

## Итоги

- Сначала договоритесь о **RPO** (сколько данных можно потерять) и **RTO** (сколько можно простаивать): они определяют архитектуру.
- **WAL** записывает каждое изменение до того, как оно произойдёт; на нём держатся восстановление после сбоя, восстановление на момент времени и репликация. Большие `DELETE` пишут его очень много.
- **`pg_dump`/`pg_restore`**: переносимые логические снимки одной базы данных, хороши для обновлений и копий, но медленно восстанавливаются, если база большая.
- **`pg_basebackup` + архивирование WAL** (через pgBackRest, Barman или WAL-G) дают **PITR** с точностью до секунды. Регулярно **проверяйте восстановление** и следите за архивом.
- **Потоковые реплики** дают HA и масштабирование чтения; асинхронные могут потерять последние транзакции, **синхронные** (`ANY 1 (a, b)`) — нет, но добавляют задержку коммита. Остерегайтесь **устаревших чтений** с реплик.
- **Логическая репликация** копирует выбранные таблицы между версиями: обновления без простоя и CDC.
- **Репликация — это не бэкап**: ошибки реплицируются мгновенно.
- Автоматическому **переключению** нужны консенсус и изоляция (Patroni, операторы, управляемые сервисы) и приложения, которые повторяют запросы.
- Используйте **пулер соединений** (PgBouncer, режим транзакций) с маленькими пулами; держите состояние сессии на уровне транзакции через **`SET LOCAL`** / **`set_config(…, true)`**.
