So far every query has read from **one** table. But the answer to most real questions is spread over several: an order knows *which* customer placed it, but the customer's name lives in a different table. A **join** puts the pieces back together. It's the single most important skill in SQL after `SELECT` itself. 🔗

## Why data lives in several tables

Look at the first few orders, and at the customers they point to:

<CodeExample output={` id | customer_id |     ordered_at      |  status
----+-------------+---------------------+-----------
  1 |           8 | 2025-01-07 12:17:00 | delivered
  2 |          15 | 2025-01-11 15:34:00 | shipped
  3 |           5 | 2025-01-15 18:51:00 | paid
(3 rows)

 id |    name     |    city
----+-------------+-------------
  5 | Ravi Patel  | Mumbai
  8 | Sofia Rossi | Rome
 15 | Diego López | Mexico City
(3 rows)`}>

```sql
SELECT id, customer_id, ordered_at, status
FROM orders
ORDER BY id
LIMIT 3;

SELECT id, name, city
FROM customers
WHERE id IN (5, 8, 15)
ORDER BY id;
```

</CodeExample>

Order 1 doesn't store "Sofia Rossi". It stores `customer_id = 8`, and customer 8 is Sofia. That's deliberate:

- Each customer's details are stored **once**. If Sofia changes her email, one row changes, not every order she ever placed.
- `customers.id` is the table's **primary key**: a value that identifies exactly one customer.
- `orders.customer_id` is a **foreign key**: it points at a primary key in another table. The database refuses an order whose `customer_id` doesn't exist.

```text
orders                                customers
 id | customer_id | status             id | name
----+-------------+-----------        ----+-------------
  1 |           8 | delivered  ───►     8 | Sofia Rossi
  2 |          15 | shipped    ───►    15 | Diego López
  3 |           5 | paid       ───►     5 | Ravi Patel
```

The sample shop has more links like this: `order_items.order_id` points at `orders.id`, and `order_items.product_id` points at `products.id`. You'll design keys like these yourself later in Level 1.

## Your first JOIN

`JOIN` adds a second table to the `FROM`, and `ON` says **which rows belong together**: here, an order and the customer whose `id` equals the order's `customer_id`:

<CodeExample output={` id |     name     |  status
----+--------------+-----------
  1 | Sofia Rossi  | delivered
  2 | Diego López  | shipped
  3 | Ravi Patel   | paid
  4 | Chloe Martin | cancelled
  5 | Sam Ortiz    | delivered
(5 rows)`}>

```sql
SELECT orders.id, customers.name, orders.status
FROM orders
JOIN customers ON customers.id = orders.customer_id
ORDER BY orders.id
LIMIT 5;
```

</CodeExample>

Because two tables are involved, we write columns as `table.column`: `orders.id` is the order's id, `customers.name` the customer's name.

Think of a join like this: the database looks at **every pair** of an order and a customer, and keeps the pairs where the `ON` condition is true. Each order has exactly one matching customer, so each order appears once, now with its customer's columns attached. (The real database is much smarter than trying every pair, but the result is the same.)

## Table aliases with AS

Writing `customers.` and `orders.` everywhere gets long. Give each table a short **alias** with `AS` and use it instead. With aliases, a join reads nicely even with filters on both tables:

<CodeExample output={` order_id |    name    | ordered_on
----------+------------+------------
       10 | Ada Brooks | 2025-02-13
       31 | Zara Khan  | 2025-05-11
(2 rows)`}>

```sql
SELECT o.id AS order_id, c.name, o.ordered_at::date AS ordered_on
FROM orders AS o
JOIN customers AS c ON c.id = o.customer_id
WHERE c.country = 'UK' AND o.status = 'delivered'
ORDER BY o.ordered_at;
```

</CodeExample>

Once the tables are joined, `WHERE` can use columns from **both**: the country comes from `customers`, the status from `orders`. Aliases are usually the first letter (or two) of the table name: `o` for orders, `c` for customers, `oi` for order_items.

## Ambiguous columns

Both tables have a column called `id`. If you don't say which one you mean, PostgreSQL refuses to guess:

<CodeExample output={`ERROR:  column reference "id" is ambiguous
LINE 1: SELECT id, name, status
               ^`}>

```sql
SELECT id, name, status
FROM orders
JOIN customers ON customers.id = orders.customer_id;
```

</CodeExample>

`name` and `status` exist in only one table each, so they would work alone, but `id` must be written as `orders.id` or `customers.id`. A good habit: in a join, **prefix every column** with its table's alias. Your query keeps working even if someone later adds a `status` column to `customers`.

## Joining on the wrong columns

A join only knows what you tell it in `ON`. Join on the wrong columns and you get no error, just wrong answers:

<CodeExample output={` order_id |   name
----------+-----------
        1 | Mei Lin
        2 | Sam Ortiz
(2 rows)`}>

```sql
-- Wrong: matches order 1 with customer 1
SELECT o.id AS order_id, c.name
FROM orders AS o
JOIN customers AS c ON c.id = o.id
ORDER BY o.id
LIMIT 2;
```

</CodeExample>

Order 1 belongs to Sofia Rossi, not Mei Lin! `c.id = o.id` compares an order number with a customer number, which means nothing. The rule: join a **foreign key** to the **primary key** it points at (`o.customer_id = c.id`).

<Callout type="warning" title="Check your joins on a row you know">

Wrong joins return believable-looking rows, so they are easy to miss. After writing a join, look up one row by hand (order 1 → customer 8 → Sofia Rossi) and make sure the joined result agrees.

</Callout>

## How many rows come out?

Joining each order to its **one** customer keeps one row per order. Joining each order to its **many** items gives one row per **item**:

<CodeExample output={` order_rows
------------
         40
(1 row)

 joined_rows
-------------
          40
(1 row)

 item_rows
-----------
        80
(1 row)`}>

```sql
SELECT count(*) AS order_rows FROM orders;

SELECT count(*) AS joined_rows
FROM orders AS o
JOIN customers AS c ON c.id = o.customer_id;

SELECT count(*) AS item_rows
FROM orders AS o
JOIN order_items AS oi ON oi.order_id = o.id;
```

</CodeExample>

It works the other way round too. A customer with three orders appears **three times** when you join customers to orders:

<CodeExample output={`   name    | order_id |  status
-----------+----------+-----------
 Sam Ortiz |        5 | delivered
 Sam Ortiz |       22 | shipped
 Sam Ortiz |       39 | cancelled
(3 rows)`}>

```sql
SELECT c.name, o.id AS order_id, o.status
FROM customers AS c
JOIN orders AS o ON o.customer_id = c.id
WHERE c.name = 'Sam Ortiz'
ORDER BY o.id;
```

</CodeExample>

This isn't a bug: it's what a join means. But keep it in mind before you `sum()` something, because a value repeated three times gets added three times.

## Joining and grouping

Joins and `GROUP BY` work together. The join brings the columns together, then grouping summarises them. How many orders came from each country?

<CodeExample output={` country | orders
---------+--------
 UK      |      6
 Japan   |      4
 Russia  |      4
 Brazil  |      3
 France  |      3
(5 rows)`}>

```sql
SELECT c.country, count(*) AS orders
FROM orders AS o
JOIN customers AS c ON c.id = o.customer_id
GROUP BY c.country
ORDER BY orders DESC, c.country
LIMIT 5;
```

</CodeExample>

The same works for any pair of linked tables. Here are the lines of order 5, with each product's name from `products` and a calculated line total:

<CodeExample output={`     name      | quantity | unit_price | line_total
---------------+----------+------------+------------
 Clean Python  |        2 |      24.99 |      49.98
 Panda Cookies |        1 |       3.75 |       3.75
 Tea Pot       |        3 |      32.00 |      96.00
(3 rows)`}>

```sql
SELECT p.name,
  oi.quantity,
  oi.unit_price,
  oi.quantity * oi.unit_price AS line_total
FROM order_items AS oi
JOIN products AS p ON p.id = oi.product_id
WHERE oi.order_id = 5
ORDER BY p.name;
```

</CodeExample>

<Callout type="note" title="JOIN, INNER JOIN and USING">

`JOIN` is short for `INNER JOIN`: both mean the same thing. "Inner" means only rows **with a match on both sides** come out. When the two columns have the **same name** in both tables, `USING` is a shortcut: `JOIN b USING (account_id)` means `ON b.account_id = a.account_id`. Our sample tables name their keys `id` and `customer_id`, so they need `ON`.

</Callout>

The shop wants to know its **best sellers**. Each row of `order_items` says how many units (`quantity`) of a product were in an order. Join it to `products` and show the **top 5 products by units sold**:

- `units_sold`: the total `quantity` across all orders.

Sort by `units_sold`, **highest first**. Several products tie, so sort ties by `name`. The top row should be *Algorithms in Pictures* with 17 units.

<Hint>

Join `order_items AS oi` to `products AS p` on `p.id = oi.product_id`. Then `GROUP BY p.name, p.category`, select `sum(oi.quantity) AS units_sold`, and finish with `ORDER BY units_sold DESC, p.name LIMIT 5`.

```sql
LIMIT 5;
```

## Recap

- Data is split into tables so each fact is stored **once**; a **foreign key** (`orders.customer_id`) points at a **primary key** (`customers.id`).
- `FROM a JOIN b ON …` keeps the pairs of rows where the `ON` condition is true. `JOIN` and `INNER JOIN` are the same.
- Give tables **aliases** (`FROM orders AS o`) and prefix columns with them; a column that exists in both tables must be prefixed.
- Join a foreign key to the primary key it points at; a wrong `ON` gives wrong answers **without an error**.
- Joining to the "many" side gives **one row per match**, so rows can repeat.
- `WHERE`, `GROUP BY` and `ORDER BY` work on the joined rows, with columns from every table.

Inner joins drop rows that have no match, like customers who have never ordered. In the next lesson, [outer joins](/learn/sql/outer-joins) keep them.
