Joins aren't limited to two different tables. A table can be joined to **itself**, which is how you answer "who is this employee's manager?". And a query can chain **as many joins as it needs**, walking from customers to orders to order items to products. In this lesson you'll do both, and meet the join that pairs *everything* with everything: `CROSS JOIN`. 🧩

## A table that points at itself

In the `employees` table, `manager_id` is a foreign key, but it doesn't point at another table. It points at **another row of the same table**:

<CodeExample output={` id |     name     | manager_id
----+--------------+------------
  1 | Grace Hopper |       NULL
  8 | Don Norman   |          1
  9 | Susan Kare   |          8
 10 | Dieter Rams  |          8
(4 rows)`}>

```sql
SELECT id, name, manager_id
FROM employees
WHERE department_id = 2 OR id = 1
ORDER BY id;
```

</CodeExample>

Susan Kare's manager is employee 8, Don Norman, whose manager is employee 1, Grace Hopper. Grace is the CEO, so her `manager_id` is `NULL`: she has no manager.

```text
Grace Hopper (1)
└── Don Norman (8)
    ├── Susan Kare (9)
    └── Dieter Rams (10)
```

## Joining a table to itself

To show each employee next to their manager's **name**, use `employees` twice, with **two different aliases**. Think of them as two copies of the same list: `e` for the employees, `m` for the managers:

<CodeExample output={`  employee   |   manager
-------------+--------------
 Don Norman  | Grace Hopper
 Susan Kare  | Don Norman
 Dieter Rams | Don Norman
(3 rows)`}>

```sql
SELECT e.name AS employee, m.name AS manager
FROM employees AS e
JOIN employees AS m ON m.id = e.manager_id
WHERE e.department_id = 2
ORDER BY e.id;
```

</CodeExample>

This is an ordinary join: the foreign key (`e.manager_id`) meets the primary key it points at (`m.id`). The aliases are what make it possible. Without them, `employees.name` would be ambiguous, because the table appears twice. Name the aliases after their **role** (`e` and `m`, or `emp` and `boss`), and the query explains itself.

## Keeping the boss

An inner self join drops Grace Hopper, because her `manager_id` is NULL and matches nobody. You already know the fix: a `LEFT JOIN`. `coalesce()` then replaces the missing name with a friendlier label:

<CodeExample output={`   employee   |   manager
--------------+--------------
 Grace Hopper | (nobody)
 Alan Turing  | Grace Hopper
 Ada Lovelace | Alan Turing
 Linus Park   | Ada Lovelace
(4 rows)`}>

```sql
SELECT e.name AS employee,
  coalesce(m.name, '(nobody)') AS manager
FROM employees AS e
LEFT JOIN employees AS m ON m.id = e.manager_id
WHERE e.id <= 4
ORDER BY e.id;
```

</CodeExample>

## Counting direct reports

Group by the **manager** side to count how many people report to each manager:

<CodeExample output={`   manager    | direct_reports
--------------+----------------
 Grace Hopper |              5
 Ada Lovelace |              3
 Mary Kay     |              3
 Alan Turing  |              2
 Don Norman   |              2
 Hana Sato    |              2
 Marie Curie  |              2
(7 rows)`}>

```sql
SELECT m.name AS manager, count(*) AS direct_reports
FROM employees AS e
JOIN employees AS m ON m.id = e.manager_id
GROUP BY m.id, m.name
ORDER BY direct_reports DESC, m.name;
```

</CodeExample>

Each joined row is one "employee → manager" link, so counting rows per manager counts their direct reports. People who manage nobody have no links and don't appear (a `LEFT JOIN` from the manager side would list them with 0). Walking the *whole* tree, managers of managers and so on, needs a **recursive** query, which you'll meet in Level 2.

## Pairs within one table

Self joins also find **pairs**. The Design team wants to pair everyone up for code reviews. Joining employees to employees in the same department gives every combination, but too many of them:

<CodeExample output={`    first    |   second
-------------+-------------
 Don Norman  | Don Norman
 Don Norman  | Susan Kare
 Don Norman  | Dieter Rams
 Susan Kare  | Don Norman
 Susan Kare  | Susan Kare
 Susan Kare  | Dieter Rams
 Dieter Rams | Don Norman
 Dieter Rams | Susan Kare
 Dieter Rams | Dieter Rams
(9 rows)

   first    |   second
------------+-------------
 Don Norman | Susan Kare
 Don Norman | Dieter Rams
 Susan Kare | Dieter Rams
(3 rows)`}>

```sql
-- Every combination, including people paired with themselves
SELECT a.name AS first, b.name AS second
FROM employees AS a
JOIN employees AS b ON b.department_id = a.department_id
WHERE a.department_id = 2
ORDER BY a.id, b.id;

-- Each pair once: a.id < b.id
SELECT a.name AS first, b.name AS second
FROM employees AS a
JOIN employees AS b
  ON b.department_id = a.department_id AND a.id < b.id
WHERE a.department_id = 2
ORDER BY a.id, b.id;
```

</CodeExample>

The first query pairs everyone with themselves (Don with Don) and lists each pair twice (Don–Susan and Susan–Don). Adding `a.id < b.id` to the `ON` keeps only the version where the first person has the smaller id: each pair once, nobody with themselves.

## Joining three or more tables

Each `JOIN` adds one more table to the rows you have so far, so you can keep chaining. To see what Mei Lin bought, walk the keys from customer to product:

```text
customers ──► orders ──► order_items ──► products
   c.id = o.customer_id
              o.id = oi.order_id
                         oi.product_id = p.id
```

<CodeExample output={` order_id |    product    | quantity
----------+---------------+----------
       17 | Bamboo Crisps |        3
       17 | Rice Cooker   |        2
       17 | Wooden Puzzle |        1
       34 | Matcha Powder |        3
       34 | Rice Crackers |        1
(5 rows)`}>

```sql
SELECT o.id AS order_id, p.name AS product, oi.quantity
FROM customers AS c
JOIN orders AS o ON o.customer_id = c.id
JOIN order_items AS oi ON oi.order_id = o.id
JOIN products AS p ON p.id = oi.product_id
WHERE c.name = 'Mei Lin'
ORDER BY o.id, product;
```

</CodeExample>

Each `ON` links the new table to one that's **already** in the query. Four tables need three join conditions; forget one and the result explodes, as you'll see below.

The same chain answers business questions. Who are the shop's best customers, counting only orders that weren't cancelled?

<CodeExample output={`    name     | orders | spent
-------------+--------+--------
 Ravi Patel  |      3 | 282.23
 Sam Ortiz   |      2 | 273.83
 Sofia Rossi |      3 | 260.13
 Diego López |      2 | 258.17
 Kenji Mori  |      2 | 207.67
(5 rows)`}>

```sql
SELECT c.name,
  count(DISTINCT o.id) AS orders,
  sum(oi.quantity * oi.unit_price) AS spent
FROM customers AS c
JOIN orders AS o ON o.customer_id = c.id
JOIN order_items AS oi ON oi.order_id = o.id
WHERE o.status <> 'cancelled'
GROUP BY c.id, c.name
ORDER BY spent DESC, c.name
LIMIT 5;
```

</CodeExample>

Look at `count(DISTINCT o.id)`. After joining to `order_items`, each order appears **once per item**, so a plain `count(o.id)` would count items, not orders. `DISTINCT` counts each order once. Whenever you join to a "many" table, ask yourself what one row now means.

Different join types mix freely in one chain. Here each recent hire is shown with their department and their manager, using the `employees` table twice and `departments` once:

<CodeExample output={`  employee   | department |  manager
-------------+------------+------------
 Dieter Rams | Design     | Don Norman
 Aiko Suzuki | Support    | Hana Sato
 Paul Allen  | Sales      | Mary Kay
(3 rows)`}>

```sql
SELECT e.name AS employee,
  d.name AS department,
  m.name AS manager
FROM employees AS e
JOIN departments AS d ON d.id = e.department_id
JOIN employees AS m ON m.id = e.manager_id
WHERE e.hired_on >= '2023-01-01'
ORDER BY e.hired_on;
```

</CodeExample>

These three all have a department and a manager, so inner joins are fine here. If some might not, make those joins `LEFT JOIN`s.

## CROSS JOIN: every combination

`CROSS JOIN` has no `ON` at all: it pairs **every** row of one table with **every** row of the other. That's occasionally exactly what you want. The London office plans three weeks of team lunches, one per department per week. `generate_series(1, 3)` is a built-in function that produces the numbers 1, 2 and 3 as rows:

<CodeExample output={` department  | week
-------------+------
 Design      |    1
 Engineering |    1
 Design      |    2
 Engineering |    2
 Design      |    3
 Engineering |    3
(6 rows)`}>

```sql
SELECT d.name AS department, week
FROM departments AS d
CROSS JOIN generate_series(1, 3) AS week
WHERE d.location = 'London'
ORDER BY week, department;
```

</CodeExample>

2 departments × 3 weeks = 6 rows. Typical uses are building grids: every product in every size, every shop on every day of the month (so days with no sales still show up), every pair of teams in a tournament.

<Callout type="danger" title="The accidental cross join">

Row counts **multiply**: 40 orders × 20 customers = 800 rows, and 100,000 × 100,000 is ten billion. You'll see this by accident in older code that lists tables with commas: `FROM orders, customers` without a matching condition in `WHERE` is a cross join. If a query suddenly returns far too many rows (or never finishes), check that every joined table has its `ON` condition.

</Callout>

The London office needs a **team directory**. List every employee whose **department is located in London**, with:

- `employee`: their name,
- `department`: their department's name,
- `manager`: their manager's name.

Sort by `department`, then by `employee`. Today that's 9 people in Design and Engineering. Some managers work outside London (Alan Turing reports to Grace Hopper, who has no department), and a new hire might not have a manager yet: they must **still appear**, with a NULL manager.

<Hint>

You need `employees` twice (the employee `e` and the manager `m`) and `departments` once (`d`). Join `d` on `d.id = e.department_id` and filter with `WHERE d.location = 'London'`. For the manager, use `LEFT JOIN employees AS m ON m.id = e.manager_id`, so people without a manager are kept.

</Hint>

<Solution>

```sql
SELECT e.name AS employee,
  d.name AS department,
  m.name AS manager
FROM employees AS e
JOIN departments AS d ON d.id = e.department_id
LEFT JOIN employees AS m ON m.id = e.manager_id
WHERE d.location = 'London'
ORDER BY department, employee;
```

</Solution>

## Recap

- A **self join** uses one table twice with two aliases: `FROM employees AS e JOIN employees AS m ON m.id = e.manager_id`.
- Use a `LEFT` self join to keep rows whose link is NULL (like the CEO), and `coalesce()` for a friendly label.
- `a.id < b.id` in a self join lists each **pair once** and never pairs a row with itself.
- Chain joins one table at a time, each `ON` linking the new table to one already in the query; mix `JOIN` and `LEFT JOIN` as needed.
- Joining to a "many" table repeats rows: use `count(DISTINCT …)` when you count the "one" side.
- `CROSS JOIN` pairs every row with every row. Useful for grids; dangerous by accident.
