An inner join only keeps rows that have a partner on **both** sides. Usually that's what you want, but sometimes the rows *without* a partner are the whole point: customers who have never ordered, products nobody bought, employees without a department. **Outer joins** keep those rows, and they're how you answer "what's missing?" questions. 🔍

## The customers an inner join forgets

The shop has 20 customers. How many of them show up when we join customers to orders?

<CodeExample output={` customers_in_join
-------------------
                17
(1 row)

 all_customers
---------------
            20
(1 row)`}>

```sql
SELECT count(DISTINCT c.id) AS customers_in_join
FROM customers AS c
JOIN orders AS o ON o.customer_id = c.id;

SELECT count(*) AS all_customers FROM customers;
```

</CodeExample>

Three customers have no orders, so no pair matches them and the inner join silently drops them. A report of "orders per customer" built on this join would simply leave them out, and nobody would notice.

## LEFT JOIN keeps every row on the left

`LEFT JOIN` keeps **every row of the left table** (the one in `FROM`). Rows with a match are joined as usual; rows without one get **NULL** in all of the right table's columns:

<CodeExample output={`    name     | order_id |  status
-------------+----------+-----------
 Emma Wilson |        7 | shipped
 Emma Wilson |       24 | cancelled
 Ivan Petrov |       12 | shipped
 Ivan Petrov |       29 | cancelled
 Grace Kim   |     NULL | NULL
 Tom Baker   |     NULL | NULL
 Nina Novak  |     NULL | NULL
(7 rows)`}>

```sql
SELECT c.name, o.id AS order_id, o.status
FROM customers AS c
LEFT JOIN orders AS o ON o.customer_id = c.id
WHERE c.id >= 16
ORDER BY c.id, o.id;
```

</CodeExample>

Grace, Tom and Nina are still here, each once, with `NULL` where the order would be. The word **outer** is optional: `LEFT JOIN` and `LEFT OUTER JOIN` mean the same.

<Callout type="tip" title="Which table is on the left?">

"Left" simply means the table written **before** `LEFT JOIN`. Put the table whose rows you must keep all of (here: every customer) in `FROM`, and the optional one after `LEFT JOIN`.

</Callout>

## Counting with a LEFT JOIN

Now let's count orders per customer, including zero. There's a trap:

<CodeExample output={`    name     | wrong_count | orders
-------------+-------------+--------
 Emma Wilson |           2 |      2
 Ivan Petrov |           2 |      2
 Grace Kim   |           1 |      0
 Tom Baker   |           1 |      0
 Nina Novak  |           1 |      0
(5 rows)`}>

```sql
SELECT c.name,
  count(*) AS wrong_count,
  count(o.id) AS orders
FROM customers AS c
LEFT JOIN orders AS o ON o.customer_id = c.id
WHERE c.id >= 16
GROUP BY c.id, c.name
ORDER BY c.id;
```

</CodeExample>

Grace Kim has **no** orders, yet `count(*)` says 1. That's because `count(*)` counts **rows**, and the left join gave her one row (full of NULLs). `count(o.id)` counts only non-NULL order ids, so it correctly says 0. With outer joins, always count a column from the optional side.

We grouped by `c.id` *and* `c.name`: two customers could share a name, but never an id.

## Finding missing rows: the anti-join

Which customers have **never** ordered? Left join, then keep only the rows where the right side is missing:

<CodeExample output={`    name    | joined_on
------------+------------
 Grace Kim  | 2024-11-23
 Nina Novak | 2025-01-05
 Tom Baker  | 2024-12-12
(3 rows)`}>

```sql
SELECT c.name, c.joined_on
FROM customers AS c
LEFT JOIN orders AS o ON o.customer_id = c.id
WHERE o.id IS NULL
ORDER BY c.name;
```

</CodeExample>

This pattern is called an **anti-join**: "rows of A with no partner in B". Test a column that can never be NULL in a real match, like the right table's primary key (`o.id`). Remember to write `IS NULL`: `o.id = NULL` is never true, so it would return nothing.

## ON or WHERE? It matters

Say we want **every UK customer** with their number of **cancelled** orders. Where should `o.status = 'cancelled'` go?

<CodeExample output={`   name    | cancelled
-----------+-----------
 Mei Lin   |         1
 Zara Khan |         1
(2 rows)

    name    | cancelled
------------+-----------
 Ada Brooks |         0
 Mei Lin    |         1
 Tom Baker  |         0
 Zara Khan  |         1
(4 rows)`}>

```sql
-- Condition in WHERE: customers without a cancelled order vanish
SELECT c.name, count(o.id) AS cancelled
FROM customers AS c
LEFT JOIN orders AS o ON o.customer_id = c.id
WHERE c.country = 'UK' AND o.status = 'cancelled'
GROUP BY c.id, c.name
ORDER BY c.name;

-- Condition in ON: every UK customer stays
SELECT c.name, count(o.id) AS cancelled
FROM customers AS c
LEFT JOIN orders AS o
  ON o.customer_id = c.id AND o.status = 'cancelled'
WHERE c.country = 'UK'
GROUP BY c.id, c.name
ORDER BY c.name;
```

</CodeExample>

The order of events explains it:

1. The join runs first. `ON` decides **which orders count as a match**; customers without a match are kept, with NULLs.
2. Then `WHERE` filters the joined rows. For Tom Baker, `o.status` is NULL, and `NULL = 'cancelled'` isn't true, so `WHERE` throws him out, undoing the whole point of the left join.

<Callout type="warning" title="The rule of thumb">

With a `LEFT JOIN`, conditions on the **right** (optional) table go in `ON`. Conditions on the **left** table, the one you keep, go in `WHERE`. A condition on the right table in `WHERE` quietly turns your left join back into an inner join.

</Callout>

## RIGHT JOIN

`RIGHT JOIN` is the mirror image: it keeps every row of the table **after** `RIGHT JOIN`. This query keeps every customer, even though `customers` comes second:

<CodeExample output={`    name     | order_id
-------------+----------
 Ivan Petrov |       12
 Ivan Petrov |       29
 Grace Kim   |     NULL
 Tom Baker   |     NULL
 Nina Novak  |     NULL
(5 rows)`}>

```sql
SELECT c.name, o.id AS order_id
FROM orders AS o
RIGHT JOIN customers AS c ON c.id = o.customer_id
WHERE c.id >= 17
ORDER BY c.id, o.id;
```

</CodeExample>

It returns exactly the same rows as `FROM customers AS c LEFT JOIN orders AS o ON …`. In practice most people always write `LEFT JOIN` and put the "keep everything" table first, because it reads naturally from top to bottom. You'll still meet `RIGHT JOIN` in other people's code, so it's good to recognise.

## FULL JOIN keeps both sides

`FULL JOIN` (or `FULL OUTER JOIN`) keeps unmatched rows from **both** tables. It's handy for comparing two lists. Our CEO, Grace Hopper, has no department. Let's also open a new Legal department in Paris that has no employees yet. (`INSERT` adds a row; it gets its own lesson later in Level 1. Like every change here, it's gone on the next run.)

<CodeExample output={`INSERT 0 1

   employee   | department
--------------+------------
 Grace Hopper | NULL
 NULL         | Legal
(2 rows)`}>

```sql
INSERT INTO departments (name, location) VALUES ('Legal', 'Paris');

SELECT e.name AS employee, d.name AS department
FROM employees AS e
FULL JOIN departments AS d ON d.id = e.department_id
WHERE e.id IS NULL OR d.id IS NULL
ORDER BY employee, department;
```

</CodeExample>

Without the `WHERE`, you'd get all 20 employees with their departments, plus the empty Legal department. With it, you see only the loose ends on **either** side: an employee without a department and a department without employees. That's a quick consistency check between two tables.

| Join         | Keeps rows without a match from… |
| ------------ | -------------------------------- |
| `JOIN`       | neither table                    |
| `LEFT JOIN`  | the left table                   |
| `RIGHT JOIN` | the right table                  |
| `FULL JOIN`  | both tables                      |

## Recap

- `LEFT JOIN` keeps every row of the left table; missing right-hand columns become **NULL**. `RIGHT JOIN` mirrors it, and `FULL JOIN` keeps unmatched rows from both sides.
- Count with a column from the optional side (`count(o.id)`), not `count(*)`, so "no match" counts as 0.
- **Anti-join**: `LEFT JOIN … WHERE right.id IS NULL` finds rows with no partner.
- Conditions on the optional table go in `ON`; in `WHERE` they turn the left join back into an inner join.
- Most people write `LEFT JOIN` with the "keep everything" table first, rather than `RIGHT JOIN`.
