Эту историю пережил почти каждый бэкенд-разработчик. На ноутбуке, где в таблице 200 строк, запрос выполняется за 3 мс. Его выкатывают в продакшен. Через полгода в таблице 20 миллионов строк, тот же запрос идёт 9 секунд, и вместе с ним тормозит весь сайт. В SQL ничего не поменялось — выросло только количество данных. 🐢

SQL — **декларативный (declarative)** язык: вы описываете, **что** хотите получить, а PostgreSQL решает, **как** это сделать. Это прекрасно, пока всё не начинает тормозить, — и тогда нужно увидеть это самое «как». Этот модуль посвящён ускорению запросов, и начинается он с самого важного инструмента — **`EXPLAIN`**.

## Как PostgreSQL выполняет запрос

Каждый запрос (query) проходит три этапа:

1. **Парсер (parser)** проверяет SQL и выясняет, о каких таблицах и столбцах идёт речь.
2. **Планировщик (planner)**, его ещё называют оптимизатором (optimiser), перебирает множество способов выполнить запрос: прочитать всю таблицу или воспользоваться индексом? С какой таблицы начать соединение? Хеширование или сортировка? Он **оценивает стоимость (cost)** каждого плана по статистике о ваших данных и выбирает самый дешёвый.
3. **Исполнитель (executor)** выполняет этот план и выдаёт строки.

`EXPLAIN` перед запросом останавливается после второго этапа и показывает план, выбранный планировщиком, не выполняя сам запрос:

<CodeExample output={`                        QUERY PLAN
----------------------------------------------------------
 Seq Scan on products  (cost=0.00..18.88 rows=4 width=86)
   Filter: (category = 'tea'::text)
(2 rows)`}>

```sql
EXPLAIN
SELECT *
FROM products
WHERE category = 'tea';
```

</CodeExample>

В этом плане один шаг, который называется **узлом (node)**: **Seq Scan on products** — **последовательное сканирование (sequential scan)**, которое читает все строки таблицы одну за другой и оставляет те, что проходят **Filter**. Числа в скобках — **оценки (estimates)** планировщика:

- **`cost=0.00..18.88`**: стоимость запуска (до выдачи первой строки) и полная стоимость (всех строк). Стоимость измеряется в условных единицах, примерно «чтение одной страницы с диска = 1». Она полезна только для сравнения планов между собой, а не как миллисекунды.
- **`rows=4`**: сколько строк, по **ожиданиям** планировщика, вернёт этот узел. (На самом деле — 3: это догадка, сделанная без статистики по только что созданной таблице.)
- **`width=86`**: ожидаемый средний размер строки в байтах.

Стоимость зависит от размера таблицы и статистики, поэтому она меняется вместе с данными. Дальше в этом модуле мы будем писать **`EXPLAIN (COSTS OFF)`** — так виден только сам план, без чисел.

## Таблица, размер которой имеет значение

Учебные таблицы крошечные, а для крошечной таблицы прочитать всё целиком — **действительно** лучший план. Чтобы увидеть настоящие решения планировщика, нужен настоящий объём. `generate_series` создаёт таблицу на 100 000 строк за доли секунды:

<CodeExample output={`CREATE TABLE AS

ANALYZE

        QUERY PLAN
--------------------------
 Seq Scan on events
   Filter: (user_id = 42)
(2 rows)`}>

```sql
CREATE TABLE events AS
SELECT g AS id,
  g % 2500 AS user_id,
  (ARRAY['view', 'click', 'buy'])[g % 3 + 1] AS kind,
  timestamp '2025-01-01' + g * interval '1 minute' AS created_at
FROM generate_series(1, 100000) AS g;

ANALYZE events;

EXPLAIN (COSTS OFF)
SELECT *
FROM events
WHERE user_id = 42;
```

</CodeExample>

Обратите внимание на две вещи:

- **`ANALYZE events`** собирает **статистику (statistics)** о таблице: сколько в ней строк, сколько разных значений в каждом столбце, какие значения встречаются чаще всего и так далее. Оценки планировщика хороши ровно настолько, насколько хороша эта статистика. Обычно PostgreSQL собирает её автоматически в фоне (autovacuum), но сразу после загрузки данных полезно запустить `ANALYZE` самому.
- План — это **Seq Scan**. Чтобы найти 40 событий одного пользователя, PostgreSQL читает все 100 000 строк и отбрасывает остальные. Это и есть тот самый 9-секундный запрос из истории, который только ждёт своего часа.

## EXPLAIN ANALYZE: что произошло на самом деле

`EXPLAIN` показывает план. **`EXPLAIN ANALYZE`** ещё и **выполняет** запрос и добавляет к каждому узлу то, что случилось на самом деле. Настоящий вывод содержит время, которое меняется при каждом запуске, поэтому здесь мы отключаем его с помощью `TIMING OFF` (вместе со стоимостью, итоговой сводкой и счётчиками буферов):

<CodeExample output={`CREATE TABLE AS

ANALYZE

                   QUERY PLAN
------------------------------------------------
 Seq Scan on events (actual rows=40.00 loops=1)
   Filter: (user_id = 42)
   Rows Removed by Filter: 99960
(3 rows)`}>

```sql
CREATE TABLE events AS
SELECT g AS id,
  g % 2500 AS user_id,
  (ARRAY['view', 'click', 'buy'])[g % 3 + 1] AS kind,
  timestamp '2025-01-01' + g * interval '1 minute' AS created_at
FROM generate_series(1, 100000) AS g;

ANALYZE events;

EXPLAIN (ANALYZE, COSTS OFF, TIMING OFF, SUMMARY OFF, BUFFERS OFF)
SELECT *
FROM events
WHERE user_id = 42;
```

</CodeExample>

**`actual rows=40.00`** — сколько строк узел вернул на самом деле, а **`loops=1`** — сколько раз он выполнялся. **`Rows Removed by Filter: 99960`** — главная улика: база данных проделала работу на 100 000 строк, чтобы вернуть 40. Если рядом с маленьким «actual rows» вы видите большое «Rows Removed by Filter», скорее всего, поможет индекс.

<Callout type="danger" title="EXPLAIN ANALYZE действительно выполняет инструкцию">

`EXPLAIN ANALYZE DELETE FROM orders` удалит ваши заказы, а `EXPLAIN ANALYZE` для 10-минутного отчёта займёт 10 минут. Чтобы проанализировать инструкцию, которая меняет данные, оберните её в транзакцию (transaction), которую потом отмените:

```sql
BEGIN;
EXPLAIN ANALYZE DELETE FROM sessions WHERE expires_at < '2025-01-01';
ROLLBACK;
```

</Callout>

## Сканирование по индексу

**Индекс (index)** — это отдельная отсортированная структура данных, которая указывает на строки таблицы. Он похож на предметный указатель в конце книги: вместо того чтобы читать каждую страницу в поисках слова «панда», вы находите его в указателе и сразу открываете страницу 212. Подробно индексы мы разберём в [следующем уроке](/learn/sql/choosing-indexes), а пока давайте добавим один и посмотрим, как изменится план:

<CodeExample output={`CREATE TABLE AS

ANALYZE

CREATE INDEX

CREATE INDEX

                  QUERY PLAN
-----------------------------------------------
 Bitmap Heap Scan on events
   Recheck Cond: (user_id = 42)
   ->  Bitmap Index Scan on events_user_id_idx
         Index Cond: (user_id = 42)
(4 rows)

                QUERY PLAN
------------------------------------------
 Index Scan using events_id_idx on events
   Index Cond: (id = 1234)
(2 rows)`}>

```sql
CREATE TABLE events AS
SELECT g AS id,
  g % 2500 AS user_id,
  (ARRAY['view', 'click', 'buy'])[g % 3 + 1] AS kind,
  timestamp '2025-01-01' + g * interval '1 minute' AS created_at
FROM generate_series(1, 100000) AS g;

ANALYZE events;

CREATE INDEX events_user_id_idx ON events (user_id);
CREATE INDEX events_id_idx ON events (id);

EXPLAIN (COSTS OFF)
SELECT *
FROM events
WHERE user_id = 42;

EXPLAIN (COSTS OFF)
SELECT *
FROM events
WHERE id = 1234;
```

</CodeExample>

Теперь в плане **два уровня**. Строки с отступом, начинающиеся с **`->`**, — это **дочерние узлы (child nodes)**: они поставляют строки узлу над ними. Читайте план **от самого вложенного узла наружу**:

1. **Bitmap Index Scan** ищет `user_id = 42` в индексе и отмечает, на каких страницах таблицы лежат подходящие строки (получается «битовая карта» (bitmap) страниц).
2. **Bitmap Heap Scan** затем читает из таблицы (её называют **кучей**, heap) только эти страницы и перепроверяет условие для каждой строки.

Второй запрос находит одну-единственную строку, поэтому PostgreSQL использует обычный **Index Scan**: найти запись в индексе и сразу перейти к строке. Вот виды сканирования, которые встречаются чаще всего:

| Узел | Что делает | Когда хорош |
| --- | --- | --- |
| **Seq Scan** | Читает всю таблицу | Маленькие таблицы или когда нужна большая часть строк |
| **Index Scan** | Проходит по индексу и достаёт каждую подходящую строку | Несколько строк или строки нужны в порядке индекса |
| **Bitmap Index + Heap Scan** | Сначала собирает подходящие страницы, потом читает их по порядку | От сотен до тысяч строк |
| **Index Only Scan** | Отвечает только по индексу, вообще не заглядывая в таблицу | Все нужные столбцы есть в индексе |

<Callout type="tip" title="Seq Scan — не всегда плохо">

Если запросу нужно 30% таблицы, прочитать её всю по порядку быстрее, чем прыгать через индекс к каждой строке, — и PostgreSQL это знает. То же самое с маленькими таблицами: учебная таблица `products` помещается на одну страницу в 8 КБ, так что Seq Scan для неё — самый дешёвый план из возможных. Беспокоиться стоит о Seq Scan по **большой** таблице, который возвращает **мало** строк.

</Callout>

## Сортировка и ограничение

Планы показывают и остальную работу, которую делает запрос. **Sort** сортирует входные строки, а **Limit** останавливается после первых N строк:

<CodeExample output={`           QUERY PLAN
--------------------------------
 Limit
   ->  Sort
         Sort Key: ordered_at
         ->  Seq Scan on orders
(4 rows)

                      QUERY PLAN
-------------------------------------------------------
 Limit
   ->  Index Scan Backward using orders_pkey on orders
(2 rows)`}>

```sql
EXPLAIN (COSTS OFF)
SELECT *
FROM orders
ORDER BY ordered_at
LIMIT 5;

EXPLAIN (COSTS OFF)
SELECT *
FROM orders
ORDER BY id DESC
LIMIT 5;
```

</CodeExample>

Читаем первый план изнутри: просканировать все заказы, отсортировать их по `ordered_at`, вернуть первые 5. Второй план хитрее. Индекс **уже отсортирован**, поэтому, чтобы получить 5 самых больших id, PostgreSQL читает индекс первичного ключа (primary key) **в обратном порядке** и останавливается после 5 записей — никакого узла Sort. Запомните: индекс может обслуживать не только `WHERE`, но и `ORDER BY`.

## Как планируются соединения

Для каждого соединения (JOIN) планировщик выбирает один из трёх **алгоритмов соединения (join algorithms)**. Чтобы увидеть все три, создадим две таблицы побольше — аккаунты и их платежи:

<CodeExample output={`CREATE TABLE AS

ALTER TABLE

CREATE TABLE AS

ALTER TABLE

ANALYZE

ANALYZE

                     QUERY PLAN
----------------------------------------------------
 Nested Loop
   ->  Index Scan using payments_pkey on payments p
         Index Cond: (id < 10)
   ->  Index Scan using accounts_pkey on accounts a
         Index Cond: (id = p.account_id)
(5 rows)

                QUERY PLAN
------------------------------------------
 HashAggregate
   Group Key: a.country
   ->  Hash Join
         Hash Cond: (p.account_id = a.id)
         ->  Seq Scan on payments p
         ->  Hash
               ->  Seq Scan on accounts a
(7 rows)

                       QUERY PLAN
---------------------------------------------------------
 Merge Join
   Merge Cond: (a.id = p.id)
   ->  Index Only Scan using accounts_pkey on accounts a
   ->  Index Only Scan using payments_pkey on payments p
(4 rows)`}>

```sql
CREATE TABLE accounts AS
SELECT g AS id,
  'user' || g || '@example.com' AS email,
  (ARRAY['UK', 'Spain', 'Japan', 'India', 'Brazil'])[g % 5 + 1]
    AS country
FROM generate_series(1, 20000) AS g;
ALTER TABLE accounts ADD PRIMARY KEY (id);

CREATE TABLE payments AS
SELECT g AS id,
  g % 20000 + 1 AS account_id,
  round((g % 997) / 10.0, 2) AS amount
FROM generate_series(1, 100000) AS g;
ALTER TABLE payments ADD PRIMARY KEY (id);

ANALYZE accounts;
ANALYZE payments;

-- 1. Несколько платежей, каждый со своим аккаунтом
EXPLAIN (COSTS OFF)
SELECT a.email, p.amount
FROM payments AS p
JOIN accounts AS a ON a.id = p.account_id
WHERE p.id < 10;

-- 2. Все платежи, просуммированные по странам
EXPLAIN (COSTS OFF)
SELECT a.country, sum(p.amount) AS total
FROM accounts AS a
JOIN payments AS p ON p.account_id = a.id
GROUP BY a.country;

-- 3. Два больших входа, оба уже отсортированы по ключу соединения
EXPLAIN (COSTS OFF)
SELECT a.id, p.id
FROM accounts AS a
JOIN payments AS p ON p.id = a.id;
```

</CodeExample>

- **Nested Loop** (вложенный цикл): для **каждой** строки внешнего (первого) входа ищет совпадения во внутреннем. Отлично работает, когда внешняя сторона маленькая, а у внутренней есть индекс: 9 платежей — значит, 9 быстрых поисков по первичному ключу. Ужасно — когда обе стороны большие и индекса нет: миллион на миллион.
- **Hash Join** (хеш-соединение): один раз читает меньшую таблицу и строит в памяти **хеш-таблицу (hash table)** по столбцу соединения (узел **Hash**), а затем проходит по большей таблице и ищет каждую её строку в хеш-таблице. Рабочая лошадка для соединения больших наборов по `=`.
- **Merge Join** (соединение слиянием): идёт параллельно по двум входам, **отсортированным по ключу соединения**, — как будто сводит вместе два отсортированных списка. Отлично подходит, когда порядок уже обеспечивают индексы; иначе сначала нужен Sort с каждой стороны.

В первом плане также видно, как работает **`loops`**: с `EXPLAIN ANALYZE` внутренний Index Scan показал бы `loops=9`, потому что он выполнялся один раз на каждую внешнюю строку. Когда читаете `actual rows` у внутреннего узла, умножайте на `loops`, чтобы получить общее число.

У агрегатов тоже есть свои узлы: **HashAggregate** группирует строки в хеш-таблице (как выше), **GroupAggregate** группирует уже отсортированный вход, а обычный **Aggregate** вычисляет один итог, например `count(*)`.

## Оценки и реальность

Планировщик выбирает план по **оценочному** числу строк. Когда оценки сильно расходятся с реальностью, он может выбрать ужасный план — например, Nested Loop, потому что ожидает 1 строку, а на самом деле их 80 000. Вот почему `EXPLAIN ANALYZE` на настоящем сервере так полезен: он печатает оценку и фактическое число рядом. Вот типичная строка с включёнными стоимостью и временем:

```text
Index Scan using orders_customer_id_idx on orders
  (cost=0.43..8.45 rows=1 width=40)
  (actual time=0.031..212.904 rows=81234.00 loops=1)
```

Оценка `rows=1`, на деле `rows=81234`: планировщик ошибся в 80 000 раз. Обычные причины — **устаревшая статистика (stale statistics)** (большой импорт после последнего `ANALYZE`), условия на связанные столбцы, которые планировщик считает независимыми, или условия, которые он не умеет оценивать, например функция, применённая к столбцу. Исправлять всё это вы будете в [уроке о настройке запросов](/learn/sql/query-tuning).

`actual time=0.031..212.904` — в миллисекундах: время до первой строки и время до последней. Чтобы понять, куда уходит время, ищите узел, на котором время резко **скачет** по сравнению с его дочерними узлами.

## На настоящем сервере

Несколько вещей, которые вы увидите в продакшене, но которых не показывает эта база данных в браузере:

- **Параллельные планы**: большой Seq Scan часто выглядит как `Gather` → `Parallel Seq Scan` — несколько рабочих процессов, каждый читает свою часть таблицы.
- **Буферы**: `EXPLAIN (ANALYZE, BUFFERS)` показывает, сколько страниц по 8 КБ пришло из памяти (`shared hit`), а сколько — с диска (`read`). Много чтений с диска — значит, данных не было в кэше.
- **Как вообще найти медленные запросы**: расширение `pg_stat_statements` записывает общее и среднее время каждого запроса, так что можно отсортировать по «суммарно потраченному времени» и исправить несколько верхних. `auto_explain` автоматически записывает в лог планы медленных запросов.

```sql
-- На сервере с включённым pg_stat_statements
SELECT calls, round(mean_exec_time::numeric, 1) AS avg_ms, query
FROM pg_stat_statements
ORDER BY total_exec_time DESC
LIMIT 10;
```

Длинные планы трудно читать как текст. Вставьте их в визуализатор, например **explain.dalibo.com** или **explain.depesz.com**, — они подсвечивают самые медленные узлы.

Каждый раз, когда пользователь открывает свой профиль, приложение выполняет запрос «ленты активности» внизу: 5 его последних просмотров страниц. Сейчас запрос читает все 100 000 строк **и** сортирует найденное.

1. Нажмите **«Запустить»** и прочитайте план изнутри наружу: какие узлы делают работу?
2. Добавьте **один** `CREATE INDEX` так, чтобы в плане **не было ни Seq Scan, ни узла Sort**.
3. Запустите ещё раз и проверьте новый план.

<Hint>

Индекс только по `user_id` избавит от Seq Scan, но подходящие строки всё равно выйдут в неправильном порядке, так что Sort останется. Вспомните, что индекс отсортирован: если его записи упорядочены по `user_id`, **а затем** по `viewed_at`, все просмотры пользователя 1234 лежат рядом и уже по времени. Индекс по нескольким столбцам выглядит так: `CREATE INDEX name ON table (col1, col2);`.

</Hint>

<Solution>

```sql
-- 100 000 просмотров страниц от 5 000 пользователей
CREATE TABLE page_views AS
SELECT g AS id,
  g % 5000 AS user_id,
  '/page/' || g % 50 AS path,
  timestamp '2025-01-01' + g * interval '1 minute' AS viewed_at
FROM generate_series(1, 100000) AS g;
ANALYZE page_views;

-- Сортировка по пользователю, затем по времени: самые новые
-- просмотры пользователя — последние записи в его группе
CREATE INDEX page_views_user_time_idx
  ON page_views (user_id, viewed_at);

-- Лента активности: 5 последних просмотров страниц пользователя
EXPLAIN (COSTS OFF)
SELECT path, viewed_at
FROM page_views
WHERE user_id = 1234
ORDER BY viewed_at DESC
LIMIT 5;
```

</Solution>

</Exercise>

## Итоги

- SQL говорит, **что** нужно; **планировщик** решает, **как**, выбирая самый дешёвый план, какой найдёт, по **статистике** (её собирает `ANALYZE`).
- **`EXPLAIN`** показывает план, не выполняя запрос; **`EXPLAIN ANALYZE`** выполняет запрос и добавляет фактическое число строк, loops и (на настоящем сервере) время. Инструкции, меняющие данные, оборачивайте в `BEGIN` … `ROLLBACK`.
- Читайте планы **от самого вложенного узла наружу**: каждый дочерний узел `->` поставляет строки родителю.
- Сканирования: **Seq Scan** (вся таблица), **Index Scan**, **Bitmap Index/Heap Scan**, **Index Only Scan**. Большое «Rows Removed by Filter» при малом числе фактических строк намекает на недостающий индекс.
- Соединения: **Nested Loop** (маленькая внешняя сторона + индекс у внутренней), **Hash Join** (большие наборы, равенство), **Merge Join** (входы отсортированы по ключу).
- Индексы отсортированы, поэтому могут заменить **Sort** для `ORDER BY … LIMIT`.
- Сравнивайте **оценочное** и **фактическое** число строк: большие расхождения приводят к плохим планам.
