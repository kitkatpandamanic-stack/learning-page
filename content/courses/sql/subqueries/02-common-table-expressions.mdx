In the last lesson you averaged order totals with a subquery in `FROM`. It worked, but the brackets made you read the query **inside out**: the first thing PostgreSQL does is buried in the middle. Add one more step and nobody will want to touch it.

`WITH` fixes that. It lets you give each step a **name** at the top of the query, and then use that name like a table. These named steps are called **common table expressions**, or **CTEs**. They're one of the most useful tools in everyday SQL, because they turn a puzzle into a recipe you can read from top to bottom.

## Your first CTE

Here's the "average order value" query again, rewritten with `WITH`:

<CodeExample output={` orders | average_order
--------+---------------
     40 |         70.23
(1 row)`}>

```sql
WITH order_totals AS (
  SELECT order_id, sum(quantity * unit_price) AS total
  FROM order_items
  GROUP BY order_id
)
SELECT count(*) AS orders, round(avg(total), 2) AS average_order
FROM order_totals;
```

</CodeExample>

The shape is always the same:

```text
WITH step_name AS (
  a query
)
SELECT … FROM step_name …;
```

- `WITH order_totals AS ( … )` runs the inner query and calls its result `order_totals`.
- The main query that follows can use `order_totals` exactly like a table.
- There's **no semicolon** after the closing bracket: the `WITH` part and the main query are one statement.

The result is the same as with the derived table, but now the first step comes first, and it has a name that says what it is.

## Several steps in a row

Separate steps with **commas**. Each step can use the steps above it. This query finds the shop's best customers, skipping cancelled orders:

<CodeExample output={`    name     | orders | spent
-------------+--------+--------
 Ravi Patel  |      3 | 282.23
 Sam Ortiz   |      2 | 273.83
 Sofia Rossi |      3 | 260.13
 Diego López |      2 | 258.17
 Kenji Mori  |      2 | 207.67
(5 rows)`}>

```sql
WITH order_totals AS (
  SELECT o.id, o.customer_id, sum(oi.quantity * oi.unit_price) AS total
  FROM orders AS o
  JOIN order_items AS oi ON oi.order_id = o.id
  WHERE o.status <> 'cancelled'
  GROUP BY o.id
),
customer_spend AS (
  SELECT customer_id, count(*) AS orders, sum(total) AS spent
  FROM order_totals
  GROUP BY customer_id
)
SELECT c.name, cs.orders, cs.spent
FROM customer_spend AS cs
JOIN customers AS c ON c.id = cs.customer_id
ORDER BY cs.spent DESC, c.name
LIMIT 5;
```

</CodeExample>

Read it like a recipe:

1. **order_totals**: work out what each (non-cancelled) order was worth.
2. **customer_spend**: add those up per customer.
3. The main query: put names on the customers and keep the top five.

Each step is a small query you could understand on its own. Try writing the same thing with nested subqueries and you'll see why people love CTEs.

<Callout type="tip" title="Build and debug one step at a time">

When a CTE query gives a strange answer, change the main query to `SELECT * FROM order_totals;` (or whichever step you suspect) and look at what that step really produces. Then move down to the next step. Writing new queries works the same way: get step one right, then add step two.

</Callout>

## Using a step twice

A step can be used more than once. Which orders were worth **more than the average order**? You need the order totals twice: once for the list, once for the average.

<CodeExample output={` order_id | total
----------+--------
        2 | 200.17
       17 | 200.17
       32 | 200.17
        5 | 149.73
       20 | 149.73
       35 | 149.73
(6 rows)`}>

```sql
WITH order_totals AS (
  SELECT order_id, sum(quantity * unit_price) AS total
  FROM order_items
  GROUP BY order_id
)
SELECT order_id, total
FROM order_totals
WHERE total > (SELECT avg(total) FROM order_totals)
ORDER BY total DESC, order_id
LIMIT 6;
```

</CodeExample>

Without a CTE you'd have to write the whole "total each order" query twice and keep both copies in sync. With a CTE it lives in one place.

## Naming the columns

You can list a step's column names right after its name. It's handy when the inner query has expressions you'd otherwise have to alias one by one:

<CodeExample output={` category | products | avg_price
----------+----------+-----------
 kitchen  |        3 |     42.03
 books    |        3 |     22.16
 toys     |        3 |     14.80
(3 rows)`}>

```sql
WITH category_stats (category, products, avg_price) AS (
  SELECT category, count(*), round(avg(price), 2)
  FROM products
  GROUP BY category
)
SELECT category, products, avg_price
FROM category_stats
WHERE avg_price > 10
ORDER BY avg_price DESC;
```

</CodeExample>

## A CTE lives for one statement

A CTE isn't saved anywhere. It exists only for the one statement it belongs to, and after the semicolon it's gone:

<CodeExample output={` cheap_products
----------------
              3
(1 row)

ERROR:  relation "cheap" does not exist
LINE 6: SELECT name FROM cheap;
                         ^`}>

```sql
WITH cheap AS (
  SELECT name, price FROM products WHERE price < 4
)
SELECT count(*) AS cheap_products FROM cheap;

SELECT name FROM cheap;
```

</CodeExample>

If you need the same step in many queries, you'll want a **view**, a saved query with a name, which you'll meet in Level 2.

<Callout type="note" title="Are CTEs slower than subqueries?">

You may read old advice that CTEs are an "optimisation fence" that PostgreSQL computes separately. That was true before PostgreSQL 12. Today a CTE that's used **once** is folded into the main query, so it's planned exactly like the equivalent subquery. A CTE used **more than once** is computed once and reused, which is usually what you want. You can still force either behaviour with `WITH step AS MATERIALIZED ( … )` or `AS NOT MATERIALIZED`, but you'll rarely need to.

</Callout>

## CTEs or subqueries?

They do the same job, so pick the one that reads best:

| Use a subquery when… | Use a CTE when… |
| --- | --- |
| it's short and used once, like `WHERE price > (SELECT avg(price) FROM products)` | the query has two or more steps |
| it's an `EXISTS` / `IN` filter | a step is used more than once |
| | you want to name what each step means |

`WITH` has two more tricks you'll meet later: **recursive** CTEs, which walk trees like the org chart in `employees` (in Level 2), and CTEs that **change data**, which the [INSERT lesson](/learn/sql/insert-rows) shows.

<TryIt language="sql" code={`-- Change the first step, then see how the second one follows.

  SELECT category, sum(price * stock) AS value
  FROM products
  GROUP BY category

ranked AS (
  SELECT category, value
  FROM stock_value
  WHERE value > 300
)
SELECT category, value
FROM ranked
ORDER BY value DESC;`} />

The first step, `dept_pay`, already works out each department's headcount and average salary. Finish the query so it shows **only the departments whose average salary is higher than the company-wide average** (the average over **all** employees, including the CEO, who has no department).

Keep the columns `name, headcount, avg_salary` and the order (highest average first).

<Hint>

Add a second step after a comma: `company AS (SELECT avg(salary) AS avg_salary FROM employees)`. Then in the main query, compare with it, for example with `WHERE dp.avg_salary > (SELECT avg_salary FROM company)`.

</Hint>

<Solution>

```sql
WITH dept_pay AS (
  SELECT
    department_id,
    count(*) AS headcount,
    avg(salary) AS avg_salary
  FROM employees
  WHERE department_id IS NOT NULL
  GROUP BY department_id
),
company AS (
  SELECT avg(salary) AS avg_salary
  FROM employees
)
SELECT d.name, dp.headcount, round(dp.avg_salary) AS avg_salary
FROM dept_pay AS dp
JOIN departments AS d ON d.id = dp.department_id
WHERE dp.avg_salary > (SELECT avg_salary FROM company)
ORDER BY dp.avg_salary DESC;
```

</Solution>

## Recap

- `WITH name AS ( query )` gives a step a name; the main query uses it like a table.
- Chain steps with **commas**; each step can use the ones above it. One semicolon at the very end.
- A step can be used **more than once**, so you never copy the same logic twice.
- `WITH name (col1, col2) AS ( … )` names the step's columns.
- A CTE lasts for **one statement**; for a reusable saved query you'll use a view.
- Since PostgreSQL 12, CTEs perform like the equivalent subqueries, so choose whichever reads best.
