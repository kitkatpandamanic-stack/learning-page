Соединение (JOIN) ставит таблицы **рядом**: оно добавляет столбцы. Иногда нужно обратное: взять строки одного запроса и поставить строки другого запроса **под ними**. Единый список всех, кому можно написать письмо, — покупатели и сотрудники вместе. Единая лента активности из регистраций и заказов. Отчёт со строкой «итого» внизу.

Именно это делают **операции над множествами (set operations)**. Их три, и они работают так же, как множества в математике:

- **UNION**: строки, которые есть в первом результате **или** во втором.
- **INTERSECT**: строки, которые есть в **обоих**.
- **EXCEPT**: строки из первого результата, которых **нет** во втором.

## UNION ALL: два результата друг под другом

Напишите два полных запроса и поставьте между ними `UNION ALL`. Вот список контактов из покупателей в Великобритании и команды Design:

<CodeExample output={`    name     |   kind
-------------+----------
 Ada Brooks  | customer
 Mei Lin     | customer
 Tom Baker   | customer
 Zara Khan   | customer
 Dieter Rams | employee
 Don Norman  | employee
 Susan Kare  | employee
(7 rows)`}>

```sql
SELECT name, 'customer' AS kind
FROM customers
WHERE country = 'UK'
UNION ALL
SELECT name, 'employee'
FROM employees
WHERE department_id = 2
ORDER BY kind, name;
```

</CodeExample>

На что стоит обратить внимание:

- Оба запроса возвращают **одинаковое число столбцов** (два), и соответствующие столбцы имеют **совместимые типы** (текст и текст).
- **Имена столбцов берутся из первого запроса**. Значению `'employee'` во втором запросе псевдоним не понадобился.
- Единственный `ORDER BY` в конце сортирует **весь объединённый результат**, а не только второй запрос.
- Текстовый столбец `kind` — распространённый приём: он помечает, откуда пришла каждая строка.

## UNION убирает дубликаты

Простой `UNION` (без `ALL`) ещё и удаляет повторяющиеся строки из объединённого результата. Сравните города, где есть офисы, с городами покупателей из Великобритании:

<CodeExample output={`    city
------------
 Berlin
 London
 London
 London
 London
 Madrid
 Manchester
 Tokyo
 NULL
(9 rows)

    city
------------
 Berlin
 London
 Madrid
 Manchester
 Tokyo
 NULL
(6 rows)`}>

```sql
SELECT location AS city FROM departments
UNION ALL
SELECT city FROM customers WHERE country = 'UK'
ORDER BY city;

SELECT location AS city FROM departments
UNION
SELECT city FROM customers WHERE country = 'UK'
ORDER BY city;
```

</CodeExample>

С `UNION ALL` вы получаете все 9 строк, London — четыре раза. С `UNION` каждый город появляется один раз. Посмотрите и на `NULL`: у двух британских покупателей город не указан, и `UNION` оставил **один** `NULL`. Операции над множествами считают два `NULL` одинаковыми строками, хотя в `WHERE` условие `NULL = NULL` не истинно.

<Callout type="tip" title="Выбирайте UNION ALL, если удаление дубликатов не нужно">

Чтобы убрать дубликаты, `UNION` приходится сортировать или хешировать весь результат, а на больших данных это стоит времени. Если две части не могут пересекаться или дубликаты настоящие (два заказа в один день — это два заказа!), используйте `UNION ALL`. Берите `UNION`, когда вам действительно нужно «каждое значение по одному разу».

</Callout>

## Правила — и ошибки, если их нарушить

Два запроса должны совпадать столбец в столбец. Разное число столбцов — это ошибка:

<CodeExample output={`ERROR:  each UNION query must have the same number of columns
LINE 3: SELECT name FROM employees;
               ^`}>

```sql
SELECT name, email FROM customers
UNION
SELECT name FROM employees;
```

</CodeExample>

Как и столбцы с несовместимыми типами — например, текст в одном запросе и число в другом:

<CodeExample output={`ERROR:  UNION types text and integer cannot be matched
LINE 3: SELECT salary FROM employees;
               ^`}>

```sql
SELECT name FROM customers
UNION
SELECT salary FROM employees;
```

</CodeExample>

Если вы действительно хотите их смешать, преобразуйте одну сторону: `salary::text`.

У сортировки тоже есть правило. `ORDER BY` после операции над множествами может использовать только **имена выходных столбцов** (или их номера), но не выражения. Чтобы отсортировать по чему-то другому, оберните всё в CTE или производную таблицу и сортируйте снаружи, как в отчёте ниже.

## INTERSECT: строки, которые есть в обоих

В каких городах есть и покупатели, **и** один из наших офисов?

<CodeExample output={`  city
--------
 Berlin
 London
 Madrid
 Tokyo
(4 rows)`}>

```sql
SELECT city FROM customers
INTERSECT
SELECT location FROM departments
ORDER BY city;
```

</CodeExample>

Как и `UNION`, `INTERSECT` возвращает каждую строку один раз. (`INTERSECT ALL` сохраняет дубликаты, но он нужен редко.)

## EXCEPT: строки из первого, которых нет во втором

`EXCEPT` берёт первый результат и удаляет из него все строки, которые есть и во втором. Вот знакомый вопрос «какие покупатели ни разу не заказывали?», решённый третьим способом:

<CodeExample output={` id
----
 18
 19
 20
(3 rows)`}>

```sql
SELECT id FROM customers
EXCEPT
SELECT customer_id FROM orders
ORDER BY id;
```

</CodeExample>

**Порядок важен**: `A EXCEPT B` — это «есть в A, нет в B», и это другой вопрос, чем `B EXCEPT A`. Здесь `SELECT customer_id FROM orders EXCEPT SELECT id FROM customers` не вернул бы ничего, потому что каждый заказ принадлежит реальному покупателю.

А поскольку операции над множествами считают `NULL` равными, у `EXCEPT` нет ловушки `NOT IN` из [урока про подзапросы](/learn/sql/queries-inside-queries). Подвох в другом: `EXCEPT` может вернуть только те столбцы, которые сравнивает. Чтобы показать имена, придётся снова сделать соединение или использовать `NOT EXISTS`.

<Callout type="note" title="Несколько операций в одном запросе">

Их можно объединять в цепочку: `A UNION B EXCEPT C`. `INTERSECT` связывает сильнее, чем `UNION` и `EXCEPT` — примерно как `*` выполняется раньше `+`, — поэтому, смешивая их, ставьте скобки: `(A UNION B) EXCEPT C`. Скобки также позволяют дать одной части собственный `ORDER BY … LIMIT`.

</Callout>

## Отчёт со строкой итога

`UNION ALL` отлично подходит для отчётов. Вот стоимость товарного запаса в каждой категории и общий итог под ними. Дополнительный столбец `sort_key` удерживает итог внизу: внешний запрос сортирует по нему и не включает его в результат:

<CodeExample output={` category | stock_value
----------+-------------
 kitchen  |     1391.60
 snacks   |      827.55
 toys     |      762.60
 tea      |      428.00
 books    |      174.50
 TOTAL    |     3584.25
(6 rows)`}>

```sql
WITH report AS (
  SELECT category, sum(price * stock) AS stock_value, 1 AS sort_key
  FROM products
  GROUP BY category
  UNION ALL
  SELECT 'TOTAL', sum(price * stock), 2
  FROM products
)
SELECT category, stock_value
FROM report
ORDER BY sort_key, stock_value DESC;
```

</CodeExample>

(PostgreSQL умеет добавлять строки итогов и сам — с помощью `GROUP BY ROLLUP (category)`, но вариант с `UNION ALL` работает где угодно, и его легко подправить.)

Соберите единую **ленту активности** за январь 2025 года. Запрос в редакторе уже выводит покупателей, зарегистрировавшихся в этом месяце. Добавьте под ними **заказы, сделанные в январе 2025 года**, чтобы в ленте были:

- `day`: дата регистрации или дата заказа (превратите метку времени `ordered_at` в дату с помощью `::date`)
- `customer`: имя покупателя (в заказах есть только `customer_id`, так что понадобится соединение)
- `event`: `'joined'` или `'ordered'`

Отсортируйте всю ленту по `day`, затем по `customer`. Подумайте, какая операция над множествами подходит: два заказа одного покупателя в один день должны отображаться как **две** строки.

<Hint>

Поставьте `UNION ALL` перед `ORDER BY` и добавьте второй запрос: `SELECT o.ordered_at::date, c.name, 'ordered' FROM orders AS o JOIN customers AS c ON c.id = o.customer_id WHERE …`. Отфильтруйте заказы условием `o.ordered_at >= '2025-01-01' AND o.ordered_at < '2025-02-01'`. Единственный `ORDER BY` в конце отсортирует всё.

</Hint>

<Solution>

```sql
SELECT joined_on AS day, name AS customer, 'joined' AS event
FROM customers
WHERE joined_on >= '2025-01-01' AND joined_on < '2025-02-01'
UNION ALL
SELECT o.ordered_at::date, c.name, 'ordered'
FROM orders AS o
JOIN customers AS c ON c.id = o.customer_id
WHERE o.ordered_at >= '2025-01-01' AND o.ordered_at < '2025-02-01'
ORDER BY day, customer;
```

</Solution>

## Итоги

- Операции над множествами ставят строки двух запросов друг под другом; соединения ставят столбцы рядом.
- `UNION ALL` сохраняет все строки; `UNION` удаляет дубликаты (и обходится дороже).
- `INTERSECT` оставляет строки, найденные в обоих результатах; `EXCEPT` оставляет строки первого, которых нет во втором, и порядок здесь важен.
- В обоих запросах должно быть **одинаковое число столбцов** с **совместимыми типами**; имена берутся из **первого** запроса.
- Один `ORDER BY` в конце сортирует весь результат по именам выходных столбцов.
- Операции над множествами считают `NULL` равными, поэтому у `EXCEPT` нет ловушки `NOT IN`.
- Столбец-метка вроде `'customer' AS kind` и строка итога через `UNION ALL` — удобные приёмы для отчётов.
