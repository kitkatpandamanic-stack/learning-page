A join puts tables **side by side**: it adds columns. Sometimes you want the opposite: take the rows of one query and put the rows of another query **underneath**. One list of everyone you could email, customers and staff together. One activity feed of sign-ups and orders. A report with a "total" row at the bottom.

That's what **set operations** do. There are three of them, and they work just like sets in maths:

- **UNION**: rows that are in the first result **or** the second.
- **INTERSECT**: rows that are in **both**.
- **EXCEPT**: rows in the first result but **not** in the second.

## UNION ALL: stacking two results

Write two complete queries and put `UNION ALL` between them. Here's a contact list of UK customers and the Design team:

<CodeExample output={`    name     |   kind
-------------+----------
 Ada Brooks  | customer
 Mei Lin     | customer
 Tom Baker   | customer
 Zara Khan   | customer
 Dieter Rams | employee
 Don Norman  | employee
 Susan Kare  | employee
(7 rows)`}>

```sql
SELECT name, 'customer' AS kind
FROM customers
WHERE country = 'UK'
UNION ALL
SELECT name, 'employee'
FROM employees
WHERE department_id = 2
ORDER BY kind, name;
```

</CodeExample>

A few things to notice:

- Both queries return **the same number of columns** (two), and the matching columns have **compatible types** (text and text).
- The column **names come from the first query**. The second query's `'employee'` didn't need an alias.
- The single `ORDER BY` at the end sorts the **whole combined result**, not just the second query.
- The text column `kind` is a common trick: it labels where each row came from.

## UNION removes duplicates

Plain `UNION` (without `ALL`) also removes duplicate rows from the combined result. Compare the cities with an office with the cities of UK customers:

<CodeExample output={`    city
------------
 Berlin
 London
 London
 London
 London
 Madrid
 Manchester
 Tokyo
 NULL
(9 rows)

    city
------------
 Berlin
 London
 Madrid
 Manchester
 Tokyo
 NULL
(6 rows)`}>

```sql
SELECT location AS city FROM departments
UNION ALL
SELECT city FROM customers WHERE country = 'UK'
ORDER BY city;

SELECT location AS city FROM departments
UNION
SELECT city FROM customers WHERE country = 'UK'
ORDER BY city;
```

</CodeExample>

With `UNION ALL` you get all 9 rows, London four times. With `UNION` every city appears once. Look at the `NULL` too: two UK customers have no city, and `UNION` kept **one** `NULL`. Set operations treat two `NULL`s as the same row, even though `NULL = NULL` isn't true in a `WHERE` clause.

<Callout type="tip" title="Prefer UNION ALL unless you need the de-duplication">

To remove duplicates, `UNION` has to sort or hash the whole result, which costs time on big data. If the two parts can't overlap, or duplicates are real (two orders on the same day are two orders!), use `UNION ALL`. Reach for `UNION` when "each value once" is really what you want.

</Callout>

## The rules, and the errors when you break them

The two queries must line up column by column. A different number of columns is an error:

<CodeExample output={`ERROR:  each UNION query must have the same number of columns
LINE 3: SELECT name FROM employees;
               ^`}>

```sql
SELECT name, email FROM customers
UNION
SELECT name FROM employees;
```

</CodeExample>

So are columns whose types don't match, like text in one query and a number in the other:

<CodeExample output={`ERROR:  UNION types text and integer cannot be matched
LINE 3: SELECT salary FROM employees;
               ^`}>

```sql
SELECT name FROM customers
UNION
SELECT salary FROM employees;
```

</CodeExample>

If you really want to mix them, convert one side: `salary::text`.

Sorting has a rule too. `ORDER BY` after a set operation can only use the **output column names** (or positions), not expressions. To sort by something else, wrap the whole thing in a CTE or derived table and sort outside, as the report below does.

## INTERSECT: rows in both

Which cities have both customers **and** one of our offices?

<CodeExample output={`  city
--------
 Berlin
 London
 Madrid
 Tokyo
(4 rows)`}>

```sql
SELECT city FROM customers
INTERSECT
SELECT location FROM departments
ORDER BY city;
```

</CodeExample>

Like `UNION`, `INTERSECT` returns each row once. (`INTERSECT ALL` keeps duplicates, but you'll rarely need it.)

## EXCEPT: rows in the first but not the second

`EXCEPT` takes the first result and removes every row that also appears in the second. Here's a familiar question, "which customers have never ordered?", answered a third way:

<CodeExample output={` id
----
 18
 19
 20
(3 rows)`}>

```sql
SELECT id FROM customers
EXCEPT
SELECT customer_id FROM orders
ORDER BY id;
```

</CodeExample>

The **order matters**: `A EXCEPT B` is "in A, not in B", which is a different question from `B EXCEPT A`. Here, `SELECT customer_id FROM orders EXCEPT SELECT id FROM customers` would return nothing, because every order belongs to a real customer.

And because set operations treat `NULL`s as equal, `EXCEPT` doesn't have the `NOT IN` trap from [the subqueries lesson](/learn/sql/queries-inside-queries). The catch is that `EXCEPT` can only return the columns you compare. To show names you'd join back, or use `NOT EXISTS`.

<Callout type="note" title="Several operations in one query">

You can chain them: `A UNION B EXCEPT C`. `INTERSECT` binds tighter than `UNION` and `EXCEPT`, a bit like `*` before `+`, so add brackets whenever you mix them: `(A UNION B) EXCEPT C`. Brackets also let you give one part its own `ORDER BY … LIMIT`.

</Callout>

## A report with a total row

`UNION ALL` is great for reports. Here's the value of the stock in each category, with a grand total underneath. The extra `sort_key` column keeps the total at the bottom; the outer query sorts by it and leaves it out of the result:

<CodeExample output={` category | stock_value
----------+-------------
 kitchen  |     1391.60
 snacks   |      827.55
 toys     |      762.60
 tea      |      428.00
 books    |      174.50
 TOTAL    |     3584.25
(6 rows)`}>

```sql
WITH report AS (
  SELECT category, sum(price * stock) AS stock_value, 1 AS sort_key
  FROM products
  GROUP BY category
  UNION ALL
  SELECT 'TOTAL', sum(price * stock), 2
  FROM products
)
SELECT category, stock_value
FROM report
ORDER BY sort_key, stock_value DESC;
```

</CodeExample>

(PostgreSQL can also add total rows for you with `GROUP BY ROLLUP (category)`, but the `UNION ALL` version works anywhere and is easy to tweak.)

Build a single **activity feed** for January 2025. The query in the editor already lists the customers who joined that month. Add the **orders placed in January 2025** underneath, so the feed has:

- `day`: the sign-up date, or the order's date (turn the `ordered_at` timestamp into a date with `::date`)
- `customer`: the customer's name (orders only have `customer_id`, so you'll need a join)
- `event`: `'joined'` or `'ordered'`

Sort the whole feed by `day`, then `customer`. Think about which set operation is right: two orders by the same customer on the same day must show up as **two** rows.

<Hint>

Put `UNION ALL` before the `ORDER BY` and add a second query: `SELECT o.ordered_at::date, c.name, 'ordered' FROM orders AS o JOIN customers AS c ON c.id = o.customer_id WHERE …`. Filter the orders with `o.ordered_at >= '2025-01-01' AND o.ordered_at < '2025-02-01'`. The single `ORDER BY` at the end sorts everything.

</Hint>

<Solution>

```sql
SELECT joined_on AS day, name AS customer, 'joined' AS event
FROM customers
WHERE joined_on >= '2025-01-01' AND joined_on < '2025-02-01'
UNION ALL
SELECT o.ordered_at::date, c.name, 'ordered'
FROM orders AS o
JOIN customers AS c ON c.id = o.customer_id
WHERE o.ordered_at >= '2025-01-01' AND o.ordered_at < '2025-02-01'
ORDER BY day, customer;
```

## Recap

- Set operations stack the rows of two queries; joins put columns side by side.
- `UNION ALL` keeps every row; `UNION` removes duplicates (and costs more).
- `INTERSECT` keeps rows found in both results; `EXCEPT` keeps rows of the first that aren't in the second, and the order matters.
- Both queries need the **same number of columns** with **compatible types**; names come from the **first** query.
- One `ORDER BY` at the end sorts the whole result, using output column names.
- Set operations treat `NULL`s as equal, so `EXCEPT` has no `NOT IN` trap.
- A label column like `'customer' AS kind` and a `UNION ALL` total row are handy reporting tricks.
