Reports rarely want raw values. They want **labels** ("budget", "premium"), **custom orders** ("paid before shipped before delivered") and **side-by-side numbers** ("orders per month, one column per status"), the kind of table you'd otherwise build by hand in a spreadsheet.

This lesson covers the tools for that: **`CASE`** for if/else logic, **`FILTER`** for conditional aggregation, and the pattern that combines them into **pivot tables**. 🧮

## CASE: if/else inside a query

A **searched `CASE`** checks conditions from top to bottom and returns the result of the **first** one that's true:

<CodeExample output={`       name        | price | price_band
-------------------+-------+------------
 Bamboo Chopsticks |  4.20 | budget
 Earl Grey         |  5.25 | standard
 Jasmine Tea       |  6.50 | standard
 Matcha Powder     | 14.00 | standard
 Tea Pot           | 32.00 | premium
 Rice Cooker       | 89.90 | premium
(6 rows)`}>

```sql
SELECT name, price,
  CASE
    WHEN price < 5 THEN 'budget'
    WHEN price < 20 THEN 'standard'
    ELSE 'premium'
  END AS price_band
FROM products
WHERE category IN ('tea', 'kitchen')
ORDER BY price;
```

</CodeExample>

Matcha Powder (14.00) is "standard", not "premium": the first true condition wins and the rest are never checked, so order the `WHEN`s from the most specific to the most general. If no condition matches and there's no `ELSE`, `CASE` returns `NULL`. Leaving out the `ELSE` is a common source of mysterious `NULL`s, so it's a good habit to always write one.

`CASE` is an **expression**, so it works anywhere a value does: in `SELECT`, `WHERE`, `ORDER BY`, `GROUP BY`, inside functions, even inside another `CASE`.

## Simple CASE and custom sort orders

When every condition compares the **same** value with `=`, the **simple `CASE`** form is shorter: write the value once, then list the matches. A favourite use is a custom sort order. Order statuses sort alphabetically by default (cancelled, delivered, paid, shipped), which makes no sense to a human; a `CASE` in `ORDER BY` puts them in the order an order travels:

<CodeExample output={`  status   | orders
-----------+--------
 paid      |      8
 shipped   |      8
 delivered |     16
 cancelled |      8
(4 rows)`}>

```sql
SELECT status, count(*) AS orders
FROM orders
GROUP BY status
ORDER BY CASE status
    WHEN 'paid' THEN 1
    WHEN 'shipped' THEN 2
    WHEN 'delivered' THEN 3
    ELSE 4
  END;
```

</CodeExample>

<Callout type="warning" title="Two CASE traps">

- **`CASE x WHEN NULL` never matches.** The simple form uses `=`, and `NULL = NULL` is not true. To catch missing values use the searched form: `CASE WHEN city IS NULL THEN 'unknown' ELSE city END` (or simply `coalesce(city, 'unknown')`).
- **All results must have one type.** `CASE WHEN stock > 0 THEN stock ELSE 'sold out' END` fails with "invalid input syntax for type integer", because PostgreSQL tries to turn `'sold out'` into a number. Cast the other branches instead: `THEN stock::text`.

</Callout>

## Grouping by a CASE

Because `CASE` makes a new value for every row, you can **group** by it. That turns a continuous number like a price into **buckets**:

<CodeExample output={` price_band | products | cheapest | dearest
------------+----------+----------+---------
 budget     |        4 |     2.50 |    4.20
 standard   |        7 |     5.25 |   18.00
 premium    |        4 |    24.99 |   89.90
(3 rows)`}>

```sql
SELECT
  CASE
    WHEN price < 5 THEN 'budget'
    WHEN price < 20 THEN 'standard'
    ELSE 'premium'
  END AS price_band,
  count(*) AS products,
  min(price) AS cheapest,
  max(price) AS dearest
FROM products
GROUP BY price_band
ORDER BY min(price);
```

</CodeExample>

PostgreSQL lets `GROUP BY` use the output name `price_band`, so the `CASE` is written once. Sorting by `min(price)` keeps the bands in a natural order without another `CASE`.

## Conditional aggregation with FILTER

How many orders were paid, shipped, delivered and cancelled **each month**? You could run four queries, but **conditional aggregation** does it in one pass. Add **`FILTER (WHERE ...)`** after an aggregate, and that aggregate only sees the rows that match:

<CodeExample output={`  month  | orders | paid | shipped | delivered | cancelled
---------+--------+------+---------+-----------+-----------
 2025-01 |      6 |    1 |       1 |         3 |         1
 2025-02 |      7 |    2 |       2 |         2 |         1
 2025-03 |      8 |    1 |       1 |         4 |         2
 2025-04 |      7 |    2 |       2 |         2 |         1
 2025-05 |      7 |    1 |       1 |         3 |         2
 2025-06 |      5 |    1 |       1 |         2 |         1
(6 rows)`}>

```sql
SELECT to_char(ordered_at, 'YYYY-MM') AS month,
  count(*) AS orders,
  count(*) FILTER (WHERE status = 'paid') AS paid,
  count(*) FILTER (WHERE status = 'shipped') AS shipped,
  count(*) FILTER (WHERE status = 'delivered') AS delivered,
  count(*) FILTER (WHERE status = 'cancelled') AS cancelled
FROM orders
GROUP BY month
ORDER BY month;
```

</CodeExample>

Congratulations, that's a **pivot table**: the statuses, which are **values in rows** in the `orders` table, have become **columns**. Each row is a month, each column a status, and each cell an aggregate. Spreadsheet users will feel right at home.

`FILTER` is standard SQL, but not every database has it (MySQL and SQL Server don't). The portable way, which you'll see a lot in older code, puts a `CASE` **inside** the aggregate:

```sql
count(CASE WHEN status = 'paid' THEN 1 END) AS paid,
sum(CASE WHEN status = 'paid' THEN 1 ELSE 0 END) AS paid_too
```

`count` ignores the `NULL`s that a `CASE` without `ELSE` returns, so both lines count the paid orders. In PostgreSQL prefer `FILTER`: it says what it means and works with any aggregate (`sum`, `avg`, `array_agg`…).

## Pivoting money: quarter by quarter

The same pattern pivots any measure. Here's revenue per category, with the first and second quarter of 2025 side by side, plus the change, which is easy now that the numbers sit in the same row:

<CodeExample output={` category |   q1   |   q2   | change
----------+--------+--------+---------
 books    | 481.45 | 348.96 | -132.49
 kitchen  | 675.10 | 485.00 | -190.10
 snacks   |  44.19 |  42.72 |   -1.47
 tea      |  35.25 |  45.75 |   10.50
 toys     | 139.80 | 147.60 |    7.80
(5 rows)`}>

```sql
SELECT p.category,
  sum(oi.quantity * oi.unit_price)
    FILTER (WHERE o.ordered_at < '2025-04-01') AS q1,
  sum(oi.quantity * oi.unit_price)
    FILTER (WHERE o.ordered_at >= '2025-04-01') AS q2,
  sum(oi.quantity * oi.unit_price)
    FILTER (WHERE o.ordered_at >= '2025-04-01')
  - sum(oi.quantity * oi.unit_price)
    FILTER (WHERE o.ordered_at < '2025-04-01') AS change
FROM order_items AS oi
JOIN orders AS o ON o.id = oi.order_id
JOIN products AS p ON p.id = oi.product_id
WHERE o.status <> 'cancelled'
GROUP BY p.category
ORDER BY p.category;
```

</CodeExample>

<Callout type="note" title="Pivot columns are fixed when you write the query">

SQL needs to know a query's columns before it runs, so every pivot column is written out by hand. If a new status appears tomorrow, the query won't grow a column for it. PostgreSQL's `crosstab()` function (from the `tablefunc` extension, which isn't available in this browser database) has the same limitation. For truly dynamic columns, generate the SQL in your application, or return long rows (`month, status, orders`) and let the spreadsheet, BI tool or front end pivot them.

</Callout>

## Unpivoting: columns back into rows

Sometimes data arrives **wide** (a column per quarter) and you need it **long** (a row per quarter), for example to feed a chart or to `GROUP BY` the quarter. Join each row to a small **`VALUES`** list that builds the rows. The **`LATERAL`** keyword lets that list refer to the current row's columns:

<CodeExample output={` category | quarter | revenue
----------+---------+---------
 tea      | Q1      |   35.25
 tea      | Q2      |   45.75
 toys     | Q1      |  139.80
 toys     | Q2      |  147.60
(4 rows)`}>

```sql
WITH by_quarter AS (
  SELECT p.category,
    sum(oi.quantity * oi.unit_price)
      FILTER (WHERE o.ordered_at < '2025-04-01') AS q1,
    sum(oi.quantity * oi.unit_price)
      FILTER (WHERE o.ordered_at >= '2025-04-01') AS q2
  FROM order_items AS oi
  JOIN orders AS o ON o.id = oi.order_id
  JOIN products AS p ON p.id = oi.product_id
  WHERE o.status <> 'cancelled'
  GROUP BY p.category
)
SELECT b.category, v.quarter, v.revenue
FROM by_quarter AS b
CROSS JOIN LATERAL (
  VALUES ('Q1', b.q1), ('Q2', b.q2)
) AS v (quarter, revenue)
WHERE b.category IN ('tea', 'toys')
ORDER BY b.category, v.quarter;
```

</CodeExample>

Every category row is joined to two rows of the `VALUES` list, one per quarter. `AS v (quarter, revenue)` names the list and its columns.

Try it: add a "Q2 vs Q1" percentage, pivot by country instead of status, or add a `FILTER`ed `avg()`.

<TryIt language="sql" code={`SELECT c.country,

FROM orders AS o
JOIN customers AS c ON c.id = o.customer_id

ORDER BY cancel_pct DESC, c.country

The buyers want one row per category with:

- `category` and `products` (how many products it has),
- `out_of_stock`: products with `stock = 0`,
- `low_stock`: products with 1 to 9 in stock,
- `stock_value`: the total of `price * stock`,
- `action`: `'reorder'` if anything is out of stock, otherwise `'watch'` if anything is low, otherwise `'ok'`,
- sorted by category.

<Hint>

Use `count(*) FILTER (WHERE stock = 0)` and `count(*) FILTER (WHERE stock BETWEEN 1 AND 9)`. For `action`, write a searched `CASE` that repeats those aggregates: `CASE WHEN count(*) FILTER (WHERE stock = 0) > 0 THEN 'reorder' WHEN ... THEN 'watch' ELSE 'ok' END`. (You can't use the aliases `out_of_stock` and `low_stock` inside the same `SELECT` list; a CTE is the other way.)

</Hint>

<Solution>

```sql
SELECT category,
  count(*) AS products,
  count(*) FILTER (WHERE stock = 0) AS out_of_stock,
  count(*) FILTER (WHERE stock BETWEEN 1 AND 9) AS low_stock,
  sum(price * stock) AS stock_value,
  CASE
    WHEN count(*) FILTER (WHERE stock = 0) > 0 THEN 'reorder'
    WHEN count(*) FILTER (WHERE stock BETWEEN 1 AND 9) > 0
      THEN 'watch'
    ELSE 'ok'
  END AS action
FROM products
GROUP BY category
ORDER BY category;
```

</Solution>

## Recap

- A **searched `CASE`** (`CASE WHEN condition THEN ... ELSE ... END`) returns the first matching result; without `ELSE`, no match gives `NULL`.
- A **simple `CASE`** (`CASE x WHEN value THEN ...`) compares one value with `=`, so it can't match `NULL`. All branches must share one type.
- `CASE` works anywhere a value does: labels in `SELECT`, custom sort orders in `ORDER BY`, buckets in `GROUP BY`.
- **`aggregate(...) FILTER (WHERE ...)`** aggregates only matching rows: count several things in one pass. The portable form is `count(CASE WHEN ... THEN 1 END)`.
- A **pivot** is `GROUP BY` the row label plus one filtered aggregate per column; the columns are fixed when you write the query.
- **Unpivot** with `CROSS JOIN LATERAL (VALUES ...)`, one `VALUES` row per column.
