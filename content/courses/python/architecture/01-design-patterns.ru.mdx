Где-то в районе 5000 строк любая кодовая база начинает задавать одни и те же вопросы: *куда положить новую функциональность? Почему изменение кода счетов ломает письма?* **Паттерны проектирования (design patterns)** — это названия, которые опытные разработчики дают решениям, проверенным временем. Это общий словарь: скажите на код-ревью «сделай это стратегией», и все поймут, что вы имеете в виду. 🧱

Но есть подвох. Большинство книг о паттернах написаны для Java и C++, и если переносить их в Python строка за строкой, получится куча классов, которые ничего не делают. В этом уроке вы изучите несколько паттернов, которые действительно окупаются в Python, в их **питоновской (Pythonic)** форме. Часто это просто функция, словарь или `Protocol`.

## SOLID на языке Python

**SOLID** — это пять принципов проектирования, о которых говорят в любом обсуждении архитектуры. Вот что каждый из них означает в повседневной работе на Python:

| Принцип | Одним предложением | Как это выглядит в Python |
| --- | --- | --- |
| **S** — единственная ответственность (single responsibility) | У куска кода должна быть одна причина для изменения | Маленькие функции и классы; «получить, отформатировать и отправить отчёт» — это три части, а не одна |
| **O** — открытость/закрытость (open/closed) | Добавляйте поведение новым кодом, а не правкой старого | Реестр или стратегия вместо растущей цепочки `if/elif` |
| **L** — подстановка Лисков (Liskov substitution) | Подкласс должен работать везде, где работает родитель | Не переопределяйте метод только ради того, чтобы выбросить `NotImplementedError` |
| **I** — разделение интерфейсов (interface segregation) | Не заставляйте код зависеть от методов, которыми он не пользуется | Маленькие `Protocol` с одним-двумя методами |
| **D** — инверсия зависимостей (dependency inversion) | Зависьте от абстракций, а не от конкретных деталей | Передавайте помощников снаружи, с типом `Protocol` |

Вот классический признак нарушения единственной ответственности. У этого класса **три** причины для изменения: новая база данных, новый вид отчёта, новый почтовый сервис:

```python
class ReportService:
    def send_weekly_report(self, team_id):
        rows = sqlite3.connect("app.db").execute(...)  # хранение
        html = "<table>" + ...                         # форматирование
        smtplib.SMTP("mail.example.com").sendmail(...) # доставка
```

Любое изменение в одной из частей грозит сломать две другие, а форматирование нельзя протестировать без базы данных и почтового сервера. Остаток этого урока (и всего модуля) посвящён тому, как разделить эти обязанности, а потом снова собрать их вместе.

<Callout type="note" title="Принципы, а не законы">

SOLID — это набор «запахов», которые стоит замечать, а не чек-лист, который нужно выполнить. 40-строчному скрипту инверсия зависимостей не нужна. Спросите себя: «Что, скорее всего, изменится и что это изменение сломает?» — и примените тот принцип, который защищает именно это место.

</Callout>

## Композиция вместо наследования

Наследование (inheritance) означает **«является»**: `Panda` является `Animal`. Это правильный инструмент для настоящих отношений «является», но часто наследование используют просто чтобы поделиться кодом, и это быстро превращается в путаницу. Представьте уведомления, которые можно отправлять по почте или по SMS, в вежливом или в крикливом стиле. С наследованием вы напишете `PoliteEmailNotifier`, `ShoutingEmailNotifier`, `PoliteSmsNotifier`, `ShoutingSmsNotifier`... а с добавлением Slack классов станет шесть.

**Композиция (composition)** означает **«содержит»**: у уведомителя *есть* отправитель и *есть* форматтер, и их можно комбинировать как угодно:

<CodeExample output={`письмо для mei: Здравствуйте! Обед готов. Спасибо!
SMS для sam: ОБЕД ГОТОВ!!!`}>

```python
class EmailSender:
    def send(self, to, text):
        return f"письмо для {to}: {text}"

class SmsSender:
    def send(self, to, text):
        return f"SMS для {to}: {text}"

class Polite:
    def format(self, text):
        return f"Здравствуйте! {text}. Спасибо!"

class Shouting:
    def format(self, text):
        return text.upper() + "!!!"

class Notifier:
    def __init__(self, sender, formatter):
        self.sender = sender
        self.formatter = formatter

    def notify(self, to, text):
        return self.sender.send(to, self.formatter.format(text))

text = "Обед готов"
print(Notifier(EmailSender(), Polite()).notify("mei", text))
print(Notifier(SmsSender(), Shouting()).notify("sam", text))
```

</CodeExample>

Два отправителя плюс два форматтера — это четыре маленьких класса и **любая** их комбинация. Добавить Slack — это один новый класс, и больше ничего не меняется (это и есть открытость/закрытость). А в тесте можно передать `Notifier` подставного отправителя, который просто запоминает сообщения.

Хорошее практическое правило: наследуйтесь от **базовых классов фреймворков** (`BaseModel`, `DeclarativeBase`, `Exception`) и для настоящих отношений «является»; во всех остальных случаях используйте композицию. Глубокие деревья наследования (четыре уровня и больше) — классический признак того, что композиция была бы лучшим выбором.

## Протоколы: утиная типизация с аннотациями типов

Заметьте: `Notifier` ни разу не проверил, что `sender` — это `EmailSender`. Он просто вызвал `.send()`. Это **утиная типизация (duck typing)**: если у объекта есть метод `send`, значит, это отправитель. `typing.Protocol` позволяет записать эту идею в виде типа, чтобы редакторы и программы проверки типов (mypy, pyright) могли её проверить:

<CodeExample output={`письмо для ops
True
False`}>

```python
from typing import Protocol, runtime_checkable

@runtime_checkable
class Sender(Protocol):
    def send(self, to: str, text: str) -> str: ...

class EmailSender:              # нигде нет "(Sender)"!
    def send(self, to: str, text: str) -> str:
        return f"письмо для {to}"

class Printer:
    def print_page(self, text: str) -> str:
        return "печатаем"

def alert(sender: Sender, to: str) -> str:
    return sender.send(to, "Сервер упал")

print(alert(EmailSender(), "ops"))
print(isinstance(EmailSender(), Sender))
print(isinstance(Printer(), Sender))
```

</CodeExample>

Это **структурная типизация (structural typing)**: класс подходит под протокол благодаря своей *форме* (своим методам), а не потому, что от чего-то наследуется. `EmailSender` даже не импортирует `Sender`. Именно поэтому протоколы идеально подходят для инверсии зависимостей: бизнес-код говорит «мне нужно что-то с методом `send(to, text)`», и сторонние классы, подставные объекты и настоящие реализации подходят, ничего не зная друг о друге.

- Тело `...` означает «реализации здесь нет, это только форма».
- `@runtime_checkable` разрешает проверки через `isinstance`, но они проверяют только наличие методов с такими **именами**, а не их аргументы. Настоящая проверка происходит в программе проверки типов.
- Альтернатива — `abc.ABC` с `@abstractmethod`: классы должны **наследоваться** от него, и Python откажется создавать объекты, в которых забыт какой-то метод. Вы воспользуетесь этим в следующем уроке. Практическое правило: протокол — когда чужой код должен подходить без изменений, ABC — когда все реализации ваши и вам нужна жёсткая ошибка.

## Стратегия: функции — это уже стратегии

**Паттерн «стратегия» (strategy)** означает «сделать алгоритм заменяемым». В Java это интерфейс плюс по классу на каждый алгоритм. В Python функции — это объекты, поэтому **стратегия обычно — просто функция**:

<CodeExample output={`80
56.0
75 30
40.0`}>

```python
from typing import Callable

PriceRule = Callable[[float], float]

def regular(total: float) -> float:
    return total

def black_friday(total: float) -> float:
    return round(total * 0.7, 2)

def loyalty(total: float) -> float:
    return total - 5 if total >= 50 else total

def checkout(total: float, rule: PriceRule = regular) -> float:
    return rule(total)

print(checkout(80))
print(checkout(80, black_friday))
print(checkout(80, loyalty), checkout(30, loyalty))
print(checkout(80, lambda t: t / 2))
```

</CodeExample>

`Callable[[float], float]` читается как «функция, которая принимает float и возвращает float». В `checkout` нет ни одного `if` про акции: отдел маркетинга может завтра придумать новую, и это будет новая функция из трёх строк. Вы уже пользовались этим паттерном, не зная его названия: `sorted(items, key=len)` принимает стратегию сравнения элементов.

Используйте класс (или протокол с несколькими методами), когда стратегии нужны **настройки или состояние**, например `PercentOff(20)`, или больше одной операции. В остальных случаях функция проще.

## Фабрика и реестр

Иногда выбор стратегии приходит в виде **данных**: `"csv"` из строки запроса, `"stripe"` из файла конфигурации. **Фабрика (factory)** превращает это имя в нужный объект, а **реестр (registry)** позволяет каждой реализации зарегистрировать себя самой, обычно с помощью декоратора:

<CodeExample output={`['csv', 'json']
name,xp
Mei,120
Sam,80
[{"name": "Mei", "xp": 120}]
неизвестный формат 'xml' (csv, json)`}>

```python
import json

EXPORTERS = {}

def exporter(name):
    def register(func):
        EXPORTERS[name] = func
        return func
    return register

@exporter("json")
def to_json(rows):
    return json.dumps(rows)

@exporter("csv")
def to_csv(rows):
    lines = [",".join(rows[0])]
    lines += [",".join(str(v) for v in r.values()) for r in rows]
    return "\n".join(lines)

def make_exporter(name):
    try:
        return EXPORTERS[name]
    except KeyError:
        known = ", ".join(sorted(EXPORTERS))
        raise ValueError(f"неизвестный формат {name!r} ({known})")

rows = [{"name": "Mei", "xp": 120}, {"name": "Sam", "xp": 80}]
print(sorted(EXPORTERS))
print(make_exporter("csv")(rows))
print(make_exporter("json")(rows[:1]))
try:
    make_exporter("xml")
except ValueError as error:
    print(error)
```

</CodeExample>

Сравните с версией, с которой начинается любой проект:

```python
def export(rows, name):
    if name == "json":
        ...
    elif name == "csv":
        ...
    elif name == "xml":     # каждый новый формат правит эту функцию
        ...
```

С реестром добавить XML — значит написать новую функцию с декоратором, возможно, в новом файле, а `make_exporter` никогда не меняется. Именно так устроены плагины pytest, маршруты FastAPI (`@app.get` регистрирует функцию) и админка Django. Важны две детали: декоратор должен **возвращать** функцию (иначе имя `to_csv` станет `None`), а фабрика выдаёт **понятную ошибку** со списком допустимых имён.

## Наблюдатель: события вместо вызовов

Когда пользователь регистрируется, нужно отправить приветственное письмо, добавить его в рассылку и уведомить отдел продаж. Если `sign_up()` вызывает все три действия, она знает о почте, рассылках и продажах, и каждая новая просьба «когда случится X, сделай ещё и Y» снова её меняет. **Паттерн «наблюдатель» (observer)** переворачивает это: `sign_up()` просто объявляет *«пользователь зарегистрировался»*, а все заинтересованные **подписываются (subscribe)**:

<CodeExample output={`отправляем приветственное письмо на mei@example.com
добавляем mei@example.com в рассылку
отправляем заказ 42`}>

```python
from collections import defaultdict
from typing import Callable

Handler = Callable[[dict], None]

class EventBus:
    def __init__(self):
        self._handlers: dict[str, list[Handler]] = defaultdict(list)

    def subscribe(self, event: str, handler: Handler) -> None:
        self._handlers[event].append(handler)

    def publish(self, event: str, data: dict) -> None:
        for handler in self._handlers[event]:
            handler(data)

bus = EventBus()
bus.subscribe("user_signed_up",
              lambda d: print("отправляем приветственное письмо на",
                              d["email"]))
bus.subscribe("user_signed_up",
              lambda d: print("добавляем", d["email"], "в рассылку"))
bus.subscribe("order_paid",
              lambda d: print("отправляем заказ", d["id"]))

bus.publish("user_signed_up", {"email": "mei@example.com"})
bus.publish("order_paid", {"id": 42})
bus.publish("nobody_listens", {})
```

</CodeExample>

Издатель не знает, кто его слушает и слушает ли кто-нибудь вообще (с `"nobody_listens"` всё в порядке). В большем масштабе та же идея превращается в очередь сообщений (RabbitMQ, Kafka, SQS) между сервисами. Цена — **косвенность (indirection)**: по строке `publish(...)` уже не видно, что произойдёт дальше. Поэтому держите названия событий в одном месте и не используйте события для того, что должно выполняться по порядку внутри одной операции.

<Callout type="warning" title="Исключения в обработчиках">

В этой простой шине, если один обработчик выбросит исключение, следующие за ним обработчики уже не выполнятся, а ошибка всплывёт в код, который опубликовал событие. В настоящих системах событий это решают сознательно: либо записывают ошибку в лог и продолжают, либо выполняют обработчики позже в фоновом обработчике с повторными попытками. Сбой сервиса рассылок никогда не должен мешать пользователю зарегистрироваться.

</Callout>

## Адаптер: подогнать под себя

Вы спроектировали аккуратный протокол `PaymentGateway`, а потом бизнес выбирает платёжного провайдера, чей SDK использует другие названия методов и евро вместо центов. Не позволяйте этому SDK просочиться в ваш код. Напишите **адаптер (adapter)**: маленький класс, у которого снаружи *ваш* интерфейс, а внутри — вызовы *их* API:

<CodeExample output={`ZP-mei-12.5`}>

```python
from typing import Protocol

class PaymentGateway(Protocol):
    def charge(self, cents: int, customer: str) -> str: ...

# Сторонний SDK, который нельзя изменить: другие имена и единицы
class ZebraPayClient:
    def make_payment(self, amount_eur: float, account_id: str):
        return {"status": "ok", "ref": f"ZP-{account_id}-{amount_eur}"}

class ZebraPayAdapter:
    def __init__(self, client: ZebraPayClient):
        self.client = client

    def charge(self, cents: int, customer: str) -> str:
        result = self.client.make_payment(cents / 100, customer)
        if result["status"] != "ok":
            raise RuntimeError("платёж не прошёл")
        return result["ref"]

def buy_bamboo(gateway: PaymentGateway) -> str:
    return gateway.charge(1250, "mei")

print(buy_bamboo(ZebraPayAdapter(ZebraPayClient())))
```

</CodeExample>

Всё знание о ZebraPay (название метода, перевод в евро, способ сообщать об ошибках) живёт в одном классе. Когда компания сменит провайдера, а это случается чаще, чем кто-либо планирует, вы напишете один новый адаптер, и `buy_bamboo` ничего не заметит. В адаптерах же переводят исключения поставщика в ваши собственные, чтобы остальному коду никогда не приходилось писать `except ZebraPayTimeout`.

## Когда паттерны вредят

Паттерны решают проблемы. Без проблемы это просто лишние слои. Вот несколько антипаттернов, которые встречаются на настоящих код-ревью:

- **Интерфейс с одной реализацией.** `UserRepositoryInterface`, `UserRepositoryImpl` и `UserRepositoryFactory` ради одного класса, у которого никогда не будет второй версии. Добавляйте абстракцию, когда вторая реализация (или подставной объект для тестов) действительно появляется.
- **Java на Python.** Методы `getName()` / `setName()` (используйте атрибуты, а если позже понадобится логика — `@property`), класс с единственным методом `__call__` (используйте функцию), класс `Singleton` (модуль уже является синглтоном: создайте объект один раз в модуле и импортируйте его).
- **Паттерны как цель.** Фраза «давайте применим здесь паттерн „посетитель“» на планировании — тревожный сигнал. Начинайте с изменения, которое ожидаете, а потом выбирайте самый маленький паттерн, который это изменение упрощает.
- **Спекулятивная обобщённость.** Система плагинов для экспортёров, когда в продукте одна кнопка экспорта. YAGNI: *You Aren't Gonna Need It* («вам это не понадобится»). Отрефакторить позже, с тестами, дёшево; вечно таскать за собой неиспользуемую гибкость — нет.

Одна команда заменила функцию из 30 строк иерархией `AbstractExporterFactoryProvider` — «чтобы быть готовыми к новым форматам». Через два года формат по-прежнему был только один — CSV, а каждый новый разработчик терял день, выясняя, где на самом деле живёт код для CSV. Простой код, который можно изменить, лучше хитроумного кода, который нельзя прочитать.

```python
from dataclasses import dataclass
from typing import Callable


@dataclass
class Order:
    id: int
    subtotal: float
    weight_kg: float


ShippingRule = Callable[[Order], float]
SHIPPING: dict[str, ShippingRule] = {}


def shipping(name: str):
    def register(rule: ShippingRule) -> ShippingRule:
        SHIPPING[name] = rule
        return rule
    return register


@shipping("standard")
def standard(order: Order) -> float:
    return 0.0 if order.subtotal >= 50 else 4.99


@shipping("express")
def express(order: Order) -> float:
    return round(9.99 + 2 * order.weight_kg, 2)


@shipping("pickup")
def pickup(order: Order) -> float:
    return 0.0


def get_shipping(name: str) -> ShippingRule:
    if name not in SHIPPING:
        raise ValueError(f"неизвестный способ доставки: {name}")
    return SHIPPING[name]


PaidListener = Callable[[Order, float], None]


class Checkout:
    def __init__(self, shipping_rule: ShippingRule):
        self.shipping_rule = shipping_rule
        self.listeners: list[PaidListener] = []

    def on_paid(self, listener: PaidListener) -> None:
        self.listeners.append(listener)

    def pay(self, order: Order) -> float:
        total = round(order.subtotal + self.shipping_rule(order), 2)
        for listener in self.listeners:
            listener(order, total)
        return total


checkout = Checkout(get_shipping("express"))
checkout.on_paid(lambda o, t: print(f"Заказ {o.id} оплачен: {t}"))
checkout.pay(Order(1, 20.0, 1.5))
```

## Итоги

- Паттерны — это **общий словарь** для решений, проверенных временем; в Python это часто функция, словарь или протокол, а не иерархия классов.
- **SOLID**: одна причина для изменения, расширение новым кодом, подклассы должны действительно заменять родителя, маленькие интерфейсы, зависимость от абстракций. Используйте их как сигналы, которые стоит замечать, а не как правила, которым нужно подчиняться.
- Чтобы поделиться поведением, предпочитайте **композицию** («содержит») наследованию («является»); наследуйтесь от базовых классов фреймворков и для настоящих отношений «является».
- **`typing.Protocol`** описывает форму; подходит любой класс с подходящими методами (структурная типизация). `abc.ABC` требует наследования и не даёт создать неполный класс.
- **Стратегия** = передать функцию. **Фабрика/реестр** = декоратор заполняет словарь, фабрика ищет имена и выдаёт понятную ошибку. **Наблюдатель** = подписать обработчики, публиковать события. **Адаптер** = спрятать сторонний API за вашим интерфейсом.
- Паттерны без проблемы — это просто слои: добавляйте абстракции, когда вторая реализация или подставной объект для тестов действительно появляется.
