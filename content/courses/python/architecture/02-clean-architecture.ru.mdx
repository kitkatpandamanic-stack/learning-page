Большинство приложений начинаются одинаково: бизнес-правила внутри эндпоинтов FastAPI, SQL-запросы рядом с `if` про скидки и письмо, отправленное посреди транзакции базы данных. Писать так быстро, и для маленького приложения это нормально. Потом приложение растёт. Одна команда, которой понадобилось перейти с SQLite на PostgreSQL, нашла обращения к базе данных в 40 файлах, а некоторые — прямо в шаблонах Jinja. Миграция, запланированная на неделю, заняла три месяца. 🏗️

**Чистая архитектура (clean architecture)** — это способ организовать код так, чтобы самая важная его часть, ваши **бизнес-правила**, не зависела от деталей вроде веб-фреймворка или базы данных. В этом уроке вы узнаете три её слоя, единственное правило, которое их связывает, и два паттерна, которые делают её практичной в Python: **репозиторий (repository)** и **единицу работы (unit of work)**.

## Три слоя

Представьте приложение в виде колец: в центре — самый важный и самый стабильный код:

| Слой (layer) | Что содержит | О чём знает |
| --- | --- | --- |
| **Домен** (domain, ядро) | Сущности и бизнес-правила: `Product`, `Order`, «нельзя зарезервировать больше, чем есть на складе» | Ни о чём, кроме обычного Python |
| **Сервисы** (services, сценарии использования) | По функции на каждое действие пользователя: `place_order`, `cancel_order` | О домене плюс об абстрактных интерфейсах для хранения и сообщений |
| **Адаптеры** (adapters, внешний край) | Маршруты FastAPI, модели и репозитории SQLAlchemy, отправка писем, команды CLI | Обо всём: они подключают внешний мир к сервисам |

В папке проекта это часто выглядит так:

```text
shop/
├── domain/        model.py: Product, OutOfStock     (чистый Python)
├── services/      orders.py: place_order(uow, ...)
├── adapters/      orm.py, repository.py, unit_of_work.py
└── entrypoints/   api.py: маршруты FastAPI (тонкие!)
```

Ещё это называют **порты и адаптеры (ports and adapters)** или **гексагональной архитектурой (hexagonal architecture)**. Названия различаются в деталях, но идея одна: внутренняя часть определяет **порты** (интерфейсы вроде «что-то, что умеет хранить товары»), а внешняя предоставляет **адаптеры**, которые их реализуют (репозиторий на SQLAlchemy, репозиторий в памяти для тестов).

## Правило зависимостей

Единственное правило, на котором всё держится: **зависимости в исходном коде направлены внутрь**. Домен ничего не импортирует из сервисов и адаптеров; сервисы импортируют домен, но никогда не `fastapi` и не `sqlalchemy`; адаптеры могут импортировать что угодно.

Вот как выглядит модель домена. Обратите внимание на импорты: только стандартная библиотека.

<CodeExample output={`Product(sku='BMB-1', name='бамбук', stock=2)
Не получилось: бамбук — осталось только 2 шт.`}>

```python
from dataclasses import dataclass

class OutOfStock(Exception):
    pass

@dataclass
class Product:
    sku: str
    name: str
    stock: int

    def reserve(self, qty: int) -> None:
        if qty <= 0:
            raise ValueError("количество должно быть положительным")
        if qty > self.stock:
            raise OutOfStock(
                f"{self.name} — осталось только {self.stock} шт.")
        self.stock -= qty

bamboo = Product("BMB-1", "бамбук", stock=5)
bamboo.reserve(3)
print(bamboo)
try:
    bamboo.reserve(4)
except OutOfStock as error:
    print("Не получилось:", error)
```

</CodeExample>

Правило «нельзя зарезервировать больше, чем есть на складе» живёт **в домене**, а не в эндпоинте и не в SQL-ограничении `CHECK`. Это значит:

- Его тестируют за микросекунды, без базы данных и без HTTP.
- Эндпоинт FastAPI, CLI-скрипт и ночная пакетная задача используют одно и то же правило.
- Бизнес-логику можно читать, не продираясь через код фреймворка.

Быстрый способ проверить правило зависимостей в настоящем проекте: `grep -r "import fastapi\|import sqlalchemy" shop/domain shop/services` не должен ничего найти. Инструменты вроде `import-linter` могут следить за этим в CI.

<Callout type="tip" title="Делайте эндпоинты тонкими">

В чистой архитектуре эндпоинт FastAPI делает три вещи: превращает запрос в простые значения, вызывает **одну** функцию сервиса и превращает результат (или исключение домена) в ответ. Если в эндпоинте есть бизнес-`if`, им, скорее всего, место в домене или в сервисе.

</Callout>

## Паттерн «репозиторий»

Сервисам нужно загружать и сохранять товары, но импортировать SQLAlchemy им нельзя. Решение — **репозиторий**: объект, который выглядит как коллекция объектов домена (`get`, `save`, `list_all`) и скрывает, как они хранятся. Сначала **порт** (port) — абстрактный базовый класс, затем простой **адаптер** (adapter) в памяти:

<CodeExample output={`5
None
Can't instantiate abstract class HalfDoneRepository without an implementation for abstract methods 'list_all', 'save'`}>

```python
from abc import ABC, abstractmethod
from dataclasses import dataclass, replace

@dataclass
class Product:
    sku: str
    name: str
    stock: int

class ProductRepository(ABC):
    @abstractmethod
    def get(self, sku: str) -> Product | None: ...

    @abstractmethod
    def save(self, product: Product) -> None: ...

    @abstractmethod
    def list_all(self) -> list[Product]: ...

class InMemoryProductRepository(ProductRepository):
    def __init__(self):
        self._items: dict[str, Product] = {}

    def get(self, sku):
        item = self._items.get(sku)
        return replace(item) if item else None   # копия

    def save(self, product):
        self._items[product.sku] = replace(product)

    def list_all(self):
        return [replace(p) for p in self._items.values()]

repo = InMemoryProductRepository()
repo.save(Product("BMB-1", "бамбук", 5))
p = repo.get("BMB-1")
p.stock = 0                  # изменили, но не сохранили...
print(repo.get("BMB-1").stock)
print(repo.get("NOPE"))

class HalfDoneRepository(ProductRepository):
    def get(self, sku):
        return None

try:
    HalfDoneRepository()
except TypeError as error:
    print(error)
```

</CodeExample>

Обратите внимание на две вещи:

- `abc.ABC` с `@abstractmethod` заставляет Python **отказаться** создавать репозиторий, в котором забыт какой-то метод (сообщение в последней строке: нельзя создать абстрактный класс без реализации методов `list_all` и `save`). Здесь нам нужна именно жёсткая ошибка, потому что все реализации наши. (Протокол из прошлого урока тоже подошёл бы, просто он не пожаловался бы, пока не запустится программа проверки типов.)
- Репозиторий в памяти хранит и возвращает **копии** (`dataclasses.replace(obj)` без изменений создаёт копию). Так сделано намеренно: настоящая база данных тоже каждый раз выдаёт новый объект, и изменения теряются, если их не сохранить. Если бы фейк возвращал тот же самый объект, сервис, который **забыл** вызвать `save`, проходил бы все тесты с фейком и молча терял данные в продакшене. Фейк полезен, только если ведёт себя как настоящий объект.

## Репозиторий на SQLAlchemy

Теперь настоящий адаптер. Модель SQLAlchemy (`ProductRow`) — это забота **базы данных**, и она живёт в слое адаптеров; репозиторий переводит строки таблицы в объекты домена и обратно, поэтому никто выше него никогда не видит `ProductRow`:

<CodeExample output={`[Product(sku='APL-7', name='яблоко', stock=12), Product(sku='BMB-1', name='бамбук', stock=5)]
Product`}>

```python
from abc import ABC, abstractmethod
from dataclasses import dataclass
from sqlalchemy import create_engine, select
from sqlalchemy.orm import (
    DeclarativeBase, Mapped, mapped_column, Session,
)

# --- домен + порт (здесь нет SQLAlchemy) ---
@dataclass
class Product:
    sku: str
    name: str
    stock: int

class ProductRepository(ABC):
    @abstractmethod
    def get(self, sku: str) -> Product | None: ...
    @abstractmethod
    def save(self, product: Product) -> None: ...
    @abstractmethod
    def list_all(self) -> list[Product]: ...

# --- адаптер: SQLAlchemy ---
class Base(DeclarativeBase):
    pass

class ProductRow(Base):
    __tablename__ = "products"
    sku: Mapped[str] = mapped_column(primary_key=True)
    name: Mapped[str]
    stock: Mapped[int]

def to_domain(row: ProductRow) -> Product:
    return Product(sku=row.sku, name=row.name, stock=row.stock)

class SqlProductRepository(ProductRepository):
    def __init__(self, session: Session):
        self.session = session

    def get(self, sku):
        row = self.session.get(ProductRow, sku)
        return to_domain(row) if row else None

    def save(self, product):
        row = self.session.get(ProductRow, product.sku)
        if row is None:
            row = ProductRow(sku=product.sku)
            self.session.add(row)
        row.name, row.stock = product.name, product.stock

    def list_all(self):
        rows = self.session.scalars(
            select(ProductRow).order_by(ProductRow.sku))
        return [to_domain(r) for r in rows]

engine = create_engine("sqlite://")
Base.metadata.create_all(engine)

with Session(engine) as session:
    repo = SqlProductRepository(session)
    repo.save(Product("BMB-1", "бамбук", 5))
    repo.save(Product("APL-7", "яблоко", 12))
    session.commit()

with Session(engine) as session:
    repo = SqlProductRepository(session)
    print(repo.list_all())
    print(type(repo.get("BMB-1")).__name__)
```

</CodeExample>

`save` работает как «upsert»: загружает строку, если она есть, создаёт, если нет, и копирует поля. Заметьте, чего репозиторий **не** делает: он никогда не вызывает `session.commit()`. Решать, когда работа закончена, — задача следующего паттерна.

Стоит ли код преобразования таких усилий? Это главная цена этой архитектуры: каждое поле записано дважды. Для CRUD-приложения, где таблицы базы данных *и есть* бизнес, чаще всего не стоит, и использовать модели SQLAlchemy напрямую — вполне хороший выбор. Окупается это, когда в домене есть настоящие правила или когда нужно быстро тестировать много бизнес-логики. (В SQLAlchemy есть ещё «императивное отображение» (imperative mapping), которое связывает обычные dataclass-классы с таблицами без отдельного класса строки; это мощно, но больше похоже на магию.)

## Единица работы

**Сценарий использования (use case)** часто меняет несколько объектов, и они должны сохраниться все вместе или не сохраниться вовсе. Заказ одного бамбука и трёх яблок, когда яблок осталось только два, не должен оставить бамбук зарезервированным. Паттерн **«единица работы»** оборачивает одну бизнес-операцию в одну транзакцию: открывает сессию, выдаёт вам репозитории и фиксирует изменения, только когда вы скажете. Инструкция `with` в Python подходит для этого идеально:

<CodeExample output={`[4, 1]
Заказ не оформлен: яблоко — осталось только 1 шт.
[4, 1]`}>

```python
from dataclasses import dataclass
from sqlalchemy import create_engine
from sqlalchemy.orm import (
    DeclarativeBase, Mapped, mapped_column, Session, sessionmaker,
)

@dataclass
class Product:
    sku: str
    name: str
    stock: int

    def reserve(self, qty: int) -> None:
        if qty > self.stock:
            raise ValueError(
                f"{self.name} — осталось только {self.stock} шт.")
        self.stock -= qty

class Base(DeclarativeBase):
    pass

class ProductRow(Base):
    __tablename__ = "products"
    sku: Mapped[str] = mapped_column(primary_key=True)
    name: Mapped[str]
    stock: Mapped[int]

class SqlProductRepository:
    def __init__(self, session: Session):
        self.session = session

    def get(self, sku):
        row = self.session.get(ProductRow, sku)
        return Product(row.sku, row.name, row.stock) if row else None

    def save(self, product):
        row = self.session.get(ProductRow, product.sku)
        if row is None:
            row = ProductRow(sku=product.sku)
            self.session.add(row)
        row.name, row.stock = product.name, product.stock

class SqlUnitOfWork:
    def __init__(self, session_factory):
        self.session_factory = session_factory

    def __enter__(self):
        self.session = self.session_factory()
        self.products = SqlProductRepository(self.session)
        return self

    def __exit__(self, *exc_info):
        self.rollback()          # ничего не делает, если commit() уже был
        self.session.close()

    def commit(self):
        self.session.commit()

    def rollback(self):
        self.session.rollback()

# --- сценарий использования: все строки или ничего ---
def place_order(uow, lines: dict[str, int]) -> None:
    with uow:
        for sku, qty in lines.items():
            product = uow.products.get(sku)
            product.reserve(qty)
            uow.products.save(product)
        uow.commit()

engine = create_engine("sqlite://")
Base.metadata.create_all(engine)
make_session = sessionmaker(engine)
with SqlUnitOfWork(make_session) as uow:
    uow.products.save(Product("BMB-1", "бамбук", 5))
    uow.products.save(Product("APL-7", "яблоко", 2))
    uow.commit()

def stock():
    with SqlUnitOfWork(make_session) as uow:
        return [uow.products.get(s).stock for s in ("BMB-1", "APL-7")]

place_order(SqlUnitOfWork(make_session), {"BMB-1": 1, "APL-7": 1})
print(stock())
try:
    place_order(SqlUnitOfWork(make_session),
                {"BMB-1": 3, "APL-7": 9})
except ValueError as error:
    print("Заказ не оформлен:", error)
print(stock())
```

</CodeExample>

Второй заказ зарезервировал три бамбука, а потом споткнулся на яблоках. Поскольку до `commit()` дело не дошло, `__exit__` откатил всю транзакцию, и на складе по-прежнему 4 бамбука. Функция сервиса читается как бизнес-процесс («для каждой строки заказа зарезервировать и сохранить, потом зафиксировать») и не содержит ни одного вызова SQLAlchemy.

- `sessionmaker(engine)` — это **фабрика сессий (session factory)**: при вызове она выдаёт новую `Session`. Единица работы создаёт свежую сессию для каждого блока `with`.
- **Фиксируйте изменения явно.** Безопасное поведение по умолчанию — «откатить, если сценарий не сказал, что всё готово». Автоматический commit при успехе соблазнителен, но явный commit ясно показывает, где заканчивается транзакция.
- В FastAPI эндпоинт получал бы единицу работы через `Depends`, вызывал сервис и превращал ошибку домена вроде `OutOfStock` в ответ 409. Вы свяжете это в следующем уроке.

```python
@app.post("/orders", status_code=201)
def create_order(body: OrderIn, uow=Depends(get_uow)):
    try:
        place_order(uow, body.lines)
    except OutOfStock as error:
        raise HTTPException(409, str(error))
    return {"status": "reserved"}
```

## Тестирование с фейками

А теперь награда. Сервису нужно только «что-то с `.products`, `.commit()` и поддержкой `with`», поэтому тесты могут дать ему **фейковую единицу работы**, которая хранит всё в памяти и просто запоминает, был ли вызван `commit()`:

<CodeExample output={`....                                                 [100%]
4 passed in 0.01s`}>

```python
import pytest
from dataclasses import dataclass, replace

@dataclass
class Product:
    sku: str
    name: str
    stock: int

    def reserve(self, qty: int) -> None:
        if qty > self.stock:
            raise ValueError(
                f"{self.name} — осталось только {self.stock} шт.")
        self.stock -= qty

class InMemoryProductRepository:
    def __init__(self, *products):
        self._items = {p.sku: replace(p) for p in products}

    def get(self, sku):
        item = self._items.get(sku)
        return replace(item) if item else None

    def save(self, product):
        self._items[product.sku] = replace(product)

class FakeUnitOfWork:
    def __init__(self, *products):
        self.products = InMemoryProductRepository(*products)
        self.committed = False

    def __enter__(self):
        return self

    def __exit__(self, *exc_info):
        pass

    def commit(self):
        self.committed = True

class UnknownProduct(Exception):
    pass

def reserve(uow, sku: str, qty: int) -> int:
    with uow:
        product = uow.products.get(sku)
        if product is None:
            raise UnknownProduct(sku)
        product.reserve(qty)
        uow.products.save(product)
        uow.commit()
        return product.stock

@pytest.fixture
def uow():
    return FakeUnitOfWork(Product("BMB-1", "бамбук", 5))

def test_reserve_lowers_stock_and_commits(uow):
    assert reserve(uow, "BMB-1", 2) == 3
    assert uow.products.get("BMB-1").stock == 3
    assert uow.committed

def test_unknown_product(uow):
    with pytest.raises(UnknownProduct):
        reserve(uow, "NOPE", 1)
    assert not uow.committed

def test_not_enough_stock_commits_nothing(uow):
    with pytest.raises(ValueError, match="осталось только 5"):
        reserve(uow, "BMB-1", 6)
    assert not uow.committed

def test_can_reserve_everything(uow):
    assert reserve(uow, "BMB-1", 5) == 0

pytest.main([__file__])
```

</CodeExample>

Этим тестам не нужны ни база данных, ни `Mock`, ни `patch`: только обычные объекты, переданные в функцию. В проекте их могут быть тысячи, и весь набор всё равно выполнится за секунды. Вот стратегия тестирования, которую даёт чистая архитектура:

- **Много быстрых модульных тестов** для домена и сервисов, с фейками.
- **Несколько интеграционных тестов** для каждого адаптера с настоящей базой данных (SQLite в памяти или одноразовый PostgreSQL в CI), чтобы доказать, что отображение на SQL работает.
- Горстка **сквозных (end-to-end) тестов** через API с `TestClient`.

Полезный приём для среднего слоя — **контрактный тест (contract test)**: один набор тестов репозитория, который запускается на *обеих* реализациях с помощью параметризованной фикстуры (`@pytest.fixture(params=["memory", "sql"])`). Если фейк и настоящий репозиторий проходят одни и те же тесты, фейку можно доверять во всех быстрых тестах. Именно это вы напишете в упражнении.

<Callout type="warning" title="Не стройте архитектуру для списка дел">

Слои, репозитории и единицы работы стоят кода: функции преобразования, интерфейсы, лишние файлы. Для маленького CRUD-сервиса, прототипа или скрипта правильный выбор — FastAPI и модели SQLAlchemy напрямую (как на Уровне 2). Берите чистую архитектуру, когда **бизнес-правила** сложные, приложение будет жить годами или над ним работают несколько команд. Внедрять её можно и постепенно: начните с переноса правил в домен, добавьте репозиторий, когда тестировать станет больно.

</Callout>

import pytest
from abc import ABC, abstractmethod
from dataclasses import dataclass, replace
from sqlalchemy import create_engine
from sqlalchemy.orm import (
    DeclarativeBase, Mapped, mapped_column, Session, sessionmaker,
)


# ---------- домен (готов) ----------

class BookNotFound(Exception):
    pass


class AlreadyBorrowed(Exception):
    pass


class NotBorrowed(Exception):
    pass


@dataclass
class Book:
    isbn: str
    title: str
    borrower: str | None = None

    def lend_to(self, member: str) -> None:
        if self.borrower is not None:
            raise AlreadyBorrowed(self.title)
        self.borrower = member

    def give_back(self) -> None:
        if self.borrower is None:
            raise NotBorrowed(self.title)
        self.borrower = None


class BookRepository(ABC):
    @abstractmethod
    def get(self, isbn: str) -> Book | None: ...

    @abstractmethod
    def save(self, book: Book) -> None: ...


# ---------- адаптеры ----------

class Base(DeclarativeBase):
    pass


class BookRow(Base):
    __tablename__ = "books"
    isbn: Mapped[str] = mapped_column(primary_key=True)
    title: Mapped[str]
    borrower: Mapped[str | None]


class InMemoryBookRepository(BookRepository):
    def __init__(self):
        self._books: dict[str, Book] = {}

    def get(self, isbn):
        book = self._books.get(isbn)
        return replace(book) if book else None

    def save(self, book):
        self._books[book.isbn] = replace(book)


class SqlBookRepository(BookRepository):
    def __init__(self, session: Session):
        self.session = session

    def get(self, isbn):
        row = self.session.get(BookRow, isbn)
        if row is None:
            return None
        return Book(row.isbn, row.title, row.borrower)

    def save(self, book):
        row = self.session.get(BookRow, book.isbn)
        if row is None:
            row = BookRow(isbn=book.isbn)
            self.session.add(row)
        row.title = book.title
        row.borrower = book.borrower


class FakeUnitOfWork:
    def __init__(self):
        self.books = InMemoryBookRepository()
        self.committed = False

    def __enter__(self):
        return self

    def __exit__(self, *exc_info):
        pass

    def commit(self):
        self.committed = True


class SqlUnitOfWork:
    def __init__(self, session_factory):
        self.session_factory = session_factory

    def __enter__(self):
        self.session = self.session_factory()
        self.books = SqlBookRepository(self.session)
        return self

    def __exit__(self, *exc_info):
        self.session.rollback()
        self.session.close()

    def commit(self):
        self.session.commit()

def borrow_book(uow, isbn: str, member: str) -> Book:
    with uow:
        book = uow.books.get(isbn)
        if book is None:
            raise BookNotFound(isbn)
        book.lend_to(member)
        uow.books.save(book)
        uow.commit()
        return book


def return_book(uow, isbn: str) -> Book:
    with uow:
        book = uow.books.get(isbn)
        if book is None:
            raise BookNotFound(isbn)
        book.give_back()
        uow.books.save(book)
        uow.commit()
        return book

## Итоги

- В чистой архитектуре три слоя: **домен** (сущности и правила, обычный Python), **сервисы** (по функции на сценарий использования) и **адаптеры** (FastAPI, SQLAlchemy, почта...).
- **Правило зависимостей**: импорты направлены внутрь. Домен ничего не знает о фреймворках; сервисы знают домен и абстрактные порты.
- **Репозиторий** выглядит как коллекция объектов домена (`get`, `save`) и скрывает хранилище. Опишите порт через `abc.ABC`, реализуйте его на SQLAlchemy и в памяти; превращайте строки в объекты домена на внешнем краю.
- Фейки должны вести себя как настоящие объекты: репозиторий в памяти должен хранить и возвращать **копии**. Контрактные тесты (один набор тестов, обе реализации) это доказывают.
- **Единица работы** оборачивает один сценарий использования в одну транзакцию: `with uow:`, изменения через `uow.products`, `uow.commit()`; всё остальное откатывается.
- Тестируйте сервисы с фейковой единицей работы: тысячи быстрых тестов, без базы данных и без моков. Оставьте несколько интеграционных тестов для настоящих адаптеров.
- Это стоит дополнительного кода, поэтому используйте такой подход там, где бизнес-правила сложные и приложение будет жить долго, а не в каждом CRUD-сервисе.
