До сих пор вы строили одно приложение на одной машине. У настоящих продуктов миллионы пользователей, и один сервер с такой нагрузкой не справится. **Проектирование систем (system design)** — это искусство выбирать крупные части (серверы, базы данных, кэши, очереди) и то, как они общаются друг с другом. Единственно верного ответа почти никогда нет, есть только компромиссы (trade-offs). В этом уроке вы выучите словарь и, что ещё важнее, научитесь рассуждать, какая часть вам нужна и *почему*. 🏗️

Сквозной пример — **PandaRun**, мобильная игра с глобальной таблицей рекордов (leaderboard). Игрок заканчивает забег, приложение отправляет его очки, и каждый может посмотреть топ-100 и своё место в рейтинге.

## Начинайте с требований, а не с квадратиков

Самая частая ошибка в обсуждениях архитектуры (и на собеседованиях) — рисовать квадратики раньше, чем все договорились, что система должна делать. Разделите требования (requirements) на два вида:

| Вид | На какой вопрос отвечает | Примеры для PandaRun |
| --- | --- | --- |
| **Функциональные** (functional) | Что система делает? | Отправить очки; показать топ-100; показать моё место |
| **Нефункциональные** (non-functional) | Насколько хорошо она должна это делать? | Топ-100 загружается быстрее чем за 200 мс; доступность 99,9%; новые очки могут появиться через несколько секунд |

Архитектуру определяют нефункциональные требования. «Показать топ-100» легко сделать на ноутбуке. «Показывать топ-100 трём тысячам человек в секунду быстрее чем за 200 мс, даже когда падает сервер» — это уже задача проектирования систем.

Запишите и то, что **не входит в рамки** (out of scope) проекта: «списка друзей в первой версии нет». Это держит обсуждение в фокусе и не даёт архитектуре потихоньку разрастись до размеров, которые никто не сможет построить.

## Прикидочные расчёты

Прежде чем выбирать технологии, оцените **нагрузку (load)**. Точность не нужна, нужен правильный порядок величины: 10 запросов в секунду или 10 000? Для этого нужны очень разные системы. Такие оценки называют расчётами «на обратной стороне конверта» (back-of-the-envelope maths).

<CodeExample output={`Записей очков в день:  10,000,000
В среднем записей/с:   116
Пик записей/с:         347
Пик чтений/с:          3,472
Данных за год:         365 GB`}>

```python
daily_users = 2_000_000
games_per_user = 5
seconds_per_day = 86_400

writes_per_day = daily_users * games_per_user
avg_writes = writes_per_day / seconds_per_day
peak_writes = avg_writes * 3        # по вечерам нагрузка выше
peak_reads = peak_writes * 10       # 10 чтений на одну запись

bytes_per_score = 100
gb_per_year = writes_per_day * 365 * bytes_per_score / 1e9

print(f"Записей очков в день:  {writes_per_day:,}")
print(f"В среднем записей/с:   {avg_writes:,.0f}")
print(f"Пик записей/с:         {peak_writes:,.0f}")
print(f"Пик чтений/с:          {peak_reads:,.0f}")
print(f"Данных за год:         {gb_per_year:,.0f} GB")
```

</CodeExample>

О чём говорят эти числа: несколько сотен записей в секунду — нормальная нагрузка для одной хорошо настроенной базы данных. Тысячи чтений в секунду **одного и того же** списка топ-100 — сильный намёк, что нам нужен **кэш (cache)**. А 365 ГБ в год помещаются на один диск, значит, шардирование в первый же день не понадобится.

Несколько чисел, которые стоит запомнить:

| Правило | Значение |
| --- | --- |
| Секунд в сутках | 86 400 (около 10⁵) |
| Чтение из памяти | ~100 наносекунд |
| Чтение с SSD | ~100 микросекунд (в 1000 раз медленнее памяти) |
| Сетевой запрос туда и обратно внутри одного дата-центра | ~0,5 мс |
| Туда и обратно Европа ↔ США | ~80–150 мс |
| Один веб-воркер на Python | сотни простых запросов в секунду |

<Callout type="tip" title="Пик, а не среднее">

Трафик никогда не бывает ровным. Игра достигает пика вечером, магазин — в «чёрную пятницу», новостной сайт — когда что-то случилось. Проектируйте под **пик** (часто в 2–10 раз выше среднего) и называйте свой множитель вслух, чтобы другие могли его оспорить.

</Callout>

## Вертикальное и горизонтальное масштабирование

Когда одного сервера мало, есть два варианта **масштабирования (scaling)**:

| | **Вертикальное** (scale up) | **Горизонтальное** (scale out) |
| --- | --- | --- |
| Что это | Машина мощнее: больше CPU, RAM | Больше машин того же размера |
| Плюсы | Код менять не нужно, просто | Почти нет верхнего предела, переживает падение машины |
| Минусы | Есть самая большая машина; всё ещё одна точка отказа | Нужен балансировщик нагрузки, серверы должны быть **stateless** |
| Подходит для | Баз данных (поначалу), быстрых решений | Веб- и API-серверов, воркеров |

Ответ уровня senior обычно звучит как «и то и другое»: масштабируйте базу данных вертикально, пока это дёшево, а stateless API-серверы — горизонтально с самого начала.

**Stateless** (без состояния) означает, что сервер не хранит ничего важного в своей памяти между запросами: сессии лежат в общем хранилище (базе данных или Redis), файлы — в объектном хранилище (например, S3). Тогда любой сервер может обработать любой запрос, а серверы можно свободно добавлять и убирать.

## Балансировщики нагрузки

**Балансировщик нагрузки (load balancer, LB)** стоит перед вашими серверами и распределяет между ними запросы. Ещё он выполняет **проверки здоровья (health checks)** — например, обращается к `/health` каждые несколько секунд — и перестаёт отправлять трафик на сервер, который не отвечает.

```text
                  ┌──▶ [ app-1 ] ──┐
 клиенты ──▶ [LB] ┼──▶ [ app-2 ] ──┼──▶ [ база данных ]
                  └──▶ [ app-3 ] ──┘
```

Два распространённых способа выбрать сервер:

<CodeExample output={`['app-1', 'app-2', 'app-3', 'app-1', 'app-2']
app-2`}>

```python
from itertools import cycle

class RoundRobin:
    def __init__(self, servers):
        self._next = cycle(servers)

    def pick(self):
        return next(self._next)

def least_connections(active):
    return min(active, key=active.get)

lb = RoundRobin(["app-1", "app-2", "app-3"])
print([lb.pick() for _ in range(5)])

active = {"app-1": 12, "app-2": 3, "app-3": 7}
print(least_connections(active))
```

</CodeExample>

**Round robin** (по кругу) выбирает серверы по очереди и отлично работает, когда запросы похожи друг на друга. **Least connections** (наименьшее число соединений) отправляет следующий запрос на наименее загруженный сервер, что помогает, когда некоторые запросы медленные. На практике это настраивают в nginx, HAProxy или облачном балансировщике, а не пишут сами, но теперь вы знаете, что означает эта настройка.

## Кэширование

**Кэш (cache)** хранит копию данных там, где их быстрее достать (в памяти, в Redis), чтобы не вычислять и не читать их заново каждый раз. Самый распространённый шаблон — **cache-aside** (его ещё называют «ленивой загрузкой», lazy loading): приложение сначала заглядывает в кэш и идёт в базу данных только при **промахе (miss)**. Если значение нашлось в кэше, это **попадание (hit)**.

```text
 get(user 1)
     │
     ▼
 ┌────────┐ попадание ┌──────────────────┐
 │  кэш   │─────────▶ │ вернуть значение │
 └────────┘           └──────────────────┘
     │ промах
     ▼
 ┌────────┐           ┌──────────────────┐
 │   БД   │─────────▶ │ сохранить в кэш  │──▶ вернуть значение
 └────────┘           └──────────────────┘
```

<CodeExample output={`['mei', 'kai', 'mei', 'mei', 'luna', 'kai', 'mei']
Запросов: 7, чтений из БД: 3
mei-mei | чтений из БД: 4`}>

```python
db = {1: "mei", 2: "kai", 3: "luna"}
db_reads = 0
cache = {}

def load_name(user_id):
    global db_reads
    db_reads += 1
    return db[user_id]

def get_name(user_id):
    if user_id in cache:              # 1. пробуем кэш
        return cache[user_id]
    name = load_name(user_id)         # 2. промах: спрашиваем БД
    cache[user_id] = name             # 3. запоминаем
    return name

def rename(user_id, new_name):
    db[user_id] = new_name            # сначала пишем в БД
    cache.pop(user_id, None)          # потом удаляем копию из кэша

requests = [1, 2, 1, 1, 3, 2, 1]
names = [get_name(uid) for uid in requests]
print(names)
print(f"Запросов: {len(requests)}, чтений из БД: {db_reads}")

rename(1, "mei-mei")
print(get_name(1), "| чтений из БД:", db_reads)
```

</CodeExample>

Семь запросов и всего три чтения из базы данных: **доля попаданий (hit ratio)** — 4/7. В таблице рекордов PandaRun, где тысячи людей читают один и тот же топ-100, доля попаданий была бы близка к 100%.

Самое сложное — поддерживать кэш **свежим**. Есть известная шутка: две самые сложные вещи в информатике — это инвалидация кэша, именование и ошибки на единицу. Ваши основные инструменты:

| Инструмент | Как работает | Компромисс |
| --- | --- | --- |
| **TTL** (time to live, время жизни) | Каждая запись истекает через N секунд | Просто и само восстанавливается, но данные могут устареть до N секунд |
| **Инвалидация при записи** (invalidate on write) | Когда данные меняются, ключ удаляется из кэша (как в `rename` выше) | Данные свежие, но каждый путь записи должен об этом помнить |
| **Оба способа** | Инвалидация при записи плюс TTL как страховка | Так делает большинство реальных систем |

Обратите внимание на порядок в `rename`: **сначала** пишем в базу данных, потом удаляем запись из кэша. Если сделать наоборот, другой запрос может между этими двумя шагами снова положить в кэш старое значение.

<Callout type="warning" title="Кэши скрывают проблемы — до поры до времени">

Однажды команда перезапустила все свои узлы Redis одновременно. Кэш опустел, все запросы разом пошли в базу данных, и база упала. Это называется **лавиной кэша (cache stampede)**. Кэш, без которого система не выживает, — уже не оптимизация, а критическая зависимость. Защищайте базу данных лимитами, прогревайте кэш постепенно и добавляйте к TTL небольшие случайные сдвиги, чтобы ключи не истекали все одновременно.

</Callout>

## Реплики и шардирование базы данных

Базу данных обычно масштабировать сложнее всего, потому что в ней хранится **состояние (state)**. Есть два инструмента — в том порядке, в котором к ним стоит обращаться:

**Реплики для чтения (read replicas).** Одна **основная (primary)** база данных принимает все записи и передаёт изменения одной или нескольким **репликам (replicas)**, которые обслуживают чтение. Это идеально для приложений, где чтений намного больше, чем записей, — как PandaRun. Подвох — **задержка репликации (replication lag)**: реплика может отставать на доли секунды, поэтому игрок, который только что отправил очки, может их ещё не увидеть, если читать с реплики. Частое решение — «свои собственные записи читать с основной базы» (read your own writes).

```text
            запись                       чтение
 app ───────────────▶ [ основная ] ─┬─▶ [ реплика 1 ] ◀── app
                                    └─▶ [ реплика 2 ] ◀── app
                       (репликация, с небольшой задержкой)
```

**Шардирование (sharding)**, или партиционирование. Когда данных или записей слишком много для одной машины, их делят: каждый **шард (shard)** хранит часть данных, а часть выбирается по **ключу шардирования (shard key)**, например по id пользователя.

<CodeExample output={`mei -> шард 1
kai -> шард 0
luna -> шард 2
bao -> шард 0
Добавление 4-го шарда перемещает 74% пользователей`}>

```python
import zlib

def shard_for(key, shards):
    return zlib.crc32(key.encode()) % shards

for user in ["mei", "kai", "luna", "bao"]:
    print(user, "-> шард", shard_for(user, 3))

users = [f"user{i}" for i in range(10_000)]
moved = sum(shard_for(u, 3) != shard_for(u, 4) for u in users)
print(f"Добавление 4-го шарда перемещает {moved / len(users):.0%} пользователей")
```

</CodeExample>

В этом примере спрятаны два урока. Во-первых, мы используем `zlib.crc32`, а не встроенную в Python `hash()`: `hash()` от строки меняется при каждом запуске Python (это защитная мера), поэтому разные серверы не договорились бы, где живёт пользователь. Во-вторых, простое `hash % n` означает, что добавление одного шарда перемещает примерно три четверти данных. Реальные системы используют **консистентное хеширование (consistent hashing)** или таблицу диапазонов ключей, чтобы при добавлении шарда переезжала только небольшая часть.

Шардирование — мощный, но дорогой инструмент: запросы между шардами, соединения таблиц (joins) и транзакции становятся сложнее. Считайте его крайней мерой — после индексов, кэширования, реплик и более мощной машины.

## Очереди и фоновые воркеры

Часть работы не обязательно делать, пока пользователь ждёт: отправку писем, уменьшение картинок, пересчёт рейтингов. Положите **задачу (job)** в **очередь (queue)** и сразу верните ответ (HTTP-статус **202 Accepted**). Отдельные процессы-**воркеры (workers)** забирают задачи из очереди и делают медленную часть.

```text
 API ──положить──▶ [ очередь ] ──взять──▶ воркер 1
                        │      └─взять──▶ воркер 2
              (задачи ждут здесь, пока воркеры заняты)
```

<CodeExample output={`{'status': 202, 'queued': 1}
{'status': 202, 'queued': 2}
обновляю рейтинг: mei 4200
обновляю рейтинг: kai 3100
осталось задач: 0`}>

```python
from collections import deque

jobs = deque()

def submit_score(player, score):
    """Эндпоинт API: быстрый, только ставит работу в очередь."""
    jobs.append({"player": player, "score": score})
    return {"status": 202, "queued": len(jobs)}

def worker():
    """Работает в другом месте и делает медленную часть."""
    while jobs:
        job = jobs.popleft()
        print(f"обновляю рейтинг: {job['player']} {job['score']}")

print(submit_score("mei", 4200))
print(submit_score("kai", 3100))
worker()
print("осталось задач:", len(jobs))
```

</CodeExample>

Ещё очередь **сглаживает всплески**: если за одну секунду приходит 10 000 результатов, они ждут в очереди, а воркеры постепенно их разбирают, вместо того чтобы вся нагрузка разом обрушилась на базу данных. В продакшене очередь — это отдельный сервис (RabbitMQ, Redis, Amazon SQS, Kafka), а воркеры используют библиотеку вроде Celery, RQ, Dramatiq или arq. Заранее продумайте две вещи: задача может выполниться **больше одного раза** (поэтому делайте задачи безопасными для повтора — это будет в следующем уроке), а задачи, которые падают снова и снова, попадают в **очередь недоставленных сообщений (dead-letter queue)**, где на них посмотрит человек.

## CAP простыми словами

Когда данные лежат на нескольких машинах, сеть между ними иногда будет отказывать — это называется **разделением сети (partition)**. В такой момент машина, которая не может связаться с остальными, должна выбрать:

- **Согласованность (Consistency, C):** отказаться отвечать (или вернуть ошибку), чтобы не рисковать выдать устаревшие данные.
- **Доступность (Availability, A):** всё равно ответить тем, что есть, даже если данные могли устареть.

Это и есть **теорема CAP**: во время разделения сети (**P**artition) вы получаете **C** или **A**, но не оба. Когда сеть в порядке, можно иметь и то и другое. Это не экзотическая теория, а продуктовое решение:

| Данные | Лучший выбор | Почему |
| --- | --- | --- |
| Баланс счёта, остатки товара в магазине | Согласованность | Продать последний товар дважды — это реальные деньги |
| Таблица рекордов, лайки, счётчики просмотров | Доступность | Отставание на несколько секунд допустимо |
| Корзина покупок | Доступность | Слегка устаревшая корзина лучше страницы с ошибкой |

Системы, которые выбирают доступность, обычно **согласованы в конечном счёте (eventually consistent)**: реплики могут недолго расходиться, но догоняют друг друга, когда сеть восстанавливается. Для PandaRun требование «новые очки могут появиться через несколько секунд» — это именно такой выбор, записанный явно.

Допишите класс `CacheAside`, чтобы он действительно кэшировал. Часы **внедряются** снаружи: класс вызывает `self.clock()`, чтобы узнать время, поэтому тесты могут использовать `FakeClock` вместо того, чтобы ждать настоящие секунды (в продакшене вы бы передали `time.monotonic`).

1. `get(key)`: если ключ есть в кэше и запись ещё свежая, засчитайте **попадание** и верните значение из кэша. Иначе засчитайте **промах**, вызовите `self.load(key)`, сохраните значение вместе со временем истечения (`now + ttl`) и верните его.
2. Запись свежая, пока `now < expires_at`, то есть ровно через `ttl` секунд она уже истекла.
3. `invalidate(key)`: забудьте ключ. Инвалидация ключа, которого нет в кэше, не должна приводить к ошибке.

```python
class FakeClock:
    """Часы для тестов: время идёт, только когда мы скажем."""
    def __init__(self):
        self.now = 0.0

    def time(self):
        return self.now

    def advance(self, seconds):
        self.now += seconds


class CacheAside:
    def __init__(self, load, ttl, clock):
        self.load = load      # функция: ключ -> значение (медленная)
        self.ttl = ttl        # сколько секунд запись остаётся свежей
        self.clock = clock    # функция: -> текущее время
        self.hits = 0
        self.misses = 0
        self._entries = {}    # ключ -> (значение, expires_at)

    def get(self, key):
        now = self.clock()
        entry = self._entries.get(key)
        if entry is not None:
            value, expires_at = entry
            if now < expires_at:
                self.hits += 1
                return value
        self.misses += 1
        value = self.load(key)
        self._entries[key] = (value, now + self.ttl)
        return value

    def invalidate(self, key):
        self._entries.pop(key, None)


prices = {"tea": 3.5, "mug": 8.0}
clock = FakeClock()
cache = CacheAside(lambda item: prices[item], ttl=60,
                   clock=clock.time)

print(cache.get("tea"), cache.get("tea"))   # промах, попадание
prices["tea"] = 4.0
clock.advance(30)
print(cache.get("tea"))                     # всё ещё в кэше: 3.5
clock.advance(30)
print(cache.get("tea"))                     # истекло: 4.0
prices["mug"] = 9.0
cache.invalidate("mug")
print(cache.get("mug"))                     # 9.0
print("попаданий:", cache.hits, "промахов:", cache.misses)
```

## Итоги

- Начинайте с **функциональных** и **нефункциональных** требований (и того, что не входит в рамки); архитектуру определяют нефункциональные.
- **Прикидочные расчёты** (запросы в секунду в пик, объём данных за год) показывают порядок величины и то, какие проблемы у вас действительно есть.
- **Вертикальное масштабирование** — машина мощнее, **горизонтальное** — больше машин за **балансировщиком нагрузки**; для горизонтального серверы должны быть **stateless**.
- **Cache-aside**: проверьте кэш, при промахе загрузите из БД и сохраните. Поддерживайте свежесть с помощью **TTL** и **инвалидации при записи** и остерегайтесь лавины кэша.
- **Реплики для чтения** распределяют чтения (следите за задержкой репликации); **шардирование** делит данные по ключу шардирования и остаётся крайней мерой.
- **Очереди и воркеры** выносят медленную работу из запроса и сглаживают всплески трафика; задачи могут выполниться дважды.
- **CAP**: во время разделения сети выбирайте согласованность или доступность — отдельно для каждого вида данных.
