В какой-то момент ваш главный вклад перестаёт быть кодом, который вы пишете сами. Им становятся баги, которые вы ловите в чужих пул-реквестах (pull requests), архитектура, о которой вы договорились до того, как кто-то написал хоть строчку, и junior-разработчики, которые стали вдвое сильнее, потому что вы им помогли. Это и есть **техническое лидерство (technical leadership)**, и чтобы начать им заниматься, должность «лида» не нужна. Этот урок — практический набор инструментов: на что смотреть на ревью, как об этом говорить, шаблон дизайн-документа, технический долг, оценки сроков и менторство. 🧭

## Зачем нужно код-ревью

**Код-ревью (code review)** — это не шлагбаум, у которого senior-разработчики доказывают, какие они умные. У него три задачи:

1. **Ловить проблемы**, пока их дёшево исправить: баги, дыры в безопасности, архитектурные решения, которые навредят позже.
2. **Делиться знаниями**: теперь этот код понимают как минимум два человека, а автор узнаёт соглашения команды (и ревьюер тоже!).
3. **Сохранять единообразие кодовой базы**, чтобы следующий человек мог в ней сориентироваться.

Смотрите на код примерно в таком порядке. Если неверна сама архитектура, шлифовать имена переменных пока нет смысла:

| Область | Какие вопросы задать |
| --- | --- |
| **Корректность** | Делает ли код то, что написано в задаче? Граничные случаи: пусто, `None`, ноль, дубликаты, очень большие входные данные, два запроса одновременно? |
| **Архитектура** | Находится ли код в правильном месте? Вписывается ли в архитектуру? Он проще, чем мог бы быть, или универсальнее, чем нужно? |
| **Тесты** | Покрывают ли тесты новое поведение и граничные случаи? Упадут ли они, если код сломать? |
| **Безопасность** | Проверяется ли пользовательский ввод? Нет ли SQL, собранного через f-строки, секретов в коде, персональных данных в логах? |
| **Эксплуатация** | Есть ли тайм-ауты у сетевых вызовов? Полезные логи и метрики? Безопасная миграция и откат? |
| **Читаемость** | Говорят ли имена, что они обозначают? Поймёт ли код новичок? Есть ли комментарий о том, *почему* сделано так? |
| **Производительность** | Только там, где это важно: запросы в цикле (N+1), загрузка всего подряд в память. |

Форматирование и порядок импортов оставьте инструментам (ruff, black, isort), которые запускаются в CI. Людям не стоит тратить время ревью на то, что может проверить машина.

## Читаем код как ревьюер

Некоторые баги легко пропустить, когда читаешь код в настроении «вроде всё нормально». Вот классика, которая проскочила через множество ревью:

<CodeExample output={`['срочно']
['срочно', 'баг']
['срочно']
['баг']`}>

```python
def add_tag(tag, tags=[]):
    tags.append(tag)
    return tags

print(add_tag("срочно"))
print(add_tag("баг"))       # совершенно новый список... правда же?

def add_tag_fixed(tag, tags=None):
    if tags is None:
        tags = []           # новый список при каждом вызове
    tags.append(tag)
    return tags

print(add_tag_fixed("срочно"))
print(add_tag_fixed("баг"))
```

</CodeExample>

Значение по умолчанию `[]` создаётся **один раз**, когда определяется функция, и потом его разделяют все вызовы. Ревьюер, который знает типичных подозреваемых (изменяемые значения по умолчанию, циклы с ошибкой на единицу, пропущенный `await`, `try`, который глотает любые исключения, сравнение чисел с плавающей точкой через `==`, переменная, которой значение присваивается только внутри `if`), замечает их за секунды. Когда вы нашли такой баг, лучший комментарий на ревью просит написать **тест**, который доказывает баг, — чтобы он больше никогда не вернулся.

## Пишем доброжелательные и конкретные замечания

Вот пул-реквест, очень похожий на настоящий:

```python
# PR #482: "Добавить промокоды в оформление заказа"
def apply_discount(order, code):
    d = DISCOUNTS[code]
    order.total = order.total - order.total * d / 100
    log.info(f"applied {code} to {order}")
    return order
```

А вот комментарии на ревью, которые помогают автору, а не просто его оценивают. Метка в начале (из соглашения под названием **Conventional Comments**) сообщает автору, насколько важен каждый комментарий:

- **issue (blocking):** `DISCOUNTS[code]` выбрасывает `KeyError` для неизвестного кода, и пользователь видит ошибку 500. Может, будем возвращать 400 «неизвестный промокод» — и добавим на это тест?
- **question:** Что будет, если один и тот же код применить дважды? Насколько я вижу, сумма каждый раз снова уменьшается. Так и задумано?
- **suggestion:** Если переименовать `d` → `percent_off`, строка 3 будет читаться как бизнес-правило. И ещё: деньги во `float` могут давать результаты вроде `29.990000000000002`; в остальном коде оформления заказа мы используем `Decimal`.
- **issue:** Если логировать весь `order`, в наши логи может попасть адрес клиента. Достаточно логировать `order.id`.
- **nit (non-blocking):** У нас логирование принято писать так: `log.info("applied %s to %s", code, order.id)`.
- **praise:** То, что функция возвращает заказ, делает её очень удобной для тестирования. 👍

Метки означают: **issue** — проблема (blocking — блокирует слияние), **question** — вопрос, **suggestion** — предложение, **nit** — мелочь (non-blocking — не блокирует), **praise** — похвала. Почему эти комментарии хороши:

| Вместо... | Попробуйте... | Почему |
| --- | --- | --- |
| «Это неправильно». | «Здесь `KeyError` для неизвестных кодов; может, вернём 400?» | Говорит, **что** не так и **почему**, и предлагает путь вперёд |
| «Зачем вы вообще так сделали??» | «Почему вы выбрали X, а не Y? Я бы ожидал Y, потому что...» | Вопросы приглашают к обсуждению; возможно, автор знает то, чего не знаете вы |
| «Вы забыли тесты». | «Может, добавим тест для просроченного кода?» | Про **код**, а не про человека |
| Двадцать мелочей и никакого итога | «В целом хорошо; две блокирующие проблемы, остальное — мелочи» | Автор понимает, что действительно важно |
| Молчание, когда работа хорошая | «Здорово, стало гораздо понятнее, чем было» | Похвала подсказывает людям, что стоит делать и дальше |

Если вы **автор**: делайте пул-реквесты маленькими (меньше ~400 строк — хорошая цель; большие PR пролистывают, а не ревьюят), пишите описание (что, зачем, как проверить, скриншоты), сначала сами просмотрите свой diff и воспринимайте комментарии как замечания о коде. Если вы **ревьюер**: отвечайте в течение дня, одобряйте с мелкими замечаниями, когда остались только мелочи, а длинные споры переносите в короткий созвон.

<Callout type="tip" title="Начинайте ревью с тестов">

Многие опытные ревьюеры читают тесты **раньше** кода. Тесты рассказывают, что, по мнению автора, должен делать код. Если по тестам этого не понять — это ваш первый комментарий, и он часто сразу же выявляет пропущенный граничный случай.

</Callout>

## Дизайн-документы и RFC

Для всего, что занимает больше нескольких дней, затрагивает несколько команд или что трудно отменить (новый сервис, изменение базы данных, публичный API), напишите короткий **дизайн-документ (design doc)** — в некоторых компаниях его называют **RFC** («request for comments», запрос комментариев) — **до** того, как начнёте строить. Десять минут обсуждения документа экономят недели переписывания кода. А ещё он заставляет всё продумать: многие идеи разваливаются прямо во время написания раздела «альтернативы».

Шаблон, который хорошо работает (1–3 страниц вполне достаточно):

```markdown
# Дизайн: глобальная таблица рекордов для PandaRun

Автор: Mei · Ревьюеры: Kai, Luna · Статус: на ревью

## Контекст
Какую проблему мы решаем и почему сейчас? Ссылка на задачу.

## Цели и не-цели
- Цель: топ-100 загружается быстрее 200 мс при 3500 чтениях/с
- Не цель: таблицы рекордов среди друзей (позже)

## Предложение
Как это работает: компоненты, модель данных, API, схема.

## Оценки
Трафик, объём данных, стоимость (прикидочные расчёты).

## Рассмотренные альтернативы
Что ещё мы рассматривали и почему не выбрали.

## Риски и открытые вопросы
Что может пойти не так? Чего мы пока не знаем?

## Выкатка и тестирование
Флаг функциональности, план миграции, метрики для наблюдения, откат.
```

Два самых ценных раздела — **не-цели (non-goals)**: они не дают проекту разрастаться, — и **рассмотренные альтернативы (alternatives considered)**: они показывают, что вы не просто взяли первую попавшуюся идею, и избавляют следующего человека от необходимости исследовать всё заново. После принятия решения сохраните в репозитории короткую **ADR** (architecture decision record, запись об архитектурном решении): одну страницу о том, что решили и почему. Через год на вопрос «почему, ради всего святого, это так устроено?» найдётся ответ.

## Технический долг

**Технический долг (tech debt)** — это дополнительная цена изменения кода, который писали в спешке или который со временем запутался: каждая новая функция в этой области занимает больше времени, как проценты по кредиту. Не всякий долг плох. «Квадрант технического долга» Мартина Фаулера (Martin Fowler) раскладывает его так:

| | Безрассудный (reckless) | Благоразумный (prudent) |
| --- | --- | --- |
| **Намеренный** (deliberate) | «У нас нет времени на тесты». | «Выпустим сейчас и приберёмся после запуска». (и это записано!) |
| **Случайный** (inadvertent) | «Что такое слоистая архитектура?» | «Теперь мы знаем, как *надо было* это построить». |

Благоразумный намеренный долг — это бизнес-инструмент, как и кредит. Проблема — в долге, который никто не отслеживает. Что работает на практике:

- **Сделайте долг видимым.** Держите задачи по техдолгу в бэклоге и указывайте **цену** на языке команды: «каждое изменение цен занимает 3 дня вместо 1».
- **Гасите понемногу.** Улучшайте код, который вы и так трогаете ради новой функции («правило бойскаута»: оставьте код чуть чище, чем он был).
- **Резервируйте время.** Многие команды тратят на долг 10–20% каждого спринта, вместо того чтобы надеяться на «месяц уборки», который так и не наступит.
- **Расставляйте приоритеты по боли:** сначала код, который часто меняется и часто ломается. Некрасивый код, который никто не трогает, может ждать вечно.

## Оценки сроков

Оценки ошибаются по предсказуемым причинам: мы представляем себе счастливый сценарий, забываем про тестирование, ревью и развёртывание и называем одно число, которое звучит как обещание. Две привычки исправляют большую часть проблем: **разбивайте работу** на кусочки по день-два и **называйте диапазон**. **Трёхточечная оценка (three-point estimate)** — лучший случай, наиболее вероятный, худший — простой способ получить и то и другое:

<CodeExample output={`Эндпоинт API     2.2 дн.
Миграция БД      1.2 дн.
Тесты + ревью    1.7 дн.
Выкатка          1.4 дн.
Итого            6.5 дн.
Говорите: от 5 до 8 дней`}>

```python
def pert(best, likely, worst):
    """Трёхточечная оценка: ожидаемое значение и разброс."""
    expected = (best + 4 * likely + worst) / 6
    spread = (worst - best) / 6
    return expected, spread

tasks = {
    "Эндпоинт API": (1, 2, 4),
    "Миграция БД": (0.5, 1, 3),
    "Тесты + ревью": (1, 1.5, 3),
    "Выкатка": (0.5, 1, 4),
}

total = 0
total_spread = 0
for name, (best, likely, worst) in tasks.items():
    expected, spread = pert(best, likely, worst)
    total += expected
    total_spread += spread
    print(f"{name:<15}{expected:>5.1f} дн.")

low, high = total - total_spread, total + total_spread
print(f"{'Итого':<15}{total:>5.1f} дн.")
print(f"Говорите: от {low:.0f} до {high:.0f} дней")
```

</CodeExample>

Это формула **PERT**: наиболее вероятный случай учитывается четыре раза, а худший тянет оценку вверх — и это честно, потому что дела редко идут *лучше*, чем планировалось. (Если просто сложить разбросы, получится намеренно осторожный диапазон.) Обратите внимание, что в списке есть «Тесты + ревью» и «Выкатка»: именно про эти части люди забывают. А если на полпути вы узнали что-то новое, обновите оценку и сообщите об этом заранее. Сюрприз на второй день — это разговор; сюрприз в день дедлайна — это кризис.

## Менторство junior-разработчиков

Команда с одним блестящим senior и тремя застрявшими junior работает медленнее, чем команда, где растут все. Что работает:

- **Программируйте в паре и давайте им вести.** Вы штурман и задаёте вопросы, а печатают они. Люди учатся, делая сами, а не глядя, как быстро работаете вы.
- **Сначала спросите, потом подскажите.** «Как думаете, что будет, если список пустой?» учит большему, чем «добавь проверку на пустой список». А потом дайте им найти ответ.
- **Объясняйте, почему.** «Мы внедряем часы, *чтобы тесты не ждали 60 секунд*» запоминается; «всегда внедряй часы» — нет.
- **Давайте задачи на вырост со страховкой.** Чуть сложнее, чем по силам, но вы рядом. Хорошие первые задачи — настоящие, небольшие и чётко поставленные.
- **Сделайте так, чтобы спрашивать было не страшно.** Сами говорите «Не знаю, давайте выясним». Junior, которые боятся спрашивать, теряют дни, молча застряв на месте.
- **Ревьюйте великодушно.** В пул-реквесте junior выберите 2–3 самых важных момента и объясните их; не хороните их под мелочами.
- **Хвалите публично, критикуйте наедине.**

<Callout type="note" title="Лидерство без должности">

Написать дизайн-документ, о котором никто не просил, починить нестабильный тест, который все игнорируют, ввести в курс дела новичка, сказать на планировании «по-моему, мы это недооцениваем» — так техническое лидерство выглядит в повседневной работе. Senior-инженеров оценивают не столько по их собственной выработке, сколько по тому, насколько лучше работает команда благодаря их присутствию.

</Callout>

Для демонстрационных заказов она должна дважды напечатать `{'orders': 3, 'total': 45.3, 'average': 15.1, 'top_customer': 'mei'}`. Заодно дайте переменным имена, которые говорят, что в них хранится, и уберите параметр `seen` (вызывающему коду не нужно о нём знать).

```python
def summarise_orders(orders):
    """Количество, сумма, среднее и лучший клиент по учтённым заказам.

    Заказ, присланный дважды (тот же id), учитывается один раз;
    отменённые заказы не учитываются. Деньги округляются до 2 знаков.
    """
    seen_ids = set()
    spent_by_customer = {}
    count = 0
    total = 0
    for order in orders:
        if order["id"] in seen_ids:
            continue
        seen_ids.add(order["id"])
        if order["status"] == "cancelled":
            continue
        count += 1
        total += order["amount"]
        customer = order["customer"]
        spent_by_customer[customer] = (
            spent_by_customer.get(customer, 0) + order["amount"]
        )

    average = total / count if count else 0
    top_customer = max(spent_by_customer,
                       key=spent_by_customer.get, default=None)
    return {
        "orders": count,
        "total": round(total, 2),
        "average": round(average, 2),
        "top_customer": top_customer,
    }
```
