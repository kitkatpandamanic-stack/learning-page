At some point your biggest impact stops being the code you type yourself. It becomes the bugs you catch in other people's pull requests, the design you agree on before anyone writes a line, and the juniors who get twice as good because you helped them. That's **technical leadership**, and you don't need a "lead" title to start doing it. This lesson is a practical kit: what to look for in a review, how to say it, a design doc template, tech debt, estimates and mentoring. 🧭

## What code review is for

Code review is not a gate where seniors prove they're clever. It has three jobs:

1. **Catch problems** while they're cheap to fix: bugs, security holes, designs that will hurt later.
2. **Share knowledge**: at least two people now understand this code, and the author learns the team's conventions (so does the reviewer!).
3. **Keep the codebase consistent**, so the next person can find their way around.

Look at things roughly in this order. If the design is wrong, there's no point polishing variable names yet:

| Area | Questions to ask |
| --- | --- |
| **Correctness** | Does it do what the ticket says? Edge cases: empty, `None`, zero, duplicates, very large inputs, two requests at once? |
| **Design** | Is it in the right place? Does it fit the architecture? Is it simpler than it could be, or more general than needed? |
| **Tests** | Do tests cover the new behaviour and the edge cases? Would they fail if the code were broken? |
| **Security** | Is user input validated? Any SQL built with f-strings, secrets in code, personal data in logs? |
| **Operability** | Timeouts on network calls? Useful logs and metrics? A safe migration and rollback? |
| **Readability** | Do names say what things are? Would a newcomer understand it? Is there a comment for the *why*? |
| **Performance** | Only where it matters: queries in loops (N+1), loading everything into memory. |

Leave formatting and import order to tools (ruff, black, isort) running in CI. Humans shouldn't spend review time on what a machine can check.

## Reading code like a reviewer

Some bugs are easy to miss when you read code in the "it looks fine" mood. Here's a classic that has slipped past many reviews:

<CodeExample output={`['urgent']
['urgent', 'bug']
['urgent']
['bug']`}>

```python
def add_tag(tag, tags=[]):
    tags.append(tag)
    return tags

print(add_tag("urgent"))
print(add_tag("bug"))       # a brand-new list... right?

def add_tag_fixed(tag, tags=None):
    if tags is None:
        tags = []           # a new list on every call
    tags.append(tag)
    return tags

print(add_tag_fixed("urgent"))
print(add_tag_fixed("bug"))
```

</CodeExample>

The default `[]` is created **once**, when the function is defined, and then shared by every call. A reviewer who knows the usual suspects (mutable defaults, off-by-one loops, missing `await`, a `try` that swallows every exception, comparing floats with `==`, a variable that's only set inside an `if`) catches them in seconds. When you spot one, the best review comment asks for a **test** that proves the bug, so it can never come back.

## Writing kind, specific feedback

Here's a real-looking pull request:

```python
# PR #482: "Add discount codes to checkout"
def apply_discount(order, code):
    d = DISCOUNTS[code]
    order.total = order.total - order.total * d / 100
    log.info(f"applied {code} to {order}")
    return order
```

And here are review comments that help the author, not just judge them. The label at the start (from a convention called **Conventional Comments**) tells the author how important each one is:

- **issue (blocking):** `DISCOUNTS[code]` raises `KeyError` for an unknown code, which the user sees as a 500 error. Could we return a 400 "unknown discount code" instead, with a test for it?
- **question:** What happens if the same code is applied twice? As far as I can tell the total shrinks again each time. Is that intended?
- **suggestion:** `d` → `percent_off` would make line 3 read like the business rule. Also, money in floats can give results like `29.990000000000002`; we use `Decimal` elsewhere in checkout.
- **issue:** Logging the whole `order` may write the customer's address into our logs. Logging `order.id` is enough.
- **nit (non-blocking):** Our logging style is `log.info("applied %s to %s", code, order.id)`.
- **praise:** Returning the order makes this really easy to test. 👍

What makes these good:

| Instead of... | Try... | Why |
| --- | --- | --- |
| "This is wrong." | "This raises `KeyError` for unknown codes; could we return a 400?" | Says **what** and **why**, and suggests a way forward |
| "Why would you do it like this??" | "What made you choose X over Y? I'd have expected Y because..." | Questions invite a discussion; maybe they know something you don't |
| "You forgot the tests." | "Could we add a test for an expired code?" | About the **code**, not the person |
| Twenty nits, no summary | "Looks good overall; two blocking issues, the rest are nits" | The author knows what really matters |
| Silence on good work | "Nice, this is much clearer than before" | Praise tells people what to keep doing |

And as an **author**: keep pull requests small (under ~400 lines is a good target; big PRs get skimmed, not reviewed), write a description (what, why, how to test, screenshots), review your own diff first, and treat comments as being about the code. As a **reviewer**: respond within a day, approve with nits when only nits are left, and move long debates to a quick call.

<Callout type="tip" title="Review the tests first">

Many experienced reviewers read the tests **before** the code. The tests tell you what the author thinks the code should do. If you can't tell from the tests, that's your first comment, and it often reveals a missing edge case straight away.

</Callout>

## Design docs and RFCs

For anything that takes more than a few days, touches several teams, or is hard to undo (a new service, a database change, a public API), write a short **design doc** (some companies call it an **RFC**, "request for comments") **before** building it. Ten minutes of discussion on a doc saves weeks of rewriting code. It also forces you to think it through: many designs fall apart while you're writing the "alternatives" section.

A template that works well (1–3 pages is plenty):

```markdown
# Design: Global leaderboard for PandaRun

Author: Mei · Reviewers: Kai, Luna · Status: In review

## Context
What problem are we solving, and why now? Link the ticket.

## Goals and non-goals
- Goal: top 100 loads in < 200 ms at 3,500 reads/s
- Non-goal: friends leaderboards (later)

## Proposal
How it works: components, data model, API, a diagram.

## Estimates
Traffic, storage, cost (back-of-the-envelope maths).

## Alternatives considered
What else we looked at and why we didn't pick it.

## Risks and open questions
What could go wrong? What don't we know yet?

## Rollout and testing
Feature flag, migration plan, metrics to watch, rollback.
```

The two most valuable sections are **non-goals** (they stop the project from growing) and **alternatives considered** (they show you didn't just pick the first idea, and they save the next person from re-researching them). After the decision, keep a short **ADR** (architecture decision record) in the repository: one page saying what was decided, and why. A year later, "why on earth is it built like this?" has an answer.

## Tech debt

**Tech debt** is the extra cost of changing code that was written in a hurry or has grown messy: every new feature in that area takes longer, like interest on a loan. Not all debt is bad. Martin Fowler's "debt quadrant" sorts it like this:

| | Reckless | Prudent |
| --- | --- | --- |
| **Deliberate** | "We don't have time for tests." | "We'll ship now and clean up after the launch." (written down!) |
| **Inadvertent** | "What's a layered architecture?" | "Now we know how we *should* have built it." |

Prudent, deliberate debt is a business tool, just like a loan. The problem is debt nobody tracks. What works in practice:

- **Make it visible.** Keep debt tickets in the backlog with the **cost** in the team's language: "every pricing change takes 3 days instead of 1".
- **Pay as you go.** Improve the code you're already touching for a feature (the "boy scout rule": leave it a bit cleaner than you found it).
- **Reserve capacity.** Many teams spend 10–20% of each sprint on debt, instead of hoping for a "clean-up month" that never comes.
- **Prioritise by pain:** code that changes often and breaks often first. Ugly code that nobody touches can wait forever.

## Estimates

Estimates go wrong for predictable reasons: we picture the happy path, forget testing, review and deployment, and give a single number that sounds like a promise. Two habits fix most of it: **break the work down** into pieces of a day or two, and **give a range**. A **three-point estimate** (best case, most likely, worst case) is a simple way to get both:

<CodeExample output={`API endpoint     2.2 days
DB migration     1.2 days
Tests + review   1.7 days
Rollout          1.4 days
Total            6.5 days
Say: 5 to 8 days`}>

```python
def pert(best, likely, worst):
    """Three-point estimate: expected value and spread."""
    expected = (best + 4 * likely + worst) / 6
    spread = (worst - best) / 6
    return expected, spread

tasks = {
    "API endpoint": (1, 2, 4),
    "DB migration": (0.5, 1, 3),
    "Tests + review": (1, 1.5, 3),
    "Rollout": (0.5, 1, 4),
}

total = 0
total_spread = 0
for name, (best, likely, worst) in tasks.items():
    expected, spread = pert(best, likely, worst)
    total += expected
    total_spread += spread
    print(f"{name:<15}{expected:>5.1f} days")

low, high = total - total_spread, total + total_spread
print(f"{'Total':<15}{total:>5.1f} days")
print(f"Say: {low:.0f} to {high:.0f} days")
```

</CodeExample>

This is the **PERT** formula: the most likely case counts four times, and the worst case pulls the estimate up, which is honest, because things rarely go *better* than planned. (Adding up the spreads gives a deliberately cautious range.) Notice that "Tests + review" and "Rollout" are on the list: those are the parts people forget. And when you learn something new halfway through, update the estimate and tell people early. A surprise on day 2 is a conversation; a surprise on the deadline is a crisis.

## Mentoring juniors

A team with one brilliant senior and three stuck juniors is slower than a team where everyone grows. Things that work:

- **Pair, and let them drive.** You navigate and ask questions; they type. People learn by doing, not by watching you be fast.
- **Ask before you tell.** "What do you think happens if the list is empty?" teaches more than "add a check for empty lists". Then let them find it.
- **Explain the why.** "We inject the clock *so the tests don't wait 60 seconds*" sticks; "always inject the clock" doesn't.
- **Give stretch tasks with a safety net.** Slightly too hard, with you available. Good first tasks are real, small and well-defined.
- **Make it safe to ask.** Say "I don't know, let's find out" yourself. Juniors who are afraid to ask lose days being stuck in silence.
- **Review generously.** For a junior's PR, pick the 2–3 most important points, and explain them; don't bury them in nits.
- **Give credit in public, feedback in private.**

<Callout type="note" title="Leadership without a title">

Writing the design doc nobody asked for, fixing the flaky test everyone ignores, onboarding the new person, saying "I think we're underestimating this" in planning: that's what technical leadership looks like day to day. Senior engineers are judged less by their own output and more by how much better the team works because they're there.

</Callout>

A teammate opened a pull request with `summarise_orders`, and you're the reviewer. It "worked on their machine", but it has **at least five bugs**. Fix them and tidy the code up so the next reader understands it. The function should:

- Take a list of orders (dicts with `id`, `customer`, `amount` and `status`) and return a dict with `orders` (how many orders counted), `total`, `average` and `top_customer` (who spent the most).
- Count **every** order in the list, but an order sent twice (the same `id`) only **once**.
- Ignore orders whose status is `"cancelled"`.
- Give the same answer no matter how many times it's called.
- Return `0` for `total` and `average`, and `None` for `top_customer`, when no orders count.
- Round `total` and `average` to 2 decimal places.

For the demo orders it should print `{'orders': 3, 'total': 45.3, 'average': 15.1, 'top_customer': 'mei'}` twice. While you're there, give the variables names that say what they hold, and remove the `seen` parameter (callers shouldn't have to know about it).

<Hint>

The bugs: `range(len(o) - 1)` skips the last order (loop with `for order in orders:`); `"canceled"` is misspelt; `seen=[]` is a mutable default shared between calls (use a local `seen_ids = set()` instead); the average divides by **all** orders, including duplicates and cancelled ones, and crashes on an empty list (divide by the count of valid orders, or use 0); `max()` on an empty dict crashes (`max(spent, key=spent.get, default=None)`); and the money isn't rounded (`round(total, 2)`).

</Hint>

```python
def summarise_orders(orders):
    """Count, total, average and top customer of the valid orders.

    An order sent twice (same id) counts once; cancelled orders
    don't count. Money is rounded to 2 decimal places.
    """
    seen_ids = set()
    spent_by_customer = {}
    count = 0
    total = 0
    for order in orders:
        if order["id"] in seen_ids:
            continue
        seen_ids.add(order["id"])
        if order["status"] == "cancelled":
            continue
        count += 1
        total += order["amount"]
        customer = order["customer"]
        spent_by_customer[customer] = (
            spent_by_customer.get(customer, 0) + order["amount"]
        )

    average = total / count if count else 0
    top_customer = max(spent_by_customer,
                       key=spent_by_customer.get, default=None)
    return {
        "orders": count,
        "total": round(total, 2),
        "average": round(average, 2),
        "top_customer": top_customer,
    }
```

## Recap

- Code review exists to **catch problems**, **share knowledge** and **keep code consistent**; check correctness, design and tests before naming and style, and let tools handle formatting.
- Good review comments are **specific** (what and why), **kind** (about the code, not the person), often **questions**, and **labelled** (issue, suggestion, question, nit, praise).
- Authors keep PRs **small**, describe them well and review their own diff first.
- Write a **design doc** before big or hard-to-undo work: context, goals and **non-goals**, proposal, estimates, **alternatives**, risks, rollout. Record decisions in ADRs.
- **Tech debt** is fine when it's deliberate and visible; pay it down continuously, starting where code changes and breaks most.
- **Estimate** by breaking work down, including tests, review and rollout, and give a **range** (three-point/PERT); update it early.
- **Mentor** by pairing (they drive), asking before telling, explaining why and making it safe to ask.
