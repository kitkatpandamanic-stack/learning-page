Every programmer, from day one to year twenty, writes code that breaks. The difference is that experienced programmers **read the error** instead of panicking. An error message isn't a telling-off: it's Python pointing at the problem and saying what it saw. In this lesson you'll learn to read those messages and track down bugs step by step. 🔍

## Reading a traceback

Here's a small program with a bug. It has three functions calling each other:

```python title="main.py"
def average(scores):
    total = sum(scores)
    return total / len(scores)

def report(name, scores):
    avg = average(scores)
    return f"{name}: {avg}"

print(report("Mei", [80, 90]))
print(report("Sam", []))
```

Running it on your computer prints Mei's line, then a **traceback**:

```text
Mei: 85.0
Traceback (most recent call last):
  File "main.py", line 10, in <module>
    print(report("Sam", []))
          ~~~~~~^^^^^^^^^^^
  File "main.py", line 6, in report
    avg = average(scores)
  File "main.py", line 3, in average
    return total / len(scores)
           ~~~~~~^~~~~~~~~~~~~
ZeroDivisionError: division by zero
```

Read it **from the bottom up**:

1. **The last line** says *what* went wrong: the error type (`ZeroDivisionError`) and a message (`division by zero`).
2. **The lines above** are the **call stack**: the chain of function calls that led there. *Most recent call last* means the bottom one is where Python actually stopped: line 3, inside `average`.
3. Going up, you see **who called whom**: `average` was called by `report` on line 6, which was called on line 10. The `^^^` markers point at the exact piece of code that failed.

So the story is: line 10 called `report` with an empty list, `report` passed it on to `average`, and `average` divided by `len(scores)`, which was `0`.

Notice that `Mei: 85.0` was printed first. Python runs your code from top to bottom, and everything before the crash really happened. On PandaDev, the output shows the last line of the traceback, together with the line number:

<CodeExample output={`Mei: 85.0
ZeroDivisionError: division by zero`}>

```python
def average(scores):
    total = sum(scores)
    return total / len(scores)

def report(name, scores):
    avg = average(scores)
    return f"{name}: {avg}"

print(report("Mei", [80, 90]))
print(report("Sam", []))
```

</CodeExample>

<Callout type="tip" title="Last line first">

When you see red text, read the **last line** first, then find the **line number** in your code. Most of the time, that's all you need.

</Callout>

## The errors you'll meet most

These few error types cover most beginner bugs. Learn what each one *usually* means and you'll often know the fix straight away:

| Error | What it usually means | Example |
| --- | --- | --- |
| `NameError` | A typo in a name, or using a variable before creating it | `print(scroe)` |
| `TypeError` | Mixing types that don't go together, or calling a function with the wrong number of arguments | `"Age: " + 12` |
| `ValueError` | The right type, but a value Python can't use | `int("twelve")` |
| `IndexError` | A list position that doesn't exist | `["cat", "dog"][2]` |
| `KeyError` | A dictionary key that doesn't exist (dictionaries come in Level 1) | `prices["coffee"]` |
| `ZeroDivisionError` | Dividing by zero, often because something was empty | `total / len([])` |
| `SyntaxError` | Python can't even read the code: a missing `:`, bracket or quote | `if x > 3` |
| `IndentationError` | The spaces at the start of a line are wrong | a function body that isn't indented |

The message after the error type gives you the details. A few real examples:

```text
NameError: name 'scroe' is not defined. Did you mean: 'score'?
TypeError: can only concatenate str (not "int") to str
TypeError: area() missing 1 required positional argument: 'height'
ValueError: invalid literal for int() with base 10: 'twelve'
IndexError: list index out of range
```

For typos, Python even suggests a fix: *Did you mean: 'score'?* Read the whole last line: the answer is often right there.

### The sneaky one: None

This `TypeError` confuses almost everyone at first:

```python
def double(n):
    print(n * 2)       # prints, but doesn't return!

x = double(4)
print(x + 1)
```

```text
8
Traceback (most recent call last):
  File "main.py", line 5, in <module>
    print(x + 1)
          ~~^~~
TypeError: unsupported operand type(s) for +: 'NoneType' and 'int'
```

`NoneType` in a message is a big clue: some value is `None`. Here `double` printed `8` but didn't **return** anything, and as you saw in [Writing Functions](/learn/python/writing-functions), a function without `return` gives back `None`. The fix is `return n * 2`.

### Syntax errors: the code never starts

A `SyntaxError` or `IndentationError` happens **before** your program runs, because Python can't understand the code at all. Nothing is printed except the error:

```text
  File "main.py", line 1
    if score > 10
                 ^
SyntaxError: expected ':'
```

```text
  File "main.py", line 2
    print(f"Hello, {name}!")
    ^^^^^
IndentationError: expected an indented block after function definition on line 1
```

<Callout type="warning" title="Look at the line before, too">

With syntax errors, Python reports where it **noticed** the problem, which can be a line or two after the real mistake. If line 5 looks fine, check line 4 for a missing `)` or `"`. A message like `'(' was never closed` is a strong hint.

</Callout>

## A debugging routine

When something goes wrong, don't change random things and hope. Follow the same calm steps every time:

1. **Read the message.** Which error type? What does the message say?
2. **Find the line.** Go to the line number in the traceback. If it's inside a function, look at the line that called it as well.
3. **Print the values.** Look at what your variables *really* contain.
4. **Check your assumptions.** Is that variable the type and size you think it is?
5. **Change one thing at a time**, then run again. Change three things at once and you won't know which one helped (or broke something new).
6. **Explain it to a rubber duck.** More on that below.

### Print the values with `f"{x=}"`

The quickest debugging tool is `print`. An f-string with `=` after the name prints the **name and the value** together, so you don't have to type labels:

<CodeExample output={`price=3 total=3
price=5 total=5
price=2 total=2
2`}>

```python
def total_price(prices):
    for price in prices:
        total = 0
        total += price
        print(f"{price=} {total=}")
    return total

print(total_price([3, 5, 2]))
```

</CodeExample>

The total should be `10`, but the prints show it **starting again** every time round the loop. That points straight at the bug: `total = 0` is inside the loop, so it resets on every item. Move it above the `for` and the function works. Once it's fixed, delete the debugging prints.

### Check your assumptions

Bugs often hide in something you were *sure* about. The `=` form shows strings in quotes, which makes a sneaky type problem easy to spot:

<CodeExample output={`quantity='3'
33
type(quantity)=<class 'str'>`}>

```python
quantity = "3"   # imagine this came from a form
print(f"{quantity=}")
print(quantity * 2)
print(f"{type(quantity)=}")
```

</CodeExample>

The quotes around `'3'` give it away: it's text, not a number, so `* 2` repeats it instead of doubling it. No error, just a wrong answer. `int(quantity)` fixes it. Bugs without an error message are called **logic errors**, and printing values is how you catch them.

<Callout type="tip" title="Rubber duck debugging 🦆">

Explain your code, line by line, out loud, to a rubber duck (or a plant, or a stuffed panda). *"This line sets total to zero, then for each price... oh, it sets it to zero again."* Saying what each line **really** does, not what you meant it to do, finds a surprising number of bugs. Programmers really do this!

</Callout>

## assert: a quick sanity check

`assert` checks that something you believe is true **really is** true. If it is, nothing happens. If it isn't, Python stops with an `AssertionError` and your message:

<CodeExample output={`5.0
All good!`}>

```python
def average(scores):
    assert len(scores) > 0, "average() needs at least one score"
    return sum(scores) / len(scores)

print(average([4, 6]))

assert average([4, 6]) == 5
assert average([1, 2, 3]) == 2
print("All good!")
```

</CodeExample>

Both checks passed silently. Now add `print(average([]))` at the end and run it again:

```text
Traceback (most recent call last):
  File "main.py", line 10, in <module>
    print(average([]))
          ~~~~~~~^^^^
  File "main.py", line 2, in average
    assert len(scores) > 0, "average() needs at least one score"
           ^^^^^^^^^^^^^^^^
AssertionError: average() needs at least one score
```

Instead of a puzzling `ZeroDivisionError` somewhere deep inside, you get a clear message right where the assumption broke. A few `assert` lines after a function, like `assert average([4, 6]) == 5`, are also a cheap way to check it still works after every change.

<Callout type="note" title="assert is for catching your own mistakes">

Use `assert` for things that should **never** happen if your code is right. For problems you expect, like a user typing `"ten"` instead of `10`, check with `if` and show a friendly message. In Level 1, the [Exceptions](/learn/python/exceptions) lesson shows how to catch errors with `try` and `except`, and later you'll write whole test files full of `assert`s.

</Callout>

## Recap

- Read a traceback **bottom up**: the last line is the error type and message; the lines above are the call stack, with the most recent call last.
- `NameError` is usually a typo, `TypeError` mixed types (or `None` from a function that forgot to `return`), `ValueError` a bad value, `IndexError`/`KeyError` a missing position or key.
- `SyntaxError` and `IndentationError` stop the code before it runs; check the line before, too.
- Debugging routine: read the message, find the line, print values with `f"{x=}"`, check assumptions, change one thing at a time, explain it to a duck.
- `assert condition, "message"` stops with an `AssertionError` when something you believe isn't true.
