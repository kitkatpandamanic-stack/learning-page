Two programs can give the same answer, yet one finishes instantly and the other takes all night. The difference usually isn't the computer: it's how the **work grows** when the data gets bigger. **Big-O** is the language programmers use to talk about that growth. You don't need any maths beyond counting. 📈

## Count steps, not seconds

You could time a program with a stopwatch, but the number changes with every computer, and even between two runs on the same one. Instead, we **count the steps** the code takes and ask: *what happens to that count when the input gets 10 times bigger?*

<CodeExample output={`n = 10: 10 steps
n = 100: 100 steps
n = 1000: 1000 steps`}>

```python
def largest(numbers):
    steps = 0
    best = numbers[0]
    for number in numbers:
        steps += 1
        if number > best:
            best = number
    return best, steps

for n in [10, 100, 1000]:
    best, steps = largest(list(range(n)))
    print(f"n = {n}: {steps} steps")
```

</CodeExample>

We call the size of the input **n**. Here the steps grow exactly like `n`: 10 times more numbers means 10 times more work. That's written **O(n)** and read "big O of n", or simply "linear".

## O(1): constant time

Some operations take the same time no matter how big the data is. That's **O(1)**, "constant time":

- reading `items[0]` or `items[500_000]` (Python jumps straight to the position),
- `len(items)` (lists remember their length),
- `items.append(x)` and `items.pop()` at the **end** of a list,
- looking up a key in a dict, or checking `x in some_set` (more on that soon).

Whether the list holds 10 items or 10 million, these are one step each.

## O(n²): loops inside loops

Does a list contain the same value twice? The obvious way compares **every pair** of items, with a loop inside a loop:

<CodeExample output={`n = 10: 45 comparisons
n = 100: 4950 comparisons
n = 1000: 499500 comparisons`}>

```python
def has_duplicates(items):
    comparisons = 0
    found = False
    for i in range(len(items)):
        for j in range(i + 1, len(items)):
            comparisons += 1
            if items[i] == items[j]:
                found = True
    return found, comparisons

for n in [10, 100, 1000]:
    found, count = has_duplicates(list(range(n)))
    print(f"n = {n}: {count} comparisons")
```

</CodeExample>

10 times more items, but **100 times** more work! For each of the `n` items, the inner loop runs through (up to) `n` items again, so the steps grow like `n × n`, written **O(n²)** ("quadratic"). A million items would need about 500 **billion** comparisons.

<Callout type="tip" title="Spotting O(n²)">

A loop over the data **inside** another loop over the same data is the classic sign of O(n²). Watch out for hidden loops too: `x in some_list`, `some_list.index(x)`, `some_list.count(x)` and `some_list.remove(x)` each loop over the list behind the scenes.

</Callout>

## O(log n): halving the problem

Some algorithms throw away **half** of the remaining data at each step, like guessing a number between 1 and 100 when someone tells you "higher" or "lower". How many times can you halve `n` before only one item is left?

<CodeExample output={`8 items: 3 halvings
1,000 items: 9 halvings
1,000,000 items: 19 halvings
1,000,000,000 items: 29 halvings`}>

```python
def halvings(n):
    steps = 0
    while n > 1:
        n = n // 2
        steps += 1
    return steps

for n in [8, 1000, 1_000_000, 1_000_000_000]:
    print(f"{n:,} items: {halvings(n)} halvings")
```

</CodeExample>

A billion items in under 30 steps! That's **O(log n)** ("logarithmic"): multiplying the data by 1000 adds only about 10 steps. You'll write the famous halving algorithm, **binary search**, in the next lesson.

## O(n log n): good sorting

The best general sorting algorithms, including Python's own `sorted()`, take about `n × log n` steps: **O(n log n)**. That's a little more than O(n), and enormously less than O(n²). Here's how the common shapes compare as `n` grows:

<CodeExample output={`n          log n   n log n        n²
10         3       30             100
100        7       700            10,000
1,000      10      10,000         1,000,000
1,000,000  20      20,000,000     1,000,000,000,000`}>

```python
import math

print(f"{'n':<10} {'log n':<7} {'n log n':<14} n²")
for n in [10, 100, 1000, 1_000_000]:
    log_n = round(math.log2(n))
    line = f"{n:<10,} {log_n:<7} {n * log_n:<14,} {n * n:,}"
    print(line)
```

</CodeExample>

From best to worst: **O(1)** → **O(log n)** → **O(n)** → **O(n log n)** → **O(n²)**. With a million items, O(n log n) is 20 million steps (fine, a blink), while O(n²) is a trillion (hours or days).

## Best case and worst case

The number of steps can depend on the data, not just its size. A **linear search** looks at items one by one until it finds the target:

<CodeExample output={`Mei: found, steps = 1
Zoe: found, steps = 5
Ali: not found, steps = 5`}>

```python
def linear_search(items, target):
    steps = 0
    for item in items:
        steps += 1
        if item == target:
            return True, steps
    return False, steps

names = ["Mei", "Sam", "Kai", "Ben", "Zoe"]
for target in ["Mei", "Zoe", "Ali"]:
    found, steps = linear_search(names, target)
    word = "found" if found else "not found"
    print(f"{target}: {word}, steps = {steps}")
```

</CodeExample>

- **Best case**: the target is first, 1 step.
- **Worst case**: the target is last or missing, `n` steps.

When people say "linear search is O(n)", they mean the **worst case**. It's the honest promise: *it will never be slower than this*.

## Why `in` is slow on a list but fast on a set

`x in some_list` is a linear search: Python compares `x` with the items one by one. A **set** (and a dict's keys) works differently. It uses **hashing**: Python turns the value into a number (its **hash**) and uses that number to jump straight to the one place where the value would be stored, like a coat check that gives you a ticket number.

We can watch this happen. This `Spy` class counts every time Python compares two of its objects with `==`:

<CodeExample output={`in list: True, comparisons = 1000
in set:  True, comparisons = 1
missing in list: comparisons = 1000
missing in set:  comparisons = 0`}>

```python
class Spy:
    comparisons = 0

    def __init__(self, value):
        self.value = value

    def __eq__(self, other):
        Spy.comparisons += 1
        return self.value == other.value

    def __hash__(self):              # lets Spy objects go in a set
        return hash(self.value)

as_list = [Spy(i) for i in range(1000)]
as_set = set(as_list)

Spy.comparisons = 0
found = Spy(999) in as_list
print(f"in list: {found}, comparisons = {Spy.comparisons}")

Spy.comparisons = 0
found = Spy(999) in as_set
print(f"in set:  {found}, comparisons = {Spy.comparisons}")

Spy.comparisons = 0
Spy(5000) in as_list
print(f"missing in list: comparisons = {Spy.comparisons}")

Spy.comparisons = 0
Spy(5000) in as_set
print(f"missing in set:  comparisons = {Spy.comparisons}")
```

</CodeExample>

The list compared all 1000 items. The set jumped to the right spot and compared **one**, or **none** when nothing was stored there. Checking `in` on a set or a dict is **O(1) on average**, however big it gets.

So the duplicate check from before becomes O(n) with a set: one pass, remembering what we've seen:

<CodeExample output={`n = 10: 10 steps
n = 100: 100 steps
n = 1000: 1000 steps`}>

```python
def has_duplicates(items):
    steps = 0
    seen = set()
    for item in items:
        steps += 1
        if item in seen:         # O(1) on average
            return True, steps
        seen.add(item)
    return False, steps

for n in [10, 100, 1000]:
    found, steps = has_duplicates(list(range(n)))
    print(f"n = {n}: {steps} steps")
```

</CodeExample>

499,500 comparisons became 1,000 steps. The one-line version, `len(set(items)) < len(items)`, is O(n) too.

<Callout type="note" title="Why 'on average'?">

Two different values can occasionally get the same slot (a **collision**), and then Python has to compare a few items. Python's sets and dicts keep collisions rare, so in practice lookups stay O(1). The price: only **hashable** values (numbers, strings, tuples) can be set items or dict keys, as you saw in [Tuples and Sets](/learn/python/tuples-and-sets).

</Callout>

## Space complexity

Big-O can also describe **memory**. Code that keeps a running total uses the same few variables whatever `n` is: **O(1) space**. Code that builds a new list as long as the input uses **O(n) space**:

```python
def total_of_squares(numbers):     # O(1) extra space
    total = 0
    for n in numbers:
        total += n * n
    return total

def squares(numbers):              # O(n) extra space
    return [n * n for n in numbers]
```

Faster code often uses more memory: the set version of `has_duplicates` is O(n) in time **and** O(n) in space, because the `seen` set can grow to `n` items. Recursion uses space too: every waiting call sits on the call stack, so `sum_list` from [Recursion](/learn/python/recursion) uses O(n) stack space. That's why it hits the recursion limit on long lists.

## Rules of thumb

When you work out a Big-O, keep only the part that grows fastest:

- **Drop constants**: `3n + 5` steps is still **O(n)**. Doubling the data doubles the time, which is what matters.
- **Keep the biggest term**: `n² + n` is **O(n²)**. When `n` is a million, the `+ n` is a rounding error.
- **One after another, add**: a loop followed by another loop is `n + n`, still O(n).
- **Inside each other, multiply**: a loop inside a loop is `n × n`, O(n²).

And don't optimise everything. What matters is how big `n` really gets:

| Real data                                | Typical n        | What's fine                     |
| ---------------------------------------- | ---------------- | ------------------------------- |
| Pupils in a class, items in a menu       | 10–100           | Anything, even O(n²)            |
| Products in a shop, words in a book      | 10,000–100,000   | O(n log n) or better            |
| Lines in a server log, users of an app   | Millions+        | O(n) or better, with sets/dicts |

<Callout type="tip" title="Clear first, fast where it counts">

Write the clearest code first. If it's slow, find the loop inside a loop or the `in` on a big list, and switch to a set or dict. That one change fixes most slow beginner programs.

</Callout>

2. `common(a, b)` returns a **set** of the values that are in both lists.

<Hint>

For `find_duplicates`, loop **once** and keep a `seen` set: if `item in seen`, add it to `duplicates`, otherwise add it to `seen`. For `common`, turn both lists into sets and use the intersection operator `&` from [Tuples and Sets](/learn/python/tuples-and-sets).

def find_duplicates(items):
    seen = set()
    duplicates = set()
    for item in items:
        if item in seen:
            duplicates.add(item)
        else:
            seen.add(item)
    return duplicates


def common(a, b):
    return set(a) & set(b)

## Recap

- **Big-O** describes how the work grows as the input size **n** grows. Count steps, not seconds.
- **O(1)** constant, **O(log n)** halving, **O(n)** one pass, **O(n log n)** good sorting, **O(n²)** a loop inside a loop.
- Big-O usually means the **worst case**.
- `x in list` is O(n); `x in set` and `key in dict` are **O(1) on average** thanks to hashing.
- **Space complexity** counts extra memory; faster code often trades memory for speed.
- Drop constants and smaller terms, and worry about speed when `n` is really big.
