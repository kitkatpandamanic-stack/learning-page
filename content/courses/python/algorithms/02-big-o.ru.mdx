Две программы могут выдавать один и тот же ответ, но одна справляется мгновенно, а другая работает всю ночь. Обычно дело не в компьютере, а в том, как **растёт объём работы**, когда данных становится больше. **O-нотация** (Big-O) — это язык, на котором программисты говорят об этом росте. Никакой математики сложнее счёта вам не понадобится. 📈

## Считайте шаги, а не секунды

Можно засечь время работы программы секундомером, но результат меняется от компьютера к компьютеру и даже между двумя запусками на одном и том же. Вместо этого мы **считаем шаги**, которые делает код, и спрашиваем: *что станет с этим числом, если входные данные вырастут в 10 раз?*

<CodeExample output={`n = 10: 10 шагов
n = 100: 100 шагов
n = 1000: 1000 шагов`}>

```python
def largest(numbers):
    steps = 0
    best = numbers[0]
    for number in numbers:
        steps += 1
        if number > best:
            best = number
    return best, steps

for n in [10, 100, 1000]:
    best, steps = largest(list(range(n)))
    print(f"n = {n}: {steps} шагов")
```

</CodeExample>

Размер входных данных обозначают буквой **n**. Здесь число шагов растёт ровно как `n`: в 10 раз больше чисел — в 10 раз больше работы. Это записывают как **O(n)** и читают «O от n» или просто «линейная сложность».

## O(1): константное время

Некоторые операции занимают одно и то же время, каким бы большим ни был объём данных. Это **O(1)**, «константное время»:

- чтение `items[0]` или `items[500_000]` (Python сразу переходит к нужной позиции),
- `len(items)` (списки помнят свою длину),
- `items.append(x)` и `items.pop()` в **конце** списка,
- поиск ключа в словаре или проверка `x in some_set` (об этом чуть позже).

Будь в списке 10 элементов или 10 миллионов — каждая из этих операций занимает один шаг.

## O(n²): циклы внутри циклов

Есть ли в списке повторяющееся значение? Очевидный способ — сравнить **каждую пару** элементов с помощью цикла внутри цикла:

<CodeExample output={`n = 10: 45 сравнений
n = 100: 4950 сравнений
n = 1000: 499500 сравнений`}>

```python
def has_duplicates(items):
    comparisons = 0
    found = False
    for i in range(len(items)):
        for j in range(i + 1, len(items)):
            comparisons += 1
            if items[i] == items[j]:
                found = True
    return found, comparisons

for n in [10, 100, 1000]:
    found, count = has_duplicates(list(range(n)))
    print(f"n = {n}: {count} сравнений")
```

</CodeExample>

Элементов в 10 раз больше, а работы — **в 100 раз**! Для каждого из `n` элементов внутренний цикл снова проходит (до) `n` элементов, поэтому число шагов растёт как `n × n`. Это записывают как **O(n²)** («квадратичная сложность»). Для миллиона элементов понадобилось бы около 500 **миллиардов** сравнений.

<Callout type="tip" title="Как распознать O(n²)">

Цикл по данным **внутри** другого цикла по тем же данным — классический признак O(n²). Остерегайтесь и скрытых циклов: `x in some_list`, `some_list.index(x)`, `some_list.count(x)` и `some_list.remove(x)` перебирают список «за кулисами».

</Callout>

## O(log n): делим задачу пополам

Некоторые алгоритмы (algorithm) на каждом шаге отбрасывают **половину** оставшихся данных — как при угадывании числа от 1 до 100, когда вам подсказывают «больше» или «меньше». Сколько раз можно поделить `n` пополам, пока не останется один элемент?

<CodeExample output={`8 элементов: делений пополам — 3
1,000 элементов: делений пополам — 9
1,000,000 элементов: делений пополам — 19
1,000,000,000 элементов: делений пополам — 29`}>

```python
def halvings(n):
    steps = 0
    while n > 1:
        n = n // 2
        steps += 1
    return steps

for n in [8, 1000, 1_000_000, 1_000_000_000]:
    print(f"{n:,} элементов: делений пополам — {halvings(n)}")
```

</CodeExample>

Миллиард элементов — меньше чем за 30 шагов! Это **O(log n)** («логарифмическая сложность»): если умножить объём данных на 1000, добавится всего около 10 шагов. Знаменитый алгоритм деления пополам, **бинарный поиск** (binary search), вы напишете в следующем уроке.

## O(n log n): хорошая сортировка

Лучшие универсальные алгоритмы сортировки, включая встроенную в Python `sorted()`, делают около `n × log n` шагов: **O(n log n)**. Это чуть больше, чем O(n), и несравнимо меньше, чем O(n²). Вот как основные виды сложности соотносятся при росте `n` (запятые здесь разделяют разряды):

<CodeExample output={`n          log n   n log n        n²
10         3       30             100
100        7       700            10,000
1,000      10      10,000         1,000,000
1,000,000  20      20,000,000     1,000,000,000,000`}>

```python
import math

print(f"{'n':<10} {'log n':<7} {'n log n':<14} n²")
for n in [10, 100, 1000, 1_000_000]:
    log_n = round(math.log2(n))
    line = f"{n:<10,} {log_n:<7} {n * log_n:<14,} {n * n:,}"
    print(line)
```

</CodeExample>

От лучшего к худшему: **O(1)** → **O(log n)** → **O(n)** → **O(n log n)** → **O(n²)**. Для миллиона элементов O(n log n) — это 20 миллионов шагов (нормально, одно мгновение), а O(n²) — триллион (часы или дни).

## Лучший и худший случай

Число шагов может зависеть не только от размера данных, но и от самих данных. **Линейный поиск** (linear search) просматривает элементы по одному, пока не найдёт искомый:

<CodeExample output={`Mei: найдено, шагов = 1
Zoe: найдено, шагов = 5
Ali: не найдено, шагов = 5`}>

```python
def linear_search(items, target):
    steps = 0
    for item in items:
        steps += 1
        if item == target:
            return True, steps
    return False, steps

names = ["Mei", "Sam", "Kai", "Ben", "Zoe"]
for target in ["Mei", "Zoe", "Ali"]:
    found, steps = linear_search(names, target)
    word = "найдено" if found else "не найдено"
    print(f"{target}: {word}, шагов = {steps}")
```

</CodeExample>

- **Лучший случай** (best case): искомый элемент первый — 1 шаг.
- **Худший случай** (worst case): искомый элемент последний или его нет — `n` шагов.

Когда говорят «линейный поиск — это O(n)», имеют в виду **худший случай**. Это честное обещание: *медленнее этого не будет никогда*.

## Почему `in` медленный для списка, но быстрый для множества

`x in some_list` — это линейный поиск: Python сравнивает `x` с элементами по одному. **Множество** (set) и ключи словаря устроены иначе. Они используют **хеширование** (hashing): Python превращает значение в число (его **хеш**, hash) и по этому числу сразу переходит в то единственное место, где значение должно храниться, — как в гардеробе, где вам выдают номерок.

Это можно увидеть своими глазами. Класс `Spy` считает, сколько раз Python сравнивает два его объекта через `==`:

<CodeExample output={`список:    True, сравнений = 1000
множество: True, сравнений = 1
нет в списке:    сравнений = 1000
нет в множестве: сравнений = 0`}>

```python
class Spy:
    comparisons = 0

    def __init__(self, value):
        self.value = value

    def __eq__(self, other):
        Spy.comparisons += 1
        return self.value == other.value

    def __hash__(self):              # позволяет класть объекты Spy в множество
        return hash(self.value)

as_list = [Spy(i) for i in range(1000)]
as_set = set(as_list)

Spy.comparisons = 0
found = Spy(999) in as_list
print(f"список:    {found}, сравнений = {Spy.comparisons}")

Spy.comparisons = 0
found = Spy(999) in as_set
print(f"множество: {found}, сравнений = {Spy.comparisons}")

Spy.comparisons = 0
Spy(5000) in as_list
print(f"нет в списке:    сравнений = {Spy.comparisons}")

Spy.comparisons = 0
Spy(5000) in as_set
print(f"нет в множестве: сравнений = {Spy.comparisons}")
```

</CodeExample>

Список сравнил все 1000 элементов. Множество сразу перешло в нужное место и сравнило **один** элемент — или **ни одного**, если там ничего не хранилось. Проверка `in` для множества или словаря — это **O(1) в среднем**, каким бы большим он ни был.

Поэтому проверка на повторы из примера выше с множеством становится O(n): один проход, в котором мы запоминаем всё, что уже видели:

<CodeExample output={`n = 10: 10 шагов
n = 100: 100 шагов
n = 1000: 1000 шагов`}>

```python
def has_duplicates(items):
    steps = 0
    seen = set()
    for item in items:
        steps += 1
        if item in seen:         # O(1) в среднем
            return True, steps
        seen.add(item)
    return False, steps

for n in [10, 100, 1000]:
    found, steps = has_duplicates(list(range(n)))
    print(f"n = {n}: {steps} шагов")
```

</CodeExample>

499 500 сравнений превратились в 1000 шагов. Однострочная версия `len(set(items)) < len(items)` тоже работает за O(n).

<Callout type="note" title="Почему «в среднем»?">

Иногда два разных значения попадают в одно и то же место (это называется **коллизией**, collision), и тогда Python приходится сравнить несколько элементов. Множества и словари Python делают коллизии редкими, поэтому на практике поиск остаётся O(1). Цена за это: элементами множества и ключами словаря могут быть только **хешируемые** значения (числа, строки, кортежи), как вы видели в уроке [Кортежи и множества](/learn/python/tuples-and-sets).

</Callout>

## Пространственная сложность

O-нотацией можно описывать и **память**. Код, который хранит накапливаемую сумму, использует одни и те же несколько переменных при любом `n`: это **O(1) по памяти**. Код, который строит новый список такой же длины, как входные данные, использует **O(n) памяти**. Это называют **пространственной сложностью** (space complexity), в отличие от **временной сложности** (time complexity):

```python
def total_of_squares(numbers):     # O(1) дополнительной памяти
    total = 0
    for n in numbers:
        total += n * n
    return total

def squares(numbers):              # O(n) дополнительной памяти
    return [n * n for n in numbers]
```

Более быстрый код часто тратит больше памяти: версия `has_duplicates` с множеством — это O(n) по времени **и** O(n) по памяти, потому что множество `seen` может вырасти до `n` элементов. Рекурсия тоже расходует память: каждый ожидающий вызов лежит в стеке вызовов, поэтому `sum_list` из урока [Рекурсия](/learn/python/recursion) занимает O(n) памяти в стеке. Вот почему на длинных списках она упирается в ограничение рекурсии.

## Практические правила

Когда оцениваете сложность в O-нотации, оставляйте только ту часть, которая растёт быстрее всего:

- **Отбрасывайте константы**: `3n + 5` шагов — это всё равно **O(n)**. Вдвое больше данных — вдвое больше времени, и именно это важно.
- **Оставляйте самое большое слагаемое**: `n² + n` — это **O(n²)**. Когда `n` равно миллиону, `+ n` — ничтожная погрешность.
- **Одно за другим — складывайте**: цикл, за которым идёт ещё один цикл, — это `n + n`, всё ещё O(n).
- **Одно внутри другого — умножайте**: цикл внутри цикла — это `n × n`, O(n²).

И не нужно оптимизировать всё подряд. Важно, насколько большим на самом деле бывает `n`:

| Реальные данные                              | Типичное n        | Что приемлемо                          |
| -------------------------------------------- | ----------------- | -------------------------------------- |
| Ученики в классе, пункты меню                | 10–100            | Что угодно, даже O(n²)                 |
| Товары в магазине, слова в книге             | 10 000–100 000    | O(n log n) или лучше                   |
| Строки в логе сервера, пользователи сервиса  | Миллионы и больше | O(n) или лучше, с множествами/словарями |

<Callout type="tip" title="Сначала понятно, быстро — где это важно">

Сначала пишите самый понятный код. Если он тормозит, найдите цикл внутри цикла или `in` по большому списку и замените список на множество или словарь. Это одно изменение исправляет большинство медленных программ новичков.

</Callout>

def find_duplicates(items):
    seen = set()

    for item in items:
        if item in seen:

def common(a, b):

## Итоги

- **O-нотация** описывает, как растёт объём работы при росте размера входных данных **n**. Считайте шаги, а не секунды.
- **O(1)** — константа, **O(log n)** — деление пополам, **O(n)** — один проход, **O(n log n)** — хорошая сортировка, **O(n²)** — цикл внутри цикла.
- Обычно O-нотация описывает **худший случай**.
- `x in list` — это O(n); `x in set` и `key in dict` — **O(1) в среднем** благодаря хешированию.
- **Пространственная сложность** учитывает дополнительную память; быстрый код часто платит памятью за скорость.
- Отбрасывайте константы и меньшие слагаемые, а о скорости беспокойтесь, когда `n` действительно большое.
