Some problems contain smaller copies of themselves. A folder holds files **and other folders**, which hold files and other folders... A list can hold lists. **Recursion** is a way to solve these problems with a function that **calls itself** on a smaller piece, until the piece is so small the answer is obvious. 🪆

## A function that calls itself

Here's a countdown written without any loop:

<CodeExample output={`3
2
1
Lift off!`}>

```python
def countdown(n):
    if n == 0:
        print("Lift off!")
        return
    print(n)
    countdown(n - 1)   # the function calls itself

countdown(3)
```

</CodeExample>

`countdown(3)` prints `3` and calls `countdown(2)`, which prints `2` and calls `countdown(1)`, and so on. When `n` reaches `0`, the function prints `Lift off!` and stops calling itself.

## Base case and recursive case

Every recursive function needs two parts:

- The **base case**: a problem so small you can answer it straight away, **without** calling the function again. Here: `n == 0`.
- The **recursive case**: do a little work, then call the function on a **smaller** problem that moves towards the base case. Here: `countdown(n - 1)`.

A classic example is the **factorial**: `4!` means `4 × 3 × 2 × 1`. Notice that `4!` is just `4 × 3!`, a smaller copy of the same problem:

<CodeExample output={`24
1
3628800`}>

```python
def factorial(n):
    if n <= 1:                       # base case
        return 1
    return n * factorial(n - 1)      # recursive case

print(factorial(4))
print(factorial(1))
print(factorial(10))
```

</CodeExample>

<Callout type="tip" title="Trust the function">

When you write the recursive case, **assume the function already works** for the smaller problem. "If `factorial(3)` gives me `6`, then `factorial(4)` is `4 * 6`." You don't need to follow every call in your head. That's the trick to thinking recursively.

</Callout>

## The call stack

How does Python keep track of all those unfinished calls? Each call gets its own little box of local variables, and the boxes pile up on the **call stack**. A call stays on the stack, **waiting**, until the call it made returns. Let's print what happens, indenting each line by how deep we are:

<CodeExample output={`factorial(4) called
  factorial(3) called
    factorial(2) called
      factorial(1) called
      base case: return 1
    return 2 * 1 = 2
  return 3 * 2 = 6
return 4 * 6 = 24
24`}>

```python
def factorial(n, depth=0):
    indent = "  " * depth
    print(f"{indent}factorial({n}) called")
    if n <= 1:
        print(f"{indent}base case: return 1")
        return 1
    smaller = factorial(n - 1, depth + 1)
    result = n * smaller
    print(f"{indent}return {n} * {smaller} = {result}")
    return result

print(factorial(4))
```

</CodeExample>

The calls go **down** until they hit the base case, then the answers come back **up**, each waiting call finishing its multiplication. Every call has its own `n`: the `n` in `factorial(4)` is still `4` when `factorial(3)` returns.

This is exactly the stack you see in a traceback ("most recent call last"), which you met in [Exceptions](/learn/python/exceptions).

## Recursion on lists

A list is "the first item, followed by a smaller list". That makes lists a natural fit for recursion:

<CodeExample output={`8
0
15`}>

```python
def sum_list(numbers):
    if not numbers:          # base case: an empty list
        return 0
    return numbers[0] + sum_list(numbers[1:])

print(sum_list([3, 1, 4]))
print(sum_list([]))
print(sum_list([5, 5, 5]))
```

</CodeExample>

Written out, the calls look like this:

```text
sum_list([3, 1, 4])
= 3 + sum_list([1, 4])
= 3 + 1 + sum_list([4])
= 3 + 1 + 4 + sum_list([])
= 3 + 1 + 4 + 0
= 8
```

## Recursion on nested data

Recursion really shines when data is **nested** and you don't know how deep it goes. A loop can walk through one level, but what about lists inside lists inside lists? Let the function call itself whenever it finds another list:

<CodeExample output={`[1, 2, 3, 4, 5, 6]
[]`}>

```python
def flatten(items):
    flat = []
    for item in items:
        if isinstance(item, list):
            flat.extend(flatten(item))   # a list: go inside
        else:
            flat.append(item)            # a plain value
    return flat

print(flatten([1, [2, 3], [4, [5, [6]]]]))
print(flatten([[], [[]]]))
```

</CodeExample>

Here the base case is hidden in the loop: a plain value doesn't cause another call, and an empty list has nothing to loop over.

Folders work the same way. Let's store a folder as a **dict**: each key is a name, and each value is either a file's size in KB (a number) or another folder (a dict):

<CodeExample output={`notes.txt (120 KB)
photos/
  cat.jpg (2400 KB)
  holiday/
    beach.jpg (3100 KB)
    sea.png (2800 KB)
todo.txt (40 KB)`}>

```python
drive = {
    "notes.txt": 120,
    "photos": {
        "cat.jpg": 2400,
        "holiday": {"beach.jpg": 3100, "sea.png": 2800},
    },
    "todo.txt": 40,
}

def show(folder, depth=0):
    indent = "  " * depth
    for name, item in folder.items():
        if isinstance(item, dict):
            print(f"{indent}{name}/")
            show(item, depth + 1)       # a subfolder
        else:
            print(f"{indent}{name} ({item} KB)")

show(drive)
```

</CodeExample>

The same pattern works for JSON from the internet, family trees, comment threads with replies, and menus with submenus.

## RecursionError: when it never stops

If the base case is missing, or the function never reaches it, the calls pile up forever. Python protects itself with a **recursion limit** (1000 calls deep by default) and raises a `RecursionError`:

<CodeExample output={`RecursionError: maximum recursion depth exceeded
1000`}>

```python
import sys

def countdown(n):
    if n == 0:
        return "Lift off!"
    return countdown(n - 2)   # oops: 5, 3, 1, -1, -3...

try:
    countdown(5)
except RecursionError as error:
    print("RecursionError:", error)

print(sys.getrecursionlimit())
```

</CodeExample>

Counting down by 2 from an odd number jumps right over `0`, so the base case never happens. On your computer, the traceback ends like this:

```text
  File "main.py", line 6, in countdown
    return countdown(n - 2)
  [Previous line repeated 996 more times]
RecursionError: maximum recursion depth exceeded
```

<Callout type="warning" title="Checklist for a recursive function">

1. Is there a base case?
2. Does **every** recursive call get **smaller**, so it's guaranteed to reach the base case?

A safer base case here is `if n <= 0:`, which catches negative numbers too.

</Callout>

## When a loop is better

Recursion isn't always the best tool. `sum_list` above makes a new call (and a new list slice) for every item, so a list of 5,000 numbers would hit the recursion limit, while `sum(numbers)` or a simple `for` loop handles millions without a problem.

| Use a **loop** when...                          | Use **recursion** when...                                 |
| ----------------------------------------------- | --------------------------------------------------------- |
| you walk through items **one after another**    | the data is **nested** (folders, JSON, trees)             |
| the data could be very long (thousands+)        | the problem splits into **smaller copies** of itself      |
| a loop reads just as clearly                    | the recursive version is much shorter and clearer         |

Python programmers usually reach for a loop first, and for recursion when the data has a tree shape. You'll use it again for **merge sort** in [Searching and Sorting](/learn/python/searching-and-sorting).

## Memoisation: remembering answers

The **Fibonacci numbers** go 0, 1, 1, 2, 3, 5, 8, 13... Each one is the sum of the two before it. The recursive version is beautifully short, but it has a hidden problem. Let's count how many times the function runs, using a dict as a counter that every call can update:

<CodeExample output={`fib(5) = 5 after 15 calls
fib(10) = 55 after 177 calls
fib(15) = 610 after 1973 calls
fib(20) = 6765 after 21891 calls`}>

```python
stats = {"calls": 0}

def fib(n):
    stats["calls"] += 1
    if n < 2:
        return n
    return fib(n - 1) + fib(n - 2)

for n in [5, 10, 15, 20]:
    stats["calls"] = 0
    answer = fib(n)
    print(f"fib({n}) = {answer} after {stats['calls']} calls")
```

</CodeExample>

Almost 22,000 calls for `fib(20)`! `fib(20)` calls `fib(19)` **and** `fib(18)`, but `fib(19)` calls `fib(18)` again, and each of those calls `fib(17)`... The same small answers are worked out thousands of times.

The fix is **memoisation**: remember each answer the first time you compute it, and look it up next time. A dict does the job:

<CodeExample output={`6765 after 21 calls`}>

```python
stats = {"calls": 0}
memo = {}

def fib(n):
    if n in memo:
        return memo[n]          # already know it: no work
    stats["calls"] += 1
    if n < 2:
        answer = n
    else:
        answer = fib(n - 1) + fib(n - 2)
    memo[n] = answer
    return answer

print(f"{fib(20)} after {stats['calls']} calls")
```

</CodeExample>

### functools.lru_cache does it for you

Memoising is so useful that the standard library has it built in. Put `@lru_cache` on the line above the function, and Python remembers every answer for you:

<CodeExample output={`6765 after 21 calls
12586269025 after 51 calls`}>

```python
from functools import lru_cache

stats = {"calls": 0}

@lru_cache(maxsize=None)
def fib(n):
    stats["calls"] += 1
    if n < 2:
        return n
    return fib(n - 1) + fib(n - 2)

print(f"{fib(20)} after {stats['calls']} calls")
print(f"{fib(50)} after {stats['calls']} calls")
```

</CodeExample>

From 21,891 calls down to 21, and `fib(50)` needs only 30 more calls (`fib(21)` to `fib(50)`), because the first 21 answers were already cached. Without the cache, `fib(50)` would take **billions** of calls.

<Callout type="note" title="What's that @ line?">

`@lru_cache(maxsize=None)` is a **decorator**: it wraps your function with extra behaviour, here a dict of remembered answers. You'll learn to write your own in [Decorators](/learn/python/decorators). `maxsize=None` means "remember everything". Only cache functions whose answer depends **only** on their arguments, and whose arguments are hashable (numbers, strings, tuples, not lists).

</Callout>

<Hint>

Both functions loop over `folder.items()` and check `isinstance(item, dict)`. For a subfolder, call the function itself on `item`: add its result to the total, or `extend` your list with it. In `find_files`, pass a longer path down: `path + name + "/"`. A file's full path is `path + name`, and `name.endswith(ending)` checks the ending.

```python
def total_size(folder):
    total = 0
    for name, item in folder.items():
        if isinstance(item, dict):
            total += total_size(item)
        else:
            total += item
    return total


def find_files(folder, ending, path=""):
    found = []
    for name, item in folder.items():
        if isinstance(item, dict):
            found.extend(find_files(item, ending, path + name + "/"))
        elif name.endswith(ending):
            found.append(path + name)
    return found
```

## Recap

- A **recursive** function calls itself on a **smaller** version of the problem.
- It needs a **base case** (answered directly) and a **recursive case** that moves towards it.
- Each call waits on the **call stack** until the call it made returns; every call has its own local variables.
- Recursion fits **nested** data: lists of lists, folders, JSON. Loops fit long, flat sequences.
- No reachable base case means a `RecursionError` (the limit is about 1000 calls deep).
- **Memoisation** remembers answers so repeated calls are free: use a dict or `@lru_cache(maxsize=None)`.
