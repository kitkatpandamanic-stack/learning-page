Finding things and putting them in order are two of the most common jobs in programming. In this lesson you'll write the classic algorithms yourself, **count their steps** to see why some are so much faster, and then learn the built-in tools Python programmers actually use every day. 🔍

## Linear search: the simple way

The simplest search checks every item in turn until it finds the target. It works on **any** list, sorted or not, and it's what `x in items` and `items.index(x)` do behind the scenes:

<CodeExample output={`2
-1`}>

```python
def linear_search(items, target):
    for index, item in enumerate(items):
        if item == target:
            return index
    return -1          # a common way to say "not found"

names = ["Mei", "Sam", "Kai", "Zoe"]
print(linear_search(names, "Kai"))
print(linear_search(names, "Ali"))
```

</CodeExample>

As you saw in [Big-O](/learn/python/big-o), linear search is **O(n)**: a million items can mean a million checks.

## Binary search: halve it every time

When the list is **sorted**, you can do much better. Think of guessing a number between 1 and 100: you guess 50, hear "higher", and **half** of the numbers are gone in one go. **Binary search** does the same: look at the middle item, and throw away the half that can't contain the target.

<CodeExample output={`low=0 high=9 mid=4 -> 16
low=5 high=9 mid=7 -> 56
low=5 high=6 mid=5 -> 23
5`}>

```python
def binary_search(items, target):
    low, high = 0, len(items) - 1
    while low <= high:
        mid = (low + high) // 2
        print(f"low={low} high={high} mid={mid} -> {items[mid]}")
        if items[mid] == target:
            return mid
        if items[mid] < target:
            low = mid + 1      # target is in the right half
        else:
            high = mid - 1     # target is in the left half
    return -1

numbers = [2, 5, 8, 12, 16, 23, 38, 56, 72, 91]
print(binary_search(numbers, 23))
```

</CodeExample>

`low` and `high` mark the part of the list that could still hold the target. `16` is too small, so everything up to it goes. `56` is too big, so everything from it goes. Then `23` is found, after 3 looks instead of 6. If `low` passes `high`, nothing is left to search and we return `-1`.

Let's count the looks for a list of a million numbers:

<CodeExample output={`linear search: 1000000 looks
binary search: 20 looks`}>

```python
def count_linear(items, target):
    looks = 0
    for item in items:
        looks += 1
        if item == target:
            break
    return looks

def count_binary(items, target):
    low, high, looks = 0, len(items) - 1, 0
    while low <= high:
        mid = (low + high) // 2
        looks += 1
        if items[mid] == target:
            break
        if items[mid] < target:
            low = mid + 1
        else:
            high = mid - 1
    return looks

numbers = list(range(1_000_000))
print(f"linear search: {count_linear(numbers, 999_999)} looks")
print(f"binary search: {count_binary(numbers, 999_999)} looks")
```

</CodeExample>

That's **O(log n)** in action: 20 looks for a million items, 30 for a billion.

<Callout type="warning" title="Binary search rules">

- The list **must be sorted**. On an unsorted list, binary search confidently gives wrong answers.
- Use `while low <= high` (not `<`), or you'll miss the last item.
- Move past `mid` with `mid + 1` and `mid - 1`. Writing `low = mid` can loop forever.

These off-by-one mistakes are so easy to make that even experienced programmers usually use the `bisect` module instead.

</Callout>

## The bisect module

`bisect` is Python's ready-made, well-tested binary search. `bisect_left(items, x)` returns the position where `x` **is** in a sorted list, or where it **would go**. `insort(items, x)` inserts `x` in the right place so the list stays sorted:

<CodeExample output={`3 True
4 False
[12, 25, 31, 47, 50, 58, 66, 90]`}>

```python
from bisect import bisect_left, insort

scores = [12, 25, 31, 47, 58, 66, 90]

i = bisect_left(scores, 47)
print(i, i < len(scores) and scores[i] == 47)   # found it

i = bisect_left(scores, 50)
print(i, i < len(scores) and scores[i] == 50)   # would go here

insort(scores, 50)
print(scores)
```

</CodeExample>

`bisect` is also brilliant for "which band does this number fall into?" questions, like turning marks into grades:

<CodeExample output="['F', 'D', 'C', 'B', 'A']">

```python
from bisect import bisect_right

def grade(mark):
    boundaries = [50, 60, 70, 80]   # D from 50, C from 60...
    letters = "FDCBA"
    return letters[bisect_right(boundaries, mark)]

print([grade(m) for m in [35, 50, 69, 70, 99]])
```

</CodeExample>

`bisect_right(boundaries, 69)` counts how many boundaries are less than or equal to 69 (that's 2), which picks `"C"`. No `if`/`elif` ladder needed.

## Insertion sort

Now for sorting. You'll almost always use `sorted()`, but writing a couple of sorting algorithms yourself shows **why** some are faster, and they're a favourite job-interview topic.

**Insertion sort** works like sorting playing cards in your hand: take the next card and slide it left until it sits in the right place:

<CodeExample output={`[2, 5, 4, 1, 3]
[2, 4, 5, 1, 3]
[1, 2, 4, 5, 3]
[1, 2, 3, 4, 5]`}>

```python
def insertion_sort(items):
    items = items.copy()            # don't change the caller's list
    for i in range(1, len(items)):
        current = items[i]
        j = i - 1
        while j >= 0 and items[j] > current:
            items[j + 1] = items[j]   # shift a bigger item right
            j -= 1
        items[j + 1] = current
        print(items)
    return items

insertion_sort([5, 2, 4, 1, 3])
```

</CodeExample>

Each row shows the list after one more card has been slotted in; the left part is always sorted. In the worst case each new item slides past **all** the earlier ones, so insertion sort is **O(n²)**. But on a list that's already **almost sorted**, items barely move and it's nearly O(n). Remember that: it comes back in a minute.

## Merge sort

**Merge sort** uses [recursion](/learn/python/recursion) and a simple idea: merging two lists that are **already sorted** is easy. Keep taking the smaller of the two front items:

<CodeExample output="[1, 2, 3, 4, 9, 10]">

```python
def merge(left, right):
    result = []
    i = j = 0
    while i < len(left) and j < len(right):
        if left[i] <= right[j]:
            result.append(left[i])
            i += 1
        else:
            result.append(right[j])
            j += 1
    result.extend(left[i:])     # one list ran out:
    result.extend(right[j:])    # add what's left of the other
    return result

print(merge([1, 4, 9], [2, 3, 10]))
```

</CodeExample>

Then merge sort is: split the list in half, **sort each half with merge sort**, and merge them. The base case is a list of 0 or 1 items, which is already sorted:

<CodeExample output={`[1, 2, 3, 4, 5, 6, 7, 8]
['Ali', 'Kai', 'Mei', 'Zoe']`}>

```python
def merge(left, right):
    result = []
    i = j = 0
    while i < len(left) and j < len(right):
        if left[i] <= right[j]:
            result.append(left[i])
            i += 1
        else:
            result.append(right[j])
            j += 1
    return result + left[i:] + right[j:]

def merge_sort(items):
    if len(items) <= 1:              # base case
        return items
    middle = len(items) // 2
    left = merge_sort(items[:middle])
    right = merge_sort(items[middle:])
    return merge(left, right)

print(merge_sort([5, 8, 1, 4, 7, 3, 6, 2]))
print(merge_sort(["Mei", "Zoe", "Ali", "Kai"]))
```

</CodeExample>

The list is halved about `log n` times, and each level of halving does about `n` steps of merging, so merge sort is **O(n log n)** every time, even in the worst case. Let's count comparisons on shuffled lists:

<CodeExample output={`n = 10: insertion 29, merge 23
n = 100: insertion 2498, merge 549
n = 1000: insertion 244958, merge 8723`}>

```python
import random

def insertion_count(items):
    items, count = items.copy(), 0
    for i in range(1, len(items)):
        current, j = items[i], i - 1
        while j >= 0:
            count += 1
            if items[j] <= current:
                break
            items[j + 1] = items[j]
            j -= 1
        items[j + 1] = current
    return count

def merge_count(items):
    if len(items) <= 1:
        return items, 0
    middle = len(items) // 2
    left, a = merge_count(items[:middle])
    right, b = merge_count(items[middle:])
    result, i, j, count = [], 0, 0, a + b
    while i < len(left) and j < len(right):
        count += 1
        if left[i] <= right[j]:
            result.append(left[i])
            i += 1
        else:
            result.append(right[j])
            j += 1
    return result + left[i:] + right[j:], count

random.seed(7)
for n in [10, 100, 1000]:
    items = random.sample(range(n), n)
    _, merge_steps = merge_count(items)
    print(f"n = {n}: insertion {insertion_count(items)}, "
          f"merge {merge_steps}")
```

</CodeExample>

For small lists it hardly matters. For 1000 items, merge sort does about **28 times less work**, and the gap keeps growing with `n`.

## sorted() and list.sort(): use these

In real code, use Python's built-in sorting. It's an algorithm called **Timsort**: a clever mix of merge sort and insertion sort (remember: insertion sort is great on almost-sorted pieces), written in C. It's **O(n log n)**, and extra fast on data that's already partly in order, which real data often is.

You already know `sorted(items)` returns a new list and `items.sort()` sorts in place, both with `key=` and `reverse=True` (from [Lists in Depth](/learn/python/lists-in-depth)). One more property matters: Python's sort is **stable**. Items with equal keys keep their **original order**:

<CodeExample output="[('Sam', 'coffee'), ('Zoe', 'coffee'), ('Mei', 'tea'), ('Kai', 'tea')]">

```python
orders = [("Mei", "tea"), ("Sam", "coffee"),
          ("Kai", "tea"), ("Zoe", "coffee")]

print(sorted(orders, key=lambda order: order[1]))
```

</CodeExample>

Both coffees come first, and among them Sam is still before Zoe, just like in the original list. Mei stays before Kai too.

## Sorting by several keys

To sort by one thing and then break ties with another, return a **tuple** from the key. Tuples compare item by item. A minus sign flips a **number** to sort it high-to-low:

<CodeExample output={`Kai 90 10
Mei 90 12
Ali 75 9
Sam 75 9`}>

```python
players = [
    {"name": "Mei", "score": 90, "minutes": 12},
    {"name": "Sam", "score": 75, "minutes": 9},
    {"name": "Kai", "score": 90, "minutes": 10},
    {"name": "Ali", "score": 75, "minutes": 9},
]

# highest score, then fastest time, then name A-Z
ranked = sorted(players, key=lambda p: (-p["score"],
                                        p["minutes"],
                                        p["name"]))
for p in ranked:
    print(p["name"], p["score"], p["minutes"])
```

</CodeExample>

You can't put a minus in front of a string, though. To sort strings Z–A as a **tiebreaker**, use stability: sort several times, **least important key first**:

<CodeExample output={`London Zoe
London Ben
Paris Sam
Paris Kai`}>

```python
people = [("Paris", "Kai"), ("London", "Ben"),
          ("Paris", "Sam"), ("London", "Zoe")]

people.sort(key=lambda p: p[1], reverse=True)   # name Z-A
people.sort(key=lambda p: p[0])                 # then city A-Z
for city, name in people:
    print(city, name)
```

</CodeExample>

The second sort puts cities in order, and because it's stable, the names inside each city stay in the Z–A order from the first sort.

## Top k with heapq

Need only the **best few** items, like the top 3 scores out of a million? Sorting everything is wasteful. The `heapq` module's `nlargest` and `nsmallest` keep just the best `k` as they go, and accept a `key` like `sorted()`:

<CodeExample output={`[99, 95, 88]
[3, 7]
['pen', 'mug']`}>

```python
import heapq

scores = [72, 95, 88, 61, 99, 3, 7, 40]
print(heapq.nlargest(3, scores))
print(heapq.nsmallest(2, scores))

products = [("lamp", 25.0), ("pen", 1.5),
            ("mug", 6.0), ("desk", 120.0)]
cheapest = heapq.nsmallest(2, products, key=lambda p: p[1])
print([name for name, price in cheapest])
```

</CodeExample>

A **heap** is a structure that always keeps the smallest item at the front. You'll use it as a priority queue in the next lesson.

<Callout type="tip" title="Which one should I use?">

- One item: `max()` / `min()`.
- A few items from a big list: `heapq.nlargest(k, ...)` / `nsmallest`.
- Everything in order, or most of it: `sorted()`.
- Searching the same sorted list many times: `bisect`. Searching once, or an unsorted list: `in` or a set.

</Callout>

def binary_search(items, target):

## Recap

- **Linear search** checks every item: O(n), works on any list.
- **Binary search** halves a **sorted** list each step: O(log n). Watch the off-by-one details, or use `bisect`.
- `bisect_left` finds where a value is or would go; `insort` inserts in order; `bisect_right` turns numbers into bands.
- **Insertion sort** is O(n²) but quick on almost-sorted data; **merge sort** splits, sorts the halves recursively and merges: O(n log n).
- In real code use `sorted()` / `.sort()` (**Timsort**, O(n log n), **stable**). Sort by several keys with a tuple key, or with several stable sorts.
- `heapq.nlargest` / `nsmallest` get the top k without sorting everything.
