"It works on my machine" is where most projects stop, and where the real work begins. A production service has to start the same way on every server, tell you when it's unhealthy, survive deploys without dropping requests, and leave enough clues behind that you can debug it at 3 a.m. In this lesson you'll build the pieces that live in your Python code (settings, logs, health checks), then see how containers, CI and monitoring fit around them. 🚀

## Config from the environment (the 12-factor way)

The **Twelve-Factor App** is a set of rules for services that are easy to deploy, written by engineers at Heroku. Rule number three is: **store config in the environment**. The same build (the same Docker image) runs in development, staging and production, and only environment variables differ: database URLs, secret keys, log levels, feature flags.

Reading `os.environ["WORKERS"]` all over the code has two problems: values are always **strings**, and a typo or missing value only blows up when that line finally runs, maybe days later. The fix is a **settings object** that is loaded and **validated once, at startup**. Pydantic does the hard work:

<CodeExample output={`5 dev
**********
40
database_url -> missing
secret_key -> too_short
workres -> extra_forbidden`}>

```python
from collections.abc import Mapping
from typing import Literal

from pydantic import (
    BaseModel, ConfigDict, Field, SecretStr, ValidationError,
)

class Settings(BaseModel):
    model_config = ConfigDict(extra="forbid", frozen=True)

    environment: Literal["dev", "staging", "prod"] = "dev"
    database_url: str
    secret_key: SecretStr = Field(min_length=32)
    workers: int = Field(default=2, ge=1, le=32)

def load_settings(env: Mapping[str, str]) -> Settings:
    values = {
        name.removeprefix("APP_").lower(): value
        for name, value in env.items()
        if name.startswith("APP_")
    }
    return Settings.model_validate(values)

env = {
    "APP_DATABASE_URL": "postgresql://db/shop",
    "APP_SECRET_KEY": "x" * 40,
    "APP_WORKERS": "4",
    "HOME": "/home/mei",            # not ours: ignored
}
settings = load_settings(env)
print(settings.workers + 1, settings.environment)
print(settings.secret_key)
print(len(settings.secret_key.get_secret_value()))

bad = {"APP_SECRET_KEY": "short", "APP_WORKRES": "4"}
try:
    load_settings(bad)
except ValidationError as e:
    for error in e.errors():
        print(error["loc"][0], "->", error["type"])
```

</CodeExample>

A lot of good things happen in a few lines:

- `"4"` became the integer `4`, and `ge=1, le=32` rejects silly values.
- **`SecretStr`** prints as `**********`, so the key can't leak into logs or error pages by accident; you have to ask for it with `get_secret_value()`.
- The **`APP_` prefix** keeps our variables apart from everything else in the environment, and `extra="forbid"` turns the typo `APP_WORKRES` into an error instead of a silently ignored setting.
- `load_settings` takes the environment **as a parameter**. In the app you call `load_settings(os.environ)`; in tests you pass a plain dict. No monkeypatching needed.

On your machine, the **`pydantic-settings`** package does the same thing with less code, and can also read a local `.env` file:

```python
# pip install pydantic-settings
from pydantic import Field, SecretStr
from pydantic_settings import BaseSettings, SettingsConfigDict

class Settings(BaseSettings):
    model_config = SettingsConfigDict(
        env_prefix="APP_", env_file=".env"
    )
    database_url: str
    secret_key: SecretStr = Field(min_length=32)
    workers: int = 2

settings = Settings()   # reads APP_* from the environment
```

<Callout type="tip" title="Fail fast, fail loudly">

A service with broken config should **refuse to start**, with a clear message naming the bad variable. During a deploy, that means the new version never becomes healthy, so the old version keeps serving traffic while you fix the typo. A service that starts anyway and fails on the first real request is much worse.

</Callout>

## Structured logging

In production, nobody reads logs line by line: they're collected from every server into a tool like Grafana Loki, Datadog or CloudWatch and **searched**. A free-text line like `Order 42 placed, total 19.99` is hard to filter. A **structured** log line is a small JSON object with named fields, so "show me every warning for order 42" is a simple query:

<CodeExample output={`{"level": "INFO", "logger": "shop.orders", "msg": "order placed", "order_id": 42, "total": 19.99}
{"level": "WARNING", "logger": "shop.orders", "msg": "payment slow", "order_id": 42, "ms": 2300}`}>

```python
import json
import logging
import sys

class JsonFormatter(logging.Formatter):
    def format(self, record: logging.LogRecord) -> str:
        entry = {
            "level": record.levelname,
            "logger": record.name,
            "msg": record.getMessage(),
        }
        entry.update(getattr(record, "fields", {}))
        return json.dumps(entry)

handler = logging.StreamHandler(sys.stdout)
handler.setFormatter(JsonFormatter())
logging.basicConfig(
    level=logging.INFO, handlers=[handler], force=True
)

log = logging.getLogger("shop.orders")
log.info("order placed",
         extra={"fields": {"order_id": 42, "total": 19.99}})
log.debug("cart details")     # below INFO: not shown
log.warning("payment slow",
            extra={"fields": {"order_id": 42, "ms": 2300}})
```

</CodeExample>

A real formatter also adds a timestamp (`"time": self.formatTime(record)`); we left it out here so the output stays the same every run. Some habits that make logs useful:

- **Log to stdout**, not to files. The container platform collects stdout; that's another twelve-factor rule.
- Add a **request id** to every line of a request (a middleware creates it and passes it on, often via `contextvars`), so you can follow one request through all its log lines and across services.
- Choose levels deliberately: `INFO` for business events, `WARNING` for "odd but handled", `ERROR` for "someone should look at this".
- **Never log secrets or personal data**: passwords, tokens, full card numbers. Log ids instead.

The `structlog` and `python-json-logger` packages give you all of this ready-made.

## Health checks

Load balancers and container platforms constantly ask your service *"are you OK?"* by calling an HTTP endpoint. There are two different questions, and mixing them up causes outages:

- **Liveness** (`/health/live`): *is the process working at all?* If not, the platform **restarts** it. Keep this check trivial.
- **Readiness** (`/health/ready`): *can you handle requests right now?* If not, the load balancer **stops sending traffic** to this instance until it recovers. This is where you check the database.

<CodeExample output={`{'status': 'ok'}
{'status': 'ok', 'database': 'ok'}
503 {'status': 'unavailable', 'database': 'down'}
200`}>

```python
import sqlite3
from collections.abc import Callable

from fastapi import FastAPI
from fastapi.responses import JSONResponse
from fastapi.testclient import TestClient

def create_app(check_db: Callable[[], bool]) -> FastAPI:
    app = FastAPI()

    @app.get("/health/live")
    def live():
        return {"status": "ok"}

    @app.get("/health/ready")
    def ready():
        try:
            db_ok = check_db()
        except Exception:
            db_ok = False
        if not db_ok:
            return JSONResponse(
                {"status": "unavailable", "database": "down"},
                status_code=503,
            )
        return {"status": "ok", "database": "ok"}

    return app

conn = sqlite3.connect(":memory:")

def check_sqlite() -> bool:
    return conn.execute("SELECT 1").fetchone() == (1,)

client = TestClient(create_app(check_sqlite))
print(client.get("/health/live").json())
print(client.get("/health/ready").json())

conn.close()                          # the database "goes down"
response = client.get("/health/ready")
print(response.status_code, response.json())
print(client.get("/health/live").status_code)
```

</CodeExample>

When the database goes down, readiness answers **503 Service Unavailable** while liveness stays happy. That's exactly right: restarting the app wouldn't fix the database. Notice the **app factory** `create_app(...)`: instead of a global `app`, a function builds the app from its dependencies, so tests can build one with a fake database check.

<Callout type="warning" title="Don't let the database restart your whole fleet">

A classic outage: someone checks the database in the **liveness** probe. The database has a 30-second hiccup, every instance fails liveness, the platform restarts all of them at once, and they all reconnect at the same moment, which knocks the database over again. Keep liveness trivial, keep health endpoints fast and unauthenticated, and don't let them leak details like versions of internal systems.

</Callout>

## Packaging the app in a container

A **container image** bundles your code, its dependencies and a Python interpreter into one artifact that runs the same on your laptop, in CI and in production. A good Dockerfile for a Python service uses two tricks: a **multi-stage build** (install dependencies in one stage, copy only the result into a small final image without compilers and caches) and a **non-root user** (if someone breaks into the app, they aren't root inside the container):

```dockerfile
# ---- stage 1: build the dependencies ----
FROM python:3.14-slim AS build
RUN python -m venv /venv
ENV PATH="/venv/bin:$PATH"
COPY requirements.txt .
RUN pip install --no-cache-dir -r requirements.txt

# ---- stage 2: the small runtime image ----
FROM python:3.14-slim
ENV PYTHONDONTWRITEBYTECODE=1 \
    PYTHONUNBUFFERED=1 \
    PATH="/venv/bin:$PATH"
RUN useradd --create-home --uid 10001 app
WORKDIR /app
COPY --from=build /venv /venv
COPY src/ ./src/
USER app
EXPOSE 8000
CMD ["uvicorn", "src.main:app", "--host", "0.0.0.0", \
     "--port", "8000", "--proxy-headers"]
```

Line by line, the important parts:

- `requirements.txt` is copied and installed **before** the source code. Docker caches each step, so changing your code doesn't reinstall every package.
- `PYTHONUNBUFFERED=1` makes logs appear immediately instead of sitting in a buffer.
- The code stays owned by root and only readable for the `app` user, so a compromised process can't rewrite it.
- `CMD` uses the **list form**, so uvicorn is the main process and receives the `SIGTERM` signal on shutdown (more on that below).

Add a `.dockerignore` so secrets and junk never end up in the image:

```text
# .dockerignore
.env
.git
.venv
__pycache__
tests
```

For local development, **Docker Compose** starts the app together with its database, with one command (`docker compose up --build`):

```yaml
services:
  api:
    build: .
    ports:
      - "8000:8000"
    environment:
      APP_ENVIRONMENT: dev
      APP_DATABASE_URL: postgresql+psycopg://app:app@db:5432/app
    env_file: .env          # APP_SECRET_KEY lives here, not in git
    depends_on:
      db:
        condition: service_healthy

  db:
    image: postgres:17
    environment:
      POSTGRES_USER: app
      POSTGRES_PASSWORD: app
      POSTGRES_DB: app
    volumes:
      - pgdata:/var/lib/postgresql/data
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U app"]
      interval: 5s
      retries: 5

volumes:
  pgdata:
```

Services reach each other by name (`db:5432`), the named volume keeps the database between restarts, and `condition: service_healthy` waits for Postgres to accept connections before starting the API. The dev password `app` is fine here; production secrets come from the platform's secret store, never from a compose file in git.

## Workers behind a reverse proxy

In production you don't expose uvicorn directly to the internet. A **reverse proxy** (nginx, Caddy, Traefik, or a cloud load balancer) sits in front and handles HTTPS certificates, compression, slow clients, request size limits and often rate limiting, then forwards requests to your app:

```bash
# one container, several worker processes
uvicorn src.main:app --host 0.0.0.0 --port 8000 \
  --workers 4 --proxy-headers --forwarded-allow-ips "10.0.0.0/8"

# or with FastAPI's own CLI
fastapi run src/main.py --workers 4
```

A few rules of thumb:

- One Python process uses **one CPU core** for Python code (the GIL from the internals module), so you run several **worker processes**, roughly one per core for async apps.
- On **Kubernetes** or similar platforms, the usual choice is **one worker per container** and more container replicas: the platform does the process management and restarts.
- `--proxy-headers` makes uvicorn trust `X-Forwarded-For` and `X-Forwarded-Proto` from the proxy, so the app sees the real client IP and `https`. Only trust them from your proxy's addresses (`--forwarded-allow-ips`), or clients could fake their IP to dodge your rate limits.
- Workers are separate processes: anything kept in memory (a rate-limit counter, a cache) is **per worker**. Shared state belongs in Redis or the database.

## Continuous integration

**CI** runs your checks automatically on every push and pull request, so broken code never reaches `main`. With GitHub Actions, it's a YAML file in `.github/workflows/`:

```yaml
name: CI
on:
  push:
    branches: [main]
  pull_request:

jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v5
      - uses: actions/setup-python@v6
        with:
          python-version: "3.14"
          cache: pip
      - run: pip install -r requirements.txt -r requirements-dev.txt
      - run: ruff check .
      - run: pytest
      - run: pip-audit -r requirements.txt

  image:
    needs: test
    if: github.ref == 'refs/heads/main'
    runs-on: ubuntu-latest
    permissions:
      contents: read
      packages: write
    steps:
      - uses: actions/checkout@v5
      - uses: docker/login-action@v3
        with:
          registry: ghcr.io
          username: ${{ github.actor }}
          password: ${{ secrets.GITHUB_TOKEN }}
      - uses: docker/build-push-action@v6
        with:
          push: true
          tags: ghcr.io/${{ github.repository }}:${{ github.sha }}
```

The `test` job lints, tests and audits dependencies on every pull request. Only when that passes on `main` does the `image` job build the Docker image and push it to a registry, **tagged with the commit hash**, so you always know exactly which code is running and can roll back to any earlier tag. Secrets come from GitHub's encrypted secrets (`secrets.GITHUB_TOKEN`), never from the YAML, and `permissions` gives the job only what it needs. From there, a deploy step (or a tool like Argo CD) rolls out the new image.

## Deploying without downtime

Users shouldn't notice a deploy. The common strategies:

| Strategy | How it works | Trade-off |
| --- | --- | --- |
| **Rolling** | replace instances a few at a time; each new one must pass readiness first | simple; old and new versions run side by side for a while |
| **Blue-green** | start a full new set ("green"), then switch all traffic at once | instant rollback by switching back; needs double capacity briefly |
| **Canary** | send 1–5% of traffic to the new version, watch the metrics, then increase | catches problems early with few users affected; needs good monitoring |

All of them depend on the pieces from this lesson. **Readiness checks** keep traffic away from instances that aren't ready. **Graceful shutdown** matters too: when the platform stops an old instance it sends `SIGTERM`, and uvicorn stops accepting new connections and finishes the requests in progress before exiting, so give it enough time (`--timeout-graceful-shutdown`).

The hardest part is usually the **database**. During a rolling deploy, old and new code run against the **same** schema, so changes go in backwards-compatible steps, a pattern called **expand and contract**: first add the new column (old code ignores it), deploy code that writes both, backfill, switch reads, and only in a later release drop the old column. Renaming a column in one go is the classic way to break a "zero-downtime" deploy.

## Monitoring and alerts

Once it's live, you need to know it's working **before** your users tell you. Observability has three pillars:

- **Metrics**: numbers over time, cheap to store and great for dashboards and alerts. For every service, track the **RED** metrics: **R**ate (requests per second), **E**rrors (failed requests) and **D**uration (latency, as percentiles like p50 and p99, since averages hide the slow requests). Add saturation: CPU, memory, database connections. Prometheus and Grafana are the classic open-source pair.
- **Logs**: the structured events from earlier, for the details of what happened.
- **Traces**: one request's journey through every service and database call, with timings, so you can see *where* the slow part is. **OpenTelemetry** is the standard, with automatic instrumentation for FastAPI, SQLAlchemy and httpx.

Plus **error tracking** (Sentry and similar) that groups exceptions with their stack traces.

For **alerts**, page a human only for **symptoms users feel**: "error rate above 2% for 5 minutes" or "p99 latency above 1 second", not "CPU at 80%". Teams often define **SLOs** (service level objectives, like "99.9% of requests succeed each month") and alert when they're burning through the allowed failures too fast. Every alert should be actionable and link to a **runbook** saying what to check first; an alert that fires daily and gets ignored is worse than none, because it trains people to ignore the real one.

from collections.abc import Callable, Mapping
from typing import Literal

import pytest
from fastapi import FastAPI
from fastapi.responses import JSONResponse
from fastapi.testclient import TestClient
from pydantic import (
    BaseModel, ConfigDict, Field, SecretStr, ValidationError,
    model_validator,
)


class Settings(BaseModel):
    model_config = ConfigDict(extra="forbid", frozen=True)

    app_name: str = "panda-api"
    environment: Literal["dev", "staging", "prod"] = "dev"
    database_url: str
    secret_key: SecretStr = Field(min_length=32)
    debug: bool = False
    workers: int = Field(default=2, ge=1, le=32)

    @model_validator(mode="after")
    def no_debug_in_prod(self):
        if self.environment == "prod" and self.debug:
            raise ValueError("debug must be off in prod")
        return self


def load_settings(env: Mapping[str, str]) -> Settings:
    values = {
        name.removeprefix("APP_").lower(): value
        for name, value in env.items()
        if name.startswith("APP_")
    }
    return Settings.model_validate(values)


def create_app(
    settings: Settings, check_db: Callable[[], bool]
) -> FastAPI:
    app = FastAPI(title=settings.app_name, debug=settings.debug)

    @app.get("/health/live")
    def live():
        return {"status": "ok"}

    @app.get("/health/ready")
    def ready():
        try:
            db_ok = check_db()
        except Exception:
            db_ok = False
        if not db_ok:
            return JSONResponse(
                {"status": "unavailable"}, status_code=503
            )
        return {"status": "ok", "environment": settings.environment}

    return app

## Recap

- **Twelve-factor config**: one build for every environment, settings from **environment variables**, loaded into a validated, frozen settings object at startup (`APP_` prefix, `extra="forbid"`, `SecretStr`), and **fail fast** when something is wrong.
- **Structured logs** are JSON lines to stdout with named fields and request ids, and never contain secrets.
- **Liveness** says "restart me if this fails" and stays trivial; **readiness** says "don't send me traffic" and checks dependencies like the database (503 when down). An **app factory** makes both easy to test.
- A good **Dockerfile** is multi-stage, installs dependencies before copying code, runs as a **non-root user** and uses the list form of `CMD`; **Compose** runs the app with its database locally.
- Run several **uvicorn workers** (or one per container on Kubernetes) behind a **reverse proxy** that handles HTTPS; trust forwarded headers only from the proxy.
- **CI** lints, tests and audits every change, then builds an image tagged with the commit hash.
- **Zero-downtime deploys** (rolling, blue-green, canary) rely on readiness checks, graceful shutdown and expand-and-contract database migrations.
- **Monitor** with metrics (RED), logs and traces (OpenTelemetry), and alert on symptoms users feel, with a runbook for every alert.
