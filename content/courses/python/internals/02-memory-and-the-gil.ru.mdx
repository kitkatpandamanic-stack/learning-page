Python управляет памятью за вас: вы никогда не вызываете `free()`. Это прекрасно — пока сервис за выходные медленно не разрастётся с 200 МБ до 4 ГБ и кому-то не придётся выяснять почему. А ещё есть знаменитый **GIL** (глобальная блокировка интерпретатора, Global Interpreter Lock), который в интернете винят в медленности любой программы на Python — обычно те, кто не может объяснить, что он на самом деле делает. В этом уроке вы узнаете, как CPython на самом деле освобождает память, как выследить утечку и что GIL означает для ваших потоков в 3.14. 🧠

## Подсчёт ссылок

У каждого объекта CPython есть счётчик: **сколько ссылок на меня указывает?** Ссылка — это всё, что ссылается на объект: имя переменной, ячейка в списке, значение в словаре, атрибут. Механизм называется **подсчётом ссылок** (reference counting), а `sys.getrefcount()` показывает значение счётчика:

<CodeExample output={`2
0`}>

```python
import sys

data = [1, 2, 3]
before = sys.getrefcount(data)

alias = data
box = {"items": data}
print(sys.getrefcount(data) - before)

del alias
box.clear()
print(sys.getrefcount(data) - before)
```

</CodeExample>

Две новые ссылки (`alias` и значение в словаре) увеличивают счётчик на 2; когда мы их убираем, он возвращается назад. Мы специально печатаем **разницу**: абсолютное число включает временные ссылки (сам аргумент функции тоже считается), а CPython 3.14 пропускает часть подсчёта с помощью «заимствованных» (borrowed) ссылок — помните `LOAD_FAST_BORROW` из прошлого урока? — поэтому точные числа меняются от версии к версии.

Главное правило: **когда счётчик падает до нуля, объект освобождается немедленно**. Обратите внимание: `del alias` не удаляет список, он убирает одно имя. Момент «смерти» объекта можно увидеть с помощью `__del__` — метода, который CPython вызывает прямо перед освобождением объекта:

<CodeExample output={`открыто db-1
работаем
освобождено db-1
запрос обработан`}>

```python
class Connection:
    def __init__(self, name):
        self.name = name
        print(f"открыто {name}")

    def __del__(self):
        print(f"освобождено {self.name}")

def handle_request():
    conn = Connection("db-1")
    print("работаем")

handle_request()
print("запрос обработан")
```

</CodeExample>

Когда `handle_request` возвращает управление, её фрейм исчезает, вместе с ним уходит локальная `conn`, счётчик достигает нуля, и объект освобождается тут же, **до** строки `запрос обработан`. Такая предсказуемость — особенность CPython. Но не стройте на ней логику:

<Callout type="warning" title="Не освобождайте ресурсы в __del__">

Другие реализации Python (например, PyPy) освобождают объекты позже, трейсбек исключения может держать объекты живыми дольше, чем вы ожидаете, а `__del__` не обязательно выполнится при завершении интерпретатора. Закрывайте файлы, соединения и блокировки **явно** с помощью `with` (менеджеров контекста). Используйте `__del__` разве что для отладки.

</Callout>

## Циклы и сборщик мусора

У подсчёта ссылок есть одно слепое пятно: **циклы**. Если `a` указывает на `b`, а `b` обратно на `a`, оба счётчика навсегда остаются равными 1, даже когда больше ничто не может до них добраться. Для этого и нужен **циклический сборщик мусора** (cyclic garbage collector) CPython — модуль `gc`:

<CodeExample output={`имён нет, объекты ещё живы
освобождён a
освобождён b
сборщик отработал: True`}>

```python
import gc

class Node:
    def __init__(self, name):
        self.name = name
        self.partner = None

    def __del__(self):
        print(f"освобождён {self.name}")

a = Node("a")
b = Node("b")
a.partner = b
b.partner = a    # цикл: a -> b -> a

del a, b
print("имён нет, объекты ещё живы")
found = gc.collect()
print("сборщик отработал:", found > 0)
```

</CodeExample>

Сборщик запускается автоматически время от времени (в зависимости от того, сколько объектов создано с прошлого запуска), находит группы объектов-контейнеров, достижимых только друг из друга, и освобождает их. Мы вызвали `gc.collect()` вручную, чтобы это произошло прямо сейчас. В реальном коде циклы встречаются часто: деревья «родитель — потомок» с обратными ссылками, объекты, которые хранят собственный связанный метод как колбэк, исключения, которые хранят трейсбек, ссылающийся на фрейм, где лежит само исключение.

Сборщик группирует объекты по возрасту («поколениям», generations), потому что большинство объектов умирают молодыми; точная схема и пороги менялись от версии к версии Python, так что не настраивайте их без измерений. История из практики: Instagram, как известно, **отключил** сборщик в своих Django-воркерах (а позже использовал для той же цели `gc.freeze()`, появившийся в 3.7), потому что его проходы трогали память, общую для форкнутых процессов, и вынуждали её копировать. Это крайняя, тщательно измеренная оптимизация, а не настройка по умолчанию.

## Слабые ссылки для кэшей

Иногда нужно **ссылаться** на объект, не **удерживая его в живых**. **Слабая ссылка** (weak reference) не увеличивает счётчик ссылок. Когда объект умирает, слабая ссылка возвращает `None`:

<CodeExample output={`True
Продажи за Q3
None`}>

```python
import weakref

class Report:
    def __init__(self, title):
        self.title = title

report = Report("Продажи за Q3")
ref = weakref.ref(report)

print(ref() is report)
print(ref().title)

del report       # единственная сильная ссылка
print(ref())
```

</CodeExample>

Главный сценарий — **кэш**, который не должен вызывать утечку. Обычный кэш-словарь хранит каждое значение вечно. **`WeakValueDictionary`** хранит запись, только пока значение ещё использует кто-то в программе:

<CodeExample output={`загружаю logo.png
True 1
0
загружаю logo.png`}>

```python
import weakref

class Image:
    def __init__(self, name):
        self.name = name

cache = weakref.WeakValueDictionary()

def load(name):
    image = cache.get(name)
    if image is None:
        print(f"загружаю {name}")
        image = Image(name)
        cache[name] = image
    return image

logo = load("logo.png")
again = load("logo.png")      # из кэша
print(logo is again, len(cache))

del logo, again               # теперь его никто не использует
print(len(cache))
load("logo.png")
```

</CodeExample>

Пока кто-то держит картинку, каждый `load` возвращает один и тот же объект. Как только последний пользователь её отпускает, запись исчезает сама. Не каждый объект поддерживает слабые ссылки: встроенные `int`, `str`, `list` и `dict` не поддерживают, как и классы со `__slots__`, если вы об этом специально не попросите (это понадобится в упражнении).

## __slots__ и размер объекта

Обычный экземпляр может в любой момент получить новые атрибуты, потому что у него есть **`__dict__`**. Если вы создаёте миллионы маленьких объектов, можно сообщить Python точные имена атрибутов через **`__slots__`**. Тогда экземпляры получают хранилище фиксированного размера и не имеют `__dict__`:

<CodeExample output={`True False
AttributeError: 'SlimPoint' object has no attribute 'z' and no __dict__ for setting new attributes
True
True`}>

```python
import sys

class Point:
    def __init__(self, x, y):
        self.x = x
        self.y = y

class SlimPoint:
    __slots__ = ("x", "y")

    def __init__(self, x, y):
        self.x = x
        self.y = y

p = Point(1, 2)
s = SlimPoint(1, 2)
p.z = 3                         # всё в порядке: у p есть __dict__
print(hasattr(p, "__dict__"), hasattr(s, "__dict__"))

try:
    s.z = 3
except AttributeError as error:
    print("AttributeError:", error)

big = list(range(100_000))
wrapper = [big]
print(sys.getsizeof(wrapper) < 100)
print(sys.getsizeof(big) > 100_000)
```

</CodeExample>

Два урока в одном примере:

- `__slots__` экономит память и **ловит опечатки** (`s.z = 3` падает, вместо того чтобы молча создать атрибут). Цена: нельзя добавлять атрибуты «на лету», а некоторым инструментам, которые ждут `__dict__` (или слабые ссылки), нужны дополнительные слоты. `@dataclass(slots=True)` сгенерирует их за вас.
- **`sys.getsizeof` поверхностный**. Он измеряет только сам объект, а не то, на что тот ссылается: список `wrapper` из одного элемента выглядит крошечным, хотя в нём лежит список из 100 000 чисел. Размеры в байтах ещё и отличаются между платформами (этот сайт работает на 32-битном WebAssembly, а ваш ноутбук — 64-битный).

Чтобы измерить, сколько объекты стоят **на самом деле**, считайте реальные выделения памяти с помощью `tracemalloc`:

<CodeExample output={`True`}>

```python
import tracemalloc

class Point:
    def __init__(self, x, y):
        self.x = x
        self.y = y

class SlimPoint:
    __slots__ = ("x", "y")

    def __init__(self, x, y):
        self.x = x
        self.y = y

def memory_used(cls, n=10_000):
    tracemalloc.start()
    points = [cls(i, i) for i in range(n)]
    size, peak = tracemalloc.get_traced_memory()
    tracemalloc.stop()
    return size

print(memory_used(SlimPoint) < memory_used(Point))
```

</CodeExample>

Слоты выигрывают, но меньше, чем утверждают старые статьи в блогах: современный CPython и так хранит атрибуты экземпляра компактно и создаёт настоящий `__dict__`, только когда вы его запрашиваете. Берите `__slots__`, когда экземпляров **очень много** и измерения говорят, что память важна.

## Ищем утечку с помощью tracemalloc

«Утечка» в Python — это почти никогда не потерянная память; это память, на которую **всё ещё ссылается** что-то, о чём вы забыли: список на уровне модуля, кэш без ограничения, список колбэков, который только растёт. **`tracemalloc`** записывает, где произошло каждое выделение памяти, а сравнение двух **снимков** (snapshots) указывает прямо на виноватую строку:

<CodeExample output={`строка 6: +2 МБ
200 новых блоков`}>

```python
import tracemalloc

_seen = []

def handle(request_id):
    body = "x" * 10_000
    _seen.append(body)     # упс: хранится вечно
    return len(body)

tracemalloc.start()
before = tracemalloc.take_snapshot()

for request_id in range(200):
    handle(request_id)

after = tracemalloc.take_snapshot()
tracemalloc.stop()

top = after.compare_to(before, "lineno")[0]
frame = top.traceback[0]
print(f"строка {frame.lineno}: +{top.size_diff // 1_000_000} МБ")
print(f"{top.count_diff} новых блоков")
```

</CodeExample>

Больше всего памяти прибавилось на строке 6 — в `"x" * 10_000`, и 200 таких блоков выжили. Строка выделения говорит, **что** накапливается; дальше вы ищете, **кто** это держит (здесь — `_seen`). В продакшене порядок действий тот же: сделать снимок, дать сервису поработать под нагрузкой, сделать ещё один, сравнить. `tracemalloc` замедляет программу, поэтому включайте его на одном инстансе или за флагом.

<Callout type="tip" title="Обычные подозреваемые">

Когда память в долгоживущем сервисе растёт, проверяйте в таком порядке: кэши без ограничения размера (используйте `functools.lru_cache(maxsize=...)` или слабый кэш), списки и словари на уровне модуля, которые собирают данные каждого запроса, обработчики событий, которые добавляют и никогда не удаляют, и большие объекты, которые держит живыми сохранённое исключение или трейсбек.

</Callout>

## GIL: что это на самом деле

**Global Interpreter Lock** (GIL, глобальная блокировка интерпретатора) в CPython — это блокировка, которую поток должен удерживать, чтобы выполнять байт-код Python. Поэтому в обычном процессе CPython **в каждый момент Python-код выполняет только один поток**, даже на 16-ядерной машине.

Зачем она нужна? Вспомните счётчики ссылок: их меняет каждое присваивание. Без GIL два потока, одновременно обновляющие один счётчик, могли бы испортить его и освободить объект, который ещё используется. Одна большая блокировка сделала внутренности CPython (и тысячи C-расширений) простыми и быстрыми для однопоточного кода, а такого кода большинство.

Чего GIL **не** делает — так это не делает **ваш** код потокобезопасным. Он лишь гарантирует, что отдельные инструкции байт-кода не будут разорваны посередине. Посмотрите на `counter += 1`:

<CodeExample output={`  5           RESUME                   0

  7           LOAD_GLOBAL              0 (counter)
              LOAD_SMALL_INT           1
              BINARY_OP               13 (+=)
              STORE_GLOBAL             0 (counter)
              LOAD_CONST               1 (None)
              RETURN_VALUE`}>

```python
import dis

counter = 0

def increment():
    global counter
    counter += 1

dis.dis(increment)
```

</CodeExample>

Это загрузка, сложение и сохранение. CPython может переключить потоки **между** любыми двумя инструкциями (по умолчанию он просит работающий поток уступить каждые 5 миллисекунд). Если два потока оба загрузят `counter` равным 41, оба сохранят 42, и одно увеличение потеряется. На своей машине общее состояние защищают блокировкой:

```python
import threading

counter = 0
lock = threading.Lock()

def increment_many():
    global counter
    for _ in range(100_000):
        with lock:            # здесь одновременно только один поток
            counter += 1

threads = [threading.Thread(target=increment_many) for _ in range(4)]
for t in threads:
    t.start()
for t in threads:
    t.join()
print(counter)                # 400000, каждый раз
```

(В среде выполнения этого сайта потоков нет, так что этот блок — для вашей машины. В следующем модуле мы подробно разберём потоки, процессы и блокировки.)

## Потоки для I/O, процессы для CPU

Если Python в каждый момент выполняет только один поток, зачем вообще нужны потоки? Потому что GIL **отпускается во время ожидания**. Блокирующий ввод-вывод (чтение из сокета, ожидание базы данных, `time.sleep`) отпускает его, как и многие C-расширения, пока они перемалывают числа (NumPy, сжатие, хэширование больших буферов). Поэтому:

- **Работа, ограниченная вводом-выводом** (I/O-bound: HTTP-вызовы, запросы к базе данных, передача файлов): потоки работают хорошо, потому что они проводят время в ожидании с отпущенным GIL. Другой хороший вариант — `asyncio`.
- **Работа на чистом Python, ограниченная процессором** (CPU-bound: парсинг, вычисления в циклах): потоки **не дают ускорения**, а часто даже немного замедляют. Используйте **процессы** (`multiprocessing`, `ProcessPoolExecutor`): у каждого процесса свой интерпретатор и свой GIL. Цена — время запуска и копирование (pickle) данных между процессами.
- **Векторизованная работа**: перенесите цикл в NumPy или другую библиотеку на C/Rust, которая может отпустить GIL и сама задействовать несколько ядер.

## Free-threaded Python и субинтерпретаторы

GIL наконец становится необязательным. [PEP 703](https://peps.python.org/pep-0703/) добавил **free-threaded-сборку** (free-threaded build) CPython, которая работает без GIL, так что потоки могут выполнять Python-код на нескольких ядрах по-настоящему параллельно:

- В **3.13** она была **экспериментальной**: отдельная сборка (часто устанавливается как `python3.13t`).
- В **3.14** она **официально поддерживается** (больше не экспериментальная), но по-прежнему остаётся **необязательной отдельной сборкой** (`python3.14t`). Обычный `python3.14`, который вы скачиваете, всё ещё с GIL.
- Она стоит некоторой **однопоточной скорости** (документация 3.14 оценивает потери примерно в 5–10%) и дополнительной памяти, потому что без глобальной блокировки подсчёт ссылок требует дополнительной осторожности.
- C-расширения должны объявить, что они безопасны без GIL. Импорт расширения, которое этого не сделало, **снова включает GIL** (с предупреждением), так что проверьте зависимости, прежде чем праздновать.

Во время выполнения можно узнать, какая у вас сборка. На этом сайте — обычная:

<CodeExample output={`0
True`}>

```python
import sys
import sysconfig

print(sysconfig.get_config_var("Py_GIL_DISABLED"))
print(sys._is_gil_enabled())
```

</CodeExample>

Второй путь — **субинтерпретаторы** (sub-interpreters): несколько независимых интерпретаторов внутри **одного** процесса. С 3.12 у каждого из них может быть **собственный GIL** ([PEP 684](https://peps.python.org/pep-0684/)), а в 3.14 для них появился API в стандартной библиотеке: модуль `concurrent.interpreters` и `concurrent.futures.InterpreterPoolExecutor` ([PEP 734](https://peps.python.org/pep-0734/)). Они дают изоляцию как у процессов (объекты не общие, данные передаются через очереди), но с меньшими накладными расходами, чем отдельные процессы.

Так что же использовать сегодня? Для большинства команд в 2026 году: `asyncio` или потоки для I/O, процессы для тяжёлых вычислений на чистом Python, и следите за free-threading по мере того, как ваши библиотеки добавляют поддержку. У «зависит от ситуации» здесь есть конкретный критерий: **сначала профилируйте**, а потом выбирайте инструмент, который подходит туда, куда уходит время.

1. `ThumbnailCache` хранил миниатюры в `weakref.WeakValueDictionary`, чтобы запись исчезала, когда эту миниатюру больше никто не использует. `get` по-прежнему должен возвращать закэшированный объект, пока тот жив, и вызывать `render` только при необходимости. `len(cache)` считает живые записи.

```python
import weakref


class Thumbnail:
    __slots__ = ("name", "pixels", "__weakref__")

    def __init__(self, name, pixels):
        self.name = name
        self.pixels = pixels


class ThumbnailCache:
    def __init__(self, render):
        self.render = render       # функция: name -> Thumbnail
        self._items = weakref.WeakValueDictionary()

    def get(self, name):
        thumb = self._items.get(name)
        if thumb is None:
            thumb = self.render(name)
            self._items[name] = thumb
        return thumb

    def __len__(self):
        return len(self._items)


renders = []

def render(name):
    renders.append(name)
    return Thumbnail(name, b"\x00" * 1_000)

cache = ThumbnailCache(render)
a = cache.get("cat.png")
b = cache.get("cat.png")
print(a is b, renders)

del a, b
print(len(cache))
```

## Итоги

- CPython освобождает большинство объектов через **подсчёт ссылок**: когда счётчик достигает нуля, объект освобождается немедленно. `del` удаляет имя, а не объект.
- **Циклический сборщик мусора** (`gc`) освобождает группы объектов, которые ссылаются только друг на друга.
- Не полагайтесь на `__del__` для очистки ресурсов; используйте `with`.
- **Слабые ссылки** (`weakref.ref`, `WeakValueDictionary`) указывают на объекты, не удерживая их в живых, — идеально для кэшей.
- **`__slots__`** убирает `__dict__` у каждого экземпляра, экономя память и ловя опечатки; добавьте `"__weakref__"`, если нужны слабые ссылки. `sys.getsizeof` — **поверхностный**.
- Снимки **`tracemalloc`** показывают, какая строка выделила накапливающуюся память; дальше ищите, кто её всё ещё держит.
- **GIL** позволяет выполнять байт-код Python только одному потоку за раз. Он защищает интерпретатор, а не ваши данные: для общего состояния используйте блокировки. Потоки помогают с **I/O**, процессы — с **CPU-bound**-кодом на чистом Python.
- **Free-threaded** CPython официально поддерживается в 3.14 как необязательная отдельная сборка; **субинтерпретаторы** с собственным GIL получили в 3.14 стандартный API (`concurrent.interpreters`).
