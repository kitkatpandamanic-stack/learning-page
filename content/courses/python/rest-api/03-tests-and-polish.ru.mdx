Projects API работает. Но «у меня всё работало, когда я пробовал» — недостаточно для API, от которого зависят другие приложения: следующее изменение может незаметно сломать эндпоинт (endpoint), который вы даже не трогали. В этой заключительной части вы напишете **полный набор тестов API**, чтобы каждый эндпоинт, каждая ошибка и каждое сохранение проверялись автоматически — меньше чем за секунду. 🧪

Вам пригодится всё из урока [Фикстуры и параметризация](/learn/python/fixtures-and-parametrize) и фикстура `client` с `dependency_overrides` из [API списка дел](/learn/python/todo-api) — только теперь под ними настоящая база данных.

## Два слоя — два вида тестов

**Тесты репозитория** у нас уже есть с первой части. Они быстрые и точные, но не видят ничего, что связано с HTTP. **Тесты API** отправляют настоящие запросы (requests) через `TestClient` и проверяют то, что увидел бы клиент. Вместе они ловят разные ошибки:

| Ошибка в... | Кто её поймает |
| --- | --- |
| запросе к базе, фильтре, каскаде | тесты репозитория (и тесты API) |
| правиле `Field`, забытом 404, неверном коде ответа | тесты API |
| форме JSON (`response_model`, `from_attributes`) | тесты API |
| связке частей: `Depends`, забытом `commit()` в эндпоинте | тесты API |

Большая часть поведения API приходится на вторую группу, поэтому в хорошем наборе **много** тестов API. Они всё равно быстрые, потому что база данных живёт в памяти.

## Свежая база данных для каждого теста

Тесты API никогда не должны работать с настоящей базой приложения: они заполнили бы её тестовыми данными, а тесты видели бы остатки друг друга и проходили или падали в зависимости от порядка запуска. Решение — приём из API списка дел: фикстура (fixture) `client`, которая **подменяет `get_session`**, чтобы во время теста каждый эндпоинт получал сессию на **совершенно новой пустой тестовой базе**. Вот весь шаблон на маленьком API заметок:

<CodeExample output={`...........                                          [100%]
11 passed in 0.01s`}>

```python
import pytest
from fastapi import Depends, FastAPI, HTTPException
from fastapi.testclient import TestClient
from pydantic import BaseModel, ConfigDict, Field
from sqlalchemy import create_engine, select
from sqlalchemy.orm import (
    DeclarativeBase, Mapped, Session, mapped_column,
)
from sqlalchemy.pool import StaticPool

class Base(DeclarativeBase):
    pass

class Note(Base):
    __tablename__ = "notes"
    id: Mapped[int] = mapped_column(primary_key=True)
    text: Mapped[str]

class NoteIn(BaseModel):
    text: str = Field(min_length=1)

class NoteOut(BaseModel):
    model_config = ConfigDict(from_attributes=True)
    id: int
    text: str

engine = create_engine(
    "sqlite://",
    connect_args={"check_same_thread": False},
    poolclass=StaticPool,
)
Base.metadata.create_all(engine)

def get_session():
    with Session(engine) as session:
        yield session

def get_note_or_404(
    note_id: int, session: Session = Depends(get_session)
) -> Note:
    note = session.get(Note, note_id)
    if note is None:
        raise HTTPException(status_code=404, detail="Note not found")
    return note

app = FastAPI()

@app.post("/notes", status_code=201, response_model=NoteOut)
def api_add_note(
    data: NoteIn, session: Session = Depends(get_session)
):
    note = Note(text=data.text)
    session.add(note)
    session.commit()
    return note

@app.get("/notes/{note_id}", response_model=NoteOut)
def api_get_note(note: Note = Depends(get_note_or_404)):
    return note

@app.delete("/notes/{note_id}", status_code=204)
def api_delete_note(
    note: Note = Depends(get_note_or_404),
    session: Session = Depends(get_session),
):
    session.delete(note)
    session.commit()

# ---------- тесты ----------

@pytest.fixture
def client():
    test_engine = create_engine(
        "sqlite://",
        connect_args={"check_same_thread": False},
        poolclass=StaticPool,
    )
    Base.metadata.create_all(test_engine)

    def get_test_session():
        with Session(test_engine) as session:
            yield session

    app.dependency_overrides[get_session] = get_test_session
    yield TestClient(app)
    app.dependency_overrides.clear()

@pytest.fixture
def note(client):
    return client.post("/notes", json={"text": "Buy milk"}).json()

def test_add_note(client):
    response = client.post("/notes", json={"text": "Buy milk"})
    assert response.status_code == 201
    assert response.json() == {"id": 1, "text": "Buy milk"}

def test_get_note(client, note):
    assert client.get(f"/notes/{note['id']}").json() == note

def test_every_test_has_its_own_database(client, note):
    assert note["id"] == 1

def test_the_app_database_is_never_touched(client, note):
    with Session(engine) as session:
        assert session.scalars(select(Note)).all() == []

@pytest.mark.parametrize("method, url", [
    ("GET", "/notes/99"),
    ("DELETE", "/notes/99"),
    ("GET", "/notes/0"),
])
def test_unknown_ids_give_404(client, method, url):
    response = client.request(method, url)
    assert response.status_code == 404
    assert response.json() == {"detail": "Note not found"}

@pytest.mark.parametrize("body", [
    {},
    {"text": ""},
    {"text": None},
    {"txt": "Buy milk"},
])
def test_bad_data_gives_422(client, body):
    response = client.post("/notes", json=body)
    assert response.status_code == 422

pytest.main([__file__])
```

</CodeExample>

Как работает фикстура `client`, шаг за шагом:

1. Она создаёт **новый движок** только для этого теста: пустую базу в памяти со `StaticPool` и `check_same_thread=False` — по тем же причинам, что и во второй части.
2. `create_all` создаёт таблицы.
3. `get_test_session` — зависимость (dependency) с `yield`, такая же, как `get_session`, но на тестовом движке.
4. `app.dependency_overrides[get_session] = get_test_session` делает так, что **каждый** эндпоинт и каждая зависимость, которые запрашивают `get_session` (включая `get_note_or_404`), получают вместо неё тестовую сессию.
5. После `yield` подмены очищаются, чтобы ничего не просочилось в следующий тест.

Последние два теста это доказывают: первая заметка в каждом тесте получает id `1`, а собственная база приложения остаётся пустой. В настоящих проектах иногда встречается движок, созданный один раз на весь прогон тестов (`scope="session"`), и транзакция, которая откатывается после каждого теста, — для больших баз так быстрее. Для SQLite в памяти новый движок на каждый тест — это просто и быстро.

## Фикстуры поверх фикстур

`note` — это фикстура, которая **запрашивает другую фикстуру**, `client`. pytest это видит и сначала создаёт клиента (и его свежую базу), а потом заметку. Тестам, которым нужны готовые данные, достаточно перечислить обе: `def test_get_note(client, note)`. Обе получают **один и тот же** клиент, потому что pytest создаёт каждую фикстуру один раз на тест.

В Projects API ту же работу делает фикстура `project`: она создаёт через API проект `"Garden"` и возвращает его JSON, так что тесты задач могут начинаться с `def test_...(client, project)`.

## Тестируем ошибки с parametrize

Ошибки — тоже поведение, и у API их много: любой эндпоинт с id может ответить 404, а любой эндпоинт с телом запроса (request body) — 422. `@pytest.mark.parametrize` превращает это в таблицу случаев вместо груды скопированных тестов:

- `client.request(method, url)` отправляет запрос любым HTTP-методом, так что один тест может попробовать `GET`, `DELETE` и другие. Можно передать и тело: `client.request("PATCH", url, json={...})`.
- Каждый случай показывается как отдельный тест, поэтому при падении видно, какой именно запрос сломался, например `test_unknown_ids_give_404[DELETE-/notes/99]`.
- Случаи для 422 перечисляют классические ошибки: отсутствующее поле, пустое значение, `None` и ключ с опечаткой.

<Callout type="tip" title="Что профессионалы проверяют в тестах API">

Для каждого эндпоинта: **код ответа (status code)**, **всё тело JSON целиком** (сравнение через `==` с полным словарём ловит лишние и пропавшие поля) и **побочный эффект** (действительно ли сохранилось, действительно ли удалилось?). Затем — случаи ошибок. Этот чек-лист ловит большинство реальных ошибок в API.

</Callout>

## Действительно ли сохранилось?

Вот ошибка, которую по одному ответу не увидеть. Этот эндпоинт `PATCH` меняет заметку, но забывает сделать коммит:

<CodeExample output={`PATCH вернул: {'id': 1, 'text': 'Buy oat milk'}
GET вернул:   {'id': 1, 'text': 'Buy milk'}`}>

</CodeExample>

Ответ на `PATCH` выглядит идеально, потому что он собран из изменённого объекта, пока сессия ещё открыта. Затем запрос заканчивается, сессия закрывается, изменение откатывается, и следующий запрос видит старый текст. Тест, который проверяет только ответ на `PATCH`, прошёл бы. Поэтому после каждой записи **читайте данные обратно новым запросом**: `PATCH`, потом `GET`; `DELETE`, потом `GET` с ожиданием 404.

Наш тест репозитория из первой части этого тоже не поймает: он проверяет тот же объект `task` в той же сессии. Именно поэтому полезно иметь оба вида тестов.

## Запускаем по-настоящему

На вашем компьютере набор тестов разбит на файлы, а фикстура `client` лежит в **`tests/conftest.py`**, чтобы её мог использовать любой тестовый файл:

```python
# tests/conftest.py
import pytest
from fastapi.testclient import TestClient
from sqlalchemy import create_engine
from sqlalchemy.orm import Session
from sqlalchemy.pool import StaticPool

from app.database import get_session
from app.main import app
from app.models import Base


@pytest.fixture
def client():
    test_engine = create_engine(
        "sqlite://",
        connect_args={"check_same_thread": False},
        poolclass=StaticPool,
    )
    Base.metadata.create_all(test_engine)

    def get_test_session():
        with Session(test_engine) as session:
            yield session

    app.dependency_overrides[get_session] = get_test_session
    yield TestClient(app)
    app.dependency_overrides.clear()
```

Затем из папки проекта (с пустым `__init__.py` в `app/` и `tests/`):

```bash
pip install "fastapi[standard]" sqlalchemy pytest pytest-cov
pytest
pytest --cov=app --cov-report=term-missing
fastapi dev app/main.py
```

`pytest` находит и запускает все файлы `test_*.py`. Отчёт о покрытии (coverage) из урока [Моки, покрытие и TDD](/learn/python/mocks-and-coverage) показывает строки, до которых ваши тесты так и не дошли: с набором тестов, который вы сейчас напишете, эндпоинты и репозиторий должны быть покрыты на **100%** или почти. А `fastapi dev` запускает сервер, чтобы вы могли пощёлкать по `/docs`.
