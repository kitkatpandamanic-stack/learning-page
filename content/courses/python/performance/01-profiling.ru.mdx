У каждого опытного разработчика есть похожая история. Команда неделю переписывает «медленный» парсер JSON на более быструю библиотеку, выкатывает его — а страница грузится так же медленно, как раньше. На самом деле всё тормозил запрос к базе данных внутри цикла, и его никто не измерял. Первое правило работы с производительностью короткое: **измеряйте, а не гадайте**. 🔍

Этот модуль о том, как сделать код на Python быстрым. Начнём с самого важного навыка — выяснять, **куда** на самом деле уходят время и память.

## Измеряйте, а не гадайте

Интуиция о том, что тормозит, обычно ошибается — и ваша, и чужая. Большую часть времени программа проводит в нескольких небольших **горячих точках (hot spots)**, и часто там, где их никто не ждёт. Поэтому работа над производительностью всегда идёт по одному и тому же циклу:

1. **Воспроизведите** медленный случай на реалистичных данных.
2. **Измерьте** его, чтобы получить исходную цифру.
3. **Профилируйте** (profiling), чтобы найти горячую точку.
4. **Исправьте** только эту горячую точку.
5. **Измерьте ещё раз**, чтобы доказать, что стало лучше, и запустите тесты, чтобы доказать, что всё по-прежнему работает.

В стандартной библиотеке Python для этого есть три инструмента: **`timeit`** замеряет время небольшого фрагмента кода, **`cProfile`** показывает, какие функции съедают время, а **`tracemalloc`** — какие строки занимают память.

## timeit: замер небольших фрагментов кода

Замерить время двумя вызовами `time.perf_counter()` можно, но результат будет шумным: один запуск может замедлить что угодно ещё, что делает ваш компьютер. Модуль **`timeit`** запускает код **много раз** и возвращает общее время в секундах:

<CodeExample output={`float
множество быстрее в 50+ раз: True`}>

```python
import timeit

items = list(range(10_000))
lookup = set(items)

list_time = timeit.timeit(lambda: 9_999 in items, number=1_000)
set_time = timeit.timeit(lambda: 9_999 in lookup, number=1_000)

print(type(list_time).__name__)   # всего секунд на 1000 запусков
print("множество быстрее в 50+ раз:", list_time > 50 * set_time)
```

</CodeExample>

Настоящее время мы здесь не печатаем: оно меняется от запуска к запуску и от компьютера к компьютеру. Важно **соотношение**, а проверка `in` на множестве в сотни раз быстрее, чем на списке из 10 000 элементов. Запустите сами и посмотрите на реальные цифры:

<TryIt language="python" code={`import timeit

items = list(range(10_000))
lookup = set(items)

# repeat() повторяет весь замер несколько раз
list_runs = timeit.repeat(lambda: 9_999 in items,
                          number=1_000, repeat=5)
set_runs = timeit.repeat(lambda: 9_999 in lookup,
                         number=1_000, repeat=5)

# самый быстрый запуск меньше всех пострадал от других программ
print(f"список:    {min(list_runs) * 1000:.3f} мс на 1000 поисков")
print(f"множество: {min(set_runs) * 1000:.3f} мс на 1000 поисков")
print(f"множество быстрее в {min(list_runs) / min(set_runs):.0f} раз")
`}
/>

Две привычки тех, кто замеряет производительность профессионально:

- Используйте **`timeit.repeat()`** и берите **минимум**. Более медленным запускам что-то помешало; минимум ближе всего к настоящей стоимости.
- Для быстрых экспериментов замеряйте из командной строки. `-s` — это код подготовки, его время не учитывается:

```bash
python -m timeit -s "items = list(range(10_000))" "9_999 in items"
# 5000 loops, best of 5: 52.1 usec per loop
```

## Big-O на практике

`timeit` говорит, **сколько времени** что-то занимает для одних входных данных. **Big-O** говорит, как время **растёт** вместе с данными, — и именно это решает, выдержит ли ваш код реальные данные.

Вот два способа найти общие элементы двух списков. Вместо замера времени мы считаем шаги — так рост виден точно:

<CodeExample output={`n=   10: вложенный       100 шагов, множество    10 шагов
n=  100: вложенный    10,000 шагов, множество   100 шагов
n= 1000: вложенный 1,000,000 шагов, множество 1,000 шагов`}>

```python
def common_nested(a, b):
    steps, found = 0, []
    for x in a:
        for y in b:
            steps += 1
            if x == y:
                found.append(x)
    return found, steps

def common_set(a, b):
    steps, found = 0, []
    lookup = set(b)
    for x in a:
        steps += 1
        if x in lookup:
            found.append(x)
    return found, steps

for n in [10, 100, 1_000]:
    a = list(range(n))
    b = list(range(n // 2, n + n // 2))
    slow, nested = common_nested(a, b)
    fast, flat = common_set(a, b)
    assert slow == fast
    print(f"n={n:>5}: вложенный {nested:>9,} шагов, "
          f"множество {flat:>5,} шагов")
```

</CodeExample>

Обе функции возвращают одинаковый ответ. Но вложенный цикл — это **O(n²)** («квадратичная» сложность): в 10 раз больше данных — в **100 раз** больше работы. Версия с множеством — **O(n)** («линейная»): в 10 раз больше данных — в 10 раз больше работы. На 1000 элементов вы разницы не заметите; на 1 000 000 пользователей вложенному циклу понадобится триллион шагов.

Повседневные факты о Big-O, из-за которых случается большинство реальных замедлений:

| Операция                                      | Стоимость |
| --------------------------------------------- | --------- |
| `x in list`, `list.index(x)`, `list.count(x)` | O(n)      |
| `x in set`, `x in dict`, `d[key]`             | O(1)      |
| `list.append(x)`, `list.pop()`                | O(1)      |
| `list.insert(0, x)`, `list.pop(0)`            | O(n), используйте `collections.deque` |
| `sorted(items)`                               | O(n log n) |
| цикл внутри цикла по тем же данным            | O(n²)     |

<Callout type="tip" title="Скрытый цикл">

Самые коварные ошибки O(n²) не выглядят как два цикла. `if user in active_users:` внутри цикла `for` — это цикл в цикле, если `active_users` — список. То же самое с `results = results + [x]` (каждый раз копируется весь список) и с `emails[:i]` в цикле. Если код замедляется по мере роста данных, ищите `in`, срез или `.count()` на списке внутри цикла.

</Callout>

## cProfile: куда уходит время?

Для целой программы замерять кусочки вручную не получится. **Профилировщик (profiler)** наблюдает за работой программы и записывает каждый вызов функции. В Python встроен **`cProfile`**. Любой вызов можно обернуть в `profiler.runcall(func, *args)`, а затем прочитать результаты с помощью **`pstats`**:

<CodeExample output={`лучший заказ: 9.6
строка  6: price_of     ncalls=700
строка  9: order_total  ncalls=300
строка 10: <genexpr>    ncalls=1000
строка 12: report       ncalls=1`}>

```python
import cProfile
import pstats

PRICES = {"tea": 2.5, "cake": 4.0, "bun": 3.2}

def price_of(item):
    return PRICES[item]

def order_total(order):
    return sum(price_of(item) for item in order)

def report(orders):
    totals = [order_total(order) for order in orders]
    return round(max(totals), 2)

orders = [["tea", "cake"], ["bun"] * 3, ["cake"] * 2] * 100

profiler = cProfile.Profile()
best = profiler.runcall(report, orders)
print("лучший заказ:", best)

profile = pstats.Stats(profiler).get_stats_profile()
mine = [(name, fn) for name, fn in profile.func_profiles.items()
        if fn.file_name != "~"]        # пропускаем встроенные
for name, fn in sorted(mine, key=lambda pair: pair[1].line_number):
    print(f"строка {fn.line_number:>2}: {name:<12} ncalls={fn.ncalls}")
```

</CodeExample>

`get_stats_profile()` отдаёт результаты в виде данных: словарь, где имени функции соответствует `FunctionProfile` с полями `ncalls`, `tottime`, `cumtime`, `file_name` и `line_number`. У встроенных функций вроде `sum` имя файла — `"~"`, поэтому мы их пропускаем. Порядок в словаре ничего не значит, так что мы сортируем по номеру строки.

Счётчики уже полезны: 300 заказов, 700 товаров, значит, `price_of` выполнилась 700 раз. (Генератор считается «вызванным» каждый раз, когда возобновляет работу, поэтому у `<genexpr>` их 1000.) **Число вызовов, которое растёт быстрее, чем данные**, — классический признак ошибки O(n²).

### Как читать таблицу профиля

Чаще всего вы будете печатать классическую таблицу, отсортированную по нужному столбцу. Нажмите **«Запустить»**, чтобы профилировать увеличенную версию той же программы:

<TryIt language="python" code={`import cProfile

    return PRICES[item]

# попробуйте также sort_stats("tottime")
`}
/>

Вы увидите примерно такое (ваши цифры будут другими):

```text
   ncalls  tottime  percall  cumtime  percall filename:lineno(function)
        1    0.002    0.002    0.023    0.023 <lesson>:12(report)
     6000    0.004    0.000    0.021    0.000 <lesson>:9(order_total)
     6000    0.007    0.000    0.018    0.000 {built-in method builtins.sum}
    20000    0.008    0.000    0.011    0.000 <lesson>:10(<genexpr>)
    14000    0.003    0.000    0.003    0.000 <lesson>:6(price_of)
```

Столбцы:

- **`ncalls`** — сколько раз функцию вызвали. `51/1` означает 51 вызов всего, из них 1 нерекурсивный.
- **`tottime`** — время, проведённое **внутри самой функции**, без учёта функций, которые она вызвала. Высокий `tottime` значит «медленный код прямо здесь».
- **`cumtime`** — **накопленное (cumulative)** время, включая всё, что функция вызвала. У `report` самый большой `cumtime`, потому что всё происходит внутри неё.
- **`percall`** — два столбца `percall` равны `tottime / ncalls` и `cumtime / ncalls`.

Как читать: отсортируйте по **`cumtime`**, чтобы увидеть, какая часть программы медленная (идите по цепочке сверху вниз), а затем по **`tottime`**, чтобы найти функцию, где на самом деле выполняется работа.

Настоящие программы профилируют целиком из терминала, и многим нравится смотреть на те же данные визуально:

```bash
python -m cProfile -s cumtime app.py      # печать с сортировкой по cumtime
python -m cProfile -o app.prof app.py     # сохранить результаты
pip install snakeviz && snakeviz app.prof # изучить их в браузере
```

<Callout type="warning" title="Профилировщик меняет то, что измеряет">

`cProfile` добавляет небольшие накладные расходы к **каждому** вызову, поэтому код с миллионами крошечных вызовов под профилировщиком выглядит медленнее, чем есть на самом деле. Используйте его, чтобы найти, **куда** уходит время, а затем подтвердите исправление с помощью `timeit` или обычного таймера без профилировщика. Для работающих продакшн-серверов используйте **сэмплирующий профилировщик (sampling profiler)**, например `py-spy` (`py-spy top --pid 12345`): он заглядывает в программу сто раз в секунду и почти не замедляет её.

</Callout>

## tracemalloc: куда уходит память?

Медленный код — одна проблема; сервер, память которого растёт, пока он не упадёт, — другая. **`tracemalloc`** записывает, какая строка выделила каждый блок памяти. Сделайте **снимок (snapshot)** до и после и сравните их:

<CodeExample output={`сильнее всего выросла строка 6
новые объекты: True
выросло больше чем на 1 МБ: True`}>

```python
import tracemalloc

history = []

def handle(request):
    history.append(request * 100)    # никогда не очищается!
    return len(request)

tracemalloc.start()
before = tracemalloc.take_snapshot()
for i in range(2_000):
    handle(f"req-{i}")
after = tracemalloc.take_snapshot()
tracemalloc.stop()

top = after.compare_to(before, "lineno")[0]
frame = top.traceback[0]
print("сильнее всего выросла строка", frame.lineno)
print("новые объекты:", top.count_diff >= 2_000)
print("выросло больше чем на 1 МБ:", top.size_diff > 1_000_000)
```

</CodeExample>

`compare_to()` возвращает различия, отсортированные по размеру, от самого большого, поэтому `[0]` указывает прямо на строку 6: `append` в список, который никто никогда не очищает. Это самая частая «утечка памяти» в Python: на самом деле никакой утечки нет, просто список, словарь или кеш, который всё растёт. Если напечатать сам `top`, вы увидите строку вроде `app.py:6: size=1503 KiB (+1503 KiB), count=2001 (+2001)`.

Чтобы быстро получить одно число, `tracemalloc.get_traced_memory()` возвращает `(current, peak)` в байтах — текущий и пиковый объём. В следующем уроке вы с его помощью сравните список с генератором.

## Порядок работы с профилированием

Если собрать всё вместе, вот как senior-разработчики подходят к жалобе «приложение тормозит»:

1. **Определите, что значит «медленно».** «Эндпоинт отчёта отвечает 4 с, а должен — быстрее 500 мс». Без цели вы никогда не поймёте, когда остановиться.
2. **Воспроизведите на реалистичных данных.** Десять тестовых строк скрывают любую ошибку O(n²).
3. **Профилируйте, отсортируйте по `cumtime`** и спуститесь до горячей точки. Проверьте `ncalls`: не вызывается ли что-то гораздо чаще, чем вы ожидали?
4. **Сначала исправьте алгоритм** (множество вместо списка, индекс-словарь вместо поиска, один запрос вместо запроса на каждую строку). Именно там выигрыш в 10–1000 раз. Микрооптимизации дают 10–30%.
5. **Измерьте снова** и сохраните бенчмарк, лучше в виде теста, чтобы замедление не прокралось обратно.

Импорт регистраций слишком медленно работает на больших файлах. Докажите профилировщиком, почему, а затем исправьте.

Результаты должны остаться прежними: каждый повторяющийся (нормализованный) адрес один раз, в порядке нахождения повторов.

Когда всё заработает, внизу напечатается `['mei@panda.dev', 'bo@panda.dev']` и `{'normalise': 5, 'find_duplicates': 1}` (порядок в словаре может отличаться).

<Hint>

Для `call_counts`: `profiler = cProfile.Profile()`, `profiler.runcall(func, *args)`, а затем `pstats.Stats(profiler).get_stats_profile().func_profiles` — это словарь «имя → профиль». Соберите `{name: int(fn.ncalls) for name, fn in ... .items() if fn.file_name != "~"}`.

Для `find_duplicates`: пройдите по списку один раз. Нормализуйте каждый адрес, затем проверьте **множество** `seen`. Если адрес там уже есть и о нём ещё не сообщали, добавьте его в `dupes` (заведите второе множество, `reported`, чтобы каждый адрес добавлялся только один раз). Затем добавьте адрес в `seen`.

```python
import cProfile
import pstats

def call_counts(func, *args):
    """Запускает func(*args) под cProfile. Возвращает словарь
    {имя функции: ncalls} только для ваших функций
    (встроенные пропускаем: их file_name равен "~")."""
    profiler = cProfile.Profile()
    profiler.runcall(func, *args)
    profile = pstats.Stats(profiler).get_stats_profile()
    return {
        name: int(fn.ncalls)
        for name, fn in profile.func_profiles.items()
        if fn.file_name != "~"
    }

def normalise(email):
    return email.strip().lower()

def find_duplicates(emails):
    """Каждый email, который встречается больше одного раза
    (после нормализации), в порядке нахождения повторов."""
    seen = set()
    reported = set()
    dupes = []
    for email in emails:
        email = normalise(email)
        if email in seen and email not in reported:
            dupes.append(email)
            reported.add(email)
        seen.add(email)
    return dupes

emails = ["mei@panda.dev", "Bo@panda.dev", " MEI@panda.dev",
          "kai@panda.dev", "bo@panda.dev "]
print(find_duplicates(emails))
print(call_counts(find_duplicates, emails))
```

- **`cProfile`** + **`pstats`** показывают для каждой функции **`ncalls`**, **`tottime`** (её собственный код) и **`cumtime`** (включая вызванные функции). Сортируйте по `cumtime`, чтобы найти медленную область, и по `tottime`, чтобы найти конкретную функцию.
