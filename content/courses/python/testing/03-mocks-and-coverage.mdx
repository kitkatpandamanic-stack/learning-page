Real code talks to the outside world. It sends emails, calls web APIs, reads the clock and rolls dice. You don't want your tests to email real customers, fail whenever the Wi-Fi drops, or pass only before lunchtime. The answer is to swap those parts for stand-ins while testing. In this lesson you'll learn how, plus two habits of professional teams: measuring **coverage** and working **test-first**. 🎭

## Test doubles

A **test double** is anything that stands in for the real thing during a test, like a stunt double in a film. You'll hear a few names:

- A **stub** returns canned answers: "the exchange rate is always 1.25".
- A **fake** is a simple working version, like an in-memory list instead of a real database.
- A **mock** also **records how it was called**, so the test can check: "was the email sent, to whom, with what text?"

The simplest way to use a double is to design your code so you can **pass it in**. This is called **dependency injection**: instead of the function reaching out for the real email sender, the caller hands one over:

<CodeExample output={`..                                                   [100%]
2 passed in 0.01s`}>

```python
import pytest

def welcome(user, send_email):
    if not user["email"]:
        return False
    send_email(user["email"], f"Welcome, {user['name']}!")
    return True

def test_sends_a_welcome_email():
    sent = []
    fake_send = lambda to, text: sent.append((to, text))
    user = {"name": "Mei", "email": "mei@example.com"}
    assert welcome(user, fake_send) is True
    assert sent == [("mei@example.com", "Welcome, Mei!")]

def test_no_email_address_means_no_email():
    sent = []
    fake_send = lambda to, text: sent.append((to, text))
    assert welcome({"name": "Sam", "email": ""}, fake_send) is False
    assert sent == []

pytest.main([__file__])
```

</CodeExample>

In the real app you'd call `welcome(user, smtp_send)`. In tests, a tiny fake records what would have been sent. No real emails, no network, and the test runs in a millisecond.

## Mock: a double that records everything

Writing fakes by hand gets tedious. Python's built-in **`unittest.mock.Mock`** creates one for you. You can call a `Mock` with any arguments, and it remembers every call:

<CodeExample output={`True
1
call('mei@example.com', 'Hi!')
expected call not found.
Expected: mock('sam@example.com', 'Hi!')
  Actual: mock('mei@example.com', 'Hi!')
1.25
[call('EUR')]`}>

```python
from unittest.mock import Mock

send = Mock()
send("mei@example.com", "Hi!")
print(send.called)
print(send.call_count)
print(send.call_args)

send.assert_called_once_with("mei@example.com", "Hi!")
try:
    send.assert_called_once_with("sam@example.com", "Hi!")
except AssertionError as error:
    print(error)

rates = Mock()
rates.get_rate.return_value = 1.25
print(rates.get_rate("EUR"))
print(rates.get_rate.call_args_list)
```

</CodeExample>

- `called`, `call_count`, `call_args` and `call_args_list` tell you how the mock was used.
- `assert_called_once_with(...)` checks it was called exactly once, with exactly those arguments. There are also `assert_called_with` (the last call), `assert_any_call` and `assert_not_called()`.
- Any attribute of a mock is another mock, so `rates.get_rate` just works. Set **`return_value`** to choose what it returns.

That last point has a catch: a typo like `send.asert_called_once()` silently "works" too. Create mocks with `Mock(spec=RealClass)` to make them reject attributes the real class doesn't have.

## side_effect: errors and sequences

**`side_effect`** makes a mock do more than return one value. Give it an exception and the mock raises it; give it a list and each call returns (or raises) the next item. That's perfect for testing how code handles a flaky network:

<CodeExample output={`..                                                   [100%]
2 passed in 0.01s`}>

```python
import pytest
from unittest.mock import Mock

def fetch_with_retry(fetch, attempts=3):
    for attempt in range(attempts):
        try:
            return fetch()
        except ConnectionError:
            if attempt == attempts - 1:
                raise

def test_retries_until_it_works():
    fetch = Mock(side_effect=[
        ConnectionError("down"),
        ConnectionError("down"),
        {"temp": 21},
    ])
    assert fetch_with_retry(fetch) == {"temp": 21}
    assert fetch.call_count == 3

def test_gives_up_after_three_attempts():
    fetch = Mock(side_effect=ConnectionError("down"))
    with pytest.raises(ConnectionError):
        fetch_with_retry(fetch)
    assert fetch.call_count == 3

pytest.main([__file__])
```

</CodeExample>

Making a real server fail twice and then succeed would be almost impossible. With a mock it's one line.

## patch: replace something for a moment

Dependency injection is the cleanest option, but sometimes code calls something directly, like `random.randint`. **`unittest.mock.patch`** replaces a name **temporarily**, and puts the original back when the `with` block ends:

<CodeExample output={`.                                                    [100%]
1 passed in 0.01s`}>

```python
import random
import pytest
from unittest.mock import patch

def roll_for_treasure():
    roll = random.randint(1, 6)
    if roll == 6:
        return "golden bamboo"
    return "nothing"

def test_rolling_a_six_finds_treasure():
    with patch("random.randint", return_value=6) as fake:
        assert roll_for_treasure() == "golden bamboo"
    fake.assert_called_once_with(1, 6)

pytest.main([__file__])
```

</CodeExample>

The string `"random.randint"` says **where** to replace: the `randint` attribute of the `random` module. Inside the `with` block it's a `Mock` with `return_value=6`. You can also use `@patch("random.randint")` as a decorator, and the mock arrives as an extra test argument.

<Callout type="warning" title="Patch where it's used, not where it's defined">

If `weather.py` says `from httpx import get` and then calls `get(...)`, the name `get` now lives **in `weather`**. Patching `"httpx.get"` changes the httpx module but not weather's own copy of the name, so you must patch `"weather.get"`. If instead it says `import httpx` and calls `httpx.get(...)`, patching `"httpx.get"` works. Rule of thumb: patch the name in the module that **looks it up**.

</Callout>

## pytest's monkeypatch fixture

pytest has its own built-in fixture for the same job, **`monkeypatch`**. It's often simpler, and it also handles environment variables. Everything it changes is undone automatically when the test ends:

<CodeExample output={`...                                                  [100%]
3 passed in 0.01s`}>

```python
import os
import random
import pytest

def currency():
    return os.environ.get("SHOP_CURRENCY", "GBP")

def lucky_number():
    return random.randint(1, 100)

def test_default_currency(monkeypatch):
    monkeypatch.delenv("SHOP_CURRENCY", raising=False)
    assert currency() == "GBP"

def test_currency_from_environment(monkeypatch):
    monkeypatch.setenv("SHOP_CURRENCY", "EUR")
    assert currency() == "EUR"

def test_lucky_number(monkeypatch):
    monkeypatch.setattr(random, "randint", lambda a, b: 42)
    assert lucky_number() == 42

pytest.main([__file__])
```

</CodeExample>

- `monkeypatch.setattr(module_or_object, "name", new_value)` replaces an attribute.
- `monkeypatch.setenv` and `monkeypatch.delenv` change environment variables, which is how real apps get settings like API keys.

Use whichever you prefer: `patch` when you want a `Mock` to inspect afterwards, `monkeypatch` for quick swaps and environment variables.

## Time and randomness: inject them

Code that calls `datetime.now()` or `random.choice()` deep inside gives a different answer each run, which makes it hard to test. Patching works, but the professional fix is simpler: **make the time or the random generator a parameter**, with the real one as the default:

<CodeExample output={`...                                                  [100%]
3 passed in 0.01s`}>

```python
import random
from datetime import datetime
import pytest

def greeting(now=None):
    now = now or datetime.now()
    if now.hour < 12:
        return "Good morning"
    if now.hour < 18:
        return "Good afternoon"
    return "Good evening"

def pick_winner(names, rng=random):
    return rng.choice(sorted(names))

def test_morning():
    assert greeting(datetime(2026, 5, 1, 9, 30)) == "Good morning"

def test_six_pm_is_evening():
    assert greeting(datetime(2026, 5, 1, 18, 0)) == "Good evening"

def test_pick_winner_is_repeatable_with_a_seed():
    names = ["Mei", "Sam", "Ali"]
    first = pick_winner(names, random.Random(7))
    again = pick_winner(names, random.Random(7))
    assert first == again
    assert first in names

pytest.main([__file__])
```

</CodeExample>

In the app you call `greeting()` and `pick_winner(names)` as normal. Tests pass in a fixed time, or a `random.Random(seed)` generator that always produces the same sequence. No patching needed, and the code is more flexible too.

## Coverage: what did your tests miss?

**Code coverage** measures which lines of your code ran during the tests. Lines that never ran are definitely not tested. The usual tool is the `pytest-cov` plugin (not available in the browser, so try it on your computer):

```bash
pip install pytest-cov
pytest --cov=shop --cov-report=term-missing
```

After the normal test results you get a table like this:

```text
Name              Stmts   Miss  Cover   Missing
-----------------------------------------------
shop/__init__.py      0      0   100%
shop/pricing.py      24      3    88%   31-33
-----------------------------------------------
TOTAL                24      3    88%
```

`Missing` lists the line numbers no test ran, here lines 31 to 33 of `pricing.py`. Maybe that's an error branch you forgot to test. Add `--cov-branch` to also check that both sides of every `if` ran. Teams often add `--cov-fail-under=80` in their CI (the server that runs the tests on every push), so the build fails if coverage drops.

<Callout type="note" title="100% coverage is not 100% correct">

Coverage tells you what you **didn't** test. It can't tell you whether your tests check the **right** things: a test that calls a function without any `assert` still "covers" it. Use coverage to find gaps, not as a score to max out. Many teams aim for around 80–90% and focus on the important logic.

</Callout>

## The TDD loop: red, green, refactor

So far you've written code first and tests second. **Test-driven development (TDD)** flips that around, in a short loop:

1. **Red**: write a small test for behaviour that doesn't exist yet. Run it and watch it **fail**.
2. **Green**: write the simplest code that makes it pass.
3. **Refactor**: tidy the code (and tests) while all tests stay green.

Say you need `slugify`, which turns a post title into a URL part. Start with a test, before the function exists:

```python
def test_spaces_become_dashes():
    assert slugify("Hello World") == "hello-world"
# Red: NameError: name 'slugify' is not defined
```

Then the simplest code that passes:

```python
def slugify(title):
    return title.lower().replace(" ", "-")
# Green: 1 passed
```

Next behaviour, next test: punctuation should disappear. It fails (red), you improve the code (green), and then you tidy up (refactor). A few loops later you have:

<CodeExample output={`...                                                  [100%]
3 passed in 0.01s`}>

```python
import re
import pytest

def slugify(title):
    words = re.findall(r"[a-z0-9]+", title.lower())
    return "-".join(words)

def test_spaces_become_dashes():
    assert slugify("Hello World") == "hello-world"

def test_punctuation_disappears():
    assert slugify("Hi, Panda!") == "hi-panda"

def test_extra_spaces_do_not_double_dashes():
    assert slugify("  Big   news ") == "big-news"

pytest.main([__file__])
```

</CodeExample>

The rewrite to `re.findall` in the refactor step was safe because the earlier tests kept guarding the old behaviour. TDD keeps steps small, makes sure every test has been seen failing, and pushes you towards code that's easy to test. Not every team does strict TDD, but almost every good developer uses the loop when fixing a bug: first a test that reproduces it (red), then the fix (green).

<Callout type="tip" title="Don't mock too much">

Mock the **edges** of your program: email, network, clock, randomness, payment providers. Don't mock your own small functions and classes; test them for real. A test full of mocks only checks that your code calls things in a certain order, and it breaks every time you refactor.

</Callout>

import pytest
from datetime import date
from unittest.mock import Mock


def send_reminders(members, today, send_email):
    """Email members whose membership ends in 0 to 7 days.
    Return how many emails were sent."""
    sent = 0
    for member in members:
        days_left = (member["ends"] - today).days
        if 0 <= days_left <= 7:
            text = f"Your membership ends on {member['ends']}"
            send_email(member["email"], text)
            sent += 1
    return sent


def test_reminds_a_member_who_is_due():
    send = Mock()
    members = [{"email": "mei@example.com", "ends": date(2026, 3, 5)}]
    count = send_reminders(members, date(2026, 3, 1), send)
    assert count == 1
    send.assert_called_once_with(

    )

def test_no_email_when_nobody_is_due():
    send = Mock()
    members = [{"email": "sam@example.com", "ends": date(2027, 1, 1)}]
    assert send_reminders(members, date(2026, 3, 1), send) == 0
    send.assert_not_called()

## Recap

- A **test double** (stub, fake or mock) stands in for email, APIs, the clock or randomness during tests.
- **Dependency injection** (passing collaborators in as parameters) is the simplest way to use doubles.
- `Mock()` records calls: check them with `assert_called_once_with`, `call_args` and friends; set `return_value` to choose results.
- `side_effect` makes a mock raise an exception or return a sequence of values.
- `patch("module.name")` and pytest's `monkeypatch` replace things temporarily; **patch where the name is looked up**.
- Make time and randomness parameters (`now=None`, `rng=random`) so tests can pass in fixed values.
- **Coverage** (`pytest --cov`) shows untested lines; it finds gaps but doesn't prove correctness.
- **TDD**: red (failing test), green (simplest code), refactor (tidy with tests passing).
