Когда тестов становится больше нескольких штук, начинают мешать две вещи. Каждый тест в начале создаёт одни и те же объекты, а один и тот же тест вы копируете пять раз с разными числами. У pytest есть инструмент для каждой из проблем: **фикстуры (fixtures)** для общей подготовки и **параметризация (parametrize)** для множества входных данных. Во многом именно из-за этих двух возможностей pytest стал любимым инструментом тестирования в Python. 🧰

## Проблема: скопированная подготовка

Вот тесты для музыкального плейлиста. Посмотрите, как начинается каждый из них:

```python
def test_total_length():
    playlist = Playlist("В дорогу")
    playlist.add("Hey Jude", 431)
    playlist.add("Yellow", 266)
    assert playlist.total_seconds() == 697

def test_remove_song():
    playlist = Playlist("В дорогу")
    playlist.add("Hey Jude", 431)
    playlist.add("Yellow", 266)
    playlist.remove("Yellow")
    assert playlist.total_seconds() == 431
```

Шаг **подготовки** (arrange) скопирован. Если у `Playlist` появится новый обязательный аргумент, придётся исправлять каждый тест. А суть каждого теста теряется под подготовкой.

## Фикстуры: подготовка, которую запрашивают по имени

**Фикстура** — это функция с декоратором `@pytest.fixture`, которая что-то готовит для тестов. Тест запрашивает её, объявив **параметр с таким же именем**, и pytest передаёт в него то, что вернула фикстура:

<CodeExample output={`...                                                  [100%]
3 passed in 0.01s`}>

```python
import pytest

class Playlist:
    def __init__(self, name):
        self.name = name
        self.songs = {}

    def add(self, title, seconds):
        self.songs[title] = seconds

    def remove(self, title):
        del self.songs[title]

    def total_seconds(self):
        return sum(self.songs.values())

@pytest.fixture
def road_trip():
    playlist = Playlist("В дорогу")
    playlist.add("Hey Jude", 431)
    playlist.add("Yellow", 266)
    return playlist

def test_total_length(road_trip):
    assert road_trip.total_seconds() == 697

def test_remove_song(road_trip):
    road_trip.remove("Yellow")
    assert road_trip.total_seconds() == 431

def test_add_song(road_trip):
    road_trip.add("Wonderwall", 258)
    assert len(road_trip.songs) == 3

pytest.main([__file__])
```

</CodeExample>

Вы никогда не вызываете `road_trip()` сами. pytest видит имя параметра, находит фикстуру с этим именем и вызывает её **для каждого теста**. Поэтому то, что `test_remove_song` удаляет песню, никак не влияет на `test_add_song`: каждый тест получает совершенно новый плейлист. Такая **изоляция (isolation)** очень важна. Тесты, которые делят изменяемые данные, проходят или падают в зависимости от порядка запуска, и отлаживать это — настоящий кошмар.

## Подготовка и уборка с yield

Иногда после теста нужно **убрать за собой**: закрыть соединение с базой данных, удалить файл, остановить сервер. Напишите фикстуру с `yield` вместо `return`. Код до `yield` — это подготовка, значение после `yield` уходит в тест, а код после `yield` — это **уборка (teardown)**. Она выполняется, когда тест закончился, даже если он упал:

<CodeExample output={`открываем базу данных
тест выполняется
.закрываем базу данных

1 passed in 0.01s`}>

```python
import pytest

class FakeDatabase:
    def __init__(self):
        self.rows = []
        print("открываем базу данных")

    def close(self):
        print("закрываем базу данных")

@pytest.fixture
def db():
    database = FakeDatabase()   # подготовка
    yield database              # здесь выполняется тест
    database.close()            # уборка

def test_starts_empty(db):
    print("тест выполняется")
    assert db.rows == []

pytest.main([__file__, "-s"])
```

</CodeExample>

Обычно pytest скрывает всё, что печатают тесты (и показывает это только для упавших). Опция `-s` отключает это, и вы видите порядок: подготовка, тест, затем уборка. Точка перед `закрываем базу данных` — это pytest отмечает тест как пройденный, прямо перед уборкой.

Если это напоминает вам `@contextlib.contextmanager` из [урока о генераторах и менеджерах контекста](/learn/python/generators-and-context-managers), так и должно быть: это тот же шаблон «подготовка, yield, уборка».

## Область действия фикстуры

По умолчанию фикстура выполняется один раз **на каждый тест** (её **область действия (scope)** — `"function"`). Это самый безопасный выбор. Если фикстура медленная, а тесты только читают из неё, можно разделить один результат между тестами, расширив область действия:

<CodeExample output={`загружаем данные (медленно!)
..
2 passed in 0.01s`}>

```python
import pytest

@pytest.fixture(scope="module")
def big_data():
    print("загружаем данные (медленно!)")
    return list(range(1_000))

def test_length(big_data):
    assert len(big_data) == 1000

def test_last(big_data):
    assert big_data[-1] == 999

pytest.main([__file__, "-s"])
```

</CodeExample>

Данные загрузились один раз для обоих тестов. Области действия бывают такие: `"function"` (по умолчанию), `"class"`, `"module"` (один раз на тестовый файл) и `"session"` (один раз на весь запуск тестов). В реальных проектах **движок (engine)** базы данных часто делают с областью `session`, а каждый тест поверх него всё равно получает собственную свежую **транзакцию** с областью `function`.

<Callout type="warning" title="Общие фикстуры нельзя менять">

При широкой области действия каждый тест получает **один и тот же** объект. Если один тест его изменит (добавит элемент в список, удалит строку), следующий тест увидит это изменение. Расширяйте область действия только для того, что тесты используют только для чтения.

</Callout>

## Общие фикстуры в conftest.py

Фикстуры, которые нужны нескольким тестовым файлам, кладут в специальный файл **`conftest.py`**. pytest загружает его автоматически, и любой тест в этой папке (и её подпапках) может использовать его фикстуры без всякого импорта:

```text
shop/
├── pricing.py
└── tests/
    ├── conftest.py        # здесь живут общие фикстуры
    ├── test_cart.py
    └── test_checkout.py
```

```python
# tests/conftest.py
import pytest
from shop.cart import Cart

@pytest.fixture
def cart():
    cart = Cart()
    cart.add("tea", 3.50, quantity=2)
    return cart
```

Теперь `def test_total(cart):` работает и в `test_cart.py`, и в `test_checkout.py`. Фикстуры тоже могут запрашивать **другие фикстуры** — точно так же, как тесты: `def checkout(cart):` получит фикстуру `cart`.

В pytest есть и **встроенные фикстуры**. С `tmp_path` вы познакомитесь ниже, а с `monkeypatch` — в следующем уроке.

## Один тест, много входных данных: parametrize

Нужно проверить функцию на множестве входных данных и ожидаемых результатов? Не копируйте тест. **`@pytest.mark.parametrize`** запускает одну тестовую функцию по разу для каждого набора значений:

<CodeExample output={`......                                               [100%]
6 passed in 0.01s`}>

```python
import pytest

def duration_text(seconds):
    minutes, secs = divmod(seconds, 60)
    return f"{minutes}:{secs:02}"

@pytest.mark.parametrize("seconds, expected", [
    (0, "0:00"),
    (5, "0:05"),
    (59, "0:59"),
    (60, "1:00"),
    (61, "1:01"),
    (431, "7:11"),
])
def test_duration_text(seconds, expected):
    assert duration_text(seconds) == expected

pytest.main([__file__])
```

</CodeExample>

- Первый аргумент перечисляет имена параметров одной строкой через запятую.
- Второй — список кортежей, по одному кортежу на каждый **случай (case)**.
- pytest запускает тест шесть раз и считает каждый случай отдельным тестом.

Когда случай падает, pytest называет его по значениям, например `FAILED lesson.py::test_duration_text[61-1:01]`, так что вы точно знаете, какие входные данные всё сломали. Новый случай теперь добавляется одной строкой, и покрыть все границы из прошлого урока становится легко.

## Временные файлы с tmp_path

Код, который читает и пишет файлы, неудобно тестировать: не хочется, чтобы тесты оставляли после себя файлы или перезаписывали настоящие данные. Встроенная фикстура **`tmp_path`** выдаёт каждому тесту собственную новую пустую папку в виде `pathlib.Path`:

<CodeExample output={`..                                                   [100%]
2 passed in 0.01s`}>

```python
import json
import pytest

def save_playlist(path, songs):
    path.write_text(json.dumps(songs))

def load_playlist(path):
    if not path.exists():
        return {}
    return json.loads(path.read_text())

def test_save_then_load(tmp_path):
    file = tmp_path / "playlist.json"
    save_playlist(file, {"Yellow": 266})
    assert load_playlist(file) == {"Yellow": 266}

def test_missing_file_gives_empty_playlist(tmp_path):
    assert load_playlist(tmp_path / "nope.json") == {}

pytest.main([__file__])
```

</CodeExample>

Обратите внимание на устройство кода: функции принимают **путь как параметр**, а не используют внутри фиксированное имя файла. Именно это небольшое решение делает их удобными для тестирования. Старые временные папки pytest удаляет сам.

## Skip и xfail

Иногда тест сейчас запускать не нужно. Для этого есть две **метки (marks)**:

- `@pytest.mark.skip(reason=...)` пропускает тест, а `@pytest.mark.skipif(condition, reason=...)` пропускает его, только если условие истинно (например, на Windows или на старой версии Python).
- `@pytest.mark.xfail(reason=...)` означает «мы знаем, что этот тест падает». Он запускается, но его падение не делает весь запуск красным. Это удобно, чтобы задокументировать известную ошибку, пока её кто-нибудь не исправит.

<CodeExample output={`.sx                                                  [100%]
1 passed, 1 skipped, 1 xfailed in 0.01s`}>

```python
import sys
import pytest

def shout(text):
    return text.upper() + "!"

def test_shout():
    assert shout("hi") == "HI!"

@pytest.mark.skipif(sys.version_info < (4, 0), reason="нужен Python 4")
def test_future_feature():
    assert shout("hi") == "HI!!!"

@pytest.mark.xfail(reason="ошибка: пустой текст должен оставаться пустым")
def test_empty_text():
    assert shout("") == ""

pytest.main([__file__])
```

</CodeExample>

`s` отмечает пропущенный тест (skipped), а `x` — ожидаемое падение (xfailed). Используйте обе метки умеренно: пропущенный тест ничего не проверяет, а старые `xfail` имеют свойство забываться.

<Callout type="tip" title="Как делают профессионалы">

Настоящие наборы тестов активно опираются на фикстуры: свежая база данных для каждого теста, вошедший в систему пользователь, тестовый клиент веб-приложения. Если тест начинается с подготовки длиннее нескольких строк, это знак, что подготовка просится в фикстуру.

</Callout>

## Итоги

- **Фикстура** (`@pytest.fixture`) готовит что-то для тестов; тест получает её, указав её имя как параметр.
- С областью действия **function** (по умолчанию) каждый тест получает свежую копию, и тесты остаются изолированными.
- Используйте `yield` в фикстуре для **уборки**: код после `yield` выполняется после теста, даже если тот упал.
- `scope="module"` или `"session"` делит один результат между тестами; делайте так только для медленных объектов, которые используются только для чтения.
- Общие фикстуры кладите в **`conftest.py`**; pytest загружает его автоматически.
- `@pytest.mark.parametrize("a, b", [(...), (...)])` запускает один тест для множества случаев, и каждый учитывается отдельно.
- `tmp_path` даёт каждому тесту собственную пустую папку; `skip`, `skipif` и `xfail` отмечают тесты, которые не нужно запускать или которые заведомо падают.
