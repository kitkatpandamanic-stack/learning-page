So far you've checked your code by running it and looking at what it prints. That works for ten lines. In a real project, every change you make could quietly break something you checked last week, and nobody re-checks everything by hand. **Automated tests** are small pieces of code that check your code for you, in a second, every time. In Python, the tool almost everyone uses for this is **pytest**. 🧪

## Why automate your checks?

You already know the core idea. The `assert` statement checks that something is true. If it is, nothing happens. If it isn't, Python raises an `AssertionError`:

<CodeExample output={`All checks passed!
Check failed: 15% off 40`}>

```python
def apply_discount(price, percent):
    return price - price * percent / 100

assert apply_discount(200, 10) == 180
assert apply_discount(50, 0) == 50
print("All checks passed!")

try:
    assert apply_discount(40, 15) == 35, "15% off 40"
except AssertionError as error:
    print("Check failed:", error)
```

</CodeExample>

The text after the comma is an optional message. This check failed because *we* expected the wrong number: 15% off 40 really is 34. Checks can be wrong too, so a failure always means "look closer", not "the code is broken".

Writing checks like this pays off fast:

- **Regressions get caught.** A **regression** is a bug in something that used to work. Tests notice it the moment it appears.
- **You can change code without fear.** Rename, tidy up, speed up: if the tests still pass, you didn't break anything.
- **Tests document behaviour.** `test_free_shipping_over_50` tells the next developer exactly what the code is meant to do.

## Your first pytest tests

A loose list of `assert`s stops at the first failure and gives you no summary. **pytest** fixes that. The rules are simple:

- A **test** is a function whose name starts with `test_`.
- Inside it, use plain `assert` statements.
- pytest finds every test, runs each one separately, and reports what passed and what failed.

<CodeExample output={`...                                                  [100%]
3 passed in 0.01s`}>

```python
import pytest

def apply_discount(price, percent):
    return price - price * percent / 100

def test_ten_percent_off():
    assert apply_discount(200, 10) == 180

def test_zero_percent_changes_nothing():
    assert apply_discount(50, 0) == 50

def test_half_price():
    assert apply_discount(30, 50) == 15

pytest.main([__file__])
```

</CodeExample>

Each dot is one passing test, and the last line sums it up. pytest also says how long the run took: your timing will be different, which is fine.

The last line, `pytest.main([__file__])`, asks pytest to run the tests in **this** code. That's how we run tests here in the browser. In a real project, the tests live in their own files whose names start with `test_`, usually in a `tests` folder:

```text
shop/
├── pricing.py          # apply_discount lives here
└── tests/
    └── test_pricing.py # from pricing import apply_discount
```

Then you install pytest once and run it from the project folder. It finds the tests on its own:

```bash
pip install pytest
pytest -q
```

The `-q` (quiet) option gives exactly the short report you see on this page. Without it, pytest also prints a header and the name of every test file.

## Reading a failure report

Passing tests are boring (in a good way). The interesting part is what pytest tells you when one **fails**. Here's a word counter with a bug in it:

<CodeExample output={`.F                                                   [100%]
========================= FAILURES =========================
____________________ test_double_space _____________________

    def test_double_space():
>       assert count_words("pandas  eat") == 2
E       AssertionError: assert 3 == 2
E        +  where 3 = count_words('pandas  eat')

lesson.py:10: AssertionError
================= short test summary info ==================
FAILED lesson.py::test_double_space - AssertionError: ass...
1 failed, 1 passed in 0.01s`}>

```python
import pytest

def count_words(text):
    return len(text.split(" "))

def test_simple_sentence():
    assert count_words("pandas eat bamboo") == 3

def test_double_space():
    assert count_words("pandas  eat") == 2

pytest.main([__file__])
```

</CodeExample>

Read it from top to bottom:

1. `.F`: the first test passed, the second **F**ailed.
2. Under **FAILURES**, each failed test gets a section with its name and its code. The `>` arrow points at the line that failed.
3. The `E` lines are the **E**rror. pytest shows the actual values: `count_words` returned `3`, but the test expected `2`. You get this detail from a plain `assert`, because pytest rewrites asserts to remember both sides.
4. `lesson.py:10` is the file and line number. (Your lesson code is saved as `lesson.py`.)
5. The summary at the bottom lists all failures, then the totals.

Now the bug is obvious: `"pandas  eat".split(" ")` gives `['pandas', '', 'eat']`, three pieces. The fix is `text.split()` with no argument, which splits on any run of whitespace.

<Callout type="tip" title="Watch every test fail once">

A test that can never fail is worse than no test, because it makes you feel safe. When you write a test, break the code on purpose for a moment (or write the test before the code) and check that the test goes red. Then fix it and watch it go green.

</Callout>

## Arrange, act, assert

Good tests are short and follow the same three steps, often called **arrange, act, assert**:

1. **Arrange**: set up the objects and data you need.
2. **Act**: do the one thing you're testing.
3. **Assert**: check the result.

<CodeExample output={`..                                                   [100%]
2 passed in 0.01s`}>

```python
import pytest

class PiggyBank:
    def __init__(self):
        self.coins = []

    def add(self, amount):
        self.coins.append(amount)

    def total(self):
        return sum(self.coins)

def test_total_adds_up_all_coins():
    # Arrange
    bank = PiggyBank()
    bank.add(2)
    bank.add(5)
    # Act
    result = bank.total()
    # Assert
    assert result == 7

def test_new_bank_is_empty():
    bank = PiggyBank()
    assert bank.total() == 0

pytest.main([__file__])
```

</CodeExample>

Notice the names: `test_total_adds_up_all_coins` says what **behaviour** is being checked, not which method is called. When it fails six months from now, the name alone tells you what broke. Test one behaviour per test, so a failure points at one thing.

## Testing errors with pytest.raises

Sometimes the correct behaviour **is** an error. If someone adds a negative coin, `add()` should raise a `ValueError`. To test that, wrap the call in `with pytest.raises(...)`:

<CodeExample output={`...                                                  [100%]
3 passed in 0.01s`}>

```python
import pytest

class PiggyBank:
    def __init__(self):
        self.coins = []

    def add(self, amount):
        if amount <= 0:
            raise ValueError("amount must be positive")
        self.coins.append(amount)

def test_rejects_zero():
    bank = PiggyBank()
    with pytest.raises(ValueError):
        bank.add(0)

def test_explains_the_problem():
    with pytest.raises(ValueError, match="positive"):
        PiggyBank().add(-5)

def test_nothing_is_saved_after_an_error():
    bank = PiggyBank()
    with pytest.raises(ValueError):
        bank.add(-1)
    assert bank.coins == []

pytest.main([__file__])
```

</CodeExample>

- The test **passes** only if the code inside the `with` block raises that exception (or a subclass of it).
- If nothing is raised, the test fails with `Failed: DID NOT RAISE <class 'ValueError'>`.
- `match="positive"` also checks that the error message contains that text. (It's a regular expression, but plain words work as you'd expect.)

## Comparing decimals with pytest.approx

Computers store decimals approximately, so `0.1 + 0.2 == 0.3` is `False`! For float results, compare with **`pytest.approx`**, which allows a tiny difference:

<CodeExample output={`False
.                                                    [100%]
1 passed in 0.01s`}>

```python
import pytest

def test_split_the_bill():
    share = 1.0 / 3
    assert share * 3 == pytest.approx(1.0)
    assert 0.1 + 0.2 == pytest.approx(0.3)

if __name__ == "__main__":
    print(0.1 + 0.2 == 0.3)
    pytest.main([__file__])
```

</CodeExample>

This example also uses the `if __name__ == "__main__":` idiom from the modules lesson. When pytest imports your code to look for tests, that block is skipped, so the `print` runs only once. Keep code that does things (like printing) inside it, and keep the top level for definitions.

## What should you test?

You can't test every possible input, so choose wisely. A good set of tests covers:

- **The normal case** (the "happy path"): typical input, typical result.
- **Edge cases**: empty strings and lists, zero, one item, negative numbers, very large numbers, odd text like extra spaces or capitals.
- **Boundaries**: if the rules change at 18, test 17 **and** 18. Off-by-one mistakes (`>` instead of `>=`) hide exactly there.
- **Errors**: bad input should fail in the way you promised.

Here a cinema charges children (5 to 17) £6, adults £10 and seniors (65 and over) £7. Testing the boundaries finds a bug the happy path would miss:

<CodeExample output={`....F                                                [100%]
========================= FAILURES =========================
____________ test_sixty_five_gets_senior_price _____________

    def test_sixty_five_gets_senior_price():
>       assert ticket_price(65) == 7
E       assert 10 == 7
E        +  where 10 = ticket_price(65)

lesson.py:25: AssertionError
================= short test summary info ==================
FAILED lesson.py::test_sixty_five_gets_senior_price - ass...
1 failed, 4 passed in 0.01s`}>

```python
import pytest

def ticket_price(age):
    if age < 5:
        return 0
    if age < 18:
        return 6
    if age > 65:
        return 7
    return 10

def test_toddlers_are_free():
    assert ticket_price(4) == 0

def test_five_year_olds_pay_child_price():
    assert ticket_price(5) == 6

def test_seventeen_is_still_a_child():
    assert ticket_price(17) == 6

def test_eighteen_pays_adult_price():
    assert ticket_price(18) == 10

def test_sixty_five_gets_senior_price():
    assert ticket_price(65) == 7

pytest.main([__file__])
```

</CodeExample>

The code says `age > 65`, so a 65-year-old pays the adult price. A test with age `70` would have passed and hidden the bug. Changing it to `age >= 65` makes all five tests pass.

<Callout type="warning" title="Keep tests simple">

Tests should be so simple that they obviously have no bugs. Write the expected value out (`== 7`) instead of recalculating it with the same logic as the code; otherwise a mistake in that logic would be copied into the test, and both would agree on the wrong answer.

</Callout>

## Recap

- An **automated test** is code that checks your code; tests catch **regressions** and let you change code with confidence.
- pytest runs every function named `test_...`; inside, use plain `assert`. Run it with `pytest` in a terminal (here: `pytest.main([__file__])`).
- In a failure report, `>` marks the failing line and the `E` lines show the actual values.
- Structure tests as **arrange, act, assert**, one behaviour per test, with names that describe that behaviour.
- `with pytest.raises(ValueError, match="..."):` tests that code raises the right error.
- Compare floats with `pytest.approx`.
- Test the normal case, **edge cases**, **boundaries** and errors, and watch each test fail at least once.
