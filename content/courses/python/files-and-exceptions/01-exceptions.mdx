Things go wrong in real programs: a user types `"ten"` instead of `10`, a file is missing, a list is empty. When Python hits a problem it can't handle, it **raises an exception**. In this lesson you'll learn to read those errors and deal with them gracefully instead of letting your program crash. 🛟

## Reading a traceback

Here's a small program with a bug:

```python title="main.py"
def average(numbers):
    return sum(numbers) / len(numbers)

scores = []
print(average(scores))
```

Running it on your computer prints a **traceback**:

```text
Traceback (most recent call last):
  File "main.py", line 5, in <module>
    print(average(scores))
          ~~~~~~~^^^^^^^^
  File "main.py", line 2, in average
    return sum(numbers) / len(numbers)
           ~~~~~~~~~~~~~^~~~~~~~~~~~~~
ZeroDivisionError: division by zero
```

Read it **from the bottom up**:

1. The last line tells you **what** went wrong: the exception type (`ZeroDivisionError`) and a message.
2. The lines above tell you **where**: line 2, inside `average`, which was called from line 5.
3. The `^^^` markers point at the exact piece of code that failed.

The list was empty, so `len(numbers)` was `0`, and we divided by zero.

<Callout type="tip" title="Tracebacks are your friend">

Don't panic at a wall of red text. Jump to the **last line** first, then look for the first line that mentions **your** file. On PandaDev you'll see the last line plus the line number it happened on.

</Callout>

## Common exceptions

You'll meet these all the time:

| Exception | What it means | Example |
| --- | --- | --- |
| `ValueError` | Right type, wrong value | `int("abc")` |
| `TypeError` | Wrong type for the operation | `"3" + 4` |
| `KeyError` | A dictionary key doesn't exist | `stock["pears"]` |
| `IndexError` | A list position doesn't exist | `[10, 20][5]` |
| `ZeroDivisionError` | Dividing by zero | `10 / 0` |
| `FileNotFoundError` | Opening a file that isn't there | `open("nope.txt")` |

Let's trigger the first five on purpose and print what each one says:

<CodeExample output={`ValueError: invalid literal for int() with base 10: 'abc'
TypeError: can only concatenate str (not "int") to str
KeyError: 'pears'
IndexError: list index out of range
ZeroDivisionError: division by zero`}>

```python
stock = {"apples": 3}

mistakes = [
    lambda: int("abc"),
    lambda: "3" + 4,
    lambda: stock["pears"],
    lambda: [10, 20][5],
    lambda: 10 / 0,
]

for mistake in mistakes:
    try:
        mistake()
    except Exception as e:
        print(f"{type(e).__name__}: {e}")
```

</CodeExample>

Don't worry about every detail yet. The next sections explain `try`, `except` and `as e` step by step.

## try and except

Put the risky code in a **`try`** block. If an exception happens, Python jumps straight to the matching **`except`** block instead of crashing:

<CodeExample output={`'42' doubled is 84
'twelve' is not a whole number
'7' doubled is 14`}>

```python
for text in ["42", "twelve", "7"]:
    try:
        number = int(text)
        print(f"'{text}' doubled is {number * 2}")
    except ValueError:
        print(f"'{text}' is not a whole number")
```

</CodeExample>

When `int("twelve")` fails, the rest of the `try` block is skipped, the `except` block runs, and then the loop carries on with the next item. The program never crashes.

## Catching specific exceptions with as e

Always name the exception you expect. You can have several `except` blocks, and `as e` gives you the exception object, so you can show its message:

<CodeExample output={`Missing item: 'pears'
Not a number: invalid literal for int() with base 10: 'lots'
Bananas: 6`}>

```python
stock = {"apples": "3", "bananas": "6", "kiwis": "lots"}

def show_count(fruit):
    try:
        count = int(stock[fruit])
        print(f"{fruit.title()}: {count}")
    except KeyError as e:
        print(f"Missing item: {e}")
    except ValueError as e:
        print(f"Not a number: {e}")

show_count("pears")
show_count("kiwis")
show_count("bananas")
```

</CodeExample>

You can also catch several types in one block with a tuple: `except (KeyError, ValueError):`.

<Callout type="warning" title="Don't catch everything">

A bare `except:` (or `except Exception:`) catches **every** error, including typos like a misspelt variable name. Your bugs get silently hidden. Catch only the exceptions you know how to handle, and let the rest crash loudly so you can fix them.

</Callout>

## else and finally

A `try` statement has two optional extra parts:

- **`else`** runs only if **no** exception happened. It keeps the `try` block small: only the risky line goes in `try`.
- **`finally`** runs **always**, error or not. It's perfect for clean-up, like closing something or printing "done".

<CodeExample output={`Result: 2.5
Finished dividing 10 by 4
Can't divide by zero!
Finished dividing 10 by 0
Both values must be numbers.
Finished dividing 10 by 2`}>

```python
def divide(a, b):
    try:
        result = a / b
    except ZeroDivisionError:
        print("Can't divide by zero!")
    except TypeError:
        print("Both values must be numbers.")
    else:
        print(f"Result: {result}")
    finally:
        print(f"Finished dividing {a} by {b}")

divide(10, 4)
divide(10, 0)
divide(10, "2")
```

</CodeExample>

## Raising your own exceptions

Your own functions can **`raise`** exceptions too. This is how a function says "I can't work with this value". Pick a fitting type and write a helpful message:

<CodeExample output={`30
Sorry: not enough money (balance is 50)
Sorry: amount must be positive`}>

```python
def withdraw(balance, amount):
    if amount <= 0:
        raise ValueError("amount must be positive")
    if amount > balance:
        raise ValueError(f"not enough money (balance is {balance})")
    return balance - amount

print(withdraw(50, 20))

for amount in [80, -5]:
    try:
        withdraw(50, amount)
    except ValueError as e:
        print(f"Sorry: {e}")
```

</CodeExample>

`raise` stops the function immediately, just like `return`, but it sends back an error instead of a value. Whoever **calls** the function decides how to handle it.

## Validating input

Combine a loop, `try` and `raise` to keep asking until you get a good answer. Our code can't use `input()` here, so a list stands in for what the user types:

<CodeExample output={`'ten' is not valid: please type a number
'-4' is not valid: must be between 1 and 10
Thanks! You picked 7`}>

```python
typed = ["ten", "-4", "7", "3"]

def parse_choice(text):
    try:
        number = int(text)
    except ValueError:
        raise ValueError("please type a number")
    if not 1 <= number <= 10:
        raise ValueError("must be between 1 and 10")
    return number

for text in typed:
    try:
        choice = parse_choice(text)
    except ValueError as e:
        print(f"'{text}' is not valid: {e}")
    else:
        print(f"Thanks! You picked {choice}")
        break
```

</CodeExample>

## EAFP vs LBYL

There are two styles of dealing with things that might fail:

- **LBYL**, "look before you leap": check first with `if`.
- **EAFP**, "easier to ask forgiveness than permission": just try it and handle the exception.

<CodeExample output={`No pears (checked first)
No pears (caught KeyError)`}>

```python
stock = {"apples": 3}

# LBYL: check first
if "pears" in stock:
    print(stock["pears"])
else:
    print("No pears (checked first)")

# EAFP: try it, handle the failure
try:
    print(stock["pears"])
except KeyError:
    print("No pears (caught KeyError)")
```

</CodeExample>

Both are fine. Python programmers often prefer **EAFP**, especially when checking first is hard, like "is this text a valid number?" or "does this file exist and can I open it?".

## Recap

- Read a traceback **bottom up**: the last line says what went wrong, the lines above say where.
- Common exceptions: `ValueError`, `TypeError`, `KeyError`, `IndexError`, `ZeroDivisionError`, `FileNotFoundError`.
- `try` / `except SomeError as e:` handles a problem; `else` runs on success; `finally` always runs.
- Catch **specific** exceptions, never everything.
- `raise ValueError("message")` signals a problem from your own functions.
- **EAFP** (try it) and **LBYL** (check first) are both valid; EAFP is very Pythonic.
