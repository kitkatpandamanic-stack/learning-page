Посмотрите на строку `def send(user, items, express):`. Что такое `user`? Имя? Идентификатор? Словарь? И что функция возвращает? Придётся читать всё тело функции (или гадать). **Аннотации типов (type hints)** отвечают на эти вопросы прямо в первой строке:

```python
def send(user: str, items: list[str], express: bool) -> float:
```

Теперь любой человек (и любой инструмент) видит, что `user` — это строка, `items` — список строк, а функция возвращает число. В реальных проектах почти весь новый код на Python пишут с аннотациями типов, а фреймворки вроде FastAPI на них построены. 🏷️

## Аннотируем функцию

Поставьте `: тип` после каждого параметра и `-> тип` перед двоеточием, чтобы указать **тип возвращаемого значения (return type)**. Значение по умолчанию пишется после аннотации:

<CodeExample output={`Привет, Мэй!!
5.25
{'name': <class 'str'>, 'times': <class 'int'>, 'return': <class 'str'>}`}>

```python
def greet(name: str, times: int = 1) -> str:
    return f"Привет, {name}" + "!" * times

def average(a: float, b: float) -> float:
    return (a + b) / 2

print(greet("Мэй", 2))
print(average(3, 7.5))
print(greet.__annotations__)
```

</CodeExample>

Аннотации хранятся в самой функции (в `__annotations__`), но работает функция точно так же, как раньше. Обратите внимание: `average(3, 7.5)` — это нормально, `int` принимается везде, где ожидается `float`.

Функция, которая ничего не возвращает, получает `-> None`:

```python
def log(message: str) -> None:
    print(f"[log] {message}")
```

Аннотировать можно и переменные (`count: int = 0`), но это редко нужно: инструменты сами понимают, что `count = 0` — это `int`. Важнее всего аннотации в **сигнатурах функций**.

## Python их не проверяет

Поначалу это удивляет всех: сам Python **игнорирует** аннотации типов при выполнении кода. Ничто не мешает передать «не тот» тип:

<CodeExample output={`9
хахаха`}>

```python
def triple(x: int) -> int:
    return x * 3

print(triple(3))
print(triple("ха"))   # str, а не int!
```

</CodeExample>

Никакой ошибки: `"ха" * 3` — совершенно корректный Python. Кто же тогда пользуется аннотациями? **Инструменты** — ещё до запуска кода:

- Ваш **редактор** (VS Code, PyCharm) использует их для автодополнения и подчёркивает ошибки красным прямо во время набора.
- **Проверщик типов (type checker)**, например **mypy** (или pyright), читает весь проект и сообщает об ошибках типов — как проверка орфографии, только для кода:

```bash
$ pip install mypy
$ mypy app.py
app.py:4: error: Argument 1 to "triple" has incompatible type "str"; expected "int"  [arg-type]
Found 1 error in 1 file (checked 1 source file)
```

<Callout type="warning" title="Аннотации — это обещания, а не охрана">

Аннотация типа описывает, что функция *ожидает*, но не защищает её. Если нужно отклонять плохие входные данные во время выполнения (например, то, что ввёл пользователь), их всё равно придётся проверять, выбрасывать ошибки или использовать библиотеку вроде pydantic, которая проверит всё за вас (подробнее ниже).

</Callout>

## Списки, словари и другие коллекции

Для коллекций в квадратных скобках указывают тип **элементов**:

| Аннотация | Значит |
| --- | --- |
| `list[int]` | список целых чисел, например `[3, 1, 2]` |
| `dict[str, float]` | ключи — строки, значения — дробные числа |
| `tuple[str, int]` | ровно два элемента: str, затем int |
| `tuple[int, ...]` | сколько угодно целых чисел |
| `set[str]` | множество строк |

<CodeExample output={`85.0
{'Мэй': 92.0, 'Сэм': 78.5}
('Мэй', 92.0)`}>

```python
def mean(scores: list[float]) -> float:
    return sum(scores) / len(scores)

def best_scores(results: dict[str, list[float]]) -> dict[str, float]:
    return {name: max(marks) for name, marks in results.items()}

def top_student(best: dict[str, float]) -> tuple[str, float]:
    name = max(best, key=best.get)
    return name, best[name]

print(mean([92, 78, 85]))
best = best_scores({"Мэй": [85.5, 92.0], "Сэм": [78.5, 64.0]})
print(best)
print(top_student(best))
```

</CodeExample>

Аннотации вкладываются друг в друга так же глубоко, как ваши данные: `dict[str, list[float]]` читается как «словарь из строк в списки дробных чисел».

<Callout type="note" title="Старый стиль: List, Dict, Optional">

В старом коде (до Python 3.9) вы встретите `from typing import List, Dict` и аннотации вроде `List[int]` и `Dict[str, float]`. Они означают то же самое. Сегодня используйте встроенные типы в нижнем регистре: `list[int]` и `dict[str, float]`.

</Callout>

## Может, ничего: X | None

Многие функции возвращают значение *или* `None` — например, поиск, который может ничего не найти. Это записывают через `|` («или»):

<CodeExample output={`92
None
Не найдено`}>

```python
def find_score(scores: dict[str, int], name: str) -> int | None:
    if name in scores:
        return scores[name]
    return None

scores = {"Мэй": 92, "Сэм": 78}
print(find_score(scores, "Мэй"))
print(find_score(scores, "Али"))

result = find_score(scores, "Али")
if result is None:
    print("Не найдено")
```

</CodeExample>

Аннотация `int | None` напоминает каждому вызывающему коду: *проверьте на `None`, прежде чем использовать результат*. Проверщик типов пожаловался бы, если бы вы написали `find_score(...) + 1` без такой проверки.

Вам встретятся и такие варианты записи — они означают то же самое:

```python
from typing import Optional, Union

def find_score(name: str) -> Optional[int]: ...   # = int | None
def parse(value: Union[int, str]) -> int: ...     # = int | str
```

Необязательные параметры часто сочетают обе идеи — `| None` и значение по умолчанию: `def connect(timeout: float | None = None) -> None:`.

## Псевдонимы типов: даём типу имя

Когда аннотация становится длинной или встречается повсюду, дайте ей имя — это **псевдоним типа (type alias)**. В Python 3.12+ для этого есть инструкция `type`; в старом коде аннотацию просто присваивают переменной:

<CodeExample output={`5.0
[(0, 0), (3, 4)]`}>

```python
import math

type Point = tuple[float, float]
type Route = list[Point]

def distance(a: Point, b: Point) -> float:
    return math.dist(a, b)

def route_start_end(route: Route) -> Route:
    return [route[0], route[-1]]

print(distance((0, 0), (3, 4)))
print(route_start_end([(0, 0), (1, 1), (3, 4)]))
```

</CodeExample>

```python
Point = tuple[float, float]   # старый способ, всё ещё очень распространён
```

## TypedDict и Literal

Ещё два инструмента из модуля `typing`, которые вы встретите в реальном коде:

- **`TypedDict`** описывает словарь с фиксированными ключами, у каждого из которых свой тип. Удобно для данных в формате JSON.
- **`Literal`** ограничивает значение несколькими точными вариантами.

<CodeExample output={`Вверх (2009)
{'title': 'Вверх', 'year': 2009}
dict`}>

```python
from typing import Literal, TypedDict

class Movie(TypedDict):
    title: str
    year: int

Size = Literal["small", "medium", "large"]

def label(movie: Movie) -> str:
    return f"{movie['title']} ({movie['year']})"

def order(size: Size) -> None: ...

up: Movie = {"title": "Вверх", "year": 2009}
print(label(up))
print(up)
print(type(up).__name__)   # во время выполнения это обычный dict
```

</CodeExample>

TypedDict во время выполнения остаётся обычным `dict`; класс лишь сообщает инструментам, какие ключи существуют. А с `Size` проверщик типов отметит `order("huge")` как ошибку.

## Почему инструменты любят аннотации типов

Аннотации — это обычные объекты Python, поэтому библиотеки могут читать их прямо во время работы программы и **делать за вас работу**. Один пример вы уже видели: `@dataclass` строит `__init__` по аннотациям. **pydantic** идёт дальше: он действительно проверяет и преобразует данные на их основе:

<CodeExample output={`name='Мэй' age=5
int
Ошибка: возраст должен быть целым числом`}>

```python
from pydantic import BaseModel, ValidationError

class User(BaseModel):
    name: str
    age: int

mei = User(name="Мэй", age="5")   # "5" преобразуется в число
print(mei)
print(type(mei.age).__name__)

try:
    User(name="Сэм", age="пять")
except ValidationError:
    print("Ошибка: возраст должен быть целым числом")
```

</CodeExample>

**FastAPI**, с которым вы поработаете позже в этом курсе, построен на той же идее. По аннотации `item_id: int` он понимает, что из URL нужно прочитать число, преобразовать его и вернуть понятную ошибку, если кто-то запросит `/items/abc`:

```python
from fastapi import FastAPI

app = FastAPI()

@app.get("/items/{item_id}")
def read_item(item_id: int, details: bool = False) -> dict:
    return {"item_id": item_id, "details": details}
```

<Callout type="tip" title="Как аннотации добавляют профессионалы">

Не нужно аннотировать всё сразу. Начните с **параметров функций и типов возвращаемых значений** — особенно у функций, которые вызывают другие люди. Используйте самую простую аннотацию, которая верна, запустите mypy (или дайте проверить редактору) и исправьте найденное. Аннотации у локальных переменных нужны редко.

</Callout>

def find_price(prices: dict[str, float], item: str) -> float | None:

## Итоги

- Аннотации типов подписывают параметры (`name: str`) и возвращаемые значения (`-> str`); если функция ничего не возвращает, пишите `-> None`.
- Для коллекций указывают, что внутри: `list[int]`, `dict[str, float]`, `tuple[str, int]`, `set[str]`.
- `X | None` (или `Optional[X]`) означает «X или ничего»; `int | str` — любой из двух типов.
- Длинным аннотациям давайте имя с помощью **псевдонима типа**: `type Point = tuple[float, float]`.
- `TypedDict` описывает словари с фиксированными ключами; `Literal["a", "b"]` допускает только точные значения.
- Python **не проверяет** аннотации во время выполнения. Редакторы и проверщики типов вроде **mypy** используют их, чтобы ловить баги заранее, а библиотеки вроде **pydantic**, **FastAPI** и `@dataclass` читают их, чтобы делать настоящую работу.
