Look at this line: `def send(user, items, express):`. What is `user`? A name? An id? A dictionary? What does the function give back? You'd have to read the whole body (or guess). **Type hints** answer those questions right in the first line:

```python
def send(user: str, items: list[str], express: bool) -> float:
```

Now anyone (and any tool) can see that `user` is a string, `items` is a list of strings, and the function returns a number. In real projects almost all new Python code is written with type hints, and frameworks like FastAPI are built on them. 🏷️

## Annotating a function

Put `: type` after each parameter and `-> type` before the colon for the **return type**. Defaults go after the hint:

<CodeExample output={`Hi Mei!!
5.25
{'name': <class 'str'>, 'times': <class 'int'>, 'return': <class 'str'>}`}>

```python
def greet(name: str, times: int = 1) -> str:
    return f"Hi {name}" + "!" * times

def average(a: float, b: float) -> float:
    return (a + b) / 2

print(greet("Mei", 2))
print(average(3, 7.5))
print(greet.__annotations__)
```

</CodeExample>

The hints are stored on the function (in `__annotations__`), but the function itself works exactly as before. Notice `average(3, 7.5)` is fine: an `int` is accepted wherever a `float` is expected.

A function that doesn't return anything gets `-> None`:

```python
def log(message: str) -> None:
    print(f"[log] {message}")
```

You can also annotate variables (`count: int = 0`), but you rarely need to: tools work out that `count = 0` is an `int` on their own. Hints matter most on **function signatures**.

## Python doesn't check them

This surprises everyone at first: Python itself **ignores** type hints when your code runs. Nothing stops you passing the "wrong" type:

<CodeExample output={`9
hahaha`}>

```python
def triple(x: int) -> int:
    return x * 3

print(triple(3))
print(triple("ha"))   # a str, not an int!
```

</CodeExample>

No error: `"ha" * 3` is perfectly valid Python. So who uses the hints? **Tools** do, before your code runs:

- Your **editor** (VS Code, PyCharm) uses them for autocomplete and underlines mistakes in red as you type.
- A **type checker** such as **mypy** (or pyright) reads your whole project and reports type errors, like a spell checker for code:

```bash
$ pip install mypy
$ mypy app.py
app.py:4: error: Argument 1 to "triple" has incompatible type "str"; expected "int"  [arg-type]
Found 1 error in 1 file (checked 1 source file)
```

<Callout type="warning" title="Hints are promises, not guards">

A type hint documents what a function *expects*; it doesn't protect it. If you need to reject bad input at runtime (say, data typed by a user), you still have to check it, raise errors, or use a library like pydantic that does the checking for you (more on that below).

</Callout>

## Lists, dicts and other collections

For collections, put the type of the **items** in square brackets:

| Hint | Means |
| --- | --- |
| `list[int]` | a list of ints, e.g. `[3, 1, 2]` |
| `dict[str, float]` | keys are strings, values are floats |
| `tuple[str, int]` | exactly two items: a str, then an int |
| `tuple[int, ...]` | any number of ints |
| `set[str]` | a set of strings |

<CodeExample output={`85.0
{'Mei': 92.0, 'Sam': 78.5}
('Mei', 92.0)`}>

```python
def mean(scores: list[float]) -> float:
    return sum(scores) / len(scores)

def best_scores(results: dict[str, list[float]]) -> dict[str, float]:
    return {name: max(marks) for name, marks in results.items()}

def top_student(best: dict[str, float]) -> tuple[str, float]:
    name = max(best, key=best.get)
    return name, best[name]

print(mean([92, 78, 85]))
best = best_scores({"Mei": [85.5, 92.0], "Sam": [78.5, 64.0]})
print(best)
print(top_student(best))
```

</CodeExample>

Hints nest as deep as your data: `dict[str, list[float]]` reads as "a dict from strings to lists of floats".

<Callout type="note" title="Old style: List, Dict, Optional">

In older code (before Python 3.9) you'll see `from typing import List, Dict` and hints like `List[int]` and `Dict[str, float]`. They mean the same thing. Today, use the built-in lowercase `list[int]` and `dict[str, float]`.

</Callout>

## Maybe nothing: X | None

Lots of functions return a value *or* `None`, like a search that might not find anything. Write that with `|` ("or"):

<CodeExample output={`92
None
Not found`}>

```python
def find_score(scores: dict[str, int], name: str) -> int | None:
    if name in scores:
        return scores[name]
    return None

scores = {"Mei": 92, "Sam": 78}
print(find_score(scores, "Mei"))
print(find_score(scores, "Ali"))

result = find_score(scores, "Ali")
if result is None:
    print("Not found")
```

</CodeExample>

The hint `int | None` is a reminder to every caller: *check for `None` before using the result*. A type checker would complain if you wrote `find_score(...) + 1` without checking first.

You'll also meet these spellings, which mean the same:

```python
from typing import Optional, Union

def find_score(name: str) -> Optional[int]: ...   # = int | None
def parse(value: Union[int, str]) -> int: ...     # = int | str
```

Optional parameters often combine both ideas, `| None` and a default: `def connect(timeout: float | None = None) -> None:`.

## Type aliases: naming a type

When a hint gets long or appears everywhere, give it a name. Python 3.12+ has a `type` statement for this; older code simply assigns the hint to a variable:

<CodeExample output={`5.0
[(0, 0), (3, 4)]`}>

```python
import math

type Point = tuple[float, float]
type Route = list[Point]

def distance(a: Point, b: Point) -> float:
    return math.dist(a, b)

def route_start_end(route: Route) -> Route:
    return [route[0], route[-1]]

print(distance((0, 0), (3, 4)))
print(route_start_end([(0, 0), (1, 1), (3, 4)]))
```

</CodeExample>

```python
Point = tuple[float, float]   # the older way, still very common
```

## TypedDict and Literal

Two more tools from the `typing` module you'll meet in real code:

- **`TypedDict`** describes a dictionary with fixed keys, each with its own type. Handy for JSON data.
- **`Literal`** limits a value to a few exact options.

<CodeExample output={`Up (2009)
{'title': 'Up', 'year': 2009}
dict`}>

```python
from typing import Literal, TypedDict

class Movie(TypedDict):
    title: str
    year: int

Size = Literal["small", "medium", "large"]

def label(movie: Movie) -> str:
    return f"{movie['title']} ({movie['year']})"

def order(size: Size) -> None: ...

up: Movie = {"title": "Up", "year": 2009}
print(label(up))
print(up)
print(type(up).__name__)   # still a plain dict at runtime
```

</CodeExample>

A TypedDict is still an ordinary `dict` when the code runs; the class only tells tools which keys exist. With `Size`, a type checker would flag `order("huge")` as an error.

## Why tools love type hints

Because hints are just Python objects, libraries can read them while your program runs and **do work for you**. You've already seen one: `@dataclass` uses the hints to build `__init__`. **pydantic** goes further and actually checks and converts data based on them:

<CodeExample output={`name='Mei' age=5
int
Error: age must be a whole number`}>

```python
from pydantic import BaseModel, ValidationError

class User(BaseModel):
    name: str
    age: int

mei = User(name="Mei", age="5")   # "5" is converted
print(mei)
print(type(mei.age).__name__)

try:
    User(name="Sam", age="five")
except ValidationError:
    print("Error: age must be a whole number")
```

</CodeExample>

**FastAPI**, which you'll use later in this course, is built on the same idea. From the hint `item_id: int` it knows to read a number from the URL, convert it, and send back a clear error if someone asks for `/items/abc`:

```python
from fastapi import FastAPI

app = FastAPI()

@app.get("/items/{item_id}")
def read_item(item_id: int, details: bool = False) -> dict:
    return {"item_id": item_id, "details": details}
```

<Callout type="tip" title="How pros add hints">

You don't need to annotate everything at once. Start with **function parameters and return types**, especially for functions other people call. Use the simplest hint that is true, run mypy (or let your editor check) and fix what it finds. Hints on local variables are rarely needed.

</Callout>

Write the hints out in full (no type aliases), using the lowercase built-in types.

<Hint>

The first line of the first function is `def find_price(prices: dict[str, float], item: str) -> float | None:`. Inside, `prices.get(item)` already returns `None` for a missing key. For the total, loop over the basket and add `prices[item]` only `if item in prices`, then `return round(total, 2)`. For counting, use `counts[item] = counts.get(item, 0) + 1`.

</Hint>

<Solution>

```python
def find_price(prices: dict[str, float], item: str) -> float | None:
    return prices.get(item)


def basket_total(prices: dict[str, float], basket: list[str]) -> float:
    total = 0.0
    for item in basket:
        if item in prices:
            total += prices[item]
    return round(total, 2)


def count_items(basket: list[str]) -> dict[str, int]:
    counts: dict[str, int] = {}
    for item in basket:
        counts[item] = counts.get(item, 0) + 1
    return counts


prices = {"bamboo": 2.5, "apple": 0.4, "tea": 3.0}

```

## Recap

- Type hints label parameters (`name: str`) and return values (`-> str`); use `-> None` when nothing is returned.
- Collections say what's inside: `list[int]`, `dict[str, float]`, `tuple[str, int]`, `set[str]`.
- `X | None` (or `Optional[X]`) means "an X or nothing"; `int | str` means either type.
- Name long hints with a **type alias**: `type Point = tuple[float, float]`.
- `TypedDict` describes dicts with fixed keys; `Literal["a", "b"]` allows only exact values.
- Python **doesn't enforce** hints at runtime. Editors and type checkers like **mypy** use them to catch bugs early, and libraries like **pydantic**, **FastAPI** and `@dataclass` read them to do real work.
