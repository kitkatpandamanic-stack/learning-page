Imagine a log file with ten million lines. If you read it all into a list first, your program needs memory for ten million strings before it can do anything. A **generator** hands you the lines **one at a time**, only when you ask for the next one, so it works with a file of any size.

In this lesson you'll learn two power tools that pros use daily: **generators** (`yield`) for lazy sequences, and **context managers** (`with`) for setting something up and always cleaning it up again. 🎋

## yield: a function that pauses

A normal function runs to its `return` and is done. A function containing **`yield`** is a **generator function**: calling it doesn't run the body, it gives you a **generator** object. Each time you ask for a value, the body runs until the next `yield`, hands over that value, and **pauses** right there:

<CodeExample output={`generator
3
2
Lift off!
[3, 2, 1]`}>

```python
def countdown(start):
    n = start
    while n > 0:
        yield n        # hand over n, then pause here
        n -= 1

gen = countdown(3)
print(type(gen).__name__)
print(next(gen))       # runs until the first yield
print(next(gen))       # carries on from where it paused

print("Lift off!")
print(list(countdown(3)))
```

</CodeExample>

You'll rarely call `next()` yourself. A `for` loop, `list()`, `sum()` and friends all ask for values one by one until the generator runs out (when its body ends, Python raises `StopIteration` behind the scenes and the loop stops).

## Lazy: values only when needed

Compare a function that builds a whole list with a generator. The `print` inside shows *when* each value is made:

<CodeExample output={`-- list --
making 1
making 2
making 3
using 1
using 2
using 3
-- generator --
making 1
using 1
making 2
using 2
making 3
using 3`}>

```python
def squares_list(n):
    result = []
    for i in range(1, n + 1):
        print(f"making {i}")
        result.append(i * i)
    return result

def squares_gen(n):
    for i in range(1, n + 1):
        print(f"making {i}")
        yield i * i

print("-- list --")
for sq in squares_list(3):
    print(f"using {int(sq ** 0.5)}")

print("-- generator --")
for sq in squares_gen(3):
    print(f"using {int(sq ** 0.5)}")
```

</CodeExample>

The list version makes everything up front; the generator makes each value **just in time**. That has two big benefits:

- **Memory**: only one value exists at a time, so a generator over a huge file or a million records uses almost no memory.
- **Infinite sequences**: a generator can go on forever, and you just stop asking when you have enough.

<CodeExample output={`[1, 1, 2, 3, 5, 8, 13, 21]
55`}>

```python
def fibonacci():
    a, b = 1, 1
    while True:          # never ends, and that's fine
        yield a
        a, b = b, a + b

numbers = []
for n in fibonacci():
    if n > 30:
        break
    numbers.append(n)
print(numbers)

for i, n in enumerate(fibonacci()):
    if i == 9:
        print(n)
        break
```

</CodeExample>

## Generator expressions

Just like list comprehensions, there's a short form. Use **round brackets** instead of square ones and you get a generator:

<CodeExample output={`[1, 4, 9, 16]
<class 'generator'>
333333833333500000
True`}>

```python
nums = [1, 2, 3, 4]
print([n * n for n in nums])        # list: built now
print(type(n * n for n in nums))    # generator: lazy

# Inside a function call you can drop the extra brackets
print(sum(n * n for n in range(1, 1_000_001)))
print(any(n > 3 for n in nums))
```

</CodeExample>

`sum(n * n for n in range(1, 1_000_001))` adds a million squares without ever building a list of a million numbers. `any()` even **stops early**: it quits at the first `True`.

<Callout type="warning" title="A generator can only be used once">

A generator remembers where it paused, so once it's finished it stays empty. Looping over it a second time gives nothing, with no error:

```python
squares = (n * n for n in [1, 2, 3])
print(sum(squares))   # 14
print(sum(squares))   # 0, already used up!
```

If you need the values more than once, turn them into a list (`list(...)`) or call the generator function again.

</Callout>

## Generator pipelines

Generators shine when you chain them: each step takes an iterable and yields cleaned-up values. Nothing is read or processed until the end of the chain asks for it, just like a factory conveyor belt. Here's a pipeline that reads numbers from file-like text, skipping blank lines and comments:

<CodeExample output={`[12, 7, 30]
49`}>

```python
import io

data = io.StringIO("12\n\n# delivery 2\n7\n30\n")

def clean(lines):
    for line in lines:
        line = line.strip()
        if line and not line.startswith("#"):
            yield line

def to_ints(lines):
    for line in lines:
        yield int(line)

print(list(to_ints(clean(data))))

data.seek(0)                         # rewind the "file"
print(sum(to_ints(clean(data))))
```

</CodeExample>

`io.StringIO` behaves like an open file, and a real file opened with `open()` works the same way: looping over it reads **one line at a time**. So this exact pipeline could process a file far bigger than your computer's memory.

## itertools: ready-made generator tools

The standard library's **`itertools`** module has fast building blocks for lazy sequences. A few you'll use often:

<CodeExample output={`[10, 11, 12]
[0, 2, 4, 6, 8]
['a', 'b', 'c', 'd']
[(1, 2, 3), (4, 5, 6), (7,)]
[1, 3, 6, 10]`}>

```python
import itertools

counter = itertools.count(10)       # 10, 11, 12, ... forever
print([next(counter) for _ in range(3)])

evens = (n for n in itertools.count() if n % 2 == 0)
print(list(itertools.islice(evens, 5)))     # the first 5

# chain: one after another, batched: groups of 3
print(list(itertools.chain(["a", "b"], ["c", "d"])))
print(list(itertools.batched(range(1, 8), 3)))
print(list(itertools.accumulate([1, 2, 3, 4])))   # running totals
```

</CodeExample>

**`islice`** is the key to infinite generators: it takes just the first few values (it's like slicing `[:5]`, but for anything lazy). `batched` (Python 3.12+) is great for sending data in chunks, for example 100 rows at a time to a database.

## with: always clean up

You already know `with open(...) as file:`. The point of `with` is a guarantee: whatever happens inside the block, **even an error**, the cleanup runs afterwards (here: the file is closed).

An object that works with `with` is a **context manager**. It has two special methods:

- **`__enter__`** runs at the start of the block. Whatever it returns goes into the `as` variable.
- **`__exit__`** runs at the end, **always**, and receives details of any error that happened.

<CodeExample output={`<pandas>
  Mei
  Bao
</pandas>
<numbers>
  Oops, the error is coming...
</numbers>
Caught: something broke`}>

```python
class Tag:
    def __init__(self, name):
        self.name = name

    def __enter__(self):
        print(f"<{self.name}>")
        return self

    def __exit__(self, exc_type, exc_value, traceback):
        print(f"</{self.name}>")
        return False   # don't hide errors

with Tag("pandas"):
    print("  Mei")
    print("  Bao")

try:
    with Tag("numbers"):
        print("  Oops, the error is coming...")
        raise ValueError("something broke")
except ValueError as error:
    print(f"Caught: {error}")
```

</CodeExample>

Look at the second block: the error happened, but `</numbers>` was still printed before the error reached the `except`. That's the guarantee. If `__exit__` returns `True`, the error is **swallowed**; returning `False` (or nothing) lets it continue, which is almost always what you want.

Real-world context managers do exactly this pattern: open and close files, connect and disconnect from databases, start and **commit or roll back** transactions, acquire and release locks. You'll meet `with Session(engine) as session:` in the databases module.

## @contextlib.contextmanager: the short way

Writing a class is a bit long. The **`@contextlib.contextmanager`** decorator turns a generator function into a context manager: code **before** `yield` is the setup, the yielded value goes into `as`, and code **after** `yield` is the cleanup. Put the `yield` inside `try`/`finally` so the cleanup runs even after an error:

<CodeExample output={`inside: {'theme': 'dark', 'debug': True}
after: {'theme': 'dark', 'debug': False}
after error: {'theme': 'dark', 'debug': False}`}>

```python
from contextlib import contextmanager

settings = {"theme": "dark", "debug": False}

@contextmanager
def debug_mode(config):
    old = config["debug"]
    config["debug"] = True        # setup
    try:
        yield config              # the with block runs here
    finally:
        config["debug"] = old     # cleanup, always

with debug_mode(settings) as config:
    print("inside:", config)
print("after:", settings)

try:
    with debug_mode(settings):
        raise RuntimeError("test failed")
except RuntimeError:
    print("after error:", settings)
```

</CodeExample>

This "change something temporarily and always put it back" pattern is extremely common, especially in tests. `contextlib` also has ready-made helpers, such as `suppress`, which ignores one kind of error:

<CodeExample output={`gone
done`}>

```python
import os
from contextlib import suppress

with open("temp.txt", "w") as file:
    file.write("bye")

os.remove("temp.txt")
print("gone")

with suppress(FileNotFoundError):
    os.remove("temp.txt")      # already deleted: ignored
print("done")
```

</CodeExample>

<Callout type="tip" title="Which one should I use?">

Use a **generator** when you produce a sequence of values that might be big, slow to make or endless; return a **list** when it's small and you need to use it several times. Use **`@contextmanager`** for most of your own context managers; write a class with `__enter__`/`__exit__` when the object also has other methods or state.

</Callout>

Write three small power tools:

1. **`running_total(numbers)`**: a generator that yields the total so far after each number. `[1, 2, 3, 4]` gives `1, 3, 6, 10`. It must be lazy, so it also works on an endless iterator like `itertools.count()`.
2. **`chunks(items, size)`**: a generator that yields **lists** of up to `size` items. `chunks([1, 2, 3, 4, 5], 2)` gives `[1, 2]`, `[3, 4]`, `[5]`.
3. **`temp_value(data, key, value)`**: a context manager (use `@contextmanager`) that sets `data[key] = value` for the duration of the `with` block. Afterwards, the old value is put back, or the key is removed if it wasn't there before. That must happen **even if the block raises an error** (the error should still reach the caller).

<Hint>

`running_total`: keep `total = 0`, loop over `numbers`, add each one and `yield total`. `chunks`: collect items into a `batch` list; when `len(batch) == size`, yield it and start a new list; after the loop, yield the last batch if it isn't empty. `temp_value`: remember `missing = key not in data` and `old = data.get(key)`, set the new value, then `try: yield` and in `finally:` either `del data[key]` or put `old` back.

</Hint>

<Solution>

```python
from contextlib import contextmanager

def running_total(numbers):
    total = 0
    for n in numbers:
        total += n
        yield total


def chunks(items, size):
    batch = []
    for item in items:
        batch.append(item)
        if len(batch) == size:
            yield batch
            batch = []
    if batch:
        yield batch


@contextmanager
def temp_value(data, key, value):
    missing = key not in data
    old = data.get(key)
    data[key] = value
    try:
        yield data
    finally:
        if missing:
            del data[key]
        else:
            data[key] = old


print(list(running_total([1, 2, 3, 4])))
print(list(chunks([1, 2, 3, 4, 5], 2)))
```

</Solution>

## Recap

- A function with **`yield`** is a generator function: it returns a generator that produces values **lazily**, pausing after each `yield`.
- Generators save memory, can be **endless**, and chain nicely into **pipelines**; a generator can only be used **once**.
- **Generator expressions** use round brackets: `sum(n * n for n in nums)`.
- `itertools` has lazy helpers: `count`, `islice`, `chain`, `batched`, `accumulate`.
- `with` guarantees cleanup, even after an error. A **context manager** has `__enter__` (setup, value for `as`) and `__exit__` (cleanup).
- `@contextlib.contextmanager` builds one from a generator: setup, then `try: yield` / `finally:` cleanup.
