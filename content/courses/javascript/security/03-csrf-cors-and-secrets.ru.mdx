Два прошлых урока были про ошибки в **вашем** коде. Этот — про всё, что его окружает: что браузеры автоматически делают от имени ваших пользователей, какие заголовки включают их встроенную защиту, от каких секретов зависит ваше приложение и тысячи npm-пакетов, которые вы не писали, но всё равно отправляете в продакшен. ## CSRF: запросы, которые пользователи не собирались отправлять

Браузеры прикрепляют cookie **автоматически** к каждому запросу на сайт, неважно, какая страница его начала. **Подделка межсайтовых запросов (cross-site request forgery, CSRF)** этим злоупотребляет. Mei вошла в свой банк, а потом открыла страницу на другом сайте, где есть вот это:

```html
<!-- на https://cute-panda-pics.example -->
<form action="https://bank.example/transfer" method="POST">
  <input type="hidden" name="to" value="attacker">
  <input type="hidden" name="amount" value="500">
</form>
<script>document.forms[0].submit();</script>
```

Её браузер отправляет форму в банк **вместе с её cookie сессии**, и банк видит совершенно корректный запрос от вошедшего пользователя. Атакующий так и не видит ответа (и ему это не нужно): деньги уже ушли. Обратите внимание, чем CSRF **не является**: атакующий не может прочитать cookie Mei или страницы банка. Он может только заставить её браузер **отправлять** запросы.

Защита, слоями:

- **Cookie с `SameSite`.** С `SameSite=Lax` (именно его вы ставили в [прошлом уроке](/learn/javascript/authentication-and-sessions), и это же значение по умолчанию в Chrome, если атрибута нет) cookie не отправляется с межсайтовыми `POST`, так что форма выше приходит без входа. `SameSite=Strict` не отправляет её даже при переходе по ссылке с другого сайта.
- **Никогда не меняйте данные на `GET`.** Cookie с `Lax` **отправляются**, когда пользователь переходит по ссылке или при навигации верхнего уровня, поэтому `GET /transfer?to=attacker` не должен ничего делать.
- **CSRF-токены** для всего важного. `SameSite` работает на уровне **сайта (site)**, а взломанный или подконтрольный пользователям поддомен вроде `https://evil.pandadev.example` считается тем же *сайтом*, что и `https://app.pandadev.example`. Токен закрывает эту брешь и заодно защищает старые браузеры.
- **Проверяйте `Origin` / `Sec-Fetch-Site`.** Современные браузеры отправляют `Sec-Fetch-Site: cross-site` на запросах с других сайтов и заголовок `Origin` на POST-запросах. Отклонять небезопасные методы, у которых `Origin` не ваш, — дешёвый дополнительный слой защиты.

### Шаблон синхронизирующего токена

Сервер хранит случайный **CSRF-токен** в сессии и отдаёт его своей собственной странице (в HTML или в JSON-ответе). Страница отправляет его обратно в заголовке с каждым запросом, меняющим состояние. Страница атакующего может заставить браузер **отправить** cookie, но политика одного источника (same-origin policy) не даёт ей **прочитать** ваши ответы, поэтому узнать токен она не сможет. Это **шаблон синхронизирующего токена (synchroniser token pattern)**:

<CodeExample output={`подделка: 403 { error: 'Bad CSRF token' }
настоящий: 200 { sent: 20 }`}>

```js
import express from "express";
import cookieParser from "cookie-parser";
import request from "supertest";

const sessions = new Map(); // sid -> { username, csrfToken }

function safeEqual(a, b) {
  if (typeof a !== "string" || a.length !== b.length) return false;
  let diff = 0;
  for (let i = 0; i < a.length; i++) {
    diff |= a.charCodeAt(i) ^ b.charCodeAt(i);
  }
  return diff === 0;
}

function requireCsrf(req, res, next) {
  if (["GET", "HEAD", "OPTIONS"].includes(req.method)) return next();
  const session = sessions.get(req.cookies.sid);
  const sent = req.get("X-CSRF-Token");
  if (!session || !safeEqual(sent, session.csrfToken)) {
    return res.status(403).json({ error: "Bad CSRF token" });
  }
  next();
}

const app = express();
app.use(express.json());
app.use(cookieParser());

app.post("/login", (req, res) => {
  const sid = crypto.randomUUID();
  const csrfToken = crypto.randomUUID();
  sessions.set(sid, { username: "mei", csrfToken });
  res.cookie("sid", sid, {
    httpOnly: true, secure: true, sameSite: "lax",
  });
  // Наша собственная страница читает его и возвращает в заголовке
  res.json({ csrfToken });
});

app.use(requireCsrf);
app.post("/transfer", (req, res) => {
  res.json({ sent: req.body.amount });
});

const browser = request.agent(app);
const { csrfToken } = (await browser.post("/login")).body;

// Поддельная отправка формы: cookie уходит, а токен неизвестен
const forged = await browser.post("/transfer").send({ amount: 500 });
console.log("подделка:", forged.status, forged.body);

const real = await browser
  .post("/transfer")
  .set("X-CSRF-Token", csrfToken)
  .send({ amount: 20 });
console.log("настоящий:", real.status, real.body);
```

</CodeExample>

В браузере ваш фронтенд хранит токен в памяти (или читает его из тега `<meta name="csrf-token">`) и добавляет к каждому `fetch`: `headers: { "X-CSRF-Token": csrfToken }`. Вариант без состояния на сервере — **подписанная cookie двойной отправки (signed double-submit cookie)**: токен лежит в читаемой cookie и должен повторяться в заголовке, а сам он — HMAC от id сессии, так что поддомен не сможет подсунуть свой. Библиотеки вроде `csrf-csrf` реализуют это для Express, а фреймворки вроде Next.js (Server Actions) и SvelteKit проверяют заголовок `Origin` за вас.

<Callout type="tip" title="Bearer-токены и CSRF">

CSRF — это проблема cookie. Если ваш API принимает только заголовок `Authorization: Bearer ...`, который ваш JavaScript добавляет явно, поддельная форма не сможет его включить, и CSRF вам не грозит. Обратная сторона, как вы видели в прошлом уроке, в том, что токен тогда хранится там, где его может прочитать JavaScript, а значит, и украсть XSS.

</Callout>

## CORS: кто может читать ваши ответы

Браузеры соблюдают **политику одного источника (same-origin policy)**: JavaScript с одного **источника (origin)** (схема + хост + порт, например `https://app.pandadev.example:443`) может **отправлять** запросы на другой источник, но не может **читать** ответы. Именно это не даёт `cute-panda-pics.example` загрузить банковские выписки ваших пользователей с их cookie.

Но иногда нужно, чтобы другой источник читал ваш API: ваш фронтенд на `app.pandadev.example` обращается к `api.pandadev.example`. **CORS** (Cross-Origin Resource Sharing, совместное использование ресурсов между источниками) — это способ, которым **сервер** говорит браузеру «этот другой источник может читать мои ответы», с помощью заголовков ответа:

| Заголовок | Значение |
| --- | --- |
| `Access-Control-Allow-Origin: https://app.pandadev.example` | этот источник может читать ответ (один источник или `*`) |
| `Access-Control-Allow-Credentials: true` | ...даже если запрос пришёл с cookie |
| `Access-Control-Allow-Methods: GET, POST` | для предварительных запросов: разрешённые методы |
| `Access-Control-Allow-Headers: Content-Type` | для предварительных запросов: разрешённые заголовки запроса |
| `Access-Control-Max-Age: 600` | браузер может закешировать этот ответ на предварительный запрос на 10 минут |
| `Vary: Origin` | ответ зависит от `Origin`, поэтому кеши не должны их путать |

**Предварительные запросы (preflights).** Для «простых» запросов (GET или POST обычной формы) браузер просто отправляет запрос, а потом решает, можно ли показать ответ странице. Для всего остального — `PUT`/`DELETE`, JSON в `Content-Type` или собственный заголовок вроде `X-CSRF-Token` — он сначала автоматически отправляет запрос **`OPTIONS`** с `Access-Control-Request-Method` и `Access-Control-Request-Headers`, спрашивая разрешения. Настоящий запрос следует только если ответ это разрешает.

Вот небольшой middleware для CORS с **белым списком (allowlist)** источников:

<CodeExample output={`200 https://app.pandadev.example
200 (нет заголовка CORS)
204 https://app.pandadev.example
GET, POST`}>

```js
import express from "express";
import request from "supertest";

function cors({ origins }) {
  const allowed = new Set(origins);
  return (req, res, next) => {
    const origin = req.get("Origin");
    res.set("Vary", "Origin"); // ответы зависят от источника
    if (origin && allowed.has(origin)) {
      res.set("Access-Control-Allow-Origin", origin);
    }
    if (req.method === "OPTIONS") { // preflight: отвечаем здесь
      res.set("Access-Control-Allow-Methods", "GET, POST");
      res.set("Access-Control-Allow-Headers", "Content-Type");
      return res.status(204).end();
    }
    next();
  };
}

const app = express();
app.use(cors({ origins: ["https://app.pandadev.example"] }));
app.get("/api/pandas", (req, res) => res.json(["Mei", "Po"]));

const show = (res) => console.log(res.status,
  res.headers["access-control-allow-origin"] ?? "(нет заголовка CORS)");

show(await request(app).get("/api/pandas")
  .set("Origin", "https://app.pandadev.example"));
show(await request(app).get("/api/pandas")
  .set("Origin", "https://evil.example"));

const preflight = await request(app)
  .options("/api/pandas")
  .set("Origin", "https://app.pandadev.example")
  .set("Access-Control-Request-Method", "POST")
  .set("Access-Control-Request-Headers", "Content-Type");
show(preflight);
console.log(preflight.headers["access-control-allow-methods"]);
```

</CodeExample>

Посмотрите внимательно на вторую строку: запрос с `evil.example` всё равно получил **200** и данные. Сервер ничего не заблокировал, он просто не добавил заголовок, поэтому **браузер** откажется передавать ответ JavaScript-коду вредоносной страницы. Это самое важное, что нужно понять про CORS:

- **CORS — это не контроль доступа.** `curl`, скрипты и другие серверы его полностью игнорируют. Вашему API всё равно нужны аутентификация и авторизация.
- **CORS не останавливает CSRF.** Простые запросы (вроде поддельной формы) всё равно **отправляются**; CORS управляет только чтением ответа.
- **CORS ослабляет** политику одного источника. Неправильно настроенный CORS делает вас *менее* защищёнными, чем отсутствие CORS вообще.

Классическая ошибка конфигурации — **отражать любой `Origin`** вместе с `Access-Control-Allow-Credentials: true` («ошибка CORS ведь исчезла!»). Теперь любой сайт может читать данные ваших вошедших пользователей. Именно поэтому браузеры отказываются принимать `*` вместе с учётными данными, и люди отражают источник, чтобы это обойти. Всегда сравнивайте с **точным белым списком**: `origin.endsWith("pandadev.example")` подходит и для `evilpandadev.example`, а `includes` — для `pandadev.example.evil.com`.

В реальных проектах то же самое по той же идее белого списка делает пакет `cors`:

```js
// npm install cors
import cors from "cors";

app.use(cors({
  origin: ["https://app.pandadev.example"],  // никогда true + credentials
  credentials: true,
  methods: ["GET", "POST", "DELETE"],
  allowedHeaders: ["Content-Type", "X-CSRF-Token"],
  maxAge: 600,
}));
```

А самая простая настройка CORS — никакой: отдавайте фронтенд и API с **одного источника** (например, `/api` на том же домене через ваш фреймворк или обратный прокси), и CORS вообще не понадобится.

## Заголовки безопасности

У браузеров есть мощная защита, которая **выключена**, пока ваш сервер не попросит её заголовком ответа. Вот те **заголовки безопасности (security headers)**, которые стоит отправлять в каждом ответе:

| Заголовок | Типичное значение | Защищает от |
| --- | --- | --- |
| `Content-Security-Policy` | `default-src 'self'; frame-ancestors 'none'` | XSS (блокирует внедрённые скрипты) и кликджекинга |
| `X-Content-Type-Options` | `nosniff` | того, что браузер «угадает» в загруженном файле HTML или JS |
| `X-Frame-Options` | `DENY` | кликджекинга в старых браузерах (`frame-ancestors` из CSP — современная версия) |
| `Referrer-Policy` | `strict-origin-when-cross-origin` | утечки полных URL (с токенами или id) на другие сайты |
| `Strict-Transport-Security` | `max-age=31536000; includeSubDomains` | понижения до HTTP во враждебном Wi-Fi (HSTS) |

**Кликджекинг (clickjacking)** — это когда атакующий загружает ваш сайт в невидимый `<iframe>` поверх своей страницы и обманом заставляет пользователей нажимать ваши кнопки; `frame-ancestors 'none'` вообще запрещает встраивать ваш сайт во фреймы. **HSTS** говорит браузеру «для этого домена год используй только HTTPS», так что даже набранная вручную ссылка `http://` повышается до HTTPS ещё до отправки. Включайте его, только когда HTTPS работает везде на домене, ведь браузеры его запомнят.

В Express пакет `helmet` одной строкой ставит разумные версии всех этих заголовков (и не только), а CSP вы настраиваете под своё приложение:

```js
// npm install helmet
import helmet from "helmet";

app.use(helmet({
  contentSecurityPolicy: {
    directives: {
      "script-src": ["'self'", "https://js.stripe.com"],
      "frame-ancestors": ["'none'"],
    },
  },
}));
// helmet ещё и убирает заголовок X-Powered-By: Express
```

Многие команды вместо этого ставят эти заголовки на **границе (edge)** (в настройках Vercel или Netlify, в nginx, в Cloudflare), чтобы их получали даже статические файлы. Бесплатные сканеры вроде HTTP Observatory от Mozilla за секунды оценивают заголовки сайта.

## Секреты: держите их вне кода и бандлов

API-ключи, пароли от баз данных и секреты для подписей дают тому, у кого они есть, возможность действовать от имени вашего приложения. Три правила:

**1. Секреты живут в окружении, а не в коде.** Читайте их в **одном** месте при запуске, проверяйте и падайте сразу, если чего-то не хватает, а не на первом запросе в три часа ночи:

<CodeExample output={`Не хватает настроек: SESSION_SECRET, STRIPE_KEY
DATABASE_URL=postgres://localhost/pandas
SESSION_SECRET=[скрыто]
STRIPE_KEY=[скрыто]`}>

```js
const REQUIRED = ["DATABASE_URL", "SESSION_SECRET", "STRIPE_KEY"];
const SECRETS = new Set(["SESSION_SECRET", "STRIPE_KEY"]);

// Читаем и проверяем настройки ОДИН раз при запуске:
// падаем сразу и громко
function loadConfig(env) {
  const missing = REQUIRED.filter((name) => !env[name]);
  if (missing.length > 0) {
    throw new Error(`Не хватает настроек: ${missing.join(", ")}`);
  }
  if (env.SESSION_SECRET.length < 32) {
    throw new Error("SESSION_SECRET должен быть не короче 32 символов");
  }
  return Object.freeze(Object.fromEntries(
    REQUIRED.map((name) => [name, env[name]])
  ));
}

// Безопасно для логов: значения секретов заменены
function redact(config) {
  return Object.fromEntries(Object.entries(config).map(
    ([name, value]) => [name, SECRETS.has(name) ? "[скрыто]" : value]
  ));
}

try {
  loadConfig({ DATABASE_URL: "postgres://localhost/pandas" });
} catch (error) {
  console.log(error.message);
}

// В Node: loadConfig(process.env)
const config = loadConfig({
  DATABASE_URL: "postgres://localhost/pandas",
  SESSION_SECRET: "x".repeat(40),
  STRIPE_KEY: "sk_test_not_a_real_key",
});
for (const [name, value] of Object.entries(redact(config))) {
  console.log(`${name}=${value}`);
}
```

</CodeExample>

`loadConfig` принимает `env` как параметр, поэтому тесты передают обычный объект, а настоящий сервер — `process.env`. Локально храните значения в файле `.env`, который **никогда** не попадает в Git, и закоммитьте `.env.example` с именами и фейковыми значениями, чтобы коллеги знали, что нужно задать:

```bash
# .gitignore
.env
.env.*
!.env.example

# запуск с загруженным файлом (Node 20.6+)
node --env-file=.env server.js
```

В продакшене задавайте значения в настройках хостинга (Vercel, Render, Fly.io) или в менеджере секретов (AWS Secrets Manager, Doppler, 1Password), но никогда не в репозитории и не в Docker-образе.

**2. Всё, что попало в клиентский бандл, публично.** Любую строку JavaScript, которую вы отправляете в браузер, может прочитать кто угодно через DevTools. Инструменты сборки **намеренно** встраивают в бандл определённые переменные окружения: `VITE_*` в Vite и `NEXT_PUBLIC_*` в Next.js. Эти префиксы означают «это значение публичное»:

```js
// ❌ Уходит каждому посетителю: любой может скопировать ключ
const res = await fetch("https://api.openweather.example/data", {
  headers: { "X-API-Key": import.meta.env.VITE_WEATHER_KEY },
});

// ✅ Браузер обращается к ВАШЕМУ серверу, а тот добавляет ключ
const res2 = await fetch("/api/weather?city=London");
// сервер: fetch(upstream, { headers: { "X-API-Key":
//   process.env.WEATHER_KEY } })  // без префикса: только на сервере
```

Ключи, которые *задуманы* публичными (**publishable**-ключ Stripe, DSN Sentry, ключ карт, ограниченный вашим доменом), в бандле допустимы. Секретные ключи — никогда.

**3. Исходите из того, что утечки случаются, и готовьтесь к ним.** Боты сканируют каждый публичный push на GitHub в поисках ключей и пускают их в ход за **минуты**. Если секрет хоть раз попал в коммит или был вставлен куда-то публично:

- **Немедленно смените его (ротация)**: создайте новый ключ, разверните его, затем отзовите старый. Удалить коммит недостаточно: он продолжает жить в истории, форках, кешах и копиях ботов.
- Проверьте в логах провайдера, для чего использовали утёкший ключ.
- Включите **сканирование секретов (secret scanning)**: защита при push на GitHub блокирует коммиты с известными форматами ключей, а инструменты вроде `gitleaks` или `trufflehog` сканируют вашу историю и запускаются в CI или в pre-commit-хуке.
- Никогда не пишите секреты в логи (отсюда `redact`) и давайте каждому окружению **собственные** ключи с минимально достаточными правами, чтобы утёкший тестовый ключ не мог добраться до продакшена.

## Безопасность цепочки поставок

В типичном Node-проекте в `node_modules` **сотни** пакетов, о большинстве которых вы даже не слышали, и каждый может выполнять код на вашем ноутбуке, в CI и в продакшене. Атакующие это знают — так появляются **атаки на цепочку поставок (supply chain)**:

- **Тайпсквоттинг (typosquatting)**: публикация `crossenv` рядом с настоящим `cross-env` (реальная атака 2017 года, крадущая переменные окружения) или `reqeusts` рядом с `requests`.
- **Взломанные мейнтейнеры**: в 2018 году у `event-stream` появился новый «услужливый» мейнтейнер, который добавил код для кражи из биткоин-кошельков; в 2025 году через фишинг аккаунтов мейнтейнеров вредоносный код попал в очень популярные пакеты вроде `chalk` и `debug` с сотнями миллионов загрузок в неделю.
- **Скрипты установки**: скрипты `preinstall`/`postinstall` автоматически выполняются при `npm install`, ещё до того, как вы что-либо импортировали.

Привычки, которые вас защищают:

```bash
# Коммитьте package-lock.json и устанавливайте в CI РОВНО его
npm ci

# Известные уязвимости в дереве зависимостей
npm audit
npm audit --omit=dev     # только то, что уходит в продакшен

# Проверка подписей и происхождения пакетов из реестра
npm audit signatures

# Не запускайте скрипты установки, если пакету они действительно не нужны
npm install --ignore-scripts
```

- **Lock-файлы фиксируют всё**, включая зависимости зависимостей. Без `npm ci` свежая установка может подтянуть совсем новую (возможно, вредоносную) патч-версию. `^1.2.3` в `package.json` — это нормально, пока lock-файл закоммичен и соблюдается.
- **Думайте, прежде чем добавлять зависимость**: поддерживается ли она, широко ли используется, правильно ли написано имя? Действительно ли функции на 10 строк нужен пакет? Каждая зависимость — это код, которому вы доверяете свои секреты.
- **Автоматизируйте обновления** через Dependabot или Renovate, чтобы исправления безопасности приходили маленькими пул-реквестами, которые легко проверить, а не пугающим ежегодным обновлением:

```yaml
# .github/dependabot.yml
version: 2
updates:
  - package-ecosystem: "npm"
    directory: "/"
    schedule:
      interval: "weekly"
    groups:
      minor-and-patch:
        update-types: ["minor", "patch"]
```

pnpm (начиная с версии 10) идёт ещё дальше и вообще не запускает скрипты установки зависимостей, пока вы не разрешите их поимённо, — это блокирует целый класс атак.

Команда «починила» ошибку CORS на стейджинге, отражая любой пришедший `Origin` с `credentials: true`, и эта настройка уехала в продакшен. Любой сайт, который посещал вошедший клиент, теперь мог вызывать API с его cookie **и читать ответы**: имена, адреса, заказы. Исправление заняло одну строку — точный белый список. Когда настройка безопасности «просто убирает ошибку», остановитесь и выясните, что она на самом деле разрешает.

Notes API скоро начнёт получать запросы с cookie от своего нового фронтенда на `https://notes.pandadev.example`. Напишите два middleware, которые он использует:

1. **`securityHeaders()`** возвращает middleware, который устанавливает каждый заголовок из `HEADERS` в **каждом** ответе (в том числе в 404), а затем вызывает `next()`. Подсказка: `res.set()` принимает объект.
2. **`cors({ allowedOrigins })`** возвращает middleware, который:
   - всегда устанавливает `Vary: Origin`;
   - если `Origin` запроса **в точности** совпадает с одним из `allowedOrigins`, устанавливает `Access-Control-Allow-Origin` равным этому источнику (никогда не `*`) и `Access-Control-Allow-Credentials: true`;
   - сам отвечает на **предварительные запросы** (`OPTIONS`): для разрешённого источника — **204** с `Access-Control-Allow-Methods: GET, POST, DELETE`, `Access-Control-Allow-Headers: Content-Type, X-CSRF-Token` и `Access-Control-Max-Age: 600`; для любого другого — **403** без заголовков CORS;
   - пропускает все остальные запросы дальше через `next()`, даже с неизвестных источников (CORS соблюдает браузер; вашим маршрутам всё равно нужна аутентификация).

Проверки пробуют несколько разрешённых источников и хитрые двойники вроде `https://notes.pandadev.example.evil.com` и `http://notes.pandadev.example`.

<Hint>

Создайте `Set` из `allowedOrigins` один раз, вне возвращаемой функции, и используйте `set.has(origin)`: это точное совпадение, в отличие от `includes` на строке или `endsWith`. Внутри прочитайте `req.get("Origin")`, сначала установите `Vary`, затем — два allow-заголовка, если источник разрешён. Для `OPTIONS` сделайте `return res.status(403).end()` или установите три заголовка для предварительного запроса и `return res.status(204).end()`. Предварительный запрос никогда не доходит до ваших маршрутов.

</Hint>

<Solution>

```js
import express from "express";
import request from "supertest";

const HEADERS = {
  "Content-Security-Policy":
    "default-src 'self'; frame-ancestors 'none'; object-src 'none'",
  "X-Content-Type-Options": "nosniff",
  "X-Frame-Options": "DENY",
  "Referrer-Policy": "strict-origin-when-cross-origin",
  "Strict-Transport-Security": "max-age=31536000; includeSubDomains",
};

function securityHeaders() {
  return (req, res, next) => {
    res.set(HEADERS);
    next();
  };
}

function cors({ allowedOrigins }) {
  const allowed = new Set(allowedOrigins);
  return (req, res, next) => {
    const origin = req.get("Origin");
    const isAllowed = origin !== undefined && allowed.has(origin);
    res.set("Vary", "Origin");
    if (isAllowed) {
      res.set("Access-Control-Allow-Origin", origin);
      res.set("Access-Control-Allow-Credentials", "true");
    }
    if (req.method === "OPTIONS") {
      if (!isAllowed) return res.status(403).end();
      res.set({
        "Access-Control-Allow-Methods": "GET, POST, DELETE",
        "Access-Control-Allow-Headers": "Content-Type, X-CSRF-Token",
        "Access-Control-Max-Age": "600",
      });
      return res.status(204).end();
    }
    next();
  };
}

function createApp({ allowedOrigins }) {
  const notes = ["Buy bamboo"];
  const app = express();
  app.use(securityHeaders());
  app.use(cors({ allowedOrigins }));
  app.use(express.json());

  app.get("/api/notes", (req, res) => res.json(notes));
  app.post("/api/notes", (req, res) => {
    notes.push(String(req.body.text));
    res.status(201).json(notes);
  });
  app.use((req, res) => {
    res.status(404).json({ error: "Not found" });
  });
  return app;
}

const app = createApp({
  allowedOrigins: ["https://notes.pandadev.example"],
});
const res = await request(app)
  .get("/api/notes")
  .set("Origin", "https://notes.pandadev.example");
console.log(res.status, res.body);
console.log(res.headers["access-control-allow-origin"]);
console.log(res.headers["x-content-type-options"]);
```

## Итоги

- **CSRF** заставляет браузер жертвы отправлять запросы с её cookie. Защищайтесь cookie с `SameSite=Lax`/`Strict`, отсутствием побочных эффектов на `GET`, **CSRF-токенами** (синхронизирующими или подписанными double-submit) для запросов, меняющих состояние, и проверками `Origin` / `Sec-Fetch-Site`.
- **Политика одного источника** не даёт страницам читать ответы с других источников; **CORS** позволяет вашему серверу ослабить её для **точного белого списка** источников. Отвечайте на **предварительные** запросы `OPTIONS`, отправляйте `Vary: Origin` и никогда не отражайте любой источник вместе с credentials.
- CORS — **не** контроль доступа и не останавливает CSRF: серверы всё равно отвечают, а небраузерные клиенты его игнорируют.
- **Заголовки безопасности** включают защиту браузера: CSP, `X-Content-Type-Options: nosniff`, `frame-ancestors`/`X-Frame-Options`, `Referrer-Policy`, HSTS. В Express их ставит `helmet`.
- **Секреты** живут в окружении, проверяются один раз при запуске (`loadConfig(process.env)`) и никогда не попадают в Git, логи или клиентский бандл (`VITE_`/`NEXT_PUBLIC_` означают «публично»). Утекли? Немедленно проведите **ротацию** и включите сканирование секретов.
- **Цепочка поставок**: коммитьте lock-файл и используйте `npm ci`, запускайте `npm audit`, осторожно относитесь к скриптам установки и тайпсквоттингу, и пусть Dependabot или Renovate поддерживают зависимости свежими.
