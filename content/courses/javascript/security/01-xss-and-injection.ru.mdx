Большинство уязвимостей в JavaScript-приложениях вырастает из одной коренной ошибки: **данные начинают считаться кодом**. Комментарий разбирается как HTML, поисковый запрос становится частью SQL, ключ из JSON тихо переписывает `Object.prototype`. В каждом случае кто-то посторонний получает право решать, что делает ваша программа. В этом уроке вы научитесь замечать места, где такое возможно, посмотрите, как несколько атак срабатывают в безопасной песочнице, а затем закроете каждую дыру тем способом, которым это делают профессионалы. 🛡️

Всё здесь — про **защиту**: вы увидите ровно столько от каждой атаки, сколько нужно, чтобы её понять и написать тест, который доказывает, что исправление работает.

## Думайте как атакующий

Работа над безопасностью начинается с простого вопроса к каждой функции приложения: **что может пойти не так и кто этого добьётся?** Это называется **моделированием угроз (threat modelling)**, и для начала не нужен никакой формальный метод:

- **Что мы защищаем?** Аккаунты, персональные данные, деньги, возможность что-то менять, процессорное время ваших серверов.
- **Где к нам попадают недоверенные данные?** Тела запросов, строки запроса, заголовки, cookie, загруженные файлы, `location.hash`, `postMessage`, сторонние API и даже данные из **вашей собственной базы данных**, которые когда-то ввёл пользователь. Каждое такое место — это **граница доверия (trust boundary)**.
- **Что будет, если этим злоупотребят?** «Кто-то прочитает сообщения всех пользователей» заслуживает куда больше внимания, чем «кто-то увидит опечатку».

**OWASP Top 10** (от проекта Open Worldwide Application Security Project) — это список самых распространённых серьёзных рисков веб-приложений. Вот как главные из них выглядят в JavaScript:

| Риск | Типичная ошибка в JavaScript | Где вы это исправите |
| --- | --- | --- |
| Сломанный контроль доступа | проверяют вход, но не владение | [аутентификация](/learn/javascript/authentication-and-sessions) |
| Внедрение (включая XSS) | `innerHTML`, SQL из строк, `{ "$ne": "" }` | этот урок |
| Криптографические ошибки | пароли в MD5/SHA-256, токены в `localStorage` | [аутентификация](/learn/javascript/authentication-and-sessions) |
| Ошибки конфигурации | слишком открытый CORS, нет заголовков безопасности | [CSRF, CORS и секреты](/learn/javascript/csrf-cors-and-secrets) |
| Уязвимые и вредоносные пакеты | старые lock-файлы, npm-пакеты с похожими именами (тайпсквоттинг) | [CSRF, CORS и секреты](/learn/javascript/csrf-cors-and-secrets) |
| Ошибки аутентификации | нет ограничения попыток входа, вечные сессии | [аутентификация](/learn/javascript/authentication-and-sessions) |

Всё это связывает один подход — **эшелонированная защита (defence in depth)**: никогда не полагайтесь на одну-единственную проверку. Валидируйте ввод, **и** экранируйте вывод, **и** отправляйте Content-Security-Policy — тогда одна ошибка не превратится во взлом.

## Межсайтовый скриптинг (XSS)

**XSS** (cross-site scripting) случается, когда атакующему удаётся запустить **свой** JavaScript на **вашей** странице, в браузерах ваших пользователей. Такой скрипт получает те же возможности, что и ваш код: он может прочитать всё на странице (включая токены в `localStorage`), отправлять запросы от имени вошедшего пользователя или подменить вашу форму входа поддельной. Бывает три вида XSS:

- **Хранимый XSS (stored XSS)**: вредоносная нагрузка (payload) сохраняется (комментарий, имя в профиле, отзыв о товаре) и отдаётся **каждому** посетителю. Самый опасный вид.
- **Отражённый XSS (reflected XSS)**: нагрузка находится в ссылке, например `/search?q=<payload>`, а сервер вставляет её прямо в страницу. Атакующий обманом заставляет кого-то перейти по ссылке.
- **DOM-based XSS**: сервер её вообще не видит. Ваш собственный фронтенд-код читает что-то вроде `location.hash` и записывает это в страницу через `innerHTML`.

Все три заканчиваются одинаково: строка извне **разбирается как HTML**. Классической нагрузке даже не нужен тег `<script>` (браузеры не запускают скрипты, вставленные через `innerHTML`), потому что атрибут-обработчик события работает ничуть не хуже.

### innerHTML или textContent

Нажмите **«Запустить»** и попробуйте обе кнопки. «Комментарий» — это картинка с битым `src` и обработчиком `onerror`. Здесь он безобиден и лишь пишет сообщение на странице, но обработчик настоящего атакующего отправил бы куда-нибудь ваши cookie или токены.

<TryIt
  html={`<p>Посетитель оставил такой комментарий:</p>
<textarea id="comment" rows="3" cols="56"><img src="x" onerror="document.querySelector('#alarm').textContent = '😱 Внедрённый код только что выполнился!'"></textarea>
<p>
  <button id="unsafe">Показать через innerHTML</button>
  <button id="safe">Показать через textContent</button>
</p>
<div id="output"></div>
<p id="alarm"></p>`}
  code={`const comment = document.querySelector("#comment");
const output = document.querySelector("#output");
const alarm = document.querySelector("#alarm");

document.querySelector("#unsafe").addEventListener("click", () => {
  alarm.textContent = "";
  output.innerHTML = comment.value; // ❌ разбирается как HTML
});

document.querySelector("#safe").addEventListener("click", () => {
  alarm.textContent = "";
  output.textContent = comment.value; // ✅ показывается как текст
});`}
/>

С **`innerHTML`** браузер создаёт настоящий элемент `<img>`, картинка не загружается, и выполняется код атакующего из `onerror`. С **`textContent`** та же самая строка показывается как безобидные символы. Это первое правило защиты от XSS:

- Чтобы показать **текст**, используйте `textContent`, `createElement` + `append` или `setAttribute` с безопасным значением. Они никогда не разбирают HTML.
- Считайте `innerHTML`, `outerHTML`, `insertAdjacentHTML` и `document.write` **опасными зонами**. Передавайте в них только HTML, который вы собрали сами, или HTML, прошедший санитизацию (об этом ниже).

## Экранирование HTML: важен контекст

Иногда вы действительно собираете HTML-строку: серверный шаблон, письмо, строку, которую потом положите в `innerHTML`. Тогда каждый кусок недоверенных данных нужно **экранировать (escape)**: специальные символы заменяются **HTML-сущностями (HTML entities)**, которые показывают символ, а не работают как разметка.

| Символ | Сущность | Чем опасен |
| --- | --- | --- |
| `&` | `&amp;` | начинает сущность (экранируйте его **первым**) |
| `<` и `>` | `&lt;` и `&gt;` | открывают и закрывают теги |
| `"` | `&quot;` | закрывает значение атрибута в `"…"` |
| `'` | `&#39;` | закрывает значение атрибута в `'…'` |

Частое полуисправление экранирует только `<` и `>`. Посмотрите, что будет, когда значение попадёт внутрь **атрибута**:

<CodeExample output={`<a href="/pandas" title="Cute pandas">
<a href="/pandas" title="" onmouseover="steal()">`}>

```js
// Экранировать только < и > недостаточно
function escapeAngles(text) {
  return text.replaceAll("<", "&lt;").replaceAll(">", "&gt;");
}

function renderLink(url, title) {
  const href = escapeAngles(url);
  return `<a href="${href}" title="${escapeAngles(title)}">`;
}

console.log(renderLink("/pandas", "Cute pandas"));
console.log(renderLink("/pandas", '" onmouseover="steal()'));
```

</CodeExample>

Угловые скобки не понадобились: кавычка раньше времени закрывает атрибут `title`, и атакующий добавляет совершенно новый обработчик события. Полноценную функцию `escapeHtml` вы напишете в упражнении.

Экранирование зависит от того, **куда** попадают данные. HTML-сущности защищают текст HTML и атрибуты в кавычках, но не URL внутри `href`: в `javascript:alert(1)` нечего экранировать, а при клике он всё равно выполнится. Ссылки, которые приходят от пользователей, нужно **разобрать** и разрешить только ожидаемые схемы:

<CodeExample output={`true https://example.com/pandas
true /profile/mei
false javascript:alert(document.cookie)
false  JaVaScRiPt:alert(1)
false data:text/html,<script>alert(1)</script>`}>

```js
function isSafeUrl(text) {
  try {
    const url = new URL(text, "https://pandadev.example");
    return ["http:", "https:", "mailto:"].includes(url.protocol);
  } catch {
    return false;
  }
}

const links = [
  "https://example.com/pandas",
  "/profile/mei",
  "javascript:alert(document.cookie)",
  " JaVaScRiPt:alert(1)",
  "data:text/html,<script>alert(1)</script>",
];
for (const link of links) {
  console.log(isSafeUrl(link), link);
}
```

</CodeExample>

Парсер URL справляется с уловками (смешанный регистр, пробелы в начале), которые пропустила бы самописная проверка `startsWith("javascript:")`. Этот приём стоит запомнить: **разберите, а затем сверьтесь с белым списком (allowlist)**, вместо того чтобы пытаться распознать каждый плохой ввод по чёрному списку (blocklist).

## React экранирует за вас (почти всегда)

Хорошая новость: React экранирует всё, что вы помещаете в `{фигурные скобки}`. Плохая: у него есть лазейка с нарочно пугающим названием. Отредактируйте комментарий и сравните два результата:

<TryIt
  language="react"
  code={`import { useState } from "react";
import { createRoot } from "react-dom/client";

const evil =
  '<img src="x" onerror="this.parentNode.append(\\'😱 код выполнился!\\')">';

function Comment({ text }) {
  // ✅ React экранирует {text}: теги видны как обычный текст
  return <p className="safe">{text}</p>;
}

function RawComment({ html }) {
  // ❌ dangerouslySetInnerHTML вставляет строку как настоящий HTML
  return (
    <p className="raw" dangerouslySetInnerHTML={{ __html: html }} />
  );
}

function App() {
  const [text, setText] = useState(evil);
  return (
    <div>
      <textarea
        value={text}
        onChange={(e) => setText(e.target.value)}
        rows={3}
        cols={50}
      />
      <h3>{"{text}"}</h3>
      <Comment text={text} />
      <h3>dangerouslySetInnerHTML</h3>
      <RawComment html={text} />
    </div>
  );
}

createRoot(document.getElementById("root")).render(<App />);`}
/>

Поэтому в React XSS обычно пробирается через несколько известных дверей:

- **`dangerouslySetInnerHTML`**: только с HTML, которому вы доверяете или который прошёл санитизацию. Ищите его на код-ревью.
- **URL в `href` / `src`**, собранные из данных пользователя: проверяйте их, как `isSafeUrl` выше. Свежие версии React блокируют URL вида `javascript:`, но не делайте это своей единственной защитой.
- **Рефы и эффекты (effects)**, которые напрямую трогают DOM (`ref.current.innerHTML = ...`): React не может защитить код, который его обходит.
- **Состояние при серверном рендеринге**, встроенное в тег `<script>` через `JSON.stringify` (`</script>` внутри данных раньше времени закрывает тег). Фреймворки вроде Next.js экранируют это за вас, а самописный SSR часто — нет.

### Если нужно показать HTML пользователя — санитизируйте его

Редакторы форматированного текста, превью Markdown и HTML-письма требуют настоящего HTML. Не пишите собственный фильтр (атакующие знают сотни уловок), а используйте проверенный **санитайзер (sanitiser)**, например **DOMPurify**: он оставляет безопасные теги и вырезает скрипты и обработчики событий:

```bash
npm install dompurify
```

```jsx
import DOMPurify from "dompurify";

function RichComment({ html }) {
  const clean = DOMPurify.sanitize(html, {
    ALLOWED_TAGS: ["b", "i", "em", "strong", "a", "p", "ul", "li"],
    ALLOWED_ATTR: ["href"],
  });
  return <div dangerouslySetInnerHTML={{ __html: clean }} />;
}

// '<img src=x onerror=steal()><b>hi</b>' превращается в '<b>hi</b>'
```

Санитизируйте как можно **позже**, прямо перед рендером, чтобы через санитайзер проходил любой путь на страницу. На сервере Node для DOMPurify нужна реализация DOM (`isomorphic-dompurify` оборачивает его вместе с jsdom).

## Content-Security-Policy: страховочная сетка

Даже аккуратные команды рано или поздно выпускают XSS-баг. Заголовок **Content-Security-Policy** (CSP) сообщает браузеру, какие скрипты вообще разрешено запускать, поэтому внедрённый скрипт блокируется, даже если попал на страницу:

```text
Content-Security-Policy: default-src 'self';
  script-src 'self' 'nonce-r4nd0mPerRequest';
  object-src 'none'; base-uri 'self'; frame-ancestors 'none'
```

(Это одна строка заголовка, здесь она разбита, чтобы поместиться.) С такой политикой скрипты загружаются только с вашего собственного источника (origin) или из тегов `<script nonce="r4nd0mPerRequest">`, чей **nonce** совпадает с тем, что сервер сгенерировал для этого ответа, а **встроенные обработчики событий** вроде `onerror="..."` блокируются полностью. Один этот заголовок остановил бы все атаки из демонстраций этого урока.

- Включайте его сначала через **`Content-Security-Policy-Report-Only`**: браузер сообщает о нарушениях, ничего не блокируя, и вы находите встроенные скрипты, о которых забыли.
- Избегайте `'unsafe-inline'` и `'unsafe-eval'` в `script-src`: они отключают большую часть защиты.
- CSP — это **вторая** линия обороны. Первой остаются экранирование и безопасные DOM API.

Отправлять CSP и другие заголовки безопасности из Express вы будете в уроке [CSRF, CORS и секреты](/learn/javascript/csrf-cors-and-secrets).

<Callout type="warning" title="Токены в localStorage превращают XSS в захват аккаунта">

Любой скрипт на вашей странице может прочитать `localStorage`. Если там хранится токен входа, одной XSS-уязвимости хватит, чтобы атакующий скопировал его и пользовался аккаунтом со своего компьютера — даже когда жертва давно закрыла вкладку. Cookie с флагом `HttpOnly` JavaScript прочитать вообще не может. Этот компромисс вы как следует взвесите в [следующем уроке](/learn/javascript/authentication-and-sessions).

</Callout>

## Внедрение на сервере

XSS — это внедрение в **HTML**. Та же ошибка на сервере приводит к внедрению в **запросы** и **команды**.

### SQL-внедрение

Когда SQL склеивают из строк, ввод может изменить **смысл** запроса — это **SQL-внедрение (SQL injection)**:

<CodeExample output={`SELECT * FROM users WHERE email = 'mei@example.com'
SELECT * FROM users WHERE email = 'x' OR '1'='1'
SELECT * FROM users WHERE email = 'x'; DROP TABLE users; --'`}>

```js
function findUserSql(email) {
  return `SELECT * FROM users WHERE email = '${email}'`;
}

console.log(findUserSql("mei@example.com"));
console.log(findUserSql("x' OR '1'='1"));
console.log(findUserSql("x'; DROP TABLE users; --"));
```

</CodeExample>

Второй запрос находит **всех** пользователей, третий удаляет таблицу. Исправление — никогда не «экранировать кавычки самому». Это **параметризованные запросы (parameterised queries)**: SQL и значения отправляются в базу данных по отдельности, поэтому значение никогда не станет SQL. На вашем компьютере с PostgreSQL или SQLite:

```js
// node-postgres (npm i pg): $1, $2 — плейсхолдеры
const { rows } = await pool.query(
  "SELECT id, email FROM users WHERE email = $1",
  [email],
);

// better-sqlite3 (npm i better-sqlite3): плейсхолдеры ?
const user = db
  .prepare("SELECT id, email FROM users WHERE email = ?")
  .get(email);
```

Построители запросов и ORM (Prisma, Drizzle, Knex, Sequelize) параметризуют за вас — **кроме** своих лазеек для сырого SQL. `prisma.$queryRaw` с тегированным шаблоном безопасен, а `` prisma.$queryRawUnsafe(`... ${email}`) `` — это ровно тот же баг, только с более красивым названием. То же правило касается команд оболочки: `execFile("convert", [file, "out.png"])` передаёт аргументы безопасно, а `` exec(`convert ${file} out.png`) `` позволяет имени файла вроде `x; rm -rf ~` запустить вторую команду.

### Внедрение операторов в NoSQL

Запросы MongoDB — это объекты, а не строки, поэтому их часто считают безопасными. Но `express.json()` охотно превращает тело запроса в **объекты**, а MongoDB считает ключи, начинающиеся с `$`, **операторами**. Ниже крошечная замена `findOne` из MongoDB понимает `$ne` («не равно») — совсем как настоящая:

<CodeExample output={`/login-unsafe 200 { loggedIn: true }
/login 400 { error: 'Invalid input' }`}>

```js
import express from "express";
import request from "supertest";

// Крошечная замена findOne из MongoDB: понимает
// обычные значения и оператор $ne («не равно»).
// (Пароли открытым текстом — только для краткости: см. следующий урок!)
const users = [{ username: "admin", password: "s3cret!" }];
function findOne(query) {
  return users.find((user) =>
    Object.entries(query).every(([field, wanted]) =>
      wanted?.$ne !== undefined
        ? user[field] !== wanted.$ne
        : user[field] === wanted
    )
  );
}

const app = express();
app.use(express.json());

app.post("/login-unsafe", (req, res) => {
  const { username, password } = req.body;
  const user = findOne({ username, password });
  res.json({ loggedIn: Boolean(user) });
});

app.post("/login", (req, res) => {
  const { username, password } = req.body ?? {};
  if (typeof username !== "string" ||
      typeof password !== "string") {
    return res.status(400).json({ error: "Invalid input" });
  }
  const user = findOne({ username, password });
  res.json({ loggedIn: Boolean(user) });
});

const attack = { username: "admin", password: { $ne: "" } };
for (const url of ["/login-unsafe", "/login"]) {
  const res = await request(app).post(url).send(attack);
  console.log(url, res.status, res.body);
}
```

</CodeExample>

«Впусти меня как admin, у которого пароль **не равен** пустой строке» находит администратора, каким бы ни был его пароль. Исправление скучное, но действенное: **проверяйте тип** каждого поля, прежде чем оно попадёт в запрос. Библиотека схем вроде Zod (`z.string()`) делает это для целых объектов, а у Mongoose есть опция `sanitizeFilter`, которая обезвреживает ключи с `$` в фильтрах, — как дополнительный слой защиты.

## Загрязнение прототипа

Эта уязвимость — особенность именно JavaScript. Каждый обычный объект наследует от `Object.prototype`, а ключ `"__proto__"` — это **геттер/сеттер прототипа объекта**. `JSON.parse` создаёт `"__proto__"` как обычный ключ, но небрежное **глубокое слияние (deep merge)** потом записывает в него, а значит — в `Object.prototype`, общий для **всех** объектов. Это и есть **загрязнение прототипа (prototype pollution)**:

<CodeExample output={`{ font: 18 } light
true true
false`}>

```js
// Самописное глубокое слияние — таких в npm тысячи
function merge(target, source) {
  for (const key in source) {
    const value = source[key];
    if (value && typeof value === "object") {
      target[key] ??= {};
      merge(target[key], value);
    } else {
      target[key] = value;
    }
  }
  return target;
}

const defaults = { theme: "light", sizes: { font: 14 } };
const body = JSON.parse(
  '{"sizes": {"font": 18}, "__proto__": {"isAdmin": true}}'
);
const settings = merge(structuredClone(defaults), body);
console.log(settings.sizes, settings.theme);

const visitor = { name: "Po" }; // совершенно новый, посторонний объект
console.log("isAdmin" in visitor, visitor.isAdmin);
console.log(Object.hasOwn(visitor, "isAdmin"));

delete Object.prototype.isAdmin; // прибираемся после демонстрации
```

</CodeExample>

Слияние выглядело правильным, настройки получились верными, и всё же совершенно посторонний объект теперь сообщает `isAdmin: true`. Любой код вроде `if (user.isAdmin)` для пользователя без этого поля теперь обманут — для **каждого запроса**, пока сервер не перезапустится. В зависимости от того, что читает приложение, загрязнение прототипа приводило к повышению привилегий, падениям и даже удалённому выполнению кода через шаблонизаторы. В 2019 году ровно такой баг был в `defaultsDeep` из lodash, и бесчисленным проектам пришлось обновляться.

Как обезопасить себя:

<CodeExample output={`null [ '__proto__' ]
true undefined
true undefined
true false`}>

```js
const body = JSON.parse('{"__proto__": {"isAdmin": true}}');

// 1. Словарь вообще без прототипа
const dict = Object.create(null);
dict["__proto__"] = { isAdmin: true };
console.log(Object.getPrototypeOf(dict), Object.keys(dict));

// 2. Map: ключи — просто ключи
const map = new Map(Object.entries(body));
console.log(map.has("__proto__"), {}.isAdmin);

// 3. Копируете? Используйте structuredClone, а не самописную глубокую копию
const copy = structuredClone(body);
console.log(Object.hasOwn(copy, "__proto__"), {}.isAdmin);

// 4. Поиск в обычных объектах: проверяйте, что ключ действительно свой
const roles = { mei: "admin" };
const who = "constructor";
console.log(roles[who] !== undefined, Object.hasOwn(roles, who));
```

</CodeExample>

- Используйте **`Map`** или **`Object.create(null)`** для словарей, ключи которых приходят от пользователей.
- Используйте **`structuredClone`** для глубоких копий: он создаёт обычные собственные свойства и никогда не заходит в прототипы.
- Если без слияния не обойтись, **отклоняйте** ключи `__proto__`, `constructor` и `prototype` и копируйте только **собственные** ключи (`Object.keys`, а не `for...in`). Это вы сделаете в упражнении.
- Проверяйте поиск по ключу через **`Object.hasOwn`**: последняя строка показывает, что `roles["constructor"]` находит унаследованную функцию `Object`, а она истинна.
- Для дополнительной защиты Node умеет полностью убрать аксессор `__proto__`: `node --disable-proto=delete server.js`.

## eval, new Function и ReDoS

Ещё два способа отдать управление атакующему:

```js
// ❌ Каждая из этих строк выполняет строку как код
eval(req.query.expr);
new Function("return " + userFormula)();
setTimeout(userString, 100); // строка здесь тоже проходит через eval

// ✅ Данные остаются данными
const data = JSON.parse(req.body.raw);
const ops = { add: (a, b) => a + b, mul: (a, b) => a * b };
const result = ops[op]?.(a, b); // фиксированный белый список действий
```

Хорошей причины применять `eval` к вводу почти никогда не бывает. Если пользователям нужны формулы, используйте небольшой парсер выражений с фиксированным набором операций. Строгий CSP без `'unsafe-eval'` в качестве подстраховки блокирует `eval` в браузере.

**ReDoS** (Regular expression Denial of Service, отказ в обслуживании через регулярные выражения) коварнее. Некоторые регулярные выражения с **вложенными квантификаторами**, например `/^(a+)+$/`, работают экспоненциально долго на вводе, который *почти* подходит, — скажем, тридцать букв `a`, а за ними `!`. В JavaScript один главный поток, поэтому один такой запрос замораживает **весь сервер** для всех пользователей.

```js
// ❌ Не запускайте это на длинном вводе: вложенный + взрывается
const bad = /^(a+)+$/;
bad.test("a".repeat(30) + "!"); // секунды... или минуты

// ✅ Тот же смысл, без вложенности, и сначала ограничиваем длину
const good = /^a+$/;
if (input.length <= 100 && good.test(input)) { /* ... */ }
```

Защита: ограничивайте длину ввода **до** проверки, избегайте вложенных квантификаторов вроде `(a+)+` и `(.*)*`, включите правила линтера из `eslint-plugin-regexp`, чтобы он отмечал опасные шаблоны, а для шаблонов, которые присылают пользователи, используйте пакет `re2` — его движок работает за линейное время.

<Callout type="tip" title="Валидируйте на входе, кодируйте на выходе">

Две привычки покрывают большую часть этого урока. **На входе** валидируйте каждый ввод на границе: тип, длину, формат, допустимые ключи. **На выходе** кодируйте данные для того места, куда они попадают: HTML-экранирование для HTML, параметры для SQL, массив аргументов для команд оболочки, `JSON.stringify` для JSON. Одной валидации мало: совершенно корректная фамилия вроде `O'Brien` всё равно ломает запрос, склеенный из строк.

</Callout>

function escapeHtml(value) {
  return String(value)
    .replaceAll("&", "&amp;") // первым, иначе экранируем свои же &
    .replaceAll("<", "&lt;")
    .replaceAll(">", "&gt;")
    .replaceAll('"', "&quot;")
    .replaceAll("'", "&#39;");
}

  return `<li title="${escapeHtml(author)}">` +
    `<b>${escapeHtml(author)}</b>: ${escapeHtml(text)}</li>`;

  return value !== null && typeof value === "object" &&
    !Array.isArray(value);
}

const UNSAFE_KEYS = new Set(["__proto__", "constructor", "prototype"]);

function safeMerge(target, source) {
  for (const key of Object.keys(source)) {
    if (UNSAFE_KEYS.has(key)) {

      if (!isPlainObject(target[key])) target[key] = {};
      safeMerge(target[key], value);
    } else {
      target[key] = value;
    }
  }
  return target;
}

## Итоги

- **Моделирование угроз**: спросите себя, что вы защищаете, где входят недоверенные данные (каждая граница доверия) и во что обойдётся злоупотребление. Стройте защиту слоями (**эшелонированная защита**).
- **XSS** (хранимый, отражённый, DOM-based) — это строка, разобранная как HTML на вашей странице. Показывайте текст через `textContent`; оставьте `innerHTML` и `dangerouslySetInnerHTML` для доверенного или **санитизированного** HTML (DOMPurify).
- **Экранируйте с учётом контекста**: `& < > " '` для HTML (`&` первым); разбирайте URL и разрешайте в ссылках только схемы `http:`/`https:`. React экранирует `{значения}` за вас.
- **Content-Security-Policy** с nonce в роли страховочной сетки блокирует внедрённые и встроенные скрипты; включайте её сначала в режиме Report-Only.
- **SQL-внедрение**: всегда используйте параметризованные запросы (`$1`, `?`), в том числе в хелперах ORM для сырого SQL; для команд оболочки — массивы аргументов.
- **Внедрение операторов в NoSQL**: проверяйте **тип** каждого поля (`typeof password === "string"`), прежде чем оно попадёт в запрос.
- **Загрязнение прототипа**: отклоняйте `__proto__`/`constructor`/`prototype`, копируйте только собственные ключи, предпочитайте `Map`, `Object.create(null)` и `structuredClone`, проверяйте через `Object.hasOwn`.
- Никогда не применяйте `eval` к вводу и избегайте регулярных выражений с вложенными квантификаторами (**ReDoS**): ограничивайте длину ввода, проверяйте шаблоны линтером, для пользовательских шаблонов берите `re2`.
