The last two lessons were about bugs in **your** code. This one is about the space around it: what browsers do automatically on your users' behalf, the headers that switch on their built-in protections, the secrets your app depends on, and the thousands of npm packages you didn't write but ship anyway. Most of these fixes are a few lines each, and skipping any one of them has caused real breaches. 🧱

## CSRF: requests your users didn't mean to send

Browsers attach cookies **automatically** to every request to a site, no matter which page started it. **Cross-site request forgery** (CSRF) abuses that. Mei is logged in to her bank; she then visits a page on another site that contains:

```html
<!-- on https://cute-panda-pics.example -->
<form action="https://bank.example/transfer" method="POST">
  <input type="hidden" name="to" value="attacker">
  <input type="hidden" name="amount" value="500">
</form>
<script>document.forms[0].submit();</script>
```

Her browser posts the form to the bank **with her session cookie**, and the bank sees a perfectly valid, logged-in request. The attacker never sees the response (and doesn't need to): the money has moved. Note what CSRF is **not**: the attacker can't read Mei's cookie or the bank's pages. They can only make her browser **send** requests.

Defences, in layers:

- **`SameSite` cookies.** With `SameSite=Lax` (what you set in the [last lesson](/learn/javascript/authentication-and-sessions), and the default in Chrome when it's missing), the cookie isn't sent on cross-site `POST`s, so the form above arrives logged out. `SameSite=Strict` doesn't even send it when following a link from another site.
- **Never change data on `GET`.** `Lax` cookies **are** sent when the user follows a link or a top-level navigation, so `GET /transfer?to=attacker` must not do anything.
- **CSRF tokens** for anything important. `SameSite` works per **site**, and a compromised or user-controlled subdomain like `https://evil.pandadev.example` counts as the same *site* as `https://app.pandadev.example`. A token closes that gap and protects older browsers too.
- **Check `Origin` / `Sec-Fetch-Site`.** Modern browsers send `Sec-Fetch-Site: cross-site` on requests from other sites, and an `Origin` header on POSTs. Rejecting unsafe methods whose `Origin` isn't yours is a cheap extra layer.

### The synchroniser token pattern

The server stores a random **CSRF token** in the session and gives it to its own page (in the HTML or a JSON response). The page sends it back in a header with every state-changing request. The attacker's page can make the browser **send** cookies, but the same-origin policy stops it from **reading** your responses, so it can never learn the token:

<CodeExample output={`forged: 403 { error: 'Bad CSRF token' }
real: 200 { sent: 20 }`}>

```js
import express from "express";
import cookieParser from "cookie-parser";
import request from "supertest";

const sessions = new Map(); // sid -> { username, csrfToken }

function safeEqual(a, b) {
  if (typeof a !== "string" || a.length !== b.length) return false;
  let diff = 0;
  for (let i = 0; i < a.length; i++) {
    diff |= a.charCodeAt(i) ^ b.charCodeAt(i);
  }
  return diff === 0;
}

function requireCsrf(req, res, next) {
  if (["GET", "HEAD", "OPTIONS"].includes(req.method)) return next();
  const session = sessions.get(req.cookies.sid);
  const sent = req.get("X-CSRF-Token");
  if (!session || !safeEqual(sent, session.csrfToken)) {
    return res.status(403).json({ error: "Bad CSRF token" });
  }
  next();
}

const app = express();
app.use(express.json());
app.use(cookieParser());

app.post("/login", (req, res) => {
  const sid = crypto.randomUUID();
  const csrfToken = crypto.randomUUID();
  sessions.set(sid, { username: "mei", csrfToken });
  res.cookie("sid", sid, {
    httpOnly: true, secure: true, sameSite: "lax",
  });
  // Our own page reads this and sends it back in a header
  res.json({ csrfToken });
});

app.use(requireCsrf);
app.post("/transfer", (req, res) => {
  res.json({ sent: req.body.amount });
});

const browser = request.agent(app);
const { csrfToken } = (await browser.post("/login")).body;

// A forged form post: the cookie is sent, the token isn't known
const forged = await browser.post("/transfer").send({ amount: 500 });
console.log("forged:", forged.status, forged.body);

const real = await browser
  .post("/transfer")
  .set("X-CSRF-Token", csrfToken)
  .send({ amount: 20 });
console.log("real:", real.status, real.body);
```

</CodeExample>

In the browser, your front end keeps the token in memory (or reads it from a `<meta name="csrf-token">` tag) and adds it to every `fetch`: `headers: { "X-CSRF-Token": csrfToken }`. A variant without server-side state is the **signed double-submit cookie**: the token sits in a readable cookie and must be echoed in a header, and it's an HMAC of the session id so a subdomain can't plant its own. Libraries such as `csrf-csrf` implement it for Express; frameworks like Next.js Server Actions and SvelteKit check the `Origin` header for you.

<Callout type="tip" title="Bearer tokens and CSRF">

CSRF is a cookie problem. If your API only accepts an `Authorization: Bearer ...` header that your JavaScript adds explicitly, a forged form can't include it, so CSRF doesn't apply. The trade-off, as you saw in the last lesson, is that the token then lives somewhere JavaScript can read, which XSS can steal.

</Callout>

## CORS: who may read your responses

Browsers enforce the **same-origin policy**: JavaScript on one **origin** (scheme + host + port, e.g. `https://app.pandadev.example:443`) can **send** requests to another origin, but can't **read** the responses. That's what stops `cute-panda-pics.example` from fetching your users' bank statements with their cookies.

But sometimes you want another origin to read your API: your front end on `app.pandadev.example` calling `api.pandadev.example`. **CORS** (Cross-Origin Resource Sharing) is how the **server** tells the browser "this other origin may read my responses", using response headers:

| Header | Meaning |
| --- | --- |
| `Access-Control-Allow-Origin: https://app.pandadev.example` | this origin may read the response (one origin, or `*`) |
| `Access-Control-Allow-Credentials: true` | ...even when the request carried cookies |
| `Access-Control-Allow-Methods: GET, POST` | for preflights: methods allowed |
| `Access-Control-Allow-Headers: Content-Type` | for preflights: request headers allowed |
| `Access-Control-Max-Age: 600` | the browser may cache this preflight answer for 10 minutes |
| `Vary: Origin` | the answer depends on `Origin`, so caches must not mix them up |

**Preflights.** For "simple" requests (GET, or a POST of a plain form), the browser just sends the request and then decides whether the page may see the response. For anything else, like a `PUT`/`DELETE`, a JSON `Content-Type` or a custom header such as `X-CSRF-Token`, it first sends an automatic **`OPTIONS`** request with `Access-Control-Request-Method` and `Access-Control-Request-Headers`, asking permission. Only if the answer allows it does the real request follow.

Here's a small CORS middleware with an **allowlist** of origins:

<CodeExample output={`200 https://app.pandadev.example
200 (no CORS header)
204 https://app.pandadev.example
GET, POST`}>

```js
import express from "express";
import request from "supertest";

function cors({ origins }) {
  const allowed = new Set(origins);
  return (req, res, next) => {
    const origin = req.get("Origin");
    res.set("Vary", "Origin"); // answers differ per origin
    if (origin && allowed.has(origin)) {
      res.set("Access-Control-Allow-Origin", origin);
    }
    if (req.method === "OPTIONS") { // a preflight: answer it here
      res.set("Access-Control-Allow-Methods", "GET, POST");
      res.set("Access-Control-Allow-Headers", "Content-Type");
      return res.status(204).end();
    }
    next();
  };
}

const app = express();
app.use(cors({ origins: ["https://app.pandadev.example"] }));
app.get("/api/pandas", (req, res) => res.json(["Mei", "Po"]));

const show = (res) => console.log(res.status,
  res.headers["access-control-allow-origin"] ?? "(no CORS header)");

show(await request(app).get("/api/pandas")
  .set("Origin", "https://app.pandadev.example"));
show(await request(app).get("/api/pandas")
  .set("Origin", "https://evil.example"));

const preflight = await request(app)
  .options("/api/pandas")
  .set("Origin", "https://app.pandadev.example")
  .set("Access-Control-Request-Method", "POST")
  .set("Access-Control-Request-Headers", "Content-Type");
show(preflight);
console.log(preflight.headers["access-control-allow-methods"]);
```

</CodeExample>

Look closely at the second line: the request from `evil.example` still got **200** and the data. The server didn't block anything; it just didn't add the header, so a **browser** will refuse to hand the response to the evil page's JavaScript. That's the most important thing to understand about CORS:

- **CORS is not access control.** `curl`, scripts and other servers ignore it completely. Your API still needs authentication and authorisation.
- **CORS doesn't stop CSRF.** Simple requests (like the forged form) are **sent** anyway; CORS only controls reading the answer.
- **CORS relaxes** the same-origin policy. A misconfigured CORS setup makes you *less* safe than none at all.

The classic misconfiguration is **reflecting any `Origin`** together with `Access-Control-Allow-Credentials: true` ("it fixed the CORS error!"). Now every website can read your logged-in users' data. Browsers refuse `*` with credentials for exactly this reason, so people reflect the origin to get around it. Always compare against an **exact allowlist**: `origin.endsWith("pandadev.example")` also matches `evilpandadev.example`, and `includes` matches `pandadev.example.evil.com`.

In real projects, the `cors` package does this with the same allowlist idea:

```js
// npm install cors
import cors from "cors";

app.use(cors({
  origin: ["https://app.pandadev.example"],  // never true + credentials
  credentials: true,
  methods: ["GET", "POST", "DELETE"],
  allowedHeaders: ["Content-Type", "X-CSRF-Token"],
  maxAge: 600,
}));
```

And the simplest CORS setup is none: serve the front end and the API from the **same origin** (e.g. `/api` behind the same domain via your framework or reverse proxy), and you don't need CORS at all.

## Security headers

Browsers have powerful protections that are **off** until your server asks for them with a response header. These are the ones worth sending on every response:

| Header | Typical value | Protects against |
| --- | --- | --- |
| `Content-Security-Policy` | `default-src 'self'; frame-ancestors 'none'` | XSS (blocks injected scripts) and clickjacking |
| `X-Content-Type-Options` | `nosniff` | browsers "guessing" an upload is HTML or JS |
| `X-Frame-Options` | `DENY` | clickjacking in older browsers (CSP's `frame-ancestors` is the modern version) |
| `Referrer-Policy` | `strict-origin-when-cross-origin` | leaking full URLs (with tokens or ids) to other sites |
| `Strict-Transport-Security` | `max-age=31536000; includeSubDomains` | downgrade to HTTP on hostile Wi-Fi (HSTS) |

**Clickjacking** is when an attacker loads your site in an invisible `<iframe>` over their own page and tricks users into clicking your buttons; `frame-ancestors 'none'` forbids being framed at all. **HSTS** tells the browser "only ever use HTTPS for this domain, for a year", so even a typed `http://` link is upgraded before anything is sent. Only send it once HTTPS works everywhere on the domain, because browsers will remember it.

In Express, the `helmet` package sets sensible versions of all of these (and more) in one line, and you tune the CSP for your app:

```js
// npm install helmet
import helmet from "helmet";

app.use(helmet({
  contentSecurityPolicy: {
    directives: {
      "script-src": ["'self'", "https://js.stripe.com"],
      "frame-ancestors": ["'none'"],
    },
  },
}));
// helmet also removes the X-Powered-By: Express header
```

Many teams set these headers at the **edge** instead (Vercel or Netlify config, nginx, Cloudflare), so even static files get them. Free scanners such as Mozilla's HTTP Observatory grade a site's headers in seconds.

## Secrets: keep them out of code and bundles

API keys, database passwords and signing secrets give whoever holds them the power to act as your app. Three rules:

**1. Secrets live in the environment, not in code.** Read them in **one** place at startup, check them, and fail fast if anything is missing, rather than crashing on the first request at 3 a.m.:

<CodeExample output={`Missing settings: SESSION_SECRET, STRIPE_KEY
DATABASE_URL=postgres://localhost/pandas
SESSION_SECRET=[hidden]
STRIPE_KEY=[hidden]`}>

```js
const REQUIRED = ["DATABASE_URL", "SESSION_SECRET", "STRIPE_KEY"];
const SECRETS = new Set(["SESSION_SECRET", "STRIPE_KEY"]);

// Read and check settings ONCE at startup: fail fast and loudly
function loadConfig(env) {
  const missing = REQUIRED.filter((name) => !env[name]);
  if (missing.length > 0) {
    throw new Error(`Missing settings: ${missing.join(", ")}`);
  }
  if (env.SESSION_SECRET.length < 32) {
    throw new Error("SESSION_SECRET must be at least 32 characters");
  }
  return Object.freeze(Object.fromEntries(
    REQUIRED.map((name) => [name, env[name]])
  ));
}

// Safe to log: secret values are replaced
function redact(config) {
  return Object.fromEntries(Object.entries(config).map(
    ([name, value]) => [name, SECRETS.has(name) ? "[hidden]" : value]
  ));
}

try {
  loadConfig({ DATABASE_URL: "postgres://localhost/pandas" });
} catch (error) {
  console.log(error.message);
}

// In Node: loadConfig(process.env)
const config = loadConfig({
  DATABASE_URL: "postgres://localhost/pandas",
  SESSION_SECRET: "x".repeat(40),
  STRIPE_KEY: "sk_test_not_a_real_key",
});
for (const [name, value] of Object.entries(redact(config))) {
  console.log(`${name}=${value}`);
}
```

</CodeExample>

`loadConfig` takes `env` as a parameter, so tests pass a plain object and the real server passes `process.env`. Locally, keep values in a `.env` file that **never** goes into Git, and commit a `.env.example` with the names and fake values so teammates know what to set:

```bash
# .gitignore
.env
.env.*
!.env.example

# run with the file loaded (Node 20.6+)
node --env-file=.env server.js
```

In production, set the values in your host's settings (Vercel, Render, Fly.io) or a secret manager (AWS Secrets Manager, Doppler, 1Password), never in the repository or the Docker image.

**2. Anything in the client bundle is public.** Every line of JavaScript you send to the browser can be read by anyone with DevTools. Build tools inline certain environment variables into the bundle **on purpose**: `VITE_*` in Vite and `NEXT_PUBLIC_*` in Next.js. Those prefixes mean "this value is public":

```js
// ❌ Shipped to every visitor: anyone can copy the key
const res = await fetch("https://api.openweather.example/data", {
  headers: { "X-API-Key": import.meta.env.VITE_WEATHER_KEY },
});

// ✅ The browser calls YOUR server, which adds the key
const res2 = await fetch("/api/weather?city=London");
// server: fetch(upstream, { headers: { "X-API-Key":
//   process.env.WEATHER_KEY } })  // no prefix: server only
```

Public keys that are *designed* to be public (a Stripe **publishable** key, a Sentry DSN, a maps key restricted to your domain) are fine in the bundle. Secret keys never are.

**3. Assume leaks happen, and plan for them.** Bots scan every public GitHub push for keys and use them within **minutes**. If a secret is ever committed or pasted somewhere public:

- **Rotate it immediately**: create a new key, deploy it, then revoke the old one. Deleting the commit isn't enough: it lives on in history, forks, caches and the bots' copies.
- Check the provider's logs for what the leaked key was used for.
- Turn on **secret scanning**: GitHub's push protection blocks commits containing known key formats, and tools like `gitleaks` or `trufflehog` scan your history and run in CI or a pre-commit hook.
- Never log secrets (hence `redact`), and give each environment its **own** keys with the fewest permissions that work, so a leaked test key can't touch production.

## Supply-chain security

A typical Node project has **hundreds** of packages in `node_modules`, most of which you've never heard of, and every one can run code on your laptop, in CI and in production. Attackers know it:

- **Typosquatting**: publishing `crossenv` next to the real `cross-env` (a real 2017 attack that stole environment variables) or `reqeusts` next to `requests`.
- **Compromised maintainers**: in 2018 `event-stream` got a new "helpful" maintainer who added code to steal from bitcoin wallets; in 2025, phished maintainer accounts pushed malware into very popular packages such as `chalk` and `debug`, with hundreds of millions of weekly downloads.
- **Install scripts**: `preinstall`/`postinstall` scripts run automatically on `npm install`, before you've imported anything.

Habits that protect you:

```bash
# Commit package-lock.json, and install EXACTLY it in CI
npm ci

# Known vulnerabilities in your dependency tree
npm audit
npm audit --omit=dev     # only what ships to production

# Check package signatures and provenance from the registry
npm audit signatures

# Don't run install scripts unless a package really needs them
npm install --ignore-scripts
```

- **Lockfiles pin everything**, including dependencies of dependencies. Without `npm ci`, a fresh install can pull a brand-new (possibly malicious) patch version. `^1.2.3` in `package.json` is fine as long as the lockfile is committed and respected.
- **Think before adding a dependency**: is it maintained, widely used, spelled correctly? Does a 10-line function really need a package? Every dependency is code you trust with your secrets.
- **Automate updates** with Dependabot or Renovate, so security fixes arrive as small, reviewable pull requests instead of a terrifying yearly upgrade:

```yaml
# .github/dependabot.yml
version: 2
updates:
  - package-ecosystem: "npm"
    directory: "/"
    schedule:
      interval: "weekly"
    groups:
      minor-and-patch:
        update-types: ["minor", "patch"]
```

pnpm (version 10 and later) goes a step further and doesn't run dependencies' install scripts at all unless you allow them by name, which blocks a whole class of attacks.

<Callout type="warning" title="A war story worth remembering">

A team "fixed" a CORS error in staging by reflecting whatever `Origin` arrived, with `credentials: true`, and the setting shipped to production. Any website a logged-in customer visited could now call the API with their cookies **and read the answers**: names, addresses, orders. The fix was one line, an exact allowlist. When a security setting "just makes the error go away", stop and find out what it actually allows.

</Callout>

2. **`cors({ allowedOrigins })`** returns a middleware that:
   - always sets `Vary: Origin`;
   - if the request's `Origin` is **exactly** one of `allowedOrigins`, sets `Access-Control-Allow-Origin` to that origin (never `*`) and `Access-Control-Allow-Credentials: true`;
   - answers **preflights** (`OPTIONS`) itself: for an allowed origin, **204** with `Access-Control-Allow-Methods: GET, POST, DELETE`, `Access-Control-Allow-Headers: Content-Type, X-CSRF-Token` and `Access-Control-Max-Age: 600`; for any other origin, **403** with no CORS headers;
   - lets every other request continue with `next()`, even from unknown origins (the browser enforces CORS; your routes still need auth).

The checks try several allowed origins and some sneaky look-alikes like `https://notes.pandadev.example.evil.com` and `http://notes.pandadev.example`.

<Hint>

Build a `Set` from `allowedOrigins` once, outside the returned function, and use `set.has(origin)`: that's an exact match, unlike `includes` on a string or `endsWith`. Inside, read `req.get("Origin")`, set `Vary` first, then the two allow headers if allowed. For `OPTIONS`, `return res.status(403).end()` or set the three preflight headers and `return res.status(204).end()`. A preflight never reaches your routes.

</Hint>

<Solution>

```js
import express from "express";
import request from "supertest";

const HEADERS = {
  "Content-Security-Policy":
    "default-src 'self'; frame-ancestors 'none'; object-src 'none'",
  "X-Content-Type-Options": "nosniff",
  "X-Frame-Options": "DENY",
  "Referrer-Policy": "strict-origin-when-cross-origin",
  "Strict-Transport-Security": "max-age=31536000; includeSubDomains",
};

function securityHeaders() {
  return (req, res, next) => {
    res.set(HEADERS);
    next();
  };
}

function cors({ allowedOrigins }) {
  const allowed = new Set(allowedOrigins);
  return (req, res, next) => {
    const origin = req.get("Origin");
    const isAllowed = origin !== undefined && allowed.has(origin);
    res.set("Vary", "Origin");
    if (isAllowed) {
      res.set("Access-Control-Allow-Origin", origin);
      res.set("Access-Control-Allow-Credentials", "true");
    }
    if (req.method === "OPTIONS") {
      if (!isAllowed) return res.status(403).end();
      res.set({
        "Access-Control-Allow-Methods": "GET, POST, DELETE",
        "Access-Control-Allow-Headers": "Content-Type, X-CSRF-Token",
        "Access-Control-Max-Age": "600",
      });
      return res.status(204).end();
    }
    next();
  };
}

function createApp({ allowedOrigins }) {
  const notes = ["Buy bamboo"];
  const app = express();
  app.use(securityHeaders());
  app.use(cors({ allowedOrigins }));
  app.use(express.json());

  app.get("/api/notes", (req, res) => res.json(notes));
  app.post("/api/notes", (req, res) => {
    notes.push(String(req.body.text));
    res.status(201).json(notes);
  });
  app.use((req, res) => {
    res.status(404).json({ error: "Not found" });
  });
  return app;
}

const app = createApp({
  allowedOrigins: ["https://notes.pandadev.example"],
});
const res = await request(app)
  .get("/api/notes")
  .set("Origin", "https://notes.pandadev.example");
console.log(res.status, res.body);
console.log(res.headers["access-control-allow-origin"]);
console.log(res.headers["x-content-type-options"]);
```

## Recap

- **CSRF** makes a victim's browser send requests with their cookies. Defend with `SameSite=Lax`/`Strict` cookies, no side effects on `GET`, **CSRF tokens** (synchroniser or signed double-submit) for state-changing requests, and `Origin` / `Sec-Fetch-Site` checks.
- The **same-origin policy** stops pages reading other origins' responses; **CORS** lets your server relax it for an **exact allowlist** of origins. Answer **preflight** `OPTIONS` requests, send `Vary: Origin`, and never reflect any origin with credentials.
- CORS is **not** access control and doesn't stop CSRF: servers still answer, and non-browser clients ignore it.
- **Security headers** switch on browser protections: CSP, `X-Content-Type-Options: nosniff`, `frame-ancestors`/`X-Frame-Options`, `Referrer-Policy`, HSTS. `helmet` sets them in Express.
- **Secrets** live in the environment, are validated once at startup (`loadConfig(process.env)`), and never appear in Git, logs or the client bundle (`VITE_`/`NEXT_PUBLIC_` mean public). Leaked? **Rotate** immediately, and turn on secret scanning.
- **Supply chain**: commit the lockfile and use `npm ci`, run `npm audit`, be careful with install scripts and typosquats, and let Dependabot or Renovate keep dependencies fresh.
