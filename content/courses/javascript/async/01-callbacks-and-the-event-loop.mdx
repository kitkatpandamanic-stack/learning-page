Until now, your code mostly ran from top to bottom, and each line finished before the next one started. Real applications spend a lot of their time **waiting**: for a server to answer, a timer to finish or a user to click. In this module you'll learn how JavaScript waits without freezing, starting with the oldest tool for the job: **callbacks**. Then come promises and `async`/`await`, which is how most modern code is written. ⏳

## Why code has to wait

Some operations are fast: adding numbers or changing a string takes a few nanoseconds. Others are slow, because they depend on something outside your program:

- **network requests**: asking a server for data can take anything from 20 milliseconds to several seconds;
- **timers**: "show this message in 3 seconds";
- **files and databases** (in Node.js);
- **people**: a click or a key press might come now, later or never.

JavaScript runs your code on a **single thread**: it can only do one thing at a time. If it stood still while waiting for a server, the whole page would freeze, so buttons wouldn't react and nothing would scroll. Instead, JavaScript says *"call me back when it's ready"* and carries on with other work. Code that runs later like this is called **asynchronous** (async for short).

The simplest way to see it is `setTimeout(callback, ms)`, which runs a function after a delay in milliseconds:

<CodeExample output={`Ordering a pizza...
Watching TV while we wait
🍕 Pizza delivered!`}>

```js
console.log("Ordering a pizza...");

setTimeout(() => {
  console.log("🍕 Pizza delivered!");
}, 100);

console.log("Watching TV while we wait");
```

</CodeExample>

`setTimeout` doesn't wait. It **schedules** the function and returns immediately, so the last line runs first. 100 milliseconds later, the pizza arrives.

## Callbacks

A **callback** is a function you pass to another function, so that it can call it later. You've used them before: the functions you give to `map` and `forEach` are callbacks that run straight away, and the ones you give to `addEventListener` run whenever the event happens.

Here's a pretend server that "loads" a user after 100 ms. Because the answer isn't ready when `loadUser` returns, the caller passes in a callback to receive it:

<CodeExample output={`Loading...
Hello, Mei!`}>

```js
const users = { 1: "Mei", 2: "Sam" };

// Pretend server: answers after 100 ms
function loadUser(id, callback) {
  setTimeout(() => {
    callback(users[id]);
  }, 100);
}

loadUser(1, (name) => {
  console.log(`Hello, ${name}!`);
});
console.log("Loading...");
```

</CodeExample>

Why not simply `return` the name? Because when the function returns, the timer hasn't fired yet, so there's nothing to return:

<CodeExample output="undefined">

```js
const users = { 1: "Mei", 2: "Sam" };

function loadUserName(id) {
  let name;
  setTimeout(() => {
    name = users[id]; // runs 100 ms later...
  }, 100);
  return name; // ...but this runs right now
}

console.log(loadUserName(1));
```

</CodeExample>

This is the number one beginner mistake with async code. A value that arrives later can only be used **inside** the code that runs later.

### Error-first callbacks

What if loading fails? Node.js made a convention popular: the callback's **first** argument is an error (or `null` if all went well), and the result comes second. That's why they're called **error-first callbacks**:

<CodeExample output={`Found: Sam
Failed: No user with id 7`}>

```js
const users = { 1: "Mei", 2: "Sam" };

function loadUser(id, callback) {
  setTimeout(() => {
    if (users[id]) {
      callback(null, users[id]);
    } else {
      callback(new Error(`No user with id ${id}`));
    }
  }, 100);
}

function show(error, name) {
  if (error) {
    console.log("Failed:", error.message);
    return;
  }
  console.log("Found:", name);
}

loadUser(2, show);
loadUser(7, show);
```

</CodeExample>

You'll still meet this style in older Node.js code and libraries, like `fs.readFile(path, (error, data) => { ... })`.

## Timers

Timers fire in order of **time**, not in the order you wrote them. A delay of `0` doesn't mean "now", it means "as soon as possible, after the current code":

<CodeExample output={`Start
A (0 ms)
B (30 ms)
C (60 ms)`}>

```js
setTimeout(() => console.log("C (60 ms)"), 60);
setTimeout(() => console.log("A (0 ms)"), 0);
setTimeout(() => console.log("B (30 ms)"), 30);
console.log("Start");
```

</CodeExample>

`setTimeout` returns an id that you can pass to `clearTimeout` to cancel the timer. Its sibling `setInterval` calls the callback again and again, every `ms` milliseconds, until you stop it with `clearInterval`:

<CodeExample output={`3
2
1
Go!`}>

```js
const reminder = setTimeout(() => {
  console.log("You never see this");
}, 100);
clearTimeout(reminder); // cancelled

let count = 3;
const id = setInterval(() => {
  console.log(count);
  count--;
  if (count === 0) {
    clearInterval(id);
    console.log("Go!");
  }
}, 50);
```

</CodeExample>

<Callout type="tip" title="The delay is a minimum">

`setTimeout(fn, 100)` means "not before 100 ms". If JavaScript is busy when the time is up, the callback has to wait until it's free. That's why timers are fine for "show this soon", but no good for precise timing. To measure how long something took, compare `Date.now()` or `performance.now()` before and after.

</Callout>

## The event loop

So who keeps track of all these callbacks? Several parts work together:

- The **call stack** is the code that's running right now. JavaScript runs it to the end without interruption.
- The **browser** (or Node.js) keeps track of everything that's waiting: timers, network requests, event listeners. Your JavaScript isn't busy while that happens.
- When a timer finishes or a click happens, its callback goes into the **task queue**, a line of callbacks waiting for their turn.
- The **event loop** is a simple loop: *when the call stack is empty, take the next task from the queue and run it.* Then repeat, forever.

```text
   your code          waiting               ready to run
 ┌────────────┐   ┌──────────────┐   ┌───────────────────────┐
 │ call stack │ → │ timers, HTTP │ → │ task queue: cb1, cb2  │
 └────────────┘   │ clicks, ...  │   └───────────┬───────────┘
       ↑          └──────────────┘               │
       └──── event loop: stack empty? run next ──┘
```

This explains why a `0` ms timer still waits for **all** of the current code to finish, however long it takes:

<CodeExample output={`Loop finished: 12499997500000
Timer: finally my turn`}>

```js
setTimeout(() => console.log("Timer: finally my turn"), 0);

let total = 0;
for (let i = 0; i < 5_000_000; i++) {
  total += i;
}
console.log("Loop finished:", total);
```

</CodeExample>

### Microtasks jump the queue

There's one more queue. Promise callbacks (which you'll meet in the next lesson) and `queueMicrotask` go into the **microtask queue**. After each piece of code finishes, the event loop runs **all** waiting microtasks before it picks up the next task. So promise callbacks always run before timers that are already waiting:

<CodeExample output={`1. script start
2. script end
3. promise (microtask)
4. queueMicrotask (microtask)
5. timeout (task)`}>

```js
console.log("1. script start");

setTimeout(() => console.log("5. timeout (task)"), 0);

Promise.resolve().then(() => {
  console.log("3. promise (microtask)");
});
queueMicrotask(() => console.log("4. queueMicrotask (microtask)"));

console.log("2. script end");
```

</CodeExample>

Step by step:

| Step | What runs                         | Why                                         |
| ---- | --------------------------------- | ------------------------------------------- |
| 1    | `1. script start`, `2. script end` | Synchronous code always finishes first      |
| 2    | `3. promise`, `4. queueMicrotask` | The stack is empty: all microtasks run next |
| 3    | `5. timeout`                      | Only then does the event loop take a task   |

<Callout type="warning" title="Don't block the event loop">

While your code runs, nothing else can: no clicks, no timers, no screen updates. A loop that takes 3 seconds freezes the page for 3 seconds. Keep each piece of work short. Really heavy work (image processing, huge calculations) belongs in a **Web Worker**, a separate thread. PandaDev runs your lesson code in one, so an endless loop here doesn't freeze the site.

</Callout>

## Callback hell

Callbacks work, but real tasks often need several steps, each needing the result of the one before. Load a user, then their posts, then the likes of the first post. With callbacks, each step goes **inside** the previous one:

<CodeExample output={`Mei's "Bamboo" has 42 likes`}>

```js
// Pretend server functions, each answering after 50 ms
function getUser(id, callback) {
  setTimeout(() => callback(null, { id, name: "Mei" }), 50);
}
function getPosts(user, callback) {
  setTimeout(() => callback(null, ["Bamboo", "Naps"]), 50);
}
function getLikes(post, callback) {
  setTimeout(() => callback(null, 42), 50);
}

getUser(1, (error, user) => {
  if (error) return console.log(error.message);
  getPosts(user, (error, posts) => {
    if (error) return console.log(error.message);
    getLikes(posts[0], (error, likes) => {
      if (error) return console.log(error.message);
      console.log(`${user.name}'s "${posts[0]}" has ${likes} likes`);
    });
  });
});
```

</CodeExample>

Developers call this shape **callback hell** or the *pyramid of doom*. Every extra step pushes the code further right, and the problems pile up:

- **Errors are checked by hand at every level**, and a `try/catch` around the whole thing doesn't help, because the callbacks run later (you saw this in [Handling Errors with try/catch](/learn/javascript/try-catch)).
- **Combining tasks is awkward.** "Load these three things at the same time and continue when all are done" needs counters and flags.
- **You hand over control.** You trust `getUser` to call your callback exactly once. A buggy library might call it twice, or never.

Promises fix all three, and they're the topic of the [next lesson](/learn/javascript/promises).

Write `countdown(from, onTick, onDone)` for a rocket launch screen. It takes a number and **two callbacks**:

1. Every **20 ms**, call `onTick` with the next number: first `from`, then `from - 1`, and so on down to `1`.
2. After the tick for `1`, stop the timer and call `onDone()` once.

`countdown` itself must return straight away, so the program prints `Countdown started` before the first number.

<Hint>

`setInterval(callback, 20)` gives you a tick every 20 ms. Keep the current number in a variable outside the callback. Inside the callback: if the number has reached `0`, call `clearInterval(id)` and `onDone()`; otherwise call `onTick` with the number and then lower it by one.

</Hint>

<Solution>

```js
function countdown(from, onTick, onDone) {
  let current = from;
  const id = setInterval(() => {
    if (current === 0) {
      clearInterval(id);
      onDone();
      return;
    }
    onTick(current);
    current--;
  }, 20);
}

countdown(
  3,
  (n) => console.log(n),
  () => console.log("Lift off! 🚀"),
);
console.log("Countdown started");
```

</Solution>

</Exercise>

## Recap

- Slow work (network, timers, files, people) is handled **asynchronously**: JavaScript schedules it and carries on instead of freezing.
- A **callback** is a function passed to another function to be called later. A value that arrives later can only be used inside that callback, not `return`ed.
- **Error-first callbacks** receive `(error, result)`; check the error before using the result.
- `setTimeout`/`clearTimeout` run code once after a delay, `setInterval`/`clearInterval` repeat it. A delay is a minimum, not a promise of exact timing.
- The **event loop** runs the next task only when the call stack is empty. **Microtasks** (promise callbacks) run before the next task.
- Nested callbacks lead to **callback hell**: deep nesting, repeated error checks and hard-to-combine tasks. Promises are the cure.
