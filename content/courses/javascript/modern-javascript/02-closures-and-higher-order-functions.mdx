In JavaScript, a function is a **value**, just like a number or an array. You can store it in a variable, pass it to another function and even return it from a function. Combine that with **closures** (functions that remember where they were born) and you get some of the most powerful patterns in the language: private data, caching, and the debounce trick that keeps a search box from flooding a server. 🔒

You've already used these ideas without naming them: every `map`, `filter` and `addEventListener` call takes a function as an argument. In this lesson you'll learn to write such tools yourself.

## Functions are values

A function can live in a variable or an object property, and you can hand it to another function to call later:

<CodeExample output={`HELLO!
panda time...
function`}>

```js
const shout = (text) => text.toUpperCase() + "!";
const whisper = (text) => text.toLowerCase() + "...";

const voices = { shout, whisper };
console.log(voices.shout("hello"));

function speak(text, voice) {
  return voice(text);
}

console.log(speak("Panda time", whisper));
console.log(typeof shout);
```

</CodeExample>

Notice `speak("Panda time", whisper)` passes `whisper` **without** brackets. `whisper` is the function itself; `whisper("Hi")` would call it right away and pass its *result* instead. Mixing those two up is one of the most common beginner bugs, like `button.addEventListener("click", save())`, which runs `save` immediately instead of on click.

## Higher-order functions

A function that **takes** a function as an argument, or **returns** one, is called a **higher-order function**. `map` and `filter` are higher-order functions, and there's no magic in them. Here's how you could write them yourself:

<CodeExample output={`[ 10, 24, 60 ]
[ 12, 30 ]`}>

```js
function myMap(array, transform) {
  const result = [];
  for (const item of array) {
    result.push(transform(item));
  }
  return result;
}

function myFilter(array, keep) {
  const result = [];
  for (const item of array) {
    if (keep(item)) result.push(item);
  }
  return result;
}

const prices = [5, 12, 30];
console.log(myMap(prices, (p) => p * 2));
console.log(myFilter(prices, (p) => p > 10));
```

</CodeExample>

The loop is written **once**, and the part that changes (*what* to do with each item) is passed in as a function. That's the whole point of higher-order functions: they separate the boring repeated machinery from the interesting bit.

## Functions that return functions

A function can also **build** and return a new function. Here `multiplyBy` is a little function factory:

<CodeExample output={`10
15
[ 3, 6, 9 ]
40`}>

```js
function multiplyBy(factor) {
  return (n) => n * factor;
}

const double = multiplyBy(2);
const triple = multiplyBy(3);

console.log(double(5));
console.log(triple(5));
console.log([1, 2, 3].map(triple));
console.log(multiplyBy(10)(4));
```

</CodeExample>

`multiplyBy(2)` returns the arrow function `(n) => n * factor`. But wait: by the time we call `double(5)`, `multiplyBy` has already finished. How does the returned function still know that `factor` is `2`?

## Closures

When a function is created, it keeps a link to the variables around it. Even after the outer function returns, the inner function can still read **and change** those variables. A function together with the variables it remembers is called a **closure**.

That makes closures perfect for state that should survive between calls:

<CodeExample output={`1
2
3
1
4`}>

```js
function makeCounter() {
  let count = 0;
  return () => {
    count += 1;
    return count;
  };
}

const clicks = makeCounter();
console.log(clicks());
console.log(clicks());
console.log(clicks());

const likes = makeCounter(); // a brand-new count
console.log(likes());
console.log(clicks());
```

</CodeExample>

Each call to `makeCounter()` creates a **new** `count` variable and a new function that remembers it. So `clicks` and `likes` each have their own count, and they never interfere.

<Callout type="note" title="A closure remembers variables, not values">

The inner function doesn't take a snapshot of `count` when it's created. It holds on to the **variable itself**, so it always sees the latest value, and changes it makes are kept for next time. That's why `clicks()` keeps counting up.

</Callout>

## Private state

Nobody outside `makeCounter` can reach `count` directly: the only way to touch it is through the function you returned. That makes closures a simple way to keep data **private**. Return an object of functions and you have a small module with a controlled public interface:

<CodeExample output={`12
undefined
Not enough money`}>

```js
function createWallet(start = 0) {
  let balance = start; // private: only these functions see it

  return {
    deposit(amount) {
      if (amount <= 0) throw new Error("Amount must be positive");
      balance += amount;
    },
    spend(amount) {
      if (amount > balance) throw new Error("Not enough money");
      balance -= amount;
    },
    getBalance() {
      return balance;
    },
  };
}

const wallet = createWallet(10);
wallet.deposit(5);
wallet.spend(3);
console.log(wallet.getBalance());
console.log(wallet.balance); // not reachable from outside

try {
  wallet.spend(100);
} catch (error) {
  console.log(error.message);
}
```

</CodeExample>

The only way to change `balance` is through `deposit` and `spend`, which check the rules first. Nobody can write `wallet.balance = 1000000`. This does the same job as the `#private` class fields you met in Level 1, and you'll see both styles in real code.

## Useful wrappers: once and memoize

Higher-order functions really shine as **wrappers**: you give them a function and get back an improved version of it. Two classics are `once`, which makes sure a function only ever runs one time, and `memoize`, which remembers results so slow work isn't repeated.

`once` is handy for set-up code that must not run twice, like connecting to a database or showing a welcome tour:

<CodeExample output={`Setting up for Mei...
Ready, Mei!
Ready, Mei!`}>

```js
function once(fn) {
  let called = false;
  let result;
  return (...args) => {
    if (!called) {
      called = true;
      result = fn(...args);
    }
    return result;
  };
}

const setUp = once((name) => {
  console.log(`Setting up for ${name}...`);
  return `Ready, ${name}!`;
});

console.log(setUp("Mei"));
console.log(setUp("Sam")); // fn doesn't run again
```

</CodeExample>

The wrapper uses rest (`...args`) to accept any arguments and spread (`fn(...args)`) to pass them on, so it works for **any** function.

**Memoizing** means caching a function's results by argument. The cache lives in a closure, so it survives between calls but stays hidden:

<CodeExample output={`Working hard on 9...
81
(from cache: 9)
81
Working hard on 4...
16`}>

```js
function memoize(fn) {
  const cache = {};
  return (n) => {
    if (n in cache) {
      console.log(`(from cache: ${n})`);
      return cache[n];
    }
    const result = fn(n);
    cache[n] = result;
    return result;
  };
}

function slowSquare(n) {
  console.log(`Working hard on ${n}...`);
  return n * n;
}

const fastSquare = memoize(slowSquare);
console.log(fastSquare(9));
console.log(fastSquare(9));
console.log(fastSquare(4));
```

</CodeExample>

Memoizing only makes sense for **pure** functions: ones that always return the same result for the same input and don't change anything else. Memoizing "get the current time" or "fetch the latest messages" would give you stale answers. (In the next lesson you'll meet `Map`, which makes an even better cache than a plain object.)

## The debounce idea

Imagine a search box that asks a server for results on every key press. Typing "panda" would send five requests, and only the last one matters. **Debouncing** waits until the calls *stop* for a moment, then runs the function once with the latest arguments:

<CodeExample output={`Made 4 calls
Searching for "panda"`}>

```js
function debounce(fn, ms) {
  let timer;
  return (...args) => {
    clearTimeout(timer); // cancel the previous wait
    timer = setTimeout(() => fn(...args), ms);
  };
}

const search = debounce((text) => {
  console.log(`Searching for "${text}"`);
}, 200);

// Someone types quickly: p, pa, pan, panda
search("p");
search("pa");
search("pan");
search("panda");
console.log("Made 4 calls");
```

</CodeExample>

The `timer` variable lives in the closure, shared by every call. Each call cancels the previous timer and starts a new one, so only the last call survives the 200 ms wait. On a real page you'd write `input.addEventListener("input", debounce(runSearch, 300))`. In real projects people often import a ready-made, well-tested `debounce` from a library such as Lodash, but now you know there's no magic inside.

## The classic loop bug with var

Closures explain one of JavaScript's most famous puzzles. Old code uses `var` instead of `let`, and `var` is **not** block-scoped: the whole loop shares one single `i`. Here the timers run after the loops have finished:

<CodeExample output={`var: 4
var: 4
var: 4
let: 1
let: 2
let: 3`}>

```js
for (var i = 1; i <= 3; i++) {
  setTimeout(() => console.log(`var: ${i}`), 10);
}

for (let j = 1; j <= 3; j++) {
  setTimeout(() => console.log(`let: ${j}`), 20);
}
```

</CodeExample>

All three `var` callbacks close over the **same** `i`, and by the time they run, the loop has pushed it up to `4`. With `let`, every turn of the loop gets a **fresh** `j`, so each callback remembers its own value.

<Callout type="warning" title="Use let and const, never var">

`var` is still valid JavaScript, which is why you'll meet it in old tutorials and Stack Overflow answers. But it leaks out of blocks and causes bugs like this one. In your own code, use `const` by default and `let` when a variable must change. Linters such as ESLint can flag every `var` for you (the `no-var` rule).

</Callout>

Build a small toolkit of closure-powered helpers:

1. `createCounter(start = 0, step = 1)` returns an object with three methods. `next()` adds `step` to the count and returns the new count, `reset()` puts the count back to `start` and returns it, and `value()` returns the current count. The count stays private (the object has only these methods).
2. `once(fn)` returns a function that calls `fn` with its arguments the **first** time it's called, and returns that first result every time after, without calling `fn` again.
3. `memoize(fn)` takes a one-argument function and returns a version that remembers results, so `fn` runs only once for each different argument. Each memoized function needs its **own** cache.

Right now `once` and `memoize` just hand back `fn` unchanged, so it runs on every call.

<Hint>

1. The methods can read and change `count` because they close over it: `count += step; return count;`.
2. Keep `let called = false;` and `let result;` inside `once`, and return `(...args) => { ... }` that only calls `fn(...args)` while `called` is `false`.
3. Create `const cache = {};` **inside** `memoize` (not outside it, or all memoized functions would share it). Check `arg in cache` before calling `fn`.

</Hint>

<Solution>

```js
function createCounter(start = 0, step = 1) {
  let count = start; // private: only the methods below see it
  return {
    next() {
      count += step;
      return count;
    },
    reset() {
      count = start;
      return count;
    },
    value() {
      return count;
    },
  };
}

function once(fn) {
  let called = false;
  let result;
  return (...args) => {
    if (!called) {
      called = true;
      result = fn(...args);
    }
    return result;
  };
}

function memoize(fn) {
  const cache = {};
  return (arg) => {
    if (!(arg in cache)) {
      cache[arg] = fn(arg);
    }
    return cache[arg];
  };
}

const tickets = createCounter(100, 10);
console.log(tickets.next());  // 110
console.log(tickets.next());  // 120
console.log(tickets.reset()); // 100

const greet = once((name) => `Welcome, ${name}!`);
console.log(greet("Mei")); // Welcome, Mei!
console.log(greet("Sam")); // Welcome, Mei!

const square = memoize((n) => {
  console.log(`Calculating ${n}...`);
  return n * n;
});
console.log(square(7)); // Calculating 7... then 49
console.log(square(7)); // 49 (no calculating)
```

</Solution>

## Recap

- Functions are **values**: store them, pass them (`speak(text, whisper)`, no brackets) and return them.
- A **higher-order function** takes or returns a function. `map` and `filter` are just loops with the changing part passed in.
- A **closure** is a function plus the variables it remembers from where it was created. It keeps the variables themselves, so it sees and keeps changes.
- Closures give you **private state**: `makeCounter` and `createWallet` hide their data behind the functions they return.
- Wrappers like `once`, `memoize` and `debounce` take a function and return an improved one; `(...args) => fn(...args)` passes any arguments through.
- `var` shares one variable across a whole loop, which breaks closures. Use `let` and `const`.
