Однажды команда две недели меняла библиотеку для работы с датами на «более быструю», потому что дашборд казался медленным. После замены дашборд тормозил ровно так же. Когда кто-то наконец записал профиль, виновник нашёлся за десять минут: `.find()` внутри `.map()`, который сравнивал каждый заказ с каждым клиентом — 400 миллионов раз. Первое правило работы с производительностью короткое: **измеряйте, а не гадайте**. 🔍

Этот модуль о том, как сделать JavaScript быстрым — в браузере и на сервере. Начнём с самого важного навыка: выяснять, **куда** на самом деле уходит время и **какие** цифры важны вашим пользователям.

## Измеряйте, а не гадайте

Интуиция о том, что тормозит, обычно ошибается — и ваша, и чужая. Большую часть времени программа проводит в нескольких **горячих точках (hot spots)**, и часто там, где их никто не ждёт. Поэтому работа над производительностью (performance) всегда идёт по одному и тому же циклу:

1. **Выберите важную цифру**: «результаты поиска появляются не позже 200 мс после ввода», а не «сделайте быстрее».
2. **Воспроизведите** медленный случай на реалистичных данных и реалистичном устройстве (ваш ноутбук — не телефон ваших пользователей).
3. **Измерьте**, чтобы получить исходную цифру (baseline).
4. **Профилируйте** (profiling), чтобы найти горячую точку.
5. **Исправьте** только эту горячую точку, а потом **измерьте ещё раз**, чтобы доказать, что стало лучше, и запустите тесты, чтобы доказать, что всё по-прежнему работает.

Шаг 5 важнее, чем кажется. Многие «оптимизации» делают код менее читаемым и ничуть не быстрее, потому что движок и так уже делал что-то хитрое. Если вы не можете показать цифры «до» и «после», это не оптимизация, а догадка.

## Замеряем время с performance.now

Время можно замерять через `Date.now()`, но у него две проблемы: он считает только целые миллисекунды и следует за системными часами, которые могут прыгнуть, когда компьютер синхронизирует время. **`performance.now()`** создан именно для замеров: он возвращает дробное число миллисекунд (например, `1234.5678`) с момента запуска страницы или воркера и всегда идёт только вперёд.

Запустите это несколько раз и посмотрите, как меняются цифры:

<TryIt code={`function timeIt(label, fn) {
  const start = performance.now();
  const result = fn();
  const ms = performance.now() - start;
  console.log(\`\${label}: \${ms.toFixed(3)} мс\`);
  return result;
}

const numbers = Array.from({ length: 200_000 }, (_, i) => i);

timeIt("цикл for", () => {
  let total = 0;
  for (let i = 0; i < numbers.length; i++) total += numbers[i];
  return total;
});

timeIt("reduce", () => numbers.reduce((a, b) => a + b, 0));

timeIt("сортировка копии", () => [...numbers].sort((a, b) => b - a));`}
/>

Цифры скачут от запуска к запуску, и первый запуск часто самый медленный. Запомните это — мы ещё вернёмся к тому, почему так.

<Callout type="note" title="Почему цифры выглядят округлёнными">

Браузеры специально делают `performance.now()` чуть менее точным (до 5 или 100 микросекунд, в зависимости от настроек безопасности страницы), потому что сверхточные таймеры можно использовать для атак вроде Spectre, которые читают память через замеры времени. Для замеров вашего кода этого более чем достаточно: всё, что стоит оптимизировать, длится гораздо дольше.

</Callout>

### performance.mark и performance.measure

Для замера шагов в реальном приложении **User Timing API** удобнее, чем вычитать числа вручную. `performance.mark(name)` ставит именованную метку времени, а `performance.measure(name, startMark, endMark)` записывает время между двумя метками:

<CodeExample output={`parse measure
строк: 10000
есть длительность: true`}>

```js
const json = JSON.stringify(
  Array.from({ length: 10_000 }, (_, i) => ({ id: i, ok: true })),
);

performance.mark("parse:start");
const rows = JSON.parse(json);
performance.mark("parse:end");

performance.measure("parse", "parse:start", "parse:end");

const [entry] = performance.getEntriesByName("parse");
console.log(entry.name, entry.entryType);
console.log("строк:", rows.length);
console.log("есть длительность:", entry.duration >= 0);
```

</CodeExample>

Главный плюс: метки и замеры появляются в **панели Performance в DevTools** браузера, на дорожке «Timings» прямо над флейм-графиком. Так вы видите свои именованные шаги («parse», «render list», «save draft») рядом со всем, что делал браузер. Инструменты мониторинга умеют собирать их и у реальных пользователей — вы увидите это в конце урока. (То же API есть в Node.js: через `performance` из `node:perf_hooks` или глобальный объект.)

## Ловушки микробенчмарков

**Микробенчмарк (micro-benchmark)** замеряет один крошечный кусочек кода, например «что быстрее, `for` или `forEach`?». Они полезны, но легко врут. Три классические ловушки:

- **Прогрев JIT (JIT warm-up).** Как вы видели в уроке [Как движки выполняют код](/learn/javascript/how-engines-run-code), движки JavaScript сначала интерпретируют код, следят, какие функции запускаются часто («горячие» функции), и затем компилируют их в быстрый машинный код. Первые несколько сотен вызовов могут быть во много раз медленнее последующих. Если замерить только холодный старт, вы замерите интерпретатор, а не свой код.
- **Удаление мёртвого кода (dead-code elimination).** Если результат нигде не используется, оптимизирующий компилятор может вообще пропустить работу, и бенчмарк гордо сообщит, что сортировка миллиона чисел занимает 0,001 мс. Всегда **используйте** результат (например, прибавляйте его к переменной, которую выводите в конце).
- **Шум (noise).** Другие вкладки, сборщик мусора, энергосбережение процессора и троттлинг из-за нагрева замедляют случайные запуски. Никогда не доверяйте одному замеру: запускайте много раз и смотрите на **медиану**, а не на среднее (один медленный запуск сильно сдвигает среднее).

Вот маленький помощник для бенчмарков, который учитывает все три ловушки. Запустите его и сравните поиск через `Array.includes` с поиском через `Set.has`:

<TryIt code={`function bench(label, fn, { runs = 15, iterations = 200 } = {}) {
  let sink = 0; // используем каждый результат, чтобы ничего не выкинули
  for (let i = 0; i < iterations; i++) sink += fn(i); // прогрев

  const perCall = [];
  for (let r = 0; r < runs; r++) {
    const start = performance.now();
    for (let i = 0; i < iterations; i++) sink += fn(i);
    perCall.push((performance.now() - start) / iterations);
  }
  perCall.sort((a, b) => a - b);
  const median = perCall[Math.floor(runs / 2)];
  console.log(\`\${label}: \${(median * 1000).toFixed(2)} мкс на вызов\`);
  return sink;
}

const ids = Array.from({ length: 10_000 }, (_, i) => i * 2);
const idSet = new Set(ids);

const last = 19_998; // ближе к концу массива
const a = bench("array.includes", (i) => +ids.includes(last - i));
const b = bench("set.has       ", (i) => +idSet.has(last - i));
console.log("ответы совпадают:", a === b);`}
/>

`includes` приходится идти по массиву, пока не найдётся значение, поэтому он замедляется с ростом массива. `Set` сразу переходит к ответу. На большинстве компьютеров разница здесь — в сотни раз.

В реальных проектах используйте библиотеку для бенчмарков, а не свой цикл. Она сама позаботится о прогреве, статистике и выбросах:

```js
// lookup.bench.js, запуск: npx vitest bench
import { bench, describe } from "vitest";

const ids = Array.from({ length: 10_000 }, (_, i) => i);
const idSet = new Set(ids);

describe("lookup", () => {
  bench("array.includes", () => {
    ids.includes(9_999);
  });
  bench("set.has", () => {
    idSet.has(9_999);
  });
});
```

Библиотеки вроде **tinybench** (её использует Vitest) и **mitata** делают то же самое вне Vitest. И помните: микробенчмарк отвечает на крошечный вопрос. Важно ли изменение для **вашего приложения**, скажет только профиль всего приложения.

## Big-O на практике

Бенчмарк говорит, сколько времени занимает работа для **одного** размера входных данных. **Big-O** говорит, как время **растёт** вместе с данными, и именно это решает, выживет ли ваш код на production-данных. Функция, которая работает 2 мс на 100 тестовых строках, может работать 20 минут на 100 000 настоящих.

| Big-O | Название | Типичный JavaScript | 1 000 элементов → 100 000 элементов |
| --- | --- | --- | --- |
| O(1) | константная | `map.get(key)`, `set.has(x)`, `arr[i]`, `arr.push(x)` | то же время |
| O(log n) | логарифмическая | двоичный поиск в отсортированном массиве | чуть медленнее |
| O(n) | линейная | `arr.includes(x)`, `find`, `filter`, один цикл | в 100 раз медленнее |
| O(n log n) | n log n | `arr.sort()` | примерно в 170 раз медленнее |
| O(n²) | квадратичная | цикл внутри цикла по тем же данным | в 10 000 раз медленнее |

Опасный код O(n²) редко выглядит как два цикла `for`. Он прячется внутри дружелюбных методов массивов. Вот классика: каждому посту приписываем пользователя. Вместо замера времени мы **считаем шаги** — так рост виден точно:

<CodeExample output={`вложенные циклы: 500500 шагов
поиск в Map: 2000 шагов`}>

```js
const users = Array.from({ length: 1000 }, (_, i) => ({
  id: i,
  name: `user${i}`,
}));
const posts = Array.from({ length: 1000 }, (_, i) => ({
  id: i,
  userId: 999 - i,
}));

// Как posts.map(p => users.find(u => u.id === p.userId))
let steps = 0;
for (const post of posts) {
  for (const user of users) {
    steps++;
    if (user.id === post.userId) break;
  }
}
console.log("вложенные циклы:", steps, "шагов");

// Один раз строим индекс, и каждый поиск — один шаг
steps = 0;
const usersById = new Map();
for (const user of users) {
  steps++;
  usersById.set(user.id, user);
}
for (const post of posts) {
  steps++;
  usersById.get(post.userId);
}
console.log("поиск в Map:", steps, "шагов");
```

</CodeExample>

При 1 000 тех и других вложенная версия делает примерно в 250 раз больше работы. При 100 000 было бы 5 **миллиардов** шагов против 200 000. Исправление всегда строится на одной идее: **один раз постройте индекс** (`Map` или `Set`), а потом ищите за O(1).

Остерегайтесь таких скрытых циклов внутри циклов:

- `.find()`, `.filter()`, `.includes()`, `.indexOf()` или `.some()`, вызванные внутри `.map()`, `.forEach()` или цикла `for` по другому большому массиву.
- `arr.shift()` или `arr.splice(0, 1)` в цикле: удаление первого элемента сдвигает все остальные.
- Копирование в `reduce`: `items.reduce((acc, x) => ({ ...acc, [x.id]: x }), {})` на каждом шаге копирует весь объект, поэтому это O(n²). Используйте `Object.fromEntries(items.map((x) => [x.id, x]))` или `Map`.
- `await` внутри цикла для независимых запросов: это не про Big-O, но запах тот же. N ожиданий подряд вместо одного `Promise.all`.

<Callout type="tip" title="Big-O — это ещё не всё">

Для 20 элементов «медленная» версия O(n²) обычно быстрее, чем построение `Map`, и гораздо проще читается. Big-O — это про **рост**. Если данных мало и так и останется (7 дней недели, 3 вкладки формы), пишите самый понятный код. Если данные приходят от пользователей или из базы данных, считайте, что они вырастут.

</Callout>

## Ищем медленную часть: профилировщики

Ручные замеры работают, только когда вы уже подозреваете конкретную функцию. Чтобы найти горячую точку во всём приложении, используйте **профилировщик (profiler)**: он тысячи раз в секунду записывает, чем занята программа.

В Chrome (в Edge и Firefox похоже) откройте DevTools → **Performance**:

1. Нажмите на шестерёнку и выберите **CPU: 4× slowdown** (и, может быть, медленную сеть). Это примерно имитирует средний телефон. У пользователей нет вашего ноутбука.
2. Нажмите запись, сделайте медленное действие (введите текст в поиск, откройте меню), остановите запись.
3. Читайте **флейм-график (flame chart)** на дорожке Main: каждая полоска — вызов функции, её ширина — сколько он длился, а полоски под ней — функции, которые она вызвала. Ищите широкие полоски.
4. Задачи длиннее 50 мс — это **длинные задачи (long tasks)**, они помечены красным уголком. Пока идёт длинная задача, страница не может отвечать на клики и ввод.
5. Переключитесь на вкладку **Bottom-Up** и отсортируйте по **Self Time**, чтобы увидеть, какие функции сами по себе сожгли больше всего времени — неважно, откуда их вызывали.

**Lighthouse** (тоже в DevTools) автоматически проверяет загрузку страницы и выдаёт оценки и конкретные советы: «эта картинка слишком большая», «этот скрипт блокирует отрисовку». Используйте его как чек-лист, а не как цель: идеальные 100 баллов на быстром офисном Wi-Fi мало говорят о пользователе в поезде.

Для серверов на Node.js доступны те же флейм-графики:

```bash
# Записать CPU-профиль, пока работает сервер, затем открыть
# файл .cpuprofile в Chrome DevTools (Performance → Load profile)
node --cpu-prof server.js

# Или подключить DevTools вживую: откройте chrome://inspect в Chrome
node --inspect server.js
```

## Core Web Vitals

Что измерять на сайте? **Core Web Vitals** от Google — три числа, которые отражают то, что пользователи реально ощущают. Они также влияют на позиции в поиске, поэтому бизнесу они небезразличны:

| Метрика | На какой вопрос отвечает | Хорошо | Плохо |
| --- | --- | --- | --- |
| **LCP**, Largest Contentful Paint | Через сколько виден основной контент (самая большая картинка или блок текста)? | ≤ 2,5 с | > 4 с |
| **INP**, Interaction to Next Paint | Когда я кликаю или печатаю, через сколько экран реагирует? (примерно худшее взаимодействие за визит) | ≤ 200 мс | > 500 мс |
| **CLS**, Cumulative Layout Shift | Прыгает ли что-то, пока я читаю? (это оценка, а не время) | ≤ 0,1 | > 0,25 |

Страница «проходит», когда не меньше **75%** реальных визитов хорошие по каждой метрике (75-й перцентиль). INP заменил старую метрику FID в 2024 году, поэтому в старых статьях ещё может встречаться FID.

### Частые причины и исправления

**Медленный LCP** обычно означает, что основной контент приходит поздно:
- медленный ответ сервера (смотрите **TTFB**, time to first byte — время до первого байта): добавьте кеширование, исправьте медленные запросы, используйте CDN;
- огромная главная картинка: сожмите её, отдавайте современные форматы (AVIF/WebP), добавьте `fetchpriority="high"` и никогда не ставьте ей `loading="lazy"`;
- контент, который появляется только после того, как JavaScript загрузится, выполнится и получит данные: отрисуйте его на сервере или начните загрузку данных раньше;
- CSS и шрифты в `<head>`, которые блокируют отрисовку.

**Плохой INP** означает, что основной поток занят, когда пользователь взаимодействует со страницей:
- длинные задачи из-за тяжёлого JavaScript: разбейте работу на порции, перенесите её в Web Worker, делайте меньше;
- медленные обработчики событий: сначала сделайте видимое обновление, остальное отложите;
- повторный рендер огромных деревьев компонентов или DOM-списков при каждом нажатии клавиши.

Следующий урок полон исправлений для этих проблем.

**Высокий CLS** означает, что элементы сдвигаются уже после появления:
- картинки и видео без `width` и `height` (браузер не знает, сколько места оставить);
- реклама, баннеры и уведомления о cookie, вставленные над контентом;
- веб-шрифты, которые подменяются шрифтами другого размера;
- контент, вставленный после запроса выше того места, которое читает пользователь.

## Измеряем реальных пользователей

Lighthouse и DevTools дают **лабораторные данные (lab data)**: одно устройство, одна сеть, один запуск. У реальных пользователей медленные телефоны, плохая сеть и заполненный кеш. **Полевые данные (field data)**, их ещё называют **RUM** (real user monitoring — мониторинг реальных пользователей), собираются с настоящих визитов, и именно они — правда.

Почему «75-й перцентиль», а не среднее? Потому что среднее прячет пользователей, которым плохо. Вот 12 замеров LCP с реальных визитов:

<CodeExample output={`среднее: 2596 мс
медиана (p50): 1700 мс
p75: 2600 мс
p95: 7200 мс`}>

```js
function percentile(values, p) {
  const sorted = [...values].sort((a, b) => a - b);
  const index = Math.ceil((p / 100) * sorted.length) - 1;
  return sorted[Math.max(0, index)];
}

// LCP 12 реальных загрузок страницы, в миллисекундах
const lcp = [1200, 1350, 1400, 1500, 1600, 1700,
             1800, 2100, 2600, 3900, 4800, 7200];

const average = lcp.reduce((a, b) => a + b, 0) / lcp.length;
console.log("среднее:", Math.round(average), "мс");
console.log("медиана (p50):", percentile(lcp, 50), "мс");
console.log("p75:", percentile(lcp, 75), "мс");
console.log("p95:", percentile(lcp, 95), "мс");
```

</CodeExample>

Медиана говорит: «1,7 с, отлично!» — а при этом каждый четвёртый посетитель ждёт дольше 2,5 с, а самые невезучие — 7 секунд. p75 едва не дотягивает до «хорошо». Senior-инженеры говорят о **перцентилях (percentiles)** — p50, p75, p95, p99 — именно поэтому, причём и для веб-страниц, и для времени ответа API.

В браузере API **PerformanceObserver** доставляет записи о производительности по мере их появления. Маленькая библиотека **web-vitals** от Google построена на нём и правильно считает LCP, INP и CLS — вручную это на удивление кропотливо:

```js
// npm i web-vitals
import { onLCP, onINP, onCLS } from "web-vitals";

function sendToAnalytics(metric) {
  const body = JSON.stringify({
    name: metric.name, // "LCP", "INP" или "CLS"
    value: metric.value,
    rating: metric.rating, // "good", "needs-improvement", "poor"
    page: location.pathname,
  });
```

Ежедневный отчёт магазина добавляет к каждому заказу имя клиента. На тестах всё работало, но с десятками тысяч заказов и клиентов отчёт зависает на несколько секунд, потому что **для каждого заказа ищет по всему списку клиентов**.

Перепишите `attachCustomers(orders, customers)`, чтобы она работала за **O(n)**:

1. **Один раз**, до прохода по заказам, постройте `Map` из id клиента в клиента.
2. Для каждого заказа верните **новый** объект со всеми полями заказа плюс `customerName` (или `"Unknown"`, если такого клиента нет). Не изменяйте входные массивы и объекты.
3. Сохраните порядок заказов.

Проверки считают, сколько раз ваш код читает `id` клиента, и замеряют время запуска на 60 000 заказов и клиентов. Медленная версия на этой проверке работает несколько секунд (в этом и смысл), так что наберитесь терпения, если запустите проверки до исправления.

<Hint>

Перед `map` создайте индекс: `const byId = new Map(customers.map((c) => [c.id, c]));` (так каждый `id` читается один раз). Затем внутри `map` замените `find` на `byId.get(order.customerId)`. Всё остальное можно оставить как есть.

</Hint>

<Solution>

```js
function attachCustomers(orders, customers) {
  // Строим индекс один раз: O(клиенты)
  const byId = new Map(customers.map((c) => [c.id, c]));

  // Один поиск за O(1) на заказ: O(заказы)
  return orders.map((order) => {
    const customer = byId.get(order.customerId);
    return {
      ...order,
      customerName: customer ? customer.name : "Unknown",
    };
  });
}

const customers = [
  { id: 1, name: "Mei" },
  { id: 2, name: "Bao" },
];
const orders = [
  { id: 101, customerId: 2, total: 30 },
  { id: 102, customerId: 1, total: 12 },
  { id: 103, customerId: 9, total: 5 },
];

for (const row of attachCustomers(orders, customers)) {
  console.log(row.id, row.customerName, row.total);
}
```

## Итоги

- **Измеряйте, а не гадайте**: выберите важную цифру, воспроизведите проблему на реалистичных данных, измерьте, профилируйте, исправьте горячую точку и измерьте ещё раз.
- **`performance.now()`** — правильные часы для замеров кода. **`performance.mark`/`measure`** дают имена вашим шагам, и они появляются в панели Performance в DevTools.
- Микробенчмарки врут, если не делать **прогрев**, не **использовать результаты** (удаление мёртвого кода) и не брать **медиану** многих запусков. Лучше используйте `vitest bench`, tinybench или mitata.
- **Big-O** описывает рост. Скрытый O(n²) обычно выглядит как `find`/`includes`/`filter` внутри цикла; исправляйте его, один раз построив индекс на `Map` или `Set`.
- Ищите горячие точки в **панели Performance** (замедление CPU в 4 раза, флейм-график, длинные задачи, Bottom-Up) и проверяйте страницы с помощью **Lighthouse**; профилируйте Node через `--cpu-prof` или `--inspect`.
- **Core Web Vitals**: LCP ≤ 2,5 с (основной контент виден), INP ≤ 200 мс (реакция на ввод), CLS ≤ 0,1 (ничего не прыгает) — по **75-му перцентилю** реальных визитов.
- Лабораторные данные помогают находить проблемы, а **полевые данные** (PerformanceObserver, `web-vitals`, сервис мониторинга) показывают, что чувствуют реальные пользователи. Смотрите на перцентили, а не на средние, и задавайте **бюджеты производительности**.
