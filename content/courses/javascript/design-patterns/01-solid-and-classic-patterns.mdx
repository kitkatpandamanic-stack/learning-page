Design patterns can make a codebase calmer or much worse. One team I know wrapped every feature in a `Manager`, a `Factory` and a `Strategy` class "to be flexible": adding one field to a form meant touching nine files. Another team had a single 4,000-line `utils.js` that everybody was scared to edit. Both teams were smart. One used patterns as a goal, the other never used them at all. 🧭

A **design pattern** is a named, proven shape for solving a recurring problem. Knowing the names helps you spot the problem, and it lets you say "make it a strategy" in a code review instead of drawing diagrams. Most classic patterns were written down for Java and C++. JavaScript has first-class functions, closures and object literals, so many patterns become **a few lines**, or disappear completely. In this lesson you'll learn the principles behind them (SOLID), the patterns you'll actually meet in JavaScript codebases, and when to leave them out.

## SOLID in JavaScript terms

**SOLID** is five design principles collected by Robert C. Martin. They're often explained with Java interfaces, but they translate well to JavaScript:

| Letter | Principle | In JavaScript terms |
| --- | --- | --- |
| **S** | Single responsibility | A module or function has **one reason to change**. `checkout.js` calculates orders; it doesn't also build email HTML. |
| **O** | Open/closed | Add new behaviour by **adding** code (a new entry in a map of functions, a new event handler), not by editing a growing `switch`. |
| **L** | Liskov substitution | Anything passed where a "cache" is expected must **behave** like a cache: same methods, same kind of results, no surprise errors. |
| **I** | Interface segregation | Ask for the **smallest** thing you need: a `save` function, not the whole database client. |
| **D** | Dependency inversion | Important code **receives** its dependencies (`fetch`, a clock, a repository) instead of reaching for concrete ones. [Lesson 3](/learn/javascript/dependency-injection-and-domain-modelling) of this module is all about it. |

Here's open/closed in practice. A pricing function whose `if/else` chain grows with every marketing campaign is **closed for extension**: each new promo code means editing (and re-testing) the same function:

```js
// ❌ Every new promotion means editing this function
function price(cart, promo) {
  let total = subtotal(cart);
  if (promo === "STUDENT") total *= 0.9;
  else if (promo === "BULK" && cart.length >= 3) total -= 5;
  // ...and 30 more else-ifs a year later
  return total;
}
```

Turn each rule into a **function** and keep the rules in a `Map`. Now a new promotion is a new line, and `price` never changes:

<CodeExample output={`35
30
27
Unknown promo code: toString`}>

```js
const subtotal = (cart) =>
  cart.reduce((sum, item) => sum + item.price * item.qty, 0);

// Each rule: (total, cart) => new total
const promotions = new Map([
  ["STUDENT", (total) => total * 0.9],
  ["BULK", (total, cart) => (cart.length >= 3 ? total - 5 : total)],
  ["FREEBIE", (total) => Math.max(0, total - 20)],
]);

function price(cart, codes = []) {
  return codes.reduce((total, code) => {
    const rule = promotions.get(code);
    if (!rule) throw new Error(`Unknown promo code: ${code}`);
    return rule(total, cart);
  }, subtotal(cart));
}

const cart = [
  { name: "bamboo", price: 4, qty: 5 },
  { name: "tea", price: 6, qty: 1 },
  { name: "mug", price: 9, qty: 1 },
];
console.log(price(cart));
console.log(price(cart, ["BULK"]));
console.log(price(cart, ["BULK", "STUDENT"]));
try {
  price(cart, ["toString"]);
} catch (error) {
  console.log(error.message);
}
```

</CodeExample>

Why a `Map` and not a plain object? With `const promotions = { STUDENT: … }`, the lookup `promotions["toString"]` finds `Object.prototype.toString` and happily calls it. A `Map` only contains what you put in. (If you prefer objects, use `Object.hasOwn(promotions, code)` or `Object.create(null)`.)

Liskov substitution is the subtle one. It's not only about subclasses: in JavaScript **any** object you pass in has to keep the promises its callers rely on:

<CodeExample output={`42
Surprise: this cache is read-only`}>

```js
class MemoryCache {
  #items = new Map();
  get(key) {
    return this.#items.get(key);
  }
  set(key, value) {
    this.#items.set(key, value);
  }
}

// Looks like a cache... but breaks what callers rely on
class ReadOnlyCache extends MemoryCache {
  set() {
    throw new Error("this cache is read-only");
  }
}

function remember(cache, key, compute) {
  if (cache.get(key) === undefined) cache.set(key, compute());
  return cache.get(key);
}

console.log(remember(new MemoryCache(), "answer", () => 42));
try {
  remember(new ReadOnlyCache(), "answer", () => 42);
} catch (error) {
  console.log("Surprise:", error.message);
}
```

</CodeExample>

`ReadOnlyCache` **is a** `MemoryCache` according to `instanceof`, but code written for caches breaks when it gets one. If something can't do everything the parent promises, it shouldn't pretend to be one: give it its own, smaller shape (`{ get }`), and let functions that only read ask for just that. That's interface segregation solving a Liskov problem.

<Callout type="note" title="Principles, not laws">

SOLID describes **forces**, not rules to apply everywhere. Splitting a 20-line function into five "single responsibility" classes makes code harder to read, not easier. Use the principles to explain why some code hurts ("this file changes for three different reasons"), then fix that.

</Callout>

## Composition over inheritance

Inheritance looks great in tutorials: `Animal → Bird → Eagle`. Then a `Penguin` arrives that can't fly, a `Duck` that flies **and** swims, and a `RobotDuck` that swims and needs charging. A tree can't describe "a bit of this, a bit of that", and every change near the root ripples down to every leaf. This is sometimes called the **fragile base class** problem.

JavaScript has two common ways out. The first is a **mixin**: a function that takes a class and returns a new class with extra methods:

<CodeExample output={`Rex: Woof! | Rex charged to 100%
true
[ 'RoboDog', 'CanBark', 'CanCharge', 'Machine' ]`}>

```js
const CanBark = (Base) =>
  class CanBark extends Base {
    bark() {
      return `${this.name}: Woof!`;
    }
  };

const CanCharge = (Base) =>
  class CanCharge extends Base {
    charge() {
      this.battery = 100;
      return `${this.name} charged to ${this.battery}%`;
    }
  };

class Machine {
  constructor(name) {
    this.name = name;
    this.battery = 0;
  }
}

class RoboDog extends CanBark(CanCharge(Machine)) {}

const rex = new RoboDog("Rex");
console.log(rex.bark(), "|", rex.charge());
console.log(rex instanceof Machine);

// Walk the prototype chain to see what we really built
const chain = [];
let proto = Object.getPrototypeOf(rex);
while (proto !== Object.prototype) {
  chain.push(proto.constructor.name);
  proto = Object.getPrototypeOf(proto);
}
console.log(chain);
```

</CodeExample>

Mixins work (React used them before hooks, many libraries still do), but look at that prototype chain: the mixins are hidden **inheritance**. Two mixins with a method of the same name silently override each other, depending on the order you wrapped them in.

The second way is **composition**: build an object from small behaviour pieces that share some state, and return exactly the methods you want:

<CodeExample output={`Rex: Woof!
Rex charged to 100%
100
[ 'bark', 'charge', 'battery' ]`}>

```js
const barker = (state) => ({
  bark: () => `${state.name}: Woof!`,
});

const charger = (state) => ({
  charge() {
    state.battery = 100;
    return `${state.name} charged to ${state.battery}%`;
  },
});

function createRoboDog(name) {
  const state = { name, battery: 0 }; // private: only the pieces see it
  return {
    ...barker(state),
    ...charger(state),
    get battery() {
      return state.battery;
    },
  };
}

const rex = createRoboDog("Rex");
console.log(rex.bark());
console.log(rex.charge());
console.log(rex.battery);
console.log(Object.keys(rex));
```

</CodeExample>

Everything is explicit: you can read `createRoboDog` and see every capability, the state is private thanks to the closure, and each piece can be tested on its own. "Composition" also simply means **has-a** instead of **is-a**: a `Player` that *has* an `inventory` object is easier to change than a `Player` that *extends* `InventoryHolder`.

Inheritance is still fine for **shallow**, genuinely "is-a" relationships, especially when a framework expects it (`class ValidationError extends Error`, a web component that `extends HTMLElement`). A good rule: one level of inheritance is normal, two needs a reason, three needs a meeting.

## Strategy: functions are already strategies

The **strategy** pattern means "pick one of several interchangeable algorithms at runtime". In Java that's an interface and a class per algorithm. In JavaScript it's a function you pass in, and you've used it since your first `array.sort((a, b) => a - b)`: the comparator **is** a strategy.

Strategies often come from small **factory functions** that configure them with a closure. Here are three retry delay strategies (you'll use one in the security and system-design modules):

<CodeExample output={`[ 500, 500, 500, 500 ]
[ 500, 1000, 1500, 2000 ]
[ 500, 1000, 2000, 3000, 3000 ]
[ 'Bao', 'Mei', 'Zoe' ]
[ 'Mei', 'Zoe', 'Bao' ]`}>

```js
const fixed = (ms) => () => ms;
const linear = (ms) => (attempt) => ms * attempt;
const exponential = (ms, max = Infinity) => (attempt) =>
  Math.min(max, ms * 2 ** (attempt - 1));

// Code that USES a strategy doesn't care which one it gets
function delays(strategy, attempts) {
  return Array.from({ length: attempts }, (_, i) => strategy(i + 1));
}

console.log(delays(fixed(500), 4));
console.log(delays(linear(500), 4));
console.log(delays(exponential(500, 3000), 5));

const pandas = [
  { name: "Mei", age: 4 },
  { name: "Zoe", age: 7 },
  { name: "Bao", age: 9 },
];
const byName = (a, b) => a.name.localeCompare(b.name);
const byAge = (a, b) => a.age - b.age;
console.log(pandas.toSorted(byName).map((p) => p.name));
console.log(pandas.toSorted(byAge).map((p) => p.name));
```

</CodeExample>

When a strategy needs several operations (say `validate` and `format`), pass an **object** with those methods instead of a single function. Same idea.

## Factory: hide how objects are made

A **factory** is a function that creates objects for you, so callers don't need to know which class or which setup is involved. In JavaScript the everyday factory is just `createSomething(options)`: it can return different implementations, set up private state in a closure, and validate options in one place.

A common variant is a **registry**: implementations register themselves under a name, and the factory builds whichever one the configuration asks for. This is how loggers, payment providers and plugin systems are usually wired:

<CodeExample output={`[ops] Deploy finished
[ 'Deploy finished' ]
Unknown notifier "pigeon" (try: console, memory)`}>

```js
const notifierTypes = new Map();

function registerNotifier(type, create) {
  notifierTypes.set(type, create);
}

function createNotifier({ type, ...options }) {
  const create = notifierTypes.get(type);
  if (!create) {
    const known = [...notifierTypes.keys()].join(", ");
    throw new Error(`Unknown notifier "${type}" (try: ${known})`);
  }
  return create(options);
}

registerNotifier("console", ({ prefix = "" }) => ({
  send: (text) => console.log(prefix + text),
}));
registerNotifier("memory", () => {
  const sent = [];
  return { send: (text) => sent.push(text), sent };
});

// The config could come from a JSON file or environment variables
const config = [{ type: "console", prefix: "[ops] " }, { type: "memory" }];
const notifiers = config.map(createNotifier);
for (const notifier of notifiers) notifier.send("Deploy finished");
console.log(notifiers[1].sent);

try {
  createNotifier({ type: "pigeon" });
} catch (error) {
  console.log(error.message);
}
```

</CodeExample>

Both notifiers have the same shape (`send(text)`), so the rest of the app can use either. Adding a Slack notifier is one `registerNotifier` call: open/closed again. Notice the helpful error message listing the known types; future-you debugging a typo in a config file will be grateful.

## Observer: events instead of calls

When an order is paid, the app needs to send a receipt, update stats and notify the warehouse. If `payOrder` calls all three directly, it has to know about all of them, and every new feature edits `payOrder`. The **observer** pattern turns it around: `payOrder` announces "an order was paid", and anyone interested **subscribes**.

You've used observers since Level 1 (`button.addEventListener`). Node has `EventEmitter` and browsers have `EventTarget`, but writing a small emitter yourself shows there's no magic:

<CodeExample output={`audit: order 7 paid
email: receipt for £30 to mei@pandadev.test
email: receipt for £12 to bao@pandadev.test`}>

```js
function createEmitter() {
  const handlers = new Map(); // event name → Set of handlers

  function on(event, handler) {
    if (!handlers.has(event)) handlers.set(event, new Set());
    handlers.get(event).add(handler);
    return () => handlers.get(event).delete(handler); // unsubscribe
  }

  function emit(event, payload) {
    // Copy first, so handlers that unsubscribe don't upset the loop
    for (const handler of [...(handlers.get(event) ?? [])]) {
      handler(payload);
    }
  }

  return { on, emit };
}

const events = createEmitter();
const stopAudit = events.on("order:paid", (order) =>
  console.log(`audit: order ${order.id} paid`),
);
events.on("order:paid", (order) =>
  console.log(`email: receipt for £${order.total} to ${order.email}`),
);

events.emit("order:paid", { id: 7, total: 30, email: "mei@pandadev.test" });
stopAudit();
events.emit("order:paid", { id: 8, total: 12, email: "bao@pandadev.test" });
events.emit("nobody:listens", {});
```

</CodeExample>

Returning an **unsubscribe function** from `on` is the modern style (React's `useEffect` cleanup, Redux's `store.subscribe`, RxJS). It makes cleanup hard to forget, and forgotten listeners are one of the classic memory leaks in long-running apps.

The same thing with the built-in `EventTarget`, which works in browsers and in Node:

<CodeExample output={`stock low: bamboo (2 left)`}>

```js
const warehouse = new EventTarget();
warehouse.addEventListener("stock-low", (event) => {
  const { item, left } = event.detail;
  console.log(`stock low: ${item} (${left} left)`);
});
warehouse.dispatchEvent(
  new CustomEvent("stock-low", { detail: { item: "bamboo", left: 2 } }),
);
```

</CodeExample>

<Callout type="warning" title="The price of events">

Events decouple code, which also makes it **harder to follow**: "what happens when an order is paid?" now means searching the codebase for `"order:paid"`. Use events for genuinely independent reactions (emails, stats, caches), not for steps that must happen in order for the operation to be correct. And decide what a failing handler does: in the emitter above, one handler throwing stops the others from running. Node's `EventEmitter` behaves the same way, and it prints a "possible memory leak" warning when one event gets more than 10 listeners, a hint that something keeps subscribing without unsubscribing.

</Callout>

## Adapter: make it fit

Third-party code never has quite the shape your app wants. An **adapter** wraps it and translates: names, argument order, callbacks into promises, their errors into yours. Say your app expects every message channel to look like `send(to, text) → Promise<{ id }>`, and the SMS provider's SDK looks like this:

<CodeExample output={`{ id: 'sms-1' }
SMS failed: invalid number`}>

```js
// A third-party SMS SDK (we can't change it)
const smsSdk = {
  dispatch(payload, done) {
    setTimeout(() => {
      if (!payload.msisdn.startsWith("+")) {
        done({ code: "E_NUMBER", detail: "invalid number" });
      } else {
        done(null, { messageId: "sms-1", state: "QUEUED" });
      }
    }, 10);
  },
};

// Our app's shape: send(to, text) → Promise<{ id }>
function createSmsChannel(sdk) {
  return {
    send(to, text) {
      return new Promise((resolve, reject) => {
        sdk.dispatch({ msisdn: to, body: text }, (err, result) => {
          if (err) reject(new Error(`SMS failed: ${err.detail}`));
          else resolve({ id: result.messageId });
        });
      });
    },
  };
}

const sms = createSmsChannel(smsSdk);
console.log(await sms.send("+447700900123", "Hi Mei"));
try {
  await sms.send("07700", "Hi");
} catch (error) {
  console.log(error.message);
}
```

</CodeExample>

The adapter is the **only** file that knows the words `msisdn` and `messageId`. When the company switches SMS providers (it will), you write one new adapter and nothing else changes. This is also called an **anti-corruption layer**: it stops a vendor's vocabulary from leaking into your code. In Node, `util.promisify(fn)` is a ready-made adapter for callback-style functions.

## Decorator: wrap behaviour around a function

A **decorator** adds behaviour around something without changing it. In JavaScript the natural decorator is a **higher-order function**: it takes a function and returns a new function with the same signature that does a bit more. Logging, caching, retries, timing and permission checks are all decorators:

<CodeExample output={`→ db(1)
← db: {"id":1,"name":"Mei"}
→ db(2)
← db: {"id":2,"name":"Bao"}
db calls: 2`}>

```js
function withLogging(fn, label = fn.name) {
  return async (...args) => {
    console.log(`→ ${label}(${args.join(", ")})`);
    const result = await fn(...args);
    console.log(`← ${label}: ${JSON.stringify(result)}`);
    return result;
  };
}

function withCache(fn) {
  const cache = new Map();
  return (key) => {
    // Caching the promise means parallel calls share one load
    if (!cache.has(key)) cache.set(key, fn(key));
    return cache.get(key);
  };
}

let dbCalls = 0;
async function loadUser(id) {
  dbCalls++;
  return { id, name: id === 1 ? "Mei" : "Bao" };
}

const getUser = withCache(withLogging(loadUser, "db"));
await getUser(1);
await getUser(1); // from the cache: no log, no db call
await getUser(2);
console.log("db calls:", dbCalls);
```

</CodeExample>

Order matters. `withCache(withLogging(loadUser))` logs only real database calls; `withLogging(withCache(loadUser))` would log every call, cached or not. Both are useful; just choose on purpose. Also note this cache keeps a **failed** promise forever; a production version deletes the key when the promise rejects (and probably needs a size limit and expiry).

You'll also see decorators written with `@`, the TC39 decorators proposal. TypeScript 5 and Babel support it, and frameworks like Angular, NestJS and MobX use it heavily:

```js
// TypeScript or Babel (not plain JavaScript in most engines yet)
class UserService {
  @logged
  async getUser(id) {
    return this.repo.get(id);
  }
}
```

Under the hood, `@logged` is a function that receives the method and returns a wrapped one: the same idea as `withLogging`.

## Singletons and module state

A **singleton** is a class with exactly one instance that everyone shares. In JavaScript you rarely write the classic `getInstance()` version, because **every ES module is already a singleton**: it's evaluated once, and everyone who imports it gets the same exports. So `export const cart = createCart()` or a top-level `const items = []` in `cart.js` is a singleton too.

That's convenient, and it's a trap for tests, because the state survives from one test to the next:

<CodeExample output={`✓ module-level cart > adds an item
× module-level cart > starts empty
  → expected 1 to be 0 // Object.is equality
✓ cart from a factory > adds an item
✓ cart from a factory > starts empty

Tests  1 failed | 3 passed (4)`}>

```js
import { describe, it, expect, beforeEach } from "vitest";

// Imagine this is cart.js: state at the top of a module
const items = [];
const cart = {
  add: (item) => items.push(item),
  count: () => items.length,
};

describe("module-level cart", () => {
  it("adds an item", () => {
    cart.add("bamboo");
    expect(cart.count()).toBe(1);
  });
  it("starts empty", () => {
    expect(cart.count()).toBe(0); // fails: the last test's item is here
  });
});

// The fix: export a factory, create instances where they're needed
function createCart() {
  const items = [];
  return {
    add: (item) => items.push(item),
    count: () => items.length,
  };
}

describe("cart from a factory", () => {
  let cart;
  beforeEach(() => {
    cart = createCart(); // a fresh cart for every test
  });
  it("adds an item", () => {
    cart.add("bamboo");
    expect(cart.count()).toBe(1);
  });
  it("starts empty", () => {
    expect(cart.count()).toBe(0);
  });
});
```

</CodeExample>

Module-level state causes tests that pass alone but fail together (or only fail in a different order), and on a server it's worse: a module-level `currentUser` is shared by **every request** at once. A few things genuinely exist once per process (a database connection pool, a logger), and that's fine, but create them in **one** place at startup and pass them to the code that needs them. That place is called the **composition root**, and it's the star of lesson 3.

## When patterns are over-engineering

Every pattern adds indirection: one more file to open, one more name to learn. It earns its place when it removes a **real** pain you have now. Some signs you've gone too far:

- An "interface" or factory with exactly **one** implementation that will never get a second one.
- A strategy map with one strategy, or an event with one listener that must always run (just call the function).
- Class names that describe patterns instead of the business: `AbstractNotificationStrategyFactoryManager`.
- A new teammate needs a diagram to follow how a button click reaches the database.

A practical habit is the **rule of three**: write it plainly the first time, notice the duplication the second time, and extract the pattern the third time, when you know what actually varies. Plain functions and objects are not a failure to design; in JavaScript they're often the best design.

Build a small notification module from the patterns in this lesson. The emitter is ready; you write a **decorator** and a **factory** that uses **strategies** and **events**:

1. `withRetry(fn, attempts)` returns an `async` function that calls `fn` with the same arguments. If `fn` rejects, try again, up to `attempts` tries in total, then rethrow the **last** error.
2. `createNotifier({ channels, events, attempts = 3 })` returns `{ notify(channel, to, text) }`:
   - `channels` is a `Map` of channel name → `async (to, text) => result` (each channel is a strategy).
   - An unknown channel rejects with `Error("Unknown channel: <name>")`.
   - Send through `withRetry`. On success, emit `"sent"` with `{ channel, to }` and resolve to the channel's result.
   - When all attempts fail, emit `"failed"` with `{ channel, to, error: error.message }`, then reject with the error.

```js
// ---- Given: the event emitter from the lesson ----
function createEmitter() {
  const handlers = new Map();
  return {
    on(event, handler) {
      if (!handlers.has(event)) handlers.set(event, new Set());
      handlers.get(event).add(handler);
      return () => handlers.get(event).delete(handler);
    },
    emit(event, payload) {
      for (const handler of [...(handlers.get(event) ?? [])]) {
        handler(payload);
      }
    },
  };
}

function withRetry(fn, attempts) {
  return async (...args) => {
    let lastError;
    for (let i = 1; i <= attempts; i++) {
      try {
        return await fn(...args);
      } catch (error) {
        lastError = error;
      }
    }
    throw lastError;
  };
}

function createNotifier({ channels, events, attempts = 3 }) {
  return {
    async notify(channel, to, text) {
      const strategy = channels.get(channel);
      if (!strategy) {
        throw new Error(`Unknown channel: ${channel}`);
      }
      const send = withRetry(strategy, attempts);
      try {
        const result = await send(to, text);
        events.emit("sent", { channel, to });
        return result;
      } catch (error) {
        events.emit("failed", { channel, to, error: error.message });
        throw error;
      }
    },
  };
}

// ---- Try it ----
let smsTries = 0;
const channels = new Map([
  ["console", async (to, text) => console.log("[to " + to + "] " + text)],
  ["sms", async (to) => {
    smsTries++;
    if (smsTries === 1) throw new Error("network blip");
    return { id: "sms-" + smsTries };
  }],
]);
const events = createEmitter();
events.on("sent", (e) => console.log("sent:", e));
events.on("failed", (e) => console.log("failed:", e));

const notifier = createNotifier({ channels, events });
await notifier.notify("console", "mei", "Your order shipped");
console.log(await notifier.notify("sms", "+4477", "Hi"));
try {
  await notifier.notify("pigeon", "bao", "Coo");
} catch (error) {
  console.log(error.message);
}
```

## Recap

- **SOLID** in JavaScript: one reason to change per module; extend by adding functions to a map or handlers to an event; anything passed in must keep its promises (Liskov); ask for the smallest thing you need; receive dependencies instead of reaching for them.
- Prefer **composition** (objects built from small pieces sharing private state) over deep inheritance; mixins work but are hidden inheritance.
- **Strategy** = pass a function (or an object of functions). **Factory** = `createX(options)`, often with a registry of named implementations.
- **Observer** = an emitter where `on` returns an unsubscribe function; great for independent reactions, harder to follow.
- **Adapter** = wrap a third-party API in your app's shape, so its vocabulary stays in one file.
- **Decorator** = a higher-order function that wraps behaviour (logging, caching, retries) around a function; the wrapping order matters.
- ES modules are singletons: module-level state leaks between tests and requests. Export factories and create instances at startup.
- Patterns are vocabulary, not goals: apply one when it removes a pain you have now.
