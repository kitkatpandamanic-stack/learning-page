Паттерны проектирования могут сделать кодовую базу спокойнее, а могут — гораздо хуже. Одна знакомая команда оборачивала каждую фичу в класс `Manager`, `Factory` и `Strategy` «для гибкости»: чтобы добавить одно поле в форму, приходилось править девять файлов. У другой команды был один `utils.js` на 4000 строк, который все боялись трогать. Обе команды были умными. Просто одна сделала паттерны целью, а другая не использовала их вовсе. 🧭

**Паттерн проектирования (design pattern)** — это проверенная форма решения повторяющейся задачи, у которой есть имя. Знание названий помогает распознать задачу и позволяет на код-ревью сказать «сделай это стратегией», а не рисовать диаграммы. Большинство классических паттернов описаны для Java и C++. В JavaScript есть функции первого класса, замыкания (closure) и объектные литералы, поэтому многие паттерны превращаются в **пару строк** или исчезают совсем. В этом уроке вы разберёте принципы, на которых они держатся (SOLID), паттерны, которые действительно встречаются в JavaScript-проектах, и случаи, когда без них лучше.

## SOLID на языке JavaScript

**SOLID** — это пять принципов проектирования, которые собрал Роберт Мартин (Robert C. Martin). Их часто объясняют через интерфейсы Java, но они хорошо переводятся на JavaScript:

| Буква | Принцип | На языке JavaScript |
| --- | --- | --- |
| **S** | Единственная ответственность (single responsibility) | У модуля или функции **одна причина для изменения**. `checkout.js` считает заказы и не собирает заодно HTML для писем. |
| **O** | Открытость/закрытость (open/closed) | Новое поведение добавляется **новым** кодом (новой записью в таблице функций, новым обработчиком события), а не правкой разрастающегося `switch`. |
| **L** | Подстановка Лисков (Liskov substitution) | Всё, что передают туда, где ждут «кэш», должно **вести себя** как кэш: те же методы, такие же результаты, никаких неожиданных ошибок. |
| **I** | Разделение интерфейсов (interface segregation) | Просите **минимум** того, что нужно: функцию `save`, а не весь клиент базы данных. |
| **D** | Инверсия зависимостей (dependency inversion) | Важный код **получает** свои зависимости (`fetch`, часы, репозиторий), а не тянется за конкретными реализациями сам. Этому целиком посвящён [урок 3](/learn/javascript/dependency-injection-and-domain-modelling) модуля. |

Вот открытость/закрытость на практике. Функция расчёта цены, чья цепочка `if/else` растёт с каждой маркетинговой акцией, **закрыта для расширения**: каждый новый промокод означает правку (и повторное тестирование) одной и той же функции:

```js
// ❌ Каждая новая акция — правка этой функции
function price(cart, promo) {
  let total = subtotal(cart);
  if (promo === "STUDENT") total *= 0.9;
  else if (promo === "BULK" && cart.length >= 3) total -= 5;
  // ...и ещё 30 else-if через год
  return total;
}
```

Превратите каждое правило в **функцию** и храните правила в `Map`. Теперь новая акция — это новая строка, а `price` не меняется никогда:

<CodeExample output={`35
30
27
Неизвестный промокод: toString`}>

```js
const subtotal = (cart) =>
  cart.reduce((sum, item) => sum + item.price * item.qty, 0);

// Каждое правило: (total, cart) => новая сумма
const promotions = new Map([
  ["STUDENT", (total) => total * 0.9],
  ["BULK", (total, cart) => (cart.length >= 3 ? total - 5 : total)],
  ["FREEBIE", (total) => Math.max(0, total - 20)],
]);

function price(cart, codes = []) {
  return codes.reduce((total, code) => {
    const rule = promotions.get(code);
    if (!rule) throw new Error(`Неизвестный промокод: ${code}`);
    return rule(total, cart);
  }, subtotal(cart));
}

const cart = [
  { name: "bamboo", price: 4, qty: 5 },
  { name: "tea", price: 6, qty: 1 },
  { name: "mug", price: 9, qty: 1 },
];
console.log(price(cart));
console.log(price(cart, ["BULK"]));
console.log(price(cart, ["BULK", "STUDENT"]));
try {
  price(cart, ["toString"]);
} catch (error) {
  console.log(error.message);
}
```

</CodeExample>

Почему `Map`, а не обычный объект? С `const promotions = { STUDENT: … }` поиск `promotions["toString"]` найдёт `Object.prototype.toString` и спокойно его вызовет. В `Map` есть только то, что вы туда положили. (Если вам больше нравятся объекты, используйте `Object.hasOwn(promotions, code)` или `Object.create(null)`.)

Подстановка Лисков — самый тонкий принцип. Он касается не только подклассов: в JavaScript **любой** объект, который вы передаёте, обязан выполнять обещания, на которые рассчитывает вызывающий код:

<CodeExample output={`42
Сюрприз: этот кэш только для чтения`}>

```js
class MemoryCache {
  #items = new Map();
  get(key) {
    return this.#items.get(key);
  }
  set(key, value) {
    this.#items.set(key, value);
  }
}

// Выглядит как кэш... но ломает то, на что рассчитывают вызывающие
class ReadOnlyCache extends MemoryCache {
  set() {
    throw new Error("этот кэш только для чтения");
  }
}

function remember(cache, key, compute) {
  if (cache.get(key) === undefined) cache.set(key, compute());
  return cache.get(key);
}

console.log(remember(new MemoryCache(), "answer", () => 42));
try {
  remember(new ReadOnlyCache(), "answer", () => 42);
} catch (error) {
  console.log("Сюрприз:", error.message);
}
```

</CodeExample>

По мнению `instanceof`, `ReadOnlyCache` **является** `MemoryCache`, но код, написанный для кэшей, на нём ломается. Если что-то не умеет всего, что обещает родитель, ему не стоит притворяться родителем: дайте ему собственную, меньшую форму (`{ get }`), а функции, которые только читают, пусть просят только её. Так разделение интерфейсов решает проблему подстановки Лисков.

<Callout type="note" title="Принципы, а не законы">

SOLID описывает **силы**, а не правила, которые надо применять везде. Если разбить функцию на 20 строк на пять классов «с единственной ответственностью», код станет читать труднее, а не легче. Используйте принципы, чтобы объяснить, почему какой-то код причиняет боль («этот файл меняется по трём разным причинам»), и устраняйте именно это.

</Callout>

## Композиция вместо наследования

В учебниках наследование (inheritance) выглядит отлично: `Animal → Bird → Eagle`. Потом появляется `Penguin`, который не умеет летать, `Duck`, который летает **и** плавает, и `RobotDuck`, который плавает и требует зарядки. Дерево не умеет описывать «немного того, немного этого», а каждое изменение у корня расходится волнами до каждого листа. Это иногда называют проблемой **хрупкого базового класса (fragile base class)**.

В JavaScript есть два распространённых выхода. Первый — **миксин (mixin)**: функция, которая принимает класс и возвращает новый класс с дополнительными методами:

<CodeExample output={`Rex: Гав! | Rex заряжен до 100%
true
[ 'RoboDog', 'CanBark', 'CanCharge', 'Machine' ]`}>

```js
const CanBark = (Base) =>
  class CanBark extends Base {
    bark() {
      return `${this.name}: Гав!`;
    }
  };

const CanCharge = (Base) =>
  class CanCharge extends Base {
    charge() {
      this.battery = 100;
      return `${this.name} заряжен до ${this.battery}%`;
    }
  };

class Machine {
  constructor(name) {
    this.name = name;
    this.battery = 0;
  }
}

class RoboDog extends CanBark(CanCharge(Machine)) {}

const rex = new RoboDog("Rex");
console.log(rex.bark(), "|", rex.charge());
console.log(rex instanceof Machine);

// Пройдём по цепочке прототипов и посмотрим, что получилось
const chain = [];
let proto = Object.getPrototypeOf(rex);
while (proto !== Object.prototype) {
  chain.push(proto.constructor.name);
  proto = Object.getPrototypeOf(proto);
}
console.log(chain);
```

</CodeExample>

Миксины работают (React пользовался ими до хуков, многие библиотеки пользуются до сих пор), но посмотрите на цепочку прототипов: миксины — это скрытое **наследование**. Если у двух миксинов есть методы с одинаковым именем, один молча перекроет другой, и какой именно — зависит от порядка обёртывания.

Второй выход — **композиция (composition)**: соберите объект из маленьких кусочков поведения с общим состоянием и верните ровно те методы, которые нужны:

<CodeExample output={`Rex: Гав!
Rex заряжен до 100%
100
[ 'bark', 'charge', 'battery' ]`}>

```js
const barker = (state) => ({
  bark: () => `${state.name}: Гав!`,
});

const charger = (state) => ({
  charge() {
    state.battery = 100;
    return `${state.name} заряжен до ${state.battery}%`;
  },
});

function createRoboDog(name) {
  const state = { name, battery: 0 }; // приватно: видят только кусочки
  return {
    ...barker(state),
    ...charger(state),
    get battery() {
      return state.battery;
    },
  };
}

const rex = createRoboDog("Rex");
console.log(rex.bark());
console.log(rex.charge());
console.log(rex.battery);
console.log(Object.keys(rex));
```

</CodeExample>

Всё явно: читая `createRoboDog`, вы видите каждую возможность, состояние приватно благодаря замыканию, а каждый кусочек можно протестировать отдельно. Ещё «композиция» означает просто **«содержит»** вместо **«является»**: `Player`, у которого *есть* объект `inventory`, менять проще, чем `Player`, который *наследует* `InventoryHolder`.

Наследование по-прежнему уместно для **неглубоких**, по-настоящему «является»-отношений, особенно когда этого ждёт фреймворк (`class ValidationError extends Error`, веб-компонент, который `extends HTMLElement`). Хорошее правило: один уровень наследования — норма, два требуют причины, три требуют совещания.

## Стратегия: функции уже и есть стратегии

Паттерн **«стратегия» (strategy)** означает «выбрать один из нескольких взаимозаменяемых алгоритмов во время выполнения». В Java это интерфейс и по классу на каждый алгоритм. В JavaScript это функция, которую вы передаёте, и вы пользуетесь ею с первого `array.sort((a, b) => a - b)`: компаратор **и есть** стратегия.

Стратегии часто создаются маленькими **фабричными функциями**, которые настраивают их через замыкание. Вот три стратегии задержки между повторными попытками (одна из них пригодится вам в модулях о безопасности и проектировании систем):

<CodeExample output={`[ 500, 500, 500, 500 ]
[ 500, 1000, 1500, 2000 ]
[ 500, 1000, 2000, 3000, 3000 ]
[ 'Bao', 'Mei', 'Zoe' ]
[ 'Mei', 'Zoe', 'Bao' ]`}>

```js
const fixed = (ms) => () => ms;
const linear = (ms) => (attempt) => ms * attempt;
const exponential = (ms, max = Infinity) => (attempt) =>
  Math.min(max, ms * 2 ** (attempt - 1));

// Коду, который ИСПОЛЬЗУЕТ стратегию, всё равно, какая ему досталась
function delays(strategy, attempts) {
  return Array.from({ length: attempts }, (_, i) => strategy(i + 1));
}

console.log(delays(fixed(500), 4));
console.log(delays(linear(500), 4));
console.log(delays(exponential(500, 3000), 5));

const pandas = [
  { name: "Mei", age: 4 },
  { name: "Zoe", age: 7 },
  { name: "Bao", age: 9 },
];
const byName = (a, b) => a.name.localeCompare(b.name);
const byAge = (a, b) => a.age - b.age;
console.log(pandas.toSorted(byName).map((p) => p.name));
console.log(pandas.toSorted(byAge).map((p) => p.name));
```

</CodeExample>

Когда стратегии нужно несколько операций (скажем, `validate` и `format`), передавайте **объект** с этими методами вместо одной функции. Идея та же.

## Фабрика: спрячьте, как создаются объекты

**Фабрика (factory)** — это функция, которая создаёт объекты за вас, чтобы вызывающему коду не нужно было знать, какой класс или какая настройка за этим стоят. В JavaScript повседневная фабрика — это просто `createSomething(options)`: она может возвращать разные реализации, хранить приватное состояние в замыкании и проверять параметры в одном месте.

Частый вариант — **реестр (registry)**: реализации регистрируются под именем, а фабрика собирает ту, которую просит конфигурация. Так обычно подключают логгеры, платёжных провайдеров и системы плагинов:

<CodeExample output={`[ops] Деплой завершён
[ 'Деплой завершён' ]
Неизвестный тип уведомителя "pigeon" (доступны: console, memory)`}>

```js
const notifierTypes = new Map();

function registerNotifier(type, create) {
  notifierTypes.set(type, create);
}

function createNotifier({ type, ...options }) {
  const create = notifierTypes.get(type);
  if (!create) {
    const known = [...notifierTypes.keys()].join(", ");
    throw new Error(
      `Неизвестный тип уведомителя "${type}" (доступны: ${known})`,
    );
  }
  return create(options);
}

registerNotifier("console", ({ prefix = "" }) => ({
  send: (text) => console.log(prefix + text),
}));
registerNotifier("memory", () => {
  const sent = [];
  return { send: (text) => sent.push(text), sent };
});

// Конфигурация может прийти из JSON-файла или переменных окружения
const config = [{ type: "console", prefix: "[ops] " }, { type: "memory" }];
const notifiers = config.map(createNotifier);
for (const notifier of notifiers) notifier.send("Деплой завершён");
console.log(notifiers[1].sent);

try {
  createNotifier({ type: "pigeon" });
} catch (error) {
  console.log(error.message);
}
```

</CodeExample>

У обоих уведомителей одинаковая форма (`send(text)`), поэтому остальное приложение может пользоваться любым из них. Уведомитель для Slack добавляется одним вызовом `registerNotifier` — снова открытость/закрытость. Обратите внимание на полезное сообщение об ошибке со списком известных типов: вы из будущего, отлаживая опечатку в конфиге, скажете себе спасибо.

## Наблюдатель: события вместо вызовов

Когда заказ оплачен, приложению нужно отправить чек, обновить статистику и уведомить склад. Если `payOrder` вызывает все три действия напрямую, она обязана знать о каждом, и каждая новая фича правит `payOrder`. Паттерн **«наблюдатель» (observer)** переворачивает это: `payOrder` объявляет «заказ оплачен», а все заинтересованные **подписываются**.

Вы пользуетесь наблюдателями с Уровня 1 (`button.addEventListener`). В Node есть `EventEmitter`, в браузерах — `EventTarget`, но если написать маленький эмиттер самому, станет видно, что никакой магии нет:

<CodeExample output={`аудит: заказ 7 оплачен
письмо: чек на £30 для mei@pandadev.test
письмо: чек на £12 для bao@pandadev.test`}>

```js
function createEmitter() {
  const handlers = new Map(); // имя события → Set обработчиков

  function on(event, handler) {
    if (!handlers.has(event)) handlers.set(event, new Set());
    handlers.get(event).add(handler);
    return () => handlers.get(event).delete(handler); // отписка
  }

  function emit(event, payload) {
    // Сначала копируем, чтобы отписка внутри обработчика не сбила цикл
    for (const handler of [...(handlers.get(event) ?? [])]) {
      handler(payload);
    }
  }

  return { on, emit };
}

const events = createEmitter();
const stopAudit = events.on("order:paid", (order) =>
  console.log(`аудит: заказ ${order.id} оплачен`),
);
events.on("order:paid", (order) =>
  console.log(`письмо: чек на £${order.total} для ${order.email}`),
);

events.emit("order:paid", { id: 7, total: 30, email: "mei@pandadev.test" });
stopAudit();
events.emit("order:paid", { id: 8, total: 12, email: "bao@pandadev.test" });
events.emit("nobody:listens", {});
```

</CodeExample>

Возвращать из `on` **функцию отписки** — современный стиль (очистка в `useEffect` в React, `store.subscribe` в Redux, RxJS). Так про очистку трудно забыть, а забытые обработчики — одна из классических утечек памяти в долго работающих приложениях.

То же самое со встроенным `EventTarget`, который работает и в браузерах, и в Node:

<CodeExample output={`заканчивается товар: bamboo (осталось 2)`}>

```js
const warehouse = new EventTarget();
warehouse.addEventListener("stock-low", (event) => {
  const { item, left } = event.detail;
  console.log(`заканчивается товар: ${item} (осталось ${left})`);
});
warehouse.dispatchEvent(
  new CustomEvent("stock-low", { detail: { item: "bamboo", left: 2 } }),
);
```

</CodeExample>

<Callout type="warning" title="Цена событий">

События развязывают код, но из-за этого за ним **труднее следить**: вопрос «что происходит, когда заказ оплачен?» теперь означает поиск `"order:paid"` по всей кодовой базе. Используйте события для действительно независимых реакций (письма, статистика, кэши), а не для шагов, которые должны выполниться по порядку, чтобы операция была корректной. И решите, что делать с упавшим обработчиком: в эмиттере выше исключение в одном обработчике не даёт запуститься остальным. `EventEmitter` в Node ведёт себя так же, а ещё печатает предупреждение «possible memory leak», когда у одного события больше 10 обработчиков: это намёк, что что-то постоянно подписывается и не отписывается.

</Callout>

## Адаптер: подогнать по форме

Сторонний код никогда не бывает ровно той формы, которая нужна вашему приложению. **Адаптер (adapter)** оборачивает его и переводит: названия, порядок аргументов, колбэки в промисы, чужие ошибки в ваши. Допустим, ваше приложение ждёт, что любой канал сообщений выглядит как `send(to, text) → Promise<{ id }>`, а SDK провайдера SMS выглядит так:

<CodeExample output={`{ id: 'sms-1' }
Не удалось отправить SMS: invalid number`}>

```js
// Сторонний SDK для SMS (изменить его мы не можем)
const smsSdk = {
  dispatch(payload, done) {
    setTimeout(() => {
      if (!payload.msisdn.startsWith("+")) {
        done({ code: "E_NUMBER", detail: "invalid number" });
      } else {
        done(null, { messageId: "sms-1", state: "QUEUED" });
      }
    }, 10);
  },
};

// Форма нашего приложения: send(to, text) → Promise<{ id }>
function createSmsChannel(sdk) {
  return {
    send(to, text) {
      return new Promise((resolve, reject) => {
        sdk.dispatch({ msisdn: to, body: text }, (err, result) => {
          if (err) {
            reject(new Error(`Не удалось отправить SMS: ${err.detail}`));
          } else {
            resolve({ id: result.messageId });
          }
        });
      });
    },
  };
}

const sms = createSmsChannel(smsSdk);
console.log(await sms.send("+447700900123", "Привет, Mei"));
try {
  await sms.send("07700", "Привет");
} catch (error) {
  console.log(error.message);
}
```

</CodeExample>

Адаптер — **единственный** файл, который знает слова `msisdn` и `messageId`. Когда компания сменит провайдера SMS (а она сменит), вы напишете один новый адаптер, и больше ничего не изменится. Это ещё называют **антикоррупционным слоем (anti-corruption layer)**: он не даёт словарю поставщика просочиться в ваш код. В Node `util.promisify(fn)` — готовый адаптер для функций в стиле колбэков.

## Декоратор: обернуть поведение вокруг функции

**Декоратор (decorator)** добавляет поведение вокруг чего-то, не меняя его. В JavaScript естественный декоратор — это **функция высшего порядка (higher-order function)**: она принимает функцию и возвращает новую функцию с той же сигнатурой, которая делает чуть больше. Логирование, кэширование, повторные попытки, замер времени и проверка прав — всё это декораторы:

<CodeExample output={`→ db(1)
← db: {"id":1,"name":"Mei"}
→ db(2)
← db: {"id":2,"name":"Bao"}
вызовов БД: 2`}>

```js
function withLogging(fn, label = fn.name) {
  return async (...args) => {
    console.log(`→ ${label}(${args.join(", ")})`);
    const result = await fn(...args);
    console.log(`← ${label}: ${JSON.stringify(result)}`);
    return result;
  };
}

function withCache(fn) {
  const cache = new Map();
  return (key) => {
    // Кэшируем промис, чтобы параллельные вызовы делили одну загрузку
    if (!cache.has(key)) cache.set(key, fn(key));
    return cache.get(key);
  };
}

let dbCalls = 0;
async function loadUser(id) {
  dbCalls++;
  return { id, name: id === 1 ? "Mei" : "Bao" };
}

const getUser = withCache(withLogging(loadUser, "db"));
await getUser(1);
await getUser(1); // из кэша: ни лога, ни обращения к БД
await getUser(2);
console.log("вызовов БД:", dbCalls);
```

</CodeExample>

Порядок важен. `withCache(withLogging(loadUser))` логирует только настоящие обращения к базе данных, а `withLogging(withCache(loadUser))` логировал бы каждый вызов, из кэша или нет. Полезны оба варианта — просто выбирайте осознанно. Заметьте также, что этот кэш навсегда запоминает **отклонённый** промис; рабочая версия удаляет ключ, когда промис отклоняется (и, скорее всего, ограничивает размер и срок хранения).

Ещё вы встретите декораторы, записанные через `@`, — это предложение TC39 о декораторах. Его поддерживают TypeScript 5 и Babel, а фреймворки вроде Angular, NestJS и MobX активно им пользуются:

```js
// TypeScript или Babel (в большинстве движков это ещё не обычный JavaScript)
class UserService {
  @logged
  async getUser(id) {
    return this.repo.get(id);
  }
}
```

Под капотом `@logged` — это функция, которая получает метод и возвращает обёрнутый: та же идея, что и `withLogging`.

## Синглтоны и состояние модуля

**Синглтон (singleton)** — это класс ровно с одним экземпляром, общим для всех. В JavaScript классическую версию с `getInstance()` пишут редко, потому что **каждый ES-модуль уже синглтон**: он выполняется один раз, и все, кто его импортирует, получают одни и те же экспорты. Поэтому `export const cart = createCart()` или `const items = []` на верхнем уровне `cart.js` — тоже синглтон.

Это удобно, но для тестов это ловушка: состояние переживает переход от одного теста к другому:

<CodeExample output={`✓ корзина на уровне модуля > добавляет товар
× корзина на уровне модуля > изначально пуста
  → expected 1 to be 0 // Object.is equality
✓ корзина из фабрики > добавляет товар
✓ корзина из фабрики > изначально пуста

Tests  1 failed | 3 passed (4)`}>

```js
import { describe, it, expect, beforeEach } from "vitest";

// Представьте, что это cart.js: состояние на верхнем уровне модуля
const items = [];
const cart = {
  add: (item) => items.push(item),
  count: () => items.length,
};

describe("корзина на уровне модуля", () => {
  it("добавляет товар", () => {
    cart.add("bamboo");
    expect(cart.count()).toBe(1);
  });
  it("изначально пуста", () => {
    expect(cart.count()).toBe(0); // падает: тут товар из прошлого теста
  });
});

// Исправление: экспортируйте фабрику и создавайте экземпляры там,
// где они нужны
function createCart() {
  const items = [];
  return {
    add: (item) => items.push(item),
    count: () => items.length,
  };
}

describe("корзина из фабрики", () => {
  let cart;
  beforeEach(() => {
    cart = createCart(); // новая корзина для каждого теста
  });
  it("добавляет товар", () => {
    cart.add("bamboo");
    expect(cart.count()).toBe(1);
  });
  it("изначально пуста", () => {
    expect(cart.count()).toBe(0);
  });
});
```

</CodeExample>

Из-за состояния на уровне модуля появляются тесты, которые проходят поодиночке, но падают вместе (или падают только в другом порядке), а на сервере всё ещё хуже: `currentUser` на уровне модуля общий сразу для **всех запросов**. Некоторые вещи действительно существуют в процессе в одном экземпляре (пул соединений с базой данных, логгер), и это нормально, но создавайте их в **одном** месте при запуске и передавайте коду, которому они нужны. Это место называется **корнем композиции (composition root)**, и оно — главный герой урока 3.

## Когда паттерны — это переусложнение

Каждый паттерн добавляет косвенность: ещё один файл, который нужно открыть, ещё одно имя, которое нужно запомнить. Он оправдан, когда убирает **реальную** боль, которая есть у вас сейчас. Признаки того, что вы зашли слишком далеко:

- «Интерфейс» или фабрика ровно с **одной** реализацией, у которой никогда не будет второй.
- Таблица стратегий с одной стратегией или событие с одним обработчиком, который обязан выполниться всегда (просто вызовите функцию).
- Имена классов описывают паттерны, а не бизнес: `AbstractNotificationStrategyFactoryManager`.
- Новому коллеге нужна диаграмма, чтобы понять, как клик по кнопке доходит до базы данных.

Практичная привычка — **правило трёх (rule of three)**: в первый раз напишите просто, во второй раз заметьте дублирование, а в третий выделите паттерн — когда уже понятно, что на самом деле меняется. Обычные функции и объекты — не провал проектирования; в JavaScript это часто лучший дизайн.

// ---- Дано: эмиттер событий из урока ----
function createEmitter() {
  const handlers = new Map();
  return {
    on(event, handler) {
      if (!handlers.has(event)) handlers.set(event, new Set());
      handlers.get(event).add(handler);
      return () => handlers.get(event).delete(handler);
    },
    emit(event, payload) {
      for (const handler of [...(handlers.get(event) ?? [])]) {
        handler(payload);
      }
    },
  };
}

function withRetry(fn, attempts) {
  return async (...args) => {
    let lastError;
    for (let i = 1; i <= attempts; i++) {
      try {
        return await fn(...args);
      } catch (error) {
        lastError = error;
      }
    }
    throw lastError;
  };
}

function createNotifier({ channels, events, attempts = 3 }) {
  return {
    async notify(channel, to, text) {
      const strategy = channels.get(channel);
      if (!strategy) {
        throw new Error(`Unknown channel: ${channel}`);
      }
      const send = withRetry(strategy, attempts);
      try {
        const result = await send(to, text);
        events.emit("sent", { channel, to });
        return result;
      } catch (error) {
        events.emit("failed", { channel, to, error: error.message });
        throw error;
      }
    },
  };
}

const channels = new Map([

    smsTries++;
    if (smsTries === 1) throw new Error("сбой сети");
    return { id: "sms-" + smsTries };
  }],
]);
const events = createEmitter();
events.on("sent", (e) => console.log("sent:", e));
events.on("failed", (e) => console.log("failed:", e));

  await notifier.notify("pigeon", "bao", "Курлык");

## Итоги

- **SOLID** в JavaScript: у модуля одна причина для изменения; расширяйте код, добавляя функции в таблицу или обработчики к событию; всё, что передаётся внутрь, обязано выполнять свои обещания (Лисков); просите минимум того, что нужно; получайте зависимости, а не тянитесь за ними.
- Предпочитайте **композицию** (объекты из маленьких кусочков с общим приватным состоянием) глубокому наследованию; миксины работают, но это скрытое наследование.
- **Стратегия** = передать функцию (или объект с функциями). **Фабрика** = `createX(options)`, часто с реестром именованных реализаций.
- **Наблюдатель** = эмиттер, в котором `on` возвращает функцию отписки; отлично подходит для независимых реакций, но за ним труднее следить.
- **Адаптер** = обёртка над сторонним API в форме вашего приложения, чтобы чужой словарь жил в одном файле.
- **Декоратор** = функция высшего порядка, которая оборачивает поведение (логирование, кэширование, повторные попытки) вокруг функции; порядок обёртывания важен.
- ES-модули — синглтоны: состояние на уровне модуля протекает между тестами и запросами. Экспортируйте фабрики и создавайте экземпляры при запуске.
- Паттерны — это словарь, а не цель: применяйте паттерн, когда он убирает боль, которая есть у вас сейчас.
