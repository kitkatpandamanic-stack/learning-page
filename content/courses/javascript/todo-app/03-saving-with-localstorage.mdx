Your to-do app works, but it has the memory of a goldfish 🐠: reload the page and every task is gone. That's because `tasks` lives in a variable, and variables are wiped whenever the page loads again. In this final part you'll save the tasks **in the browser itself**, so they're still there tomorrow.

You'll use **JSON** from **Arrays & Objects**, **try/catch** from **Errors & Debugging**, `reduce` to fix a sneaky id bug, and a quick look at how **classes** and **modules** could organise the app.

## Meet localStorage

Every browser gives each website a small storage space called **`localStorage`**. Whatever you put in it stays there after a reload, after closing the tab, even after restarting the computer. It has four methods you need:

| Method                           | What it does                                       |
| -------------------------------- | -------------------------------------------------- |
| `localStorage.setItem(key, value)` | saves `value` under the name `key`               |
| `localStorage.getItem(key)`      | gives the saved value back, or `null` if there's none |
| `localStorage.removeItem(key)`   | deletes that one entry                             |
| `localStorage.clear()`           | deletes everything this site saved                 |

Press **Run** a few times on this example and watch the number go up:

<TryIt

<button id="forget">Forget me</button>`}

const saved = localStorage.getItem("visits");
console.log("Saved value:", saved, typeof saved);

The first time, `getItem` gives `null` because nothing is saved yet. After that, it gives back the number you saved... but as a **string**! `localStorage` can only store **text**. Anything you save is turned into a string first.

<Callout type="note" title="localStorage in the previews">

In your own browser, `localStorage` really is kept across page reloads. The previews on PandaDev run in a locked-down sandbox where the real `localStorage` isn't allowed, so the site **simulates** it: it keeps what your code saved, and pressing **Run** again behaves like reloading the page. Press **Reset** to wipe the saved data and start fresh.

</Callout>

## Saving arrays and objects as JSON

Since `localStorage` only stores strings, what happens if you save the `tasks` array directly? Let's find out:

<TryIt
  html={`<p>Check the console below the preview. 👇</p>`}
  code={`const tasks = [{ id: 1, text: "Water the bamboo", done: false }];

localStorage.setItem("oops", tasks);
console.log(localStorage.getItem("oops"));

localStorage.setItem("pandadev-todos", JSON.stringify(tasks));
const text = localStorage.getItem("pandadev-todos");
console.log(text);

const back = JSON.parse(text);
console.log(back[0].text, back[0].done);`}
/>

Saving the array directly gives you the useless text `[object Object]`, and your tasks are lost. The fix is the JSON pair you already know:

- **Saving:** `JSON.stringify(tasks)` turns the array into JSON text, and `setItem` stores it.
- **Loading:** `getItem` gives the text back, and `JSON.parse` turns it into a real array of objects again.

That gives us our first function. We keep the key in a constant so it's spelled the same everywhere:

```js
const STORAGE_KEY = "pandadev-todos";

function saveTasks() {
  localStorage.setItem(STORAGE_KEY, JSON.stringify(tasks));
}
```

## Saving after every change

When should we save? After **every** change to `tasks`: adding, ticking, deleting and clearing. Because the app follows the render pattern, every change is already followed by a `render()` call, so there's a neat trick: one helper that does both.

```js
function saveAndRender() {
  saveTasks();
  render();
}
```

Then, in the listeners that **change the tasks** (the form, the list and **Clear completed**), call `saveAndRender()` instead of `render()`. The filter buttons only change what's **shown**, not the tasks, so they keep calling plain `render()`.

## Loading tasks safely

When the page starts, we read the saved text back. Two things can go wrong:

1. **Nothing is saved yet** (the very first visit). `getItem` returns `null`.
2. **The saved data is broken.** Maybe an old version of your app saved something different, or someone edited it by hand in the browser's developer tools. Then `JSON.parse` **throws** a `SyntaxError`, and without protection the whole app would crash before drawing anything.

Here's where `try/catch` earns its place: if parsing fails, we catch the error and start with an empty list instead. There's one more check worth doing. `JSON.parse` happily reads `"hello"` or `42` too, and those aren't lists of tasks. **`Array.isArray(value)`** is a built-in check that's `true` only for arrays:

<CodeExample output={`true
false
false`}>

```js
console.log(Array.isArray([1, 2]));
console.log(Array.isArray("hello"));
console.log(Array.isArray(null));
```

</CodeExample>

Put together, `loadTasks()` always returns an array, whatever is in storage:

<TryIt
  html={`<p>Check the console below the preview. 👇</p>`}
  code={`const STORAGE_KEY = "pandadev-todos";

function loadTasks() {
  const saved = localStorage.getItem(STORAGE_KEY);
  if (saved === null) return [];

  try {
    const data = JSON.parse(saved);
    return Array.isArray(data) ? data : [];
  } catch (error) {
    console.warn("Saved tasks were broken, starting fresh.");
    return [];
  }
}

localStorage.removeItem(STORAGE_KEY);
console.log("Nothing saved:", loadTasks());

localStorage.setItem(STORAGE_KEY, '[{"id":1,"text":"Nap","done":true}]');
console.log("Good data:", loadTasks());

localStorage.setItem(STORAGE_KEY, "{ oops, not JSON");
console.log("Broken data:", loadTasks());

localStorage.setItem(STORAGE_KEY, '"hello"');
console.log("Not a list:", loadTasks());`}
/>

At the start of the app, `tasks` now comes from storage instead of a hard-coded list:

```js
let tasks = loadTasks();
```

<Callout type="warning" title="What not to keep in localStorage">

`localStorage` is fine for to-dos, settings and drafts. It's **not** safe for passwords, tokens or anything secret: any JavaScript running on the page can read it. It's also small (around 5 MB per site) and belongs to one browser on one device, so it's not a replacement for a real database.

</Callout>

## Fixing the next id

There's a sneaky bug waiting. In Part 1, `nextId` started at a fixed number. But now `tasks` might come back from storage with ids `1`, `2` and `7`. If `nextId` starts at `3` again, a new task gets id `3`... and the next one gets `7`, which is **already taken**. Two tasks with the same id means ticking one could tick the other!

The fix: after loading, start counting from the **biggest id + 1**. `reduce` finds the biggest id by carrying the largest value seen so far:

<CodeExample output={`8
1`}>

```js
function findNextId(savedTasks) {
  const biggest = savedTasks.reduce(
    (max, task) => (task.id > max ? task.id : max),
    0,
  );
  return biggest + 1;
}

console.log(findNextId([{ id: 1 }, { id: 7 }, { id: 3 }]));
console.log(findNextId([]));
```

</CodeExample>

With an empty list, `reduce` just returns its starting value `0`, so the first task gets id `1`. In the app:

```js
let tasks = loadTasks();
let nextId = findNextId(tasks);
```

## Functions or a class?

In the Classes module you learned to bundle data and the functions that work on it into a **class**. Should the app be a `TodoList` class? It could be:

<CodeExample output={`1 task left at home
1 task left at work`}>

```js
class TodoList {
  tasks = [];
  nextId = 1;

  add(text) {
    const clean = text.trim();
    if (clean === "") return;
    this.tasks.push({ id: this.nextId, text: clean, done: false });
    this.nextId++;
  }

  toggle(id) {
    const task = this.tasks.find((task) => task.id === id);
    if (task) task.done = !task.done;
  }

  get left() {
    return this.tasks.filter((task) => !task.done).length;
  }
}

const home = new TodoList();
const work = new TodoList();
home.add("Water the bamboo");
home.add("Nap in the sun");
home.toggle(1);
work.add("Write the report");

console.log(`${home.left} task left at home`);
console.log(`${work.left} task left at work`);
```

</CodeExample>

For **this** app, we'll keep plain functions. There's only **one** list, the whole app fits in one script, and the functions you already wrote are short and easy to test. A class starts to pay off when you need **several** lists (like `home` and `work` above), or when the app grows big enough to split into **modules**. Then the task logic, the storage code and the DOM code could each live in their own file:

```js
// main.js (a bigger version of the app)
import { TodoList } from "./todo-list.js";
import { loadTasks, saveTasks } from "./storage.js";
import { render } from "./render.js";
```

Both styles are fine. What matters most is the idea behind them: **state in one place, changed by small functions, drawn by `render()`**.

## What you built

- **`localStorage`** keeps data in the browser across reloads, but only as **strings**, so tasks are saved with `JSON.stringify` and read back with `JSON.parse`.
- **`saveAndRender()`** saves after every change to the tasks, while the filter buttons only re-render.
- **`loadTasks()`** always returns an array: `[]` for no data, broken JSON (caught with `try/catch`) or anything that isn't a list.
- **`findNextId()`** uses `reduce` to keep ids unique after loading.
- You chose **functions over a class** on purpose, and saw how a `TodoList` class and modules could organise a bigger version.

## Take it further

Your app is finished, but there's always more to build. Here are some ideas to try in your own editor:

- **Edit on double-click:** listen for `dblclick` on the list, swap the task's text for an `<input>`, and save the new text when the user presses Enter (`keydown`) or leaves the box (`change`).
- **Drag to reorder:** make items `draggable`, use the `dragstart`, `dragover` and `drop` events, then move the task to its new place in the `tasks` array with `splice` and save.
- **Due dates:** add an `<input type="date">` to the form, store a `due` property on each task, sort by it, and highlight tasks that are overdue.
- **Dark/light theme:** add a theme switch that toggles a class on `<body>`, and save the choice under its own `localStorage` key so the page remembers it too.
- **Remember the filter:** save `filter` as well, so the app opens on the view you used last.
