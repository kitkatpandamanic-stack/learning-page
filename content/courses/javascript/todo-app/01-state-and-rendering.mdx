Welcome to the Level 1 capstone! Over three parts you'll build a real **to-do app**: you can add tasks, tick them off, delete them, filter them, and (the best bit) it **remembers your tasks** when you reload the page. 🐼📝

You'll use almost everything from Level 1: **arrays of objects** and array methods, the **DOM** and **events**, the **render pattern**, `dataset`, **JSON** and **try/catch**. Here's the plan:

- **Part 1 (this one):** store tasks in an array, draw them on the page, add new ones with a form.
- **Part 2:** tick tasks off, delete them, filter them and count what's left.
- **Part 3:** save everything in the browser with `localStorage`, so your tasks survive a reload.

## The plan: state, then render

Before writing any code, let's decide how the app will work. We'll use the **render pattern** from the DOM & Events module:

1. All the app's data lives in one variable, the **state**: an array of tasks.
2. One function, **`render()`**, clears the list on the page and rebuilds it from the state.
3. When the user does something (submits the form, clicks a button), we **change the state**, then call `render()`.

```text
  user does something  ──▶  change the state  ──▶  render()
          ▲                                           │
          └──────────── the page shows the state ◀────┘
```

We **never** add or remove `<li>` elements by hand. If the page looks wrong, there are only two places to look: the state, or `render()`. That's what keeps an app like this from turning into spaghetti as it grows.

## Tasks as objects

Each task needs a few pieces of information, so an **object** is the perfect fit:

- **`id`**: a number that's different for every task, so we can always find the right one.
- **`text`**: what the task says.
- **`done`**: `true` once it's ticked off, `false` until then.

The whole state is an **array** of these objects:

<CodeExample output={`Learn the DOM
2
[ 'Water the bamboo', 'Learn the DOM', 'Nap in the sun' ]`}>

```js
const tasks = [
  { id: 1, text: "Water the bamboo", done: false },
  { id: 2, text: "Learn the DOM", done: true },
  { id: 3, text: "Nap in the sun", done: false },
];

console.log(tasks[1].text);
console.log(tasks.filter((task) => !task.done).length);
console.log(tasks.map((task) => task.text));
```

</CodeExample>

All the array methods you know already work on it: `filter` for tasks that aren't done yet, `map` for just the texts, `find` to look one up. You'll use all of them in Part 2.

### Why not just use the position?

You might wonder why we need an `id` at all, when every task already has an index (`0`, `1`, `2`...). The problem is that **indexes change**. Delete the first task and every other task moves up one place. Show only the unfinished tasks and the positions on the page no longer match the positions in the array. An `id` belongs to the task itself and **never changes**, so it always points at the right one.

## Adding tasks with unique ids

To give every task a different id, we keep a **counter** in a variable. Each new task takes the current number, then the counter goes up by one:

<CodeExample output={`{ id: 1, text: 'Water the bamboo', done: false }
{ id: 2, text: 'Learn the DOM', done: false }
2 tasks, next id: 3`}>

```js
const tasks = [];
let nextId = 1;

function addTask(text) {
  const clean = text.trim();
  if (clean === "") return;

  tasks.push({ id: nextId, text: clean, done: false });
  nextId++;
}

addTask("Water the bamboo");
addTask("   Learn the DOM   ");
addTask("     ");

tasks.forEach((task) => console.log(task));
console.log(`${tasks.length} tasks, next id: ${nextId}`);
```

</CodeExample>

Two small details make the app feel polished:

- **`trim()`** removes spaces from the start and end, so `"   Learn the DOM   "` is saved as `"Learn the DOM"`.
- If nothing is left after trimming, **`return`** stops the function early, so blank tasks are ignored.

Notice that `addTask` only changes the **state**. It doesn't touch the page at all. Drawing is `render()`'s job.

## Drawing the tasks

Now let's turn the state into a page. We'll split the work into two functions:

- **`createTaskItem(task)`** builds and returns the `<li>` for **one** task.
- **`render()`** empties the list, then appends one item per task.

Each `<li>` remembers its task's id in a **data attribute** (`li.dataset.id`). We don't need it yet, but in Part 2 it's how a click will know which task it belongs to. Finished tasks get a `done` class, so CSS can cross them out.

const tasks = [
  { id: 1, text: "Water the bamboo", done: false },
  { id: 2, text: "Learn the DOM", done: true },
  { id: 3, text: "Nap in the sun", done: false },
];

function createTaskItem(task) {
  const li = document.createElement("li");
  li.dataset.id = task.id;
  if (task.done) {
    li.classList.add("done");
  }

  const text = document.createElement("span");
  text.className = "text";
  text.textContent = task.text;

  li.append(text);
  return li;
}

function render() {
  list.replaceChildren();
  tasks.forEach((task) => {
    list.append(createTaskItem(task));
  });
}

render();
console.log(list.children.length, "tasks on the page");`}
/>

Try changing `done: false` to `done: true` on the first task and press **Run**: the page follows the state.

<Callout type="danger" title="Tasks are user input, so use textContent">

Every task text is typed by a user. If you built the item with `` li.innerHTML = `<span>${task.text}</span>` ``, someone could type HTML (even a script) as a task, and it would run on the page. Creating elements and setting `textContent` is always safe, which is why `createTaskItem` does it that way.

</Callout>

## Connecting the form

The last piece is the form. You already know the recipe from the Events lesson:

1. Listen for **`submit`** on the `<form>` (that covers both the button and pressing Enter).
2. Call **`event.preventDefault()`** so the page doesn't reload.
3. **Change the state** with `addTask(input.value)`.
4. Clear the input and call **`render()`**.

```js
form.addEventListener("submit", (event) => {
  event.preventDefault();
  addTask(input.value);
  input.value = "";
  render();
});
```

And don't forget a `render()` call at the very **end** of your script, so the starting tasks are drawn when the page loads.

<Callout type="tip" title="Keep the jobs separate">

`addTask` changes the data, `render` draws the page, and the listener connects the two. Each function has **one job**. When something breaks, you'll know exactly where to look: wrong data means `addTask`, wrong page means `render`.

</Callout>

## What you built

- A clear **plan**: the state lives in one array, `render()` draws it, and every event changes the state and then renders.
- Tasks are **objects** `{ id, text, done }` in an array, and a `nextId` **counter** gives each one a unique id that never changes.
- **`addTask(text)`** trims the text and ignores blank input, without touching the page.
- **`createTaskItem(task)`** builds one `<li>` safely with `createElement` and `textContent`, and stores the id in `data-id`.
- **`render()`** rebuilds the whole list from the state, and a **submit** listener connects the form to it all.

In Part 2 you'll make the list interactive: ticking tasks off, deleting them and filtering them.
