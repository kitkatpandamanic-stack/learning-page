В уроке [Колбэки и цикл событий](/learn/javascript/callbacks-and-the-event-loop) вы познакомились с циклом событий (event loop): один поток, стек вызовов, очередь задач и микрозадачи, которые проходят без очереди. Этой картины хватает, чтобы писать асинхронный код. Но чтобы его **отлаживать** (интерфейс, который зависает; лог, который появляется в «неправильном» порядке; тест, который проходит отдельно и падает в общем прогоне), нужны точные правила. В этом уроке вы получите эти правила, а затем примените их: научитесь сохранять отзывчивость страниц и узнаете, чем цикл Node отличается от браузерного. 🔁

## Один поток, две очереди

JavaScript выполняет ваш код в **одном потоке (thread)**. Пока работает функция, в JavaScript больше ничего не происходит: ни другой колбэк, ни обработчик клика, а в браузере даже страница не перерисовывается. Всё, что случается «потом», ждёт в очереди:

| Очередь | Другое название | Что туда попадает |
| --- | --- | --- |
| **Очередь задач (task queue)** | очередь макрозадач (macrotask queue) | колбэки `setTimeout`/`setInterval`, события (клики, нажатия клавиш), сетевые сообщения и сообщения `MessageChannel`, сам скрипт |
| **Очередь микрозадач (microtask queue)** | job queue | реакции промисов (колбэки `.then`/`.catch`/`.finally`, код после `await`), `queueMicrotask`, `MutationObserver` |

Сам цикл короткий. В браузере один его оборот выглядит так:

```text
 ┌──────────────────────────────────────────────────────────┐
 │ 1. взять ОДНУ задачу из очереди задач и выполнить её     │
 │ 2. выполнить ВСЕ микрозадачи, включая поставленные       │
 │    микрозадачами, пока очередь микрозадач не опустеет    │
 │ 3. пора рисовать новый кадр? (примерно каждые 16,7 мс    │
 │    при 60 Гц) колбэки requestAnimationFrame → стили      │
 │      → раскладка (layout) → отрисовка (paint)            │
 │ 4. снова к шагу 1                                        │
 └──────────────────────────────────────────────────────────┘
```

Отсюда следуют два правила, и они объясняют почти любую головоломку с порядком вывода:

1. **Микрозадачи всегда выполняются до следующей задачи.** Колбэк `.then` обгоняет `setTimeout(fn, 0)`, даже если таймер поставили раньше.
2. **Очередь микрозадач опустошается полностью.** Если микрозадача ставит в очередь другую микрозадачу, та выполнится в том же обороте, раньше любой задачи.

## Точный порядок

Вот головоломка со всеми видами колбэков. Прочитайте её, запишите свой ответ и только потом проверьте:

<CodeExample output={`1: начало скрипта
2: конец скрипта
3: then 1
4: queueMicrotask
5: поставлено в очередь внутри then 1
6: then 2
7: тайм-аут 1
8: микрозадача из тайм-аута 1
9: тайм-аут 2`}>

```js
console.log("1: начало скрипта");

setTimeout(() => {
  console.log("7: тайм-аут 1");
  Promise.resolve().then(() => {
    console.log("8: микрозадача из тайм-аута 1");
  });
}, 0);
setTimeout(() => console.log("9: тайм-аут 2"), 0);

Promise.resolve()
  .then(() => {
    console.log("3: then 1");
    queueMicrotask(() => console.log("5: поставлено в очередь внутри then 1"));
  })
  .then(() => console.log("6: then 2"));

queueMicrotask(() => console.log("4: queueMicrotask"));
console.log("2: конец скрипта");
```

</CodeExample>

Разбор по шагам:

| Фаза | Печатает | Почему |
| --- | --- | --- |
| Скрипт (это задача) | 1, 2 | Синхронный код завершается первым. Он поставил два таймера и две микрозадачи (`then 1`, `queueMicrotask`). |
| Микрозадачи | 3, 4 | В том порядке, в каком их поставили. `then 1` ставит «5», а его завершение ставит `then 2`. |
| Всё ещё микрозадачи | 5, 6 | Очередь ещё не пуста, поэтому выполняются и они — по-прежнему до любого таймера. |
| Задача: тайм-аут 1 | 7 | Теперь цикл берёт первый таймер. Он ставит микрозадачу... |
| Микрозадачи | 8 | ...которая выполняется **до** следующей задачи. |
| Задача: тайм-аут 2 | 9 | |

Обратите внимание: `then 2` ждал, пока `then 1` **завершится**. Каждый `.then` в цепочке ставится в очередь только тогда, когда завершился предыдущий шаг. Поэтому «5», поставленное *внутри* `then 1`, обгоняет «6».

## async-функции — это цепочки промисов

`async`/`await` построены на промисах, поэтому действуют те же правила. Точная модель:

- Вызов `async`-функции выполняет её тело **синхронно** до первого `await`.
- `await x` приостанавливает функцию и **возвращает управление вызывающему коду**. Остаток функции ставится в очередь как **микрозадача (microtask)**, когда `x` завершится (даже если `x` вовсе не промис, как в `await null`).
- Сама `async`-функция всегда возвращает промис, который выполняется с тем, что она вернула через `return`.

<CodeExample output={`A: старт
B: старт
синхронный код закончился
A: после первого await
B: после первого await
A: после второго await
B: после второго await`}>

```js
async function task(name) {
  console.log(`${name}: старт`);
  await null;
  console.log(`${name}: после первого await`);
  await null;
  console.log(`${name}: после второго await`);
}

task("A");
task("B");
console.log("синхронный код закончился");
```

</CodeExample>

Два вызова **чередуются** на каждом `await`. Под капотом движок превращает функцию в нечто очень похожее на такую цепочку промисов:

```js
function task(name) {
  console.log(`${name}: старт`);
  return Promise.resolve(null)
    .then(() => {
      console.log(`${name}: после первого await`);
      return null;
    })
    .then(() => {
      console.log(`${name}: после второго await`);
    });
}
```

Два практических следствия:

- **Код до первого `await` синхронный.** Если он бросит ошибку, она всё равно превратится в отклонённый промис (а не в обычное исключение), поэтому вызывающий код должен сделать `await` или `.catch`.
- **Каждый `await` — это точка, где может выполниться другой код** и изменить общее состояние. Классическая гонка: `if (!cache.has(id)) { const user = await load(id); cache.set(id, user); }`, вызванный дважды подряд, запускает **две** загрузки, потому что оба вызова прошли проверку `has` до того, как хоть один миновал свой `await`. Решение — сразу класть в кэш **промис**; вы сделаете это в модуле о проектировании систем.

<Callout type="warning" title="Не полагайтесь на точное число микрозадач">

Сколько «прыжков» по микрозадачам делает `await`, менялось от версии к версии движков (например, `return await promise` против `return promise` в `async`-функции). Используйте правила выше, чтобы понимать код, но если программа работает правильно только потому, что один `await` обгоняет другой на один тик, — это состояние гонки (race condition). Сделайте порядок явным с помощью `await`, `Promise.all` или очереди.

</Callout>

## Голодание из-за микрозадач

У правила 2 есть тёмная сторона. Раз цикл опустошает **все** микрозадачи, прежде чем двигаться дальше, микрозадача, которая постоянно ставит новые микрозадачи, никогда не даст выполниться задаче. Это называется **голоданием (starvation)**:

<CodeExample output={`таймер наконец сработал после 100000 микрозадач`}>

```js
let count = 0;

setTimeout(() => {
  console.log(`таймер наконец сработал после ${count} микрозадач`);
}, 0);

function spin() {
  count++;
  if (count < 100_000) queueMicrotask(spin); // когда-нибудь остановится
}
queueMicrotask(spin);
```

</CodeExample>

Таймер всё это время был готов, но ему пришлось ждать 100 000 микрозадач. Без ограничения страница зависла бы точно так же, как при цикле `while (true)`: ни кликов, ни таймеров, ни перерисовки. То же самое происходит с рекурсивным циклом на промисах вроде `function poll() { return check().then(poll); }`, если `check()` выполняется сразу (например, из кэша). Всегда добавляйте **задачу** (таймер, сетевой запрос) в цикл, который может работать бесконечно.

## Отрисовка и requestAnimationFrame

В браузере экран можно обновить только **между задачами** (шаг 3 цикла). Пока ваш код работает, страница застыла в старом состоянии, поэтому этот код покажет только последнее число:

```js
for (let i = 1; i <= 100; i++) {
  progress.textContent = `${i}%`; // пользователь увидит только 100%
}
```

Для анимаций используйте **`requestAnimationFrame(callback)`**. Браузер вызывает колбэк прямо перед отрисовкой следующего кадра, один раз за кадр, в такт с частотой обновления экрана (и приостанавливает его в фоновых вкладках, чтобы экономить батарею):

```js
function animate(time) {
  // time: миллисекунды с момента загрузки страницы
  box.style.transform = `translateX(${(time / 10) % 300}px)`;
  requestAnimationFrame(animate); // просим следующий кадр
}
requestAnimationFrame(animate);
```

`setTimeout(animate, 16)` выглядит похоже, но постепенно рассинхронизируется с экраном, вызывает рывки и продолжает работать в скрытых вкладках.

## Длинные задачи: сохраняем отзывчивость страницы

При 60 кадрах в секунду у браузера примерно **16 мс** на кадр. **Длинная задача (long task)** — это любая задача дольше **50 мс**; пока она идёт, страница не может реагировать. Пользователи замечают задержку примерно со 100 мс. Метрика Core Web Vitals **INP** (Interaction to Next Paint) измеряет именно это: сколько времени проходит от клика или нажатия клавиши до того, как на экране появится результат. Длинные задачи — её главная причина.

Когда в основном потоке нужно сделать много работы (отфильтровать 50 000 строк, разобрать большой файл), разбейте её на **порции (chunks)** и между ними **уступайте (yield)** циклу событий, дожидаясь новой задачи. Другие задачи (клик, таймер, отрисовка) получат свою очередь в промежутках:

<CodeExample output={`обработано 1, 2
🖱️ клик обработан
обработано 3, 4
обработано 5, 6
всё готово`}>

```js
const nextTask = () => new Promise((r) => setTimeout(r, 0));

async function processAll(items, chunkSize) {
  for (let i = 0; i < items.length; i += chunkSize) {
    const chunk = items.slice(i, i + chunkSize);
    console.log(`обработано ${chunk.join(", ")}`);
    await nextTask(); // пропускаем клик (и отрисовку)
  }
  console.log("всё готово");
}

// Пользователь кликает, пока мы заняты
setTimeout(() => console.log("🖱️ клик обработан"), 0);
processAll([1, 2, 3, 4, 5, 6], 2);
```

</CodeExample>

Без `await nextTask()` клик ждал бы, пока не закончатся все порции. Учтите, что `await null` или `await Promise.resolve()` **не** помогли бы: после них выполнение продолжается микрозадачей, а она выполняется раньше задачи клика и раньше отрисовки.

В новых браузерах есть инструмент получше — **`scheduler.yield()`**. Он уступает управление, как таймер, но ваш код продолжается в **начале** очереди, а не в конце, так что другой код не может отодвигать вашу работу всё дальше и дальше (и на него не влияет то, что браузеры ограничивают вложенные таймеры минимумом в 4 мс). Он есть ещё не во всех браузерах, поэтому проверяйте его наличие:

```js
const yieldToMain = () =>
  globalThis.scheduler?.yield
    ? scheduler.yield()
    : new Promise((resolve) => setTimeout(resolve, 0));

for (const row of rows) {
  render(row);
  if (performance.now() - lastYield > 40) {
    await yieldToMain();
    lastYield = performance.now();
  }
}
```

Если уступать по **времени** (каждые ~40 мс), а не каждые N элементов, код подстраивается и под быстрые, и под медленные устройства. А когда работа — это чистые вычисления без DOM, вынесите её из основного потока целиком в **Web Worker** (вы сделаете это в модуле о производительности).

<Callout type="tip" title="История из практики">

Команда, делавшая дашборд, не могла понять, почему ввод в поле поиска «залипает» на офисных ноутбуках, но нормально работает на их MacBook. Профилирование показало задачу на 400 мс при каждом нажатии клавиши: заново фильтровались и отрисовывались сразу 20 000 строк. Debounce для ввода и отрисовка результатов порциями сократили задачи до менее чем 30 мс, хотя ничего не стало «быстрее». Отзывчивость определяется **самой длинной** задачей, а не общим временем.

</Callout>

## Цикл событий в Node

Node.js использует те же правила языка (задачи, микрозадачи, промисы), но его цикл берётся из C-библиотеки **libuv** и работает **фазами (phases)**. Каждый оборот проходит их по порядку и выполняет все микрозадачи после каждого отдельного колбэка:

```text
 ┌─▶ timers          колбэки setTimeout / setInterval, которым пора сработать
 │   pending         некоторые системные колбэки (например, ошибки TCP)
 │   poll            ожидание ввода-вывода; его колбэки (файлы, сеть)
 │   check           колбэки setImmediate
 └── close           события 'close' (сокеты, дескрипторы)
```

В Node есть ещё две функции планирования, которых нет в браузере. Вот что они печатают в Node на вашем компьютере:

```js title="order.cjs"
const fs = require("node:fs");

setTimeout(() => console.log("timeout"), 0);
setImmediate(() => console.log("immediate"));
Promise.resolve().then(() => console.log("promise"));
process.nextTick(() => console.log("nextTick"));
console.log("sync");

fs.readFile(__filename, () => {
  setTimeout(() => console.log("io: timeout"), 0);
  setImmediate(() => console.log("io: immediate"));
});
```

```bash
node order.cjs
# sync
# nextTick
# promise
# timeout        (порядок timeout и immediate здесь не гарантирован!)
# immediate
# io: immediate  (внутри колбэка ввода-вывода: всегда первым)
# io: timeout
```

- **`process.nextTick(fn)`** выполняет `fn`, как только завершится текущая операция, **раньше** микрозадач промисов (в CommonJS; в ES-модуле сам код модуля выполняется внутри задания промиса, поэтому `promise` печатается раньше `nextTick`). Он ещё срочнее микрозадачи, а значит, тоже может заморить цикл голодом. Документация Node советует для большей части нового кода `queueMicrotask`.
- **`setImmediate(fn)`** выполняет `fn` в фазе **check**, сразу после ввода-вывода. Внутри колбэка ввода-вывода он всегда обгоняет `setTimeout(fn, 0)`; на верхнем уровне их порядок зависит от того, как быстро запустился процесс. Это лучший в Node способ «уступить циклу».

Правило для серверов то же, что и для страниц: длинная синхронная задача (огромный `JSON.parse`, медленное регулярное выражение, `bcrypt.hashSync`) блокирует **все** запросы этого процесса, а не только текущий.

## Асинхронная итерация

Некоторые данные приходят постепенно: страницы из API, строки из файла, сообщения из сокета. **Асинхронная итерация (async iteration)** позволяет перебирать их в цикле, как массив. **Асинхронный генератор (async generator)** (`async function*`) умеет и `await`, и `yield`, а **`for await...of`** дожидается каждого значения:

<CodeExample output={`(загружена страница 1 из 3)
The Bamboo Heist 7.8
Panda Express to Mars 6.9
Midnight in the Forest 8.1
The Last Dumpling 7.2
(загружена страница 2 из 3)
Code Red 6.4
Snow Leopard Summer 7.6
Остановились раньше: страница 3 так и не загружена`}>

```js
const API = "https://api.pandadev.test";

async function* allMovies() {
  for (let page = 1; ; page++) {
    const res = await fetch(`${API}/movies?limit=4&page=${page}`);
    const data = await res.json();
    console.log(`(загружена страница ${page} из ${data.totalPages})`);
    yield* data.results; // отдаём фильмы этой страницы по одному
    if (page >= data.totalPages) return;
  }
}

let shown = 0;
for await (const movie of allMovies()) {
  console.log(movie.title, movie.rating);
  if (++shown === 6) break; // заодно завершает генератор
}
console.log("Остановились раньше: страница 3 так и не загружена");
```

</CodeExample>

(В PandaDev встроен учебный API, поэтому пример работает офлайн и каждый раз даёт одинаковые ответы. Настоящие API с пагинацией работают так же.)

Генератор **ленивый (lazy)**: он загружает следующую страницу, только когда цикл просит новые значения, а `break` останавливает его навсегда. Вызывающий код вообще не знает о страницах и не думает о них. За кулисами `for await` вызывает у объекта метод `[Symbol.asyncIterator]()` и ждёт каждый `next()` — это асинхронный двойник протокола итерации из урока [Map, Set и генераторы](/learn/javascript/map-set-and-generators). Потоки Node, файловые дескрипторы `fs.promises` и веб-`ReadableStream` тоже асинхронно итерируемые:

```js
// В Node на вашем компьютере: читаем большой файл построчно
import { createReadStream } from "node:fs";
import { createInterface } from "node:readline";

const lines = createInterface({ input: createReadStream("big.log") });
for await (const line of lines) {
  if (line.includes("ERROR")) console.log(line);
}
```

`processInChunks(items, chunkSize, work)` вызывает `work(item, index)` для каждого элемента и выполняется с массивом результатов — как асинхронный `map`. Сейчас она делает всё в одной длинной задаче, поэтому клику в демо приходится ждать. Сделайте так, чтобы она **уступала** циклу событий:

1. Обрабатывайте по `chunkSize` элементов за раз. **Первую** порцию начинайте сразу (синхронно, в момент вызова функции).
2. Между порциями дожидайтесь **новой задачи** через `setTimeout(..., 0)`, чтобы могли выполниться таймеры, клики и отрисовка. (Микрозадача вроде `await null` не подойдёт: попробуйте и посмотрите, как проверки упадут!)
3. Выполняйте промис со всеми результатами в исходном порядке. Демо должно напечатать сначала клик, а затем `1 4 9 16 25 36 49 64 81 100`.

Сделайте помощник `const nextTask = () => new Promise((resolve) => setTimeout(resolve, 0));`. Перебирайте начала порций циклом `for (let start = 0; start < items.length; start += chunkSize)`, а в начале тела цикла напишите `if (start > 0) await nextTask();`.
```js
const nextTask = () => new Promise((resolve) => setTimeout(resolve, 0));

async function processInChunks(items, chunkSize, work) {
  const results = [];
  for (let start = 0; start < items.length; start += chunkSize) {
    if (start > 0) await nextTask(); // даём выполниться другим задачам
    const end = Math.min(start + chunkSize, items.length);
    for (let i = start; i < end; i++) {
      results.push(work(items[i], i));
    }
  }
  return results;
}

const ids = Array.from({ length: 10 }, (_, i) => i + 1);
setTimeout(() => console.log("🖱️ клик обработан"), 0);
const squares = await processInChunks(ids, 4, (n) => n * n);
console.log(squares.join(" "));
```

## Итоги

- Один оборот цикла: выполнить **одну задачу**, затем **все микрозадачи** (включая новые), затем, возможно, **отрисовка** (rAF → стили → раскладка → отрисовка).
- Задачи: таймеры, события, сообщения. Микрозадачи: реакции промисов, код после `await`, `queueMicrotask`. Микрозадачи всегда выполняются раньше следующей задачи.
- `async`-функция выполняется синхронно до первого `await`; остальное продолжается микрозадачами. Каждый `await` — точка, где может выполниться другой код, поэтому следите за гонками в общем состоянии.
- Бесконечные микрозадачи **морят цикл голодом** так же, как бесконечный цикл; добавляйте где-нибудь настоящую задачу.
- Задачи дольше **50 мс** — длинные задачи, и они ухудшают **INP**. Разбивайте работу на порции и уступайте через **задачу** (`setTimeout(…, 0)`, `scheduler.yield()`), а не через микрозадачу; для анимаций используйте `requestAnimationFrame`, для тяжёлых вычислений — Web Workers.
- У цикла Node есть **фазы** (timers, poll, check...). `process.nextTick` выполняется раньше микрозадач промисов (в CommonJS); `setImmediate` — после ввода-вывода.
- **Асинхронные генераторы** и `for await...of` превращают данные, приходящие постепенно (страницы, строки, сообщения), в ленивый цикл; `break` останавливает источник данных.
