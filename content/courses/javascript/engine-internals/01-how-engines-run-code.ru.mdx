Вы уже умеете собрать протестированный API на Express и React-приложение, которое с ним общается. Это настоящая инженерия. Но рано или поздно вам попадётся баг, который можно понять, только если знать, что делает **движок (engine)**: метод, который «забывает» свой объект, когда его передают как колбэк; переменная, которая существует, но её нельзя прочитать; функция, которая быстрая в бенчмарке и медленная в продакшене. В этом модуле мы заглянем под капот. Первый урок проследит путь вашего кода от текста до машинного кода и объяснит правила, по которым движок действует по дороге. 🔧

## Движки: программы, которые выполняют JavaScript

JavaScript — это язык, описанный спецификацией **ECMAScript**, которую пишет комитет **TC39**. Новая редакция выходит каждый год (ES2024, ES2025...). Спецификация говорит, что код должен *делать*, но не как сделать это быстро. Это работа **движка**:

| Движок | Кто делает | Где работает |
| --- | --- | --- |
| **V8** | Google | Chrome, Edge, Node.js, Deno, Electron |
| **SpiderMonkey** | Mozilla | Firefox |
| **JavaScriptCore** | Apple | Safari, все браузеры на iOS, Bun |

Движок — это только половина истории. Он ничего не знает о страницах, таймерах и файлах. Всё это даёт **хост-среда (host)**: браузер добавляет `document`, `fetch` и `setTimeout`, а Node.js — `fs`, `process` и `http`. Поэтому один и тот же `Array.prototype.map` работает везде, а `document` в Node не существует.

## От исходного кода к машинному

Все современные движки следуют примерно одному и тому же конвейеру. Вот он с названиями частей из V8:

```text
 исходный код (текст)
       │  парсер
       ▼
 AST (абстрактное синтаксическое дерево: структура вашего кода)
       │  генератор байт-кода
       ▼
 байт-код ──────▶ интерпретатор Ignition: сразу начинает выполнять код
       │          и записывает «обратную связь о типах» (что он реально видел)
       │  функция «горячая» (вызывается часто)?
       ▼
 Sparkplug / Maglev / TurboFan: оптимизирующие JIT-компиляторы
 строят быстрый машинный код, который ПРЕДПОЛАГАЕТ уже виденные типы
       │  предположение нарушено (строка там, где были числа)?
       ▼
 деоптимизация: машинный код выбрасывается, назад к байт-коду
```

По шагам:

1. **Парсинг (parsing).** Парсер читает весь скрипт и строит **AST**. Если где-то есть синтаксическая ошибка, не выполнится ничего, даже строка 1. (Тела функций движки разбирают **лениво (lazily)**: сначала лишь быстро проверяют их, а полную структуру строят при первом вызове функции. Так страницы запускаются быстрее.)
2. **Байт-код (bytecode).** AST превращается в **байт-код** — компактные инструкции для виртуальной машины. **Интерпретатор (interpreter)** сразу же его выполняет. Для кода, который запускается один раз, быстрый старт важнее быстрой работы.
3. **JIT-компиляция.** Во время интерпретации движок наблюдает. Когда функция становится **горячей (hot)**, оптимизирующий **JIT-компилятор (just-in-time compiler)** превращает её в машинный код, опираясь на увиденное: «`add` до сих пор вызывали только с маленькими целыми числами — скомпилируем целочисленное сложение».
4. **Деоптимизация (deoptimisation).** Если предположение оказалось неверным (теперь в `add` пришла строка), движок **деоптимизирует** функцию: выбрасывает машинный код и продолжает в интерпретаторе. Программа по-прежнему работает правильно, просто медленнее, пока движок не оптимизирует её заново.

Правило «сначала парсинг» можно проверить самим. `new Function(source)` разбирает код, но не выполняет его:

<CodeExample output={`SyntaxError
Ничего не выполнилось, даже строка 1`}>

```js
const source = `
  console.log("строка 1 выполнилась");
  let total = ;
`;

try {
  new Function(source); // только парсинг
} catch (error) {
  console.log(error.name);
  console.log("Ничего не выполнилось, даже строка 1");
}
```

</CodeExample>

На вашем компьютере Node.js может показать JIT в действии. Здесь `add` оптимизируется, а потом получает строку:

```js title="deopt.js"
function add(a, b) {
  return a + b;
}
for (let i = 0; i < 100_000; i++) add(i, 1); // горячая: оптимизируем
add("panda", 1); // сюрприз!
```

```bash
node --trace-opt --trace-deopt deopt.js
# [marking <JSFunction add> for optimization to MAGLEV,
#    reason: hot and stable]
# [bailout (kind: deopt-eager, reason: not a Smi):
#    deoptimizing <JSFunction add>]
```

«Smi» означает *small integer* (маленькое целое) — быстрый формат чисел в V8. Оптимизированный код поставил на целые числа и проиграл. Одна деоптимизация безвредна. А функция, которая деоптимизируется снова и снова, потому что каждый раз получает другой тип, так никогда и не станет быстрой.

<Callout type="tip" title="Что это значит для повседневного кода">

Вы не пишете код *для* JIT. Вы пишете **скучный, последовательный** код, и JIT вас за это вознаграждает: функции получают аргументы одних и тех же типов, массивы хранят значения одного вида, объекты сохраняют одну и ту же форму. Код вроде `function process(x)`, который принимает число, строку, массив *или* объект, тяжело читать людям и тяжело оптимизировать движку.

</Callout>

## Скрытые классы и инлайн-кэши

Объекты в JavaScript выглядят как гибкие словари: добавляйте свойства когда угодно. Наивный движок хранил бы каждый объект как хеш-таблицу и каждый раз искал бы `point.x` по имени. Это медленно, поэтому движки тайно назначают объектам **форму (shape)** (в V8 её называют *скрытым классом (hidden class)* или *map*). Форма записывает, какие свойства есть у объекта, **в каком порядке** и где каждое лежит в памяти:

```text
const a = { x: 1, y: 2 };     форма S1: x в ячейке 0, y в ячейке 1
const b = { x: 5, y: 9 };     снова форма S1 (те же ключи, тот же порядок)
const c = { y: 2, x: 1 };     форма S2: y в ячейке 0, x в ячейке 1
```

Объекты с одинаковой формой делят её между собой, поэтому на каждый объект форма почти ничего не стоит. А теперь самое хитрое — **инлайн-кэш (inline cache)**. Когда строка вроде `total += point.x` выполняется впервые, движок честно ищет `x` и запоминает: «у формы S1 `x` лежит в ячейке 0». Когда в этом месте снова попадётся объект формы S1, поиск будет пропущен целиком. Место обращения к свойству, которое видит только одну форму, называется **мономорфным (monomorphic)** — это быстро. Несколько форм делают его **полиморфным (polymorphic)** — немного медленнее. Много форм делают его **мегаморфным (megamorphic)**: движок отказывается от кэширования и каждый раз выполняет медленный поиск.

**Порядок** свойств — часть формы, и объекты действительно его запоминают:

<CodeExample output={`[ 'x', 'y' ] [ 'y', 'x' ]
User { id: 1, name: 'Mei', email: undefined }
[ 'id', 'name', 'email' ]`}>

```js
const a = { x: 1, y: 2 };
const b = { y: 2, x: 1 };
console.log(Object.keys(a), Object.keys(b)); // две формы

class User {
  constructor(id, name, email) {
    // Все поля, каждый раз, в одном порядке: одна форма
    this.id = id;
    this.name = name;
    this.email = email; // даже если это undefined
  }
}
const mei = new User(1, "Mei");
console.log(mei);
console.log(Object.keys(mei));
```

</CodeExample>

Привычки, которые сохраняют формы стабильными:

- **Инициализируйте все поля в конструкторе** (или как поля класса) в одном и том же порядке, даже если значение пока `null` или `undefined`. Не добавляйте свойства позже в случайных местах.
- **Не удаляйте свойства через `delete`** у объектов, которыми продолжаете пользоваться. В V8 `delete` часто переводит объект в медленный «режим словаря» (dictionary mode). Присвойте свойству `undefined` или соберите новый объект без него: `const { password, ...safeUser } = user;`.
- Если объект действительно словарь (ключи берутся из данных, постоянно добавляются и удаляются), используйте **`Map`**. Он для этого и создан.

На своём компьютере можно спросить V8 напрямую с помощью отладочного флага (эти функции с `%` — не настоящий JavaScript, они работают только с флагом):

```js title="shapes.js"
class Point {
  constructor(x, y) {
    this.x = x;
    this.y = y;
  }
}
const a = new Point(1, 2);
const b = new Point(3, 4);
const c = { y: 4, x: 3 };
const d = new Point(5, 6);
d.z = 7;
const e = new Point(1, 2);
delete e.y;

console.log(%HaveSameMap(a, b)); // true
console.log(%HaveSameMap(a, c)); // false: другой порядок
console.log(%HaveSameMap(a, d)); // false: лишнее свойство
console.log(%HasFastProperties(e)); // false: режим словаря
```

```bash
node --allow-natives-syntax shapes.js
```

Насколько это важно? Запустите этот бенчмарк сами. Он суммирует одни и те же числа из объектов одной формы и из объектов 30 разных форм. На обычном ноутбуке вариант с множеством форм примерно **в 3 раза медленнее**, но точные цифры зависят от компьютера и браузера, так что не верьте ничьим цифрам (включая наши), пока не измерите сами:

## Контексты выполнения и стек вызовов

Каждый раз, когда вызывается функция, движок создаёт для неё **контекст выполнения (execution context)**: её параметры и локальные переменные, ссылку на область видимости, в которой она определена (так работают [замыкания](/learn/javascript/closures-and-higher-order-functions)), и её значение `this`. Контексты хранятся в **стеке вызовов (call stack)**: вызов функции **кладёт (push)** контекст на стек, возврат из неё **снимает (pop)** его. Движок всегда выполняет то, что лежит на вершине.

<CodeExample output={`global: вызываем greet
  greet: вызываем shout
    shout: я на вершине стека
  greet: shout вернула результат
global: ПРИВЕТ, MEI!`}>

```js
function shout(text) {
  console.log("    shout: я на вершине стека");
  return text.toUpperCase() + "!";
}

function greet(name) {
  console.log("  greet: вызываем shout");
  const message = shout(`привет, ${name}`);
  console.log("  greet: shout вернула результат");
  return message;
}

console.log("global: вызываем greet");
console.log("global:", greet("mei"));
```

</CodeExample>

В самой глубокой точке на стеке три контекста: глобальный код, `greet` и `shout`. **Трассировка стека (stack trace)** — это снимок стека вызовов в момент, когда была создана ошибка. Читайте её сверху: первая строка — место, где всё сломалось, каждая следующая — «кто это вызвал»:

```text
TypeError: Cannot read properties of undefined (reading 'toUpperCase')
    at shout (app.js:2:15)
    at greet (app.js:7:19)
    at app.js:13:29
```

У стека фиксированный размер (около десяти тысяч кадров в Chrome и Node, больше в Firefox). Рекурсия без работающего базового случая его переполняет:

<CodeExample output={`1000
RangeError
Слишком глубоко: используйте цикл или явный стек`}>

```js
// Считает, на сколько вызовов в глубину она уходит
function depth(n) {
  if (n === 0) return 0;
  return 1 + depth(n - 1);
}

console.log(depth(1_000));

try {
  depth(1_000_000);
} catch (error) {
  console.log(error.name);
  console.log("Слишком глубоко: используйте цикл или явный стек");
}
```

</CodeExample>

Chrome, Node и Safari бросают `RangeError: Maximum call stack size exceeded`, а Firefox называет это `InternalError: too much recursion`. Рекурсия отлично подходит для древовидных данных разумной глубины (меню, ветки комментариев, JSON-документ). Когда глубина зависит от **пользовательских данных** (связный список из 100 000 элементов, глубоко вложенный JSON, который кто-то прислал в ваш API), используйте цикл. Злоумышленники знают, что «прислать что-нибудь глубиной 100 000 уровней» роняет наивные рекурсивные парсеры.

## Hoisting и временная мёртвая зона

Прежде чем выполнить функцию (или скрипт), движок просматривает её и создаёт все объявленные в ней переменные. Это называется **поднятием (hoisting)**, и каждый вид объявления подготавливается по-своему:

| Объявление | В начале своей области видимости создаётся как... | Использование до этой строки |
| --- | --- | --- |
| `function greet() {}` | готовая функция | работает |
| `var count` | `undefined` | молча даёт `undefined` |
| `let`, `const`, `class` | **неинициализированная** переменная | `ReferenceError` |

Промежуток от начала области видимости до строки объявления, когда `let`/`const`/`class` уже существует, но трогать её нельзя, называется **временной мёртвой зоной (temporal dead zone, TDZ)**:

<CodeExample output={`function
undefined
ReferenceError`}>

```js
console.log(typeof helper); // поднята целиком
console.log(count); // поднята, но значение — нет
var count = 5;

function helper() {
  return "Меня можно вызвать до моей строки";
}

try {
  console.log(total); // во временной мёртвой зоне
  const total = 10;
} catch (error) {
  console.log(error.name);
}
```

</CodeExample>

TDZ — это не баг, а возможность: чтение переменной до того, как она получила значение, почти всегда ошибка, и `let`/`const` превращают её в громкую ошибку вместо тихого `undefined`. Ещё TDZ ловит коварный баг с **затенением (shadowing)**:

<CodeExample output={`ReferenceError
12`}>

```js
const price = 10;

function withTax() {
  // Этот `price` — НОВЫЙ, объявленный ниже, он ещё в своей TDZ
  const price = price * 1.2;
  return price;
}

try {
  withTax();
} catch (error) {
  console.log(error.name);
}

function withTaxFixed() {
  const total = price * 1.2; // другое имя: никакого затенения
  return total;
}
console.log(withTaxFixed());
```

</CodeExample>

Поскольку объявления функций поднимаются целиком, во многих проектах основную логику пишут в начале файла, а вспомогательные функции — ниже. С классами так нельзя: `new Panda()` выше `class Panda {}` бросит ошибку.

## Как определяется this

`this` сбивает с толку даже опытных разработчиков, потому что он определяется **не** там, где функция написана. У обычных функций он определяется **в момент вызова** — тем, **как** функцию вызвали. Движок проверяет эти правила по порядку:

| Как вызвана | `this` — это |
| --- | --- |
| `new Thing()` | только что созданный объект |
| `fn.call(obj, ...)`, `fn.apply(obj, [...])` или функция из `fn.bind(obj)` | `obj` |
| `obj.fn()` (**вызов метода**: прямо перед вызовом стоит точка или `[]`) | `obj` |
| `fn()` (**простой вызов**) | `undefined` в строгом режиме (модули, классы, этот раннер); глобальный объект в старых нестрогих скриптах |
| **стрелочная функция**, как бы её ни вызвали | `this` окружающего кода, зафиксированный при создании стрелки |

<CodeExample output={`Mei
никто (undefined)
Bao
Bao
Bao
никто (undefined)`}>

```js
function whoAmI() {
  return this === undefined ? "никто (undefined)" : this.name;
}

const mei = { name: "Mei", whoAmI };
const bao = { name: "Bao" };

console.log(mei.whoAmI()); // вызов метода: this = mei
console.log(whoAmI()); // простой вызов: undefined
console.log(whoAmI.call(bao)); // явно: this = bao

const boundToBao = whoAmI.bind(bao);
console.log(boundToBao()); // привязана навсегда
console.log(boundToBao.call(mei)); // bind сильнее call

const detached = mei.whoAmI; // просто функция, без объекта
console.log(detached()); // снова простой вызов!
```

</CodeExample>

Последняя строка — ключ ко всему: `mei.whoAmI` — это просто **ссылка на функцию**. Функция не принадлежит `mei`. Единственное, что делало `this` равным `mei`, — это `mei.` перед вызовом, и как только вы сохранили функцию в другом месте, этого больше нет.

### Стрелочные функции заимствуют this

У стрелочных функций нет своего `this`. Они используют `this` окружающего кода — именно это и нужно для колбэков внутри методов:

<CodeExample output={`[ 'Mei из команды Панды', 'Bao из команды Панды' ]
[ 'Mei из команды undefined', 'Bao из команды undefined' ]`}>

```js
const team = {
```

Обратная сторона: **не** используйте стрелочную функцию как метод объекта (`{ name: "Mei", hi: () => this.name }`). Она заимствует `this` снаружи объекта, а не сам объект.

### Баг с потерянным this в колбэке

Это классика. Вы передаёте метод как колбэк, а тот, кто вызовет его позже, вызывает его **просто**:

<CodeExample output={`TypeError

3`}>

```js
class Stopwatch {
  seconds = 0;

  tick() {
    this.seconds++;
  }
}

const watch = new Stopwatch();
const tick = watch.tick; // то же самое, что setInterval(watch.tick, 1000)

try {
  tick(); // this — undefined: this.seconds падает
} catch (error) {
  console.log(error.name);
}

// Способ 1: обернуть в стрелку, чтобы снова получился вызов метода
const viaArrow = () => watch.tick();
viaArrow();
console.log(watch.seconds);

// Способ 2: привязать через bind
const bound = watch.tick.bind(watch);
bound();
console.log(watch.seconds);

// Способ 3: стрелочная функция в поле класса
class SafeStopwatch {
  seconds = 0;
  tick = () => {
    this.seconds++; // `this` — всегда экземпляр
  };
}
const safe = new SafeStopwatch();
const safeTick = safe.tick;
safeTick();
safeTick();
safeTick();
console.log(safe.seconds);
```

</CodeExample>

Этот баг встречается в виде `setTimeout(this.save, 1000)`, `button.addEventListener("click", this.open)` (где `this` становится **кнопкой**, а не вашим объектом), `promise.then(this.handle)` или деструктуризации `const { tick } = watch`. Какой способ выбрать?

- **Обёртка-стрелка** в месте вызова — самый явный и самый распространённый вариант.
- **Стрелочные поля класса** делают метод безопасным для передачи куда угодно. Цена: у каждого экземпляра своя копия функции (она не общая в прототипе), и подклассы не могут вызвать её через `super.tick()`. Отлично для обработчиков событий, расточительно для класса с миллионом экземпляров.
- **`bind`** в конструкторе (`this.tick = this.tick.bind(this)`) делает то же самое; вы встретите это в старых классовых компонентах React.

<Callout type="warning" title="this внутри обработчиков событий">

При `element.addEventListener("click", function () { ... })` браузер вызывает вашу функцию с `this`, равным элементу. Некоторый старый код на это полагается. В новом коде используйте `event.currentTarget`: это явно и одинаково работает в стрелочных функциях.

</Callout>

## Итоги

- JavaScript описан спецификацией **ECMAScript**; выполняют его **движки** (V8, SpiderMonkey, JavaScriptCore), а **хост-среда** (браузер, Node.js) добавляет API вроде `document`, `fetch` и `fs`.
- Код **разбирается** в AST (синтаксическая ошибка где угодно останавливает всё), превращается в **байт-код** для интерпретатора, а горячие функции **JIT-компилируются** с учётом увиденных типов. Когда предположение нарушается, движок **деоптимизирует** код.
- Объекты получают скрытые **формы**; **инлайн-кэши** делают обращение к свойству быстрым, когда место видит одну форму. Инициализируйте все поля в конструкторе в одном порядке, избегайте `delete`, используйте `Map` для настоящих словарей.
- Каждый вызов кладёт **контекст выполнения** на **стек вызовов**; трассировку стека читают сверху вниз; неконтролируемая рекурсия бросает `RangeError` (`InternalError` в Firefox), поэтому для глубины, зависящей от данных, используйте циклы.
- **Hoisting**: объявления функций готовы сразу, `var` начинается с `undefined`, а `let`/`const`/`class` находятся во **временной мёртвой зоне** до своей строки.
- `this` определяется **вызовом**: `new`, затем `call`/`apply`/`bind`, затем `obj.method()`, иначе `undefined` в строгом режиме. **Стрелочные функции** заимствуют `this` у окружения. Передача `obj.method` как колбэка теряет `this`: чините обёрткой-стрелкой, `bind` или стрелочными полями класса.
