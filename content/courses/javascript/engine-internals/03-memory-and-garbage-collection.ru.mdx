В JavaScript есть **сборщик мусора (garbage collector)**: вы никогда не освобождаете память вручную, и у вас не бывает ошибок «использования после освобождения» (use-after-free), которые мучают программистов на C. Значит, память — не ваша забота? Спросите любого, кто держал одностраничное приложение открытым во вкладке целый день или неделю гонял сервер на Node. Вкладка постепенно разрастается до 2 ГБ и начинает тормозить; график памяти сервера поднимается лесенкой, пока процесс не убьют и не перезапустят. Сборщик мусора освобождает то, что **недостижимо (unreachable)**, а утечки случаются, когда ваш код случайно оставляет что-то достижимым. В этом уроке вы увидите, как рассуждает сборщик, и разберёте несколько шаблонов, которые стоят почти за каждой реальной утечкой. 🧹

## Стек и куча

Работающая программа хранит данные в двух местах:

- **Стек (stack)** содержит стек вызовов, с которым вы познакомились в [первом уроке этого модуля](/learn/javascript/how-engines-run-code): по одному кадру на каждую работающую функцию, с её локальными переменными. Он маленький, быстрый и убирает за собой сам: когда функция возвращает результат, её кадр исчезает.
- **Куча (heap)** — большой пул памяти для всего, что должно пережить один вызов или чей размер заранее неизвестен: объектов, массивов, функций, замыканий, Map, длинных строк.

Переменная, в которой лежит объект, хранит не сам объект, а **ссылку (reference)** — стрелку, указывающую в кучу. Копируя переменную, вы копируете стрелку:

<CodeExample output={`Bao
Bao`}>

```js
let a = { name: "Mei" }; // объект живёт в куче
let b = a; // копируется ссылка, а не объект
b.name = "Bao";
console.log(a.name); // один объект, две стрелки

a = null; // убираем одну стрелку...
console.log(b.name); // ...объект всё ещё достижим через b

b = null; // стрелок не осталось: теперь это мусор
```

</CodeExample>

(Движки хитро выбирают, где физически хранить данные; например, маленькие числа обычно хранятся напрямую, а не в куче. Но для утечек важна модель «ссылки на объекты в куче».)

## Достижимость и mark-and-sweep

Сборщик мусора задаёт себе один вопрос: **может ли программа ещё добраться до этого объекта?** Он начинает с **корней (roots)**:

- глобальных переменных (`globalThis`, переменные уровня модуля в долгоживущем модуле);
- локальных переменных всех функций на стеке вызовов;
- всего, что хост-среда хранит для вас: ожидающих таймеров и их колбэков, обработчиков событий на живых DOM-узлах, ожидающих промисов с подписанными колбэками, открытых сокетов.

От корней он проходит по каждой ссылке (свойствам, элементам массивов, записям Map, переменным, захваченным замыканиями...) и **помечает (mark)** всё, до чего может добраться. Затем он **подметает (sweep)**: всё непомеченное освобождается. Отсюда название алгоритма — **mark-and-sweep** («пометить и подмести»).

```text
 корни ─▶ app ─▶ store ─▶ listeners ─▶ [fn1, fn2]
                   │                     │
                   └─▶ state             └─▶ (замыкание) bigData ✓

 oldPage ◀─▶ oldHeader      (указывают друг на друга, но на них не
                             указывает ничего достижимого: оба освобождены)
```

Два следствия:

- **Циклы — не проблема.** Два объекта, указывающие друг на друга, но недостижимые ни из одного корня, собираются вместе. (Старый Internet Explorer вместо этого считал ссылки и терял память на циклах; современные движки так не делают.)
- **Утечка — это просто забытая ссылка.** Память, которая вам больше не нужна, но всё ещё достижима из корня, никогда не может быть освобождена. Сборщик делает свою работу идеально; ошибка — в ваших ссылках.

## Сборка мусора по поколениям

Пометить всю кучу — это время, а пока сборщик работает, вашему JavaScript, возможно, придётся постоять на паузе. Движки делают это дешёвым благодаря одному наблюдению — **гипотезе о поколениях (generational hypothesis)**: *большинство объектов умирают молодыми*. Временный массив внутри `map`, объект, который вы возвращаете из функции и тут же деструктурируете, строки, которые вы собираете для строки лога, — всё это становится мусором за микросекунды.

Поэтому куча делится на две части (названия из V8):

| Область | Что там живёт | Как она очищается |
| --- | --- | --- |
| **Молодое поколение (young generation)**, «ясли» (nursery) | новые объекты | Часто и быстро: **scavenger** копирует наружу немногих выживших и стирает остальное за один раз. Его стоимость зависит от числа выживших, а не от количества мусора. |
| **Старое поколение (old generation)** | объекты, пережившие пару сборок молодого поколения | Редко: полная сборка **mark-sweep-compact**, в основном **инкрементально** (небольшими кусочками между вашими задачами) и **параллельно** во вспомогательных потоках, чтобы паузы были короткими. |

Что это значит на практике: короткоживущий мусор дешёвый, но не бесплатный. Горячий цикл, который выделяет миллионы маленьких объектов в секунду, загружает scavenger работой (это называется **нагрузкой на GC (GC pressure)** и видно в панели Performance как «Minor GC»). Долгоживущие данные, которые растут без конца, оказываются в старом поколении, замедляют каждую полную сборку и в итоге упираются в лимит кучи: `FATAL ERROR: Reached heap limit Allocation failed - JavaScript heap out of memory` — сообщение, которого разработчики на Node учатся бояться.

## Что течёт в реальных JavaScript-приложениях

Почти любая утечка, которую вы встретите, — одна из этих.

### 1. Кэши и Map, которые только растут

Map, используемый как кэш, — коллекция, достижимая из корня: из него ничего не освобождается, пока вы сами не удалите запись. Мемоизация по ключу, который всегда новый (метка времени, id запроса, текст поиска пользователя), — это утечка с красивым названием:

<CodeExample output={`записей после напряжённого дня: 50000`}>

```js
const cache = new Map();

function formatPrice(amount, currency) {
  const key = `${amount}:${currency}`;
  if (!cache.has(key)) {
    cache.set(key, `${currency} ${amount.toFixed(2)}`);
  }
  return cache.get(key);
}

// Каждая новая сумма добавляет запись — навсегда
for (let cents = 0; cents < 50_000; cents++) {
  formatPrice(cents / 100, "GBP");
}
console.log("записей после напряжённого дня:", cache.size);
```

</CodeExample>

Каждому кэшу нужен **лимит** (максимальный размер, время жизни или и то и другое). Классическая политика — **LRU**, *least recently used* («давно не использовавшийся»): когда кэш заполнен, выбрасывается запись, которую дольше всех никто не запрашивал. Вы напишете такой кэш в упражнении. В продакшене это хорошо делают библиотеки вроде `lru-cache`.

### 2. Обработчики и подписки, которые никогда не удаляются

Каждый `addEventListener`, `store.subscribe`, `socket.on` или `emitter.on` даёт **источнику** ссылку на ваш колбэк, а через его замыкание — на всё, что колбэк использует. Если источник живёт дольше того, кто на него подписался (глобальное хранилище, `window`, WebSocket), подписчик никогда не будет освобождён:

<CodeExample output={`хранилище с утечкой: 1000 обработчиков
чистое хранилище: 0 обработчиков`}>

```js
function createStore() {
  const listeners = new Set();
  return {
    subscribe(fn) {
      listeners.add(fn);
      return () => listeners.delete(fn); // очистка
    },
    get listenerCount() {
      return listeners.size;
    },
  };
}

const leaky = createStore();
const clean = createStore();

function mountLeakyWidget() {
  const rows = new Array(1_000).fill("🐼"); // данные виджета
  leaky.subscribe(() => rows.length); // отписки никогда не будет
}

function mountCleanWidget() {
  const rows = new Array(1_000).fill("🐼");
  const unsubscribe = clean.subscribe(() => rows.length);
  return unsubscribe; // вызывающий код запустит это при размонтировании
}

// Пользователь открывает и закрывает виджет 1000 раз
for (let i = 0; i < 1_000; i++) {
  mountLeakyWidget();
  const unmount = mountCleanWidget();
  unmount();
}
console.log(`хранилище с утечкой: ${leaky.listenerCount} обработчиков`);
console.log(`чистое хранилище: ${clean.listenerCount} обработчиков`);
```

</CodeExample>

Хранилище с утечкой держит 1000 мёртвых виджетов, у каждого свой массив `rows`, и при каждом изменении будет вызывать все 1000 колбэков. Именно поэтому `useEffect` в React позволяет вернуть **функцию очистки (cleanup function)**, и поэтому любой хороший API `subscribe` возвращает `unsubscribe`.

### 3. Таймеры, которые никогда не очищаются

Активный `setInterval` — это корень: его колбэк и всё, на что ссылается замыкание колбэка, живут до `clearInterval`. Интервал опроса, запущенный компонентом, которого потом удалили, продолжает опрашивать сервер (и держать данные компонента в памяти) вечно. То же касается `setTimeout`, который сам себя перезапускает.

### 4. Замыкания, которые держат больше, чем нужно

Замыкание сохраняет в живых каждую переменную, которую использует. В этом смысл замыканий, но так легко случайно захватить что-то большое:

<CodeExample output={`10001`}>

```js
function createLogger() {
  const history = []; // живёт столько же, сколько `log`
  return function log(message) {
    history.push(message);
    return history.length;
  };
}

const log = createLogger(); // уровень модуля: живёт вечно
for (let i = 0; i < 10_000; i++) log(`запрос ${i}`);
console.log(log("ещё один")); // все они хранятся в памяти
```

</CodeExample>

Коварный вариант: обработчик, которому нужен только `response.items.length`, но который замыкает весь `response`, держит в памяти весь ответ, пока существует обработчик. Прежде чем создавать долгоживущие колбэки, скопируйте то, что нужно, в маленькую переменную.

### 5. Отсоединённые DOM-узлы

Вы удаляете элемент со страницы через `element.remove()`, но на него всё ещё указывает переменная, массив или Map в JavaScript. Теперь элемент (и всё его поддерево, и их обработчики) **отсоединён (detached)**: его нет в документе, но и собрать его нельзя. Классические источники — переменные вроде «последняя выбранная строка» и кэши, где ключами служат элементы. Очищайте такие ссылки при удалении элемента или используйте `WeakMap` (следующий раздел).

### 6. Случайные глобальные переменные

В старых скриптах в «нестрогом режиме» (sloppy mode) присваивание необъявленной переменной (`totl = 5` вместо `total = 5`) молча создаёт глобальную переменную, которая живёт вечно. Модули, классы и строгий режим превращают это в ошибку — ещё одна причина всегда ими пользоваться:

<CodeExample output={`ReferenceError`}>

```js
function addUp(prices) {
  let total = 0;
  for (const price of prices) {
    totl = total + price; // опечатка!
  }
  return total;
}

try {
  addUp([1, 2, 3]);
} catch (error) {
  console.log(error.name); // строгий режим: никаких случайных глобальных
}
```

</CodeExample>

<Callout type="warning" title="График-лесенка">

График памяти здорового приложения похож на **пилу**: память растёт, пока вы выделяете объекты, падает, когда срабатывает сборщик, а нижние точки остаются на одном уровне. Утечка выглядит как **лесенка**: каждый спад заканчивается чуть выше предыдущего. На сервере эта лесенка обычно заканчивается тем, что процесс убивают из-за нехватки памяти, он перезапускается, и всё начинается заново. Перезапуск «чинит» проблему, поэтому некоторые утечки годами живут в продакшене.

</Callout>

## WeakMap и WeakSet: данные, которые следуют за объектом

Часто нужно привязать дополнительную информацию к объектам, которые вам не принадлежат: сколько раз кликнули по DOM-элементу, какие объекты вы уже обработали, вычисленное значение для объекта запроса. Обычный `Map` с объектом в качестве ключа держит этот объект в памяти вечно. **`WeakMap`** хранит свои ключи **слабо (weakly)**: запись не считается ссылкой, и когда объект-ключ становится недостижимым в остальной программе, запись исчезает вместе с ним.

<CodeExample output={`2
1
undefined
true false`}>

```js
// Дополнительные данные для чужих объектов (DOM-узлы, запросы...)
const clickCounts = new WeakMap();

function trackClick(element) {
  clickCounts.set(element, (clickCounts.get(element) ?? 0) + 1);
  return clickCounts.get(element);
}

const saveButton = { id: "save" }; // представьте настоящие DOM-элементы
const helpButton = { id: "help" };
trackClick(saveButton);
console.log(trackClick(saveButton));
console.log(trackClick(helpButton));
console.log(clickCounts.get({ id: "save" })); // это другой объект

// WeakSet: «видел ли я этот объект?»
const validated = new WeakSet();
validated.add(saveButton);
console.log(validated.has(saveButton), validated.has(helpButton));
```

</CodeExample>

Когда `saveButton` удалят и забудут, его счётчик уйдёт вместе с ним, и никакого кода очистки не нужно. Цена: ключами могут быть только **объекты** (или незарегистрированные символы), и перебрать WeakMap или узнать его размер нельзя, потому что содержимое зависит от того, когда в последний раз работал сборщик. Фреймворки повсюду используют WeakMap именно для такой задачи «метаданные для объекта» (например, система реактивности Vue, с которой вы встретитесь в следующем уроке).

## WeakRef и FinalizationRegistry: обращаться осторожно

Ещё два продвинутых инструмента дают слабую ссылку на **один** объект:

<CodeExample output={`1 true`}>

```js
let photo = { id: 1, pixels: new Uint8Array(1_000_000) };
const ref = new WeakRef(photo);

// deref() возвращает объект или undefined, если его уже собрали
console.log(ref.deref()?.id, ref.deref() === photo);
```

</CodeExample>

```js
// Вызовет вас (возможно!) после того, как объект собран
const registry = new FinalizationRegistry((id) => {
  console.log(`фото ${id} собрано сборщиком мусора`);
});
registry.register(photo, photo.id);
photo = null; // позже, может быть, гораздо позже, а может, никогда
```

Звучит идеально для кэшей и очистки, но спецификация языка почти ничего не гарантирует: **когда** объект соберут (и соберут ли вообще), зависит от движка, нагрузки на память и фазы Луны. Колбэк финализации может сработать поздно или вовсе не сработать, если страницу закроют раньше. Используйте их только как оптимизацию — например, для кэша, которому *разрешено* терять записи, — и никогда для того, от чего зависит правильность программы: закрытия файлов, сохранения данных, освобождения блокировок. Для этого пишите явные методы `close()`/`dispose()`. (В новом JavaScript появилось ключевое слово `using`, которое автоматически вызывает `[Symbol.dispose]()` в конце блока; сейчас оно приходит в движки и в TypeScript.)

## Удаляем много обработчиков разом с AbortController

Удалять пять обработчиков и таймер по одному утомительно, а каждый забытый — утечка. `addEventListener` принимает опцию **`signal`**: когда его `AbortController` отменяется, все обработчики, зарегистрированные с этим сигналом, удаляются разом. Сам сигнал тоже генерирует событие `abort` — удобное место, чтобы очистить таймеры:

<CodeExample output={`A получил привет
B получил привет
после abort: true`}>

```js
const socket = new EventTarget(); // например, WebSocket или window
const controller = new AbortController();
const { signal } = controller;

socket.addEventListener(
  "message",
  (event) => console.log("A получил", event.detail),
  { signal },
);
socket.addEventListener(
  "message",
  (event) => console.log("B получил", event.detail),
  { signal },
);
const timer = setInterval(() => console.log("пинг"), 1000);
signal.addEventListener("abort", () => clearInterval(timer));

socket.dispatchEvent(new CustomEvent("message", { detail: "привет" }));

controller.abort(); // виджет закрывается: всё убрано
socket.dispatchEvent(new CustomEvent("message", { detail: "?" }));
console.log("после abort:", signal.aborted);
```

</CodeExample>

Тот же сигнал умеет отменять и запросы `fetch` (`fetch(url, { signal })`), так что один `controller.abort()` в очистке компонента разом убирает его обработчики, таймеры и незавершённые запросы. В React это выглядит так:

```jsx
useEffect(() => {
  const controller = new AbortController();
  const { signal } = controller;
  window.addEventListener("resize", onResize, { signal });
  window.addEventListener("keydown", onKey, { signal });
  fetch(`/api/items/${id}`, { signal }).then(/* ... */);
  return () => controller.abort(); // очистка в одну строку
}, [id]);
```

## Ищем утечки с DevTools

Если подозреваете утечку, не гадайте — **измеряйте**. DevTools в Chrome (в Firefox и Safari есть похожие инструменты) дают вам:

- **Панель Performance** с галочкой *Memory*: записывайте, пока повторяете действие (откройте и закройте диалог десять раз). Лесенка на линии JS heap после принудительной сборки мусора (кнопка 🗑️) означает, что что-то удерживается.
- **Панель Memory → Heap snapshot**: полная картина всех объектов в куче. Хорошо работает **техника трёх снимков**: сделайте снимок, несколько раз повторите подозрительное действие, сделайте второй, снова повторите, сделайте третий. В третьем снимке выберите *Objects allocated between snapshots 1 and 2*. То, что было создано тогда и *до сих пор* живо, — ваши подозреваемые.
- **Retainers** (удерживающие ссылки): выберите подозрительный объект, и нижняя панель покажет цепочку ссылок, которая держит его в живых, вплоть до корня. Эта цепочка указывает на строку, которую надо исправить: часто это обработчик, Map или замыкание. Если ввести `Detached` в фильтр классов, найдутся отсоединённые DOM-деревья.
- **Allocation instrumentation on timeline**: показывает, *когда* объекты были выделены и какие из них выжили, — синими полосками, которые остаются синими.

Для Node те же инструменты работают через инспектор:

1. **`get(key)`**: при попадании верните значение **и** сделайте ключ самым свежим. При промахе верните `undefined` (и ничего не добавляйте).

```js
class LRUCache {
  #map = new Map();

  constructor(limit, onEvict = () => {}) {
    this.limit = limit;
    this.onEvict = onEvict;
  }

  get size() {
    return this.#map.size;
  }

  has(key) {
    return this.#map.has(key);
  }

  get(key) {
    if (!this.#map.has(key)) return undefined;
    const value = this.#map.get(key);
    this.#map.delete(key); // переносим в конец:
    this.#map.set(key, value); // теперь он самый новый
    return value;
  }

  set(key, value) {
    this.#map.delete(key);
    this.#map.set(key, value);
    if (this.#map.size > this.limit) {
      const oldest = this.#map.keys().next().value;
      const oldValue = this.#map.get(oldest);
      this.#map.delete(oldest);
      this.onEvict(oldest, oldValue);
    }
    return this;
  }

  keys() {
    return [...this.#map.keys()];
  }
}

  console.log(`вытеснен ${key}`);

thumbnails.set("panda.png", "🐼");
thumbnails.get("cat.png"); // кот снова свежий
thumbnails.set("fox.png", "🦊"); // кэш заполнен
console.log(thumbnails.keys());
console.log(thumbnails.size, thumbnails.get("dog.png"));
```

## Итоги

- Объекты живут в **куче**; переменные хранят **ссылки** на них. Сборщик мусора освобождает всё, что больше не **достижимо** из корней (глобальные переменные, стек вызовов, таймеры, обработчики...), с помощью **mark-and-sweep**. Циклы — не проблема.
- **Сборка по поколениям**: большинство объектов умирают молодыми, поэтому новые объекты собираются часто и дёшево; выжившие переходят в старое поколение, которое собирается инкрементально и параллельно.
- **Утечка** — это забытая ссылка. Обычные подозреваемые: неограниченные **кэши/Map**, никогда не удаляемые **обработчики и подписки**, неочищенные **таймеры**, **замыкания**, держащие большие данные, **отсоединённые DOM-узлы**, случайные **глобальные переменные**.
- Давайте каждому кэшу лимит (например, **LRU** на `Map`), а каждой подписке — **unsubscribe**.
- **WeakMap/WeakSet** привязывают данные к объектам, не удерживая их в памяти. **WeakRef/FinalizationRegistry** недетерминированы: только для оптимизаций, никогда для правильности.
- **AbortController**: передайте `{ signal }` многим обработчикам и запросам `fetch`, и один `abort()` уберёт их все.
- Ищите утечки измерениями: график памяти в панели Performance, **снимки кучи** (техника трёх снимков, retainers, `Detached`) и `node --inspect` на серверах.
