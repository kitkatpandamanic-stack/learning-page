До сих пор «бэкенд» был одним приложением на Express на одной машине. Для начала это правильно, и многим успешным продуктам большего никогда не требуется. Но когда трафик растёт, одного процесса Node становится мало, и приходится выбирать части покрупнее: больше серверов, кэши, реплики, очереди. **Проектирование систем (system design)** — это выбор таких частей и того, как они общаются друг с другом. Единственно верного ответа почти никогда нет, есть только компромиссы (trade-offs). Поэтому этот урок — про словарь и, что гораздо важнее, про рассуждения: какая часть вам нужна и *почему*? 🏗️

Сквозной пример всего модуля — **PandaPoll**: ведущий создаёт опрос («Табы или пробелы?»), зрители голосуют с телефонов, и все видят, как результаты обновляются вживую на большом экране.

## Начинайте с требований, а не с квадратиков

Классическая ошибка на обсуждениях архитектуры (и на собеседованиях) — рисовать квадратики раньше, чем все договорились, что система должна делать. Сначала запишите требования (requirements), они бывают двух видов:

| Вид | На какой вопрос отвечает | Примеры для PandaPoll |
| --- | --- | --- |
| **Функциональные** (functional) | Что система делает? | Создать опрос; один голос на человека; смотреть результаты вживую; выгрузить результаты в CSV |
| **Нефункциональные** (non-functional) | Насколько хорошо она должна это делать? | Голос подтверждается быстрее чем за 300 мс; результаты доходят до каждого экрана за 1 с; доступность 99,9% во время мероприятий; ни один голос не теряется |

Архитектуру определяют именно нефункциональные требования. «Показывать результаты вживую» — проект на выходные. «Показывать результаты вживую 5000 человек на конференции, с задержкой не больше секунды, даже если посреди выступления упадёт сервер» — это уже задача проектирования систем.

Запишите и то, что **не входит в рамки** (out of scope) проекта: «в первой версии нет анонимных опросов», «никаких комментариев». Незаписанные рамки потихоньку расползаются, пока систему уже никто не может построить в срок.

## Прикидочные расчёты

Прежде чем выбирать технологии, оцените **нагрузку (load)**. Точность не нужна, нужен порядок величины: 10 запросов в секунду или 10 000? Для этого нужны очень разные системы. Такие оценки называют расчётами «на обратной стороне конверта» (back-of-the-envelope maths).

<CodeExample output={`Голосов в день:           3,000,000
В среднем голосов/с:      35
Голосов/с на выступлении: 500
Обновлений/с, по голосу:  2,500,000
Обновлений/с, 2 раза в с: 10,000
Данных за год:            66 GB`}>

```js
const fmt = (n) => Math.round(n).toLocaleString("en-US");
const show = (label, value) =>
  console.log(`${label.padEnd(26)}${value}`);

const pollsPerDay = 40_000;
const votersPerPoll = 75;
const votesPerDay = pollsPerDay * votersPerPoll;
show("Голосов в день:", fmt(votesPerDay));
show("В среднем голосов/с:", fmt(votesPerDay / 86_400));

// Худший случай: выступление перед 5000 зрителей,
// и все голосуют примерно за 10 секунд
const audience = 5_000;
const peakVotes = audience / 10;
show("Голосов/с на выступлении:", fmt(peakVotes));

// Результаты вживую: каждый голос обновляет каждый экран
show("Обновлений/с, по голосу:", fmt(peakVotes * audience));
show("Обновлений/с, 2 раза в с:", fmt(2 * audience));

const bytesPerVote = 60;
const gbPerYear = (votesPerDay * 365 * bytesPerVote) / 1e9;
show("Данных за год:", `${fmt(gbPerYear)} GB`);
```

</CodeExample>

Пять минут арифметики — и архитектура уже начинает вырисовываться:

- **35 голосов в секунду в среднем — это ничто.** С этим легко справятся один процесс Node и одна база Postgres. Но *среднее* обманчиво: трафик PandaPoll приходит **всплесками (spikes)** — когда ведущий говорит «голосуем!». Проектируйте под пик.
- **Настоящая опасность — веерная рассылка (fan-out).** Если после каждого голоса отправлять новые результаты на каждый экран, за одно выступление это 2,5 миллиона сообщений в секунду. А если вместо этого рассылать свежий снимок результатов дважды в секунду — 10 000. Для пользователя разницы нет (быстрее всё равно никто не прочитает), а работы в 250 раз меньше. Это одно решение важнее любого выбора фреймворка.
- **66 ГБ в год помещаются на один диск.** Делить базу данных нам не придётся ещё много лет.

Несколько чисел, которые стоит держать в голове:

| Эмпирическое правило | Значение |
| --- | --- |
| Секунд в сутках | 86 400 (примерно 10⁵) |
| Чтение из памяти | ~100 наносекунд |
| Чтение с SSD | ~100 микросекунд (в 1000 раз медленнее) |
| Запрос туда и обратно внутри одного дата-центра | ~0,5 мс |
| Запрос туда и обратно Европа ↔ США | ~80–150 мс |
| Один процесс Node, простой JSON API | тысячи запросов/с (одно ядро CPU) |

<Callout type="tip" title="Проговаривайте свои допущения вслух">

«75 участников в опросе» и «все голосуют за 10 секунд» — это догадки. И это нормально: запишите их рядом с числами, чтобы другие могли с ними поспорить («наш крупнейший клиент проводит мероприятия на 20 000 человек»). Архитектуру, построенную на видимых догадках, можно поправить; архитектура на скрытых догадках ломается в продакшене.

</Callout>

## Вертикальное и горизонтальное масштабирование

Когда одного сервера мало, расти можно двумя способами:

| | Масштабирование **вверх** (вертикальное, scale up) | Масштабирование **вширь** (горизонтальное, scale out) |
| --- | --- | --- |
| Что | Машина побольше: больше CPU и RAM | Больше машин (или процессов) того же размера |
| Плюсы | Код менять не нужно | Почти нет верхнего предела; система переживёт гибель одной машины |
| Минусы | Самая большая машина всё-таки существует, и это по-прежнему единая точка отказа | Нужен балансировщик нагрузки, а серверы должны быть **stateless** (без состояния) |
| Подходит для | Баз данных (довольно долго) | API-серверов, WebSocket-серверов, воркеров |

У Node здесь есть своя особенность. Ваш JavaScript выполняется в **одном потоке**, поэтому один процесс Node использует **одно ядро CPU**, какой бы большой ни была машина. 16-ядерный сервер, на котором запущен один `node server.js`, почти всё время простаивает. Поэтому на практике масштабируются вширь даже на одной машине: один процесс на ядро с помощью модуля `cluster` или менеджера процессов, либо (сегодня это самый частый вариант) несколько небольших контейнеров за балансировщиком нагрузки.

```bash
# На вашей машине: по одному процессу Node на ядро CPU с PM2
npm install --global pm2
pm2 start server.js -i max   # "max" = столько, сколько ядер
pm2 list
```

## Серверы без состояния

Горизонтальное масштабирование работает, только если любой сервер может обработать любой запрос. Значит, между запросами сервер **не хранит ничего важного в собственной памяти**: сессии лежат в общем хранилище (Redis или база данных), загруженные файлы — в объектном хранилище (вроде S3) и так далее. Такой сервер называют **stateless** (без состояния).

Вот что бывает, если это не так. Два сервера приложения стоят за балансировщиком, который отправляет запросы им по очереди:

<CodeExample output={`app-2: не авторизован
app-2: mei
app-1: mei`}>

```js
// Каждый «сервер» — крошечное приложение; сессии берутся из хранилища
function createAppServer(name, sessions = new Map()) {
  return {
    name,
    login(sid, user) {
      sessions.set(sid, user);
    },
    me(sid) {
      const user = sessions.get(sid);
      return `${name}: ${user ?? "не авторизован"}`;
    },
  };
}

function* roundRobin(servers) {
  for (let i = 0; ; i++) yield servers[i % servers.length];
}

// ❌ С состоянием: каждый сервер хранит сессии в своей памяти
let lb = roundRobin([createAppServer("app-1"),
  createAppServer("app-2")]);
lb.next().value.login("s1", "mei");
console.log(lb.next().value.me("s1"));

// ✅ Без состояния: сессии живут в одном общем хранилище
const shared = new Map(); // в реальности это Redis или база данных
lb = roundRobin([createAppServer("app-1", shared),
  createAppServer("app-2", shared)]);
lb.next().value.login("s1", "mei");
console.log(lb.next().value.me("s1"));
console.log(lb.next().value.me("s1"));
```

</CodeExample>

Мэй входит в систему на `app-1`, её следующий запрос попадает на `app-2` — и она «разлогинена». Это настоящий и очень частый баг: на ноутбуке разработчика (один процесс) всё прекрасно работает и ломается в тот день, когда кто-то добавляет второй сервер. Обратите внимание: исправление — это снова **внедрение зависимостей (dependency injection)**. Сервер получает хранилище сессий снаружи, а не создаёт его сам, поэтому в продакшене ему передают общее хранилище на Redis, а в тестах — `Map`.

Остерегайтесь и другого скрытого состояния в приложениях на Node: счётчиков ограничения частоты запросов в памяти, `Map` на уровне модуля, который служит кэшем, файлов на локальном диске, задач в `setInterval`, которые теперь будут запускаться **в каждом процессе**. Каждому такому месту нужен общий дом — или осознанное решение, что «по отдельности в каждом процессе» нас устраивает.

## Балансировщики нагрузки и проверки здоровья

**Балансировщик нагрузки (load balancer, LB)** стоит перед вашими серверами и распределяет между ними запросы. Ещё он выполняет **проверки здоровья (health checks)** — каждые несколько секунд обращается к чему-нибудь вроде `/health` — и перестаёт отправлять трафик на сервер, который не отвечает. Две распространённые стратегии:

<CodeExample output={`[ 'app-1', 'app-3', 'app-1', 'app-3' ]
app-3`}>

```js
const servers = [
  { name: "app-1", active: 12, healthy: true },
  { name: "app-2", active: 3, healthy: false },
  { name: "app-3", active: 7, healthy: true },
];

function* roundRobin(list) {
  for (let i = 0; ; i++) yield list[i % list.length];
}

function leastConnections(list) {
  return list
    .filter((s) => s.healthy)
    .reduce((best, s) => (s.active < best.active ? s : best));
}

const next = roundRobin(servers.filter((s) => s.healthy));
console.log([1, 2, 3, 4].map(() => next.next().value.name));
console.log(leastConnections(servers).name);
```

</CodeExample>

**Round robin** (по кругу) отправляет запросы серверам по очереди — отлично, когда запросы похожи друг на друга. **Least connections** (наименьшее число соединений) выбирает наименее загруженный сервер — это важно, когда часть запросов медленные или долгоживущие (как WebSocket-соединения из следующего урока). Обе стратегии пропускают `app-2`, который не прошёл проверку здоровья. Обычно это не пишут вручную, а настраивают в nginx, HAProxy или балансировщике вашего облака, но теперь вы знаете, что означают эти настройки.

Хороший эндпоинт здоровья дешёвый и честный: он сообщает, может ли *этот* процесс выполнять свою работу, и не делает тяжёлой работы при каждом вызове.

```js
app.get("/health", async (req, res) => {
  try {
    await db.query("SELECT 1"); // достучимся ли до базы данных?
    res.json({ status: "ok" });
  } catch {
    res.status(503).json({ status: "db unreachable" });
  }
});
```

## Слои кэша

**Кэш (cache)** хранит копию данных там, откуда их быстрее достать, чтобы не вычислять и не перечитывать их каждый раз. На запрос страницы PandaPoll могут ответить несколько слоёв — от ближайшего к пользователю до самого дальнего:

| Слой | Что кэширует | Как этим управлять |
| --- | --- | --- |
| **Браузер** | Скрипты, картинки, ответы API | Заголовки `Cache-Control`, ETag |
| **CDN** (Cloudflare, CloudFront…) | Статические файлы и публичные страницы — в дата-центрах рядом с пользователями | `Cache-Control`, очистка при деплое |
| **Кэш приложения** (Redis или `Map` в одном процессе) | Результаты запросов к базе, вычисленные значения | Ваш код: cache-aside, TTL, инвалидация |
| **База данных** | Собственные страницы в памяти | В основном автоматически |

Каждый слой, который смог ответить сам, — это запрос, которого слои за ним даже не увидят. Хэши в именах файлов бандлов вместе с `Cache-Control: max-age=31536000, immutable` означают, что вернувшиеся посетители скачивают ваш JavaScript один раз, а всем остальным его раздаёт CDN. Дешевле масштабирования не бывает.

### Cache-aside

Самый распространённый шаблон на уровне приложения — **cache-aside** (его ещё называют ленивой загрузкой, lazy loading): заглядываем в кэш; при **промахе (miss)** загружаем данные из базы и сохраняем результат на следующий раз.

<CodeExample output={`по одному: 1 чтение из БД
все сразу: 500 чтений из БД
Табы или пробелы?`}>

```js
const db = new Map([[7, { id: 7, question: "Табы или пробелы?" }]]);
let dbReads = 0;

async function loadPoll(id) {
  dbReads++;
  await new Promise((r) => setTimeout(r, 50)); // медленный запрос
  return db.get(id);
}

const cache = new Map();

async function getPoll(id) {
  if (cache.has(id)) return cache.get(id);  // 1. попадание
  const poll = await loadPoll(id);          // 2. промах: спросим БД
  cache.set(id, poll);                      // 3. запомним
  return poll;
}

await getPoll(7);
await getPoll(7);
await getPoll(7);
console.log("по одному:", dbReads, "чтение из БД");

// Начинается выступление: 500 человек открывают опрос разом
cache.clear();
dbReads = 0;
const opens = Array.from({ length: 500 }, () => getPoll(7));
const polls = await Promise.all(opens);
console.log("все сразу:", dbReads, "чтений из БД");
console.log(polls[499].question);
```

</CodeExample>

Когда запросы идут по одному, кэш работает идеально. Но посмотрите на вторую часть: 500 запросов приходят одновременно, и **все** промахиваются (первая загрузка ещё не закончилась, когда остальные заглядывают в кэш), а база получает 500 одинаковых запросов. Это **лавина промахов кэша (cache stampede**, или «thundering herd» — «топот стада»), и она случается ровно тогда, когда кэш нужнее всего: во время всплеска трафика или сразу после деплоя или перезапуска кэша.

Решение — **объединение запросов (request coalescing)**: первый промах запускает загрузку и кладёт её **промис** в `Map` текущих загрузок; каждый промах, пришедший, пока она идёт, ждёт тот же самый промис. 500 запросов — один запрос к базе. В JavaScript это получается на редкость элегантно, ведь промис — это значение, которым можно поделиться. Вы реализуете это в упражнении.

### Как поддерживать кэш свежим

Известная шутка гласит, что в информатике есть две сложные вещи: инвалидация кэша, именование и ошибки на единицу. Ваши инструменты:

| Инструмент | Как работает | Компромисс |
| --- | --- | --- |
| **TTL** (time to live, время жизни) | Каждая запись истекает через N секунд | Просто и само себя чинит, но данные могут отставать на N секунд |
| **Инвалидация при записи** | Когда данные меняются, удаляем ключ из кэша | Данные свежие, но об этом должен помнить каждый путь в коде, который что-то записывает |
| **И то и другое** | Инвалидация при записи плюс TTL как страховка | Так делает большинство реальных систем |

Удаляйте ключ **после** записи в базу, а не до неё, иначе другой запрос успеет снова положить в кэш старое значение. А TTL выбирайте исходя из требований продукта: вопрос опроса можно кэшировать минутами, а живые счётчики голосов — может быть, на полсекунды.

<Callout type="warning" title="Кэш, без которого вы не можете жить, — это зависимость">

Однажды команда во время деплоя перезапустила все узлы Redis одновременно. Кэш вернулся пустым, весь трафик разом ударил по базе данных, база упала и потянула за собой весь сайт. Объединяйте запросы, добавляйте к TTL немного случайного **разброса (jitter)**, чтобы ключи не истекали все вместе, и убедитесь, что база данных переживёт хотя бы холодный старт.

</Callout>

## Базы данных: индексы, реплики и шарды

Базу данных обычно масштабировать сложнее всего, потому что именно она хранит **состояние**. Берите инструменты в таком порядке:

**1. Индексы.** Прежде всего убедитесь, что запросы их используют. Без индекса запрос «найди голоса для опроса 7» заставляет базу прочитать **каждую** строку — как `array.filter` по всей таблице. Индекс (index) — это отсортированная структура (обычно B-дерево), которая сразу переходит к нужным строкам, — больше похоже на `map.get(7)`. Отсутствующий индекс — самая частая причина «медленной базы данных», а добавить его — это миграция в одну строку:

```sql
CREATE INDEX votes_poll_id_idx ON votes (poll_id);

-- Спросите Postgres, как он выполняет запрос: на больших таблицах
-- ищите "Index Scan", а не "Seq Scan"
EXPLAIN ANALYZE SELECT * FROM votes WHERE poll_id = 7;
```

Индексы не бесплатны: каждая вставка должна обновлять и их тоже, поэтому индексируйте столбцы, по которым фильтруете, соединяете и сортируете, а не всё подряд.

**2. Машина побольше.** Вертикальное масштабирование базы данных — скучно, зато работает удивительно долго.

**3. Реплики для чтения.** **Основной сервер (primary)** принимает все записи и передаёт изменения **репликам (replicas)**, которые обслуживают чтение. Отлично подходит для приложений, где чтений намного больше, чем записей. Подвох — **задержка репликации (replication lag)**: реплика может немного отставать, и пользователь, который только что проголосовал, может не увидеть свой голос, если читать с реплики. Распространённое правило: **свои** недавние записи читайте с основного сервера.

**4. Шардирование.** Когда данных или записей слишком много для одной машины, их делят: каждый **шард (shard)** хранит часть данных, а какую именно — определяет **ключ шардирования (shard key)**, например id опроса. Наивный способ — `hash(key) % numberOfShards`, но посмотрите, что происходит, когда добавляется шард:

<CodeExample output={`mei -> шард 1
kai -> шард 0
luna -> шард 0
по модулю, 3 -> 4 шарда: переезжает 75%
кольцо, 3 -> 4 шарда: переезжает 27%`}>

```js
// FNV-1a: маленький быстрый хэш строк (везде даёт один результат)
function hash(text) {
  let h = 2166136261;
  for (const ch of text) {
    h = Math.imul(h ^ ch.codePointAt(0), 16777619);
  }
  h ^= h >>> 16; // перемешиваем биты, чтобы похожие ключи разошлись
  h = Math.imul(h, 0x85ebca6b);
  h ^= h >>> 13;
  return h >>> 0; // как беззнаковое 32-битное число
}

const byModulo = (key, n) => hash(key) % n;

for (const user of ["mei", "kai", "luna"]) {
  console.log(user, "-> шард", byModulo(user, 3));
}

const users = Array.from({ length: 10_000 }, (_, i) => `u${i}`);
const share = (moved) =>
  `${Math.round((users.filter(moved).length / 10_000) * 100)}%`;

console.log("по модулю, 3 -> 4 шарда: переезжает",
  share((u) => byModulo(u, 3) !== byModulo(u, 4)));

// Консистентное хэширование: у каждого шарда 100 точек на кольце
function createRing(shards) {
  const points = shards
    .flatMap((shard) =>
      Array.from({ length: 100 }, (_, i) => ({
        at: hash(`${shard}#${i}`),
        shard,
      })),
    )
    .sort((a, b) => a.at - b.at);
  // ключ принадлежит первой точке, равной его хэшу или после него
  return (key) => {
    const h = hash(key);
    return (points.find((p) => p.at >= h) ?? points[0]).shard;
  };
}

const ring3 = createRing(["a", "b", "c"]);
const ring4 = createRing(["a", "b", "c", "d"]);
console.log("кольцо, 3 -> 4 шарда: переезжает",
  share((u) => ring3(u) !== ring4(u)));
```

</CodeExample>

С `% n` переход от 3 к 4 шардам перемещает между машинами **три четверти** всех данных. **Консистентное хэширование (consistent hashing)** размещает шарды во множестве точек на кольце хэш-значений; ключ принадлежит следующей точке по кольцу. Новый шард `d` забирает только ключи прямо перед своими точками — примерно четверть (идеал для 4 шардов — ровно 25%), и между старыми шардами ничего не переезжает. Redis Cluster, Cassandra и DynamoDB используют разные варианты этой идеи. (Настоящее кольцо искало бы точку двоичным поиском, а не `find`, и использовало бы хорошо проверенную хэш-функцию из библиотеки.)

Обратите внимание: хэш должен давать **одинаковый ответ на каждом сервере**, поэтому здесь это фиксированный алгоритм, а не что-то случайное в каждом процессе. Шардирование — мощный, но дорогой инструмент: запросы через несколько шардов, соединения таблиц (joins) и транзакции становятся сложнее. Считайте его крайней мерой — после индексов, кэширования, машины побольше и реплик.

## Очереди и фоновые воркеры

Часть работы не обязательно делать, пока пользователь ждёт: выгрузку результатов, отправку писем, уменьшение картинок. Положите **задачу (job)** в **очередь (queue)**, сразу ответьте **202 Accepted** и пусть медленную часть выполняют отдельные процессы-**воркеры (workers)**.

<CodeExample output={`202 string
{ status: 'queued' }
{ status: 'done', result: 'poll-7.csv' }`}>

```js
import express from "express";
import request from "supertest";

const queue = [];         // в реальности RabbitMQ, SQS или Redis
const jobs = new Map();   // id задачи -> { status, result }

const app = express();

app.post("/polls/:id/export", (req, res) => {
  const job = { id: crypto.randomUUID(), pollId: req.params.id };
  jobs.set(job.id, { status: "queued" });
  queue.push(job);
  res.status(202).json({ jobId: job.id }); // отвечаем сразу
});

app.get("/jobs/:id", (req, res) => {
  const job = jobs.get(req.params.id);
  if (!job) return res.status(404).json({ error: "No such job" });
  res.json(job);
});

// Воркер работает в другом процессе и делает медленную часть
async function runWorker() {
  while (queue.length > 0) {
    const job = queue.shift();
    jobs.set(job.id, { status: "running" });
    await new Promise((r) => setTimeout(r, 100)); // собираем CSV
    const result = `poll-${job.pollId}.csv`;
    jobs.set(job.id, { status: "done", result });
  }
}

const res = await request(app).post("/polls/7/export");
console.log(res.status, typeof res.body.jobId);

const check = () => request(app).get(`/jobs/${res.body.jobId}`);
console.log((await check()).body);
await runWorker();
console.log((await check()).body);
```

</CodeExample>

Клиент сразу получает id задачи и может проверять `/jobs/:id` (или получить уведомление по WebSocket), когда файл будет готов. Ещё очереди **сглаживают всплески**: если за минуту запросили 10 000 выгрузок, они подождут в очереди, пока воркеры разбираются с ними в своём темпе, вместо того чтобы разом перегрузить базу данных. А медленная работа на CPU остаётся **за пределами цикла событий (event loop) API**, и все остальные запросы по-прежнему обрабатываются быстро.

В Node популярный выбор — **BullMQ** поверх Redis:

```js
import { Queue, Worker } from "bullmq";
const connection = { host: "localhost", port: 6379 };

// В процессе API
const exports = new Queue("exports", { connection });
await exports.add("csv", { pollId: 7 }, {
  attempts: 3,
  backoff: { type: "exponential", delay: 1000 },
});

// В процессе воркера (node worker.js)
new Worker("exports", async (job) => {
  return buildCsv(job.data.pollId);
}, { connection });
```

Заранее продумайте две вещи: задача может выполниться **больше одного раза** (воркер упал на полпути, и задачу повторили), поэтому повторный запуск задач должен быть безопасным; а задачи, которые падают снова и снова, отправляются в **очередь недоставленных сообщений (dead-letter queue)**, где на них может посмотреть человек, вместо того чтобы повторять их бесконечно.

## CAP простыми словами

Когда данные живут на нескольких машинах, сеть между ними время от времени будет ломаться. Во время такого **разделения сети (partition)** машина, которая не может связаться с остальными, должна выбрать:

- **Согласованность (Consistency, C):** отказаться отвечать (или вернуть ошибку), лишь бы не выдать устаревшие данные.
- **Доступность (Availability, A):** ответить тем, что есть, даже если это может быть устаревшим.

Это и есть **теорема CAP**: во время разделения сети (**P**artition) вы получаете либо **C**, либо **A**, но не оба сразу. Когда сеть в порядке, можно иметь и то и другое, так что на самом деле это вопрос о том, как должна вести себя каждая функция в плохой день. И это решение **продуктовое** не меньше, чем техническое:

| Данные | Лучший выбор | Почему |
| --- | --- | --- |
| Платежи, продажа билетов, «один голос на человека» | Согласованность | Продать последнее место дважды — это потерянные деньги и доверие |
| Живые счётчики голосов, лайки, счётчики просмотров | Доступность | Счётчик, отстающий на секунду, — это нормально |
| Аватар пользователя | Доступность | Устаревшая картинка лучше страницы с ошибкой |

Системы, которые выбирают доступность, обычно **согласованы в конечном счёте (eventually consistent)**: копии могут ненадолго расходиться, но догоняют друг друга, когда сеть восстанавливается. Требование PandaPoll «результаты доходят до каждого экрана за 1 с» — это и есть такой выбор, записанный словами. А сам голос нельзя потерять или посчитать дважды, поэтому запись голоса — это согласованная запись в основную базу данных.

function createFakeClock() {
  let time = 0;
  return {
    now: () => time,
    advance(ms) {
      time += ms;
    },
  };
}

function createCache({ load, ttlMs, now = Date.now }) {
  const entries = new Map(); // ключ -> { value, expiresAt }
  const inFlight = new Map(); // ключ -> промис значения
  const stats = { hits: 0, misses: 0 };

  async function get(key) {
    const entry = entries.get(key);
    if (entry && now() < entry.expiresAt) {
      stats.hits++;
      return entry.value;
    }
    stats.misses++;
    if (inFlight.has(key)) return inFlight.get(key);

    const promise = (async () => {
      try {
        const value = await load(key);
        entries.set(key, { value, expiresAt: now() + ttlMs });
        return value;
      } finally {
        inFlight.delete(key);
      }
    })();
    inFlight.set(key, promise);
    return promise;
  }

  function invalidate(key) {
    entries.delete(key);
  }

  return { get, invalidate, stats };
}

## Итоги

- Начинайте с **функциональных** и **нефункциональных** требований, а также с того, что **не входит в рамки**. Архитектуру определяют нефункциональные.
- **Прикидочные расчёты** находят настоящую проблему: для PandaPoll это всплески трафика и **веерная рассылка (fan-out)**, а не средняя нагрузка.
- Один процесс Node использует **одно ядро CPU**: масштабируйтесь вширь несколькими процессами или контейнерами за **балансировщиком нагрузки** с проверками здоровья.
- Горизонтальному масштабированию нужны серверы **без состояния**: сессии, счётчики и кэши, которые должны быть общими, живут в общем хранилище.
- Кэшируйте слоями (браузер, CDN, приложение). **Cache-aside** с **TTL** плюс инвалидация при записи; **лавину промахов** предотвращают объединение запросов и разброс (jitter) TTL.
- Базы данных: сначала **индексы**, потом машина побольше, **реплики для чтения** (помните о задержке) и **шардирование** с консистентным хэшированием как крайняя мера.
- **Очереди и воркеры** выносят медленную работу из запроса (202 Accepted) и сглаживают всплески; задачи должны безопасно переживать повторный запуск.
- **CAP**: во время разделения сети выбирайте согласованность или доступность — отдельно для каждого вида данных.
