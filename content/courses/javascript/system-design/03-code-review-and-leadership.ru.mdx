Наступает момент, когда ваш главный вклад — уже не код, который вы набираете сами. Это баг, который вы поймали в чужом пул-реквесте (pull request); архитектура, о которой команда договорилась раньше, чем кто-то написал хоть строчку; junior-разработчик, который стал вдвое сильнее, потому что вы с ним программировали в паре; и спокойный разбор после тяжёлой ночи. Это и есть **техническое лидерство (technical leadership)**, и чтобы им заниматься, должность «лида» не нужна. Этот урок — практический набор инструментов для всего этого. 🧭

## Зачем нужно код-ревью

**Код-ревью (code review)** — это не шлагбаум, у которого senior-разработчики доказывают, какие они умные. У него три задачи:

1. **Ловить проблемы, пока их дёшево исправить**: баги, дыры в безопасности, архитектурные решения, которые навредят через полгода.
2. **Делиться знаниями**: теперь этот код понимают как минимум два человека, и что-то новое узнают и автор, и ревьюер.
3. **Сохранять единообразие кодовой базы**, чтобы следующий человек мог в ней сориентироваться.

Смотрите на код примерно в таком порядке. Если неверна сама архитектура, шлифовать имена переменных — напрасный труд:

| Область | Какие вопросы задать в кодовой базе на JavaScript |
| --- | --- |
| **Корректность** | Делает ли код то, что написано в задаче? Пустые массивы, `null`/`undefined`, `0` и `""`, дубликаты, два запроса одновременно? Каждый промис дождались через await или обработали? |
| **Архитектура** | Находится ли код на правильном слое (обработчик маршрута, сценарий использования или репозиторий)? Он проще, чем мог бы быть, или универсальнее, чем нужно? |
| **Тесты** | Покрывают ли тесты новое поведение и граничные случаи? Упадут ли они, если код сломать? |
| **Безопасность** | Проверяется ли ввод? Нет ли `innerHTML` с данными пользователя, SQL, собранного из строк, секретов в коде, персональных данных в логах или в рассылках по WebSocket? |
| **Эксплуатация** | Есть ли тайм-ауты у сетевых вызовов? Полезные логи и метрики? Безопасная миграция, фича-флаг, способ откатиться? |
| **Производительность** | Только там, где это важно: запросы в цикле (N+1), `includes` внутри цикла по большим массивам, огромные бандлы, лишние перерисовки. |
| **Читаемость** | Говорят ли имена, что они обозначают? Разберётся ли новичок? Есть ли комментарий о том, *почему* сделано так? |

Форматирование и простые правила оставьте машинам. **Prettier** форматирует код, **ESLint** ловит вещи вроде `==`, неиспользуемых переменных и (с правилом `no-floating-promises` из typescript-eslint) забытых `await`, а **TypeScript** отлавливает целые классы ошибок. Запускайте их в CI, чтобы люди тратили время ревью на то, что инструменты оценить не могут.

## Читаем код как ревьюер

Некоторые баги легко проскальзывают мимо, когда читаешь код в режиме «вроде всё нормально». У опытных ревьюеров в голове есть список типичных подозреваемых в JavaScript:

<CodeExample output={`[ 1, 10, 100, 9 ]
[ 1, 9, 10, 100 ]
[ 1, NaN, 3 ]
[ 1, 7, 11 ]
10 0
сохранено после forEach: []
сохранено с Promise.all: [ 1, 2, 3 ]`}>

```js
// 1. Сортировка чисел
console.log([10, 9, 1, 100].sort());
console.log([10, 9, 1, 100].sort((a, b) => a - b));

// 2. map передаёт (value, index), а parseInt принимает основание
console.log(["1", "7", "11"].map(parseInt));
console.log(["1", "7", "11"].map(Number));

// 3. || считает 0 и "" отсутствующими значениями
const settings = { maxVotes: 0 };
console.log(settings.maxVotes || 10, settings.maxVotes ?? 10);

// 4. forEach не ждёт асинхронные колбэки
const save = (id) => new Promise((r) => setTimeout(r, 10, id));
const saved = [];
[1, 2, 3].forEach(async (id) => saved.push(await save(id)));
console.log("сохранено после forEach:", saved);

const all = await Promise.all([1, 2, 3].map(save));
console.log("сохранено с Promise.all:", all);
```

</CodeExample>

- `sort()` без функции сравнения сортирует **как строки**, поэтому `100` оказывается раньше `9`.
- `map(parseInt)` вызывает `parseInt("7", 1)`, потому что `map` передаёт вторым аргументом индекс, а parseInt считает его основанием системы счисления.
- `||` заменяет **любое** ложное (falsy) значение, поэтому намеренный `0` превращается в `10`. `??` заменяет только `null` и `undefined`.
- `forEach` игнорирует промисы, которые возвращает его колбэк: код после него выполняется раньше, чем что-либо сохранится. Используйте `for...of` с `await` или `Promise.all`.

Ещё в этом списке: `==` вместо `===`, изменение аргументов или состояния React, числа с плавающей точкой для денег (`0.1 + 0.2`), `catch`, который глотает любые ошибки, потерянный в колбэке `this`, и `Map` или массив, который растёт бесконечно. Когда вы нашли такой баг, самый полезный комментарий просит написать **тест**, который доказывает баг, — чтобы он больше никогда тихо не вернулся.

## Пишем доброжелательные и конкретные замечания

Вот пул-реквест, который на первый взгляд выглядит разумно:

```js
// PR #212: "Ведущие могут закрыть опрос"
app.post("/polls/:id/close", async (req, res) => {
  const poll = await polls.findById(req.params.id);
  poll.closed = true;
  polls.save(poll);
  for (const s of wss.clients) s.send(JSON.stringify(poll));
  res.json(poll);
});
```

А вот комментарии на ревью, которые помогают автору, а не судят его. Метка в начале (это соглашение называется **Conventional Comments**) говорит, насколько важен каждый комментарий:

- **issue (blocking):** Ничто не проверяет, что опрос принадлежит тому, кто его закрывает, так что любой залогиненный пользователь может закрыть чужой опрос. Может, переиспользуем middleware `requireOwner` из маршрута редактирования — и добавим тест на 403?
- **issue (blocking):** `polls.save(poll)` вызывается без `await`. Если сохранение упадёт, мы уже сообщили всем экранам, что опрос закрыт, а отклонённый промис никто не обработает.
- **question:** Что должно происходить для неизвестного id? Сейчас `poll` равен `null`, строка 3 выбрасывает TypeError, и пользователь получает 500. Может, имелся в виду 404?
- **suggestion:** Это обновление уходит **всем** подключённым клиентам, включая тех, кто смотрит другие опросы, а полный объект опроса содержит email владельца. Что думаете о том, чтобы рассылать `{ type: "closed", pollId }` только зрителям этого опроса?
- **nit (non-blocking):** `s` → `socket` читается чуть легче.
- **praise:** То, что здесь используется репозиторий `polls`, а не прямой запрос к базе, делает этот маршрут удобным для тестирования. 👍

Метки означают: **issue** — проблема (blocking — блокирует слияние), **question** — вопрос, **suggestion** — предложение, **nit** — мелочь (non-blocking — не блокирует), **praise** — похвала. Почему эти комментарии работают:

| Вместо… | Попробуйте… | Почему |
| --- | --- | --- |
| «Это неправильно». | «Неизвестные id падают с TypeError (500); может, здесь нужен 404?» | Говорит, **что** не так и **почему**, и предлагает путь вперёд |
| «Зачем вы вообще так сделали??» | «Почему вы выбрали X? Я бы ожидал Y, потому что…» | Настоящий вопрос приглашает к обсуждению; возможно, автор знает то, чего не знаете вы |
| «Вы забыли тесты». | «Может, добавим тест на закрытие чужого опроса?» | Про **код**, а не про человека |
| Двадцать мелочей и никакого итога | «Две блокирующие проблемы (авторизация, пропущенный await); остальное — мелочи» | Автор понимает, что действительно важно |
| Молчание, когда работа хорошая | «Здорово, стало гораздо понятнее, чем было» | Похвала подсказывает людям, что стоит делать и дальше |

Если вы **автор**: делайте пул-реквесты маленькими (несколько сотен строк; огромные PR пролистывают, а не ревьюят), пишите описание (что, зачем, как проверить, скриншоты для интерфейса), сначала сами просмотрите свой diff и помните, что комментарии — о коде. Если вы **ревьюер**: отвечайте в течение дня, одобряйте с пометкой «остались только мелочи» вместо ещё одного круга и переносите длинные переписки в короткий созвон.

<Callout type="tip" title="Просите тесты, которые сначала падают">

«Можете добавить тест, который падает без этого исправления?» — один из самых ценных комментариев на ревью. Он доказывает, что баг поняли, документирует его и навсегда защищает от него. А ещё это мягкий способ обнаружить, что исправление ничего не исправляет.

</Callout>

## Дизайн-документы и RFC

Для всего, что занимает больше нескольких дней, затрагивает несколько команд или что трудно отменить (новый сервис, изменение базы данных, публичный API, протокол между клиентом и сервером), перед началом работы напишите короткий **дизайн-документ (design doc)**. В некоторых компаниях его называют **RFC** («request for comments», запрос комментариев). Час обсуждения документа экономит недели переписывания кода, а при написании раздела «альтернативы» часто выясняется, что первая идея была не лучшей.

Шаблон, который хорошо работает (1–3 страниц вполне достаточно):

```markdown
# Дизайн: результаты вживую для PandaPoll

Автор: Мэй · Ревьюеры: Кай, Луна · Статус: на ревью

## Контекст
Результаты обновляются polling'ом раз в 10 с; ведущие хотят «мгновенно».

## Цели и не-цели
- Цель: результаты на каждом экране за 1 с для 5000 зрителей
- Не цель: комментарии вживую (позже, может быть)

## Предложение
WebSocket через `ws`, результаты пачками дважды в секунду,
Redis pub/sub между серверами. Протокол сообщений: ...

## Оценки
Пик 500 голосов/с, 10 000 исходящих сообщений/с (см. таблицу).

## Рассмотренные альтернативы
- Более частый polling: 5000 запросов/с ради небольшого выигрыша
- Server-Sent Events: подходит экранам, но телефоны тоже отправляют

## Риски и открытые вопросы
Лавина переподключений при деплое? Корпоративные прокси блокируют WS?

## Выкатка и тестирование
Фича-флаг на каждое мероприятие, нагрузочный тест на 10 тыс. клиентов, откат.
```

Два самых ценных раздела — **не-цели** (non-goals: они не дают проекту тихо разрастаться) и **рассмотренные альтернативы** (alternatives considered: они доказывают, что вы не просто взяли первую идею, и избавляют следующего человека от изучения тех же вариантов). Когда решение принято, зафиксируйте его в **ADR** (architecture decision record, запись об архитектурном решении): одностраничном Markdown-файле в репозитории, например `docs/adr/0007-websockets-for-live-results.md`, где сказано, что решили, почему и от чего отказались. Через год на вопрос «почему, ради всего святого, это сделано именно так?» найдётся ответ.

## Технический долг

**Технический долг (tech debt)** — это дополнительная цена изменения кода, который написали в спешке или который со временем запутался. Как и кредит, он требует **проценты**: каждая фича, которая затрагивает этот код, делается дольше. И как кредит, часть долга — разумный бизнес-инструмент («выпускаем к конференции, приберёмся в следующем спринте», записанное в виде задачи). Опасен долг, который никто не отслеживает, и код, который никто не решается трогать.

Впрочем, не весь некрасивый код стоит исправлять. Проценты платятся, только когда вы код **меняете**. Быстрый способ найти, где долг действительно болит, — совместить, как часто меняется каждый файл и как часто эти изменения приводят к багам. И то и другое можно достать из `git log`:

<CodeExample output={` 576  votes/count.js (620 строк)
 270  live/broadcast.js (340 строк)
 105  polls/routes.js (210 строк)
   1  legacy/export.js (1900 строк)`}>

```js
// Из `git log` за последние 90 дней, плюс размер каждого файла
const files = [
  { file: "votes/count.js", commits: 48, fixes: 11, lines: 620 },
  { file: "polls/routes.js", commits: 35, fixes: 2, lines: 210 },
  { file: "legacy/export.js", commits: 1, fixes: 0, lines: 1900 },
  { file: "live/broadcast.js", commits: 27, fixes: 9, lines: 340 },
];

// Боль: как часто мы его меняем x как часто изменения его ломают
const hotspots = files
  .map((f) => ({ ...f, pain: f.commits * (1 + f.fixes) }))
  .sort((a, b) => b.pain - a.pain);

for (const { file, pain, lines } of hotspots) {
  const score = String(pain).padStart(4);
  console.log(`${score}  ${file} (${lines} строк)`);
}
```

</CodeExample>

Устаревший файл на 1900 строк самый уродливый, но его никто не трогает, поэтому он почти ничего не стоит. А `votes/count.js` меняется через день и постоянно ломается — вот где рефакторинг окупится быстрее всего. Приносите такие цифры на планирование вместе с ценой на языке команды («каждое изменение подсчёта голосов занимает 3 дня и заканчивается хотфиксом»). На практике:

- **Платите по ходу дела**: оставляйте код, который вы и так меняете, чуть лучше, чем он был («правило бойскаута»).
- **Резервируйте время**: многие команды оставляют 10–20% каждого спринта на долг, а не надеются на месяц уборки, который никогда не наступит.
- **Рефакторьте под защитой тестов**: сначала напишите характеризационные тесты (characterisation tests), которые фиксируют сегодняшнее поведение, а потом меняйте код маленькими безопасными шагами.

## Оценки сроков

Оценки ошибаются предсказуемо: мы представляем себе «счастливый путь», забываем про тестирование, ревью и выкатку и называем одно число, которое все слышат как обещание. Большую часть проблем решают две привычки. Во-первых, **разбивайте работу** на куски по день-два, включая скучные части. Во-вторых, давайте каждому куску **диапазон** (лучший случай, вероятный, худший) и честно складывайте. Быстрая симуляция показывает, почему сумма «вероятных» оценок не работает:

<CodeExample output={`Сумма "вероятных" оценок: 12 дней
Шанс уложиться в 12 дней: 5%
Уверенность 50%: 14.6 дня
Уверенность 85%: 16.5 дня`}>

```js
// Генератор случайных чисел с seed: те же «случайные» числа каждый раз
function mulberry32(seed) {
  return () => {
    seed = (seed + 0x6d2b79f5) | 0;
    let t = Math.imul(seed ^ (seed >>> 15), 1 | seed);
    t = (t + Math.imul(t ^ (t >>> 7), 61 | t)) ^ t;
    return ((t ^ (t >>> 14)) >>> 0) / 4294967296;
  };
}

// Случайная длительность от best до worst, чаще всего около likely
function sample([best, likely, worst], random) {
  const u = random();
  const split = (likely - best) / (worst - best);
  return u < split
    ? best + Math.sqrt(u * (worst - best) * (likely - best))
    : worst - Math.sqrt((1 - u) * (worst - best) * (worst - likely));
}

const tasks = {
  "WebSocket server": [2, 3, 6],
  "Redis pub/sub": [1, 2, 5],
  "Big-screen UI": [2, 3, 5],
  "Tests + review": [1, 2, 4],
  "Load test + rollout": [1, 2, 5],
};

const random = mulberry32(42);
const runs = Array.from({ length: 10_000 }, () =>
  Object.values(tasks).reduce((sum, t) => sum + sample(t, random), 0),
).sort((a, b) => a - b);

const likelySum = Object.values(tasks).reduce((s, t) => s + t[1], 0);
const chance = Math.round(
  runs.filter((days) => days <= likelySum).length / 100,
);
const percentile = (p) => runs[Math.floor((p / 100) * runs.length)];

console.log(`Сумма "вероятных" оценок: ${likelySum} дней`);
console.log(`Шанс уложиться в ${likelySum} дней: ${chance}%`);
console.log(`Уверенность 50%: ${percentile(50).toFixed(1)} дня`);
console.log(`Уверенность 85%: ${percentile(85).toFixed(1)} дня`);
```

</CodeExample>

Это оценка методом **Монте-Карло (Monte Carlo)**: она «делает» фичу 10 000 раз, выбирая случайную длительность для каждой задачи, и смотрит на разброс итоговых сумм. (Генератор с фиксированным seed делает запуск воспроизводимым — точно так же, как внедрённый `random` в функции повторов.) У каждой задачи плохой «хвост» длиннее хорошего, поэтому самый вероятный итог заметно больше суммы вероятных частей. Сумма «вероятных» оценок, 12 дней, получается лишь примерно в 5% случаев.

Поэтому говорите «примерно три недели; на 85% уверен в 17 днях» и обновляйте оценку, как только узнаёте что-то новое. Сюрприз на второй день — повод поговорить; сюрприз в день дедлайна — кризис.

## Менторство junior-разработчиков

Команда с одним блестящим senior и тремя застрявшими junior работает медленнее, чем команда, где растут все. Что работает:

- **Программируйте в паре и пусть за клавиатурой будут они.** Вы штурман и задаёте вопросы; они печатают. Люди учатся, делая сами, а не глядя, как быстро это делаете вы.
- **Спрашивайте, прежде чем подсказывать.** «Что будет, если два голоса придут в один и тот же момент?» учит больше, чем «добавь блокировку». А потом дайте им найти ответ самим.
- **Объясняйте, почему.** «Мы внедряем часы, *чтобы тесты не ждали 30 секунд*» запоминается; «всегда внедряй часы» — нет.
- **Давайте задачи на вырост со страховкой**: настоящую, небольшую, чётко очерченную работу, которая чуть сложнее, чем они умеют, — и будьте рядом.
- **Сделайте так, чтобы «не знать» было безопасно.** Сами говорите: «Не знаю, давай выясним». Junior, который боится спросить, может молча потерять несколько дней.
- **Ревьюйте великодушно.** В PR от junior выберите 2–3 самых важных момента и объясните их; не хороните их под мелочами.
- **Хвалите публично, поправляйте наедине.**

## Дежурства и разбор инцидентов без поиска виноватых

Как только от вашей системы зависят реальные люди, кто-то должен отвечать, когда она ломается в 3 часа ночи. Хорошие **дежурства (on-call)** продумывают, а не терпят:

- **Настраивайте оповещения на симптомы, которые чувствуют пользователи** (доля ошибок, задержка, «WebSocket-соединений стало на 50% меньше»), а не на каждый скачок CPU. Оповещение, на которое не нужно реагировать, приучает людей игнорировать оповещения.
- Каждое оповещение ссылается на **ранбук (runbook)**: что оно значит, как проверить, как смягчить последствия.
- Во время инцидента **сначала устраняйте последствия, потом расследуйте**: откатитесь, выключите фича-флаг, добавьте серверы. Поиск первопричины подождёт, пока у пользователей всё не наладится.
- Назначьте **координатора инцидента (incident commander)**, который управляет процессом (и сам не пишет исправления), и публикуйте короткие обновления в одном канале.
- Делайте графики дежурств человечными: минимум 5–6 человек, передача смены раз в неделю и отгул после тяжёлой ночи.

После каждого серьёзного инцидента пишите **постмортем (postmortem)**. Его задача — научиться, а не наказать, поэтому он должен быть **без поиска виноватых (blameless)**: исходите из того, что все действовали разумно с учётом того, что знали в тот момент, и спрашивайте, как **система** допустила сбой. Люди, которых обвиняют, скрывают ошибки; люди, которые чувствуют себя в безопасности, сообщают о «почти инцидентах» раньше, чем те превратятся в аварии.

| С поиском виноватых | Без поиска виноватых |
| --- | --- |
| «Бао задеплоил во время выступления». | «Наш инструмент деплоя разрешал деплой во время живого мероприятия, и ничто не показывало, что оно идёт». |
| «Кай должен был заметить оповещение». | «В тот день оповещение пришло в канал, где было ещё 200 других». |
| Задача по итогам: «Быть внимательнее». | Задача по итогам: «Блокировать деплой во время живого мероприятия; переподключаться с экспоненциальной задержкой и разбросом». |

Полезная техника — **пять «почему»** (five whys): спрашивайте «почему?», пока не дойдёте до того, что можно исправить в системе. *Экраны зависли.* Почему? Все WebSocket-серверы перезапустились одновременно. Почему? Деплой заменил все серверы за один шаг. Почему? Конфигурацию деплоя скопировали со stateless API. Почему это так сильно ударило? 5000 клиентов мгновенно переподключились без задержки, и новые серверы упали. Теперь у нас три конкретных исправления, и ни одно из них не называется «Бао».

Что должна делать `summarizeVotes(votes, poll)`:

- `votes` — массив `{ pollId, voterId, option }` в порядке поступления; `poll` — это `{ id, options }`.
- Учитываются только голоса за **этот** опрос и за один из **его вариантов**.
- Участники могут передумать: каждый участник учитывается **один раз**, по своему **последнему** корректному голосу.
- Верните `{ total, results }`, где в `results` есть **каждый** вариант опроса в виде `{ option, count, percent }` (процент округлён и равен 0, когда голосов нет), отсортированные по количеству голосов, от большего к меньшему. При равенстве сохраняется порядок вариантов в опросе.
- Никогда не изменяйте массив `votes`, который передал вызывающий код.

Какие баги искать: ошибку на единицу, изменение аргумента, сломанную сортировку, объект в роли словаря и несколько невыполненных требований. Заодно используйте `const`/`let` и имена, которые говорят, что они обозначают.

<Hint>

Лучше начать заново, чем латать каждую строку. Перебирайте голоса циклом `for (const { pollId, voterId, option } of votes)` и храните `Map` из id участника в его последний вариант: `latest.set(voterId, option)` перезаписывает более ранние голоса, так что `reverse()` не нужен. Сохраняйте только голоса, где `pollId === poll.id && poll.options.includes(option)`. Затем создайте `new Map(poll.options.map((o) => [o, 0]))`, чтобы каждый вариант начинался с 0, посчитайте значения первого словаря и превратите записи в объекты результатов. Функция сравнения должна возвращать **число**: `(a, b) => b.count - a.count`. `Array.prototype.sort` стабильна, поэтому при равенстве порядок сохраняется.

</Hint>

```js
import { describe, it, expect } from "vitest";

// PR #318: "Сводка результатов вживую для большого экрана"
// votes: [{ pollId, voterId, option }] в порядке поступления
function summarizeVotes(votes, poll) {
  // Участник может передумать: учитывается его последний корректный голос
  const latestChoice = new Map(); // voterId -> option
  for (const { pollId, voterId, option } of votes) {
    if (pollId === poll.id && poll.options.includes(option)) {
      latestChoice.set(voterId, option);
    }
  }

  const counts = new Map(poll.options.map((option) => [option, 0]));
  for (const option of latestChoice.values()) {
    counts.set(option, counts.get(option) + 1);
  }

  const total = latestChoice.size;
  const percentOf = (count) =>
    total === 0 ? 0 : Math.round((count / total) * 100);

  const results = [...counts].map(([option, count]) => ({
    option,
    count,
    percent: percentOf(count),
  }));
  // sort стабильна, поэтому при равенстве сохраняется порядок опроса
  results.sort((a, b) => b.count - a.count);
  return { total, results };
}
```

## Итоги

- Код-ревью ловит проблемы на ранней стадии, распространяет знания и поддерживает единообразие кода. Проверяйте корректность и архитектуру раньше имён; остальное оставьте Prettier, ESLint и TypeScript.
- Знайте типичных подозреваемых в JavaScript: `sort()` без функции сравнения, `map(parseInt)`, `||` против `??`, асинхронный `forEach`, пропущенный `await`, изменённые аргументы.
- Пишите комментарии **конкретные, доброжелательные и с метками** (issue, question, suggestion, nit, praise) — о коде, а не о человеке — и просите тесты, которые падают без исправления.
- Перед большой или трудно обратимой работой пишите короткий **дизайн-документ**; ключевые разделы — **не-цели** и **альтернативы**. Фиксируйте решения в **ADR**.
- Разбирайтесь с **техническим долгом** там, где скапливаются изменения и баги, а не там, где код просто некрасивый; выплачивайте его постоянно.
- Оценивайте сроки **диапазонами** и включайте скучные задачи; сумма «вероятных» оценок почти всегда слишком оптимистична.
- **Наставляйте**: пусть junior сидит за клавиатурой, задавайте вопросы и объясняйте, почему.
- Дежурства: оповещения на симптомы, сначала устранение последствий, а учиться — на **постмортемах без поиска виноватых**, задачи из которых исправляют систему.
