So far, all your code has lived in one file. That's fine for small programs, but a real app might have thousands of lines. Scrolling through one giant file to find a function gets painful fast! **Modules** let you split code into separate files, each with one job, and share pieces between them.

## Why split code into modules?

A **module** is simply a JavaScript file that can **export** things (share them) and **import** things from other files (use them). Modules give you:

- **Organisation**: `cart.js` handles the cart, `prices.js` handles prices. You always know where to look.
- **Reuse**: write a helper once and import it wherever you need it.
- **Their own scope**: variables in one module can't accidentally clash with variables in another.
- **Clear connections**: the `import` lines at the top of a file show exactly what it depends on.

</Callout>

## Named exports

Put `export` in front of anything you want to share: variables, functions or classes.

```js title="math.js"
export const PI = 3.14159;

export function add(a, b) {
  return a + b;
}

export function circleArea(radius) {
  return PI * radius * radius;
}

// Not exported: only this file can use it
function secretHelper() {}
```

Then **import** them by name, inside curly braces:

```js title="main.js"
import { add, circleArea } from "./math.js";

console.log(add(2, 3)); // 5
console.log(circleArea(1)); // 3.14159
```

- The names in `{ }` must **match** the exported names exactly.
- The path starts with `./` (meaning "in this folder") and includes the `.js` extension.
- You only import what you need. `secretHelper` wasn't exported, so `main.js` can't use it.

You can also export a list in one go at the bottom of a file:

```js title="math.js"
const PI = 3.14159;
function add(a, b) {
  return a + b;
}

export { PI, add };
```

## Default exports

A file can also have **one default export**: the main thing that file provides. It's often used when a file contains a single class or function:

```js title="ShoppingCart.js"
export default class ShoppingCart {
  items = [];

  add(item) {
    this.items.push(item);
  }
}
```

When importing a default export, you **don't** use curly braces, and you can pick any name you like:

```js title="main.js"
import ShoppingCart from "./ShoppingCart.js";

const cart = new ShoppingCart();
cart.add("bamboo");
```

A file can have both. The default comes first, then the named ones in braces:

```js title="main.js"
import formatPrice, { TAX_RATE } from "./prices.js";
```

| | Named export | Default export |
| --- | --- | --- |
| How many per file | As many as you like | At most one |
| Export | `export function add() {}` | `export default function () {}` |
| Import | `import { add } from "./x.js"` | `import anything from "./x.js"` |
| Name when importing | Must match | Your choice |

<Callout type="tip" title="Many teams prefer named exports">

Because the names must match, named exports keep the same name everywhere in a project, which makes code easier to search and tools better at auto-importing. Default exports are still common, especially for classes and components.

</Callout>

## Renaming with `as`

What if two modules export something with the same name? Rename it while importing with `as`:

```js title="main.js"
import { format as formatDate } from "./dates.js";
import { format as formatPrice } from "./prices.js";

console.log(formatDate(new Date()));
console.log(formatPrice(9.5));
```

`as` works when exporting too: `export { add as sum };` shares `add` under the name `sum`.

## Importing everything with `import * as`

To grab **all** the named exports at once, import them as one object, called a **namespace**:

```js title="main.js"
import * as math from "./math.js";

console.log(math.PI); // 3.14159
console.log(math.add(2, 3)); // 5
```

This is handy when a module exports lots of related helpers, and `math.add` makes it obvious where `add` came from.

## Modules have their own scope

Every module has its **own private scope**. Variables declared at the top of a module are **not** global: other files can only see what you export. On top of that:

- Modules **always run in strict mode**, so sloppy mistakes like using an undeclared variable become errors.
- A module's code runs **once**, the first time it's imported. Importing it again from another file reuses the same exports.

Before modules existed, developers got a private scope by wrapping code in a function that runs straight away, called an **IIFE** (Immediately Invoked Function Expression). It returns an object with only the parts it wants to share, just like an export list:

<CodeExample output={`2
undefined`}>

```js
const counter = (() => {
  let count = 0; // private: only the functions below see it

  function increment() {
    count++;
    return count;
  }

  return { increment }; // the "exports"
})();

counter.increment();
console.log(counter.increment());
console.log(counter.count);
```

</CodeExample>

`count` lives inside the function, so the outside world can only change it through `increment()`. Real modules give you this privacy for free, with much nicer syntax. You'll still see IIFEs in older code.

## Modules in the browser

To use modules in a web page, add `type="module"` to your script tag. You only need to load the entry file; it imports the rest:

```html title="index.html"
<script type="module" src="main.js"></script>
```

Module scripts are **deferred** automatically: they wait until the HTML has been read, so the page's elements already exist when your code runs.

<Callout type="warning" title="Use a local server">

If you open `index.html` by double-clicking it (a `file://` address), browsers block module imports for security reasons. Run a small local server instead, such as the **Live Server** extension in VS Code.

</Callout>

## Modules in Node.js

Node.js (JavaScript outside the browser, more on it in the next lesson) supports the same `import` and `export`. Tell Node your project uses them by adding `"type": "module"` to `package.json`:

```json title="package.json"
{
  "name": "my-app",
  "type": "module"
}
```

Then run the entry file from a terminal:

```bash
node main.js
```

Alternatively, name a file with the `.mjs` extension and Node treats it as a module without any settings.

<Callout type="note" title="You'll also see require()">

Older Node code uses a different system called **CommonJS**: `const fs = require("fs")` and `module.exports = ...`. It does the same job. For new code, use `import` and `export`, the official standard that works in both the browser and Node.

</Callout>

Use the IIFE pattern to build a `scoreboard` "module". Keep the scores **private** inside the function, and return an object with just two functions:

- `add(name, points)` adds points to that player's score.
- `total(name)` returns that player's total, or `0` if they haven't scored yet.

<Hint>

Inside the IIFE, create `const scores = {};`. In `add`, if `scores[name]` is `undefined`, set it to `0` first, then add the points. In `total`, do the same check before returning. Finally `return { add, total };`.

</Hint>

<Solution>

```js
const scoreboard = (() => {
  const scores = {};

  function add(name, points) {
    if (scores[name] === undefined) {
      scores[name] = 0;
    }
    scores[name] += points;
  }

  function total(name) {
    if (scores[name] === undefined) {
      return 0;
    }
    return scores[name];
  }

  return { add, total };
})();

scoreboard.add("Mei", 10);
scoreboard.add("Mei", 5);
console.log(scoreboard.total("Mei")); // 15
```

</Solution>

## Recap

- A **module** is a file that shares code with `export` and uses other files' code with `import`.
- **Named exports** are imported with braces and matching names; a file's single **default export** is imported without braces, under any name.
- Rename with `as`, or grab everything with `import * as name`.
- Modules have their **own scope**, run in **strict mode** and run only once.
- Use `<script type="module">` in the browser, and `"type": "module"` (or `.mjs`) in Node.
