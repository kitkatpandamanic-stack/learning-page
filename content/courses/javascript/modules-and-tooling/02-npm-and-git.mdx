Real projects don't start from nothing. Developers reuse code that other people have shared, and they keep a history of every change so they can undo mistakes and work in teams. The two tools that make this possible are **npm** and **Git**. You'll use both in almost every JavaScript project, so let's get comfortable with the essentials. 🐼

<Callout type="note" title="These commands run on your computer">

Everything in this lesson happens in a **terminal** on your own machine, not in the PandaDev code runner. Lines in `bash` blocks are commands to type; the text after them is what you might see.

</Callout>

## Node.js and npm

**Node.js** lets you run JavaScript outside the browser: on your computer or on a server. When you install Node (from nodejs.org, the **LTS** version is the safe choice), you also get **npm**, the **Node Package Manager**.

npm connects you to the **npm registry**, a huge online library of free, reusable code **packages**: date helpers, testing tools, whole frameworks like React. Check both are installed:

```bash
node --version
npm --version
```

You can run any JavaScript file with Node:

```bash
node hello.js
```

## Starting a project with `npm init`

Every npm project has a **`package.json`** file in its main folder. It describes your project: its name, version, the packages it needs and handy commands. Create one with:

```bash
mkdir panda-app
cd panda-app
npm init -y
```

`npm init` asks a few questions; `-y` says "yes, use the defaults" to all of them. You'll get a file like this:

```json title="package.json"
{
  "name": "panda-app",
  "version": "1.0.0",
  "main": "index.js",
  "scripts": {
    "test": "echo \"Error: no test specified\" && exit 1"
  }
}
```

## Installing packages

Use `npm install` (or the shorter `npm i`) followed by a package name:

```bash
npm install dayjs
```

Three things happen:

1. npm downloads the package (and anything it depends on) into a **`node_modules`** folder.
2. It's added to **`dependencies`** in `package.json`.
3. A **`package-lock.json`** file records the **exact** version of every package installed.

Then you can import it in your code, just like your own modules:

```js title="index.js"
import dayjs from "dayjs";

console.log(dayjs().format("D MMMM YYYY"));
```

### `dependencies` vs `devDependencies`

Some packages are only needed **while you develop**, like a testing tool. Install those with `--save-dev` (or `-D`):

```bash
npm install --save-dev vitest
```

```json title="package.json"
{
  "name": "panda-app",
  "version": "1.0.0",
  "type": "module",
  "dependencies": {
    "dayjs": "^1.11.13"
  },
  "devDependencies": {
    "vitest": "^3.2.4"
  }
}
```

- **`dependencies`**: packages your app needs to **run** (for example a date library).
- **`devDependencies`**: packages you only need to **build or test** it. They aren't needed by your finished app.

### Version numbers and `^`

Package versions follow **semantic versioning** (semver): `MAJOR.MINOR.PATCH`, like `1.11.13`.

| Part | Goes up when... | Example |
| --- | --- | --- |
| **PATCH** | Bugs are fixed | `1.11.13` → `1.11.14` |
| **MINOR** | New features are added, nothing breaks | `1.11.13` → `1.12.0` |
| **MAJOR** | Something changes that could break your code | `1.11.13` → `2.0.0` |

The **`^`** (caret) in `"^1.11.13"` means "this version or any newer one, as long as the MAJOR number stays `1`". So you get bug fixes and new features, but not breaking changes. The lock file then pins down exactly which version you got, so everyone on the team installs the same one.

## npm scripts

The `"scripts"` section stores commands with short names, so nobody has to remember long ones:

```json title="package.json"
{
  "scripts": {
    "start": "node index.js",
    "test": "vitest"
  }
}
```

Run a script with `npm run <name>`:

```bash
npm run start
npm run test
```

`start` and `test` are so common they have shortcuts: `npm start` and `npm test`.

## `npx`: run a package's command

Some packages are **tools** you run from the terminal. `npx` runs them without a global install. If the package isn't in your project, npx downloads it temporarily:

```bash
npx vitest
npx prettier --write .
```

You'll often see `npx` in setup guides, for example to create a brand new app from a template.

## `node_modules`: never commit it

`node_modules` can easily contain **thousands** of files and hundreds of megabytes. You never edit it, and you never share it. Anyone can rebuild it exactly from `package.json` and `package-lock.json`:

```bash
npm install
```

Running `npm install` with no package name installs everything the project lists. That's the first thing you do after downloading someone else's project.

<Callout type="warning" title="Commit the lock file, ignore node_modules">

Always save `package.json` and `package-lock.json` in Git. Always **ignore** `node_modules`. You'll see how to do that with `.gitignore` in a moment.

</Callout>

## Git: a history of your code

**Git** is a **version control** system. It takes **snapshots** of your project, called **commits**, so you can:

- see what changed, when and why,
- go back to a version that worked,
- try ideas safely on a separate **branch**,
- work with other people on the same code.

A folder that Git tracks is called a **repository** (or **repo**).

## Your first commits

Turn your project folder into a repository:

```bash
git init
```

Check what Git sees at any time with `git status`. It's the command you'll use most:

```bash
git status
```

```text
On branch main
Untracked files:
  index.js
  package.json
```

Saving a snapshot takes two steps: **stage** the changes you want with `git add`, then **commit** them with a message:

```bash
git add index.js package.json
git commit -m "Add first version of the panda app"
```

`git add .` stages every change in the folder at once. To see your history, use `git log`:

```bash
git log --oneline
```

```text
3f2a9c1 Add first version of the panda app
```

<Callout type="tip" title="Write useful commit messages">

Describe **what** the commit does, in a short sentence: `Fix total when cart is empty` beats `stuff` or `changes`. Make small, focused commits often, rather than one huge one at the end of the day.

</Callout>

## Ignoring files with `.gitignore`

Create a file called `.gitignore` in your project's main folder. Git won't track anything that matches the patterns in it:

```text title=".gitignore"
node_modules/
.env
dist/
.DS_Store
```

- `node_modules/` can be rebuilt with `npm install`.
- `.env` files often hold **secrets** like API keys.
- `dist/` is build output that can be regenerated.

## Branches

A **branch** is a separate line of work. You can build a new feature on a branch without disturbing the working code on `main`:

```bash
git switch -c dark-mode
# ...edit files...
git add .
git commit -m "Add dark mode toggle"
```

`git switch -c` creates a new branch and moves onto it (older guides use `git checkout -b`, which does the same). When the feature is ready, go back to `main` and **merge** it in:

```bash
git switch main
git merge dark-mode
```

`git branch` lists your branches and marks the one you're on with a `*`.

## Pushing to GitHub

**GitHub** is a website that stores Git repositories online, so your code is backed up and others can see it and help. Git and GitHub are different things: Git runs on your computer, GitHub hosts copies of repos.

After creating an empty repository on GitHub, connect it and **push** your commits:

```bash
git remote add origin https://github.com/your-name/panda-app.git
git push -u origin main
```

- `origin` is the usual nickname for your main online copy.
- `-u` remembers the connection, so next time a plain `git push` is enough.
- `git pull` does the opposite, downloading new commits from GitHub.

<Callout type="danger" title="Never commit secrets">

Passwords, API keys and tokens must never go into a commit, even in a private repo. Once pushed, they live on in the history. Keep them in a `.env` file that's listed in `.gitignore`. If you leak a key by accident, **revoke it** and create a new one straight away.

</Callout>

## Recap

- **Node.js** runs JavaScript outside the browser; **npm** installs packages from the npm registry.
- `npm init -y` creates **`package.json`**; `npm install name` adds a **dependency**, and `-D` adds a **devDependency**.
- `^1.2.3` accepts newer minor and patch versions, but not a new major version. The lock file pins exact versions.
- **Scripts** run with `npm run name`; **npx** runs package tools without installing them globally.
- Never commit **`node_modules`**: `npm install` rebuilds it.
- Git basics: `git init`, `git status`, `git add`, `git commit -m`, `git log`.
- Use **branches** for new work, **`.gitignore`** for files Git should skip, and `git push` to back up to **GitHub**.
