Almost every real app talks to a server. The weather app asks for today's forecast, the shop asks for its products, the chat asks for new messages. They all do it the same way: they send an **HTTP request** to an **API** (a URL made for programs, not people) and get **JSON** back. In JavaScript, the tool for that is **`fetch`**. 🌐

## HTTP in two minutes

Every conversation with a server is a **request** followed by a **response**. A request has:

- a **method**: what you want to do,
- a **URL**: what you want to do it to,
- optional **headers** (extra information, like "I'm sending JSON") and a **body** (the data you send).

The response comes back with a **status code**, headers and a body. Here's what a request and its response really look like as text:

```text
GET /movies/3 HTTP/1.1
Host: api.pandadev.test
Accept: application/json

HTTP/1.1 200 OK
Content-Type: application/json

{"id":3,"title":"Midnight in the Forest","year":2015,...}
```

The methods you'll use most, and the status codes worth knowing by heart:

| Method | Means |
| --- | --- |
| `GET` | read something |
| `POST` | create something |
| `PUT` / `PATCH` | replace / change something |
| `DELETE` | delete something |

| Status | Means |
| --- | --- |
| `200` OK | it worked |
| `201` Created | a new thing was made |
| `204` No Content | it worked, and there's no body |
| `400` Bad Request / `404` Not Found | your mistake: bad data / no such thing |
| `500` Internal Server Error / `503` Service Unavailable | the server's problem |

The rule of thumb: **2xx** means success, **4xx** means the client (you) did something wrong, **5xx** means the server failed.

<Callout type="note" title="The PandaDev practice API">

PandaDev has a practice API built in at `https://api.pandadev.test`, so these lessons work offline and always give the same answers. It has movies, weather, recipes, users, posts and a to-do list you can change. Real APIs work exactly the same way: only the URL changes.

</Callout>

## Your first fetch

`fetch(url)` sends a `GET` request and returns a **promise** of a `Response`. Reading the body as JSON is a second step, with its own promise:

<CodeExample output={`200 true
Midnight in the Forest
2015, directed by Ada Brooks
[ 'drama', 'mystery' ]`}>

```js
const response = await fetch("https://api.pandadev.test/movies/3");
console.log(response.status, response.ok);

const movie = await response.json();
console.log(movie.title);
console.log(`${movie.year}, directed by ${movie.director}`);
console.log(movie.genres);
```

</CodeExample>

Why two `await`s? The server sends the **status and headers first**, and the body can follow later (it might be megabytes). The first `await` waits for the start of the response, so you can check the status straight away; `response.json()` then waits for the whole body and turns the JSON text into a JavaScript object.

## Reading the response

The `Response` object tells you everything about the answer:

<CodeExample output={`200
OK
true
application/json; charset=utf-8
string 123
The Bamboo Heist`}>

```js
const response = await fetch("https://api.pandadev.test/movies/1");

console.log(response.status);        // 200
console.log(response.statusText);    // "OK"
console.log(response.ok);            // true for 200–299
console.log(response.headers.get("content-type"));

const text = await response.text();  // the raw body
console.log(typeof text, text.length);
const movie = JSON.parse(text);      // what .json() does
console.log(movie.title);
```

</CodeExample>

`response.json()` is really just `response.text()` followed by `JSON.parse`. Use `.text()` when an API sends plain text or HTML.

<Callout type="warning" title="You can read the body only once">

The body is a **stream**: once `.json()` or `.text()` has read it, it's gone. Calling `.json()` a second time on the same response throws a `TypeError`. Read it once, keep the result in a variable, and use that.

</Callout>

## Query strings with URL and URLSearchParams

Many endpoints take options in the **query string**, the part after `?`: `/movies?search=bamboo&genre=comedy`. It's tempting to glue that together with a template string, but some characters have special meaning in URLs (`&`, `?`, `#`, `+`, spaces…) and break it:

<CodeExample output={`[ [ 'search', 'tea ' ], [ ' cake', '' ] ]
https://api.pandadev.test/movies?search=tea+%26+cake&limit=3
[ [ 'search', 'tea & cake' ], [ 'limit', '3' ] ]`}>

```js
const search = "tea & cake";

// ❌ Gluing strings: the & splits the value in two
const bad = new URL(
  `https://api.pandadev.test/movies?search=${search}`,
);
console.log([...bad.searchParams]);

// ✅ URLSearchParams encodes everything for you
const url = new URL("https://api.pandadev.test/movies");
url.searchParams.set("search", search);
url.searchParams.set("limit", 3);
console.log(url.href);
console.log([...url.searchParams]);
```

</CodeExample>

With the glued string, the server would search for `"tea "` and get a mysterious extra parameter called `" cake"`. The `URL` object's **`searchParams`** encodes each value safely (`&` becomes `%26`, spaces become `+`). Numbers are fine too: they're turned into text.

You can pass a `URL` object straight to `fetch`. The movie list is **paginated**: it answers with one page of results plus enough information to ask for the next:

<CodeExample output={`Page 2 of 2
4 comedies in total
- Ninja Pandas II (5.9)
- Tea for Two Thousand (6.7)`}>

```js
const url = new URL("https://api.pandadev.test/movies");
url.searchParams.set("genre", "comedy");
url.searchParams.set("limit", 2);
url.searchParams.set("page", 2);

const response = await fetch(url);
const data = await response.json();

console.log(`Page ${data.page} of ${data.totalPages}`);
console.log(`${data.total} comedies in total`);
for (const movie of data.results) {
  console.log(`- ${movie.title} (${movie.rating})`);
}
```

</CodeExample>

<Callout type="tip" title="new URL(path, base)">

`new URL("/movies", "https://api.pandadev.test")` joins a path onto a base URL. Real projects keep the base in one constant (`const API = "https://..."`), so switching from a test server to the real one is a one-line change.

</Callout>

## When things go wrong: 404 vs network errors

Here's the surprise that catches everyone: **`fetch` does not throw for 404 or 500**. As far as `fetch` is concerned, the server *answered*, so the request worked. You get a normal `Response` with `ok` set to `false`:

<CodeExample output={`/movies/2 → 200 true
/movies/99 → 404 false
/status/500 → 500 false`}>

```js
const API = "https://api.pandadev.test";

for (const path of ["/movies/2", "/movies/99", "/status/500"]) {
  try {
    const response = await fetch(API + path);
    console.log(path, "→", response.status, response.ok);
  } catch (error) {
    console.log(path, "→ never answered:", error.name);
  }
}
```

</CodeExample>

(`/status/500` is a practice endpoint that answers with whatever status you put in the URL.) The `catch` never ran. `fetch` only **rejects** when there is no answer at all: the user is offline, the domain doesn't exist, or the browser blocked the request. Then you get a `TypeError`:

```text
TypeError: Failed to fetch
```

So there are two different failures to handle:

| What happened | What `fetch` does | How you notice |
| --- | --- | --- |
| The server said no (404, 500…) | resolves | `response.ok === false` |
| No answer at all (offline…) | rejects | `try/catch` around `await fetch(...)` |

<Callout type="danger" title="Always check response.ok">

Code like `const movie = await (await fetch(url)).json();` happily "works" on a 404: `movie` becomes `{ error: 'Movie not found' }` and your page shows *undefined (undefined)*. Check `response.ok` (or `response.status`) before you trust the body.

</Callout>

## A small getJSON helper

Checking `ok` every time gets repetitive, so real projects wrap `fetch` in a small helper that **turns a bad status into an error**. Then a single `try/catch` handles both kinds of failure:

<CodeExample output={`[ 'Panda Express to Mars', 'Ninja Pandas II' ]
[ 'mei', 'sam', 'ada' ]
HTTP 404 for /movies/42`}>

```js
const API = "https://api.pandadev.test";

async function getJSON(path, params = {}) {
  const url = new URL(path, API);
  for (const [key, value] of Object.entries(params)) {
    url.searchParams.set(key, value);
  }

  const response = await fetch(url);
  if (!response.ok) {
    throw new Error(`HTTP ${response.status} for ${url.pathname}`);
  }
  return response.json();
}

const page = await getJSON("/movies", { search: "panda" });
console.log(page.results.map((movie) => movie.title));

const users = await getJSON("/users");
console.log(users.map((user) => user.username));

try {
  await getJSON("/movies/42");
} catch (error) {
  console.log(error.message);
}
```

</CodeExample>

Notice `return response.json()` without `await`: returning a promise from an `async` function is fine, the caller's `await` waits for it.

Because `getJSON` returns a promise, you can run several requests **at the same time** with `Promise.all`, which you met in the Asynchronous JavaScript module:

<CodeExample output={`[ 'The Bamboo Heist', 'The Last Dumpling', 'The Great Bamboo Race' ]
in parallel`}>

```js
const API = "https://api.pandadev.test";

async function getJSON(path) {
  const response = await fetch(API + path);
  if (!response.ok) throw new Error(`HTTP ${response.status}`);
  return response.json();
}

const start = Date.now();
const movies = await Promise.all(
  [1, 4, 12].map((id) => getJSON(`/movies/${id}`)),
);
const took = Date.now() - start;

console.log(movies.map((movie) => movie.title));
console.log(took < 300 ? "in parallel" : "one by one");
```

</CodeExample>

Each request takes about 100 ms, so three in parallel take about 100 ms, not 300.

## In real projects: API keys

Most real APIs want to know who's asking, so they give you an **API key**. You usually send it in a header:

```js
const url = new URL("https://api.themoviedb.org/3/search/movie");
url.searchParams.set("query", "panda");

const response = await fetch(url, {
  headers: { Authorization: `Bearer ${API_KEY}` },
});
```

Keep two things in mind. First, anything in front-end JavaScript can be read by every visitor, so **secret keys belong on your server**, never in browser code. Second, browsers only let a page read answers from another domain if that server allows it (a security rule called **CORS**); when an API doesn't, the request fails with the same `TypeError` as being offline. Calling such APIs from your own server avoids both problems, which you'll do in the Node.js & Express module.

## Recap

- An HTTP request has a **method** (`GET`, `POST`, `PATCH`, `DELETE`…), a **URL**, headers and maybe a body; the response has a **status code**, headers and a body. 2xx = success, 4xx = client mistake, 5xx = server problem.
- `const response = await fetch(url)` gives you the status and headers; `await response.json()` reads the body (only once!).
- Build query strings with `new URL(path, base)` and `url.searchParams.set(...)`, never by gluing strings.
- `fetch` **doesn't throw on 404 or 500**: check `response.ok`. It only rejects (with a `TypeError`) when there's no answer at all.
- A small `getJSON` helper that throws on bad statuses keeps the rest of your code short, and `Promise.all` runs several requests in parallel.
- Secret API keys never go in browser code.
