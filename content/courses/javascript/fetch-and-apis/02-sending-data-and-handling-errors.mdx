Reading data is only half the story. Apps also **send** data: a new to-do, a changed profile, a deleted photo. And real networks are messy: servers say no, answer slowly or fall over for a moment. In this lesson you'll send data with `fetch`, then build the kind of small, sturdy request helper that real projects rely on. 🛠️

## Sending data with POST

`fetch` takes a second argument, an **options object**. To create something, you set three options:

- `method: "POST"`,
- a `Content-Type` **header** that tells the server the body is JSON,
- the `body` itself, turned into a JSON **string** with `JSON.stringify`.

<CodeExample output={`201 Created
{ id: 4, title: 'Learn fetch options', done: false }`}>

```js
const response = await fetch("https://api.pandadev.test/todos", {
  method: "POST",
  headers: { "Content-Type": "application/json" },
  body: JSON.stringify({ title: "Learn fetch options" }),
});

console.log(response.status, response.statusText);
const todo = await response.json();
console.log(todo);
```

</CodeExample>

The API answers **201 Created** and sends back the new to-do, including the `id` the server gave it. That's the usual pattern: you send what you know, the server fills in the rest (ids, dates, defaults) and returns the complete object.

When the server doesn't like what you sent, it answers **400 Bad Request**, and good APIs explain why in the body:

<CodeExample output={`400 { error: 'title is required' }
400 { error: 'title is required' }`}>

```js
const API = "https://api.pandadev.test";

// ❌ Forgot JSON.stringify: the body becomes "[object Object]"
const oops = await fetch(`${API}/todos`, {
  method: "POST",
  headers: { "Content-Type": "application/json" },
  body: { title: "Buy bamboo" },
});
console.log(oops.status, await oops.json());

// ❌ Forgot the title altogether
const empty = await fetch(`${API}/todos`, {
  method: "POST",
  headers: { "Content-Type": "application/json" },
  body: JSON.stringify({ done: true }),
});
console.log(empty.status, await empty.json());
```

</CodeExample>

<Callout type="warning" title="The body must be a string">

`fetch` doesn't turn objects into JSON for you. Pass an object as `body` and it is converted with `String(...)`, which gives the useless text `"[object Object]"`. Always write `body: JSON.stringify(data)`, and add the `Content-Type: application/json` header: many servers (Express included, as you'll see later) ignore a JSON body without it.

</Callout>

## Changing and deleting

`PATCH` changes only the fields you send; `PUT` replaces the whole thing. `DELETE` removes it and usually answers **204 No Content**, which means exactly what it says: there is **no body**, so don't call `.json()` on it (it would throw a `SyntaxError`).

<CodeExample output={`200 { id: 2, title: 'Build the movie app', done: true }
204 No Content
[ 'Learn fetch', 'Build the movie app' ]`}>

```js
const API = "https://api.pandadev.test";
const json = { "Content-Type": "application/json" };

// PATCH: change only the fields you send
const patched = await fetch(`${API}/todos/2`, {
  method: "PATCH",
  headers: json,
  body: JSON.stringify({ done: true }),
});
console.log(patched.status, await patched.json());

// DELETE: 204 No Content, so there's no body to read
const deleted = await fetch(`${API}/todos/3`, { method: "DELETE" });
console.log(deleted.status, deleted.statusText);

const list = await fetch(`${API}/todos`).then((r) => r.json());
console.log(list.map((todo) => todo.title));
```

</CodeExample>

This set of operations (create, read, update, delete) is called **CRUD**, and an API that maps them onto HTTP methods and URLs like `/todos` and `/todos/2` is called a **REST API**:

| Request | Does | Success |
| --- | --- | --- |
| `GET /todos` | list all to-dos | 200 + a list |
| `POST /todos` | create one | 201 + the new to-do |
| `GET /todos/2` | read one | 200 + the to-do |
| `PATCH /todos/2` | change some fields | 200 + the updated to-do |
| `DELETE /todos/2` | delete it | 204, no body |

## A robust request helper

Look at how much code each request needed: options, headers, `JSON.stringify`, checking `ok`, reading the error message. Repeat that across an app and bugs creep in. So real projects write **one** helper that does it all, and throws a proper error with the API's own message when something goes wrong:

<CodeExample output={`{ id: 4, title: 'Write a request helper', done: false }
null
ApiError 404: Todo not found
ApiError 400: city is required
ApiError 418: I'm a teapot`}>

```js
const API = "https://api.pandadev.test";

class ApiError extends Error {
  constructor(status, message) {
    super(message);
    this.name = "ApiError";
    this.status = status;
  }
}

async function request(path, { method = "GET", body } = {}) {
  const options = { method, headers: {} };
  if (body !== undefined) {
    options.headers["Content-Type"] = "application/json";
    options.body = JSON.stringify(body);
  }

  const response = await fetch(API + path, options);
  // 204 or a body that isn't JSON: use null instead of crashing
  const data = await response.json().catch(() => null);

  if (!response.ok) {
    const message = data?.error ?? `HTTP ${response.status}`;
    throw new ApiError(response.status, message);
  }
  return data;
}

const todo = await request("/todos", {
  method: "POST",
  body: { title: "Write a request helper" },
});
console.log(todo);
console.log(await request(`/todos/${todo.id}`, { method: "DELETE" }));

for (const path of ["/todos/99", "/weather", "/status/418"]) {
  try {
    await request(path);
  } catch (error) {
    console.log(`${error.name} ${error.status}: ${error.message}`);
  }
}
```

</CodeExample>

A few details make this helper sturdy:

- **Destructuring with defaults** (`{ method = "GET", body } = {}`) means you can call `request("/todos")` with no options at all.
- **`response.json().catch(() => null)`** copes with a 204 (no body) and with servers that send an HTML error page instead of JSON.
- **`ApiError` keeps the status**, so callers can react differently: show "not found" for 404, ask the user to log in for 401, try again later for 503.
- **`data?.error ?? ...`** uses the API's message when there is one, and falls back to the status code when there isn't. Every API names this field differently (`error`, `message`, `detail`…), so this is the one line you adapt.

<Callout type="tip" title="In real projects">

Teams often use a small library for this, such as `ky` or `axios`, which add JSON handling, errors for bad statuses, timeouts and retries out of the box. They're built on exactly the ideas in this lesson, so once you've written your own helper, they hold no mystery:

```js
import ky from "ky";

const todo = await ky
  .post("https://api.example.com/todos", { json: { title: "Hi" } })
  .json();
```

</Callout>

## Timeouts with AbortSignal

What if the server never answers? By default `fetch` waits a very long time, and your user stares at a spinner. Give up after a sensible limit with **`AbortSignal.timeout(ms)`**, passed as the `signal` option. When time runs out, `fetch` rejects with an error named `TimeoutError`:

<CodeExample output={`Gave up after 500 ms
Fast one: { waited: 200 }`}>

```js
const API = "https://api.pandadev.test";

// /delay/1500 answers after 1.5 seconds: too slow for us
try {
  const response = await fetch(`${API}/delay/1500`, {
    signal: AbortSignal.timeout(500),
  });
  console.log("Answered:", response.status);
} catch (error) {
  if (error.name === "TimeoutError") {
    console.log("Gave up after 500 ms");
  } else {
    throw error;
  }
}

const fast = await fetch(`${API}/delay/200`, {
  signal: AbortSignal.timeout(500),
});
console.log("Fast one:", await fast.json());
```

</CodeExample>

Sometimes you want to cancel a request yourself, for example when the user types a new search before the old one has answered. An **`AbortController`** gives you a signal plus an `abort()` button. Aborting makes `fetch` reject with an `AbortError`:

<CodeExample output={`Request sent...
AbortError
Aborted? true`}>

```js
const API = "https://api.pandadev.test";
const controller = new AbortController();

const search = fetch(`${API}/movies?search=panda`, {
  signal: controller.signal,
});
console.log("Request sent...");

// The user typed something new, so this answer is useless now
controller.abort();

try {
  await search;
} catch (error) {
  console.log(error.name);
}
console.log("Aborted?", controller.signal.aborted);
```

</CodeExample>

Check `error.name` (`"TimeoutError"`, `"AbortError"`) rather than the message: the messages differ from browser to browser.

## Retries with backoff

Some failures are **temporary**: the server is restarting or overloaded and answers **503 Service Unavailable**. Trying again a moment later often works. The practice API's `/flaky` endpoint fails twice, then succeeds, so you can practise:

<CodeExample output={`Got 503, retrying in 100 ms
Got 503, retrying in 200 ms
{ ok: true, attempt: 3 }
No retry for HTTP 404`}>

```js
const API = "https://api.pandadev.test";
const wait = (ms) => new Promise((resolve) => setTimeout(resolve, ms));

async function getWithRetry(path, retries = 3) {
  for (let attempt = 0; ; attempt++) {
    const response = await fetch(API + path);
    const data = await response.json();
    if (response.ok) return data;

    const canRetry = response.status >= 500 && attempt < retries;
    if (!canRetry) throw new Error(`HTTP ${response.status}`);

    const delay = 100 * 2 ** attempt; // 100, 200, 400...
    console.log(`Got ${response.status}, retrying in ${delay} ms`);
    await wait(delay);
  }
}

console.log(await getWithRetry("/flaky"));

try {
  await getWithRetry("/status/404");
} catch (error) {
  console.log("No retry for", error.message);
}
```

</CodeExample>

Doubling the wait each time is called **exponential backoff**. If a server is struggling, a thousand apps hammering it every 10 ms only make things worse; backing off gives it room to recover. Real apps also add a little randomness ("jitter") so all those apps don't retry at the very same moment, and they retry network errors (the `TypeError` from the last lesson) too.

<Callout type="danger" title="Only retry what is safe to repeat">

Retry **5xx** errors, timeouts and network failures, never **4xx**: a 404 or 400 will fail in exactly the same way next time. And be careful with `POST`: if the first request *did* reach the server but the answer got lost, retrying creates a **duplicate** order or payment. `GET`, `PUT` and `DELETE` are safe to repeat; `POST` needs extra care (APIs like Stripe accept an "idempotency key" for this).

</Callout>

const API = "https://api.pandadev.test";
const wait = (ms) => new Promise((resolve) => setTimeout(resolve, ms));

class ApiError extends Error {
  constructor(status, message) {
    super(message);
    this.name = "ApiError";
    this.status = status;
  }
}

async function request(
  path,
  { method = "GET", body, timeout = 1000 } = {},
) {
  const options = {
    method,
    headers: {},
    signal: AbortSignal.timeout(timeout),
  };
  if (body !== undefined) {
    options.headers["Content-Type"] = "application/json";
    options.body = JSON.stringify(body);
  }

  const response = await fetch(API + path, options);
  const data = await response.json().catch(() => null);
  if (!response.ok) {
    throw new ApiError(
      response.status,
      data?.error ?? `HTTP ${response.status}`,
    );
  }
  return data;
}

async function getWithRetry(path, retries = 2) {
  for (let attempt = 0; ; attempt++) {
    try {
      return await request(path);
    } catch (error) {
      const serverError = error.status >= 500;
      if (!serverError || attempt >= retries) throw error;
      await wait(100 * 2 ** attempt);
    }
  }
}

## Recap

- Send data with `fetch(url, { method, headers, body })`: `body: JSON.stringify(data)` plus the `Content-Type: application/json` header.
- `POST` creates (201 Created), `PATCH` changes some fields, `PUT` replaces, `DELETE` removes (often 204 No Content, with no body to read). Together they make a **REST** API for **CRUD**.
- One `request` helper sends JSON, reads the answer safely and throws an `ApiError` with the status and the API's own message.
- `signal: AbortSignal.timeout(ms)` gives up on slow requests (`TimeoutError`); an `AbortController` cancels them yourself (`AbortError`).
- Retry temporary failures (5xx, timeouts, network errors) with **exponential backoff**, never 4xx, and be careful retrying `POST`.
