So far your components have been **pure**: they take props and state and return JSX, nothing else. But apps also need to talk to the outside world: load data from an API, start a timer, change the page title. Those are **side effects**, and React has a dedicated place for them: the **`useEffect`** hook. In this lesson you'll use it to load real data from PandaDev's practice API, with proper loading and error states. 🌐

## Rendering must stay pure

React may call your component many times: on every state change, when a parent re-renders, and twice in development to catch bugs (more on that below). So the component body should only **calculate** JSX. If it fetched data directly, every render would fire another request, and the response would set state, which causes a render, which fires another request...

```jsx
function Recipes() {
  const [recipes, setRecipes] = useState([]);

  // ❌ Runs on EVERY render, and setRecipes causes another render
  fetch(`${API}/recipes`)
    .then((res) => res.json())
    .then(setRecipes);

  return <p>{recipes.length} recipes</p>;
}
```

That's an infinite loop of requests. Side effects need to run **after** rendering, and only when something relevant changed.

## Your first effect

`useEffect(fn)` tells React: *"after you've updated the screen, run `fn`"*. Run this and click the button:

<TryIt
  language="react"
  code={`import { useState, useEffect } from "react";
import { createRoot } from "react-dom/client";

function Clicker() {
  const [count, setCount] = useState(0);
  console.log("1. render, count =", count);

  useEffect(() => {
    console.log("2. effect, the screen shows", count);
    document.title = \`Clicked \${count} times\`;
  });

  return (
    <button onClick={() => setCount(count + 1)}>
      Clicked {count} times
    </button>
  );
}

createRoot(document.getElementById("root")).render(<Clicker />);`}
/>

The render always comes first, then the effect. Setting `document.title` (the text in the browser tab) is a typical effect: it changes something **outside** React.

## The dependency array

An effect without a second argument runs after **every** render. Usually that's too often. The second argument, the **dependency array**, lists the values the effect uses, and React re-runs the effect only when one of them has changed:

| You write | The effect runs |
| --- | --- |
| `useEffect(fn)` | after every render |
| `useEffect(fn, [])` | once, after the first render |
| `useEffect(fn, [name])` | after the first render, and whenever `name` changes |

Click both buttons and watch which effects run:

<TryIt
  language="react"
  code={`import { useState, useEffect } from "react";
import { createRoot } from "react-dom/client";

function Demo() {
  const [count, setCount] = useState(0);
  const [name, setName] = useState("Mei");

  useEffect(() => {
    console.log("every render");
  });

  useEffect(() => {
    console.log("only once, after the first render");
  }, []);

  useEffect(() => {
    console.log("name is now", name);
  }, [name]);

  return (
    <>
      <button onClick={() => setCount(count + 1)}>
        Count: {count}
      </button>{" "}
      <button onClick={() => setName(name === "Mei" ? "Bao" : "Mei")}>
        Name: {name}
      </button>
    </>
  );
}

createRoot(document.getElementById("root")).render(<Demo />);`}
/>

The rule is simple: **every value from the component that the effect reads goes in the array** (props, state, and anything calculated from them). If you leave one out, the effect keeps using an old value, and that's a hard bug to spot.

<Callout type="tip" title="Let the linter keep you honest">

In real projects the ESLint plugin `eslint-plugin-react-hooks` checks your dependency arrays and warns when one is missing. Vite's React template switches it on for you. Don't silence it: if it complains, the fix is almost always to add the dependency, or to move the code out of the effect.

</Callout>

## Fetching data

Loading data is the most common effect. A good data-loading component handles **three states**: still loading, failed, and loaded. PandaDev has a practice API built in, so these lessons work offline and always give the same answers. Real APIs work the same way.

<TryIt
  language="react"
  code={`import { useState, useEffect } from "react";
import { createRoot } from "react-dom/client";

const API = "https://api.pandadev.test";

function VeganRecipes() {
  const [recipes, setRecipes] = useState([]);
  const [loading, setLoading] = useState(true);
  const [error, setError] = useState(null);

  useEffect(() => {
    async function load() {
      try {
        const res = await fetch(\`\${API}/recipes?tag=vegan\`);
        if (!res.ok) throw new Error(\`HTTP \${res.status}\`);
        setRecipes(await res.json());
      } catch (err) {
        setError(err.message);
      } finally {
        setLoading(false);
      }
    }
    load();
  }, []);

  if (loading) return <p>Loading...</p>;
  if (error) return <p>😿 Something went wrong: {error}</p>;
  return (
    <ul>
      {recipes.map((r) => (
        <li key={r.id}>{r.name} ({r.minutes} min)</li>
      ))}
    </ul>
  );
}

createRoot(document.getElementById("root")).render(<VeganRecipes />);`}
/>

You'll see **Loading...** for a moment, then the list. To see the error state, change the URL to `${API}/status/500` and run it again.

Why the inner `load` function? Because the effect function itself **can't be `async`**. An async function always returns a promise, but React expects an effect to return either nothing or a **cleanup function**:

```jsx
// ❌ The effect returns a promise
useEffect(async () => {
  const res = await fetch(url);
}, []);

// ✅ Define an async function inside, then call it
useEffect(() => {
  async function load() {
    const res = await fetch(url);
  }
  load();
}, []);
```

## Cleanup: cancelling stale requests

An effect can **return a function**. React calls this **cleanup** function before running the effect again, and when the component disappears from the page. It's where you undo what the effect started: stop a timer, remove a listener, cancel a request.

Cancelling matters for searches. Type **pa** quickly: the request for `p` is sent, then the one for `pa`. If the `p` answer arrives **last**, the page would show results for the wrong search. With an **`AbortController`** in the cleanup, each new search cancels the previous request:

<TryIt
  language="react"
  code={`import { useState, useEffect } from "react";
import { createRoot } from "react-dom/client";

const API = "https://api.pandadev.test";

function RecipeSearch() {
  const [query, setQuery] = useState("");
  const [recipes, setRecipes] = useState([]);
  const [loading, setLoading] = useState(true);

  useEffect(() => {
    const controller = new AbortController();
    const params = new URLSearchParams({ search: query });

    fetch(\`\${API}/recipes?\${params}\`, { signal: controller.signal })
      .then((res) => res.json())
      .then((data) => {
        setRecipes(data);
        setLoading(false);
      })
      .catch((err) => {
        if (err.name === "AbortError") {
          console.log(\`Cancelled the search for "\${query}"\`);
        }
      });

    return () => controller.abort();
  }, [query]);

  function handleChange(event) {
    setQuery(event.target.value);
    setLoading(true);
  }

  return (
    <>
      <input
        value={query}
        onChange={handleChange}
        placeholder="Try: soup, rice, mushrooms"
      />
      {loading ? (
        <p>Searching...</p>
      ) : (
        <ul>
          {recipes.map((r) => <li key={r.id}>{r.name}</li>)}
        </ul>
      )}
    </>
  );
}

createRoot(document.getElementById("root")).render(<RecipeSearch />);`}
/>

Type quickly and you'll see cancelled searches in the output. The order of events for one keystroke is: render with the new `query`, **cleanup** of the previous effect (abort the old request), then the new effect (send the new request).

Notice that `setLoading(true)` happens in the **event handler**, not in the effect. The user typing is what starts a new search, so that's where it belongs.

If you can't cancel something (not every async API takes a `signal`), use an **ignore flag** instead. The response still arrives, but the old effect knows it's out of date:

```jsx
useEffect(() => {
  let ignore = false;
  fetch(url)
    .then((res) => res.json())
    .then((data) => {
      if (!ignore) setRecipes(data);
    });
  return () => {
    ignore = true;
  };
}, [url]);
```

<Callout type="note" title="Why does my effect run twice?">

Real projects wrap the app in `<StrictMode>` (Vite's template does). In **development only**, Strict Mode renders every component twice and runs every effect, its cleanup, and the effect again, straight after the first render. With the search above you'd see one cancelled request on start-up. That's on purpose: if your app breaks when an effect runs twice, your cleanup is missing. In production, effects run once.

</Callout>

## When you don't need an effect

Effects are for syncing with things **outside** React. Many beginner effects aren't needed at all, and they make the app slower and buggier. Three common cases:

**1. Values you can calculate.** Derive them while rendering, as you did in the last lesson:

```jsx
// ❌ An extra state and an extra render
const [visible, setVisible] = useState([]);
useEffect(() => {
  setVisible(recipes.filter((r) => r.tags.includes(tag)));
}, [recipes, tag]);

// ✅ Just calculate it
const visible = recipes.filter((r) => r.tags.includes(tag));
```

**2. Things caused by a user action.** Put them in the event handler. The effect version runs whenever `saved` changes for **any** reason, not just a click:

```jsx
// ❌ Sending a request because some state changed
useEffect(() => {
  if (saved) fetch(`${API}/todos`, { method: "POST", body });
}, [saved]);

// ✅ Send it when the user clicks
function handleSave() {
  fetch(`${API}/todos`, { method: "POST", body });
}
```

**3. Resetting state when a prop changes.** Give the component a **`key`** instead: a new key makes React start it fresh with new state.

```jsx
// ✅ A new recipeId means a brand-new RecipeNotes with empty state
<RecipeNotes key={recipeId} recipeId={recipeId} />
```

A good test: *"Is this code here because the component is **on the screen**?"* Loading the data it shows, connecting to a chat room, starting a clock: effect. *"Is it here because the user **did something**?"* Event handler.

In bigger projects, teams usually load data with a library such as **TanStack Query** or **SWR**, or with their framework's data loading (Next.js, React Router). They handle caching, retries and stale responses for you, but underneath they do what you just built by hand.

```jsx
import { useState, useEffect } from "react";
import { createRoot } from "react-dom/client";

const API = "https://api.pandadev.test";

function RecipeViewer() {
  const [id, setId] = useState(1);
  const [recipe, setRecipe] = useState(null);
  const [error, setError] = useState(null);
  const [loading, setLoading] = useState(true);

  function handleChange(event) {
    setId(Number(event.target.value));
    setLoading(true);
  }

  useEffect(() => {
    let ignore = false;

    async function load() {
      try {
        const res = await fetch(`${API}/recipes/${id}`);
        const data = await res.json();
        if (ignore) return;
        if (res.ok) {
          setRecipe(data);
          setError(null);
        } else {
          setRecipe(null);
          setError(data.error);
        }
      } catch (err) {
        if (!ignore) setError(err.message);
      } finally {
        if (!ignore) setLoading(false);
      }
    }

    load();
    return () => {
      ignore = true;
    };
  }, [id]);

  return (
    <div>
      <label>
        Recipe #{" "}
        <input
          type="number"
          name="id"
          min="1"
          value={id}
          onChange={handleChange}
        />
      </label>
      {loading ? (
        <p className="status">Loading...</p>
      ) : error ? (
        <p className="error">{error}</p>
      ) : (
        <article>
          <h2>{recipe.name}</h2>
          <p className="meta">
            {recipe.minutes} min · serves {recipe.servings}
          </p>
          <ul className="ingredients">
            {recipe.ingredients.map((item) => (
              <li key={item}>{item}</li>
            ))}
          </ul>
        </article>
      )}
    </div>
  );
}

createRoot(document.getElementById("root")).render(
  <RecipeViewer />
);
```

## Recap

- Rendering must stay **pure**. Side effects (fetching, timers, the page title, subscriptions) go in **`useEffect`**, which runs **after** React updates the screen.
- The **dependency array** decides when it runs: no array means after every render, `[]` means once, `[a, b]` means when `a` or `b` changes. List every value the effect reads.
- Load data with an `async` function **inside** the effect, and handle **loading**, **error** and **loaded** states. Check `res.ok`.
- Return a **cleanup** function to undo the effect: abort the request with an `AbortController`, or set an **ignore** flag so stale responses are dropped.
- Strict Mode runs effects twice in development to find missing cleanups.
- You **don't** need an effect for values you can calculate (derive them), for reactions to user actions (use the event handler), or to reset state (use a `key`).
