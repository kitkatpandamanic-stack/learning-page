The components from the last lesson always showed the same thing for the same props. Real interfaces change: a counter goes up, a box fills with text, an item gets ticked off. In React, data that changes over time and should update the screen is called **state**. In this lesson you'll give components state, respond to events, and learn the one rule that makes React apps predictable: **never change state in place, replace it**. 🔁

## Why a normal variable isn't enough

Let's try a like button with an ordinary variable. Press **Run** and click the button a few times:

<TryIt
  language="react"
  code={`import { createRoot } from "react-dom/client";

function LikeButton() {
  let likes = 0;

  function handleClick() {
    likes = likes + 1;
    console.log("likes is now", likes);
  }

  return <button onClick={handleClick}>🤍 {likes} likes</button>;
}

createRoot(document.getElementById("root")).render(<LikeButton />);`}
/>

The output says the number goes up, but the button stays at 0. Two problems:

1. Changing a local variable doesn't tell React anything, so it never **re-renders** (calls `LikeButton` again).
2. Even if it did, `let likes = 0` would run again and start from zero. A component function forgets its local variables after every render.

## useState: a component's memory

The **`useState`** hook solves both problems. It gives you the current value and a **setter function**. Calling the setter stores the new value **and** asks React to render the component again:

<TryIt
  language="react"
  code={`import { useState } from "react";
import { createRoot } from "react-dom/client";

function LikeButton() {
  const [likes, setLikes] = useState(0);
  console.log("rendering with likes =", likes);

  return (
    <button onClick={() => setLikes(likes + 1)}>
      💜 {likes} likes
    </button>
  );
}

createRoot(document.getElementById("root")).render(
  <>
    <LikeButton />{" "}
    <LikeButton />
  </>
);`}
/>

- `useState(0)` sets the **initial** value. It's only used on the first render.
- It returns an array of two things, which we destructure: `[likes, setLikes]`. The naming convention is `[thing, setThing]`.
- Each button has **its own** state: clicking one doesn't change the other.

Functions starting with `use` are called **hooks**. Two rules keep them working: call them only **inside components** (or your own hooks), and only at the **top level**, never inside `if`, loops or nested functions. React tells hooks apart by the order they're called in, so that order must be the same on every render.

### State is a snapshot

Here's something that surprises everyone. Click **+3 (wrong)**:

<TryIt
  language="react"
  code={`import { useState } from "react";
import { createRoot } from "react-dom/client";

function Counter() {
  const [count, setCount] = useState(0);
  console.log("render, count =", count);

  function addThreeWrong() {
    setCount(count + 1);
    setCount(count + 1);
    setCount(count + 1);
    console.log("still", count, "in this render");
  }

  function addThreeRight() {
    setCount((c) => c + 1);
    setCount((c) => c + 1);
    setCount((c) => c + 1);
  }

  return (
    <>
      <h2>{count}</h2>
      <button onClick={addThreeWrong}>+3 (wrong)</button>{" "}
      <button onClick={addThreeRight}>+3 (right)</button>
    </>
  );
}

createRoot(document.getElementById("root")).render(<Counter />);`}
/>

It only adds 1. Inside one render, `count` is a **fixed value** (a snapshot), so all three calls say `setCount(0 + 1)`. The setter doesn't change `count` straight away; it schedules a new render with the new value. React also **batches** the three calls into a single render.

When the new value depends on the old one, pass an **updater function** instead: `setCount((c) => c + 1)`. React calls it with the latest value, so three of them really add 3.

## Handling events

You've been using **`onClick`** already. React's event props work like `addEventListener`, but you pass the handler directly in JSX. All the usual events are there, camelCased: `onClick`, `onChange`, `onSubmit`, `onKeyDown`, `onMouseEnter`...

```jsx
function Toolbar({ onDelete }) {
  function handleSave(event) {
    console.log("Saving!", event.target);
  }

  return (
    <>
      <button onClick={handleSave}>Save</button>
      <button onClick={() => onDelete(42)}>Delete #42</button>
    </>
  );
}
```

- Pass the function, **don't call it**: `onClick={handleSave}`, not `onClick={handleSave()}`. With brackets, it runs during rendering, and if it sets state, you get an infinite loop of renders.
- To pass arguments, wrap the call in an arrow function: `onClick={() => onDelete(42)}`.
- The handler receives an **event object** with `target`, `key`, `preventDefault()` and friends, just like in the [events lesson](/learn/javascript/events).
- Passing a function **as a prop** (like `onDelete`) is how a child tells its parent that something happened. By convention, such props start with `on`.

## Updating arrays and objects

React decides whether to re-render by comparing the old and new state with `Object.is`. If you **mutate** an array (`push`, `splice`, `item.done = true`), it's still the **same array**, so React may think nothing changed and skip the update. The fix is to treat state as **read-only** and always make a **new** array or object:

<CodeExample output={`true [ 'flour', 'eggs', 'milk' ]
3 1 false
{ id: 2, name: 'eggs', got: true }
{ id: 2, name: 'eggs', got: false }
true`}>

```js
const list = ["flour", "eggs"];
const before = list;
list.push("milk");
console.log(Object.is(before, list), list);

const items = [
  { id: 1, name: "flour", got: false },
  { id: 2, name: "eggs", got: false },
];

const added = [...items, { id: 3, name: "milk", got: false }];
const removed = items.filter((item) => item.id !== 1);
const toggled = items.map((item) =>
  item.id === 2 ? { ...item, got: !item.got } : item
);

console.log(added.length, removed.length, Object.is(items, toggled));
console.log(toggled[1]);
console.log(items[1]);
console.log(toggled[0] === items[0]);
```

</CodeExample>

After `push`, `before` and `list` are still the same object (`true`), which is exactly why React can't see the change. The three non-mutating versions are the patterns you'll write again and again:

| To... | Write |
| --- | --- |
| add an item | `setItems([...items, newItem])` |
| remove an item | `setItems(items.filter((i) => i.id !== id))` |
| change one item | `setItems(items.map((i) => i.id === id ? { ...i, got: true } : i))` |
| change a field of an object | `setUser({ ...user, name: "Mei" })` |

The original `items[1]` is untouched, and unchanged items (`toggled[0]`) are reused as they are, so the copy is cheap.

<Callout type="danger" title="Don't mutate state">

`items.push(x); setItems(items)` is the most common React bug. Sometimes it seems to work, then the screen stops updating or shows old data. Methods that **change** an array (`push`, `pop`, `splice`, `sort`, `reverse`) need a copy first: `[...items].sort(...)`, or the newer non-mutating `items.toSorted(...)`.

</Callout>

## Controlled inputs and forms

To read what the user types, store the input's text in state and connect both directions: **`value`** shows the state, **`onChange`** updates it on every keystroke. This is called a **controlled input**, because React is always in control of what the box contains:

<TryIt
  language="react"
  code={`import { useState } from "react";
import { createRoot } from "react-dom/client";

let nextId = 3;

function Ingredients() {
  const [items, setItems] = useState([
    { id: 1, name: "flour" },
    { id: 2, name: "eggs" },
  ]);
  const [text, setText] = useState("");

  function handleSubmit(event) {
    event.preventDefault();
    const name = text.trim();
    if (!name) return;
    setItems([...items, { id: nextId++, name }]);
    setText("");
  }

  return (
    <form onSubmit={handleSubmit}>
      <input
        value={text}
        onChange={(event) => setText(event.target.value)}
        placeholder="Add an ingredient"
      />
      <button>Add</button>
      <p>You are typing: {text || "(nothing yet)"}</p>
      <ul>
        {items.map((item) => (
          <li key={item.id}>{item.name}</li>
        ))}
      </ul>
    </form>
  );
}

createRoot(document.getElementById("root")).render(<Ingredients />);`}
/>

Because the text lives in state, clearing the box is just `setText("")`, and the paragraph updates as you type. Forms work like in plain JavaScript: listen with **`onSubmit`** on the `<form>` (so both the button and the Enter key work) and call **`event.preventDefault()`** so the browser doesn't reload the page.

Notice `nextId` lives **outside** the component: it isn't shown on screen, it just needs to keep counting. In a real app the id usually comes from the server, or from `crypto.randomUUID()`.

## Lifting state up

What if two components need the same state? Say a search box filters a recipe list. The box knows the text, but the list needs it too. The answer is to **lift the state up** to their closest common parent, and pass it down as props, together with a function to change it:

<TryIt
  language="react"
  code={`import { useState } from "react";
import { createRoot } from "react-dom/client";

const RECIPES = [
  { id: 1, name: "Bamboo Shoot Stir-fry" },
  { id: 2, name: "Pancakes" },
  { id: 3, name: "Tomato Soup" },
  { id: 5, name: "Guacamole" },
];

function SearchBox({ value, onChange }) {
  return (
    <input
      value={value}
      onChange={(event) => onChange(event.target.value)}
      placeholder="Search recipes"
    />
  );
}

function RecipeList({ recipes }) {
  if (recipes.length === 0) return <p>No recipes found.</p>;
  return (
    <ul>
      {recipes.map((r) => <li key={r.id}>{r.name}</li>)}
    </ul>
  );
}

function App() {
  const [query, setQuery] = useState("");
  const matches = RECIPES.filter((r) =>
    r.name.toLowerCase().includes(query.toLowerCase())
  );

  return (
    <>
      <SearchBox value={query} onChange={setQuery} />
      <p>{matches.length} of {RECIPES.length} recipes</p>
      <RecipeList recipes={matches} />
    </>
  );
}

createRoot(document.getElementById("root")).render(<App />);`}
/>

Data flows **down** through props (`value`, `recipes`); events flow **up** through callback props (`onChange`). `SearchBox` and `RecipeList` hold no state at all, which makes them easy to reuse and test. In React this one-way data flow is the norm: each piece of state has **one owner**.

## Derive values, don't store them

Look again at `matches` above: it isn't state. It's **calculated** from `query` during every render. Beginners often store it in state too:

```jsx
// ❌ Two states that must be kept in sync by hand
const [query, setQuery] = useState("");
const [matches, setMatches] = useState(RECIPES);

function handleChange(text) {
  setQuery(text);
  setMatches(RECIPES.filter((r) => r.name.includes(text)));
}

// ✅ One state, everything else derived while rendering
const [query, setQuery] = useState("");
const matches = RECIPES.filter((r) => r.name.includes(query));
```

The first version works until someone adds a second way to change `query` and forgets `setMatches`. Then the screen shows a list that doesn't match the search box. Ask yourself: **can I calculate this from props or other state?** If yes, it isn't state. Counts, totals, filtered and sorted lists, "is this form valid?" are all derived values.

<Callout type="tip" title="Keep state minimal">

Good React state is the **smallest** set of data the app needs: what the user typed, which items exist, which one is selected. Everything you can compute from that, compute in the render. It's less code, and there's nothing to get out of sync.

</Callout>

import { useState } from "react";
import { createRoot } from "react-dom/client";

let nextId = 3;

function ShoppingList() {
  const [items, setItems] = useState([
    { id: 1, name: "bamboo", got: false },
    { id: 2, name: "rice", got: false },
  ]);
  const [text, setText] = useState("");

  function handleSubmit(event) {
    event.preventDefault();
    const name = text.trim();
    if (!name) return;
    setItems([...items, { id: nextId++, name, got: false }]);
    setText("");
  }

  function toggle(id) {
    setItems(
      items.map((item) =>
        item.id === id ? { ...item, got: !item.got } : item
      )
    );
  }

  function remove(id) {
    setItems(items.filter((item) => item.id !== id));
  }

  const left = items.filter((item) => !item.got).length;

  return (
    <div>
      <form onSubmit={handleSubmit}>
        <input
          name="item"
          placeholder="Add an item"
          value={text}
          onChange={(event) => setText(event.target.value)}
        />
        <button type="submit">Add</button>
      </form>
      <ul>
        {items.map((item) => (
          <li key={item.id} className={item.got ? "got" : ""}>
            <label>
              <input
                type="checkbox"
                checked={item.got}
                onChange={() => toggle(item.id)}
              />
              {item.name}
            </label>{" "}
            <button
              className="remove"
              onClick={() => remove(item.id)}
            >
              Remove
            </button>
          </li>
        ))}
      </ul>
      <p className="count">{left} of {items.length} left</p>
    </div>
  );
}

  <ShoppingList />
);

## Recap

- **State** is data that changes and should update the screen. `const [value, setValue] = useState(initial)` gives a component memory; calling the setter re-renders it.
- Call hooks only at the **top level** of a component. State is a **snapshot** per render; use an **updater** `setCount((c) => c + 1)` when the new value depends on the old.
- Event props like `onClick={handleClick}` take a function: pass it, don't call it. Use an arrow function to pass arguments; callback props (`onChange`, `onDelete`) let children talk to parents.
- Never mutate state: create new arrays and objects with **spread**, `filter` and `map`.
- **Controlled inputs** use `value` + `onChange`; forms use `onSubmit` with `event.preventDefault()`.
- **Lift state up** to the closest common parent when several components need it, and **derive** anything you can calculate instead of storing it.
