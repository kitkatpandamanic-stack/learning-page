Функции из прошлого урока тестировать было легко: на входе числа, на выходе число. Настоящий код запутаннее. Он **ждёт** ответа от серверов, отправляет письма, читает `localStorage`, бросает кубики и смотрит на часы. Вы не хотите, чтобы тесты отправляли настоящие письма, зависели от интернета или падали в полночь. В этом уроке вы научитесь тестировать асинхронный код и подменять «грязные» части **тестовыми двойниками (test doubles)**, которыми управляете сами. 🎭

## Тестирование асинхронного кода

Чтобы протестировать функцию, которая возвращает **промис (promise)**, сделайте тестовую функцию `async` и дождитесь результата через `await`. Vitest дожидается промиса теста и только потом решает, прошёл ли тест:

<CodeExample output={`✓ getScore > находит очки Mei
✓ getScore > возвращает число
✓ getScore > отклоняет неизвестных игроков

Tests  3 passed (3)`}>

```js
import { describe, it, expect } from "vitest";

// Ненастоящий сервер: отвечает через 100 миллисекунд
function getScore(player) {
  return new Promise((resolve, reject) => {
    setTimeout(() => {
      if (player === "Mei") {
        resolve(95);
      } else {
        reject(new Error(`Игрок ${player} не найден`));
      }
    }, 100);
  });
}

describe("getScore", () => {
  it("находит очки Mei", async () => {
    const score = await getScore("Mei");
    expect(score).toBe(95);
  });

  it("возвращает число", async () => {
    await expect(getScore("Mei")).resolves.toBeTypeOf("number");
  });

  it("отклоняет неизвестных игроков", async () => {
    await expect(getScore("Bob")).rejects.toThrow("не найден");
  });
});
```

</CodeExample>

- Первый тест написан в самом распространённом стиле: дождитесь значения через `await` и проверьте его как обычно.
- **`.resolves`** дожидается промиса и проверяет значение, с которым он выполнился.
- **`.rejects`** проверяет, что промис **отклонён**. Вместе с `toThrow` он проверяет ошибку — так же, как `toThrow` делал это для обычных функций.

<Callout type="danger" title="Всегда пишите await перед resolves и rejects">

`expect(promise).rejects.toThrow()` тоже возвращает промис. Забудьте `await` — и тестовая функция закончится **раньше**, чем выполнится проверка:

```js
it("отклоняет неизвестных игроков", () => {
  // ❌ Нет await: тест закончится раньше, чем эта проверка
  expect(getScore("Bob")).rejects.toThrow("не найден");
});
```

Свежие версии Vitest на это жалуются, но многие инструменты тестирования молча пропускают такой код, и тогда тест проходит при любом результате. Каждый раз пишите `await expect(...)` (и делайте тест `async`).

</Callout>

## Тестовые двойники и vi.fn

**Тестовый двойник** — это замена чего-то настоящего, как дублёр-каскадёр в кино. Самый полезный двойник — **мок-функция (mock function)**, которую создаёт **`vi.fn()`**. Она ничего не делает, но **запоминает каждый вызов**, так что тест может спросить, как её использовали:

<CodeExample output={`[ [ 'bao@pandadev.test', 'Заказ 2 задерживается, извините!' ] ]
✓ пишет только тем, чей заказ сильно задерживается

Tests  1 passed (1)`}>

```js
import { it, expect, vi } from "vitest";

function notifyLateOrders(orders, sendEmail) {
  for (const order of orders) {
    if (order.daysLate > 2) {
      sendEmail(
        order.email,
        `Заказ ${order.id} задерживается, извините!`,
      );
    }
  }
}

it("пишет только тем, чей заказ сильно задерживается", () => {
  const sendEmail = vi.fn();
  const orders = [
    { id: 1, email: "mei@pandadev.test", daysLate: 0 },
    { id: 2, email: "bao@pandadev.test", daysLate: 5 },
  ];

  notifyLateOrders(orders, sendEmail);

  console.log(sendEmail.mock.calls);
  expect(sendEmail).toHaveBeenCalledTimes(1);
  expect(sendEmail).toHaveBeenCalledWith(
    "bao@pandadev.test",
    "Заказ 2 задерживается, извините!",
  );
});
```

</CodeExample>

`notifyLateOrders` получает `sendEmail` как параметр, поэтому тест может передать вместо настоящей отправки писем мок. Ни одно письмо никуда не уходит, а тест проверяет, что именно **было бы** отправлено:

- `sendEmail.mock.calls` — массив с аргументами каждого вызова.
- **`toHaveBeenCalled()`** проверяет, что функцию вообще вызвали, **`toHaveBeenCalledTimes(n)`** — сколько раз, а **`toHaveBeenCalledWith(...)`** — с какими аргументами. Добавьте `.not`, чтобы проверить, что чего-то **не** произошло.
- Если проверка падает, сообщение выглядит так: `expected "vi.fn()" to be called 1 times, but got 2 times`.

Мок может ещё и **возвращать** то, что нужно тесту. Тогда это **заглушка (stub)**: фальшивый ответ от зависимости.

<CodeExample output={`0.85 0.85
6 1 3 3
{ name: 'Mei' }
42
[ [ 21 ] ] [ { type: 'return', value: 42 } ]`}>

```js
import { vi } from "vitest";

const getRate = vi.fn().mockReturnValue(0.85);
console.log(getRate("GBP"), getRate("EUR"));

const rollDie = vi.fn()
  .mockReturnValueOnce(6)
  .mockReturnValueOnce(1)
  .mockReturnValue(3);
console.log(rollDie(), rollDie(), rollDie(), rollDie());

const loadUser = vi.fn().mockResolvedValue({ name: "Mei" });
console.log(await loadUser(7));

const double = vi.fn((n) => n * 2);
console.log(double(21));
console.log(double.mock.calls, double.mock.results);
```

</CodeExample>

- `mockReturnValue(x)` возвращает `x` каждый раз; `mockReturnValueOnce(x)` — только при следующем вызове (такие значения выстраиваются в очередь).
- `mockResolvedValue(x)` возвращает промис, который выполняется со значением `x`, — идеально для подмены асинхронных функций. `mockRejectedValue(error)` возвращает отклонённый промис.
- `vi.fn(implementation)` выполняет вашу собственную функцию и при этом всё равно записывает вызовы и результаты.

## Внедрение зависимостей

Вот главная идея тестируемого кода. Функцию, которая сама тянется к `fetch`, `localStorage` или `Date.now()`, тестировать трудно: тест не может запретить ей пользоваться настоящими вещами. Функцию, которая **получает** их как параметры, тестировать легко: приложение передаёт настоящие, а тесты — двойников. Это называется **внедрением зависимостей (dependency injection)**.

В PandaDev встроен учебный API, поэтому эти уроки работают офлайн и всегда дают одни и те же ответы. Настоящие API работают точно так же. Ниже приложение пользуется настоящим `fetch`, а тесты внедряют поддельный:

<CodeExample output={`The Bamboo Heist (2019)
✓ getMovieTitle > запрашивает нужный фильм
✓ getMovieTitle > форматирует название и год
✓ getMovieTitle > выбрасывает ошибку, если фильма нет

Tests  3 passed (3)`}>

```js
import { describe, it, expect, vi } from "vitest";

const API = "https://api.pandadev.test";

async function getMovieTitle(id, fetchFn = fetch) {
  const res = await fetchFn(`${API}/movies/${id}`);
  if (!res.ok) {
    throw new Error(`Фильм ${id} не найден`);
  }
  const movie = await res.json();
  return `${movie.title} (${movie.year})`;
}

// Настоящее приложение пользуется настоящим fetch:
console.log(await getMovieTitle(1));

// Тесты передают поддельный:
function fakeResponse(status, body) {
  return {
    ok: status >= 200 && status < 300,
    status,
    json: async () => body,
  };
}

describe("getMovieTitle", () => {
  it("запрашивает нужный фильм", async () => {
    const fakeFetch = vi.fn().mockResolvedValue(
      fakeResponse(200, { title: "Test Film", year: 2001 }),
    );
    await getMovieTitle(42, fakeFetch);
    expect(fakeFetch).toHaveBeenCalledWith(`${API}/movies/42`);
  });

  it("форматирует название и год", async () => {
    const fakeFetch = vi.fn().mockResolvedValue(
      fakeResponse(200, { title: "Test Film", year: 2001 }),
    );
    const title = await getMovieTitle(42, fakeFetch);
    expect(title).toBe("Test Film (2001)");
  });

  it("выбрасывает ошибку, если фильма нет", async () => {
    const fakeFetch = vi.fn().mockResolvedValue(
      fakeResponse(404, { error: "Movie not found" }),
    );
    await expect(getMovieTitle(999, fakeFetch)).rejects.toThrow(
      "Фильм 999 не найден",
    );
  });
});
```

</CodeExample>

Обратите внимание на несколько вещей:

- **Параметр по умолчанию** `fetchFn = fetch` означает, что обычному коду ничего передавать не нужно. Передают только тесты.
- Поддельный ответ — это простой объект только с теми частями, которыми пользуется код: `ok`, `status` и `json()`. Двойнику достаточно выглядеть настоящим **с точки зрения кода**.
- Тесты быстрые, никогда не лезут в сеть и легко изображают ситуации, которые по-настоящему создать трудно, например 404 или ошибку сервера.

## Шпионим за существующими методами с vi.spyOn

Иногда зависимость не передаётся в функцию, а живёт на глобальном объекте, как `Math.random` или `console.warn`. **`vi.spyOn(object, "method")`** заменяет этот метод моком — **шпионом (spy)**, который по-прежнему вызывает оригинал, если не сказать ему иначе. После теста **`vi.restoreAllMocks()`** возвращает настоящие методы на место:

<CodeExample output={`✓ rollDie > превращает самое маленькое случайное число в 1
✓ rollDie > превращает самое большое случайное число в 6
✓ saveSettings > предупреждает, если тема не выбрана

Tests  3 passed (3)`}>

```js
import { describe, it, expect, vi, afterEach } from "vitest";

function rollDie() {
  return Math.floor(Math.random() * 6) + 1;
}

function saveSettings(settings) {
  if (!settings.theme) {
    console.warn("Тема не выбрана, используем light");
  }
  return { theme: "light", ...settings };
}

afterEach(() => {
  vi.restoreAllMocks(); // возвращаем настоящие методы
});

describe("rollDie", () => {
  it("превращает самое маленькое случайное число в 1", () => {
    vi.spyOn(Math, "random").mockReturnValue(0);
    expect(rollDie()).toBe(1);
  });

  it("превращает самое большое случайное число в 6", () => {
    vi.spyOn(Math, "random").mockReturnValue(0.9999);
    expect(rollDie()).toBe(6);
  });
});

describe("saveSettings", () => {
  it("предупреждает, если тема не выбрана", () => {
    const warn = vi.spyOn(console, "warn").mockImplementation(() => {});
    expect(saveSettings({}).theme).toBe("light");
    expect(warn).toHaveBeenCalledWith("Тема не выбрана, используем light");
  });
});
```

</CodeExample>

Случайные числа — враги тестов: тест должен каждый раз давать один и тот же результат. Шпион на `Math.random` делает его предсказуемым. `mockImplementation(() => {})` на `console.warn` проглатывает предупреждение, так что отчёт остаётся чистым, а тест всё равно проверяет, что предупреждение было выведено.

## Свежая подготовка в beforeEach

Если нескольким тестам нужна одинаковая подготовка, не копируйте её в каждый. **`beforeEach(fn)`** запускает `fn` перед **каждым** тестом в файле (или в блоке `describe`, где он написан), а **`afterEach(fn)`** — после каждого. (Есть ещё `beforeAll` и `afterAll`, которые запускаются один раз.)

Здесь поддельный `localStorage` создаётся заново для каждого теста, поэтому ни один тест не видит, что сохранил другой:

<CodeExample output={`✓ избранное > изначально пусто
✓ избранное > сохраняет новое избранное как JSON
✓ избранное > не сохраняет один фильм дважды

Tests  3 passed (3)`}>

```js
import { describe, it, expect, vi, beforeEach } from "vitest";

function createFavourites(storage) {
  const load = () => JSON.parse(storage.getItem("favs") ?? "[]");
  return {
    list: load,
    add(id) {
      const favs = load();
      if (!favs.includes(id)) {
        favs.push(id);
        storage.setItem("favs", JSON.stringify(favs));
      }
    },
  };
}

// Поддельный localStorage: Map с теми же методами
function fakeStorage() {
  const data = new Map();
  return {
    getItem: vi.fn((key) => data.get(key) ?? null),
    setItem: vi.fn((key, value) => data.set(key, String(value))),
  };
}

describe("избранное", () => {
  let storage;
  let favourites;

  beforeEach(() => {
    storage = fakeStorage(); // новое пустое хранилище для каждого теста
    favourites = createFavourites(storage);
  });

  it("изначально пусто", () => {
    expect(favourites.list()).toEqual([]);
  });

  it("сохраняет новое избранное как JSON", () => {
    favourites.add(3);
    expect(storage.setItem).toHaveBeenCalledWith("favs", "[3]");
    expect(favourites.list()).toEqual([3]);
  });

  it("не сохраняет один фильм дважды", () => {
    favourites.add(3);
    favourites.add(3);
    expect(storage.setItem).toHaveBeenCalledTimes(1);
  });
});
```

</CodeExample>

В браузере приложение вызывает `createFavourites(localStorage)`. Тесты вызывают её с подделкой, которая ведёт себя так же, а её методы — моки, поэтому тесты могут проверить, что было сохранено.

## Управляем временем с помощью фейковых таймеров

Поле поиска, которое ждёт 300 мс после последнего нажатия клавиши (поиск с **debounce**), трудно тестировать в реальном времени: пришлось бы ждать, а ожидание делает тесты медленными и ненадёжными. **Фейковые таймеры (fake timers)** заменяют `setTimeout` и его родственников часами, которые идут только тогда, когда это велит тест:

<CodeExample output={`✓ debounce > ждёт, пока пользователь перестанет печатать

Tests  1 passed (1)`}>

```js
import { describe, it, expect, vi, beforeEach, afterEach } from "vitest";

function debounce(fn, ms) {
  let timer;
  return (...args) => {
    clearTimeout(timer);
    timer = setTimeout(() => fn(...args), ms);
  };
}

describe("debounce", () => {
  beforeEach(() => {
    vi.useFakeTimers();
  });

  afterEach(() => {
    vi.useRealTimers();
  });

  it("ждёт, пока пользователь перестанет печатать", () => {
    const search = vi.fn();
    const searchSoon = debounce(search, 300);

    searchSoon("p");
    searchSoon("pa");
    searchSoon("pan");
    vi.advanceTimersByTime(299);
    expect(search).not.toHaveBeenCalled();

    vi.advanceTimersByTime(1);
    expect(search).toHaveBeenCalledTimes(1);
    expect(search).toHaveBeenCalledWith("pan");
  });
});
```

</CodeExample>

- **`vi.useFakeTimers()`** включает фейковые часы; **`vi.useRealTimers()`** возвращает настоящие (делайте это в `afterEach`, чтобы не задеть другие тесты).
- **`vi.advanceTimersByTime(ms)`** переводит часы вперёд и запускает все таймеры, которым пора сработать. `vi.runAllTimers()` запускает сразу все ожидающие таймеры.
- Проверка на 299 мс **и** на 300 мс тестирует границу — точно как граничные случаи из прошлого урока.

Фейковые таймеры управляют и самими часами. **`vi.setSystemTime(date)`** задаёт, что вернёт `Date.now()`, — так тестируют всё, что зависит от «сейчас»:

<CodeExample output={`✓ хранит сессию 24 часа

Tests  1 passed (1)`}>

```js
import { it, expect, vi, afterEach } from "vitest";

const HOUR = 60 * 60 * 1000;

function isExpired(session) {
  return Date.now() - session.createdAt > 24 * HOUR;
}

afterEach(() => {
  vi.useRealTimers();
});

it("хранит сессию 24 часа", () => {
  vi.useFakeTimers();
  vi.setSystemTime(new Date("2026-03-01T12:00:00Z"));
  const session = { createdAt: Date.now() };

  vi.advanceTimersByTime(24 * HOUR);
  expect(isExpired(session)).toBe(false);

  vi.advanceTimersByTime(1);
  expect(isExpired(session)).toBe(true);
});
```

</CodeExample>

Целые сутки проходят за миллисекунду реального времени. 🕰️

<Callout type="note" title="А как же vi.mock?">

В настоящих проектах вы встретите и **`vi.mock`**: он заменяет для тестового файла целый **модуль (module)**, так что мок получает даже код, который импортирует `fetchMovie` напрямую:

```js
// movies.test.js
import { it, expect, vi } from "vitest";
import { fetchMovie } from "./api.js";
import { getMovieTitle } from "./movies.js";

vi.mock("./api.js", () => ({ fetchMovie: vi.fn() }));

it("форматирует название", async () => {
  fetchMovie.mockResolvedValue({ title: "Test Film", year: 2001 });
  expect(await getMovieTitle(42)).toBe("Test Film (2001)");
});
```

Это мощный инструмент, но немного магический (Vitest переносит `vi.mock` в начало файла ещё до всех импортов). Подмене модулей нужны настоящие файлы, поэтому в этом редакторе она не работает. Внедрение зависимостей работает везде, честно показывает, от чего зависит код, и именно его мы используем в этих уроках.

</Callout>

Когда кто-то регистрируется, `sendWelcome` находит пользователя и отправляет ему письмо. Обе зависимости **внедряются**, поэтому ваши тесты могут передать моки, созданные через `vi.fn()`. Напишите не меньше **3** тестов (саму `sendWelcome` не меняйте). Проверки подсунут в `sendWelcome` ошибки, поэтому ваши тесты должны проверять:

- что `fetchUser` вызывается с тем **id**, который передали (возьмите число, например `42`);
- что `sendEmail` вызывается один раз с **адресом** пользователя и точным сообщением `"Добро пожаловать, Mei!"` (для пользователя по имени Mei), а `sendWelcome` выполняется с адресом почты;
- что для пользователя **без** адреса `sendWelcome` отклоняется с ошибкой, в которой есть `"нет адреса"`, и что **ни одного** письма не отправлено.

<Hint>

Сделайте `fetchUser` заглушкой, которая возвращает пользователя: `const fetchUser = vi.fn().mockResolvedValue({ name: "Mei", email: "mei@pandadev.test" });` и `const sendEmail = vi.fn();`. Затем `await sendWelcome(42, { fetchUser, sendEmail });` и проверка через `toHaveBeenCalledWith`. Для ошибки: `await expect(sendWelcome(7, { fetchUser, sendEmail })).rejects.toThrow("нет адреса")`, а затем `expect(sendEmail).not.toHaveBeenCalled()`.

```js
import { describe, it, expect, vi } from "vitest";

// ---- Тестируемый код (не меняйте его) ----
async function sendWelcome(userId, { fetchUser, sendEmail }) {
  const user = await fetchUser(userId);
  if (!user.email) {
    throw new Error("У пользователя нет адреса почты");
  }
  await sendEmail(user.email, "Добро пожаловать, " + user.name + "!");
  return user.email;
}

// ---- Ваши тесты ----
describe("sendWelcome", () => {
  it("находит нужного пользователя", async () => {
    const fetchUser = vi.fn().mockResolvedValue({
      name: "Mei",
      email: "mei@pandadev.test",
    });
    const sendEmail = vi.fn();
    await sendWelcome(42, { fetchUser, sendEmail });
    expect(fetchUser).toHaveBeenCalledWith(42);
  });

  it("отправляет пользователю приветствие", async () => {
    const fetchUser = vi.fn().mockResolvedValue({
      name: "Mei",
      email: "mei@pandadev.test",
    });
    const sendEmail = vi.fn();
    const sentTo = await sendWelcome(42, { fetchUser, sendEmail });
    expect(sendEmail).toHaveBeenCalledTimes(1);
    expect(sendEmail).toHaveBeenCalledWith(
      "mei@pandadev.test",
      "Добро пожаловать, Mei!",
    );
    expect(sentTo).toBe("mei@pandadev.test");
  });

  it("отклоняет пользователей без адреса и ничего не шлёт", async () => {
    const fetchUser = vi.fn().mockResolvedValue({ name: "Bao" });
    const sendEmail = vi.fn();
    await expect(
      sendWelcome(7, { fetchUser, sendEmail }),
    ).rejects.toThrow("нет адреса");
    expect(sendEmail).not.toHaveBeenCalled();
  });
});
```

## Итоги

- Асинхронный код тестируйте `async`-тестами и `await`. `await expect(promise).resolves...` проверяет значение, `await expect(promise).rejects.toThrow(...)` — ошибку. Никогда не забывайте `await`.
- **`vi.fn()`** создаёт мок-функцию, которая записывает свои вызовы. Проверяйте их через `toHaveBeenCalled`, `toHaveBeenCalledTimes` и `toHaveBeenCalledWith`; задавайте возвращаемые значения через `mockReturnValue` / `mockResolvedValue`.
- **Внедрение зависимостей**: передавайте `fetch`, хранилище, отправителей писем и часы **внутрь** функции — тогда приложение пользуется настоящими, а тесты двойниками.
- **`vi.spyOn(object, "method")`** подменяет метод вроде `Math.random` или `console.warn`; `vi.restoreAllMocks()` возвращает его на место.
- **`beforeEach`/`afterEach`** дают каждому тесту свежую подготовку.
- **Фейковые таймеры** (`vi.useFakeTimers`, `vi.advanceTimersByTime`, `vi.setSystemTime`) позволяют тестировать тайм-ауты, debounce и даты без ожидания.
- В настоящих проектах `vi.mock` подменяет целые модули; внедрение зависимостей работает везде.
