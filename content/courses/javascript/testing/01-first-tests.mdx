Until now you've checked your code by running it and reading what it prints. That's fine for ten lines. In a real project, every change you make could quietly break something you checked last week, and nobody re-checks everything by hand. **Automated tests** are small pieces of code that check your code for you, in a second, every time you change something. In modern JavaScript projects, the tool most teams reach for is **Vitest**. 🧪

## Why automate your checks?

Here's how you've been checking code so far:

<CodeExample output={`180
50
34`}>

```js
function applyDiscount(price, percent) {
  return price - (price * percent) / 100;
}

console.log(applyDiscount(200, 10)); // should be 180
console.log(applyDiscount(50, 0)); // should be 50
console.log(applyDiscount(40, 15)); // should be 34
```

</CodeExample>

It works, but **you** are the test: you have to remember what each number should be and compare them with your eyes. Turn those comments into code that compares for you, and you get:

- **Regressions caught early.** A **regression** is a bug in something that used to work. Tests notice it the moment it appears, not when a customer does.
- **Changes without fear.** Rename, tidy up, speed things up: if the tests still pass, you didn't break anything.
- **Living documentation.** A test called `"charges 18-year-olds the adult price"` tells the next developer exactly what the code is meant to do.

## describe, it and expect

A Vitest test file uses three functions, which you import from `"vitest"`:

- **`it(name, fn)`** defines one test. The name describes the behaviour; the function checks it. (`test` is another name for exactly the same function.)
- **`expect(value)`** wraps the value you got, and a **matcher** like `.toBe(180)` compares it with the value you expected. If they don't match, the test fails.
- **`describe(name, fn)`** groups related tests, usually all the tests for one function.

<CodeExample output={`The code ran. Now Vitest runs the tests:
✓ applyDiscount > takes 10% off
✓ applyDiscount > changes nothing at 0%
✓ applyDiscount > halves the price at 50%

Tests  3 passed (3)`}>

```js
import { describe, it, expect } from "vitest";

function applyDiscount(price, percent) {
  return price - (price * percent) / 100;
}

describe("applyDiscount", () => {
  it("takes 10% off", () => {
    expect(applyDiscount(200, 10)).toBe(180);
  });

  it("changes nothing at 0%", () => {
    expect(applyDiscount(50, 0)).toBe(50);
  });

  it("halves the price at 50%", () => {
    expect(applyDiscount(30, 50)).toBe(15);
  });
});

console.log("The code ran. Now Vitest runs the tests:");
```

</CodeExample>

Notice the order. `describe` and `it` don't run the tests straight away: they **collect** them. Vitest runs them after the rest of the code has finished, then prints a report. Each `✓` is a passing test, shown as `group > test name`, and the last line counts them up. Read the names out loud: "applyDiscount takes 10% off". Good test names make a sentence.

## Running Vitest in a real project

On this page the code and its tests share one editor. In a real project, the tests live in their own file next to the code, with `.test.js` in the name. Vitest finds those files automatically:

```text
shop/
├── package.json
├── pricing.js        # export function applyDiscount(...)
└── pricing.test.js   # import { applyDiscount } from "./pricing.js";
```

You install Vitest once as a **dev dependency** (it's only needed while developing, as you saw in the npm lesson) and add a `test` script to `package.json`:

```bash
npm install --save-dev vitest
```

```json title="package.json"
{
  "type": "module",
  "scripts": {
    "test": "vitest"
  }
}
```

Now `npm test` (or `npx vitest`) starts Vitest in **watch mode**: it runs your tests, then waits and re-runs them every time you save a file. `npx vitest run` runs them once and exits, which is what build servers use. The report looks something like this:

```text
 ✓ pricing.test.js (3 tests) 2ms

 Test Files  1 passed (1)
      Tests  3 passed (3)
   Duration  210ms
```

## Reading a failure report

Passing tests are quiet. The interesting part is what Vitest tells you when one **fails**. Here's a word counter with a bug in it:

<CodeExample output={`✓ countWords > counts a simple sentence
× countWords > ignores extra spaces
  → expected 3 to be 2 // Object.is equality
× countWords > returns 0 for an empty string
  → expected 1 to be 0 // Object.is equality

Tests  2 failed | 1 passed (3)`}>

```js
import { describe, it, expect } from "vitest";

function countWords(text) {
  return text.split(" ").length;
}

describe("countWords", () => {
  it("counts a simple sentence", () => {
    expect(countWords("pandas eat bamboo")).toBe(3);
  });

  it("ignores extra spaces", () => {
    expect(countWords("pandas  eat")).toBe(2);
  });

  it("returns 0 for an empty string", () => {
    expect(countWords("")).toBe(0);
  });
});
```

</CodeExample>

- `×` marks a failed test, and the `→` line under it says why: the code returned `3`, but the test expected `2`. The first value is always **what you got**, the second **what you expected**.
- `// Object.is equality` tells you which comparison `toBe` used (more on that in a moment).
- The summary counts failures first, so you can't miss them.

Now the bugs are easy to see: `"pandas  eat".split(" ")` gives `['pandas', '', 'eat']`, and `"".split(" ")` gives `['']`. Throwing away the empty strings fixes both:

<CodeExample output={`✓ countWords > counts a simple sentence
✓ countWords > ignores extra spaces
✓ countWords > returns 0 for an empty string

Tests  3 passed (3)`}>

```js
import { describe, it, expect } from "vitest";

function countWords(text) {
  return text.split(" ").filter((word) => word !== "").length;
}

describe("countWords", () => {
  it("counts a simple sentence", () => {
    expect(countWords("pandas eat bamboo")).toBe(3);
  });

  it("ignores extra spaces", () => {
    expect(countWords("pandas  eat")).toBe(2);
  });

  it("returns 0 for an empty string", () => {
    expect(countWords("")).toBe(0);
  });
});
```

</CodeExample>

<Callout type="tip" title="Watch every test fail once">

A test that can never fail is worse than no test, because it makes you feel safe. When you write a test, break the code on purpose for a moment (or write the test before the code, as you'll do in the TDD lesson) and check that the test goes red. Then undo the break and watch it go green.

</Callout>

## toBe or toEqual?

The matcher you'll use most is `toBe`. It compares with **`Object.is`**, which is almost the same as `===`. That's perfect for numbers, strings and booleans. But remember: two objects are only `===` if they are the **same** object, not just objects that look alike:

<CodeExample output={`✓ toBe works for numbers and strings
× toBe compares objects by identity
  → expected { name: 'Mei', food: [ 'bamboo' ] } to be { name: 'Mei', food: [ 'bamboo' ] } // If it should pass with deep equality, replace "toBe" with "toStrictEqual"
✓ toEqual compares what is inside

Tests  1 failed | 2 passed (3)`}>

```js
import { it, expect } from "vitest";

function makePanda(name) {
  return { name, food: ["bamboo"] };
}

it("toBe works for numbers and strings", () => {
  expect(2 + 2).toBe(4);
  expect(makePanda("Mei").name).toBe("Mei");
});

it("toBe compares objects by identity", () => {
  expect(makePanda("Mei")).toBe({ name: "Mei", food: ["bamboo"] });
});

it("toEqual compares what is inside", () => {
  expect(makePanda("Mei")).toEqual({ name: "Mei", food: ["bamboo"] });
});
```

</CodeExample>

The rule of thumb:

- **`toBe`** for **primitive** values: numbers, strings, booleans, `null`, `undefined`.
- **`toEqual`** for **objects and arrays**: it walks through them and compares every property and item ("deep equality").
- **`toStrictEqual`** is a stricter `toEqual`: it also notices properties that are `undefined` and objects made by different classes. Many teams use it as their default for objects.

## Common matchers

You don't have to squeeze every check into `toBe`. Vitest has a matcher for most situations, and the right one gives you a clearer failure message. Here are the ones you'll use every day:

<CodeExample output={`✓ common matchers > checks truthiness and missing values
✓ common matchers > checks numbers
✓ common matchers > checks strings, arrays and objects
✓ common matchers > can say what should NOT happen

Tests  4 passed (4)`}>

```js
import { describe, it, expect } from "vitest";

const user = {
  name: "Mei",
  email: "mei@pandadev.test",
  roles: ["student", "admin"],
  address: { city: "Chengdu" },
  nickname: null,
};

describe("common matchers", () => {
  it("checks truthiness and missing values", () => {
    expect(user.roles.length).toBeTruthy();
    expect(user.nickname).toBeNull();
    expect(user.age).toBeUndefined();
    expect(user.name).toBeDefined();
  });

  it("checks numbers", () => {
    expect(user.roles.length).toBeGreaterThan(1);
    expect(user.roles.length).toBeLessThanOrEqual(2);
    expect(0.1 + 0.2).toBeCloseTo(0.3);
  });

  it("checks strings, arrays and objects", () => {
    expect(user.email).toMatch(/@pandadev\.test$/);
    expect(user.email).toContain("mei");
    expect(user.roles).toContain("admin");
    expect(user.roles).toHaveLength(2);
    expect(user).toHaveProperty("address.city", "Chengdu");
  });

  it("can say what should NOT happen", () => {
    expect(user.roles).not.toContain("banned");
    expect(user.name).not.toBe("");
  });
});
```

</CodeExample>

- `toBeTruthy` / `toBeFalsy`, `toBeNull`, `toBeUndefined`, `toBeDefined` check for "empty" values.
- `toBeGreaterThan`, `toBeLessThan` (and their `OrEqual` versions) compare numbers. Use **`toBeCloseTo`** for decimals: `0.1 + 0.2` is really `0.30000000000000004`, so `toBe(0.3)` would fail.
- `toMatch` tests a string against a regular expression (or a piece of text). `toContain` checks that a string contains some text, or an array contains an item.
- `toHaveLength` checks `.length`, and `toHaveProperty` checks that a property exists (with a dotted path for nested objects) and, optionally, its value.
- Put **`.not`** in front of any matcher to flip it.

## Testing errors with toThrow

Sometimes the correct behaviour **is** an error. If `parseAge` gets `"twelve"`, it should throw. To test that, pass `expect` a **function** that makes the call, and use `toThrow`:

<CodeExample output={`✓ parseAge > returns the age as a number
✓ parseAge > rejects text
✓ parseAge > says what was wrong
✓ parseAge > uses the right error type
× parseAge > forgets the arrow function (wrong!)
  → TypeError: "abc" is not a whole number

Tests  1 failed | 4 passed (5)`}>

```js
import { describe, it, expect } from "vitest";

function parseAge(text) {
  const age = Number(text);
  if (!Number.isInteger(age)) {
    throw new TypeError(`"${text}" is not a whole number`);
  }
  if (age < 0 || age > 130) {
    throw new RangeError(`${age} is not between 0 and 130`);
  }
  return age;
}

describe("parseAge", () => {
  it("returns the age as a number", () => {
    expect(parseAge("12")).toBe(12);
  });

  it("rejects text", () => {
    expect(() => parseAge("twelve")).toThrow();
  });

  it("says what was wrong", () => {
    expect(() => parseAge("2.5")).toThrow("not a whole number");
    expect(() => parseAge("150")).toThrow(/between 0 and 130/);
  });

  it("uses the right error type", () => {
    expect(() => parseAge("-1")).toThrow(RangeError);
  });

  it("forgets the arrow function (wrong!)", () => {
    expect(parseAge("abc")).toThrow();
  });
});
```

</CodeExample>

- `toThrow()` passes if the function throws anything at all.
- `toThrow("text")` also checks that the error **message contains** that text; `toThrow(/regex/)` matches the message against a regular expression.
- `toThrow(RangeError)` checks the **type** of error.

Look at the last test. Without the `() =>`, `parseAge("abc")` runs **before** `expect` is even called, so the error escapes and crashes the test. `toThrow` needs a function it can call itself, inside its own `try/catch`.

## Arrange, act, assert

Good tests are short and follow the same three steps, often called **arrange, act, assert**:

1. **Arrange**: set up the objects and data you need.
2. **Act**: do the one thing you're testing.
3. **Assert**: check the result with `expect`.

<CodeExample output={`✓ Cart > adds up price times quantity
✓ Cart > starts empty
✓ Cart > refuses a quantity of 0

Tests  3 passed (3)`}>

```js
import { describe, it, expect } from "vitest";

class Cart {
  #items = [];

  add(name, price, quantity = 1) {
    if (quantity < 1) {
      throw new RangeError("quantity must be at least 1");
    }
    this.#items.push({ name, price, quantity });
  }

  get total() {
    return this.#items.reduce(
      (sum, item) => sum + item.price * item.quantity,
      0,
    );
  }
}

describe("Cart", () => {
  it("adds up price times quantity", () => {
    // Arrange
    const cart = new Cart();
    cart.add("tea", 4, 2);
    cart.add("dumplings", 6);
    // Act
    const total = cart.total;
    // Assert
    expect(total).toBe(14);
  });

  it("starts empty", () => {
    expect(new Cart().total).toBe(0);
  });

  it("refuses a quantity of 0", () => {
    const cart = new Cart();
    expect(() => cart.add("tea", 4, 0)).toThrow(RangeError);
    expect(cart.total).toBe(0);
  });
});
```

</CodeExample>

Each test creates its **own** `Cart`, so no test depends on what another one did. If tests share an object, one test's leftovers can make another fail (or pass!) for the wrong reason. Also notice that the tests only use what the class offers to the outside world (`add` and `total`), never the private `#items`. That way you can rewrite the inside of `Cart` and the tests still tell you whether it works.

## Which cases should you test?

You can't test every possible input, so choose wisely. A good set of tests covers:

- **The normal case** (the "happy path"): typical input, typical result.
- **Edge cases**: empty strings and arrays, `0`, one item, negative numbers, odd text like extra spaces or capitals.
- **Boundaries**: if the rules change at 18, test 17 **and** 18. Off-by-one mistakes (`>` instead of `>=`) hide exactly there.
- **Errors**: bad input should fail the way you promised.

Here a cinema charges children (5 to 17) £6, adults £10 and seniors (65 and over) £7. Testing the boundaries finds a bug the happy path would miss:

<CodeExample output={`✓ ticketPrice > lets toddlers in free
✓ ticketPrice > charges 5-year-olds the child price
✓ ticketPrice > still treats 17 as a child
✓ ticketPrice > charges 18-year-olds the adult price
× ticketPrice > gives 65-year-olds the senior price
  → expected 10 to be 7 // Object.is equality

Tests  1 failed | 4 passed (5)`}>

```js
import { describe, it, expect } from "vitest";

// Children (5 to 17) pay £6, adults £10,
// seniors (65 and over) £7. Under 5s are free.
function ticketPrice(age) {
  if (age < 5) return 0;
  if (age < 18) return 6;
  if (age > 65) return 7;
  return 10;
}

describe("ticketPrice", () => {
  it("lets toddlers in free", () => {
    expect(ticketPrice(4)).toBe(0);
  });
  it("charges 5-year-olds the child price", () => {
    expect(ticketPrice(5)).toBe(6);
  });
  it("still treats 17 as a child", () => {
    expect(ticketPrice(17)).toBe(6);
  });
  it("charges 18-year-olds the adult price", () => {
    expect(ticketPrice(18)).toBe(10);
  });
  it("gives 65-year-olds the senior price", () => {
    expect(ticketPrice(65)).toBe(7);
  });
});
```

</CodeExample>

The code says `age > 65`, so a 65-year-old pays the adult price. A test with age `70` would have passed and hidden the bug. Changing it to `age >= 65` makes all five tests pass.

<Callout type="warning" title="Keep tests simple">

Tests should be so simple that they obviously have no bugs. Write the expected value out (`toBe(7)`) instead of calculating it with the same logic as the code. Otherwise a mistake in that logic gets copied into the test, and both agree on the wrong answer.

</Callout>

This time the code is already written and correct. Your job is to write the **tests**. Good tests fail when the code is wrong, so the checks will sneak four different bugs into `passwordStrength` and make sure your tests catch every one. (Don't change the function itself.)

The rules: fewer than **8** characters is `"weak"`. Otherwise, a password with a number **and** a capital letter is `"strong"`, and anything else is `"medium"`. Anything that isn't a string throws a `TypeError`.

Write at least **4** tests inside the `describe` that check:

- a short password is `"weak"`,
- the **boundary**: a password of exactly 8 characters is no longer weak,
- `"strong"` needs **both** a number and a capital (test a password with only one of them, too),
- passing something that isn't a string (like the number `12345678`) throws a `TypeError`.

Run your code: every test should pass on the correct function.

<Hint>

Each test looks like `it("calls 7 characters weak", () => { expect(passwordStrength("Bamboo1")).toBe("weak"); });`. `"bamboo12"` is exactly 8 characters. For the error, remember the arrow function: `expect(() => passwordStrength(12345678)).toThrow(TypeError)`.

</Hint>

```js
import { describe, it, expect } from "vitest";

// ---- The code under test (don't change it) ----
function passwordStrength(password) {
  if (typeof password !== "string") {
    throw new TypeError("password must be a string");
  }
  if (password.length < 8) {
    return "weak";
  }
  const hasNumber = /[0-9]/.test(password);
  const hasCapital = /[A-Z]/.test(password);
  if (hasNumber && hasCapital) {
    return "strong";
  }
  return "medium";
}

// ---- Your tests ----
describe("passwordStrength", () => {
  it("calls 7 characters weak", () => {
    expect(passwordStrength("Bamboo1")).toBe("weak");
  });

  it("calls exactly 8 characters long enough", () => {
    expect(passwordStrength("bamboo12")).toBe("medium");
  });

  it("needs a number AND a capital to be strong", () => {
    expect(passwordStrength("Bamboo12")).toBe("strong");
    expect(passwordStrength("Bambooooo")).toBe("medium");
    expect(passwordStrength("bamboo123")).toBe("medium");
  });

  it("throws a TypeError for anything but a string", () => {
    expect(() => passwordStrength(12345678)).toThrow(TypeError);
  });
});
```

</Solution>

## Recap

- **Automated tests** check your code for you; they catch **regressions** and let you change code with confidence.
- `describe` groups tests, `it` (or `test`) defines one, and `expect(value).toBe(expected)` makes a check. Tests run after the code, and the report shows `✓`/`×` per test.
- In a real project: `npm install --save-dev vitest`, put tests in `*.test.js` files and run `npx vitest` (watch mode) or `npx vitest run` (once).
- In a failure, `expected X to be Y` means you **got** X but **expected** Y.
- Use `toBe` for primitives and `toEqual` (or `toStrictEqual`) for objects and arrays. Learn the common matchers and `.not`.
- Test errors with `expect(() => fn()).toThrow(...)`: the arrow function matters.
- Structure tests as **arrange, act, assert**, one behaviour per test, and test the normal case, edge cases, **boundaries** and errors.
