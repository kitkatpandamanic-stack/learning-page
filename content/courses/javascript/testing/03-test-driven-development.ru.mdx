До сих пор вы сначала писали код, а потом тесты. **Разработка через тестирование (test-driven development, TDD)** меняет порядок: сначала вы пишете **падающий** тест, а потом ровно столько кода, чтобы он прошёл. Звучит задом наперёд, но так вы решаете, *что* должен делать код, прежде чем утонуть в том, *как*, и каждая написанная строка оказывается протестированной. В этом уроке вы соберёте небольшую функцию по TDD, протестируете API-клиент без сети и разберётесь, что вообще стоит тестировать. 🚦

## Red, green, refactor

TDD — это короткий цикл, который повторяется снова и снова:

1. 🔴 **Red** (красный): напишите один маленький тест на поведение, которого ещё нет. Запустите его и убедитесь, что он **падает**.
2. 🟢 **Green** (зелёный): напишите **самый простой** код, который проходит тест. Ничего лишнего.
3. 🔵 **Refactor** (рефакторинг): пока тесты зелёные, приведите код в порядок (имена получше, меньше повторов). Запустите тесты снова и убедитесь, что они всё ещё зелёные.

Соберём `formatRuntime(minutes)` для приложения о фильмах: `45` должно показываться как `"45m"`, а `136` — как `"2h 16m"`. Первый шаг — тест, пока функция ещё пустая:

<CodeExample output={`× formatRuntime > показывает короткие фильмы в минутах
  → expected undefined to be '45m' // Object.is equality

Tests  1 failed (1)`}>

```js
import { describe, it, expect } from "vitest";

function formatRuntime(minutes) {
  // Ещё не написана!
}

describe("formatRuntime", () => {
  it("показывает короткие фильмы в минутах", () => {
    expect(formatRuntime(45)).toBe("45m");
  });
});
```

</CodeExample>

Красный, как и ожидалось. Это не потеря времени: раз тест упал, значит, он **может** падать и действительно что-то проверяет.

Теперь самый простой код, который проходит тест, — это `` return `${minutes}m`; ``. Похоже на жульничество, но в этом и смысл: код делает только то, о чём просят тесты. Чтобы он делал больше, нужен ещё один тест, поэтому следующий цикл снова начинается с красного:

<CodeExample output={`✓ formatRuntime > показывает короткие фильмы в минутах
× formatRuntime > делит длинные фильмы на часы и минуты
  → expected '136m' to be '2h 16m' // Object.is equality

Tests  1 failed | 1 passed (2)`}>

```js
import { describe, it, expect } from "vitest";

function formatRuntime(minutes) {
  return `${minutes}m`;
}

describe("formatRuntime", () => {
  it("показывает короткие фильмы в минутах", () => {
    expect(formatRuntime(45)).toBe("45m");
  });

  it("делит длинные фильмы на часы и минуты", () => {
    expect(formatRuntime(136)).toBe("2h 16m");
  });
});
```

</CodeExample>

Чтобы стало зелёным, функция делит минуты на часы и остаток. Третий цикл добавляет граничный случай: `120` должно превращаться в `"2h"`, а не в `"2h 0m"`. Красный, затем ещё один `if` — и снова зелёный. Наконец, шаг рефакторинга: тесты страхуют нас, пока мы делаем код читаемым:

<CodeExample output={`✓ formatRuntime > показывает короткие фильмы в минутах
✓ formatRuntime > делит длинные фильмы на часы и минуты
✓ formatRuntime > не показывает 0 минут

Tests  3 passed (3)`}>

```js
import { describe, it, expect } from "vitest";

function formatRuntime(minutes) {
  const hours = Math.floor(minutes / 60);
  const rest = minutes % 60;
  if (hours === 0) return `${rest}m`;
  if (rest === 0) return `${hours}h`;
  return `${hours}h ${rest}m`;
}

describe("formatRuntime", () => {
  it("показывает короткие фильмы в минутах", () => {
    expect(formatRuntime(45)).toBe("45m");
  });

  it("делит длинные фильмы на часы и минуты", () => {
    expect(formatRuntime(136)).toBe("2h 16m");
  });

  it("не показывает 0 минут", () => {
    expect(formatRuntime(120)).toBe("2h");
  });
});
```

</CodeExample>

<Callout type="tip" title="Маленькие шаги побеждают">

Секрет TDD — делать каждый шаг **крошечным**: один тест, несколько строк кода, несколько секунд работы Vitest в режиме наблюдения. Если что-то неожиданно покраснело, вы знаете, что виноваты последние пара строк, которые вы трогали. Если застряли на большой задаче, спросите себя: «Какой самый маленький следующий тест я могу написать?»

</Callout>

TDD особенно хороша для логики с чёткими правилами: вычислений, форматирования, валидации, разбора данных и исправления ошибок. Чтобы исправить баг, сначала напишите тест, который его **воспроизводит** (красный), потом исправьте (зелёный). Тогда баг уже не сможет незаметно вернуться. Когда вы исследуете идею или набрасываете интерфейс, многие разработчики пишут тесты после первой черновой версии, и это тоже нормально.

## Таблицы случаев с it.each

Три теста выше почти одинаковые: меняются только числа. **`it.each`** принимает таблицу случаев и запускает один и тот же тест для каждой строки. Значения строки становятся аргументами тестовой функции, а `%s` в имени заменяется на них:

<CodeExample output={`✓ formatRuntime > переводит 0 мин в 0m
✓ formatRuntime > переводит 59 мин в 59m
✓ formatRuntime > переводит 60 мин в 1h
✓ formatRuntime > переводит 61 мин в 1h 1m
✓ formatRuntime > переводит 136 мин в 2h 16m

Tests  5 passed (5)`}>

```js
import { describe, it, expect } from "vitest";

function formatRuntime(minutes) {
  const hours = Math.floor(minutes / 60);
  const rest = minutes % 60;
  if (hours === 0) return `${rest}m`;
  if (rest === 0) return `${hours}h`;
  return `${hours}h ${rest}m`;
}

describe("formatRuntime", () => {
  it.each([
    [0, "0m"],
    [59, "59m"],
    [60, "1h"],
    [61, "1h 1m"],
    [136, "2h 16m"],
  ])("переводит %s мин в %s", (minutes, expected) => {
    expect(formatRuntime(minutes)).toBe(expected);
  });
});
```

</CodeExample>

Каждая строка — отдельный тест, поэтому при падении сразу видно, какой именно случай сломался. Посмотрите, как дёшево обошлось добавить границы `59`, `60` и `61`: по одной короткой строке на каждую.

Строки таблицы могут быть и **объектами**. Тогда тестовая функция получает объект (деструктурируйте его!), а `$name` в заголовке подставляет значение свойства:

<CodeExample output={`✓ доставка стоит 4.99 при сумме корзины 10
✓ доставка стоит 4.99 при сумме корзины 49.99
✓ доставка стоит 0 при сумме корзины 50

Tests  3 passed (3)`}>

```js
import { it, expect } from "vitest";

function shippingCost(total) {
  return total >= 50 ? 0 : 4.99;
}

it.each([
  { total: 10, cost: 4.99 },
  { total: 49.99, cost: 4.99 },
  { total: 50, cost: 0 },
])("доставка стоит $cost при сумме корзины $total", ({ total, cost }) => {
  expect(shippingCost(total)).toBe(cost);
});
```

</CodeExample>

Объекты читаются легче, когда в строке больше двух-трёх значений. (`test.each` — то же самое, ведь `test` — просто другое имя для `it`.)

## Тестируем API-клиент с поддельным fetch

В настоящих приложениях весь код, который общается с API, обычно живёт в одном **API-клиенте (API client)**: объекте, у которого по методу на каждый запрос. Остальная часть приложения вызывает `movies.search("panda")` и никогда не собирает URL сама. Клиент получает `fetch` как опцию (внедрение зависимостей из прошлого урока), поэтому его можно целиком протестировать с подделкой:

<CodeExample output={`[ 'Panda Express to Mars', 'Ninja Pandas II' ]
✓ клиент фильмов > собирает URL поиска
✓ клиент фильмов > возвращает данные из API
✓ клиент фильмов > выбрасывает сообщение об ошибке от API
✓ клиент фильмов > пропускает сетевые ошибки дальше

Tests  4 passed (4)`}>

```js
import { describe, it, expect, vi } from "vitest";

function createMovieClient({ fetch, baseUrl }) {
  async function get(path) {
    const res = await fetch(baseUrl + path);
    const data = await res.json();
    if (!res.ok) {
      throw new Error(data.error ?? `Запрос не удался: ${res.status}`);
    }
    return data;
  }

  return {
    search(text, page = 1) {
      const params = new URLSearchParams({ search: text, page });
      return get(`/movies?${params}`);
    },
    getMovie(id) {
      return get(`/movies/${id}`);
    },
  };
}

function fakeResponse(status, body) {
  return {
    ok: status >= 200 && status < 300,
    status,
    json: async () => body,
  };
}

describe("клиент фильмов", () => {
  const baseUrl = "https://movies.test";

  it("собирает URL поиска", async () => {
    const fetch = vi.fn().mockResolvedValue(fakeResponse(200, {}));
    const client = createMovieClient({ fetch, baseUrl });
    await client.search("panda pals", 2);
    expect(fetch).toHaveBeenCalledWith(
      "https://movies.test/movies?search=panda+pals&page=2",
    );
  });

  it("возвращает данные из API", async () => {
    const page = { page: 1, results: [{ id: 7, title: "Test" }] };
    const fetch = vi.fn().mockResolvedValue(fakeResponse(200, page));
    const client = createMovieClient({ fetch, baseUrl });
    await expect(client.search("test")).resolves.toEqual(page);
  });

  it("выбрасывает сообщение об ошибке от API", async () => {
    const fetch = vi.fn().mockResolvedValue(
      fakeResponse(404, { error: "Movie not found" }),
    );
    const client = createMovieClient({ fetch, baseUrl });
    await expect(client.getMovie(99)).rejects.toThrow("Movie not found");
  });

  it("пропускает сетевые ошибки дальше", async () => {
    const fetch = vi.fn().mockRejectedValue(new TypeError("нет сети"));
    const client = createMovieClient({ fetch, baseUrl });
    await expect(client.getMovie(1)).rejects.toThrow(TypeError);
  });
});

// А в приложении тот же самый клиент общается с настоящим API:
const movies = createMovieClient({
  fetch,
  baseUrl: "https://api.pandadev.test",
});
const found = await movies.search("panda");
console.log(found.results.map((movie) => movie.title));
```

</CodeExample>

Последние строки используют настоящий `fetch` со встроенным учебным API PandaDev, который работает офлайн и всегда даёт одни и те же ответы. Настоящие API работают точно так же. А вот тесты в сеть не ходят никогда, поэтому проверяют то, что с настоящим API подстроить трудно:

- **Запрос**: правильно ли собран URL и закодирован ли текст поиска (`panda+pals`)?
- **«Счастливый путь»**: отдаёт ли клиент то, что вернул API?
- **Пути ошибок**: 404 с сообщением от API и сбой сети (`fetch` сам отклоняется — именно так бывает, когда нет интернета).

Опция `baseUrl` тоже окупается: тесты используют выдуманный хост, а приложение может переключаться между тестовым (staging) и боевым (production) сервером, не меняя клиент.

## Что тестировать (а что нет)

Тесты стоят времени — и на написание, и на поддержку, поэтому тратьте его там, где действительно живут ошибки.

**Тестируйте:**

- **Свою логику**: вычисления, правила, `if`, форматирование, валидацию. Большинство ошибок прячется именно там.
- **Граничные случаи и границы**: пустой ввод, `0`, точное значение, на котором меняется правило.
- **Пути ошибок**: что происходит, когда сервер отвечает 404 или ввод бессмысленный.
- **Договор с зависимостями**: какой URL вы вызываете, какие данные сохраняете, какое письмо отправляете.

**Не тестируйте:**

- **Сам язык или библиотеки**: что `Array.prototype.sort` сортирует, а `fetch` загружает. Их авторы это уже сделали.
- **Приватные детали**: вспомогательные переменные и внутренние шаги функции. Тестируйте через **публичные** функции и методы — тогда внутренности можно свободно рефакторить. Тесты, которые ломаются от каждой уборки в коде (хотя поведение не меняется), — это обуза, а не страховка.
- **Код без логики**: константу или функцию, которая просто передаёт значение дальше.

Большинство тестов проекта должны быть быстрыми **модульными тестами (unit tests)**, как в этом модуле. Чуть меньше пишут **интеграционных тестов (integration tests)**, которые проверяют, что настоящие части работают вместе (например, сервер на Express с Supertest — позже на этом уровне), и совсем немного медленных **сквозных тестов (end-to-end tests)**, которые прокликивают настоящее приложение в браузере с помощью инструментов вроде Playwright.

<Callout type="warning" title="Не мокайте всё подряд">

Подменяйте только то, что на **краях** программы: сеть, часы, случайность, хранилище, письма. Для собственных простых функций используйте настоящий код. Тест, где замокано всё, доказывает лишь то, что моки согласны друг с другом, и ломается при каждой перестановке кода.

</Callout>

## Измеряем покрытие

**Покрытие (coverage)** показывает, какие строки кода выполнялись во время тестов, а какие — ни разу. Vitest измеряет его с помощью дополнительного пакета (ему нужны настоящие файлы, поэтому в этом редакторе он не работает):

```bash
npm install --save-dev @vitest/coverage-v8
npx vitest run --coverage
```

Отчёт выглядит примерно так:

```text
 % Coverage report from v8
------------|---------|----------|---------|---------|-------------------
File        | % Stmts | % Branch | % Funcs | % Lines | Uncovered Line #s
------------|---------|----------|---------|---------|-------------------
All files   |   91.66 |    83.33 |     100 |   91.66 |
 movies.js  |   91.66 |    83.33 |     100 |   91.66 | 7
------------|---------|----------|---------|---------|-------------------
```

Самое полезное здесь — **Uncovered Line #s**: строка 7 ни разу не выполнилась, значит, ни один тест не проверяет, что там происходит. Возможно, это путь ошибки, и вы только что нашли недостающий тест. **% Branch** считает обе ветки каждого `if` и `??`, а это строже, чем подсчёт строк.

Покрытие показывает, что вы **не** протестировали, но не говорит, насколько хорошо протестировано остальное. Тест без единого `expect` тоже может дать 100%. Многие команды ориентируются примерно на 70–90% и куда больше заботятся о том, чтобы хорошо была покрыта важная логика, чем о точной цифре.

```js
import { describe, it, expect, vi } from "vitest";

// ---- Тестируемый код (не меняйте его) ----
function cookingLabel(minutes) {
  if (minutes <= 20) return "quick";
  if (minutes <= 45) return "medium";
  return "long";
}

function createRecipeClient({ fetch, baseUrl }) {
  async function get(path) {
    const res = await fetch(baseUrl + path);
    const data = await res.json();
    if (!res.ok) {
      throw new Error(data.error ?? "Запрос не удался");
    }
    return data;
  }
  return {
    search(text, tag) {
      const params = new URLSearchParams({ search: text });
      if (tag) params.set("tag", tag);
      return get("/recipes?" + params);
    },
    getRecipe(id) {
      return get("/recipes/" + id);
    },
  };
}

// Поддельный ответ только с тем, чем пользуется клиент
function fakeResponse(status, body) {
  return {
    ok: status >= 200 && status < 300,
    status,
    json: async () => body,
  };
}

// ---- Ваши тесты ----
describe("cookingLabel", () => {
  it.each([
    [5, "quick"],
    [20, "quick"],
    [21, "medium"],
    [45, "medium"],
    [46, "long"],
  ])("помечает %s мин как %s", (minutes, label) => {
    expect(cookingLabel(minutes)).toBe(label);
  });
});

describe("клиент рецептов", () => {
  const baseUrl = "https://recipes.test";

  it("ищет по тексту", async () => {
    const fetch = vi.fn().mockResolvedValue(fakeResponse(200, []));
    const client = createRecipeClient({ fetch, baseUrl });
    await client.search("soup");
    expect(fetch).toHaveBeenCalledWith(
      "https://recipes.test/recipes?search=soup",
    );
  });

  it("добавляет тег, если он есть", async () => {
    const fetch = vi.fn().mockResolvedValue(fakeResponse(200, []));
    const client = createRecipeClient({ fetch, baseUrl });
    await client.search("soup", "vegan");
    expect(fetch).toHaveBeenCalledWith(
      "https://recipes.test/recipes?search=soup&tag=vegan",
    );
  });

  it("возвращает рецепт", async () => {
    const recipe = { id: 3, name: "Tomato soup" };
    const fetch = vi.fn().mockResolvedValue(fakeResponse(200, recipe));
    const client = createRecipeClient({ fetch, baseUrl });
    await expect(client.getRecipe(3)).resolves.toEqual(recipe);
    expect(fetch).toHaveBeenCalledWith("https://recipes.test/recipes/3");
  });

  it("выбрасывает ошибку от API для несуществующего рецепта", async () => {
    const fetch = vi.fn().mockResolvedValue(
      fakeResponse(404, { error: "Recipe not found" }),
    );
    const client = createRecipeClient({ fetch, baseUrl });
    await expect(client.getRecipe(99)).rejects.toThrow(
      "Recipe not found",
    );
  });
});
```

## Итоги

- **TDD** — это цикл **red** (напишите падающий тест), **green** (самый простой код, который его проходит), **refactor** (наведите порядок под защитой тестов). Делайте каждый шаг маленьким.
- Чтобы исправить баг, сначала напишите тест, который его воспроизводит.
- **`it.each(table)(name, fn)`** запускает по тесту на каждую строку таблицы; `%s` (или `$property` для строк-объектов) подставляет значения в имя.
- Выносите вызовы API в **клиент**, который получает `fetch` и `baseUrl`, и проверяйте URL, «счастливый путь» и пути ошибок с поддельным `fetch`.
- Тестируйте свою логику, граничные случаи, ошибки и договор с зависимостями; не тестируйте библиотеки и приватные детали. Мокайте только на краях программы.
- `npx vitest run --coverage` показывает строки, которые не выполнил ни один тест. Высокое покрытие — подсказка, а не доказательство того, что тесты хорошие.
