The functions you tested last lesson were easy: numbers in, number out. Real code is messier. It **waits** for servers, sends emails, reads `localStorage`, rolls dice and checks the clock. You don't want your tests to send real emails, depend on the internet or fail at midnight. In this lesson you'll learn how to test async code, and how to swap the messy parts for **test doubles** that you control. 🎭

## Testing async code

To test a function that returns a **promise**, make the test function `async` and `await` the result. Vitest waits for the test's promise before it decides whether the test passed:

<CodeExample output={`✓ getScore > finds Mei's score
✓ getScore > resolves to a number
✓ getScore > rejects for unknown players

Tests  3 passed (3)`}>

```js
import { describe, it, expect } from "vitest";

// Pretend server: answers after 100 milliseconds
function getScore(player) {
  return new Promise((resolve, reject) => {
    setTimeout(() => {
      if (player === "Mei") {
        resolve(95);
      } else {
        reject(new Error(`No player called ${player}`));
      }
    }, 100);
  });
}

describe("getScore", () => {
  it("finds Mei's score", async () => {
    const score = await getScore("Mei");
    expect(score).toBe(95);
  });

  it("resolves to a number", async () => {
    await expect(getScore("Mei")).resolves.toBeTypeOf("number");
  });

  it("rejects for unknown players", async () => {
    await expect(getScore("Bob")).rejects.toThrow("No player");
  });
});
```

</CodeExample>

- The first test is the most common style: `await` the value, then check it as usual.
- **`.resolves`** waits for the promise and checks the value it resolves to.
- **`.rejects`** checks that the promise **fails**. Followed by `toThrow`, it checks the error, just like `toThrow` did for normal functions.

<Callout type="danger" title="Always await resolves and rejects">

`expect(promise).rejects.toThrow()` returns a promise too. Forget the `await` and the test function ends **before** the check has run:

```js
it("rejects for unknown players", () => {
  // ❌ No await: the test is over before this check finishes
  expect(getScore("Bob")).rejects.toThrow("No player");
});
```

Recent Vitest versions complain about this, but many test tools let it slide, and then the test passes no matter what. Write `await expect(...)` every time (and make the test `async`).

</Callout>

## Test doubles with vi.fn

A **test double** is a stand-in for something real, like a stunt double in a film. The most useful one is a **mock function**, made with **`vi.fn()`**. It's a function that does nothing, but **remembers every call**, so your test can ask how it was used:

<CodeExample output={`[ [ 'bao@pandadev.test', 'Order 2 is late, sorry!' ] ]
✓ emails only customers whose order is very late

Tests  1 passed (1)`}>

```js
import { it, expect, vi } from "vitest";

function notifyLateOrders(orders, sendEmail) {
  for (const order of orders) {
    if (order.daysLate > 2) {
      sendEmail(order.email, `Order ${order.id} is late, sorry!`);
    }
  }
}

it("emails only customers whose order is very late", () => {
  const sendEmail = vi.fn();
  const orders = [
    { id: 1, email: "mei@pandadev.test", daysLate: 0 },
    { id: 2, email: "bao@pandadev.test", daysLate: 5 },
  ];

  notifyLateOrders(orders, sendEmail);

  console.log(sendEmail.mock.calls);
  expect(sendEmail).toHaveBeenCalledTimes(1);
  expect(sendEmail).toHaveBeenCalledWith(
    "bao@pandadev.test",
    "Order 2 is late, sorry!",
  );
});
```

</CodeExample>

`notifyLateOrders` receives `sendEmail` as a parameter, so the test can hand it a mock instead of a real email sender. No emails leave the building, and the test checks exactly what **would** have been sent:

- `sendEmail.mock.calls` is an array with the arguments of every call.
- **`toHaveBeenCalled()`** checks it was called at all, **`toHaveBeenCalledTimes(n)`** how often, and **`toHaveBeenCalledWith(...)`** with which arguments. Add `.not` to check that something did **not** happen.
- If the check fails, the message reads like `expected "vi.fn()" to be called 1 times, but got 2 times`.

A mock can also **return** whatever the test needs. That makes it a **stub**: a fake answer from a dependency.

<CodeExample output={`0.85 0.85
6 1 3 3
{ name: 'Mei' }
42
[ [ 21 ] ] [ { type: 'return', value: 42 } ]`}>

```js
import { vi } from "vitest";

const getRate = vi.fn().mockReturnValue(0.85);
console.log(getRate("GBP"), getRate("EUR"));

const rollDie = vi.fn()
  .mockReturnValueOnce(6)
  .mockReturnValueOnce(1)
  .mockReturnValue(3);
console.log(rollDie(), rollDie(), rollDie(), rollDie());

const loadUser = vi.fn().mockResolvedValue({ name: "Mei" });
console.log(await loadUser(7));

const double = vi.fn((n) => n * 2);
console.log(double(21));
console.log(double.mock.calls, double.mock.results);
```

</CodeExample>

- `mockReturnValue(x)` returns `x` every time; `mockReturnValueOnce(x)` only for the next call (they queue up).
- `mockResolvedValue(x)` returns a promise that resolves to `x`, perfect for faking async functions. `mockRejectedValue(error)` returns one that fails.
- `vi.fn(implementation)` runs your own function, and still records the calls and results.

## Injecting dependencies

Here's the big idea behind testable code. A function that reaches out for `fetch`, `localStorage` or `Date.now()` by itself is hard to test: the test can't stop it from using the real thing. A function that **receives** them as parameters is easy: the app passes the real thing, and the tests pass a double. This is called **dependency injection**.

PandaDev has a practice API built in, so these lessons work offline and always give the same answers. Real APIs work the same way. Below, the app uses the real `fetch`, while the tests inject a fake one:

<CodeExample output={`The Bamboo Heist (2019)
✓ getMovieTitle > asks for the right movie
✓ getMovieTitle > formats the title and year
✓ getMovieTitle > throws when the movie doesn't exist

Tests  3 passed (3)`}>

```js
import { describe, it, expect, vi } from "vitest";

const API = "https://api.pandadev.test";

async function getMovieTitle(id, fetchFn = fetch) {
  const res = await fetchFn(`${API}/movies/${id}`);
  if (!res.ok) {
    throw new Error(`Movie ${id} not found`);
  }
  const movie = await res.json();
  return `${movie.title} (${movie.year})`;
}

// The real app uses the real fetch:
console.log(await getMovieTitle(1));

// The tests pass in a fake one:
function fakeResponse(status, body) {
  return {
    ok: status >= 200 && status < 300,
    status,
    json: async () => body,
  };
}

describe("getMovieTitle", () => {
  it("asks for the right movie", async () => {
    const fakeFetch = vi.fn().mockResolvedValue(
      fakeResponse(200, { title: "Test Film", year: 2001 }),
    );
    await getMovieTitle(42, fakeFetch);
    expect(fakeFetch).toHaveBeenCalledWith(`${API}/movies/42`);
  });

  it("formats the title and year", async () => {
    const fakeFetch = vi.fn().mockResolvedValue(
      fakeResponse(200, { title: "Test Film", year: 2001 }),
    );
    const title = await getMovieTitle(42, fakeFetch);
    expect(title).toBe("Test Film (2001)");
  });

  it("throws when the movie doesn't exist", async () => {
    const fakeFetch = vi.fn().mockResolvedValue(
      fakeResponse(404, { error: "Movie not found" }),
    );
    await expect(getMovieTitle(999, fakeFetch)).rejects.toThrow(
      "Movie 999 not found",
    );
  });
});
```

</CodeExample>

A few things to notice:

- The **default parameter** `fetchFn = fetch` means normal code doesn't have to pass anything. Only tests do.
- The fake response is a plain object with just the parts the code uses: `ok`, `status` and `json()`. A double only has to look real **from the code's point of view**.
- The tests are fast, never touch the network, and can easily fake situations that are hard to create for real, like a 404 or a server error.

## Spying on existing methods with vi.spyOn

Sometimes the dependency isn't passed in but lives on a global object, like `Math.random` or `console.warn`. **`vi.spyOn(object, "method")`** replaces that method with a mock (which still calls the original, unless you tell it otherwise). Afterwards, **`vi.restoreAllMocks()`** puts the real methods back:

<CodeExample output={`✓ rollDie > turns the lowest random number into 1
✓ rollDie > turns the highest random number into 6
✓ saveSettings > warns when the theme is missing

Tests  3 passed (3)`}>

```js
import { describe, it, expect, vi, afterEach } from "vitest";

function rollDie() {
  return Math.floor(Math.random() * 6) + 1;
}

function saveSettings(settings) {
  if (!settings.theme) {
    console.warn("No theme chosen, using light");
  }
  return { theme: "light", ...settings };
}

afterEach(() => {
  vi.restoreAllMocks(); // put the real methods back
});

describe("rollDie", () => {
  it("turns the lowest random number into 1", () => {
    vi.spyOn(Math, "random").mockReturnValue(0);
    expect(rollDie()).toBe(1);
  });

  it("turns the highest random number into 6", () => {
    vi.spyOn(Math, "random").mockReturnValue(0.9999);
    expect(rollDie()).toBe(6);
  });
});

describe("saveSettings", () => {
  it("warns when the theme is missing", () => {
    const warn = vi.spyOn(console, "warn").mockImplementation(() => {});
    expect(saveSettings({}).theme).toBe("light");
    expect(warn).toHaveBeenCalledWith("No theme chosen, using light");
  });
});
```

</CodeExample>

Random numbers are the enemy of tests: a test must give the same result every time. Spying on `Math.random` makes it predictable. The `mockImplementation(() => {})` on `console.warn` swallows the warning, so the test report stays clean while the test still checks it was printed.

## Fresh setup with beforeEach

When several tests need the same setup, don't copy it into each one. **`beforeEach(fn)`** runs `fn` before **every** test in the file (or in the `describe` block it's written in), and **`afterEach(fn)`** runs after each one. (There are also `beforeAll` and `afterAll`, which run once.)

Here a fake `localStorage` gets created fresh for every test, so no test sees what another one saved:

<CodeExample output={`✓ favourites > starts empty
✓ favourites > saves new favourites as JSON
✓ favourites > doesn't save the same movie twice

Tests  3 passed (3)`}>

```js
import { describe, it, expect, vi, beforeEach } from "vitest";

function createFavourites(storage) {
  const load = () => JSON.parse(storage.getItem("favs") ?? "[]");
  return {
    list: load,
    add(id) {
      const favs = load();
      if (!favs.includes(id)) {
        favs.push(id);
        storage.setItem("favs", JSON.stringify(favs));
      }
    },
  };
}

// A fake localStorage: a Map with the same methods
function fakeStorage() {
  const data = new Map();
  return {
    getItem: vi.fn((key) => data.get(key) ?? null),
    setItem: vi.fn((key, value) => data.set(key, String(value))),
  };
}

describe("favourites", () => {
  let storage;
  let favourites;

  beforeEach(() => {
    storage = fakeStorage(); // a fresh, empty one for every test
    favourites = createFavourites(storage);
  });

  it("starts empty", () => {
    expect(favourites.list()).toEqual([]);
  });

  it("saves new favourites as JSON", () => {
    favourites.add(3);
    expect(storage.setItem).toHaveBeenCalledWith("favs", "[3]");
    expect(favourites.list()).toEqual([3]);
  });

  it("doesn't save the same movie twice", () => {
    favourites.add(3);
    favourites.add(3);
    expect(storage.setItem).toHaveBeenCalledTimes(1);
  });
});
```

</CodeExample>

In the browser, the app calls `createFavourites(localStorage)`. The tests call it with a fake that behaves the same way, and whose methods are mocks, so the tests can check what got saved.

## Controlling time with fake timers

A search box that waits 300 ms after the last key press (a **debounced** search) is hard to test with real time: you'd have to wait, and waiting makes tests slow and unreliable. **Fake timers** replace `setTimeout` and friends with a clock that only moves when the test says so:

<CodeExample output={`✓ debounce > waits until the typing stops

Tests  1 passed (1)`}>

```js
import { describe, it, expect, vi, beforeEach, afterEach } from "vitest";

function debounce(fn, ms) {
  let timer;
  return (...args) => {
    clearTimeout(timer);
    timer = setTimeout(() => fn(...args), ms);
  };
}

describe("debounce", () => {
  beforeEach(() => {
    vi.useFakeTimers();
  });

  afterEach(() => {
    vi.useRealTimers();
  });

  it("waits until the typing stops", () => {
    const search = vi.fn();
    const searchSoon = debounce(search, 300);

    searchSoon("p");
    searchSoon("pa");
    searchSoon("pan");
    vi.advanceTimersByTime(299);
    expect(search).not.toHaveBeenCalled();

    vi.advanceTimersByTime(1);
    expect(search).toHaveBeenCalledTimes(1);
    expect(search).toHaveBeenCalledWith("pan");
  });
});
```

</CodeExample>

- **`vi.useFakeTimers()`** switches to the fake clock; **`vi.useRealTimers()`** switches back (do it in `afterEach` so other tests aren't affected).
- **`vi.advanceTimersByTime(ms)`** moves the clock forward and runs every timer that's due. `vi.runAllTimers()` runs all waiting timers at once.
- Checking at 299 ms **and** at 300 ms tests the boundary, exactly like the edge cases from last lesson.

Fake timers also control the clock itself. **`vi.setSystemTime(date)`** sets what `Date.now()` returns, which is how you test anything that depends on "now":

<CodeExample output={`✓ keeps a session for 24 hours

Tests  1 passed (1)`}>

```js
import { it, expect, vi, afterEach } from "vitest";

const HOUR = 60 * 60 * 1000;

function isExpired(session) {
  return Date.now() - session.createdAt > 24 * HOUR;
}

afterEach(() => {
  vi.useRealTimers();
});

it("keeps a session for 24 hours", () => {
  vi.useFakeTimers();
  vi.setSystemTime(new Date("2026-03-01T12:00:00Z"));
  const session = { createdAt: Date.now() };

  vi.advanceTimersByTime(24 * HOUR);
  expect(isExpired(session)).toBe(false);

  vi.advanceTimersByTime(1);
  expect(isExpired(session)).toBe(true);
});
```

</CodeExample>

A full day passes in a millisecond of real time. 🕰️

<Callout type="note" title="What about vi.mock?">

In real projects you'll also see **`vi.mock`**, which replaces a whole **module** for the test file, so even code that imports `fetchMovie` directly gets a mock:

```js
// movies.test.js
import { it, expect, vi } from "vitest";
import { fetchMovie } from "./api.js";
import { getMovieTitle } from "./movies.js";

vi.mock("./api.js", () => ({ fetchMovie: vi.fn() }));

it("formats the title", async () => {
  fetchMovie.mockResolvedValue({ title: "Test Film", year: 2001 });
  expect(await getMovieTitle(42)).toBe("Test Film (2001)");
});
```

It's powerful, but a bit magical (Vitest moves `vi.mock` to the top of the file before anything is imported). Module mocking needs real files, so it doesn't work in this editor. Dependency injection works everywhere, keeps your code honest about what it depends on, and is what we use in these lessons.

</Callout>

import { describe, it, expect, vi } from "vitest";

// ---- The code under test (don't change it) ----
async function sendWelcome(userId, { fetchUser, sendEmail }) {
  const user = await fetchUser(userId);
  if (!user.email) {
    throw new Error("User has no email address");
  }
  await sendEmail(user.email, "Welcome, " + user.name + "!");
  return user.email;
}

// ---- Your tests ----
describe("sendWelcome", () => {
  it("looks up the right user", async () => {
    const fetchUser = vi.fn().mockResolvedValue({
      name: "Mei",
      email: "mei@pandadev.test",
    });
    const sendEmail = vi.fn();
    await sendWelcome(42, { fetchUser, sendEmail });
    expect(fetchUser).toHaveBeenCalledWith(42);
  });

  it("emails the user a welcome message", async () => {
    const fetchUser = vi.fn().mockResolvedValue({
      name: "Mei",
      email: "mei@pandadev.test",
    });
    const sendEmail = vi.fn();
    const sentTo = await sendWelcome(42, { fetchUser, sendEmail });
    expect(sendEmail).toHaveBeenCalledTimes(1);
    expect(sendEmail).toHaveBeenCalledWith(
      "mei@pandadev.test",
      "Welcome, Mei!",
    );
    expect(sentTo).toBe("mei@pandadev.test");
  });

  it("rejects users without an email and sends nothing", async () => {
    const fetchUser = vi.fn().mockResolvedValue({ name: "Bao" });
    const sendEmail = vi.fn();
    await expect(
      sendWelcome(7, { fetchUser, sendEmail }),
    ).rejects.toThrow("no email");
    expect(sendEmail).not.toHaveBeenCalled();
  });
});

## Recap

- Test async code with `async` tests and `await`. `await expect(promise).resolves...` checks the value, `await expect(promise).rejects.toThrow(...)` checks the failure. Never forget the `await`.
- **`vi.fn()`** makes a mock function that records its calls. Check them with `toHaveBeenCalled`, `toHaveBeenCalledTimes` and `toHaveBeenCalledWith`; make it return values with `mockReturnValue` / `mockResolvedValue`.
- **Dependency injection**: pass `fetch`, storage, senders and clocks **in**, so the app uses the real ones and tests use doubles.
- **`vi.spyOn(object, "method")`** replaces a method like `Math.random` or `console.warn`; `vi.restoreAllMocks()` puts it back.
- **`beforeEach`/`afterEach`** give every test a fresh setup.
- **Fake timers** (`vi.useFakeTimers`, `vi.advanceTimersByTime`, `vi.setSystemTime`) test timeouts, debouncing and dates without waiting.
- `vi.mock` replaces whole modules in real projects; injection works everywhere.
