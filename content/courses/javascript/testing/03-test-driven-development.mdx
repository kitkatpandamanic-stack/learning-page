So far you've written the code first and the tests afterwards. **Test-driven development** (TDD) flips that around: you write a failing test **first**, then just enough code to make it pass. It sounds backwards, but it makes you decide what the code should do before you get lost in how, and every line you write ends up tested. In this lesson you'll build a small feature the TDD way, test an API client without the network, and learn what's worth testing at all. 🚦

## Red, green, refactor

TDD is a short loop that you repeat again and again:

1. 🔴 **Red**: write one small test for behaviour that doesn't exist yet. Run it and watch it **fail**.
2. 🟢 **Green**: write the **simplest** code that makes it pass. No extras.
3. 🔵 **Refactor**: with the tests green, tidy up the code (better names, less repetition). Run the tests again to make sure they're still green.

Let's build `formatRuntime(minutes)` for a movie app: `45` should show as `"45m"` and `136` as `"2h 16m"`. Step one is a test, while the function is still empty:

<CodeExample output={`× formatRuntime > shows short films in minutes
  → expected undefined to be '45m' // Object.is equality

Tests  1 failed (1)`}>

```js
import { describe, it, expect } from "vitest";

function formatRuntime(minutes) {
  // Not written yet!
}

describe("formatRuntime", () => {
  it("shows short films in minutes", () => {
    expect(formatRuntime(45)).toBe("45m");
  });
});
```

</CodeExample>

Red, as expected. That's not a waste of time: seeing it fail proves the test **can** fail, so it really checks something.

Now the simplest code that passes is `` return `${minutes}m`; ``. It feels like cheating, but that's the point: the code only does what the tests ask for. To make it do more, we need another test, so the next cycle starts with red again:

<CodeExample output={`✓ formatRuntime > shows short films in minutes
× formatRuntime > splits long films into hours and minutes
  → expected '136m' to be '2h 16m' // Object.is equality

Tests  1 failed | 1 passed (2)`}>

```js
import { describe, it, expect } from "vitest";

function formatRuntime(minutes) {
  return `${minutes}m`;
}

describe("formatRuntime", () => {
  it("shows short films in minutes", () => {
    expect(formatRuntime(45)).toBe("45m");
  });

  it("splits long films into hours and minutes", () => {
    expect(formatRuntime(136)).toBe("2h 16m");
  });
});
```

</CodeExample>

To get green, the function splits the minutes into hours and the rest. A third cycle adds an edge case: `120` should be `"2h"`, not `"2h 0m"`. Red, then one more `if` makes it green. Finally, the refactor step: the tests protect us while we make the code read nicely:

<CodeExample output={`✓ formatRuntime > shows short films in minutes
✓ formatRuntime > splits long films into hours and minutes
✓ formatRuntime > leaves out 0 minutes

Tests  3 passed (3)`}>

```js
import { describe, it, expect } from "vitest";

function formatRuntime(minutes) {
  const hours = Math.floor(minutes / 60);
  const rest = minutes % 60;
  if (hours === 0) return `${rest}m`;
  if (rest === 0) return `${hours}h`;
  return `${hours}h ${rest}m`;
}

describe("formatRuntime", () => {
  it("shows short films in minutes", () => {
    expect(formatRuntime(45)).toBe("45m");
  });

  it("splits long films into hours and minutes", () => {
    expect(formatRuntime(136)).toBe("2h 16m");
  });

  it("leaves out 0 minutes", () => {
    expect(formatRuntime(120)).toBe("2h");
  });
});
```

</CodeExample>

<Callout type="tip" title="Small steps win">

The secret of TDD is keeping each step **tiny**: one test, a few lines of code, a few seconds of running Vitest in watch mode. If something goes red unexpectedly, you know it was the last couple of lines you touched. When you're stuck on a big feature, ask: "What's the smallest next test I could write?"

</Callout>

TDD shines for logic with clear rules: calculations, formatting, validation, parsing, and bug fixes. For a bug, first write a test that **reproduces** it (red), then fix it (green). The bug can never sneak back unnoticed. For exploring an idea or sketching a UI, many developers write the tests after the first rough version, and that's fine too.

## Tables of cases with it.each

The three tests above are almost identical: only the numbers change. **`it.each`** takes a table of cases and runs the same test once per row. The values of each row become the test function's arguments, and `%s` in the name is replaced by them:

<CodeExample output={`✓ formatRuntime > formats 0 minutes as 0m
✓ formatRuntime > formats 59 minutes as 59m
✓ formatRuntime > formats 60 minutes as 1h
✓ formatRuntime > formats 61 minutes as 1h 1m
✓ formatRuntime > formats 136 minutes as 2h 16m

Tests  5 passed (5)`}>

```js
import { describe, it, expect } from "vitest";

function formatRuntime(minutes) {
  const hours = Math.floor(minutes / 60);
  const rest = minutes % 60;
  if (hours === 0) return `${rest}m`;
  if (rest === 0) return `${hours}h`;
  return `${hours}h ${rest}m`;
}

describe("formatRuntime", () => {
  it.each([
    [0, "0m"],
    [59, "59m"],
    [60, "1h"],
    [61, "1h 1m"],
    [136, "2h 16m"],
  ])("formats %s minutes as %s", (minutes, expected) => {
    expect(formatRuntime(minutes)).toBe(expected);
  });
});
```

</CodeExample>

Each row is a separate test, so a failure tells you exactly which case broke. Look at how cheap it was to add the boundaries `59`, `60` and `61`: one short line each.

Rows can also be **objects**. Then the test function receives the object (destructure it!), and `$name` in the title shows a property:

<CodeExample output={`✓ charges 4.99 when the basket is 10
✓ charges 4.99 when the basket is 49.99
✓ charges 0 when the basket is 50

Tests  3 passed (3)`}>

```js
import { it, expect } from "vitest";

function shippingCost(total) {
  return total >= 50 ? 0 : 4.99;
}

it.each([
  { total: 10, cost: 4.99 },
  { total: 49.99, cost: 4.99 },
  { total: 50, cost: 0 },
])("charges $cost when the basket is $total", ({ total, cost }) => {
  expect(shippingCost(total)).toBe(cost);
});
```

</CodeExample>

Objects are easier to read when a row has more than two or three values. (`test.each` is the same thing, as `test` is just another name for `it`.)

## Testing an API client with a fake fetch

In real apps, all the code that talks to an API usually lives in one **API client**: an object with a method per request. The rest of the app calls `movies.search("panda")` and never builds URLs itself. Because the client receives `fetch` as an option (dependency injection, from the last lesson), you can test every bit of it with a fake:

<CodeExample output={`[ 'Panda Express to Mars', 'Ninja Pandas II' ]
✓ movie client > builds the search URL
✓ movie client > returns the data from the API
✓ movie client > throws the API's error message
✓ movie client > passes on network errors

Tests  4 passed (4)`}>

```js
import { describe, it, expect, vi } from "vitest";

function createMovieClient({ fetch, baseUrl }) {
  async function get(path) {
    const res = await fetch(baseUrl + path);
    const data = await res.json();
    if (!res.ok) {
      throw new Error(data.error ?? `Request failed: ${res.status}`);
    }
    return data;
  }

  return {
    search(text, page = 1) {
      const params = new URLSearchParams({ search: text, page });
      return get(`/movies?${params}`);
    },
    getMovie(id) {
      return get(`/movies/${id}`);
    },
  };
}

function fakeResponse(status, body) {
  return {
    ok: status >= 200 && status < 300,
    status,
    json: async () => body,
  };
}

describe("movie client", () => {
  const baseUrl = "https://movies.test";

  it("builds the search URL", async () => {
    const fetch = vi.fn().mockResolvedValue(fakeResponse(200, {}));
    const client = createMovieClient({ fetch, baseUrl });
    await client.search("panda pals", 2);
    expect(fetch).toHaveBeenCalledWith(
      "https://movies.test/movies?search=panda+pals&page=2",
    );
  });

  it("returns the data from the API", async () => {
    const page = { page: 1, results: [{ id: 7, title: "Test" }] };
    const fetch = vi.fn().mockResolvedValue(fakeResponse(200, page));
    const client = createMovieClient({ fetch, baseUrl });
    await expect(client.search("test")).resolves.toEqual(page);
  });

  it("throws the API's error message", async () => {
    const fetch = vi.fn().mockResolvedValue(
      fakeResponse(404, { error: "Movie not found" }),
    );
    const client = createMovieClient({ fetch, baseUrl });
    await expect(client.getMovie(99)).rejects.toThrow("Movie not found");
  });

  it("passes on network errors", async () => {
    const fetch = vi.fn().mockRejectedValue(new TypeError("offline"));
    const client = createMovieClient({ fetch, baseUrl });
    await expect(client.getMovie(1)).rejects.toThrow(TypeError);
  });
});

// And in the app, the very same client talks to a real API:
const movies = createMovieClient({
  fetch,
  baseUrl: "https://api.pandadev.test",
});
const found = await movies.search("panda");
console.log(found.results.map((movie) => movie.title));
```

</CodeExample>

The last lines use the real `fetch` with PandaDev's built-in practice API, which works offline and always gives the same answers. Real APIs work the same way. The tests, however, never touch the network, so they check things the real API makes hard to arrange:

- **The request**: is the URL built correctly, with the search text encoded (`panda+pals`)?
- **The happy path**: does the client hand back what the API returned?
- **The error paths**: a 404 with the API's message, and a network failure (`fetch` itself rejects, which is what happens when you're offline).

Taking `baseUrl` as an option pays off too: tests use a made-up host, and the app can switch between a staging and a production server without changing the client.

## What to test (and what not to)

Tests cost time to write and to maintain, so spend them where bugs actually live.

**Do test:**

- **Your logic**: calculations, rules, `if`s, formatting, validation. That's where most bugs hide.
- **Edge cases and boundaries**: empty input, `0`, the exact value where a rule changes.
- **Error paths**: what happens when the server says 404, or the input is nonsense.
- **The contract with your dependencies**: what URL you call, what data you save, which email you send.

**Don't test:**

- **The language or libraries**: that `Array.prototype.sort` sorts, or that `fetch` fetches. Their authors already did.
- **Private details**: helper variables and the inner steps of a function. Test through the **public** functions and methods, so you can refactor the inside freely. Tests that break whenever you tidy up code (without changing what it does) are a burden, not a safety net.
- **Code without logic**: a constant or a function that only passes a value along.

Most of a project's tests should be fast **unit tests** like the ones in this module. Add fewer **integration tests**, which check that real pieces work together (for example, an Express server with Supertest, later in this level), and only a handful of slow **end-to-end tests** that click through the real app in a browser with tools like Playwright.

<Callout type="warning" title="Don't mock everything">

Mock at the **edges** of your program: the network, the clock, randomness, storage, emails. Use the real thing for your own plain functions. A test where everything is mocked only proves that the mocks agree with each other, and it breaks every time you rearrange the code.

</Callout>

## Measuring coverage

**Coverage** tells you which lines of your code ran during the tests, and which never did. Vitest measures it with an extra package (it needs real files, so it doesn't run in this editor):

```bash
npm install --save-dev @vitest/coverage-v8
npx vitest run --coverage
```

The report looks something like this:

```text
 % Coverage report from v8
------------|---------|----------|---------|---------|-------------------
File        | % Stmts | % Branch | % Funcs | % Lines | Uncovered Line #s
------------|---------|----------|---------|---------|-------------------
All files   |   91.66 |    83.33 |     100 |   91.66 |
 movies.js  |   91.66 |    83.33 |     100 |   91.66 | 7
------------|---------|----------|---------|---------|-------------------
```

**Uncovered Line #s** is the useful part: line 7 never ran, so no test checks what happens there. Maybe it's the error path, and you just found a missing test. **% Branch** counts both sides of every `if` and `??`, which is stricter than counting lines.

Coverage shows what you **didn't** test, not how well you tested the rest. A test without a single `expect` can still give you 100%. Many teams aim for roughly 70–90% and care far more that the important logic is well covered than about the exact number.

import { describe, it, expect, vi } from "vitest";

// ---- The code under test (don't change it) ----
function cookingLabel(minutes) {
  if (minutes <= 20) return "quick";
  if (minutes <= 45) return "medium";
  return "long";
}

function createRecipeClient({ fetch, baseUrl }) {
  async function get(path) {
    const res = await fetch(baseUrl + path);
    const data = await res.json();
    if (!res.ok) {
      throw new Error(data.error ?? "Request failed");
    }
    return data;
  }
  return {
    search(text, tag) {
      const params = new URLSearchParams({ search: text });
      if (tag) params.set("tag", tag);
      return get("/recipes?" + params);
    },
    getRecipe(id) {
      return get("/recipes/" + id);
    },
  };
}

// A fake response with just what the client uses
function fakeResponse(status, body) {
  return {
    ok: status >= 200 && status < 300,
    status,
    json: async () => body,
  };
}

// ---- Your tests ----
describe("cookingLabel", () => {
  it.each([
    [5, "quick"],
    [20, "quick"],
    [21, "medium"],
    [45, "medium"],
    [46, "long"],
  ])("labels %s minutes as %s", (minutes, label) => {
    expect(cookingLabel(minutes)).toBe(label);
  });
});

describe("recipe client", () => {
  const baseUrl = "https://recipes.test";

  it("searches by text", async () => {
    const fetch = vi.fn().mockResolvedValue(fakeResponse(200, []));
    const client = createRecipeClient({ fetch, baseUrl });
    await client.search("soup");
    expect(fetch).toHaveBeenCalledWith(
      "https://recipes.test/recipes?search=soup",
    );
  });

  it("adds the tag when there is one", async () => {
    const fetch = vi.fn().mockResolvedValue(fakeResponse(200, []));
    const client = createRecipeClient({ fetch, baseUrl });
    await client.search("soup", "vegan");
    expect(fetch).toHaveBeenCalledWith(
      "https://recipes.test/recipes?search=soup&tag=vegan",
    );

    const recipe = { id: 3, name: "Tomato soup" };
    const fetch = vi.fn().mockResolvedValue(fakeResponse(200, recipe));

## Recap

- **TDD** is the loop **red** (write a failing test), **green** (simplest code that passes), **refactor** (tidy up with the tests as a safety net). Keep each step small.
- To fix a bug, first write a test that reproduces it.
- **`it.each(table)(name, fn)`** runs one test per row; `%s` (or `$property` for object rows) puts the values in the name.
- Put API calls in a **client** that receives `fetch` and `baseUrl`, then test the URL, the happy path and the error paths with a fake `fetch`.
- Test your logic, edge cases, errors and the contract with dependencies; don't test libraries or private details. Mock only at the edges.
- `npx vitest run --coverage` shows which lines no test ran. High coverage is a hint, not proof that the tests are good.
