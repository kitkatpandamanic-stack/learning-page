До сих пор вы проверяли код так: запускали его и смотрели, что он печатает. Для десяти строк это работает. Но в настоящем проекте любое изменение может незаметно сломать то, что вы проверяли на прошлой неделе, а перепроверять всё вручную никто не станет. **Автоматические тесты (automated tests)** — это маленькие фрагменты кода, которые проверяют ваш код за вас: за секунду и после каждого изменения. В современных JavaScript-проектах для этого чаще всего берут **Vitest**. 🧪

## Зачем автоматизировать проверки?

Вот как вы проверяли код до сих пор:

<CodeExample output={`180
50
34`}>

```js
function applyDiscount(price, percent) {
  return price - (price * percent) / 100;
}

console.log(applyDiscount(200, 10)); // должно быть 180
console.log(applyDiscount(50, 0)); // должно быть 50
console.log(applyDiscount(40, 15)); // должно быть 34
```

</CodeExample>

Это работает, но тест здесь — **вы**: нужно помнить, каким должно быть каждое число, и сравнивать глазами. Превратите эти комментарии в код, который сравнивает сам, и вы получите:

- **Регрессии ловятся сразу.** **Регрессия (regression)** — это ошибка в том, что раньше работало. Тесты замечают её в момент появления, а не тогда, когда на неё наткнётся клиент.
- **Код можно менять без страха.** Переименовывайте, наводите порядок, ускоряйте: если тесты по-прежнему проходят, вы ничего не сломали.
- **Тесты документируют поведение.** Тест с именем `"берёт с 18-летних взрослую цену"` сразу говорит следующему разработчику, что именно должен делать код.

## describe, it и expect

В тестовом файле Vitest используются три функции, которые импортируются из `"vitest"`:

- **`it(name, fn)`** описывает один тест. Имя описывает поведение, а функция его проверяет. (`test` — другое имя той же самой функции.)
- **`expect(value)`** оборачивает полученное значение, а **матчер (matcher)** вроде `.toBe(180)` сравнивает его с ожидаемым. Если они не совпадают, тест падает.
- **`describe(name, fn)`** группирует связанные тесты — обычно все тесты одной функции.

<CodeExample output={`Код выполнен. Теперь Vitest запускает тесты:
✓ applyDiscount > снимает 10%
✓ applyDiscount > ничего не меняет при 0%
✓ applyDiscount > делит цену пополам при 50%

Tests  3 passed (3)`}>

```js
import { describe, it, expect } from "vitest";

function applyDiscount(price, percent) {
  return price - (price * percent) / 100;
}

describe("applyDiscount", () => {
  it("снимает 10%", () => {
    expect(applyDiscount(200, 10)).toBe(180);
  });

  it("ничего не меняет при 0%", () => {
    expect(applyDiscount(50, 0)).toBe(50);
  });

  it("делит цену пополам при 50%", () => {
    expect(applyDiscount(30, 50)).toBe(15);
  });
});

console.log("Код выполнен. Теперь Vitest запускает тесты:");
```

</CodeExample>

Обратите внимание на порядок. `describe` и `it` не запускают тесты сразу, а **собирают** их. Vitest запускает тесты, когда остальной код уже выполнился, и затем печатает отчёт. Каждый `✓` — пройденный тест в виде `группа > имя теста`, а последняя строка подводит итог. Прочитайте имена вслух: «applyDiscount снимает 10%». Хорошие имена тестов складываются в предложение.

## Vitest в настоящем проекте

На этой странице код и его тесты живут в одном редакторе. В настоящем проекте тесты лежат в отдельном файле рядом с кодом, и в имени файла есть `.test.js`. Vitest находит такие файлы сам:

```text
shop/
├── package.json
├── pricing.js        # export function applyDiscount(...)
└── pricing.test.js   # import { applyDiscount } from "./pricing.js";
```

Vitest устанавливается один раз как **dev-зависимость (dev dependency)** — он нужен только во время разработки, как вы видели в уроке про npm, — и в `package.json` добавляется скрипт `test`:

```bash
npm install --save-dev vitest
```

```json title="package.json"
{
  "type": "module",
  "scripts": {
    "test": "vitest"
  }
}
```

Теперь `npm test` (или `npx vitest`) запускает Vitest в **режиме наблюдения (watch mode)**: он прогоняет тесты, а потом ждёт и перезапускает их при каждом сохранении файла. `npx vitest run` запускает тесты один раз и завершается — так делают серверы сборки. Отчёт выглядит примерно так:

```text
 ✓ pricing.test.js (3 tests) 2ms

 Test Files  1 passed (1)
      Tests  3 passed (3)
   Duration  210ms
```

## Как читать отчёт о падении

Пройденные тесты ведут себя тихо. Самое интересное — что Vitest сообщает, когда тест **падает**. Вот счётчик слов с ошибкой:

<CodeExample output={`✓ countWords > считает слова в простом предложении
× countWords > игнорирует лишние пробелы
  → expected 3 to be 2 // Object.is equality
× countWords > возвращает 0 для пустой строки
  → expected 1 to be 0 // Object.is equality

Tests  2 failed | 1 passed (3)`}>

```js
import { describe, it, expect } from "vitest";

function countWords(text) {
  return text.split(" ").length;
}

describe("countWords", () => {
  it("считает слова в простом предложении", () => {
    expect(countWords("панды едят бамбук")).toBe(3);
  });

  it("игнорирует лишние пробелы", () => {
    expect(countWords("панды  едят")).toBe(2);
  });

  it("возвращает 0 для пустой строки", () => {
    expect(countWords("")).toBe(0);
  });
});
```

</CodeExample>

- `×` отмечает упавший тест, а строка `→` под ним объясняет причину: код вернул `3`, а тест ожидал `2`. Первое значение — всегда **то, что получилось**, второе — **то, что ожидалось**.
- `// Object.is equality` говорит, каким сравнением пользовался `toBe` (об этом чуть ниже).
- Итоговая строка начинается с падений, чтобы их нельзя было пропустить.

Теперь ошибки легко заметить: `"панды  едят".split(" ")` даёт `['панды', '', 'едят']`, а `"".split(" ")` даёт `['']`. Если выбросить пустые строки, исправятся обе:

<CodeExample output={`✓ countWords > считает слова в простом предложении
✓ countWords > игнорирует лишние пробелы
✓ countWords > возвращает 0 для пустой строки

Tests  3 passed (3)`}>

```js
import { describe, it, expect } from "vitest";

function countWords(text) {
  return text.split(" ").filter((word) => word !== "").length;
}

describe("countWords", () => {
  it("считает слова в простом предложении", () => {
    expect(countWords("панды едят бамбук")).toBe(3);
  });

  it("игнорирует лишние пробелы", () => {
    expect(countWords("панды  едят")).toBe(2);
  });

  it("возвращает 0 для пустой строки", () => {
    expect(countWords("")).toBe(0);
  });
});
```

</CodeExample>

<Callout type="tip" title="Пусть каждый тест хоть раз упадёт">

Тест, который не может упасть, хуже, чем отсутствие теста: он создаёт ложное чувство безопасности. Написав тест, ненадолго сломайте код намеренно (или напишите тест раньше кода, как вы сделаете в уроке про TDD) и убедитесь, что тест краснеет. Затем верните код и посмотрите, как тест снова зеленеет.

</Callout>

## toBe или toEqual?

Чаще всего вы будете пользоваться матчером `toBe`. Он сравнивает через **`Object.is`** — это почти то же самое, что `===`. Для чисел, строк и логических значений это идеально. Но помните: два объекта равны по `===`, только если это **один и тот же** объект, а не просто похожие объекты:

<CodeExample output={`✓ toBe работает для чисел и строк
× toBe сравнивает объекты по ссылке
  → expected { name: 'Mei', food: [ 'бамбук' ] } to be { name: 'Mei', food: [ 'бамбук' ] } // If it should pass with deep equality, replace "toBe" with "toStrictEqual"
✓ toEqual сравнивает содержимое

Tests  1 failed | 2 passed (3)`}>

```js
import { it, expect } from "vitest";

function makePanda(name) {
  return { name, food: ["бамбук"] };
}

it("toBe работает для чисел и строк", () => {
  expect(2 + 2).toBe(4);
  expect(makePanda("Mei").name).toBe("Mei");
});

it("toBe сравнивает объекты по ссылке", () => {
  expect(makePanda("Mei")).toBe({ name: "Mei", food: ["бамбук"] });
});

it("toEqual сравнивает содержимое", () => {
  expect(makePanda("Mei")).toEqual({ name: "Mei", food: ["бамбук"] });
});
```

</CodeExample>

Простое правило:

- **`toBe`** — для **примитивных** значений: чисел, строк, логических значений, `null`, `undefined`.
- **`toEqual`** — для **объектов и массивов**: он обходит их и сравнивает каждое свойство и каждый элемент («глубокое равенство», deep equality).
- **`toStrictEqual`** — более строгий `toEqual`: он замечает ещё и свойства со значением `undefined`, и объекты, созданные разными классами. Многие команды используют его для объектов по умолчанию.

## Популярные матчеры

Не обязательно втискивать каждую проверку в `toBe`. В Vitest есть матчер почти для любой ситуации, и правильно выбранный матчер даёт более понятное сообщение о падении. Вот те, что пригодятся каждый день:

<CodeExample output={`✓ популярные матчеры > проверяют истинность и отсутствующие значения
✓ популярные матчеры > проверяют числа
✓ популярные матчеры > проверяют строки, массивы и объекты
✓ популярные матчеры > умеют проверять то, чего быть НЕ должно

Tests  4 passed (4)`}>

```js
import { describe, it, expect } from "vitest";

const user = {
  name: "Mei",
  email: "mei@pandadev.test",
  roles: ["student", "admin"],
  address: { city: "Chengdu" },
  nickname: null,
};

describe("популярные матчеры", () => {
  it("проверяют истинность и отсутствующие значения", () => {
    expect(user.roles.length).toBeTruthy();
    expect(user.nickname).toBeNull();
    expect(user.age).toBeUndefined();
    expect(user.name).toBeDefined();
  });

  it("проверяют числа", () => {
    expect(user.roles.length).toBeGreaterThan(1);
    expect(user.roles.length).toBeLessThanOrEqual(2);
    expect(0.1 + 0.2).toBeCloseTo(0.3);
  });

  it("проверяют строки, массивы и объекты", () => {
    expect(user.email).toMatch(/@pandadev\.test$/);
    expect(user.email).toContain("mei");
    expect(user.roles).toContain("admin");
    expect(user.roles).toHaveLength(2);
    expect(user).toHaveProperty("address.city", "Chengdu");
  });

  it("умеют проверять то, чего быть НЕ должно", () => {
    expect(user.roles).not.toContain("banned");
    expect(user.name).not.toBe("");
  });
});
```

</CodeExample>

- `toBeTruthy` / `toBeFalsy`, `toBeNull`, `toBeUndefined`, `toBeDefined` проверяют «пустые» значения.
- `toBeGreaterThan`, `toBeLessThan` (и их варианты с `OrEqual`) сравнивают числа. Для дробей используйте **`toBeCloseTo`**: `0.1 + 0.2` на самом деле равно `0.30000000000000004`, так что `toBe(0.3)` упадёт.
- `toMatch` проверяет строку регулярным выражением (или фрагментом текста). `toContain` проверяет, что строка содержит текст или что массив содержит элемент.
- `toHaveLength` проверяет `.length`, а `toHaveProperty` — что свойство существует (для вложенных объектов — путь через точку) и, если нужно, его значение.
- Поставьте **`.not`** перед любым матчером, чтобы перевернуть его смысл.

## Проверка ошибок через toThrow

Иногда правильное поведение — **это** ошибка. Если `parseAge` получает `"двенадцать"`, она должна выбросить исключение (exception). Чтобы это проверить, передайте в `expect` **функцию**, которая делает вызов, и используйте `toThrow`:

<CodeExample output={`✓ parseAge > возвращает возраст числом
✓ parseAge > отклоняет текст
✓ parseAge > сообщает, что не так
✓ parseAge > использует правильный тип ошибки
× parseAge > забывает стрелочную функцию (неправильно!)
  → TypeError: "abc" — не целое число

Tests  1 failed | 4 passed (5)`}>

```js
import { describe, it, expect } from "vitest";

function parseAge(text) {
  const age = Number(text);
  if (!Number.isInteger(age)) {
    throw new TypeError(`"${text}" — не целое число`);
  }
  if (age < 0 || age > 130) {
    throw new RangeError(`${age} не входит в диапазон от 0 до 130`);
  }
  return age;
}

describe("parseAge", () => {
  it("возвращает возраст числом", () => {
    expect(parseAge("12")).toBe(12);
  });

  it("отклоняет текст", () => {
    expect(() => parseAge("двенадцать")).toThrow();
  });

  it("сообщает, что не так", () => {
    expect(() => parseAge("2.5")).toThrow("не целое число");
    expect(() => parseAge("150")).toThrow(/от 0 до 130/);
  });

  it("использует правильный тип ошибки", () => {
    expect(() => parseAge("-1")).toThrow(RangeError);
  });

  it("забывает стрелочную функцию (неправильно!)", () => {
    expect(parseAge("abc")).toThrow();
  });
});
```

</CodeExample>

- `toThrow()` проходит, если функция выбрасывает хоть что-нибудь.
- `toThrow("текст")` дополнительно проверяет, что **сообщение ошибки содержит** этот текст; `toThrow(/regex/)` сверяет сообщение с регулярным выражением.
- `toThrow(RangeError)` проверяет **тип** ошибки.

Посмотрите на последний тест. Без `() =>` вызов `parseAge("abc")` выполняется **ещё до** вызова `expect`, поэтому ошибка вырывается наружу и роняет тест. `toThrow` нужна функция, которую он вызовет сам, внутри собственного `try/catch`.

## Arrange, act, assert

Хорошие тесты короткие и состоят из одних и тех же трёх шагов. Их часто называют **arrange, act, assert** («подготовка, действие, проверка»):

1. **Arrange**: подготовьте нужные объекты и данные.
2. **Act**: выполните то единственное действие, которое тестируете.
3. **Assert**: проверьте результат через `expect`.

<CodeExample output={`✓ Cart > складывает цену, умноженную на количество
✓ Cart > изначально пуста
✓ Cart > не принимает количество 0

Tests  3 passed (3)`}>

```js
import { describe, it, expect } from "vitest";

class Cart {
  #items = [];

  add(name, price, quantity = 1) {
    if (quantity < 1) {
      throw new RangeError("количество должно быть не меньше 1");
    }
    this.#items.push({ name, price, quantity });
  }

  get total() {
    return this.#items.reduce(
      (sum, item) => sum + item.price * item.quantity,
      0,
    );
  }
}

describe("Cart", () => {
  it("складывает цену, умноженную на количество", () => {
    // Arrange (подготовка)
    const cart = new Cart();
    cart.add("чай", 4, 2);
    cart.add("пельмени", 6);
    // Act (действие)
    const total = cart.total;
    // Assert (проверка)
    expect(total).toBe(14);
  });

  it("изначально пуста", () => {
    expect(new Cart().total).toBe(0);
  });

  it("не принимает количество 0", () => {
    const cart = new Cart();
    expect(() => cart.add("чай", 4, 0)).toThrow(RangeError);
    expect(cart.total).toBe(0);
  });
});
```

</CodeExample>

Каждый тест создаёт **свою** корзину `Cart`, поэтому ни один тест не зависит от того, что сделал другой. Если тесты делят один объект, остатки одного теста могут заставить другой упасть (или пройти!) по неправильной причине. Заметьте также, что тесты пользуются только тем, что класс предлагает внешнему миру (`add` и `total`), и никогда не трогают приватное поле `#items`. Тогда внутренности `Cart` можно переписать, а тесты по-прежнему скажут, работает ли он.

## Какие случаи тестировать?

Проверить все возможные входные данные невозможно, поэтому выбирайте с умом. Хороший набор тестов покрывает:

- **Обычный случай** («счастливый путь», happy path): типичный ввод, типичный результат.
- **Граничные случаи (edge cases)**: пустые строки и массивы, `0`, один элемент, отрицательные числа, странный текст вроде лишних пробелов или заглавных букв.
- **Границы (boundaries)**: если правила меняются в 18 лет, проверьте 17 **и** 18. Ошибки на единицу (`>` вместо `>=`) прячутся именно там.
- **Ошибки**: плохой ввод должен приводить к той ошибке, которую вы обещали.

Здесь кинотеатр берёт с детей (от 5 до 17 лет) £6, со взрослых £10, а с пенсионеров (65 лет и старше) £7. Тесты на границах находят ошибку, которую «счастливый путь» пропустил бы:

<CodeExample output={`✓ ticketPrice > пускает малышей бесплатно
✓ ticketPrice > берёт с 5-летних детскую цену
✓ ticketPrice > считает 17-летних детьми
✓ ticketPrice > берёт с 18-летних взрослую цену
× ticketPrice > даёт 65-летним цену для пенсионеров
  → expected 10 to be 7 // Object.is equality

Tests  1 failed | 4 passed (5)`}>

```js
import { describe, it, expect } from "vitest";

// Дети (от 5 до 17) платят £6, взрослые £10,
// пенсионеры (65 и старше) £7. До 5 лет бесплатно.
function ticketPrice(age) {
  if (age < 5) return 0;
  if (age < 18) return 6;
  if (age > 65) return 7;
  return 10;
}

describe("ticketPrice", () => {
  it("пускает малышей бесплатно", () => {
    expect(ticketPrice(4)).toBe(0);
  });
  it("берёт с 5-летних детскую цену", () => {
    expect(ticketPrice(5)).toBe(6);
  });
  it("считает 17-летних детьми", () => {
    expect(ticketPrice(17)).toBe(6);
  });
  it("берёт с 18-летних взрослую цену", () => {
    expect(ticketPrice(18)).toBe(10);
  });
  it("даёт 65-летним цену для пенсионеров", () => {
    expect(ticketPrice(65)).toBe(7);
  });
});
```

</CodeExample>

В коде написано `age > 65`, поэтому 65-летний платит как взрослый. Тест с возрастом `70` прошёл бы и спрятал эту ошибку. Если заменить условие на `age >= 65`, все пять тестов пройдут.

<Callout type="warning" title="Тесты должны быть простыми">

Тесты должны быть настолько простыми, чтобы в них заведомо не было ошибок. Записывайте ожидаемое значение явно (`toBe(7)`), а не вычисляйте его той же логикой, что и код. Иначе ошибка в этой логике скопируется в тест, и оба согласятся на неправильном ответе.

</Callout>

```js
import { describe, it, expect } from "vitest";

// ---- Тестируемый код (не меняйте его) ----
function passwordStrength(password) {
  if (typeof password !== "string") {
    throw new TypeError("пароль должен быть строкой");
  }
  if (password.length < 8) {
    return "weak";
  }
  const hasNumber = /[0-9]/.test(password);
  const hasCapital = /[A-Z]/.test(password);
  if (hasNumber && hasCapital) {
    return "strong";
  }
  return "medium";
}

// ---- Ваши тесты ----
describe("passwordStrength", () => {
  it("считает 7 символов слабым паролем", () => {
    expect(passwordStrength("Bamboo1")).toBe("weak");
  });

  it("считает ровно 8 символов достаточной длиной", () => {
    expect(passwordStrength("bamboo12")).toBe("medium");
  });

  it("для strong нужны цифра И заглавная буква", () => {
    expect(passwordStrength("Bamboo12")).toBe("strong");
    expect(passwordStrength("Bambooooo")).toBe("medium");
    expect(passwordStrength("bamboo123")).toBe("medium");
  });

  it("выбрасывает TypeError для всего, кроме строки", () => {
    expect(() => passwordStrength(12345678)).toThrow(TypeError);
  });
});
```

## Итоги

- **Автоматические тесты** проверяют код за вас: они ловят **регрессии** и позволяют менять код уверенно.
- `describe` группирует тесты, `it` (или `test`) описывает один тест, а `expect(value).toBe(expected)` делает проверку. Тесты запускаются после кода, и в отчёте у каждого теста стоит `✓` или `×`.
- В настоящем проекте: `npm install --save-dev vitest`, тесты — в файлах `*.test.js`, запуск — `npx vitest` (режим наблюдения) или `npx vitest run` (один раз).
- При падении `expected X to be Y` означает, что вы **получили** X, а **ожидали** Y.
- `toBe` — для примитивов, `toEqual` (или `toStrictEqual`) — для объектов и массивов. Запомните популярные матчеры и `.not`.
- Ошибки проверяйте через `expect(() => fn()).toThrow(...)`: стрелочная функция здесь обязательна.
- Стройте тесты по схеме **arrange, act, assert**, по одному поведению на тест, и проверяйте обычный случай, граничные случаи, **границы** и ошибки.
