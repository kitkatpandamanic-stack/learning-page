In the last lesson, every error stopped the program. That's what you want while hunting bugs. But some errors are **expected**: a user types `"abc"` where a number should go, saved data is broken, or a server is down. In those cases you want to **handle** the error and carry on. That's the job of `try` and `catch`.

## try and catch

Put the risky code inside `try`. If anything in it throws an error, JavaScript jumps straight to `catch`:

<CodeExample output={`Could not read the settings (SyntaxError)
The program keeps going!`}>

```js
const text = "{ this is not JSON }";

try {
  const settings = JSON.parse(text);
  console.log("Loaded:", settings); // skipped
} catch (error) {
  console.log(`Could not read the settings (${error.name})`);
}

console.log("The program keeps going!");
```

</CodeExample>

- If the code in `try` runs **without** an error, the `catch` block is skipped.
- If an error happens, the rest of `try` is **skipped**, and `catch` runs instead.
- Either way, the program continues after the whole `try/catch`.

## The error object

The `catch` block receives the error as a value (we called it `error`, but any name works). Every error object has a `name` and a `message`:

<CodeExample output={`ReferenceError
missingValue is not defined
ReferenceError: missingValue is not defined`}>

```js
try {
  console.log(missingValue);
} catch (error) {
  console.log(error.name);
  console.log(error.message);
  console.log(String(error)); // both together
}
```

</CodeExample>

If you don't need the error object at all, you can leave it out: `try { ... } catch { ... }`.

## Throwing your own errors

You can create errors too, with `throw`. Like `return`, `throw` **stops** the function immediately. But instead of handing back a value, it raises an error that the caller has to deal with:

<CodeExample output={`Error: Amount must be more than 0
RangeError: Not enough money: balance is 50
Withdrew 20, 30 left`}>

```js
function withdraw(balance, amount) {
  if (amount <= 0) {
    throw new Error("Amount must be more than 0");
  }
  if (amount > balance) {
    throw new RangeError(`Not enough money: balance is ${balance}`);
  }
  return balance - amount;
}

for (const amount of [-5, 80, 20]) {
  try {
    const left = withdraw(50, amount);
    console.log(`Withdrew ${amount}, ${left} left`);
  } catch (error) {
    console.log(`${error.name}: ${error.message}`);
  }
}
```

</CodeExample>

`new Error("...")` creates a general error. You can also use the built-in types you met last lesson, like `TypeError` and `RangeError`, to say what *kind* of problem it is.

<Callout type="tip" title="Always throw an Error object">

JavaScript lets you `throw "oops"` (a plain string), but don't. A string has no `name`, no `message` and no stack trace showing where it came from. Always write `throw new Error("oops")`.

</Callout>

## Validating input

Throwing is perfect for checking input. The function refuses bad data loudly, and the caller decides what to do about it:

<CodeExample output={`12
Invalid age: "twelve" is not a number
Invalid age: 150 is not between 0 and 130`}>

```js
function parseAge(text) {
  const age = Number(text);
  if (Number.isNaN(age)) {
    throw new TypeError(`"${text}" is not a number`);
  }
  if (age < 0 || age > 130) {
    throw new RangeError(`${age} is not between 0 and 130`);
  }
  return age;
}

for (const input of ["12", "twelve", "150"]) {
  try {
    console.log(parseAge(input));
  } catch (error) {
    console.log(`Invalid age: ${error.message}`);
  }
}
```

</CodeExample>

`Number("twelve")` gives `NaN` (*Not a Number*), and `Number.isNaN` checks for it. Checking input like this is called **validation**, and it stops bad data from causing confusing bugs later on.

## finally: code that always runs

A `finally` block runs **after** `try` and `catch`, whether there was an error or not. It's the place for clean-up work, like hiding a loading spinner:

<CodeExample output={`Saving...
Saved!
Done
Saving...
Save failed: Name can't be empty
Done`}>

```js
function save(name) {
  console.log("Saving...");
  try {
    if (name === "") {
      throw new Error("Name can't be empty");
    }
    console.log("Saved!");
  } catch (error) {
    console.log(`Save failed: ${error.message}`);
  } finally {
    console.log("Done"); // runs both times
  }
}

save("Mei");
save("");
```

</CodeExample>

## Rethrowing errors you can't handle

Only catch the errors you **expect** and know how to deal with. Anything else is probably a real bug, so pass it on with `throw error`. This is called **rethrowing**. Use `instanceof` to check what kind of error you caught:

<CodeExample output={`Can't play: Level must be 10 or less
ReferenceError: levle is not defined`}>

```js
function startLevel(level) {
  if (level > 10) {
    throw new RangeError("Level must be 10 or less");
  }
  return levle * 100; // oops, a typo!
}

function play(level) {
  try {
    return startLevel(level);
  } catch (error) {
    if (error instanceof RangeError) {
      console.log(`Can't play: ${error.message}`);
      return 0;
    }
    throw error; // not ours to handle: pass it on
  }
}

play(99);
play(3);
```

</CodeExample>

`play(99)` hits the expected `RangeError` and handles it nicely. `play(3)` hits a typo. Because `play` rethrows it, the bug shows up loudly, so you can find and fix it.

<Callout type="warning" title="Don't swallow errors">

An empty `catch {}` hides every error, including your own bugs. The program then fails silently somewhere else, which is much harder to debug. If you catch an error, either handle it properly or rethrow it.

</Callout>

## Errors in async code

Some code has to **wait**: for a timer, a file or a reply from a server. You'll study this properly in Level 2, but here's a sneak peek. A **Promise** is a value that arrives *later*. Inside an `async` function, `await` pauses until the promise is ready. If the promise fails (we say it **rejects**), `await` throws the error, so a normal `try/catch` handles it:

<CodeExample output={`Loading Mei...
Mei scored 95
Finished
Loading Bob...
Failed: No player called Bob
Finished`}>

```js
// Pretend server: answers after 100 milliseconds
function fetchScore(player) {
  return new Promise((resolve, reject) => {
    setTimeout(() => {
      if (player === "Mei") {
        resolve(95);
      } else {
        reject(new Error(`No player called ${player}`));
      }
    }, 100);
  });
}

async function showScore(player) {
  try {
    console.log(`Loading ${player}...`);
    const score = await fetchScore(player);
    console.log(`${player} scored ${score}`);
  } catch (error) {
    console.log(`Failed: ${error.message}`);
  } finally {
    console.log("Finished");
  }
}

await showScore("Mei");
await showScore("Bob");
```

</CodeExample>

The last two lines use `await` outside any function. That's called **top-level await**. It works in these lessons, in the browser console and in JavaScript **modules** (which you'll meet later in this level), but not in old-style scripts.

<Callout type="danger" title="try/catch can't reach into the future">

A `try` block around `setTimeout` does **not** catch errors thrown inside the timer's callback. By the time the callback runs, the `try` block has long finished:

```js
try {
  setTimeout(() => {
    throw new Error("Too late!"); // NOT caught below
  }, 100);
} catch (error) {
  console.log("This never runs");
}
```

Put the `try/catch` **inside** the callback, or wrap the timer in a Promise and use `await` as shown above.

</Callout>

## A preview: custom error classes

Big programs often create their own error types, so they can tell their errors apart with `instanceof`. This uses **classes**, which you'll learn in the Classes & OOP module, so for now just enjoy the preview:

<CodeExample output={`ValidationError: Email must contain @
true`}>

```js
class ValidationError extends Error {
  constructor(message) {
    super(message);
    this.name = "ValidationError";
  }
}

try {
  throw new ValidationError("Email must contain @");
} catch (error) {
  console.log(`${error.name}: ${error.message}`);
  console.log(error instanceof ValidationError);
}
```

</CodeExample>

1. `parseQuantity(text)` turns the text into a number and **validates** it:

   - if it's smaller than `1` or bigger than `99`, throw a `RangeError` with the message `Quantity must be between 1 and 99`;
   - otherwise, return the number.
2. `safeQuantity(text)` calls `parseQuantity` inside `try/catch`. If it works, return the quantity. If it throws, print `Invalid: ` followed by the error's message, and return `1` as a sensible default.

<Hint>

`Number.isInteger(n)` is `false` for decimals **and** for `NaN`, so one check covers both `"lots"` and `"2.5"`. Throw with `throw new TypeError("...")`. In the `catch` block, use `` `Invalid: ${error.message}` ``.

</Hint>

<Solution>

```js
function parseQuantity(text) {
  const quantity = Number(text);
  if (!Number.isInteger(quantity)) {
    throw new TypeError("Quantity must be a whole number");
  }
  if (quantity < 1 || quantity > 99) {
    throw new RangeError("Quantity must be between 1 and 99");
  }
  return quantity;
}

function safeQuantity(text) {
  try {
    return parseQuantity(text);
  } catch (error) {
    console.log(`Invalid: ${error.message}`);
    return 1;
  }
}

console.log(safeQuantity("3"));    // 3
console.log(safeQuantity("lots")); // Invalid: ... then 1
console.log(safeQuantity("500"));  // Invalid: ... then 1
```

## Recap

- `try { ... } catch (error) { ... }` handles errors so the program can keep going.
- Every error has a `name` and a `message`.
- `throw new Error("...")` (or `TypeError`, `RangeError`…) stops a function and reports a problem; use it to validate input.
- `finally` always runs, error or not, which makes it ideal for clean-up.
- Catch only what you can handle, and rethrow everything else with `throw error`.
- With `async`/`await`, a rejected promise throws at the `await`, so wrap it in `try/catch`. A `try` around `setTimeout` can't catch errors inside the callback.
