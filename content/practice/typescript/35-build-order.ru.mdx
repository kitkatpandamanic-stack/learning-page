Инструмент сборки знает, какие задачи от каких зависят: `test` нужен `build`, а `build` нужен `install`. Напишите две функции, которые лежат в сердце такого инструмента. Задачи передаются объектом, сопоставляющим имени каждой задачи список задач, от которых она **зависит**:

```ts
const tasks = {
  install: [],
  lint: ["install"],
  build: ["install"],
  test: ["build", "lint"],
} as const;
```

- `buildOrder(tasks)` возвращает каждую задачу по одному разу, причём каждую — после всех её зависимостей. Когда готовы сразу несколько задач, берите **наименьшую по алфавиту** (сравнивайте имена через `<`). Для `tasks`: `["install", "build", "lint", "test"]`.
- `waves(tasks)` группирует задачи для параллельного запуска: в волне 0 — задачи без зависимостей, а в каждой следующей волне — задачи, все зависимости которых находятся в предыдущих волнах. Каждая волна отсортирована по алфавиту. Для `tasks`: `[["install"], ["build", "lint"], ["test"]]`.
- Если какие-то задачи никогда не смогут запуститься (они в цикле или зависят от цикла), обе функции выбрасывают `CycleError`: это `Error` с `name`, равным `"CycleError"`, массивом `stuck` с этими задачами, отсортированными по алфавиту, и сообщением `"Cycle among: a, b, c"` (застрявшие имена через `", "`).

Задача, зависящая от самой себя, — это цикл, а зависимость, указанная дважды, считается один раз.

Типы тоже важны: зависимость должна быть одним из имён задач самого объекта, поэтому `{ test: ["biuld"], build: [] }` — ошибка типов, а результат типизирован именами задач, а не как `string[]`. (Объекту задач, сохранённому в переменной, нужен `as const`, как выше, чтобы списки зависимостей сохранили литеральные имена, а не расширились до `string[]`.)

```ts
buildOrder({ a: [], b: ["a"], c: [] });    // ["a", "b", "c"]
waves({ a: [], b: ["a"], c: [] });         // [["a", "c"], ["b"]]
buildOrder({ x: ["y"], y: ["x"], z: ["x"], ok: [] });
// выбрасывает CycleError: "Cycle among: x, y, z"
```

Сделайте обе функции дженериками по именам задач и реализуйте их. Строки `Expect<Equal<…>>` и строка с `@ts-expect-error` — это тесты типов; вторая проходит, только когда в этой строке **есть** ошибка.

<Hint>

Тип: `function buildOrder<T extends string>(tasks: Record<T, readonly NoInfer<T>[]>): T[]`. `NoInfer` велит TypeScript выводить `T` только из ключей, а имена зависимостей затем **проверять** по нему, поэтому зависимость с опечаткой — ошибка. Внутри `Object.keys(tasks) as T[]` возвращает имена.

</Hint>

<Hint>

Используйте **алгоритм Кана** (Kahn's algorithm). Посчитайте для каждой задачи число различных невыполненных зависимостей (`new Set(deps).size`) и храните карту от каждой задачи к задачам, которые от неё зависят. Для `buildOrder` раз за разом берите наименьшую задачу со счётчиком 0, добавляйте её в результат и уменьшайте счётчики её зависимых. Для `waves` берите *все* задачи со счётчиком 0 сразу как одну отсортированную волну. Если готовые задачи кончились раньше, чем все задачи расставлены, оставшиеся — застрявшие.

</Hint>

<Solution>

```ts
// ===== Помощники для тестов типов: не меняйте =====
type Expect<T extends true> = T;
type Equal<A, B> =
  (<X>() => X extends A ? 1 : 2) extends
  (<X>() => X extends B ? 1 : 2) ? true : false;

class CycleError extends Error {
  readonly stuck: string[];

  constructor(stuck: string[]) {
    super("Cycle among: " + stuck.join(", "));
    this.name = "CycleError";
    this.stuck = stuck;
  }
}

const byName = (a: string, b: string) => (a < b ? -1 : a > b ? 1 : 0);

function prepare<T extends string>(tasks: Record<T, readonly T[]>) {
  const names = Object.keys(tasks) as T[];
  const waiting = new Map<T, number>();
  const dependents = new Map<T, T[]>(names.map((n) => [n, []]));
  for (const name of names) {
    const deps = new Set(tasks[name]);
    waiting.set(name, deps.size);
    for (const dep of deps) dependents.get(dep)?.push(name);
  }
  // Отмечает задачу выполненной; возвращает задачи, которые только что стали готовы
  const finish = (name: T): T[] => {
    const ready: T[] = [];
    for (const next of dependents.get(name) ?? []) {
      const left = waiting.get(next)! - 1;
      waiting.set(next, left);
      if (left === 0) ready.push(next);
    }
    return ready;
  };
  const initial = names.filter((n) => waiting.get(n) === 0);
  const stuck = (done: Set<T>) =>
    new CycleError(names.filter((n) => !done.has(n)).sort(byName));
  return { names, finish, initial, stuck };
}

function buildOrder<T extends string>(
  tasks: Record<T, readonly NoInfer<T>[]>,
): T[] {
  const { names, finish, initial, stuck } = prepare(tasks);
  const ready = [...initial];
  const order: T[] = [];
  while (ready.length > 0) {
    ready.sort(byName);
    const name = ready.shift()!;
    order.push(name);
    ready.push(...finish(name));
  }
  if (order.length < names.length) throw stuck(new Set(order));
  return order;
}

function waves<T extends string>(
  tasks: Record<T, readonly NoInfer<T>[]>,
): T[][] {
  const { names, finish, initial, stuck } = prepare(tasks);
  const result: T[][] = [];
  const done = new Set<T>();
  let wave = initial;
  while (wave.length > 0) {
    wave.sort(byName);
    result.push(wave);
    for (const name of wave) done.add(name);
    wave = wave.flatMap(finish);
  }
  if (done.size < names.length) throw stuck(done);
  return result;
}

// ===== Тесты типов: не меняйте их =====
function typeTests() {
  const order = buildOrder({
    install: [],
    build: ["install"],
    test: ["build"],
  });
  const groups = waves({ a: [], b: ["a"] });
  type cases = [
    Expect<Equal<typeof order, ("install" | "build" | "test")[]>>,
    Expect<Equal<typeof groups, ("a" | "b")[][]>>,
  ];
  // @ts-expect-error: задачи "lint" нет
  buildOrder({ build: ["lint"], test: ["build"] });
}

const tasks = {
  install: [],
  lint: ["install"],
  build: ["install"],
  test: ["build", "lint"],
} as const;
console.log(buildOrder(tasks));
console.log(waves(tasks));
```

Алгоритм Кана хранит для каждой задачи счётчик невыполненных зависимостей и освобождает задачу, когда счётчик доходит до 0; задачи, которые так и не освободились, — ровно те, что находятся в цикле или за ним. Построение графа стоит O(V + E). Сортировка списка готовых задач на каждом шаге делает `buildOrder` O(V² log V) в худшем случае (двоичная куча снизила бы это до O((V + E) log V)), но для графов сборки этого более чем достаточно; `waves` сортирует каждую волну один раз.

</Solution>
